## 一、这份规范要修掉的四个毛病

### 1.1 讲义读起来像提纲，不像技术报告

现有讲义（1.1–1.4、2.1、2.2）的语言形态是"加粗短语 + 一句解释"的重复。例如："**第二样是描述。** 这一样最容易被轻视，而它实际上是工具系统里最重要的字段（1.2 整节讲它）。"这类句式在单位篇幅里能传递信息，但它有一个副作用：读者的眼睛被加粗片段牵引，读的是一串结论，而不是一条论证。读完能复述出五六条要点，却说不出这些要点之间的推导关系——这正是"看了确实有东西，但只是了解"的直接来源。

技术报告的做法不同：它用连续的自然语言段落推进论证，句子之间是因果关系而不是并列关系，加粗只用来标出读者需要单独记住的那一两个判据。这份规范要求讲义改成后者。

### 1.2 深度停在"是什么"，没到"为什么非这样不可"

现有讲义在讲一个设计时，通常会给出现象与结论，偶尔给一条理由。而一个工程师真正需要的是：这个设计解决的具体故障是什么、它是从哪条约束推出来的、还有哪两种方案被放弃了、被放弃的方案代价落在谁身上、以及怎么用一条命令验证自己的实现确实满足它。缺了后面三项，读者拿到的是"知道"，不是"会用"。

第四节把这些要求写成六问；第二节 2.4 规定"六问中第①③⑤项齐备才算讲透"。

### 1.3 作业是练习册，不是 CS336 那种作业

现在的作业引导分散在两处：卷级 `README.md`（工作区说明）与旧的 `作业引导.md`（仅在 `homework/1.3`、`homework/1.4` 下留有存档）。两者的读者不同——一份面向"我要交什么"，一份面向"我现在该做什么、为什么这一步必要"——却被混在同一层。结果是学习者读到一个组织良好的目录说明，但在他真正卡住的那一刻，没有一个文件告诉他"卡在这里说明你误解了什么"。

CS336 的作业 PDF 有三件我们现在没有的东西：**分阶段任务与阶段检查点**、**每阶段末尾的"你应该看到什么"**、以及**明确的提交物与逐项评分口径**。第三节把它拆成 12 个固定小节。

### 1.4 各篇之间的标准漂移

七篇讲义里，有的每节末尾带"面试视角"框，有的没有；有的决策表附完整论证，有的只给选择；有的 L9 写了八条缺陷，有的三条；有的给了图，有的从头到尾没有一张图。单看每一篇都不算差，合起来却不像一套课程。这份规范第二节的固定骨架与第四节检查清单就是用来消除这种漂移的。

## 二、讲义规范

### 2.1 定位与读者

讲义的目标读者是一个已经会写代码、但**没有写过 agent harness 的工程师**。对读者的默认假设是：他读过 1.1–1.2 关于可逆性与复杂度的内容，能读懂 TypeScript 与 JSON，能自己运行 Node 脚本，但他没有见过插件容器、没有处理过流式响应、也没有为"模型可能填错参数"这类失败写过代码。

由此得到一条贯穿全文的禁令：**不许用"众所周知"、"显然"、"一般来说"来跳过推导。** 一个决定之所以能出现在讲义里，是因为它值得被推导；如果它真的显然，删除它比解释它更快。反过来，讲义也不许假设读者熟悉某个具体的库或框架——凡出现具体工具名（Triton、Firecracker、Fivetran 之类），必须当它是第一次出现来解释。

讲义不追求覆盖一个主题的全部知识，它追求的是一件更具体的事：**读完并做完作业之后，读者能从零写出这一层的实现，并且在写错时能自己发现。** 这个目标决定了两条取舍——凡不影响"写出来"与"发现写错"的背景知识一律不讲；凡影响这两者的细节一律给出可运行的验证方式。

### 2.2 语言规则

**段落是基本单位。** 每一个段落承载一次论证的推进，通常 150 至 400 字，由完整句子构成，句与句之间是因果、让步、递进或对比关系。禁止把一句话拆成多行；禁止用空行代替连接词；禁止在一个段落里并列三条互不相关的结论（那就该拆成三段，每段各自有推导）。

**加粗只用于四种场合。** 术语在首次定义时加粗一次；一条必须能被单独记住的判据加粗；结论句中真正承重的短语加粗；以及需要与上下文明确区分开的反直觉点。除此之外不加粗。一份讲义的加粗字数占比应低于全文的百分之五，同一段落内不超过两处。判断标准是：如果去掉加粗，句子结构是否仍然成立——如果不成立，说明加粗在代替句子成分，必须改写。

**禁止以下写法。** 第一是用加粗句首词伪造列表（"**第一，**……**第二，**……"），它把并列关系伪装成论证顺序；并列关系就该写成一张表或一段并列句。第二是滥用心智标记符号：星号只留给真正的反直觉点，每节至多一处。第三是口语化的第二人称引导（"你会发现"、"让我们看看"、"接下来我们要"）——技术报告不使用课堂引导语，需要建立先行组织者时用一段完整的引言，而不是一句口令。第四是用"首先、其次、最后"机械串联全文；真正的顺序应当由内容决定，并且能在句子里被解释（"先定这个，因为后面两项都依赖它"）。

**鼓励以下写法。** 因果链要写完整："因为模型只能生成 token，所以一段结构只能以字符串形式传来；而这意味着解析必须发生在边界处——一旦错过那一刻，原始文本就不再完整。"让步要给得具体："这一点看上去与上一条矛盾，区别在于前者约束的是调用方，后者约束的是实现方。"反例要指名道姓："如果这里只保留头部，那么一个命令的失败输出会把结论丢掉——而结论恰恰在最后几行。"

**术语与中英混排。** 术语首次出现时给出中文名与英文原名，之后统一用其中一个（全文一致，不来回切换）。代码、标识符、命令、文件路径、以及业界通用缩写（token、JSON Schema、append-only）保持原文。不造新词：如果找不到合适的中文，就用英文并解释它。

### 2.3 固定骨架与各节职责

每一篇讲义由下列部分组成，顺序固定。**每节的存在理由都写在这里；写的时候如果发现某一节没有内容可写，先怀疑自己对这一篇的理解不够，而不是删掉这一节。**

**元信息表**（篇号、主题、目标级别、解决的清单条目、参考来源、预计阅读与动手时长、产出物、配套作业链接）。参考来源必须是可核实的原始材料——教材、论文、官方规范、以及本仓库的具体文件；不接受"某篇博客说"。

**本篇新词**。这一篇会反复用到、且读者可能第一次见到的术语，每个术语用一段话解释，包含它在本文里的准确含义与最容易被误解成什么。写完后自问：如果读者读完这节仍然把术语用错，最可能错在哪。

**第 0 节 · 学完你能做出什么**。读者导向的开场，必须回答"我学完能做出什么、我能因此多做哪一类判断"、给出先行组织者结构图、并且提供一个十分钟内可完成的体感练习（打印某段代码只看声明、或者只跑一条命令看它会失败的方式）。这一节的写法是"先给终局，再给路径"。

**第 0.5 节 · 系统视角**。这一篇在整个系统里所处的位置、它的产物被谁消费（下游依赖表，逐行标注消费方式与强度）、以及三个以上的连锁影响——每一条都要指出"这个决定会在几步之后以什么形式回来"。连锁影响不能写成"很重要"，必须写成可追踪的路径：某个字段的形状会成为某类数据的格式，某个错误分类的正确性会在第几步被检验。

**L0 · 要解决的问题**。用现象开场，每个现象都必须是可复现的具体故障（谁在什么情况下做了什么、然后发生了什么、后果是什么），而不是抽象的能力缺失。L0 的最后一节把现象收拢成"这一篇要正面回答的几个问题"，并与后面各节一一对应。

**L1 · 设计与原理**。这是全文最长的部分。每个设计决定都要给出第一性原理的推导（它由哪条约束逼出来）与至少一个替代方案（如果选它会发生什么）。凡涉及"为什么不做 X"，都要把 X 的支持理由写出来再反驳，不做稻草人。

**L2 · 决策表**。表格列为：编号、决策、我们的选择、替代方案、代价落在谁身上。表后挑选两条以上展开完整论证（挑那些替代方案真正有诱惑力的），论证必须包含"如果选另一个会怎么坏"的具体运行过程。

**L3 · 实现（施工图）**。文件结构（分段与每段的职责）、关键类型定义、关键函数实现、验收判据（表格，逐条给检查方式）、实现顺序（按能独立验证的步骤切分）。判据要能被自动检查的比例越高越好；不能被自动检查的必须写清人工检查的观察点。

**L4 · 运行与验证**。验证分三层：自检（契约测试）、外部否定（换一个实现或写一个新扩展看行为是否不变）、真实运行（端到端一次）。给出可直接复制的命令，并说明每一步"如果失败，最可能的原因是什么"。这一节的核心要求是**用外部工具否定程序自己的报告**——不能让程序自证正确。

**L5 · 语法速查**。术语表（准确含义与易误解为）、命令速查、三条容易踩的规则。这一节的定位是"事后查阅"，因此条目要短、要可搜索，不承担推导任务。

**L6 · 重建判据**。分级的判定标准（读懂、改动、重建、设计、评审五级），以及"必须能独立做到的"与"应该能做到的"两张表。

**L7 · 挑战题**。不少于六道，不给答案，每道都必须是开放设计题而不是知识复述题，并且至少一道要求反驳本篇的某个决定。

**L8 · 自检清单**。理解层、应用层、判断层三层，每层三到四条，每条都写成可验证的动作（"能说出"、"实现过"、"用某条命令确认过"）。

**L9 · 仍未解决**。不少于五条已知缺陷，表格列为：缺陷、后果、修法、以及**当初为什么这么写**（最后一列最重要，它让读者看到取舍而不仅是错误）。其中至少两条要分别属于"位置放错"与"前提会变"两类。

**L10 · 提问训练**。五个层次的示例问题、五种提问模板、本篇引出的十二个问题（按读懂、重建、设计、评审分层）、以及一次"模糊问题升级为精确问题"的演示，演示后必须写出提升点说明。

**L11 · 系统影响回溯**。逐条对账第 0.5 节的连锁影响：哪些兑现了、以什么形式兑现、哪一处的预判需要修正。最后写出通向下一个篇目的桥：这一篇留下了哪几个没有答案的问题，下一篇如何接管。

**记忆锚点与复述练习**。骨架（四块或更少，含一行总记）、情境绑定（不少于十条"当你……就想起……"）、主动回忆（十二道闭卷题）、间隔重复计划（当天、第 2 天、第 7 天、第 30 天各做什么）、复述练习（用五分钟讲给不写代码的人听，三道题）。

**全篇知识结构图**。一张大图把全篇串起来，图后给出一句"关键线索"，说明从哪一格到哪一格的顺序是有讲究的，以及"如果只能记一个，记哪个"。

### 2.4 深度标准：讲透一个决定必须回答的六问

任何被当作"设计决定"写进 L1 或 L2 的内容，都必须回答下列六问。其中第①③⑤项齐备，才算讲透；只答了其一其二的，属于"要点"，应当补写或降级为术语解释。

1. **它解决的具体故障是什么**——给出可复现的现象，最好带数量级（"一次成功的文件读取可以把请求撑爆十倍"），不带数量级的现象陈述通常说明作者自己没算过。
2. **它由哪条约束推出来**——第一性原理。约束可能是物理的（模型只能生成 token）、协议的（HTTP 状态码语义）、或者是经济学上的（命中价约为未命中的三十分之一）。凡不能追溯到约束的设计，多半是习惯。
3. **被放弃的替代方案是什么，代价落在谁身上**——至少给出两个替代方案，并说明它们的代价由谁承担。只谈收益不谈代价的设计描述没有决策价值。
4. **这个代价什么时候暴露**——立即、几篇之后、还是上线之后。凡是"几篇之后/上线之后"暴露的代价，都要在这一篇里显式标注时间差，因为它是读者日后回查的线索。
5. **怎么验证自己真的做到了**——一条命令、一个测试、或一个外部观察方法。无法验证的结论在这一篇里只能作为待验证的假设出现，必须标注。
6. **它什么时候会失效**——边界条件与前提变化。前提会变的设计要写成"它的正确性依赖一个当前成立、将来可能不成立的前提"，并指出那个前提是什么。

### 2.4.1 技术内容下限

六问解决的是"想清楚"，而一份讲义要真的达到"技术报告"这个密度，还必须包含下列硬材料。这不是风格偏好，它们是"知道"与"能用"的实际分界：一个读者如果只知道结论，他在面对真实代码时仍然不知道从哪一行开始改。

**规范与原始材料的引用。** 每一篇至少引用一处可核实的规范或原始材料，并且引用到条款级：SemVer 的具体规则（主版本何时升、预发布标识怎么比较）、HTTP 的 `Retry-After` 语义（秒数还是 HTTP 日期）、Meyer 在 Eiffel 里的三个关键字（`require` / `ensure` / `invariant`）、Hyrum 定律在《Software Engineering at Google》里的原始表述。凡是转述某个原则，必须给出它能被追溯的出处；找不到出处的按"经验"标注，并说明置信度下降。

**真实代码的逐行引用。** 每一篇至少三处引用本仓库或 `D:\dsh-mini` 的真实代码（文件、符号、关键行），并解释那一行为什么必须写成这样、改成相邻的另一种写法会发生什么。引用代码时不允许只贴一段然后说"看这段代码"，必须指出难点行。

**数量级。** 每一篇至少两处给出可计算的数量级：token 数、字节数、调用次数、毫秒数、比例。数量级的作用是让判断可校验——说"大输出会撑爆上下文"没有用，说"一个 5 MB 的文本约 125 万 token，而窗口是 128K 量级"才能让读者自己算。

**可复现的最小反例。** 每一篇至少一个能贴进终端跑起来的最小反例（五到二十行），用来演示"写错了会怎样"。反例比正面规范更有效，因为它把判定标准交给了读者。

**失败模式的分类学。** 讲"会坏"时必须给出坏的几种具体方式：是静默给出错误结果、是在异常通道里丢失、是在并发下偶发、还是在某个边界值上才出现。分类之后要说明每一类的观察方式不同——这一点直接决定读者日后怎么调试。

**数据结构层面的结论。** 每一篇都要落到字段、类型、不变量、复杂度这些可以写进代码的东西上。只说"要注意时序"是无效的，说"这个消息表中 `seq` 必须严格递增，`append` 是唯一的写入点，因此 `seq` 可以在读取时由下标推出"才是可执行的结论。

### 2.4.2 篇幅分配与引导语禁令

**篇幅按职责分配**：元信息表、本篇新词、第 0 节、第 0.5 节合计不超过全篇的百分之二十；L1 设计与原理与 L3 施工图合计，判断力型篇目不低于百分之四十二，实现型篇目不低于百分之三十五；两类都不低于导论段的二倍。之所以要卡这条线，是因为导论性内容写起来最省力、读起来最有"学到东西"的错觉，而它承载的判据最少。一条经验判断是：如果一篇文档被删掉前四节之后读者说不出自己少了什么，那前四节就写多了。

门槛的数字是从实测校准的，且经过三次修正。第一版取 45%（从 1.4 一篇推出），第二版降到 40% 并加比例约束，第三版改为分档。分档的依据是十六篇的实测分布：第 1 卷（判断力型）的 L1 与 L3 合计为 44%–54%，第 2、3 卷（实现型）为 35%–40%。两类篇目的结构不同——判断力型篇目的 L1 是原理主体，而实现型篇目的 L0（现象）与 L5–L11（速查、判据、挑战题、自检、缺陷、提问、回溯）占比天然更高，L3 又承载施工图。**这条修正记录本身也是一个例子：门槛应当由实测分布决定，而不是由一篇的数值推出。**

**禁止课堂引导语。** 技术报告不使用"你会获得"、"你会得到"、"这一篇要给你的是"、"让我们"、"接下来我们"这类句子。需要建立先行组织者时，直接陈述这一篇建立的判据是什么，或者直接进入技术内容。凡是"你会 X"的句子，通常都能改写成"这一篇建立的判据是 X"，而后者同时给出了内容与用途。

### 2.5 图与代码块的使用规则

**只在关系无法用一句话说清时使用图。** 合法的图有三类：结构图（分层与归属）、关系图（谁依赖谁、谁影响谁、谁在什么时候被调用）、时序或状态图（步骤顺序与状态迁移）。不合法的图也有三类：把要点排成方框的假图、用箭头装饰的一句话、以及为了版面好看而存在的表格式插图。

每张图后面必须跟一句"这张图的关键线索"，说明图的读法。全篇图的数量通常在两张到四张之间；数量超过五张通常说明文字没有承担它该承担的说明责任。

**代码块只放三类内容**：必须逐行理解的接口或类型定义、能直接复制运行的命令、以及错误写法与正确写法的对照。禁止把大段实现粘进讲义充当解释——讲义里的实现必须配一段说明"这段代码里哪一行是难点"。所有代码块必须能通过语法检查，示例中的数据必须是真实的（不要用 `foo`、`bar` 这类占位符）。

### 2.6 记忆设计

讲义不是一次读完就丢的材料，因此它必须为长期记忆设计。以下是硬性要求，不是建议。

记忆锚点给的是骨架而不是摘要：四块以内、可以默画出来的结构、以及一行总记。情境绑定把知识与触发场景绑定，写法是"当你……就想起……"，条目必须来自真实工作场景而不是本章小标题的改写。主动回忆的十二道题必须闭卷可答，且不得在题干里泄露答案的组织方式。

间隔重复计划要给到第 30 天，并说明每次复访的动作不同（当天是默画骨架，第 2 天是把方法用到一个真实对象上，第 7 天是拿规则去解决实际问题，第 30 天是对比当初的判断差异）。复述练习的目标是"讲给不写代码的人听"，因此要求用不带行话的五分钟口述完成三件事。

生成效应的落实方式是：讲义不直接给答案，而是给出"去哪里找"与"什么情况下应当警惕"。最典型的形态是"三类证据都没有就不算承诺"这种判据，它让读者必须自己去对象上验证。

### 2.7 批判性与第一性原理

每一篇至少要有三处显式的自我批判，且批判的形式要多样：L9 的缺陷表是"承认现有产物的问题"，L2 的完整论证是"承认替代方案的合理性"，L11 的回溯是"承认开篇预判的错误"。三处缺一处，这一篇就有自我吹捧的嫌疑。

第一性原理的写法有一条硬要求：**推导要从约束出发，而不是从惯例出发**。写"业界通常这么做"是反例；写"因为模型没有记忆，所以每轮必须重新传上下文；而这意味着'传什么、按什么顺序、传多少'是一等一的设计问题"是正例。

反例要具体到可复现：不说"这样会导致难以维护"，而说"这样会导致第 9 步的重试无差别地重试限流与服务错误，而这两者的正确应对相反"。

### 2.8 面试接口

课程以面试为其中一个重要导引，因此每篇的关键节点给出面试视角框，写法固定为三行：高频问法、追问方向（含一两句可直接使用的回答）、以及对应岗位。框的出现位置不固定，密度上限按篇幅计——每 4000 字符正文至多一处，且同一节内不超过一处。这条密度是用 1.4 的实测结果校准的：它 57 KB 的篇幅配 13 处，恰好平均每节一处，而原先"一篇至多六处"的绝对上限与本篇的实际需要不符，属于标准本身的缺陷。框必须挂在真正会被问到的技术点上，不能为了凑数挂在术语解释上；低于这个上限是正常的，不要为凑数而加。

附录材料（面试题库、问题清单、能力要求）遵守独立的证据等级体系：【规范】（RFC、W3C、官方规范）、【官方文档】（厂商文档、官方博客）、【书籍】（有作者与版次的出版物）、【经验】（工程共识、可复现的实践观察）、【不确定】（无法核实）、【推算】（由已知量推导）。在正文中指出出处的同时标注等级；找不到出处的必须写"我找不到可靠出处"，并说明因此降低了哪一条结论的置信度。这条要求是这门课相对于公开课程的一项独占优势，不得为了版面整洁而省略。

## 三、作业规范

### 3.1 目录布局与职责

讲义、作业引导、作业环境、判分器、参考答案分属四个位置，各自的读者与修改权限不同：

```
D:\dsh-course\
├── 02-最小闭环\
│   └── 2.2-工具系统.md          ← 讲义（课程作者维护，学习者只读）
└── homework\
    └── ch02-loop\               ← 一个"章"一个工作区（与 CS336 相同）
        ├── 作业引导.md           ← 独立文件，唯一的"我现在该做什么"入口
        ├── README.md            ← 工作区索引：目录结构、判分怎么跑、进度表
        ├── kit\                 ← 学习者的工作区（唯一可改的地方）
        │   ├── CONTRACT-*.md    契约（依据，不许改）
        │   ├── src\             实现骨架（要改）
        │   ├── problems\        题面与作答模板（只读）
        │   ├── answers\         作答（要填）
        │   └── writeup.md       报告模板（要填）
        ├── tests\               ← 判分器（不许改）
        └── grade\               ← 参考答案与解析（做完再看）
```

**为什么作业引导与 README 分成两份**：README 回答"这个工作区里有什么、怎么跑判分"，作业引导回答"我为什么要做这一步、现在该做什么、卡在这里说明什么"。二者的更新频率也不同——README 随工作区结构变，作业引导随教学意图变。混在一起的结果是两者都写不好，而现在的 `ch01-judgment/README.md` 正是这个混写的样本。

**作业环境（kit）与判分器（tests）为什么必须是两个文件夹**：判分器不许被改，是评分可信的前提；而作业环境必须被改，是学习发生的前提。把它们放在同一个目录下会诱发"顺手改一下判分器让它过"的行为，而这类行为一旦发生，整个作业的价值就归零了。参考答案也遵守同样的隔离：它在 `grade\`，允许看，但引导文档必须在恰当的位置写明"不建议现在看，理由是……"。

### 3.2 作业引导文档的固定结构

作业引导是一份独立文档，篇幅通常在 400 到 900 行之间，由下列十二节组成。它的目标是 CS336 作业 PDF 的那一级：读者读完它就应该知道每一步该做什么、做完之后该看到什么、以及失败时该怀疑哪里。

**第一节 · 封面表**。所属讲义与篇节、你将造出的东西、前置作业、预计用时（读与做分开）、提交物清单、判分口径、以及"你需要什么环境"。

**第二节 · 为什么有这份作业**。说明它训练的能力，以及这个能力在讲义哪几节被讲过、在面试与实际工作中以什么形式出现。这一节要正面回答"我能不能跳过它"——如果确实可以跳过（例如前面几篇的作业已经覆盖），就应当说出来。

**第三节 · 你将造出什么**。用一段话与一张可观察的成功判据表描述产物。判据必须是客观的：能跑起来、能通过哪一组测试、在多少并发下不变量仍成立。

**第四节 · 环境与布局**。给出目录树，逐个说明每个文件夹的作用与修改权限，指出判分器与参考答案的位置，并解释为什么它们不许改。同时给出环境检查命令（一条命令确认 Node 版本、依赖、以及判分器能被找到）。

**第五节 · 分阶段任务**。作业拆成三到六个阶段，每个阶段包含：目标（一句话）、你要做的动作（可执行）、检查点（"你应该看到什么"——具体的输出或现象）、卡住时的提问（三个以内，指向讲义的具体小节）、完成判据。**阶段之间必须有依赖**：后一阶段的检查点会用到前一阶段的产物，这样"敷衍通过"会在下一步暴露，而不是在很久以后。

**第六节 · 提交物与格式**。代码与报告并列，说明报告的节标题与每节要回答的问题。报告不是总结，而是指出"你在实现时发现哪几处最容易误读，以及你是怎么判断的"。

**第七节 · 评分**。逐项给分（不是"这道题 10 分"），说明如何重跑、部分完成如何计分、以及哪些项是硬性门槛（例如不变量被破坏则整项不计分）。

**第八节 · 鲁棒性与压力测试**。给出需要重复运行的次数、故障注入清单（延迟、乱序、丢包、中断、进程被杀）、以及为什么"跑一次通过"不算通过。凡是涉及并发、持久化、取消的作业，这一节必须存在。

**第九节 · 常见坑（故意留的）**。三到五条，每条写清"你会怎么想错"、"为什么会这么想"、以及"正确的方法是什么"。这一节是引导性的集中体现，不写"注意不能这样做"，而要写清错误思路的吸引力在哪。

**第十节 · 荣誉守则**。沿用 CS336 的边界：允许用 LLM 问概念与低级编程问题，禁止让它直接解题；建议关闭自动补全；允许讨论，但提交的实现必须自己写。

**第十一节 · 时间预算与检查点节奏**。给出建议的分次安排（例如分三次做，中间隔一天），并与记忆设计挂钩：第 2 天做哪个阶段、第 7 天回访哪一节的判据。

**第十二节 · 附录**。环境故障排查、判分器输出的读法、以及"如果你只有三小时该怎么办"的最小路径。

### 3.3 引导性的写法：每个关键节点写三件事

引导不等于鼓励，也不等于把答案拆碎。它指的是：在读者最可能卡住的节点，写清三件事。

**必要性**：不做这一步会在后面哪一步以什么形式暴露。写法是给出具体的故障或判分失败，而不是"这很重要"。例如"如果你跳过参数校验直接调用实现，那么当模型给出一个多余的字段时，失败会在工具内部以 `undefined` 的形式出现，而那时你已经丢失了'模型填错了参数'这个判断"。

**我是怎么想到的**：给出一条可复用的推理起点，而不是"经验告诉我"。可复用的起点通常是一个提问（"这个操作撤销时需要外部世界变回去吗"）、一条约束（"模型的输出是外部输入，而外部输入的校验必须在边界处"）、或者一个反事实（"如果不是这样设计，那么第 9 步会拿到什么样的错误对象"）。读者带走的应该是这个提问方式。

**如果你现在想做 X，说明你可能误解了 Y**：把错误思路的吸引力写出来，并指出它对应的误解。这一条比正面讲解更能防止弯路，因为它针对的是读者当下真实的冲动。

### 3.4 作业形态：构建型、递进、可否定

判断力地基（第 1 卷）的作业可以是分析型，因为那一卷训练的就是在动手之前做判断。从第 2 卷起，作业必须是构建型：产出物是一个能运行、能通过测试的东西，而不是一份分析报告。

构建型作业遵守三条约束。第一，**判分器判行为而不判答案**：它 import 学习者的实现并调用它，检查返回的对象、抛出的错误、以及不变量是否成立；客观题只用于概念确认，不作为主要得分项。第二，**递进依赖**：本章后续作业依赖前面的正确性，跨章也尽量保留这条依赖（例如 2.2 的构建题明确依赖 2.1 的 `parseArguments`）。第三，**必须能被否证**：每一份构建题作业都配一个负向验证脚本，从参考答案出发制造几个"看起来合理但违反契约"的变体，确认判分器能把它们全部抓住。一个只能给参考答案满分的判分器没有价值，这条在当前工作区已经落地（`grade/negative-check*.mjs`，均为 4/4）。

### 3.5 心理学依据与落实方式

**认知负荷理论**区分三种负荷：任务本身的难度、呈现方式带来的难度、以及用于构建理解的难度。作业只保留第三种。因此凡是"数文件、找路径、抄样板"这类工作，一律预置为工具或模板（`kit/tools/`、`problems/` 下的作答模板）；而"判断哪些依赖是必要的"这类工作必须留给学习者。

**最近发展区与脚手架**要求提示随进度递减，并且这种递减要可量化：1.1 的作答模板包含十余处提示，到 1.5 只剩三处；同一个工作区里，前一阶段的"卡住时的提问"比后一阶段具体。脚手架的拆除必须在引导文档里说明，否则学习者会把"提示变少"理解为"文档写得差"。

**生成效应**要求作业不提供结论。判分器可以给出对错，但引导文档不能给出答案的推导过程——它只能指出"去哪里找"和"什么情况下应当警惕"。

**测试效应**要求以判分代替自评。判分器的输出必须能让学习者判断"我错在哪一类"，而不只是"我错了"。

**间隔重复**要求把五次作答安排在不同日子，并在引导文档里给出第 2 天、第 7 天、第 30 天的具体回访动作。

**避免习得性无助**要求起点分数低但可解释：空模板得零分不是因为设计缺陷，而是因为还没有作答，这一点必须在引导文档里说明；同时每次失败都要给出"差在哪一类"，不允许只给一个总分。

## 四、可核对检查清单

下列条目用于任何一篇文档完成后的自检。**不能机械核对的条目允许人工判断，但必须写出判断依据。**

### 4.1 讲义

- [ ] 每个被当作设计决定的内容，六问全部齐备（不再是"三分之二"）
- [ ] 技术内容下限六项齐备：条款级引用、三处真实代码、两处数量级、一个可复现最小反例、失败模式分类学、数据结构层面的结论
- [ ] 导论性四节合计不超过全篇 20%；L1 + L3 判断力型 ≥42%、实现型 ≥35%，且不低于导论段的 2 倍
- [ ] 不存在"你会获得/你会得到/让我们/接下来我们"这类课堂引导语
- [ ] 加粗字数占比低于 5%；同一段内加粗不超过两处
- [ ] 不存在"**第一，**……**第二，**"式伪列表（决策表、术语表、速查表除外）
- [ ] 每节至少给出一条可复制的命令或一个可观察的判据
- [ ] 图不超过四张，每张图后有一句关键线索；没有装饰性插图
- [ ] 代码块都能通过语法检查，无 `foo`/`bar` 占位符
- [ ] L9 的缺陷不少于五条，且含"位置放错"与"前提会变"各至少一条
- [ ] L2 有至少两条完整论证，每条都描述了"选替代方案会怎么坏"的具体过程
- [ ] L11 逐条对账了 0.5 的连锁影响，并至少修正一处开篇预判
- [ ] 记忆锚点五件齐备（骨架、情境绑定、十二题主动回忆、间隔重复、复述）
- [ ] 面试视角框密度不超过每 4000 字符一处，且同一节内不超过一处
- [ ] 术语首次出现时给出中英对照，之后全文一致
- [ ] 全篇没有"众所周知""显然""一般来说"这类跳过推导的表述

### 4.2 作业引导

- [ ] 引导文档是独立文件，与工作区 README 分开
- [ ] 十二节齐备；分阶段任务每阶段都有检查点与完成判据
- [ ] 每阶段的"卡住时的提问"指向讲义的具体小节号
- [ ] 阶段之间存在依赖（后一阶段用到前一阶段的产物）
- [ ] 构建型作业的判分器 import 实现并检查行为；负向验证脚本存在且全部变体被抓住
- [ ] 存在至少一件"只靠读文档无法完成"的动作（真实运行、压测、故障注入）
- [ ] 报告模板存在，且报告要求是"指出易误读处"而不是"总结"
- [ ] 荣誉守则、时间预算、附录（含最小路径）齐备

## 六、迁移计划

既有材料按下面的顺序改造。**顺序不能颠倒**，因为语言风格与目录结构一旦定了，后面的工作才有基准。

**第一，示范篇。** 选 1.4（接口与契约）作为语言风格的样板：按第二节重写全文，按第三节把它的作业引导从 `ch01-judgment/README.md` 里拆成独立文件。示范完成后暂停，由你判断风格是否达到预期；达不到就改规范，而不是改这一篇。

**第二，第 1 卷其余篇目。** 1.1、1.2、1.3 按同一标准重写，并把第 1 卷的作业目录改成 `作业引导.md + README.md + kit + tests + grade` 的形态。这一批同时要补齐各处漂移：面试视角框、L9 的缺陷条数、图的取舍、间隔重复计划。

**第三，第 2 卷已完成的两篇。** 2.1 与 2.2 的结构已经符合规范，缺的是语言层（加粗密度、段落化、伪列表）与作业引导的独立化。这一批只改语言与目录，不动技术内容，改动量可控。

**第四，第 2 卷剩余篇目。** 2.3 到 2.7 直接按新规范撰写，不再产生返工。

**第五，附录材料。** 面试题库、问题清单、体系设计、习题总纲按证据等级与框架对齐；这一批的前置条件是面试内容的核实与去幻觉已经完成（`面试题库-v2.md` 是当前的基线）。

**关于"效仿 CS336"的边界**：作业引导要学到它的分阶段、检查点、逐项评分、荣誉守则与环境隔离；但 CS336 的作业是"从零造一个语言模型"，它的难度来自实现量。本课程的难度来自**判断密度**——每一个作业都要求学习者在若干条都说得通的做法中选一条并说清代价。因此作业引导里不能出现"照着这个公式实现即可"的段落，那样会把判断训练退化为抄写。

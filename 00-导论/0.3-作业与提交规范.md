## 读完这一篇你会知道什么

1. **作业形态**：六个阶段，同一个 harness 逐卷加能力，不是六个独立项目。
2. 每次的交付物：代码、可跑的验证、以及一份决策记录。
3. "边界只增不改"：新阶段不推翻旧阶段已通过的验收。
4. 判分依据：功能、可靠性、成本、可观测、可扩展、安全六维（见 0.2）。
5. 自检清单：提交前十项，全部要给出你跑出来的结果。
6. 常见错误：为什么"能跑"不等于"通过"。

## 一、作业的形态

**主干是一个 harness，作业是给它的六次增量。**

| 特征 | 说明 |
|---|---|
| **同一个系统** | 六个阶段都在同一个代码库上做 |
| **逐卷加能力** | 每个阶段对应课程某个卷的主题 |
| **边界只增不改** | 旧阶段的验收必须继续通过 |
| **每次留档** | 每次交付带一份决策记录 |

为什么这样设计：**真实项目就是这样演进的**——你不会在第二个季度重写第一个季度的代码。所以作业要训练的是"在已有系统上正确地加东西"，而不是"从零写一个新东西"。

## 二、六个阶段与交付物

| 阶段 | 加什么能力 | 对应卷 |
|---|---|---|
| **S1 最小闭环** | 模型调用、工具执行、会话日志 | 02 |
| **S2 可靠性** | 重试、守卫、上下文压缩、进程与持久化 | 03 |
| **S3 可观测** | 四段延迟分解、成本三档、护栏指标 | 03 |
| **S4 学习进化** | 记忆、技能、诊断闭环 | 04 |
| **S5 规模化** | 预设、并发调度、审批交互 | 05 |
| **S6 评测与出口** | 任务集、验收脚本、研究问题转化 | 06 |

依赖关系：**S1 是地基，S2/S3 依赖它，S4 依赖 S3（没有可观测就无法诊断），S5/S6 在最后。**

## 三、怎么做

### 3.1 交付物清单

每次交付三样东西：

| 交付物 | 内容 | 为什么 |
|---|---|---|
| **代码** | 可运行的系统 | 终点是产物（见 0.2） |
| **验证** | 可跑的检查脚本 + 你跑出的结果 | 证明它工作 |
| **决策记录** | 关键参数与依据 | 证明你掌握它 |

"决策记录"是最容易被跳过、也最能区分等级的一项：**它要求你写出"为什么是这个值"**（见 0.2 的 L3 判据）。

决策记录的最小内容：

```
参数：单命令超时 = 30 秒
依据：交互场景，用户等待超过 30 秒会认为系统挂了（见 3.4 的参数表）
反推：最大步数 20 × 30 秒 = 10 分钟，与回合总预算一致
替代方案：60 秒 —— 否决，因为交互体验不可接受
```

注意最后一行：**记录被否决的方案**（这与 1.1 的 ADR 是同一个要求）。没有它，决策记录只是参数说明。

### 3.2 边界只增不改

**新阶段不得让旧阶段的验收失败。**

| 做法 | 后果 |
|---|---|
| 加能力时顺带重构 | 允许，但旧验收必须继续通过 |
| 为了新能力改旧接口 | 需要说明为什么，并更新调用方 |
| 推翻旧设计 | 需要写出理由与影响面 |

为什么这条是硬约束：**真实系统的维护成本主要来自"改一处坏三年"**（见 1.2 的债务利息）。"只增不改"训练的是对已有边界的尊重。

执行方式：**把每个阶段的验收脚本保留下来，每次提交前全部跑一遍。** 这就是"回归测试"的最小形式。

### 3.3 判分依据

判分按 0.2 的**六维验收**：

| 维度 | 看什么 |
|---|---|
| **功能** | 任务成功率与区间 |
| **可靠性** | 故障注入后的完成率 |
| **成本** | 每任务成本与缓存命中率 |
| **可观测** | 四段分解可用、残余小于 10% |
| **可扩展** | 新增能力改了几处 |
| **安全** | 注入与越权用例的拦截率 |

**六项都要给出数字**。"做得不错"不是判据——与 4.7 的"约束必须可检查"一致。

### 3.4 特殊情况与处理技巧

| 情况 | 为什么 | 处理 |
|---|---|---|
| 上一阶段的验收坏了 | 改动影响了旧边界 | 先修回归，再加新能力 |
| 某个维度无法测量 | 缺可观测 | 先补测量（这本身就是作业内容） |
| 参数只能照抄默认值 | 没有反推 | 用对应篇目的公式从你的场景反推 |
| 安全用例过不了 | 守卫只挡一条路径 | 见 3.2 的绕过清单 |
| 任务集太小 | 区间过宽 | 加大样本或分层报告（见 6.3） |
| 新能力让成本翻倍 | 上下文或派发开销 | 查缓存命中率与派发划算判据（见 5.4） |
| 只有一个阶段做完 | 时间不够 | 优先 S1 + S2 + S3，它们决定系统是否可用 |
| 系统能跑但说不清为什么 | 决策记录缺失 | 补写，这比补代码更值得 |

最后一条值得强调：**决策记录是判分的一部分**，补写它比补功能更能提升等级。

### 3.5 判分的原理

判分标准为什么是这六维而不是"功能 + 代码质量"？三个理由：

| 理由 | 说明 |
|---|---|
| **六维对应真实约束** | 一个能跑但贵十倍的系统没有价值 |
| **可测量才可判分** | 每一项都有数字（见 0.2 的 3.1） |
| **硬约束与权衡分开** | 安全是一票否决，其余是权衡 |

"硬约束与权衡分开"这一条来自 6.3：**安全违规不能与其他维度加权平均**——否则一个高分系统可以"买"到几次危险操作。

这也是这门课在评测上的一贯立场：**能用代码判定的就不用人工判定，能一票否决的就不做加权**（见 4.7）。

### 3.6 提交前自检清单

| # | 检查项 | 你的结果 |
|---|---|---|
| 1 | 全部代码能一条命令启动 | |
| 2 | 本阶段与之前所有阶段的验收脚本全部通过 | |
| 3 | 六维验收各有数字 | |
| 4 | 故障注入覆盖三类（限流、超时、进程被杀） | |
| 5 | 安全用例（注入 + 越权）全部被拦 | |
| 6 | 四段延迟分解可用，残余小于 10% | |
| 7 | 缓存命中率有记录 | |
| 8 | 每个关键参数都能说出依据 | |
| 9 | 决策记录含被否决的方案 | |
| 10 | 状态可续作（见 4.7 的六字段） | |

第 10 项经常被漏：**如果别人（或明天的你）无法接手，这个交付就是不可维护的。**

### 3.7 工程化与实战建议

**把作业当成真实项目做**，几条实战建议：

| 建议 | 理由 |
|---|---|
| 每个阶段结束时打一个标记 | 回归时能定位是哪一阶段引入的 |
| 验收脚本与代码同仓 | 分开存放会让它过期 |
| 参数写进配置文件 | 便于在不同场景重算（见 5.1） |
| 决策记录与代码一起提交 | 分开写会忘 |
| 每个阶段做一次故障注入 | 可靠性无法靠正常路径证明 |
| 保留每次的验收结果 | 用于对比这次比上次好在哪 |
| 成本从第一天就记账 | 事后补账通常补不全（见 3.6） |
| 做不完就砍范围 | 半个可用系统强过五个半成品 |

**"成本从第一天就记账"值得强调**：成本数据的历史无法追溯重建——如果前三个月没记，那三个月的成本结构就永久缺失了（这与 3.6 的"分段之和必须对得上总量"是同一个要求）。

**这一篇只要记住一句**：作业是给同一个 harness 的六次增量，每次交三样东西——代码、可跑的验证、以及能说出依据的决策记录。而"边界只增不改"与"六维都要有数字"是判分的底线。

## 四、涉及的能力与算例

本规范涉及的判据都来自课程正文，配套算例可自行运行验证：

```powershell
cd D:\dsh-course
node examples/sa01_retry.mjs     # 重试与预算（可靠性）
node examples/sa11_observe.mjs   # 四段分解与成本三档（可观测）
node examples/sa06_bench.mjs     # 成功率与区间（评测）
```

建议：**每完成一个阶段，先跑一遍对应篇目的算例**，把它的数字与你系统的数字对照。差异本身是学习材料——它可能说明你的场景与讲义假设不同，而这正是需要写进决策记录的东西。

## 五、练习

### 第一题：写出一个阶段的交付清单

选 S2（可靠性）为例。

要求：

- 列出这一阶段要加的能力，以及每一项对应的篇目。
- 为每一项写出验收方式（怎么知道它生效了）。
- 列出至少三个关键参数，并说明你会怎么反推。
- 指出这一阶段可能破坏的旧验收，以及如何防止。

---

### 第二题：写一份决策记录

要求：

- 为你系统里的一个关键参数（超时、预算、阈值、并发上限任选）写决策记录。
- 包含：参数值、依据、反推过程、被否决的替代方案。
- 说明如果场景变化（例如从交互改为后台），这个值该怎么改。

---

### 第三题（进阶）：设计回归套件

要求：

- 设计一套跨阶段保留的回归脚本，说明它检查什么。
- 说明如何做到"新增能力时自动发现旧能力被破坏"。
- 指出这套套件在什么情况下会给出假通过。
- 如果真的发现旧验收被破坏，你的处理顺序是什么，为什么。

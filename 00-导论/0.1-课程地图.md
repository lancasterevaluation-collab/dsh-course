## 一、为什么要改结构，而不是改内容

先说清这次调整针对的是什么问题。旧结构（v1）由两部分组成：一份 PM 指南（问题清单 + 体系设计 + 习题总纲 + 3.x 正文），和一套 harness 技术课程（dsh-mini 的 24 步文档）。它们各自都是完整的，但把它们放在一起会产生三个具体的毛病。

**第一个毛病是"两套主线争注意力"。** 学 PM 时你在想"需求怎么定义、优先级怎么排"，学 harness 时你在想"容器怎么注册、事件怎么传播"。这两套思维都需要建立，但它们之间**没有发生连接**——你在 PM 篇里学到的"验收判据"，和在 harness 篇里写下的"验收判据"，看起来是两件事。而实际上它们必须是同一件事：**harness 的每一个能力，都应该有产品意义上的验收判据**。

**第二个毛病是"技术篇里缺判断，方法篇里缺场景"。** 现有的 24 步技术文档质量不低（每个决策都有"替代方案与代价"），但它们缺一个东西：**为什么这一步值得做**——不是"它会解决什么技术问题"，而是"它让这个产品具备了什么、谁会因此受益、怎么证明它有效"。反过来，PM 篇讲了"怎么定义问题、怎么定验收"，但它的例子往往与你的实际工作隔了一层。**两份材料各自都留着另一份该填的洞。**

**第三个毛病是"终点的定义被拆散了"。** v1 里有一个《毕业标准》，但它定义的是 harness 的技术规格；而 PM 篇的终点是"成为 1% 的 PM"。两个终点之间没有关系，于是"学完这门课我做出了什么"这个问题仍然没有答案。

v2 的设计目标就是修掉这三个毛病：**让技术、产品判断、工程原理在同一条线上发生连接，并指向一个可运行的终点。**

## 二、课程的最终交付物

### 2.1 一句话

**一个可供他人长期运行的、面向 DeepSeek 优化的、具备自进化学习闭环的 agent harness。**

这句话里有四个限定词，每一个都对应课程的实质内容：

**"可供他人长期运行"** 意味着它必须具备生产纵深——进程管理、持久化、恢复、可观测、交互边界。这是 dsh-mini 现有 24 步里第 18–22 步的内容，也是"能跑演示"与"能被别人信任"之间的分界线。

**"面向 DeepSeek 优化"** 意味着它必须针对 DeepSeek 的上下文缓存做专门设计，并且**能报告自己的缓存命中率**。这个限定是整个课程里最"产品"的一项——因为它把一个工程指标（前缀稳定性）和一笔真实的钱（命中价约为未命中的 1/30）绑在了一起。

**"具备自进化学习闭环"** 意味着它要包含记忆、技能、用户建模、诊断、演化这五个环节，并满足 Hermes Agent 那个反直觉的设计准则：**写满即拒绝，而不是丢弃最旧的**。

**"harness"** 意味着它的价值不在于模型，而在于**模型之外的一切**——工具、上下文、循环、失败处理、状态管理。这门课的全部技术内容都落在这个括号里。

### 2.2 目标水平：怎么算"达到 dsh / Hermes 水平"

这是一个必须落到判据上的问题，否则"至少达到"就是一句空话。三个可比较的维度：

| 维度 | 判据 | 对照对象 |
|---|---|---|
| **架构机制** | 六个核心机制齐备：插件容器、依赖注入、事件与扩展点、作用域隔离、配置组合、可卸载的 effect | dsh 的 `vendor/cordis`（9 个文件） |
| **自进化闭环** | 五环齐备且**有门控**：记忆（有界）→ 技能（渐进披露）→ 用户模型 → 诊断（可归因）→ 演化（提议/门控/回滚） | Hermes Agent 的机制拆解 |
| **生产纵深** | 四条硬指标：连续 100 任务不崩、中断后可恢复一致、缓存命中率可报告、加一个能力的改动点 ≤ 5 处 | dsh 的 54 个包组 |

**明确不比较的东西**（避免把力气用错地方）：包组数量、功能清单长度、目录结构相似度、单次运行的绝对延迟。理由在 `03-毕业标准.md` 里已经写过，这里只强调一条：**dsh 的框架本体只有 9 个文件，它的"大"全在能力层**。所以"接近 dsh 水平"在框架机制上是一个可达的目标，而在能力广度上不是——后者需要的是时间而不是方法。

## 三、三合一怎么落地（这一节最重要）

如果"三合一"只写在课程介绍里，它就是一个口号。所以这里给出**具体的落地方式**，后面的每一篇都要按它写。

### 3.1 每一篇都含三条线，但它们不是三节

三条线分别是：

**技术线**回答：这个机制怎么设计、怎么实现、怎么验收。

**工程线（SE）**回答：它引入了什么复杂度、它的契约与不变量是什么、它可逆吗、它让哪一类改动变贵。

**产品线（PM）**回答：它解决谁的问题、为什么值得做而不是做别的、怎么判断它真的有效。

**关键在于：三条线讲的是同一件事，只是视角不同。** 它们不能写成三个并列的章节，因为那样读者会把它们当成"三份材料"。正确的组织方式是：**技术线作为主干，工程线与产品线作为对同一个决定的两次追问。**

举一个具体的例子——上下文压缩这一篇：

```
【技术】阈值触发 → 摘要 → 派生视图从压缩点往后算
   │
   ├─ 工程追问：压缩会不会破坏"模型可见 ⟺ 日志可重建"？
   │            会。所以压缩本身要写一条事件，而不是改写历史。
   │            代价：派生多一层；换来：不变量不破。
   │
   └─ 产品追问：压缩解决的是成本还是可用性？
                两者，但权重不同——可用性是硬需求（不压缩就无法继续对话），
                成本是收益（长会话更便宜）。所以它的验收判据必须有两个：
                一个证明"还能继续对话"，一个证明"每轮成本下降了"。
```

**这段结构来自 3.3 的写法**（"你会怎么想错" + "为什么做这个" + 技术步骤），而 v2 把它固化成每一篇的必需部分。

### 3.2 三条线在课程各阶段的权重不同

三合一的第二个要点是：**三条线不是全程等权，而是随阶段转移重心**。

| 阶段 | 重心 | 为什么 |
|---|---|---|
| 判断力地基（第 1 卷） | 产品线 + 工程线为主，技术线只作例子 | 先建立判断力，否则后面每一步都在盲选 |
| 最小闭环（第 2 卷） | 技术线为主，工程线为辅 | 这一段的"对错"由运行结果裁决，产品判断的空间小 |
| 可靠性与纵深（第 3 卷） | 三条线等权 | 每一个机制都同时有技术解、工程代价、产品价值 |
| 学习进化（第 4 卷） | 产品线 + 技术线为主 | 这一段的难点是"该进化什么"，那是产品判断；而机制本身有 Hermes 的现成设计 |
| 规模化与出口（第 5–6 卷） | 三条线合一 | 到这里三条线应该已经无法分开——这正是课程的目标状态 |

**这张表的用途是决定每一篇该把力气花在哪。** 如果一篇在"最小闭环"阶段的文档里花大量篇幅讲产品价值，那多半是跑偏了；反之，在"学习进化"阶段只讲实现而不讲"为什么进化这个"，那是更严重的跑偏。

### 3.3 一个可检验的判断标准

怎么知道一篇文档真的做到了三合一？用这个问题检验：

> **把这篇文档给三种读者看，他们各自能拿走什么？**
> 一个只想实现它的人（拿走技术方案）；
> 一个要评审它的人（拿走代价与边界）；
> 一个要决定"做不做它"的人（拿走价值与判据）。

**如果第三种读者读完之后仍然只能问"所以这个有什么用"，那么这一篇的三合一是失败的**——而它恰好是最常见的一种失败。

### 第 2 卷 · 最小闭环（7 篇）

**目标**：让 harness 能跑完一个真实任务。这一卷结束时，你有一个能对话、能用工具、能记录历史的系统。

| 篇 | 主题 | 技术核心 | SE 线 | PM 线 | 状态 |
|---|---|---|---|---|---|

| 2.2 | **工具系统** | 注册表、schema、副作用等级 | 扩展点而非硬编码 | 能力边界怎么定 | ✅ 已完成（含作业 a2：客观题 + 构建题） |
| 2.3 | **容器与依赖注入** | 服务注册、所有权、卸载回滚 | 生命周期与所有权 | 为什么要可卸载 | ⬜ 待写 |
| 2.4 | **事件与扩展点** | waterfall、inject、短路 | 直接调用的代价 | 行为该挂在哪 | ⬜ 待写 |
| 2.5 | **作用域与隔离** | 多 agent 各见不同世界 | 隔离的边界 | 何时需要隔离 | ⬜ 待写 |

**作业包的位置**：第 2 卷的七个作业包合并成一个工作区 `homework/ch02-loop/`（判分项 t1–t9，每篇按"客观 + 构建"两项记）——**这一卷的七篇会产出一个完整的系统，分成七个工作区会让人以为它们是七个练习。**

**2.7 是整个课程的技术枢纽**：后面每一篇都会威胁它的一条不变量，而正确处理它的能力决定了一个 harness 是"能用"还是"会悄悄坏掉"。

### 第 3 卷 · 可靠性与生产纵深（6 篇）

| 篇 | 主题 | 关键判据 |
|---|---|---|
| 3.1 | **重试与错误分类** | 可重试与不可重试的区分；重试不破坏日志 |
| 3.2 | **守卫、审批与沙箱** | 越权被拦且给出原因；沙箱的实际约束逐平台诚实标注 |
| 3.3 | **上下文压缩与溢出** | 压缩后仍能从日志重建"模型当时看到什么" |
| 3.4 | **进程与后台作业** | 取消能杀掉整棵进程树；无孤儿 |
| 3.5 | **持久化与恢复** | 重启后能继续对话；恢复只认日志不认内存 |
| 3.6 | **可观测：token、延迟、成本、缓存命中** ★ | 每轮可回答"花了多少、慢在哪、命中了没有" |

**3.6 是"面向 DeepSeek 优化"这项要求的落点**，也是《毕业标准》第一条验收测试的实现处：没有它，后面所有优化都无法验证。

### 第 4 卷 · 学习进化（7 篇）★ Hermes 式

**这一卷是本课程与 dsh 的差异所在**——dsh 没有学习进化闭环，而 Hermes Agent 有。

| 篇 | 主题 | 来自 Hermes 的关键设计 |
|---|---|---|
| 4.1 | **记忆：有界与"写满即拒绝"** | 写满时**失败**而不是丢最旧的；强制合并 |
| 4.2 | **技能库与渐进披露** | 元数据先给、正文按需取；长期不用的转 archived |
| 4.3 | **用户建模与检索** | 派生结论而非存原文；FTS5 检索历史 |
| 4.4 | **诊断：失败归因** | 归因到组件；用 Macro-F1 与 κ 评估 |
| 4.5 | **演化：提议、门控、回滚** | 自改必须留证据链，且可回滚 |
| 4.6 | **复盘周期与真实门控** | 用真实任务集当回归基线 |
| 4.7 | **长程任务：任务级状态、续作与目标保持** | 任务状态外部化为唯一权威；续作靠检查点而不是重读全文；进度判断与目标漂移 |

**4.7 是补充进来的**：前六篇覆盖"跨会话积累"（记忆、技能、用户模型、诊断、演化、复盘），而它们都不处理"一个任务跨多次会话推进"这件事——3.5 的恢复是进程级、4.1 的记忆是事实级、3.3 的压缩是单会话级，三层都不能回答"我们做到哪了"。第 6 卷的 6.1 把"长程 agent 的开放问题"列为科研出口，而工程侧的机制正是这一篇——**科研问题与工程机制在这里配对**。

## 五、每篇的固定结构

沿用并扩展 3.3 已经验证的形态：

```
元信息（篇号 / 目标级别 / 解决哪些清单条目 / 参考来源 / 产出物）
本篇新词
第 0 节 · 学完能做出什么（含"先看骨架"的先行组织者图）
第 0.5 节 · 系统视角（位置图 + 下游依赖表 + ≥3 连锁影响）
L0 · 要解决的问题（现象，不是口号）
L1 · 设计与原理（含每小节的知识关系图）
L2 · 决策表（决策 × 选择 × 替代 × 代价落在谁身上）
L3 · 实现（施工图 + 验收判据 + 风险型里程碑）
L4 · 运行与验证（含"怎么用外部工具否定程序自己的报告"）
L5 · 语法速查（术语 + 命令 + 模板）
L6 · ★ 分级重建判据
L7 · 挑战题（≥6 道，不给答案）
L8 · 自检清单（理解 / 应用 / 判断三层）
L9 · 仍未解决（≥3 条真实缺陷）
```

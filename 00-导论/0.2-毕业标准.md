## 1. 为什么需要这样一份文档

先说清它要解决的问题。

你之前的工作方式是"一课一课地学、一题一题地做"。这种方式有一个隐患：**每一课的产物是独立的**，课程结束时你手上会有一堆笔记、几份分析、若干脚本，但它们拼不起来，也无法回答"我到底做出了什么"。更糟的是，你可能在每一课里都用了同一个词（比如"扩展性"）却给了它不同的含义，于是越学越模糊。

这份文档的作用是**把终点写死**，让每一份作业都有可对账的目标。它的基本要求是三条。

**第一，终点必须是一个可运行的东西，而不是一个"能力清单"。** 所以终点定为"一个可直接运行的 harness"，而不是"你掌握了 12 项技能"。这两者的差别在于：前者可以被运行、被测量、被否定；后者只能被自我感觉评估。

**第二，验收标准必须是可测量的。** 所以每个维度都给判据与测法，而不给形容词。"扩展性好"不是标准，"加一个新工具需要改动 5 处，且其中只有 3 处会被类型系统提醒"才是标准。

**第三，必须有一个能对标的外部基准。** 所以对照 `dsh` 与 `reasonix`。因为"好"如果没有参照物，就会退化成审美判断；而有了参照物，"接近或超过"就是一个可以被回答的问题。

## 2. 终点的定义：要交付什么

### 2.1 一句话定义

**交付一个能长期运行的、面向 DeepSeek 模型优化的 agent harness**：它能接受一个任务、自主使用工具完成它、在失败时可靠恢复、在需要时请求人确认、并在成本上做到尽可能低。

这句话里的每个短语都对应下面的一个维度。而它的关键限定是"**面向 DeepSeek 优化**"——不是通用 harness，而是**针对 DeepSeek 的 API 特性（尤其是上下文缓存）做过专门优化**的 harness。这是本文档与一般产品需求最大的区别，也是 §5 要展开的部分。

### 2.2 它与 dsh-mini 的关系

你现在手上的 `dsh-mini` 是这个终点的**前半程**：它已经具备了完整的架构骨架（容器、事件、插件、会话、循环、重试、守卫、记忆、技能、检索、诊断、演化、模式、PTC、多智能体），验证脚本 23 项全过，能跑真实任务。

但它离终点还差三件事，而这三件事恰好就是本课程剩余作业的内容：

**第一，它缺少"生产级"的稳定性机制**：进程管理（第 19 步）、持久化与恢复（第 20 步）、可观测（第 21 步）、交互边界（第 22 步）。没有这四步，它能在你的机器上跑通演示，但不能连续跑一周。

**第二，它的性能从未被测量过**：它目前不知道自己的 token 成本、不知道缓存命中率、不知道每个任务的延迟构成。一个没有被测量的系统，无法被优化——这是第 21 步的内容，也是本文档 §5 的核心。

**第三，它的扩展性从未被验证过**：它号称"插件化"，但加一个新能力实际要改几处、其中几处会报错，没有人测过。§3.3 给出了这个测量方法。

### 2.3 交付形态

最终交付物由四部分组成，缺一不可。

**一是可运行的代码**：一个仓库，`README` 里有一条命令能启动它，第二条命令能跑通一个真实任务。

**二是可复现的验证**：一份自动化检查（类似 dsh-mini 现在的 `src/apps/verify.ts`），它必须覆盖六维标准里的每一条，并且能在干净环境里跑通。

**三是可对照的性能数据**：一份测量报告，包含缓存命中率、每任务 token 成本、延迟构成，并且与 `dsh` 在同一任务集上的数据并列。

**四是可追溯的设计记录**：每个关键决策有一份 ADR（含被否掉的替代方案与代价），因为"符合软件工程原则"的证据不是代码漂亮，而是**决策可追溯**。

## 3. 六个维度的验收标准

下面六个维度，每个都给三样东西：**判据**（什么样的状态算达标）、**测法**（怎么测出来）、**对应的作业**（哪几份作业在往这个方向推）。

### 3.1 可用性：它能完成真实任务，而不只是演示任务

**判据**：在一个你**没有为它专门准备过**的任务集上（至少 10 个任务，覆盖文件操作、命令执行、多步推理、需要读文档四类），任务完成率不低于设定阈值，且失败案例有明确的原因分类。

这里的关键限定是"没有专门准备过"。演示任务有一个隐蔽的问题：**它们是被挑选过的**——你知道哪条命令能跑通、哪个路径一定存在。所以用一个"你熟悉但设计者不熟悉"的任务集，才能真正测出可用性。

**测法**：准备 10 个任务，记录每个的完成状态与失败原因；把失败原因用错误分类学（第 15 步的 `docs/research/error-taxonomy.md` 给了一份分类）归类，看是否有某一类占了多数——**如果某一类错误占了 40% 以上，那说明它是系统性的，不是运气问题**。

**对应作业**：3.1（十站模型的验证站）、3.7（测试与发布）、以及第 23 步的规模化。

### 3.2 稳定性：连续运行不退化

**判据**：三条具体的标准。第一，连续跑 100 个任务不出现进程级崩溃。第二，任何一个任务被中断（Ctrl-C、进程被杀、网络断开）之后，重启能恢复到一致状态。第三，内存与句柄不随时间单调增长。

第二条是最容易被忽略的，也是最有价值的。**"恢复后状态一致"这个要求会强迫你面对一个根本问题：什么状态必须被持久化、什么状态可以重建。** dsh-mini 的会话日志设计（`kernel/session.ts` 的 append-only 事件流）已经为这件事打好了地基——因为事件流可以重放，所以"重建"是可行的；但这需要第 20 步把重放真正实现出来。

**测法**：写一个循环脚本跑 100 个任务，每 10 个记录一次内存与句柄数；写一个脚本在任务执行到一半时 `kill` 进程，重启后检查会话文件与内存状态是否一致。

**对应作业**：第 19 步（进程管理）、第 20 步（持久化与恢复）、3.6（数据与状态）。

### 3.3 拓展性：加一个能力要改几处，而且要能测出来

**判据**：加一个**新的工具**，需要改动的文件数不超过 5 个；其中"会报错"的（类型不匹配、校验失败）应占多数，"会静默失效"的（配置、文档、提示词）应占少数。加一个**新的插件**不超过 2 处（插件文件 + 配置行）。

这个判据的来源很具体：dsh-mini 现在的实测数据是——加一个新工具要改 5 处，其中 3 处会报错（工具定义、工具池、模式白名单）、2 处不会（验收期望、文档表格）。**2 处"不会报错"就是这 5 处里最危险的部分**，因为漏了它们不会有人发现，直到某天有人照着文档做而失败。

**测法**：真的加一个工具，把改动点逐条记下来，标注每一处"漏了会怎样"。这份记录本身就是 3.2 里讲的"同步清单"，它也是 §5 里那套度量的输入。

**对应作业**：3.2（复杂度的五个测量方法）、3.4（接口与契约）、以及 3.3 作业里的 P2。

### 3.4 鲁棒性：异常输入不产生异常状态

**判据**：四类边界各有明确的处理与验证——**输入边界**（空、超长、非法编码）、**资源边界**（磁盘满、输出过大、超时）、**并发边界**（同一会话并发任务、同一文件并发写）、**外部依赖边界**（模型返回畸形 JSON、网络中断、API 限流）。

其中最容易被忽略的是"模型返回畸形 JSON"这一类。它在真实运行中一定会发生（模型偶尔会输出不完整的工具调用），而一个没有处理的 harness 会在那一刻抛出一个与真实原因毫无关系的错误。

**测法**：为每一类构造一个具体的失败注入（把一个假的 provider 接进去，让它返回畸形响应），确认系统给出**可理解的错误**而不是崩溃。

**对应作业**：第 22 步（交互边界）、3.6（数据与状态）、3.7（测试与发布）。

### 3.5 性能：不是"快"，而是"知道慢在哪里"

**判据**：三件事。第一，每个任务的延迟可以分解成**模型调用、工具执行、框架开销**三段，且三段各自有数据。第二，框架开销占总延迟的比例有上限（一个 harness 的框架开销如果超过模型调用的 20%，说明它有问题）。第三，工具执行里最慢的三个有记录。

这条之所以写成"知道慢在哪里"而不是"要快"，是因为**在没有测量的情况下优化是赌博**。而测量的门槛比想象中低：dsh-mini 已经有一条完整的事件流，只要在事件里记录时间戳（第 21 步的内容），三段分解立刻可得。

**测法**：跑 10 个任务，从会话事件里提取每段的耗时，画一张分解图。

**对应作业**：3.10（性能与容量）、第 21 步（可观测）。

### 3.6 缓存复用：本项目的核心技术指标

这个维度单独展开，因为它既是**成本的决定因素**（命中价格约为未命中的 1/30），又是**延迟的决定因素**（128K 提示词的首 token 延迟可从秒级降到亚秒级），而且它的技术要求与其他维度**会发生冲突**。下一节专门讲。

---

## 4. 缓存复用：为什么它是核心指标

### 4.1 机制：必须从第 0 个 token 起完全匹配

DeepSeek 的上下文缓存（官方的"上下文硬盘缓存"）对**所有 API 用户默认开启，无需改代码**。它的机制有三条关键规则，理解这三条是后续一切优化的前提。

**第一条，只有完全相同的前缀才命中，且匹配必须从第 0 个 token 开始。** 这意味着**在输入中间出现的重复内容不产生任何缓存收益**。举例来说，如果你的系统提示词每次都在开头插入一个时间戳，那么后面所有的内容即使一字未变，也全部是未命中——因为从第 0 个 token 起就已经不同了。

**第二条，缓存的存储单位是 64 个 token。** 短于这个长度的内容不会被缓存。所以"把系统提示词压缩到 50 token 以节省成本"这个想法是错的：那样它根本不进缓存。

**第三条，缓存是尽力而为（best-effort），不保证 100% 命中。** 命中需要完整复用一段已持久化的前缀单元，而持久化发生在请求/输出的边界处、以及固定的 token 间隔上。所以"看起来相似"不等于命中，你必须在运行时**测量**它，而不能假设。

测量的方法是读 API 响应里的两个字段：`prompt_cache_hit_tokens` 与 `prompt_cache_miss_tokens`。命中率就是前者与 `prompt_tokens` 的比值：

$$\text{命中率} = \frac{\text{prompt\_cache\_hit\_tokens}}{\text{prompt\_cache\_hit\_tokens} + \text{prompt\_cache\_miss\_tokens}}$$

而成本可以这样算：

$$\text{cost} = \frac{\text{hit}}{10^6} \times P_{\text{hit}} + \frac{\text{miss}}{10^6} \times P_{\text{miss}} + \frac{\text{out}}{10^6} \times P_{\text{out}}$$

这两个公式的价值在于：**它们把"性能优化"从一个模糊的工程目标，变成了一个可以被日常观察的数字**。一旦命中率进入你的可观测面板，任何破坏它的改动都会立刻显形。

### 4.2 五条实现规则

从上面的机制可以直接推出五条工程规则。它们有一个共同的形式：**任何会让"前缀"发生变化的操作，都要付出成本**。

**规则一：系统提示词固定在最前，且内容稳定。** 官方建议把系统提示词固定为 `messages[0]`，让前缀的起点稳定。具体到实现上，这意味着**不要在系统提示词里放变化的东西**——当前时间、随机的鼓励语、每次重新格式化的工具清单，都会让整个前缀失效。dsh-mini 的 `Session.deriveMessages` 与 `systemPromptOf` 是纯函数（从事件流派生），这是有利的；但要注意它派生出的内容必须**逐字节稳定**。

**规则二：历史只能追加，不能重写。** 第 N 轮的请求应当以第 N-1 轮的请求为前缀。dsh-mini 的 append-only 会话日志天然符合这一条——事件只增不改，派生结果也因此稳定。

**规则三（最关键）：压缩过的那一段，在后续轮次里必须保持字节不变，而且每条消息只压缩一次。**

这一条与直觉冲突，值得展开。压缩的直觉做法是"每次压缩都重新摘要前面全部的历史"，而按缓存机制，这个做法会让**每一轮都产生全新的前缀**，从而把命中率打到底。正确的做法是：**压缩发生时，把结果固化成一条不可变的事件**，后续轮次派生的前缀里，这一段与压缩那一刻完全一致。

dsh-mini 的设计恰好符合这一条：压缩写在 `session/compaction` 事件里，**不删除原始事件**，派生时"跳过压缩点之前的部分"（第 18 步的 `deriveView`）。这个设计当初的理由是"保持模型可见与日志可重建的一致性"，而它在缓存上还有一个额外的收益：**压缩点之前的内容在派生视图里是稳定的，因此前缀的长度虽然缩短了，但后续轮次之间仍然互相命中**。

反过来说，任何"每轮重新摘要"或"压缩后重新格式化历史"的实现，都会在缓存上付出代价。**这正是"工程原则"与"性能指标"相互印证的一个例子**：append-only 与不可变事件在工程上是好设计，在成本上也是。

**规则四：工具定义的顺序与格式保持稳定。** 工具清单通常紧跟在系统提示词之后，是前缀的第二段。因此**工具的顺序、JSON 的字段顺序、以及 schema 的生成方式都会影响命中**。这一条在实现上有一个常被忽略的细节：如果工具清单是从一个字典（哈希表）生成的，而不同运行中字典的遍历顺序不同，那么即使内容一样，前缀也会不同。**所以工具清单必须是显式的有序列表**——dsh-mini 的 `TOOL_POOL_NAMES` 是一个数组而不是对象，这在缓存上是正确的选择，虽然当初的理由只是"顺序可控"。

**规则五：为缓存设计可观测性。** 因为缓存是 best-effort，所以必须测量而不能假设。要记录每一轮的 hit/miss，并按任务聚合成命中率；要能回答"这个任务的命中率为什么低"——常见原因有：首轮无前缀可复（正常）、系统提示词里有变量（bug）、压缩策略重新摘要（bug）、工具顺序不稳定（bug）。

### 4.3 会破坏缓存的六种做法（对照表）

下面这张表是 §4.2 的反面，用于自查。它在读代码与做改动时都可以直接使用。

| 做法 | 为什么破坏缓存 | 正确的做法 |
|---|---|---|
| 系统提示词里插入当前时间/随机内容 | 前缀从第 0 token 起就变了 | 把时间放在**最后**一条消息里 |
| 每轮重新格式化历史（缩进、日期、角色标记） | 格式变化即前缀变化 | 格式固定，派生逻辑纯函数 |
| 每次压缩都重新摘要全部历史 | 每轮产生全新前缀 | 压缩结果固化为不可变事件，只压一次 |
| 工具清单从无序结构生成 | 遍历顺序不稳定 | 用显式有序数组 |
| 多轮对话中重置历史（开新会话） | 丢失了可复用的长前缀 | 追加；需要分段时用模式切换而非重置 |
| 把变化的内容放在输入开头 | 前缀立即失效 | 稳定内容在前，变化内容在后 |

**这张表里有一条值得单独说明**：第六行"稳定内容在前、变化内容在后"是一个通用原则，它的适用范围超出缓存——它也适用于人类阅读（先看结论）与调试（先看固定部分）。但当它与缓存结合时，它变成了一个**量化的成本选择**：把一个 20K token 的固定提示词放在开头，在有缓存的情况下，它的成本约等于没有缓存的 1/30。

### 4.4 与 dsh-mini 现状的对照

把上面五条规则用在 dsh-mini 上，会得到一份具体的待办清单。

**已经符合的**：会话日志是 append-only（规则二）；派生函数是纯函数（规则一的基础）；工具池是有序数组（规则四）；压缩写事件而不删历史（规则三的正向设计）。

**需要补的**：dsh-mini **目前完全没有缓存可观测性**——它的 `DeepSeekProvider` 读到了 `usage`，但没有把 `prompt_cache_hit_tokens` 与 `prompt_cache_miss_tokens` 记下来，也没有按任务聚合。这意味着**它无法回答"我的命中率是多少"这个最基本的问题**。这是第 21 步（可观测）要补的第一件事，也是本文档 §6 里"验收测试"的第一条。

**需要警惕的**：dsh-mini 的**模式系统**在切换模式时更换提示词（每个模式有自己的 `prompt` 字段）。这在缓存上的含义是：**跨模式切换会让前缀失效**。这不是缺陷（模式切换本来就意味着换了一套指令），但它是一个必须在文档里写明的成本——否则使用者会以为"换个模式是免费的"。

## 5. 怎么算"接近或超过 dsh"

### 5.1 三个可比较的量

"接近或超过"如果不落到具体数字上，就是一句空话。所以这里定三个可比较的量，并说明各自的比较方式。

**第一个量是缓存命中率。** 同一个任务集、同一个模型，比命中率。这个量的比较需要注意一点：**首轮任务的命中率天然低**（没有前缀可复用），所以比较时必须按"第 2 轮及以后"或者"多轮会话"来统计，否则数字没有意义。调优良好的架构在这个口径下可以达到 95% 以上——这是第三方实践数据给出的区间，不是理论极限，所以它是一个可以逼近的目标。

**第二个量是每任务的 token 成本。** 把命中 token 按命中价、未命中 token 按未命中价折算，得到每个任务的实际成本。这个量比命中率更直接，因为它同时包含了"前缀有多长"与"命中率有多高"两个因素。**一个前缀很长但命中率 99% 的系统，成本可能远低于前缀很短但命中率 50% 的系统。**

**第三个量是框架开销占比。** 总延迟减去模型调用时间与工具执行时间，剩下的就是框架自己的开销。这个量的比较不受模型速度影响，因此最能反映 harness 本身的工程质量。

### 5.2 明确不比较什么

有三件事**不应该**作为比较对象，说明理由是为了避免把力气用错地方。

**不比较"功能数量"。** 一个支持 50 个工具的 harness 不比支持 10 个的更"接近 dsh"——因为工具数量增加会拉长前缀、降低缓存效率，同时增加理解成本。功能的多少是产品选择，不是工程水准。

**不比较"代码行数"或"目录结构的相似度"。** 这是 3.2 里已经讲透的道理：复杂度不等于代码量。模仿 dsh 的目录结构不会让你更接近它。

**不比较单次运行的绝对延迟。** 因为它主要取决于模型与网络，而不是 harness。要比较的是"框架开销占比"这个剥离了外部因素的量。

### 5.3 差距分析的写法

每次做完一份作业，用下面三句话更新一次差距分析：

```
【已达到】这一维度上，我的系统现在的数据是 ______，dsh 的对应数据是 ______。
【差距原因】差距来自 ______（一个具体机制，不是"做得不够好"）。
【下一步】消除它需要做 ______（一份作业，不是一个愿望）。
```

这个格式的用处在于：**它强迫"差距"必须归因到一个具体机制上**。如果归不出来，说明你还没找到问题所在——那也是一条有用的结论。

## 6. 验收测试：怎么证明达到了

终点不是靠自述达到的，而是靠一组能跑出结果的检查。下面七条构成验收测试，它们全部是可执行的。

**第一条（缓存可观测）**：跑一个 5 轮以上的会话，从输出里读到每一轮的 `prompt_cache_hit_tokens` 与 `prompt_cache_miss_tokens`，并算出聚合命中率。**这条是其余六条的前提**——没有它，你无法判断任何优化是否有效。

**第二条（缓存正确性）**：在同一个会话里，连续两轮的请求，第二轮的前缀与第一轮完全一致（除了末尾新增的消息）。验证方式是保存两次请求的完整 payload 并逐字节比对前缀部分。

**第三条（压缩不破坏缓存）**：触发一次压缩之后，接下来的两轮之间仍然互相命中。这条专门验证 §4.2 的规则三是否真的实现对了。

**第四条（可用性）**：10 个未专门准备的任务，完成率与失败原因分类。

**第五条（稳定性）**：连续 100 个任务不崩溃；中断后重启状态一致。

**第六条（拓展性）**：真的加一个工具，记录改动点数量与"漏了会怎样"。

**第七条（鲁棒性）**：四类边界注入测试全部给出可理解的错误。

**这七条里，第一条与第三条是"缓存复用"维度的直接验收**，也是这份文档与其他产品需求最大的不同——把这个维度的验收写得比功能验收还具体，是因为它最容易在"能跑就行"的心态下被遗忘。

## 7. 作业与终点的映射

最后把这份标准与作业体系接起来。下表说明每份作业对哪个维度贡献什么，**它也是你判断"这份作业要不要认真做"的依据**：没有贡献的作业可以跳，贡献越直接的越值得投入。

| 作业 | 主要贡献的维度 | 具体贡献 |
|---|---|---|
| 3.1 一个功能的一生 | 全部维度的过程保障 | 让每个改动都有验收判据与回滚方案 |
| 3.2 复杂度与技术债 | 拓展性 | 五个测量方法，直接产出"加一个能力要改几处"的数据 |
| 3.3 读代码与架构 | 拓展性 · 稳定性 | 能判断一处改动会波及谁；能找出未写下的不变量 |
| 3.4 接口与契约 | 拓展性 · 鲁棒性 | 接口的承诺写清楚，边界行为可预测 |
| 3.5 可逆与不可逆 | 稳定性 | 区分可回滚与不可回滚的改动 |
| 3.6 数据与状态 | 稳定性 · 鲁棒性 | 状态所有权、恢复、边界 |
| 3.7 测试与 CI 与发布 | 可用性 · 稳定性 | 每次改动都有验证 |
| 3.8 估计与不确定性 | 全部 | 让计划可执行 |
| 3.9 模式词汇 | 拓展性 | 听懂方案讨论，能独立设计扩展点 |
| 3.10 性能与容量 | **性能 · 缓存复用** | 延迟分解、token 成本、命中率优化 |
| 第 19–22 步作业 | 稳定性 · 性能 | 进程、持久化、可观测、交互边界 |
| 第 23–24 步作业 | 可用性 · 拓展性 | 规模化与自进化深化 |

**这张表里最需要现在就知道的一点**：**"缓存复用"这个维度目前没有任何一份作业在直接负责**。3.10 会讲性能与容量，但它是第三册的最后一篇；而第 21 步（可观测）是它的数据前提。所以如果你想让这条主线真的落地，需要在做 3.10 的作业时**把缓存指标作为一等公民**，并在第 21 步实现时就把 hit/miss 的采集做进去——而不是等到最后再补。

## 8. 仍未解决（这份标准自己的缺陷）

| 缺陷 | 后果 | 修法 | 当初为什么这么写 |
|---|---|---|---|
| 六个维度之间会冲突，但本文没有给出冲突的裁决规则 | 例如"极致缓存复用"会鼓励少改前缀，而"极致鲁棒性"会鼓励多加校验信息到提示词 | 补一节"冲突裁决"：明确缓存优先于鲁棒性的边界在哪里 | 先把每个维度的判据写清，才有条件谈冲突 |
| 所有阈值都是建议值，没有数据支撑 | 读者可能把"5 处""95%"当成硬标准 | 在真实跑出数据后回填阈值，并标注测量条件 | 目前没有真实运行数据；写死假数字比留空更糟 |
| 价格与机制来自公开文档，会随时间变化 | 成本计算结果可能过期 | 每次做性能作业时重新核对官方定价页 | 定价是外部事实，本文只能给测量方法 |
| 完全没有涉及"多用户/服务化" | 若最终要部署成服务，还需额外的维度（隔离、配额、并发） | 单列一节"服务化附加维度" | 当前目标是单机可运行的 harness，服务化是另一个量级 |
| 与 dsh 的比较缺少可复现的任务集 | "接近或超过"目前无法被第三方验证 | 构造一个公开的任务集与测量脚本 | 需要先有一个能跑的自己版本，才有比较的意义 |
| 对 reasonix 的引用目前是定性的 | 无法给出"接近 reasonix 缓存水准"的具体差距 | 在做完第一条验收测试后，用同一任务集跑一次对比 | 没有测量数据之前，任何比较都是猜测 |

## 9. 下一步

这份标准现在是一份**承诺**，不是一份**成绩**。把它变成成绩的路径是清楚的：

**最近的一步**是做 §6 的**第一条验收测试**——让 harness 能报告自己的缓存命中率。这一步不大（把 `usage` 里的两个字段读出来、按任务聚合、打印），但它是后面所有优化的前提。它属于第 21 步（可观测），所以在你做那一步时，请把这条要求一起做进去。

**同时要做的一件事**是更新 `3.3-作业引导.md`：在每份作业的末尾加一节「这份作业对 §3 的哪个维度贡献了什么」。这样作业就不再是孤立的练习，而是有账可对的进度。

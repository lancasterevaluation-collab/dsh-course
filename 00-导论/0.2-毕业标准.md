## 读完这一篇你会知道什么

1. **终点的定义**：一个能通过六维验收的 agent harness，而不是一份文档。
2. 六个维度：功能、可靠性、成本、可观测、可扩展、安全。
3. 每一项的判据：每个维度都有可跑出来的数字。
4. 验收测试的形态：你可以自己写的检查脚本。
5. 缓存复用为什么是核心指标：它同时反映架构质量与成本控制（见 2.1 的 96.1%）。
6. 四级能力与验收的对应：L1–L4 各自需要交付什么。

## 一、终点的定义

**终点是"一个 harness"，不是"一份总结"。**

它要满足四条：

| 条件 | 含义 |
|---|---|
| **能运行** | 一条命令启动，能完成真实任务 |
| **能通过验收** | 六维检查全部通过（见第二节） |
| **能被自己解释** | 关键决策都有量化依据，而不是"我选的" |
| **能被别人接手** | 有可续作的状态与文档（见 4.7） |

"能被自己解释"是最容易被跳过的一条：**如果你的系统参数说不出依据，那你没有掌握它，只是碰对了。**

## 二、六个验收维度

| 维度 | 验收什么 | 判据形态 |
|---|---|---|
| **功能** | 能完成目标类型的任务 | 任务成功率 |
| **可靠性** | 出错时能恢复、不会挂死 | 故障注入下的通过率 |
| **成本** | 单位任务的花费 | 每任务 token 与费用 |
| **可观测** | 能回答"慢在哪、贵在哪、坏了没" | 四段分解 + 成本三档 |
| **可扩展** | 加一个能力不需要改核心 | 新增能力的改动行数 |
| **安全** | 越权与危险操作被挡住 | 红队用例全部被拦 |

六者的关系不都是"分数越高越好"：**安全是硬约束**（与 6.3 的一票否决一致），其余五项是权衡。

## 三、怎么做

### 3.1 逐项判据

每一项都要有**可跑出来的数字**，而不是"做得不错"。

| 维度 | 判据 | 依据篇目 |
|---|---|---|
| **功能** | 在你的任务集上成功率达到设定目标 | 6.3 评测 |
| **可靠性** | 注入限流、超时、崩溃后仍能完成 | 3.1 / 3.4 / 3.5 |
| **成本** | 每任务成本低于预算，且缓存命中率达标 | 2.1 / 3.6 |
| **可观测** | 四段延迟分解可用、残余项小于 10% | 3.6 |
| **可扩展** | 新增一个工具/技能不改核心循环 | 2.2 / 4.2 |
| **安全** | 注入类与越权类用例全部被拒绝 | 3.2 / 5.3 |

"残余项小于 10%"这一条值得注意：它是**可观测性是否真的落地的直接证据**。如果你分段之和对不上总量，说明有一处开销没被测量（见 3.6）。

"新增能力不改核心"是最有区分度的一条：**它衡量的是架构质量**——如果加一个工具要改循环代码，说明能力接缝没有划对（见 2.1 的三角色）。

### 3.2 验收测试

**验收测试是你自己写的检查脚本。** 它至少覆盖四类：

| 类型 | 检查什么 | 例 |
|---|---|---|
| **功能** | 任务能完成 | 跑一组任务集，报成功率与区间 |
| **故障注入** | 出错能恢复 | 注入限流/超时/崩溃，看是否仍完成 |
| **护栏** | 优化未伤害别处 | 检查延迟、成本、准确率的约束 |
| **安全** | 危险被拦 | 注入用例与越权用例全部被拒 |

为什么"故障注入"是必需的：**可靠性是这门课第 3 卷的全部主题**，而它无法靠"正常路径跑通"证明。你必须主动制造失败——这与 3.1 的故障注入、3.4 的三类进程用例、3.5 的崩溃相位测试是同一套方法。

为什么"护栏"也是必需的：**优化一个维度常常伤害另一个**（见 3.6）。没有护栏的验收会让"刷指标"通过。

### 3.3 为什么缓存复用是核心指标

缓存命中率是一个缩影：它同时反映三件事。

| 反映 | 原因 |
|---|---|
| **架构质量** | 缓存要求前缀稳定，而前缀稳定要求系统提示与工具定义不频繁变化 |
| **成本控制** | 1 写 9 读时有效价格降到 **0.215 倍**（省 4.65 倍） |
| **可观测水平** | 命中率下降的原因需要能定位（例如插入了时间戳） |

算例给出的数字：长会话下前缀缓存能**节省 96.1%**（见 2.1）。

为什么它值得作为核心指标：

| 如果它高 | 如果它低 |
|---|---|
| 前缀稳定（架构好） | 前缀频繁变动（有设计问题） |
| 成本可控 | 成本失控 |
| 你清楚它为什么变 | 你在猜 |

这与 6.3 的"饱和放大"有相同的道理：**一个好的指标应当同时反映多个维度，且它的下降有明确的诊断路径。**

### 3.4 能力等级与判据

**四级能力**（与 0.1 的 3.4 一致），每一级的交付物不同：

| 等级 | 交付物 | 判据 |
|---|---|---|
| **L1 能读懂** | 一份说明 | 能说清每卷的关键判据与依据 |
| **L2 能复现** | 一份算例报告 | 能在自己的系统上算出同样的量（重试预算、样本量、覆盖窗口） |
| **L3 能判断** | 一份决策记录 | 面对新问题能给出做法与量化依据 |
| **L4 能设计** | **一个能通过验收的 harness** | 六维验收全部通过，且关键参数都能反推 |

**L4 是这门课的终点，也是"毕业标准"的字面含义。**

**每一级的判据都是"能说出数字或写出检查"**，这与 4.7 的"约束必须可检查"是同一个要求——如果一件事无法被检查，那它还没有被真正掌握。

### 3.5 特殊情况与处理技巧

验收过程中会遇到几种典型情况，它们的处理方式不同：

| 情况 | 为什么 | 处理 |
|---|---|---|
| 任务集太小 | 区间太宽，结论不可靠 | 加大样本或用分层报告（见 6.3） |
| 成功率接近饱和 | 失去区分度 | 改用 pass^k 或加成本维度 |
| 故障注入通不过 | 没有重试或没有超时 | 回到 3.1 / 3.4 补机制 |
| 成本超预算 | 上下文或工具调用过多 | 查缓存命中率与四段分解 |
| 新增能力要改核心 | 能力接缝没划对 | 检查是否只依赖接口（见 2.1） |
| 安全用例有漏网 | 守卫只挡了一条路径 | 见 3.2 的绕过清单 |
| 参数说不出依据 | 抄了默认值 | 用各篇的公式反推 |
| 验收通过但用户不满 | 指标与体验脱节 | 检查是否只看均值（见 3.6） |

最后一条值得展开：**指标全绿而用户体验差，通常是"只看均值"造成的。** 加 P95 与失败分类，通常就能发现原因。

### 3.6 验收判据的原理

六个维度不是随意选的，它们对应四类必须回答的问题：

| 维度 | 回答的问题 | 对应的篇 |
|---|---|---|
| 功能 | 它做对了吗 | 6.3 |
| 可靠性 | 出错时它还工作吗 | 3.1 / 3.4 / 3.5 |
| 成本 | 它贵吗 | 2.1 / 3.6 |
| 可观测 | 我能知道它为什么这样吗 | 3.6 |
| 可扩展 | 加东西要动核心吗 | 2.1 / 2.2 |
| 安全 | 它会伤到不该伤的东西吗 | 3.2 / 5.3 |

**"可观测"与"可扩展"最容易被当成软指标**，而它们其实最硬：

- **可观测是排障的前提**：没有它，前三个维度出问题时你只能猜。
- 可扩展是维护成本的前提：它决定"加第十个能力的代价"，而这直接决定系统能走多远（见 1.2 的债务利息模型）。

这两条与 1.2 的结论一致：**利息 $i = f \times c$ 里的两个因子，恰好对应"改动多难"（可扩展）与"多频繁要改"（可观测决定你能多快定位）。**

## 四、常见问题

| 问题 | 回答 |
|---|---|
| 必须从零写一个 harness 吗 | 不必。可以在理解现有 harness 的基础上，逐卷加上缺失的能力 |
| 六维必须全满分吗 | 不必。安全是硬约束，其余五项按你的场景设定目标 |
| 没有真实任务集怎么办 | 用你自己的日常任务构造（见 6.3 的构造方式） |
| 成本怎么算 | 按输入/输出/缓存三档记账（见 3.6） |
| 验收测试要多大 | 够覆盖四类即可，规模取决于你的时间预算 |
| 学完但没有 harness 算不算毕业 | 不算。**这门课的终点是产物，不是理解** |

## 五、自评清单

六维验收（每项都要给出你跑出来的数字）：

| # | 检查项 | 你的结果 |
|---|---|---|
| 1 | 功能：任务成功率与置信区间 | |
| 2 | 可靠性：三类故障注入后的完成率 | |
| 3 | 成本：每任务成本与缓存命中率 | |
| 4 | 可观测：四段分解与残余比例 | |
| 5 | 可扩展：新增一个能力改了几处 | |
| 6 | 安全：注入与越权用例的拦截率 | |

四级能力（每级给出证据）：

| # | 等级 | 你的证据 |
|---|---|---|
| 7 | L1：能说清每卷的关键判据 | |
| 8 | L2：能复现至少三篇算例的数字 | |
| 9 | L3：能为一类新问题给出做法与依据 | |
| 10 | L4：六维验收全部通过 | |

如果第 10 项填不出来，说明还没到 L4 —— 这正是"毕业标准"这个标题的意思。

**这一篇只要记住一句**：这门课的终点是一个能通过六维验收的 harness，而每一维都要给出你跑出来的数字——安全是硬约束，可观测与可扩展最容易被低估，而"参数说不出依据"就等于没有掌握。

## 六、练习

### 第一题：为你的系统定验收目标

要求：

- 为六个维度各写一个目标值（含依据）。
- 说明哪一项是硬约束（不可权衡）。
- 指出哪一项你现在最弱，以及最便宜的改进方式是什么。

---

### 第二题：写一个验收检查脚本

要求：

- 用代码写出至少两类检查（功能与故障注入）。
- 故障注入至少包含三类（限流、超时、进程被杀）。
- 说明每类检查的通过判据。
- 指出这套检查在什么情况下会给出假通过。

---

### 第三题（进阶）：证明你到了 L4

要求：

- 逐项填写第五节的十项自评，每项给出可验证的证据。
- 对其中三项，说明你的参数是**怎么反推出来的**（而不是抄的默认值）。
- 指出你的系统与验收标准差距最大的一项，并给出改进计划与预期收益。
- 说明如果要把这个 harness 交给别人接手，你需要额外补什么（提示：见 4.7）。

## 一、这份作业要求你做什么

第 1 卷不写 harness，它的全部内容是从真实代码里读出判断。因此这一章的作业也以分析为主，只有最后一份是构建型的。五份作答训练的是同一件事的五个侧面：一次改动会波及什么（1.1）、这些波及的成本用什么度量（1.2）、怎么从代码里把结构读出来（1.3）、那个被波及的东西承诺了什么（1.4）、以及什么样的状态是可回滚的（1.5）。

**能不能跳过。** 不能，但可以调整顺序。1.1 与 1.2 训练"预测代价"，它们依赖你的工作经验而非这份代码，如果你已经维护过一个有历史的系统，这两份作答会快很多。1.3 与 1.4 必须做，因为它们训练的是"从材料里读出约束"这项技能，而第 2 卷的每一篇都在用它。1.5 是唯一一份写代码的作业，它同时也是 1.4 的验证——只做过分析的人会讲得头头是道但没写过，只写过的人会写得出来但说不清为什么，两份都做才能合上。

**为什么五份放在一个工作区。** 它们共用同一批工具、同一份报告、同一套跑法。更重要的是，判断力不是五个独立技能，而是同一件事的五个侧面，分成五个工作区会让人以为它们是五门课。

## 四、Part A（1.1）：预测一次改动的波及面

**目标。** 用一个你亲手做过或维护过的功能，把它的一生走一遍，并判断它的改动属于哪一级可逆性。

**动作。** 从模板复制作答：`copy kit\problems\a1-lifecycle.template.md kit\answers\a1-lifecycle.md`，然后按五节依次填写：选定功能、十站模型（每站留下什么材料）、三类信息损失、可逆性分级、以及"如果你是评审者会拦在哪一站"。讲义对应小节是 1.1 的十站模型与可逆性分级两节。

填写时有两条硬要求。第一，十站那一栏的"留下了什么材料"必须写到具体形式（一份文档、一次提交、一个工单、一次口头决定），因为后面所有判断都建立在这些材料上；如果某一站写不出材料，就如实写"没有"，那本身就是发现。第二，"如果你只看到第 3 站的材料能不能预判后面的问题"这一问必须给出判断，答不上来说明第 3 站的材料不够，而这也是发现。

**检查点。** 你应当看到 `kit/answers/a1-lifecycle.md` 里不再有 `← 在这里写`，且文件长度明显超过模板；跑 `node tests/run.mjs`，末尾的 notes 项从 `0/2` 变成 `1/2`。

**卡住时的提问。** 不知道选什么功能，看 1.1 开头对"好的选择"的描述（有一次明确改动、留下了可观察后果）。分不清可逆性等级，问"撤销它需要动什么"（删文件、回滚一次提交、修数据、还是无法撤销）。想不出信息损失，看讲义里三类传递（需求到方案、方案到代码、代码到使用）各自会丢什么。

**完成判据。** notes 计分项通过，且你能不翻讲义讲出十站的顺序与每一站的材料形态。

## 五、Part B（1.2）：把"感觉复杂"变成数字

**目标。** 对一个真实模块给出三组可测量的数字，并判断身边的一笔技术债是必要的债还是在付利息的债。

**动作。** `copy kit\problems\a2-debt.template.md kit\answers\a2-debt.md`，然后按五节填写。第一节要求先给数字再给判断，顺序反了就会变成先有结论再找证据；三组维度分别是体量（行数、导出符号数、最大函数行数）、连接（扇入、扇出、跨目录依赖数）、变化（最近三个月的改动次数、平均涉及文件数、有没有一次改动碰了五个以上文件）。第二节找一笔债，写清它怎么形成的、利息表现在哪一次具体操作上、还它要多久与由谁承担。第四节要求凭记忆写出讲义里那个反直觉的结论并说明你是否同意。

度量要用命令取数，不要目测。行数与导出数用 `rg -c` 与 `Select-String`；扇入扇出用预置工具 `node kit\tools\depgraph.mjs --repo D:\dsh-mini --module kernel\session.ts`（不带 `--module` 时它输出全仓诊断，带 `--json` 输出机器可读结果）；改动频率用 `git log`——`D:\dsh-mini` 若没有 git 历史，就用文件的最近修改时间代替，并在作答里说明你的替代口径。

**检查点。** notes 项变成 `2/2`；你的每个数字都能回答"怎么测的"这一栏；第二节的"利息表现"写的是具体操作（例如"每次加一个字段要改三个地方"），而不是"代码不优雅"。

**卡住时的提问。** 不知道选哪个模块，选一个你改过两次以上的。算不出改动频率，用文件的最近修改时间排序取变化最快的那几个。判断不了债的性质，问"借钱时有没有约定还的时点"，没有约定而又每次都要绕它，那就是在付利息。

**完成判据。** 第二节的结论有数字支撑，且第四节的"反直觉一问"答案是凭记忆写出的（翻着讲义抄不算）。

## 六、Part C（1.3）：从源码读出结构与约束

**目标。** 不看文档，只用 `rg` 与源码，把一个模块的依赖、热点与不变量读出来；并自己写一条可运行的架构检查规则。

**动作。** `copy kit\problems\a3-architecture.template.json kit\answers\a3-architecture.json`，按五组键填写。判分口径写在 `tests/t3-architecture.mjs` 开头的注释里，动笔之前先读它——它会告诉你哪些依赖算数（例如只计算 `./` 与 `../` 的相对导入）、路径怎么归一、以及哪些项按集合相等比对。

第三组要求交一个自测脚本：`kit/scripts/check.mjs` 是搭好架子、写满引导注释的骨架，你只需要填三处标着 `TODO` 的地方（选一条规则、实现它、取消一行注释让它跑起来）。这一组还要交一次"抓到人为违规"的实际输出——做法是复制一份仓库、人为写进一行违规导入、跑脚本、确认它报警，然后删掉副本。

**检查点。** 跑 `node tests/t3-architecture.mjs --answers kit/answers/a3-architecture.json --verbose`，你应当看到第一组与第二组的题目由红变绿。注意起点并不为零：如 README 第七节记录的，`t3` 的若干小题标准答案是空集合，而集合相等会让空答卷白拿约 28 分，所以"分数上升"不是判据，"哪些小题由红变绿"才是。

**卡住时的提问。** 读不出不变量，去三个地方找（实现里的断言、`tests/` 里在测什么、README 里承诺了什么），三处都没有就是发现。不确定哪些依赖算数，读判分器开头的口径注释——它比任何建议都准确。`depgraph.mjs` 的输出看不懂，先只看它的第一层（谁 import 谁），不要一次看全图。

**完成判据。** `t3` 达到 90 以上，且你交的自测脚本真的报过一次警（输出里出现过 FAIL 与违规文件名）。

## 七、Part D（1.4）：读出承诺，判断破坏性

**目标。** 对 harness 的三个核心接口做一次契约审计，并判断一系列改动是否破坏性。

**动作。** `copy kit\problems\a4-contract.template.json kit\answers\a4-contract.json`。三组客观题分别考破坏性变更的判断（依据是"谁依赖了被改掉的那部分"，不是"改了什么"）、承诺的归类（行为、时序、错误、所有权，其中时序最容易被漏写）、以及术语。第四组是分析题，共 28 分，写在 `kit/writeup.md` 里而不是 JSON 里，按报告模板的节自评。

分析题的做法直接用讲义 L3 的审计清单：列出签名能表达的部分、对三类承诺逐条问"写清了没有"、为每条不变量找证据来源、最后对照"承诺"与"谁有能力兑现它"找出信任型契约。第三个接口（会话事件契约）是这三者里最特殊的，它的使用者包括尚未写出的代码。

**检查点。** 跑 `node tests/t4-contract.mjs --answers kit/answers/a4-contract.json --verbose`，三组分数应当逐步上升；`node tests/run.mjs --only t4` 能看到折算后的得分。报告里应当至少有两条不变量，且四类证据（断言、测试、文档、都没有）中至少有一条是"都没有"——如果没有，回看第十二节第三条。

**卡住时的提问。** 判断不了某个改动是否破坏性，问"谁依赖了被改掉的那部分，他会怎么坏"。分不清承诺属于哪一类，问"使用者需要在什么时刻知道它"。找不到信任型契约，问"这条承诺，实现方有能力保证吗"——答"只能相信写的人"就是。

**完成判据。** 三组客观题达到 90% 以上，且你能指认出至少一处信任型契约并说出"限制能力而不是加校验"的修法。

## 八、Part E（1.5）：按契约实现一个可回滚的状态容器

**目标。** 在只有契约、没有实现的情况下，写出一个 `BoundedMemory`，并让它经得起重复测试。

**动作。** 读 `kit/CONTRACT.md`，然后在 `kit/src/memory.mjs` 里实现它。契约里有六节需要逐句读：行为承诺（六个方法与 `Entry` 的形状）、时序承诺（不是并发安全的、`remove` 后容量立即释放、`merge` 不能让容量更紧、`list` 返回快照）、错误承诺（五种失败各自的错误类型，且必须是可被 `instanceof` 判断的导出类）、不变量（五条，其中第四条与第五条的差别是"数组是副本"与"元素也是副本"）、以及明确声明为"不属于承诺"的四项。

**检查点。** 三个层次，按顺序做。

```powershell
node tests/t5-build.mjs                                          # 你的实现
$env:IMPL='../grade/memory.reference.mjs'; node tests/t5-build.mjs; Remove-Item Env:\IMPL   # 参考答案
node grade/negative-check.mjs                                     # 判分器的鉴别力
```

第一步看每个用例重复三十次后的成功率（见第十一节），第二步确认参考答案拿满分——如果它拿不到满分，问题在判分器而不在你的实现，这是一个可以被排除的变量；第三步确认四种违规实现都被抓住。

**卡住时的提问。** 不确定某个行为算不算承诺，看契约第六节是否把它明确排除了。不确定错误类型怎么写才对，看契约里"必须能被 `instanceof` 判断"那一段。`merge` 的容量语义想不通，问"合并之后条目数变多了还是变少了"。不确定要不要做深拷贝，看不变量的第四条与第五条。

**完成判据。** 三十次运行的成功率接近 100%，且 `CONTRACT-NOTES.md` 里指出了至少两处"最容易读漏"的位置——如果你觉得契约写得很清楚没有歧义，那多半说明没有真正逐句读它。

## 十一、鲁棒性与重复运行

第 1 卷的作业里只有 `t5` 是构建型的，而它要求**每个用例重复运行三十次**，成功率要接近 100。这条要求不是形式主义，它对应一个真实的工程判断。

顺序执行一次的测试无法区分两件事：你的实现是对的，还是它这一次恰好没暴露问题。有界容器的实现里有一类缺陷只在特定顺序下出现，例如删除后忘记释放容量、或合并时先移除旧条目再检查容量。这类缺陷在单次运行中通过的概率很高，而在真实使用中会在某个特定序列上失败——那时你面对的是一次偶发故障，而不是一个可复现的失败。

同一条道理也解释了为什么 `grade/negative-check.mjs` 必须存在：一个只会在正确答案上给满分的判分器与没有判分器等价，你必须亲眼看到它把四种错误的实现判为失败，才能相信它在判你的实现时是有判断力的。

**报告里要记下你实际运行的结果**（次数、成功率、以及失败时是哪一条用例）。如果三十次里有失败，不要重跑一次看它是否消失——把它记下来并找出顺序依赖，那才是这一节要训练的东西。

## 十二、你会怎么想错

**第一条：你会把"多写一点"当成更保险。** 在 1.3 的依赖题上，多列一个依赖得到的不是"更完整"，而是更低的分数，因为判分器同时惩罚漏报与误报。它的理由不是苛刻，而是一个真实的能力差别：多写一个依赖会让你基于一个不存在的依赖做出判断，而在真实工作里这类错误会让你做无用的改动，或者在一个其实无关的地方找问题。遇到这类题时，判据不是"它看起来有关"，而是"它是否真的被依赖了"。

**第二条：你会用感觉代替测量。** 1.2 要求先给数字再给判断，而这个顺序会让人不舒服，因为大多数人对一个模块的复杂度早就有印象了，填写数字看起来像在浪费时间。但"感觉复杂"无法比较两个模块，也无法说明它复杂在哪里；而三组数字可以立刻回答"该重构哪一个"。如果你发现自己在给数字之前就已经写下了结论，回看第一个数字是怎么来的。

**第三条：你会在找不到"无证据的不变量"时认为代码写得好。** 报告模板第二节要求你标出一条"三类证据都没有"的不变量。多数人第一次做时会一条都找不到，并把结论写成"这个模块的约束表达得比较完整"。更可能的解释是读得不够深：不变量藏在三处（实现里的断言、`tests/` 里在测什么、README 里承诺了什么），而这三处要主动去找，不会自己出现。找不到就再读一遍实现的写入路径，看哪个关系在所有分支上都必须成立——那通常就是一条没有任何断言守护的不变量。

## 十三、荣誉守则

允许用 LLM 问概念与低级编程问题（例如"JavaScript 的私有字段语法是什么"、"`instanceof` 在跨模块时为什么可能失败"），也允许与同学讨论思路。不允许让它直接产出你的作答、你的实现、或你的报告——这三样都是这份作业的判据本身。建议在做这份作业时关闭编辑器的自动补全，因为判断训练与补全的直觉相反：补全会替你完成"接下来该写什么"，而这份作业要问的正是"接下来该写什么，为什么"。

参考答案在 `grade/` 里，随时可看。看过之后你仍然可以重做，但你失去的是"我原来怎么想的"这条记录——而它的价值比正确答案高。如果实在想看，先把你的猜测写进 `writeup.md` 再去看。

## 十四、时间预算与检查点节奏

建议分五次做，每次对应一个 Part，两次之间至少隔一天。这个节奏不是日程安排，而是记忆设计：判断力依赖即时反馈，隔得越久反馈效力越低，但同一件事间隔一天再看一遍，效果比连续做三遍好。

| 时间 | 做什么 | 它为什么在这个时点 |
|---|---|---|
| 第 1 天 | Part A（1.1）＋ Part B（1.2） | 这两份不依赖仓库细节，适合作为起步 |
| 第 2 天 | 读 1.3，做 Part C | 依赖分析需要完整的注意力，不要放在一天末尾 |
| 第 4 天 | 读 1.4，做 Part D | 1.4 的结论要用到 1.3 的依赖读法 |
| 第 7 天 | 读 1.5，做 Part E 的第一轮实现 | 与 Part C 隔几天，让判分反馈沉淀 |
| 第 10 天 | 重跑全部判分，补报告 | 对比第 1 天与第 2 天的判断差异 |

**三个检查点。** 第一次跑 `node tests/run.mjs` 看到起点分数；`t3` 与 `t4` 双双过线；`t5` 的三十次运行稳定通过。卡住超过两小时不算失败，但请把卡点写进 `writeup.md`——它比分数更有信息量，因为它精确指出你的边界在哪。

## 十五、附录

### 附录 A · 环境故障排查

`node src/apps/verify.ts` 不通过时先修它，1.3 与 1.4 的判分都要读这份源码。`t3` 的 `--repo` 必须指向一份完好的仓库（默认 `D:\dsh-mini`），仓库残缺会让所有依赖题判错。若 `tests/run.mjs` 报找不到模块，检查当前目录是否是 `homework\ch01-judgment`。PowerShell 下设置环境变量用 `$env:IMPL='...'`，用完 `Remove-Item Env:\IMPL` 清掉，否则会影响后续命令。

### 附录 B · 只有三小时的最小路径

时间不够时按这个顺序做，它保证产出仍然可用：先做 Part D 的客观题（它权重最高，且只依赖 1.4 一节的阅读）；再做 Part C 的第一、二组（依赖与约束，判分器能自动核对）；然后补 Part A 的十站模型与可逆性分级两节（它们只需要你手上已有的工作经历）；最后如果还剩时间，做 Part E 的最小实现（`add`、`get`、`remove`、`list`、`size` 五个方法，先不管 `merge` 的容量语义）。跳过 Part B 的代价最小，因为它训练的是度量习惯，而那个习惯可以在别的时间补。

### 附录 C · 与毕业标准的对接

这一卷的作业会产出两组数字，它们直接进入《毕业标准》的差距分析（见 `kit/writeup.md` 第六节）。第一组是拓展性：Part C 的第二组要你算一次改动的波及面，把它填进"加一个能力改几处"这一栏。第二组是稳定性：报告第二节里"无证据的不变量"条数，就是"还有多少约束只存在于人的脑子里"的一个估计。这两组数字不需要精确，它们的用途是让你在后续卷次里有一个可对比的起点——第 3 卷与第 4 卷会各自再测一次，而三次之间的差值才是有意义的量。

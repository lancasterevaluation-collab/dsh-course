# 1.4 构建作业 · 按契约实现一个模块

> **这篇作业与 1.4 的分析型作业互补**：
> · 分析型（`homework/1.4/`）：**读别人的契约**，找出缺口与信任型声明。
> · 构建型（本篇）：**按契约实现**，并让你的实现经得起检查。
>
> **为什么两个都要**：只做分析的人会"讲得头头是道但没写过"；只做构建的人会"写得出来但说不清为什么"。**而 200 万档的岗位要求同时具备。**

| | |
|---|---|
| **产出** | `kit/src/memory.mjs`（实现）+ `CONTRACT-NOTES.md`（报告） |
| **目标级别** | L2（能按契约独立实现一个模块，并说明关键判断） |
| **预计用时** | 3–5 小时 |
| **前置** | 1.4 正文（契约的三类承诺、不变量、破坏性改动） |
| **约束** | **不许修改 `tests/`**；不许改 `CONTRACT.md`；只能改 `kit/src/` 下的文件 |

---

## 一、你要做什么

实现 **`BoundedMemory`**——一个有**容量硬上限**的记忆容器。

**它的契约在 `kit/CONTRACT.md`，那份文件是你唯一的依据。**

**为什么是"按契约实现"而不是"按需求实现"**：

| | 按需求实现 | **按契约实现** |
|---|---|---|
| 依据 | "做一个有上限的记忆容器" | **一份写清了行为、时序、错误、不变量、以及"不属于承诺的部分"的声明** |
| 你要做的 | 按常识猜 | **逐句读，并判断每一句的后果** |
| 判分 | 看像不像 | **看每一条承诺有没有被遵守** |

**这个差别就是 1.4 这一篇要训练的能力**——而它是**一篇正文教不会的**：你必须亲手实现一次，才会知道"契约里的一句话"在代码里意味着什么。

## 二、交付物与分值

**总分 100**，逐项给分：

| # | 判据 | 分值 | 它考什么 |
|---|---|---|---|
| **A** | 基本行为（add / get / size / list / remove） | 10 | 跑通 |
| **B** | ★ **满仓时失败，而不是丢弃最旧的** | **20** | 契约的核心立场 |
| **C** | `remove` 后容量立即释放 | 10 | 时序承诺 |
| **D** | ★ `merge` 在满仓时**不能**失败 | **15** | 时序承诺（最反直觉的一条） |
| **E** | 错误类型必须能被 `instanceof` 判断 | 15 | 错误承诺 |
| **F** | ★ 任意随机操作序列下 `size <= limit` | **15** | 不变量 |
| **G** | `list` / `get` 返回的是**深**副本 | 10 | 不变量（4 与 5 的区别） |
| **H** | `remove` 幂等（不存在时返回 false） | 5 | 行为承诺 |

**★ 标出的三项合计 50 分**——它们是"看起来对但实际违反契约"的高发区。

## 三、怎么判分

```
node tests/run.mjs
```

**判分的方式是跑 30 次，每次用不同的随机操作序列**（种子固定，可复现）。

**为什么是"跑多次"而不是"跑一次"**：**这个模块是确定性的**——所以跑多次不是为了测非确定性，而是为了**覆盖更多输入组合**。契约里的不变量必须在**任意**操作序列下成立，而"跑一次"只能覆盖一条序列。

**扣分是乘性的**（$\text{得分} = \text{分值} \times \text{成功率}^2$）：

| 成功率 | 线性 | **乘性（本作业）** |
|---|---|---|
| 100% | 满分 | 满分 |
| 90% | 90% | **81%** |
| 50% | 50% | **25%** |

**乘性扣分的理由**：**一个偶发失败在生产环境里就是事故**。这与 MIT 6.5840 的立场一致（"run the tests multiple times before submitting"）——**鲁棒性优于单次正确**。

**部分完成有分**：只做对 A–C 也能拿到 40 分左右。**不要因为做不完就放弃。**

## 四、常见失分点（不直接给答案）

以下是过去最常出现的六类错误。**它们都在契约里有对应的一句话**——**能不能自己找到那一句，就是这道题的核心训练**。

| # | 现象 | 契约里的哪一句管它 |
|---|---|---|
| 1 | 满仓时删掉最旧的那条 | 【二】的 `add` 行 |
| 2 | `merge` 时先检查容量，导致满仓无法合并 | 【三】的第三条 |
| 3 | `remove` 之后"用过的额度"没有还回来 | 【三】的第二条 |
| 4 | `throw new Error('容量满了')` | 【四】的第一行 |
| 5 | `list()` 返回 `[...内部数组]`（只复制了数组） | 【五】的不变量 5 |
| 6 | `remove` 一个不存在的 id 时抛错 | 【二】的 `remove` 行 |

**注意这张表不给代码**——它只指出"你应该去读契约的哪一句"。**如果你只照抄这里的描述而没读契约，D 与 G 两项仍然会失分**（因为契约里的表述比这张表更精确）。

## 五、报告要求（`CONTRACT-NOTES.md`）

**长度：400–800 字。** 它不是总结，而是回答三个问题：

1. **契约里哪几处最容易读漏？** 具体到你读第一遍时是怎么理解的、第二遍发现不对。
2. **你为哪几处做了"契约没规定"的判断？** 例如：如果同时"id 重复"且"已达上限"，应该抛哪个错误——**契约没有规定顺序**，你选了哪个、为什么。
3. **你实现的哪一处，在你看来"可能是过度设计"？** 以及为什么还是做了它。

**第 3 条是刻意的**：它训练的是"能说出自己方案的代价"——而这正是 200 万档面试要考的东西（**"我放弃了什么"**）。

## 六、评测机制（与另外两篇的关系）

```
   CONTRACT.md（唯一的依据）
        │
        ▼
   你的实现 ──► tests/run.mjs ──► 分数 + 失败分类
        │              │
        │              └──► ★ 失败分类告诉你"哪一类错"，
        │                    而修根因比逐个修有效（见 2.4.2）
        ▼
   CONTRACT-NOTES.md（你的判断记录）
```

**测试的鉴别力是被验证过的**：`grade/negative-check.mjs` 会从参考答案出发制造四个"看起来合理但违反契约"的变体（丢弃最旧、浅复制、merge 查容量、容量不释放），**并确认测试能把它们全部抓住**。

**这也是你可以自己跑的一个检查**：

```
node grade/negative-check.mjs
```

**如果它输出"4/4 个变体被正确抓住"，说明测试是可信的。** 反之——**如果测试抓不住这些变体，那说明是测试有问题，不是你的实现有问题**（这一点 6.5840 有明确教训）。

## 七、荣誉守则（借鉴 Stanford CS336 的做法）

CS336 直面了"学生一定会用 AI"这个现实，并给出了明确的边界。本作业采用同样的立场：

| 允许 | 禁止 |
|---|---|
| 用 AI 问**概念**（"`instanceof` 怎么工作"） | **用 AI 直接生成 `memory.mjs`** |
| 用 AI 问**低级编程问题**（语法、API） | 用 AI 生成报告的主体内容 |
| 与同学讨论**契约的理解** | 互相拷贝实现 |

**这条守则不是形式**：**这道题的全部价值在于"你自己读契约时踩了哪些坑"**。如果实现是生成的，那么报告里的第一条（"哪几处容易读漏"）就必然是编的——而**面试官会在追问里发现这一点**。

## 八、做完之后

跑一遍完整验证：

```
node tests/run.mjs                    # 你的实现
node grade/negative-check.mjs         # 测试的鉴别力（应 4/4）
IMPL=../grade/memory.reference.mjs node tests/run.mjs   # 参考答案（应 100/100）
```

三样都对上，说明：**你的实现符合契约、测试是可信的、参考答案确实能满分**。

**最后一步**：回到 `homework/1.4/` 的分析型作业，**用你实现时的体会，重读一遍 `CONTRACT.md`**——你会发现**同一份文件在读与写时的含义是不同的**。**这个差别本身，就是这一篇最重要的收获。**

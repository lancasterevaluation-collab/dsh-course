## 本篇新词

恢复（recovery） 指从磁盘上的持久数据重建出可以继续运行的状态。它与"重放"的差别在于它还要回答"上一次停在哪里"：重放只重建状态，恢复要判断中断点的性质。

重做（redo） 指把已提交但未反映到状态里的操作重新应用。撤销（undo） 指把未提交的操作回退。这一对概念来自 Gray 与 Reuter 的事务恢复，而它们的顺序在 ARIES 里被明确规定（先分析、再重做、最后撤销）。

检查点（checkpoint） 指一个"到此为止的状态已经被完整写出"的位置。它的作用是让恢复不必从日志的开头开始——这是把恢复成本从 O(全部历史) 降到 O(自上个检查点以来) 的唯一手段。

水位线（watermark） 指已应用的进度记录（2.7 已引入）。它与检查点的差别在粒度：水位线是"应用到哪一条"，检查点是"状态已经被物化"。前者用于增量重放，后者用于避免重放。

快照（snapshot） 指某一时刻状态的物化副本。它与检查点的区别是它可能会话级地独立存在（例如"把这条会话导出成一份文件"），而检查点只是恢复流程中的一个位置。

分段（segment） 指把日志切成多个文件。它的作用是让"归档旧部分"与"读取新部分"可以分别进行，代价是读取时要按顺序拼接多段，而拼接逻辑本身是一个新的出错点。

轮转（rotation） 指达到大小或时间阈值时切换到新文件。它与分段是同一件事的两个侧面（分段是结果，轮转是动作）。轮转的原子性是一个真实的难点：切换文件时崩溃可能留下两个半成品。

迁移（migration） 指把已有数据从一种格式变成另一种（1.5 已引入）。在恢复的语境下，它的特殊要求是恢复流程必须能读旧格式的日志——因为崩溃可能发生在迁移过程中间。

```
 一句话串起来：恢复读什么 → 怎么恢复 → 成本怎么压 → 残留与迁移怎么处理
```

这张图的关键线索在第三块：恢复的正确性由前两块决定，而它的可用性由第三块决定。一个每次都从头重放全部历史的恢复算法在正确性上没问题，而在百万条事件之后它的启动时间会让人放弃使用——"能用"与"可用"之间的差距就是这一篇后半部分的主题。

### 0.1 一个具体的判断：全量重放与检查点的差距

设一条长会话有 100 万条事件、每条解析与应用的耗时约 10 微秒，那么全量重放需要约 10 秒。而如果每 10 万条写一个检查点，那么恢复只需从最后一个检查点重放（约 10 万条，约 1 秒）加一次快照读取（假设 50 毫秒）。

这个量级差（10 秒对 1 秒）解释了检查点的必要性，而它的代价同样可算：每 10 万条写一次快照，写快照的成本与状态大小成正比（假设 5MB，写盘约 20 毫秒），因此检查点让正常运行多付出约 0.02% 的开销。这个交换在任何规模下都成立，因为检查点的成本是状态的函数，而全量重放的成本是历史总量的函数——后者随时间无上限增长。

### 0.2 本篇建立的三项判据

第一项用于判断恢复是否完整：问"哪些内存状态没有从磁盘重建出来"。判据由 1.5 的 1.1 给出（三类状态的划分），而这一篇给出它的检查方式：在恢复之后立刻比对一个已知的派生值（例如事件条数与最后一个顺序号）。

第二项用于判断恢复是否可用：问"最坏情况下要重放多少条"。答案应当在配置里有一个上限（例如十万条），超过它说明检查点间隔设置不当。

第三项用于判断残留是否被清理干净：问"上一次运行启动的进程还有活着的吗"。这条判据的检验方式与 3.4 相同——必须用外部工具观察，不能靠程序自报。

### 0.3 十分钟练习：尾部损坏的三种情形

下面这段代码用二十行枚举日志尾部可能出现的三种损坏形态。

```js
const cases = {
  '完整行': '{"seq":3,"type":"session/assistant","text":"ok"}\n',
  '半行（写入中断）': '{"seq":3,"type":"session/assist',
  '完整但类型未知': '{"seq":3,"type":"session/unknown-kind"}\n',
}
function classify(line) {
  try { JSON.parse(line) } catch { return '丢弃（尾部不完整）' }
  const obj = JSON.parse(line)
  if (!obj.type) return '丢弃（缺类型字段）'
  if (!KNOWN_TYPES.has(obj.type)) return '拒绝整份日志（未知类型且不可忽略）'
  return '接受'
}
const KNOWN_TYPES = new Set(['session/assistant', 'session/user'])
for (const [name, line] of Object.entries(cases)) console.log(`${name} → ${classify(line)}`)
```

三种情形的处置不同，而它们的区分依据是 2.7 的两条规则：解析失败意味着尾部不完整（丢弃），缺必填字段意味着写入实现有问题（丢弃并告警），未知类型意味着它是更高版本写的（默认拒绝整份日志，除非带可忽略标记）。把三者混为一谈的实现在前两种情形上表现为"日志少了几条"，而在第三种上表现为"读到一半报错"——正确性上都不致命，而诊断上会指向错误的方向。

> **面试视角**
> **高频问法**："崩溃恢复你怎么做？"
> **高分要点**：说出三步（分析、重做、撤销），并说明检查点的作用（把重放量从历史总量降到检查点之后）。只说"读日志重放"是常见的欠缺——它没有回答"重放多少"。

### 0.5.3 三个连锁影响

第一，恢复的正确性依赖"日志记录了全部影响状态的事实"，而这一点在加入新机制时容易被破坏。 每个新机制（重试、守卫、压缩、作业）都会产生新的状态，而如果它的状态只存在内存里，那么恢复之后它就不存在了——例如守卫的"本会话已批准的等级"如果不落盘，恢复之后所有危险操作会重新询问（可用性下降），而作业表如果不落盘，残留进程就无人认领。

第二，检查点把恢复成本从历史总量解耦，而它引入了一个新的失效方式：检查点本身损坏。 如果快照文件损坏，恢复只能回退到更早的检查点（或者从头重放）。因此检查点的写入必须是原子的（先写临时文件再改名），并且要保留前一个检查点——这条要求与 1.5 的"先写日志"是同一条原则在另一层的应用。

第三，迁移与恢复的组合会产生"中间格式"这个状态。 迁移进行到一半时崩溃，数据既不是旧格式也不是新格式（1.5 的 0.4 已经描述过）。在恢复的语境下，它的处置方式是迁移本身也必须先写日志：迁移进度与格式版本一起落盘，恢复时据此判断"这次迁移完成了多少，要不要继续"。

### 0.5.4 它与本书其余部分的关系

本篇的持久化是单机、单写者、文件系统的。它的结论在两类情形下不成立：多进程同时写需要单写者模型或锁；分布式存储需要复制与共识。两者都在本课程之外，而第 5 卷的多会话会触及第一个的边界（一个进程内多条会话的存储组织）。

> **面试视角**
> **高频问法**："你的系统崩溃后多久能恢复？"
> **追问方向**："最坏情况要重放多少？"落点是检查点间隔（它决定重放量的上界），并说明检查点的成本与收益之比。

## L0 要解决的问题

### 0.1 现象一：重启之后，状态对不上一部分

第一个现象的形态很具体：日志读出来了，消息数组重建了，而系统行为仍然与崩溃前不同。差别通常出在那些"只存在内存里"的状态上：守卫在本会话里已批准的等级、后台作业的进度、某个工具连接的当前状态、模型调用的累计用量。

它们的共同点是它们都是在崩溃之前"顺便"建立起来的，因此没有人觉得它们需要落盘。而恢复的定义（1.5 的 1.1 节）要求"内存中的每一项都能从磁盘重建"——按这个定义，只存在内存里的状态是恢复的缺口，而不是可以省略的细节。

### 0.2 现象二：启动越来越慢

第二个现象在长会话上出现：每次启动都从头重放全部日志，而日志随时间增长，于是启动时间线性上升。一条跑了一个月的会话可能有几百万条事件，而每次启动都要等十几秒——这个等待会让人倾向于不重启，而"不敢重启"是运维上的一个真实退化。

它的修法是检查点（0.1 的量化）：把"重放全部"换成"读快照加重放增量"。这里的判据是恢复时间的上界应当由配置给出（例如"任何情况下不超过三秒"），而它反过来决定检查点的间隔。

### 0.3 现象三：检查点损坏，而它没有备份

第三个现象是检查点自身的失效。快照写入过程中崩溃会留下一个半成品文件，而恢复流程若直接读它，会读到一份不完整的状态——比"没有检查点"更糟，因为不完整的状态不会报错，它只是让系统带着错误的状态继续运行。

修法有两条：原子写入（写临时文件，完成后重命名——重命名在多数文件系统上是原子的）与保留前一个检查点（恢复时若最新检查点不可读，回退到前一个）。两条合起来把"检查点损坏"从致命故障降级为"多花一点恢复时间"。

### 0.4 现象四：恢复之后进程互相冲突

第四个现象与 3.4 相接。上一次运行的残留进程（尤其是那些被取消但没被杀干净的）会与新启动的进程争抢同一个端口、文件或锁。表现是"启动失败，理由是资源被占用"，而那个占用者是一个已经没有对应任务的进程。

处置方式是把残留清理作为恢复流程的第一步，而不是一个可选的维护动作。它的顺序有意义：先清理，再重建状态——否则重建出的状态会与残留进程的行为交错，而那会产生无法解释的数据。

### 0.5 这一篇要正面回答的四个问题

第一，恢复要读哪些东西，它们各自的作用是什么（1.1）。第二，恢复的算法是什么（1.2）。第三，如何把恢复成本压到一个上界内（1.3）。第四，残留与迁移这两个"上下文"如何与恢复共存（1.4、1.5）。

四个问题里第二是这一篇的核心算法，第三是它的可用性保证，而第一与第四是它的输入与前提。

## L1 设计与原理

### 1.1 恢复读什么

恢复的输入有三样，而它们各自回答一个不同的问题。

日志回答"发生过什么"：它是权威状态（2.7），提供全部事实的序列。恢复的第一步是把它读进来（含尾部不完整的截断）。

水位线回答"应用到了哪里"：它是一个位置标记，让重放从中间开始。它必须与它所声明的进度在同一次写入中更新（2.7 的 1.6），否则会留下空洞。

检查点回答"状态曾经是什么"：它是物化的状态副本，让重放不必从头部开始。它比水位线更强：水位线只省去"应用"的工作，而检查点还省去"解析与计算"的工作。

三者的关系可以用一句话说明：日志是事实，水位线是进度，检查点是加速器。缺少日志时无法恢复；缺少水位线时每次全量重放；缺少检查点时重放量随时间增长。因此它们的必要性不同：日志是必须的，后两者是规模上来之后才必须的。

### 1.2 三步恢复算法

ARIES 给出的三趟结构在本课程的场景下可以简化，而三趟的分工仍然成立。

第一趟是分析。 从头（或从最后一个检查点）读日志，建立两张表：已提交的操作集合，以及未提交的操作集合。分析还要确定"重做应该从哪个位置开始"——它由检查点给出。

第二趟是重做。 把已提交的操作重新应用到状态上。这里的关键约定是重做是幂等的：同样的操作应用两次的结果与一次相同。这条约定让恢复可以在任意时刻被中断并重新开始（恢复本身也可能崩溃）。

第三趟是撤销。 把未提交的操作回退。在本课程的场景里，"未提交的操作"主要是两类：写入日志但未完成的状态迁移，以及"开始但没有结果"的工具调用（3.1 的 1.7 讨论过它的处置）。

```ts
export async function recover(store: SessionStore): Promise<RecoveryReport> {
  const { events, truncatedAt } = await store.readAll()          // 第一趟：读日志并截断尾部
  const committed = new Set(events.filter(isCommitted).map((e) => e.seq))
  const pending = events.filter((e) => !committed.has(e.seq))     // 未提交
  const state = await store.loadCheckpoint() ?? emptyState()      // 从检查点起步
  for (const e of events.filter((e) => isCommitted(e) && e.seq > state.lastSeq)) apply(state, e)  // 第二趟
  for (const e of pending) revert(state, e)                       // 第三趟
  return { truncatedAt, redone: events.length - state.lastSeq, reverted: pending.length }
}
```

这段实现里有两个要点与前面的分析对应。第一，`apply` 必须幂等（因为恢复可能被再次中断）。第二，`truncatedAt` 被返回而不是被静默忽略——恢复过程中丢弃了多少条尾部事件，是一个必须被报告的事实（它决定了"丢失了多少最近的记录"）。

### 1.3 检查点与增量重放

检查点的间隔是一个成本平衡：写检查点的成本与状态大小成正比，而重放的成本与间隔成正比。设状态大小为 `S`、每条事件的重放成本为 `r`、间隔为 `n`，那么每次检查点的成本约 `S` 的写入时间加固定开销，而两次检查点之间的重放成本上界是 `n × r`。

这个平衡给出两条实践规则。第一，间隔按"恢复时间上界"反推：如果要求恢复不超过三秒，而每条事件的重放成本是 10 微秒，那么间隔不超过约三十万条。第二，检查点应当写在与日志不同的文件里（否则一次损坏会同时毁掉事实与加速器）。

增量重放的另一个收益是它让"恢复"变成一个可以增量使用的操作：不只是崩溃后，正常启动时也可以用它（水位线告诉系统"状态已经到哪一条"，而新的日志只需要追加处理）。

### 1.4 残留清理

残留清理是恢复流程的第零步（0.4 的分析），而它的实现依赖 3.4 的作业表：读作业表、找出状态为运行中的作业、检查它们的进程是否仍存在且属于本系统。

清理的顺序有两个约束。第一，先清理再重建状态（0.4 已说明理由）。第二，清理必须报告它做了什么——杀了哪些进程、跳过了哪些（因为无法确认归属）。这份报告是排查"为什么某个进程还在跑"的唯一依据，而它必须是可查的（与 2.7 的"可查询"一致）。

### 1.5 迁移与恢复的组合

迁移进行到一半时崩溃会产生"中间格式"（1.5 的 0.4）。处置方式是把迁移本身也做成可恢复的：先写一条迁移开始事件（含源格式与目标格式），逐批迁移，每批完成后写进度，最后写迁移完成事件。

恢复时读到"有开始但没有完成"的迁移，它的处置有两个选择：继续迁移（向前恢复）或回退到旧格式（向后恢复）。选择依据与 1.5 的 1.3 一致——看哪一边的实现更可靠：如果迁移逻辑是幂等的且已被测试，那么继续迁移；如果回退更容易（旧格式仍然可读），那么回退。

这里有一条工程上的建议值得写下来：优先设计成"可继续"而不是"可回退"。理由是可回退意味着两套读代码必须长期并存（旧格式在迁移完成后仍然要能读，否则回退就不可用），而可继续只需要迁移逻辑幂等。

### 1.6 原子写与崩溃安全

所有对持久状态的写入都必须是原子的，否则崩溃会留下半成品。原子性的实现方式依赖文件系统的能力：写临时文件加重命名是最通用的一种（重命名在多数文件系统上原子），而它的要求是临时文件与目标在同一目录（跨目录重命名不保证原子）。

```ts
export async function atomicWrite(path: string, content: string): Promise<void> {
  const tmp = `${path}.tmp-${process.pid}`
  await writeFile(tmp, content, 'utf8')
  await rename(tmp, path)          // 原子替换
}
```

这段实现里 `process.pid` 出现在临时文件名里，用途是避免两个进程（或两次写入）使用同一个临时文件——没有它时，并发写入会互相覆盖临时文件，而结果是两份内容混合的产物。

日志的追加不需要原子写（它天然是追加，尾部不完整可被识别），而检查点与迁移进度需要——这正是本节与 1.3 的分工。

### 1.7 分段与轮转

日志的分段是为了让"归档旧部分"与"读取新部分"分开。它的实现要点在轮转的原子性：切换文件时崩溃可能留下两个半成品，因此轮转需要一条明确的规则——只有当新段的第一条事件写入成功之后，旧段才算关闭。

分段带来的额外复杂度有三处。第一，读取要按顺序拼接多段，而"顺序"需要一个可从文件名推断的规则（例如零填充的序号）。第二，跨段的读取边界容易出错（一条事件横跨两段是不可能的，因为写入以行为单位，而读取以段为单位）。第三，归档与删除的策略需要明确（旧段何时可以被删——依据是"还有没有恢复需要它"）。

本课程在第 3 卷不做分段（会话规模有限），而把它列为 L9 的一条缺陷——因为它的缺失意味着单文件的日志在极大时会遇到文件系统的限制与读取性能的下降。

### 1.8 两次追问

工程侧的问题是什么时候该做一次崩溃演练。答案是"每次改动涉及持久化或恢复时"，而演练的内容是固定的三步：在关键路径中间杀掉进程、重启、核对状态与不变量。这条演练不能自动化到"点一下按钮"的程度（因为它要真的杀进程），因此它的频率由改动频率决定，而不是由日程决定。

产品侧的问题是恢复对用户意味着什么。答案取决于丢失的东西：如果恢复之后只是少了几条最近的记录，那么用户需要被明确告知（"恢复了，最近两条消息可能丢失"）；如果恢复之后状态不一致，那么正确动作是拒绝启动并提示（宁可不可用，也不要带着错误状态运行）。这条选择的依据与 3.2 的超时默认一致：在不确定时选择保守的那一边。

---

### 1.9 崩溃演练的设计

恢复的正确性只有一种验证方式：真的杀掉进程。而演练的设计要点在于在哪些位置杀——不同位置暴露的缺陷类型不同。

请求中间（模型调用已发出、结果未收到）暴露的是"未提交操作"的处置：那次调用要不要重放（按幂等性判断），以及它在日志里留下什么。这个位置最常见的缺陷是"重放了一次非幂等操作"。

工具执行中间（工具已开始、结果未写入）暴露的是配对与撤销：那一次工具调用在恢复后必须有结果，否则消息序列不合法。这个位置最常见的缺陷是"恢复后序列缺一条结果"。

检查点写入中间暴露的是原子性：快照文件必须要么完整要么不存在。这个位置最常见的缺陷是"读到半成品快照"——而它的表现不是报错，是系统带着错误的状态继续运行。

三个位置之外还有一个组合位置：恢复过程中再杀一次。它验证的是重做的幂等性（L2 第 7 条）——如果重做不幂等，第二次恢复会把状态应用两遍。

演练不能自动化的原因在于它必须真的杀进程：用 mock 代替会跳过"进程被杀时磁盘上的状态是什么"这个问题，而那正是恢复要处理的。因此演练的频率由改动频率决定，判据是"每次涉及持久化或恢复的改动之后做一次"。

## L2 决策表

| # | 决策 | 我们的选择 | 替代方案 | 代价落在谁身上 |
|---|---|---|---|---|
| 1 | 权威状态的载体 | append-only 日志文件 | 数据库表 | 要自己实现读取与截断；换来格式简单可审 |
| 2 | 状态落盘的范围 | 全部影响后续行为的状态 | 只落消息数组 | 写入更多；换来恢复后行为一致 |
| 3 | 恢复的起点 | 最后一个检查点 | 日志开头 | 要维护检查点；换来恢复时间有上界 |
| 4 | 检查点间隔 | 按恢复时间上界反推 | 按事件条数定 | 间隔可能更小；换来恢复时间可承诺 |
| 5 | 检查点的写入 | 临时文件加重命名 | 直接覆盖 | 多一次重命名；换来不产生半成品 |
| 6 | 旧检查点 | 保留一个 | 只留最新 | 占用一份空间；换来最新损坏时能回退 |
| 7 | 重做的幂等性 | 必须保证 | 只保证一次成功 | 每个应用函数要多想一步；换来恢复可重入 |
| 8 | 撤销的范围 | 未提交的状态迁移与无结果的调用 | 全部未完成操作 | 撤销逻辑要区分类型；换来处置精确 |
| 9 | 残留进程清理 | 恢复流程的第一步 | 作为独立的维护动作 | 恢复稍慢；换来不与残留争抢资源 |
| 10 | 清理的报告 | 输出杀掉了哪些、跳过了哪些 | 静默清理 | 多一份输出；换来可排查 |
| 11 | 迁移的中断处置 | 优先"可继续"而不是"可回退" | 优先可回退 | 迁移逻辑要幂等；换来不必长期维护两套读代码 |
| 12 | 恢复失败时的动作 | 拒绝启动并提示 | 带着不一致状态继续 | 系统不可用；换来不产生错误数据 |

其中两条值得展开，因为它们的选择在实践中经常被做成另一个。

### 关于第 3 与第 4 条的完整论证（检查点为什么按时间反推而不是按条数）

替代方案是"每 N 条事件写一次检查点"，N 取一个经验值（例如十万条）。它的优点是与时间解耦（间隔的语义稳定），缺点是它没有回答"恢复要多久"这个问题——因为重放时间取决于每条事件的处理成本，而那个成本随事件的类型而变化（一条工具结果与一条状态迁移的成本相差很大）。

按恢复时间反推的做法是：先承诺一个恢复时间的上界（例如三秒），再用实测的单条重放成本（例如 10 微秒）反推间隔（约三十万条）。它的缺点是间隔会随事件类型分布变化（实测成本变了就要调），优点是它把"恢复时间"从一个观测值变成了一个承诺。

这条选择与 2.7 的步数上限、3.1 的次数上限、3.4 的超时是同一个方法：上限由分布决定，而分布由观测得到。它的一般形式是"先把要保证的性质写成一个数，再反推参数"，而不是"先设参数，再看它带来什么"。

### 关于第 7 条的完整论证（重做为什么必须幂等）

替代方案是"重做只在恢复正常结束时才执行一次"，也就是假设恢复过程不会被打断。这个假设在多数情况下成立，而在两种情形下不成立：恢复过程中再次崩溃（例如机器反复重启），以及恢复被并发触发（两个进程同时尝试恢复同一份日志）。

幂等性的实现要求有两处。第一，`apply` 函数必须能识别"这条事件已经应用过"——通常靠状态里记录的最后应用位置（`lastSeq`）来判断。第二，一旦涉及外部副作用（例如向外部服务发送消息），就必须有一个可去重的标识（3.1 的 1.5 讨论的幂等键）。

这条决策的代价落在每个 `apply` 函数的实现者身上：他必须多想一步"如果这条被应用两次会怎样"。而它的收益是恢复流程可以被安全地重试——在一个会崩溃的流程里，可重试是最基本的健壮性要求。

## L3 实现（施工图）

### 3.1 文件结构

```
// kernel/persistence.ts
// ┌─ 日志段 ── readAll（含尾部截断）/ append（2.7 的接口）
// ├─ 检查点段 ── saveCheckpoint（原子写）/ loadCheckpoint（含回退）
// ├─ 水位线段 ── 与应用进度同一次写入
// ├─ 恢复段 ── recover（分析、重做、撤销）
// └─ 清理段 ── 残留进程清理（读 3.4 的作业表）
```

五段的分工与 2.7 的日志段相接：日志段是复用，检查点与恢复段是新增，水位线段是对 2.7 那条约束的实现，清理段与 3.4 相接。

### 3.2 日志读取与尾部截断

```ts
export async function readAll(path: string): Promise<{ events: SessionEvent[]; truncatedAt?: number }> {
  const events: SessionEvent[] = []
  for (const line of readLines(path)) {
    let rec: SessionEvent
    try { rec = JSON.parse(line) } catch { return { events, truncatedAt: events.length } }  // 尾部不完整
    if (typeof rec.seq !== 'number') return { events, truncatedAt: events.length }           // 缺字段
    if (rec.seq !== events.length + 1) throw new Error(`顺序号跳号：期望 ${events.length + 1}，读到 ${rec.seq}`)
    events.push(rec)
  }
  return { events }
}
```

三处判断的差异值得说明：解析失败与缺字段都返回截断位置（它们是"尾部不完整"的两种形态），而顺序号跳号抛错——因为跳号意味着日志中间有缺口，那不是崩溃的正常结果，而是文件被外部修改过的信号。

### 3.3 检查点的读写

```ts
export async function saveCheckpoint(dir: string, state: Checkpoint): Promise<void> {
  await atomicWrite(join(dir, 'checkpoint.new'), JSON.stringify(state))       // 原子写入新检查点
  const old = join(dir, 'checkpoint')
  if (existsSync(old)) await rename(old, join(dir, 'checkpoint.prev'))         // 旧检查点降级为备份
  await rename(join(dir, 'checkpoint.new'), old)
}

export async function loadCheckpoint(dir: string): Promise<Checkpoint | null> {
  for (const name of ['checkpoint', 'checkpoint.prev']) {                      // 最新损坏时回退
    try { return JSON.parse(await readFile(join(dir, name), 'utf8')) } catch { /* 试下一个 */ }
  }
  return null                                                                  // 都没有则从头重放
}
```

这两段实现的三个要点：原子写入（1.6）、保留一份备份（0.3）、以及"都没有则返回 null"（恢复从日志开头开始，而不是失败）。

### 3.4 恢复段

```ts
export async function recover(store: SessionStore): Promise<RecoveryReport> {
  await cleanResidualProcesses(store.jobTable)         // 第零步：清理残留（3.4）
  const { events, truncatedAt } = await store.readAll()
  const checkpoint = await store.loadCheckpoint()
  const state = checkpoint ?? emptyState()
  let redone = 0, reverted = 0
  for (const e of events) {
    if (e.seq <= state.lastSeq) continue                // 已被检查点覆盖
    if (isCommitted(e)) { apply(state, e); redone++ }    // 重做（幂等）
    else { revert(state, e); reverted++ }                // 撤销
  }
  return { redone, reverted, truncatedAt, fromCheckpoint: checkpoint !== null }
}
```

`RecoveryReport` 的四个字段都是可观测的（3.6 会用到）：重做与撤销的条数说明恢复的工作量，`truncatedAt` 说明丢失的尾部，`fromCheckpoint` 说明是否用上了加速器。

### 3.5 验收判据

| # | 判据 | 怎么检查 |
|---|---|---|
| 1 | 尾部不完整行被截断且被报告 | 写入半行，核对 `truncatedAt` 有值 |
| 2 | 顺序号跳号时报错 | 手工删除中间一行，核对抛错 |
| 3 | 检查点原子写入 | 写入过程中杀进程，核对没有半成品的 `checkpoint` 文件 |
| 4 | 最新检查点损坏时回退到备份 | 损坏 `checkpoint`，核对从 `checkpoint.prev` 恢复 |
| 5 | 两个检查点都不可读时从头重放 | 删除两者，核对恢复仍然成功 |
| 6 | 重做是幂等的 | 对同一份日志连做两次恢复，核对状态相同 |
| 7 | 未提交的迁移被撤销 | 构造一条开始但无完成的迁移，核对状态回到迁移前 |
| 8 | 残留进程被清理且被报告 | 留下一个运行中的作业记录与进程，核对清理报告 |
| 9 | 恢复之后不变量成立 | 恢复后跑 2.7 的断言 |
| 10 | 恢复报告含四项字段 | 核对 `redone`、`reverted`、`truncatedAt`、`fromCheckpoint` |
| 11 | 从检查点恢复与从头重放结果相同 | 两种方式各恢复一次，核对状态逐字段相同 |
| 12 | 恢复过程中再次崩溃可重入 | 恢复中途杀进程再恢复，核对最终状态正确 |

第 11 条是这一篇最关键的一条：它验证"检查点没有改变语义"——检查点只是加速器，它的存在与否不应当影响恢复的结果。第 6 与第 12 条验证重入性，第 8 条验证与 3.4 的配合。

### 3.6 实现顺序

先做日志读取与截断（判据 1、2），再做检查点的读写与回退（判据 3、4、5），然后做恢复三步（判据 6、7、11），接着做清理与报告（判据 8、10），最后做重入与不变量验证（判据 9、12）。

### 3.7 实现里最容易写错的三处

第一处是重做的幂等判断。正确做法是用状态里的 `lastSeq` 跳过已应用的事件；错误做法是依赖"恢复只执行一次"这个前提。后者在两种情形下失效：恢复过程中再次崩溃，以及两个进程并发尝试恢复同一份日志。它失效的表现是状态被应用了两遍，而多数应用是幂等的（覆盖写），因此它只在涉及累计量（计数、追加）时才暴露。

第二处是检查点的重命名顺序。正确顺序是"写新文件 → 旧检查点降级为备份 → 新文件改名为正式"；错误顺序是"先把正式文件改名为备份，再写新文件"——后者在写新文件失败时会同时失去正式与备份（正式被改名了，而新文件没写成）。这条缺陷在磁盘空间不足或权限异常时暴露。

第三处是截断的报告。正确做法是把 `truncatedAt` 返回并记录；错误做法是静默截断。后者让"恢复时丢了几条"这个事实消失，而它恰好是用户最需要知道的（REST 的"最近两条消息可能丢失"那句提示就来自这个字段）。

## L5 语法速查

### 5.1 术语表

| 术语 | 在本篇里的准确含义 | 容易误解为 |
|---|---|---|
| 恢复 | 从持久数据重建可继续运行的状态 | "重放"（它还要判断中断点的性质） |
| 重做 / 撤销 | 重新应用已提交 / 回退未提交的操作 | "重试"（那是在运行期，与恢复无关） |
| 检查点 | 状态已被完整写出的位置 | "备份"（它是恢复流程中的一个位置） |
| 水位线 | 已应用到哪一条 | "检查点"（粒度与用途都不同） |
| 快照 | 某一时刻状态的物化副本 | "检查点"（快照可独立存在） |
| 原子写 | 写完或完全没写，不存在中间态 | "加锁"（原子性不依赖锁） |
| 分段 / 轮转 | 日志切成多文件 / 切换文件 | "归档"（归档是策略，分段是形态） |

### 5.2 命令速查

| 目的 | 命令 | 说明 |
|---|---|---|

### 5.3 三条容易踩的规则

第一条，重做必须幂等。恢复本身可能崩溃并重来。

第二条，检查点要保留一份备份。最新损坏时不至于从头重放。

第三条，清理残留进程是恢复的第一步。顺序反了会让重建出的状态与残留进程的行为交错。

## L7 挑战题（不给答案）

第一题：给恢复加"部分恢复"。 某些会话很长，全量恢复的等待不可接受。设计一个按需恢复（先恢复最近的部分、历史按需加载）的方案，并说明它对不变量的影响。

第二题：检查点的增量写。 每次写完整快照的成本随状态增长。设计增量检查点（只写变化部分），并说明它与恢复流程的配合。

第三题：多会话的恢复顺序。 一个进程里有多条会话，它们之间存在依赖（例如共享的资源池）。设计恢复顺序，并说明它如何避免资源争抢。

第四题：迁移的可继续与可回退并存。 说明在什么条件下两套读代码必须长期并存，以及这带来的维护成本。

第五题：恢复的可观测。 设计一组指标，回答"恢复是否在变慢"与"重放量是否在增长"。

第六题：跨版本的恢复。 日志由旧版本写入，而恢复由新版本执行，且两者的格式有三处差异。给出兼容方案并说明它的代价。

## L9 仍未解决（这一篇自己的缺陷）

| 缺陷 | 后果 | 修法 | 当初为什么这么写 |
|---|---|---|---|

### 五种提问模板

反例逼问：如果检查点不是原子写的，哪一条判据会失败。

边界追问：检查点间隔设到多大就不再有意义。

代价追问：把全部状态都落盘，代价落在谁身上。

替代对比：为什么用日志加检查点而不是直接用数据库。

验证追问：怎么证明"从检查点恢复与从头重放等价"。

### 本篇引出的十二个问题

读懂层。 第一，恢复要读哪三样，各自用途是什么？第二，三步算法分别做什么？第三，状态落盘的范围由什么决定？

重建层。 第四，为什么重做要幂等？第五，检查点为什么要保留备份？第六，原子写为什么能避免半成品？

设计层。 第七，检查点间隔如何反推？第八，残留清理为什么是第一步？第九，迁移中断为什么优先设计成可继续？

评审层。 第十，拿到一套恢复方案，你会先检查哪一处？第十一，怎么判断一次崩溃演练是有效的？第十二，如果有人说"我们的进程很少崩，不需要恢复机制"，你怎么回应？

### 问题升级练习

模糊问题：「我该怎么让系统崩了之后还能用？」

升级后的精确问题：

> 崩溃后可用至少包含三件互相制约的事：记什么（哪些状态必须落盘）、快不快（恢复时间的上界如何保证）、以及对不对（恢复之后状态与不变量是否成立）。
> 第一件与第二件互相制约——落盘的状态越多，检查点越大，而检查点的写入成本反过来限制了它的频率。
> 我能不能为这三件事各找出一条**可检查的判据**？
> 特别是：有没有哪一条判据，是**能在一次真的杀掉进程的演练里被验证的**？

提升点说明：原问题无法回答，因为"还能用"没有边界。升级后的版本把它拆成三件具体的事，指出前两件的制约关系，并追加以一个更强的问题：哪一条判据能在真杀进程的演练里验证。

一处需要修正的预判：0.5.2 把"水位线和增量重放"标为对 3.6 的强依赖。读完之后要补两层：它与检查点是两种不同粒度的加速器，而它们的适用场景不同——水位线用于"状态已物化但需要继续处理新事件"（常规启动），检查点用于"状态需要被重建"（崩溃恢复）。把两者混为一谈会导致一个具体问题：正常启动时做一次不必要的全量检查点读取。

通向下一篇的桥。 本篇让系统能崩溃后继续，而它留下了一个没有答案的问题：怎么知道它运行得好不好、贵不贵。恢复耗时、重放条数、检查点频率都是数字，而这一篇把它们列为"可观测"却没有给出观测方式。

下一篇 `3.6 可观测：token、延迟、成本、缓存命中` 处理这件事，它是第 3 卷的收口，也是"面向 DeepSeek 优化"这项课程要求的落点。它与本篇的连接点是明确的：恢复的四个报告字段（重做、撤销、截断、是否来自检查点）正是它的第一批指标，而缓存命中率这个指标会反过来要求本篇的日志结构保持前缀稳定。

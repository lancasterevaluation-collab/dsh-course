## 本篇新词

可观测（observability） 在本课程里指从已有数据（日志）回答运行问题的能力。它与"加日志"的区别是那些日志是否被组织成能回答具体问题的形状——一道无法回答"这轮花了多少"的日志，在可观测的意义上等于没有记录。

度量口径（metric definition） 指一个指标的计算方式：分子分母各是什么、时间窗口多长、异常值怎么处理。口径不清时，同名的指标会有多个值，而讨论会变成各自引用自己算的数。

前缀缓存（prefix caching） 指服务端把请求的前缀部分缓存起来、下次遇到相同前缀时跳过计算的机制。它的收益取决于前缀在两次请求之间是否相同，因此它把"上下文如何组装"这件事变成了一个直接影响成本的设计问题。

缓存命中率 指命中缓存的输入 token 占输入 token 总数的比例。它是一个派生指标：由每次请求的 `cachedPromptTokens` 与 `promptTokens` 算出。

成本归因（cost attribution） 指把总成本分摊到具体的请求、会话、任务或工具上。它的判据是"能不能回答'这个功能的成本是多少'"——而这需要每条成本都带着归属信息（哪条会话、哪个任务）。

延迟分解（latency breakdown） 指把一次调用的耗时拆成几段（排队、首 token、生成、重试等待）。它的必要性来自一个事实：总耗时相同而构成不同的两次调用，优化方向完全相反。

分布而不是平均值 指用分位数（P50、P95、P99）而不是均值来描述一组测量。它的理由是均值会被长尾掩盖：一百次一百毫秒与一次十秒的平均值仍是两百毫秒，而用户的体验由后者决定。

饱和度（saturation） 指一个资源被使用的程度（连接池占用、并发槽位、上下文窗口占用）。它是四个黄金信号里唯一"在故障之前就有信号"的一个——其余三个都在故障发生时才有变化。


这张图的关键线索在第三块：缓存命中率是这四个问题里唯一与前缀设计直接相关的。前两个问题只要记录就能回答，而第三个问题会反过来要求设计——它要求上下文的组装方式保持前缀稳定，而那是一个跨越 2.7 与 3.3 的设计约束。

### 0.1 一个具体的判断：命中价与未命中价的量级差

DeepSeek 的上下文硬盘缓存把输入 token 分成两档计费：命中缓存的部分与未命中的部分，而前者的单价明显低于后者（量级上差数倍到十倍，具体数字随模型与时间变化，应查当时的官方文档）。另有一档是缓存写入（存储）的费用。

这个量级差给出两条直接推论。第一，命中率是成本的一等影响因素，而不是一个次要的优化指标——一次长会话里输入 token 占绝大多数，因此命中率从零变到八成就可能让成本降几倍。第二，命中率取决于前缀是否逐字节相同，因此"上下文的组装顺序"这件事有了经济含义：把变化的部分（例如当前时间戳、随机 id）放在前面会让整段前缀失效，而把它们放在后面则不影响前缀。

第 2.7 篇要求"模型可见的必须可重建"，这一篇的补充是：组装的顺序也应当被固定下来——因为顺序会影响成本，而它本身也是一个会被依赖的性质。

### 0.2 本篇建立的三项判据

第一项用于判断一道指标是否可用：问它能不能回答一个具体的决策问题（"这个功能该不该留"、"这段提示词该不该改"）。答不上的指标是装饰，而它们会消耗维护成本。

第二项用于判断成本记录是否完整：问"能不能算出某条会话或某个任务的总成本"。这要求每条成本记录带着归属（会话 id、任务 id、工具名），而不只是记在总量上。

第三项用于判断缓存策略是否有效：问"前缀在两次请求之间变了多少"。变化的来源通常是时间戳、随机 id、以及随轮次增长的字段位置——它们都能通过调整组装顺序被消除。

### 0.3 十分钟练习：算一次请求的实际成本

下面这段代码把三档单价放进一次成本计算。

```js
// 单价按量级示例（实际数字以官方文档为准，且随模型变化）
const price = { missPerMTok: 2, hitPerMTok: 0.2, outPerMTok: 8 }   // 元/百万 token，仅作量级示例

function costOf({ promptTokens, cachedPromptTokens, completionTokens }) {
  const miss = promptTokens - cachedPromptTokens
  return {
    miss: (miss / 1e6) * price.missPerMTok,
    hit: (cachedPromptTokens / 1e6) * price.hitPerMTok,
    out: (completionTokens / 1e6) * price.outPerMTok,
  }
}
const round = { promptTokens: 40000, cachedPromptTokens: 0, completionTokens: 500 }
const cached = { promptTokens: 40000, cachedPromptTokens: 32000, completionTokens: 500 }
console.log('命中率为 0：', costOf(round))
console.log('命中率为 80%：', costOf(cached))
```

两次输出的差别说明命中率的作用：输入 token 总数相同，而成本相差数倍。这条练习的结论是"命中率是一个成本参数"，而它接着给出下一篇的设计要求：把不影响模型判断的内容（时间戳、随机 id）放到前缀之后。

> **面试视角**
> **高频问法**："你怎么控制 agent 的成本？"
> **高分要点**：说出三档计费（未命中输入、命中输入、输出），并指出命中率取决于前缀稳定性——因此成本控制的一部分是"上下文组装顺序"的设计，而不只是"少发内容"。

### 0.5.3 三个连锁影响

第一，没有度量时，前五篇的机制无法被验证。 重试是否在放大拥塞、压缩是否真的省了钱、守卫的审批是否过多、恢复是否在变慢——这五个问题都只能靠数字回答。没有度量时它们的默认状态是"看起来在工作"，而"看起来在工作"与"确实在起作用"之间的差距，在成本与稳定性上是可观的。

第二，度量本身会改变行为，而这是它最有价值也最危险的一面。 一个被度量的指标会成为优化目标（古德哈特定律：当度量成为目标，它就不再是好的度量）。例如"步数"被度量之后，实现者会倾向于让任务用更少的步数结束（包括提前放弃），而那不是原来的目的。处置方式是每个指标都配一个护栏指标（步数配任务成功率），并定期检查它们的相关性。

第三，缓存命中率把"上下文组装"从一个实现细节变成了设计问题。 这是本篇最具体的后果：两份在语义上等价的历史，如果组装顺序不同，成本可能相差数倍。它要求组装逻辑有明确的规定（哪些内容在前、哪些在后、变化的部分放哪里），而这条规定需要在第 2.7 篇的不变量之外单独成立。

### 0.5.4 它与本书其余部分的关系

本篇的度量是单进程、单机的。多机场景下的度量需要聚合与采样（第 5 卷的规模化会触及），而分布式追踪（trace）不在本课程范围内。这个边界意味着本篇的结论在"同一进程内的成本与延迟"上是完整的，而在"跨服务的调用链"上只覆盖了本进程发起的那一段。

> **面试视角**
> **高频问法**："你怎么知道你的优化有效？"
> **高分要点**：说出"先定口径、再看分布、最后配护栏"这三步，并给一个具体的例子（例如压缩的净省 token 与任务成功率的对比）。只说"看指标下降了"是不完整的——它没有回答"这个下降有没有带来副作用"。

## L0 要解决的问题

### 0.1 现象一：一轮跑了多少 token、花了多少钱，答不出来

第一个现象是最常见的：系统能跑，日志里也有一堆消息，而"这一轮花了多少"这个问题没有答案。原因是 token 计数只在响应的 `usage` 字段里出现过一次，而它既没有被持久化，也没有被按会话聚合。

它的后果在三个场景里显现。第一，成本失控时无法定位是哪类任务、哪条会话、哪个工具造成的。第二，优化无法被验证——改了一段提示词之后成本是升是降，没有数据可比较。第三，预算无法被管理：不知道当前单价下的消耗速度，就无法在超支之前采取措施。

### 0.2 现象二：一次调用花了八秒，而优化方向完全不明

第二个现象是延迟的不可分解。总耗时八秒这个数字本身没有指引——它可能是排队等了六秒、首 token 等了一秒、生成用了半秒，也可能是重试了两次各三秒。三种构成的优化动作完全不同（加并发、换模型、减少重试），而一个只有总数的度量无法区分它们。

这条现象的修法是延迟分解（1.4），而它的实现要求在每个阶段结束时记录时间戳——这件事必须在实现时就做，事后无法从总数里恢复。

### 0.3 现象三：命中率无从得知，而它的量级影响成本

第三个现象在长会话里最明显。前缀缓存本来应当让重复部分的成本降到更低档，而系统既没有记录 `cachedPromptTokens`，也没有计算命中率——因此"我们有没有享受到缓存"这个问题没有答案。

它的后果不只是少省了钱：前缀不稳定时会有一个反直觉的现象——系统看上去在正常工作，成本却是稳定状态的数倍，而没有任何信号指出原因。0.1 的练习给出了量级（命中率从零到八成，输入成本相差数倍），因此把 `cachedPromptTokens` 记录下来并把命中率算出来，是这一篇里性价比最高的一件小事。

### 0.4 现象四：口径不清，同一个指标有两个值

第四个现象是协作问题。两个人都统计"平均每次任务成本"，而一个人按会话算、另一个人按任务算；一个包含重试、另一个不包含。于是讨论变成各自引用自己算的数，而结论无法推进。

口径不清的危害不止于争论：它让指标失去可比性，因此跨时间的对比（这周比上周贵了多少）也不成立。修法是把口径写成定义（分子、分母、窗口、包含什么），而这与 1.4 的契约是同一条原则——一个会被多人使用的量，必须有明确的定义。

### 0.5 这一篇要正面回答的四个问题

第一，四个度量分别是什么、从哪里来（1.1）。第二，成本如何计算、它由哪几档构成（1.2、1.3）。第三，延迟如何分解（1.4）。第四，缓存命中取决于什么、如何提高（1.5）。

四个问题里第四是唯一"会反过来要求设计"的：前三个只要记录与计算，而第四个要求上下文组装有规定——这也是本篇放在第 3 卷末尾的原因（它要用到前面全部关于日志与压缩的结论）。

## L1 设计与原理

### 1.1 四个度量与它们的来源

本课程要求四个度量，而它们的来源全部是 2.7 的日志（不需要额外的埋点设施）。

| 度量 | 口径 | 来源 |
|---|---|---|
| token | 每轮与每条会话的输入、输出、缓存命中三类计数 | 模型响应事件里的 `usage` |
| 延迟 | 每轮的总耗时，以及分解后的排队、首 token、生成、重试等待 | 请求与响应事件的时间戳差 |
| 成本 | 按三档单价算出的金额，可归因到会话与任务 | token × 单价 |
| 缓存命中率 | 命中输入 token 占输入 token 总数的比例 | `cachedPromptTokens / promptTokens` |

四行里最有价值的一点是来源单一：它们都从日志派生，因此不需要维护第二套数据通路。这条性质与 2.7 的"派生可重算"一致——如果某个度量需要额外的埋点，说明日志里缺了某类事件，正确的做法是补事件而不是加通路。

### 1.2 token 计数的三档

模型响应的 `usage` 提供三类计数：输入总 token、其中命中缓存的 token、以及输出 token。前两者的关系是包含关系（命中是输入的一部分，而不是并列的一类）。

```ts
interface LLMUsage {
  readonly promptTokens: number          // 输入总数（含命中部分）
  readonly completionTokens: number      // 输出
  readonly totalTokens: number
  readonly cachedPromptTokens?: number   // 其中命中缓存的部分（可选：不是所有实现都提供）
}
```

`cachedPromptTokens` 之所以是可选字段，理由在 2.1 已经讨论过：不同实现能提供的 usage 不同，而契约要求消费者处理缺失——因此计算成本时必须把它的缺失当成零命中，而不是让整个计算失败。

一个容易搞错的地方是输出的 token 不区分命中（缓存只作用于输入前缀），而这一点在某些实现里表现为"输出没有缓存字段"，容易被误读成"输出不计费"。

### 1.3 成本的算法

成本是三档的加权和：未命中输入、命中输入、输出，各自乘以其单价。单价是配置（它随模型与时间变化），而计算是派生（它在每次请求后就能算出来）。

三档之外还有两处常被忽略的项。第一是缓存写入（存储）的费用——它通常在首次填充缓存时产生，因此"冷启动"那一次比后续更贵。第二是失败请求的费用：被限流或超时的请求通常不计费，而被接受但后续失败的请求可能已经计费。把这两项算进去，成本才与实际账单对得上，而只有与账单对得上时，成本度量才有资格被用来做决策。

```ts
function costOf(usage: LLMUsage, price: PriceTable): Cost {
  const miss = usage.promptTokens - (usage.cachedPromptTokens ?? 0)   // 缺失当成零命中
  return {
    missInput: (miss / 1e6) * price.missPerMTok,
    hitInput: ((usage.cachedPromptTokens ?? 0) / 1e6) * price.hitPerMTok,
    output: (usage.completionTokens / 1e6) * price.outPerMTok,
  }
}
```

### 1.4 延迟分解

延迟分解要求把一次调用拆成四段：排队（等并发槽位）、首 token（服务端开始响应的时刻）、生成（从首 token 到结束）、以及重试等待（3.1 的退避时间）。四段的含义不同，而它们的优化动作也不同。

| 段 | 含义 | 优化动作 |
|---|---|---|
| 排队 | 本地或服务端的并发受限 | 提高并发或减少并发请求 |
| 首 token | 服务端的预填充时间（受输入长度与缓存命中影响） | 压缩输入、提高命中率 |
| 生成 | 输出 token 的生成时间（与输出长度成正比） | 减少输出、换更快的模型 |
| 重试等待 | 失败后的退避 | 降低失败率、调整退避策略 |

这张表里第二行与前两节直接相连：首 token 的时间与输入长度和命中率有关，因此压缩与缓存优化会体现在这一段上。这也是为什么"延迟分解"必须与 token 度量放在一起看——单独看任何一个都无法判断"慢"的原因。

### 1.5 缓存命中的条件

前缀缓存命中的条件是前缀逐字节相同。这件事给出三条可执行的规则。

第一，把稳定的内容放在前面：系统提示、工具定义、以及那些在整个会话里不变的部分。第二，把变化的内容放在后面：当前轮次的消息、当前时间、随机的会话 id。第三，不要在稳定的内容里嵌入可变值：例如把"当前时间"插进系统提示，会让整个系统提示的缓存失效——而它恰好是最常被复用的那一段。

第三条是最容易犯的错误，而它的形式往往很隐蔽：一段提示词模板里包含`${date}`，看起来只是一句信息，实际它让每一次请求的前缀都不同。检查方法是问"这段文本在两次请求之间会变吗"，而它可以用一条命令验证（取两次请求的前缀做字节比较）。

### 1.6 分布而不是平均值

四个度量都应当以分布的形式呈现，而平均值只作为摘要。三条理由。

第一，均值被长尾掩盖：一百次一百毫秒与一次十秒的均值是两百毫秒，而用户的体验由后者决定。第二，不同的分布可能有相同的均值：两个版本的均值相同而 P99 差三倍，而尾部才是故障的来源。第三，分位数是可承诺的："P95 延迟低于两秒"是一个可以被检验的承诺，而"平均延迟低"不是。

实践中的做法是记录每个请求的原始值（它们已经在日志里），然后按需计算分位数。这比对每个请求预先计算分桶更灵活，代价是计算需要扫描——而扫描的成本在单机规模下可以接受。

### 1.7 归因

归因指把总量分摊到具体对象上：哪条会话、哪个任务、哪个工具、哪类错误。它的前提是每条记录带着归属信息，而归属的来源是 2.5 的作用域与 2.7 的事件（每条事件都写着它属于哪条会话）。

归因的三种常用维度各有用途。按会话回答"哪条会话最贵"（用于发现异常的长会话）。按任务回答"哪类任务最贵"（用于决定优化哪一类）。按工具回答"哪些工具的输出最占上下文"（用于决定哪些工具该截断得更狠）。

三种维度的共同前提是成本记录必须带上这些标识，而这件事在设计日志事件时就应当考虑——它属于 2.7 那条"可查询"原则的延伸。

### 1.8 两次追问

工程侧的问题是什么时候该报警。判据是"这个指标超过阈值意味着需要人介入吗"。多数指标不需要报警（它们只需要被查看）：只有那些"超出之后会迅速恶化"的才值得报警——例如饱和度（1.1 的 0.5.1 提到的四个黄金信号里唯一有预警能力的那个）。报警太多会让报警失去意义，这与 3.2 的审批疲劳是同一个机制。

产品侧的问题是这些数字对用户意味着什么。多数用户不关心 token 与延迟分解，而他们关心两件事：这次任务花了多少（可能是钱，也可能是配额），以及为什么这么慢。因此面向用户的呈现应当是两个数加一句解释，而分解后的细节留给需要排查的场合——这与 2.2 的"给模型看的描述"是同一条原则：信息的组织方式应当匹配读者的目的。

---

### 1.9 度量的腐化与它的审计

指标会随系统演化失去意义，而这个过程没有信号。三种形态值得预先知道。

第一种是口径漂移：某个指标的定义随实现改动而变（例如"每次任务成本"从"不含重试"变成"含重试"），而历史数据没有被重算。后果是跨时间的对比失效，而它看起来只是"这周贵了"。处置方式是把口径写成可执行的代码（同一个函数），并在改动时重算历史——口径的变更应当被当作一次数据迁移对待。

第二种是无人查看：某个指标被建立之后再也没有人因为它的变化做过决定。判据是"最近三个月有没有一次决策引用过它"，而它的处置是删除——保留一个没人看的指标的成本不在存储，而在它给人"我们在度量"的错觉。

第三种是目标替代：指标被当成目标之后偏离原意（0.5.3 的古德哈特定律）。它的信号是"指标改善了而没有对应的实际改善"，因此需要与护栏指标的对照。

三种形态的共同点是它们都无法靠单次检查发现，因此需要定期审计。审计的三个问题是：这个指标的口径最近变过吗、最近三个月有没有人用它做过决定、它有没有对应的护栏。

## L2 决策表

| # | 决策 | 我们的选择 | 替代方案 | 代价落在谁身上 |
|---|---|---|---|---|
| 1 | 度量的来源 | 从日志派生 | 单独的埋点通路 | 派生要扫日志；换来只有一套事实 |
| 2 | token 的记录粒度 | 每次请求都记 | 只记总量 | 日志变大；换来可归因 |
| 3 | 缓存命中缺失的处置 | 当成零命中 | 让计算失败 | 成本偏高估；换来计算不中断 |
| 4 | 成本的单价来源 | 配置（可更新） | 硬编码 | 要维护配置；换来单价变化不用改代码 |
| 5 | 延迟的粒度 | 分解成四段 | 只记总耗时 | 实现要打时间戳；换来优化有方向 |
| 6 | 统计方式 | 记录原始值，按需算分位 | 预先分桶聚合 | 计算要扫；换来灵活 |
| 7 | 呈现方式 | 分位数为主、均值为摘要 | 只报均值 | 实现稍复杂；换来长尾可见 |
| 8 | 前缀的组装 | 稳定内容在前、可变在后 | 按自然顺序拼 | 组装逻辑要显式规定；换来命中率 |
| 9 | 归因维度 | 会话、任务、工具三个 | 只按会话 | 记录要带标识；换来能定位成本来源 |
| 10 | 报警的范围 | 只报会迅速恶化的指标（饱和度等） | 所有指标都报 | 可能漏报缓慢恶化；换来报警有效 |
| 11 | 面向用户的呈现 | 两个数加一句解释 | 展示全部分解 | 信息少；换来用户能读懂 |
| 12 | 指标与护栏 | 每个指标配一个护栏指标 | 只看主指标 | 要维护成对的指标；换来不产生偏差 |

其中两条值得展开，因为它们的选择在实践中经常被做成另一个。

### 关于第 8 条的完整论证（为什么组装顺序是一个设计问题）

替代方案是按自然顺序拼接上下文：系统提示、历史消息、当前输入，各自取自它们产生的地方。它在语义上完全正确，而在成本上可能差数倍——因为前缀缓存要求逐字节相同。

三种常见的破坏方式各有来源。第一种是时间戳（"今天是 X"），它让每次请求的前缀都不同。第二种是随机 id 或会话标识被放在前面（例如把 session id 拼进系统提示）。第三种是工具定义的顺序不稳定（例如按对象键的遍历顺序生成，而那个顺序在不同运行里可能不同——这与 2.6 的可复现性要求是同一件事）。

三条规则的实现方式是把"组装"写成一个显式的函数，而不是散落在几处拼接：

```ts
function assembleRequest(session: Session, turn: Turn, now: number): LLMRequest {
  return {
    system: STABLE_SYSTEM_PROMPT,                    // 稳定：不含时间与随机值
    tools: sortByName(session.tools),                // 稳定：固定排序
    messages: deriveMessages(session.events),        // 大部分稳定（历史），尾部会增长
    trailing: { now, turnId: turn.id },              // 可变部分放在最后
  }
}
```

这段实现里四处注释都对应一条规则，而它的价值在于顺序成了代码里可见的东西——它不再是一个"取决于各处怎么拼"的偶然结果。

### 关于第 12 条的完整论证（为什么每个指标都要配护栏）

替代方案是只度量主指标（成本、延迟、成功率）。它的失效方式正是 0.5.3 提到的古德哈特定律：当度量成为目标，它就不再是好的度量。

三个具体的形态。度量"成本"而不配"任务成功率"，会让实现者倾向于提前放弃（任务早早结束，成本自然下降）。度量"延迟"而不配"输出质量"，会让实现者倾向于减少输出（更短的输出更快）。度量"步数"而不配"任务完成度"，会让循环倾向于用更少的步数强行结束。

护栏指标的作用是让"通过牺牲主指标之外的东西来改善主指标"这条路可见。它的实现成本是维护成对的指标，而它的收益是让优化不偏离目标。这条决策与 3.2 的"声明与强制配对"在形状上相同：主指标是声明，护栏是兜住它被误用的手段。

## L3 实现（施工图）

### 3.1 文件结构

```
// plugins/observability.ts
// ┌─ 采集段 ── 从事件里取 usage 与时间戳（不新增埋点）
// ├─ 计算段 ── costOf / latencyBreakdown / hitRate
// ├─ 聚合段 ── 按会话、任务、工具三种维度的归因
// ├─ 呈现段 ── 分位数与摘要
// └─ 护栏段 ── 成对指标的相关性检查
```

五段的划分对应前四节的四个度量与 L2 第 12 条的护栏。采集段刻意不新增埋点：它只读日志里已有的事件，因为"需要额外埋点"意味着日志缺了某类事件。

### 3.2 采集段

```ts
export function collect(events: readonly SessionEvent[]): Measurement[] {
  const out: Measurement[] = []
  for (const [i, e] of events.entries()) {
    if (e.type !== 'session/assistant') continue
    const req = events[i - 1]                       // 约定：请求事件紧随其前
    if (req?.type !== 'session/request') continue
    out.push({
      sessionId: e.sessionId,
      taskId: req.taskId,
      usage: e.usage,                                // 含 cachedPromptTokens（可能缺省）
      totalMs: e.at - req.at,
      queueMs: req.startedAt - req.at,               // 排队
      firstTokenMs: e.firstTokenAt - req.startedAt,  // 首 token
      generateMs: e.at - e.firstTokenAt,             // 生成
      retryWaitMs: req.retryWaitMs ?? 0,
    })
  }
  return out
}
```

这段实现依赖三个字段（`firstTokenAt`、`startedAt`、`retryWaitMs`），而它们必须在事件设计时就存在——这是"延迟分解必须在实现时做、事后无法恢复"的具体形态（0.2 的分析）。

### 3.3 计算与聚合

```ts
export function summarize(ms: readonly Measurement[], price: PriceTable) {
  const costs = ms.map((m) => costOf(m.usage, price))
  const total = (f: (c: Cost) => number) => costs.reduce((n, c) => n + f(c), 0)
  return {
    requests: ms.length,
    tokens: { miss: ..., hit: ..., out: ... },
    cost: { missInput: total((c) => c.missInput), hitInput: total((c) => c.hitInput), output: total((c) => c.output) },
    hitRate: ms.reduce((n, m) => n + (m.usage.cachedPromptTokens ?? 0), 0) /
             Math.max(1, ms.reduce((n, m) => n + m.usage.promptTokens, 0)),
    latency: { p50: percentile(ms.map((m) => m.totalMs), 0.5), p95: ..., p99: ... },
  }
}
```

`hitRate` 的分母用了 `Math.max(1, ...)`：它防的是空集合上的除零，而这类细节在聚合代码里很容易被漏掉（测试通常在非空数据上跑）。

### 3.4 呈现与护栏

呈现段提供两个视图：面向用户的（两个数加一句解释）与面向排查的（全部分解与分位数）。护栏段做一件具体的事：检查主指标与护栏指标的相关性——如果成本下降而任务成功率同时下降，那么成本下降就值得怀疑。

### 3.5 验收判据

| # | 判据 | 怎么检查 |
|---|---|---|
| 1 | 每次请求都产生一条度量 | 跑三轮，核对度量条数 |
| 2 | token 三档被分别统计 | 构造含命中与不含命中的两次请求 |
| 3 | `cachedPromptTokens` 缺失时按零命中计 | 用不提供该字段的假 provider |
| 4 | 成本与手算一致 | 给定 usage 与单价，核对金额 |
| 5 | 延迟四段之和等于总耗时 | 核对分解自洽 |
| 6 | 分位数计算正确 | 用已知分布核对 P50 与 P99 |
| 7 | 归因到会话与工具 | 两条会话各跑几次，核对分组结果 |
| 8 | 命中率随前缀稳定性变化 | 固定前缀跑两次，核对第二次命中率上升 |
| 9 | 可变内容放在前缀之后 | 检查组装函数：稳定部分不含时间与随机值 |
| 10 | 度量不新增埋点 | 检查采集段只读已有事件 |
| 11 | 护栏指标成对出现 | 核对输出里主指标与护栏同时存在 |
| 12 | 面向用户的视图只有两个数加一句解释 | 核对呈现函数 |

第 8 与第 9 条是这一篇的特色判据：它们检验的是"前缀设计"，而其他条检验的是"度量正确"。第 10 条检验的是本课程的一条坚持——度量应当从既有事实派生，而不是靠新增通路。

### 3.6 实现顺序

先做采集与计算（判据 1、2、3、4、5），再做聚合与分位（判据 6、7），然后做前缀稳定性检查（判据 8、9），最后做呈现与护栏（判据 11、12）。

### 3.7 实现里最容易写错的三处

第一处是归因字段的完整性。正确做法是在采集时就取到会话 id、任务 id 与工具名；错误做法是先只记总量、之后再想办法分摊。后者无法补——因为分摊需要的信息在事后已经不存在（一条总成本无法拆回三条会话）。这条与 0.2 那句"延迟分解必须在实现时做"是同一类。

第二处是时间戳的成对性。正确做法是请求与响应各记一个时间戳（以及首 token 的时刻）；错误做法是只在响应时记一个时间。后者只能算出总耗时，而总耗时无法分解——0.2 那个"八秒的三种构成"就是这样被丢掉的。

第三处是护栏指标的缺失。正确做法是主指标与护栏同时定义、同时实现；错误做法是先做主指标（因为它更容易度量），护栏留到以后。后者的问题是护栏的价值在于它参与优化决策的那一刻，而那时如果它不存在，优化就已经偏离了目标。

### 3.8 一次完整的度量流程

把本篇与前五篇串起来，一次请求从发生到进入报表的五步如下（括号里是责任方）。

```
1 请求发出        （2.7 的循环）      记录 request 事件：时间戳、会话、任务、工具
2 响应返回        （2.1 的模型层）    记录 assistant 事件：usage、首 token 时刻
3 派生度量        （本篇）            每条请求算一次成本与四段延迟
4 聚合归因        （本篇）            按会话、任务、工具分组
5 呈现与护栏      （本篇）            分位数、命中率、以及主指标与护栏的对照
```

五步里有三个检查点。第 1 步是归因字段的落点——缺了它，后面的分摊无法进行。第 2 步是 token 与时间戳的落点——缺了它，成本与延迟都算不出来。第 5 步是护栏的落点——缺了它，优化会失去方向。

三个检查点的共同形态是它们都发生在请求正在被处理的时刻，而不是事后补记的时刻。这与前几篇的结论一致：延迟分解、归因字段、配对结果都必须在产生它们的时刻记录，事后无法恢复。

这套流程有一个直接推论：度量字段的位置在事件设计时就固定了（3.2 的采集段依赖三个时间戳字段，而它们必须在事件里存在），而事后补字段意味着历史日志无法参与统计——这是 1.9 的"不得改变已有字段含义"在度量侧的对应约束。

推论的第二半是派生字段不进日志：成本与命中率都是可以从 `usage` 算出的量（它们随时间与单价变化），因此它们不应当被写进事件。写进去的代价是历史数据会带着过时的单价，而这会让"上个月的成本"与账单对不上。派生可重算（2.7），而重算需要原始值在场——这两条要求把"记什么、算什么"划清了。

第一层是契约测试：用假 provider 产生可控的 usage 与时间，按 3.5 的十二条判据逐条检查。

第二层是账单核对：用真实 API 跑几次调用，把算出的成本与账单对比。这一层是成本度量的唯一可信验证——算错口径时，只有账单能发现。

### 5.3 三条容易踩的规则

第一条，把可变内容放在前缀之后。时间戳与随机 id 在稳定段里会让整段前缀失效。

第二条，`cachedPromptTokens` 缺失时按零命中算，不要让计算失败。

第三条，每个主指标配一个护栏指标。只看主指标会让优化偏离目标。

## L7 挑战题（不给答案）

第一题：给命中率加归因。 命中率下降时，如何判断是"前缀变了"还是"服务端缓存被清"？给出至少两种可区分的观察方式。

第二题：多会话下的前缀设计。 三条会话共享同一个系统提示但工具集不同。设计组装方式，使共享部分的命中率最大化。

第三题：成本预算与门控。 给定一次任务的预算上限，设计一个在超支之前介入的机制，并说明它对任务成功率的影响。

第四题：延迟分解的采样。 逐请求打时间戳有成本（尤其在低延迟阶段）。设计一个采样方案，并说明它会不会漏掉长尾。

第五题：护栏指标的选择。 为一个具体的优化目标（例如"提高缓存命中率"）选出两个护栏指标，并说明它们各自防哪种偏离。

第六题：度量的自证。 设计一种方式，让度量系统自己报告"它的数据是否完整"（例如有没有请求没有产生度量记录）。

## L9 仍未解决（这一篇自己的缺陷）

| 缺陷 | 后果 | 修法 | 当初为什么这么写 |
|---|---|---|---|
| 单价随模型与时间变化 | 硬编码会让成本算错 | 单价来自配置并在每次变更时更新（本文已如此） | 单价无法从代码推出，只能外部提供 |
| 没有跨进程的度量聚合 | 多进程部署时看不到全局成本 | 指标汇聚（第 5 卷） | 本卷是单进程的 |
| 延迟分解依赖服务端提供首 token 时间 | 不提供的实现只能算总耗时 | 用流式的第一个响应块代替首 token 时间 | 本课程的实现不启用流式（2.1 的决策） |
| 没有区分"计费的失败"与"不计费的失败" | 成本与账单可能有小额差异 | 按错误类型分别统计实际计费情况 | 需要真实账单数据来校准 |
| 饱和度指标只在个别资源上有 | 无法全面预警 | 为连接池、并发槽、上下文窗口各建一个 | 本卷的资源种类有限 |
| 护栏指标的相关性检查是人工的 | 偏离可能很久才被发现 | 自动化相关性检查与告警 | 自动化需要足够的样本量与统计方法 |

第三条属于"位置放错"（它本该在模型层的决策里被考虑，而不只是在这里应对）；第四条属于数据校准；第五条属于覆盖范围；其余属于规模与本卷的简化。第三条值得单独标记：因为 2.1 明确选择了不做流式，而延迟分解的第一段（首 token）恰好依赖流式提供的时间点——这是两篇决策之间的一处真实张力，它的处置方式是用替代信号（首个响应块）近似，而近似的误差在长输出时不可忽略。

### 本篇引出的十二个问题

读懂层。 第一，四个度量与它们的来源是什么？第二，三档计费如何构成成本？第三，延迟分解的四段各是什么？

评审层。 第十，拿到一套度量，你会先检查哪一处？第十一，怎么判断一个指标是不是装饰？第十二，如果有人说"先上线，成本以后再说"，你怎么回应？

### 问题升级练习

模糊问题：「我该怎么控制 agent 的成本与延迟？」

升级后的精确问题：

> 控制成本与延迟至少包含三件互相制约的事：度量（花在哪、慢在哪，以及口径）、归因（分摊到会话、任务与工具）、以及前置设计（前缀稳定性与输出长度这类在请求发出前就能决定的量）。
> 第二件与第三件互相制约——归因越细，可做的前置优化越多，但归因本身要求记录更多字段，而那会影响日志体积与写入成本。
> 我能不能为这三件事各找出一条**可检查的判据**？
> 特别是：有没有哪一条判据，是**能用账单核对的**？

提升点说明：原问题无法回答，因为"成本"可以是很多层的意思。升级后的版本把它拆成三件具体的事，指出后两件的制约关系，并追加以一个更强的问题：哪一条判据能用账单核对——因为只有与账单对齐的成本度量才有资格被用来做决策。

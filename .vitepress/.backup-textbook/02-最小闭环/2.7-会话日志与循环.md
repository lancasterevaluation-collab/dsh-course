## 本篇新词

会话日志指一次会话里所有事件的追加序列。它是本课程的权威状态（1.5 的第 1.1 节）：模型每一轮看到什么由它派生，而不是相反。日志的写入方式是只追加，已写入的事件不修改、不删除。

派生视图指从日志算出来的、供某个用途使用的数据，例如"给模型的消息数组""用量统计""当前任务的状态"。它的正确性判据是：删掉重算，结果与之前一致。

模型可见的必须可重建（model-visible ⟺ logged）是本课程的核心不变量：模型在任意一轮看到的全部输入，都必须能从日志重建。它的作用是让"为什么它当时那么决定"这个问题永远有答案——而这需要日志记录的不只是消息，还包括工具定义、系统提示、以及压缩摘要这些同样进入请求的东西。

agent 循环指"请求模型 → 若有工具调用则执行 → 把结果回给模型 → 再请求"这个反复过程。它的核心不在请求，而在终止条件：什么时候停下来，以及停不下来时怎么办。

配对（pairing） 指每个工具调用必须恰好有一个对应的结果。它是消息格式的硬约束（缺一条服务端会拒绝整个请求），因此它不能靠"记得配对"来保证，而要靠循环的结构来保证——每一条路径都必须产出结果，包括被拒绝、被取消与失败的那些路径。

收敛（convergence） 指循环在有限步内结束。它的反例是模型反复调用同一个工具、或者两个工具互相触发，而循环没有步数上限时会一直转下去。收敛不是模型的性质，而是循环必须提供的保证。

水位线（watermark） 指"已经应用到哪一条事件"的记录。它让恢复不必从头重放全部日志，代价是它必须与它所声明的进度在同一次写入中更新——顺序反了会留下一个空洞。

恢复（resume） 指从日志重建出可以继续运行的会话。它与"重放"的区别是重放只重建状态，而恢复还要处理"上一次停在哪里"：如果停在一次工具调用中间，那么那条调用要么被重放（幂等时），要么被标记为结果未知（不幂等时）。

```
│  ④ 可重建 —— 模型可见的一切都能从日志算出              → 1.4          │
└──────────────────────────────────────────────────────────────────────┘

 一句话串起来：真相源是日志 → 调用必须配对 → 循环必须收敛 → 可见的必须可重建
```

这张图的关键线索在第四块：它是前三块合起来才能成立的性质。日志是真相源（否则无处重建）、配对完整（否则重建出的消息序列不合法）、循环终止（否则日志永远写不完）——任何一块缺失，可重建都不成立，而第 3 卷的全部机制都建立在它上面。

### 0.1 一个具体的判断：压缩之后还能不能重建

第 1.5 篇已经用过这个例子，这里给出它在实现层的形态。压缩把一段历史替换成摘要，而它是本课程里第一个会威胁"可重建"的机制。三种实现方式对应三种后果。

改写历史（用摘要替换掉原始事件）：日志变小，派生简单，代价是原始事件永久丢失，于是"模型当时看到了什么"只能重建到摘要的粒度。

只在内存里保留摘要：日志不变，代价是压缩结果不在日志里，于是重放时算不出同样的摘要（摘要由模型生成，重放会得到不同结果），因此同一份历史在不同时间呈现出不同的样子。

压缩作为事件追加：日志里多一条"压缩点"事件，记录压缩发生在哪个位置、摘要是什么；派生视图从最后一个压缩点往后算，原始事件全部保留。它比第一种多占存储，比第二种多一层派生逻辑，换来的是可重建。

本课程选第三种。判据不是"它更安全"，而是第一种与第二种都会让某类问题永远无法回答——前者失去原始历史，后者失去一致性。而第 3 卷的诊断、恢复与观测都要依赖"能重建"这个前提。

### 0.2 本篇建立的三项判据

第一项用于判断一段数据该不该进日志：问它是否影响模型的决定。影响决定的都必须进（消息、工具定义、系统提示、压缩摘要），不影响的可以派生（用量统计、耗时、当前步数）。这条判据的边界情况是"影响决定但不属于消息"的东西——工具定义是典型例子，它进请求但不进消息数组，因此日志必须单独记它。

第二项用于判断循环是否会收敛：问每一步之后"距结束的距离"是否在减少。所有正常的步骤都会减少它（模型给出回答、工具返回结果），而重复调用同一个工具、或者工具之间互相触发不会减少。因此上限是必要的兜底，而它的值应当来自"正常任务需要多少步"的分布。

第三项用于判断配对是否完整：问每一条路径是否都产出了结果，包括被守卫拒绝、被用户取消、以及实现抛异常的路径。判据是"消息数组里 assistant 的工具调用数与 tool 结果数相等"，而它可以被一条运行时断言守住。

### 0.3 十分钟练习：一个不收敛的循环

下面这段代码用十五行演示循环缺少收敛保证时的行为。

```js
// 一个"总是要求再查一次"的假模型
const model = {
  async respond(messages) {
    const asked = messages.some((m) => m.role === 'tool')
    return asked
      ? { content: '再查一次确认', toolCalls: [] }      // 没有工具调用 → 应终止
      : { content: '', toolCalls: [{ id: 'c1', name: 'lookup', arguments: '{}' }] }
  },
}
async function loop(model, tools, maxSteps = 5) {
  const messages = [{ role: 'user', content: '查一下' }]
  for (let step = 0; step < maxSteps; step++) {
    const res = await model.respond(messages)
    messages.push({ role: 'assistant', content: res.content, toolCalls: res.toolCalls })
    if (res.toolCalls.length === 0) return { steps: step + 1, content: res.content }
    for (const call of res.toolCalls) {
      messages.push({ role: 'tool', toolCallId: call.id, content: await tools[call.name](call.arguments) })
    }
  }
  return { steps: maxSteps, content: null, exhausted: true }   // 兜底：步数用尽
}
console.log(await loop(model, { lookup: async () => '结果' }))
```

这段代码的重点是最后那个 `exhausted: true` 分支。没有它，一次模型行为异常就会让程序永远循环下去（而"模型行为异常"不是假设，它可能是提示词写错、工具返回了空结果、或者模型真的绕进了死循环）。这条练习的结论是：收敛保证必须由循环提供，而不能假设模型会自动结束。

> **面试视角**
> **高频问法**："agent 循环你怎么保证它会停？"
> **高分要点**：说出两层——正常的终止条件是模型不再请求工具，而兜底是步数上限；并补充"上限的值来自正常任务的步数分布"，而不是拍一个数字。

### 0.5.3 三个连锁影响

第一，"可重建"这条不变量决定了系统在出问题时能否被解释。 一个 agent 的行为难以解释，因为它由模型、提示词、历史与工具四个因素共同决定。如果历史不被完整记录，那么"为什么它当时那么做"这个问题就只能靠推测——而推测在排查时的价值很低。这条连锁的量化形态是"一次诊断需要回溯多少轮"，而它直接取决于日志记录了什么：只记消息的日志无法解释工具定义变化导致的行为差异，只记摘要的日志无法解释压缩之后的行为变化。

第二，循环的每一步都会放大成本，而成本与步数的关系是超线性的。 每一步都要把到目前为止的全部历史发给模型，因此第 n 步的输入规模是前 n-1 步的累积。这意味着一次十步的任务并不是"一次调用的十倍"，而是接近五十倍（按累积和估算）。这条连锁解释了为什么上下文压缩（第 3 卷）不是优化而是必需——它同时决定了成本上限与可行步数上限。

第三，事件格式的演进成本会随系统存活时间上升。 一条事件一旦被写入，它就要被未来的每个版本读懂。这与 2.6 的配置覆盖是同一类问题的两端：配置回答"新旧两份输入如何共存"，事件格式回答"新旧两份数据如何共存"。而事件的特殊之处在于它无法被重新生成——历史就是历史。

### 0.5.4 它与本书其余部分的关系

本篇的日志是本地的、单进程的、单写者的。它的结论在两类情形下需要补充：多进程同时写入同一份日志需要单写者模型或锁；分布式场景下的事件顺序需要逻辑时钟或共识。两者都不在本课程范围内，但第 5 卷的多会话会触及第一个的边界。

> **面试视角**
> **高频问法**："你系统的真相源是什么？"

## L0 要解决的问题

### 0.1 现象一：重启之后，系统"忘了"刚才发生了什么

第一个现象在前面几篇里出现过两次（1.5 的现象一与 2.5 的串扰），而它在会话这一层的形态最具体：进程重启之后，模型对上一轮说过的话一无所知。原因是历史只存在内存里——而这类实现通常不是因为没写持久化，而是因为持久化的对象选错了：它把"当前的消息数组"存下来，而消息数组是派生结果，压缩、截断、工具结果的形态变化都会让它与事实不符。

更隐蔽的一种是"存了但存不全"。日志里只有 user 与 assistant 消息，没有工具定义、没有系统提示、没有压缩点。于是重启后重建出的输入与当时的输入不同，而模型的行为差异会被归因为"模型不稳定"——这是一个把系统缺陷误判成模型特性的典型例子。

### 0.2 现象二：请求被服务端拒绝，理由是不合法的消息序列

第二个现象出现在工具调用处理不完备时。消息格式有一条硬约束：每一条 assistant 的工具调用都必须有一条对应的 tool 结果，数量与顺序都要对上。而实现里总有一些路径会漏掉结果——被守卫拦截的那条、被取消的那条、实现抛异常的那条。它们的共同点是"流程中途退出了，但没有产出结果"，而模型的请求在下一次就会因为序列不合法被拒绝。

这个约束的特殊性在于它不能靠"记得配对"来保证，因为需要记得的地方会随功能增加而增加（每加一种拦截机制就多一条路径）。可行的做法是让循环的结构保证它：无论工具调用返回什么、被什么拦住，都走同一个产出结果的出口。

### 0.3 现象三：循环不收敛

第三个现象在提示词写错或工具返回异常时出现：模型反复请求同一个工具，而循环没有步数上限，于是一直转下去。它的表现形式是"任务卡住不动"或者"账单短时间内增长很快"，而两者的排查都不容易——日志里只有一串相同的工具调用。

收敛保证必须由循环提供，而且要有两层：正常终止条件（模型不再请求工具）与兜底上限（步数用尽）。只有前者时，一次模型行为异常就会让程序永远运行；只有后者时，正常任务会在达到上限时被截断。 两者的配合方式通常是：上限设得比正常任务的步数分布高一个量级，达到上限时按"未完成"结束并把原因写进日志。

### 0.4 现象四：无法解释"为什么它当时那么决定"

第四个现象是前三个的综合后果。用户问"为什么它上一次把那个文件删了"，而答案需要复原当时的完整输入：系统提示是什么、有哪些工具可用、历史里有哪几条消息、中间有没有发生过压缩。如果这四样里缺任何一样，答案就只能是推测。

这个现象的量级值得估一下：一次诊断要回溯的轮数通常是几轮到几十轮，而每一轮的输入包含当时的工具定义（几百到几千 token）与历史（随轮数增长）。把所有轮的完整输入都存下来的代价不小，而它换来的能力是"系统可被解释"——这也是本篇把它定为不变量的原因。

### 0.5 这一篇要正面回答的四个问题

第一，真相源是什么，什么由它派生（1.1）。第二，工具调用与结果的配对如何被结构保证（1.2）。第三，循环的终止条件是什么，上限设在哪里（1.3）。第四，"模型可见的必须可重建"这条不变量具体包含哪些内容（1.4）。

四个问题里第四是其余三个的目的：日志存在的意义是让重建成为可能，配对保证重建出的序列合法，收敛保证日志会写完。

## L1 设计与原理

### 1.1 唯一真相源：日志与它的派生

本课程把会话日志定为唯一真相源，其它一切都可以从它派生。这条选择的判据是"能不能从日志重算出当前状态"，而它对每一种数据都给出明确的位置。

| 数据 | 位置 | 理由 |
|---|---|---|
| 事件序列（含 seq） | 日志（权威） | 无法从别处重建 |
| 给模型的消息数组 | 派生 | 由事件映射而来 |
| 工具定义清单 | 日志（权威） | 它进入请求，因此影响模型决定 |
| 系统提示 | 日志（权威） | 同上 |
| 压缩点与摘要 | 日志（权威） | 它改变派生规则 |
| 用量统计、耗时、步数 | 派生 | 由事件算出 |

这张表里前三行是"必须进日志"的，而它们的共同点是都进入过请求。第四行（压缩点）之所以是权威，是因为它改变派生规则——它不是输入的一部分，而是"如何从输入算出输入"的规则。

派生数据的唯一纪律是它可以被删掉重算。 这条纪律的实践形式是：任何时刻删掉内存里的派生视图、从日志重算一次，结果必须与之前一致。它是第 3 卷的压缩、恢复与观测三篇共同的前提，也是可以写成一条测试的性质。

### 1.2 配对约束与它的结构保证

配对约束是消息格式的硬要求：assistant 消息里的每个工具调用都必须有一条对应的 tool 结果。它的实现难点不在写法，而在路径的完备性——每一条可能导致"没有结果"的路径都必须被堵住。

本课程的做法是把"产出结果"收拢到循环的一个出口。工具调用的处理只有三种结局：正常返回、返回失败、被拦下（守卫或用户取消）。三种结局都走同一个函数产出 tool 消息：

```ts
function toToolMessage(call: ToolCall, outcome: ToolOutcome): ChatMessage {
  return {
    role: 'tool',
    toolCallId: call.id,                                    // 与调用配对
    content: outcome.ok ? outcome.content : outcome.error,  // 失败也要有内容
    isError: !outcome.ok,
  }
}
```

这段实现有两个要点。第一，失败也必须产出消息内容（错误文本），因为"空的 tool 结果"在某些实现里会导致请求被拒。第二，`toolCallId` 必须来自调用本身而不是重新生成——配对靠的是这个 id 相等。

它的结构意义在于：循环里不再有"跳过这个调用"的分支。被守卫拦下的调用同样走这个出口，只是 outcome 是失败。这条规则会在第 3 卷的守卫篇里被再次引用，因为拦截是最容易漏掉配对的路径。

### 1.3 循环的结构与终止条件

循环的结构只有四步，但它有四个必须被规定的细节。

```
1 组装请求（消息 + 工具定义 + 系统提示）
2 请求模型
3 若没有工具调用 → 结束
4 否则执行每个工具调用，把结果加入消息，回到 1
```

四个细节分别是：终止条件（第 3 步）、步数上限（兜底）、工具调用的执行顺序（顺序还是并发）、以及每一轮是否把全部历史发出去（本课程是，因此才有第 3 卷的压缩）。

步数上限的值应当来自分布而不是直觉。一个可用的做法是记录正常任务的步数分布，取它的高分位数（例如 99 分位）再乘以一个安全系数。这个值的作用不是"防止浪费"，而是把不可收敛的情形变成一个可观测的失败：达到上限时系统应当明确结束并记录原因，而不是静默地停止。

循环的另一条与配对相关的规则是：每一轮结束时的消息数组必须是合法的。这条规则可以写成一条运行时断言（2.1 的 `assertModelVisibleMatchesLog` 就是这类断言），而它的价值在于把"某条路径漏了配对"这个缺陷从"下一次请求被拒"提前到"这一轮结束时立刻失败"。

### 1.4 "模型可见的必须可重建"的完整表述

这条不变量的完整形式需要说清三件事：什么算"可见"、什么算"可重建"、以及违反它的后果。

可见指进入请求的全部内容：消息数组（含工具结果）、工具定义、系统提示、以及任何影响生成的参数（温度之类的采样参数虽然不影响"看到什么"，但影响"生成什么"，因此也应当记录）。压缩摘要属于"影响派生规则"，它进入请求的方式是通过派生视图，因此也必须记录。

可重建指存在一个纯函数，输入是日志，输出是当时的请求内容。它的判据可以写成一个可检查的性质：对任意一次请求，把日志重放一遍得到的请求内容与实际发出的内容一致。这条性质在实现上可以每次请求前校验一次（代价是重放的成本），或者只在测试与调试时开启。

违反它的后果分三种：诊断失效（无法回答"它当时看到了什么"）、恢复不一致（重启后重建的输入与崩溃前不同，于是行为变化）、以及优化不可验证（第 3 卷的压缩与缓存优化都以"能算出当时的输入"为前提）。

这条不变量的实现代价是日志比"只记消息"更大：工具定义与系统提示在每一轮都可能变化（工具的可用集随模式变化，系统提示随配置变化），因此它们的变化也要作为事件被记录。这个代价是刻意的：省下的是存储，失去的是可解释性，而可解释性在系统出问题时的价值远高于存储。

### 1.5 日志的物理形态

日志的物理形态决定了它在崩溃时的行为。本课程采用行分隔的 JSON（NDJSON）：每条事件一行，行内是完整的 JSON 对象，行尾换行。三条性质随之而来。

第一，不完整只能出现在尾部。只追加意味着已写入的行不会被修改，因此一次崩溃最多损坏最后一行。这正好是 3.5 的恢复算法所需要的性质：扫描到第一行无法解析为止，丢弃其后的一切。

第二，每条事件带顺序号。顺序号用于三个地方：检测缺口（读取时发现跳号说明日志损坏或被截断）、幂等重放（按顺序号去重）、以及派生视图的增量更新（记住处理到哪一号）。

第三，格式简单到可以用文本工具检查。这一点在实际排查里的价值很高：用 `tail` 看最后一条、用 `rg` 找某类事件、用 `wc -l` 数条数，都不需要专门的工具。

事件类型的集合（`SessionEventMap`）有一个重要的规则：成员默认是读取时必需的，也就是说不认识某个事件类型的旧版本会拒绝读取包含它的日志。这条规则看起来严苛，而它保护的正是"可重建"这条不变量——一条未被理解的事件可能改变派生结果，跳过它会让重建出错。需要放宽时用第二条规则：带可忽略标记的事件允许被跳过，判据是"不知道它时派生出的结果会不会错"（2.4 的 1.6 已经建立这条判据）。

### 1.6 水位线与恢复

水位线是"已经应用到哪一条"的记录，它的作用是让恢复不必从头重放。它的正确性依赖一条与先写日志同源的约束：水位线必须与它所声明的进度在同一次写入中更新。

两种错误顺序的后果不对称。先更新水位线再应用那批记录，崩溃会留下一个空洞——水位线声称已应用，而数据里没有，于是恢复后会缺失一段历史。先应用再更新水位线，崩溃只会导致重复应用，而重复应用对幂等的派生是安全的（派生视图是可重算的）。因此可用的顺序只有一个，这与 1.5 里 `merge` 必须先释放再占用是同一类推理：先做可重复的那一步。

恢复时还剩一个必须回答的问题：如果日志的最后一条是"工具调用开始"而没有结果，该怎么办。答案取决于那个工具是否幂等（2.1 要求工具声明幂等性，正是为了这里）。幂等的可以重放，非幂等的只能标记为结果未知并把决定交给上层——因为重放可能造成第二次效果。这一条与 1.5 的 1.8 节是同一个结论，只是那里的对象是状态迁移，这里是工具调用。

### 1.7 成本与步数的关系

循环每一步都把到目前为止的全部历史发给模型，因此第 n 步的输入规模是之前全部步骤的累积。这个性质让成本与步数的关系是超线性的。

按一个具体的量级估算：假设每步产生约 500 token 的新增内容（一条 assistant 消息加一条工具结果），那么第 n 步的输入约 500n token，而一次 n 步任务的总输入约 500 × n(n+1)/2。十步的任务总输入约 27500 token，二十步约 105000 token——后者的步数是前者的两倍，而总输入是它的近四倍。

这个量级有两个直接后果。第一，它给步数上限提供了一个经济学依据：超过某个步数之后，单次任务的成本增长会让"继续尝试"变得不划算，而这条边界应当由成本数据而不是直觉决定。第二，它是第 3 卷上下文压缩必要性的来源——压缩把"全部历史"变成"摘要加最近若干条"，从而把每步的输入规模从 O(n) 降到 O(1)。因此压缩不是优化，它是让长任务可行的前提。

### 1.8 两次追问

工程侧的问题是什么时候该写一条新事件类型。判据是"这件事会不会影响模型看到的内容或派生规则"：会影响的必须写（工具的可用集变化、系统提示变化、压缩发生），不影响的可以派生（用量、耗时）。这条判据有一个边界情况值得说明——同一个事实的两种粒度：工具调用可以记成一条事件（含完整的调用与结果），也可以记成三条（调用开始、结果、失败）。前者更省，后者更接近"发生过什么"的原始顺序。本课程选前者，理由是工具调用是一个原子动作，它的中间状态没有独立的语义。

产品侧的问题是什么让用户信任这个系统。答案是"它的行为可以被解释"。用户问"为什么它删了那个文件"时，唯一可接受的回答是复原当时的输入并指出是哪一条信息导致了那个决定——而这件事只有日志完整时才可能。因此"可重建"这条不变量不只是工程要求，它直接支撑一个产品能力：可复盘。这条映射与 1.5 的 1.3.4 是同一个结论（那里说的是不变量支撑可复盘性），只是对象从状态换成了行为。

其中两条值得展开，因为它们的选择在实践中经常被做成另一个。

### 关于第 3 条的完整论证（工具定义为什么必须进日志）

替代方案是"日志只记消息，工具定义从当前代码里取"。它在单一版本、单一模式下完全可用，而在三种情形下出错。

第一，工具集随模式变化。2.6 的 profile 决定装载哪些工具，而同一个会话可能在运行中切换模式（第 5 卷的模式与预设）。此时"当时有哪些工具可用"不能从当前代码读出。

第二，工具描述会变化。同一段代码在不同版本里给出的工具描述可能不同（描述改进了、参数增加了），而这会改变模型对工具的用法。只记消息的日志无法区分"模型没用那个工具"与"当时那个工具的描述不清晰"。

第三，压缩与截断会改变工具清单的呈现方式。第 3 卷的上下文压缩可能对工具定义做筛选（只保留相关的几个），而那次筛选是模型可见内容的一部分。

本课程的选择是把工具定义与系统提示都作为事件记录。它的代价是日志体积增长——一次会话里工具定义可能占几百到几千 token，而它在每一轮都可能变化。缓解方式是只在变化时记录（工具的可用集变化、系统提示变化），而不是每一轮都记一遍。这条优化保留了可重建性，同时把体积控制在可接受范围，而它要求派生逻辑能从"最近一次变化"往后重建。

### 关于第 10 条的完整论证（未知事件为什么默认拒绝）

替代方案是"遇到不认识的事件就跳过"。它的好处是向前兼容（旧版本能读新日志），代价在两类事件上变得严重。

第一类改变派生规则的事件。压缩点是典型例子：跳过它之后，派生出的消息数组会把已经被压缩掉的历史重新展开，于是重建出的输入与当时完全不同。此时的"能读"是假象——系统读进去了，但重建的结果是错的。

第二类是影响配对的工具调用与结果。跳过其中一条会让消息序列不合法，于是请求被拒——故障从"读不了日志"变成"读进去之后请求失败"，而后者更难定位。

本课程的选择是默认拒绝，理由是它对不变量最安全：拒绝读取是显式的失败，而跳过是静默的错误。需要放宽的场合用可忽略标记逐条声明，而每个声明的依据是"不知道它时派生出的结果会不会错"。这条规则把兼容性从一个全局策略变成逐事件的判断，代价是每次新增事件类型都要回答一次这个问题。

## L3 实现（施工图）

### 3.1 文件结构

```
// kernel/session.ts
// ┌─ 事件段 ──────────────────────────────────────────
// │  SessionEventMap：事件类型到载荷的映射
// ├─ 日志段 ──────────────────────────────────────────
// │  append(event)：追加一行并分配 seq
// │  read(fromSeq)：按顺序读取，遇到不完整行即停止
// ├─ 派生态段 ────────────────────────────────────────
// │  deriveMessages(events) / deriveTools(events) / computeStats(events)
// ├─ 断言段 ──────────────────────────────────────────
// │  assertModelVisibleMatchesLog(events, request)
// └─ 循环段 ───────────────────────────────────────────
//    runTurn(session, ctx, maxSteps)：请求、执行、记录、直到结束
```

五段的划分依据是"哪一段会因为什么原因被改动"：事件段随格式演进变化，日志段随存储方式变化，派生态段随压缩与筛选规则变化，断言段是这一篇不变量的守门人，循环段随控制流变化。

### 3.2 事件类型与顺序号

```ts
type SessionEventMap = {
  'session/user': { text: string }
  'session/assistant': { text: string; toolCalls: readonly ToolCall[] }
  'session/tool-result': { callId: string; ok: boolean; content: string }
  'session/tools-changed': { tools: readonly string[] }       // 工具可用集变化
  'session/system-prompt': { text: string }                   // 系统提示变化
  'session/compaction': { atSeq: number; summary: string }     // 压缩点（第 3 卷）
  'session/end-turn': { step: number; reason: string }
}
```

这段映射里有两条规则来自 1.4：`session/tools-changed` 与 `session/system-prompt` 只在变化时记录（而不是每轮记录）；`session/compaction` 携带它作用的顺序号，因为派生需要从它往后算。

顺序号的分配方式只有一种正确的做法：由日志本身决定下一个值（长度加一，或者维护一个持久化的计数器并与日志在同一次写入中更新）。用时间戳或随机数都不行——前者不保证单调（时钟回拨），后者不保证顺序（1.5 的可复现性要求）。

### 3.3 追加与读取

```ts
export async function append(event: SessionEvent): Promise<number> {
  const seq = (await readLastSeq()) + 1
  await appendLine(logPath, JSON.stringify({ seq, ...event }))    // 先落盘
  cache.push({ seq, ...event })                                    // 再改内存
  return seq
}

export async function read(fromSeq = 0): Promise<SessionEvent[]> {
  const out: SessionEvent[] = []
  for (const line of readLines(logPath, fromSeq)) {
    try { out.push(JSON.parse(line)) } catch { break }             // 解析失败即尾部不完整
    }
  }
  return out
}
```

两处要点。第一，`append` 的顺序是先落盘再改内存——反过来会在"落盘失败"时让内存与日志不一致（这正是 1.5 的 1.4 节的先写日志规则）。第二，`read` 遇到解析失败就停止，而不是跳过这一行继续——因为只追加的日志里不完整只可能出现在尾部，而"中间有一行坏了"意味着日志被外部修改过，那是一个更严重的问题，应当被显式发现。

### 3.4 派生视图

派生视图是纯函数：输入事件数组，输出该用途的数据。本课程有三处派生，它们的共同纪律是"删掉重算结果不变"。

```ts
export function deriveMessages(events: readonly SessionEvent[]): ChatMessage[] {
  const lastCompaction = events.findLast((e) => e.type === 'session/compaction')
  const from = lastCompaction ? events.indexOf(lastCompaction) : 0
  return events.slice(from).flatMap(toMessages)      // 压缩点之后的事件 + 摘要本身
}
```

这段实现的要点是从最后一个压缩点往后算，并把压缩事件本身转成一条摘要消息。它同时体现了两条规则：压缩不改写历史（原始事件仍在 `events` 里），而派生视图的起点可以被压缩点前移。

### 3.5 断言

```ts
/**
 * 校验"模型可见的必须可重建"。
 *
 * 做法：把日志重放一遍，与实际即将发出的请求内容比较。
 * 它在开发与测试时开启，在生产上按需开启（重放有成本）。
 */
export function assertModelVisibleMatchesLog(
  events: readonly SessionEvent[],
  request: { messages: readonly ChatMessage[]; tools: readonly ToolDef[] },
): void
```

这条断言的价值在 1.3 已经说明：它把"某条路径漏了记录"这个缺陷从"下一轮行为异常"提前到"这一轮结束立刻失败"。它的成本是重放一次，因此应当可开关，而它的开关本身也应当在日志里留下记录（否则"为什么这次没校验"又成了一个未记录的事实）。

### 3.6 循环

```ts
export async function runTurn(session: Session, ctx: Context, maxSteps = 40): Promise<TurnResult> {
  for (let step = 1; step <= maxSteps; step++) {
    const request = { messages: deriveMessages(session.events), tools: deriveTools(session.events) }
    const res = await ctx.require('llm').chat(request)
    await session.append({ type: 'session/assistant', text: res.content, toolCalls: res.toolCalls })
    if (res.toolCalls.length === 0) {
      await session.append({ type: 'session/end-turn', step, reason: 'no-tool-calls' })
      return { ok: true, steps: step, content: res.content }
    }
    for (const call of res.toolCalls) {
      const outcome = await executeOne(call, ctx)          // 三种结局都走这里
      await session.append({ type: 'session/tool-result', callId: call.id, ok: outcome.ok, content: outcome.ok ? outcome.content : outcome.error })
    }
  }
  await session.append({ type: 'session/end-turn', step: maxSteps, reason: 'step-limit' })
  return { ok: false, steps: maxSteps, reason: 'step-limit' }
}
```

这段实现里有三处对应前三节的分析。第一，`executeOne` 是配对的唯一出口（1.2），它内部区分正常返回、失败与拦截三种结局。第二，达到上限时追加一条事件并返回失败（1.3），而不是静默退出。第三，每一轮的请求都由 `deriveMessages` 重算（1.1），因此内存里不保存"当前消息数组"这份可能不一致的状态。

### 3.7 验收判据

| # | 判据 | 怎么检查 |
|---|---|---|
| 1 | 追加的事件可按顺序读回 | 追加三条，读回三条，字段一致 |
| 2 | 顺序号连续且唯一 | 读回后检查 seq 为 1..n |
| 3 | 尾部不完整行被丢弃 | 手工写入半行，读回的前缀仍然完整 |
| 4 | 派生视图可从日志重算 | 清掉派生缓存重算，结果一致 |
| 5 | 工具定义变化被记录 | 改变模式后，日志里出现一条 `session/tools-changed` |
| 6 | 系统提示变化被记录 | 同上 |
| 7 | 每次请求的输入可由日志重建 | 开启断言，跑一轮任务，断言不抛 |
| 8 | 每个工具调用都有对应结果 | 跑一轮含工具调用的任务，核对消息数组里调用数与结果数相等 |
| 9 | 被拦截的调用同样产出结果 | 让守卫拦下一个调用，核对结果存在且 `ok: false` |
| 10 | 循环在无工具调用时结束 | 用假 provider 返回无工具调用的响应，核对返回 `no-tool-calls` |
| 11 | 循环在达到上限时结束并记录原因 | 用假 provider 一直返回工具调用，核对返回 `step-limit` 且日志里有对应事件 |
| 12 | 崩溃后可从日志重建 | 杀掉进程再读日志，重建出的消息数组与崩溃前一致 |

第 7 条与第 12 条是这一篇的核心判据，它们分别对应该不变量的两个侧面：运行时的输入可重建、崩溃后的状态可重建。第 9 条是最容易被漏掉的一条，因为它需要构造"被拦截"这个路径。

### 3.8 实现顺序

先做事件段与日志段（判据 1、2、3），再做派生视图（判据 4、5、6），然后做断言（判据 7），接着做循环与配对（判据 8、9、10、11），最后做崩溃重建的验证（判据 12）。

### 5.3 三条容易踩的规则

第一条，先落盘再改内存。反过来会在落盘失败时让两者不一致。

第二条，配对走单一出口。每多一条"跳过调用"的分支，就多一处可能漏掉结果的地方。

第三条，未知事件默认拒绝而不是跳过。跳过会让重建出的结果与当时不同，而那种错误是静默的。

## L9 仍未解决（这一篇自己的缺陷）

| 缺陷 | 后果 | 修法 | 当初为什么这么写 |
|---|---|---|---|
| 日志是单写者的 | 多进程同时写会互相覆盖 | 引入单写者模型或文件锁（第 5 卷多会话会触及） | 本卷是单进程的 |
| 恢复只处理"尾部不完整"，不处理中间损坏 | 中间损坏会被当成尾部截断而静默丢弃后半段 | 引入每行的校验和与段文件 | NDJSON 的简单性换来了"不完整只能在尾部"这个假设 |
| 断言的重放有成本 | 大日志下每次请求前重放一次不可接受 | 增量重放（从水位线往后）或抽样校验 | 断言在开发与测试时开启，生产按需 |
| 没有日志的保留策略 | 日志无限增长 | 归档与分片（挑战题第四题） | 第 2 卷的会话时长有限 |
| 事件类型没有版本化 | 载荷结构变化无法单独演进 | 引入每个事件类型的版本或按新类型承载 | 整体版本号覆盖了多数情形 |
| 步数上限是全局常量 | 不同任务的合理上限不同 | 按任务类型配置上限 | 全局常量在早期便于发现异常 |

第一条与第二条属于边界与假设（单写者、不完整只在尾部），第四条与第五条属于能力缺失，第三条属于性能取舍，第六条属于简化。第二条值得单独标记：它是本篇的一个隐含假设，而它在两类情形下不成立——日志被外部工具修改、或者存储介质出现坏块。这两类情形下，"扫描到解析失败就停止"会把后面的内容全部丢弃，而正确的做法是报告损坏位置而不是静默截断。

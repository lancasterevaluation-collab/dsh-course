## 本篇新词

这一篇的术语不多，但每一个都会在后面反复用到，值得先讲清楚——因为后面几篇会用它们来解释自己的设计，而你如果只是"大致知道"，那些解释就落不到实处。

provider 指的是"真正会去调模型的那个东西"。它不是模型本身，也不是接口，而是一个适配器：它的职责是把你的系统内部的数据结构翻译成某家厂商的线上格式，再把对方的回应翻译回来。所以 provider 这个词的重点在"翻译"，而不在"调用"。理解这一点很重要，因为后面所有的可替换性讨论都建立在这个定位上。

线格式（wire format） 指实际在网络上传输的那份 JSON 的结构。它与你系统内部的数据结构不是一回事：内部你用的是有类型的对象，而线上传的是某个厂商规定的一串字段。把这两者分开看待，是这一篇最重要的一个习惯——它们一旦混在一起，你的系统就与某家厂商绑定了。

role 指一条消息在对话里的位置。主流格式有四种：system（系统指令）、user（用户）、assistant（模型）、tool（工具返回）。它们不是简单的标签，而是有语义的：模型被训练成按位置来理解信息的重要性，所以同一段文字放在 system 里和放在 user 里，模型的行为会不同。

tool call 指模型返回的一个"我想调用某个工具"的请求。它带着工具名与参数，而参数是一个字符串——这一点是本篇最大的坑（1.5 会专门讲）。

错误分类 指把不同性质的失败区分开。它不是"把错误包装得好看一点"，而是一个决策依据：3.1 篇的重试机制要靠它来判断"这一次失败要不要重试"。所以错误分类的正确性直接决定了重试机制的正确性——分类错了，重试就会做错事。

可替换性 指"换一个实现，调用方不需要改"。它在本篇有一个很具体的判据：接口里有没有出现某家厂商专有的概念。如果出现了，那么可替换性就已经破了。

幂等 指"做一次和做多次的结果相同"。它在重试的场景下是核心概念：只有幂等的操作才可以被安全地重试。而模型调用是不是幂等的，比大多数人想的要复杂（L2 会讨论）。

## 第 0 节 · 学完这一篇你能做出什么

### 0.1 你会获得一条第一原理

这一篇真正要给你的东西只有一条，但它决定了后面所有关于"上下文"的决定：

> **模型没有记忆。它每次看到的只有你这一次传过去的东西。**

这句话听起来像常识，但它的推论不是。因为如果模型没有记忆，那么"它在上一轮说过什么"这件事，就必须由你的系统重新传给它——而"重新传什么、按什么顺序传、传多少"就从一个实现细节变成了一门设计。

而这个认识会解释后面很多看起来奇怪的设计：为什么会话日志必须能被重建成消息历史（第 3 卷）、为什么压缩之后还要能还原"模型当时看到了什么"（第 3 卷）、为什么缓存命中率与"前缀是否稳定"直接相关（第 3 卷）。它们全都是这一条原理的下游。

### 0.2 你会得到三个判断工具

第一个工具是"接口够不够窄"的判据。 你会学到怎么用一个具体的问题来检查它：接口里有没有出现某家厂商专有的概念？ 如果有一个字段叫 `deepseekReasoningEffort`，那么无论把它放在哪一层，可替换性都已经破了。这个判据可以立刻用在任何你评审的接口上。

第二个工具是"错误该怎么分类"的判据。 你会学到一条比"记住有哪些错误码"更有用的规则：分类的依据是"遇到它该怎么办"，而不是"它是什么"。同一个底层错误（比如超时）在不同位置的处理方式不同，所以分类要跟着处理方式走。

第三个工具是"参数为什么是字符串"的推导。 你会学到为什么模型返回的工具参数是一个 JSON 字符串而不是一个对象——这个设计不是偏好，而是由"模型只能生成 token"这个事实推出来的。理解这条推导，你就能判断哪些类似的"奇怪设计"是必然的、哪些是可以改的。

### 0.3 你会做出一个真实产物

这一篇的产物是 `kernel/llm.ts`：一个可替换的 provider 抽象，加上一套能被重试机制直接使用的错误分类。

它不大（约 250 行），但它的每一处都对应一个判断。而它的正确性有一个明确的验收方式：用一个 MockProvider 替换真实 provider，整套系统的行为不变——如果换了之后有地方报错，说明某个地方还在依赖厂商细节。

## 第 0.5 节 · 系统视角

### 0.5.1 你在哪里

篇目坐标：第 2 卷的第一篇。这一卷要做出"最小闭环"——一个能对话、能用工具、能记录历史的系统，共 7 篇。

层次坐标：这一篇做的是 `kernel/` 层的第一个文件。`kernel/` 是这套系统的"能力层"，它只依赖类型与纯函数，不依赖任何具体的运行环境。把它放在最底层有一个直接的理由：上面所有东西（agent 循环、工具、会话）都要用模型，而它们不应该各自知道怎么调模型。

它在课程里的特殊位置：这是整套课程里第一次出现"外部世界"。前面第 1 卷全部是判断题，没有代码；而从这一篇开始，你的系统第一次要面对一个你无法控制的东西——一个会失败的远程服务。这个转变带来一整套新的设计问题：超时、重试、限流、错误分类。它们不是"额外的健壮性工作"，而是这个系统能不能用的前提。

### 0.5.2 下游依赖表

| 这一篇的产物 | 谁会用到 | 用途 | 强度 |
|---|---|---|---|
| `ChatMessage` / `Role` | 会话日志、上下文压缩、记忆 | 消息的结构决定"历史怎么存、怎么重建" | 强 |
| `ToolCall` | 工具系统、agent 循环 | 参数是字符串这件事会传到很远 | 强 |
| `LLMErrorCode` | 3.1 篇的重试、4.4 篇的诊断 | 重试要不要重试、归因归到哪 | 强 |
| `Provider` 接口 | 测试（MockProvider）、3.6 篇的指标 | 可替换性让测试不需要真 API | 中 |
| `LLMUsage` | 3.6 篇的可观测 | token 统计的唯一来源 | 中 |

这张表里有一行值得单独看：`LLMErrorCode` 被两处使用，而这两处对它的要求不同——重试机制需要的是"这个错误可不可以重试"，诊断机制需要的是"这个错误指向哪个组件"。一个类型同时服务两个消费者时，它的定义就会被两个方向拉扯。1.6 会给出这个拉扯的解法。

### 0.5.3 三个连锁影响

第一个连锁影响：消息结构一旦定下来，它就变成了所有历史数据的格式。

这是第 1 卷反复讲过的那个机制（"持久化会把一次性设计变成长期契约"）在这一篇的第一次兑现。你在这里定义的 `ChatMessage` 会直接成为会话日志里每条消息的形状——而会话日志是真相源，它落盘之后就不能随意改。

这条影响的量级值得算一下。假设你的 `ChatMessage` 定义了一个字段 `content: string`，三个月后你发现工具调用的返回值可能是结构化数据而不只是字符串。要把它改成 `content: string | object`，你需要处理的是：已有的日志文件（它们里面是字符串）、所有读日志的地方、所有写日志的地方、以及任何持久化过派生结果的地方。这不是一次"改类型"的改动，而是一次数据迁移。

所以这一篇的接口设计要按"它会被存下来"的标准来做，而不是按"现在能用"的标准。这个标准会具体地影响几个决定：字段名要不要带厂商色彩（不要，因为厂商会变）、可选字段要不要给默认值（要，因为旧数据没有它）、枚举要不要封闭（要，因为新值会让旧代码读不懂）。

第二个连锁影响：错误分类的正确性会在3.1 篇才被检验，但错误在这里就埋下了。

这一篇只定义错误类型，不做重试——重试是3.1 篇（本卷第 4 篇左右）。所以这里有一个时间差：你在这里做的分类对不对，要等几篇之后才会暴露。

而这个时间差有一个具体的后果：如果你在这里把"限流"和"服务错误"归成同一类，那么3.1 篇会无差别地重试它们。而这两者的正确应对是不同的——限流应该等待更久（对方的窗口在恢复），服务错误应该快速重试（可能只是那一个实例的问题）。把它们的区别丢在这里，3.1 篇就很难再找回来，因为那时你看到的只是一个"可重试的错误"。

所以这一篇要按"下游需要什么判据"来设计错误分类，而不是按"上游给了什么错误码"来设计。 这个方向很重要，1.6 会展开。

第三个连锁影响：这一次的可替换性决定，会成为后面每一次的模板。

第 1 卷的 1.4 讲过"契约表面积"——一个接口暴露的东西越多，改它就越贵。这一篇是你在课程里第一次亲手画一条接口边界，而这条边界会成为一个被反复参照的例子。

具体来说，后面会反复出现"要不要为了某个功能而放宽这条接口"的诱惑：加一个 `reasoningEffort` 参数（为了支持某个厂商的推理模式）、加一个 `cacheControl` 字段（为了精确控制缓存）、加一个 `stream` 选项（为了更快看到输出）。每一个单独看都合理，而它们合起来就是"接口不再窄"。

所以这一篇会给你一条可以反复使用的判据（0.2 的"接口里有没有厂商专有概念"），而不只是给你一个具体的设计。它的价值在于它是可以搬迁的——你在评审任何接口时都能用它。

## L0 要解决的问题

### 0.1 现象一：新手会把厂商细节散落到各处

如果让一个没受过训练的人来写这一层，最可能的结果是这样：在 agent 循环里直接构造 HTTP 请求，在工具系统里直接判断 `response.choices[0].message.tool_calls`，在错误处理里直接检查 HTTP 状态码。

这个写法在只有一家厂商、只有一种调用方式时工作得很好。问题在于它埋下了三件事：测试必须连真实 API（因为没有地方能替换）、加一个厂商要改多个文件、某个厂商改了字段名就要全局搜索替换。

而这三件事的严重程度是递增的。第一种只是不方便；第二种是成本；第三种是危险——因为它意味着"厂商的一个改动会让你的多个模块同时失效"，而那时你已经很难判断哪些地方依赖了它。

### 0.2 现象二：不知道哪些错误该重试

新手处理错误的常见做法是"捕获所有异常，然后重试三次"。这个做法在多数情况下看起来是对的（毕竟重试确实常常能成功），但它有两个问题。

第一个问题是它会对不该重试的错误重试。比如"参数格式错误"（400）——这个错误重试一百次的结果都一样，因为你的请求本身就是错的。而重试它除了浪费时间和钱，还会掩盖真正的 bug。

第二个问题更隐蔽：它会对幂等性不确定的操作重试。模型调用在大多数情况下是幂等的（同一个请求得到同一个回应，虽然内容可能不同），但如果你在调用前后还做了别的事（比如计费、写日志），那么重试就会让那些事情发生两次。而"重试安全"这件事不是由错误类型决定的，而是由"这个操作做两次会怎样"决定的——这是一个比错误分类更深的问题，L2 会讨论它。

### 0.3 现象三：参数是字符串这件事会在很久之后才炸

模型返回工具调用时，参数是一个 JSON 字符串。这一点是它与其他返回值最大的不同：`content` 是字符串（本来就该是），而 `arguments` 也是字符串——但它表达的是一个对象。

新手最常见的做法是把这个字符串直接往下传，在真正要用的时候再 `JSON.parse`。这个做法能工作，直到某一天模型返回了一个不合法的 JSON。那时错误会出现在"使用参数的地方"——而那个地方离"参数进来的地方"可能隔了好几层。

这类问题的代价不在修复，而在定位。因为报错的位置与原因的位置隔得很远，所以定位它需要沿着调用链往回找。而正确的做法是在边界处处理：参数一进来就解析，解析失败就立刻报错，并指出是哪一次工具调用。

### 0.4 现象四：以为"支持多 provider"是一种能力

这是一个判断上的现象，不是代码上的。很多人在设计这一层时会把"支持多个 provider"当成一个目标，于是设计出一个能同时管 OpenAI、Anthropic、DeepSeek 的注册表。

这个目标在真实项目里通常不值得。理由是它引入的复杂度与它带来的收益不成比例：每多支持一个 provider，你就要多维护一套线格式翻译、一套错误码映射、一套能力差异处理（有的支持并行工具调用、有的不支持），而收益只是"可以换一家"，那是大多数产品从不需要的能力。

而正确的做法是把目标从"支持多 provider"改成"让替换成为可能"。这两者的差别是具体的：前者要求你现在就把三家都实现，后者只要求你不挡住将来的替换——也就是把厂商细节收在一个地方。后者几乎不花额外成本，而前者是持续成本。

这个区分是本篇的产品线内容，1.7 会展开。

### 0.5 这一篇要回答的五个问题

把四个现象收拢，这一篇要正面回答五个问题。

参数从哪来？答案是"模型没有记忆，所以每一轮都要重新传"（1.1）。一条消息有哪几种位置？答案是四种 role，而它们的差别是语义性的（1.2）。接口要多窄才算窄？答案是"到没有厂商专有概念为止"（1.3）。厂商细节该放在哪？答案是"只准出现在一个函数里"（1.4）。错误该怎么分类？答案是"按遇到它该怎么办分类"（1.6）。

## L1 设计与原理

### 1.1 第一原理：模型没有记忆

这一节的结论在 0.1 已经给过，这里要讲的是它的推导过程——因为只有走一遍推导，你才会在遇到"要不要把某样东西存进上下文"这类问题时，知道该往哪个方向想。

推导的第一步是认清模型的输入是什么。 一次模型调用的输入是一串消息，输出是下一条消息。除了这串消息，模型看不到任何东西：它不知道上一轮你说过什么（除非那也在消息里）、不知道你昨天问过它什么、不知道它自己上次回答了什么。它的全部"记忆"就是这一次输入里的那串消息。

第二步是看它会带来什么。 既然模型只看到这一次的消息，那么"让对话继续"这件事就完全落在你的系统身上：你必须把历史重新传一遍。而这件事有一个立刻的后果——上下文长度是有上限的，而历史是无限的。两者的矛盾就是第 3 卷全部内容的起点：压缩、溢出、记忆、检索，全都是为了在"必须带历史"与"带不下"之间找平衡。

第三步是看它对调试的影响。 如果模型的行为只由这一次的输入决定，那么"它为什么这样回答"这个问题就等价于"这次传进去的是什么"。这意味着系统的可调试性取决于一件事：你能不能还原出"模型当时看到了什么"。 而这正是后面那条核心不变量（"模型可见 ⟺ 日志可重建"）的由来——它不是一条形式化要求，而是"可调试性"在架构上的投影。

这条推导还有一个容易被忽略的推论。 如果模型没有记忆，那么"记忆"这件事就变成你的系统的职责——而你的系统要靠什么来记住？靠把它写下来。所以"模型没有记忆"这条性质，最终会推出"系统必须有持久化的记忆"。而这个推论把第 2 卷和第 3 卷连了起来。

```ts
/**
 * 一次模型调用的输入。
 *
 * 注意 messages 是【全部】输入：模型看不到这个数组以外的任何东西。
 * 这一条性质决定了后面所有关于上下文的设计。
 */
export interface LLMRequest {
  readonly messages: readonly ChatMessage[]
  readonly tools?: readonly ToolSpec[]
}

/**
 * 一条消息。
 *
 * content 是字符串；工具调用的参数也是字符串（见 1.5）。
 * 这个"都是字符串"的相似性是巧合，它们的处理方式完全不同。
 */
export interface ChatMessage {
  readonly role: Role
  readonly content: string
  /** 仅 assistant 消息可能有：它请求调用的工具 */
  readonly toolCalls?: readonly ToolCall[]
  /** 仅 tool 消息有：它回应的是哪一次调用 */
  readonly toolCallId?: string
}
```

### 1.2 四种 role：位置本身就是语义

四个 role 分别是 system、user、assistant、tool。它们不是标签，而是有语义的位置——模型被训练成按位置理解信息的重要性，所以同一句话放在不同位置，效果不同。

`system` 是系统指令。它的特点是由你的系统写，而不是由用户写——所以它承载的是"这个 agent 是谁、它的行为边界在哪"这类内容。把它与用户输入分开有一个实际的好处：用户可以注入任意文本，而系统指令不会被用户的文本覆盖。

`user` 是用户输入。这里有一个实践上的要点：不要把系统指令混进 user 消息。有些实现为了省事会这么做（"你现在是一个帮助助手……用户说：……"），而它的问题是用户可以通过构造输入来覆盖前面的指令——因为对模型来说它们在同一段文本里，没有优先级差别。

`assistant` 是模型的输出。它有一个特殊性：它是历史里唯一"由模型生成"的部分。所以当你重新构造历史时，assistant 消息必须原样保留——不能重新生成、不能摘要（除非你明确在做压缩）。

`tool` 是工具返回值。它的特点是必须与某一次工具调用配对：每条 tool 消息都要带一个 `toolCallId`，指向它在回应哪一次调用。这个配对关系不是可选的——如果它错位了，模型会看到"一个没有请求过的结果"，而它对这种输入的反应是不可预期的。

四种 role 里最容易出错的是最后一种，因为它的正确性依赖一个跨越两条消息的引用关系。而这正是"契约里最难写清的那一类"（1.4 讲过）——它约束的是两条消息之间的关系，而不是一条消息的性质。

### 1.3 Provider 抽象：把接口收窄到可替换

这一节回答 0.5 的第一个问题：接口要多窄才算窄。

先看一个"太宽"的接口长什么样。如果 `Provider` 暴露的是厂商的原始响应：

```ts
// ✗ 反面例子：把厂商的响应直接暴露出去
interface BadProvider {
  chat(body: DeepSeekRequestBody): Promise<DeepSeekResponse>
}
```

这个接口有两个问题。第一，`DeepSeekRequestBody` 与 `DeepSeekResponse` 是厂商的概念——调用方一旦用了这个接口，它就知道自己在跟 DeepSeek 说话。第二，更严重的是，这个接口把"请求的构造方式"也暴露了：调用方要自己组装 body，也就意味着它要知道这家厂商的字段名。

再看一个"够窄"的接口：

```ts
/**
 * 模型提供者。
 *
 * 这个接口里没有任何厂商专有的概念——它的所有类型都是本系统自己的。
 * 这条性质有一个可检验的判据：把实现从 DeepSeek 换成别的，
 * 调用方一行都不用改。
 */
export interface Provider {
  readonly name: string
  chat(request: LLMRequest): Promise<LLMResponse>
}
```

两个接口的差别可以用一句话概括：窄接口的输入输出都是"本系统的概念"，宽接口的是"厂商的概念"。 而这个差别带来的后果是具体的：窄接口能用 MockProvider 替换（测试不需要网络），宽接口不能（因为 Mock 要造出厂商的原始响应，而那份响应包含很多与测试无关的字段）。

这条判据是可以搬迁的，它不只适用于 provider：

> **问：这个接口里有没有出现"某个具体实现"的概念？**
> 如果有，那么"可替换性"这件事已经破了——无论它的抽象层看起来有多完整。

而当这条判据被违反时，通常的借口是"只加一个字段，问题不大"。这个借口在单个例子上成立，在系统上不成立——因为接口的表面积是累积的（1.4 的概念），而每一个"只加一个字段"都在把它撑大。

### 1.4 线格式：厂商细节只准出现在一个函数里

有了窄接口之后，还有一个位置需要决定：厂商细节放在哪？

答案是一个函数，而且只有一个：

```ts
/**
 * 把本系统的消息翻译成某家厂商的线格式。
 *
 * 这是整个文件里唯一允许出现厂商专有概念的地方。
 *   这条约束不是洁癖——它是"换一家厂商要改多少"的直接答案：
 *   改这一处，其余不动。
 */
function toWireMessages(messages: readonly ChatMessage[]): WireMessage[] {
  return messages.map((m) => ({
    role: m.role,
    content: m.content,
    // 这里是厂商细节：不同厂商对 tool 消息的字段名不一样
    ...(m.toolCallId ? { tool_call_id: m.toolCallId } : {}),
    ...(m.toolCalls ? { tool_calls: m.toolCalls.map(toWireToolCall) } : {}),
  }))
}
```

为什么这个约束值得被写死成一条规则，而不是"尽量这样做"？因为它把"替换成本"从一个不确定的量变成了一个确定的量。如果不写死，厂商细节会逐渐扩散；而扩散之后，"换一家要改多少"这个问题的答案就变成了"不知道，得先找一遍"——而"不知道"本身就是一种成本，它会让"要不要换"这个决策无法进行。

这条规则还有一个测试上的用途。因为厂商细节只在一个函数里，所以这个函数可以被单独测试：给它一组内部消息，断言它产出的线格式符合厂商规范。而在细节扩散的实现里，这类测试无法写——因为没有一个地方能代表"全部的翻译逻辑"。

### 1.5 `arguments` 是字符串：这一篇最大的坑

模型返回工具调用时，参数是一个 JSON 字符串。这一节要讲的是为什么必然如此，以及由此推出的处理方式。

为什么必然如此。 模型生成的是 token 序列。它没有办法"生成一个对象"，只能生成一段文本——而如果这段文本要表达一个结构，那么唯一可行的方式就是把它生成为一个 JSON（或类似格式）的字符串。所以"参数是字符串"不是某个厂商的偷懒，而是"模型只能生成 token"这个事实的直接后果。

这个推导的用途在于：它能让你判断哪些"奇怪设计"是必然的、哪些是可以改的。比如"为什么工具调用的名字是字符串而不是一个枚举"——那同样是因为模型生成的是 token，它可能生成一个不存在的名字，而枚举在生成过程中没有意义。

由此推出的处理方式：在边界处解析，而且立刻报错。

```ts
/**
 * 解析工具调用的参数。
 *
 * 位置很重要：它在参数【进入系统】的地方，而不是在它被使用的地方。
 *   原因是模型可能返回不合法的 JSON，而如果等到使用处才解析，
 *   报错的位置会与原因的位置隔很远（L0 的现象三）。
 *
 * @param raw 模型给的原始字符串
 * @param toolName 出错的工具名——只用于错误信息
 * @throws 当 raw 不是合法 JSON，或不是对象时
 */
export function parseArguments(raw: string, toolName: string): Record<string, unknown> {
  let parsed: unknown
  try {
    parsed = JSON.parse(raw)
  } catch {
    // 空 catch 里要说清是什么错：模型返回了截断或不合法的 JSON
    throw new LLMError(
      'invalid_tool_arguments',
      `工具 ${toolName} 的参数不是合法 JSON：${raw.slice(0, 120)}`,
    )
  }
  if (parsed === null || typeof parsed !== 'object' || Array.isArray(parsed)) {
    throw new LLMError('invalid_tool_arguments', `工具 ${toolName} 的参数不是对象：${raw.slice(0, 120)}`)
  }
  return parsed as Record<string, unknown>
}
```

这段代码里有两处值得注意。 第一处是它把错误信息里带上了原始字符串的前 120 个字符——这样在排查时，你能直接看到模型到底生成了什么，而不需要再去日志里找。第二处是它区分了"不是合法 JSON"与"是合法 JSON 但不是对象"——因为这两种情况的含义不同：前者通常是生成被截断，后者通常是模型的格式理解有偏差。而它们的应对方式不同（前者可能重试有效，后者重试无用）。

这两处的共同点是：错误信息要携带"下一步需要的信息"。 这是一个可以反复使用的原则——错误信息不是给人"看一眼"的，而是给人"据此决定下一步"的。

### 1.6 错误分类：按"遇到它该怎么办"分

这一节回答 0.4 的问题，也是本篇对下游影响最大的一节——因为3.1 篇的重试机制完全建立在它之上。

先说清分类的依据。 一个自然的做法是按"错误是什么"分类（认证错误、限流错误、服务错误……），这个分类是描述性的。而本篇采用的分类依据是"遇到它该怎么办"，也就是决策性的。

这两个依据有时会给出相同的分类，有时不会。 举个不同的例子：认证错误（401）与参数错误（400）在描述性分类里是两类，但在决策性分类里属于同一类——因为遇到两者都只有一个正确的做法：不要重试，直接失败并报告。把它们分成两类不会带来任何处理上的差别。

而反过来，一个描述性上相同的错误可能在决策性上需要分开。 比如"超时"——它发生在连接建立阶段与发生在响应接收阶段，应对方式不同（前者通常是网络问题，后者可能是请求太大）。如果按描述性分类，它们都是"超时"；按决策性分类，它们需要被分开。

```ts
/**
 * 错误的分类。
 *
 * 这些取值的依据不是"错误是什么"，而是【遇到它该怎么办】。
 *   所以判断一个新错误该归到哪一类时，问的是：
 *   "3.1 篇的重试遇到它，应当做什么？"
 */
export type LLMErrorCode =
  /** 重试有意义，且应当快速重试（瞬时故障） */
  | 'rate_limited'
  /** 重试有意义，但应当等待更久（配额或窗口恢复中） */
  | 'overloaded'
  /** 重试无意义，请求本身有问题（改参数或改代码才能解决） */
  | 'invalid_request'
  | 'invalid_tool_arguments'
  /** 重试无意义，是环境问题（凭据、网络可达性） */
  | 'auth_failed'
  | 'network_unreachable'
  /** 重试有意义，但次数应当受限（对方服务异常） */
  | 'server_error'
  /** 无法归类——它的存在本身就是设计的一部分 */
  | 'unknown'

/**
 * 一个模型层错误。
 *
 * 它同时携带两类信息：#code 用于【决策】（重试与否），
 * #message 用于【诊断】（给人看）。分成两个字段而不是把决策编码进字符串，
 * 是因为下游的消费者不同——重试只读 code，诊断只读 message。
 */
export class LLMError extends Error {
  readonly #code: LLMErrorCode
  readonly #retryable: boolean
  readonly #retryAfterMs?: number

  constructor(code: LLMErrorCode, message: string, options?: {
    /** 对方明确给出的等待时长（如 Retry-After 头） */
    retryAfterMs?: number
  }) {
    super(message)
    this.#code = code
    this.#retryable = RETRYABLE.has(code)
    this.#retryAfterMs = options?.retryAfterMs
  }

  get code(): LLMErrorCode { return this.#code }
  /** 3.1 篇的重试据此决定要不要再试一次 */
  get retryable(): boolean { return this.#retryable }
  /** 对方建议的等待时长；有它时不该用指数退避的估算值 */
  get retryAfterMs(): number | undefined { return this.#retryAfterMs }
}

const RETRYABLE = new Set<LLMErrorCode>(['rate_limited', 'overloaded', 'server_error'])
```

这段定义里有三个决定值得说明。

第一个决定是把"可重试"作为错误自身的属性，而不是让重试机制自己去判断。这看起来是把职责放错了地方——重试的规则难道不该归重试模块管吗？而它放在这里有一个具体理由：只有错误产生的地方知道完整的上下文。重试机制拿到的是一个 `LLMError`，它看不到原始的 HTTP 状态码与响应体；而错误产生的地方两者都有。所以判断"能不能重试"这个动作，只能在产生错误的地方做，而结果是作为属性带上去的。

第二个决定是 `retryAfterMs` 的来源。当对方在响应里给出了 `Retry-After` 时，它比任何指数退避的估算都准确——因为它是对方告诉你的，而不是你猜的。所以这个字段存在时，3.1 篇应当优先使用它。这也是"错误信息要携带下一步需要的信息"（1.5）的又一例。

第三个决定是 `unknown` 这一分类的存在。它看起来像偷懒，实际上是一条安全设计：如果错误分类是封闭的（没有兜底），那么遇到一个没见过的错误时，实现者只有两个选择——归到最像的那一类（可能是错的），或者让程序崩掉。而 `unknown` 提供第三个选择：承认不知道。 而"不知道"的正确处理是保守处理——不重试（因为不确定重试安全不安全），并把它记下来（因为它可能是新问题）。这一类错误的存在，让系统在面对未知时有一个明确的行为，而不是未定义的行为。

### 1.7 为什么不做多 provider

这一节是产品线的内容："支持多家 provider"这个目标，为什么不值得追求？

先算收益。 支持多家的收益是"可以换一家"。而"换一家"这个能力在什么情况下被用到？三种情况：当前这家持续不可用（但那通常是暂时性的，换一家成本更高）、价格变化（但换一家要重新验证质量，成本远超差价）、以及合规要求（那是少数企业的需求）。三种情况都不是常规需求。

再算成本，而成本是持续的。 每多支持一家，你就要维护：一套线格式翻译、一套错误码映射（每家的错误码完全不同）、一套能力差异处理（有的支持并行工具调用、有的支持图片、有的对系统消息的处理不同）、以及一套测试。而其中"能力差异处理"是最贵的——因为它是发散性的：每遇到一个新功能，你都要问"这在几家上分别怎么做"。

成本与收益的这个比例，决定了一个更好的目标：不是"支持多 provider"，而是"让替换成为可能"。

这两个目标的差别是具体的。前者要求你现在就把三家都实现；后者只要求你不挡住将来的替换——也就是把厂商细节收在一个函数里（1.4）。后者几乎不花额外成本（它就是良好的接口设计的自然结果），而前者是持续的维护成本。

而这个选择还有一个更深的理由：它把复杂度放在了"将来可能付出"的位置，而不是"现在就付出"的位置。 这是一个可以反复使用的判断模式——当一件事的收益不确定、而成本是确定且持续的时候，正确做法通常是"保持它能被做到"，而不是"现在就做到"。

最后要说明这个选择的边界。 "不做多 provider"不等于"不做抽象"——恰恰相反，正因为不做多实现，抽象才更重要（因为抽象是将来能做的唯一保证）。而如果有人把它理解成"不需要抽象，直接写死一家就行"，那就把这条判断读反了。

### 1.8 动手试一下：看一次真实的线格式

这一节带你实际看一次"内部消息"与"线格式"的差别。这个练习不需要你写任何代码——用一段临时代码和一个假响应就能看清。

第一步是先看清内部的形状。 假设有这么一段对话：用户提问、模型要求调用工具、工具返回结果、模型给出最终答案。用本系统的类型表示，它是四条消息：

```js
// 存成 _probe.mjs，放在 D:\dsh-mini 下
import { writeFileSync } from 'node:fs'

const internal = [
  { role: 'system', content: '你是一个助手。' },
  { role: 'user', content: '读一下 package.json 的 name 字段' },
  { role: 'assistant', content: '', toolCalls: [
      { id: 'call_1', name: 'read_file', arguments: '{"path":"package.json"}' },
  ] },
  { role: 'tool', content: '{"name":"dsh-mini"}', toolCallId: 'call_1' },
]

writeFileSync('_internal.json', JSON.stringify(internal, null, 2))
console.log('内部形状已写出')
```

第二步是看它翻译成线格式之后长什么样。 这一步的用途是让你亲眼看一遍"哪些字段变了"：

```powershell
node _probe.mjs
```

打开 `_internal.json`，然后与下面这份线格式对照——左边是本系统的字段，右边是 DeepSeek 的：

| 内部字段 | 线格式字段 | 说明 |
|---|---|---|
| `toolCalls` | `tool_calls` | 命名风格变了（camelCase → snake_case） |
| `toolCalls[].name` | `tool_calls[].function.name` | 多了一层嵌套 |
| `toolCalls[].arguments` | `tool_calls[].function.arguments` | 同上，且仍是字符串 |
| `toolCallId` | `tool_call_id` | 命名风格变了 |
| 其余字段 | 同名 | 这些恰好一样 |

这张对照表里的四行就是"厂商细节"的全部。所以"厂商细节只准出现在一个函数里"（1.4）这句话是具体的：要收起来的就是这四行的翻译逻辑，而不是什么抽象的东西。

第三步是确认"参数是字符串"这件事。 注意上面 `arguments` 在两边都是字符串——它在翻译过程中没有被解析。这是刻意的（3.2 说明了理由）：日志要记录模型给出的原始字符串，因为解析可能失败，而失败的那份原始输入恰恰是排查的依据。

```js
// 接上 _probe.mjs：模拟"模型给了一个坏 JSON"的情形
const bad = '{"path":"package.json"'   // 少一个右花括号
try { JSON.parse(bad) } catch (e) { console.log('解析失败：', e.message) }
```

最后的清理：

```powershell
Remove-Item _probe.mjs, _internal.json
```

做完这一步你应该能回答：线格式与内部形状的差别具体是哪几处、以及为什么 `arguments` 在两边都是字符串。如果这两点都能答上来，1.4 与 1.5 的设计你就看到了它们的实物，而不只是描述。

| # | 决策 | 我们的选择 | 替代方案 | 代价落在谁身上 |
|---|---|---|---|---|
| 1 | 接口暴露什么 | 本系统的类型（`LLMRequest` / `LLMResponse`） | 直接暴露厂商的请求与响应类型 | 实现量：要做一层翻译；换来可替换性与可 Mock |
| 2 | 厂商细节放哪 | 只允许出现在 `toWireMessages` 一个函数里 | 分散在需要的地方 | 函数变长；换来"换一家只改一处"是确定的量 |
| 3 | 消息表示 | 一个 `ChatMessage` 类型，四种 role | 泛化的 `{ role: string }` + 各自扩展 | 扩展性：加一种 role 要改类型；换来类型检查能挡住错用 |
| 4 | 工具参数 | \*\*字符串，在边界处立刻解析\*\* | 直接透传，用到时再解析 | 解析开销与一处额外代码；换来报错位置贴近原因 |
| 5 | 错误分类依据 | \*\*遇到它该怎么办\*\* | 错误是什么（描述性） | 需要更仔细地定义分类；换来重试机制可以直接消费 |
| 6 | 可重试性的归属 | 作为错误的属性（`error.retryable`） | 由重试模块自己判断 | 错误类型变大；换来判断发生在有完整上下文的地方 |
| 7 | 是否支持流式 | 不做 | SSE 流式输出 | 首字延迟变长；换来实现简单、与"可重建"这条不变量不冲突 |
| 8 | provider 数量 | 一个（DeepSeek）+ 一个 Mock | 内置多家 | 放弃"可换一家"的现成能力；换来持续的维护成本为 0 |
| 9 | 未知错误的处理 | 保留 `unknown` 分类并保守处理 | 归到最像的一类 | 需要一条额外分支；换来"面对未知有明确行为" |
| 10 | `retryAfterMs` | 记录对方给的建议值 | 统一用指数退避 | 错误对象多一个字段；换来比估算更准的等待 |

这张表里有三条值得展开论证。

### 关于第 3 条的完整论证（消息为什么用封闭类型）

第 3 条的选项是：用一个定义了四种 role 的 `ChatMessage`，还是一个泛化的 `{ role: string }` 加上各自的扩展。后者看起来更灵活——它允许你将来加第五种 role 而不用改类型。所以要论证为什么选前者。

先看"灵活"在哪一步变成了负担。 泛化类型的代价出现在每一个读消息的地方：因为 `role` 是任意字符串，所以每个处理消息的函数都要问"如果它不是我知道的那四种怎么办"。而这个问题没有好答案——回答"那就不该发生"意味着你在代码里依赖了一个类型系统没有保证的前提；回答"那就跳过它"意味着你可能静默丢弃了本该处理的数据。

而封闭类型把这个问题消灭在产生的地方：类型系统保证 `role` 只能是那四种，所以读它的地方不需要防御性分支。这就是"把检查从使用处移到边界处"这个模式在类型层面的又一次应用——它与 1.5 的"参数在边界处解析"是同一个思路。

再看"将来要加 role 怎么办"这个反对意见。 这个意见的合理之处在于：封闭类型确实让"加一种 role"变成了一次跨文件的改动（类型定义、所有 switch 分支、所有构造消息的地方）。而这恰恰是它的价值——因为加一种 role 本来就应该是一次慎重的改动：它会影响到存下来的数据（0.5.3 的第一个连锁影响）、影响到线格式的翻译、以及影响到模型看到的东西。

换句话说是：封闭类型把"加一种 role"的成本如实反映出来了，而泛化类型把这份成本推迟到了运行时——推迟不等于消除，它只是把它从"编译期的一次改动"变成了"某个夜晚的一个未定义行为"。

这个决策的边界也值得写清。 封闭类型适用于枚举的取值少且变化慢的场景（role 只有四种，且十年未变）；而不适用于取值会持续增长的场景（比如"工具名"——工具是会被不断加进来的）。判据是"这个集合的规模会随需求增长，还是随协议稳定"：

| 集合 | 会增长吗 | 该用 |
|---|---|---|
| role | 不会（协议级） | 封闭联合类型 |
| LLMErrorCode | 慢（每加一家厂商或一类失败） | 封闭联合类型 |
| 工具名 | 会（每个新能力加一个） | 字符串 + 运行时校验 |
| 模型名 | 会 | 字符串 |

这张表可以反复使用。它把"该用枚举还是字符串"这个常见的争论变成了一个可回答的问题——问这个集合的增长是被需求驱动的还是被协议规定的。

### 关于第 4 条的完整论证（参数为什么不该透传）

第 4 条的两个选项看起来差别很小：都是在某个时刻调一次 `JSON.parse`。所以要论证"在哪解析"为什么值得单独成为一个决策。

关键区别在于错误发生的位置。 如果透传，那么解析发生在使用参数的地方——而那个地方通常在最内层（真的要用这个参数去执行操作的地方）。此时报出的错误是"JSON.parse 失败"，而它不携带任何能让调用方回溯的信息：它不知道这是哪一次工具调用、哪个工具、原始字符串是什么。

而如果解析发生在边界，那么出错的时刻就是参数进入系统的时刻——此时所有上下文都还在手上：工具名、原始的字符串、以及它属于哪一条消息。所以错误信息可以精确到"工具 X 的第 N 次调用的参数不是合法 JSON，前 120 个字符是……"。

这两者的差别在日常开发里几乎看不出来（因为模型绝大多数时候返回合法 JSON），所以它很容易被当成不重要。而它真正的代价出现在那些不常见的时刻——模型被截断、模型的输出格式理解出现偏差、或者某次请求的返回被损坏。这些时刻本来就难查，而如果错误信息里没有上下文，查它们会变成一项很耗时的工作。

这条决策的一般形式是：在边界处转换数据，而不是在使用处。 它的理由是"上下文在使用处已经丢失了"，而错误信息能带走多少上下文，取决于你在哪里发现它。

最后补一个这条决策容易被忽略的后果。 在边界处解析，意味着解析的失败率会成为一个可观测的指标——你可以在一个地方统计"参数解析失败了多少次"。而在使用处解析的设计里，这些失败散落在各处，统计它们需要先找到所有使用点。所以"在哪解析"这个决定不只影响错误的可读性，还影响这类错误能不能被看见——而后者往往是更重要的：一个反复出现但没人统计的失败，会以"偶尔有点怪"的形式长期存在。

### 关于第 6 条的完整论证（可重试性该归谁判断）

第 6 条把"能不能重试"的判断放在了错误对象上，而直觉上这更像是重试机制的职责。所以要论证这个归属。

先看直觉的说法。 "哪些错误可重试"是一条策略，而策略通常属于使用方——就像"这个操作要不要重试"是调用方的决定。按这个逻辑，重试模块应该拿着错误码自己判断。

而问题在于重试模块能看到什么。 它拿到的是一个 `LLMError` 对象（或者更糟，一个 `Error`）。它能从里面知道什么？如果错误里只带了错误码，那么它只能依据错误码判断——而错误码是产生错误的地方压缩过的信息。原始响应的状态码、响应体里的错误信息、以及对方的 `Retry-After` 头，这些在压缩过程中都已经丢掉了。

所以结论是：判断的位置应当跟着信息的完备性走，而不是跟着职责的名字走。 产生错误的地方有完整上下文，所以它做判断；重试模块只消费结果（`error.retryable`）。

而这个归属还有一个附带的好处：它让"可重试"这件事可以被单独测试。因为它是错误的属性，所以可以写一组断言——"给定这个 HTTP 响应，产出的错误应当 `retryable === true`"。而在"重试模块自己判断"的设计里，要测同样的东西就必须起一个重试循环。

最后要说明它的一条隐含约束：把判断放在错误上，意味着每次新增一个错误码，都要同时回答"它可不可重试"。这不是负担，而是这个设计的价值所在——它强制"新增错误"与"新增处理策略"同时发生，从而避免了"新错误被默默归进默认分支"这种情况。

### 关于第 7 条的完整论证（为什么不做流式）

第 7 条选择不做流式输出，而这在很多人看来是一个明显的缺失——因为流式带来的首字延迟改善是用户体验上的硬收益。所以要论证这个放弃。

先看流式的收益。 它让用户更早看到部分输出。在一次需要十秒的生成里，流式可能让首字在 0.5 秒内出现，而整体的十秒不变。所以它的收益是"感知延迟"，而不是"实际延迟"。

再看它的成本，而成本比直觉的高。 流式要求把一次调用拆成多个增量事件，于是带来三件事：每一个增量都要进日志（否则"模型可见 ⟺ 可重建"这条不变量就破了）、错误处理要处理"中途断了"这种情况（而它比"整体失败"复杂得多，因为已经产生了一部分输出）、以及测试要能构造增量序列。

其中第一件是关键。 它意味着流式不是一个"调用方式的选项"，而是一个影响数据模型的变化：从"一次调用产生一条消息"变成"一次调用产生一串增量，最后由它们合成一条消息"。而这条变化会传到会话日志、传到压缩、传到恢复。

所以这个决策的实质是：是否愿意为了"感知延迟"而改动核心数据模型。 在本项目的阶段（第 2 卷，目标是先跑通闭环），把数据模型保持在最简形式的价值更高——因为后面几篇都会建立在这个模型上，越晚改越贵。

这个决策有明确的复核时机：如果后来发现首字延迟是一个真实的产品问题（比如用户会因此放弃使用），那么流式应当被重新评估。而那时的做法不是把流式塞进现有模型，而是先设计"增量如何落进日志"，再实现它。记住这个顺序——它会在第 3 卷出现同类问题时再次用到。

### 3.2 类型段

```ts
export type Role = 'system' | 'user' | 'assistant' | 'tool'

export interface ToolCall {
  /** 模型给的调用 id，用于把结果配回去（1.2 讲的配对关系） */
  readonly id: string
  readonly name: string
  /**
   * 参数是【字符串】，不是对象。
   *   理由在 1.5：模型只能生成 token，所以结构只能以文本形式传来。
   *   解析发生在边界处，不在这里——这个字段保持原样，便于日志记录原始输入。
   */
  readonly arguments: string
}

export interface LLMUsage {
  readonly promptTokens: number
  readonly completionTokens: number
  readonly totalTokens: number
}

export interface LLMResponse {
  readonly content: string
  readonly toolCalls: readonly ToolCall[]
  readonly usage: LLMUsage
  /** 用于统计与缓存诊断：命中了多少缓存 token（3.6 篇的可观测会用到） */
  readonly cachedPromptTokens?: number

```

`ToolCall.arguments` 保持字符串这一点值得单独说明：虽然 1.5 要求"在边界处解析"，但这个类型是"边界之内、解析之前"的形状。所以它保持原样有两个理由：日志要记录模型给出的原始字符串（而不是解析后的对象，因为解析可能失败，而失败的那份原始输入恰恰是排查的依据）；以及解析结果的类型（`Record<string, unknown>`）比字符串弱，用它是信息损失。

### 3.3 错误段

```ts
export type LLMErrorCode =
  | 'rate_limited' | 'overloaded'
  | 'invalid_request' | 'invalid_tool_arguments'
  | 'auth_failed' | 'network_unreachable'
  | 'server_error' | 'unknown'

const RETRYABLE = new Set<LLMErrorCode>(['rate_limited', 'overloaded', 'server_error'])

export class LLMError extends Error {
  readonly #code: LLMErrorCode
  readonly #retryAfterMs?: number

  constructor(code: LLMErrorCode, message: string, options?: { retryAfterMs?: number }) {
    super(message)
    this.name = 'LLMError'
    this.#code = code
    this.#retryAfterMs = options?.retryAfterMs
  }

  get code(): LLMErrorCode { return this.#code }
  get retryable(): boolean { return RETRYABLE.has(this.#code) }
  get retryAfterMs(): number | undefined { return this.#retryAfterMs }
}
```

### 3.4 翻译段（唯一允许出现厂商概念的地方）

```ts
/** 厂商的线格式消息。这个类型不导出——它不该出现在任何接口上。 */
interface WireMessage {
  role: string
  content: string
  tool_call_id?: string
  tool_calls?: { id: string; type: 'function'; function: { name: string; arguments: string } }[]
}

/**
 * 把本系统的消息翻译成厂商的线格式。
 *
 * 这是整个文件里唯一允许出现厂商字段名（tool_call_id / tool_calls）的地方。
 *   这条约束的用途是把"换厂商要改多少"变成一个确定的答案：改这一个函数。
 */
function toWireMessages(messages: readonly ChatMessage[]): WireMessage[] {
  return messages.map((m) => {
    const wire: WireMessage = { role: m.role, content: m.content }
    if (m.toolCallId) wire.tool_call_id = m.toolCallId
    if (m.toolCalls?.length) {
      wire.tool_calls = m.toolCalls.map((tc) => ({
        id: tc.id,
        type: 'function',
        function: { name: tc.name, arguments: tc.arguments },
      }))
    }
    return wire
  })
}

/**
 * 解析工具调用的参数。位置在【边界】（1.5）。
 *
 * @param raw 模型给的原始字符串
 * @param toolName 出错时用于定位的工具名
 * @returns 解析后的参数对象
 * @throws {LLMError} raw 不是合法 JSON，或解析结果不是对象时
 */
export function parseArguments(raw: string, toolName: string): Record<string, unknown> {
  let parsed: unknown
  try {
    parsed = JSON.parse(raw)
  } catch {
    // 空 catch 要说清是什么错：模型生成了不合法的 JSON（常见于输出被截断）
    throw new LLMError('invalid_tool_arguments', `工具 ${toolName} 的参数不是合法 JSON：${raw.slice(0, 120)}`)
  }
  if (parsed === null || typeof parsed !== 'object' || Array.isArray(parsed)) {
    throw new LLMError('invalid_tool_arguments', `工具 ${toolName} 的参数不是对象：${raw.slice(0, 120)}`)
  }
  return parsed as Record<string, unknown>
}
```

### 3.5 抽象段与实现段

```ts
export interface Provider {
  readonly name: string
  chat(request: LLMRequest, signal?: AbortSignal): Promise<LLMResponse>
}

/**
 * 测试用的 provider。
 *
 * 它的存在是"接口够窄"（1.3）的直接证据：因为接口里没有厂商概念，
 * 所以可以用一个不联网、可预测的实现替换真实的 provider。
 * 而如果接口暴露了厂商的响应类型，这种替换就要伪造大量无关字段。
 */
export class MockProvider implements Provider {
  readonly name = 'mock'
  #steps: readonly MockStep[]
  #cursor = 0

  constructor(steps: readonly MockStep[]) { this.#steps = steps }

  async chat(request: LLMRequest): Promise<LLMResponse> {
    const step = this.#steps[this.#cursor++]
    if (!step) throw new LLMError('unknown', `MockProvider 的脚本已用尽（第 ${this.#cursor} 次调用）`)
    if (step.kind === 'error') throw step.error
    return {
      content: step.content ?? '',
      toolCalls: step.toolCalls ?? [],
      usage: { promptTokens: 0, completionTokens: 0, totalTokens: 0 },
    }
  }
}
```

MockProvider 里有一处值得注意：脚本用尽时会抛 `unknown` 错误，而不是返回一个空的成功响应。这个选择是一个测试设计上的决定：如果返回空成功，那么"脚本写少了"这个测试错误会表现为"某处行为不对"，需要推理才能发现；而抛错会让它直接暴露为"第 N 次调用没有脚本"。测试工具的错误也要在边界处暴露——理由与 1.5 相同。

### 3.6 验收判据

| # | 判据 | 怎么验 | 期望 |
|---|---|---|---|
| 1 | 接口里没有厂商概念 | 读 `Provider` 接口与它引用的所有类型 | 只看得出"这是一个模型调用"，看不出是哪家 |
| 2 | 厂商字段名只出现在翻译段 | 全局搜索 `tool_call_id` / `tool_calls` | 只命中 `toWireMessages` 与 `WireMessage` |
| 3 | MockProvider 能替换真实 provider | 用 Mock 跑一个完整对话 | 不联网、结果可预测 |
| 4 | 参数在边界处解析 | 让 Mock 返回一个不合法的 JSON 字符串 | 立刻抛 `invalid_tool_arguments`，且错误信息含原始字符串 |
| 5 | 错误分类可被消费 | 构造各类错误，读 `retryable` | `rate_limited`/`overloaded`/`server_error` 为真，其余为假 |
| 6 | `unknown` 走保守路径 | 构造一个未分类的错误 | `retryable === false` |
| 7 | `retryAfterMs` 被保留 | 构造一个带该字段的错误 | 取到的值与传入的一致 |
| 8 | 类型能被序列化往返 | 把 `ChatMessage` 写成 JSON 再读回 | 得到相同的消息 |
| 9 | 负面判据：接口不泄漏实现 | 在 `Provider` 上找任何 `deepseek` 字样的成员 | 一个都找不到 |
| 10 | 负面判据：错误不掩盖原因 | 检查 `LLMError.message` | 含有足以定位的上下文（工具名或原始字符串） |

第 9 条与第 10 条是负面判据。 第 9 条防的是"抽象层里混进厂商概念"——它是可替换性最常见的破法（因为它往往是以"只加一个字段"的形式发生的，见 0.2 的第三个工具）。第 10 条防的是"错误信息失去定位能力"——错误被包装了好几层之后，原始原因可能只剩一句"请求失败"。

### 3.7 实现顺序

| 里程碑 | 消除的不确定性 | 验证方式 | 如果不成立 |
|---|---|---|---|
| M1 | 消息类型足以表达一次完整对话（含工具调用与结果） | 用固定消息序列序列化再读回 | 说明类型有缺，要补字段——而这一步必须在写 provider 之前 |
| M2 | 线格式翻译能被单独测试 | 给定内部消息，断言线格式 | 说明翻译逻辑还是散的 |
| M3 | MockProvider 能驱动完整对话 | 判据 3 | 说明接口上有厂商概念 |
| M4 | 错误分类能被重试直接消费 | 判据 5、6 | 说明分类依据混了描述性与决策性 |
| M5 | 参数解析在边界处报错 | 判据 4 | 说明还留在使用处 |

M1 排在第一位的原因与3.5 篇的 M1 相同：它是"如果不成就要回头改设计"的那一条。消息类型是这个系统的核心数据结构，它一旦落盘（本卷最后一篇会做），改动成本就上升一个量级。所以在写 provider 之前先确认它能表达一次完整对话，是成本最低的验证点。

## L4 运行与验证

### 4.1 三层验证

第一层是判据全过（3.6 的十条）。这一层能确认功能存在。

第二层是"用一个假 provider 跑通一次完整对话"。这一层是这一篇特有的，因为它的产物是一个抽象——而抽象的正确性无法靠读代码确认，只能靠"换一个实现，行为不变"来确认。做法是用 `MockProvider` 写一个脚本，让它依次返回"调用工具"与"给出最终答案"，看系统能不能走完。

第三层是"把错误分类真的用一次"。做法是构造一个 `rate_limited` 错误，然后手写一个三行的重试循环（真重试是3.1 篇的事，这里只需要用到 `error.retryable`），确认它重试了；再造一个 `invalid_request`，确认它没重试。

为什么这一层不能等到3.1 篇再做：因为3.1 篇会一次性建立在错误分类之上，而如果那时才发现分类不可用（比如缺少某个字段），返工的范围会更大。这一层的作用是提前消费一次自己的产物——而"提前用一次"是一种便宜且有效的接口验收方式。

### 4.2 一次完整的验证流程

```
① 跑 apps/verify.ts，确认既有检查未被打破
② 跑 3.6 的十条判据
③ 用 MockProvider 走完一次"工具调用 → 工具结果 → 最终回答"
④ 构造两类错误，各跑一次三行的重试循环，确认行为相反
⑤ 全局搜索厂商字段名，确认只出现在翻译段
```

第 ⑤ 步是可以被自动化的，而且值得自动化——因为它是"可替换性"这个性质唯一可检查的形式（判据 2、9）。它的实现方式很简单：`rg -n 'tool_call_id|tool_calls' src/kernel/`，然后断言命中的行数在一个白名单里。

### 4.3 动手试一下：用假 provider 走一次对话

这一节带你实际验证"可替换性"。判据 3 说"MockProvider 能替换真实 provider"，这一节就把它做一遍。

为什么要专门做这一步：因为一个抽象层的正确性无法靠读代码确认。你只能通过"换一个实现，行为不变"来确认它——而这需要真的换一次。

第一步：写一个三行的假 provider。 它不联网，而是按脚本返回预设的回应：

```js
// 存成 _mock-run.mjs，放在 D:\dsh-mini 下
import { MockProvider } from './src/kernel/llm.ts'

// 脚本：第一次调用要求读文件，第二次给出最终答案
const provider = new MockProvider([
  { kind: 'ok', toolCalls: [{ id: 'c1', name: 'read_file', arguments: '{"path":"package.json"}' }] },
  { kind: 'ok', content: 'package.json 的 name 是 dsh-mini。', toolCalls: [] },
])

const r1 = await provider.chat({ messages: [{ role: 'user', content: '读 package.json' }] })
console.log('第一次调用 →', r1.toolCalls[0].name, r1.toolCalls[0].arguments)

const r2 = await provider.chat({ messages: [] })
console.log('第二次调用 →', r2.content)
```

```powershell
cd D:\dsh-mini
node _mock-run.mjs
```

期望的输出：

```
第一次调用 → read_file {"path":"package.json"}
第二次调用 → package.json 的 name 是 dsh-mini。
```

这个输出说明什么：整个过程中没有任何网络请求，也没有 API key，而系统的行为与真实调用时一样（都是"拿到一个 `LLMResponse`"）。这就是"可替换"的具体含义——它不是"代码结构看起来分层了"，而是"真的换了之后能跑"。

第二步：验证参数解析在边界处报错。 让假 provider 返回一个坏的参数：

```js
import { MockProvider, parseArguments } from './src/kernel/llm.ts'

const provider = new MockProvider([
  { kind: 'ok', toolCalls: [{ id: 'c1', name: 'read_file', arguments: '{"path":"package.json"' }] },
])
const r = await provider.chat({ messages: [] })

try {
  parseArguments(r.toolCalls[0].arguments, r.toolCalls[0].name)
} catch (e) {
  console.log('错误码：', e.code)          // 期望：invalid_tool_arguments
  console.log('可重试：', e.retryable)     // 期望：false
  console.log('信息：', e.message)         // 期望：含工具名与原始字符串
}
```

第三步：验证两类错误的行为相反。 这一段是判据 5、6 的直接检验：

```js
import { LLMError } from './src/kernel/llm.ts'

for (const code of ['rate_limited', 'overloaded', 'server_error', 'invalid_request', 'unknown']) {
  const err = new LLMError(code, '测试')
  console.log(code.padEnd(18), '可重试 =', err.retryable)
}
```

期望的输出（前三行为 `true`，后两行为 `false`）：

```

overloaded         可重试 = true
server_error       可重试 = true
invalid_request    可重试 = false
unknown            可重试 = false
```

这三步做完，你就亲手验证了判据 2、3、4、5、6。 而它们覆盖了这一篇最重要的几个设计点：可替换、边界解析、决策性分类、以及未知的保守处理。

## L5 语法速查

### 5.1 术语表

| 术语 | 在本篇里的准确含义 | 容易误解为 |
|---|---|---|
| provider | 一个翻译适配器：把内部结构翻译成厂商线格式，再翻译回来 | "模型"（模型是服务端的东西，provider 是你这边的代码） |
| 线格式 | 实际在网络上传输的那份 JSON 的结构 | "接口"（接口是你系统内部的类型） |
| role | 一条消息在对话里的位置，有语义 | "标签"（换成标签就丢掉了位置本身的语义） |
| tool call | 模型返回的"我想调用某个工具"的请求，参数是字符串 | "工具调用"（那指的是真的调用了，而这是一个请求） |
| 错误分类 | 按"遇到它该怎么办"给错误分组 | "错误码"（那只是标识，不表达处理方式） |
| 可替换性 | 换一个实现，调用方不需要改 | "抽象"（有抽象不等于可替换） |
| 幂等 | 做一次与做多次结果相同 | "没有副作用"（那是更强的要求） |
| 边界处解析 | 在数据进入系统的地方做转换与校验 | "早解析"（"早"是时间，而这里指的是位置） |

### 5.2 命令速查

| 目的 | 命令 | 说明 |
|---|---|---|
| 检查厂商概念是否泄漏 | `rg -n 'tool_call_id\|tool_calls' src/kernel/` | 期望只命中翻译段 |
| 检查接口成员名 | `rg -n 'interface Provider' -A 5 src/kernel/llm.ts` | 看有没有 `deepseek` 之类的字样 |
| 用假 provider 跑一次 | 见 `demos/` 里的 mock 脚本 | 不需要 API key |
| 真实调用一次 | 需要 `DEEPSEEK_API_KEY` | 失败时看 `err.code` 与 `err.retryable` |

### 5.3 三条容易踩的规则

第一条：厂商字段名不要出现在类型定义里。 一旦出现，可替换性就破了——即使它只出现在一个可选字段上（因为可选字段也会被调用方读到）。

第二条：不要在解析失败时返回空对象。 返回 `{}` 会让错误延后到"某个参数是 undefined"的地方，而那正是 1.5 要避免的。解析失败就抛错。

第三条：`retryAfterMs` 存在时不要用指数退避。 对方给了等待时长就去等那么久——你的估算不会比它的更准。

## L7 挑战题（不给答案）

第一题：给 `Provider` 加一个"能力查询"接口。 有些模型支持并行工具调用、有些不支持。设计一个方式让上层能知道当前 provider 支持什么，并说明这个设计会不会让接口变宽。

## L9 仍未解决（这一篇自己的缺陷）

这一节列出这一篇交付的产物里，已知但未解决的问题。它们都是真实的——不是"将来可以优化"，而是"现在就有代价"。

| 缺陷 | 后果 | 修法 | 当初为什么这么写 |
|---|---|---|---|
| `MockProvider` 的脚本是静态的 | 只能按固定顺序返回，无法表达"根据输入变化" | 让脚本接受一个函数而不是数组 | 固定顺序覆盖了绝大多数测试场景，动态脚本会让测试本身变复杂 |
| 没有区分"请求太大"与"请求无效" | 两者都归 `invalid_request`，而前者缩短输入后可能成功 | 增加一个 `request_too_large` 分类 | 第 2 卷阶段上下文还小，这个情形不常出现 |
| `retryAfterMs` 只在错误里，没有全局的等待上限 | 对方给一个很大的值时会直接等那么久 | 加一个 clamp 到上限 | 对方给的值通常合理；上限属于重试机制（3.1 篇）的职责 |
| `LLMResponse` 没有记录"实际使用的模型名" | 如果服务端做了模型路由，看不到实际是哪个 | 把响应里的模型名字段保留下来 | 当前只用一家、一个模型，还没有这个问题 |
| `parseArguments` 不校验参数是否符合工具的 schema | 解析成功但参数缺字段时，错误要在工具内层才暴露 | 把 schema 校验也放在边界处 | schema 属于工具系统（下一篇），这一篇还没有它 |
| 错误信息里带上原始字符串前 120 字符 | 如果参数含敏感数据，它会进日志 | 增加脱敏规则 | 当前场景下参数不含凭据；而这条在工具系统引入凭据之后会变成真问题 |
| `MockProvider` 不产生 `usage` | 用它跑的场景无法验证 token 统计链路 | 支持在脚本里给 usage | 测试不需要真实 token 数；而它意味着统计链路在 mock 下未被覆盖 |

其中第三条与第六条值得单独指出，因为它们的性质不同。

第三条的"等待上限"是一个边界缺失：当前的设计把"等多久"完全交给了对方（`retryAfterMs`）或估算（指数退避），而没有一条"无论如何不超过 N 秒"的兜底。这个缺失在正常情况下不会暴露——因为对方给的值通常合理；而它会在对方出错（或恶意）时暴露，那时等待时间由对方的响应决定。这是一个"信任外部输入"的位置，而它存在于一个本该最不信任外部输入的地方（错误处理路径）。

第六条则是一个当前位置无害、但会随功能变化而变成问题的选择。把原始字符串放进错误信息，在当前是纯收益（排查更方便）；而当工具系统开始接收含凭据的参数时，同一行代码会把凭据写进日志。所以它不是"写错了"，而是"它的正确性依赖一个当前成立、将来不成立的前提"——而把这类问题列出来的价值，正是为了让那个前提被记住。

## L11 系统影响回溯

回看第 0.5 节的三个连锁影响，这一篇的实现给出了它们各自的具体形态，以及一处需要修正的预判。

连锁 1（消息结构会成为所有历史数据的格式） 的解法在 3.2 的类型定义与 3.6 的判据 8。而 0.5.3 说"要按'它会被存下来'的标准来做"，读完之后可以给出更具体的三条：字段名不带厂商色彩（因为厂商会变）、可选字段要有明确行为（因为旧数据没有它）、枚举要封闭（因为新值会让旧代码读不懂）。而其中"枚举要封闭"这一条的代价是可见的——它意味着每加一种 role 或一种错误码，都必须同步更新所有读它们的地方，而这是刻意的。

连锁 2（错误分类的正确性会在3.1 篇才被检验） 在这一篇有了一处补充：0.5.3 说"如果在这里把限流与服务错误归成同一类，3.1 篇会无差别地重试它们"，而这个说法可以更准确——它们其实都属于"可重试"，差别在等待策略（限流等更久、服务错误快速重试）。所以真正的损失不是"重试与否"判断错，而是"怎么重试"的信息丢了。这个更精确的表述来自 L2 第 10 条那条关于 `retryAfterMs` 的决策。

连锁 3（这次的可替换性决定会成为后面的模板） 在这一篇被兑现为一个可搬迁的判据（"接口里有没有某个具体实现的概念"）。而它有一处 0.5.3 没有预见到的用法：这条判据不只适用于"换厂商"，也适用于测试——因为 MockProvider 能成立的前提正是接口够窄（3.5）。所以可替换性的第一个受益者不是"将来换一家"，而是"现在能测"。

一处需要修正的预判：0.5.2 说 `LLMErrorCode` 被重试与诊断两处使用，而它们的需求不同——重试要"可不可以重试"，诊断要"指向哪个组件"。读完之后我会补一句：这个拉扯的解法不是把分类拆成两套，而是让错误同时携带决策信息与诊断信息（`code` + `retryable` + `message`）。拆分会让同一个错误在两个地方各自被分类一次，而两次分类可能不一致——那是一类比"分类不够细"更麻烦的问题。

通向下一步的桥。

做完这一篇，系统第一次能与外部世界说话。但它还只会说话——不能做事。

而"做事"带来的问题比"说话"多：工具需要注册（谁提供、谁发现）、需要参数校验（模型给的可能不对）、需要副作用分级（有些操作不可逆）、以及失败之后需要把错误回给模型而不是直接崩掉。

所以下一篇是 2.2 工具系统——它要把"模型说了一句话"变成"真的做了某件事，并把结果告诉模型"。

而这一篇给它留了一个具体的接口：`ToolCall.arguments` 是字符串（1.5）。工具系统在调用任何工具之前，必须先经过 `parseArguments`——而这个解析失败的情形，正是工具系统要处理的第一类错误。

## L12 练习题（带答案）

这一组题与 L7 不同：它们有明确答案，用来检验你是否真的理解了上面几节。建议先自己写，再展开对照。

### 练习 1：判断接口够不够窄

下面这个接口是某个 agent 框架里的真实形态。它够窄吗？如果不够，是哪一处破坏了可替换性？

```ts
interface LLMClient {
  createCompletion(params: {
    model: string
    temperature?: number
    messages: Message[]
    stream?: boolean
    toolChoice?: 'auto' | 'none' | { type: 'function'; function: { name: string } }
  }): Promise<Completion>
}
```

答案

不够窄，破坏点有两处。

第一处是 `toolChoice` 里的 `{ type: 'function'; function: { name: string } }`——这是 OpenAI 的线格式形状，它把嵌套结构原样暴露到了接口上。一个够窄的写法是 `toolChoice?: 'auto' | 'none' | { toolName: string }`，把厂商的嵌套结构挡在翻译层里。

第二处是 `stream?: boolean`。它单独看只是一个开关，但它意味着返回值 `Completion` 有两种形态（一次性的与增量的）——而一个接口的返回值有多种形态时，调用方必须判断自己拿到的是哪种。所以它不是"加一个参数"，而是改变了接口的形状（L2 第 7 条论证的就是这件事）。

而 `model`、`temperature`、`messages` 这三个不算破坏可替换性——它们是模型的通用概念，而不是某家厂商专有的。

### 练习 2：给错误分类

下面四种情况，按"遇到它该怎么办"分类，并指出哪些可重试。

① HTTP 429，响应头含 `Retry-After: 30`
② HTTP 500，响应体是内部的空指针异常信息
③ HTTP 400，错误信息说她 `max_tokens` 超过上限
④ 连接建立超时（TCP 握手阶段）

答案

① 属于"限流"，可重试，且应当等 30 秒（对方给了明确值，不要用指数退避的估算）。这是 L2 第 10 条那条决策的典型场景。

② 属于"服务端错误"，可重试，但次数应当受限——因为它是对方内部的异常，可能持续存在。这里要注意与 ① 的区别：① 等更久是有必要的（配额在恢复），② 快速重试更合理（可能只是那一个实例的问题）。

③ 属于"请求无效"，不可重试——重试一百次的结果都一样，因为问题在你的请求里。而它的正确应对是报告出来让人改参数，而不是自动重试。

④ 属于"网络不可达"，不可重试（在同一环境下）。它与其他三类的区别在于：它是环境问题而不是服务问题，所以重试不会改变任何条件。而如果它持续发生，正确的做法是失败并提示用户检查网络。

这四种的分布值得注意：两类可重试、两类不可重试，而它们各自的"等待策略"又不同（① 等 30 秒、② 快速重试）。这张分布表就是"按遇到它该怎么办分类"这句话的具体形态。

### 练习 3：找出下面代码的问题

```ts
async function callModel(messages: ChatMessage[]): Promise<string> {
  const res = await fetch(url, { method: 'POST', body: JSON.stringify({ messages }) })
  const json = await res.json()
  return json.choices[0].message.content
}
```

答案

这段代码有四个问题，它们的严重程度递增。

第一，它没有检查 HTTP 状态码。 `res.json()` 在 4xx/5xx 时通常也能成功（因为错误响应也是 JSON），于是错误信息会被当成正常响应解析——结果是"错误被当成了成功"。

第二，它没有构造错误分类。 即使它检查了状态码，直接把错误抛出去也不够——因为调用方需要知道"可不可重试"，而原始的 HTTP 错误不携带这个信息（L2 第 6 条）。

第三，它把厂商字段名写在了函数体里。 `json.choices[0].message.content` 是 OpenAI/DeepSeek 的线格式，它出现在这里意味着厂商细节不在翻译层（违反 1.4）。后果是"换一家要改多少"变成了不确定的量。

第四，也是最严重的：它的返回类型是 `string`，而工具调用被丢掉了。 一个只返回字符串的模型层无法支持工具调用——因为工具调用不在 `content` 里，而在另一个字段里。这意味着这个函数的能力被假定了：它假设模型只会返回文本。

而这第四个问题的性质与前三个不同：前三个是"实现有缺陷"，而它是"接口表达了错误的能力假设"。前者可以改实现，后者要改的是签名——而签名改了，所有调用方都要改。

### 练习 4：一句话回答

下面四个问题，每个用一句话回答。

① 为什么模型返回的工具参数是字符串？

② 为什么 `unknown` 这一错误分类必须存在？

③ 为什么"支持多 provider"不是一个值得追求的目标？

④ 为什么可重试性应当作为错误的属性，而不是由重试模块判断？

答案

① 因为模型只能生成 token，而一段文本要表达一个结构，只能以 JSON 这类字符串形式传来。

② 因为去掉它之后，实现者面对一个未见过的错误时只能"归到最像的一类"（可能错）或"让程序崩掉"，而这两者都不如"承认不知道并保守处理"。

③ 因为它的收益（可以换一家）是不确定的，而它的成本（多套翻译、错误映射、能力差异处理）是持续且发散的。

④ 因为只有产生错误的地方同时掌握状态码、响应体与响应头，而重试模块拿到的错误对象已经是被压缩过的信息。

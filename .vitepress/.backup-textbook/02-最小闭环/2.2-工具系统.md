## 本篇新词

这一篇的术语有一个共同特点：它们大多是"给模型看的"，而不是"给人看的"。这个区别会在后面反复出现，所以在开头就把它立起来。

工具（tool） 在这套系统里指的不是"一个函数"，而是一份能被模型读懂的说明加上它背后的实现。这个定义的重点在前半句：一个不能被人读懂、但能被模型读懂的东西也是工具。所以工具的"接口"有两层——给模型看的那层（名称、描述、参数 schema）与给人看的那层（实现）。

JSON Schema 是描述"一个 JSON 应该长什么样"的格式。它在工具系统里的用途是告诉模型参数该怎么填。而本篇只用它的一个极小子集（类型、必填、属性、枚举），原因是模型对复杂 schema 的理解能力有限——写得越复杂，模型填错的概率越高。

副作用等级 指一个工具被调用后，外部世界被改动的程度。它在本篇分四级（只读、可逆写、不可逆写、外部副作用）。这个分级不是分类癖好，而是权限系统与审批系统的输入（第 3 卷会用它）。

可逆性 指一个操作能不能被撤销。它与副作用等级相关但不等同：写入一个文件是"可逆写"（删除即可恢复），而发送一封邮件是"不可逆"（发出去了就收不回来）。区分它们的关键是"撤销时外部世界会不会受影响"。

注册表（registry） 指"工具名到工具定义"的映射。它的价值不在数据结构，而在它让工具可以被动态添加——也就是谁也想不到的新工具，能通过一个统一的入口进来。

扩展点 指"插件可以挂上行为的地方"。本篇的注册表就是一个扩展点：注册表本身不包含任何具体工具，具体工具由插件注册进来。

参数校验 指检查模型给的参数是否符合 schema。它是边界处校验（1.5 的模式的又一次应用）：模型的输出是外部输入，所以在进入工具实现之前必须校验。

失败是返回值 是这一篇最重要的一条设计：工具执行失败时不抛异常，而是返回一个带 `ok: false` 的结果对象。理由是模型需要看到失败——而异常会被框架层捕获，模型永远看不到。

## 第 0 节 · 学完这一篇你能做出什么

### 0.1 你会获得一条设计立场

这一篇真正要给你的东西是一条立场，它会在后面很多地方复现：

> **失败不是异常，失败是正常返回值。**

这句话听起来像风格偏好，而它是被一个约束逼出来的：模型必须能看到失败。因为如果工具执行失败了，模型需要知道"这条路不通"，才能换一条路——而这是 agent 与普通程序最大的差别之一。

而如果失败以异常的形式抛出，它会经过框架层、经过循环的错误处理、最后变成一个"这一步出错了"的通用消息——模型看到的就不再是"文件不存在"这个具体事实，而是"某处出错了"。而后者无法指导它下一步做什么。

### 0.2 你会得到三个判断工具

第一个是"工具的能力边界该定在哪"的判据。 你会学到怎么用一句话回答这个问题：这个工具能不能被模型正确地用一次？ 如果一个工具需要模型理解五个参数之间的相互作用才能用对，那么它的边界划错了。

第二个是"描述该写给谁看"的判断。 你会学到怎么检查一段工具描述：把它交给一个不知道代码的人，他能不能照着填对参数？ 如果不能，那么这段描述就没写到点子上——因为它真正的读者是模型，而模型和你一样，只能读到这段文字。

第三个是"副作用该分几级"的推导。 你会学到四级分级是怎么从"撤销时外部世界会不会受影响"这个问题推出来的。

### 0.3 你会做出一个真实产物

这一篇的产物是 `kernel/tools.ts`：一套工具契约、一个注册表、一个参数校验器、以及一个结果截断策略。

它的正确性有一个明确的验收方式：注册一个新工具不需要改任何已有的代码——只需要调用注册函数。这条性质可以立刻被检查：写一个"什么都没做"的测试工具，看能不能只靠注册就让它出现在模型可见的工具列表里。

## 第 0.5 节 · 系统视角

### 0.5.1 你在哪里

篇目坐标：第 2 卷第二篇。上一篇做出了"会说话的系统"，这一篇做出"能做事"的那一半。

层次坐标：这一篇做的是 `kernel/` 层的第二个文件。它与 `llm.ts` 是并列的——两者都不依赖对方，而 agent 循环（本卷最后一篇）同时用它们。

它在课程里的特殊位置：这是课程里第一次出现"能力边界"这个问题。前面所有篇章都在设计机制，而这一篇第一次要回答"这个机制应该提供什么能力、不该提供什么能力"。而这个问题的答案不来自技术，来自产品判断——这就是这一篇的产品线内容（0.5.3 的第三个连锁影响、以及 1.7 那一节）。

### 0.5.2 下游依赖表

| 这一篇的产物 | 谁会用到 | 用途 | 强度 |
|---|---|---|---|
| `ToolDefinition` 的形状 | 会话日志、提示词组装 | 工具定义要进日志、要进请求 | 强 |
| 副作用等级 | 第 3 卷的守卫与审批 | "哪些操作要问人"的依据 | 强 |
| `ToolResult` 的 `ok` 约定 | agent 循环 | 失败要回给模型看 | 强 |
| 参数校验器 | 所有工具 | 边界处校验 | 中 |
| 结果截断策略 | 上下文管理 | 大输出不能直接进上下文 | 中 |

这张表里第三行是最重要的：`ToolResult` 的 `ok` 约定决定了循环怎么写。如果约定是"失败抛异常"，那么循环需要一整段 try/catch；如果约定是"失败是返回值"，循环就是一条直线。一个数据形状的选择，决定了控制流的形状——这是本篇第一条连锁影响的内容。

### 0.5.3 三个连锁影响

第一个连锁影响：`ToolResult` 的形状会决定 agent 循环的形状。

这一条影响值得先看一个对比。假设工具有两种约定：

```ts
// 约定 A：失败抛异常
try {
  const output = await tool.run(args)
  messages.push(toolMessage(output))
} catch (err) {
  messages.push(toolMessage(`工具失败：${err.message}`))
}

// 约定 B：失败是返回值
const output = await tool.run(args)
messages.push(toolMessage(output.ok ? output.content : `工具失败：${output.error}`))
```

两者的差别不只是三行代码，而是"谁负责把失败变成模型能读的东西"。 在约定 A 里，那份工作在循环层——而循环层不知道工具的具体语义，所以它只能给出一句笼统的话。在约定 B 里，那份工作在工具层——而工具层知道"文件不存在"与"权限不足"的区别，所以它能给出具体的话。

而这个差别会随工具数量增长而放大。 十个工具在约定 A 下，循环里那一句笼统的错误信息会被用在十种完全不同的失败上；而在约定 B 下，每个工具自己决定怎么说。所以这个选择在第一个工具时看不出区别，在第十个工具时已经无法回头——因为约定 A 的实现里，每个工具都没有"自己描述失败"这个能力。

第二个连锁影响：副作用等级会在第 3 卷被消费，但它必须在这一篇就分级。

这一条影响与前一篇的"错误分类"是同构的：判断的依据是下游怎么用它。第 3 卷的守卫要回答"这个操作要不要问人"，而它需要的信息是"这个操作有多危险"。

所以分级不能按"它是不是写操作"来分，而要按"撤销它要付出什么"来分。这两种分法会给出不同的结果：写一个临时文件与发送一封邮件都是写操作，但撤销它们的代价完全不同。如果这一篇只做二分（读/写），那么第 3 卷就无法区分这两者——它会要求对所有写操作都问人，而那是过度询问，会导致审批疲劳（第 5 卷的话题）。

第三个连锁影响：工具的能力边界会定义这个 agent 能做什么，而它比模型能力更重要。

这一条是产品线的内容，也是最容易被技术人员忽略的。

先说一个反直觉的事实：大多数人以为 agent 的能力上限由模型决定，而实际上它由工具集决定。 因为模型无论多强，它也只能调用你给它的工具——而"给哪些工具"是一个产品判断，不是一个技术判断。

举个具体的例子：如果你不提供"搜索"工具，那么无论模型多强，这个 agent 都无法查到最新信息；而如果你提供了搜索工具但没提供"打开网页"工具，那么它只能看到搜索摘要。这两个决定的差别，比换一个更强的模型带来的差别更大。

而这个判断容易被技术人员做错的地方在于：他们倾向于按"技术上能不能实现"来划边界（"这个功能实现起来麻烦，先不做"），而正确的依据是"用户会用它来做什么"。这两者的区别在短期看不出来，在半年后会变成"这个 agent 什么都能做一点，但什么都不好用"。

## L0 要解决的问题

### 0.1 现象一：把工具写成函数，模型就会瞎填参数

如果让一个没受过训练的人来写这一层，最可能的结果是把工具写成普通的函数，然后想办法把函数的签名转成一段描述给模型。

这个做法有一个根本性的问题：函数的签名是给人看的，而模型看不懂人看的东西。 比如一个 Python 风格的类型标注 `path: str | Path` —— 人知道它可以接受两种类型，而模型看到它只会困惑。

更麻烦的是模型会瞎填参数。这不是模型"不听话"，而是它只能根据你给的描述来推断。描述里没有说的约束，就等于不存在——而它会用一个"看起来合理"的值去填。比如一个 `path` 参数，如果描述里没写"必须是相对于工作目录的路径"，模型可能会给出一个绝对路径；而工具实现里如果没做校验，这个绝对路径就会被真的使用。

### 0.2 现象二：工具执行失败时，模型看不到

这是这一篇的核心问题，前面 0.1 已经给了结论，这里补充它的成因。

默认的写法会让失败消失在框架层。 因为绝大多数语言的默认错误传播方式是异常，而异常会沿着调用栈往上走——一直走到某个 catch，然后变成一条日志。而模型看到的上下文里，那个位置是空的。

这个消失有一个具体的后果：模型不知道刚刚发生了什么，于是它会重复同一个动作。而这会形成循环——它调用、失败（但它不知道）、再调用、再失败。而如果框架有重试限制，它会因为"步数用尽"而结束；如果没有，它会一直转下去。

所以"失败是返回值"这条设计不只是为了方便，它是让循环能收敛的必要条件。

### 0.3 现象三：大输出会撑爆上下文

一个读取文件的工具，如果读了一个 5 MB 的文件，它的返回值会直接进入下一次模型请求——而那个请求会因此变得极贵，或者直接失败。

这个问题的特殊性在于它不是错误，而是成功：工具正常工作了，返回了正确的内容。所以它不会被任何错误处理拦住——它会以"成功"的身份走到请求组装那一步，然后把请求撑爆。

而这个现象的量级值得算一下：一个 5 MB 的文本大约是 125 万 token（按 4 字符/token 估算），而主流模型的上下文窗口是 128K token 量级。也就是说，一次成功的文件读取可以让系统的输入超出上限十倍。 而如果这个错误发生在账单上，它的代价是明确的——一次这样的调用，成本可能与正常调用差三个数量级。

### 0.4 现象四：没人知道一个工具到底有多危险

这一节是产品判断上的现象。在多数工具系统里，工具的危险程度是隐含的：开发者知道"这个工具会删文件"，但这个知识存在于他的脑子里，而不在代码的任何地方。

这个状态的后果在第 3 卷才会暴露：当守卫系统要判断"这个操作要不要问人"时，它没有任何可依据的信息——于是它只能对所有工具一视同仁：要么全部放行（危险），要么全部询问（疲劳）。

所以这一篇要求把那个隐含的知识写进类型里——这就是副作用等级存在的理由。

### 0.5 这一篇要回答的五个问题

把四个现象收拢，这一篇要正面回答五个问题。

一个工具由几部分组成？答案是"四样必需的加一样可选的"（1.1）。描述该写给谁看？答案是"只有模型会读它"（1.2）。schema 该有多复杂？答案是"只用最小的子集"（1.3）。失败怎么表达？答案是"作为返回值，不作为异常"（1.5）。能力边界该定在哪？答案是"以用户会用它做什么为依据，而不是以实现难度"（1.8）。

## L1 设计与原理

### 1.1 一个工具由四样东西组成，还有一样可选

先说清这四样是什么，再说为什么是四样。

第一样是名字。 它必须在工具集里唯一，而且要能被模型准确引用——这带来一个具体的命名要求：用下划线分隔的短名（`read_file` 而不是 `ReadTheFileContents`）。理由与 1.5 的"模型生成的是 token"有关：长名字会占用更多 token，而模型在生成时更可能写错一个长名字。

第二样是描述。 这一样最容易被轻视，而它实际上是工具系统里最重要的字段（1.2 整节讲它）。

第三样是参数 schema。 它告诉模型参数的形状。描述说的是"这个工具做什么"，schema 说的是"你要给我什么"。

第四样是实现。 它是一个函数，接受校验后的参数与一个上下文对象，返回一个结果。

```ts
/**
 * 一个工具的定义。
 *
 * 前三样是给【模型】看的，第四样是给【运行时】用的。
 * 这个区分很重要：不要试图让前三样也"对人友好"——那会让它们对模型不友好。
 */
export interface ToolDefinition<A = Record<string, unknown>> {
  /** 唯一名。用下划线短名，因为模型要逐 token 生成它。 */
  readonly name: string
  /** 给模型读的一两句话。写法见 1.2。 */
  readonly description: string
  /** 参数的形状。只用最小子集，见 1.3。 */
  readonly parameters: JsonSchema
  /**
   * 副作用等级。
   *
   * 它不由工具自己声明，而由【注册它的人】声明——因为它是权限判断的依据，
   * 而"这个操作有多危险"是部署方的判断（1.8）。
   */
  readonly sideEffect: SideEffectLevel
  /** 实现。参数已校验，工具不需要再检查类型。 */
  readonly run: (args: A, ctx: ToolContext) => Promise<ToolResult>
}
```

第五样（可选的）是 `resumable` 标记——它表示"这个工具的执行可以从中断处继续"。本课程暂时不用它，所以它是可选的、默认关闭。

为什么是这四样而不是别的数量，可以用一个反推来回答：把其中任何一样去掉，会坏掉什么。去掉名字，模型无法引用；去掉描述，模型不知道什么时候用它；去掉 schema，模型不知道参数怎么填；去掉实现，它就不是工具而是文档。四样都不可去，所以是四样。

### 1.2 描述是写给模型看的

这一节是整篇里最实用的一节。先给出一条判据，再给几个例子。

判据是：

> **把这段描述交给一个不知道代码的人，他能不能照着填对参数？**

这个判据之所以有效，是因为它把"读者"从"已经知道这个工具怎么工作的你"换成了"只知道这段文字的人"——而模型恰好就是后者。它看不到你的实现、看不到你的意图、看不到你上周讨论时说的话，它只能读到这段文字。

第一个例子是一段不合格的描述：

```
read_file —— 读取文件
```

它的问题不是说错了，而是说得太少。具体缺三样：路径相对于什么（工作目录还是根目录）、目录会怎样（报错还是列出内容）、大文件会怎样（全部返回还是截断）。而模型遇到这三个不确定时不会停下来问，它会猜。

第二个例子是一段合格的描述：

```
read_file —— 读取一个文本文件的内容。

参数 path 是相对于工作目录的路径。如果 path 指向目录，会返回错误而不是列出内容。
超过 20000 字符的文件会被截断（保留开头与结尾）。

何时使用：当你需要查看某个文件的实际内容时。
何时不用：只需要知道文件是否存在或有哪些文件时，用 list_dir。
```

它比第一段长很多，而每一句都在消除一个具体的不确定。 最后两行（何时使用/何时不用）尤其重要——因为工具之间的选择也是模型要做的判断，而描述里如果不说"什么时候不要用我"，模型会在多个相似工具之间随机挑。

第三个例子是"过度描述"：

```
read_file —— 读取文件。本工具采用流式读取，内部使用 fs.createReadStream，
支持 UTF-8 与 GBK 编码，会在读取失败时重试三次，缓存命中……
```

它的问题是写了模型不需要知道的实现细节。 模型不关心你用了什么 API——而那些细节会挤占真正有用的信息的位置（因为描述也占 token）。

三段对比给出的规则是：描述里只写"模型做决定需要的信息"——也就是"这是什么、参数是什么、什么时候用、什么时候别用、失败了会怎样"。实现细节一句都不要写。

### 1.3 JSON Schema 只用最小子集

先说为什么要有 schema：因为描述是自然语言，而自然语言无法表达"这个字段必须是这三个取值之一"。所以参数的形状需要一个正式的描述——而这个正式的描述就是 schema。

再说为什么只用最小子集：因为schema 越复杂，模型填错的概率越高。这不是猜测，而是由"模型只能生成 token"推出的——它要在生成每一个参数值时"记住"全部的约束，而约束越多，忘记其中一个的可能性越大。

所以本课程只用五样：

| 能力 | 写法 | 用途 |
|---|---|---|
| 类型 | `{ type: 'string' }` | 最基本的约束 |
| 必填 | `{ required: ['path'] }` | 哪些字段不能省 |
| 属性 | `{ properties: {...} }` | 对象的字段 |
| 枚举 | `{ enum: ['a', 'b'] }` | 取值必须在这几个里 |
| 数组 | `{ type: 'array', items: {...} }` | 列表 |

不用的是那些"表达力更强但模型更难理解"的：嵌套的条件约束（`oneOf`/`allOf`）、正则约束、数值范围以外的复杂校验、以及递归结构。

这个取舍的理由可以用一句话总结：schema 是给模型看的文档，而不是给校验器用的语言。 如果你需要一个校验器能表达的约束（比如"这个字符串必须匹配某个正则"），那个约束应当由工具实现自己检查，并在失败时返回一条清晰的错误——因为那样模型能看到"你给的路径格式不对"，而 schema 校验失败只能给出"参数不符合 schema"。

### 1.4 参数校验：递归、报错要说清位置

校验器要做的事只有一件：在参数进入工具实现之前，确认它符合 schema。

位置很重要（1.5 的模式）：如果校验发生在工具实现内部，那么每个工具都要写一遍校验代码，而写法会各不相同——而校验不一致的后果是"有的工具挡得住的输入，另一些挡不住"。所以校验必须在注册表这一层统一做。

实现上有一个容易出错的地方：嵌套结构。 参数可能是一个对象里套数组，数组里套对象。校验器必须递归下去，而不是只看顶层——因为"顶层是对象"这个检查通过之后，坏数据仍然可能在深处的某一项里。

```ts
/**
 * 按 schema 校验参数。
 *
 * 它是递归的：对象要逐属性校验，数组要逐元素校验。
 * 只校验顶层是【不够】的——坏数据常在深处。
 *
 * @param schema 参数的 schema
 * @param value 模型给的参数
 * @param path 当前路径（用于报错定位，递归时累加，如 "filters.tags[2]"）
 * @returns '' 表示通过；否则返回一条【说清位置】的错误
 */
export function validate(schema: JsonSchema, value: unknown, path = ''): string {
  if (schema.type === 'object') {
    if (value === null || typeof value !== 'object' || Array.isArray(value)) {
      return `${path || '参数'} 应当是对象`
    }
    const obj = value as Record<string, unknown>
    for (const key of schema.required ?? []) {
      if (!(key in obj)) return `缺少必填参数 ${path ? `${path}.` : ''}${key}`
    }
    for (const [key, sub] of Object.entries(schema.properties ?? {})) {
      if (key in obj) {
        // 递归：把路径带上，这样报错能指到具体的字段
        const why = validate(sub, obj[key], path ? `${path}.${key}` : key)
        if (why) return why
      }
    }
    return ''
  }
  if (schema.type === 'array') {
    if (!Array.isArray(value)) return `${path || '参数'} 应当是数组`
    if (schema.items) {
      for (const [i, item] of value.entries()) {
        const why = validate(schema.items, item, `${path}[${i}]`)
        if (why) return why
      }
    }
    return ''
  }
  if (schema.type === 'string' && typeof value !== 'string') return `${path} 应当是字符串`
  if (schema.type === 'number' && typeof value !== 'number') return `${path} 应当是数字`
  if (schema.type === 'boolean' && typeof value !== 'boolean') return `${path} 应当是布尔值`
  if (schema.enum && !schema.enum.includes(value as string)) {
    return `${path} 只能是 ${schema.enum.join(' / ')} 之一，收到 ${String(value)}`
  }
  return ''
}
```

这段代码里有一处细节值得指出：`path` 参数。 它存在的唯一目的是让报错能定位。如果校验失败只说"参数不符合 schema"，那么模型（和人）都不知道该改哪一个字段；而带上路径之后，错误会说"`filters.tags[2]` 应当是字符串"——这就是 1.5 的"边界处解析"在参数校验上的同一条原则。

### 1.5 失败不是异常，失败是返回值

这一节是整篇的核心。先给结论，再给三条理由，最后给它的代价。

结论：工具执行失败时返回 `{ ok: false, error: '...' }`，而不抛异常。

```ts
export type ToolResult =
  | { readonly ok: true; readonly content: string }
  | { readonly ok: false; readonly error: string }
```

第一条理由是模型必须能看到失败。 前面 L0 的 0.2 讲了成因：异常会被框架层捕获，而模型看到的上下文里那个位置是空的。而空的后果是它会重复同一个动作——因为它不知道刚刚失败了。

第二条理由是失败的信息应当由最懂它的人写。 工具实现知道"文件不存在"与"权限不足"的区别，而框架层不知道。如果失败以异常抛出，那么最后写下那句话的是框架层——而它只能写"工具失败了"。信息在传播过程中被压缩掉了，正如 1.5 的"在边界处解析"所说：错误信息能带走多少上下文，取决于你在哪里发现它。

第三条理由与控制流有关。 在"失败是返回值"的约定下，循环是一条直线：

```ts
const result = await tool.run(args, ctx)
// 无论成功失败，都要把结果回给模型——这是同一条路径
messages.push(toolResultMessage(call.id, result.ok ? result.content : result.error))
```

而在"失败抛异常"的约定下，循环需要一个 try/catch，而那个 catch 里要做的事（把失败变成消息）与 try 里要做的事（把成功变成消息）几乎是同一个动作。代码的形状反映设计的形状——当两条路径做的事几乎相同时，它们就该是一条路径。

最后说代价，而它有两个。

第一个代价是"忘记检查 `ok`"这件事编译器不会拦。 因为 `ok` 是一个普通字段，所以调用方可以直接读 `result.content` 而不检查 `ok`——而 TypeScript 可以帮上忙：如果用可辨识联合（上面那个 `ToolResult` 的定义），那么在检查 `ok` 之前访问 `content` 会报类型错误。所以这个代价是可以被消除的，而消除它只需要把类型定义成联合而不是"一个带可选字段的对象"。

第二个代价是它不适用于所有失败。 如果工具实现里出现了一个真正的编程错误（比如访问了 undefined 的属性），那仍然会抛异常——而那是正确的，因为编程错误不应该被伪装成"工具失败"回给模型。所以约定是"可预期的失败是返回值，不可预期的错误仍然抛"。这条边界值得写进工具实现的写法里：要返回的失败是"这个操作没能完成"，要抛的异常是"这段代码写错了"。

### 1.6 结果截断：为什么是头 80% 加尾 20%

先说为什么必须截断：L0 的 0.3 给了量级——一次成功的文件读取可以把请求撑爆十倍。

再说怎么截断。 最简单的做法是"取前 N 个字符"，而它有一个问题：很多内容的结论在结尾。比如一个命令的输出，开头是过程，结尾是结果；一个日志文件，最新的在最后。所以只留头会丢掉最可能有用的一半。

本课程的做法是"头 80% + 尾 20%"，并在中间标注截断了多少：

```ts
/**
 * 截断过长的工具输出。
 *
 * 保留头【与】尾，而不是只保留头。
 *   理由：很多内容的结论在结尾（命令的结果、日志的最新一条），
 *   只留头会丢掉最可能有用的一半。
 *
 * @param text 原始输出
 * @param limit 上限（字符数）
 * @returns 截断后的文本；未超限时原样返回
 */
export function truncate(text: string, limit: number): string {
  if (text.length <= limit) return text
  const head = Math.floor(limit * 0.8)
  const tail = limit - head
  const omitted = text.length - limit
  return (
    text.slice(0, head) +
    `\n\n…（此处省略 ${omitted} 个字符，共 ${text.length} 个）\n\n` +
    text.slice(text.length - tail)
  )
}
```

那个省略说明的写法值得注意：它不只说"省略了"，还说省略了多少、总数多少。这三样信息合起来让模型能判断"我是不是需要换个方式读它"——比如它可以选择用 `read_file` 带一个范围参数再读一次。而如果只写"输出过长，已截断"，模型没有任何依据做下一步判断。

这个设计的一般形式与 1.5 是同一条：给下游的信息要携带"下一步需要的东西"。 错误信息要带定位（1.4），截断说明要带数量（1.6），失败要带原因（1.5）。

### 1.7 路径安全：最小防线

先说清这一节的范围：它不打算做一个安全的沙箱（那是第 3 卷的内容），而只做最小防线——挡住最常见的一类事故。

最常见的一类事故是路径穿越：模型给了一个 `../../etc/passwd` 这样的路径，而工具直接用了它。这个事故的成因不是恶意，而是模型的推测：它看到别的工具用相对路径，于是它也用——而它不理解"工作目录"这个概念意味着什么。

最小防线的做法是：把相对路径解析成绝对路径，然后确认它仍在工作目录之下。

```ts
/**
 * 把模型给的路径解析为工作目录内的绝对路径。
 *
 * 这是一个【最小防线】，不是沙箱：
 *   它挡住的是"路径穿越"这一类最常见的事故，而不是全部越界访问。
 *   真正的隔离要靠权限与沙箱（第 3 卷）。
 *
 * @param workspace 工作目录（绝对路径）
 * @param input 模型给的路径
 * @returns 解析后的绝对路径
 * @throws 当解析结果落在工作目录之外时
 */
export function resolveInside(workspace: string, input: string): string {
  const base = resolve(workspace)
  const target = resolve(base, input)
  // 必须比较带分隔符的前缀，否则 /work-evil 会被误判为在 /work 之内。
  if (target !== base && !target.startsWith(base + sep)) {
    throw new Error(`路径越界：${input} 解析到 ${target}，不在工作目录内`)
  }
  return target
}
```

这段代码里那个注释是这一节最值钱的一行：比较前缀时必须带上分隔符。如果不带，`/work-evil` 会通过检查（因为它的字符串以 `/work` 开头）——而这是一个真实的、常见的漏洞。它的成因是"看起来在做正确的事"：检查了前缀，写了注释说"检查是否在工作目录下"，而实际的后缀比较少了一个字符。

### 1.8 副作用等级：四级，以及它为什么是四级

这一节回答 0.4 那个问题，也是本篇产品线的落点。

先说分级的依据。前面 0.5.3 已经给过一句：撤销它要付出什么。现在把它具体化——按"撤销时外部世界会不会受影响"分：

| 级 | 名字 | 撤销的代价 | 例子 |
|---|---|---|---|
| 0 | `readonly` | 无需撤销 | 读文件、搜索、列目录 |
| 1 | `reversible` | 删除自己写的东西即可 | 写工作区内文件、创建目录 |
| 2 | `irreversible` | 外部世界已被改动 | 删除文件、覆盖已有数据、执行迁移 |
| 3 | `external` | 无法撤销 | 发邮件、调付费 API、推送到远端仓库 |

第二行与第三行的区别是这一节的关键：写一个新文件与删除一个已有文件都是"改动文件系统"，但撤销它们的代价完全不同——前者删除即可，而后者需要"把删掉的内容恢复"，而那需要它曾经被备份过。所以它们不在同一级。

第三行与第四行的区别同样关键：删除一个文件是"我能恢复（如果我有备份）"，而发一封邮件是"收件人已经看到它了"。后者的不可逆性不在于技术，而在于它已经离开了你的控制范围。

四级分完，它的用途是明确的：第 3 卷的守卫会按等级决定放行策略——0 级自动放行，1 级先问一次，2 级每次必问，3 级要求显式确认。而这正是 0.4 说的"把隐含的知识写进类型里"。

最后要说明这一节的边界：分级是声明式的，也就是说它可能不准。一个工具声明自己是 `readonly`，而它的实现里却偷偷写了文件——这种情况类型系统拦不住。

所以这条设计必须与沙箱配合：声明决定"问不问人"，而沙箱决定"能不能做"。如果两者只有其一，都会留下一个缺口——只有声明没有沙箱，声明错了就没救；只有沙箱没有声明，就会对所有操作一视同仁地限制，而那会损害可用性。这个"声明 + 强制"的配对，是第 3 卷安全设计的核心模式，而它第一次出现在这里。

### 关于第 5 条的完整论证（失败为什么必须走返回值）

第 5 条是这一篇最重要的决策，所以它的论证要比 1.5 更完整——1.5 讲的是"是什么"，这里讲"如果选另一个会怎样"。

先设想替代方案的实际运行。 假设工具失败时抛异常，那么异常会经过三层：工具实现 → 注册表的调用包装 → agent 循环。关键是第二层：注册表那层通常有一个统一的包装（用于计时、日志、结果处理），而它最容易写成这样：

```ts
try {
  return { ok: true, content: await tool.run(args, ctx) }
} catch (err) {
  logger.warn(`工具 ${tool.name} 失败`, err)
  throw err   // 或者 return { ok: false, error: String(err) }
}
```

如果它重新抛出，那么循环层要接住——而循环层只知道"有个工具失败了"，不知道是哪个（除非它把异常包装起来，而那又是一层代码）。如果它在这里转成 `ok: false`，那么它就在替工具写错误信息——而它写不出"文件不存在"这样的具体原因，因为异常对象里可能只有一句通用的消息。

再看第二层为什么容易写成这样。 因为在这个位置，写代码的人并不知道每个工具会抛出什么——语言层面也没有告诉他（异常类型不是签名的一部分）。所以"让注册表统一处理失败"这个设计，在类型上就是不完整的：它缺少"这个工具会以哪些方式失败"这个信息。

而返回值方案把这个信息补上了：`ToolResult` 的 `ok: false` 分支是一条类型层面的通道，它强制每个工具实现去填那个 `error` 字段——而填的时候，工具实现不得不回答"这个失败该怎么说"。 这就是为什么这个决策的实质不是"方便不方便"，而是"谁负责把失败翻译成模型能读的话"。

最后要说明它的一条隐含要求：如果走返回值，那么工具实现里那些"可预期的失败"必须被显式地转成 `ok: false`。而这需要写代码的人知道哪些失败是可预期的——比如"文件不存在"是可预期的，而"参数是 undefined"不是。所以这个决策把一个更早的问题推到了台面上：在写工具实现之前，先想清楚"它会以哪些方式失败"。

### 关于第 9 条的完整论证（四级与二分的实际差别）

第 9 条选了四级，而二分（读/写）更简单。所以要论证多出来的两级带来了什么。

先看二分法在第 3 卷会遇到什么。 二分的规则是"读操作放行，写操作问人"。而在这个规则下，一个"发送消息"的工具会被问人——这是对的；而一个"写临时文件"的工具也会被问人——而这是过度的。后果是用户在一次任务里被反复询问"可以写这个临时文件吗"，而当询问次数超过某个阈值后，用户会开始不看内容直接点同意。

那个后果的性质值得说清：它不只是"体验差"，而是审批机制本身失效——因为"用户点了同意"这件事不再意味着"用户看过并认可了"。所以过度询问的危害是它把一道真实的防线变成了一道形式上的防线。

再看三级与四级的区别。 如果只分三级（读、写、不可逆），那么"删除文件"与"发邮件"会被归到同一级。而它们在第 3 卷需要的处理不同：删除文件可以在"用户确认过这个操作类型"之后批量放行（因为它仍然是本地的、可恢复的），而发邮件必须每次都显式确认（因为它已经离开了你的控制）。

所以多出来的那一级，实际上是为"能不能批量批准"这个问题准备的。 而这个问题的答案取决于"操作是不是离开了本地"——而这是一个与"危险程度"不同的维度。这也是为什么它值得单独一级，而不是并入"不可逆"。

最后说明这个决策的成本：四级的定义比二级复杂，而分类时更容易犹豫（"这个操作算三级还是四级"）。但犹豫本身是有用的——它意味着分类者在认真考虑"这个操作的后果是什么"，而那个思考过程正是这一节想要的。

## L3 实现（施工图）

### 3.1 文件结构

```ts
// kernel/tools.ts
// ┌─ 契约段 ──────────────────────────────────────────
// │  JsonSchema / ToolDefinition / ToolResult / SideEffect
// ├─ 校验段 ──────────────────────────────────────────
// │  validateArgs（递归，报错带路径）
// ├─ 注册表段 ────────────────────────────────────────
// │  ToolRegistry（register / list / run）
// ├─ 结果段 ──────────────────────────────────────────
// │  truncate（头 80% + 尾 20%）
// └─ 边界段 ──────────────────────────────────────────
//    resolveInside（最小防线）
```

五段的结构本身是一个设计，而它与 `llm.ts` 的五段有一个刻意的差别：`llm.ts` 的分段里有一段是"翻译段"（厂商细节的唯一出口），而这里没有对应的一段——因为这一篇的产物不与任何外部厂商对话。

但这里多出了"校验段"与"注册表段"，它们对应两个新问题：模型给的参数可能不对（校验），而工具集是可变的（注册表）。所以"文件里有哪几段"这件事本身就是一篇文档的目录：段落的增加意味着新的失败来源被承认了。

### 3.2 契约段

先看 schema 的子集。关于"为什么只用五种能力"在 1.3 讲过，这里给出它的类型定义——而类型定义本身就是那条约束的执行者：

```ts
/**
 * 本系统支持的 JSON Schema 子集。
 *
 * 这是【白名单】，不是"完整 JSON Schema 的一个子类型"：
 *   上面没有的字段（$ref / oneOf / allOf / patternProperties…）不是"暂不支持"，
 *   而是【禁止使用】——因为模型对它们的理解能力没有保证。
 */
export interface JsonSchema {
  readonly type: 'object'
  readonly properties: Readonly<Record<string, JsonSchemaProperty>>
  readonly required?: readonly string[]
}

export interface JsonSchemaProperty {
  readonly type: 'string' | 'number' | 'boolean' | 'array' | 'object'
  readonly description: string
  readonly enum?: readonly string[]
  /** 仅当 type 为 array 时有意义 */
  readonly items?: JsonSchemaProperty
}
```

`description` 是必填的，这一条与 JSON Schema 规范不同（规范里它是可选的）。理由在于读者：规范的读者是校验器，而这里的读者是模型——而模型没有"看字段名猜用途"的能力，它只能读描述。所以在这个子集里，一个没有描述的属性是一个模型看不懂的属性。

再看工具定义与结果：

```ts
export type SideEffect =
  | 'readonly'      // 0 级：无需撤销
  | 'reversible'    // 1 级：删除自己写的东西即可
  | 'irreversible'  // 2 级：外部世界已被改动
  | 'external'      // 3 级：无法撤销

export interface ToolDefinition<A = Record<string, unknown>> {
  /** 唯一名。下划线短名——模型要逐 token 生成它（1.1）。 */
  readonly name: string
  /** 给模型读的一两句话（1.2）。 */
  readonly description: string
  /** 参数形状。只用子集（1.3）。 */
  readonly parameters: JsonSchema
  /**
   * 副作用等级。由【注册方】声明，不由工具自己声明（L2 第 10 条）。
   * 默认值是 'readonly' 还是 'irreversible'？见 3.4 的说明。
   */
  readonly sideEffect?: SideEffect
  /** 真正做事的那段代码。参数已经过解析与校验。 */
  run(args: A, ctx: ToolContext): Promise<ToolResult> | ToolResult
}

export type ToolResult =
  | { readonly ok: true; readonly content: string }
  | { readonly ok: false; readonly error: string; readonly internal?: true }
```

**`internal?: true` 这个可选字段值得单独说清。** 它的存在是为了区分两类失败：`ok: false` 而没有 `internal` 的是"这个操作没能完成"（可预期的失败，由工具实现自己描述）；带 `internal` 的是"这段代码写错了"（实现里抛出的异常，被注册表接住并标注）。为什么要保留这个区分：因为前者对模型有意义（它可以换个方式做），而后者对模型没有意义（它无论怎么做都会失败）——而人看到的应当不同：前者是"工具报告的问题"，后者是"这里有 bug，去看日志"。如果注册表把异常直接藏在 `{ok:false, error:'工具失败'}` 里，这个区别就丢了。

这一处也回答了 1.5 那条边界的一个细节：1.5 说"可预期的失败是返回值，不可预期的错误仍然抛"。那么注册表该不该接住那个异常？本课程的选择是"接住，但标注"——理由是工具实现抛出的异常如果真的向上冒出，就会破坏"循环是一条直线"这个形状（0.5.3）；而标注保留了它"这不是一次正常失败"的身份。

```ts
export interface ToolContext {
  /** 工作目录。工具的路径参数必须落在它之下（1.7）。 */
  readonly workspace: string
  /** 结果进入模型之前的字符上限（1.6）。 */
  readonly maxResultChars: number
}
```

`ToolContext` 只有两个字段，而这是刻意的收窄。 很容易想到往里加东西：日志器、取消信号、当前会话 id、权限检查器……而每一个都会让"写一个工具"这件事需要知道更多东西。当前的判断是：这两个字段都是"工具实现无法自己知道"的——工作目录由部署决定，上限由上下文预算决定。而日志与取消属于运行时的关注点，它们通过别的机制接入（第 3 卷）。

### 3.3 校验段

```ts
/**
 * 递归校验参数是否符合 schema。
 *
 * 返回【字符串】而不是抛异常，也不返回 boolean：
 *   - 返回 boolean 就丢掉了"哪里不对"（1.4 的教训）；
 *   - 抛异常会让调用方写出 try/catch，而校验失败是可预期的失败（1.5）。
 *   返回 '' 表示通过。
 *
 * @param schema 参数的形状
 * @param value 模型给的参数（已经过 parseArguments）
 * @param path 当前所在的位置，用于报错定位。调用方从 '' 开始
 * @returns 错误信息；'' 表示通过
 */
export function validateArgs(schema: JsonSchema, value: unknown, path = ''): string {
  if (value === null || typeof value !== 'object' || Array.isArray(value)) {
    return `${path || '参数'} 应当是一个对象`
  }
  const obj = value as Record<string, unknown>
  for (const key of schema.required ?? []) {
    if (!(key in obj)) return `缺少必填参数 ${join(path, key)}`
  }
  for (const [key, prop] of Object.entries(schema.properties)) {
    if (!(key in obj)) continue // 非必填且未提供：跳过
    const err = validateProp(prop, obj[key], join(path, key))
    if (err) return err
  }
  // 未知字段要报出来还是不报？见下面那段说明。
  return ''
}
```

`path` 的写法有一个细节：数组下标与字段名要用同一种表示，否则报错会变成"两套定位语法"。本课程统一成 `tags[2]` 这一种形式。

而这个形式的上限与子集的一个限制有关：`JsonSchemaProperty` 里没有 `properties`（3.2 只用五种子集能力），所以一个 `object` 类型的字段不会被递归校验，路径也就最多只到"顶层字段 + 数组下标"这一层。这是一个刻意的取舍：递归校验会让 schema 的复杂度上不封顶，而模型填错嵌套结构的概率本来就高于填错顶层字段——与其把描述写复杂，不如让工具少接嵌套参数。

未知字段的处理是一个真实的取舍。 如果模型的参数里多了一个 schema 里没有的字段，有两种做法：忽略它（宽容），或者报错（严格）。本课程选严格，理由与 1.3 的"schema 只用最小子集"是同一条：多出来的字段通常说明模型理解错了这个工具，而忽略它会让错误延后到"参数不符合预期却没人知道"的地方——而那正是 L0 的 0.1 说的那种事故。

### 3.4 注册表段

注册表要回答三个问题：谁提供工具、谁能看到工具、以及调用一个工具要走哪几步。三个问题分别对应 register / list / run。

```ts
export class ToolRegistry {
  #tools = new Map<string, ToolDefinition>()

  /**
   * 注册一个工具。
   *
   * 返回【卸载函数】，而不是注册结果码。
   *   这是本课程的一条通用约定（注册是 effect）：每一个注册动作都带一个配对的撤销动作。
   *   在 2.3 篇里它会被接进插件的生命周期，而 2.4 篇会让它成为一个扩展点。
   *
   * @param def 工具定义
   * @returns 卸载函数
   * @throws 当名字与已注册的工具重名时
   */
  register(def: ToolDefinition): () => void {
    if (this.#tools.has(def.name)) {
      throw new Error(`工具名重复：${def.name}`)
    }
    this.#tools.set(def.name, def)
    return () => {
      this.#tools.delete(def.name)
    }
  }

  /**
   * 给模型看的工具清单。
   *
   * 返回的对象里【不含 run】——它必须能被 JSON 序列化。
   *   两个理由：它要进请求（模型要读它），也要进日志（2.7 的"模型可见 ⟺ 可重建"）。
   */
  list(): readonly { name: string; description: string; parameters: JsonSchema }[] {
    return [...this.#tools.values()].map(({ name, description, parameters }) => ({
      name,
      description,
      parameters,
    }))
  }

  /**
   * 调用一个工具。这是工具唯一的入口，前置的解析与校验都在这里。
   *
   * @param name 模型给出的工具名
   * @param rawArguments 模型给出的原始参数字符串（2.1 的 ToolCall.arguments）
   * @param ctx 运行上下文
   * @returns 结果；本方法对模型的任何输入都不抛异常
   */
  async run(name: string, rawArguments: string, ctx: ToolContext): Promise<ToolResult> { /* 见 3.4.2 */ }
}
```

`register` 抛异常而 `run` 不抛，这个不对称是刻意的。 重名是一个编程错误（两个插件抢同一个名字，得由人来解决），所以它必须在启动时就炸掉而不是等模型调用时才失败（"误配置在最早可解析处失败"）。而 `run` 面对的是模型的输出，那是一个外部输入，所以它永不抛。

#### 3.4.1 为什么 `sideEffect` 的默认值不是 `'readonly'`

默认值的选择在这里是一个安全问题：默认成"最危险的那一级"还是"最无害的那一级"？

- 默认 `'readonly'`：未声明的工具会被当作只读。**后果是第 3 卷的守卫会直接放行一个可能删文件的工具**——而"忘记声明"恰恰是最可能发生的情况。
- 默认 `'irreversible'`：未声明的工具会被当作不可逆。后果是它会每次都被问人——吵，但安全。

本课程选后者，理由与 2.1 的 `unknown` 不可重试是同一条：面对信息缺失时保守处理。而它的代价是可见的：开发阶段你会被反复询问"可以执行这个工具吗"，直到你补上声明——而这个"烦"正是提醒你补声明的机制。

#### 3.4.2 `run` 的五步

```ts
async run(name, rawArguments, ctx) {
  const def = this.#tools.get(name)
  // ① 未注册的工具名
  //   返回失败而不是抛错：模型调用一个不存在的工具是可预期的
  //     （L2 第 12 条：能力查询与"模型会猜"这件事的取舍）。
  if (!def) return { ok: false, error: `没有名为 ${name} 的工具。可用的工具见工具清单。` }

  // ② 解析（复用 2.1 的 parseArguments）
  let args
  try {
    args = parseArguments(rawArguments, name)
  } catch (err) {
    // 解析失败已经是 LLMError，它的 message 已带工具名与原始串（2.1 承诺 10）
    return { ok: false, error: err.message }
  }

  // ③ 校验（含未知字段）
  const bad = validateArgs(def.parameters, args)
  if (bad) return { ok: false, error: `${name} 的参数不合法：${bad}` }

  // ④ 执行。实现内部的异常在这里被接下并标注
  let result
  try {
    result = await def.run(args, ctx)
  } catch (err) {
    return { ok: false, error: `${name} 的实现抛出了异常：${err?.message ?? err}`, internal: true }
  }

  // ⑤ 截断。成功与失败【都要】过这一道
  return result.ok
    ? { ok: true, content: truncate(result.content, ctx.maxResultChars) }
    : { ok: false, error: truncate(result.error, ctx.maxResultChars), ...(result.internal ? { internal: true } : {}) }
}
```

这五步的顺序不是随便排的，它按"信息在哪一刻还完整"排：解析在校验之前（因为校验需要对象）、校验在执行之前（因为执行需要合法参数）、截断在最后（因为它是关于"给模型看多少"的决定，与语义无关）。

第 ⑤ 步里的"成功与失败都要截断"容易被写漏。 直觉上"错误信息不会很长"，而它会：一个命令的失败输出（比如编译错误）可能上万行——而它同样是给模型看的。"凡是给模型的都要过这一道"是一条比"结果要截断"更准确的规则，因为前者管的是所有出口，后者只管了其中一个。

### 3.5 结果段与边界段

这两段的实现已经在 1.6 与 1.7 里给过（`truncate` 与 `resolveInside`），这里只补一条它们在本篇的位置关系：

两个函数都不是"工具系统的一部分"，而是"工具系统与外部世界的两个接口"。 `truncate` 管的是通向模型的出口，`resolveInside` 管的是通向文件系统的入口。它们之所以放在同一个文件里，是因为它们都是"注册表在调用实现之前/之后"要做的事——而这个位置正好是唯一能同时管住所有工具的地方。如果让每个工具自己截断、自己检查路径，那么总有一个工具会忘。

### 3.6 验收判据

以下是"这一篇做完了"的十条判据。它们全部可以被检查，其中八条可以被自动检查。

| # | 判据 | 怎么检查 |
|---|---|---|
| 1 | 注册一个新工具不需要改任何已有代码 | 写一个只返回固定字符串的工具，只调用 `register`，它出现在 `list()` 里 |
| 2 | `register` 返回的卸载函数调用后，工具从 `list()` 消失 | 调一次卸载再 list |
| 3 | 工具重名时 `register` 抛错 | 注册两次同名工具 |
| 4 | `list()` 的输出能被 JSON 往返 | `JSON.parse(JSON.stringify(list()))` 后结构一致 |
| 5 | 参数不是合法 JSON 时 `run` 返回 `ok:false`（不抛） | 传 `'{"path":"a"'` |
| 6 | 参数缺必填字段时，错误信息里含字段名 | 传 `'{}'` |
| 7 | 参数里有多余字段时被拒绝 | 传一个 schema 之外的键 |
| 8 | 工具实现抛异常时，结果是 `ok:false` 且带 `internal` | 注册一个会抛的工具 |
| 9 | 超过上限的结果被截断，且说明里含省略的字数 | 返回一个长字符串，检查首尾都在、中间有说明 |
| 10 | 未注册的工具名返回 `ok:false`，且提示里提到可用工具 | 调用 `run('nope', '{}', ctx)` |

第 8 条与第 5、6 条的区别是这一组判据里唯一的"语义"判据：它们都返回 `ok:false`，但第 8 条额外要求 `internal`。如果判分器只看 `ok`，那么"实现抛异常"与"参数不合法"就会被混成同一件事——而这正是这一篇要区分的两类失败。

### 3.7 实现顺序

按这个顺序做，每一步都能独立验证：

1. **契约段**（3.2）——先只写类型，不写实现。因为类型定错了，后面全部要重写。
2. `truncate`（1.6 已给）——它是纯函数，可以立刻单独测。
3. `validateArgs`（3.3）——先写"必填 + 类型"，再补 `enum` 与 `items`。每补一项加一个用例。
4. `resolveInside`（1.7 已给）——注意那条"带分隔符的前缀"的比较。
5. `ToolRegistry.register` / `list`——此时可以用判据 1–4 验证。
6. `ToolRegistry.run` 的 ①–③ 步——五步里最容易的一步是 ①，最难的是 ③（因为校验的报错要能定位）。
7. `run` 的 ④–⑤ 步——④ 要区分"抛异常"与"返回失败"，⑤ 要保证"两条路径都截断"。
8. 回到判据 1–10 逐条过，尤其是第 8 条（`internal`）。

## L4 运行与验证

### 4.1 三层验证

验证"工具系统做对了"不能只靠读代码，因为它的多数性质是行为性质（对某个输入给出什么结果）。所以这里用三层：

第一层是自检：契约测试。 上面十条判据都可以写成对 `run`/`list`/`register` 的调用。它们的特点是不需要模型、不需要网络、不需要文件系统——`resolveInside` 与 `truncate` 是纯函数，`validateArgs` 也是。

第二层是外部否定：写一个新工具，看能不能零改动注册。 这一层与第一层的区别是它检查的是"扩展点是否成立"，而不是"某个函数是否正确"。做法很直接：写一个 `echo` 工具（把参数原样返回），只调用 `register`，然后确认模型可见的清单里出现了它。如果这一步需要改 `tools.ts` 的任何一行，那么 0.3 的验收方式就已经失败了——而它失败得很安静（你改了一行，一切照常工作）。

第三层是真实运行：让一个真实模型用一次。 这一层检查的是描述与 schema 是否真的能被模型读懂（1.2）。它的做法是给模型两个工具（`read_file` 与 `echo`），然后让它"读一下 a.txt 的前 3 行"。观察点不是"它成功了吗"，而是"它第一次填的参数对不对"——如果它填错了，看错在哪：名字不认识、描述没说清、还是 schema 太复杂。

三层的关系是递进的：第一层证明机制对不对，第二层证明它能被扩展，第三层证明它能被用。只做第一层是最常见的情况，而它恰好证明不了"这个工具系统能不能用"——因为一个工具系统的价值在于"别人能给它加工具并且模型会用"。

### 4.2 一次完整的验证流程

```powershell
# ① 契约测试（不需要网络与模型）
node tests/t4-build.mjs                                                  # 用你的实现
$env:IMPL_TOOLS='../grade/tools.reference.mjs'; node tests/t4-build.mjs   # 用参考答案
Remove-Item Env:\IMPL_TOOLS

# ② 负向验证：判分器本身有没有鉴别力
node grade/negative-check-tools.mjs

# ③ 零改动注册（第二层）：现成的脚本，它只调了一次 register
node kit/src/echo-demo.mjs

# ④ 真实运行（需要 key）：让模型用一次这个工具
#    观察点不是成败，而是"它第一次填对了参数吗"
```

第 ① 步与第 ② 步都要做，而这个组合是有讲究的：第 ① 步只能证明"参考答案能通过"，它不能证明判分器能失败。而一个只会给参考答案满分的判分器，和没有判分器几乎没有区别——因为你无法用它判断自己的实现是不是真的对。 第 ② 步的做法是：从参考答案出发，制造几个"看起来合理但违反契约"的变体（比如漏掉某个检查），确认判分器能抓住每一个。

为什么这一步必须由判分器作者自己做：因为"判分器抓不住某种错误"这件事，只有在有人故意犯那个错误时才会暴露。而如果你自己没试过，那个缺口就会留给第一个犯这个错误的人。

### 4.3 动手试一下：注册一个工具并调用它

这一段是这一篇唯一一次完整走通"注册 → 可见 → 调用 → 结果"的练习。它不需要模型，因为调用是直接调的。

```js
// demos/echo-demo.mjs —— 第二层验证的全部代码
import { ToolRegistry } from '../src/tools.mjs'

const registry = new ToolRegistry()

// 只做这一件事：注册。不改 tools.mjs 的任何一行。
const unregister = registry.register({
  name: 'echo',
  description: '把 text 原样返回。用来确认工具系统的工作方式，不产生任何副作用。',
  parameters: {
    type: 'object',
    properties: { text: { type: 'string', description: '要回显的文本' } },
    required: ['text'],
  },
  sideEffect: 'readonly',
  run: ({ text }) => ({ ok: true, content: text }),
})

const ctx = { workspace: process.cwd(), maxResultChars: 2000 }

console.log(registry.list().map((t) => t.name))          // ['echo']
console.log(await registry.run('echo', '{"text":"你好"}', ctx))  // { ok: true, content: '你好' }
console.log(await registry.run('echo', '{}', ctx))              // ok:false，缺必填参数
console.log(await registry.run('nope', '{}', ctx))              // ok:false，没有这个工具

unregister()
console.log(registry.list().map((t) => t.name))          // []
```

这段代码值得逐行对照三条判据：判据 1（零改动注册）、判据 2（卸载后消失）、判据 10（未注册名）。

而它有一处容易被忽略的价值：`run('echo', '{}', ctx)` 与 `run('nope', ...)` 都返回 `ok:false`，而它们的原因完全不同——前者是"你的参数不对"（模型可以改），后者是"没有这个工具"（模型该换一个）。这两个提示的写法差异，正是"失败信息要携带下一步需要的东西"（1.6 的一般形式）在工具层的兑现。

### 4.4 判据

这一篇的验证做完了的标志有三条：

第一，`tests/t4-build.mjs` 在参考答案上满分，而在你故意破坏一处时丢分——而破坏的位置是你知道的（比如把必填检查删掉，应当只有"缺必填"那一条红）。

第二，`echo` 那个工具不需要改 `tools.ts` 的任何一行。

第三，你能说出"一个工具的描述写得好不好"的判断方式（0.2 的第二个工具）——把你的 `echo` 描述给一个没用过它的人看，他能填对参数吗？

## L5 语法速查

### 5.1 术语表

| 术语 | 在本篇里的准确含义 | 容易误解为 |
|---|---|---|
| 工具 | 一份能被模型读懂的说明 + 它背后的实现 | "一个函数"（函数只是实现那一半） |
| JSON Schema | 告诉模型参数该怎么填的一段结构 | "校验规则"（校验只是它的第二个用途） |
| 副作用等级 | 按"撤销它要付出什么"分的四级 | "危险程度"（那是一个模糊的整体判断，而这是可比较的维度） |
| 可逆性 | 一个操作能不能被撤销 | "幂等"（幂等说的是做多次与做一次相同，与能不能撤销无关） |
| 注册表 | 工具名到工具定义的映射，以及唯一的调用入口 | "一张表"（表是它的实现方式，入口是它的职责） |
| 扩展点 | 别人可以挂上行为的地方 | "插件系统"（那是第 2.3–2.4 篇的形态，这里只是它的最小雏形） |
| 参数校验 | 在调用实现之前检查模型给的参数 | "类型检查"（校验的是模型输出这个外部输入，而非代码内部的值） |
| 失败是返回值 | 可预期的失败用 `ok:false` 表达，不入异常通道 | "不抛异常"（不可预期的实现错误仍然要能被看见，见 3.2） |
| 能力边界 | 这个工具集让 agent 能做什么 | "功能清单"（清单说的是有什么，边界说的是能做什么事） |
| 最小防线 | 挡住路径穿越这一类最常见事故的检查 | "沙箱"（沙箱强制约束能力，这里只是拒绝一种输入） |

### 5.2 命令速查

| 目的 | 命令 | 说明 |
|---|---|---|
| 看有哪些工具被注册 | `rg -n 'register\(' src/` | 期望每一处都紧跟一个工具定义 |
| 找没有声明副作用等级的工具 | `rg -n 'register\(' -A 8 src/ \| rg -v sideEffect` | 命中即说明该工具会走"默认不可逆"（3.4.1） |
| 找偷偷写文件的"只读"工具 | `rg -n "sideEffect: 'readonly'" -A 10 src/ \| rg 'writeFile\|rm\|unlink'` | 命中就是声明与实现不一致（1.8 的边界） |
| 跑契约测试 | `node tests/t4-build.mjs` | 按契约逐条检查 |
| 跑判分器的鉴别力检查 | `node grade/negative-check-tools.mjs` | 从参考答案制造违规变体 |
| 验证零改动注册 | `node kit/src/echo-demo.mjs` | 不需要任何已有代码改动 |

第二、三条命令值得说明它们能做什么、不能做什么：它们只能扫出同一段注册代码附近的疑点。如果一个工具的实现写在另一个文件里（真实项目里通常是），它们就扫不到。而"扫不到"不代表没问题——所以 1.8 才说声明与强制必须配对：`rg` 是这里唯一能做的检查，而它挡不住全部。

### 5.3 三条容易踩的规则

第一条：不要在 `run` 里 `JSON.parse` 参数字符串。 参数必须经过 `parseArguments`（2.1），因为 2.1 处理过"合法 JSON 但不是对象"这一情形，而裸的 `JSON.parse` 不会。这条规则的意义不只是复用代码：它保证"参数字符串的解析规则"在整个系统里只有一份。

第二条：不要让工具实现自己截断输出。 截断在注册表里做一次（3.4.2 第 ⑤ 步），理由是"凡给模型的都要过这一道"。让实现自己截断，等于把这条规则复制到 N 个地方，而其中总有 N-1 个会随时间失效。

第三条：不要在 `list()` 里返回工具的 `run`。 那个函数不可序列化，而 `list()` 的输出要进请求与日志。这条规则的检查方式很直接：对 `list()` 的输出做一次 `JSON.parse(JSON.stringify(...))`，然后比较——这一条也写在验收判据第 4 条里。

## L7 挑战题（不给答案）

第一题：给参数校验加"部分成功"的情形。 现在校验要么全过、要么拒绝。设计一个方案，让"一半字段合法"这种情况下的报错能列出所有问题（而不是遇到第一个就返回）。然后说明这个改动对提示词长度的影响，以及模型是否更可能一次改对。

第二题：让工具集按会话变化。 现在注册表是全局的。设计一个方案，让同一个进程里的两条会话看到不同的工具集（第 2.5 篇要讲作用域，但你可以先想）。并指出"会话结束后该忘掉什么"。

第三题：设计一个"工具别名"机制。 有时同一个能力在不同场景下应该有不同的描述（比如 `read_file` 在"探索代码库"与"检查配置"两个场景下的说明不同）。设计一个别名机制，并说明它与"描述只写给模型"这条原则是否冲突。

第四题：给工具定义加一个"示例"。 有人主张在工具定义里加 `examples` 字段，给出 2–3 个"什么情况下用它"的例子。论证它会带来什么收益与什么代价，并说明它应该进 `list()`（给模型看）还是只留在文档里。

第五题：为"长时工具"设计一个协议。 一个工具可能跑十分钟。设计一套"开始 → 进度 → 结果"的协议，并说明它在"模型可见 ⟺ 可重建"这条不变量下的实现方式。

第六题：反驳"副作用等级由注册方声明"。 L2 第 10 条选了"注册方声明"，而一个替代方案是"工具实现自己声明它需要哪些能力"（比如"我需要写文件系统的能力"），由注册方只做批准。论证这个替代方案在什么条件下更好。

## L9 仍未解决（这一篇自己的缺陷）

这一节列出这一篇交付的产物里已知但未解决的问题。它们不是"将来可以优化"，而是"现在就有代价"。

| 缺陷 | 后果 | 修法 | 当初为什么这么写 |
|---|---|---|---|
| 注册表是进程级的，没有作用域 | 两条会话看到同一套工具；一个会话注册的工具会漏给另一个 | 把注册表挂到作用域上（2.5 篇） | 第 2 卷还没有多会话（第 5 卷才有），进程级是当前最小的正确形态 |
| `sideEffect` 只有声明，没有强制 | 声明为 `readonly` 的实现偷偷写文件时无人拦截 | 与沙箱配对（第 3 卷）：声明决定"问不问人"，沙箱决定"能不能做" | 沙箱是第 3 卷的内容；这里先把"危险程度"变成数据，否则第 3 卷没有输入 |
| 没有并发控制 | 两个工具同时写同一个文件时的结果取决于时序 | 按资源加锁，或要求工具自己声明互斥 | 单线程的 agent 循环里同时只有一个工具在跑；而并行工具调用会让它变成真问题 |
| 校验器不检查数值范围 | `{ type: 'number' }` 接受 `-1` 与 `1e300` | 增加 `minimum` / `maximum` | 五种子集能力覆盖了绝大多数参数；范围约束可以由实现自己查（并返回失败） |
| 没有"工具超时" | 一个卡住的工具会让整轮停在那里 | 在 `run` 外层加超时与取消 | 超时机制需要取消传播（第 3 卷的进程管理）；现在加了也只是"扔下不管" |
| 截断是按字符数算的 | 中文与代码的 token 密度差异很大，同一个上限对应的成本相差数倍 | 按估算 token 数截断 | 字符数是零成本的近似；精确 token 计数要引入分词器，而那是第 3.6 篇的事 |
| `ToolContext` 没有取消信号 | 用户中断时，已经开始的工具仍在跑 | 传入 `AbortSignal` 并在实现里检查 | 当前调用是同步等待的，中断语义还没定义 |
| 错误信息未脱敏 | 参数里的凭据可能随错误信息进日志（2.1 的第六条缺陷在此被放大） | 在 `run` 的错误路径上做脱敏 | 这一篇仍没有凭据类参数；而它与 2.1 的那条是同一个来源 |

其中第一条与第二条值得单独指出，因为它们的性质不同。

**第一条是一个"位置放错了"的缺陷。** 注册表现在是 `ToolRegistry` 的一个实例，而这个实例被谁持有并没有规定——它可以是一个模块级单例（最省事），也可以由容器创建。当前没规定的原因是"还没有第二个消费者"；而一旦第 5 卷有了多会话，这个选择会变成两类不同的实现：单例意味着所有会话共享工具集，容器持有意味着一会话一套。所以在这一篇里，"注册表放在哪"是一个被推迟的决定，而它的推迟是安全的——因为决定它需要的信息（会话是否隔离）此刻还不存在。但"被推迟"与"没想过"不同：这个文件的结构（`ToolRegistry` 是一个类而不是一组模块级函数）已经把将来的选择留出来了。

第二条则是一个"声明式约束的固有缺口"，而它不会因为写得更好而消失。 声明说"这个工具是只读的"，而这句话的验证需要一个能观察文件系统改动的机制——那已经超出了类型系统与注册表的能力。所以这条缺陷的正确处置不是"以后修"，而是"与另一条机制配对"（1.8 的"声明 + 强制"）。而它留了一个具体的、当下就能做的动作：`rg` 一遍声明为 `readonly` 的工具里有没有写操作（5.2 的第二条命令）——它挡不住恶意的实现，但它能挡住不小心的那一类，而后者在实际中远为常见。

模糊问题：「我该怎么设计工具系统？」

升级后的精确问题：

> 工具系统至少要回答三件事：给模型看的那部分怎么写（名字、描述、schema）、调用前要拦什么（解析、校验、越界）、以及结果怎么出去（成功、失败、截断）。
> 这三件事里第一件与第三件互相制约——描述里承诺的输出形态，决定结果该怎么包装。
> 而第二件事是独立的：它只管住入口，而入口只有一处（注册表的 `run`）。
> 我能不能为每一件事找出一条**可检查的判据**？
> 特别是：有没有哪一条判据，是**能在不理解业务的前提下自动检查的**（比如"凡给模型的都过截断"这件事，能不能用一条命令验证）？

**提升点说明**：原问题无法回答，因为"怎么设计"没有边界。升级后的版本做了三件事。第一，把目标收成三个有位置的环节（给模型看的、拦在入口的、送出去的），而不是列一堆"要考虑的点"。第二，指出其中两件之间的制约关系（描述的承诺 × 结果的形态），它解释了为什么这两件不能分开决定。第三，追加了一个更强的问题——哪一条判据能在不理解业务的前提下自动检查。这一问指向 3.4.2 第 ⑤ 步那条"成功与失败都要截断"，因为它是这一篇里唯一一条"不管工具做什么都成立"的规则；而"不管内容是什么都成立"正是自动化检查的前提。

## L11 系统影响回溯

回看第 0.5 节的三个连锁影响，这一篇的实现给出了它们各自的具体形态，以及一处需要修正的预判。

**连锁 1（`ToolResult` 的形状会决定循环的形状）** 在 3.4.2 兑现：`run` 的五步是一条直线，而它的第 ④ 步（接住实现抛出的异常并标注）是 0.5.3 没有写到的一处——0.5.3 对比的是"循环里要不要 try/catch"，而真正的选择是"try/catch 放在哪一层"。这一篇的答案放在注册表里，理由是那里是唯一同时知道"工具名、参数、失败原因"的位置（2.1 的"信息在传播中被压缩"在这条路径上又一次生效）。代价是注册表多了一个职责：它不只是查找与调度，还要为失败分类。

连锁 2（副作用等级会在第 3 卷被消费） 在 3.4.1 给出了它真正的难点——不是"分几级"，而是"默认值是什么"。0.5.3 说"如果只做二分，第 3 卷就无法区分"，而读完之后要补一句更重要的：即使分级做得再细，只要默认值是 `readonly`，整条防线就是形式上的——因为遗忘声明比故意声明错误更常见。所以这一条连锁影响的落点不是分级本身，而是那条保守默认，它把一个"分类问题"变成了一个"缺省语义问题"。

**连锁 3（能力边界比模型能力更重要）** 在这一篇被落成一条可操作的判据（0.2 的第一个工具、以及 L6 的那一问"模型能只凭描述判断该用哪一个吗"）。而它有一处 0.5.3 没有预见到的后果：能力边界不只决定"agent 能做什么"，也决定工具描述要写多细。因为工具越少，每个工具要覆盖的场景越多，描述就越容易写成"一段含糊的通用说明"；而工具越多，"该用哪一个"的判断就越依赖描述之间的区分度。所以"给几个工具"与"描述怎么写"是同一个决定的两面——这解释了为什么 1.2 把描述放在工具系统最重要的位置。

一处需要修正的预判：0.5.2 说 `ToolResult` 的 `ok` 约定"决定了循环怎么写"。读完之后我会补一句：决定性的一处其实不是 `ok`，而是"截断放在哪里"。因为 `ok` 只影响分支的写法（一行三元表达式），而截断的位置决定了"有多少条路径可能绕过它"——放在工具实现里就是 N 条，放在注册表里就是一条。一个只影响写法，一个影响正确性是否可保证；而 0.5.2 把这两件事混在了一行里。

通向下一步的桥。

做完这一篇，系统能做事了，也能把失败告诉模型了。但它的零件还在各自的位置上：模型层是一个模块、工具注册表是一个实例、agent 循环还没有写——而"谁在什么时候创建它们、谁在什么时候销毁它们"，这一篇完全没有回答。

具体来说，这一篇留下了三个没有答案的问题：注册表这个实例由谁持有（L9 第一条）？`register` 返回的卸载函数在什么时候被调用（3.4）？以及第 3 卷的守卫要以插件的形式挂进来时，它挂在哪（0.4 与 1.8 的"声明 + 强制"配对）？

所以下一篇是 2.3 容器与依赖注入——它要给这些零件一个统一的持有者与一致的销毁时机。

而这一篇给它留了一个具体的接口：`register()` 返回的卸载函数（3.4）。容器要做的事里有一件就是"把每个注册动作变成一条可撤销的记录"，而这里的返回约定正好是那条记录的形状——注册是 effect 这条约定，从这一篇的注册表开始，会在第 2.3 篇被提升为整个系统的通用约定。

## 记忆锚点与复述练习

### 一、骨架：四块

```
   四样东西 ──► 边界在哪 ──► 怎么拦住坏输入 ──► 结果怎么出去
      ↓           ↓            ↓                ↓
  名字·描述·schema  能力边界     解析 → 校验       成功 / 失败 / 截断
     实现（+副作用）  用户用途     越界防护          internal 标记
    1.1           1.8          1.3–1.7          1.5–1.6
```

只记一行就记这行：给模型看的 → 边界在哪 → 拦在入口 → 送出去。

### 二、情境绑定：当你……就想起……

| 当你…… | 立刻想起 |
|---|---|
| 要写一个新工具 | 先写描述，再写 schema，最后写实现——顺序反了会写出"给模型看不懂"的工具 |
| 要决定给不给某个工具 | 问"用户会用它做什么"，不问"实现难不难" |
| 工具执行失败了 | 返回 `{ ok: false, error }`，而且错误信息要能指导下一步 |
| 实现里抛出异常了 | 它不该伪装成普通失败——带上 `internal` |
| 要给工具加一个可选参数 | 问"schema 里加它之后，模型填错的概率会变高吗" |
| 要新增一种 schema 能力 | 先问模型能不能可靠地用对，再决定加不加 |
| 不确定一个操作危险不危险 | 问"撤销它时，外部世界会不会已经变了" |
| 忘了一个工具的副作用等级 | 它会走保守默认（等于不可逆），于是你每次都会被问——这就是提醒 |
| 工具输出可能很长 | 截断发生在注册表，成功与失败都要过 |
| 工具拿到一个路径参数 | 它必须先过 `resolveInside`，且前缀比较要带分隔符 |
| 想让工具"自己做点额外的事" | 想想它会不会绕过截断与校验——绕过哪一个都不行 |

### 三、主动回忆：闭卷回答（不要翻上面）

1. 一个工具由哪四样组成？哪一样可选？四样里哪三样是给模型看的？
2. "失败是返回值"的三条理由是什么？第二条与信息传播的哪条规律有关？
3. `ToolResult` 为什么要用可辨识联合，而不是"一个带 `ok` 可选字段的对象"？
4. `internal` 标记区分的是哪两类失败？为什么这个区分对模型和对人意义不同？
5. 头 80% + 尾 20% 的依据是什么？为什么截断说明里要写"省略了多少"？
6. `resolveInside` 的前缀比较为什么必须带分隔符？不带会放过什么样的路径？
7. 四级副作用各是什么？第三级与第四级的分界线在哪？
8. `sideEffect` 的默认值是什么？为什么？
9. `register` 与 `run` 谁抛异常、谁不抛？为什么？
10. `run` 的五步按什么顺序？这个顺序的依据是什么？
11. `list()` 为什么不能把 `run` 也返回？这条约束服务于哪条不变量？
12. 校验器为什么返回字符串而不是 boolean、也不抛异常？

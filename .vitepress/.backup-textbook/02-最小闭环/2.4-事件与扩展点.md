## 本篇新词

事件（event） 在这门课里指一次"发生了某件事"的通知，它带着一个名字与一份数据。它与函数调用的区别不在形态，而在知道谁在听：调用方知道自己调用了谁，而事件的发出方不知道有哪些响应者。这个区分的意义在于耦合方向——发出方不需要知道响应方的存在，因此新增响应者不需要改动发出方。

广播（emit） 指把一次事件通知给所有监听者的动作。它的语义是"通知并继续"，也就是说监听者的返回值被忽略，广播不会因为第一个监听者做了什么而改变行为。

waterfall 指一种特殊的广播形态：它把同一个值依次传给每个监听者，每个监听者可以选择修改它并传给下一个，也可以选择不调用 `next()` 从而终止整条链。它的名字来自"逐层落下"的意象，而它的用途是在某个动作发生的路径上允许插件介入并改写。

短路（short-circuit） 指 waterfall 链在中途停止。它是一条必须被写进契约的行为：一个监听器不调用 `next()` 会造成什么后果、后面的监听器是否被跳过、调用方能否区分"链走完了"与"链被终止了"。

扩展点（extension point） 指系统里明确允许外部挂上行为的地方。它与"任何地方都可以被改"的区别在于它有契约：挂在哪、什么时候被调用、能不能改写数据、抛错会怎样，这四件事都是被规定的。

钩子（hook） 指挂在扩展点上的一个具体实现。它与监听者的区别在于它通常只有一个（例如"请求前的改写函数"），而监听者可以有很多。

可忽略事件（ignorable event） 指一种兼容性标记：不认识它的读取方可以跳过它而不会得到错误的派生结果。它解决的是"新版本写入的事件被旧版本的读取方读到"这个问题，判据是"不知道它时派生出来的结果会不会错"。

监听器的归属 指"这个监听器由谁挂的、由谁撤销"。它与 2.3 的服务归属是同一个概念，只是对象从服务条目换成了监听器——而后者更容易被遗漏，因为挂监听器常常发生在代码的某个角落，不像注册服务那样有明确的位置。

### 0.0 先行组织者：三种形态与三件必须约定的事

│                                                                      │
│  ② 顺序与短路 —— 多响应者之间的语义                    → 1.2          │

│                                                                      │
│  ③ 归属与撤销 —— 监听器由谁挂、由谁摘                  → 1.3          │

这张图的关键线索在第三块：事件系统里最常见的事故不是"广播没生效"，而是"广播生效了但监听器没被摘掉"。前者在开发时立刻可见，后者要等到某次卸载之后才以重复处理或幽灵行为的形式出现。因此这一篇的验收重点不在广播是否工作，而在监听器能否被完整撤销。

### 0.1 一个具体的判断：waterfall 里的 `next()` 为什么必须被调用

`vendor/cordis` 的 waterfall 语义是：监听器接收一个值，处理之后调用 `next(value)` 把（可能被改写过的）值传给下一个；调用方得到最后一个监听器返回的结果。这条语义的关键约束是"每个监听器都必须调用 `next()`，否则整条链被终止"。

这个设计容易被认为是缺陷（为什么不允许默认继续），而它的理由是让"终止"成为一个显式动作：如果默认继续，那么"我决定不改写、直接放行"与"我忘了处理"在代码上无法区分。显式 `next()` 让两种情形分开——放行要写一行，忽略则表现为链的终止，而后者在测试里立刻可见。

它带来的代价同样明确：任何一处忘记调用 `next()` 都会造成静默的功能缺失（后续监听器不再执行），而这类缺陷的表现是"某个功能在某些插件存在时莫名其妙地不生效"。因此本课程的实现要求：如果某个 waterfall 的监听器不需要改写，就在它的第一行写下 `return next(value)`，让"放行"是一个正面动作而不是遗漏。

### 0.2 本篇建立的三项判据

第一项用于判断一处行为该不该挂在事件上：问发出方是否需要知道响应方。需要知道的（例如"这个工具的返回值必须由解析器处理"）应当直接调用；不需要知道的（例如"每次会话开始都通知一下统计"）才用事件。这条判据的反面是常见错误——把本该直接调用的流程拆成事件，于是调用方失去了"这件事有没有人处理"的确定性。

第二项用于判断顺序该按什么定：问响应者之间是否存在语义上的先后。存在先后（例如守卫必须在执行之前）就用显式优先级；不存在先后（例如多个统计模块各自累计）就用注册顺序，并把"顺序不构成承诺"写进契约。按注册顺序而不写声明，等于让顺序成为一个隐式的、随代码位置变化的契约。

第三项用于判断一个事件类型是否可忽略：问不知道它时派生出来的结果会不会错。会错的必须让不认识的读取方拒绝整份日志（例如压缩点）；不会错的可以带可忽略标记（例如统计事件）。这条判据是第 2.7 篇事件契约的直接输入，也是第 3 卷格式演进规则的基础。

### 0.3 十分钟练习：顺序与短路的实跑

下面这段代码把顺序与短路两种语义放在一起，可以直接运行。

```js
class Bus {
  constructor() { this.listeners = new Map() }
  on(name, fn) {
    const list = this.listeners.get(name) ?? []
    list.push(fn)
    this.listeners.set(name, list)
    return () => {                       // 注册返回撤销函数（2.3 的约定）
      const cur = this.listeners.get(name) ?? []
      this.listeners.set(name, cur.filter((f) => f !== fn))
    }
  }
  async waterfall(name, value) {
    const list = [...(this.listeners.get(name) ?? [])]
    let acc = value
    for (const fn of list) {
      let advanced = false
      acc = await fn(acc, (next) => { advanced = true; return next })   // 记录是否调用了 next
      if (!advanced) return acc                                        // 短路
    }
    return acc
  }
}
const bus = new Bus()
bus.on('rewrite', async (v, next) => next(v.toUpperCase()))
bus.on('rewrite', async (v, next) => next(v + '!'))
console.log(await bus.waterfall('rewrite', 'hi'))    // HI!
const off = bus.on('rewrite', async () => '被短路')   // 这个监听器不调用 next
console.log(await bus.waterfall('rewrite', 'hi'))    // 被短路
off()
console.log(await bus.waterfall('rewrite', 'hi'))    // HI!（撤销之后恢复）
```

三次输出分别是 `HI!`、`被短路`、`HI!`。它们展示三件事：顺序按注册顺序、不调用 `next()` 会终止整条链、以及撤销一个监听器之后链恢复正常。第二行输出是最值得注意的——它说明一个监听器的遗漏会静默地吃掉后面所有监听器的效果，而调用方拿到的结果看起来是"正常"的。

> **面试视角**
> **高频问法**："事件和直接调用怎么选？"
> **追问方向**："waterfall 里忘写 next 会怎样？"落点是短路：后面的监听器被跳过，而调用方无法区分"处理完了"与"被终止了"，因此这类约定必须写进契约。

### 0.5.3 三个连锁影响

**第一，把流程拆成事件会让"这件事有没有人处理"变得不可判定。** 直接调用时，调用方知道自己调用了谁，因此"返回值是空的"与"没有人处理"是可区分的；改成广播之后，发出方拿不到任何返回值，于是"没有人监听"与"监听者做了但没效果"变得无法区分。这个变化在一个具体场景里变成问题：如果某个关键步骤（例如持久化）被实现成一个事件监听器，而它因为配置错误没有被装载，那么系统会静默地不持久化，直到下次重启才发现数据没了。处置方式是区分"关键路径"与"通知"：关键路径用直接调用（它的缺失必须是一个错误），通知用事件。

第二，监听器的顺序在按注册顺序时是不稳定的，而人们会不自觉地依赖它。 三个统计模块都监听同一个事件，其中两个恰好因为加载顺序而先执行，于是某个人写下了"我假设在我之前那个模块已经跑过"的代码。这类依赖不会出现在任何声明里，而它会在装配顺序变化时破裂——表现是"改了配置之后某个数字不对"，而排查方向通常会指向统计模块本身。处置方式是对有语义先后的用显式优先级，并让无序的那部分在契约里明确写成"顺序不构成承诺"。

第三，事件的格式演进比函数接口更严，因为它的使用者包括尚未写出的代码。 一个函数接口增删字段，所有调用方可以一起改；而事件一旦落盘，它的读取方包括未来的恢复逻辑、分析脚本与迁移工具，它们无法被一起改。这带来一条硬规则：任何事件格式的结构性变化都必须伴随一个处置规则——老版本读到新事件时应该跳过还是拒绝。跳过适用于可忽略事件，拒绝适用于影响派生结果的事件（例如压缩点）。这条规则在第 2.7 篇会以 `SessionEventMap` 成员默认必需的形式被固定下来。

### 0.5.4 它与本书其余部分的关系

本篇的事件是本进程内的、同步顺序的、没有投递保证的。这个边界决定了它的结论在哪里需要补充。

跨进程的事件（例如网关把外部请求转成内部事件）需要投递语义（至少一次、恰好一次、顺序保证），而那是消息系统的领域，本课程只在第 5 卷的 webhook 入口处触及它的一个简单版本。

事件溯源（把事件当作唯一真相、状态由重放得出）是本篇的一个特例：它在第 2.7 篇会成为会话日志的基础，而它的代价（重放成本、事件版本管理、派生视图的复杂度）会在第 3 卷的压缩与恢复两篇里展开。

## L0 要解决的问题

### 0.1 现象一：行为被写在调用点旁边

在一个还没有事件机制的项目里，新行为通常被直接写在它要影响的那段代码旁边。例如"每次工具调用之前检查权限"会被写进工具执行函数里，"每次模型请求失败时重试"会被写进循环的错误分支里。这种写法在行为数量少时完全合理——它最直接，也最容易读。

它的问题在行为数量增长之后出现，而且有三个具体后果。新增一个行为要改核心代码，于是每一次扩展都带着回归风险；删掉一个行为要靠搜索，而搜索会漏掉那些写得不像的地方；行为的开关无法按环境配置，因为它不是一个可装载的部件，而是一段被执行到的代码。三条后果的根因是同一个：行为的挂载点散落在流程代码里，而不是集中在扩展点上。

### 0.2 现象二：顺序依赖只存在于某些人的记忆里

第二个现象在行为数量继续增长之后出现。三个模块都监听同一个事件，其中一个的执行必须在另一个之前——例如"计算用量"必须在"上报用量"之前。而这条顺序要么来自注册顺序（它取决于加载顺序），要么来自某处的一次显式调整，而两者都没有被写进任何声明。

它的后果在配置变化时出现：加载顺序变了、或者某个模块被禁用之后，行为开始出错，而错误的形态是"某个数字不对"或"某一步用了还没准备好的数据"。这类缺陷的排查难度在于出错的代码本身完全正确，它只是被执行在了不合适的时刻。

### 0.3 现象三：卸载之后监听器还在响应

第三个现象是事件系统里最常见的事故形态。一个插件被卸载时它的入口函数返回了，但它挂在事件上的监听器还在。于是当那个事件再次发生时，一个已经"不存在"的插件仍然会对它作出反应；如果那个反应是往一个不存在的状态里写数据，故障就从幽灵响应升级成状态损坏。

这类残留之所以常见，是因为挂监听器的代码通常不在插件的初始化块里，而在某个分支中（例如"当配置了某个选项时挂一个监听器"）。于是"卸载时要摘掉哪些监听器"无法靠读初始化代码回答，只能靠一个统一的约定：每个注册动作返回它自己的撤销动作，而卸载就是把它们全部执行一遍。

### 0.4 现象四：事件格式改一次，历史就读不出来

第四个现象涉及兼容性。会话日志里的事件一旦落盘就会被未来的代码读取；如果新版本给某个事件加了字段、改了类型或者引入了新的事件类型，那么旧版本的读取方在读到它时只有两种选择：跳过（可能派生出错误的历史）或拒绝（整份日志不可读）。

两种选择的适用条件不同，而这个选择必须由写入方在写事件时就声明，因为读取方无法自己判断"跳过这条会不会导致派生出错"。缺少声明时唯一的选择是拒绝——于是任何一次新增事件类型都会让旧版本读不了新日志，而那意味着无法回滚，因为回滚后的版本读不了已经写下的日志。

### 0.5 这一篇要正面回答的四个问题

第一，一处行为该用直接调用还是事件（1.1）。第二，多个响应者之间的顺序与短路该由什么决定（1.2）。第三，监听器的归属怎么处理，卸载为什么必须撤销它们（1.3）。第四，事件格式怎么演进，可忽略这条规则解决的是什么问题（1.6）。

四个问题的顺序由依赖决定：先决定用不用事件，才有顺序问题；有了多个监听器，才需要归属；而归属与格式演进分别对应"系统能不能被长期修改"这件事的两个方向——纵向上能装卸，横向上能演进。

## L1 设计与原理

### 1.1 三种调用形态

同一个需求可以用三种方式实现，它们的差别集中在两个问题上：发出方知不知道谁在听，以及响应方能不能改变结果。

| 形态 | 发出方知道谁在听吗 | 响应方能改变结果吗 | 适用场景 |
|---|---|---|---|
| 直接调用 | 知道，它写明了函数名 | 能，通过返回值 | 关键路径，缺失必须是一个错误 |
| 广播 | 不知道 | 不能，返回值被忽略 | 通知，例如统计、日志、界面刷新 |
| waterfall | 不知道 | 能，逐个改写并传递 | 需要在路径上介入并改写，例如守卫、重试改写请求 |

三者的选择判据是"这件事的缺失该不该是一个错误"。以持久化为例：如果某个事件没有被任何监听器处理，系统应当报错还是静默继续。答案取决于它是否在关键路径上——关键路径上的缺失必须是错误，而广播这种形态恰好无法表达错误，因此它不适合承载关键路径。

直接调用与事件的另一个差别在可读性上。读一个直接调用的调用点，你能知道这一行之后发生了什么；读一次广播，你只知道"有人可能被通知了"。因此广播的代价是用流程的可读性换可扩展性，而这个交换只有在新行为会被频繁添加时才值得。

### 1.2 顺序与短路

广播与 waterfall 都是多响应者机制，因此它们必须回答顺序问题。顺序的两种来源各有代价。

按注册顺序的代价是不稳定：注册顺序取决于加载顺序，而加载顺序由配置决定，于是同一份代码在不同配置下的行为可能不同；它的优点是不需要任何声明。按显式优先级的代价是每个监听器要多写一个数字，收益是顺序成为契约的一部分——顺序依赖从"恰好如此"变成"被声明的东西"。

本课程的选择是两者并存并要求声明：需要先后的用优先级，不需要先后的必须在契约里写成"顺序不构成承诺"。这条要求的实际意义是把一种隐式依赖转成两种显式状态之一——要么它是一个承诺，要么它是一个被明确排除的东西。

短路是 waterfall 特有的语义，它的约定值得完整写出：监听器接收一个值与一个 `next` 函数；调用 `next(newValue)` 表示把值改成这样并继续；不调用 `next` 表示到此为止；调用方拿到的结果是最后一个监听器返回的值。

```ts
type Listener<T> = (value: T, next: (value: T) => T | Promise<T>) => T | Promise<T>
```

这段类型没有表达、而必须由契约表达的是"不调用 `next` 会终止整条链"。它是本篇最容易被误用的约定：一个只想观察而不改写的监听器，最自然的写法是"读完就返回"，而那在语义上等于终止。因此契约要求只观察的监听器显式写成 `return next(value)`，让放行成为一个正面动作而不是遗漏。

### 1.3 监听器的归属与撤销

监听器与 2.3 的服务在归属上是同一条规则：谁注册谁负责撤销，撤销时判断归属以避免误摘别人的监听器。差别在于实践中的隐蔽程度——服务注册通常写在初始化块里一眼可查，而监听器可能在任意分支里挂上。

实现上有两种做法。一种是让 `on` 返回撤销函数，调用方负责保存并在卸载时调用（与 2.3 的 `provide` 一致）。另一种是把监听器记在上下文上，卸载时由上下文统一撤销。两者的差别在"忘记保存返回值"这一情形：前者的忘记等于泄漏，后者不会。本课程采用后者为默认（`ctx.on` 自动登记在当前部件的 effect 列表里），同时保留前者供需要精确控制的场合使用。

这条选择与 2.3 的 `effect` 是同一件事：默认路径应当让正确做法不可能被遗漏，而不是依赖每个调用点都记得保存返回值。

### 1.4 事件即契约

事件是一种契约，而且是时序承诺的极端形态。它的特殊性有三处。

第一，事件的产生时刻不由使用者决定。函数由调用方决定何时调用，而事件的发出时机由系统内部决定（例如"请求失败时"），因此使用者必须对"什么时候会收到"有正确预期。第二，事件的顺序是外部可见行为：一次广播里监听器被调用的顺序、以及它们相对于其它事件的位置，都属于可观察行为，按 Hyrum 定律会被依赖。第三，事件的名称与载荷会进入持久化，因此它们同时是跨时间的契约——不只是当前代码要读懂它，未来的代码也要。

三处特殊性合起来给出一条原则：事件的名称、载荷与发出时机都应当按"它会被人依赖很多年"的标准设计。落到本课程，这意味着事件名不带实现细节（与 2.1 的服务命名是同一条规则）、载荷里不放临时字段、以及每次新增事件类型都要回答"不认识它的读方该怎么办"。

### 1.5 扩展点与钩子

扩展点是允许挂行为的地方，钩子是挂在它上面的具体实现。设计一个扩展点要回答四个问题，缺一个就会出现一类事故：挂在什么位置（在哪一步之后触发）、什么时候被调用（每次还是满足条件时）、能不能改写数据（能不能改，以及改的是副本还是引用）、抛错会怎样（中断整条流程还是记录后继续）。

第四个问题最常被漏掉，而它的后果是"某个插件的错误让整个流程停住"，在守卫与重试这类插件上尤其严重。本课程对四个问题的默认回答是：位置在契约里写明；每次触发，条件由监听器自己判断；能改写，但只能通过 waterfall 的返回值；抛错则中断并向上传播，由第 3 卷的错误处理决定如何处置。最后一条是刻意的选择——让插件的错误可见，而不是被吞掉，因为吞掉之后的系统行为难以解释。

### 1.6 可忽略事件与格式演进

事件格式的演进规则可以用一个问题穷尽：不认识这条事件时，读取方派生的结果会不会错。不会错的带可忽略标记，会错的必须让读取方拒绝。

以本课程后续会用到的两类事件为例。"统计事件"记录一次用量，跳过它只会让统计少一条，不会让派生的模型可见历史出错，因此它可以标记为可忽略；"压缩点事件"记录从这一条之后的历史被替换成了摘要，跳过它会让派生出的模型可见内容完全错误，因此它必须不可忽略。

这条规则与 `SESSION_FORMAT_VERSION` 一类的版本号配合使用：版本号回答"这份日志是哪一代格式"，可忽略标记回答"遇到不认识的事件该怎么办"。它们解决的是不同层次的问题——版本号是整体的，标记是逐条的。只有版本号时，遇到未知事件只能整体拒绝，粒度太粗；只有标记时，无法判断一份日志是否来自更高版本，缺少全局信息。

### 1.7 广播的成本

广播的复杂度与监听器数量成正比：一次广播要依次调用全部监听器。这个成本在监听器很少时可以忽略，而在两个场景下变得显著。

第一个场景是高频事件。如果某个事件每次模型调用都发出一次而它有十个监听器，那么每次调用会多出十次函数调用；这个量级仍然很小，但如果其中某个监听器做了同步的重活（例如遍历全部历史），成本就会累积到可见。第二个场景是瀑布链上的异步操作：每个监听器都可能 `await`，于是总延迟是它们之和。这两种成本的性质不是"广播太慢"，而是广播让成本变得分散且不可见，因此设计时应当规定哪些事件允许同步重活。

本课程的规定是：广播的监听器应当短小（不阻塞的记账与变更检测），任何重活都交给后台作业——第 3 卷的进程与作业篇会把这条规定变成机制。

### 1.8 两次追问

工程侧的问题是什么时候该放弃事件、回到直接调用。判据是"这件事有没有被处理"需不需要被检查：关键路径（持久化、鉴权、结果写回）都必须知道处理结果，因此不适合广播，但可以用 waterfall 表达（链的返回值就是处理结果）或直接调用。本课程两者都用，同时把扩展点限制在少数几处——扩展点的数量本身是一种复杂度，每多一个，系统的执行路径组合就多一层。

产品侧的问题是扩展点对交付速度的影响。只有少数扩展点时，新增能力需要改核心代码，代价是每次改动带着回归风险；扩展点很多时，新增能力只需注册，代价是行为分散在多处，排查时先要找到是哪个监听器在起作用。权衡依据是新增能力的频率：在能力快速增加的阶段扩展点优先，行为稳定之后过多的扩展点会变成理解成本。第 3.6 篇的可观测会给出这条权衡的量化方式，即每个扩展点在运行时的实际调用次数。

### 1.9 事件的载荷设计

载荷是事件的第二半。它比事件名更容易出错，因为名字是有限的而载荷是开放的。三条规则足以覆盖多数情形。

第一条是载荷必须能被 JSON 往返。这条规则与 2.1 对模型响应对象的要求是同一个理由：它会进入持久化（第 2.7 篇之后），因此凡是不可序列化的东西（函数、句柄、循环引用）都不能出现在里面。它的实际影响比想象的常见——把内部对象直接传出去时，很容易顺手带上一个方法和它的闭包捕获。

第二条是载荷只放稳定字段。一个事件载荷里出现的每个字段都会成为可被依赖的行为，因此临时值（例如"当前第几次重试"这种只有某处才关心的计数）不该进载荷，而应当由需要它的一方自己维护。判断标准是：如果这个字段明天被删掉，有没有监听器会因此出错——会出错就说明它已经成了承诺，那就该把它写进契约并慎重对待。

第三条是不放"整个对象"。把工具结果、模型响应或会话对象整体塞进载荷，看起来省事，代价是把那些对象里的每一个字段都变成了间接承诺。可行的做法是放它的稳定子集，并在需要完整对象时通过事件里的标识去取（例如放工具调用 id，而不是工具结果本身）。这条规则也解决了体积问题：广播的载荷会被每个监听器读到，放整个对象会让广播的内存开销随对象大小增长。

### 1.10 同步与异步的边界

广播里允许异步监听器，代价出现在顺序保证上。同步监听器的执行顺序就是调用顺序，这一点是确定的；而异步监听器的完成顺序取决于各自的耗时——三个异步监听器按注册顺序被调用，却可能按耗时顺序完成。这不是实现缺陷，而是异步的固有性质。

由此得到一条判据：需要保证先后关系的监听器应当是同步的，或者由被调用的链（waterfall）显式串起。异步只用在"我不关心相对顺序，只关心最终要完成"的场合，例如上报、写日志、刷新缓存。这条判据的实际用法是在评审时问一句："如果这个监听器比另一个慢十倍，结果会不会不同。"

另一个相关的量是延迟。广播的总延迟是各监听器的耗时之和（顺序执行），而瀑布链的延迟更是逐层累加。这意味着一个慢监听器会拖慢所有发出方，而它与发出方的代码毫无关系。缓解办法有两种：把重活移出广播（交给后台作业），或者按事件类型声明"这个事件的监听器可以做重活"并在发出处接受这个成本。本课程采用前者，因为广播的发出方通常是核心循环，而核心循环的延迟会被放大到每一次调用。

### 1.11 事件的命名与粒度

命名有一条可用的分界：已经发生的事用过去式或名词（`turn/end`、`request/failed`），将要发生并允许介入的事用动词短语（`before:execute`）。这条分界对应两种机制——前者是广播（通知），后者是 waterfall（可介入）。它的价值在于让事件的形态可以从名字里读出来，而不必去查它被 `emit` 还是 `waterfall` 调用。

粒度是另一个容易被做成极端的地方。一个粗粒度事件（例如"会话状态变了"）的好处是发出方不必判断"哪些变化值得通知"，代价是每个监听器都要自己判断"这次变化与我有关吗"，而那个判断会把变化的各种细节都带进载荷。多个细粒度事件（`session/turn-start`、`session/turn-end`）的好处是监听器只需订阅它关心的那一个，代价是发出方要多写几处发出动作。

选择的判据是监听器的选择条件能不能由事件名表达。如果所有监听器都必须在载荷里判断同一个条件（例如"只有当变化类型是工具调用时才处理"），那么应当把它拆成独立的事件类型；如果监听器关心的只是"有变化"，那么粗粒度更经济。这条判据的实际意义是把"判断该由谁做"变成明确的问题：能由名字表达的选择属于发出方，只能由载荷表达的选择属于接收方。

### 1.12 事件的测试策略

事件机制的测试与普通函数不同，因为被测对象的行为取决于运行时的注册集合。三类测试各自覆盖一类性质。

第一类是单监听器测试：注册一个监听器，检查它被调用、被传递了正确的值、以及它的返回值如何影响结果。这一类与普通单元测试没有区别，它的作用是确认机制本身的语义。

第二类是多监听器测试：注册若干个监听器，检查它们的调用顺序、短路行为、以及撤销其中一个之后的行为。这一类的关键是构造出顺序敏感的场景——例如让第一个监听器改写值、第二个观察改写后的结果。只测"每个监听器都被调用了"会漏掉顺序问题，因为调用次数与调用顺序是两件事。

第三类是生命周期测试：注册监听器、撤销、再广播，检查撤销之后不再被调用；以及通过上下文登记、退出上下文、再广播，检查残留为零。这一类最容易被省略，而它覆盖的正是本篇 L0.3 那个现象。做它的成本很低（三行代码），收益是把一类难以事后排查的缺陷变成一次立刻可见的失败。

三类测试的分布值得说明：第一类覆盖机制语义，第二类覆盖契约中的顺序与短路，第三类覆盖归属与撤销。与 2.2、2.3 的构建题一样，本课程要求每一类都有用例，因为它们的失败模式不同——机制错误表现为功能不对，顺序错误表现为偶发，而残留错误表现为"过一会儿才出问题"。

### 1.13 事件的版本与迁移

事件的载荷与名字都会变，而它的使用者包括已经落盘的历史与尚未写出的代码。三种变化各自的处理方式不同。

第一种是载荷新增可选字段。它是安全的：老代码读到新字段会忽略它，新代码读到老事件会得到字段缺失。唯一的代价是每个读取方都要处理"字段可能不存在"，因此契约里应当写明哪些字段是必需的、哪些是可选的。这条与 2.1 对 `usage` 字段的处理是同一条：宁可让消费者处理缺失，也不要让生产者填假数据。

第二种是载荷删除字段或改变它的含义。它不兼容，因为老代码会读到缺失或错误的值。可行做法是新增一个字段并让两个字段并存一段时间（与 1.6 的兼容层同构），或者引入一个新的事件类型承载新语义，让老类型保留但不再生效。后者更干净，代价是历史上会同时存在两种类型的事件。

第三种是事件类型改名。它看起来只是字符串变化，而因为事件名字会进入日志，改名等于让老日志里的那一类事件变成"未知类型"。因此改名必须与"不认识它的读方怎么办"这个问题一起处理：如果老事件的影响可以忽略，就把它标为可忽略；如果不能，就保留旧名字并新增新名字（两份并存）。

三种变化的共同点是：判断依据都是"老代码读到它会发生什么"，而不是"这个改动大不大"。这也是本篇与 1.4 的连接点——破坏性变更的判据是"谁依赖了被改掉的那部分"，而事件里的依赖者包含了那些还没写出来的读取方。

### 1.9 事件的命名与版本

事件的类型名是它的稳定标识，因此它需要约定。本课程采用 `<范围>/<种类>` 的形式（`session/assistant`、`tool/result`、`llm/request`），而这条约定的用途在查询上：按范围前缀可以取出某一类事实的全部事件（2.7 的"可查询"原则），而按种类可以取出某一个环节的序列。

命名里最容易出错的是让类型名承担状态（例如 `session/request-failed-retryable`）。它的代价是：每增加一种状态就多一个类型，而消费方要穷举这些类型才能判断"这次请求的结局是什么"。正确的做法是让类型固定、把状态放进载荷（`llm/result` 加一个 `outcome` 字段），理由是状态是多值的而环节是有限的——类型爆炸会让每一个新状态的加入都变成一次格式变更。

版本的问题比命名更微妙：什么时候该新增类型而不是修改旧类型。判据是"旧日志是否仍能被新代码正确理解"。三种情形：新增可选字段（旧日志可读，不需要新类型）、新增必填字段（旧日志不可读，需要新类型或版本号）、改变已有字段的含义（最危险——旧日志能被解析而含义已变，因此必须换新的类型名）。

第三种情形值得一条硬规则：不得改变已有字段的含义。它的实现成本很低（加一个新类型名），而违反它的代价是历史日志被静默误读——这与 2.7 的 "SESSION_FORMAT_VERSION" 是同一条约束在两个层面上的表达：结构性变化升版本号，字段含义变化换类型名，而两者都不允许在原处修改。

三条约定合起来给出一份事件类型的稳定契约：类型名不变、状态进载荷、含义永不复用。它的收益在长会话上体现——一条运行数月、由多个版本写入的日志里，只要这三条被遵守，读取方就不需要为每个历史版本写分支。反过来，一次"顺手改一下含义"的改动会让所有历史数据在被读取时静默地错一个语义，而这类错误没有任何信号（它不报错，只是结果不对）。

### 关于第 3 条的完整论证（短路为什么必须显式）

替代方案是"默认继续，除非监听器显式终止"。它的吸引力在于让"只观察"的监听器写法更自然——读一个值、什么也不做，就结束了。这个方案在两种情形下出错。

第一种是遗漏。一个本该改写值的监听器因为某个分支忘记返回 `next` 而变成了"终止"，于是后面所有监听器的效果消失。在默认继续的语义下，同样的遗漏只是"这个监听器没起作用"，影响面小得多。第二种是语义混淆。默认继续时，"我不打算改变它"与"我忘了处理这种情况"在代码上无法区分，而在默认终止的语义下，两者被一条 `next` 调用分开。

本课程选显式 `next` 的理由是让遗漏的后果与它的原因成正比：忘记写 `next` 会终止整条链，而终止立刻可见（后续监听器不执行、调用方拿到中间值），因此它会在第一次测试时暴露。若默认继续，同样的遗漏不会立刻可见，它的表现是"某个改写没生效"，而那需要有人记得该生效过才知道少了什么。

这条决策的代价要写清：所有只观察的监听器都要多写一行 `return next(value)`，而这一行在代码上看起来是多余的。缓解方式是把这条要求写进扩展点的契约模板，并在评审时把它作为检查项——它的成本是一次性的（写的时候多一行），收益是长期的（遗漏不再静默）。

### 关于第 1 条的完整论证（关键路径为什么不用广播）

替代方案是"一律用广播，包括持久化、鉴权这类关键路径"。它的好处是统一：所有插件都通过同一套机制挂载，新增行为不需要区分类型。代价出现在两个地方。

第一，缺失不可检测。广播没有返回值，因此发出方无法知道"这件事有没有人处理"。如果持久化被实现成一个监听器而它因为配置错误没有装载，系统会静默地不持久化——故障在下次重启时才发现，而那时已经丢失了这段时间的数据。第二，执行顺序不确定。同一个事件可能有多个监听器，而关键路径需要确定的顺序（先鉴权再执行再持久化）。广播不提供顺序保证，于是关键路径的正确性依赖于"注册顺序恰好正确"这个脆弱的前提。

用直接调用或 waterfall 可以同时解决这两点：直接调用的返回值就是处理结果，缺失会变成"调用不存在的函数"这个立刻可见的错误；waterfall 的值传递提供了明确的顺序语义。代价是新增行为需要改动调用点，而这条代价恰好是关键路径应当承担的——关键路径上的每一步都应当被显式地写出来，而不是被某个插件悄悄地接上。

这条决策的一般形式是：扩展点适合承载"可以没有"的行为，不适合承载"必须有"的行为。判断一个行为属于哪一类，问它缺失时的故障是"功能少了一点"还是"系统的核心承诺被破坏"。

## L3 实现（施工图）

### 3.1 文件结构

```
// kernel/events.ts
// ┌─ 监听器段 ────────────────────────────────────────
// │  Listener 的类型与优先级包装
// ├─ 注册段 ──────────────────────────────────────────
// │  on(name, fn, priority?)：返回撤销函数并登记进上下文
// ├─ 广播段 ──────────────────────────────────────────
// │  emit(name, payload)：顺序调用，忽略返回值
// ├─ 瀑布段 ──────────────────────────────────────────
// │  waterfall(name, value)：逐层传递，短路可见
// └─ 撤销段 ─────────────────────────────────────────
//    上下文退出时按逆序撤销它登记的监听器
```

五段的分工与 2.3 的容器是同一形状。差别在于瀑布段多出一个"短路可见"的要求——实现必须在监听器没有调用 `next` 时能识别出来，而不是把"未改写"与"终止"混为一谈。

### 3.2 监听器的存储与顺序

```ts
interface Registration {
  readonly fn: Listener<unknown>
  readonly priority: number
  readonly owner: object          // 归属，与 2.3 的条目同一条规则
}
```

排序的实现有两种：插入时按优先级有序插入（查找时直接顺序执行），或者在每次广播前排序（插入是常数时间，广播是 O(n log n)）。本课程选择后者，理由是注册发生在启动期而广播发生在运行期——把成本放在注册期更好，但启动期的注册次数远小于运行期的广播次数，因此"启动期排序一次并缓存"是最优解，也是实现的默认选择。

### 3.3 广播与瀑布的实现

```ts
async function emit(name: string, payload: unknown): Promise<void> {
  for (const reg of listOf(name)) {
    await reg.fn(payload)          // 返回值被忽略
  }
}

async function waterfall<T>(name: string, value: T): Promise<T> {
  let acc = value
  for (const reg of listOf(name)) {
    let advanced = false
    acc = await reg.fn(acc, (next: T) => { advanced = true; return next })
    if (!advanced) return acc      // 短路：后续监听器不执行
  }
  return acc
}
```

这两段代码里有一处容易被写错的地方：`waterfall` 中的 `advanced` 标记必须在调用 `next` 的那一刻置位，而不是在监听器返回之后判断"返回值是否等于传入值"。若用后者，一个把值改成相同内容（`next(value)`）的监听器会被误判为终止——这类缺陷在测试里很难被发现，因为它要求"改写后的值恰好等于原值"。

### 3.4 撤销与逆序

撤销沿用 2.3 的约定：每个 `on` 返回撤销函数，同时把监听器登记进当前上下文的 effect 列表；上下文退出时按逆序执行。逆序的理由与 2.3 相同——后注册的监听器往往依赖先注册的设施。

### 3.5 验收判据

| # | 判据 | 怎么检查 |
|---|---|---|
| 1 | 广播按注册顺序调用全部监听器 | 注册三个记录顺序的监听器，核对调用顺序 |
| 2 | 广播忽略返回值 | 让第一个监听器返回一个值，检查它不影响后续 |
| 3 | 瀑布逐层传递修改后的值 | 两个监听器分别大写与加叹号，核对最终值 |
| 4 | 不调用 `next` 时短路，后续监听器不执行 | 中间插入一个不调用 `next` 的监听器，核对其后的监听器未被调用 |
| 5 | `next` 传入相同值时不算短路 | 一个监听器 `next(value)` 原样传回，后续监听器仍执行 |
| 6 | 撤销之后该监听器不再被调用 | 撤销中间那个，核对只剩两端 |
| 7 | 优先级高的先执行 | 注册顺序与优先级相反，核对执行顺序按优先级 |
| 8 | 上下文退出时它的监听器全部被撤销 | 退出后广播，核对该上下文的监听器都没有被调用 |
| 9 | 监听器抛错时传播到调用方 | 让中间监听器抛错，核对 `emit` 抛出且错误对象一致 |
| 10 | 同一个监听器注册两次时调用两次，撤销一次只去掉一个 | 核对调用次数与撤销后的剩余数 |

第 5 条与第 10 条是最容易被漏掉的两条：前者检验短路的判断方式，后者检验撤销的粒度。它们都不属于"正常路径"，因此只在按判据逐条检查时才会被想到。

先做监听器的存储与注册（判据 1、2），再做瀑布与短路（判据 3、4、5），然后做优先级（判据 7），最后做撤销与归属（判据 6、8、10）。判据 9 在每一步都可以检查。

### 3.7 事件系统的诊断入口

事件系统是最难排查的一类机制，原因是"为什么这个行为发生了"的答案分散在多个监听器里。因此它的实现应当自带三个诊断入口。

第一个是列出某个事件的全部监听器及其来源。排查"这个事件被谁处理了"时，第一个问题是"有哪些监听器"，而如果实现只提供"广播"不提供"查看"，这个问题就只能靠搜索代码回答——而搜索会漏掉动态注册的监听器。实现方式很简单：把监听器的注册列表暴露为一个只读查询。

第二个是记录一次广播里实际被调用的监听器。它与第一个的区别在于时间点：第一个看的是"当前注册了什么"，这个看的是"刚才那次有什么被调用了"。第二个更接近排查现场，因为它能回答"我明明注册了它，为什么这次没被调用"——答案通常是短路。

第三个是标志短路发生的位置。一次 waterfall 被终止时，日志里应当有一条记录说明"在第几个监听器处短路"。缺少它时，短路的唯一表现是"后续监听器没执行"，而排查者需要逐个比较注册列表与执行结果才能发现。这条记录的成本很低（在短路的那个分支里加一行），收益是把一类难查的缺陷变成一条可读的日志。

三个入口共同体现了本课程反复出现的那条原则：机制应当自带它自己出问题时的观察方式。事件系统尤其需要，因为它的执行路径不是由代码结构决定的，而是由运行时注册决定的——读代码无法回答"这次广播经过了谁"。

### 3.8 与容器的集成

事件系统本身不实现撤销，它使用 2.3 的容器提供的能力。集成方式有两种，而本课程的选择会影响监听器的写法。

第一种是事件系统持有容器引用，`on` 在内部调用 `ctx.effect` 把撤销动作登记进当前上下文。这样调用方写 `ctx.on(name, fn)`，不需要保存返回值。第二种是事件系统与容器解耦，`on` 只返回撤销函数，由调用方登记。前者更不容易出错（忘记保存返回值等于泄漏），代价是事件系统依赖容器这一层。

```ts
// 第一种集成：on 内部登记，调用方不需要保存返回值
export function on<T>(ctx: Context, name: string, fn: Listener<T>, priority = 0): void {
  const off = bus.register(name, fn, priority)
  ctx.effect(() => off)          // 登记进上下文，退出时自动撤销
}
```

本课程选第一种，理由与 2.3 的 `ctx.on` 默认自动登记一致：默认路径应当让正确做法不可能被遗漏。第二种集成在本项目里仍然保留——当某个监听器的生命周期与部件的生命周期不同时（例如它只在某次请求期间生效），调用方需要精确控制，此时它可以直接用底层的 `register` 并自己保存撤销函数。

### 3.9 一次装配的完整事件流

把本篇与前后几篇串起来看，一次模型调用经过的事件流大致如下（括号里是发起方）。

```
turn/start          （循环）        → 通知：一轮开始
before:model        （循环，瀑布）  → 介入：重试插件可改写请求、守卫可拦截
model/failed        （模型层）      → 通知：失败，重试插件据此决定是否重试
tool/before         （循环，瀑布）  → 介入：守卫可拦截、参数可改写
tool/after          （工具系统）    → 通知：结果与耗时
turn/end            （循环）        → 通知：一轮结束，统计与日志在此收尾
```

这张清单有三个用途。第一，它说明哪些事件是瀑布（允许介入）而哪些是广播（只通知）——判据是"这个动作是否允许被改写或阻止"。第二，它给出第 3 卷各机制的挂载位置：重试挂在 `model/failed` 与 `before:model` 上，守卫挂在 `tool/before` 上，可观测挂在那几个通知事件上。第三，它可以直接作为第 2.7 篇会话事件的初稿——广播类事件往往是需要落盘的那些，因为它们描述"发生了什么"。

### 3.10 实现里最容易写错的三处

按判据实现的顺序做完之后，有三处仍然值得单独检查，因为它们的错误表现都不是"功能不对"，而是"偶发"或"很久之后"。

第一处是短路的判断方式。正确做法是在 `next` 被调用的那一刻置位；错误做法是比较返回值与传入值。后者在"监听器原样传回一个相同的值"时会误判为短路，而这要求值恰好相等——这类缺陷在测试里出现的概率取决于数据的分布，因此它可能在开发期一直不出现。

第二处是撤销时的归属判断。正确做法是只摘掉属于当前上下文的监听器；错误做法是按名字清空。后者在两个上下文注册了同一个事件的监听器时会把另一个的也摘掉，而这种情形在单部件测试里不存在。

第三处是优先级排序的时机与稳定性。正确做法是在注册期排序并缓存；错误做法是每次广播前排序（成本高）或依赖注册顺序（顺序不稳定）。另有一个细节：相同优先级的监听器之间应当保持注册顺序（稳定排序），否则同一份代码在不同的运行里可能有不同的行为，而那会让偶发缺陷变得无法复现。

三处的共同形态是"正确做法与错误做法写起来都只有几行，而错误做法的失败被推迟到特定条件下"。它们也是本卷负向验证脚本要覆盖的三类变体——判分器的鉴别力正是由这些"看起来合理"的错误实现来检验的。

## L5 语法速查

### 5.1 术语表

| 术语 | 在本篇里的准确含义 | 容易误解为 |
|---|---|---|
| 事件 | 一次"发生了某件事"的通知，发出方不知道谁在听 | "回调"（回调的发出方知道调用谁） |
| 广播 | 把事件通知给全部监听器，忽略返回值 | "调用所有监听器并收集结果" |
| waterfall | 逐层传递同一个值，每层可改写或终止 | "广播的一种"（它能改变结果，广播不能） |
| 短路 | waterfall 链在中途停止 | "提前返回"（它是契约行为，不是优化） |
| 扩展点 | 明确允许挂行为的地方，含四项约定 | "能改的地方"（没有约定的地方不算扩展点） |
| 钩子 | 挂在扩展点上的具体实现 | "事件监听器"（它通常只有一个） |
| 可忽略事件 | 不认识它时读取方可以安全跳过的事件 | "不重要的事件" |

### 5.2 命令速查

| 目的 | 命令 | 说明 |
|---|---|---|
| 跑事件契约测试 | `node tests/t7-events.mjs` | 十条判据 |
| 负向验证 | `node grade/negative-check-events.mjs` | 四类错误实现应全部被抓 |
| 找没有撤销的监听器 | `rg -n '\.on\(' src/ \| rg -v 'return\|ctx.on'` | 命中即说明它绕过了自动登记 |

### 5.3 三条容易踩的规则

第一条，只观察的监听器要显式放行。写成"读完就返回"等于终止整条链，而它的后果是后续监听器静默失效。

第二条，短路的判断看有没有调用 `next`，不看值有没有变。用值比较会把"原样传回"误判为终止。

第三条，监听器要通过上下文登记，而不是自己保存撤销函数。前者不会漏，后者依赖每个调用点都记得。

## L7 挑战题（不给答案）

第一题：给 waterfall 加"可观测的短路原因"。 现在短路只表现为链的终止，调用方无法知道是谁终止的。设计一种让它可见的方式，并说明它对性能的影响。

第二题：设计事件的超时。 某个监听器卡住会让整个广播悬挂。给出超时机制，并说明超时之后由谁决定如何继续。

第三题：可忽略事件的派生检查。 设计一种机制，在开发期自动检测"某个被标为可忽略的事件其实会影响派生结果"。

第四题：为多监听器设计背压。 当某个事件的产生速度超过监听器的处理速度时，系统会积压。给出你选择的策略（丢弃、限流、还是排队）与它的代价。

第五题：论证"一切都用事件"的一个合理场景。 找到一个场景，其中连关键路径也适合用广播，并说明它满足什么额外条件。

第六题：反驳优先级机制。 构造一个场景，说明按注册顺序可能比显式优先级更好。

## L9 仍未解决（这一篇自己的缺陷）

| 缺陷 | 后果 | 修法 | 当初为什么这么写 |
|---|---|---|---|
| 广播没有返回值，发出方无法知道有没有人处理 | 关键路径若误用广播会静默失效 | 用 waterfall 或直接调用表达关键路径（L2 第 1 条） | 广播的语义就是"通知"，让它返回结果会引入监听器之间的耦合 |
| 监听器抛错会中断整条广播 | 一个不稳定的监听器能停住整个流程 | 按事件类型声明"容忍错误"，或引入隔离执行 | 让错误可见是刻意的选择；隔离执行需要引入错误归因（第 4 卷） |
| 没有背压与积压控制 | 高频事件会让监听器排起长队 | 引入队列与丢弃策略 | 本卷的事件都是同步或短异步的，积压尚未成为问题 |
| 可忽略标记依赖人工判断 | 标错了会让旧版本派生出错误历史 | 在开发期做派生一致性检查（挑战题第三题） | 自动判定需要理解派生逻辑，而那正是要保护的东西 |
| 事件载荷没有版本 | 载荷结构的变更无法单独演进 | 引入载荷版本或按新事件类型承载 | 整体版本号（`SESSION_FORMAT_VERSION`）覆盖了绝大多数情形 |
| 没有跨进程的事件 | 多进程时无法通知 | 引入消息系统（第 5 卷的 webhook 入口触及一部分） | 本卷是单进程的 |

前两条属于"位置放错"——错误隔离与关键路径的可检测性本该在事件机制里被考虑，而本篇把它们推给了调用方；中间两条属于能力缺失（背压与自动检查）；最后两条属于边界。第二条值得特别注意：它是第 3 卷守卫与重试的直接输入，因为那两个机制都会挂在不稳定的外部依赖上，而"一个监听器抛错会停住整条广播"这条性质会对它们产生实际影响。

### 问题升级练习

模糊问题：「我该怎么设计一个可扩展的系统？」

升级后的精确问题：

> 可扩展性至少要回答三件事：哪些行为允许外挂（扩展点的位置与数量）、外挂的行为怎么被调用（顺序、短路、抛错）、以及外挂的行为如何被撤下（归属与撤销）。
> 这三件事里第一件与第二件互相制约——扩展点越多，每个扩展点的调用语义就越难统一。
> 我能不能为每一件事找出一条**可检查的判据**？
> 特别是：有没有哪一条判据，是**能在一次装卸演练里被验证的**？

提升点说明：原问题无法回答，因为"可扩展"没有边界。升级后的版本把目标收成三件有位置的事，指出其中两件的制约关系，并追加以一个更强的问题：哪一条判据能在装卸演练里验证。这一问指向的正是"卸载之后监听器不再响应"这条判据。

## L11 系统影响回溯

回看第 0.5 节的三个连锁影响。

| 预判 | 本篇分析之后的结论 | 状态 |
|---|---|---|
| 把流程拆成事件会让"有没有人处理"不可判定 | 确认，并给出了判据（关键路径用直接调用或 waterfall） | 成立 |
| 监听器顺序按注册顺序时不稳定，而人们会依赖它 | 确认，并给出"有先后的用优先级、其余声明为无序"的处置 | 成立且更具体 |
| 事件的格式演进比函数接口更严 | 确认，并给出了可忽略标记与版本号的分工 | 成立且更具体 |

一处需要修正的预判：0.5.2 把"监听器的归属撤销"标为强依赖，但没有说明它依赖的是哪一篇的机制。读完之后要补上：它依赖的是 2.3 的 `effect` 与归属约定——事件系统本身不实现撤销，它只是使用容器提供的能力。这个区别有实际影响：如果 2.3 的归属机制实现有误，本篇的十条判据里有三条会失败，而它们看起来像是事件系统的缺陷。

通向下一篇的桥。 本篇解决了"行为挂在哪里"，而它留下了一个没有答案的问题：事件的可见范围。在一个进程里同时跑两条会话时，A 会话的事件应不应该被 B 会话的监听器收到。如果答案是"不该"，那么事件系统需要一层隔离；如果答案是"该"，那么两条会话之间就存在耦合。

下一篇 `2.5 作用域与隔离` 处理这件事。它与本篇的连接点是归属：作用域的实现基础正是"这一批注册属于谁"，而本篇的监听器归属恰好是它的一部分——作用域退出时要撤销的，就是本篇里那一批被登记的监听器与服务。

## 本篇新词

长程任务（long-horizon task） 指同时满足三个条件的任务：跨越多次会话（或多次上下文窗口）、状态量超过一次能载入上下文的量、以及目标需要被保持而不能每次重新理解。三个条件缺一不可——一次会话内的大重构虽然长，但它在同一个上下文里，因此不是长程问题；一个跨三天的调研即使在技术上很简单，也是长程问题。

任务状态（task state） 指推进一个任务所需的最小信息集合：目标、约束、进度、决策记录、未决问题、产物位置、检查点、以及下一步。它与会话日志的差别是它是被筛选出来的（日志是全量的），与记忆的差别是它属于一个任务而不是一个人。

外部化（externalization） 指把任务状态写在系统之外（一个文件、一份台账），而不是留在上下文或人的记忆里。它有三个理由：上下文会被压缩（3.3）、会话会结束（4.1）、以及人和 agent 都要能读同一份状态（协作的前提）。

续作（resumption） 指在中断之后继续推进。它的成本由重建成本决定：读一份状态文件是 O(状态)，而重放全部历史是 O(历史)。两者的量级差随任务长度增长，因此续作的可行性完全取决于状态是否被外部化。

检查点（checkpoint） 在任务级指一个可验证的里程碑——它的判据是"到这里为止的产物可以被独立检查"。它与 3.5 的进程级检查点是同一个概念的两种粒度：进程级检查点让恢复不必从头重放，任务级检查点让续作不必重新理解。

进度判断（progress assessment） 指回答"做到哪了、还剩多少"。它的困难在分母：长任务的分母通常在推进过程中才变得清楚，因此百分比估算会系统性乐观（"永远快完成了"的成因）。可操作的替代是里程碑加剩余待办数。

目标漂移（objective drift） 在长程语境下指目标在推进过程中被逐步改写——每一步都合理，累积起来已经偏离原始意图。它与 4.5 的漂移同形（那里改的是系统规则，这里改的是任务目标），而防线也同形：原始目标冻结。

范围蔓延（scope creep） 指任务的范围不断扩张（"顺便也把那个改了"）。它与目标漂移的差别是前者加东西、后者改方向；两者的共同点是没有显式的变更记录。

唯一下一步（single next action） 指状态里唯一一条"接下来做什么"。它的作用是让续作的入口足够小——续作者只需要读一条就能启动，而不需要读完整个状态再自己判断。

```
 一句话串起来：状态放哪 → 怎么续作 → 怎么判断进度 → 怎么不被悄悄改掉
```

这张图的关键线索在第一块：长程任务的全部困难都可以追溯到"状态放在哪里"。放在上下文里会被压缩掉，放在记忆里会失去任务结构，放在人的脑子里会在中断后丢失——只有外部化的状态才能被多个执行者（人、多个会话、新的上下文）共享，而共享是续作的前提。

### 0.1 一个具体的判断：续作的两种成本

设一个任务的会话历史有 200K token，而它的外部化状态有 2K token。

| 续作方式 | 要读的东西 | 成本量级 | 引入的错误 |
|---|---|---|---|
| 重放历史 | 200K token 的全部历史 | 200K | 压缩有损；早期约束可能已被压掉 |
| 读状态文件 | 2K 的状态（加最近若干轮上下文） | 2K | 状态本身可能过时（需要维护纪律） |

第一行的成本不只是 token：历史里包含大量与当前进度无关的内容（讨论过的分支、试错过程），而执行者需要在噪声里自己重建"我们现在在哪"。第二行把这件事变成了读一份摘要，代价是状态必须被主动维护——而维护纪律正是本篇要讲的机制。

两行的量级差（100 倍）决定了长程任务的可行性上限：不外部化的系统在任务长度超过一个上下文之后就开始失效，而它的表现不是报错，而是"回到已经做完的事情上"或者"忘记早期确定的约束"。

### 0.2 本篇建立的三项判据

第一项用于判断状态是否合格：问"一个不知道这个任务的人读完能不能接着做"。这条判据的检验方式是找另一个人（或另一个会话）试一次续作，看它是否卡在缺失的信息上。

第二项用于判断进度判断是否可用：问"剩下的待办能不能被数出来"。不能数说明里程碑没有定义清楚，而百分比估算在此刻是不可靠的（分母不清）。

第三项用于判断目标是否被保持：问"当前的方向与原始目标最后一次比对是什么时候"。长期没有比对是漂移的信号，而它不需要发现具体偏差就能触发一次复查。

### 0.5.3 三个连锁影响

第一，任务状态与记忆会争抢容量，而它们的分工必须明确。 记忆存的是跨任务的事实（用户偏好、项目约定），任务状态存的是单个任务的结构化进度。把任务状态写进记忆会污染记忆的检索（一个已完成任务的进度对任何后续任务都无用），而把记忆当作状态会丢失任务结构。因此任务状态应当是独立的存储，且它在任务完成后可以被归档（而不是留在活跃集合里）。

第二，长程任务的失败模式主要不是能力不足，而是状态丢失。 四类失败（原地打转、遗忘约束、重复劳动、范围蔓延）里前三类的成因都是状态缺失，而它们与"模型不够聪明"无关——把状态外部化之后，同样能力的系统能推进的任务长度会显著增加。这条判断解释了为什么长程能力在工程上主要是一个状态管理问题。

第三，目标冻结把"变更"从隐性变成显性，而代价是灵活性下降。 原始目标不可被直接修改（只能追加"目标修订"记录），这意味着合法的变更要多走一步。这一步的成本正是它的目的：让每一次方向调整都被看到。它与 4.5 的元控制完全同构（门控不可被演化修改），而理由也相同——允许逐步修改等于允许漂移。

### 0.5.4 它与本书其余部分的关系

本篇的状态是单机、单任务的。多个任务并行时的调度与优先级不在范围内（第 5 卷的多会话会触及一部分），而多人协作时的状态合并（同一个任务有多人推进）也不在本课程范围内。这条边界意味着本篇的结论在"一个人或一个 agent 推进一个任务"上是完整的，而它的结构与多人协作所需的版本化状态相容（外部化是可合并的前提）。

> **面试视角**
> **高频问法**："长程任务最容易出什么问题？"
> **高分要点**：说出"状态丢失"这一类（含它的三种表现：原地打转、遗忘约束、重复劳动），并指出它不靠更强的模型解决，而靠外部化。只谈"上下文长度限制"会漏掉结构问题。

## L0 要解决的问题

### 0.1 现象一：每次接着做都要重新读一遍全部历史

第一个现象是续作成本高。任务中断之后（会话结束、上下文被压缩、或者隔了一天），重新开始时执行者要读大量的历史才能知道"现在在哪"。

它的代价有两部分：一是成本（0.1 的 100 倍量级差），二是准确性——历史被压缩之后（3.3），早期的约束与决策可能已经被压掉，而执行者不知道它们存在。第二种代价更危险：它表现为"做着做着发现方向不对"，而原因是某条早期约束没有被读到。

### 0.2 现象二：状态只存在会话里，会话一结束就没了

第二个现象是状态没有外部化。任务的目标、约束、进度都只在当前会话的上下文里，而它们不会被写下来。于是下一个会话开始时的处境是：要么从零开始理解任务，要么让用户重新说明。

它的修法是 1.2 的八个字段与 1.3 的外部化。而这里有一个容易忽略的细节：外部化的对象不只是"进度"，还包括决策记录（做过什么选择、为什么）——少了它，续作时会把已经排除的方案重新评估一遍，而那是重复劳动最常见的来源。

### 0.3 现象三："快完成了"永远是快完成了

第三个现象是进度判断失真。任务推进过程中反复得到"快完成了"的评估，而实际剩余的工作量并没有减少——因为分母在推进中才变清楚（本篇新词里的进度判断）。

它的修法是 1.5 的里程碑加剩余待办数：不问"完成了几成"，而问"还剩几件可验证的事"。前者的分母不确定，后者是可数的事实。

### 0.4 现象四：目标被悄悄改了，而没有人注意到

第四个现象是漂移与蔓延。任务推进中，目标被逐步改写（每次调整都合理），或者范围不断扩张（"顺便也把这个加了"）。单次调整看不出来，累积之后原始意图已经不在。

它的修法是 1.6 的目标冻结加变更记录：原始目标写在状态里且不被修改，任何方向调整都作为一条新增的修订记录（含理由与时间）。关键不是禁止变更，而是让变更可见——可见的变更可以被复核，而不可见的变更只能被事后发现。

### 0.5 现象五：同一个坑踩了两次

第五个现象是状态缺失的另一种表现：已经排除的方案被重新评估，已经踩过的坑被重新踩。它的成因是决策记录没有外部化（0.2 的分析），而它的代价在长任务上可观——一次重新评估的成本可能等于推进本身。

### 0.6 这一篇要正面回答的四个问题

第一，任务状态包含什么、放在哪里（1.1–1.3）。第二，怎么续作、成本如何（1.4）。第三，怎么判断进度（1.5）。第四，怎么保持目标（1.6）。

四个问题里第一个是基础，而第四个是这一篇与其他机制最相通的部分（它与 4.5 的元控制、1.5 的可逆性都同构）。

## L1 设计与原理

### 1.1 长程任务的三个特征与它们的后果

三个特征（本篇新词）各自带来一个具体的技术后果。

跨越多次会话意味着状态必须在会话之外存在（1.3），而它的实现成本是"必须维护"（没人维护的状态会过时，而过时的状态比没有状态更糟——它给出错误的方向）。

状态量超过一次可载入的量意味着需要有"摘要"这一步——不是所有状态都能进上下文，因此必须有优先级（哪些必须读、哪些按需读）。这与 4.2 的渐进披露是同一手法：先给最小入口（唯一下一步），需要时再展开。

目标需要被保持意味着目标本身要作为状态的一部分被冻结（1.6），而不能依赖执行者的记忆。

三个后果合起来给出一个设计原则：长程系统的核心设施是"可维护的外部状态"，而它的难点不在存储（一个文件足够），而在维护纪律——状态必须随推进被更新，而更新的触发点需要被设计（1.4 的检查点）。

### 1.2 任务状态的八个字段

| 字段 | 内容 | 维护时机 |
|---|---|---|
| 目标 | 原始目标（冻结）与当前精确化 | 任务开始时写一次；修订时追加记录 |
| 约束 | 不可违反的规则（判据形式） | 开始时；发现新约束时 |
| 里程碑 | 可验证的阶段（每个带检查方式） | 完成一个时更新 |
| 进度 | 已完成、进行中、待办（可数的项） | 每次推进之后 |
| 决策记录 | 做过什么选择、为什么、排除了什么 | 每次做选择时 |
| 未决问题 | 待确认的事项（谁确认、何时截止） | 出现与解决时 |
| 产物位置 | 文件、分支、外部引用 | 产生时 |
| 下一步 | 唯一的下一动作（带验证方式） | 每次推进之后 |

八个字段里有三个是需要特别说明的。

决策记录与未决问题是长程任务里最容易被省略的两个（因为它们在单会话任务里不重要——那时的状态还在脑子里）。而它们在跨会话时是成本最高的部分：决策记录少了会让已排除的方案被重新评估，未决问题少了会让同一个问题被反复提出。

"下一步"必须是唯一的。多条下一步等于没有入口（续作者要先做判断），而唯一的一条让续作的启动成本降到最小。这条要求有一个副作用：推进过程中要不断更新它，而更新它的动作本身就是一次"我清楚现在该做什么"的确认。

约束要写成判据而不是原则。"保持代码整洁"不是约束（不可检查），而"每篇 17 节骨架齐全、检查脚本通过"是约束。这条要求与 4.1 的写入策略、4.4 的可行动性判据是同一条原则的三次应用。

### 1.3 外部化：为什么必须在系统之外

四个理由按强度排列。

上下文会被压缩（3.3）：这是最直接的理由。任务状态如果只存在上下文里，压缩会不可逆地丢失它——而压缩的选择依据是相关性，任务状态恰好可能在"看起来不相关"的时候被压掉（例如在讨论具体实现时，目标那句话显得很远）。

会话会结束（2.7）：一条会话有结束的时候，而任务没有。

人需要读它：协作与自查都要求状态可读。一份只有系统能读的状态在人看来等于没有——而人在长任务里的角色（做判断、给约束）要求他能看到全貌。

它必须可 diff：状态的演进（目标改了、范围扩了）只有在可比较的形式下才能被看见。这条理由决定了外部化的形态是文本文件而不是数据库行——diff 是审查的基础。

### 1.4 续作：检查点与重建成本

续作的流程有四步，而每一步对应一个状态字段。

```ts
export interface TaskState {
  readonly goal: string                  // 原始目标（冻结）
  readonly revisions: readonly Revision[]  // 目标修订记录（追加，不修改 goal）
  readonly constraints: readonly string[]  // 判据形式
  readonly milestones: readonly Milestone[] // 每个带 check
  readonly done: readonly string[]        // 已完成项
  readonly doing: readonly string[]       // 进行中的项（通常一项）
  readonly todo: readonly string[]        // 待办（可数）
  readonly decisions: readonly Decision[] // 含理由与排除项
  readonly open: readonly OpenQuestion[]  // 待确认
  readonly artifacts: readonly string[]   // 产物位置
  readonly next: string                   // 唯一下一步（带验证方式）
  readonly updatedAt: number
}

export function resume(state: TaskState): Resumption {
  const lastCheckpoint = [...state.milestones].reverse().find((m) => m.done)
  const nextMilestone = state.milestones.find((m) => !m.done)
  return {
    startHere: state.next,                                       // 第一步：读唯一下一步
    context: { goal: state.goal, constraints: state.constraints, decisions: state.decisions },
    remaining: state.todo.length,                                // 第二步：可数的剩余
    verifyAt: nextMilestone?.check ?? null,                       // 第三步：下一个检查点
    warnings: detectStale(state),                                 // 第四步：状态是否过时
  }
}
```

四步的顺序有讲究：先给入口（`startHere`），再给必要的上下文（目标、约束、决策），然后给进度与下一个检查点，最后给出"这份状态可信吗"的警告。第四步的 `detectStale` 处理一个真实问题：状态可能已经过时（任务推进了而状态没更新），而它的判据是"产物位置的东西比状态里的记录更新"（文件时间戳）或者"已过若干天未更新"。

过时状态的危害大于没有状态：它给出方向，而方向是错的。因此警告必须是续作流程的一部分，而不是可选的检查。

### 1.5 进度判断：里程碑与剩余待办

进度判断的困难在分母（本篇新词）。三种做法的对比：

| 做法 | 缺陷 |
|---|---|
| 百分比（完成了 70%） | 分母不确定；系统性乐观 |
| 里程碑（五个里完成了三个） | 里程碑的粒度可能不均（有的里程碑大得多） |
| 剩余待办数（还剩 7 件） | 待办可能被低估（未知的工作不会出现在列表里） |

三者的组合是可行的：里程碑用于对外沟通（它给出阶段感），剩余待办数用于内部判断（它是可数的），而两者的偏差本身是一个信号——当剩余待办数持续不降而里程碑在推进时，说明发现了新工作（范围在扩张，1.6）。

这条"偏差即信号"的用法与 3.6 的"主指标配护栏"是同一种手法：两个互补的度量，它们的背离比它们各自的数值更有信息量。

### 1.6 目标冻结与变更记录

目标冻结的实现方式是原始目标字段不被修改，任何调整作为 `revisions` 里的一条追加记录（含理由、时间、以及它替代了什么）。

三个防线。

防线一是原目标可读：续作时读到的永远是原始目标加修订记录，因此执行者能看到"从哪来、改过什么"。只读最新目标会丢失这个视角。

防线二是修订要写理由：一条"把范围从 A 扩到 A+B"的记录如果没有理由，它在下一次复盘时无法被评估（是必要的补充还是蔓延？）。

防线三是范围变更要显式：新增工作项时，状态里要区分"原计划内的待办"与"新增的待办"。这条区分的成本很低（一个标记），而它让范围蔓延可见且可数——而"可数"是处理它的前提（与 1.5 的剩余待办数是同一个手法）。

### 1.7 四类长程失败模式

| 模式 | 表现 | 成因 | 防线 |
|---|---|---|---|
| 原地打转 | 反复回到已经做完或已经排除的事 | 状态缺失（决策记录） | 决策记录外部化 |
| 遗忘约束 | 做着做着违反了早期确定的规则 | 约束只在早期上下文里 | 约束写成判据并常驻状态 |
| 重复劳动 | 同一个坑踩两次 | 状态缺失（进度与决策） | 进度与决策记录 |
| 范围蔓延 | 任务无限变大 | 新增工作没有显式记录 | 新旧的标记与定期复查 |

四类的共同点是它们都不源于执行者的能力（0.5.3 的第二条），而源于状态。这给了处置一个明确的指向：把状态外部化并保持更新，四类都显著减轻。

还有第五类值得单独列出：过早收敛（为了收尾而收尾）。它的成因与前三类相反——它是目标被反过来适配于已有进度（"剩下的不好做，那就说达到了目标吧"）。防线是检查点必须可验证（1.5）：一个里程碑的完成如果只有一个模糊的说法支撑，它就不算完成。

### 1.8 第二部分：人自己的长程执行

同样一套方法用在人身上，而它的形态更简单——因为人的"上下文"不会自动压缩，但会更直接地遗忘与走神。

状态外部化：把状态写在文件里而不是记在脑子里。判据与系统侧相同（0.2 的第一项）：换一个人来接着做，他能不能只靠这份记录继续。

唯一下一步：每次中断前（下班、切换任务、开会之前）写下唯一的下一动作，且带验证方式。这条习惯的收益在恢复时体现：重新坐下来的第一件事从"想想我刚才做到哪了"变成"读那一行然后开始"。

检查点式推进：把任务切成可验证的阶段，每个阶段有明确的完成判据。没有检查点的长任务会一直处于"进行中"，而那种状态无法判断进度，也无法交接。

定期重读原始目标：至少每完成一个检查点重读一次。它不是形式——多数漂移是在"很久没看原目标"之后发生的。

记录决策理由：尤其是被排除的方案。它的收益在两周后：那时已经忘了当时为什么排除某个方案，而重新评估一遍的成本很高。

### 1.9 案例：本课程自己的多轮推进

这一套方法在这个课程的生产过程里被实际使用，而它的修正过程本身就是案例材料。

任务的特征与 1.1 的三条完全吻合：跨越多次会话（十几轮）、状态量超过一个上下文（24 篇讲义，每篇约 25K 字符）、目标需要保持（六卷结构与写作规范）。

使用的机制与它们的对应关系：

| 机制 | 本课程里的形态 |
|---|---|
| 状态外部化 | `进度.md`：总目标与验收标准、每篇的实测指标、作业状态、下一步、已知缺口 |
| 约束写成判据 | 0.3 规范的篇幅门槛、加粗口径、17 节骨架 |
| 检查点可验证 | `scripts/check-lecture.mjs`：锚点、占比、加粗、表情符号一次全查 |
| 唯一下一步 | 台账里的"下一步"节，每次更新 |
| 决策记录 | 4.7 的位置决策（`dec-91ec1639cd5835f6`）、篇幅门槛的三次校准理由 |
| 范围变更显式 | "已知缺口"节（4.7 就是从这里被提出的） |

三次真实的修正，它们的成因与修法：

第一次是"状态依赖对话摘要"。早期的进度信息只存在对话历史里，而它对长任务是有损的（摘要会丢细节）。修法是建立台账，并把"不接受'我记得'作为状态来源"写成台账的第一条规则。

第二次是"重复劳动"。每一轮都要重写一遍验证脚本（同样的检查逻辑写十几遍）。修法是固化为 `scripts/check-lecture.mjs`——一次写成工具，后续直接调用。这条修法与 4.2 的"沉淀技能"完全一致：发现重复的动作应当被沉淀为可复用的形态。

第三次是"发现的问题靠记忆"。审计发现的问题（加粗超标、锚点缺失）没有记录，于是可能被忘掉。修法是台账里的待修清单（后来清零），并规定"发现即登记，检查不通过不得标记完成"。

这个案例的结论值得写下来：课程里的方法在它自己的生产过程中被验证过，而验证的方式是它先失败过几次——前两次失败（状态丢失、重复劳动）恰好就是本篇 1.7 表格里的第二与第三类。

### 1.10 两次追问

工程侧的问题是什么时候归档任务状态。判据是"任务已完成且其决策记录已被吸收到别处"（例如沉淀成了技能或写进了项目文档）。归档而不是删除，理由是它在复盘时需要（4.6 的产出跟踪与历史复盘）。这与 4.1 的"抑制而不是删除"同类，但自由度更高——任务状态不像记忆那样涉及个人数据。

产品侧的问题是长程能力对用户意味着什么。多数用户感受到的不是"系统能记住状态"，而是不必重复交代背景——而这正是同一件事的另一面。因此面向用户的呈现应当是一句可见的承诺（"下次继续时我不需要你重新说明"）加上一个可查看的入口（状态文件本身）。

## L2 决策表

| # | 决策 | 我们的选择 | 替代方案 | 代价落在谁身上 |
|---|---|---|---|---|
| 1 | 状态的载体 | 独立的文本文件 | 会话日志的一部分 | 要维护两份；换来可读可 diff |
| 2 | 状态的粒度 | 八个字段 | 只记进度 | 维护成本更高；换来续作不缺信息 |
| 3 | 下一步 | 唯一一条，带验证方式 | 列若干条待办 | 要频繁更新；换来续作入口最小 |
| 4 | 约束的写法 | 判据形式（可检查） | 原则形式 | 写起来更费事；换来能被验证 |
| 5 | 决策记录 | 必须含理由与排除项 | 只记结论 | 记录更长；换来不重复评估 |
| 6 | 进度判断 | 里程碑加剩余待办数 | 百分比 | 要维护两份；换来偏差可作信号 |
| 7 | 里程碑的定义 | 每个带检查方式 | 只给名字 | 定义成本高；换来完成可判定 |
| 8 | 目标修改 | 冻结原目标，追加修订记录 | 直接改目标 | 要多写一条记录；换来漂移可见 |
| 9 | 范围变更 | 标记"新增"并与原计划分开数 | 混在一起 | 状态里多一个标记；换来蔓延可数 |
| 10 | 状态过时的处置 | 续作时警告并举证 | 假定状态可信 | 要多做一次时间戳比对；换来不误导 |
| 11 | 状态与记忆的关系 | 分开存储，任务完成后归档 | 写进记忆 | 两个存储；换来记忆的检索不被污染 |
| 12 | 交接的形式 | 状态可被另一个执行者直接读 | 口头或会话内交接 | 状态要写得自包含；换来可并行与可替换 |

其中两条值得展开，因为它们的选择在实践中经常被做成另一个。

### 关于第 8 与第 9 条的完整论证（为什么冻结而不是随时改）

替代方案是允许直接修改目标字段（"目标变了就改一下"）。它的优点是灵活、没有额外负担，代价在三个地方。

第一，修改是累积的而方向变化是不可见的。一个任务的目标经过十次小调整之后，与原目标的关系已经从"更精确"变成"另一件事"——而没有任何一个时刻能看出来。

第二，它让"评估是否有必要"失去依据。复盘要问"这次范围扩张是否值得"，而这个问题需要对照原始目标（4.6 的复盘输入）。没有原目标时，只能对照最新目标——而最新目标已经包含了那些扩张。

第三，它让交接失去基线。新的执行者接到的目标是"当前版本"，他无法判断哪些是原意、哪些是后来的补充，因此他无法拒绝后来的补充（因为它们看起来同样正当）。

第 9 条（新增项标记）是同一逻辑的细化：光有原目标还不够，还要能数出新增了多少。这两条合起来让范围变化成为可审查的事实，而不是一个只能靠感觉察觉的现象。

### 关于第 3 与第 5 条的完整论证（为什么要一条下一步、要记排除项）

替代方案是把待办列成清单，续作者自己选一条开始。它在单会话任务里是合理的（选一条的成本很低），而在跨会话续作里有两个问题。

第一，选择的成本落在状态最不清楚的人身上。续作者（可能是几天后的自己，或另一个会话）需要先把整个待办与上下文读完，才能判断哪一条该先做——而这正是 1.4 要避免的重建成本。写下唯一的下一步，等于让做出选择的人（当时状态最清楚的人）承担这个成本。

第二，唯一的下一步是一个可验证的承诺。写下它之后，"下次开始做什么"这件事就确定了，而它的正确性可以被后续验证（做了之后发现不对，说明当时的判断有问题）。清单里的若干条则没有这个性质。

第 5 条（记排除项）的理由在 0.5 的现象五：重新评估一个已经排除的方案，成本可能等于推进本身。而排除项的价值随时间增长——刚排除时人人都记得，两周后只有记录还在。

### 3.1 文件结构

```
// plugins/long-horizon.ts
// ┌─ 状态段 ── TaskState 的定义、读写与校验（判据式约束）
// ├─ 续作段 ── resume（入口、上下文、剩余、检查点、过时警告）
```

五段与 L2 的决策一一对应，其中状态段是基础（其余四段都在读改它），而归档段是它与其他机制的接口。

### 3.2 状态段

```ts
export function writeState(state: TaskState, ctx: Context): void {
  if (!state.next || state.next.length < 8) throw new Error('缺少唯一下一步（或它太短，无法作为入口）')
  const bad = state.constraints.filter((c) => !isCheckable(c))
  if (bad.length) throw new Error(`约束必须可检查：${bad.join('；')}`)                  // 判据形式（L2 第 4 条）
  if (state.doing.length > 1) throw new Error('进行中的项应当只有一项')                  // 聚焦
  const nextState = { ...state, updatedAt: ctx.now }
  atomicWrite(ctx.statePath, renderState(nextState))                                    // 复用 3.5 的原子写
}
```

三处校验对应三条设计约束：唯一下一步存在（L2 第 3 条）、约束可检查（第 4 条）、进行中只有一项（聚焦）。第三条容易被视为多余，而它的作用在续作时体现：进行中有三项时，续作者要先判断先做哪一项（回到 3.2 要避免的成本）。

### 3.3 续作段

```ts
export function resume(state: TaskState, ctx: Context): Resumption {
  const nextMilestone = state.milestones.find((m) => !m.done)
  const stale = detectStale(state, ctx)
  return {
    startHere: state.next,
    context: { goal: state.goal, revisions: state.revisions, constraints: state.constraints, decisions: state.decisions },
    remaining: { todos: state.todo.length, added: state.todo.filter((t) => t.added).length },
    verifyAt: nextMilestone ? { name: nextMilestone.name, check: nextMilestone.check } : null,
    warnings: stale,
  }
}

function detectStale(state: TaskState, ctx: Context): string[] {
  const out: string[] = []
  const newest = Math.max(...state.artifacts.map((a) => ctx.mtime(a)), 0)
  if (newest > state.updatedAt) out.push('产物比状态新：状态可能漏记了进展')       // 时间戳举证（L2 第 10 条）
  if (ctx.now - state.updatedAt > ctx.config.staleAfter) out.push('状态长期未更新')
  if (state.doing.length === 0 && state.todo.length > 0) out.push('有待办而没有进行中的项：进度记录可能不完整')
  return out
}
```

`detectStale` 的三条判据都是可机械检查的，而它们覆盖了状态过时的三种成因：漏记进展、长期未维护、以及记录不完整。

### 3.4 进度段

```ts
export function assess(state: TaskState): Progress {
  const ms = { done: state.milestones.filter((m) => m.done).length, total: state.milestones.length }
  const todos = { open: state.todo.length, added: state.todo.filter((t) => t.added).length }
  // 偏差即信号：里程碑在推进而待办不降，说明发现了新工作（1.5）
  const divergence = ms.done > 0 && todos.open >= state.baselineTodoCount
  return { milestones: ms, todos, divergence, note: divergence ? '里程碑推进但待办未减少：范围可能在扩张' : null }
}
```

`divergence` 是 1.5 那条"偏差即信号"的实现，而 `baselineTodoCount` 是任务开始时记录的待办基线——没有基线时无法判断"没减少"，因此它必须在任务开始时写入状态。

### 3.5 变更段与归档段

```ts
export function reviseGoal(state: TaskState, revision: Revision, ctx: Context): TaskState {
  if (!revision.reason) throw new Error('目标修订必须给出理由')                        // L2 第 8 条
  return { ...state, revisions: [...state.revisions, { ...revision, at: ctx.now }] }    // 追加，不改 goal
}

export function addScope(state: TaskState, item: TodoItem, ctx: Context): TaskState {
  return { ...state, todo: [...state.todo, { ...item, added: true, addedAt: ctx.now }] } // 标记新增（L2 第 9 条）
}

export async function archive(state: TaskState, ctx: Context): Promise<void> {
  await ctx.moveTo(ctx.archivePath, renderState(state))                                  // 归档而不是删除（1.10）
  await ctx.appendEvent({ type: 'task/archived', goal: state.goal, milestones: state.milestones.length, at: ctx.now })
}
```

两个函数都只做追加（`revisions` 与 `todo`），而 `goal` 字段从不被修改——这条不可变性是冻结的实现方式（不是靠约定，而是靠接口不给修改入口）。

### 3.6 验收判据

| # | 判据 | 怎么检查 |
|---|---|---|
| 1 | 缺少唯一下一步时写入被拒 | 构造无 `next` 的状态 |
| 2 | 约束不可检查时被拒 | 写一条"保持整洁" |
| 3 | 进行中超过一项时被拒 | 构造两项 `doing` |
| 4 | 续作返回入口与上下文 | 核对 `startHere` 与 `context` |
| 5 | 续作返回可数的剩余 | 核对 `remaining.todos` |
| 6 | 续作给出下一个检查点 | 核对 `verifyAt.check` |
| 7 | 产物比状态新时给出警告 | 造一个比状态新的产物文件 |
| 8 | 长期未更新时给出警告 | 造一个 `updatedAt` 很早的状态 |
| 9 | 里程碑推进而待办不降时给出偏差提示 | 构造该组合 |
| 10 | 目标修订必须带理由 | 构造无理由的修订，核对抛错 |
| 11 | 新增待办被标记 | 调用 `addScope` 后核对 `added` 为真 |
| 12 | 归档保留状态且记事件 | 归档后核对归档文件与日志 |
| 13 | 换一个执行者能只靠状态继续 | 人工试读（找一个不知道任务的人） |

第 13 条是这一篇的核心判据（0.2 的第一项），而它只能靠人来检查——它检验的是"状态是否自包含"，而那是一个可读性问题而不是可计算问题。

### 3.7 实现顺序

先做状态定义与校验（判据 1、2、3、10、11），再做续作（判据 4、5、6、7、8），然后做进度（判据 9），最后做归档与人工验证（判据 12、13）。

## L9 仍未解决（这一篇自己的缺陷）

| 缺陷 | 后果 | 修法 | 当初为什么这么写 |
|---|---|---|---|
| 状态的维护依赖纪律 | 不更新就会过时，而过时比没有更糟 | 自动更新（挑战题第二题）加过时警告 | 自动更新无法判断语义字段 |

| 单任务单执行者 | 并行与协作不在范围内 | 可合并的状态格式（挑战题第四题） | 本卷的任务是单线的 |
| 状态过时判据依赖文件时间戳 | 内容更新而时间戳不变时判不出来 | 增加内容哈希或版本号 | 时间戳是最低成本的信号 |
| 目标冻结增加了变更成本 | 合法调整要多走一步，可能被视为繁琐 | 保持追加记录的轻量（一行） | 显式化是它的目的 |
| 状态与复盘的产出跟踪是两套 | 两处都要看，可能不一致 | 统一为一份"未完成项"视图 | 两者的生命周期不同 |

第二条与第四条属于"信号不可靠"，第一条与第三条属于纪律与范围，第五条与第六条属于设计取舍。第一条值得单独标记：它意味着这套机制在缺少纪律时会退化——而退化的形态是最危险的（状态存在但过时，给出错误的方向）。这与 4.6 的"形式化复盘"是同一类问题：机制的存在不等于机制在起作用，而它的失效往往没有信号。

升级后的精确问题：

> 长任务不失控至少包含三件互相制约的事：状态（放在哪里、包含什么）、续作（中断之后怎么接着做）、以及保持（目标与范围如何不被悄悄改写）。

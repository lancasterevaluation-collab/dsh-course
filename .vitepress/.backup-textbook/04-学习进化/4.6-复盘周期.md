## 本篇新词

复盘周期（review cycle） 指按固定节奏回顾一段时间内的失败、改动与资产，并产出下一轮动作的机制。它与"诊断"的差别在范围：诊断处理一次失败，复盘处理一批——它要找的是模式，而不是单次的因果。

真实任务集（real task set） 指从真实使用中采样出来的任务集合，用于充当门控的回归基线。它与"人工设计的评估集"的差别在分布：人工集偏向边界情况，真实集偏向常见情况，而两者的失败模式不同。

回归基线（regression baseline） 指一组已知结果的任务，用于判断"这次改动是否让以前能做对的事情变差了"。它的要求是稳定（同一版本两次运行的结果接近），否则它无法区分改动的效果与噪声（4.5 的 0.3）。

触发（trigger） 指启动一次复盘的条件。有三种：按时间（每周一次）、按事件（同类失败在短时间内出现 N 次）、按阈值（某项指标越界）。三者的关系是互补的——按时间保证不漏，按事件保证及时。

产出（output） 指一次复盘的具体结果。它不是一份文档，而是一组可跟踪的动作：一条演化的提议、一次技能的修改、一条记忆写入规则的调整、或者一条进入待观察清单的项目。没有产出（或产出无人跟踪）的复盘等于没有发生。

跟踪（follow-up） 指对上一次复盘的产出做检查。它是复盘周期里最容易缺失的一环——多数复盘的问题不是分析不深，而是结论没有被执行。它的实现很具体：每条产出带一个状态（未开始、进行中、完成、放弃并说明理由）。

复盘的成本（review cost） 指一次复盘消耗的时间与资源。它必须被计入，因为它与收益竞争——复盘花的时间不能超过它带来的改进的价值，而这条约束决定了周期长度与样本量。

形式化复盘（ceremonial review） 指走完流程而没有产生动作的复盘。它的成因通常是产出没有被跟踪（做不做都一样）或者结论不可行动（与 4.4 的 0.2 同因）。它是这个机制最主要的失效模式。

这张图的关键线索在第三块：复盘的价值全部落在"产出被跟踪"上，而这一点与前面的机制形成一条通路——诊断给结论、演化改系统、复盘保证这两件事持续发生。前四个机制不保证自己被使用，只有复盘周期做这件事。

### 0.1 一个具体的判断：真实任务集的规模

门控的鉴别力取决于任务集规模（4.5 的 0.1 给出过漏检率）。设真实流量里某类退化发生在 5% 的请求上，而任务集有 N 个任务，那么漏检概率约为 `(1 − 0.05)^N`。

| 任务数 | 漏检概率 |
|---|---|
| 20 | 36% |
| 50 | 8% |
| 100 | 0.6% |
| 200 | 0.004% |

这张表说明五十个任务是一个有意义的门槛（漏检降到一成以下），而一百个任务能让常见退化几乎必然被发现。同时它给出成本的量级：每次门控要跑任务集两次（基线）加一次（候选），因此 100 个任务的评估意味着 300 次任务执行——这正是"复盘的成本"必须被计入的原因（本篇新词）。

两条实践推论：任务集应当分层采样（常见任务多取、罕见任务少取，因为前者更常出现），以及同一任务集可以复用多次（它的结果稳定，因此不必每次重新构建）。

### 0.2 本篇建立的三项判据

第一项用于判断复盘是否有效：问"上一轮的产出有几条被跟踪到了终态"。比例低说明复盘在形式化（本篇新词的最后一个词），而处置是先修跟踪，再谈分析深度。

第二项用于判断任务集是否合格：问"同一版本跑两次，结果的差异有多大"。差异决定了它能分辨多小的改善（4.5 的 0.3），而差异过大意味着任务数不足或任务本身不稳定。

第三项用于判断周期是否合适：问"两次复盘之间的产出条数"。长期为零说明周期太密（没事可做），而一次产出几十条说明太疏（积压）——后者还会让跟踪失去意义。

### 0.3 十分钟练习：同一版本两次运行的差异

下面这段代码用同一版本跑两次，估计任务集的稳定性。

```js
const runA = [true, true, false, true, true, true, false, true, true, true]
const runB = [true, true, true, true, false, true, false, true, true, true]
const same = runA.filter((v, i) => v === runB[i]).length
const rateA = runA.filter(Boolean).length / runA.length
const rateB = runB.filter(Boolean).length / runB.length

console.log(`一致的任务：${same}/${runA.length}`)
console.log(`成功率差异：${Math.abs(rateA - rateB).toFixed(2)}（这就是噪声下限）`)
const unstable = runA.map((v, i) => v !== runB[i]).filter(Boolean).length
if (unstable > 1) console.log(`${unstable} 个任务本身不稳定，应剔除或隔离`)
```

这段代码给出三个数字：一致的任务数（任务集的稳定性）、成功率差异（噪声下限）、以及不稳定任务数。第三个最重要：不稳定任务会让整个任务集的鉴别力下降，而它们的成因通常是任务依赖了外部状态（网络、时间、随机性）——处置是把它们隔离成一组、单独观察，而不是留在主任务集里制造噪声。

> **面试视角**
> **高频问法**："你怎么知道系统越改越好？"
> **高分要点**：说出"真实任务集加回归基线"这条机制，并指出任务集的稳定性决定了它能分辨多小的改善。只说"看指标"没有回答"怎么排除噪声"。

### 0.5.3 三个连锁影响

第一，复盘会把前面五篇串成一条因果链，而链条的强度由最弱一环决定。 诊断没结论则演化无输入；演化无门控则复盘要花更多时间看效果；任务集不稳定则门控无鉴别力。因此复盘的产出条数少，往往不是复盘做得不好，而是链条上某处断了——这条诊断线索值得写下来，因为它能把"复盘无效"这个笼统的问题定位到一个具体环节。

第二，周期会改变系统的行为模式。 周期太密时，每次改动的样本太少（改进落在噪声里）；太疏时，单次改动过多（无法归因）。这与 4.5 的"改善大于两倍噪声"相互作用：周期长度应当保证两次复盘之间有足够的样本积累。

第三，复盘是唯一会回头看"上次说的事做了吗"的机制。 这条性质让它在长程任务里成为一个天然的检查点——它可以同时承担 4.7 的"进度检查"职责（把待办、观察项与产出的跟踪状态合起来看）。

### 0.5.4 它与本书其余部分的关系

本篇的复盘是单机、单项目的。跨项目或团队级的复盘需要把多份复盘的产出聚合（它涉及数据边界与权限，与 4.3 的 1.5 同类）。本课程不覆盖团队协作的复盘流程，而只覆盖"一个系统自己回顾自己"这一形态——它的结论对团队复盘仍然适用（动作与跟踪这两条要求是共同的）。

## L0 要解决的问题

### 0.1 现象一：复盘走完了流程，而没有发生任何事

第一个现象是形式化复盘（本篇新词）。它的形态是一次完整的会（或一份完整的报告）：时间线、影响、原因、行动项都写了，而两周之后再看，那些行动项没有任何一条被完成——也没有人记得它们存在。

它的成因有两个，而处置不同。成因一是产出没有被跟踪（做不做都一样），处置是给每条产出加状态并让它在下一轮被检查。成因二是结论不可行动（4.4 的 0.2 同因），处置是回到诊断环节重做结论。两者的表现相同而修法不同，因此区分它们需要看产出本身（有没有可改对象），而不只是看完成率。

### 0.2 现象二：门控用的评估集与真实用法差得太远

第二个现象是门控脱离真实分布。它的形态很典型：评估集是设计者写的（覆盖了各种边界情况），而真实使用集中在少数几种常见任务上。于是改动在评估集上通过、在真实使用里退化——因为退化发生在那些常见任务上，而评估集里它们只占少数。

修法是 1.3 的真实任务集：从真实会话里分层采样（常见任务多取），而设计者写的边界情况作为补充而不是主体。两者的配比有一个经验值——主体是真实采样，边界情况占少数（它们用于防极端退化，而不是衡量日常表现）。

### 0.3 现象三：任务集不稳定，分辨不出改善

第三个现象是基线本身在动。同一版本跑两次的结果差异很大（0.3 的练习给出估计方式），于是任何改动的效果都落在噪声里，门控失去鉴别力。

它的成因有三类：任务依赖外部状态（网络、时间、随机种子）、任务的判定标准模糊（同一个结果有时算通过有时不算）、以及任务数量太少（少数几个任务的波动主导了整体）。三类的处置不同：第一类固定外部条件、第二类把判定写成可执行的检查（4.1 的 `check` 同源）、第三类增加任务数。

### 0.4 现象四：周期不当，要么无事可做要么积压

第四个现象是节奏。周期太密时，两次之间的样本太少（改动无法归因），而复盘本身要花时间——它变成了纯粹的开销。周期太疏时，两次之间积累了十几处改动与几十条失败，而复盘无法处理这个量级（它只能抽样，于是又回到"不知道哪个改动导致了什么"）。

判据在 0.2 的第三项（两次之间的产出条数），而它的取值区间很宽（一到十条都属于正常）——可操作的做法是先取一个较疏的周期，再按实际积压程度收紧，因为收紧比放松容易（放松意味着要接受已有的失败积累）。

### 0.5 这一篇要正面回答的四个问题

第一，什么时候复盘（1.1）。第二，复盘什么、用什么样本（1.2、1.3）。第三，产出什么、怎么跟踪（1.4、1.5）。第四，怎么算有效（1.6）。

四个问题里第三是这一篇的实质——它是唯一与前面五篇不同的部分（前两个问题在别的机制里有对应形态，而"产出与跟踪"是复盘独有的）。

## L1 设计与原理

### 1.1 三种触发与它们的互补

三种触发（本篇新词）各自覆盖不同的失效。

按时间（例如每周一次）保证不漏——即使没有任何异常，也会有一次回顾。它的作用在发现"缓慢的退化"（指标每周降一点，而单周不显著）。

按事件（同类失败在短时间内出现 N 次）保证及时——一个突发的模式不必等到下周。它的实现依赖 4.4 的诊断结论被结构化（按现象与层聚类），否则"同类"无法判定。

按阈值（某项指标越界，例如成本单日超预算）保证严重问题被立即处理。它与 3.6 的报警是同一条机制的不同粒度——阈值触发处理"必须现在处理"的，而时间触发处理"迟早要处理"的。

三者的关系是互补而不是互斥，而它们的共同前提是证据必须已经存在（日志、度量、诊断结论）。没有证据时三种触发都不会发生——因为没有任何东西越过它们的条件。

### 1.2 复盘的范围与样本

复盘的范围有三个维度，而每次复盘通常聚焦其中之一。

| 维度 | 范围 | 典型问题 |
|---|---|---|
| 按时间窗口 | 最近一周的全部失败与改动 | 有没有缓慢退化；改动有没有效果 |
| 按会话/用户 | 某条会话或某类用户 | 这类使用为什么成本高 |
| 按主题 | 某一类失败（例如超时） | 它有没有共同原因 |

三个维度的样本选法不同。按时间窗口是全量取样（它要的是不漏）。按会话是选定对象（它要的是深度）。按主题是筛选后取样（它要的是模式）。

范围过大是复盘的常见错误：一次复盘试图覆盖全部三个维度，结果是每个都只扫一眼。正确的做法是每轮选一个维度，而按时间窗口作为默认（它的成本最低且能发现缓慢退化）。

### 1.3 真实任务集的构建

三步构成。

第一步是采样：从真实会话里挑出"有明确成功判据"的任务。这个条件把可复用的候选缩小到那些结果可以被检查的任务（4.4 的失败判定依赖成功判据，这里依赖同一件事）。

第二步是分层：按任务的常见程度分层，常见的多取、罕见的少取（0.1 的两条推论）。分层的依据通常有现成的维度——任务类型（改代码、查资料、写文档）、规模（单文件、多文件）、以及是否涉及外部系统。

第三步是稳定性筛选：用 0.3 的方法跑两次，剔除或隔离不稳定的任务。这一步不能省——一个不稳定的任务会让整个任务集的鉴别力下降，而它的表现是"门控总是通不过"或"总是通过"。

```ts
interface RealTask {
  readonly id: string
  readonly kind: string                                   // 分层维度
  readonly prompt: string
  readonly check: string                                  // 可执行的检查（成功判据）
  readonly stability: number                              // 两次运行的一致度（1 表示完全一致）
  readonly environment: Record<string, string>            // 固定外部条件的字段
}

export function buildTaskSet(samples: readonly RealTask[], target = 100): RealTask[] {
  const stable = samples.filter((t) => t.stability >= 0.9 && t.check)   // 稳定性与判据双筛
  const byKind = groupBy(stable, (t) => t.kind)
  return stratifiedPick(byKind, target)                                  // 分层采样
}
```

三个字段（`check`、`stability`、`environment`）对应上面三步，而 `environment` 是"固定外部条件"这个处置的实现方式。

### 1.4 产出与跟踪

产出的四种形态与它们各自的归属。

| 产出 | 归属 | 完成判据 |
|---|---|---|
| 演化提议 | 4.5 | 通过门控并被发布 |
| 技能修改 | 4.2 | `check` 通过 |
| 记忆或写入策略调整 | 4.1 | 注入行为改变 |
| 待观察项 | 4.4 的待观察清单 | 出现模式或过期 |

四种产出的共同要求是带状态（未开始、进行中、完成、放弃）。而"放弃"这一状态值得单独强调：它必须带理由，否则跟踪会诱使人们把放弃的项目标记为"进行中"（从而看起来没有积压）。

跟踪的实现是在下一轮复盘的开头检查上一轮的产出，而它的判据是覆盖率（0.2 的第一项）——覆盖率低于某个水平时，本轮复盘的产出不应当增加（先清积压，再提新的）。这条规则防的是"产出越积越多而没人做"。

### 1.5 五环的调度顺序

一次复盘按固定顺序过五环，而这个顺序有依赖关系。

```ts
export async function runCycle(ctx: Context): Promise<CycleResult> {
  const followUps = await checkPreviousOutputs(ctx)        // 第零步：先清跟踪
  const failures = await collectFailures(ctx.window)        // 一段时间内的失败
  const patterns = clusterByPattern(failures)               // 聚类（4.4 的结论字段）
  const diagnoses = await diagnoseTop(patterns, ctx, 3)     // 只处理前几个模式（成本约束）
  const proposals = diagnoses.flatMap((d) => proposeFor(d)) // 产出提议
  return { followUps, patterns, diagnoses, proposals, cost: ctx.cost() }
}
```

三处设计要点：第零步是跟踪检查（1.4 的规则）、只处理前几个模式（复盘的成本约束，1.6）、以及成本被返回（它是下一轮判断周期是否合适的输入）。

第五步（演化提议）之后不再往下走——评审与发布由 4.5 的门控完成，复盘不越界。这条分工与"门控不可被绕过"（4.5 的 1.5）是同一条：复盘能提议，但不能决定。

### 1.6 复盘的成本与收益

成本由三部分构成：收集与聚类（读日志与度量，随窗口长度增长）、诊断（每次诊断跑任务集或重放，成本较高）、以及评审与跟踪（人的时间）。

收益有两部分：被解决的失败（可数）与被避免的失败（不可数，它来自改动的影响面）。第二部分的不可测性意味着收益往往被低估，而成本是可见的——这条不对称会让周期被不断拉长，直到复盘事实上停止。

处置方式是把成本显式记录下来（1.5 的返回值），并在判断周期长度时用它：如果一次复盘的成本超过了它带来的改进的价值，那么应当缩小范围（每轮只看一个维度）而不是延长周期——因为延长周期会让单次复盘的工作量增加（积压），而成本随之上升。

### 1.7 复盘与长程推进会合

复盘是长程任务的天然检查点（0.5.3 的第三条）。它提供三样东西：待办的跟踪状态（哪些事在做、哪些被放弃）、观察项的检查（4.4 的第六字段）、以及进度的判断依据（产出条数与完成率的趋势）。

这三样合起来回答"我们做到哪了"这个问题的一部分，而它的另一部分（原始任务的进度）由 4.7 给出。两者的关系是：复盘管"改进系统"这条线的进度，4.7 管"完成一个具体任务"这条线的进度——它们是同一套方法在两个对象上的应用。

### 1.8 两次追问

工程侧的问题是什么时候该暂停复盘。判据是"连续若干轮没有产出可行动的结论"。暂停之前应当先检查链条上哪一环断了（0.5.3 的第一条），因为暂停会掩盖断点——而断点通常在诊断或可观测那两处。

产品侧的问题是复盘对用户意味着什么。多数用户不需要知道系统在自我复盘，而他们感受到的是行为的一致性与改进的连续性（不会今天改了明天又改回来）。因此复盘产出的行为变化应当在发布时被说明（4.5 的 1.8），而不需要把复盘本身暴露给用户。

## L2 决策表

| # | 决策 | 我们的选择 | 替代方案 | 代价落在谁身上 |
|---|---|---|---|---|
| 1 | 触发方式 | 三种并存（时间、事件、阈值） | 只用时间 | 要维护三种条件；换来不漏且及时 |
| 2 | 每轮的范围 | 一个维度（默认时间窗口） | 全维度扫一遍 | 单次覆盖变窄；换来每轮都有深度 |
| 3 | 任务集的来源 | 真实会话的分层采样为主 | 设计者编写的边界用例为主 | 采样要人工筛选；换来贴近真实分布 |
| 4 | 任务集的规模 | 一百个左右 | 二十个够用 | 每次评估更贵；换来漏检率降到 1% 以下 |
| 5 | 不稳定任务的处置 | 隔离成单独一组 | 留在主集里 | 要维护两组；换来主集噪声可控 |
| 6 | 任务的可复用 | 长期复用同一集 | 每轮重建 | 任务集会过时；换来结果可跨轮比较 |
| 7 | 产出的形态 | 四种带状态的动作 | 一份报告 | 要维护跟踪；换来能做检查 |
| 8 | "放弃"状态 | 允许但必须带理由 | 不允许 | 要写理由；换来跟踪不被扭曲 |
| 9 | 覆盖率低时 | 本轮不再提新产出 | 照常提 | 一轮可能没有新产出；换来积压不失控 |
| 10 | 复盘的检查对象 | 上一轮的产出 | 全部历史 | 早期积压不复查；换来本轮成本可控 |
| 11 | 成本的处理 | 显式记录并返回 | 不计 | 一次字段；换来周期长度有依据 |
| 12 | 复盘的边界 | 只提议，不发布 | 直接应用改动 | 要走门控流程；换来与 4.5 的分工清楚 |

其中两条值得展开，因为它们的选择在实践中经常被做成另一个。

### 关于第 9 与第 10 条的完整论证（为什么先清积压）

替代方案是每轮照常产出新动作，跟踪只在有时间时做。它的吸引力是"不浪费复盘的机会"，而它的三个后果逐一显现。

第一，产出的完成率会持续下降。每轮新增的动作多于完成的，于是未完成项累积，而累积到一定程度之后，跟踪本身变成一项大工程——于是它被跳过（0.1 的形式化复盘由此产生）。

第二，动作的价值随时间衰减。一条"调整某个阈值"的动作在提出时是有上下文的（当时观察到什么），而三周之后上下文已经不在，执行它的人需要重新研究——成本上升而收益不变。

第三，放弃的动作挤占注意力。它们仍在待办列表里，而每一轮都要被扫过一遍。

第 10 条（只检查上一轮而不是全部历史）是这个处置的配套：把检查范围限制在上一轮，让成本可控，而更早的积压通过"标记为放弃并说明理由"一次性清理。两条合起来给出的规则是：覆盖率低时先清积压，再提新的。

### 关于第 3 与第 6 条的完整论证（为什么真实采样为主、为什么长期复用）

替代方案是让设计者编写任务集（它更容易覆盖边界情况）。它在早期的评估里是合理的（还没有真实数据），而它有两个长期问题。

第一，它衡量的是设计者的想象，不是系统的实际用法。真实使用的分布通常比设计者预想的更集中（少数任务类型占多数），而退化恰好容易发生那些常见类型上（0.2 的现象）。

第二，它会随系统的变化而过时。设计者写的任务集针对的是当时的能力边界，而系统改进之后那些任务变得过易（它们不再有鉴别力）。

第 6 条（长期复用同一集）与第二点看似矛盾，而它们的关系是分工：长期复用让跨轮比较成为可能（同一集上的结果可以直接比），而过时通过"逐步替换其中一部分"处理（例如每季度替换两成）。替换而不是重建——因为重建会让所有历史比较失效。

### 3.2 触发段

```ts
export function shouldReview(state: CycleState, ctx: Context): Trigger | null {
  if (ctx.now - state.lastReviewAt >= ctx.config.reviewInterval) return { kind: 'time', reason: '周期到' }
  const recent = state.failures.filter((f) => ctx.now - f.at <= ctx.config.burstWindow)
  const sameKind = maxByKind(recent)
  if (sameKind.count >= ctx.config.burstCount) return { kind: 'event', reason: `同类失败 ${sameKind.count} 次` }
  const breach = ctx.metrics.firstBreach(state.thresholds)
  if (breach) return { kind: 'threshold', reason: `${breach.metric} 越过阈值` }
  return null
}
```

三种条件按"严重程度递增"的顺序判断（时间最轻、阈值最重），因此一次触发的原因被记录下来——它决定了这次复盘该聚焦哪个维度（1.2）。

### 3.3 任务集段

```ts
export async function refreshTaskSet(current: readonly RealTask[], samples: readonly RealTask[], ctx: Context): Promise<RealTask[]> {
  const stable = samples.filter((t) => t.check && t.stability >= ctx.config.minStability)
  const candidate = stratifiedPick(groupBy(stable, (t) => t.kind), ctx.config.taskSetSize)
  const replaceRatio = ctx.config.rotationRatio                                  // 每轮替换的比例
  const keep = current.slice(0, Math.floor(current.length * (1 - replaceRatio)))
  const fresh = candidate.slice(0, Math.ceil(current.length * replaceRatio))
  const next = [...keep, ...fresh]
  const recheck = await recheckStability(next, ctx)                              // 替换后重测稳定性
  return recheck.kept
}
```

`replaceRatio` 是第 6 条那个"逐步替换两成"的实现，而 `recheckStability` 处理一个容易漏掉的点：新加入的任务可能不稳定，而它会把整个任务集的噪声抬高——因此替换之后必须重测。

### 3.4 产出与跟踪段

```ts
type OutputState = 'todo' | 'doing' | 'done' | 'dropped'

export interface ReviewOutput {
  readonly id: string
  readonly kind: 'proposal' | 'skill-edit' | 'memory-policy' | 'watch'
  readonly action: string                          // 可行动的描述（4.4 的判据）
  readonly state: OutputState
  readonly dropReason?: string                      // 放弃时必须给出（L2 第 8 条）
  readonly openedAt: number
  readonly closedAt?: number
}

export function coverage(outputs: readonly ReviewOutput[]): number {
  const closed = outputs.filter((o) => o.state === 'done' || (o.state === 'dropped' && o.dropReason))
  return closed.length / Math.max(1, outputs.length)                  // 带理由的放弃计入覆盖
}

export function gateOnCoverage(outputs: readonly ReviewOutput[], ctx: Context): boolean {
  return coverage(outputs) >= ctx.config.minCoverage                   // 覆盖率低时本轮不再新增（L2 第 9 条）
}
```

`coverage` 把"带理由的放弃"计入覆盖——这条设计避免了两种失真：把所有放弃都算作未完成（会让人不愿放弃），以及把无理由的放弃算作完成（会让覆盖率虚高）。

### 3.7 实现里最容易写错的三处

第一处是跟踪检查被放在复盘的最后。正确做法是把它放在最前（3.7 的第零步）；错误做法是先分析、最后顺带看一下上次的产出。后者的代价是分析出来的新产出会挤掉旧产出（注意力有限），而那正是积压形成的机制。

第二处是把覆盖率算成"完成数除以总数"。正确做法是把带理由的放弃计入覆盖；错误做法是只认完成。后者会让人不愿标记放弃（因为那会拉低指标），于是放弃项以"进行中"的名义长期留在列表里，而积压被隐藏。

第三处是任务集替换之后不重测稳定性。正确做法是替换后重跑一次并剔除不稳定的新任务；错误做法是直接并入。后者的代价是整个任务集的噪声被少数新任务抬高，而门控的鉴别力随之下降——它的表现是"最近门控变得很难通过"，而原因不在被评估的改动上。

## L7 挑战题（不给答案）

第一题：自动选聚焦维度。 设计一个机制，让复盘自己判断本轮该聚焦哪个维度（时间窗口、会话、主题），并说明判据。

第二题：任务集的自动补充。 真实会话里不断产生新任务，而任务集需要稳定。设计一个自动化程度更高的补充机制，并说明它如何避免把不稳定任务引入。

第三题：跨轮次的模式追踪。 一个模式在连续五轮复盘里都出现（每次都被处理但没有消失）。设计一个机制来识别并升级这个问题。

第四题：复盘的收益度量。 设计一组指标回答"复盘值不值得"，并把不可数的收益（被避免的失败）估计出来。

第五题：多人协作的复盘。 两个开发者共用一套系统。设计一个复盘机制，让产出有归属，并说明它与你现在的单机设计的差别。

第六题：论证"不做周期复盘"的一个合理场景。 构造一个场景，说明一个只做按需诊断而不做周期回顾的系统更好，并给出判据。

## L9 仍未解决（这一篇自己的缺陷）

| 缺陷 | 后果 | 修法 | 当初为什么这么写 |
|---|---|---|---|
| 任务集的构建需要人工筛选 | 采样成本高、更新慢 | 半自动筛选（从检查通过的真实会话里挑） | 成功判据的判定需要判断 |
| 聚类依赖 4.4 的字段质量 | 字段不准则模式找不对 | 先修 4.4 的结构化输出 | 复盘的输入质量不由本篇决定 |
| 每轮只处理前三个模式 | 其余模式继续积累 | 按严重度排序并设积压阈值 | 复盘的成本约束 |
| 覆盖率是唯一的健康指标 | 高频的小动作会拉高覆盖率而价值低 | 增加"产出价值"的维度（难量化） | 可量化的指标优先 |
| 不可数的收益难以估计 | 周期长度的判断偏保守 | 用被避免的失败做抽样估计 | 估计需要反事实 |
| 单机、单项目 | 团队协作与跨项目聚合不在范围内 | 见 0.5.4 的边界 | 本课程的范围 |

第一条与第二条属于输入质量，第三条与第四条属于成本与度量，第五条与第六条属于估计与范围。第四条值得单独标记：它意味着覆盖率可以被"多做小事"刷高，而系统真正需要的改进（一次较大的重构、一个结构性修复）在覆盖率指标上没有任何优势——这是古德哈特定律（3.6 与 4.5 都出现过）在本篇的第三次现身，而它说明这类健康指标都需要一个价值维度来配对。

### 五个层次

| 层次 | 例子 |
|---|---|
| 事实 | 三种触发是什么？产出的四种形态是什么？ |

| 科研 | 能不能量化复盘的收益，例如每轮复盘避免了多少次失败？ |

### 五种提问模板

反例逼问：如果产出不带状态，会发生什么。

边界追问：任务集要多大才能分辨 5% 的改善。

代价追问：把复盘周期缩短一半，代价落在谁身上。

替代对比：为什么任务集要逐步替换而不是重建。

验证追问：怎么证明"这一轮的复盘真的有用"。

### 本篇引出的十二个问题

读懂层。 第一，三种触发各覆盖什么失效？第二，复盘的三个范围维度是什么？第三，任务集的构建三步是什么？

重建层。 第四，为什么任务集要以真实采样为主？第五，为什么不稳定任务要隔离？第六，为什么替换任务时要重测稳定性？

设计层。 第七，产出为什么必须带状态？第八，带理由的放弃为什么计入覆盖？第九，五环的调度顺序为什么先清跟踪？

评审层。 第十，拿到一套复盘机制，你会先检查哪一处？第十一，怎么判断复盘是否在形式化？第十二，如果有人说"我们每周都开会复盘"，你怎么回应？

### 问题升级练习

模糊问题：「我怎么让系统持续变好？」

升级后的精确问题：

> 持续变好至少包含三件互相制约的事：发现（什么时候回顾、回顾什么，以及用什么样本）、产出（结论变成什么、谁来跟踪）、以及验证（怎么知道改进了而不是噪声）。
> 第一件与第三件互相制约——样本越多，判断越可靠，而复盘的周期就越长，积压也就越多。
> 我能不能为这三件事各找出一条**可检查的判据**？
> 特别是：有没有哪一条判据，是**能在下一轮复盘里被检查的**？

提升点说明：原问题无法回答，因为"变好"没有判据，而它默认了复盘会自动产生效果。升级后的版本把它拆成三件具体的事，指出样本量与积压的权衡，并追加以一个更强的问题：哪一条判据能在下一轮被检查——因为那一条决定了这个机制是否能自我维持。

## L11 系统影响回溯

回看第 0.5 节的三个连锁影响。

| 预判 | 本篇分析之后的结论 | 状态 |
|---|---|---|
| 复盘把五篇串成因果链，强度由最弱一环决定 | 确认，并给出"产出少往往是链条断了"这条诊断线索 | 成立 |
| 周期会改变系统的行为模式 | 确认，并把周期长度与"改善大于两倍噪声"接起来 | 成立 |
| 复盘是唯一回看"上次说的事做了吗"的机制 | 确认，并给出覆盖率与"带理由的放弃"这条实现 | 成立 |

一处需要修正的预判：0.5.2 把"真实任务集"标为对 6.2 的强依赖。读完之后要补一层方向：两者的要求不同——本篇要求任务集稳定（用于判断改动是否造成退化），而 6.2 的基准要求它有区分度（用于比较不同的方法）。两个要求可能冲突：一个稳定但过易的任务集对回归门控够用（不改坏就行），而它对科研比较毫无价值（所有方法都通过）。处置方式是维护两份：回归用的稳定任务集与实验用的挑战任务集，而它们的构建方式不同（前者采样常见任务，后者选困难任务）。

通向下一篇的桥。 第 4 卷的五环到此闭合，而这个闭环有一个共同的前提：它假设工作是在多次会话里连续推进的。记忆跨会话、技能跨会话、用户模型跨会话、复盘按周——它们全都建立在"任务比一次会话长"这个假设上，而没有任何一篇回答"一个任务跨多次会话时，进度与状态放在哪里"。

下一篇 `4.7 长程任务：任务级状态、续作与目标保持` 处理这件事，它是第 4 卷的第七篇，也是这卷的收口。它与本篇的连接点有两处：一是复盘提供"改进线"的进度，而 4.7 提供"任务线"的进度，两者合起来才是完整的"我们做到哪了"；二是复盘周期本身就是一个长程机制的实例——它需要一个外部化的状态（上一篇的覆盖率、本篇的周期时间戳），否则跨轮次无从续作。

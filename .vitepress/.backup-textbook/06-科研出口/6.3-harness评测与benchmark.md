## 本篇新词

基准（benchmark） 指一套可重复执行的评测：一个任务集、一个判定方式、一个执行环境、以及一个汇总指标。四个部分缺一不可——一个没有判定方式的任务集只是题目，不是一个基准。

任务集（task set） 指被评测的具体事项。它的关键性质是代表性：它从哪个分布里采样、覆盖了哪些情形、以及排除了哪些。"这个基准在测什么"这个问题的答案，一半在这里。

判定（judging） 指判断一次尝试是否成功的方式。它有三种：可运行的检查（测试通过、状态正确）、字符串匹配（答案比对）、以及模型评判（LLM-as-judge）。三者的可靠性递减，而成本也递减——这是评测里最需要谨慎选择的一环。

脚手架（scaffold / harness） 指把模型包装成"能完成任务的东西"的那一层：提示词、工具集、循环、重试、上下文管理。同一个模型在不同脚手架下的分数可以相差 7 个百分点以上——因此"某模型在某基准上得 X 分"这句话严格地说应当是"某模型在某脚手架下于某基准得 X 分"。

`pass@k` 与 `pass^k` 是两个方向相反的指标：`pass@k` 指 k 次尝试中至少一次成功（乐观，适合"可以挑一个最好的"场景）；`pass^k` 指 k 次尝试全部成功（悲观，适合"用户连续用 k 次"的场景）。同一个系统在两者下的差距可以是 40 个百分点（1.6 会给出量级）。

污染（contamination） 指评测数据进入了训练数据。它的后果是分数不再反映能力，而它的检测很难——因为"模型见过"与"模型会做"在输出上可能完全相同。

饱和（saturation） 指分数接近上限后失去区分度。它与"任务被解决"不同：饱和通常意味着任务集太窄或太易。

生态效度（ecological validity） 指基准里的表现与真实场景表现的一致性。它是所有基准最薄弱的一环：一个在冻结环境里得 78% 的浏览器 agent，在真实环境里可能只有 20% 出头（1.7 会给出这条差距及其六种成因）。

奖励黑客（reward hacking） 指系统利用评测本身的缺陷拿分而不是解决问题。它与"作弊"的差别是它可以是无意的：一个被训练去"让测试通过"的系统会自然发现评测的漏洞。

基准卡（benchmark card） 指一份对某个基准的结构化说明：它测什么、任务从哪来、怎么判定、现在的分数区间、已知缺陷、以及适用场景。本篇的交付物就是五张基准卡——而"会写基准卡"是读懂任何新基准的方法。

这张图的关键线索在第三块：一个基准的价值不在于它的分数，而在于它的缺陷是否被理解。同一份榜单，理解缺陷的人读出的信息量与不理解的人差一个量级——前者能说"这个数字在什么条件下成立"，后者只能说"它排第几"。

### 0.1 一个具体的判断：同一个模型的分数可以差多少

下面是四组"看起来矛盾"的数据，而它们都来自公开报道。

| 差异来源 | 量级 | 例子（来源与时间见下） |
|---|---|---|
| 脚手架不同 | 7–10 个百分点 | 同一模型在两种脚手架下的 GAIA 分数 64.9% 与 57.6% |
| 指标口径不同 | 十几到几十个百分点 | `pass@1` 与 `pass^k` 在 τ-bench 上的差距（单次约 61%，连续 8 次不足 25%） |
| 受控评测与自报 | 十几到三十几个百分点 | GAIA 的受控榜首约 74%，而厂商自报可达 84% 以上 |
| 基准版本不同 | 几十个百分点 | SWE-bench Verified 的 70–80% 与 Pro 的公开集约 23% |

四组差异的成因不同，而它们的共同教训是同一条：报一个分数而不报它的条件，等于没有报。因此读一个基准时，第一个问题不是"最高分是多少"，而是"这个分数在什么条件下取得"。

### 0.2 本篇建立的三项判据

第一项用于判断一个基准是否可信：问"它的判定方式是什么"。可运行检查 > 字符串匹配 > 模型评判——而三种判定各自的失效方式在 1.7 里被逐条列出。

第二项用于判断一个分数是否可比：问"两组数字的任务集、脚手架与指标口径是否相同"。三者有一处不同就不可直接比较——这条判据能解释多数的"榜单矛盾"。

第三项用于判断一个基准是否还活着：问"它的分数是否还在区分不同的系统"。当榜单前列的差距落在噪声内时（例如前 10 名里有 285/500 的题被所有人解出），它已经饱和——而饱和之后继续刷分不等于变强。

### 0.3 十分钟练习：`pass^k` 与可靠性悬崖

下面这段代码给出"单次成功率"与"连续 k 次全对"的关系。

```js
const single = [0.95, 0.90, 0.80, 0.70, 0.61]
const ks = [1, 2, 4, 8]

console.log('单次成功率 → ' + ks.map((k) => `pass^${k}`).join('　'))
for (const p of single) {
  const row = ks.map((k) => Math.pow(p, k).toFixed(3).padStart(6))
  console.log(`${p.toFixed(2).padStart(11)}  ${row.join('  ')}`)
}
```

输出里最值得看的一行是 0.61 那一行：单次 61%，而连续 8 次全对不到 2.5%（τ-bench 的报告给出的量级是"不足 25%"，差别在于他们把多次尝试看作近似独立而实际存在相关性——1.6 会讨论这条限制）。

这张表说明一条工程上极重要的判断："能做成"与"靠得住"是两个指标。多数基准只报前者，而生产环境需要的是后者。

> **面试视角**
> **高频问法**："你在 benchmark 上跑出的分数，你怎么判断它可信？"
> **高分要点**：说出三件事——判定方式（可运行检查优于模型评判）、口径（`pass@1` 还是 `pass^k`）、以及脚手架（同一模型换个 harness 分数就变）。只说"超过了 X 分"没有回答可信性。

### 0.5.3 三个连锁影响

第一，评测的口径会反向塑造系统设计。 如果团队的目标是"在某个基准上刷分"，那么系统会被优化成在这个基准的判定方式下得分——而当判定是字符串匹配时，这意味着输出格式会被过度优化；当判定是模型评判时，这意味着输出风格会被优化。这条影响与 3.6 的古德哈特定律是同一机制，只是这里的"指标"变成了外部基准。

第二，可靠性指标会改变对"能力"的评估方式。 一旦引入 `pass^k`，一条"单次 90% 而连续八次只有 43%"的系统与一条"单次 85% 而连续八次 40%"的系统之间，差异的排序可能与单次指标相反。处置方式是在评估时同时报告两个口径，而不是选一个更漂亮的。

第三，基准的缺陷会成为系统缺陷的来源。 一个被训练去通过测试的系统会发展出"让测试通过"的行为（例如只改测试期望、或绕过失败的用例）。这条连锁的处置不是"禁止"，而是"把判定绑定到世界状态而不是转录"（1.6 的"状态判定"）——而这条要求与 5.4 的"结果回收校验"是同一条原则：验证的是结果，不是过程叙述。

### 0.5.4 它与本书其余部分的关系

本篇讨论的是文本与工具类 agent 的公开基准，不涉及多模态专用任务集与安全红队基准的细节（它们各自有独立的方法论）。这条边界意味着本篇能让读者读懂主流基准，而它不替代安全评测的专门工作——后者需要对抗性设计与威胁模型，而那是另一套方法。

> **面试视角**
> **高频问法**："你怎么看某个 agent 榜单上的排名？"
> **高分要点**：说出三件事——它测什么（任务集来源）、怎么判（判定方式）、以及是否饱和（分数还在不在区分）。只报名字与排名是最低信息量的回答。

## L0 要解决的问题

### 0.1 现象一：榜单分数看不懂它在测什么

第一个现象是分数与能力脱钩。用户看到"某系统在 X 基准上是 74%"，而不知道这 74% 是在什么任务分布、什么判定方式、什么脚手架下取得的。

它的成因是基准的名字比它的构成更常被传播——榜单页面上最醒目的是分数，而任务集的来源、判定的实现、以及脚手架的差异都在附录里。这正是"基准卡"存在的理由（0.2 与 1.8）。

### 0.2 现象二：分数涨了而实际变差

第二个现象是优化了指标而没有优化能力。它的成因有三类：污染（模型见过答案）、饱和（题目太易，涨的那几点在噪声内）、以及奖励黑客（系统学会了让判定通过而不是完成任务）。

三类的表现相同而检测方式不同：污染要靠留出集与时间去污染检测，饱和要看榜单前列的差距是否落在噪声内，奖励黑客要靠审计执行轨迹。审计这件事在 1.7 里有一个具体的例子：某系统的 24.4% 轨迹只是执行了 `git log` 去抄修复方案。

### 0.3 现象三：两个来源的数字不可比

第三个现象是跨来源比较失效。同一模型在两个来源上的分数差十几个百分点，而两个来源都声称用的是同一个基准。

成因是口径：任务子集不同（完整集与清洗后的子集）、指标不同（`pass@1` 与 `pass@3`）、脚手架不同、以及是否使用受控评测人员（vendor 自报与第三方受控评测的差距在 GAIA 上超过十个点）。处置是把"三同"作为可比的前提（同任务集、同脚手架、同指标）。

### 0.4 现象四：判定器本身有错

第四个现象是判定错误。一个审计发现某浏览器基准的严格字符串匹配加一个粗糙的模型评判，产生了约 1.6% 到 5.2% 的绝对误判——而在这个量级上，榜单前列的排序已经不可靠。

更严重的一类问题是判定可以被绕过：一份 2026 年的公开审计（Berkeley RDI）演示了在八个主流基准上取得接近满分而零任务解决的手法，包括在测试配置文件里注入钩子、从本地配置读取标准答案、以及构造一个只对判定器说谎的输出。这份审计的结论不是"当前榜首在作弊"，而是"评测的结构性缺陷可以被自动发现"——而这正是奖励黑客的机制。

### 0.5 这一篇要正面回答的四个问题

第一，一个基准由哪些部分组成（1.1）。第二，主要基准各自出什么题、怎么判、分数在哪（1.3–1.5）。第三，它们共同的缺陷是什么（1.7）。第四，怎么读与怎么用（1.8、1.9）。

四个问题里第三个是本篇最不可替代的部分——前两个可以在榜单网站上查到，而第三个只能从审计与批评文献里学到。

## L1 设计与原理

### 1.1 一个基准的四个组成部分

任务集、判定、执行环境、汇总指标。四者缺一，前面的部分就失去意义。

| 部分 | 它决定什么 | 常见的选择 |
|---|---|---|
| 任务集 | 测什么分布 | 真实 issue、合成生成、众包查询、私有留出 |
| 判定 | 什么算成功 | 可运行检查、字符串匹配、模型评判 |
| 执行环境 | 在什么条件下跑 | 容器、虚拟机、自托管网站、真实网络 |
| 汇总指标 | 怎么报一个数 | 单次成功率、`pass@k`、`pass^k`、成本与步数 |

四者里最容易在传播中丢失的是"执行环境"——而它恰恰是生态效度的决定项。一个在冻结快照上跑的浏览器任务与在生产网站上跑同一件事，成功率可以差三倍以上（1.7 会给出成因）。

### 1.2 任务设置思想：合成与真实的两种路线

两种路线的代表与它们各自的辩护理由。

合成路线（以 RULER 为代表）的理由是可控：合成任务能自由调节长度与复杂度，并且"减少对参数化知识的依赖，从而干扰长上下文能力的使用"。RULER 把它扩展成四类任务（检索、多跳追踪、聚合、问答），因为它们认为"大海捞针"这类测试只反映检索能力。

真实路线（以 BFCL 的演进为代表）的理由是效度：BFCL 的三个阶段是"合成（受控诊断）→ 真实众包（暴露过度拟合）→ agentic（多轮、状态追踪、错误恢复）"，而它的数据显示在众包数据上的准确率一致地低于合成数据——这正是合成集合可能掩盖过拟合的证据。

两种路线的结论来自一项实证研究（HELMET，ICLR 2025）：合成任务（如大海捞针）不能可靠预测下游表现，而真实 RAG 类任务与下游的相关性更好；因此它的建议是混合——用可控的合成任务做诊断（它们的上限已知），用真实任务测泛化。

```ts
interface BenchmarkCard {
  readonly name: string
  readonly version: string
  readonly measures: string                    // 它想测什么
  readonly tasks: { source: string; size: number; sampling: string }   // 任务从哪来、多大、怎么采样
  readonly judging: 'check' | 'string' | 'judge' | 'state'             // 判定方式
  readonly environment: string                 // 容器 / 虚拟机 / 自托管服务 / 真实网络
  readonly metric: string                      // 单次 / pass@k / pass^k / 含成本
  readonly reported: { value: number; at: string; by: string }[]        // 分数的来源与时间
  readonly knownFlaws: string[]                // 已知缺陷（这一项决定它有多可用）
  readonly fit: string                          // 适用场景
}
```

九个字段里最后三个是本篇的重点：分数要带来源与时间、缺陷要写出来、适用场景要写清。一份只有前六个字段的说明是宣传材料，不是基准卡。

### 1.3 代码类：SWE-bench 系列

它的构造方式值得完整拆一遍，因为它是"真实任务 + 可运行判定"这条路线最成功的样本。

任务来源：从 GitHub 上热门 Python 仓库的已合并 PR 里抽取——每个任务由三部分组成：一个 issue 描述（自然语言）、一个基准提交（代码状态）、以及一个测试补丁（判定方式）。

判定方式：可运行检查，而且是两个方向的：`FAIL_TO_PASS`（修复前失败、修复后必须通过的测试）与 `PASS_TO_PASS`（修复前后都必须通过、用于防止回归）。这条设计的精妙处在于它同时约束了"修好了"与"没弄坏"——它是可运行判定里最成熟的一种形态。

子集与演进：完整集（两千余任务）之后有 `Verified`（人工筛出的 500 个，确认 issue 描述清楚且测试可靠）与 `Lite` 等子集。不同子集的实例集与判定不同，因此分数不可直接比较——这一点在公开报道里被反复误解。

分数演进（带来源与时间）：从 2024 年的约 49%（Claude 3.5 Sonnet 时期）到 2025 年的 70% 以上（多个前沿模型），再到 2025 年末出现首个超过 80% 的厂商自报（受控复核约为 74%）。这条曲线看起来是能力的提升，而后续审计给出了另一种解释。

已知缺陷（这是最有价值的部分）：

- **污染**：一项 2026 年的公开审计称，多个前沿模型在仅给出任务 ID 与提示的情况下能复现**精确的官方补丁**（包括变量名与注释）；该审计并称受影响任务中约六成存在测试设计或描述问题。
- **测试缺陷**：另一项独立审计（SWE-bench+）报告约 **32.7% 的解答泄漏**与约 31% 的弱测试——过滤这些问题之后，一个代表性 agent 的分数从 12.47% 降到 3.97%。
- **仓库偏差**：一项跨基准研究发现性能在生态内随仓库衰减，换到外部仓库时**下降最多 47 个百分点**，被解释为训练期暴露模式的证据。
- **饱和**：一项分析称榜单"已无法为前列排序"——前 10 名提交中 285/500 的实例被所有人解出。
- **仓库偏差下的规模化问题**：为抵抗污染而设计的后继基准（Pro，含私有与 copyleft 仓库、1865 个任务）在公开集上**把 70–80% 降到约 23%**；而它自己在八个月内从 23.3% 涨到 80.3%，同样引发了饱和与污染问题。

测量什么：真实仓库里的缺陷修复。它的任务设置思想是"用工程界真实发生过的改动与其测试来定义成功"——这条思想是可复制到自建评测里的（4.6 的三步采样与它同源）。

### 1.4 通用助手与工具类

四个代表与它们各自的结构。

GAIA：三百余个真实助手任务，分三个难度级，需要网页浏览、多模态文件处理、编码与多步推理；人类基线约 92%。它的判定方式是字符串匹配（对最终答案做规范化后比对），而这正是它最大的缺陷来源：验证集的答案公开发布，一项审计因此用"直接读取公开答案"的方式拿到了约 98% 的分数。

τ-bench：工具—agent—用户的交互，领域为零售与航空；一个模型模拟的用户提出请求，agent 通过领域 API 操作，最终比对数据库的终态而不是转录文本。它的两个贡献都值得记住：状态判定（agent 说它做了什么不算，数据库变了才算）与 `pass^k`（1.6 展开）。

BFCL：函数调用基准，判定是两阶段的——AST 子串匹配（可复现、不需要执行后端）与执行结果匹配（对有可执行后端的函数）。它的三段演进（合成 → 真实众包 → agentic）在 1.2 已经讨论；一个细节值得记住：它刻意使用确定性的预标注查询而不是模型模拟用户，理由是后者的幻觉与指令遵循错误会引入偏差。

WebArena 与 OSWorld：自托管的网站（购物、论坛、GitLab、地图）与虚拟机环境，agent 通过真实界面操作。判定是环境状态断言（而非文本比对）——而审计仍发现了字符串匹配式的实现细节（某基准的 `must_include` 是子串包含，某规范化函数会把不同的字符串折叠成同一个）。

### 1.5 上下文类：RULER 与它的后继结论

大海捞针（NIAH） 是最广为人知的长上下文测试：在一段长文本里藏一个"针"，问模型它是什么。RULER 的批评是它只测检索，于是扩展出四类任务（检索、多跳追踪、聚合、问答），并且只用合成数据以控制长度与复杂度。

它的自我限制也值得引用：作者明确说合成任务"绝不能取代更可取的真实任务"，并且语料"远不够全面"。

后续的实证结论是 1.2 提到的那条：大海捞针式的合成任务不能可靠预测下游表现，而与下游相关性更好的是真实的检索增强任务。这条结论对本课程有直接的实践含义：自建评测（4.6 的任务集与 6.2 的基准）应当优先用真实任务，而合成任务只用于"上限已知"的诊断。

### 1.6 指标：`pass@k`、`pass^k` 与状态判定

两个指标的定义与它们的适用场景。

`pass@k` 指 k 次尝试里至少一次成功（`1 - (1-p)^k`），它适合"可以生成多个候选再挑一个"的场景（代码补全、单次问答）。`pass^k` 指 k 次尝试全部成功（`p^k`），它适合"用户连续使用 k 次"的场景（服务、批处理）。

两者的量级差：单次 95% 时 `pass^8` 是 66%，单次 90% 时是 43%，单次 80% 时是 17%——这条"可靠性悬崖"解释了为什么"单次能做成"的系统在长期使用里仍然不可靠。

τ-bench 的报告给出的量级更直观：某前沿模型的零售领域单次成功率约 61%，而 `pass^8` 不足 25%。

关于 `pass^k` 本身的一条限制：它假设多次尝试独立，而实际不独立——同一个模拟器、同一段策略文本、同一个脚手架都会让失败相关。因此 `pass^k = p^k` 会低估一致性问题（或者在高相关时高估）。处置是在报告 `pass^k` 的同时报告任务的分布：永远通过 / 永远失败 / 中间不稳定——中间那一格才是可靠性问题的所在。

状态判定 vs 转录判定：一条系统在转录里叙述了它没有执行的动作，文本判定会给它高分，而状态判定不会。这条区分与 5.4 的"结果回收校验"是同一条原则。

### 1.7 缺陷分类学：七种失效模式与三种系统性偏差

七种结构性失效（来自 2026 年的一项公开审计，它用这七类手法在八个基准上取得接近满分而零任务解决）：

| # | 失效模式 | 具体形态 |
|---|---|---|
| 1 | 被判者与判定器之间没有隔离 | agent 能读到判定配置或影响它 |
| 2 | 答案随测试一起下发 | 验证集答案在公开仓库里 |
| 3 | 对 agent 可控的输入做 `eval()` | 判定器执行 agent 产出的"答案代码" |
| 4 | 模型评判的输入未做净化 | 提示注入可以改变评判结果 |
| 5 | 字符串匹配过弱 | 子串包含即判对；规范化把不同答案折叠 |
| 6 | 判定逻辑实际上没有判定 | 某基准的校验函数从不检查正确性 |
| 7 | 信任 agent 可控代码的输出 | 容器内的测试输出被无条件采信 |

三种系统性偏差：

- **污染**：训练数据里见过答案（1.3 的审计给出了检测方式：给 ID 与提示，看能否复现精确补丁）。
- **饱和**：分数不再区分系统（判据是"前列的差距是否落在噪声内"）。
- **生态效度缺口**：冻结环境与生产环境的差距。一项分析给出的对比是**某浏览器基准 78% 与生产约 22%**，并列出了六种成因：选择器漂移、截图歧义、登录与会话过期、弹窗打断、限流、以及动作不可逆（评测里的动作都可回滚，而生产里不是）。

```ts
interface FlawCheck {
  readonly id: string
  readonly kind: 'structural' | 'contamination' | 'saturation' | 'validity'
  readonly question: string                     // 用一个问题来检测它
  readonly evidence: string                     // 什么样的观察算"命中"
}
```

这份检查表的用法：读任何基准时逐条问一遍（1.8 会把它扩展成八问）。命中两条以上时，这个基准的分数只能当作方向性参考。

### 1.8 怎么读一个基准：八问

八个问题，按重要性排序。

1. **它测什么？** 任务集的来源分布（真实 issue、众包查询、合成生成、私有留出）与规模。
2. **什么算成功？** 判定方式属于哪一类（可运行检查 / 状态 / 字符串 / 模型评判），以及它有没有被绕过记录。
3. **在什么条件下跑？** 容器、虚拟机、自托管服务还是真实网络；脚手架是否固定。
4. **指标是什么？** 单次、`pass@k`、`pass^k`；有没有包含成本与步数。
5. **现在的分数区间是多少？** 带来源与时间；**并且区分受控评测与自报**。
6. **它饱和了吗？** 看前列的差距是否落在噪声内，以及"所有人都会"的题目占比。
7. **已知缺陷是什么？** 套用 1.7 的七加三类。
8. **它适合回答什么问题？** 选型、回归、论文比较、还是生产可靠性评估——**同一个基准对不同问题给出的可信度不同**。

八问的产出就是一份基准卡（1.2 的九字段结构）。

### 1.9 怎么用：三条实践规则

规则一是自建评测要优先用真实任务（1.5 的结论）：从真实使用里采样、有可运行检查、任务量小但稳定。它与公开基准的分工是：公开基准用于对外沟通与横向比较，自建评测用于自己的回归判断。

规则二是同时报三个数：单次成功率、`pass^k`、以及成本。单次给能力，`pass^k` 给可靠性，成本给可行性——只报一个数必然误导某一类读者。

规则三是把判定绑定到世界状态（1.6、1.7 的第 7 条）：判"环境变成了什么样"，不判"系统说自己做了什么"。这条规则的成本很低（多数任务本来就有可检查的终态），而它一次性消掉了一整类失效。

### 1.10 两次追问

工程侧的问题是什么时候该引进一个外部基准。判据是"我需要与外部比较吗"——需要对外沟通时用公开基准，需要判断自己的改动是否退化时用自建评测。两者的混淆会造成两类浪费：用公开基准做日常回归（它太慢、又不匹配自己的分布），或者只用自建评测做对外沟通（它不被认可）。

产品侧的问题是一个分数该对用户意味着什么。多数用户不关心基准名字，而关心两件事：这类任务能不能做成（单次能力）与我会不会反复遇到同一次失败（可靠性）。因此面向用户的表述应当是"在 X 类任务上大约能做对八成，而连续十次全对的概率约三成"——这句话比任何榜单排名都更有信息量，而它也正好是这一篇想建立的判断方式。

## L2 决策表

| # | 决策 | 我们的选择 | 替代方案 | 代价落在谁身上 |
|---|---|---|---|---|
| 1 | 读基准的方式 | 八问加基准卡 | 直接看榜单排名 | 花时间；换来知道分数在什么条件下成立 |

| 3 | 报告的口径 | 单次 + `pass^k` + 成本 | 只报单次 | 数字不好看；换来不误导可靠性读者 |
| 4 | 外部基准与自建评测 | 对外用公开基准、对内用自建 | 只用一个 | 两套维护；换来两边都准 |
| 5 | 自建评测的任务来源 | 真实使用采样为主 | 合成生成 | 采样成本；换来生态效度 |
| 6 | 合成任务的角色 | 只用于诊断（上限已知） | 作为主评测 | 覆盖面窄；换来可控与可解释 |
| 7 | 判定绑定 | 世界状态 | 转录文本 | 要写状态断言；换来消掉一类失效 |
| 8 | 分数的呈现 | 带来源、时间与条件 | 只给数字 | 表述更长；换来可比较 |
| 9 | 饱和的判断 | 看"所有人都解出"的占比 | 看最高分 | 要额外统计；换来不被噪声排名误导 |
| 10 | 污染的处理 | 留出集 + 时间轮换 | 定期换题 | 题目维护成本；换来分数反映能力 |
| 11 | 跨来源比较 | 先核对"三同" | 直接比 | 常发现不可比；换来不产生错误结论 |
| 12 | 面向用户的表述 | 单次能力 + 连续成功的概率 | 榜单排名 | 不吸睛；换来用户能理解预期 |

其中两条值得展开，因为它们的选择在实践中经常被做成另一个。

### 关于第 2 与第 7 条的完整论证（为什么判定方式决定一切）

替代方案是"用最容易实现的方式判定"（多数情况是字符串匹配或模型评判）。它的吸引力是成本，而它的代价在 1.7 的清单里被完整列出：字符串匹配过弱会让"部分正确"被判成全对（"45 + 8 分钟"与"63 分钟"的例子），模型评判的输入未净化会被提示注入改变结论，而两者都让系统有机会优化判定而不是任务。

世界状态判定之所以是首选，不是因为它的实现最简，而是因为它一次性消掉两类失效：它不可能被转录里的叙述骗过（第 7 条失效），而且它通常需要与任务语义强绑定（判定无法脱离任务单独优化）。它的成本主要在任务的构造——每个任务都要定义一个可检查的终态，而这与 4.6 的"有成功判据的任务"是同一个要求。

第 2 条的优先序（可运行检查 > 状态 > 字符串 > 模型评判）里，可运行检查排在最前是因为它的误判率最低（测试通过与否是二值的），而模型评判排在最后是因为它的偏差可能与被比较的方法相关（6.1 的 1.3 已经讨论过：模型评判必须用小样本人工标注校准）。

### 关于第 9 与第 11 条的完整论证（为什么饱和与可比性比分数更重要）

替代方案是"看最高分与排名"。它在基准刚出现时是合理的（分数在区分系统），而在饱和之后会给出错误的信息。

第一，饱和之后的分差是噪声。当"前 10 名提交中 285/500 的实例被所有人解出"时，剩下的题目太少，不足以支撑排序——这时榜单的第一名与第五名之间没有统计意义。

第二，不可比的分差会被当成能力差。同一模型在两种脚手架下的差距（7 个点以上）大于多数模型之间的差距；而"受控评测与自报"的差距更大（GAIA 上超过十个点）。不核对"三同"就跨来源比较，等于把脚手架差异与报告策略差异算成了能力差异。

两条合起来给出的判据是：在问"谁更强"之前，先问"这个基准还能不能区分"与"这两个数是不是在同一个条件下取得的"。这两个问题都不需要新数据，只需要读附录。

## L3 实现（施工图）

### 3.1 自建一个评测的七步

本篇的"施工图"不是写代码，而是建一个评测——它由七步构成，而每一步都对应本篇的一节。

```
1 选目标        —— 这份评测要回答哪个问题（能力？可靠性？成本？）
2 采任务        —— 从真实使用里采样，带可运行的检查（4.6 的三步）
3 定判定        —— 世界状态优先（1.1、1.6）
4 定指标        —— 单次 + pass^k + 成本（1.6、1.9 的规则二）
5 设隔离        —— 被判者读不到判定配置与答案（1.7 的第 1、2 条）
6 定划分与轮换  —— 开发集与测试集分开；题目按时间轮换（1.7 的污染）
7 写基准卡      —— 九字段，含已知缺陷与适用场景（1.2、1.8）
```

七步里第 5 与第 6 步最容易被跳过，而它们恰好对应 1.7 里那两类最严重的结构性缺陷。"被判者读不到答案"这条要求的实现成本很低（判定在隔离环境里跑），而它的收益是让"分数"这个数在结构上可信。

### 3.2 判定的实现要点

```ts
type Judge =
  | { kind: 'check'; run: (state: World) => boolean }
  | { kind: 'state'; assert: (before: World, after: World) => boolean }
  | { kind: 'string'; normalize: (s: string) => string; expect: string }
  | { kind: 'judge'; model: string; rubric: string; calibration: { samples: number; agreement: number } }

export function judgeIsAcceptable(j: Judge): { ok: boolean; why?: string } {
  if (j.kind === 'judge' && (!j.calibration || j.calibration.agreement < 0.7)) {
    return { ok: false, why: '模型评判必须先与人工标注校准（一致度不低于 0.7）' }
  }
  if (j.kind === 'string' && j.normalize('45 + 8').length === 0) {
    return { ok: false, why: '规范化过强会把不同答案折叠成同一个' }
  }
  return { ok: true }
}
```

这段实现的取用标准来自 6.1 的测量手段讨论（模型评判必须校准）与 1.7 的第 5 条（字符串匹配过弱）。一致度 0.7 这个门槛与结论表里"Cohen's κ > 0.7"的公开建议同源。

### 3.3 指标的计算与报告

```ts
export interface EvalResult {
  readonly singleRun: number                       // 单次成功率
  readonly passHatK: Record<number, number>        // pass^k（k 为键）
  readonly partition: { always: number; never: number; unstable: number }  // 任务分布
  readonly cost: { tokens: number; steps: number; wallMs: number }
  readonly judgeErrors?: number                    // 判定发现的错误数（审计用）
}

export function reportPartition(perTask: readonly number[]): EvalResult['partition'] {
  return {
    always: perTask.filter((p) => p === 1).length,
    never: perTask.filter((p) => p === 0).length,
    unstable: perTask.filter((p) => p > 0 && p < 1).length,
  }
}
```

`partition` 是 1.6 那条"报告任务分布"要求的实现：中间那一格（有时成功有时失败）才是可靠性问题的所在——而它的数量随评估次数的增加才显现，因此这一项要求每个任务跑多次。

### 3.4 验收判据

| # | 判据 | 怎么检查 |
|---|---|---|
| 1 | 判定属于四类之一且符合优先序 | 核对 `Judge.kind` 与它的实现 |
| 2 | 模型评判有校准记录且一致度 ≥ 0.7 | 核对 `calibration` |
| 3 | 判定绑定世界状态而不是转录 | 检查断言里是否读环境而不是输出文本 |
| 4 | 被判者读不到判定配置与答案 | 隔离检查（判定在独立环境执行） |
| 5 | 任务集来自真实采样且带可运行检查 | 核对任务的 `check` 字段 |
| 6 | 开发集与测试集不重叠 | 核对任务 id 集合 |
| 7 | 每个任务至少跑三次 | 核对运行记录 |
| 8 | 报告含单次、`pass^k` 与成本三项 | 核对 `EvalResult` |
| 9 | 报告含任务分布（永远通过/失败/不稳定） | 核对 `partition` |
| 10 | 基准卡九字段齐全 | 核对 `BenchmarkCard` |
| 11 | 基准卡含已知缺陷与适用场景 | 非空检查 |
| 12 | 五个真实 benchmark 各一份基准卡 | 人工：对照 1.3–1.5 的六个 |

第 4、6、10 条是这一篇的特色判据：它们分别对应 1.7 里最严重的两类结构性缺陷与"读基准"的产出形态。

### 3.5 实现顺序

先做判定与隔离（判据 1、2、3、4），再做任务集与划分（判据 5、6、7），然后做指标与报告（判据 8、9），最后写基准卡（判据 10、11、12）。

## L4 运行与验证

### 4.1 三层验证

第一层是契约测试：按 3.4 的十二条判据逐条检查（第 12 条需要人工产出五份基准卡）。

第二层是判定审计：对自建评测做一次对抗检查——能不能在不完成任务的情况下拿到分数。这层检查的方式是有限的几种（改判定配置、直接写答案文件、构造只对判定器说谎的输出），而它的价值极高：1.7 的七种失效模式里有一半是它一次性覆盖的。

第三层是生态效度抽样：把自建评测的成功率与真实使用中的成功率对比。两者的差距是这一层要测的东西——如果自建评测 80% 而真实使用 40%，那么问题可能在评测的任务分布（它挑的是容易的），也可能在真实环境（有评测里没有的干扰）。

```powershell
node research/eval/validate.mjs            # 十二条判据
node research/eval/judge-audit.mjs         # 判定审计（对抗检查）
node research/eval/validity-sample.mjs     # 生态效度抽样
node research/eval/card.mjs --bench=<name>  # 生成一份基准卡
```

### 4.2 判据

做完这一篇的标志有三条：十二条判据全部通过；判定审计里没有任何一种手法能无任务拿分；以及五份基准卡写完（对 1.3–1.5 里的六个基准任选五个）。

## L5 语法速查

### 5.1 术语表

| 术语 | 在本篇里的准确含义 | 容易误解为 |
|---|---|---|
| 基准 | 任务集 + 判定 + 环境 + 指标 | "数据集"（数据集缺判定与指标） |
| 判定 | 判断一次尝试是否成功 | "评分"（评分是它的实现之一） |
| 脚手架 | 把模型包装成能完成任务的那一层 | "框架"（框架是实现，脚手架是它的配置） |
| `pass@k` / `pass^k` | 至少一次成功 / 全部成功 | "两者可以互换"（方向相反） |
| 污染 | 评测数据进了训练数据 | "过拟合"（那是模型对训练集） |
| 饱和 | 分数失去区分度 | "已解决" |
| 生态效度 | 评测表现与真实表现的一致性 | "真实性"（它是两者的关系） |
| 奖励黑客 | 利用评测缺陷拿分 | "作弊"（它可以是无意的） |

### 5.2 命令速查

| 目的 | 命令 | 说明 |
|---|---|---|
| 校验自建评测 | `node research/eval/validate.mjs` | 十二条判据 |
| 判定审计 | `node research/eval/judge-audit.mjs` | 对抗检查 |
| 生态效度抽样 | `node research/eval/validity-sample.mjs` | 评测 vs 真实 |
| 生成基准卡 | `node research/eval/card.mjs --bench=<name>` | 九字段 |
| 任务分布 | `node research/eval/partition.mjs --record=<id>` | 永远通过/失败/不稳定 |

### 5.3 三条容易踩的规则

第一条，判定优先绑世界状态。它一次性消掉两类结构性失效。

第二条，报告要同时给单次、`pass^k` 与成本。只给一个数会误导某一类读者。

第三条，跨来源比较前先核对"三同"。任务集、脚手架、指标有一处不同就不可比。

## L7 挑战题（不给答案）

## L9 仍未解决（这一篇自己的缺陷）

| 缺陷 | 后果 | 修法 | 当初为什么这么写 |
|---|---|---|---|
| 引用的分数会迅速过时 | 读者可能把它当成当前值 | 全部标注来源与时间，并强调结构比数字稳定 | 用户要求"讲现在完成率" |
| 部分审计数据来自搜索到的二手报道 | 个别数字可能有偏差 | 回原始文献核对 | 交叉验证的成本高，而结构结论不依赖单一数字 |
| 缺少多模态与安全基准的细节 | 覆盖面不全 | 另行补一节 | 它们各有独立方法论 |
| 未覆盖中文基准 | 中文场景的参考缺失 | 补 C-Eval、SuperCLUE 一类的对照 | 它们主要评模型而非 harness |
| `pass^k` 的相关性修正只有方向 | 无法直接算出真实值 | 见挑战题第一题 | 需要数据与建模 |
| 生态效度的差距只有定性成因 | 无法预测某一个系统的缺口 | 见挑战题第四题 | 需要生产数据 |

第一条值得单独标记：它意味着本篇必须被当作一份"方法与结构"的文献，而不是一份"现状"的文献。这不是回避，而是评测领域的一条固有性质——任何静态的分数清单都在它写下的一刻开始过期，而"怎么读一个基准"这条能力不会。课程里其他篇的数字（恢复耗时、缓存命中、pass 率）同样是量级而非常数，本篇只是把这一点说得最明白。

### 五种提问模板

反例逼问：如果判定用字符串匹配且规范化过强，哪一类错误会变多。

边界追问：一个基准要多少任务才能在饱和前有效。

代价追问：把判定改成世界状态，代价落在谁身上。

替代对比：为什么合成任务只能做诊断而不能做主评测。

验证追问：怎么证明"这个分数不是污染带来的"。

### 本篇引出的十二个问题

读懂层。 第一，基准的四部分是什么？第二，判定方式的优先序与理由是什么？第三，`pass@k` 与 `pass^k` 的差别是什么？

重建层。 第四，为什么世界状态判定更可靠？第五，为什么模型评判必须校准？第六，为什么合成任务只能做诊断？

设计层。 第七，七种结构性失效是什么？第八，三种系统性偏差是什么？第九，八问是哪八问？

评审层。 第十，拿到一个基准，你会先检查哪一处？第十一，怎么判断一个分数不可比？第十二，如果有人说"我们在这个基准上超过了某某"，你怎么回应？

### 问题升级练习

模糊问题：「我的 agent 到底行不行？」

升级后的精确问题：

> "行不行"至少包含三件互相制约的事：**测什么**（任务分布的来源与代表性）、怎么判（判定方式的可靠性与它被绕过的可能）、以及报什么（单次能力、连续可靠性、成本）。
> 第一件与第三件互相制约——任务集越贴近自己的真实分布，得到的结果越有用，而它就越不能与外部比较。
> 我能不能为这三件事各找出一条**可检查的判据**？
> 特别是：有没有哪一条判据，是**能在不完成任务的情况下被验证为无效的**（也就是判定审计）？

提升点说明：原问题无法回答，因为"行不行"没有参照。升级后的版本把它拆成三件具体的事，指出"贴近自己"与"可比"的张力，并追加以一个更强的问题：哪一条判据能通过对抗检查来验证——因为一个能被无任务通过的判定，会让前面所有结论归零。

回看第 0.5 节的三个连锁影响。

| 预判 | 本篇分析之后的结论 | 状态 |
|---|---|---|

一处需要修正的预判：0.5.2 把"基准卡"标为对 6.1 的强依赖。读完之后要补一层方向：基准卡与本课程的自建评测是同一份东西的两个尺度——基准卡描述别人的评测（九字段），而 4.6 的任务集是自己的评测（它也需要同样的九字段，只是规模小）。处置方式是把 4.6 的任务集也写成基准卡（哪怕只有三行），这样"评测"这件事在本课程里就只有一种描述方式。

通向下一篇的桥。 本篇给出了"怎么读与怎么建评测"，而它留下了一个没有答案的问题：评测里出现的意外该怎么处理。分数与预期不符、某个任务一直失败、判定给出互相矛盾的结论——这些现象本身就是下一篇的原料。

下一篇 `6.4 从工程观察变成研究问题` 处理这件事。它与本篇的连接点有两处：一是评测是观察的主要来源（有记录、可复算的实验才能产生意外），二是本篇的缺陷分类学正是"为什么这个分数不可信"的一份诊断表——而诊断与观察的转化是同一件事的两个方向。

## 本篇新词

因素（factor） 指实验中主动改变的自变量。它与"参数"的差别是它是被设计进实验的（有取值、有对照），而参数只是可以改的东西。一个因素必须有至少两个取值，否则它不是一个实验变量。

响应（response） 指测量出来的因变量。它的选择要求与 6.1 的 1.2 相同（可观测、与因素有机制联系），而本篇补充它的尺度问题：同一个概念可以用不同尺度测量（成功率、成本、延迟），而尺度的选择会影响统计方法（比例、计数、时长各有合适的检验）。

对照（control） 指用于比较的基准条件。三种形态在 6.1 的 1.2 已经列出（消融、对比、参数扫描），而在实验设计里它们的角色不同：消融回答"这个组件有没有用"，对比回答"哪个方法更好"，扫描回答"参数如何取值"。

噪声下限（noise floor） 指同一配置重复运行的结果波动。它是实验的分辨率——小于它的差异不可测，而它的大小由任务集规模、任务稳定性与运行次数共同决定（4.6 的稳定性筛选正是为了压低它）。

可检测效应（detectable effect） 指在给定样本量与噪声下能被可靠发现的差异大小。它与样本量的关系是本篇的核心量化（0.1）。

重复（replication） 指同一条件下的多次运行。它的两个用途是估计噪声（同一配置跑多次）与提高功效（每个条件跑多次再比较）。两者不能混为一谈：前者用于定分辨率，后者用于增加样本。

多重比较（multiple comparisons） 指一次实验里比较了多个假设的情形。它的风险是假阳性随比较次数上升——比较二十个方法时，即使全部无效，出现一个"显著"的结果几乎是必然的。

效应量（effect size） 指差异的实际大小，与"是否显著"是两件事。显著但效应量很小意味着差异真实但不值得——而这类结论在样本充足时很常见。

可复现（reproducibility） 指他人能重跑出同方向的结果。它需要的记录有四个：任务集与版本、配置与代码版本、随机种子、以及环境（依赖版本、模型版本）。

```
 一句话串起来：怎么比较 → 怎么归因 → 怎么定分辨率 → 怎么不骗自己
```

这张图的关键线索在第三块：实验的很多错误不是方法用错，而是分辨率不足时下了结论。一个只有二十个任务、成功率差异五个百分点的实验，其差异完全可能来自噪声——而它会被当作发现写进报告。

### 0.1 一个具体的判断：样本量与可检测效应

设任务的成功率是二值结果（成功或失败），而两个方法在同一个任务集上比较。下表的量级来自对二项比例的粗略估算（假设基线成功率约 0.7、每个任务独立）：

| 任务数 | 能可靠发现的最小差异（约） |
|---|---|
| 20 | 30 个百分点 |
| 50 | 18 个百分点 |
| 100 | 12 个百分点 |
| 200 | 9 个百分点 |
| 500 | 5 个百分点 |

这张表给出一条直接的判断：小任务集只能发现大差异。用二十个任务去区分两个相差十个百分点的方法是不可能的——不是方法不对，是分辨率不够。

它同时给出实验设计的起点：先写下"我想发现多大的差异"，再反推样本量——这与 3.6 的"先承诺恢复时间再定检查点间隔"、4.5 的"先承诺改善再定门控阈值"是同一种做法。先定判据再定参数，而不是先跑再看。

### 0.2 本篇建立的三项判据

第一项用于判断一个比较是否可信：问"差异有没有超过噪声下限"。噪声下限由同一配置的多次运行估计，而小于它的差异不构成结论。

第二项用于判断一次消融是否有效：问"被去掉的组件是否真的被去掉了，且其他条件不变"。消融的常见失败是"去掉 A 之后 B 的行为也变了"（因为两者耦合），而那时结果无法归因到 A。

第三项用于判断结论是否可复现：问"四个记录（任务集、配置、种子、环境）是否齐全"。缺任何一个，他人都无法重跑；而"重跑出同方向的结果"是实验结论能被采纳的最低要求。

### 0.3 十分钟练习：噪声下限与可检测差异

下面这段代码用同一配置的多次运行估计噪声，并判断一个观察到的差异是否超过它。

```js
const sameConfigRuns = [0.68, 0.72, 0.70, 0.69, 0.71, 0.70]   // 同一配置跑六次（可分批）
const methodA = [0.70, 0.71, 0.69, 0.70]
const methodB = [0.74, 0.75, 0.73, 0.74]

const mean = (xs) => xs.reduce((a, b) => a + b, 0) / xs.length
const sd = (xs) => Math.sqrt(xs.reduce((a, b) => a + (b - mean(xs)) ** 2, 0) / (xs.length - 1))

const floor = 2 * sd(sameConfigRuns)
const diff = mean(methodB) - mean(methodA)
const pooled = Math.sqrt((sd(methodA)  2 + sd(methodB)  2) / 2)

console.log(`噪声下限（两倍标准差）：${floor.toFixed(3)}`)
console.log(`两个方法的差异：${diff.toFixed(3)}`)
console.log(`判断：${diff > floor ? '超过噪声，值得进一步验证' : '落在噪声内，不构成结论'}`)
console.log(`效应量（以合并标准差为单位）：${(diff / pooled).toFixed(2)}`)
```

四处输出对应四个概念：噪声下限（分辨率）、差异（点估计）、判断（是否超过）、以及效应量（折算成标准差的倍数，便于跨实验比较）。只有第一条与第四条同时可用时，结论才有意义——超过噪声说明差异可能真实，而效应量说明它是否值得关心。

> **面试视角**
> **高频问法**："你怎么知道一个改动真的有效？"
> **高分要点**：说出三件事——噪声下限（同配置多次运行）、样本量决定可检测效应、以及效应量与显著性分开报告。只说"跑了几次都更好"没有回答"好多少才算真的好"。

### 0.5.3 三个连锁影响

第一，统计判据会让很多"看起来有效"的改动变成"未验证"。 这条连锁是这一篇最直接的后果——当噪声下限被算出来之后，之前基于单次运行或小样本的结论会大面积失效。它的价值在于避免基于噪声做决策（4.5 已经指出这会带来震荡），而代价是需要更大的实验预算。

第二，成本度量会让实验的设计空间变大。 一旦成本进入报告（3.6 提供度量），比较就从"谁的成功率高"变成"在什么成本下谁更好"（6.1 的问题六）。这条变化会让"更贵而更好"的方法有位置，而不是被判为劣于便宜的方法。

第三，实验的结论会反向影响系统设计。 一个"某组件在当前规模下没有可测收益"的结论可能意味着该组件应当被移除或延后——这条影响要求实验结论进入 4.5 的演化流程，而不是停留在一份报告里。没有这条接入时，实验与系统会各自独立地演进。

### 0.5.4 它与本书其余部分的关系

本篇的统计方法限于比较性实验（A/B、消融、参数扫描），它不涉及机制研究（为什么某个现象会发生）。后者需要不同的方法（可解释性、受控的合成任务），而它不在本课程范围内。这条边界意味着本篇能让读者得到一个"可信的比较结论"，而不能让读者回答"为什么"——而 6.4 会给出从观察到机制问题的路径。

## L0 要解决的问题

### 0.1 现象一：跑了两个方法，差异落在噪声里而结论已经写了

第一个现象是小样本下的过度解读。它的形态是一份报告写着"方法 B 比方法 A 高 4 个百分点"，而两者的多次运行波动恰好是 5 个百分点。

它的修法是 0.2 的第一项判据（超过噪声下限）与 1.4 的样本量反推。这两条的实施次序很重要：先算噪声下限（它决定分辨率），再据此决定要不要扩大样本，最后才比较。

### 0.2 现象二：消融之后，其他东西也变了

第二个现象是消融的耦合。去掉组件 A 之后，系统实际上也改变了 B 的行为（因为它们共享一个状态或一个配置），于是结果的差异无法归因到 A。

修法有两条：让消融只影响一处（把 A 做成可独立开关的），以及验证消融的完整性（去掉 A 之后核对 B 的参数没有变）。第二条是本篇强调的核对步骤——它便宜（一次配置对比），而没有它时整个消融的价值归零。

### 0.3 现象三：比较了十个配置，其中一个是"显著"的

第三个现象是多重比较的假阳性。比较十个配置时，即使它们完全等效，出现一个 p 值很小的结果的概率相当高——而它会被当作发现。

修法是 1.5 的校正（多重比较的 p 值调整或降低单次阈值），以及事前登记（先写下要比较哪些，再跑）——事后挑出最好的一个进行比较是最常见的 p-hacking 形式。

### 0.4 现象四：结果无法被他人重跑

第四个现象是可复现性缺失。他人拿到代码与任务集后跑不出同方向的结果，因为种子不同、依赖版本不同、或者模型版本已经更新（而模型更新会让所有基于该模型的结论失去可比性）。

修法是 1.6 的四项记录。其中"模型版本"是最容易被忽略的一项——而它恰恰是 agent 实验里变化最快的一项。

### 0.5 这一篇要正面回答的四个问题

第一，怎么构造与使用基准（1.1、1.2）。第二，怎么做有效的消融（1.3）。第三，怎么定样本量与分辨率（1.4）。第四，怎么避免自欺（1.5、1.6）。

四个问题里第三是量化核心，第四是可信度核心。

## L1 设计与原理

### 1.1 基准的构造与它的两个性质

基准在 4.6 已经出现（真实任务集），而实验语境下它需要两个额外的性质。

性质一是区分度：基准要能区分被比较的方法。一个所有方法都接近满分的基准（4.6 的 L11 修正提到过）对回归门控够用而对实验无用——因此实验用的基准应当选困难任务，而门控用的基准选常见任务。两者是不同的集合。

性质二是可重复性：同一方法在同一基准上重复运行的结果应当稳定（4.6 的 1.3 的稳定性筛选）。它的量化表现是噪声下限，而基准的构造方式直接影响它（外部依赖越少、判定越确定，噪声越低）。

```ts
interface Bench {
  readonly name: string
  readonly version: string                                   // 版本化（任务集会变）
  readonly tasks: readonly BenchTask[]
  readonly determinism: {                                    // 可重复性的三个来源
    readonly pinnedModel: string                             // 模型版本固定（0.4 的提醒）
    readonly seeds: readonly number[]
    readonly externalDeps: 'none' | 'pinned' | 'live'        // live 会带来不可控波动
  }
  readonly split: { readonly dev: readonly string[]; readonly test: readonly string[] }  // 划分（1.5）
}
```

`split` 字段是这一篇对 4.6 的补充：开发集用于调参，测试集用于报告。没有划分时，反复在一个集合上调整会过拟合该集合——而这类过拟合的表现是"报告的数字比实际能力高"，且无法被外部发现。

### 1.2 响应的尺度与它的统计后果

三类响应尺度与它们合适的统计方法。

| 响应 | 尺度 | 合适的做法 |
|---|---|---|
| 成功率 | 比例（0 到 1） | 比例的重采样区间；注意它不是连续量 |
| 成本 / token | 计数或连续 | 中位数与分位数（长尾严重）；均值易被极值带动 |
| 延迟 | 时长（长尾） | 分位数（P50/P95/P99）；均值无意义（3.6 的 1.6） |

这张表的关键在于它否定了"一律取均值"的做法：成功率取均值尚可（它就是一种比例），而成本与延迟取均值会被长尾扭曲——一个任务花了十倍成本，会让均值明显上移而中位数不动。

正确的报告形态是分位数加极值（P50、P95、最大值），而它在成本与延迟上尤其重要。这条与 3.6 的"用分布而不是平均值"是同一条要求在实验报告里的具体化。

### 1.3 消融的设计与它的前提

消融回答"这个组件有没有用"，而它的三步。

第一步是确定被去掉的是什么。"去掉压缩"这个说法不精确（去掉之后上下文会不会溢出？），而精确的消融是"把该组件替换成一个中性的替代"——例如把压缩替换成"按同样比例截断末尾"，这样两者在行为上都"减少上下文"，差别只在压缩策略本身。

第二步是验证消融的完整性（0.2 的分析）：去掉 A 之后，核对其他因素没有被连带改变。

第三步是比较并给出判据：差异超过噪声下限才算有效，而效应量说明它值不值得保留。

```ts
export interface Ablation {
  readonly name: string
  readonly component: string
  readonly neutral: string                                   // 中性替代（而不是"删掉"）
  readonly integrity: readonly string[]                       // 需要核对未变的因素
  readonly response: { name: string; scale: 'proportion' | 'count' | 'duration' }
}
```

`neutral` 与 `integrity` 两个字段是消融质量的核心：前者避免"删掉之后系统跑不起来"这类无效消融，后者避免归因错误。

### 1.4 样本量与分辨率

反推样本量的四步。

第一步是写下要发现的差异（例如"成功率提高十个百分点"）。第二步是估计噪声下限（同一配置跑若干次）。第三步是查表或计算所需的样本量（0.1 的表给出量级）。第四步是检查预算——如果所需样本量超出预算，那么正确的动作是改变实验设计（缩小范围、提高任务集质量以降低噪声），而不是"跑少一点再说"。

一个实践要点：降低噪声比增加样本更划算。噪声下限来自任务间的异质性（不同任务难度差异大）与单任务的随机性；提高任务集的同质性（按难度分层、剔除不稳定任务）能把噪声压低，从而让更小的样本量够用。

### 1.5 多重比较与事前登记

两种处置与它们的选择。

事前登记是最有效的：在跑实验之前写下要比什么、判据是什么。它的作用是把"探索"与"确认"分开——探索阶段可以自由地看很多组合，而确认阶段只验证登记过的假设（用另一份数据或另一次运行）。

多重比较校正用于无法事前登记时：把单次比较的阈值收紧（按比较次数调整），或者使用控制错误率的方法。它的代价是功效下降（更难发现真实差异），而这正是它的目的。

```ts
export function adjust(comparisons: readonly Comparison[], family: 'holm' | 'bonferroni'): Comparison[] {
  const k = comparisons.length
  const sorted = [...comparisons].sort((a, b) => a.p - b.p)
  let previous = 0
  return sorted.map((c, i) => {
    const threshold = family === 'bonferroni' ? 0.05 / k : 0.05 / (k - i)     // Holm 比 Bonferroni 宽松
    const adjusted = Math.max(previous, threshold)
    previous = adjusted
    return { ...c, threshold: adjusted, significant: c.p < threshold }
  })
}
```

两种校正里 Holm 更常用（它在控制错误率的同时比 Bonferroni 更少损失功效），而两者的选择不影响根本结论：比较次数越多，单次判据越严。

### 1.6 可复现的四项记录

四项记录与它们各自的失效方式。

任务集与版本：任务集的改动会让所有历史结果不可比（4.6 的 L2 第 6 条）。处置是版本化并可导出。

配置与代码版本：包括所有显式参数与被启用的组件。处置与 5.1 的"消灭隐式默认"一致——隐式默认会让重跑得到不同的系统。

随机种子：所有影响结果的随机源（采样、任务顺序、并发调度）。处置是记录并在报告中固定。

环境：依赖版本、模型版本、外部服务版本。模型版本是最关键的一项（0.4 的分析）——它变化时，结论的有效范围必须被重新声明。

```ts
export interface RunRecord {
  readonly bench: { name: string; version: string; checksum: string }
  readonly code: { commit: string; config: Record<string, unknown>; profile: string }
  readonly seeds: readonly number[]
  readonly env: { deps: Record<string, string>; model: string; external: Record<string, string> }
  readonly startedAt: number
  readonly results: readonly TaskResult[]
}
```

`checksum` 是任务集版本之外的第二层保护（防止同名不同内容），而 `external` 记录外部服务的版本——在 agent 实验里，外部工具的行为变化同样会让结果不可比。

### 1.7 实验成本的核算

一次实验的成本有三个乘数：任务数 × 重复次数 × 每任务成本。前两者由 1.4 的样本量决定，而每任务成本由系统本身决定（模型的 token 消耗与工具调用）。

这条乘法关系给出一个实践判断：先压低每任务成本，再考虑扩大规模。一个每任务消耗十万 token 的系统，跑一百个任务三次需要三千万 token——而它的噪声下限可能并不比一个每任务一万 token 的系统更低（噪声主要来自任务异质性与随机性，与成本无关）。因此"把每任务成本降下来"往往比"多跑几次"更能让实验可行。

### 关于第 1 与第 2 条的完整论证（为什么实验基准与门控基准要分开、为什么要划分）

替代方案是共用一套基准（既用于门控又用于实验）。它的优点是维护成本低，而它带来两种失效。

第一，门控要的是稳定性，实验要的是区分度（1.1 的性质一）。门控基准应当由常见任务构成（它们稳定），而常见任务在实验里往往所有方法都能通过——用门控基准做实验会得到"没有差异"的结论，而那可能是任务太易而不是方法等效。

第二，共用一套会让调参污染报告。如果一个集合既用于调参又用于报告，那么报告的数字包含了针对该集合的优化（1.1 的 `split`）。这类过拟合的特点是它无法被外部发现——因为外部看到的只是数字。

分开的代价是数据利用率下降（同一批任务只能用一次），而这个代价可以用"划分 + 轮换"缓解（在多个回合里交换开发集与测试集的角色）。

### 关于第 6 与第 9 条的完整论证（为什么先定差异再反推样本、为什么要校正）

替代方案是先跑一个小规模实验，看结果再决定要不要扩大。它在探索阶段是合理的（而探索阶段本来就应该自由），而它在确认阶段会产生两个问题。

第一，"看到差异才扩大"引入了选择偏差。如果第一次跑的差异恰好大（因为噪声），扩大之后差异会缩回——而这时报告往往会用第一次的数字（因为它更好看），或者把"两次都跑过"说成"验证过"。这条偏差的机制与多重比较相同（在同一批数据上做了多次判断）。

第二，它掩盖了分辨率不足这个根本问题。差异小可能是方法等效，也可能是样本不够——而先跑再看的做法不会区分这两者（因为两种情况下都会"看到一个差异"或"看不到差异"）。

正确的次序是：先写判据（要发现多大差异、判据是什么），再算样本量，最后跑一次。探索阶段可以与确认阶段分开（用不同的数据），而两者的界限必须事前划定。

### 3.2 执行与记录

```ts
export async function run(bench: Bench, config: RunConfig, ctx: Context): Promise<RunRecord> {
  const record: RunRecord = {
    bench: { name: bench.name, version: bench.version, checksum: checksum(bench.tasks) },
    code: { commit: ctx.git.commit, config: config.values, profile: config.profile },   // 含隐式默认的显式化
    seeds: config.seeds,
    env: { deps: ctx.deps.versions(), model: ctx.model.version, external: ctx.external.versions() },
    startedAt: ctx.now,
    results: [],
  }
  for (const seed of config.seeds) {
    for (const task of bench.tasks) {
      const result = await runTask(task, { ...config, seed }, ctx)
      record.results.push(result)                                       // 每个任务都留原始结果
    }
  }
  return record
}
```

两处要点：每个任务都留原始结果（而不是只留汇总）——它让后续可以重算分位数、子集分析与噪声下限（3.6 的"记录原始值"在这里的又一次应用）；以及 `config.values` 来自 5.1 的有效配置（含显式化的默认），因此记录是完整的。

### 3.3 统计段

```ts
export function noiseFloor(runs: readonly RunRecord[], metric: 'success' | 'cost'): number {
  const values = runs.map((r) => aggregate(r, metric))
  return 2 * sd(values)                                                  // 两倍标准差（4.5 的判据）
}

export function bootstrapCI(samples: readonly number[], level = 0.95, iters = 10000): { lo: number; hi: number } {
  const means: number[] = []
  for (let i = 0; i < iters; i++) means.push(mean(resample(samples)))
  means.sort((a, b) => a - b)
  return { lo: means[Math.floor((1 - level) / 2 * iters)], hi: means[Math.floor((1 + level) / 2 * iters)] }
}

export function compare(a: TaskResult[], b: TaskResult[], opts: { family?: 'holm' }): Comparison {
  const valuesA = a.map((r) => r.metric), valuesB = b.map((r) => r.metric)
  const ciA = bootstrapCI(valuesA), ciB = bootstrapCI(valuesB)
  const overlap = ciA.hi >= ciB.lo && ciB.hi >= ciA.lo                          // 区间是否重叠
  return { delta: mean(valuesB) - mean(valuesA), ciA, ciB, significant: !overlap, effectSize: (mean(valuesB) - mean(valuesA)) / pooledSd(a, b) }
}
```

三处要点：噪声下限用同一配置的多次运行（而不是用两个方法的方差——那会把真实差异算进噪声）、重采样区间不假设正态分布（比例与长尾成本都不适合正态假设）、以及效应量与显著性同时给出。

### 3.5 报告的结构与它的必填项

一份可被他人使用的报告有六个必填项：问题（三要素）、基准（名称、版本、划分与校验和）、运行记录（四项可复现记录）、结果（分位数、极值、效应量与区间）、结论（含未检出的情形）、以及局限（本次实验没有覆盖的部分）。

第五项里有一处容易被省略的内容：未检出差异也是一条结论。它说明该组件在当前规模与当前基准上没有可测收益——这条信息的价值在于它阻止了后续的人重复投入，而它的写法必须带上分辨率（"在 N 个任务、噪声下限 X 的条件下未检出差异"），否则读者无法判断它是"确实无效"还是"测不出来"。

报告的判据只有一条：他人能否只靠这份报告重跑。它把前面五项串成一个检查——问题清楚才能重跑同一件事，基准与记录齐备才能得到同一条件，结果形态明确才能对比。

## L4 运行与验证

### 4.1 三层验证

第一层是契约测试：按 3.4 的十三条判据逐条检查。

## L7 挑战题（不给答案）

第一题：自适应样本量。 设计一个"跑一批看一次、必要时继续"的方案，并说明它如何避免选择偏差。

第二题：成本约束下的实验设计。 给定固定的总预算（token 数），设计如何分配它到任务数与重复次数之间。

第三题：跨版本比较。 模型版本升级后，如何比较新旧版本的结果（在新旧各自的最优配置下）。

第四题：主观质量的统计。 用人工标注比较两个方法时，怎么处理标注者之间的不一致。

第五题：最小的可信实验。 设计一个只需要一天算力的实验，回答 6.1 的问题四（长程成功判定）。

第六题：论证"不做统计"的一个合理场景。 构造一个场景，说明某类实验无需统计判据（提示：差异巨大或运行成本极高），并给出判据。

## L9 仍未解决（这一篇自己的缺陷）

| 缺陷 | 后果 | 修法 | 当初为什么这么写 |
|---|---|---|---|
| 统计判据假设任务间独立 | 任务相关性会让区间过窄 | 分层或聚类稳健的方法 | 独立假设便于入门 |
| 样本量估算用的是粗略近似 | 边界情况下估算不准 | 用功效分析工具或模拟 | 手算量级足够做判断 |
| 人工标注的一致性处理未展开 | 主观质量的结论偏乐观 | 报告标注者间一致度并加权 | 需要标注数据 |
| 模型版本固定而内部可能变化 | 不可见的漂移影响可比性 | 用固定版本的镜像或本地权重 | 依赖外部提供方的能力 |
| 消融的完整性核对靠人列举 | 可能漏掉隐蔽耦合 | 用配置差异自动对比 | 自动对比需要可结构化的配置 |
| 帕累托比较未给出选择准则 | 报告了前沿但没给建议 | 按场景给出推荐点 | 场景依赖需求 |

第一条与第四条属于统计与环境假设，第二条与第三条属于方法精度，第五条与第六条属于可实现性。第四条值得单独标记：它意味着即使记录了模型版本，同一版本的内部行为仍可能变化（服务方的更新、负载导致的差异），因此跨时间的比较天然带有不确定性——处置是让关键结论附带重跑验证（在报告发布时再跑一次并核对方向）。

## L10 提问训练

### 五个层次

| 层次 | 例子 |
|---|---|
| 事实 | 噪声下限是什么？可检测效应与样本量的关系是什么？ |
| 机制 | 为什么消融要换中性替代而不是删掉？ |
| 设计 | 为什么确认性比较要事前登记？ |
| 系统 | 如果模型版本升级，之前的结论怎么办？ |
| 科研 | 能不能给出一个通用的"最小可信实验"规范？ |

### 五种提问模板

反例逼问：如果没有噪声下限，哪类结论会最多。

边界追问：一个基准要多少个任务才够。

代价追问：事前登记降低灵活性，代价落在谁身上。

替代对比：为什么报告分位数而不是均值。

验证追问：怎么证明"这个结论可复现"。

### 本篇引出的十二个问题

读懂层。 第一，噪声下限怎么得出来？第二，可检测效应与样本量的关系是什么？第三，效应量与显著性的区别是什么？

重建层。 第四，为什么实验基准要与门控基准分开？第五，为什么消融要换中性替代？第六，为什么报告分位数而不是均值？

设计层。 第七，样本量反推的四步是什么？第八，事前登记与多重比较校正各解决什么？第九，可复现的四项记录是什么？

评审层。 第十，拿到一份实验报告，你会先检查哪一处？第十一，怎么判断一次消融是否有效？第十二，如果有人说"我们的方法在三个任务上更好"，你怎么回应？

### 问题升级练习

模糊问题：「我怎么证明我的方法更好？」

升级后的精确问题：

> 证明"更好"至少包含三件互相制约的事：**比较**（跟谁比、在什么基准上）、分辨率（这个基准有多少任务、噪声多低）、以及可信度（有没有事前登记、有没有校正）。
> 第二件与第三件互相制约——提高分辨率（更多任务）会提高功效，而它也让"边跑边看"的风险更大（更多的比较机会）。
> 我能不能为这三件事各找出一条**可检查的判据**？
> 特别是：有没有哪一条判据，是**能在跑之前就写下来的**？

提升点说明：原问题无法回答，因为"更好"没有判据，而它默认了"跑一次更好"就是证明。升级后的版本把它拆成三件具体的事，指出分辨率与可信度的制约，并追加以一个更强的问题：哪一条判据能在跑之前写下——因为只有事前写下的判据才排除事后挑拣。

## L11 系统影响回溯

回看第 0.5 节的三个连锁影响。

| 预判 | 本篇分析之后的结论 | 状态 |
|---|---|---|
| 统计判据会让很多"看起来有效"的改动变成"未验证" | 确认，并给出噪声下限与样本量反推两条实现 | 成立 |
| 成本度量会让实验的设计空间变大 | 确认，并给出成本与质量联合报告这条要求 | 成立 |
| 实验结论会反向影响系统设计 | 确认，并把结论接入 4.5 的演化流程 | 成立 |

一处需要修正的预判：0.5.2 把"基准与稳定性"标为对 4.6 的强依赖。读完之后要补一层方向：实验基准与门控基准的分离会给 4.6 带来新的维护负担——两者都需要采样、分层与稳定性筛选，而它们的筛选标准不同（门控要常见、实验要困难）。处置方式是共用采样管道而分设筛选标准（同一批候选任务按两套标准分成两个集合），而这条分工本篇没有在 4.6 里明确，它是 4.6 的 L9 与 6.1 的问题四、五在本篇交汇处的一个具体后果。

通向下一篇的桥。 本篇给出了怎么做对比实验，而它有一个前提：被比较的东西已经被想到了。而研究里更有价值的时刻往往是在实验里遇到意外——一个不该失败的任务失败了、一个改动带来了方向相反的两种效果、一个指标改善而另一个恶化。

下一篇 `6.3 harness 效果评测与 benchmark` 处理这件事：本篇讲的是"怎么设计一次比较"，而它讲的是"**用哪些现成的基准、以及它们的判定与缺陷**"。它与本篇的连接点有三处：本篇的统计判据正是读那些基准分数的工具（没有噪声下限与口径意识，榜单数字无法解释）、基准卡的任务描述与本篇的任务集要求同源、以及它的缺陷分类学解释了"为什么某些分数不可信"。

## 记忆锚点与复述练习

### 一、骨架：四块

```
   怎么比较 ──► 怎么归因 ──► 怎么定分辨率 ──► 怎么不骗自己
      ↓            ↓              ↓                  ↓
   基准与对照    消融与完整性   噪声与样本量      登记·校正·可复现
   1.1、1.2     1.3            1.4                1.5、1.6
```

只记一行就记这行：怎么比较 → 怎么归因 → 怎么定分辨率 → 怎么不骗自己。

### 二、情境绑定：当你……就想起……

| 当你…… | 立刻想起 |
|---|---|
| 想比较两个方法 | 先写下要发现多大差异，再反推样本量 |
| 只有二十个任务 | 它只能发现三成的差异 |
| 看到一个小差异 | 噪声下限是多少；效应量多大 |
| 要做消融 | 换中性替代，不要直接删掉；核对其他因素 |
| 想调参再报告 | 开发集与测试集必须分开 |
| 比较了多个配置 | 事前登记了吗；要不要多重比较校正 |
| 报告成本或延迟 | 用分位数加极值，不要用均值 |
| 写下结论 | 四项记录齐不齐 |
| 别人说复现不出来 | 模型版本变了吗；种子固定了吗 |
| 实验里出现意外 | 记录下来——它是下一篇的问题来源 |

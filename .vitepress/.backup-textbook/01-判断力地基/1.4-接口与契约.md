## 本篇新词

这一篇的术语来自契约式设计与 API 演进。它们描述的是代码之外的那些约定：类型系统检查不到，编译器不会报错，违反时的故障在运行时或者几个月之后才出现，而那时定位成本已经很高。

**契约（contract）** 指一个模块对外的全部可依赖行为，而不只是它的函数签名。Meyer 把契约拆成三部分并在 Eiffel 里给了它们各自的语法位置：前置条件写在 `require` 里，后置条件写在 `ensure` 里，类不变量写在 `invariant` 里。对应到本课程的语言，这三部分是行为承诺（调用它会发生什么）、时序承诺（什么时候可以调用、可以调用几次、能不能并发调用）、错误承诺（失败时怎么表现——抛异常、返回错误值，还是静默降级）。把契约理解成"签名加注释"会导致一个可预测的后果：使用者只能从当前的实现里读出后两类承诺，而实现随时可以变。

前置条件与后置条件：前置条件是调用方的义务，后置条件是实现方的义务。Meyer 在 Eiffel 里让这两者可以被运行时检查（编译时可选关闭），这个设计背后是一个更重要的用法——它明确了责任归属。违反前置条件是调用方的缺陷，违反后置条件是实现方的缺陷；调试时这个区分直接回答问题该去哪一边找。

类不变量指在对象的整个生命周期中始终为真的性质。它不属于任何一次调用，因此既不能写成前置条件也不能写成后置条件。`D:\dsh-mini` 的 `src/kernel/session.ts` 有一条这样的不变量：`#events.length` 必须等于下一个事件的 `seq`。这条关系在每次 `append` 前后都必须成立，而它的守护方式只有两种——写入点内部的断言，或者外部测试。

Liskov 可替换性（LSP） 的准确形式是行为子类型化：如果程序依赖于类型 T 的契约，那么把 T 替换为 S 时程序仍应满足它原有的性质。Liskov 与 Wing 在 1994 年的论文里把它表述为可观察行为的保持，工程上常用的推论是——子类型可以弱化前置条件、可以强化后置条件，不能反过来。原因在于调用方只知道 T 的契约：S 多给的保证它用不上，少给的保证会让它出错。

**破坏性变更（breaking change）** 指任何使依赖原有契约的代码可能失败的改动。它与改动大小的关系很弱，与依赖者数量的关系很强。SemVer 2.0.0 把它形式化成版本号规则：不兼容的 API 改动升主版本号，向后兼容地新增功能升次版本号，向后兼容的缺陷修复升修订号；主版本号为零时（`0.y.z`）公开 API 视为不稳定。Hyrum 定律解释了为什么版本规则只能兜住一部分风险：当用户足够多时，一个 API 的所有可观察行为都会被某些人依赖，包括错误信息的措辞、返回值的顺序、乃至一次调用的耗时——这些不在 SemVer 的判定范围里，却是真实存在的依赖。

稳定依赖原则在 1.3 里出现过一次，用来计算不稳定性 `I`，这里用它的另一半：一个模块被依赖得越多，它的接口就应该越稳定。因此 `I` 低的模块不应频繁改变契约，`I` 高的模块可以随意改。它给出的可执行动作是——改一个高扇入模块的接口之前，先算一下有多少人会因此动手。

契约测试（contract test） 验证的是承诺，不是实现。单元测试可能断言返回值全等，契约测试断言返回值满足承诺中的性质。两者的差别在实现对返回对象增加一个字段时立刻显现：全等断言失败，契约断言通过。这个差别决定了测试是在保护契约还是在锁死实现，而后者会让合理的重构变成一批与契约无关的测试改动。

签名表达不了的五件事是这一篇的工程清单：副作用、幂等性、调用顺序、并发安全、错误语义。它们全部属于契约的一部分，全部无法由类型签名表达。1.2 会把它们逐条展开，并给出各自的表达位置。

## 第 0 节 · 学完这一篇你能做出什么

### 0.0 先行组织者：四个判断

这一篇不写 harness 代码，它建立四个可以独立使用的判断。四者之间有依赖顺序：不知道契约由哪三部分组成，就无法判断签名缺了什么；不知道签名缺了什么，就无法判断一次改动会不会伤到别人。

```
┌──────────────────────────────────────────────────────────────────────┐
│  ① 契约是什么 —— 三类承诺与责任划分                       → 1.1        │
│     行为承诺 ／ 时序承诺 ／ 错误承诺                                  │
│                                                                      │
│  ② 签名表达不了什么 —— 为什么类型系统不够                 → 1.2        │
│     副作用、幂等性、顺序、并发、错误语义                              │
│                                                                      │
│  ③ 什么改动是破坏性的 —— 兼容性判据                       → 1.4        │
│     从"改了什么"转向"谁依赖了它"                                      │
│                                                                      │
│  ④ 契约怎么演进 —— 版本化、弃用、兼容层                   → 1.6        │
│     在不破坏承诺的前提下改变承诺                                      │
└──────────────────────────────────────────────────────────────────────┘

 一句话串起来：承诺什么 → 签名没说的 → 谁会因此动手 → 怎么安全地改
```

这张图的读法是从左到右再加一个回转：前三块回答"现在的契约是什么、它漏了什么、改动会伤到谁"，第四块回答"受伤之后怎么修"。任何一次接口改动都可以顺着这条线走一遍，而每一块的落点都是一张可核对的表。

### 0.1 一个字段的引入：`costEstimate` 会连锁到哪里

第一个判断可以用一个具体改动来检验：给 `D:\dsh-mini\src\kernel\tools.ts` 的 `Tool` 接口加一个字段 `costEstimate?: number`，用来让守卫在调用高代价工具之前先问一次人。

从类型上看这是最安全的一类改动——可选字段，老实现不改也能编译，没有类型错误。但它在运行时有四条连锁路径，每一条都能被单独验证。

第一条是工具目录的生成逻辑。框架要把已注册工具翻译成给模型看的描述，而那份描述是从 `Tool` 的字段里挑出来的；如果 `costEstimate` 不在挑选范围内，工具作者填了它也不会有任何效果，模型看不到它，这部分信息在进入请求之前就丢了。

第二条是守卫的判断。守卫在调用前决定"问不问人"，读的就是这个字段；字段为空时它必须有一个明确的语义，因为 `undefined` 与 `0` 在判断中会走向不同分支——把"未填写"当成 0 会让昂贵工具默认放行，而这正是这个字段本来要防的事故。

第三条是既有工具。`Tool` 在本项目里有多个实现，加字段之后每个实现都要决定填不填。不填的实现会走默认语义，于是同样的操作在守卫视角下行为不一致：一个被询问，一个被放行。

第四条最隐蔽：一个"填了但没人读"的字段比不写它更糟，因为它会让后来的人据此判断系统已经具备按代价询问的能力，从而在别处依赖这个并不存在的保证。

四条连锁性质相同，都源于同一个问题：这个字段要不要成为契约的一部分。如果答案是"要"，所有实现者必须遵守它、所有消费者都可以依赖它，代价是它此后不可轻易删除；如果答案是"不要"，它只是实现细节，不该出现在接口上。三类承诺的检查表就是回答这个问题的工具，而它的第一个问题是"这个新成员承担的是三类承诺中的哪一类"。

### 0.2 本篇建立的三项判据

三项判据分别服务于写接口、改接口、审接口三个场景。

写接口时使用三类承诺的检查表（1.1）。用法是逐条追问：行为说清了，时序说清了吗——这个方法能不能重入、回调在哪个线程触发、注册之后多久生效；错误说清了吗——失败走异常还是返回值、异常类型有哪些、返回值里有没有表示失败的形态。后两类最常被漏掉，而它们恰好是使用者写调用代码时最需要的信息。

改接口时使用破坏性改动的分类表（1.4）。它把"改了什么"映射到"谁会受影响"，受影响的一方分为四类：构造方（依赖构造函数签名）、调用方（依赖参数与返回）、实现方（依赖接口成员）、监听方（依赖事件与回调的时序）。同一句"加一个可选参数"在这四类上的后果完全不同，落格之后再决定要不要迁移方案。

审接口时使用契约审计的七步方法（L3）。动作是先把"只读签名与文档时会合理推断出什么"写下来，再把这些推断与实现逐条对照。要找出三类缺口：签名承诺了但文档没写、文档写了但实现没做、实现做到了但没有人依赖。第三类看起来无害，它是过度承诺，会让未来的改动变贵。

### 0.3 开始之前的十分钟练习

进入正文之前先做一次体感练习：打开 `D:\dsh-mini\src\kernel\tools.ts`，找到 `Tool` 接口定义，只读字段声明，暂时不看注释，回答四个问题。`execute` 可以被并发调用吗？如果 `execute` 抛异常，框架会怎么处理？`sideEffect` 的值由谁检查、在什么时候检查？同一个工具被注册两次会发生什么？

这四个问题分别属于时序承诺、错误承诺、行为承诺的实现方与注册语义，全部是使用者必须知道的事情，而通常能在字段声明里直接找到答案的不超过一个。找不到答案不是读得不仔细，而是签名这个载体表达不了它们——而使用者会在缺失的地方各自补一个假设，这是 0.5.3 第一条连锁的起点。

下面十行代码演示同一件事：两个 `Provider` 实现满足同一个类型签名，但错误语义不同，于是调用方在换实现时崩溃。保存为 `provider.mjs` 即可运行，不需要任何依赖。

```js
// 两个实现满足同一个类型：chat(request) -> Promise<response>。
class ThrowingProvider {                    // 语义 A：参数不合法时抛异常
  async chat(request) {
    if (!request.messages?.length) throw new Error('messages 不能为空')
    return { content: 'ok', toolCalls: [] }
  }
}
class SilentProvider {                      // 语义 B：参数不合法时返回空响应
  async chat(request) {
    if (!request.messages?.length) return { content: '', toolCalls: [] }
    return { content: 'ok', toolCalls: [] }
  }
}

// 调用方只看到了签名，于是它隐式假设了一种语义。
async function ask(provider) {
  const res = await provider.chat({ messages: [] })   // 两个实现收到同样的空消息
  return res.content
}

console.log(await ask(new SilentProvider()))   // 输出空字符串：失败被当成了"模型没说话"
console.log(await ask(new ThrowingProvider())) // 抛异常：调用方没有 try/catch，进程退出
```

这段反例的结论比"要写清错误承诺"更具体：类型相等不等于契约相等，所以可替换性不能靠类型检查验证，只能靠契约测试验证——而契约测试必须先知道承诺是什么。

> **面试视角**
> **高频问法**："你怎么设计一个给别人用的接口？"
> **追问方向**："加了一个可选参数为什么还会出问题？"回答的落点是接口的每个成员都在宣布一个能力，而宣布能力会引出"谁填、谁用、没人填怎么办"三个必须回答的问题。

### 0.5.3 三个连锁影响

**契约写不清，会让每一处调用方各自发明一套假设。** 链条的起点是一个很小的疏漏：接口没有写明这个方法会不会抛异常。接下来发生的事有固定模式。第一个调用方按"会抛"来写，加了 `try/catch`；第二个按"不会抛"来写，没加；第三个在调试时发现确实会抛，于是补了一个防御性判断。半年后接口因内部改动开始在边界情况下抛异常，第一个和第三个调用方没事，第二个崩了。这条链条的性质不是"有人写错了"，而是接口没有给出答案，于是每个人都自己给了一个，而三个人给出不同答案是必然的，因为默认值取决于各自经历。修复方式只有把答案写进契约：明确"我不抛，失败一律通过返回值表达"，或者明确"我会抛，类型是这些"。两者都可以，但必须选一个并写下来——这一处的选择会在第 3 卷的重试机制里被再次引用，因为重试必须知道失败从哪里来。

**把实现细节写进契约，会让系统失去演进能力。** 反向的问题同样致命。假设 `Tool` 的文档里写着"`execute` 返回的字符串总是以换行结尾"，这句话一旦被当作承诺，所有实现都必须遵守、所有解析方都可以依赖，于是这个换行从实现细节变成永久约束——即使某天发现不加更合理，也不能改。更麻烦的是这类约束往往不是有意写下的，而是被观察出来的，这正是 Hyrum 定律的内容：`D:\dsh-mini` 的 `Provider` 接口有三个实现，其中 `MockProvider` 的脚本数组长度决定了它能被调用几次，"超出脚本长度就抛错"这个行为一旦被写进测试，它就从实现细节变成了事实承诺。因此契约设计有一项实际任务是有意识地划线：哪些行为长期保证，哪些行为保留随时改动的权利并明确声明不要依赖。

**契约的稳定性决定了改动波及面的形状。** 这条连锁把本篇与 1.2、1.3 接起来。1.3 给出"波及面等于依赖它的模块的传递闭包"，本篇补上关键限定：波及面里的模块并不都依赖你的全部行为，它们各自依赖其中一部分。以 `D:\dsh-mini` 的 `Session` 为例，16 个文件引用它（值引用 7 个、类型引用 9 个），依赖内容各不相同：`src/kernel/agent.ts` 依赖 `append` 与 `deriveMessages` 的行为，`src/apps/web.ts` 只依赖事件类型，`src/evolution/diagnose.ts` 依赖 `SessionStats` 的字段。所以改动 `computeStats` 的返回字段时，真正受影响的是那几个读统计的地方，而不是全部 16 个。准确估计需要两张表：一张是"谁依赖我"，另一张是"我承诺了什么、谁依赖了哪一条"。只有第一张表会过度保守，只有第二张表会过度冒险，两张合起来才能得到可用的估计。

### 0.5.4 三份接口代表的三类契约形态

`D:\dsh-mini` 有三份接口适合做契约分析，它们对应三类不同的要求。

`src/kernel/tools.ts` 的 `Tool` 是面向第三方实现的契约：由工具作者实现，由框架调用。这类契约要求最高，因为实现者与调用者不是同一批人，任何未写明的期望都会变成隐患——框架假设工具返回特定形状，而工具作者不知道这个假设存在；它的契约缺口以"某个工具偶尔失败"的形式出现，而不是以类型错误的形式出现。

```ts
export interface Tool {
  readonly name: string
  readonly description: string
  readonly parameters: JsonSchema
  readonly sideEffect: SideEffect
  execute(args: Record<string, unknown>, ctx: ToolContext): Promise<string>
}
```

这段声明能读出的信息到此为止：`execute` 的参数与返回、字段的可读性。读不出的是 `execute` 能否并发调用、抛异常时框架如何处置、`sideEffect` 由谁校验、重复注册 `name` 会发生什么。这四问对应 0.3 的练习，答案只能来自实现与文档。

`src/kernel/llm.ts` 的 `Provider` 是面向替换实现的契约：`MockProvider`、`LocalProvider`、`DeepSeekProvider` 都实现它。这类契约的关键是可替换性——调用方不应分辨出用的是哪一个，任何"只有某一家才有"的行为都是契约泄漏，代价在换实现或写测试时暴露。0.3 的十行反例演示的正是这类泄漏里最常见的一种：类型签名一致而错误语义不一致。

`src/kernel/session.ts` 的事件契约是跨时间的契约：事件写入日志之后必须永远能被后续版本读懂。它的使用者包括尚未写出的代码——未来的恢复逻辑、分析工具、迁移脚本；这一条决定了"模型可见的必须可重建"为什么是核心不变量：它是唯一能让未来代码信任历史的方式。

> **面试视角**
> **高频问法**（系统设计面的扩展讨论环节）："你这个改动会影响谁？"
> **高分要点**：按两类依赖分别数——谁调用它（值依赖）、谁只用了它的类型（类型依赖），并给出数字。这一题考的是有没有结构，而不是估得准不准。
> **对应岗位**：后端技术面、Agent 工程师技术面。

## L0 要解决的问题

### 0.1 现象一：签名给出的信息量，只有契约的一小部分

看一个真实签名：

```ts
export function validateArgs(schema: ParamSchema, args: unknown): ValidatedArgs
```

签名表达的是一组类型约束：入参是 schema 与 `unknown`，返回 `ValidatedArgs`。使用者还需要知道而签名没有表达的东西有四个：参数不合法时抛异常还是返回一个带错误的对象；对 schema 之外的多余字段是忽略还是拒绝；它会不会修改传入的 `args`；它是不是纯函数，也就是结果能不能被缓存、能不能重复调用。

这四个问题在写调用代码时都必须回答。可选路径只有三条——读实现、试一次、看文档——而当三条都不可行时，使用者会写下一段基于假设的代码，假设的内容取决于他先看到了哪一部分实现。故障由此产生，而且它的形态很特殊：这类代码在接口那次未写明的行为发生变化之前一直正确，因此它不会在评审或测试里暴露。

把这件事量化一下能看清它的规模。一个二十模块的项目，若平均每个模块对外暴露五个函数，每个函数有三个未写明的行为维度，那么"只能靠猜"的点约有三百处。三百处里任何一处的底层行为变化都可能破坏某一处调用方，而调用方本人并不知情。这是 1.2 所说"偶然复杂度"的一个具体来源：复杂度不来自功能本身，而来自未被表达、只能被猜测的约定。

### 0.2 现象二：半实现的能力比没有这个能力更危险

第二个现象的触发条件很窄，后果却很广：往接口上加一个成员，但只在部分实现里填了值。

以 `Tool` 接口为例，加一个 `costEstimate?: number`。类型检查通过，老实现不需要改，编译没有错误。问题出在运行时的语义上：字段是可选的，于是"未填写"与"填了 0"在守卫的判断里会得到不同的结果。如果守卫把 `undefined` 当作 0 处理，那么一个未声明的昂贵工具会被默认放行，而这个字段本来要防的正是这件事。反过来，如果守卫把 `undefined` 当作"不可比较"，那么它就必须回答"信息缺失时该怎么办"，而那个答案决定了这个能力是完整的还是部分的。

半实现的危险来自预期管理。接口上出现了这个成员，读者会据此认为系统支持成本预估；而实际上只有一部分工具支持。使用者据此做出的判断（例如"昂贵操作会被拦截"）在真实的运行里不成立，而这类错误的代价随时间放大：越晚被发现，依赖它的代码越多。

把这类故障写成分类，它属于"静默给出错误结果"——没有任何异常，也没有任何日志，系统按错误的语义继续运行。四类失败模式里它的定位成本最高，这一点在 1.1 的失败模式分类表里会展开。

### 0.3 现象三：改了实现，调用方坏了，而接口没动

第三个现象说明契约不等于签名。改动发生在实现内部：某处遍历从插入顺序改成了排序顺序。调用方随即崩溃，而它的代码只依赖了一个从未被承诺的行为：

```js
const [firstKey] = Object.keys(result)
// 作者假设 firstKey 是最后插入的那个键
```

责任归属在这个情形里是没有争议的——按 Hyrum 定律，当一个 API 的用户足够多时，它的所有可观察行为都会被某些人依赖，包括作者从未打算承诺的那些。因此"这不是我的问题"这种回答在工程上是无效的，它只说明这条依赖没有被表达出来。

由此得到契约设计的一条操作原则，它在整门课里反复出现：打算长期保持的行为，明确承诺它；不打算保持的行为，明确声明它是实现细节。两类都不属于的情形下，默认结果是被依赖，因为使用者没有其他信息可用。这条原则的落地形式通常是注释里的两句话，第二句往往被省略而被省略的那一句恰恰决定了这条契约会不会失控：

```ts
/**
 * 工具产出的摘要文本，用于给模型一个简短预览。
 * 这是实现细节：具体格式、长度、是否包含换行都不构成承诺，调用方不应解析它的内容。
 */
summary: string
```

### 0.4 现象四：迁移决策缺少输入

第四个现象发生在决策层。当一个接口需要改动时，可选项包括写兼容层、通知使用者、提升版本号、直接改；而选择的依据是这次改动影响谁、影响多大。在缺少这个输入的情况下，决策会退化成两种极端。

一种是对一切都谨慎：每个改动都加兼容层，代码里积累起为旧版本准备的 `if`，这些分支本身又成为新的复杂度来源。另一种是对一切都无所谓：直接改，坏了再说，把代价转移给下游。两种做法都是同一个原因造成的——没有一个把"改了什么"映射到"谁受影响"的工具。1.4 节给出的分类表就是那个工具，而它的判定依据与传统直觉相反：不看改动本身的大小，看有多少依赖落在被改动的那部分承诺上。

### 0.5 这一篇要正面回答的四个问题

四个现象收拢之后是四个问题，它们分别对应 L1 的四节主干，并且在后续篇目里会被反复引用。

第一，一个契约由哪几部分构成，为什么写文档的人觉得"该写的都写了"而使用者仍然在猜。答案是把契约拆成三类承诺并补上责任归属这个被忽略的维度（1.1），附带一份失败模式的分类，用来判断缺失某一类承诺时故障会以什么形态出现。

第二，签名表达不了哪些东西，以及每一项应当在代码的什么位置表达。清单有五项：副作用、幂等性、时序、错误语义、资源所有权（1.2）。它们的共同点是类型系统管不到，而它们的表达位置并不相同——前三项靠注释与运行时的强制机制，错误语义靠类型与错误分类，所有权靠明确的复制或明确的约定。

第三，什么样的改动是破坏性的，以及为什么判据从"改了什么"转向"谁依赖了它"（1.4）。这一节会给出四类受影响方与一张落格表。

第四，怎么在不破坏承诺的前提下演进接口。四种手段（加而不改、放宽不收紧、兼容层、版本化）各自的代价落在谁身上，是 1.6 的内容。

> **面试视角**
> **高频问法**："你遇到过一个很难复现的 bug 吗？"——0.1 与 0.2 描述的两类现象都是好素材，前者是未表达的行为被假设，后者是半实现能力的静默错误。
> **追问方向**："为什么同一个失败有时抛异常、有时返回错误值？"这问的是错误承诺缺失的后果，`D:\dsh-mini` 里存在这样一处真实缺口（见 L3.2 的审计）。

## L1 设计与原理

### 1.1 契约由什么构成：三类承诺、责任归属与失败模式

函数签名是契约的一个投影，而且信息量很低。它给出的是"有哪些输入、输出是什么类型"，缺失的是"这个调用在什么条件下合法、会产生什么副作用、失败时怎么表现"。缺失的那部分恰好是使用者写调用代码时最需要的，因此契约的表达问题在本质上是一个信息传输问题：写实现的人知道全部信息，写调用方的人只看到投影。

#### 1.1.1 三类承诺，以及各自的表达位置

把契约分成三类承诺，划分依据是使用者需要在什么时刻知道它们，也就是它们各自防止哪一类错误。

行为承诺回答"调用它会发生什么"：返回值的内容、副作用的范围（触及文件、网络、环境变量还是全局状态中的哪一些）、以及幂等性。这一类最常被写下，因为它最直观，而且它的缺失通常会很快被发现——跑一次就知道结果不对。

时序承诺回答"什么时候可以调用、可以调用几次"：调用时机的前置条件（必须初始化之后、不能关闭之后）、重入性（能不能在它触发的回调里再调用它）、并发安全性、以及多次调用的效果是否与顺序有关。这一类最常被漏掉，后果也最难排查，原因在下一段解释。

错误承诺回答"失败时怎么表现"：失败走异常还是返回值、异常的类型有哪些、失败能不能重试、以及部分失败如何处理（做了三件事而第二件失败时，第一件要不要回滚）。这一类缺失的后果是调用方写不出正确的错误处理——他会写一个 `try/catch`，但不知道自己该捕获什么、捕获之后能不能重试。

时序承诺的缺失有一个与众不同的性质：它不会在任何单线程、线性执行的测试里暴露。 这类缺陷只在真实并发或真实的回调重入下出现，而它的表现形式是偶发失败或状态损坏，两者都无法从失败点反推出原因。相比之下，行为承诺的缺失会立刻给出错误结果，错误承诺的缺失会让错误处理写得不对但在测试时暴露。这个差别直接决定排查成本的量级：前两类以分钟计，时序类以天计。

举一个真实例子说明三者缺一不可。`D:\dsh-mini` 的 `ToolRegistry` 有这样一个方法：

```ts
register(tool: Tool): Disposer
```

行为承诺在文档里写明并且实现遵守：注册一个工具，返回撤销注册的 disposer；重复注册同名工具时后注册的覆盖先注册的——这一句最关键，因为它决定调用方能否安全地重复注册。错误承诺部分实现：名字非法时抛异常。时序承诺完全没有表达：没有说明"工具正在执行时能不能注册新工具"。在一个插件化的系统里这不是空想的情形——某个插件可能在一次工具调用期间被装载（例如工具触发了自改），此时注册表正在被遍历，而遍历过程中修改集合的行为取决于具体实现：`Map` 的迭代器在删除未访问项时会跳过它，在插入新项时会访问到新项，这两种行为都不是调用方能够合理预期的。

这三类承诺的表达位置并不都在注释里，把它们分清楚能避免"写在注释里就当表达了"这个常见的错误。行为承诺与错误承诺有类型系统的支撑：返回值类型能表达成功形态，可辨识联合能表达失败形态（2.1 的 `ToolResult` 就是这种用法，它让"忘记检查失败"变成编译错误）。时序承诺几乎没有类型支撑，只能靠注释、运行时的断言或明确的接口设计（例如把"只能在初始化阶段调用"这件事编码成一个只在初始化阶段可见的对象）。副作用与所有权介于两者之间：副作用的等级可以变成字段（`sideEffect`），而实际执行受限与否要靠沙箱强制。

#### 1.1.2 责任归属：契约里最实用的划分

Meyer 的契约式设计给出的划分的价值不在术语，而在它明确了出问题该去哪边找。前置条件是调用方的义务，后置条件是实现方的义务，类不变量由双方共同维持。

| 概念 | 谁负责 | 违反时的含义 | `D:\dsh-mini` 里的例子 |
|---|---|---|---|
| 前置条件 | 调用方 | 调用方传了不该传的东西——调用方的缺陷 | 调用 `deriveMessages` 之前，事件流必须已经 `endTurn` |
| 后置条件 | 实现方 | 实现没有兑现承诺的输出——实现方的缺陷 | `ok(text)` 返回的结果里 `isError` 必须为 false |
| 类不变量 | 双方共同 | 对象进入了不该存在的状态——契约表达不完整 | `#events.length` 必须等于下一个事件的 `seq` |

这个划分最实用的地方是它给出了调试的第一步。遇到失败时第一个问题不是"哪里错了"，而是"这是前置条件被违反还是后置条件被违反"：前者去查调用方传了什么，后者去查实现做了什么。跳过这个判断直接读代码，会在两个方向上各浪费一半时间；而在一个跨模块的调用链上，这个差别通常是几小时与十分钟的差别。

第三行值得单独说明，因为它的性质与前两行不同。类不变量被违反时，没有任何一方违反了规则，而系统仍然进入了坏状态；这通常意味着契约表达不完整——那个不该发生的状态既没有被任何前置条件排除，也没有被任何后置条件保证。`D:\dsh-mini` 的 `assertModelVisibleMatchesLog` 防的正是这一类：它被触发时既不能说调用方错了，也不能说某处实现错了，只能说系统在一个未被表达的地方产生了不一致。这类不变量在 harness 里的数量不多，但每一条都对应一个会让整个系统失去可信度的问题（2.7 会展开"模型可见的必须可重建"这条核心不变量）。

#### 1.1.3 失败模式的分类

判断契约缺口的严重程度，除了看缺哪一类承诺，还要看它一旦被触发会以什么形式暴露。四类失败模式的排查成本依次上升，这个顺序本身就是一个判据：越靠后的模式，越需要在设计阶段而不是调试阶段解决。

| 失败模式 | 表现形式 | 为什么难发现 | 典型来源 |
|---|---|---|---|
| 立即可见 | 错误结果、进程崩溃 | 不难发现，难在定位到契约缺口 | 行为承诺缺失（返回值语义未写明） |
| 通道丢失 | 错误被 catch 后转成日志，调用方继续执行 | 错误信息在传播中被压缩，模型或上层只看到"某处出错" | 错误承诺缺失（异常 vs 返回值的约定不统一） |
| 偶发 | 在并发、回调重入、时序交叉下失败，单线程测试通过 | 失败不可复现，无法从现象反推原因 | 时序承诺缺失 |
| 边界值 | 只在特定输入或特定规模下失败 | 测试数据不覆盖该边界 | 数量级与边界条件未被表达（"这个上限是多少"） |

这个分类的用法是在写完一个接口之后，对每一条未写明的行为问"它属于哪一类"。属于后两类的必须在接口上补写清楚或加上运行时检查，因为它们无法靠调试发现；属于前两类的可以留到实现阶段处理。

#### 1.1.4 两次追问

工程侧的追问是哪一类承诺最值得优先写。按投入产出比算答案是时序承诺：写它只需要一两句话（"这个方法不是线程安全的，调用方需要在外部同步"），而漏掉它的代价落在上表的第三行，也就是最难排查的那一类。行为承诺虽然最常被写，但它的缺失跑一次就能发现；错误承诺的缺失会让错误处理写错，但至少在测试时会暴露。由此得到一个可操作的判据：如果你说不清某个方法能不能并发调用，那么它多半不能；如果你的答案是"我没想过"，那就是一个需要现在补上的缺口，而不是一个可以留给文档的细节。

产品侧的追问是为什么承诺越少越好。契约是对使用者的公开承诺，每一个承诺都限制未来的选择权，因此一个反直觉的原则是：契约应当恰好含有使用者必须知道的东西。这不是"尽量少写"，而是"每一句写进契约的话都必须真的是承诺"，因为一旦某件事进入契约，改动它就需要迁移方案、通知与兼容层，而从未被承诺的事情可以随时改。这条原则有一处容易误解：它不意味着少写文档，恰恰相反，它要求把"这不是承诺"也写出来。`D:\dsh-mini` 的 `Tool` 接口就有一处这样的注释（见 0.3 的例子），而后半句与前一句同等重要——缺少它，使用者会按 Hyrum 定律依赖一切可观察的东西。

> **面试视角**
> **高频问法**："一个接口的契约由什么构成？"骨架是行为、时序、错误三类承诺。
> **追问方向**："为什么契约要写得越少越好？"答：每个承诺都限制未来的演进自由，而"不写"不等于"不声明"——必须显式声明哪些不属于承诺。
> **加分点**：能说出口诀"参数只能放宽、返回只能收紧"的来源，它是 Liskov 行为子类型化的方向性推论（弱化前置、强化后置）。

### 1.2 签名表达不了的五件事

这一节把 1.1 的结论具体化成一份检查表，用于写接口时逐项核对。五项的共同点是类型系统管不到，而它们的表达位置各不相同，因此下面的表除了"不写清会怎样"，还给出一列"在哪里表达"，这一列是本节比一份原则清单更有用的部分。

| # | 表达不了的 | 不写清会怎样 | 在哪里表达 |
|---|---|---|---|
| 1 | 副作用 | 调用方以为它是纯函数，于是缓存结果或重排调用顺序，而它实际触及了外部世界 | 字段（等级）+ 沙箱（强制）+ 注释（触及哪些资源） |
| 2 | 幂等性 | 重试或恢复时重复执行，产生第二次效果 | 注释（明确的"可重复调用"或"每次调用产生一次效果"） |
| 3 | 时序 | 并发、重入、生命周期边界上出现未定义行为，单线程测试照常通过 | 注释 + 运行时断言 + 用类型把阶段约束编码进接口 |
| 4 | 错误语义 | 调用方不知道要捕获什么、不知道能否重试 | 类型（错误分类或可辨识联合）+ 每个分类的可重试性 |
| 5 | 资源所有权 | 返回的内部对象被外部修改，或该释放的没有释放 | 明确返回副本，或明确声明"不要修改返回值" |

#### 1.2.1 副作用：唯一会跨出调用栈产生影响的一项

五项里副作用排在第一位，原因是它的影响不局限于本次调用的参与者。返回错误的结果是可恢复的，改对再跑一次即可；在没有权限时静默删除了一个文件是不可恢复的。因此表达副作用最清楚的接口，恰好是最需要它的那类接口，在 agent harness 里就是工具。

`D:\dsh-mini` 的 `Tool` 用字段表达这件事：

```ts
export interface Tool {
  readonly name: string
  readonly description: string
  readonly params: ParamSchema
  /**
   * 这个工具的副作用等级。守卫依据它裁决放行 / 询问 / 拒绝。
   * 它是一份承诺：声明 'read' 就意味着不会改动任何持久状态。
   */
  readonly sideEffect: 'read' | 'workspace-write' | 'irreversible'
  execute(args: Record<string, unknown>, ctx: ToolExecContext): Promise<ToolResult>
}
```

这段代码里的难点行是 `readonly sideEffect` 那一行，而不是 `execute`。它把一个原本只存在于实现者头脑中的判断变成了可被程序读取的数据：守卫需要的是运行时可读的值，注释满足不了这个需求；而一旦它成为字段，它同时获得两个新性质——必须准确（守卫据此放行，错了就是安全问题）、必须被每个实现填写（类型系统强制）。

但这个字段目前没有校验机制：一个工具声明自己是 `read` 而实际写了文件，框架无法发现。这是一个信任型承诺，不是强制型承诺。这个区分的后果是具体的——"工具声明 `read` 就是安全的"这个推断不成立，除非所有工具都出自可信来源。1.8 的"声明 + 强制"配对（第 3 卷实现沙箱时落地）正是针对这一点，而 L3 的审计会把它列为一条真实缺陷。

#### 1.2.2 幂等性：重试与恢复共同的前提

幂等性在两个地方必须被知道：重试与断点恢复，而这两处对它的要求是同一条——只有幂等的操作才可以被安全地重放。

先看重试。`D:\dsh-mini` 的重试机制针对模型调用，而模型调用是幂等的（重复问一次不改变世界）。一旦重试被扩展到工具执行，重复执行非幂等工具就会产生真实后果：测试被跑了两遍、消息被发了两条。因此幂等性不是"这个函数的一个性质"，而是"这个函数能否被安全重试"的前提。这个视角的转换决定了动作顺序：要加重试时，第一件事是确认被重试的操作幂等，而不是先写重试循环。

再看恢复。会话恢复的含义是从日志重建状态并继续，而日志里可能出现"某个工具调用已经开始但没有结果"的记录。恢复时该怎么做取决于那个工具是否幂等：幂等则重放，非幂等只能标记为结果未知并交由模型决定。这是工具接口必须表达幂等性的直接原因——它是恢复策略的输入，而恢复策略在第 3 卷的持久化篇里是硬需求。

#### 1.2.3 时序：漏掉它，代码会在测试里通过而在生产中失败

时序承诺的缺失为什么最难查，1.1.1 已经给出机制：它不在单线程线性执行的测试里暴露。这里补一个正面例子，`D:\dsh-mini` 的 `framework/context.ts` 里 `provide` 的一段说明写得比多数地方都清楚：

```
注册服务的规则：
  1) 服务的实现写进共享表，但归属记在注册者身上；
  2) 注册者卸载时，共享表里属于它的那部分被移除；
  3) 卸载后再次 require 同名服务会失败——因为提供者已经不在了。
```

第 3 条是一条时序承诺：它说明"卸载之后不能再取"。缺少这句话的后果是可预测的——调用方会在某条延迟执行的路径上持有服务引用，然后在卸载之后使用它，得到一个已经失效的对象。这类故障的表现形式是"某个功能偶尔不工作"，而原因是一次插件卸载，两点之间的联系不会从堆栈里看出来。

#### 1.2.4 错误语义与资源所有权

错误语义的核心问题是粒度，而粒度应当与调用方的决策点对齐：调用方需要做出几个不同的决定，就提供几类错误。只抛一种笼统的 `Error` 时，调用方无法区分"参数错了，不要重试"与"网络抖了，可以重试"；抛出七八种类型时，调用方又难以穷尽处理。`D:\dsh-mini` 的 `src/kernel/llm.ts` 选择了二分的粒度——可重试与不可重试——因为调用方（重试插件）恰好只需要这一个区分，而这个选择本身就是"按下游需要什么判据来分类"的一个实例（2.1 会把这条原则展开成错误分类表）。

资源所有权的核心问题是内部状态被暴露。接口返回一个内部集合时，即使类型上标注了 `readonly`，运行时它仍然是同一个对象；`readonly` 是编译期约束，对 `Object.freeze` 之外的一切都不构成运行时保护。契约在这里只有两条路：返回副本，放弃一部分性能换安全；或者明确声明不要修改返回值，承担被违反的风险。`D:\dsh-mini` 的 `Session.events` 选择了后者，于是那条声明必须写进契约——否则它只是一个未言明的假设，而 1.3 会把这类假设列为依赖分析的一个盲区。

> **面试视角**
> **高频问法**："类型系统还不够吗？"不够。签名表达不了副作用、幂等性、时序、错误语义、资源所有权这五项。
> **追问方向**："你怎么表达一个函数是不是线程安全的？"落点是时序承诺，也是五项里唯一几乎没有类型支撑的一项。
> **对应岗位**：后端技术面、Agent 工程师技术面。

### 1.3 不变量：契约里最难表达、也最重要的一项

行为、时序、错误三类承诺都围绕一次调用展开，它们有明确的挂靠点：前置条件挂在函数入口，后置条件挂在函数出口。类不变量不同，它描述对象在任何时刻都必须满足的性质，因此它没有挂靠点。这一节单独处理它，因为它是 harness 里最关键也最难写清的一类契约。

#### 1.3.1 它为什么难以表达

第一，它不属于任何一次调用。你不能把它写进某个方法的文档，因为它不属于那一个方法；写进去之后会得到一句看起来很怪的话（"这个方法保证 `#events.length` 等于下一个 `seq`"，而实际上它保证的是对象的状态，不是这次调用的结果）。

第二，它常常跨对象。以本课程的核心不变量"模型可见的消息必须能从日志重建"为例，它涉及 `Session`（持有日志）、`deriveMessages`（从日志派生消息）、以及 `Agent`（消费派生结果）。它不属于三者中的任何一个，而属于它们的组合方式——因此没有一个文件的注释是它的自然归宿。

第三，它往往延迟暴露。前置条件与后置条件被违反时问题当场出现，而不变量被违反时对象通常看起来还能用，直到某条路径依赖了那个已经不再成立的性质。这个延迟决定了它的发现成本：故障现场与故障原因之间隔着若干次调用，甚至隔着一次重启。

第四，也是最容易被忽略的一点：不变量有两种实现方式，而它们的性质不同。它可以在多个地方被存储，也可以只在一处存储、由其他数据推导出来。存储的方式会产生一致性问题（两处的值可能不同步），推导的方式则不可能不一致。`D:\dsh-mini` 的 `Session` 选择了后者：`seq` 不在事件里单独维护一个计数器，而由 `#events.length` 推出，于是"`#events.length` 等于下一个 `seq`"这条关系不可能被破坏，因为它被定义为真而不是被检查为真。

这条区分是本节最实用的一条判据。当你发现一条不变量需要被检查时，先问它能不能改成推导；能改成推导的，就不需要断言、不需要测试、也不需要文档提醒。只有那些确实无法由其他状态推出的不变量（跨对象的、跨进程的、跨时间的）才需要下面三种表达方式。

#### 1.3.2 表达不变量的三个位置与它们各自的职责

因为不变量没有天然挂靠点，它需要在三个位置被表达，而这三个位置防的是不同的失败。

运行时断言把沉默的损坏变成响亮的失败。`D:\dsh-mini` 的 `assertModelVisibleMatchesLog` 是这种用法：

```ts
/**
 * 运行时断言：模型可见的消息必须能从日志重建出来。
 *
 * 为什么这个检查值得放在热路径上：
 * 这条不变量一旦被破坏，症状会在很远的地方出现（模型行为异常、恢复失败、
 * 统计对不上），而那时已经无法定位是哪一次改动引入的。断言把远处的症状
 * 变成近处的失败。
 */
export function assertModelVisibleMatchesLog(
  events: readonly SessionEvent[],
  messages: readonly ChatMessage[],
): void
```

这段声明里的难点不在参数类型，而在它被调用在什么位置。断言的成本与收益都不体现在这个函数的实现里，而体现在调用点的选择上——这也是 1.3.3 那条工程追问要回答的问题。

测试覆盖那些你能构造出来的场景，断言覆盖那些你无法预知何时出现的路径。两者的边界是"能不能主动构造"：一次工具调用与它的结果必须配对，这个场景可以构造，用测试；而"派生消息与日志不一致"这件事可能在任意一次上下文压缩之后出现，路径组合无法穷举，用断言。

文档的作用与前两者不同，它不是为了抓住违反，而是为了让使用者知道这条约束存在。缺少文档时，一个不了解规则的开发者会写出违反它的代码而完全不自知——他会先违反，再被断言拦住，而他本可以一开始就不违反。三种表达缺一不可，缺哪一种就会漏掉哪一类问题。

#### 1.3.3 一个延迟暴露的反例

下面这段代码演示"不变量被破坏之后对象看起来还能用"这件事。它模拟了一个常见写法：计数与集合各存一份，两者的差由业务规则约束。运行它的输出是三行 `count=1 items=2`，没有任何异常——此时两项之差恰好等于未持久项的数目（一项），不变量成立。

```js
class Ledger {
  constructor() { this.items = []; this.count = 0 }
  append(item) {
    this.items.push(item)
    if (item.durable) this.count += 1        // 只统计"持久"过的
  }
}
const ledger = new Ledger()
ledger.append({ id: 1, durable: true })
ledger.append({ id: 2, durable: false })
// 不变量：items.length 与 count 的差只来自未持久项，某处代码按此推断
console.log(`count=${ledger.count} items=${ledger.items.length}`)
console.log(`count=${ledger.count} items=${ledger.items.length}`)
console.log(`count=${ledger.count} items=${ledger.items.length}`)
```

要让它坏掉，只需要在某个路径上删掉一项（例如一次压缩或一次失败回滚），而忘记同步 `count`。此后所有按 `count` 推断"还有多少未持久项"的代码都会得到错误结果，但对象本身仍然可以被继续 `append`，也不会抛错。这条不变量如果写成推导式（`count` 由 `items` 每次遍历得出，或反过来 `items` 是唯一真源），这个故障就不可能存在。

#### 1.3.4 两次追问

工程侧的问题是断言该不该放在热路径上。放在热路径的成本是每次任务都多花一点时间，收益是定位精度；放在冷路径（只在测试里跑）的成本接近零，收益是覆盖不全。判断依据是这条不变量被破坏后的定位成本，换句话说，断言的位置应当与"症状离病因的距离"成正比。如果症状是"模型行为异常"（距离以天计），那么每次多花十毫秒是划算的；如果症状是"下一次调用立刻抛异常"（距离为零），放在测试里就够了。

产品侧的问题是这条不变量为什么属于产品要求而不是工程要求。考虑一个真实的产品问题：用户想知道上一次会话里 agent 为什么做了某个决定。这个问题的答案只能来自历史记录，而如果"模型当时看到的东西"没有完整留在日志里，它就永远无法回答。因此这条不变量支撑的是一个可复盘性能力，它关系到用户能不能信任这个系统；而它一旦被破坏，损失是不可逆的——那些历史就是丢了。把工程约束映射到产品能力是这一篇要反复使用的动作：值得写进契约的条款通常不是代码整洁意义上的好习惯，而是某个产品能力的必要条件。

> **面试视角**
> **高频问法**："什么是不变量？你怎么保证它？"三处表达（断言 / 测试 / 文档）是骨架，而更强的一点是"能不变量就别存它，改成推导"（见 1.3.1 的第四条）。
> **追问方向**："把不变量检查放在每次请求的热路径上，值得吗？"按"症状离病因的距离"判断，量化形式见 L2 第 9 条。
> **加分点**：举一个"破坏后不立刻报错"的不变量例子，工具调用与结果必须配对就是这一类。

### 1.4 兼容性判据：什么改动是破坏性的

这一节给出的表用于在做改动之前用两分钟定位自己处在哪一格。它的判定依据与直觉相反，而这一点决定了它的用法。

#### 1.4.1 判据是"谁依赖了它"，不是"改了什么"

一个改动是破坏性的，当且仅当它使某个依赖原有契约的代码可能失败。定义里有三个部分需要展开。"依赖原有契约"意味着不是所有使用者都会失败，只有那些依赖了被改动的那部分承诺的使用者会——因此同一个改动在不同项目里的破坏性不同，给一个函数加可选参数在只有三个调用方的项目里无害，在被外部依赖的库里有可能是破坏性的。"可能失败"指进入了错误或未定义的状态，而不是必然抛出异常。"代码"包括尚未写出的代码，这是本课程与普通库的一个重要差别：会话日志的消费者包括未来的恢复逻辑与分析脚本，它们的依赖还没写出来，但已经被计入了这份契约。

这一定义与 SemVer 2.0.0 的规则可以对齐，而对照之后会发现版本规则只覆盖了定义的一部分。SemVer 规定不兼容的 API 改动升主版本号、向后兼容地新增功能升次版本号、向后兼容的缺陷修复升修订号，并且规定主版本号为零时公开 API 视为不稳定。这些规则回答的是"改动的性质"，而定义要求回答的是"谁会因此失败"——后者取决于依赖者的分布。当依赖者包括你无法列举的下游代码与历史数据时，SemVer 的三种分类不足以覆盖真实风险，这正是 Hyrum 定律要补充的部分。

#### 1.4.2 分类表：改动、受影响方、失败模式

表里新增的最后一列把本节与 1.1.3 的失败模式分类接起来，它回答的是"如果这次改动真的伤了人，故障会以哪种形态出现"。

| 改动 | 破坏性 | 谁受影响 | 失败模式 | 应对 |
|---|---|---|---|---|
| 加一个可选参数 | 通常否 | 无人（老调用不受影响） | — | 直接加，但要检查默认值是否改变语义 |
| 加一个必填参数 | 是 | 全部调用方 | 立即可见（编译失败） | 改为就地重载或新增函数名 |
| 加一个返回值字段 | 通常否 | 做了深比较的用例 | 立即可见（断言失败） | 直接加，同时检查契约测试是否用了全等断言 |
| 删除返回值字段 | 是 | 读该字段的一方 | 立即可见或偶发 | 保留一段时间并标注弃用 |
| 收窄参数类型 | 是 | 传了被排除值的一方 | 立即可见 | 改为放宽而非收紧 |
| 放宽参数类型 | 否 | 无人 | — | 直接改 |
| 收窄返回值类型 | 否 | 无人 | — | 直接改 |
| 放宽返回值类型 | 是 | 假设了具体类型的一方 | 通道丢失（调用方按旧类型继续决策） | 保留旧类型或新增函数 |
| 改默认值 | 是，隐蔽 | 所有未显式传参的调用方 | 静默（行为变了，无任何报错） | 视为行为变更，通知与迁移 |
| 改错误类型或错误信息 | 是，隐蔽 | 依赖错误类型做分支、或解析错误文本的一方 | 通道丢失 | 错误类型算契约；文本不算，但必须写明"不要解析" |
| 改副作用范围 | 是，最隐蔽 | 依赖"它不会做 X"的一方 | 静默或边界值 | 视为契约变更，守卫与权限一并复查 |
| 改时序属性（同步变异步） | 是 | 全部调用方 | 偶发 | 新增函数而非修改旧函数 |
| 放宽时序（不可重入变可重入） | 否 | 无人 | — | 直接改 |
| 收紧时序（可并发变不可并发） | 是，最危险 | 所有并发调用方 | 偶发，且测试通常测不出 | 必须有并发测试；优先改用新函数 |

#### 1.4.3 四类隐蔽改动与它们的检测方式

表里标了五处隐蔽（其中"改错误类型或错误信息"与"改副作用范围"分属两种情况），它们的共同特征是编译器不报错、测试通常也不失败，而行为已经变了。每一类的检测方式不同，需要分别处理。

改默认值影响的是那批什么都没写的调用方，而它们在代码里看起来完全正常。`timeoutMs` 从 30000 改成 60000，所有未显式传超时的调用都会变慢一倍，改动量是零行调用方代码。它的影响面可以直接数出来：用 `rg` 统计该参数在调用点被显式传入的比例，剩下的是受影响方。这是为数不多的"改动前就能算出影响面"的情形之一，不用算它属于浪费。

改错误信息之所以隐蔽，是因为错误文本常被当作不重要的文案，而实践中确实有大量代码在解析错误字符串。正确的划分是错误类型属于契约、错误文本不属于契约，而后者必须在契约里显式声明"文案可能变化，不要解析它"。缺少这句声明的后果与 Hyrum 定律描述的一致：文本会被依赖，而依赖发生的时候你不会收到通知。

改副作用范围改变的是调用方对"它不会做 X"的依赖。一个 `read_file` 工具如果某天开始把读过的路径记进一个全局缓存，那么"它是纯读的"这个依赖就坏了，而签名没有任何变化。检测它的方式是回到 1.2 的那张表：副作用必须在字段上声明等级，而等级的改动属于契约变更——这也解释了为什么 `sideEffect` 必须是字段而不是注释，字段的改动至少能在 diff 里被看见。

收紧时序是最危险的一类，因为它在测试里通常测不出来。把"可并发"改成"不可并发"，单线程测试全部通过，而生产中出现的是偶发的不一致状态，属于 1.1.3 的第三行。这也解释了为什么看一个接口的时序承诺比看它的类型更重要：类型错了编译器会拦，时序错了没有人会拦，只有当并发路径被真实触发时才会以偶发故障的形式出现。

#### 1.4.4 两次追问

工程侧的问题是为什么"放宽参数、收紧返回"是安全方向。答案可以直接从前置条件与后置条件的归属推出：放宽参数意味着接受更多输入，原先合法的调用仍然合法，也就是弱化了前置条件；收紧返回值意味着给出更具体的保证，原先成立的解析仍然成立，也就是强化了后置条件。Liskov 行为子类型化允许的正是这两个方向的组合，而反向的组合会要求调用方改变行为，因此是破坏性的。实用形式是一条口诀——参数只能放宽，返回只能收紧，其中"返回"指返回值的类型精度，新增字段不在其列，因为它的方向是给出更多信息。

产品侧的问题是破坏性变更的真正代价包含哪几项。第一项是改调用方代码的时间，它最直观也最容易被当作全部。第二项是信任损耗，每一次破坏性变更都在告诉使用者"你的代码可能会被我弄坏"，于是他们会倾向于自己做一层包装，而那层包装成为新的维护负担。第三项是历史断裂，对于有持久化数据的系统，破坏性变更可能让旧数据无法读取，而这一点是不可逆的。第三项对本课程尤其重要：事件格式的破坏性变更会让历史会话读不出来，它是唯一同时包含三项代价的改动类型，因此与会话日志相关的事件格式在第 2.7 篇会被单独处理（版本号机制与其迁移规则）。

> **面试视角**
> **高频问法**（Agent 岗几乎必问）："什么改动是破坏性变更？"判据是谁依赖了它，而不是改了什么。
> **追问方向**："改一个默认值算不算破坏性？"算，而且隐蔽，它影响的是什么都没写的调用方；这一类的检测方式是统计未显式传参的调用点比例。
> **进阶问法**："为什么事件格式的破坏性比函数接口更严重？"历史数据不会跟着改，而函数调用方可以一起改。

### 1.5 契约与波及面：把 1.2 和 1.3 接起来

前四节处理的是契约的构成、表达与改动性质。这一节回答一个更基础的问题：契约与一个系统的改动成本之间是什么关系。答案需要两份数据表，而只用其中任何一份都会系统性地判断错误。

#### 1.5.1 两份表的合取

1.3 给出第一份表：谁依赖我，按值与类型分成两组。本篇给出第二份表：我承诺了什么、谁依赖了哪一条。前者是静态依赖，后者是契约依赖。

只用第一份表会过度保守。以 `D:\dsh-mini` 的 `Session` 为例，16 个文件引用它（值 7、类型 9）。若按"这 16 个都可能受影响"决策，任何改动都显得危险，于是倾向于不动它；而这 16 个依赖的是不同部分——`src/apps/web.ts` 只依赖事件类型，`src/kernel/agent.ts` 依赖 `append` 与 `deriveMessages` 的行为，`src/evolution/diagnose.ts` 依赖 `SessionStats` 的字段。按第一份表算出的风险把三者混为一谈。

只用第二份表会过度冒险，因为它会漏掉那些没有直接引用你、但通过中间层受影响的使用者。若 `Session.append` 的"重复调用会怎样"这条承诺变了，`src/plugins/session.ts` 的转发逻辑要跟着改；而转发逻辑又影响所有订阅 `session/event` 的界面，这些界面从未 import 过 `Session`，因此不出现在任何扇入清单里。

准确的做法是两份表的合取：从被改动的那条承诺出发，先找直接依赖它的人，再沿依赖关系向上求传递闭包。

```
   改动点：Session.append 的「重复调用会怎样」这条承诺
        │
        ├─ ① 谁读了这条承诺？（第二份表：契约依赖）
        │     ├─ src/kernel/agent.ts        ← 直接调用 append
        │     └─ src/plugins/session.ts     ← 转发它
        │
        └─ ② 那些人又被谁依赖？（第一份表：扇入闭包）
              ├─ plugins/session 被 → apps/web.ts、apps/repl.ts 依赖
              └─ 而这两个把事件推给「界面」
                    ↑ 界面从未 import 过 Session，但它们会受影响

   结论：真实波及面 = {agent, plugins/session, apps/web, apps/repl, 界面}
        不是「16 个引用它的文件」，也不是「2 个直接用它的人」
```

这张图的关键线索在第二次扩张：直接依赖者只有两个，而真实波及面有五个以上，多出来的部分全部来自依赖的传递。因此"我 import 过什么"与"我会被什么影响"是两个不同的问题，前者可以用 `rg` 回答，后者需要顺着契约链走一遍。

#### 1.5.2 契约表面积：一个可以主动缩小的量

由上一节可以推出一个概念：契约表面积，指一个模块对外承诺的事项总数。它的用处在于波及面的大小与它成正比——承诺越多，被依赖的面越广，改动时受影响的人越多。

表面积可以数。做法是遍历一个模块对外的三处表达：类型上暴露的成员（每个成员的语义都是一条潜在承诺）、文档里出现的保证句（含"保证""必须""永远""不会"这类词的句子）、以及运行时的强制检查（断言与校验点，它们把承诺固化成了可观测行为）。三处之和就是表面积的下界，实际值通常更大，因为还有一部分承诺从未被写出来却已被依赖（0.3 节的 Hyrum 情形）。

这个概念的价值在于它可以被主动缩小，而缩小的方式不是删功能，而是把不必要的承诺移出契约。三种做法各有其适用条件。收窄承诺适用于那些"只有一种偏门用法需要"的细节：一个返回对象若既承诺内容又承诺字段顺序，而调用方并不按位置解析，那么显式声明"顺序不构成承诺"就把这份表面积移了出去。合并承诺适用于那些可以抽象成一个更宽保证的多条承诺：`ToolResult` 若承诺"包含 text、isError 以及可能的 metadata"，那是三条；若承诺"包含 text 与 isError，其余字段属于实现细节"，那是一条半，代价是调用方知道的更少。引入适配层适用于变化的部分比较集中的情形：用一个稳定的窄接口面对使用者，把易变部分藏在适配层后面，这在本质上是用一层间接把表面积从"实现的总和"缩小到"接口的承诺"，第 2 卷的作用域与装配会用这个手段。

#### 1.5.3 深模块与浅模块：用表面积重新表述的判据

Ousterhout 在《A Philosophy of Software Design》里提出一组对比：深模块是接口简单而内部复杂的模块，浅模块是接口复杂而内部几乎没做什么的模块。用本节的词汇可以把它重新表述成一句可判断的话：深模块是契约表面积小而实现量大的模块，浅模块是契约表面积大而实现量小的模块。

这个表述让"为什么浅模块是坏的"变得具体：它把复杂度暴露给了调用方，却没有换来封装收益。调用方不仅要理解这个模块做了什么，还要理解它的每一条承诺；如果那些承诺只是转发或琐碎操作，那么这些理解成本没有换回任何东西。

`D:\dsh-mini` 里有一个可以对照的例子。`src/apps/shared-mode.ts` 提供模式装配的钩子工厂，导出很少（一两个函数），而它背后的逻辑涉及 `loadModes`、`parseModeDecl`、`applyMode`、行变换与插件配置的生成。这是深模块：调用方只需要知道"给我一个装载钩子"，不需要知道模式是怎么解析的。反过来，一个模块若导出七八个细碎函数而它们各自只是转发到别处，那它就是浅的。判断方法沿用 1.3 的"读导出列表"：如果每一项都能用一句话说清、且合起来没有构成一个更大的概念，那它多半是浅的。

#### 1.5.4 两次追问

工程侧的问题是收窄承诺会不会让使用者难以使用。确实有这个风险：收窄意味着调用方知道的更少，如果它确实需要那些信息，它会转向两种替代方案——读实现（脆弱，实现一改就坏）或自己补一层（增加代码量）。因此收窄的判据不是"能收就收"，而是这条承诺使用者是否真的需要，而判断依据是"有几种合理的使用方式需要它"：只有一种偏门用法需要它时，它不该进契约，而应由那个特殊使用者自己处理。

产品侧的问题是承诺少为什么是一种产品优势。因为承诺少意味着演进自由：接口只承诺核心行为时，实现方式、性能特征、内部结构都可以随时改进而使用者不会察觉；这在产品上表现为一项实际能力——持续改进而不打扰使用者。反过来，承诺过多的接口会变成化石，它冻结所有被承诺过的行为，包括那些当初顺手实现的。这个权衡在 harness 上有具体形态：`Provider` 接口的承诺应恰好包含"调用模型并返回结果"，不应包含"结果里的 usage 字段一定有某几个"——不同 provider 能提供的 usage 不同，把它写进承诺会迫使 `MockProvider` 填假数据，而那会污染统计链路。

> **面试视角**
> **高频问法**："你怎么评估一次改动的影响面？"不要只答"看谁 import 了它"，要说清两张表的合取：谁依赖了这条承诺，加上扇入的传递闭包。
> **追问方向**："只算扇入会怎样？"过度保守，把只依赖类型的地方也算成风险；"只算契约依赖呢？"过度冒险，漏掉通过中间层受影响的界面。
> **对应岗位**：后端技术面、架构评审环节。

### 1.6 版本化与弃用：在不破坏承诺的前提下演进

前两节解决"判断危不危险"，这一节解决"危险时怎么做"。四种手段按代价从低到高排列，而选择的顺序不能颠倒，因为代价是递增的。

#### 1.6.1 手段一：加而不改

最便宜的手段是只增加、不修改：加可选参数、加返回字段、加新函数，都不破坏已有承诺。它的适用边界很窄，只有当新需求可以通过增加来表达时才可用。如果新需求要求改变已有行为（例如"默认超时应该是 60 秒而不是 30 秒"），这个手段用不上，因为问题的本质是旧行为需要变。

这个手段最常见的误用是加一个开关来切换新旧行为。它看起来是"加而不改"，实际上把一次破坏性变更变成了一份长期维护负担：两个行为都要维护，而使用者不知道该用哪个。开关只在一种情况下值得使用——它是临时的迁移通道，并且有明确的移除时间。

#### 1.6.2 手段二：放宽而非收紧

第二种手段是让契约朝宽松的方向改：放宽参数类型、放宽输入约束、增加可接受的输入形态，这些都不会让已有调用失效。它的依据是 1.4.4 那条口诀的方向性来源——弱化前置条件、强化后置条件是 Liskov 行为子类型化允许的方向。

它的用途是改变提问方式：当你想收紧某个约束（例如"这个参数以后必须是正整数"）时，先问"能不能通过放宽别处达到同样目的"。多数情况下答案是能，因为你想要的结果往往不是"拒绝非法输入"，而是"对非法输入也有合理行为"——后者可以通过定义更宽的合法域来达成，而它不破坏任何已有调用。

#### 1.6.3 手段三：兼容层

当新需求确实要求改变已有行为时，第三种手段是保留旧路径作为兼容层，同时提供新路径：旧函数保留、新函数另起名字、旧函数内部改为调用新函数，并在可能时给出弃用警告。使用者因此可以按自己的节奏迁移，而不是被迫同时改。

兼容层的代价是真实的，而且必须被明说：它会长期存在，出现在每一份文档、每一次搜索、以及每一个新人的理解成本里。所以它必须配一个移除条件，条件不是"以后再说"，而是"当 X 发生时移除"。三种常见写法的代价也不同——写在旧函数里让使用方无感，但旧函数的实现变成适配代码、其文档要同时描述两种行为；写在新函数里让新代码携带历史包袱；写在独立的适配模块里两边都干净，但多出一个模块，它本身成为新的依赖中心。默认推荐第一种，因为收益最大而代价集中在一处；唯一的限制是当旧函数与新函数在语义上真的不同（不只是参数形式不同）时，第一种做法会产出"看起来是旧函数、行为却变了"的东西，那比直接改更糟。

会话格式的版本机制是这一手段的正面例子，也是 harness 与普通库的分界线所在。它没有直接改事件格式，而是引入 `SESSION_FORMAT_VERSION` 并规定只有结构性的格式改动才允许升版本，同时规定已经提交的世代不允许被移动或覆盖。`D:\dsh-mini` 之后的版本沿用了这套规则，而同构的做法在 dsh 体系的架构文档里写得更完整：SQLite 侧用单调递增的 `SCHEMA_VERSION`，相邻迁移可以新增一个以版本命名的后继实现，但绝不回写或删除已提交的世代，并且前代既不意味着回退支持、也不意味着降级支持。把这三条放在一起看，它把"格式演进"从一次破坏性变更变成了有版本记录的变更：历史数据仍可读，而新代码知道自己面对的是哪一代。

#### 1.6.4 手段四：版本化

第四种手段最重：给接口一个版本号，让新旧版本并存。它适用于两种情况——使用者无法协调（外部依赖、跨团队），或者改动频繁到兼容层跟不上（每次改动都加一层，层数失控）。它的代价也最高，因为它引入一整套机制：版本选择、协商、每个版本都要测的测试矩阵，以及最终仍然要面对的下线问题。所以它是最后手段而不是默认做法。

对 harness 有一处特殊性：事件格式的版本化是必要的，函数接口的版本化通常不必要。区别的依据是使用者是否被时间分隔——函数的使用者是同一时刻的代码，可以一起改；事件的使用者包括未来的代码与已经落盘的历史数据，它们不会跟着你改。

#### 1.6.5 弃用周期：三个阶段，缺一个都不完整

无论用哪种手段，一个完整的演进过程都包含三个阶段，每个阶段对应一类不同的失败。

| 阶段 | 做什么 | 省掉它会怎样 |
|---|---|---|
| 标注弃用 | 在文档与（可能时的）运行时警告里写明"这个会移除，替代品是 X" | 使用者没有时间发现，移除变成突袭 |
| 并存期 | 新旧同时可用 | 使用者被迫与你的改动同步，迁移变成中断 |
| 移除 | 删掉旧路径 | 弃用成本永久保留，且不再有人知道它的理由 |

并存期的长度是一个真正的判断，依据是使用者从得知到完成迁移需要多久。只有你自己的项目里可以短到下一次提交；有外部使用者时可能是几个月。判断依据是使用者的迁移成本，不是惯例。

#### 1.6.6 两次追问

工程侧的问题是兼容层应该写在哪里，三种选择的代价已在 1.6.3 列出，默认选择是写在旧函数里。这个默认值有一条边界条件值得重复：语义真的不同时不能这么做，否则会产出行为已经改变的旧函数，那种情形下应当另起名字并保留旧的语义。

产品侧的问题为什么"移除"这一步不能省。因为弃用而不移除会让成本永久保留，而这是最容易被拖延的一步——它没有立即收益（移除不会让任何新功能可用），成本又是隐性的（理解成本、文档成本、测试成本）。判断可以量化：如果一条旧路径让每一份相关文档都变长、让每一次搜索都多出无关结果，那么它的成本每天都在发生。相应地，"当初为什么兼容"这个理由必须被重新评估，因为它在并存期结束时往往已不成立——那个使用者可能早已迁移，那个功能可能已无人使用。

> **面试视角**
> **高频问法**："你怎么做一个不破坏使用者的接口升级？"四种手段按代价递增：加而不改、放宽而非收紧、兼容层、版本化。
> **追问方向**："兼容层打算什么时候删？"答不出就说明它是永久负担，这一问在面试里几乎是标准收尾。
> **加分点**：指出"对历史数据（事件格式、持久化 schema）只能从版本化起步"，因为"加而不改"对不会自己更新的旧数据无效。

### 1.7 高级规则应变手册

这一节是可以在接口设计与评审时随手查阅的规则手册。每条规则给出症状、可能原因、确认动作、处置动作，以及什么时候不要用这条规则——最后一项是唯一能防止规则被误用的部分。十四条规则分四组：读契约、写契约、改契约、评审契约。

#### 组一 · 读契约（C-01 至 C-04）

C-01｜症状：用别人的接口，但不确定能不能这样用。 可能原因是契约不完整（缺时序或错误承诺）。确认动作是做三个尝试性提问："失败时它会抛异常吗"、"我能并发调用它吗"、"调用它两次效果一样吗"。若这三个问题在文档里都找不到答案，那不是使用者的问题，而是契约的缺口。处置动作是在被卡住的位置读实现，并在解出答案之后补一条注释——你花掉的时间，是下一个人不必再花的。不要这么做：如果你只想知道返回什么类型，类型签名就够了，不需要读实现。

C-02｜症状：某个行为看起来很奇怪，不知道为什么这么设计。 可能原因是它是一条承诺的副作用。确认动作是构造反事实："如果它不是这样，会出什么问题？"真实例子是 `Session.events` 返回内部数组的引用而不是副本：反事实是返回副本会让每次取事件都复制整个数组，而一条长会话可能有上万条事件。处置动作是把你找到的理由补进契约，因为它下次还会让人困惑。不要这么做：如果反事实只是"会慢一点"，那可能真的只是没优化，不是所有奇怪都值得解释。

C-03｜症状：不确定某个行为算不算承诺。 可能原因是没有任何标志告诉你。确认动作是看三处：文档里有没有"保证""必须""永远"这类词、有没有对应的测试、有没有实现里的显式检查。三处都没有时默认判断是"它不是承诺"，但按 Hyrum 定律它仍可能被依赖。处置动作是把它明确标注为"实现细节、不要依赖"。不要这么做：如果使用者已经依赖了它且改动会伤害他们，那么标注"不是承诺"并不会让伤害消失——此时它是一个事实上的承诺，需要按承诺处理（迁移方案）。

C-04｜症状：文档说了一套，实现是另一套。 可能原因是文档过期，或者实现有缺陷。判断是哪一种很重要，因为修法相反。确认动作是找一个最小用例跑一下看实际行为。处置动作：实现对而文档过期就改文档；文档对而实现有缺陷就不要改文档去迁就实现，那会让契约悄悄退化。不要这么做：有时两者都错（文档写的不是想要的，实现也没做到），此时先决定想要的到底是什么。

#### 组二 · 写契约（C-05 至 C-08）

C-05｜症状：你写了接口，而使用者仍在问"这个怎么用"。 可能原因是遗漏了时序或错误承诺。确认动作是让对方提三个问题，然后看你是否每个问题都要翻代码才能回答——两个以上需要翻代码就是契约缺口。处置动作是补进文档而不是口头回答，口头回答的那个"契约"会随你离开而消失。不要这么做：如果对方问的是"这个业务逻辑为什么这样"，那是需求问题，不是契约问题。

C-06｜症状：不确定某个细节该不该写进契约。 判断标准只有一条：它是使用者必须知道的事情吗，其中"必须"指不知道它就无法正确使用。举例：一个 `run_command` 工具，"超时后进程树会被终止"是必须知道的（否则使用者会自己再杀一次），而"超时后返回的错误信息里包含耗时"是可有可无的。处置动作是必须知道的进契约，可有可无的进"实现细节"说明。不要这么做：不确定时倾向于不写，因为写错的契约比不写更难改。

C-07｜症状：接口看起来很小，但每个实现都写了很多样板。 可能原因是接口把"实现者必须自己处理的细节"暴露了出来。确认动作是数一下实现一个工具平均要写多少行与业务无关的代码，超过一半说明接口位置不对。处置动作是把共性提到接口层，例如把参数校验从每个工具移进注册表（2.2 的 `run` 五步就是这种提法）。不要这么做：如果那些"样板"各不相同（每个工具都有自己的前置检查），它们不是样板而是真实的差异，此时不该合并。

C-08｜症状：想给接口加一个字段，但不确定它会不会成为负担。 确认动作是 0.1 节那个问题：这个字段要成为承诺的一部分吗。若是，所有实现者都要遵守、所有消费者都可以依赖；若不是，它不该出现在接口上，而应由需要它的一方自己维护映射。处置动作是先按"不是承诺"设计，只有在出现第二个需要它的使用者时才提升为接口字段。不要这么做：如果这个字段与安全性或正确性相关（例如 `sideEffect` 等级），它必须进接口而且必须被强制，因为"某些实现没填"会让守卫的判断不成立。

#### 组三 · 改契约（C-09 至 C-12）

C-09｜症状：你要改接口，但不知道会不会打破别人。 处置动作是查 1.4.2 的分类表，再用 1.5.1 的两表合取算出真实波及面，两步都要做：分类表说明这类改动通常危不危险，两表合取说明在你的系统里危不危险。不要这么做：当改动是"收窄时序"时，分类表会警告它危险，而两表合取会低估它，因为并发问题不体现在静态依赖上，此时唯一可靠的办法是找并发测试。

C-10｜症状：你想加一个开关来同时支持新旧两种行为。 可能原因是你在避免一次破坏性变更。确认动作是问"这个开关打算什么时候删"。处置按答案分支：有明确期限的灰度则保留；为兼容某人且无期限则改为兼容层加弃用标注；"我不想改原逻辑"属于回避，停下来先理解原逻辑。不要这么做：改动确实影响线上且没有回滚手段时，开关是必要的安全网，这不是回避。

C-11｜症状：接口要演进，但不知道该用四种手段里的哪一种。 处置动作是按改动方向选择：能用"加"就用加；需要改行为先试"放宽"；必须换行为就做"兼容层"；使用者无法协调时才"版本化"。判断顺序不能颠倒，因为代价递增。不要这么做：当使用者是未来代码时（事件格式、持久化数据），直接从版本化开始，因为"加而不改"对历史数据无效。

C-12｜症状：兼容层已经存在很久，没人记得为什么。 可能原因是它当初的理由已不成立。确认动作是找它的移除条件：没写就是缺陷，写了就检查条件是否满足。处置动作是评估移除（用 C-01 判断还有没有人在依赖），或者补写移除条件。不要这么做：当它是安全相关的兼容（例如旧格式解析里保留的数据校验）时，不要因为"看起来没人用"就删，安全的兼容层值得永久保留。

#### 手册的使用方式

与前几篇相同：遇到具体卡点时查，不要从头读。这份手册的补充时机是——当你遇到一个它没覆盖的契约问题并用时间解决了它之后，就按同样的六项格式补一条，尤其是最后一项，因为它是防止规则被误用的唯一部分。

> **面试视角**
> **用法**：这一节不是用来背的，是用来在面试现场想不起某个取舍时定位自己的。
> **典型场景**：面试官说"那如果并发呢"则查 C-09；说"那你加个开关吧"则查 C-10；说"这个字段你怎么保证"则查 C-08。

## L2 决策表

本篇的决策围绕同一件事：一个接口该承诺什么、承诺到什么程度、以及怎么改。每一行给出选择、替代方案，以及代价落在谁身上——最后一列是这张表的用法所在，因为一个决策的好坏取决于它的代价由谁承担，而不取决于它看起来是否优雅。

| # | 决策 | 选择 | 替代方案 | 代价落在谁身上 |
|---|---|---|---|---|
| 1 | 契约的粒度 | 恰好包含"不知道就无法正确使用"的部分 | 尽量多写 / 尽量少写 | 使用者要在文档里找答案；换来演进自由 |
| 2 | 是否声明"这不是承诺" | 显式声明 | 不写（默认会被依赖） | 写文档的人多写一句；换来将来能改 |
| 3 | 强制型还是信任型 | 按"违反后果"选，安全相关强制、其余信任 | 一律强制 / 一律信任 | 实现者多写样板；换来安全 |
| 4 | 契约表达在哪 | 文档、类型、断言、测试四处各司其职 | 只写在文档里 | 实现者要多写断言；换来问题早暴露 |
| 5 | 破坏性变更的处理 | 按代价递增选四种手段 | 每次都加兼容层 | 后来的维护者要维护多条路径 |
| 6 | 兼容层的存在期限 | 写明移除条件 | "以后再说" | 全体承担永久理解成本 |
| 7 | 是否版本化 | 只在"使用者受时间分隔"时用 | 一概版本化 | 测试与文档承担版本矩阵成本 |
| 8 | 契约测试的断言方式 | 断言承诺（含而不等） | 断言实现输出（全等） | 重构者承担全等断言带来的改动成本 |
| 9 | 不变量检查的位置 | 按"症状离病因的距离"决定 | 一律放测试 / 一律上热路径 | 在性能与定位精度之间取舍 |
| 10 | 错误的粒度 | 与调用方的决策点对齐 | 一种笼统错误 / 极细分类 | 粒度过粗或过细时调用方写不出正确的错误处理 |
| 11 | 谁写契约 | 实现者写初稿，使用者补漏 | 只由实现者写 | 实现者要主动收集使用者的疑问 |
| 12 | 契约变更的通知 | 变更时主动告知依赖者 | 靠对方自己发现 | 变更发起者花时间；换来不突袭 |
| 13 | 内部状态的暴露 | 明确所有权，或返回副本 | 直接返回内部引用 | 调用方要遵守未言明的约定 |
| 14 | 契约的评审时机 | 在实现之前评审接口 | 实现完之后评审代码 | 评审者提前介入；换来改动成本最低 |

其中三条值得展开，因为它们各自避免了一类常见错误，而这三类错误在真实项目里出现的频率很高。

### 关于第 3 条的完整论证（强制型与信任型的边界）

强制型契约是框架能检查并阻止违反的，它的实现手段是类型系统与运行时校验；信任型契约是框架无法检查、只能依赖约定与人为判断的。两者的分界线不是"重要不重要"，而是违反的后果与检查的可行性同时决定的结果。

| 违反后果 | 应当采用 | 例子 |
|---|---|---|
| 安全事件、数据损坏 | 强制型 | "声明为只读的不得写入"——若它写了，权限判定就形同虚设 |
| 静默的行为不一致 | 强制型（成本可接受时） | "同一事件类型不能有两种结构" |
| 可读性、风格 | 信任型 | "函数名用动词开头" |
| 性能特征 | 信任型 | "这个方法预期是 O(1)" |

`D:\dsh-mini` 的 `Tool.sideEffect` 属于第一行，而它目前是信任型，这是本篇在 L3 会记录的一处真实缺陷。值得展开的是它的修法，因为修法不是"把它改成强制型"——静态检查一个函数会不会写文件做不到，写操作通过库调用发生，而判断一个任意函数是否会触达文件系统需要跨过程分析，且结论依赖于运行时参数。

可行的折中是把"检查"换成"限制能力"：在只读等级下，框架用沙箱把工作区挂为只读，这样即使工具声明错了，它也没有能力写。这个折中带来一个可以推广的模式：当一条契约无法被检查时，有时可以通过限制能力达到同样的效果——沙箱、权限位、资源配额都属于这一类。它与检查的区别在于代价的分配：检查在违反发生时报告，限制让违反无法发生，而后者要求框架能控制被限制的资源。由此得到一条判据：契约的表达方式取决于系统能不能控制那条承诺涉及的能力，能控制就用限制，不能控制才退回到约定与检查。

### 关于第 8 条的完整论证（为什么契约测试不能全等断言）

这一条纠正一个常见且代价很高的做法。考虑一个返回统计对象的接口，实现返回 `{ turns: 3, steps: 12, toolCalls: 5 }`。全等断言写成对整个对象做深度相等比较，契约断言写成分别断言三个字段的值。两者的差别在一个具体场景里显现——当你后来给统计加了一个字段 `cachedTokens`。下面十行代码把两种断言的结果并排放在一起：

```js
const stats = { turns: 3, steps: 12, toolCalls: 5, cachedTokens: 99 }  // 实现新增了字段

// 全等断言：把实现的具体输出当作契约
const strict = { turns: 3, steps: 12, toolCalls: 5 }
console.log('全等断言通过：', JSON.stringify(stats) === JSON.stringify(strict))   // false

// 契约断言：只断言承诺过的字段与其类型
const promised = ['turns', 'steps', 'toolCalls']
console.log('契约断言通过：', promised.every((k) => typeof stats[k] === 'number')) // true
```

输出是 `false` 与 `true`。全等断言的测试失败了，尽管没有任何调用方会因此受影响——多一个字段不破坏任何承诺。于是你必须去改测试，而改测试的过程会让人产生"这个改动有风险"的错误印象；如果团队的习惯是"测试挂了就改测试"，那么这个断言实际上不再保护任何东西，它只会在每次实现结构变化时产生噪声。

契约断言不会失败，因为断言的正是承诺本身。所以两者的区别不是风格，而是测试在保护什么：一种保护契约，另一种锁死实现。这条规则有一个例外需要写清：对"必须精确"的接口，全等断言是正确的——例如序列化格式的测试必须断言输出的字节完全一致，因为格式的每一位都是承诺。判断自己处在哪种情形的方法是问：如果实现多输出或少输出了一个不影响调用方决策的东西，测试应该失败吗。

### 关于第 9 条的完整论证（不变量检查放在哪里）

判据在 1.3 给过：按"症状离病因的距离"决定。这里补上它的量化形式，因为这条判断在真实项目里经常被"性能"两个字打断。

设一次断言的成本为 `c`（例如 10 毫秒），它防止的那类问题一旦发生、定位成本为 `d`（例如 4 小时），该问题在开发过程中的出现概率为 `p`（例如每二十次改动出现一次），两次问题之间执行断言的次数为 `n`（例如一百次任务）。

放热路径的收益侧是每次改动分摊到的定位成本 `p × d`，成本侧是每次改动分摊到的断言开销约 `n × c`。代入上面的数字：收益侧是 `(1/20) × 4 小时 = 12 分钟`，成本侧是 `100 × 10 毫秒 = 1 秒`。结论是热路径明显合算。

这个估算的用途不是得出精确结论，而是把"要不要加断言"从直觉问题变成可以估的问题，而它的两个输入都可以凭经验估计——你只需要问"这类问题出现过吗、多久一次、上次查了多久"。当收益侧与成本侧接近时，默认选择是把断言留在测试里，因为热路径上的断言会长期消耗每一次任务的预算，而测试的成本只支付一次。

> **面试视角**
> **高频问法**："你怎么决定一个接口承诺多少、边界在哪？" L2 的十四条决策就是这套判断的完整清单。
> **追问方向**："如果两个方案都有代价，你怎么选？"落点是说清代价落在谁身上，然后给出你的选择——"两种都可以"在面试里通常会被追问到底。
> **加分点**：能把断言位置说成一道估算题（`p × d` 与 `n × c` 的比较），而不是"看情况"。

## L3 实现（案例逐段解析）

这一节是一次完整的契约审计，对象是 `D:\dsh-mini` 的三个核心接口。它们分别代表契约的三种典型形态，而对三种形态的要求并不相同。

| 接口 | 契约形态 | 难点 |
|---|---|---|
| `Tool`（`src/kernel/tools.ts`） | 面向第三方实现 | 实现者与调用者不是同一批人，任何未写明的期望都会变成隐患 |
| `Provider`（`src/kernel/llm.ts`） | 面向替换实现 | `MockProvider`、`LocalProvider`、`DeepSeekProvider` 必须真的可替换 |
| 会话事件（`src/kernel/session.ts`） | 面向未来代码 | 已写入日志的事件必须永远能被后续版本读懂 |

审计固定为四步，它在任何一个接口上都能用，每一步的产出物都不同。

```
① 列出签名能表达的部分 —— 产出：类型清单
② 对三类承诺逐条问"写清了没有" —— 产出：缺口清单（按行为/时序/错误分类）
③ 列出不变量并为每条找证据来源 —— 产出：无证据的条目（断言/测试/文档三选一）
④ 对照"承诺"与"谁有能力兑现它" —— 产出：信任型契约清单
```

第 ④ 步是最容易跳过的一步，也是这类审计里唯一能发现安全问题的步骤。它的问法是：这条承诺，实现方有能力保证吗；如果答案是"我们只能相信写的人说的是真的"，那它就是信任型契约。

### 3.1 审计对象一：`Tool` 接口

#### 3.1.1 契约清单

```ts
export interface Tool {
  readonly name: string
  readonly description: string
  readonly params: ParamSchema
  readonly sideEffect: 'read' | 'workspace-write' | 'irreversible'
  execute(args: Record<string, unknown>, ctx: ToolExecContext): Promise<ToolResult>
}
```

| 类别 | 承诺内容 | 写在哪里 | 完整吗 |
|---|---|---|---|
| 行为 | 工具的名字、描述、参数 schema | 类型（强） | 完整 |
| 行为 | `sideEffect` 声明它会不会改动持久状态 | 类型 + 注释 | 声明完整，但无从验证（见 3.1.3） |
| 行为 | `execute` 返回 `ToolResult`（含 `isError`） | 类型 | 完整 |
| 时序 | 同一个工具能否被并发调用 | 无处 | 缺口 |
| 时序 | 工具执行期间能否修改注册表 | 无处 | 缺口 |
| 时序 | `execute` 有没有超时，谁负责超时 | 无处 | 缺口 |
| 错误 | 抛异常与返回 `isError: true` 的区别 | 无处 | 缺口 |
| 错误 | 参数校验失败时由谁负责 | 部分（`validateArgs` 的存在暗示框架） | 不明确 |
| 边界 | 工具可以使用哪些上下文（能否改会话、能否发事件） | `ToolExecContext` 的类型 | 完整 |

这张清单里有一列值得单独看：写在哪里。前六行中有四行写着"无处"，而它们的类型都完整（`execute` 的签名本身没有问题）。这正是"签名是契约的低信息量投影"在真实接口上的样子——类型标注齐全，而使用者仍然不知道能不能并发、超时归谁管、失败用哪种形式表达。

#### 3.1.2 三处缺口的具体后果

第一处是错误表达有两种方式，但没有规则说明用哪一种。工具可以 `throw`，也可以返回 `{ isError: true }`，而这两种在框架侧的后果不同：抛出的异常向上传播到循环，`isError: true` 则作为工具结果反馈给模型。也就是说，同一个失败写成两种形式会让模型看到完全不同的东西——一种是"工具调用失败"（可能触发重试），另一种是"工具调用成功而结果是错误信息"（模型会尝试别的办法）。工具作者的选择因此直接影响模型行为，它不是实现细节，而是一条必须写明的契约。

第二处是并发语义未定义。两个工具调用能否同时执行，在当前的实现里答案是"不能"，因为循环顺序执行——但"当前实现恰好如此"不等于"契约如此"。如果将来为了性能改成并行执行（对线程安全的工具来说这是合理的优化），那么所有假设自己独占工作区的工具都会出问题。契约在这里的价值是让未来的改动知道自己的边界在哪，而边界不存在时，它只能靠"没人敢改"来维持。

第三处是超时的责任归属未定义。一个工具如果永远不返回会发生什么，框架有没有超时——从 `ToolExecContext` 提供了 `signal`（取消信号）这一点可以推断"框架会取消，工具应当响应"，但这是一条被推断出来的契约，而不是被写下的。推断型契约的性质与 0.3 节那段反例相同：推断成立与否取决于读者，而不同的读者会推出不同的答案。

#### 3.1.3 一处"承诺了但能力上做不到"的发现

`sideEffect: 'read'` 在注释里的含义是"守卫依据它裁决放行 / 询问 / 拒绝"，也就是说声明为 `read` 的工具会被自动放行。这构成一条承诺：如果这个工具声明为 read，那么调用它是安全的、不需要询问。

而框架没有任何机制验证这个声明。一个工具声明 `read` 而在实现里写了文件，守卫会照样放行。这条承诺的实际强度因此是"工具作者说的是真的"。这个发现分三层。

第一层，它是一个真实的安全缺口而不是理论问题。当工具来自不可信来源时（第 5 卷要接的 MCP 工具、或自进化生成的工具），它可以用一个错误的声明换来无审批的写权限。

第二层，修法不是"加校验"而是"限制能力"。静态判断一个函数会不会写文件做不到——写操作通过库调用发生，判断它是否触达文件系统需要跨过程分析，而且结论依赖运行时参数。可行的做法是让声明与沙箱等级联动：声明 `read` 的工具在只读沙箱下执行，于是即使它想写也没有能力写。这个模式在 1.2.1 与 L2 第 3 条里已经出现过，两处的表述互补——做不到"验证它是真的"，就做到"即使是假的也没关系"。

第三层，这个缺陷的存在证明了契约审计这一步的价值。只看类型时（`sideEffect` 是一个联合类型的字段，看起来很严谨），你会认为这个契约是完整的；只有把"承诺"与"谁有能力兑现它"对照起来，缺口才显现。

### 3.2 审计对象二：`Provider` 接口

#### 3.2.1 可替换性检查

```ts
export interface Provider {
  readonly name: string
  chat(messages: readonly ChatMessage[], options?: ChatOptions): Promise<ChatResponse>
}
```

替换实现的契约有一个直接的检查方式：用一个实现替换另一个，看调用方能否察觉。本项目有三个实现，因此这项检查是现成的。

| 检查项 | Mock | Local | DeepSeek | 调用方能否察觉 |
|---|---|---|---|---|
| `chat` 的返回结构 | 有 | 有 | 有 | 不能察觉 |
| `usage` 字段齐全度 | 部分 | 部分 | 完整 | 能察觉（统计缺数据） |
| 流式返回能力 | 无 | 无 | 有 | 不能察觉（接口没有流式方法，不构成泄漏） |
| 失败时的错误类型 | 自定义 | 自定义 | 网络错误 | 能察觉 |

四行里有两行是真实的契约泄漏，第三行不是——接口本来就没有流式能力，所以"DeepSeek 支持而 Mock 不支持"不构成泄漏，它只是实现能力差异，而且因为接口没有把这项能力暴露出来，调用方无从未经接口使用它。

#### 3.2.2 两处泄漏的分析

`usage` 字段齐全度的泄漏。`ChatResponse` 里有 `usage`，而不同实现能提供的字段不同。如果调用方（例如统计插件）假设 `usage.cachedTokens` 一定存在，那么在 Mock 或 Local 下它会拿到 `undefined`。修法是让契约表达"可以不完整"：把 `usage` 的字段标注为可选，并要求消费者处理缺失，而不是让每个实现填假数据——填假数据更糟，因为它会污染统计链路，而统计链路是 3.6 篇成本度量的输入。

错误类型的泄漏。重试逻辑需要判断"这个错误可重试吗"，而如果 Mock 抛出的错误与 DeepSeek 抛出的错误类型不同，那么重试逻辑就必须知道"当前是哪个 provider 在跑"，它因此不再可替换。修法是在接口层约定错误分类：provider 的契约写明"失败时抛出 `ProviderError` 并带上 `retryable` 标记"。本项目在 `src/kernel/llm.ts` 里做了错误分类的工作，但没有把它写进 `Provider` 的契约文档——分类存在，而"所有实现都必须按这个分类抛错"这条承诺没有被写下，因此它仍是一条依赖实现的约定。

#### 3.2.3 两次追问

工程侧的问题是可替换性为什么比类型兼容更强。因为类型兼容只保证能编译，可替换性要求行为等价。`MockProvider` 与 `DeepSeekProvider` 可以有相同的签名而完全不同的行为：前者立即返回，后者需要几秒；前者永不失败，后者会限流。这些差异对调用方可见，因此它们属于契约。可替换性的实用检查是用一个替代实现跑全部测试：如果测试在 Mock 下通过而在真实实现下失败，那么测试依赖了某个实现特有的行为，而那个行为是一条未被表达的契约。本项目的双轨测试正是这项检查的实现——`verify.ts` 用 Mock 跑，`test:e2e` 用真实 API 跑，两者的差值就是契约泄漏的量。

产品侧的问题是可替换 provider 为什么算产品能力。它决定三件事：成本可控（换到便宜的实现不改上层）、离线可用（Local 实现在无网络时代替远程实现，能力下降但系统仍可用）、可测试（Mock 让验证不花钱）。三件事都属于"用户能信任这个系统"的组成部分，其中第二件把一个硬故障（断网即完全不可用）降级成了能力退化。

### 3.3 审计对象三：会话事件契约

#### 3.3.1 为什么它的契约形态最特殊

前两个接口的使用者是同一时刻的代码，而事件契约的使用者包括尚未写出的代码——未来的恢复工具、分析脚本、格式迁移器。这个差别带来两条独特约束。第一，它不能通过"改调用方"来完成演进：函数接口变了可以把所有调用点一起改，而事件格式变了，已经写入磁盘的历史不会跟着改。第二，它的使用者无法被列举，因此不能用"谁依赖了这条承诺"来判断改动风险，那个集合是开放的。

#### 3.3.2 契约清单

| 类别 | 承诺内容 | 证据 |
|---|---|---|
| 行为 | 每条事件有 `seq`，不跳号、不重号 | 实现（`append` 里递增） |
| 行为 | `seq` 与数组长度一致：`events.length === nextSeq` | 实现保持一致，无断言 |
| 行为 | `turn/start` 与 `turn/end` 之间的 step 编号从 1 开始 | 实现 |
| 时序 | 事件只能追加，不能修改或删除 | 实现（数组只 push） |
| 时序 | turn 之间不交错（一个 turn 结束后才开下一个） | 实现（循环顺序执行） |
| 错误 | 未知事件类型如何处理 | 无处（关键缺口，见 3.3.3） |
| 边界 | 表面事件与过程事件的区分 | `SURFACE_EVENT_TYPES` 常量 |

这张表里"证据"一列给出的都是实现，而实现不是证据的一种：它只说明当前行为是什么，不说明这条承诺会被保持。契约审计要求的是断言、测试或文档三者之一，因为只有它们能在实现被改动时发出信号。

#### 3.3.3 最关键的一处缺口与它的解法

`SessionEventMap` 的成员在读取时是必需的（required-on-read）：一个不认识某个事件类型的构建会拒绝读取包含该事件的日志。这条规则能在很大程度上防止"新代码读老日志"出错，但它同时意味着无法在不破坏兼容性的前提下添加新事件类型——老版本的代码读到新事件会直接拒绝整份日志。而添加新事件类型恰恰是最高频的一种演进：上下文压缩要加 `session/compaction`，持久化恢复可能要加 `session/resumed`。

下面这段模拟展示了缺口的表现形式。它不依赖本项目代码，只演示规则本身。

```js
// 老版本的读取器：只认识两种事件类型
const KNOWN = new Set(['session/user', 'session/assistant'])
function readV1(events) {
  for (const e of events) {
    if (!KNOWN.has(e.type)) throw new Error(`不认识的事件类型：${e.type}`)
  }
  return events.length
}

const log = [
  { type: 'session/user', text: '你好' },
  { type: 'session/compaction', at: 1 },   // 新版本写入的事件
  { type: 'session/assistant', text: '在' },
]
try { readV1(log) } catch (err) { console.log('读取失败：' + err.message) }
```

输出是 `读取失败：不认识的事件类型：session/compaction`。老版本因此无法读取整份日志，尽管其中只有一条它不认识的事件。

缺口的标准解法是把"未知事件"的处置分成两类。一类可以忽略，它不影响对模型可见历史的重建，这类事件带一个 `ignorable: true` 标记；另一类不能忽略，例如压缩点——不知道它就无法正确派生模型可见历史，这类事件让老版本拒绝整份日志。划分的依据是同一个问题：如果不知道它，派生出来的模型可见历史会出错吗。dsh 体系的架构文档里这套机制写得更完整：`SessionEventMap` 的成员默认是读取时必需的，只有带 `ignorable: true` 的事件才允许被不认识它的构建跳过；而结构性的格式变化才允许提升 `SESSION_FORMAT_VERSION`。

这个例子给出的是契约设计里一条通用的做法：格式演进的关键不是设计一个能兼容所有情况的机制，而是为每一种变化提供一条明确的处置规则，让未来的代码知道该怎么做。

### 3.4 审计结论

三次审计的发现汇总成一张按严重程度排序的清单。"严重度 = 违反后的后果 × 出现的概率"。

| 严重度 | 发现 | 属于 | 后果 |
|---|---|---|---|
| 高 | `sideEffect` 是信任型，而守卫依赖它放行 | 契约强度 | 不可信工具可用错误声明换取无审批写入 |
| 高 | 事件契约没有"可忽略"机制 | 契约演进 | 新增事件类型会破坏旧版本读取日志 |
| 中 | `Provider` 的错误类型未写进契约 | 契约泄漏 | 重试逻辑事实上依赖了具体 provider |
| 中 | `Tool` 的错误表达无规则 | 契约缺口 | 同一失败在模型侧有两种不同表现 |
| 中 | `usage` 字段齐全度未声明为可能不完整 | 契约泄漏 | 统计在非 DeepSeek 实现下缺数据 |
| 低 | `Tool` 的并发与超时语义未定义 | 契约缺口 | 未来并行化时会出问题 |
| 低 | `seq` 与数组长度的一致性无断言 | 证据缺失 | 破坏后延迟暴露 |

这张表的用途是把一个模糊的问题（这个项目的接口设计得好不好）变成七条有严重度排序的具体发现，而其中三条可以在半小时内修完——补文档（`usage` 的可选性）、加断言（`seq` 的一致性）、把可选性写进契约（错误分类）。契约审计的产出多数不是设计错误，而是"没写下来"，这也是它性价比高的原因：它修的是信息，不是结构。

> **面试视角**
> **高频问法**（项目深挖环节）："你怎么 review 一个接口设计？" 4.2 的七步流程可以直接作为答案。
> **追问方向**："你从这次 review 里发现了什么？"讲那处信任型契约（声明了但没人能验证），并说出修法是"限制能力"而不是"加校验"，这是展示对契约强度这一层理解的高含金量回答。
> **对应岗位**：Agent 岗技术面、后端岗系统设计面。

## L4 运行与验证

契约的验证有一个特殊难点：它的错误通常不表现为跑不通，而表现为跑通了但用错了。因此这一节的验证方法围绕一个动作设计——让另一个人（或几天后的自己）只根据契约写一次调用代码，看他能不能写对。

### 4.1 三层验证

第一层是契约自检，用 1.2 的五项清单（副作用、幂等性、时序、错误语义、所有权）逐个过一遍接口，每一项都必须有一个明确答案。这一层是必要的，但它只验证了"你想到了"，不验证"别人能读懂"。

第二层是外部消费者测试，它是契约验证的核心方法，也是它区别于普通测试的地方。做法是找一个不知道实现的人，只给契约文档，让他写一段调用代码。他写出什么，就是这份契约实际表达的东西。这个方法的诊断力在于：他写错的每一处都对应一条你没有表达清楚的承诺。如果他把 `execute` 包在 `try/catch` 里而契约没有说明它会抛异常，那不是他的问题，而是他被迫做了一个假设。发现的假设可以按 1.1.3 的四类失败模式归位——时序假设属于最难查的一类，必须优先补写。

第三层是替换实现测试。对面向替换实现的契约（例如 `Provider`），最有效的验证是用每个实现各跑一遍完整测试，任何在某个实现下失败的测试都指向一条被泄漏的契约。本项目这一层是现成的，两者的差值就是契约泄漏的量。

```powershell
node --test verify.ts                      # 用 MockProvider，不需要网络与密钥
$env:DEEPSEEK_API_KEY='...'; pnpm run test:e2e   # 用真实 provider，需要密钥
```

### 4.2 一次完整的审计流程

把审计固定成可重复的七步，它与 L3 开头的四步是同一件事的展开：前四步是清单产出，后三步是验证。

```
① 读签名，列出类型能表达的部分
② 对三类承诺逐条问"写清了没有"，把缺口列出来
③ 列出不变量，为每条找证据来源（断言/测试/文档），无证据的标出
④ 对照"承诺"与"谁有能力兑现它"，找出信任型契约
⑤ 用外部消费者测试验证：只看文档写一段调用代码
⑥ 用替换实现测试验证（若该接口有多个实现）
⑦ 把发现按"严重度 = 后果 × 概率"排序，输出清单
```

第 ④ 步的问法是"这条承诺，我们有能力保证吗"。答案是"只能相信写的人说的是真的"时，它就是一个信任型契约，而信任型契约在安全相关的场景下需要额外手段——限制能力，而不是增加检查。

### 4.3 判据

对"掌握了契约分析"的判据有五条。

第一，能对一个接口列出完整的三类承诺清单，并指出哪几类有缺口。第二，能算出一个改动的真实波及面（1.5.1 的两表合取），而不是只说"影响面大"。第三，能判断一次改动落在 1.4.2 表里的哪一格，并说出它为什么可能隐蔽。第四，能识别出至少一处信任型契约，并给出"限制能力"而不是"增加校验"的修法。第五，也是最能说明理解的一条：能为一个当前不是承诺的行为，写出它成为承诺的代价——例如把返回字段顺序变成承诺之后，字段顺序就再也不能改了。

> **面试视角**
> **高频问法**："你怎么验证一个接口设计得好不好？"三层验证里第二层（外部消费者测试）最有说服力：给一个不知道实现的人只看契约，看他能不能写对。
> **追问方向**："怎么证明契约是完整的？"用"他写错的每一处都对应一条你没表达清楚的承诺"来回答。
> **加分点**：提到"用每个实现各跑一遍测试，差值就是契约泄漏的量"。

## L5 语法速查

### 5.1 术语表

| 术语 | 在本篇里的准确含义 | 容易误解为 |
|---|---|---|
| 契约 | 一个模块对外的全部可依赖行为，由三类承诺组成 | "函数签名" |
| 行为承诺 | 调用它会发生什么（返回、副作用、幂等性） | — |
| 时序承诺 | 何时可调用、能调用几次、能否并发 | 最常被漏掉的一类 |
| 错误承诺 | 失败时怎么表现、能否重试 | "失败时抛异常"（那只是其中一种） |
| 前置条件 | 调用方的义务 | "实现方要处理的边界情况" |
| 后置条件 | 实现方的义务 | — |
| 类不变量 | 对象生命周期中始终为真的性质 | "某次调用的后置条件" |
| 可替换性 | 换上另一个实现，调用方察觉不到 | "类型兼容" |
| 破坏性变更 | 使依赖原契约的代码可能失败 | "改动很大" |
| 契约表面积 | 一个模块对外承诺的事项总数 | — |
| 深模块 / 浅模块 | 接口小实现大 / 接口大实现小 | — |
| 强制型契约 | 框架能检查并阻止违反 | — |
| 信任型契约 | 只能依赖约定，框架无法检查 | "已经写进类型就算表达了" |
| 契约泄漏 | 某个实现特有的行为被调用方依赖 | "实现差异" |
| 可忽略事件 | 不认识它的构建可以跳过的事件类型 | "不重要的事件" |

### 5.2 三个模板

模板一用于写接口时组织注释。

```ts
/**
 * <一句话说明它做什么>
 *
 * ## 行为
 * · 返回什么、有什么副作用
 * · 幂等性：调用两次与调用一次的效果是否相同
 *
 * ## 时序
 * · 何时可以调用（前置条件）
 * · 能否并发 / 能否重入
 * · 生命周期限制（关闭后不能调用等）
 *
 * ## 错误
 * · 失败时抛什么；哪些可重试
 *
 * ## 不属于承诺的部分
 * · <列出实现细节，明确说明不要依赖>
 */
```

最后两节最容易被省略。错误一节省略的后果是调用方写不出正确的错误处理；"不属于承诺的部分"省略的后果是按 Hyrum 定律，使用者会依赖它能观察到的一切行为。

模板二用于改动之前逐条自查。

```
[ ] 有人在读返回值的这个字段吗？（删除字段 = 破坏性）
[ ] 有人在依赖这个默认值吗？（改默认值 = 隐蔽的破坏性）
[ ] 有人在解析错误信息吗？（改文案 = 隐蔽的破坏性）
[ ] 有人在依赖"它不会做 X"吗？（改副作用 = 最隐蔽的破坏性）
[ ] 有人在并发调用它吗？（收紧时序 = 最危险，且测试测不出）
```

模板三用于记录审计发现，每条四样。

```
症状 / 它属于哪一类（契约强度、契约演进、契约泄漏、契约缺口、证据缺失）
后果（严重度 × 概率）
修法（补文档 / 加断言 / 限制能力 / 加兼容层）
判断依据（为什么是这个修法而不是别的）
```

### 5.3 三条容易踩的规则

第一条，参数只能放宽，返回只能收紧。这条口诀覆盖绝大多数兼容性判断，记忆方式是"对调用方越宽松越安全"，它的依据是前置条件与后置条件的归属。

第二条，写进契约之前先问"我能不能长期保证它"。承诺的代价是永久的、收益是当次的，所以判断标准是"长期"而不是"现在对不对"。

第三条，当契约无法被检查时，用限制能力代替。这是 `sideEffect` 那个发现给出的通用解法：做不到验证它是真的，就做到即使是假的也没关系。

| 卡在哪 | 问自己 |

## L7 挑战题（不给答案）

每题后面给出了判据，它说明一个好的回答应当包含什么，但不包含答案本身。

第一题：给 `Tool` 补一份完整契约。 用 5.2 的模板，把 3.1.2 找出的三处缺口补上。要求每一处缺口都给出你的选择，而不是"两种都可以"。判据：三处选择各自解释了为什么另一种更差，且至少一处的选择改变了调用方的写法。

第二题：设计 `session/compaction` 事件的可忽略性。 上下文压缩要加一个新事件类型，它应该带 `ignorable: true` 吗。判据：给出判断依据（不知道它时派生出的模型可见历史会不会错），并说明如果判错了会怎样——两个方向的判错后果不同。

第三题：算一次真实改动的波及面。 假设要把 `ToolResult.isError` 改名为 `failed`，用 1.5.1 的两表合取算出波及面，并把发现按"会报错"与"会静默失效"分类。判据：两类发现都存在，且静默失效的那一类给出了检测方式。

第四题：为一处信任型契约设计"限制能力"的修法。 除 `sideEffect` 之外，本项目里还有别的信任型契约吗，找一处并给出修法。判据：修法说明了由谁执行限制、限制不住时会发生什么。

第五题：反驳"承诺越少越好"。 构造一个反例：什么情况下多承诺反而是对的。判据：反例满足"使用者必须知道"这条标准，而不是"写下更方便"。

第六题：审计一个你不熟悉的接口。 从 `D:\deepseek-harness\packages\` 里任选一个包，用 L4.2 的七步审计它，输出发现清单。判据：清单里有至少一条属于"证据缺失"（实现做到了但没有任何断言或测试守护），并且给出了严重度排序的理由。

## L9 仍未解决（这一篇自己的缺陷）

| 缺陷 | 后果 | 修法 | 当初为什么这么写 |
|---|---|---|---|
| 三类承诺的框架没有覆盖性能承诺 | 使用者无法从契约上判断"这个方法预期是快还是慢"，而这在 harness 里很实际（工具可能跑几秒到几分钟） | 在行为承诺里单列一节"性能特征"，或引入"预期耗时量级"的声明 | 起初把性能归入实现细节，但它实际上常被依赖（超时设置就是一例） |
| 契约表面积只有定性描述，没有可计算的度量 | 两个接口无法比较谁的表面积更大 | 定义承诺条数的计数规则（三类承诺各算几条），让它可数 | 计数规则依赖分类粒度，而粒度的确定需要真实数据 |
| 审计方法依赖人工逐条问，没有工具 | 一次审计要花几小时，容易半途而废 | 把"签名 vs 文档 vs 断言"的对照做成半自动检查（例如列出所有导出但无 JSDoc 的成员） | 契约的完整性很难静态判断，但"缺少文档"这一项确实可以自动化 |
| 对契约的心理学完全没有涉及 | 为什么人总是漏写时序承诺，这与认知偏差有关（可见的比不可见的更容易被想到），而本文没有利用这一点 | 补一节"为什么时序承诺最容易被漏"的认知解释 | 本篇定位是工程方法，但认知解释能显著提高"下次记得写"的概率 |
| 没有给出契约随时间的演化数据 | 不知道一个接口平均多久改一次契约，因而无法为"承诺周期"给出经验值 | 在真实项目里收集，例如统计 git 历史里接口文档的改动频率 | 需要真实数据，而项目还没有足够历史 |
| 与网络接口的契约实践脱节 | 读者在面对 HTTP API、gRPC 时缺少迁移 | 补一节"从函数契约到接口契约"的映射 | 本篇以库内契约为场景；网络接口还涉及序列化与网络不可靠性 |
| 契约测试没有被组织成可复用的套件 | 同一份契约的多个实现各自写测试，而"契约"与"某个实现的测试"混在一起 | 把契约测试抽成独立套件，要求每个实现都跑它（本项目的双轨测试只覆盖了两端，没有覆盖"Mock 与真实实现跑同一组契约断言"） | 双轨测试的出发点是成本（Mock 免费、真实调用要钱），而不是契约复用 |

前三条属于工具与度量的缺失，中间两条属于认知与数据的缺失，最后一条属于位置放错——契约测试本该挂在接口上，现在挂在实现上。

### 问题升级练习

模糊问题：「我该怎么设计一个好的接口？」

升级后的精确问题：

> "好接口"至少有三个各自独立的标准：
> ① 使用者能只靠契约写对调用代码（表达完整性）；
> ② 实现者能自由改进而不破坏承诺（承诺节制）；
> ③ 契约本身能被机器部分验证（可检查性）。
> 这三个标准会互相冲突——表达越完整，承诺越多，可演进性越差。
> 它们之间的最优平衡点在哪里，是否取决于接口的使用者是谁
> （同一时刻的代码 / 未来的代码 / 第三方）？

提升点说明：原问题无法回答，因为"好"没有共同尺度。升级后的版本做了三件事。第一，把"好"拆成三个会互相冲突的标准——这是关键，如果三个标准不冲突，这个问题就没有难度。第二，指出冲突的存在，从而把问题从"怎么做到好"变成"怎么权衡"。第三，引入一个调节变量（使用者是谁），因为最优平衡点确实取决于它，而这正好对应本篇区分的三种契约形态：面向实现、面向替换、面向未来。

## L11 系统影响回溯

回看第 0.5 节的三个连锁影响，本篇给出了它们各自的具体形态与一处修正。

连锁 1（契约写不清会让每处调用方各自发明假设）的机制在 1.1.1 里被拆开：问题不是有人写错了，而是接口没有给出答案，于是每个人自己给了一个。这个现象的量级在 L0.1 里做了估计，一个二十模块的项目里可能有三百个只能靠猜的点。

连锁 2（实现细节进契约会让系统失去演进能力）的机制在 1.4.3 里展开成四类隐蔽改动，其中最能说明问题的是改副作用范围——它改变的是调用方对"它不会做 X"的依赖，而签名没有任何变化。

连锁 3（契约的稳定性决定波及面的形状）在 1.5.1 里被补完：波及面的准确计算需要两张表的合取，"谁依赖我"与"我承诺了什么、谁依赖了哪一条"。只有前者会过度保守，只有后者会过度冒险。

一处需要修正的预判：0.5.3 里说"契约的稳定性决定了改动波及面的形状"，读完之后这句要说得更准确——决定波及面形状的不是契约稳不稳定，而是承诺与能力的落差。3.1.3 那个 `sideEffect` 的例子说明，一个稳定的契约（字段一直在、语义一直没变）如果它的承诺超出了系统的保证能力，它制造的风险与契约不稳定是一样的。换句话说，契约的风险有两个来源：变（不稳定）与虚（做不到）。后者更隐蔽，因为它不会出现在任何 diff 里。

通向下一篇的桥。 本篇讲完了承诺什么与怎么改，它有一个隐含前提：承诺的对象是代码——调用方是同一时刻的代码，或者未来的代码。下一篇 `1.5 数据、状态与可逆性` 处理一类更麻烦的对象：承诺的对象是数据。数据的特殊之处在于它不会因为你的代码改了而跟着改，一份已经落盘的会话日志会永远以写它那一刻的格式存在。这就是数据格式的破坏性变更比接口的破坏性变更更严重的原因——前者不可逆，后者通常可以靠改调用方解决。

## 记忆锚点与复述练习

### 一、骨架：四块

```
   承诺什么 ──► 签名没说的 ──► 谁会因此动手 ──► 怎么安全地改
      ↓            ↓              ↓               ↓
   三类承诺      五项清单       两张表合取      四种手段
   1.1          1.2            1.5             1.6
```

只记一行就记这行：承诺什么 → 签名没说的 → 谁会因此动手 → 怎么安全地改。

### 二、情境绑定：当你……就想起……

| 当你…… | 立刻想起 |
|---|---|
| 要写一个新接口 | 三类承诺逐条问一遍：行为、时序、错误 |
| 看到一个只有签名没有注释的函数 | 五项清单：副作用、幂等、时序、错误、所有权 |
| 要改一个接口 | 先算两表合取（谁依赖哪条承诺 + 扇入闭包），再查破坏性分类表 |
| 不确定某行为算不算承诺 | 看三处证据，都没有就不算——但按 Hyrum 定律它仍可能被依赖 |
| 想给接口加一个字段 | 问"它要成为承诺吗"，不是就不该进接口 |
| 想加一个开关来兼容新旧 | 问"这个开关什么时候删"，答不出就改用兼容层加弃用标注 |
| 看到一个"声明了但没人验证"的字段 | 它是信任型契约，修法是限制能力而不是加校验 |
| 写测试断言一个返回对象 | 别用全等，那会锁死实现；断言承诺的字段 |
| 要加一个新的事件类型 | 想"它可忽略吗"，判据是不认识它时派生出的历史会不会错 |
| 看到一个奇怪的实现选择 | 构造反事实："如果不是这样会怎样"（C-02） |
| 发现一条不变量需要反复检查 | 先问它能不能改成由其他数据推导（1.3.1） |
| 要给失败分类 | 按"下游需要做什么决定"分，不按现象分（1.2.4） |

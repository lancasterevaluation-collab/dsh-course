# harness-tester · 测试与评分框架

> **它是什么**：一个能对 harness **注入故障、跑多轮、自动判分**的框架。
> **它为什么存在**：对标 MIT 6.5840 的评分哲学——**测试框架就是评分者（tester is the grader）**。没有它，构建型作业无法自动判分，学生也无法知道"我到底做对了没有"。

---

## 一、设计依据（三条来自 6.5840 的机制）

| 机制 | 6.5840 的做法 | 本框架的做法 |
|---|---|---|
| **tester is the grader** | 用课程提供的 Go 测试框架评分，不靠人工检查 | **判 harness 的行为**（工具调用序列、最终状态、不变量），不判"回答对不对" |
| **故障注入** | `labrpc` 可以延迟、重排、丢包、断连 | **包装 provider 与工具**，注入超时、限流、畸形响应、执行失败 |
| **跑多轮** | `dstest -s -p 20 -n 500`；Columbia 跑 50 次并乘性惩罚 | **每个用例跑 N 次**，统计成功率与方差，**失败率高则乘性扣分** |

**为什么"跑多轮"是必需的**：**并发、进程、恢复这些功能的失败是偶发的**。单次通过不能说明任何事——这一点在题库（Q2.4.1、Q3.2.2）里已反复说明，**而本框架是它的落地**。

## 二、被测对象的接口约定

学生的 harness 只需暴露一个函数：

```js
/**
 * 跑一个任务，返回【轨迹】。
 * ★ 判分依据是轨迹，不是最终文本——因为"结果对但过程错"也是失败
 *   （对应题库里的"保真度"维度，Q2.3.2）。
 */
export async function run(task, options) {
  // options: { signal, provider, tools }  ← ★ 框架通过它注入故障
  // 返回：{ toolCalls, finalMessage, events }
}
```

**三处关键约定**：

| 字段 | 为什么需要 |
|---|---|
| `toolCalls` | **行为断言的基础**——判"它用对了工具吗" |
| `events` | **不变量检查的基础**——判"日志还能重建吗" |
| 接受注入的 `provider` / `tools` | **故障注入的入口**——不注入就没法测异常路径 |

## 三、四类故障与它们对应的真实场景

| 故障 | 注入方式 | 它模拟的真实情况 | 它检验什么 |
|---|---|---|---|
| **模型超时** | provider 延迟超过 timeout | 网络抖动、服务过载 | 超时处理、重试、取消传播 |
| **模型限流** | provider 返回 429 | API 限流 | 退避重试 |
| **畸形响应** | provider 返回被截断的 JSON | **输出被长度上限截断** | **停止原因分支**（题库 Q2.1.1 的 ②） |
| **工具失败** | 工具抛错或返回 `isError` | 环境问题 | **错误分类**（题库 Q2.1.2） |
| **工具返回超大结果** | 返回 MB 级内容 | 上下文爆炸 | 截断与溢出落盘 |

## 四、判分规则

```
每个用例跑 N 次（默认 20）
    ↓
统计：成功率 p̂、失败分类、每类失败的次数
    ↓
扣分（★ 乘性，不是线性）：
    得分 = 基础分 × p̂^α        （α 默认 2——方差大的惩罚更重）
    ↓
输出：分数 + 失败明细 + 复现命令
```

**为什么是乘性而不是线性**：

| 成功率 | 线性（基础分 × $p$） | 乘性（基础分 × $p^2$） |
|---|---|---|
| 100% | 1.00 | 1.00 |
| 90% | 0.90 | **0.81** |
| 50% | 0.50 | **0.25** |
| 10% | 0.10 | **0.01** |

**乘性惩罚的含义是**：**"十次里对九次"不是 90 分，而是 81 分**——因为**一个偶发失败在生产环境里就是事故**。

**这与 6.5840 的立场一致**：**鲁棒性优于单次正确**。

## 五、目录结构

```
harness-tester/
├── README.md          你正在读的
├── index.mjs          对外接口（runSuite / faults / assertions）
├── faults.mjs         故障注入（包装 provider 与工具）
├── runner.mjs         跑多轮 + 统计
├── assertions.mjs     行为断言与不变量检查
├── report.mjs         报告生成
├── selftest.mjs       ★ 自测：用 mock harness 验证框架本身正确
└── examples/
    └── example-tool-loop.mjs   一个示例用例集
```

**`selftest.mjs` 的存在本身就是一条原则**：**评分框架自己也要被测**。

6.5840 在这方面有已知教训——**它的一道考题就描述了"一个有 bug 的测试会让正确的实现看起来失败"**。**所以框架的正确性是它可信的前提。**

## 六、与课程的关系

```
   题库（讲清原理）  ──►  构建型作业（造出来）  ──►  本框架（自动判分）
                                │
                                └──► 沙箱章（② 号能力簇）也用它验收
```

**它服务于三个决定**：构建型作业需要它判分；沙箱章需要它验证隔离强度；而它自己就是"tester is the grader"这一条标准的落地。

## 本篇新词

派发（delegation） 指把一个任务交给另一个 agent 执行并取回结果。它与"工具调用"的差别是被派发者也能做判断与多步操作，因此派发的协议更像"交接"（写清目标、约束与产出格式）而不是"调用"（给参数、期待确定输出）。

子 agent（subagent） 指被派发任务的执行者。它是一个独立的会话（5.2 的一条会话），有自己作用域与容器，而它的授权继承自父会话（5.3 的 `origin.parentId`）。

派发协议（delegation protocol） 指父与子之间交换的内容：目标（要做什么）、上下文子集（给它看什么）、约束（不能做什么）、产出格式（要返回什么）。四者缺一个都会导致返工——缺上下文则子 agent 做错，缺产出格式则结果无法被采纳。

上下文子集（context subset） 指派发时给子 agent 的信息。它的选择是一个真实的取舍：给太少它做不对，给太多则取消派发的意义（派发的价值之一正是隔离上下文）。判据是"子任务需要的最小事实集"。

结果回收（result collection） 指把子 agent 的产出并入父会话。它的两条要求是结构化（能被父会话机械采纳）与有界（不会用大量文本淹没父会话）——后者常被忽略，而它是派发在上下文上的主要成本。

递归深度（recursion depth） 指派发的层数。它的限制是必需的——没有限制时子 agent 可以继续派发，而每一层都会放大调用与成本。

成本放大（cost amplification） 指派发带来的 token 消耗倍数。父会话的上下文会随子任务数量增长，而每个子 agent 自己也有完整的一轮轮消耗。这条量级决定了"一个任务该拆成几个子任务"。

外部工具（external tool） 指由本进程之外提供的能力（MCP 服务器、插件进程、HTTP 服务）。它与内部工具的三个差别是：它的进程可能死、它的协议可能不匹配、它的能力可能过期——三条都是内部工具不存在的问题。

信任边界（trust boundary） 指外部工具能做什么、不能做什么。它与 5.3 的权限预设是同一件事的两个方向：权限预设管"我们调用别人"，信任边界管"别人能碰到什么"。

```
│  ② 怎么收 —— 结构化、有界与失败                      → 1.3           │

│  ④ 怎么接外部 —— 能力发现与信任边界                  → 1.5、1.6       │
└──────────────────────────────────────────────────────────────────────┘

 一句话串起来：怎么派 → 怎么收 → 怎么不失控 → 怎么接外部
```

这张图的关键线索在第二块：派发的收益与成本都落在上下文上。收益是隔离（子 agent 的过程不占用父会话），成本是回收（它的产出要回到父会话）。当回收的内容等于甚至超过被隔离的内容时，派发就没有意义——这条判据决定了什么样的任务值得派发。

### 0.1 一个具体的判断：派发的成本放大

设一个父会话派发 5 个子任务，每个子 agent 的完整运行消耗 30K token（含它的输入与输出），而父会话为了派发与回收消耗 10K token。

总消耗约 160K token，而如果父会话自己顺序做这 5 件事，消耗可能是 60K（它不需要重复说明目标、不需要回收摘要、不需要为每个子任务建立上下文）。派发的直接成本是 2.7 倍，而它换来的是：父会话的上下文不被 5 个子过程占据（否则那 5 段的中间过程会全部留在父会话历史里）。

这条量化给出派发的适用判据：当被隔离的中间过程量远大于派发与回收的开销时，派发是划算的。反之（子任务很短、结果很简单）时，直接做更好——"能派发"不等于"该派发"。

### 0.2 本篇建立的三项判据

第一项用于判断一次派发是否合格：问"子 agent 拿到的信息够不够做完这件事"。检验方式是看它有没有返工（返回"缺少 X 信息"或者做出与约束不符的改动）。

第二项用于判断结果回收是否可靠：问"父会话能不能机械地采纳这个结果"。不能说明产出格式没有定义，而它会让父会话重新阅读大段文本（回收的上下文成本回到派发前的水平）。

第三项用于判断外部工具的接入是否安全：问"它能碰到什么"。答案应当由信任边界明确列出，而不是"它能做什么就做什么"——外部工具的默认权限应当是最小集，而不是全部。

### 0.3 十分钟练习：派发协议的结构与校验

下面这段代码定义派发协议并校验它的完整性。

```js
function buildDelegation(parent, spec) {
  const required = ['goal', 'context', 'constraints', 'outputFormat']
  const missing = required.filter((k) => !spec[k] || (Array.isArray(spec[k]) && spec[k].length === 0))
  if (missing.length) throw new Error(`派发缺少：${missing.join('、')}`)
  return {
    id: `d-${Math.random().toString(36).slice(2, 6)}`,
    parentSession: parent.id,
    parentTask: parent.goal,                       // 父任务语境（子 agent 判断边界用）
    depth: (parent.depth ?? 0) + 1,
    budget: { maxTokens: spec.budget?.maxTokens ?? 50000, maxToolCalls: spec.budget?.maxToolCalls ?? 30 },
    ...spec,
  }
}

const parent = { id: 's-1', goal: '把课程的第 5 卷写完', depth: 0 }
console.log(buildDelegation(parent, {
  goal: '为 5.4 写一节关于外部工具接入的内容',
  context: ['5.4 的骨架与已有章节标题', '0.3 规范的篇幅门槛'],
  constraints: ['不得改动其他篇', '必须用 17 节骨架'],
  outputFormat: { kind: 'markdown-section', maxChars: 4000 },
}))
```

四个必填字段（目标、上下文、约束、产出格式）的校验在这里是硬性的，而另外两个字段值得注意：`parentTask`（父任务的语境，让子 agent 判断自己的边界）与 `depth`（递归深度，1.4 的限制依据）。

### 0.5.3 三个连锁影响

第一，派发会让观测的归因链变长。 一条子 agent 的成本属于它的父会话（用户关心的是"这个任务花了多少"），而它的失败可能属于子 agent 自己（上下文不足）或父会话（派发协议不完整）。处置方式是把归因链记录下来（子会话记 `parentId`），而 3.6 的按会话归因需要扩展到"按派发树归因"。

第二，派发的上下文隔离与记忆的跨会话共享存在张力。 子 agent 有自己的会话（隔离），而它也在同一个用户与项目下（共享记忆与技能）。处置方式是明确子 agent 能读到什么——技能与记忆默认可见，而父会话的会话历史默认不可见（这正是隔离的意义）。

第三，外部工具会把"失败模式"从内部问题变成外部问题。 内部工具的失败是可控的（同一个代码库、同一套错误类型），而外部工具会死、会超时、会返回协议外的内容。处置方式是把外部工具的错误归一化到 3.1 的分类里，并让它参与重试与降级——否则外部工具的错误会成为一类"无法处理"的异常。

### 0.5.4 它与本书其余部分的关系

本篇的多智能体是"主从"形态（一个父派发若干子），不是对等协作。对等形态（多个 agent 平等协商）需要更复杂的协议与冲突解决，而它不在本课程范围内。这条边界意味着本篇的结论在"层级化的任务分解"上是完整的——而它覆盖了实践中绝大多数多 agent 用法。

> **面试视角**

> **高分要点**：说出成本放大的量级（约 2–3 倍）与它的收益（上下文隔离），并给出判据（被隔离的过程量是否远大于开销）。只说"多 agent 更强"会误导，因为多数任务的中间过程量并不大。

## L0 要解决的问题

### 0.1 现象一：派出去的子 agent 做错或用不上

第一个现象是派发质量差。它的两种表现：子 agent 做错了（因为它缺关键信息，或者误解了目标）、子 agent 做得对而结果用不上（因为产出格式与父会话期望的不一致）。

两种表现的成因都在派发协议（0.1 的四个要素）：前者缺上下文与约束，后者缺产出格式。它们的修法都是把协议写全，而协议之所以常被省略，是因为在单机单会话里派发看起来"就是再叫一次模型"。

### 0.2 现象二：结果淹没了父会话

第二个现象是回收没有边界。子 agent 返回一大段过程描述（因为它觉得"多说一点更保险"），而父会话的上下文被这段内容占据——派发的收益（隔离）被回收的成本抵消（0.1 的分析）。

修法是 1.3 的产出格式：明确要什么、多少（例如"只返回结论与涉及的文件，不超过 500 字"）。这条修法与 2.2 的"给模型看的描述"同源——信息的形态要匹配使用者的需要。

### 0.3 现象三：派发失控

第三个现象是失控。它的三种形态：递归派发（子 agent 又派了几个）、预算失控（一个子任务的消耗远超预期）、以及并发失控（一次派发了二十个子任务，把模型配额打满）。

三种的修法都是限制（1.4）：深度上限、每个子任务的 token 与调用次数预算、以及并发上限。三条限制的共同特点是它们必须在派发前生效——事后发现已经花掉的钱无法收回。

### 0.4 现象四：外部工具引入了一类无法处理的错误

第四个现象是外部工具的失败无法被现有机制处理。内部工具的失败有类型（3.1 的分类）、有重试策略、有降级路径；而外部工具会以各种方式失败——进程退出、协议返回不合规、连接半开、能力在加载后失效。

修法是 1.5 的归一化：把外部失败映射到内部错误类型上，从而复用 3.1 的重试与 3.2 的降级。没有这一步时，外部工具的错误会成为一类特殊分支，而特殊分支会持续积累（每接一个外部系统就多一种）。

### 0.5 现象五：外部工具碰到了不该碰的东西

第五个现象是信任越界。一个外部工具（它可能是第三方实现）读到了它不需要的文件、或者发起了一个未被授权的操作。它的成因是接入时按"它能做什么"而不是"它该做什么"来配置。

修法是 1.6 的信任边界：默认最小集（只给它完成任务必需的访问），而扩大需要显式授权（与 5.3 的权限预设走同一套记录）。

### 0.6 这一篇要正面回答的四个问题

第一，派发的协议与继承（1.1、1.2）。第二，结果如何回收（1.3）。第三，如何不失控（1.4）。第四，外部工具如何接入与约束（1.5、1.6）。

四个问题里第一与第四是这一篇的核心：前者决定派发是否有用，后者决定扩展能力时是否安全。

## L1 设计与原理

### 1.1 子 agent 的形态与继承

子 agent 是 5.2 的一条会话，因此它继承了那一篇的全部设施（作用域、容器、配额、回收）。三项特定的继承值得单独说明。

授权的继承（5.3 的 L11 修正）：父会话获得的授权对子 agent 生效，而子 agent 不能获得父会话没有的授权。这条规则让审批量不随派发数量增长——否则一次派发十个子任务会让审批量增加十倍。

约束的继承：父会话的约束（不可违反的规则）传给子 agent。它的实现是在派发协议里带上它们（0.3 的 `constraints`），而不是依赖子 agent 自己判断。

预设的选择：子 agent 可以用不同的预设（例如父是"写代码"而子是"查资料"），而它的工具集不能超过父会话的上界（5.1 的预设关系）——这条约束是安全的：否则父会话可以通过派发绕过自己的工具限制。

```ts
export function spawnSubagent(parent: SessionHandle, spec: DelegationSpec, ctx: Context): SessionHandle {
  const parentTools = new Set(ctx.presetOf(parent.preset).tools)
  const childPreset = ctx.presetOf(spec.preset ?? parent.preset)
  const escalated = childPreset.tools.filter((t) => !parentTools.has(t))
  if (escalated.length) throw new Error(`子 agent 预设超出父会话工具集：${escalated.join('、')}`)   // 不可提权
  if (childPreset.tools.length > 0 && !allowedByProfile(childPreset, ctx.profile)) throw new Error('子 agent 预设超出模式上界')
  const child = ctx.registry.create(ctx.profile, childPreset.name, ctx, { parentId: parent.id, depth: parent.depth + 1 })
  return { ...child, goal: spec.goal, constraints: [...parent.constraints, ...spec.constraints] }
}
```

两处检查都是"不能提权"的具体形态（不能超过父工具集、不能超过模式上界），而它们的顺序是先查父、再查模式——因为父是可变的而模式是固定的，先查父能给出更相关的错误信息。

### 1.2 派发协议的四个要素

四个要素各自解决一类失败，而它们的写法有具体要求。

目标要写成可判定的（"为 5.4 写一节关于外部工具接入的内容"而不是"研究一下外部工具"）。它的判据与 4.7 的任务目标一致——写成一句可判断"做完没有"的话。

上下文子集要写清"给什么"与"不给什么"。"不给什么"同样重要：它让子 agent 知道自己看不到全貌（因此不该做全局判断），而这条自我认知能避免它做出超越范围的改动。判据是最小事实集（0.2 的第一项）。

约束要写成判据而不是提醒（"不得改动其他篇"而不是"请注意不要改太多"）。这与 4.7 的"约束写成可检查的形式"一致。

产出格式要具体到形态与容量（例如 `{ kind: 'patch', maxChars: 4000 }`）。容量是必需的一项——没有它时子 agent 会倾向于多给（0.2 的现象二）。

四个要素合起来构成一个可以机械校验的结构（0.3 的练习），而校验失败应当是拒绝派发而不是带缺派发——缺协议的派发会浪费一次完整的子任务运行。

### 1.3 结果回收

回收的三个要求与它们的实现。

结构化：产出按声明的格式返回（一个补丁、一个清单、一段带标题的文本）。它的实现方式是在子 agent 的提示里给出格式要求（同时用协议里的 `outputFormat`），并在回收时校验——校验不通过时要求重做，而不是接受一个不合格式的结果。

有界：超长的产出被裁剪或要求重做。它的实现与 2.2 的截断策略同类（头尾保留），而更好的做法是在协议里限定容量（1.2 的第四要素）——限制发生在生成时比发生在回收时更有效。

可追溯：回收的内容带着子任务的标识与消耗（token 数、轮数），这样父会话能判断"这个结果值不值这些消耗"。这条信息的用途在 4.6 的复盘（哪些派发是有效的）。

```ts
export function collect(child: SessionHandle, ctx: Context, format: OutputFormat): Collected {
  const raw = ctx.registry.resultOf(child.id)
  const parsed = validateFormat(raw, format)
  if (!parsed.ok) return { ok: false, reason: `产出不符合格式：${parsed.issue}`, retryable: true }
  return {
    ok: true,
    content: clamp(parsed.value, format.maxChars),                          // 有界（1.3）
    meta: { childId: child.id, tokens: ctx.metrics.tokensOf(child.id), turns: ctx.metrics.turnsOf(child.id), at: ctx.now },
  }
}
```

`retryable` 这个字段让"格式不符"成为一个可重试的失败（而不是拿到一个坏结果硬用），而 `meta` 是追溯的实现。

### 1.4 三条件的限制

深度上限（常见取值 2 或 3）：防止无限递归。超过上限时派发请求被拒绝，而子 agent 需要知道这一点（它的协议里带着 `depth` 与 `maxDepth`），否则它会尝试派发然后失败。

预算限制：每个子任务有 token 与调用次数的上限。它的取值依据是任务规模（一个"查一段资料"的子任务不需要十万 token），而超预算的处置是返回已有的部分结果并标记未完成——这比直接失败更有用（部分结果常常够用）。

并发上限：一次派发的子任务数与全局并发的上限。它的依据是 5.2 的下游配额（并发上限由模型配额决定），而超限的处置是排队或分批。

```ts
export function admitDelegation(parent: SessionHandle, ctx: Context): { ok: boolean; reason?: string } {
  if (parent.depth + 1 > ctx.config.maxDepth) return { ok: false, reason: `派发深度已达上限 ${ctx.config.maxDepth}` }
  if (ctx.registry.runningChildrenOf(parent.id) >= ctx.config.maxChildrenPerSession) return { ok: false, reason: '该会话的子任务数已达上限' }
  if (ctx.registry.globalConcurrent() >= ctx.config.globalMaxConcurrent) return { ok: false, reason: '全局并发已满（5.2 的配额）' }
  return { ok: true }
}
```

三条检查的顺序是先局部后全局——前两者是这次派发自身的问题（可以直接告诉调用方），后者是全系统状态（可以重试）。

### 1.5 外部工具的接入

接入的四个步骤，而它比内部工具多两处。

发现：外部工具声明它提供什么能力（MCP 的 `tools/list` 一类）。发现的结果需要被缓存并带过期——因为外部进程的能力可能在运行中变化（重启后版本不同）。

归一化：把外部的描述映射到内部的工具定义（2.2 的 `ToolDefinition`），包括副作用等级（`sideEffect`）。这一映射是信任边界的基础——一个外部工具声明自己是只读时，边界可以更宽；而它的声明本身不可信，因此等级应当由配置指定而不是由它自报（1.6）。

命名冲突：两个外部工具提供同名能力时，处置是加上来源前缀（`mcp__server__tool`）而不是后者覆盖前者。覆盖会让"调用了哪个实现"变得不可知，而加前缀让调用点显式。

失败归一化：把外部错误映射到 3.1 的分类（可重试、不可重试、需要人工）。没有这一步时，每接一个外部系统就多一种错误处理（0.4 的分析）。

```ts
const MCP_ERROR_MAP: Record<string, ErrorKind> = {
  'ECONNREFUSED': 'retryable',        // 进程未起或已死
  'ECONNRESET': 'retryable',
  'ENOENT': 'fatal',                  // 命令不存在
  'InvalidRequest': 'fatal',          // 协议不匹配
  'timeout': 'retryable',
}

export function normalizeExternalError(err: unknown, server: string): NormalizedError {
  const code = String((err as { code?: string })?.code ?? 'unknown')
  const kind = MCP_ERROR_MAP[code] ?? 'unknown'
  if (kind === 'unknown') return { kind: 'fatal', message: `未识别的外部错误（${server}）：${code}`, needsHuman: true }
  return { kind, message: `${server}: ${code}` }
}
```

未识别的错误被映射为 `fatal` 且标记 `needsHuman`——这条保守默认与 3.2 的超时默认同源：在不确定时选择不重试（重试可能造成重复副作用）。

### 1.6 信任边界

边界的四个维度。

能访问什么：文件系统的可见范围、网络的可达范围、环境变量。默认最小集（0.2 的第三项判据），扩大需要显式授权（5.3 的权限预设记录）。

能改什么：是只读还是可写；写的范围。这条维度与 `sideEffect` 等级对应，而外部工具的等级由配置指定（1.5 的分析）。

能用多少：资源配额（CPU、内存、时间、调用次数）。外部进程的失控比内部代码更容易发生（它不由本进程调度），因此配额更必需。

能看到什么：它能读到哪些上下文（派发给它的内容、共享的记忆与技能）。默认不共享父会话的历史（0.5.3 的第二条），而共享的记忆应当被筛选（不把敏感的条目暴露给第三方实现）。

```ts
interface TrustBoundary {
  readonly server: string
  readonly fs: { read: readonly string[]; write: readonly string[] }        // 路径白名单
  readonly net: { allow: readonly string[] }                                 // 域名白名单
  readonly env: readonly string[]                                            // 可见的环境变量
  readonly sideEffectCeiling: SideEffectLevel                                // 允许的最高副作用等级
  readonly budget: { cpuMs: number; memoryMb: number; callsPerMinute: number }
  readonly contextSharing: { parentHistory: false; memory: 'filtered' | 'none' }
}
```

七个字段里 `sideEffectCeiling` 是最有实操价值的一项：它把"这个外部工具最多能做到什么"变成一个可校验的声明——一个被声明为"只读"的工具若尝试写文件，会被沙箱拒绝（3.2 的强制层），而不是仅仅依赖它的自觉。

## L2 决策表

| # | 决策 | 我们的选择 | 替代方案 | 代价落在谁身上 |
|---|---|---|---|---|
| 1 | 派发的判据 | 被隔离的过程量远大于开销 | 任务复杂就派 | 有时不派；换来成本可控 |
| 2 | 派发协议 | 四个要素缺一即拒 | 缺省补默认 | 派发方要写全；换来子任务不返工 |
| 3 | 上下文子集 | 最小事实集加"不给什么" | 给全部上下文 | 子 agent 可能信息不足；换来隔离有意义 |
| 4 | 产出格式 | 含形态与容量 | 只要结论 | 协议更长；换来回收不淹没父会话 |
| 5 | 回收结果 | 校验格式，不符则重做 | 接受任意产出 | 可能多跑一次；换来父会话可机械采纳 |
| 6 | 深度上限 | 有（2 或 3） | 不限制 | 深层分解被拒；换来不失控 |
| 7 | 预算超限的处置 | 返回部分结果并标记 | 直接失败 | 父会话要处理部分结果；换来不浪费已做的功 |
| 8 | 子 agent 的授权 | 继承父会话，不可提权 | 独立授权 | 灵活性下降；换来审批量不随派发增长 |
| 9 | 工具集上界 | 不得超过父与模式 | 按预设自由选 | 有些组合不可用；换来不可绕过限制 |
| 10 | 外部工具命名 | 加来源前缀 | 同名覆盖 | 名字更长；换来调用点显式 |
| 11 | 外部错误 | 归一化到内部错误类型 | 各自处理 | 映射需要维护；换来复用重试与降级 |
| 12 | 外部工具的边界 | 默认最小集，扩大要授权 | 按它所需给 | 配置更麻烦；换来第三方实现受限 |
| 13 | 未识别的外部错误 | 视为 fatal 且需人介入 | 重试 | 有时少重试；换来不产生重复副作用 |

其中两条值得展开，因为它们的选择在实践中经常被做成另一个。

### 关于第 8 与第 9 条的完整论证（为什么子 agent 不能提权）

替代方案是让子 agent 按自己的预设获得工具与授权（它需要什么就给什么）。它在功能上更方便，而在三个地方破坏安全。

第一，它让父会话的限制可以被绕过。如果父会话的预设是"只读"（5.1 的探索型会话），而它派发的子 agent 预设是"可写"，那么用户设定的边界实际上不存在了——他只是看不到绕过发生在一层之下。

第二，它让审批量随派发增长。子 agent 的每个危险操作都需要审批（因为授权不继承），而一次派发十个子任务的审批量是单会话的十倍（5.3 的 L11 修正）。

第三，它让责任链断裂。一条操作被允许时，它属于哪个任务的判断变得困难——"用户为什么同意了这个操作"的答案应当是"为了那个父任务"，而独立授权会让答案变成"某次子任务的审批"，脱离了任务的语境。

第 9 条（工具集不得超过父与模式）是同一逻辑的具体化，而它有一个可接受的代价：某些组合（父是只读、子想写）无法表达——而正确的表达方式是由用户显式地给父会话授予写权限，那是一次可见的授权。

### 关于第 5 与第 7 条的完整论证（为什么校验与部分结果都重要）

替代方案是接受任意产出、失败即丢弃。它的代价在两个具体场景里显现。

第一个场景是格式不符。子 agent 返回了一段散文，而父会话期望的是一个补丁。接受它意味着父会话要么自己从散文里提取（重新投入上下文），要么放弃这个结果——两者都抵消了派发的收益（0.2 的现象二）。要求重做的成本是一次额外的子任务运行，而它的收益是回收的内容立即可用。这个交换在多数情况下划算，因为子任务通常比父会话便宜（它的上下文更小）。

第二个场景是预算耗尽。子 agent 做了一半而预算用尽。直接失败会丢弃已有进展，而返回部分结果让父会话可以判断"这些够不够"或者"要不要再派一次"。它的实现要求协议里声明"部分结果可接受"（否则子 agent 会认为未完成等于失败，而不返回任何东西）。

两条决策的共同形态是：在边界条件下选择保留信息而不是丢弃信息——这与 3.3 的"压缩保留指针而不是直接丢弃"、4.1 的"抑制而不是删除"是同一条原则的又一次出现。

## L3 实现（施工图）

### 3.1 文件结构

```
// plugins/multi-agent.ts
// ┌─ 派发段 ── DelegationSpec 的构造与校验
// ├─ 继承段 ── 授权、约束与工具集的上界检查
// ├─ 回收段 ── 格式校验、有界裁剪与追溯元数据
// ├─ 限制段 ── 深度、预算与并发
// └─ 外部段 ── 能力发现、归一化与信任边界
```

五段与前面各节一一对应，其中外部段是唯一与进程外世界打交道的部分。

### 3.2 派发段与继承段

派发段的实现见 0.3（`buildDelegation`），继承段见 1.1（`spawnSubagent`）。两处的衔接要点是校验的顺序：

```ts
export async function delegate(parent: SessionHandle, spec: DelegationSpec, ctx: Context): Promise<Collected> {
  const built = buildDelegation(parent, spec)                       // 协议完整性（四个要素）
  const admitted = admitDelegation(parent, ctx)                     // 限制（深度、子任务数、并发）
  if (!admitted.ok) return { ok: false, reason: admitted.reason!, retryable: true }
  const child = spawnSubagent(parent, spec, ctx)                    // 继承检查（不提权）
  await ctx.registry.setState(child.id, 'running')
  const raw = await runToCompletion(child, built, ctx)
  const collected = collect(child, ctx, spec.outputFormat)          // 回收（校验与有界）
  await ctx.registry.closeChild(child.id, ctx)                       // 回收资源（5.2 的关闭流程）
  return collected
}
```

五步的顺序对应四类失败的处理：协议不全直接拒（不浪费运行）、限制不满足直接拒、继承违规抛错（这是配置错误而不是运行时状况）、运行结果经校验才采纳、无论如何先回收资源（`closeChild` 在执行路径上，而不是靠垃圾回收）。

### 3.3 回收段与限制段

回收段见 1.3（`collect`），限制段见 1.4（`admitDelegation`）。两者的补充是运行时的预算监控：

```ts
export async function runToCompletion(child: SessionHandle, spec: BuiltDelegation, ctx: Context): Promise<unknown> {
  const stop = ctx.monitor(child.id, (m) => {
    if (m.tokens > spec.budget.maxTokens) return { stop: true, reason: 'token 预算用尽' }
    if (m.toolCalls > spec.budget.maxToolCalls) return { stop: true, reason: '调用次数用尽' }
    return { stop: false }
  })
  try { return await ctx.runSession(child, ctx.specOf(spec), { stop }) }
  finally { stop.dispose() }
}
```

`ctx.monitor` 是一个在每个模型调用与工具调用之后触发的检查点，而 `stop` 让"用尽预算"成为一个优雅停止（子 agent 收到停止信号并按 7.2 的建议返回部分结果），而不是强杀（强杀会丢失已做的功）。

### 3.4 外部段

```ts
export async function attachServer(name: string, boundary: TrustBoundary, ctx: Context): Promise<ToolDefinition[]> {
  const client = await connect(name, ctx)                                    // 启动或连接外部进程
  const caps = await client.listCapabilities()                               // 发现
  const tools = caps.map((c) => ({
    name: `mcp__${sanitize(name)}__${c.name}`,                               // 命名加前缀（L2 第 10 条）
    description: `[外部] ${c.description}`,
    sideEffect: boundary.sideEffectCeiling,                                  // 等级由边界指定（1.5）
    run: async (args) => {
      try { return await client.call(c.name, args, { timeoutMs: boundary.budget.callsPerMinute > 0 ? ctx.config.externalTimeoutMs : undefined }) }
      catch (e) { const n = normalizeExternalError(e, name); if (n.kind === 'retryable') throw new RetryableError(n.message); throw new ToolError(n.message) }
    },
  }))
  ctx.registry.registerExternal(name, { boundary, tools, attachedAt: ctx.now })
  return tools
}
```

四处要点：名称加前缀、副作用等级来自边界而不是自报、错误归一化后抛出内部类型（从而复用 3.1 的重试）、以及附件被登记（可观测、可撤销）。

| # | 判据 | 怎么检查 |
|---|---|---|
| 1 | 协议缺要素时拒绝派发 | 各缺一个要素试一次 |
| 2 | 深度超限时拒绝 | 构造超过 `maxDepth` 的派发 |
| 3 | 子任务数超限时拒绝 | 构造超过上限的并发派发 |

| 对比派发与直做 | `node tools/delegation-compare.mjs --task=<id>` | 质量、成本与上下文占用 |
| 看派发树 | `node tools/delegation-tree.mjs --session=<id>` | 父子关系与各自的消耗 |
| 边界验证 | `node tools/boundary-test.mjs --server=<name>` | 越界尝试 |

### 5.3 三条容易踩的规则

第一条，派发协议四个要素缺一不可。缺协议的派发会浪费一次完整的子任务运行。

第二条，子 agent 不能提权。授权继承父会话，工具集不超过父与模式。

第三条，外部工具的错误要归一化，边界要默认最小集。

## L9 仍未解决（这一篇自己的缺陷）

| 缺陷 | 后果 | 修法 | 当初为什么这么写 |
|---|---|---|---|
| 派发质量缺乏自动评估 | 协议的问题只能靠人察觉 | 从返工率与格式失败率推断（4.6 的输入） | 自动评估需要标注 |
| 上下文子集靠人选择 | 可能给少了导致返工 | 从历史派发里学习最小集 | 学习需要样本 |
| 外部工具的边界是静态的 | 工具升级后边界可能不再匹配 | 版本变化时重新推导（挑战题第三题） | 静态边界实现简单 |
| 只支持主从形态 | 对等协作无法表达 | 见 0.5.4 的边界 | 主从覆盖多数用法 |
| 部分结果的合并是父会话的职责 | 父会话要写合并逻辑 | 提供标准合并策略 | 合并语义依格式而定 |
| 跨机派发未实现 | 无法利用多机资源 | 挑战题第四题 | 需要任务状态的序列化 |

第一条与第三条属于"评估与同步"，第二条与第五条属于输入与输出，第四条与第六条属于形态与规模。第一条值得单独标记：它意味着派发协议的质量问题不会自动浮现——协议写得不好时，表现是子 agent 频繁返工或结果用不上，而这两者都需要人从日志里发现。它接入了 4.6 的复盘（派发质量是复盘的输入之一），而那需要复盘机制先到位。

### 五种提问模板

反例逼问：如果子 agent 可以提权，哪一条安全边界会失效。

边界追问：一个任务拆成几个子任务最划算。

代价追问：要求产出格式校验，代价落在谁身上。

替代对比：为什么外部工具的副作用等级由配置指定而不是自报。

验证追问：怎么证明"外部工具没有越界"。

### 本篇引出的十二个问题

读懂层。 第一，派发协议的四要素是什么？第二，子 agent 继承什么？第三，结果回收的三个要求是什么？

重建层。 第四，为什么子 agent 不能提权？第五，为什么产出格式要含容量？第六，为什么预算用尽时返回部分结果？

设计层。 第七，三条件的限制是什么？第八，外部工具接入的四个步骤是什么？第九，信任边界的四个维度是什么？

评审层。 第十，拿到一个多 agent 设计，你会先检查哪一处？第十一，怎么判断一次派发是否划算？第十二，如果有人说"多 agent 一定能做得更好"，你怎么回应？

### 问题升级练习

模糊问题：「我想让 agent 自己拆任务分给别的 agent，怎么做？」

升级后的精确问题：

> 安全地做多 agent 至少包含三件互相制约的事：**派发**（协议是否完整、成本是否划算）、回收（结果能否被机械采纳、会不会淹没父会话）、以及约束（谁给子 agent 授权、它能碰到什么）。
> 第二件与第三件互相制约——回收要求结果简短，而约束要求子 agent 在信息不足时不要乱做，因此协议要同时给出"要什么"与"别做什么"。
> 我能不能为这三件事各找出一条**可检查的判据**？
> 特别是：有没有哪一条判据，是**能用一次越界尝试来验证的**？

提升点说明：原问题无法回答，因为"拆任务"没有边界，而它默认了拆得越细越好。升级后的版本把它拆成三件具体的事，指出回收与约束的权衡，并追加以一个更强的问题：哪一条判据能用越界尝试验证——因为约束的有效性只能通过尝试突破来证明。

## 本篇新词

模式（profile） 指一组能力的声明式组合：启用哪些插件、每者用什么配置、以及对外暴露什么入口。它与"配置文件"的差别是它可被命名与引用，因此它成为部署与讨论的单位（这一条与 1.4 的"契约要能被引用"同源）。

预设（preset） 指一个 agent 的组成方式：人格设定、工具集、技能集、模型选择。它与模式的关系是预设描述"这个 agent 是什么"，模式描述"这个系统跑什么"——一个模式里可以有多个预设（例如同一进程里两种不同用途的会话）。

装配（composition） 指把多个声明合并成一个有效配置的过程。它由覆盖顺序与合并规则两部分构成，而两者的选择决定了模式的可复现性（同一个模式名在任何地方都应得到同一组能力）。

覆盖顺序（override order） 指多个来源的优先级序列。本课程采用四层（内建默认、用户级、项目级、运行参数），而每层都可以覆盖下一层——顺序本身必须被写下来，因为它是"为什么这条配置生效了"的唯一答案。

隐式默认（implicit default） 指没有被任何一层写出来的取值（由代码里的常量或框架的默认行为提供）。它是这一层的主要敌人：隐式默认让同一个模式名在不同版本、不同机器上产生不同行为，而它的表现是"我这边是好的"。

启动校验（startup validation） 指在启动时检查模式是否自洽：引用的插件存在、配置字段符合各自的校验规则、必需的能力齐备。它的判据与 1.4 的"误配置要响亮失败"一致——校验失败的后果必须发生在启动时，而不是第一次用到它的时候。

模式切换（profile switching） 指运行期间改变生效的模式（或在一个进程里并存多个）。它是这一篇里风险最高的部分，因为它引入了 2.5 的作用域问题：切换之后，旧模式留下的状态可能仍在生效。

能力集（capability set） 指一个模式实际提供的能力总和（插件、工具、技能、模型）。它与"插件列表"的差别是它包含间接启用的部分（一个插件依赖另一个），因此它是校验的对象而不是声明的对象。

```
└──────────────────────────────────────────────────────────────────────┘

 一句话串起来：怎么定义 → 怎么组合 → 怎么校验 → 怎么切换
```

这张图的关键线索在第二块：模式的全部价值建立在"同一个名字总得到同一组能力"上，而这条性质被两件事破坏——覆盖顺序不明确（同一份配置在不同环境里被不同的层覆盖），以及隐式默认（没写出来的取值由代码决定）。两者都会让"可复现"失效，而失效的表现是"在我机器上是好的"。

### 0.1 一个具体的判断：隐式默认的代价

设一个模式声明了 30 个插件，其中 25 个的配置有显式取值、5 个依赖默认值。这 5 个默认值可能来自三处：插件自己的代码常量、框架的默认行为、或者环境变量。它们的代价有三种形态。

第一种是版本漂移：插件升级后默认值变了，而模式声明没有变——于是同一个模式名在升级前后行为不同。第二种是环境差异：框架默认从环境推断（例如并发数取 CPU 核数），于是同一份声明在开发机与服务器上不同。第三种是不可审查：审阅者读模式声明时看不到那 5 个取值，他无法判断并发上限是多少、超时是多少——而这类参数恰好是安全与成本相关的。

三种形态的修法是同一条：把隐式默认变成显式取值（在模式声明里写出来，即使它等于当前的默认值）。这条修法的成本是声明变长，收益是这份声明成为该模式行为的完整描述——它可以在别处被复现，也可以被审查。

### 0.2 本篇建立的三项判据

第一项用于判断模式是否可复现：问"把这份声明拿到另一台机器或另一个版本上，行为会变吗"。答"会"的地方就是隐式默认或环境推断，而它们需要被显式化。

第二项用于判断校验是否完整：问"现在删掉一个必需的插件配置，会在启动时报错吗"。这条判据的检验方式就是真的删一次——而多数校验的缺口正是在这类"删掉某项"的实验里暴露的。

第三项用于判断切换是否干净：问"切换之后，旧模式注册的东西还有没有在生效"。判据是可观测的（2.5 的作用域查询），而它必须被实际检查——残留的表现通常是"某些能力多了一份"，而不是报错。

### 0.3 十分钟练习：覆盖顺序的后果

下面这段代码演示四层覆盖的结果，以及"隐式默认"如何让同一份声明产生两种结果。

```js
const layers = [
  { name: '内建', values: { concurrency: 4, timeoutMs: 30000 } },   // 代码里的默认
  { name: '用户级', values: { concurrency: 8 } },
  { name: '项目级', values: { timeoutMs: 60000 } },
  { name: '运行参数', values: {} },
]

function compose(layers) {
  const out = {}
  const trace = {}
  for (const l of layers) {
    for (const [k, v] of Object.entries(l.values)) { out[k] = v; trace[k] = l.name }
  }
  return { out, trace }
}

const { out, trace } = compose(layers)
console.log('有效配置：', out)
console.log('每个值来自哪一层：', trace)
```

输出里 `concurrency` 来自用户级、`timeoutMs` 来自项目级。关键在于第二行输出：如果 `trace` 不被记录，"为什么这里并发是 8"就只能在四处配置里逐个找。这份来源追踪是校验与排查的基础，而它的实现成本只是一张表。

> **面试视角**
> **高频问法**："你们怎么管理不同部署形态的配置？"
> **高分要点**：说出"声明式模式加明确的覆盖顺序"，并指出隐式默认会让可复现性失效。只说"用配置文件"没有回答"同一份配置在两台机器上行为是否相同"。

### 0.5.3 三个连锁影响

第一，模式的隐式默认会让诊断失去条件。 4.4 要求失败时记录当时的配置，而如果配置的一部分来自隐式默认，那么"当时的配置"无法被完整记录——记录下来的只是显式的那部分。这条连锁把"消灭隐式默认"从一个整洁性问题变成了诊断的前提。

第二，模式会与技能、工具集产生组合爆炸。 一个模式启用一组工具与技能，而另一个模式启用另一组——当两者需要在同一个进程里共存时（5.2 的多会话），它们的并集可能超出上下文预算（4.1 的技能元数据预算与 3.3 的上下文预算）。处置方式是让模式声明它的能力集规模，并在共存时校验总量的上限——这条校验是 1.4 的能力集校验在多会话场景下的延伸。

第三，模式切换引入的残留是 2.5 那条"作用域"问题的第一个真实用例。 切换时若旧模式的注册没有被正确释放（2.4 的 disposer 没有全被调用），残留会表现为"某些能力重复"或"某个配置还在生效"。它的检测方式是可观测的（列出当前注册项的来源），而这条要求与 2.5 的 1.5 一致。

### 0.5.4 它与本书其余部分的关系

本篇的模式是单机、单进程内的。多机部署下的配置分发需要配置中心（它涉及一致性，不在本课程范围内），而模式的声明式与可 diff 这两条性质是与多机分发相容的前提。这条边界意味着本篇的结论在"一台机器上的多种部署形态"上是完整的。

> **高分要点**：说出两个原因——覆盖顺序里有环境相关的层，以及隐式默认从环境推断（并发数、路径、代理）。并指出"消灭隐式默认"是修复方向。

## L0 要解决的问题

### 0.1 现象一：同一条命令在另一台机器上行为不同

第一个现象是隐式默认（本篇新词）造成的不可复现。它的形态很典型：本地的模式跑得好好的，而在服务器上并发过高、超时过短、或者某个能力缺失——因为那份声明没有写出这些取值，而它们的默认值在两处不同。

它的诊断方式与 0.3 的练习相关：如果记录了每个取值的来源层，那么差异可以立刻定位到"这一层没写、取了框架默认"。没有来源追踪时，排查要在若干配置文件与代码常量之间来回找。

### 0.2 现象二：能力集散落在多处，看不出全貌

第二个现象是声明分散。插件列表在一个文件、配置在另一个、某些能力由环境变量开启，而"这个模式到底提供什么"没有人能一次说清。

它的后果有两个：校验做不到（不知道完整的期望集，无法判断缺了什么），以及组合爆炸不可见（0.5.3 的第二条）。修法是 1.1 的单一声明点加 1.4 的能力集推导——声明在一处，而有效能力集由推导得出（两者都要有，因为间接依赖无法手写全）。

### 0.3 现象三：切换模式之后有残留

第三个现象是切换不干净。切换模式（或因配置变更而重新装配）之后，旧模式注册的工具、技能、钩子仍在生效——表现是某些能力出现两份，或者某个旧配置继续影响行为。

它的成因是释放不完整（2.4 的 disposer 未全被调用）或者切换的实现方式（部分重新装配而不是整体切换）。修法是 1.5 的整体切换加效果核对——切换后列出当前注册项的来源，逐项核对没有旧模式的残留。

### 0.4 现象四：配置错了，而在用到它的时候才发现

第四个现象是校验时机太晚。缺失的插件、字段类型错误、互相冲突的两个配置——它们在启动时没有被发现，而是在第一次用到那个能力时失败（或者更糟：静默地用了默认值）。

修法是 1.4 的启动校验。它的判据与 1.4 的"misconfiguration fails loud"一致，而这一层的特殊之处在于校验的对象是能力集（含间接依赖）而不是声明（0.5 的第三项判据）。

### 0.5 这一篇要正面回答的四个问题

第一，模式如何声明、预设如何定义（1.1、1.7）。第二，覆盖顺序与合并规则是什么（1.2、1.3）。第三，校验做什么、什么时候做（1.4）。第四，切换如何做到无残留（1.5）。

四个问题里第二与第四是这一篇的难点：前者决定可复现性，后者决定多个模式能否共存。

## L1 设计与原理

### 1.1 模式与预设的定义

模式是一份声明，它有四个部分：启用的插件列表、每者的配置、对外入口（命令行、HTTP、GUI 绑定）、以及能力集的期望（哪些能力必须齐备）。

预设描述一个 agent 的组成：人格与指令（系统提示的基线）、工具集（启用哪些工具）、技能集（哪些技能可见）、模型选择（含它的预算参数）。

```ts
interface Profile {
  readonly name: string
  readonly plugins: readonly PluginRef[]                 // 启用的插件（含配置）
  readonly entries: readonly Entry[]                     // 对外入口
  readonly requires: readonly string[]                   // 必须齐备的能力（1.4 的校验对象）
  readonly presets: readonly PresetRef[]                 // 该模式支持的 agent 预设
}

interface Preset {
  readonly name: string
  readonly instructions: string                           // 系统提示的基线部分
  readonly tools: readonly string[]                       // 工具集
  readonly skills: readonly string[]                      // 技能集
  readonly model: { id: string; maxTokens: number; temperature: number }
}
```

两个定义的关系值得强调：模式是部署单位，预设是会话单位。一次部署可以跑多种会话（5.2 的多会话），每种会话用不同的预设，而它们共享同一个模式提供的插件集合。这条分工解释了为什么两者要分开——把它们合成一个概念会让"同一份部署里跑两种用途的会话"变得无法表达。

### 1.2 覆盖顺序与合并规则

四层来源与它们的关系（0.3 的练习给出实现）。

| 层 | 谁写 | 典型内容 | 优先级 |
|---|---|---|---|
| 内建默认 | 系统作者 | 安全的基线（保守的超时、较低的并发） | 最低 |
| 用户级 | 使用者 | 个人偏好（模型、输出风格） | 中 |
| 项目级 | 项目维护者 | 项目约定（工具集、检查命令） | 中高 |
| 运行参数 | 执行者 | 一次性覆盖（调试、实验） | 最高 |

合并规则分两类：对象深合并（2.6 的规则，未提及的键保留），数组整体替换（避免"我的列表和你的列表混在一起"这种意外）。这条划分在多来源场景下更重要——数组深合并会让下层的元素在下层被删除后仍然存在（因为合并只加不减）。

来源追踪（0.3 的第二行输出）的实现是合并时记录每个键来自哪一层，而它的用途有三处：排查（为什么这个值是 8）、校验（必需项是否被任何一层提供）、以及诊断（4.4 的已知条件）。

### 1.3 消灭隐式默认

显式化的三条规则。

规则一是必填项没有默认值：核心参数（并发、超时、模型 id、工作目录）必须在声明里出现，否则启动即失败。这条规则把"忘记配置"从运行时问题变成启动问题。

规则二是允许默认但必须可见：次要参数可以有默认值，但有效配置里要能看出它来自默认层（来源追踪显示"内建"）。这样审查者不会误以为它是被显式设定的。

规则三是禁止从环境推断：并发数取 CPU 核数、路径取当前目录、代理取环境变量——这些推断都会破坏可复现性。允许的唯一例外是真正属于环境的东西（例如容器里的服务发现地址），而它们也应当被显式映射而不是隐式读取。

三条规则里第三条最容易引起争议（"按机器能力自动调整不是很合理吗"），而它的答案是：自动调整是合理的，但调整应当发生在显式配置的生成阶段（例如部署脚本根据机器规格生成配置），而不是发生在运行时的隐式读取里——前者的结果可被审查、可被记录、可被复现。

### 1.4 启动校验

校验分三层，而它们的成本与覆盖不同。

第一层是声明校验（毫秒级）：字段类型、必填项、引用的插件是否存在、覆盖顺序里有没有冲突的写法。

第二层是能力集校验（毫秒级）：把声明的入口展开成实际能力（含插件之间的间接依赖），核对 `requires` 列出的能力是否齐备。这一层是间接依赖的检查点——手写声明无法覆盖它。

第三层是探测校验（可选，秒级）：对需要外部依赖的能力做一次轻量探测（例如语言服务器能否启动、凭据是否有效）。它的成本高，因此只对关键能力开启，而它避免的是"启动成功但第一次用到时失败"。

```ts
export async function validate(profile: Profile, ctx: Context): Promise<Validation> {
  const issues: Issue[] = []
  for (const p of profile.plugins) {
    if (!ctx.registry.has(p.name)) issues.push({ level: 'error', what: `插件不存在：${p.name}` })
    else issues.push(...validateConfig(p, ctx.registry.schemaOf(p.name)))      // 第一层
  }
  const capabilities = expandCapabilities(profile, ctx.registry)                // 间接依赖展开
  for (const need of profile.requires) {
    if (!capabilities.has(need)) issues.push({ level: 'error', what: `缺少必需能力：${need}`, hint: `可能由插件 ${ctx.registry.providerOf(need)} 提供` })
  }
  const total = capabilities.size                                                 // 能力集规模（0.5.3 的第二条）
  if (total > ctx.config.maxCapabilities) issues.push({ level: 'error', what: `能力集超过上限：${total}` })
  return { ok: issues.every((i) => i.level !== 'error'), issues, capabilities }
}
```

这段实现里有三处对应前面的分析：`hint` 提示可能提供该能力的插件（把失败变成可行动的，与 4.4 的可行动性一致）、能力集规模校验（多会话共存的前提）、以及错误与警告的分级（有些问题不阻断启动，但必须被看到）。

### 1.5 切换与会话的关系

模式的作用域是会话级的（一个会话用一组预设，而预设来自一个模式），而进程级的部分（插件集合）通常在启动时确定。这条划分让"切换"有两种含义。

含义一是会话内切换预设（例如从"写代码"切到"查资料"）：它的影响范围是一个会话，而它的实现是重新构造该会话的 agent 组成。风险是旧预设的一部分状态仍在（例如已加载的技能、已写入的记忆）——处置是明确哪些状态属于会话、哪些属于预设（2.5 的三类状态划分在这里的又一次应用）。

含义二是进程内切换模式（重新装配插件集合）：它的影响范围是整个进程，而它的实现只有一条安全的路径——整体切换而不是部分重装。整体切换的做法是构造一个新的容器与作用域（2.3），把入口指向它，然后释放旧的。部分重装（增删个别插件）看似省资源，而它带来的残留与半应用状态会持续制造难以定位的问题。

```ts
export async function switchProfile(next: Profile, ctx: Context): Promise<SwitchReport> {
  const validation = await validate(next, ctx)
  if (!validation.ok) throw new Error(`模式校验失败：${validation.issues.map((i) => i.what).join('；')}`)
  const old = ctx.current
  const fresh = await ctx.compose(next)                    // 整体构造新容器与作用域
  await ctx.activate(fresh)                                 // 入口指向新作用域
  const residual = await detectResidual(old, ctx)           // 切换后核对残留（0.2 的第三项判据）
  await old.dispose()
  return { profile: next.name, capabilities: validation.capabilities.size, residual }
}
```

三处要点：先校验再切换（避免切成一个坏状态）、整体构造（不是增量）、以及切换后核对残留（把"应该有残留"变成"被发现"）。

### 1.6 模式的版本与演化

模式是 4.5 的一类可演化对象（配置），因此它带着那一篇的全部要求：可 diff（文本形式）、可回滚（版本化）、变更要记录（理由与预期）。

一处补充值得写下来：模式变更的影响面比其他配置大（它改变的是整个部署的能力集），因此它的门控应当更严。具体做法是把模式的变更与普通配置变更分开：普通配置可以走自动门控（4.5 的三层），而模式变更要求一次显式的验证运行（用该模式跑一组任务），因为它的风险是"整体不可用"而不是"某项指标退化"。

### 1.7 预设与 agent 组成

预设的四个部分与它们的边界。

指令（instructions） 是系统提示的基线部分，而它不包含轮次相关的信息（那是第 0 节的记忆与 2.7 的历史）。这条边界的理由是缓存命中率（3.6 的 1.5）：预设的指令是前缀的一部分，它变化会让整个前缀失效，因此它必须是稳定的。

工具集决定这个 agent 能做什么，而它与 2.2 的 `sideEffect` 声明配合——预设可以选择"只读工具集"（例如一个探索型会话），而这是一条比运行时拦截更可靠的安全边界（3.2 的守卫仍然需要，但预设层的收窄降低了它的负担）。

技能集决定哪些技能可见（4.2 的元数据预算在此生效）。一个预设的技能集过大时，元数据层的常驻成本会侵蚀上下文，因此预设需要声明它的技能集规模。

模型选择含预算参数（最大输出 token、温度），而这些参数与 3.6 的成本度量直接相关。预设不改模型的价格档（那是部署选择），但它决定消耗的多少。

### 1.8 两次追问

工程侧的问题是什么时候该新增一个模式而不是给现有模式加配置。判据是"它与现有模式的能力集差异是否超过某个比例"——差异太小时两个模式会各自漂移（维护成本翻倍），差异太大时用一个模式加大量条件配置会让声明难以读懂。经验做法是让模式对应"部署形态"而不是"使用场景"（后者应当用预设表达）。

产品侧的问题是模式对用户意味着什么。多数用户不关心模式，而他们关心两件事：这个模式下我能做什么（能力集的可见表述）以及它的行为是否符合我的预期（例如"只读模式不会改我的文件"）。因此模式需要一段面向人的说明，而它的内容应当来自 `requires` 与能力集（从声明派生而不是另写一份，否则两者会漂移）。

## L2 决策表

| # | 决策 | 我们的选择 | 替代方案 | 代价落在谁身上 |
|---|---|---|---|---|
| 1 | 模式的声明形式 | 单一文本声明（可 diff） | 分散在多个文件与环境变量 | 声明较长；换来可审查可复现 |
| 2 | 覆盖顺序 | 四层且写下来 | 就近覆盖 | 要维护顺序文档；换来可解释 |
| 3 | 数组合并 | 整体替换 | 深合并 | 有时要重复写；换来不会留下已删元素 |
| 4 | 必填项 | 无默认值，缺失即启动失败 | 给默认值 | 配置更多；换来错误早被发现 |
| 5 | 次要默认 | 允许但要可见来源 | 静默默认 | 要记录来源；换来审查者不误判 |
| 6 | 环境推断 | 禁止运行时推断（改在生成阶段） | 允许 | 部署脚本更复杂；换来可复现 |
| 7 | 校验层次 | 声明、能力集、可选探测 | 只做声明校验 | 成本更高；换来间接依赖也被查 |
| 8 | 能力集上限 | 校验总量 | 不校验 | 有时要拆模式；换来共存不超预算 |
| 9 | 进程内切换 | 整体切换 | 增量重装 | 资源占用瞬时翻倍；换来无残留 |
| 10 | 切换后 | 核对残留并报告 | 直接释放 | 多一次检查；换来残留可见 |
| 11 | 模式变更的门控 | 比普通配置更严（要验证运行） | 与配置同门控 | 变更更慢；换来"整体不可用"被拦住 |
| 12 | 面向人的说明 | 从声明派生 | 另写一份 | 要生成逻辑；换来两者不漂移 |

其中两条值得展开，因为它们的选择在实践中经常被做成另一个。

### 关于第 6 条的完整论证（禁止运行时环境推断）

替代方案是允许运行时推断（并发取核数、路径取当前目录、代理取环境变量）。它在早期是方便的，而在规模化之后有三个具体问题。

第一，它让"同一个模式名"不再是同一件事。同一份声明在核数不同的机器上有不同的并发上限，而并发上限与 3.1 的重试、3.4 的作业调度都存在交互——行为差异的来源变得难以定位。

第二，它让配置记录不完整（0.5.3 的第一条）。诊断要求知道失败时的配置（4.4 的已知条件），而推断出来的值没有被记录在任何地方。

第三，它让审查失去意义。审阅者读声明时看不到并发上限、超时、工作目录，而这几项恰好是安全与成本相关的参数。

把推断移到生成阶段（部署脚本按机器规格生成配置）保留了自适应能力，同时让结果可审查、可记录、可复现——这条改动把"环境相关的行为"从隐式变成了显式的一项数据。

### 关于第 9 条的完整论证（为什么整体切换而不是增量重装）

替代方案是增量重装（只增删变化的插件）。它的优点是资源占用瞬时更低，而它的三个代价在运行一段时间后显现。

第一，释放不完整会产生残留。增量路径上每增加一个环节，就多一处"忘了释放"的机会（2.4 的 disposer 在增量路径里更容易被漏掉）。而残留的表现（某些能力两份、某个旧配置仍生效）很难定位。

第二，半应用状态是可能的。增量重装在中途失败时，系统处于"一半旧一半新"的状态，而它既不是旧模式也不是新模式——这与 3.5 的"半应用状态"是同一类问题。

第三，验证无法复用。整体切换可以先把新模式完整构造并校验，再切换入口（1.5 的 `switchProfile`）；增量重装没有这样一个"完整的新状态"可校验。

瞬时资源翻倍的代价是可以接受的——模式切换不是高频操作，而它发生在部署与调试时（那时资源通常有余量）。

## L3 实现（施工图）

### 3.1 文件结构

```
// plugins/profiles.ts
// ┌─ 声明段 ── Profile 与 Preset 的定义与解析
// ├─ 组合段 ── 四层覆盖、深合并与来源追踪
// ├─ 校验段 ── 声明、能力集与可选探测
// ├─ 切换段 ── 整体构造、激活与残留核对
// └─ 呈现段 ── 面向人的说明（从声明派生）
```

五段与 L2 的决策一一对应，其中组合段是全部行为的来源（它决定有效配置），而呈现段是唯一的输出方向。

### 3.2 组合段

```ts
export function compose(layers: readonly Layer[]): Composed {
  const values: Record<string, unknown> = {}
  const origin: Record<string, string> = {}                        // 来源追踪（1.2）
  for (const layer of layers) {                                     // 从低到高
    for (const [key, value] of Object.entries(layer.values)) {
      const prev = values[key]
      values[key] = isPlainObject(prev) && isPlainObject(value)
        ? { ...prev, ...value }                                     // 对象深合并
        : value                                                     // 数组与标量整体替换（L2 第 3 条）
      origin[key] = layer.name
    }
  }
  return { values, origin }
}

export function requirePresent(keys: readonly string[], composed: Composed): void {
  const missing = keys.filter((k) => !(k in composed.values))       // 必填项（L2 第 4 条）
  if (missing.length) throw new Error(`缺少必填配置：${missing.join('、')}`)
}
```

两处要点：数组走整体替换那一条分支（与对象的处理分开写，避免误用深合并），以及 `requirePresent` 在组合之后立刻执行（错误发生在启动路径上）。

### 3.3 能力集展开

```ts
export function expandCapabilities(profile: Profile, registry: Registry): Set<string> {
  const out = new Set<string>()
  const queue = profile.plugins.map((p) => p.name)
  const seen = new Set<string>()
  while (queue.length) {
    const name = queue.shift()!
    if (seen.has(name)) continue
    seen.add(name)
    for (const cap of registry.provides(name)) out.add(cap)
    for (const dep of registry.dependencies(name)) queue.push(dep)   // 间接依赖（1.4 的第二层）
  }
  return out
}
```

广度优先遍历把间接依赖展开，而 `seen` 防的是插件之间的循环依赖导致的死循环——循环依赖本身应当在注册阶段就被拒绝（2.3），这里的 `seen` 是防御性的第二道。

### 3.4 切换段与残留核对

```ts
export async function detectResidual(old: Scope, ctx: Context): Promise<string[]> {
  const survivors = ctx.listRegistrations().filter((r) => r.scope === old.id)
  const unexpected = survivors.filter((r) => !r.expectedAfterDispose)
  return unexpected.map((r) => `${r.what}（来自 ${r.plugin}）`)      // 期望存活之外的都算残留
}
```

核对的关键是 `expectedAfterDispose` 这个标记：有些注册项本来就应当在模式切换后继续存在（例如日志写入器、凭据提供者），而把它们当作残留会制造误报。因此"哪些应当存活"需要在注册时就声明，而不是在核对时判断。

### 3.5 呈现段

```ts
export function describeProfile(profile: Profile, composed: Composed): string {
  const caps = [...expandCapabilities(profile, ctx.registry)].sort()
  return [
    `模式：${profile.name}`,
    `能力：${caps.join('、')}`,                                     // 从声明派生（L2 第 12 条）
    `可用预设：${profile.presets.map((p) => p.name).join('、')}`,
    `关键参数：并发 ${composed.values.concurrency}、超时 ${composed.values.timeoutMs}ms（来源：${composed.origin.concurrency ?? '未设置'}）`,
  ].join('\n')
}
```

四行都从声明与有效配置派生，因此它们不会与实际行为漂移——这条性质与 2.2 的"给模型看的描述"同源（描述与实际必须同源）。

### 3.6 验收判据

| # | 判据 | 怎么检查 |
|---|---|---|
| 1 | 四层覆盖顺序正确 | 用 0.3 的例核对有效值与来源 |
| 2 | 数组整体替换 | 下层给两个元素、上层给一个，核对结果是一个 |
| 3 | 对象深合并 | 上下层各给一个键，核对两个键都在 |
| 4 | 必填项缺失时启动失败 | 删掉一个必填项 |
| 5 | 能力集含间接依赖 | 声明一个依赖链，核对末端能力在集里 |
| 6 | 缺少必需能力时报错并给提示 | 删掉提供该能力的插件 |
| 7 | 能力集超上限时报错 | 构造超过上限的模式 |
| 8 | 插件不存在时报错 | 引用一个不存在的插件名 |
| 9 | 切换前先校验 | 用坏模式切换，核对抛错且旧模式仍生效 |
| 10 | 切换是整体的 | 核对切换过程中没有部分应用的中间态 |
| 11 | 切换后核对残留 | 制造一个未释放的注册，核对被报告 |
| 12 | 来源追踪覆盖所有键 | 核对每个有效键都有来源 |
| 13 | 面向人的说明从声明派生 | 改一个能力，核对说明跟着变 |

第 4、6、11 条是这一篇的特色判据：它们分别检验"错误早发现"、"间接依赖被查"与"残留可见"。

### 3.7 实现顺序

先做声明与组合（判据 1、2、3、12），再做校验（判据 4、5、6、7、8），然后做切换（判据 9、10、11），最后做呈现（判据 13）。

## L4 运行与验证

### 4.1 三层验证

第一层是契约测试：按 3.6 的十三条判据逐条检查。

第二层是可复现性验证：在两个不同的环境（或同一环境的两次不同启动）里跑同一个模式，核对有效配置完全一致。这一层是"消灭隐式默认"这条要求的直接检验——它会把剩下的隐式取值暴露出来。

第三层是切换演练：在运行中切换模式数次，每次核对残留报告与能力集。这一层检验的是长期运行下的稳定性（单次切换成功不代表多次切换不累积残留）。

```powershell
node tests/ch05/p1-profiles.mjs                 # 契约测试（十三条判据）
node grade/ch05/negative-check-profiles.mjs     # 判分器的鉴别力
node tools/profile-diff.mjs --a=<A> --b=<B>     # 两个模式的有效配置差异
node tools/profile-explain.mjs --key=concurrency # 某个值来自哪一层
```

### 4.2 判据

做完这一篇的标志有三条：十三条判据全部通过；两个环境下的有效配置完全一致；以及连续切换五次之后残留报告为空。

## L7 挑战题（不给答案）

## L9 仍未解决（这一篇自己的缺陷）

| 缺陷 | 后果 | 修法 | 当初为什么这么写 |
|---|---|---|---|
| 能力集上限是人工设的 | 设小了拆模式、设大了共存时超预算 | 用实测的上下文占用反推上限 | 上限需要数据积累 |
| 切换时资源瞬时翻倍 | 资源紧张的机器上切换可能失败 | 分批切换（逐会话）或先释放再构造 | 整体切换的正确性优先 |
| 探测校验只覆盖关键能力 | 其余能力仍然可能首用失败 | 扩大探测范围（按成本分级） | 探测成本高 |
| 预设的继承未实现 | 相似预设要重复写 | 继承机制（挑战题第三题） | 深合并的语义在预设层还需细化 |
| 面向人的说明是文本 | 无法被下游自动使用 | 同时提供结构化输出 | 文本对人足够 |
| 模式的测试靠人工 | 声明与能力不一致时无人发现 | 自动测试（挑战题第五题） | 需要构造能力探针 |

第一条与第三条属于"参数与覆盖"，第二条与第六条属于实现与验证，第四条与第五条属于功能边界。第一条值得单独标记：它意味着能力集上限这个决定缺乏数据支撑，而它直接关系到 5.2 的多会话能否共存——约束的松紧在没有数据时只能靠经验，而这类经验参数会在规模化时成为瓶颈。

### 五个层次

| 层次 | 例子 |
|---|---|

### 五种提问模板

反例逼问：如果允许隐式默认，哪一类故障会变多。

边界追问：一个模式该包含多少个插件才算合理。

代价追问：整体切换的瞬时资源翻倍，代价落在谁身上。

替代对比：为什么能力集上限要在启动时校验而不是运行时。

验证追问：怎么证明"这份声明在另一台机器上行为相同"。

### 本篇引出的十二个问题

读懂层。 第一，模式与预设的差别是什么？第二，四层覆盖顺序是什么？第三，合并规则的两类是什么？

重建层。 第四，为什么必填项不能有默认值？第五，为什么禁止运行时环境推断？第六，为什么能力集要展开间接依赖？

设计层。 第七，校验的三层各查什么？第八，切换为什么要整体进行？第九，哪些注册项应当在切换后存活？

评审层。 第十，拿到一份模式声明，你会先检查哪一处？第十一，怎么判断该新增模式还是加预设？第十二，如果有人说"按机器规格自动调整并发更聪明"，你怎么回应？

### 问题升级练习

模糊问题：「我的 agent 在不同环境上行为不一样，怎么办？」

升级后的精确问题：

> 行为一致至少包含三件互相制约的事：**声明**（写清楚了什么）、组合（多层如何合并、谁覆盖谁）、以及校验（错误在哪里被发现）。
> 第一件与第二件互相制约——声明写得越全，组合规则的影响越小，而声明的维护成本越高。
> 我能不能为这三件事各找出一条**可检查的判据**？
> 特别是：有没有哪一条判据，是**能在第二台机器上验证的**？

提升点说明：原问题无法回答，因为"行为不一样"没有定位。升级后的版本把它拆成三件具体的事，指出声明完整性与维护成本的权衡，并追加以一个更强的问题：哪一条判据能在另一台机器上验证——因为只有那一条能证明可复现性。

一处需要修正的预判：0.5.2 把"预设"标为对 5.3 与 5.4 的中等依赖。读完之后要补一层方向：预设与权限的关系比预想的更强——一个预设的工具集实质上定义了权限的上界（1.7 的分析），因此 5.3 的权限设计会以预设为起点而不是从零开始。这条方向修正意味着 5.3 需要先读到预设的结构，而本篇的 `Preset` 定义（1.1）正是那个输入。

通向下一篇的桥。 本篇让一个进程能按需装配能力，而它留下了一个没有答案的问题：同一个进程里跑多条会话时，这些能力如何共存。模式与预设都是声明（它们描述"应该是什么"），而多会话引入的是运行期的问题：资源如何分配、状态如何隔离、观测如何按会话归因。

下一篇 `5.2 多会话与并发` 处理这件事。它与本篇的连接点有三处：能力集的预算分配（0.5.3 的第二条）、预设的会话级作用域（1.1）、以及切换时的分批策略（L9 第二条）。

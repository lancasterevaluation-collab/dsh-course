# Agent 开发方向 · 能力要求（教学大纲体）

> **这份文档是什么**：把面试题库里的题目**反推成能力要求**。题库回答的是"会被问什么"，这份文档回答的是"**应该具备什么能力**"——而后者才是学习目标。
> **写法约定**：每条能力用**行为动词 + 可验证的判据**写成。**没有判据的能力条目是空话**——所以每一条都给出"怎么证明你具备了它"。
> **四个层级**：L1 基础 → L2 核心 → L3 进阶 → L4 专家。**层级的划分依据是"独立承担的范围"**，不是难度。

---

## 一、总则

### 1.1 这个岗位要解决什么问题

Agent 开发岗的核心职责可以用一句话概括：**在模型之外，构建让模型能可靠行动的一切。**

这句话界定了边界与重点：

- **模型之外**——不训练模型、不调参、不优化推理内核；而是**上下文、工具、循环、状态、失败处理**；
- **可靠行动**——不是"能跑一次"，而是**能连续跑、出问题能查、成本可预测**；
- **一切**——所以这个岗位的知识面**宽而不深**（相对于模型研究者），但**在几个关键点上必须深**（工具系统、上下文工程、评估）。

### 1.2 四个层级与它们的判据

| 层级 | 独立承担的范围 | 判据（能证明你到了这一层） |
|---|---|---|
| **L1 基础** | 能在给定设计下写出正确的实现 | 能实现一个工具、一个状态机，并**说明它的失败路径** |
| **L2 核心** | 能独立设计一个可用的 harness 模块 | 能从零设计工具系统 / 上下文管理 / 会话层，**并给出验收判据** |
| **L3 进阶** | 能对一个系统做生产级改造 | 能**测量**并**优化**成本、延迟、可靠性，且**改动可回滚** |
| **L4 专家** | 能定义架构与跨系统契约 | 能设计协议层、多智能体协作、自进化闭环，**并为它们划定边界** |

### 1.3 与面试题库的对应

**本文档的每一条能力，都能在题库里找到对应的检验形式**（见 §七 的映射表）。这个对应关系是双向的：

- 学习时：按能力条目去练；
- 准备面试时：按题库去检验。

## 二、L1 基础能力

**这一层的共同特征是：可以"照着设计做"，不需要自己定架构。**

### 2.1 语言与类型系统

**熟练掌握 TypeScript 的类型系统，能够用类型表达设计约束，而不只是用它做语法检查。**

具体要求：

- 能**用类型编码"允许做什么"**：例如用联合类型表达"副作用等级"，让非法组合在编译期被拒；
- 能**区分类型层面的依赖与运行时依赖**（`import type` 不产生运行时依赖），并**在分析依赖关系时正确区分它们**；
- 能**读懂类型错误并定位到设计问题**——当一个类型很难表达时，通常说明设计有问题；
- 能**使用类型守卫与判别联合**（discriminated union）处理多形态数据，并对封闭联合使用 `assertNever` 保证穷尽。

**可验证的判据**：给定一个模块，能说出它的类型签名**没表达什么**（时序、错误语义、所有权），并给出改进方案。

**对应题库**：Q2.1.1（工具接口的设计意图）、Q2.1.3（`sideEffect` 与 `idempotent` 两个字段为什么是类型的一部分）

---

### 2.2 异步、并发与取消

**熟练掌握异步编排，能够正确处理"什么时候等、什么时候不等、什么时候取消"。**

- 能**区分"并发"与"并行"**，并知道在单线程事件循环里哪些操作是真正并发的；
- 能**正确传播取消信号**（`AbortSignal`），并保证取消路径上的资源被释放；
- 能**识别"忘了 await"** 这类错误——它不会报错，但行为会不同；
- 能**用超时保护不确定的等待**，并**在超时后清理而不是泄漏**。

**可验证的判据**：给出一个"起了后台任务，然后主流程出错"的场景，能写出**在错误路径上也清理干净**的代码。

**对应题库**：Q2.4.1（长驻进程里的 trace 为什么会丢）、Q2.1.1（并行调用工具时的时序问题）

---

### 2.3 测试与调试

**熟练掌握"用证据说话"的调试方式，能够区分"看起来对了"与"真的对了"。**

- 能**为失败路径写测试**，而不只是 happy path（**没有负面判据的测试集测不到真正的风险**）；
- 能**用外部工具否定程序自己的报告**——例如程序说"进程已杀掉"，就用 `tasklist`/`ps` 去确认；
- 能**构造最小复现**，并**在复现失败后先怀疑自己的假设**；
- 能**区分"测试挂了"与"契约变了"**，并知道前者该改测试、后者该改契约或加兼容层。

**可验证的判据**：能用一句话说清"我怎么知道这个改动没有破坏别的东西"。

**对应题库**：Q2.3.3（评估的负对照）、Q2.4.2（排查五步）

## 三、L2 核心能力

**这一层要求"从零设计一个模块"，并给出它的验收判据。**

### 3.1 工具系统设计

**能够独立设计一个工具系统：定义接口、约束参数、分类失败、并让工具选择可测量。**

- 能**从"模型不能执行任何东西"这个约束推起**，推导出完整的调用流程与两道关卡（校验 / 权限）；
- 能**设计参数的约束 schema**，并说明每类约束（类型 / 枚举 / 格式）挡住的是哪一类错误；
- 能**区分协议级错误与工具级错误**，并给出可操作的判别方法；
- 能**为工具系统设计评估**：构造含**负对照**的用例集，测量工具选择准确率；
- 能**在"拆细"与"合并"之间做裁决**，并说明裁决依据是可测的，而不是偏好。

**可验证的判据**：给定一组模糊需求，能设计出 5–8 个工具的接口定义，并说明**为什么不是别的切分方式**。

**对应题库**：Q2.1.1、Q2.1.2、Q2.1.3、Q2.1.4

---

### 3.2 上下文工程

**能够管理模型的上下文预算：知道什么该进、什么该出、以及每种取舍的代价。**

- 能**从注意力机制的结构推出上下文腐化**（$n^2$ 的规模增长与注意力摊薄），而不是把它当成经验；
- 能**设计压缩策略**，并说明**保留什么、丢弃什么、以及为什么这个选择是缓存友好的**；
- 能**实现渐进披露**，并**说明它的适用边界**（当"判断所需信息"不比"使用所需信息"少时，收益消失）；
- 能**设计记忆的分层与写入规则**，并**如实说明哪些规则没有权威出处**；
- 能**测量上下文策略的效果**：成功率随填充率的变化曲线。

**可验证的判据**：能画出一次任务中"上下文里有什么"的分解图，并指出**每一项的进出理由**。

**对应题库**：Q2.2.1、Q2.2.2、Q2.2.3、Q2.2.4、Q2.2.5

---

### 3.3 会话与状态管理

**能够把"一次运行可用的系统"改造成"跨进程可用的系统"。**

- 能**坚持"只有一个真相源"**，并把它作为可恢复性的前提；
- 能**实现恢复**：读事件 → 校验 → 用既有纯函数算出派生视图，**而不是序列化内存状态**；
- 能**识别"恢复时唯一需要额外处理的东西"**（如计数器接续）并说明为什么；
- 能**设计数据格式的演进**，并意识到**一旦落盘，格式就变成契约**。

**可验证的判据**：关掉文档，能写出"重启后能接着聊"的会话层，并给出它的验收判据。

**对应题库**：Q2.4.3（前缀稳定性与持久化的关系）、Q3.1.2（两个写无法原子化）

---

### 3.4 循环与错误处理

**能够设计 agent 循环：处理停止原因、区分错误、控制重试、并在失败时给出模型能理解的反馈。**

- 能**处理停止原因分支**（正常调用 / 输出被截断 / 最终回答），并说明**截断为什么会导致"半个工具调用"**；
- 能**按"失败发生在哪一侧"分类错误**，并**说明误分类会让模型做出什么错误反应**；
- 能**设计重试策略**：区分可重试与不可重试，并**确保重试不破坏幂等性**；
- 能**设计"拒绝"的表达**：让模型知道"为什么不行"，从而不重复尝试。

**可验证的判据**：给定一个失败场景，能说出**模型会怎么反应**，以及**你希望它怎么反应**。

**对应题库**：Q2.1.1（五步状态机）、Q2.1.2（错误分类）

## 四、L3 进阶能力

**这一层要求"对已有系统做生产级改造"，并且改动是**可测量的**。**

### 4.1 可观测性

**能够把"看不见的运行"变成"可查询的记录"，并用它回答具体问题。**

- 能**设计 trace/span 的层次结构**，让"谁调用了谁"无需从日志顺序推断；
- 能**为每类 span 定义它让什么变成可评估**（如 `function` span → 工具选择准确率）；
- 能**处理敏感数据与合规约束**（如零数据保留组织无法使用追踪——**这是硬约束，不是配置**）；
- 能**识别长驻进程里的可观测性陷阱**（批量导出可能导致最后几条记录丢失）。

**可验证的判据**：给定"用户说这个回答不对"，能在**五分钟内**定位到具体是哪一步异常。

**对应题库**：Q2.4.1、Q2.4.2

---

### 4.2 评估体系

**能够搭建可重复的评估：定义判据、控制方差、并判断"改进是否显著"。**

- 能**区分"理解阶段"与"比较阶段"**，并说明为什么前者从 trace 开始、后者才需要数据集；
- 能**计算所需的样本量**：给定要检测的差异 $\Delta$，算出需要的用例数，**并说明为什么 10–20 个用例只能发现大幅回归**；
- 能**设计负对照**，抓"过度触发"这类只在负例里暴露的失败；
- 能**按判据的性质选择 grader**：能写成检查的用确定性 grader，剩下才交给模型评分；
- 能**量化方差**（标准误与置信区间），并**说明高方差如何转化为"可承诺能力下降"**。

**可验证的判据**：能回答"这次改动让系统变好了吗"，并给出**统计上站得住**的答案。

**对应题库**：Q2.3.1、Q2.3.2、Q2.3.3、Q2.3.4

---

### 4.3 成本优化

**能够把成本写成公式，找出高杠杆项，并用测量验证优化有效。**

- 能**分解成本**：输入 token × 单价 + 输出 token × 单价，并识别出**缓存命中率是高杠杆变量**；
- 能**理解前缀缓存的机制约束**（必须从第 0 个 token 起匹配、有最小存储单位、best-effort）；
- 能**列出会让缓存失效的设计**，并说明**为什么"每轮重新摘要"是最隐蔽的一类**；
- 能**采集真实的命中率数据**（而不是估算），并**按会话聚合**；
- 能**给出量级**：命中率从 95% 掉到 30% 会让输入成本变成约 8.7 倍（**在示例价格比例下**）。

**可验证的判据**：能回答"我的优化到底省了多少"，并给出**来自服务端的数字**。

**对应题库**：Q2.4.3

---

### 4.4 沙箱与安全边界

**能够划定"什么能做什么不能做"，并在无法验证的地方用限制能力代替校验。**

- 能**区分强制型约束与信任型声明**（如"声明只读"是信任型，框架无法验证）；
- 能**用限制能力解决信任型问题**（让声明只读的工具在只读环境里执行，**而不是试图校验它**）；
- 能**设计环境清理**（抹掉凭据类环境变量），并说明它挡住的是哪一类事故；
- 能**如实标注限制**：哪些约束在哪些平台真实生效、哪些只是声明。

**可验证的判据**：能指出一个系统里**至少一处"声明了但无法验证"的地方**，并给出"限制能力"的修法。

**对应题库**：Q2.1.3（信任型声明的修法）、Q2.5.2（sampling 的分权设计）

## 五、L4 专家能力

**这一层要求"定义架构与跨系统契约"。**

### 5.1 协议与集成

**能够设计或评估一个集成协议，并说明它解决的成本结构问题。**

- 能**从"集成成本是乘法还是加法"推起**，量化协议的价值（$N\times M$ vs $N+M$，以及比值随规模的增长）；
- 能**读懂协议规范**：消息格式、生命周期、能力协商，以及**"必须/可选"的划分理由**；
- 能**处理多端点场景**：命名空间、失败隔离、权限统一——并**说明哪些是协议不覆盖、必须由实现方决定的**；
- 能**识别协议的演进风险**，并在引用时**说明依据哪一版**。

**可验证的判据**：能评估"该不该引入某个协议"，并给出**成本对比**。

**对应题库**：Q2.5.1、Q2.5.2、Q2.5.3

---

### 5.2 多智能体与任务分解

**能够判断"要不要多智能体"，并说明这个判断的依据来源。**

- 能**从"自主性层数决定失败面"推起**，说明多一层自主性新增哪一类失败；
- 能**给出"是否采用多 agent"的判据**——**由评估驱动，而不是由偏好驱动**；
- 能**设计上下文隔离**（子 agent 返回浓缩摘要），并**说明它的代价**（主 agent 无法判断摘要是否可靠）；
- 能**测量交接准确性**（多 agent 独有的评估项）。

**可验证的判据**：能回答"这个任务该不该拆成多 agent"，并给出**可测量的依据**。

**对应题库**：Q2.3.2（交接准确性）、Q2.5.3（多端点）

---

### 5.3 自进化机制

**能够设计一个"会改自己"的系统，并为它划定安全边界。**

- 能**设计记忆的写入与撤销**，并说明**为什么"错的记忆比没有更糟"**；
- 能**设计技能/知识的沉淀格式**，并说明**为什么人类可读的格式值得用它换查询性能**；
- 能**设计演化的门控**：提议 → 评估 → 门控 → 回滚，**每一步都留证据**；
- 能**为自改设计审计链**，并说明**可追溯性为什么是安全的前提**。

**可验证的判据**：能说出"这个系统改了它自己之后，我怎么知道它改了什么、以及怎么撤回去"。

**对应题库**：Q2.2.4、Q2.2.5

---

### 5.4 性能与规模

**能够在规模上升时保持系统可用，并知道瓶颈在哪一层。**

- 能**做延迟分解**（模型决策 / 工具执行 / 框架开销 / 追踪），并**先测量再优化**；
- 能**识别"加机器无效"的情形**（如热点 key——分片按 key 哈希，同一 key 永远在同一分片）；
- 能**判断瓶颈层次**：是模型、是工具、还是框架；
- 能**为规模变化准备降级路径**（限流、熔断、部分降级），并**说明降级的代价**。

**可验证的判据**：给定"延迟翻倍"的报障，能说出**先测哪一项**。

**对应题库**：Q2.4.1（延迟分解）、Q3.1.1（热点为什么加机器无效）

## 七、自评清单

**用法**：对每条给出 0–3 分（0 = 不知道，1 = 知道概念，2 = 能讲清，3 = 能动手做并说明判据）。**总分低于 60% 的层级是当前该补的重点。**

### L1

- [ ] 能用类型表达设计约束（不只是语法检查）
- [ ] 能区分类型依赖与运行时依赖
- [ ] 能正确处理取消信号的传播与清理
- [ ] 能为失败路径写测试
- [ ] 能用外部工具否定程序自己的报告

### L2

- [ ] 能从"模型不能执行"推起，推导工具调用流程
- [ ] 能区分协议级错误与工具级错误，并给出判别方法
- [ ] 能设计含负对照的工具选择评估
- [ ] 能从注意力结构推出上下文腐化
- [ ] 能设计缓存友好的压缩策略
- [ ] 能说明渐进披露的适用边界

## 八、这份文档与题库的关系（写给使用者）

**题库回答"会被问什么"，这份文档回答"该会什么"。** 两者不是替代关系：

| | 题库 | 能力文档 |
|---|---|---|
| 组织方式 | 按主题（工具、上下文、评估…） | 按**能力层级**（能独立承担什么） |
| 单位 | 一道题 | 一条能力 |
| 检验 | 能不能答出来 | 能不能**做出来并说明判据** |
| 用途 | 准备面试 | **规划学习** |

**建议的使用顺序**：先用这份文档定位自己在哪一层，再按缺失的能力去题库找对应的题，最后**用自评清单的判据检验**——**而不是把自评清单当成需要背的清单**。

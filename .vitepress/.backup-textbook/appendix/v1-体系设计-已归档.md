## 一、参考来源（为什么这套指南可信）

**原则：只引用"有出处、可查证、且被长期验证"的东西。**

不引用：AI 生成的碎片文章、内容农场的"10 个 PM 技巧"、没有署名的方法论。

### 1.1 产品经理能力框架（来自公司公开材料）

| 来源 | 它给出的东西 | 我们怎么用 |
|---|---|---|
| **Google APM 的 L3 PM Rubric** | 五个能力类别：analytics / cross-functional collaboration / craft & execution / product insight / strategic insight，每类分四档（Poor→Outstanding） | 作为「能力分级」的骨架（每篇文档的 L6 分级判据参照它） |
| **Google PM 面试的四类题** | product design / analytical / strategy / behavioral（"Googleyness"） | 作为习题的四个大类 |
| **Google 的技术门槛**（FAANG 中最高） | 技术面试**不考编码**，考"能不能跟工程师对话、在架构层面推理" | 这直接定义了本指南第三册的目标：**会读、会问、会判断**，不是会写 |
| **Meta RPM** | 明确不要求技术背景；看重分析、领导力、沟通；鼓励非传统背景 | 说明"没有工程背景"不是死刑，但**有**是巨大优势（本指南押注这一点） |
| **Amazon PM / PM-T 分轨** | PM（业务向）与 PM-T（技术向）；PM-T 要"深入技术"、"端到端 owner" | 作为「产品经理的职业分叉」的一个参照点 |

> **一条从这些材料里读出来的共同点**（三个框架都指向它）：
> 技术能力的要求**不是写代码**，是**能在约束下做判断**。
> 这句话决定了整本指南第三册的写法 —— 它教判断，不教语法。

### 1.2 软件工程经典（书籍，不是文章）

| 书 | 核心贡献 | 本指南用在哪 |
|---|---|---|
| **Code Complete**（McConnell） | 构造的完整实践手册：设计 → 编码 → 测试 → 维护 | 第三册的"一个功能的一生" |
| **Domain-Driven Design**（Evans, 2003） | 三原则（聚焦核心域 / 用领域模型承载复杂设计 / 与领域专家持续协作）+ 术语：Ubiquitous Language、Bounded Context、Context Map、Aggregate、Anti-Corruption Layer | 第三册的"接口与契约"、第四册的"概念模型" |
| **Refactoring**（Fowler & Beck） | 在测试保护下持续改善结构 | 第三册的"技术债"、第五册的"变更管理" |
| **SICP**（Abelson & Sussman） | 抽象、模块化、元语言抽象；"程序是写给人读的" | 第三册的"抽象层级" |
| **Site Reliability Engineering**（Google） | SLI/SLO/SLA、**错误预算**、消除 toil、无指责复盘 | 第六册的"指标体系"、第五册的"事故复盘" |

### 1.3 跨领域产品开发（软件之外）

**为什么必须看非软件领域**：因为它们处理的是**不可逆的约束**（钢铁、模具、模具的模具），
而软件工程师最缺的恰恰是"不可逆感"。

| 来源 | 核心贡献 | 本指南用在哪 |
|---|---|---|
| **Toyota 的 SBCE**（Set-Based Concurrent Engineering，Sobek/Ward/Liker 1999） | 三条原则：① 画出设计空间（探索多套方案而不是一套）② 用交集整合（找可行集的交集，施加最小约束）③ **先证明可行再承诺**（逐步收窄，一旦承诺就不轻易改） | 第四册的"方案设计与收窄"、第五册的"承诺与变更" |
| Toyota 的工具集 | Trade-off curves（取舍曲线）、**A3 报告**（一页纸的问题与决策）、LAMDA 循环、PDCA | 第七册的写作训练（A3 是本指南"决策记录"的模板来源） |
| **SpaceX 的 The Algorithm**（Musk，见 Isaacson 2023 传记） | 五步：质疑每一条需求（每条必须能追到一个**具名的人**）→ 删除（删不够 10% 说明删得不够）→ 简化优化 → 加速 → **最后才自动化** | 第四册的"范围与边界"、第三册的"复杂度来源" |
| **IJEMS 的 hardware-native 工程管理**（University of Debrecen） | 五原则：先仿真后制造 / 风险先于吞吐 / **决策质量先于速度** / 显式管理不可逆 / 让硬件·软件·AI 各按自己的节奏走但守住接口 | 第三册的"可逆与不可逆"（这一步的理论基础） |
| 中国航天的"归零 vs 试错"讨论 | 两条路互补：试错高效但暴露问题晚时代价高；归零严谨但慢 | 第五册的"发布策略" |

> **跨领域对照给出的最重要一条**：
> 软件的"可以随时回滚"是一种**特权**，不是常态。
> 一个 PM 如果不理解这一点，他就无法判断"哪些事可以快、哪些事必须慢"。

## 四、习题体系设计（以 dsh-mini 为对象）

### 4.1 为什么用 dsh-mini 当习题对象

| 理由 | 说明 |
|---|---|
| **它是真项目** | 不是玩具示例：有 62 个文件、12667 行、真实的决策记录与已知缺陷 |
| **它的每个决策都留了论证** | `docs/*.md` 里有"决策表 + 代价落在谁身上"—— 这是**范例库**，你可以对照学习 |
| **它有已知的缺陷清单** | 每篇文档的 L9 都列了"现在这里就是不够好" —— 这是现成的**判断题素材** |
| **它还没做完** | 24 步路线图里 18–24 未实现 —— 这是现成的**设计题素材** |
| **你能改它** | 零依赖、无构建、`node src/apps/verify.ts` 就是验收 —— 改动的反馈回路是分钟级 |

**这一点很重要**：习题必须作用在"能被验证"的对象上。
如果习题对象是一个你无法运行、无法测量、无法改动的系统，那它只能练"说"不能练"判断"。

### 4.2 五类习题与它们的训练目标

| 类型 | 练什么 | 形态 | 验收方式 | 产出物 |
|---|---|---|---|---|
| **拆解类** | 从现成系统里读出结构、约束、取舍 | 给你一个模块/一个决策，让你拆 | 与文档里的原始论证对照（有标准答案） | 拆解笔记 |
| **判断类** | 在信息不全时做取舍并论证 | 给定场景 + 约束，让你决定并写理由 | 用"是否可证伪、是否给了代价、是否留了回退"三条判 | 决策记录（A3/ADR） |
| **写作类** | 把判断变成别人能执行的东西 | 写 PRD / 复盘 / 汇报稿 | 自检清单（能否零追问开工） | 真实文档 |
| **度量类** | 把"感觉"变成可测量的东西 | 为某功能设计指标并算基线 | 指标是否**可观测、可归因、不易被刷** | 指标定义表 + 脚本 |
| **工程类** | 读懂并在约束下改动真实代码 | 读码 / 改码 / 加测试 / 验证 | `verify.ts` 通过 + 你不破坏现有不变量 | 可运行的改动 + 证据 |

### 4.3 习题的难度分级

| 级别 | 标记 | 判据 | 对应能力分档（参照 Google 的四档） |
|---|---|---|---|
| 读懂 | ★ | 能解释"为什么这么设计" | Borderline |
| 改动 | ★★ | 能按需求改一处并说清牵连 | Solid |
| 重建 | ★★★ | 关掉文档能自己设计出来 | Outstanding（入门） |
| 判断 | ★★★★ | 在新场景下做取舍并论证 | Outstanding |
| 定义标准 | ★★★★★ | 能给别人定判据 | 超越四档框架 |

### 4.4 每个习题必须包含的六件事（这是习题质量的判据）

```
① 场景：在 dsh-mini 的哪个部分、当前状态是什么
② 任务：你要产出什么（一句话说清交付物）
③ 约束：不能用什么（比如"不许改 kernel"、"只能用现有扩展点"）
④ 判据：怎么算做对了（可自检，不依赖他人打分）
⑤ 陷阱：这道题最容易错的三个地方（做错了会怎样）
⑥ 延伸：做对之后追问的三个问题（通向下一层能力）
```

### 4.5 习题与问题清单的对应

每个习题都标注它练的是 `问题清单.md` 里的哪几条。
**这样你能验证"练了之后分数真的涨了"**：

```
习题 3.5-A（给 dsh-mini 的 8 个改动标回退难度）
  → 练的是问题 4.4（不理解可逆与不可逆）
  → 做完后，4.4 这一条应从 0 分变 2 分
  → 证据：你写的那张分级表（能拿出来给人看）
```

**没有对应问题的习题是坏习题**（它要么练了个不存在的缺口，要么缺口没被识别出来）。

## 五、与教学 skill 的对接

每篇文档按 `.skills/hands-on-harness-course/SKILL.md` 的 **16 节结构**写成 **≥80 KB**：

| skill 要求的节 | 本指南里它对应什么 |
|---|---|
| 元信息 | 篇号 / 主题 / 时长 / 目标级别 / 对应的问题清单条目 |
| 本篇新词 | 本篇首次出现的术语（PM 术语 + 工程术语） |
| 第 0 节 · 成品预览 | "学完你能做出什么"（具体到作品） |
| 第 0.5 节 · 系统视角 | 这篇在整个能力结构里的位置 + ≥3 个连锁影响 |
| L0 要解决的问题 | 从 `问题清单.md` 里取对应条目，给**具体现象** |
| L1 设计与原理 | 方法本身（含来源引用与替代方案） |
| L2 决策表 | 决策 × 选择 × 替代 × **代价落在谁身上** |
| L3 实现（逐行讲解） | 把方法**用在 dsh-mini 上**的完整演示（含真实代码/文档片段） |
| L4 运行与验证 | 怎么验证你学会了（验收判据） |
| L5 语法速查 | 本篇出现的术语与模板速查 |
| L6 关文档重写判据 | ★ 分级——你能独立做到哪一步 |
| L7 挑战题 | 不给答案的设计题 |
| L8 自检清单 | 理解 / 应用 / 判断 三层 |
| L9 仍未解决 | 这套方法本身的缺陷（诚实清单） |
| L10 提问训练 | 本篇引出的好问题 + 问题升级练习 |
| L11 系统影响回溯 | 回看 0.5 节，哪些预判被推翻 |

**与 skill 的一处必要偏离（必须先说清）**：skill 的铁律要求"L3 的代码块与真实文件一字不差"。
但产品管理的方法论**没有"真实文件"** —— 它的 L3 只能是：

```
用例（dsh-mini 的真实片段）+ 我的分析（逐段解释"这里体现了什么原则/违反了它"）
```

所以在 PM 篇目里，L3 是**案例逐段解析**，不是源码逐行讲解。
这个偏离会在每篇的元信息里显式标注，不藏着。

## 六、推进方式

### 6.1 写作顺序（不是按册号）

```
第一批（打地基，先写）：1.1 → 1.2 → 1.3 → 1.5
    理由：这四篇是后面所有篇的"术语与语法"，先写它们才能保证后面统一

第二批（你的核心缺口）：3.1 → 3.2 → 3.3 → 3.5 → 3.4 → 3.6 → 3.7 → 3.8 → 3.9 → 3.10
    理由：路线 C 的全部内容

第三批（习题）：7.0 → 7.5 → 7.1 → 7.2 → 7.6
    理由：有前三批的方法，习题才有判据可依

第四批（补齐）：第一册剩余 → 第二册 → 第四册 → 第五册 → 第六册
```

### 6.2 每篇的产出规格

- 单篇 **≥80 KB**（低于此值说明密度不够 —— skill 的硬指标）
- 16 节结构齐全
- L9 至少 3 条**真实缺陷**（不是"以后会做"）
- 每篇至少 **6 个 dsh-mini 的真实片段/案例**（不能空谈）

### 6.3 规模与节奏（如实说明）

```
48 篇 × ≥80 KB ≈ 3.8 MB 以上
按每轮产出 1 篇计 ≈ 48 轮
```

**这个规模必须说清楚**，因为它决定了推进策略：

| 策略 | 做法 | 适合 |
|---|---|---|
| **按路线打通** | 先只写路线 C 的 14 篇（工程强化），其余按需 | 你想尽快能用上 |
| **按册推进** | 一册一册写完整 | 你要完整的知识体系 |
| **先出最小闭环** | 1.1/1.2 + 3.1/3.5 + 4.5 + 5.3 + 7.0/7.5/7.6（9 篇） | 你想最快跑通"问题→方案→交付→度量→复盘" |

## 七、这份体系设计自身的缺陷（诚实清单）

| 缺陷 | 后果 | 修法 |
|---|---|---|
| **48 篇的写作量极大** | 可能需要数十轮才能写完，中途可能失去动力 | 先走路线 C（14 篇），用可见的进度换取持续性 |
| **PM 篇目没有"真实代码"可逐行讲** | L3 只能是案例解析，密度比工程篇低 | 用真实项目文档（dsh-mini / DSH 的 Agent Notes）当"源码" |
| **能力分级是自评** | 自评容易高估 | 每个习题要求**产出物**；产出物是他人可检验的 |
| **参考来源偏西方大厂** | 可能不适用于国内中小团队 | 在第四、五册里补国内工程的现实约束（人少、周期短、文档弱） |
| **没有真实面试与晋升路径的内容** | 学完不等于拿得到 offer | 需要单独一篇（暂编为 7.7）：作品集、面试、能力证明 |
| **习题答案会随 dsh-mini 演进过期** | 代码改了，题目里的行号与结构就错了 | 习题只引用**结构性事实**（文件职责、扩展点），不引用行号 |

# 三合一能力要求（产品 × 工程 × Agent）

> **这份文档是什么**：把三个方向的能力**重新组织成一份**。它不是三份文档的相加——**相加得到的是清单，交集得到的才是能力**。
> **核心命题**：**设计一个 agent harness 这件事，天然同时需要产品判断、工程原理与技术实现。** 本课程的全部设计都建立在这个命题上。
> **写法约定**：每条能力用行为动词 + 可验证判据；**没有判据的条目是空话**。

---

## 一、为什么是"三合一"

### 1.1 三个方向各自解决什么

| 方向 | 它回答的核心问题 | 它最擅长的动作 |
|---|---|---|
| **产品经理** | **做什么、为什么做** | 取舍、定义成功、在信息不全时判断 |
| **软件工程** | **怎么做得可靠** | 契约、可验证性、失败处理、演进 |
| **Agent 开发** | **怎么让它动起来** | 上下文、工具、循环、评估 |

**三者的差别不只是"关注点不同"**，而是**它们处理的是同一个系统的不同侧面**：

```
做 harness 时：
    "这个能力值不值得做"        ← 产品问题
    "它怎么被别人依赖而不出问题"  ← 工程问题
    "它怎么和模型协作"          ← Agent 问题
```

**而这三个问题无法分开回答**——因为**一个能力的设计同时决定了这三件事**。

### 1.2 交集是什么

**三个方向两两之间都有交集，而三者的共同交集是"能力"的**：

| 交集 | 内容 | 例子 |
|---|---|---|
| 产品 × 工程 | **"代价"这个概念** | PM 说"替换成本"，工程说"破坏性变更的代价"——**是同一件事的两种说法** |
| 产品 × Agent | **"可测量"这个概念** | PM 说"北极星与护栏指标"，Agent 说"评估与负对照"——**是同一套方法论** |
| 工程 × Agent | **"契约"这个概念** | 工程说"接口承诺"，Agent 说"工具 schema 与错误分类"——**是同一个机制** |
| **三者共同** | **在不确定下做出可验证的选择** | 见 §二 |

### 1.3 为什么三者共同的那个交集才是关键能力

**因为三者共同的交集回答的是同一个问题**：

> **在没有充分信息、资源有限、且结果不可完全预测的情况下，如何做出一个"事后能被检验"的选择？**

这个问题在三个方向里有三种表现形式：

| 方向 | 表现形式 |
|---|---|
| 产品 | "这个功能该不该做" |
| 工程 | "这个方案该不该选" |
| Agent | "这个上下文策略该不该用" |

**而它们的解法是同一套**：

```
① 明确"成功"的判据      （否则无法事后检验）
② 找出最便宜的不确定降低方式（否则是赌博）
③ 判断可逆性            （决定要多慎重）
④ 设置复盘点            （决定何时重新评估）
```

**这套解法就是三合一的实质。** 本课程第 1 卷（判断力地基）讲的正是它。

## 二、三合一的四个支柱

**把三个方向的能力重新组织，可以得到四个支柱。** 每个支柱都由三个方向共同支撑——**这是这份文档与三份单方向文档的根本差别**。

### 支柱一 · 判断

**能够在信息不全、资源受限的条件下，做出可被事后检验的选择。**

| 方向 | 它对这个支柱的贡献 |
|---|---|
| **产品** | 取舍框架（RICE / KANO）、用户价值公式（含**替换成本**）、"哪些不做会翻车" |
| **工程** | **代价分析**：每个方案牺牲什么、代价落在谁身上；可逆性分级 |
| **Agent** | **技术边界的判断**：这个能力该由模型、由框架、还是由提示词承担 |

**具体能力要求**：

- 能**先把"成功"定义下来**，再讨论方案——**没有判据的讨论会变成偏好之争**；
- 能**用代价语言描述每个选项**（"这个方案要付出什么、谁承担"），而不是用"好坏"描述；
- 能**判断决策的可逆性**，并**分配不同的谨慎程度**；
- 能**说出自己判断的依据类型**：是数据、是经验、还是推理——**这个区分本身是能力的一部分**；
- 能**在 30–60% 的信息量下决策**，并**明确指出哪些是未知**。

**可验证的判据**：给定一个"没有标准答案"的选择，能给出**判据、代价、可逆性、复盘点**四样东西，且**判据是可被第三方检验的**。

---

### 支柱二 · 表达

**能够把判断变成他人可依赖的形式——无论是需求、契约、还是接口。**

| 方向 | 它对这个支柱的贡献 |
|---|---|
| **产品** | 需求的三要素（为谁 / 解决什么 / 怎么算成功）；验收判据 |
| **工程** | **契约的三类承诺**（行为 / 时序 / 错误）；"不属于承诺的部分"要显式声明 |
| **Agent** | **工具描述的作用是"帮助选择"而不是"帮助理解"**；错误分类的表达 |

**具体能力要求**：

- 能**写出三类承诺**，并**知道缺哪一类会导致什么失败**（缺时序 → 难复现的 bug；缺错误 → 调用方无法写错误处理）；
- 能**显式声明"不承诺什么"**——因为按 Hyrum 定律，**未声明的行为也会被依赖**；
- 能**把成功判据写成可被独立检验的形式**（分子、分母、时间窗口、分析单位）；
- 能**按读者的决策点组织表达**：给模型的描述要帮助选择，给同事的需求要帮助决策；
- 能**在"承诺多少"上做取舍**：**承诺越少，演进越自由；但太少会让使用者猜测**。

**可验证的判据**：给定一份表达（需求 / 接口 / 工具描述），能指出**它漏了哪一类承诺**，并**说明这个遗漏会导致什么具体失败**。

---

### 支柱三 · 实现

**能够把设计变成可运行的系统，并**在实现中保持设计的意图**。**

| 方向 | 它对这个支柱的贡献 |
|---|---|
| **产品** | 最小可用版本的定义（**先跑通核心路径，再加边界情况**） |
| **工程** | 原子写、幂等、失败路径、可恢复性 |
| **Agent** | 上下文管理、工具调用、循环控制、状态机 |

**具体能力要求**：

- 能**从约束推起，而不是从模板推起**：例如从"模型不能执行任何东西"推出工具调用流程；
- 能**为每个设计点写出它的理由与代价**（`sideEffect` 字段为什么是类型的一部分、压缩为什么要固化压缩点）；
- 能**处理失败路径**，并**说明"哪些失败必须消除、哪些只需接受"**——**不是所有问题都必须解决**；
- 能**保持一个真相源**，并让其余数据都是它的派生（**这让"恢复"变成"重放"而不是"反序列化"**）；
- 能**识别"看起来在优化、实际在增加复杂度"的改动**，并有勇气拒绝它。

**可验证的判据**：给定一段实现，能说出**每个非显然的设计点解决了什么问题**，以及**去掉它会怎样**。

---

### 支柱四 · 验证

**能够证明系统真的按预期工作，并**在它不工作时定位到原因**。**

| 方向 | 它对这个支柱的贡献 |
|---|---|
| **产品** | 指标体系（北极星 / 过程 / 护栏）；**护栏指标防"短期优化伤害长期"** |
| **工程** | 监控与日志的分工（日志解释一次失败，指标发现趋势）；回归测试 |
| **Agent** | 评估流水线（trace → grader → dataset）；**负对照**；样本量的统计要求 |

**具体能力要求**：

- 能**区分"能跑"与"可靠"**，并**给出可靠性的判据**（连续 N 次成功、失败可归因、可回滚）；
- 能**设计含负对照的检验**——**因为"什么情况都触发"的失败只有在负例里才暴露**；
- 能**计算所需的样本量**，并**知道小样本能发现什么、不能发现什么**；
- 能**把一次具体的失败沉淀成永久的检查**（回归用例 / 检查项）；
- 能**用外部工具否定程序自己的报告**——**当程序说"已终止"时，去看进程列表**。

**可验证的判据**：给定"这个改动让系统变好了吗"，能给出**统计上站得住的答案**，而不只是单次运行的结果。

---

## 三、交叉能力矩阵

**这张表的读法**：左边是能力，右边三列是**三个方向各自提供的"料"**——**三列都有内容的能力，才是三合一的能力**。

| 能力 | 产品提供 | 工程提供 | Agent 提供 |
|---|---|---|---|
| **定义成功** | 北极星 + 护栏指标 | 验收判据（可被独立检验） | 评估用例与 grader |
| **判断代价** | 替换成本、用户价值公式 | 破坏性变更的代价、可逆性分级 | 成本公式（token × 单价 × 命中率） |
| **表达契约** | 需求三要素 | 三类承诺、显式声明不承诺 | 工具描述、错误分类 |
| **控制复杂度** | 最小可用版本 | 单一真相源、派生数据 | 上下文预算、渐进披露 |
| **处理失败** | 失败分析与复盘 | 失败路径、幂等、重试 | 错误分级、拒绝的表达、回退 |
| **证明有效** | A/B 与显著性 | 监控与回归测试 | trace 评估、负对照、样本量 |
| **管理演进** | 产品路径与验证点 | 兼容层、版本化、弃用周期 | 上下文策略与缓存的兼容性 |

## 四、四个层级

**划分依据仍是"独立承担的范围"，但每一层都要求三个方向同时达标**——**因为三合一是这份文档的命题**。

### L1 基础 · 能做对

**独立承担**：在给定设计下把一件事做对。

| 方向 | 要求 |
|---|---|
| 产品 | 能说清"为谁、解决什么、怎么算成功" |
| 工程 | 能写出接口的三类承诺，并说明缺哪类会怎样 |
| Agent | 能实现一个工具的完整定义，并说明它的失败路径 |

**三合一检验**：**给定一个明确需求，能写出它的验收判据、接口契约与失败处理，且三者互相一致。**

---

### L2 核心 · 能设计

**独立承担**：从零设计一个模块，并给出验收判据。

| 方向 | 要求 |
|---|---|
| 产品 | 能在多个需求间排序，并说明被牺牲项的代价 |
| 工程 | 能设计缓存 / 存储 / 接口，并给出容量与失效估算 |
| Agent | 能设计工具系统或上下文策略，并让它可测量 |

**三合一检验**：**给定一组模糊需求，能给出工具切分、优先级排序、与评估方案，并说明"为什么不是别的切分方式"。**

---

### L3 进阶 · 能改造

**独立承担**：对生产系统做改造，且改动可测量、可回滚。

| 方向 | 要求 |
|---|---|
| 产品 | 能定义改造的成功指标与护栏指标 |
| 工程 | 能诊断瓶颈（先测量再优化），改动可灰度可回滚 |
| Agent | 能搭建评估流水线，并判断改进是否显著 |

**三合一检验**：**给定"延迟翻倍且成本上升"的报障，能说出先测哪三项、改动后用什么指标验证、以及回滚条件。**

---

### L4 专家 · 能定义

**独立承担**：定义架构与跨系统契约，并在不确定中下注。

| 方向 | 要求 |
|---|---|
| 产品 | 能用"放弃什么"定义策略，并给出止损条件 |
| 工程 | 能设计分布式方案，并说明它放弃了什么（CAP 的具体取舍） |
| Agent | 能设计协议层、多智能体协作与自进化闭环，并划定边界 |

**三合一检验**：**给定一个需要长期投入的方向，能给出技术方案、产品路径、与验证计划，并说明"什么情况下我们会放弃这件事"。**

## 五、三合一自评清单

**用法**：每条 0–3 分。**重点看"三个方向都达到 2 分以上"的能力**——那是三合一开始成立的标志。

- [ ] 能先把"成功"定义下来再讨论方案（产品 / 工程 / Agent 都要有判据）
- [ ] 能用代价语言描述选项（产品：替换成本 ｜ 工程：破坏性变更 ｜ Agent：token 成本）
- [ ] 能判断决策可逆性并分配谨慎程度
- [ ] 能说出判断依据的类型（数据 / 经验 / 推理）
- [ ] 能在 30–60% 信息量下决策并指出未知

- [ ] 能写出三类承诺（行为 / 时序 / 错误）
- [ ] 能显式声明"不承诺什么"
- [ ] 能把成功判据写成可独立检验的形式
- [ ] 能按读者的决策点组织表达（对模型 vs 对同事）
- [ ] 能在"承诺多少"上做取舍

### 支柱三 · 实现

- [ ] 能从约束推起，而不是从模板推起
- [ ] 能为每个设计点说出理由与代价
- [ ] 能区分"必须消除的失败"与"可接受的失败"

### 支柱四 · 验证

- [ ] 能区分"能跑"与"可靠"，并给出可靠性判据
- [ ] 能设计含负对照的检验

- [ ] 能把一次失败沉淀成永久检查
- [ ] 能用外部工具否定程序自己的报告

## 六、三个方向各自的侧重（同一份能力的不同切法）

**虽然是"三合一"，但不同角色在这份能力表上的侧重点不同**——**明确这个差别，才不会把"三合一"理解成"要求每个人都全能"**。

| 能力 | 产品更重 | 工程更重 | Agent 更重 |
|---|---|---|---|
| 定义成功 | ✅ 指标设计 | 验收判据 | 评估用例 |
| 判断代价 | 替换成本 | 可逆性 | **成本公式** |
| 表达契约 | 需求 | **接口承诺** | 工具描述 |
| 控制复杂度 | 最小可用版本 | 单一真相源 | **上下文预算** |
| 处理失败 | 复盘 | **失败路径** | 错误分级 |
| 证明有效 | A/B | 监控 | **评估流水线** |
| 管理演进 | 产品路径 | **兼容层与弃用** | 缓存兼容性 |

**"三合一"的准确含义是**：**每个人都应当理解另外两个方向的贡献，并在自己的方向上把它们纳入判断**——**而不是每个人都要精通三个方向。**

## 七、这份能力表与课程、题库的关系

```
   能力要求（本文档）          回答"应该具备什么"
        │
        ├──► 课程 33 篇       回答"怎么学会"（按知识组织）
        │
        └──► 面试题库 v2      回答"怎么检验"（按题目组织）
                │
                └──► 最终产出：一个可运行的 harness
                     （能力只有通过做出来才算数）
```

**三者的分工**：

| | 组织方式 | 单位 | 用途 |
|---|---|---|---|
| 能力要求 | 按**能力层级** | 一条能力 | 规划学习、定位差距 |
| 课程 | 按**知识顺序** | 一篇 | 系统学习 |
| 题库 | 按**主题** | 一道题 | 检验与准备面试 |

**一条必须说清的话**：

> **这份能力表上的每一条，最终都必须在"做出一个 harness"这件事上兑现。**
> **能力不是读出来的，是做出来的**——这正是本课程把"从零构建一个 harness"作为唯一载体的原因。

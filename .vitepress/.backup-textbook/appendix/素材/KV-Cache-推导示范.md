# 第一部分 · 公开课：把 KV Cache 推导出来

## 1. 起点：一次自回归生成到底在算什么

### 1.1 注意力公式与它的三个张量

Transformer 的一层注意力做的是：

$$\text{Attention}(Q, K, V) = \text{softmax}\!\left(\frac{QK^{\top}}{\sqrt{d_h}}\right)V$$

三个张量各有明确角色：

| 张量 | 形状 | 它表示什么 |
|---|---|---|
| **Q（Query）** | $[S, H, d_h]$ | 每个位置"我想问什么" |
| **K（Key）** | $[S, H, d_h]$ | 每个位置"我能被问什么" |
| **V（Value）** | $[S, H, d_h]$ | 每个位置"我实际提供什么" |

而**因果掩码（causal mask）**规定：位置 $t$ 只能注意位置 $\le t$。**这一条是后面所有推导的前提**——它意味着每个位置**不会看到未来的 token**。

### 1.2 生成第 $t$ 个 token 时，到底需要什么

假设已经有 $t-1$ 个 token，现在要生成第 $t$ 个。这一步需要：

```
① 用第 t 个位置的隐藏状态算出 q_t、k_t、v_t
② 拿 q_t 去和【所有】位置的 key 算相似度：q_t · [k_1, ..., k_t]ᵀ
③ 用相似度加权【所有】位置的 value：Σ α_i · v_i
④ 得到第 t 个位置的输出
```

**关键点在第 ②③ 步**：它们用到了**从位置 1 到位置 $t$ 的全部 K 和 V**。

### 1.3 朴素实现有多浪费

如果不做任何缓存，生成第 $t$ 个 token 时要把前面 $t-1$ 个位置的 K、V **重新算一遍**（因为它们依赖于之前各层的输出，而重算前面的输出意味着重跑整个前向）。

**逐 token 的代价**：第 $t$ 步要算 $O(t)$ 个位置的 K/V。

**整个序列的代价**：$\sum_{t=1}^{n} O(t) = O(n^2)$ 次 K/V 计算，加上注意力本身的 $O(n^2)$ 每步 → **总计 $O(n^3)$**。

**⚠️ 这里的 $O(n^3)$ 是"不做缓存、每步重算前缀"的代价**（「推算」）。它说明了为什么必须缓存——**不是优化问题，而是可行性问题**。

## 2. 关键观察：哪些量变了，哪些量没变

### 2.1 一次对比

把"生成第 $t$ 个 token"与"生成第 $t+1$ 个 token"放在一起看：

| | 第 $t$ 步 | 第 $t+1$ 步 | 变化 |
|---|---|---|---|
| 需要的 $q$ | $q_t$ | $q_{t+1}$ | **变了** |
| 需要的 $k$ | $k_1..k_t$ | $k_1..k_{t+1}$ | **前面没变，只多了一个** |
| 需要的 $v$ | $v_1..v_t$ | $v_1..v_{t+1}$ | **前面没变，只多了一个** |

**这就给出了答案**：**$k$ 和 $v$ 的历史部分是可以复用的；$q$ 没有历史部分**。

### 2.2 用矩阵形状把这件事看穿

这是理解 KV Cache 最有效的一张图（「推算」，由因果掩码推出）：

```
生成第 4 个 token 时，注意力分数矩阵 Q·Kᵀ（4×4，下三角有效）：

            k1    k2    k3    k4
        ┌─────┬─────┬─────┬─────┐
   q1   │  ✓  │  ×  │  ×  │  ×  │   ← 上一轮已算过，且【不会再变】
        ├─────┼─────┼─────┼─────┤
   q2   │  ✓  │  ✓  │  ×  │  ×  │   ← 同上
        ├─────┼─────┼─────┼─────┤
   q3   │  ✓  │  ✓  │  ✓  │  ×  │   ← 同上
        ├─────┼─────┼─────┼─────┤
   q4   │  ✓  │  ✓  │  ✓  │  ✓  │   ← ★ 只有这一行是新算的
        └─────┴─────┴─────┴─────┘
          ↑     ↑     ↑     ↑
       这些列会被【后续每一个】新 token 再次使用
```

**这张图同时解释了两件事**：

**第一，为什么只算新的一行。** 因为因果掩码下，第 4 步只有 $q_4$ 这一行是新的；上面三行在第 1、2、3 步就算过了，而且**它们不会因为后面生成新 token 而改变**。

**第二，为什么缓存的是 K 和 V 而不是 Q。** 看方向——**行（q）只被用一次，列（k、v）被后续每一步复用**。

### 2.3 一句可以背下来的表述

「未核实原始出处，但这是行业内的常见表述」：

> 每个 token 生成时，它的 query 要问所有历史 token 的 key，并汇总所有历史 token 的 value。**但历史 token 已经"发过言"了——它们的 query 完成了使命，不会再被问第二次。** 所以我们保留未来还会用到的东西（K、V），丢弃已经用掉的（历史的 Q）。

**干净的版本**：**Q 是"每步一次性的"，K 和 V 是"每 token 的、会被复用的"。**

## 3. KV Cache 的数据结构与显存公式

### 3.1 缓存的形状

每层要缓存两个张量（K 和 V），每个的形状是：

$$[B,\ H_{kv},\ S,\ d_h]$$

- $B$：batch size（**每个请求各有一份**）
- $H_{kv}$：KV 头数（MHA 下等于注意力头数 $H$）
- $S$：已生成的序列长度（**它随时间增长**）
- $d_h$：每个头的维度

### 3.2 显存公式

$$M_{KV} = 2 \times L \times H_{kv} \times d_h \times S \times B \times b$$

| 符号 | 含义 | 说明 |
|---|---|---|
| $2$ | K 和 V 两个张量 | 这是公式里最容易被忽略、也最容易被面试官问到的系数 |
| $L$ | 层数 | 每一层都有自己独立的 KV cache |
| $H_{kv}$ | KV 头数 | MHA 下 $=H$；GQA/MQA 下更小 |
| $d_h$ | 头维度 | —— |
| $S$ | 序列长度 | **动态增长** |
| $B$ | batch size | 每个并发请求一份 |
| $b$ | 每元素字节数 | FP16/BF16 为 2 |

「文档」多个来源给出的公式一致（含 Sebastian Raschka 的架构综述、以及多份工程手册）。**注意 $H_{kv} \times d_h$ 在标准 MHA 下等于 $d_{model}$**——这给了公式一个更好记的形式。

### 3.3 算例：LLaMA-2 7B

**配置**：32 层、32 个注意力头、$d_h=128$、MHA（$H_{kv}=32$）、FP16（$b=2$）

**每个 token、每个序列的 KV cache**：

```
2 × 32(层) × 32(头) × 128(d_h) × 1(token) × 1(序列) × 2(字节)
= 524,288 字节
≈ 0.5 MB / token / 序列
```

**扩展到实际场景**：

| 场景 | 计算 | KV cache 占用 |
|---|---|---|
| 单序列 4096 token | 0.5 MB × 4096 | ≈ 2 GB |
| 4096 token × batch 32 | 2 GB × 32 | **≈ 68.7 GB** |
| 128K 上下文 × batch 1 | 0.5 MB × 131072 | **≈ 64 GB** |

「文档」这组数字来自一份公开的 worked problem（LLaMA-2 7B）。

**这个算例本身就是面试中的杀手级内容**——因为：

**第一，它给出量级感。** 一个 7B 的模型，权重在 FP16 下约 14 GB，而**32 个并发 4096-token 请求的 KV cache 就有 68.7 GB**——**KV cache 可以比模型权重还大**。这是"为什么 KV cache 是推理服务的核心约束"的量化依据。

**第二，它给出扩展律。** KV cache 对**序列长度**与**batch size 都是线性**的。所以：

```
吞吐量上限 ≈ (可用显存 − 权重占用) / (每序列 KV cache)
           = (80 GB − 14 GB) / 2 GB  ≈ 33 个并发 4096-token 序列（单卡 A100/H100 80GB，示例）
```

**⚠️ 这个"吞吐上限"的算法是「推算」**，用来说明 KV cache 如何直接决定并发量。**真实系统还要考虑碎片、激活值、以及框架开销**——所以实际并发会低于这个估算。

## 4. 为什么没有 Q Cache（一道经典题）

「文档」多个来源都提到这是**最常被问的 KV cache 面试题**。

### 4.1 答案

**因为 Q 的生命周期只有一步。**

回到第 2.2 节那张矩阵图：

- **每一行（$q_i$）** 在生成第 $i$ 个 token 时被计算一次，**之后再也不用了**——因为后面生成 token 时，用的是**那些新 token 自己的 q**，而不是 $q_i$。
- **每一列（$k_j$、$v_j$）** 则会被**后续每一个新 token** 用到——生成第 $j+1$、$j+2$、……、$n$ 个 token 时都要用。

**所以缓存的判据是"这个量将来还会不会被用到"**：K、V 会（被所有后续位置用），Q 不会（它的位置已经过去了）。

### 4.2 一个更本质的说法

从计算结构看：**解码时每一步只需要算一个 query**（新 token 的那个），注意力退化为：

$$q_t \cdot [k_1, \dots, k_t]^{\top}$$

**注意 $q_t$ 是一个向量（$1 \times d_h$），而 K 是一个矩阵（$t \times d_h$）**。所以"缓存 Q"没有意义——**因为根本不存在"历史的 Q 会被用到"这件事**。

### 4.3 追问：什么时候 Q 也会有缓存价值？

**在训练（或 prefill）阶段，Q 是需要被计算的**——因为那时所有位置都要算注意力，**每个位置都是"当前位置"**。

所以更准确的说法是：

| 阶段 | Q | K、V |
|---|---|---|
| **Prefill / 训练**（一次处理整个序列） | 所有位置的 Q **都要算**（且都要算一次） | 都用 |
| **Decode**（逐 token 生成） | **只有新 token 的 Q** 要算 | **全部历史的 K、V** 都要用 |

**这就解释了为什么"没有 Q cache"只在解码阶段成立**——而推理的生产环境里，**长尾的 decode 阶段正是主导成本的部分**。

## 5. 显存压力的解法族（三个层次）

这是本题最能体现深度的地方：**三种主流技术作用在三个不同的层次上**。把它们混在一起讲（"GQA 和 PagedAttention 都是为了省显存"）会显得只有记忆没有理解。

### 5.1 第一层：减少 $H_{kv}$（改变模型结构）

**MQA（Multi-Query Attention）**：$H_{kv} = 1$——所有 query 头共享**一对** K/V。

**GQA（Grouped-Query Attention）**：$H_{kv}$ 介于 1 与 $H$ 之间——query 头分组，**每组共享一对 K/V**。

「文档」GQA 的提出者的表述是："与其只用单一的 key-value 投影权重，不如使用 $n < n_{head}$ 个 key-value 投影权重……比如 2、4 或 8"，从而在几乎保留 MQA 全部内存与速度收益的同时减少质量损失。

**效果对比**：

| 方案 | $H_{kv}$ | KV cache 相对大小 | 质量 |
|---|---|---|---|
| MHA | $H$ | 1× | 最好 |
| GQA | $H_{kv}$（如 8） | $H_{kv}/H$（如 1/8） | 接近 MHA |
| MQA | 1 | $1/H$ | 有明显损失 |

「文档」**一个关键细节**：**减少 KV 头只在"使用缓存"时有帮助——不用缓存时峰值内存不变**，因为每个头仍然有自己的 query。

**这条细节很值得在面试里说出来**——它说明 GQA 省的是**缓存**，不是**计算峰值**。

### 5.2 第二层：压缩缓存表示（MLA）

**MLA（Multi-head Latent Attention）** 是 DeepSeek-V2 提出的方案，它**不是减少头数，而是改变缓存什么**。

**核心机制**（「论文」，arXiv:2405.04434）：

```
传统做法：缓存每头的 K、V             → 每 token 缓存 2 × H_kv × d_h 个元素
MLA 做法：把 K、V 联合压缩成一个低秩潜向量
           c_t^KV = W_DKV · h_t
           缓存 c_t^KV → 每 token 只缓存 d_c 个元素
           需要时再从 c_t^KV 重建每头的 K、V
```

**DeepSeek-V3 的实际配置**（「文档」）：`kv_lora_rank = 512`，`qk_rope_head_dim = 64`

所以**每 token 每层的缓存元素数** = $512 + 64 = 576$——**而它的 query 头数是 128**。对比同规模的 MHA（需要缓存 $2 \times 128 \times 128 = 32768$ 个元素），**这是约 57 倍的压缩**。

**⚠️ 上面这个"57 倍"是「推算」**（用配置数字直接算），**不是论文里的数字**。论文报告的口径是：

「论文」DeepSeek-V2 报告 **93.3% 的 KV cache 减少**与 **5.76× 的最大生成吞吐**——**但要注意**：第三方源分析指出，**这些数字是相对稠密 MHA 基线测的，不是与 GQA 的受控对比**。**引用时必须说明这一点。**

**两个关键机制值得讲**（它们展示了"为什么不能简单压缩"）：

| 机制 | 解决什么 |
|---|---|
| **吸收技巧** | 把上投影矩阵 $W_{UK}$ 折进 $W_Q$，让注意力**直接在潜空间上运行**——这让 decode 变得像 MQA，内存友好 |
| **解耦 RoPE** | 标准 RoPE（旋转位置编码）与压缩**不兼容**（位置敏感的旋转无法被吸收），所以 MLA **额外加一个小的共享 key** $k_t^R$ 专门携带位置信息 |

**第二行是一个"看起来是细节、实际是设计约束"的例子**——面试中讲出它，比只说"MLA 用低秩压缩"深一层。

### 5.3 第三层：管理已有缓存（PagedAttention）

前两层是**减少需求**，这一层是**更有效地管理已有的缓存**——**它不减少数学上需要的 KV cache 大小**。

**问题**（「论文」，arXiv:2309.06180, SOSP 2023）：早先的系统为每个请求**预分配最大序列长度的连续内存**，产生三类浪费：

| 浪费类型 | 成因 |
|---|---|
| **预留槽** | 为尚未生成的 token 预留 |
| **内部碎片** | 实际输出比最大长度短 |
| **外部碎片** | 不同请求大小造成的内存间隙 |

**后果的量化**：「论文」在先前系统中，**只有 20.4%–38.2% 的 KV cache 内存用于存储实际的 token 状态**。

**一个具体例子**（「论文」）：13B OPT 模型，单个 token 的 KV cache 需要 **800 KB**（$2 \times 5120 \times 40 \times 2$），所以 **2048 token 的序列需要最多 1.6 GB**——**一张 GPU 上只能放下几十个请求**。

**解法：借鉴操作系统的虚拟内存与分页**（「论文」）：

```
  逻辑视图（一个请求的序列）        物理视图（GPU 显存）
  ┌────┬────┬────┬────┐          ┌────┐ ┌────┐ ┌────┐
  │ B0 │ B1 │ B2 │ B3 │          │    │ │    │ │    │  ← 物理块散布在显存各处
  └────┴────┴────┴────┘          └────┘ └────┘ └────┘
     块表：B0→物理块 7                    每个块固定大小
           B1→物理块 2                    （如 16 个 token 的 K/V）
           B2→物理块 11
           B3→物理块 5
```

四个设计点：

| 设计 | 作用 |
|---|---|
| **固定大小的块** | 消除外部碎片（所有块同样大，任何空闲块都能用） |
| **非连续存储** | 块可以散布在显存里，不需要连续大块 |
| **块表映射** | 逻辑块 → 物理块，就像页表 |
| **按需分配** | 上一块满了才分配新块 |

**效果**（「论文」）：

| 指标 | 结果 |
|---|---|
| 内部碎片 | **< 1 块**（只有最后一块可能部分填充） |
| 外部碎片 | **消除**（所有块同大小） |
| 浪费 | 从 ~60–80% 降到 **< 4%**，内存利用率提升 **3–5×** |

**代价也明确**（「论文」）：PagedAttention 的注意力内核**比 FasterTransformer 慢 20–26%**（因为增加了块表间接寻址与非连续读）——**但内存节省带来的收益远大于这个开销**，整体吞吐反而提升 2–4×。

「文档」现代 vLLM 的默认 `--block-size` 是 **16**（32 也常用）。**块大小的权衡是**：块越大，内核并行度越高、延迟越低，但内部碎片越多。

**块粒度还带来一个额外能力**（「论文」）：**块级共享 + 写时复制**——并行采样共享 prompt 的物理块、beam search 动态共享与分叉、**前缀缓存**（重复的 prompt 只编码一次）。

### 5.4 三个层次的关系（这张表是本节的核心）

| 层次 | 方案 | 它改变了什么 | 它**不**改变什么 |
|---|---|---|---|
| **模型结构** | MQA / GQA | $H_{kv}$ | —— |
| **缓存表示** | MLA | 每 token 缓存多少元素 | 模型仍需重建 K/V |
| **内存管理** | PagedAttention | 缓存的**组织方式** | **数学上需要的 KV cache 总量** |

**最后一行是最容易被混淆的**：「论文」明确说明 PagedAttention **不减少给定模型与上下文长度所需的数学 KV cache 大小**——它只提高利用率。**把 PagedAttention 说成"省显存的技术"是对的，但说成"减少 KV cache"就错了。**

## 6. decode 的性能特征：为什么它是 memory-bound

这一节解释**为什么 KV cache 是性能瓶颈而不是计算瓶颈**——它是"为什么要优化 KV cache"的根本理由。

### 6.1 算术强度

**算术强度（arithmetic intensity）** = 每读一个字节能做多少次浮点运算（FLOPs/byte）。

**decode 阶段的算术强度极低**（「文档」）：

```
每生成一个 token：
  计算量 ≈ O(N × d)      （N 是序列长度，d 是维度）
  内存读取 ≈ KV cache 的全部内容（2 × L × H_kv × d_h × N × b 字节）
```

**关键**：**每一步都必须把整个 KV cache 从显存读一遍**——**即使序列已经很长**。

### 6.2 这带来的实际后果

「文档」一个具体例子：**Llama-3-70B 在 128K 上下文下，每一步要读几十 GB 的 KV cache**。

而计算量相比之下很小——所以**这一步的时间几乎完全由显存带宽决定**，而不是由算力决定。这就是"decode 是彻底的 memory-bound"的含义。

### 6.3 三个能说明问题的数字

「论文/文档」：

| 数字 | 含义 |
|---|---|
| **H100 的 BF16 roofline ridge ≈ 295 FLOPs/byte** | 超过这个强度才进入计算受限区 |
| **MLA 吸收后的 MQA 路径 ≈ 242 FLOPs/byte** | 接近 ridge，是"对 H100 的近乎完美拟合" |
| **GQA 的算术强度受限于组数** | 所以它的上限低于 MLA |

**这解释了 DeepSeek 为什么选 MLA 而不是 GQA**——**不只是省显存，还因为它把算术强度推到了更接近硬件拐点的位置**。

「文档」补充：MLA 的 MQA 路径把所有 query 头汇聚到一个共享潜向量上，**迫使张量并行把潜向量复制到每个设备上**（TP 不友好）——**所以 MLA 模型倾向于专家并行与流水线并行，而不是张量并行**。**这一条把"算法选择"与"并行策略"连了起来**，是深入的回答。

## 7. 代价与边界：什么时候 KV Cache 不值得

任何技术都要有它的适用边界——**只说好处不讲代价，在面试里是明显的减分项**。

| 代价 | 具体表现 |
|---|---|
| **显存占用随序列长度与 batch 线性增长** | 长上下文与高并发同时要时，二者直接冲突 |
| **decode 变成 memory-bound** | 算力被浪费（GPU 在等显存） |
| **分页带来内核开销** | 20–26% 的注意力内核延迟（「论文」） |
| **压缩可能损失质量** | MQA 有明显质量损失；MLA 的收益是在特定基线下测的 |
| **跨设备通信** | 张量并行下 KV cache 需要跨卡通信；MLA 的 TP 不友好 |

**什么时候不值得**：

- **短序列、低并发**：KV cache 的节省有限，而实现复杂度仍在；
- **一次性任务**（不需要多轮生成）：cache 的收益体现不出来；
- **显存极其充裕**（比如单序列小模型）：不做特殊优化也能跑。

# 第二部分 · 面试适配

**上面是"懂"。下面解决另一个问题：面试时不可能讲 8000 字，要怎么在 30 秒、3 分钟、以及深挖追问中分别把这件事说清。**

## 8. 三种时长的讲法

### 8.1 30 秒版（对方只想知道你懂不懂）

> "KV cache 缓存的是每一层前面所有 token 的 Key 和 Value。
>
> 理由很直接：**生成新 token 时，它的 query 要问所有历史 token 的 key、汇总所有历史 token 的 value——历史部分不会因为新 token 而改变，所以可以缓存。而 query 是每步一次性的**，所以没有 Q cache。
>
> 它的价值在于把每步的 K/V 计算从 O(t) 降到只算新 token 那一个，序列级的总代价从三次方降到平方。"

**这一版的关键是**：它同时给出了"缓存什么"、"为什么缓存它"、"收益是什么"。**而这三件事只需要三句话。**

### 8.2 3 分钟版（对方想看你有没有系统理解）

在 30 秒版的基础上加四件事：

**第一，显存公式与算例**（给自己一个数字锚点）：

> "它的显存是 **2 × 层数 × KV 头数 × 头维度 × 序列长度 × batch × 每元素字节数**。拿 LLaMA-2 7B 举例：32 层、32 头、128 维、FP16——**每个 token 每个序列约 0.5 MB**。那么 4096 token 的单序列约 2 GB，32 个并发就是 68 GB——**这已经比模型权重还大了**。"

**第二，性能特征**（说明为什么它是瓶颈）：

> "而问题还不只是显存。**decode 阶段的算术强度极低**——每一步都要把整个 KV cache 从显存读一遍，而计算量很小。所以 **decode 是 memory-bound 的**，GPU 大量时间在等显存带宽。"

**第三，解法族的三个层次**（这是最能体现结构感的部分）：

> "针对它的技术分三个层次，而且**作用对象不同**：
>
> **第一层改模型结构**——MQA 把 KV 头减到 1，GQA 分组共享，把 KV 头数从 $H$ 降到 $H_{kv}$；
> **第二层改缓存表示**——DeepSeek 的 MLA 不缓存每头的 K/V，而是缓存一个低秩潜向量，用时再重建；
> **第三层不动模型，只改内存管理**——vLLM 的 PagedAttention 借鉴操作系统的分页，把缓存切成固定大小的块、非连续存放、用块表映射。
>
> **这里有一个容易混淆的点**：前两层减少的是**数学上需要的缓存**，而第三层**不减少数学需要，它提高的是利用率**——论文里说，之前系统的利用率只有 20% 到 38%，分页之后浪费降到 4% 以下。"

**第四，代价**：

> "代价也有：分页带来 20% 到 26% 的注意力内核开销；压缩可能损失质量；而且长上下文和高并发在显存上是直接冲突的。"

### 8.3 深挖版（对方在往原理上追）

**当面试官开始追问时，用"从公式推"的方式回答，而不是堆事实。** 三个示范：

| 追问 | 深挖式回答的骨架 |
|---|---|
| "为什么没有 Q cache？" | 画矩阵图 → 指出**行（q）只用一次、列（k,v）被反复用** → 给出"生命周期"判据 |
| "GQA 为什么能省显存？" | 指出**它省的是缓存不是计算峰值** → 因为每个头仍有自己的 query → 公式里 $H_{kv}$ 变小而 $H$ 不变 |
| "MLA 和 GQA 有什么本质区别？" | GQA 减头数；MLA 换表示（低秩压缩 + 吸收 + 解耦 RoPE）→ 并指出**解耦 RoPE 是因为压缩与旋转位置编码不兼容** |

## 9. 十二个高频追问与答法

| # | 追问 | 答法要点 |
|---|---|---|
| 1 | **为什么是 KV 而不是 Q？** | 生命周期：Q 每步一次，K/V 每 token 且被后续全部复用 |
| 2 | **显存公式里的 2 是什么？** | K 和 V 两个张量——这是最常被漏掉的系数 |
| 3 | **KV cache 和 batch size 什么关系？** | 线性：**每个请求一份**，所以并发量直接受它限制 |
| 4 | **为什么 decode 是 memory-bound？** | 每步读全部 cache，计算量小 → 算术强度低 |
| 5 | **GQA 省的是计算还是内存？** | **内存（缓存）**；不缓存时峰值内存不变 |
| 6 | **MLA 压缩的是什么？** | 每 token 的 K/V → 一个低秩潜向量（+ 一个携带位置的共享 key） |
| 7 | **PagedAttention 减少 KV cache 吗？** | **不减少数学需要的大小，它提高利用率**（论文明确说明） |
| 8 | **块大小怎么选？** | 大块 → 内核效率高但碎片多；默认 16 |
| 9 | **前缀缓存依赖什么？** | 块级共享——相同前缀的请求共享物理块 |
| 10 | **长上下文与高并发能同时要吗？** | **在显存上直接冲突**（两者都线性增长） |
| 11 | **KV cache 能不能落盘？** | 「未核实」——这涉及具体框架的实现，本文档没有找到权威说明 |
| 12 | **MLA 的代价是什么？** | TP 不友好（潜向量要在每个设备复制）→ 倾向 EP/PP |

**其中第 11 条我如实标注为"未核实"**——**面试中不确定的地方应当说不确定，而不是编一个听起来合理的答案。**

## 10. 常见错误答法（按 §1.6.3 的淘汰信号）

| 错误 | 为什么错 |
|---|---|
| **只背"缓存 K 和 V 加速生成"** | 没有量化，无法应对"为什么"的追问 |
| **把前缀缓存说成"缓存计算结果"** | 混淆了两个层次——KV cache 是**模型内部的注意力缓存**，前缀缓存是**请求级别的复用**（后者借助前者的块共享实现） |
| **说 PagedAttention "减少了 KV cache"** | 论文明确说明它只提高利用率 |
| **给出记不准的公式** | 比如忘了系数 2、或把 $H$ 与 $H_{kv}$ 混用——**面试官一追问参数含义就会暴露** |
| **把 GQA 说成"为了加速"** | 它的直接作用是**减少缓存**；加速是间接结果 |
| **只讲 MLA 的"低秩压缩"** | 漏掉解耦 RoPE 这个**必需的配套设计** |

## 11. 与本课程的落点

KV Cache 属于**模型侧的推理优化**，它**不在本课程的核心范围内**（本课程的对象是"模型之外的一切"，即 harness）。但两者有两处真实连接：

**第一处：前缀缓存（prefix caching）是两者的交界。** DeepSeek 的上下文缓存要求"从第 0 个 token 起完全匹配前缀"（本课程第 3 章 Q2.4.3），而**服务端实现这种缓存的方式之一，正是 PagedAttention 的块级共享**——相同的前缀 → 相同的物理块 → 不需要重新计算。

**所以"harness 怎么组织请求"直接决定了"服务端能不能命中缓存"**：把稳定内容放前面、保持工具清单顺序稳定、压缩结果固化——这些 harness 侧的设计决策，收益**正是通过服务端的 KV cache 复用兑现的**。

**第二处：它是一个"跨层优化"的范例。** 从模型结构（GQA/MLA）到内存管理（分页）到请求组织（前缀稳定性），**同一个目标在三个不同的层次上被优化**。这正是本课程反复强调的那种思维——**认出同一个结构在不同层次的重复出现**。

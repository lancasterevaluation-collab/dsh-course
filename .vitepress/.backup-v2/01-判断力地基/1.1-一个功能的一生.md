## 本篇新词

这一篇的术语都指向同一类东西：一个改动从被想到到产生后果之间，会经过哪些环节，以及每个环节会留下或丢掉什么。它们不是流程管理的词汇，而是判断的依据——判断一个改动能不能快、该在哪里设检查点、出了问题能退到哪一步，都要用到它们。

交付路径指从"有人提出一个需求"到"用户真正用上它"之间的全部环节。本课程把它归纳成十站，而归纳的目的不是画出漂亮的流程图，而是让"这一步在干什么"变成可以逐站回答的问题。一个改动在这条路径上走过的距离越长，它在两端之间丢掉的信息越多，而"做完的东西不是当初要的东西"这个现象就发生在这条路径上。

信息损失指每一次转换（想法到文档、文档到方案、方案到代码、代码到上线）都会丢掉一部分原始意图，而丢掉的部分通常无法在后续环节补回来。它的价值在于给出了每道工序存在的理由：一道工序之所以必要，是因为它拦住了某一类信息损失。反过来，如果一道工序说不出它拦住了什么，那它很可能只是习惯。

可逆性指一个改动发生后能不能回到之前的状态，以及回到那个状态需要动什么。它与"改动大小"无关，与"副作用落在哪里"有关：改一段内存里的值与改一份已经被外部系统读取的数据，撤销成本相差几个数量级。Google SRE 里的错误预算是同一件事的财务化表述——把可接受的不确定性换算成时间份额（例如 99.9% 的可用性目标对应每月约 43 分钟），再让发布速度由这个余额约束。

里程碑指一个能提前暴露风险的检查点。它与汇报节点的差别可以用一句话检验：这个时点之后，哪一个不确定性消失了。答不上来的时点不是里程碑，只是日历上的一个日期。里程碑的位置由风险的分布决定，而不是由时间的分布决定。

验收判据指在动手之前写下的、"什么状态算完成"的可判定描述。它的判据是可否判定：能被第三方按文档复现的才算，需要当事人口头补充的不算。缺少它的项目里，"完成"会退化成主观判断，而交付过程会变成反复的拉锯。

灰度发布指先让一小部分流量或用户使用新版本，观察后再决定放量。它的价值在于把一次大赌注拆成若干次小赌注，而它的成本是需要一套流量分配与观测能力。灰度能否替代回滚，取决于新版本与旧版本能否同时存在——这一点由数据结构决定，而不是由发布工具决定。

回滚指把系统恢复到改动之前的状态。它有一个容易被忽略的前提：恢复的对象不仅是代码，还包括数据。代码回滚通常是分钟级的操作，而数据回滚可能是小时级的修复，或者根本不可能——这个差别正是本篇要建立的第一个直觉。

## 第 0 节 · 学完这一篇你能做出什么

### 0.0 先行组织者：十站与三个视角

这一篇建立一张可以默画的路径图，以及三个在路径上使用的判断。图与判断的关系是：图给出位置，判断给出该位置要回答的问题。

```
   ┌── 产出物 ────────┐  ┌── 这一站丢什么 ──┐  ┌── 可逆性 ──┐
① 问题定义         ② 可行性判断      ③ 方案设计
   给谁、什么场景      值不值得、代价      选哪个、放弃什么
        │                  │                  │
        ▼                  ▼                  ▼
④ 切分排期         ⑤ 实现            ⑥ 验证
   先做哪块、里程碑     代码、自测          它对了没有
        │                  │                  │
        ▼                  ▼                  ▼
⑦ 发布             ⑧ 观测            ⑨ 迭代或回滚       ⑩ 复盘
   给谁、怎么放量      有没有用            继续还是撤         判断质量
```

这张图的读法有三个方向。横向是从具体到抽象再回到具体：前三站回答"做不做、做什么"，中间三站回答"怎么做对"，后四站回答"它是否真的有效"。纵向是每一站的三个问题：产出物是什么、丢了什么信息、可逆性属于哪一级。如果只能记一件事，记纵向的三个问题——因为横向的十站会随项目形态变化（有的项目没有灰度、有的项目没有独立的验证阶段），而纵向的问题在任何流程里都成立。

### 0.1 一个具体的判断：给一个真实功能画出十站

这一篇的判断可以用一个具体动作来检验：从 `D:\dsh-mini` 里选一个你比较熟悉的功能（模式系统或上下文压缩都可以），把它走过的十站写出来，并在每一站标出三件事——这一站的输入来自哪一站、它的产出物是什么形态、撤销这一站的改动需要动什么。

多数人第一次做这件事时会卡在同一个地方：中间几站（④切分排期、⑥验证、⑧观测）写不出产出物的具体形态。这个卡点本身就是发现——它们的产出物在真实项目里常常是口头决定或者一次临时沟通，因此无人能复核。而 1.1 后半部分要处理的问题（信息在哪一站丢失、为什么"做完的不是要的"）正是在这些地方发生的。

### 0.2 本篇建立的三项判据

第一项用于检查信息损失：在每一站的出口问"这次转换丢了什么，后面的站还能补回来吗"。能补回来说明这一站有兜底，补不回来说明这一站承担了不可逆的转换，它需要更严格的输入检查。这项检查的用法不是逐站写报告，而是在改动之前定位"哪一站的输入最不可靠"。

第二项用于判断可逆性：问撤销它需要动什么。改内存里的值、回滚一次部署、修复已经生效的数据、以及无法撤销，对应四个等级，而它们决定了"哪些事可以快、哪些必须慢"。这项判断在发布策略上直接变成动作：可逆的改动可以直接全量，不可逆的改动必须先灰度并准备好补偿操作。

第三项用于设计检查点：问最大的不确定性最早能在哪一站被消除。答案决定了里程碑的位置，而里程碑的判据是"这个时点之后哪个不确定性消失了"。没有这条判据，检查点会退化成进度汇报，而风险会全部堆到最后一次性爆发。

### 0.3 十分钟练习：错误预算的算术

这项练习用一段可运行的算术把"可接受的不确定性"变成具体的时间，它也是本篇把流程判断与量化绑在一起的方式。

```js
// 错误预算：给定可用性目标与窗口，算出允许的不可用时长
function errorBudget(slo, windowDays = 30) {
  const minutes = windowDays * 24 * 60
  return { budgetMinutes: +(minutes * (1 - slo)).toFixed(1), totalMinutes: minutes }
}
console.log(errorBudget(0.999))    // 99.9% → { budgetMinutes: 43.2, totalMinutes: 43200 }
console.log(errorBudget(0.99))     //  99%  → { budgetMinutes: 432.0, totalMinutes: 43200 }
console.log(errorBudget(0.9999))   // 99.99% → { budgetMinutes: 4.3, totalMinutes: 43200 }
```

三个输出的量级差别解释了发布策略为什么要分级：99.9% 的目标下每月有四十三分钟可以花，99.99% 的目标下只有四点三分钟——后者经不起一次全量发布的事故。而错误预算的用法不是惩罚，而是决策依据：余额充足时可以加快发布，余额耗尽时应当优先修稳定性，而不是继续加功能。

> **面试视角**
> **高频问法**："你怎么判断一个需求该不该做、什么时候做？"
> **追问方向**："可逆性怎么影响你的发布策略？"落点是四级判断加上错误预算的算术：可逆的可以全量，不可逆的要灰度并且先准备补偿操作。
> **对应岗位**：产品经理、技术负责人、SRE。

### 0.5.3 三个连锁影响

**第一，跳过问题定义，整条链会为一个错误的问题服务。** 这条连锁的起点是不显眼的：直接开始讨论方案。它的后果按顺序展开——可行性判断失去参照（相对什么值得做），方案设计失去评价标准（相对什么更好），验证阶段拿不到判据（成功没被定义过），复盘无法进行（不知道当初的判断是什么，也就无法对账）。而最后一步的代价最大：失去对账能力意味着失去了通过项目积累判断力的通道。

这条连锁最值得注意的地方在于它的延迟：跳过第一步的成本不在当天显现，而在几个月后你想复盘时才发现无账可对，而那时你会以为是复盘方法不对，于是去找复盘模板——方向从一开始就错了。把它写成可执行的判据是：每一个功能都应当在动工之前写下一句可以被证伪的成功描述，没有这句话的功能无法被复盘。

**第二，在不可逆的一站上求快，一次事故会抹掉之前所有的节省。** 假设为了赶时间砍掉验证、直接全量发布，上线后发现问题时又有数据迁移已经执行，那么回滚代码解决不了数据问题，只能再写一个"迁移回来"的脚本——而那个脚本比原改动更危险，因为它是在事故压力下写的、且很少被测试过。事故时长因此从"五分钟回滚"变成"三小时改数据"。

这条连锁的一般形式是：节省是有上限的（省下的验证时间），而损失没有上限（事故时长 × 影响面），因此风险不对称的环节不能用同一种节奏对待。可逆性是判断哪些环节属于这类的地方。

第三，把里程碑设成汇报节点，风险会全部堆到最后。 汇报式里程碑（第二周汇报开发进度、第四周汇报联调进度）只回答"做了多少"，不回答"风险释放了没有"，于是真正的不确定性（性能够不够、迁移可不可行、依赖方能不能按时）一个都没被触碰，直到上线前一天才发现性能只有目标的十分之一，此时只剩下砍功能或延期两个选择，而两者的成本都远高于在第二周就发现它。

判断一个时点是不是里程碑，只需要问：这个时点之后，哪一个不确定性消失了。

一处需要说明的边界：这三条连锁都假设改动发生在一个有真实用户与真实数据的系统里。对一个没有用户的实验性项目，错误预算与灰度的意义都很小，而"跳过问题定义"的成本也会延后到它有用户时才显现。这不是说实验性项目不需要这些判断，而是说它们的检查点应当设在不同的位置——这一点在第 6 卷的实验方法里会展开。

> **面试视角**
> **高频问法**："你遇到过的最大的一次线上事故是什么？"
> **高分要点**：不要只讲现象，而要把事故放进这条路径——哪一站的产出物缺失导致了它、那一站的可逆性是几级、如果重来你会把检查点设在哪里。把事故讲成一次流程判断的失误，比讲成一次技术失误更有区分度。

## L0 要解决的问题

### 0.1 现象一：能说出"要做这个功能"，说不出它要经过哪些站

这一节要检验的东西很具体：拿一个你熟悉的功能，不看代码与文档，说出它从想法到上线经过哪些站，以及每站的产出物是什么。多数人给出的答案是"设计、开发、测试、上线"四步，而这四步里漏掉了六站——问题定义（为什么做这个而不是别的）、可行性判断（值不值得）、切分（先做哪块）、观测（上线后看什么）、回滚（错了怎么办）、复盘（学到了什么）。

漏掉它们不是记忆力问题，而是这六站在日常工作中很少被当成独立的环节，它们要么被压缩进"设计"里，要么根本没有人负责。

这个现象有一个可观察的代价。缺了问题定义的团队会在开发完成后才发现"要的不是这个"。缺了可行性判断的团队会做出技术上可行但没有价值的东西。缺了切分与观测的团队会把风险全部堆到上线那一刻。它们的共同点是缺失的环节在当时不可见——因为没有任何产出物会因此缺席，一切看起来都在推进。

### 0.2 现象二：把"先做什么"当成排序问题，而它实际是依赖问题

第二个现象在项目排期时出现：手上有一串要做的事，于是按"哪个更重要"排序。这个做法看起来合理，而它在有依赖关系的项目里会系统性地出错。`D:\dsh-mini` 的路线图给出了一个真实的例子（见它自己的 `docs/00-course-map.md` 的 Phase 5–7 规划）。

| 事项 | 依赖谁 | 依赖的原因 |
|---|---|---|
| 上下文压缩 | 无 | 可以立刻做 |
| 会话持久化 | 压缩点的事件格式 | 压缩点要落盘并能读回，格式定错了就要迁移 |
| 可观测 | 压缩与进程管理 | 它度量的正是那两层的耗时与收益 |
| 规模化 | 持久化与可观测 | 多会话需要存储与指标 |
| 自进化深化 | 持久化与授权 | 跨会话累积证据需要人把关 |

按重要性排序时，自进化深化很可能排在前面（它最像"产品的核心价值"）。而它在依赖图上必须排在最后，因为它的输入来自前四项。这个顺序错误的代价有固定的形态：你会做到一半发现证据没有地方存，于是回头补持久化，而此时你已经写了一批依赖旧结构的代码——补的东西与已写的东西之间需要一次改造，而那次改造的成本远高于一开始就按依赖顺序做。

判断的顺序因此是：重要性决定"值不值得做"，依赖决定"能不能做"。两者的关系不是竞争，因为它们回答的是不同的问题。而当两者冲突时，依赖优先——一个排在最前面但做不了的事，没有任何价值。

### 0.3 现象三：对所有改动用同一种谨慎程度

第三个现象是对可逆性的误判。同一份路线图上的四类改动，恢复代价相差五个数量级：

| 改动 | 做错了会怎样 | 恢复代价 |
|---|---|---|
| 改一句系统提示词 | 改回来即可 | 秒级 |
| 加一个插件 | 从 bundle 配置里删掉那一行 | 分钟级 |
| 改会话日志的事件格式 | 老日志读不进来，要写迁移脚本 | 小时级，且有风险 |
| 删除用户的记忆文件 | 数据没了 | 不可恢复 |

第三行是这一类里最值得记住的例子：它看起来只是一次格式改动，而它的不可逆性来自"日志是历史"——历史不能重写。它的特殊性在于代价的落点：提示词改错由你承担（改回来），日志格式改错由所有历史数据承担（写迁移），而删除记忆由用户承担（无法挽回）。

误判的表现形式有两种，方向相反。一种是在提示词这类可逆改动上犹豫过久（因为"要严谨"），另一种是在数据格式与删除操作上草率决定（因为"看起来是个小改动"）。它们的共同原因是判断依据用错了：依据不是改动的大小或复杂度，而是撤销它需要动什么。

### 0.4 现象四：说不出"完成"是什么

第四个现象在交付时出现：代码写完、功能能跑，但被问到三个问题时答不上来——它满足什么条件才算能用，什么情况下它算失败并且要回滚，以及怎么知道它真的被用上了。答不上来说明交付的是代码而不是一个被验证的能力。

这个现象有一个可诊断的根因：验收判据没有被提前写下来。判据写得晚（或没写）会带来两个后果。第一，判据会被方案定义出来——设计完之后再写判据，人会自动写出一个当前实现容易满足的判据，这不是造假，而是注意力的自然落点。第二，验证阶段会失去检查对象，于是它退化成"跑一遍看看"，而上线后的观测也失去对照（不知道该看什么指标）。1.1 后面的第 ⑥ 与第 ⑧ 站会分别处理这两处。

### 0.5 这一篇要正面回答的四个问题

四个现象收拢成四个问题。第一，一个功能要经过哪些站，每站的产出物是什么（1.1）。第二，信息在哪几次转换里流失最严重，怎么补（1.2 的表一）。第三，每站的可逆性差异有多大，它如何决定节奏（1.2 的表二与 1.5）。第四，检查点该设在哪里，判据是什么（1.2 的表三与十站中的第 ④ 站）。

四个问题的顺序不能颠倒，原因是它们的依赖：不知道有哪几站就定位不了损失点，定位不了损失点就判断不了可逆性，判断不了可逆性就无法决定检查点的位置。

## L1 设计与原理

### 1.1 十站与每站的四个要素

十站中的每一站都回答四个问题：输入来自哪一站、产出物是什么形态、最常在哪失败、以及这一站的可逆性属于哪一级。这四个问题应当成为该站产物的一部分——一份合格的产物不仅要写出结论，还要写清它的输入、它的判据（什么状态下它算完成）、以及撤销它需要动什么。缺了最后一项的产物在发布时会变成风险，缺了第三项的产物无法被复核。

#### 第 ① 站 · 问题定义

输入是一个信号（用户抱怨、数据异常、自己的观察、或者一项外部要求），产出物是一段问题陈述，它必须包含三样东西：谁在什么场景下遇到它、现在他们怎么凑合、以及可观察的证据。第三样是这一站与"感觉"的分界线——没有证据的问题陈述在后续任何一站都无法被证伪。

这一站最常失败的方式是把方案当问题，例如把"我们要做搜索"当成问题陈述（真正的问题是"用户找不到东西"）。检验方法是把陈述念给一个不在项目里的人听，看他能不能接出"所以你要解决的是……"。如果他反问"这算个问题吗"，说明你描述的是一个方案。可逆性：修改一句话的成本，完全可逆——因此这一站是全部十站里最应当反复推翻重来的地方。

`D:\dsh-mini` 的 `docs/18-compaction.md` 给出了一个合格的问题定义：它写了四个可复现的现象（成本随轮次线性上涨、大输出永久占据上下文、撞上限后硬失败、使用者不知道一次调用多贵），每个现象都带复现路径与代价量化。这份材料的价值不在结论，而在它把"为什么这是个问题"写成了可以被别人复核的东西。

#### 第 ② 站 · 可行性判断

输入是问题陈述，产出物是"做或不做的结论 + 代价估算 + 不做的后果"三项。这一站最常失败的方式是只算收益不算代价，或者缺少对照组——"不做会怎样"这一栏空着，而那一栏空着意味着还没有确认这是不是一个真问题。另一类失败是把"技术可行"当成"值得做"，两者的区别是：前者回答能不能造出来，后者回答造出来有没有用。

这一站的判据是反事实能不能填满。Toyota 的 set-based concurrent engineering 里有一条原则在此适用：先证明可行，再对外承诺（establish feasibility before commitment）。翻译成项目语言就是，在方案被验证之前不要承诺时间——因为承诺之后的每一次修正都要额外解释一次，而解释成本会反过来压缩探索空间。

可逆性：结论本身可改，但一旦对外承诺，撤销它的代价从"改一句话"变成"失信"。

#### 第 ③ 站 · 方案设计

输入是"值得做"的结论，产出物是两个以上差异化的方案，以及每个方案的代价与取舍理由。这一站最常失败的方式是只有一个方案（那不叫设计，叫执行），或者几个方案之间只差细节（那不是选择，是同一种写法的变体）。

判断两个方案是不是真选择，有一个可操作的判据：**它们的代价是否落在不同的人身上**。

`D:\dsh-mini` 的 `docs/17-modes.md` 里有一组合格的方案对比——让模式生成补丁（代价落在模式作者：必须写出完整配置，五个模式要复制五份）、把补丁改成深合并（代价落在所有补丁的使用者：破坏了已经文档化的"整段替换"规则）、新增一个行变换钩子（代价落在装载器的维护者：多一个扩展点要维护）。三个方案的代价分别落在三群人身上，这是一个合格的设计空间。

而如果三个方案的代价都是"多花两天"，那么这次设计实际上只有一个选项。可逆性：方案可改，但改动越晚代价越大——这正是"多想一天方案省下一周实现"这句话的量化依据。

#### 第 ④ 站 · 切分与排期

输入是选定的方案，产出物是一串能独立验证的小步、每个小步的验收判据、以及里程碑。这一站最常失败的方式是沿技术模块切分（先做后端再做前端）而不是沿用户价值切分，以及把里程碑设成汇报节点。

切分的判据是每一小块做完之后能不能独立判断它有没有用。如果答案是不能（"要等全部做完才知道"），那么切的是工作量而不是价值——这类切分会让风险集中在最后一块，而最后一块的失败会推翻全部。里程碑的判据是"这个时点之后哪个不确定性消失了"：证明"用现有的日志格式能恢复会话"是一个里程碑（它消除的是格式是否足够的疑问），而"后端开发完成"不是（它只说明花了多少时间）。

#### 第 ⑤ 站 · 实现

输入是切分后的第一块，产出物是可运行的改动，而它通常不是"完整的功能"。这一站最常失败的方式是实现者按自己的理解补全需求，以及范围悄悄变大——每一次补全都是一次信息漂移，而它不会出现在任何记录里（因为实现者认为那只是"细节"）。

这一站与第 ① 到第 ③ 站的转换是全链里信息损失最严重的两处（另一处是问题到方案的转换）。原因是需求里的每一句模糊描述都需要实现者猜一个具体行为，而猜的结果取决于他的经验。减小损失的办法只有一个：把验收判据提前写成可判定的形式，让它成为实现时的检查表，而不只是验证时的评分标准。可逆性：代码可逆（除非同时改了数据格式），但消耗掉的时间不可逆。

#### 第 ⑥ 站 · 验证

输入是可运行的改动与提前写好的验收判据，产出物是能复现的验证记录与已知的未通过项。这一站最常失败的方式有三种：验收判据写成"体验流畅"这类不可判定的描述、只测正常路径、以及自己验自己。

验证分三层，它们的负责方与检验时点不同。代码正确性（实现是否符合设计）由工程负责，检验方式是测试。行为正确性（它是否做了要求它做的事）由需求方与工程共同负责，检验方式是逐条核对验收判据。价值正确性（它是否解决了问题）只能在上线后由第 ⑧ 站回答。这一站最容易被跳过，原因是它不产出功能，只产出证据。而"没有证据的完成"会在第 ⑧ 站变成无法解释的现象。

可逆性：这一站完全可逆（尚未上线），因此它是全链里最便宜的纠错点。

#### 第 ⑦ 站 · 发布

输入是验证过的改动，产出物是上线记录与回滚方案。这一站最常失败的方式是全量发布（没有灰度）、没有写回滚步骤，以及把这一站当成一个动作而不是一个过程。它是十站里唯一必须提前判断可逆性的一站，因为这一站之后，代价开始由用户承担。

可逆性在这一站内部还要再分级：提示词与文案属于秒级，插件开关属于分钟级，代码逻辑取决于有无副作用，数据结构变更需要额外的迁移或补偿，删除数据不可逆。错误预算的算术在这里给出约束：99.9% 的可用性目标对应每月约四十三分钟，99.99% 对应约四点三分钟——后者的预算经不起一次全量发布的事故，因此高可用目标的系统必须依赖灰度与渐进放量，而不是靠回滚速度。

#### 第 ⑧ 站 · 观测

输入是上线的功能与在第 ① 站写好的成功判据，产出物是真实数据与"是否达到判据"的结论。这一站最常失败的方式有三种：当初没有埋点、口径不统一（不同的人算出不同的数）、只看主指标不看护栏指标。

这一站能否进行，取决于第 ① 站：那一站定义了成功，这一站才能回答是否成功，第 ⑩ 站才能对账判断质量。缺少第 ① 站的定义时，观测只能退回到"有没有人在用"这类粗指标，而对账只能得出"感觉还行"。可逆性：观测本身可逆，但错过观测窗口不可逆——用户流失之后无法补测。

#### 第 ⑨ 站 · 迭代或回滚

输入是第 ⑧ 站的数据，产出物是一个决定：继续投入、修改后继续、或停止并回滚。这一站最常失败的方式是沉没成本（"都做了一半了"），以及把"没人用"解释成"推广不够"。

这一站要问的不是"它好不好"，而是"我现在知道了什么新信息"。没人使用的可能原因有四种——方向错、实现差、场景未到、度量错——而它们的处置完全相反，因此第一步是花时间分辨是哪一种，而不是立即加大投入。可逆性：决定可逆，但每一次"再给它一点时间"都会消耗真实资源，而消耗掉的时间不产出信息。

#### 第 ⑩ 站 · 复盘

输入是第 ① 到第 ⑨ 站的全部记录，产出物是判断质量的评估。这一站最常失败的方式是变成总结会（讲做了什么），以及只记结果不记当初的判断。

复盘的唯一有效形式是对账：当初判断什么会发生（带时间与理由）、实际发生了什么、差异来自判断错误还是执行差异还是运气、下次遇到类似情况会改哪个环节。没有"当初的判断"就没有复盘，这是第 ①、②、③ 站必须留下书面产物的直接理由，也是"复盘基准要在第 ① 站写"这条规则的依据——三个月后你记得的已经不是当时真实的判断，记忆会被结果污染。

### 1.2 三张贯穿全链的表

#### 表一：信息损失最严重的两次转换

| 转换 | 丢掉什么 | 为什么必然丢 | 怎么补 |
|---|---|---|---|
| 问题到方案 | 场景细节、约束、真实动机 | 为了可执行，方案必须抽象化，而抽象就是丢细节 | 把"用户、场景、现在怎么凑合"固定写进方案文档的抬头 |
| 方案到实现 | 边界情况、判定标准、选择理由 | 实现者要补全一切未言明之处，而补全依据的是他的经验 | 验收判据提前写；把选择理由写进决策记录而不是口头交代 |

这两次转换的共同点是它们都发生在"人"身上，而不是发生在工具或流程上。因此它们无法靠增加流程环节来消除，只能靠把关键信息固定在产物里。 与之相对，问题到方案的转换还有一个数量级上的特点：它丢掉的通常是约束条件，而约束条件的缺失要到很晚才会暴露（实现到一半才发现某个前提不成立）。

#### 表二：可逆性地图

| 等级 | 典型改动 | 决定前的动作 |
|---|---|---|
| 秒级 | 提示词、文案、界面布局 | 可以直接改，多做实验 |
| 分钟级 | 代码逻辑、插件开关 | 准备好回滚版本，正常节奏 |
| 小时级 | 数据结构、接口协议、已落盘的格式 | 先设计后动，准备迁移或补偿 |
| 不可逆 | 删除数据、对外承诺、已流失的用户 | 多重确认加预案，并考虑是否需要人工审批 |

这张表回答的是项目里最常见的一句争论——"这个很急，能不能快一点"。可用的回答是：它可逆吗。可逆就快，不可逆就不快。这句话之所以有效，是因为它把争论从"急不急"（一个无法验证的强度描述）换成了"撤销要动什么"（一个可以当场回答的问题）。

#### 表三：各产物的最晚写出时刻

| 产物 | 最晚必须在什么时候写好 |
|---|---|
| 问题陈述 | 在讨论任何方案之前 |
| 成功判据 | 在设计方案之前，否则方案会定义出一个容易达成的判据 |
| 验收判据 | 在实现开始之前 |
| 回滚方案 | 在发布之前 |
| 复盘的对账基准 | 在问题定义那一站就写，因为那时还没有结果可以污染记忆 |

这五行的顺序反映了同一件事：越靠前的产物越便宜，而它的缺失越晚暴露。成功判据尤其值得注意，因为它有一处反向激励——设计完成之后再写判据，人会不自觉地写出一个当前实现容易满足的判据，而这不是造假，只是注意力的自然落点。

### 1.3 一次完整走查：把上下文压缩从 ① 走到 ⑩

前面给出的是地图，这一节把它走一遍。对象是 `D:\dsh-mini` 的上下文压缩（它的设计文档写在 `docs/18-compaction.md`，当时尚未实现）。每一站给出的是产物样例——样例的作用不是展示标准答案，而是说明一份产物写到什么程度才算合格：能被别人复核、能被后面的站直接使用。

#### ① 问题定义（产物：问题陈述）

```markdown
## 问题
使用它跑多轮任务的开发者，在会话进行到第 10 轮以上时想继续高效对话，
但每一轮请求都把全部历史原样重发，于是出现三个后果：
(a) 成本随轮次线性上涨；
(b) 一次 3000 行的文件读取输出会永久占据上下文；
(c) 超出模型窗口时任务直接失败，没有任何降级路径。

现在他们怎么凑合：手动开新会话（丢掉上下文），或者缩短任务（做不完）。

我们观察到的证据：
· deriveMessages() 没有任何上限，全部表面事件逐条展开（kernel/session.ts）
· 第 10 轮的消息数约为第 1 轮的 10 倍
· provider 返回 context_length_exceeded 时，重试策略不认这个错误码，直接抛错
```

合格的自检方式是：把"我们观察到的证据"三行拿掉，只留问题描述，看一个不在你项目里的人能否理解为什么这是个问题。能理解才合格。如果不能，说明描述里混进了只有内部人才懂的背景。

#### ② 可行性判断（产物：做与不做的对照）

| | 做 | 不做 |
|---|---|---|
| 预期收益 | 长会话成本下降；长任务可跑完；上下文信噪比提升 | —— |
| 代价 | 实现、测试与文档；摘要本身要花一次模型调用；摘要质量难以验证 | 撞窗口即失败（用户流失）；成本线性上涨 |
| 不做的后果 | —— | 这是一面必然会被撞上的硬墙，不是"可能出问题" |
| 判断 | 做 | |

这一站的自检是"不做的后果"那一栏不能空，也不能写"没影响"——写不出来的话，说明还没有确认这是不是一个真问题，应当回到 ① 站。另一个要点是这一站判断的是必要性而不是收益大小：压缩在短会话里的收益是负的（摘要调用的成本高于省下的），但它解决的是撞墙这个必然发生的问题，因此值得做。

#### ③ 方案设计（产物：两个以上差异化方案）

| 方案 | 做法 | 得到什么 | 失去什么 | 代价落在谁身上 |
|---|---|---|---|---|
| A · 改写历史 | 压缩后删掉被压缩的事件 | 日志变小，派生简单 | 破坏 append-only，历史不可复算，无法回退 | 所有依赖日志重建的人：诊断、演化、恢复 |
| B · 内存缓存 | 压缩结果存内存，派生时使用 | 实现最快 | "模型看到什么"不再能从日志重建，重放结果不同 | 排查者：永远答不出当时看到什么 |
| C · 压缩事件加派生视图 | 压缩写一条事件，派生时跳过该点之前的事件 | 不变量仍成立，可复算，可回退 | 派生多一层，日志多一类事件 | 实现者：多写一层 |

选择 C，理由写进决策记录：愿意承担"派生多一层、日志多一类事件"的代价，换取"模型可见的必须可重建"这条不变量在压缩之后仍然成立——因为这条不变量是会话日志存在的全部价值，也是后续诊断、恢复、演化三处的地基。

这一站的自检是三个方案的代价是否落在不同的人身上（日志使用者、排查者、实现者）。如果三个方案的代价都是"多花时间"，那它们不是真选择，只是同一个方案的三种写法。

#### ④ 切分与排期（产物：风险型里程碑）

先看反面教材，它按实现顺序排期，也是最容易犯的错：

```
第 1 周：写 kernel/compaction.ts
第 2 周：接线（plugins/compaction.ts）
第 3 周：加 /compact 命令
第 4 周：测一测
```

这四行回答的都是"做了多少"，而两个最大的不确定性——派生能否保持可复算、摘要质量够不够——一个都没被触碰，它们会在第四周一起爆发。

按风险释放排期的版本如下。

| 里程碑 | 消除的不确定性 | 验证方式 | 如果失败 |
|---|---|---|---|
| M1 | 派生视图确实是纯函数 | 同一份事件流跑两次，结果深度相等 | 说明派生逻辑里有隐藏状态，需重新设计派生接口 |
| M2 | 没有压缩点时行为与旧版完全一致 | 跑项目自检全绿；对比改动前后的消息数 | 说明引入了回归，先修好再往下 |
| M3 | 压缩之后不变量仍成立 | 自检里加一条断言；跑超阈值的会话 | 说明压缩破坏了不变量，回到 ③ 重新设计方案 |
| M4 | 大输出落盘后真的能读回 | 裁剪后读落盘文件，与原文比对 | 说明溢出方案有问题，改落盘策略 |
| M5 | 摘要质量够用 | 用摘要回答五个关键事实问题 | 说明摘要提示词要改，或压缩粒度要调 |

这一站的自检是每个里程碑能否填出"不再担心什么"，并且最难的那个不确定性是否排在前半段。M5 的排位需要判断：它最难验证（要设计问题集），但也最可能推翻整个方案。这里把它排在第五位，理由是 M1 到 M4 失败得更频繁而成本更低。如果你的答案是应当把 M5 提前，只要理由成立那就是对的——这一站没有唯一正确答案，只有有没有想过。

#### ⑤ 实现（产物：第一块可运行的改动）

第一块不是完整的压缩，而是 M1 需要的最小东西：令牌估算与派生视图两个纯函数，它们不依赖任何框架设施。

```ts
// 这一块做完就能独立验证 M1，不需要接任何插件
export function estimateTokens(messages: readonly ChatMessage[]): number
export function deriveView(events: readonly SessionEvent[]): DerivedView
```

先做纯函数而不是先接插件，理由是接线会同时引入两个变量（压缩是否正确、插件是否装上了），而调试时分不清是哪一个错了。这一站的自检是你能说出"这一块做完之后我能独立验证什么"。

#### ⑥ 验证（产物：验收清单）

```markdown
| # | 判据 | 怎么验 | 期望 |
|---|---|---|---|
| 1 | 未达阈值不压缩 | 短会话调用 compact('auto') | {compacted:false}，不写事件 |
| 2 | 压缩后不变量成立 | 跑超阈值会话 | 断言不抛；自检全绿 |
| 3 | 派生是纯函数 | 同一输入调两次 | 深度相等 |
| 4 | 压缩点之前的事件仍在日志 | 看 session.events | 一条没少 |
| 5 | 摘要失败时降级 | 让 provider 抛错 | 写一条降级事件；任务继续 |
| 6 | 不应该发生：短输出也落盘 | 读一个小文件 | spilled:false，内容原样 |
| 7 | 不应该发生：系统提示词被压掉 | 看派生结果的首条 | 仍是 system |
```

第 6、7 条是负面判据，它们验证的是"不该发生的事没有发生"。一份验收清单里没有负面判据，通常说明只考虑了正常路径——而正常路径恰好是最不需要验证的那部分。

#### ⑦ 发布（产物：回滚方案与放量方式）

```markdown
## 发布
方式：以插件形式提供，在配置里默认 disabled，先只在 ptc 模式启用
原因：压缩会改变"模型看到什么"，属于行为级改动，先限定影响面

## 回滚
触发条件（任一成立即回滚）：
  · 自检出现失败
  · 任务完成率比启用前下降超过 10%
  · 出现"模型忘记用户约束"的报告两次以上
步骤：
  1. 把配置里压缩插件的开关设为 disabled
  2. 重新装载（重启进程）
预计耗时：不到一分钟
不可逆部分：无。压缩只写事件，不删数据；新事件留在日志里不影响任何读取方
回滚后的数据状态：一致，多出来的压缩事件被忽略即可
```

这一站的自检是"不可逆部分"那一栏必须被认真回答。写"无"之前先问：这个改动有没有写入任何不能撤销的东西。

#### ⑧ 观测（产物：指标定义）

```markdown
| 指标 | 口径 | 数据来源 | 期望 | 护栏 |
|---|---|---|---|---|
| 净省下的 token | Σ(压缩后−压缩前) − Σ(摘要调用成本) | 压缩事件 | 大于 0 | —— |
| 触发频率 | 压缩次数 / 轮数 | 同上 | 小于 0.3，不应每轮都压 | 大于 0.5 说明阈值太低 |
| 摘要保真度 | 关键事实问题集的答对率 | 人工抽样 | 不低于 4/5 | 低于 3/5 说明摘要提示词要改 |
| 长会话完成率 | 超过 10 轮的会话中任务成功的比例 | 会话日志 | 不低于启用前的基线 | 下降超过 10% 即回滚 |
```

第三行值得单独看：它没有现成数据，需要人工抽样。这正是成功判据必须提前写的价值——因为在 ① 站就已经确认"摘要质量"是核心风险，所以到这一站手上已经有抽样方案，而不是上线之后才发现没有任何数据能回答它有没有用。

#### ⑨ 迭代或回滚（产物：决定规则）

```markdown
| 观测结果 | 判断 | 动作 |
|---|---|---|
| 净收益大于 0 且保真度不低于 4/5 | 有效 | 扩大：默认对所有模式启用 |
| 净收益大于 0 但保真度为 3/5 | 部分有效 | 改摘要提示词，重跑 M5 |
| 净收益小于 0（短会话为主） | 场景不匹配 | 只对长会话启用，按估算规模条件触发 |
| 完成率下降 | 有副作用 | 回滚 |
```

这一站的自检是是否提前定义了"什么时候放弃"。"再观察一周"是最贵的决定，因为它不产出信息，只消耗时间。

#### ⑩ 复盘（产物：对账表）

这张表的价值在于"当初的判断"那一列是在前三站写下的，不是事后补的。

```markdown
| 当初的判断（写下日期） | 实际发生 | 差异原因 | 下次改什么 |
|---|---|---|---|
| 01-15：压缩后成本会明显下降，因为长会话占比高 | 长会话只占 12%，整体成本下降 4% | 高估了长会话占比，没看数据就假设 | 下判断前先查一次分布 |
| 01-15：摘要质量是最大的风险 | 抽样保真度 4.5/5，不是瓶颈 | 低估了摘要提示词的效果 | 风险排序要靠证据，不靠直觉 |
| 01-20：M1 到 M4 会顺利 | M2 卡了两天，旧行为有隐藏依赖 | 低估了改动前行为的复杂度 | 先写改动前行为的测试，再动手 |
```

这一站是整个循环真正的产出物：它产出的不是功能，是判断力的修正。缺少这张表，做完十件事之后判断力不会变化。

### 1.4 走查之后应当看到的三件事

第一，最贵的错误不在实现里。 按成本排序，上面十站里最贵的三处错误是：问题定义时没查分布就下判断（差一点做出一个收益只有 4% 的功能）、切分时按实现顺序排里程碑（风险堆到最后）、观测前没准备抽样方案（无法回答摘要质量如何）。三处都不是编码问题。

第二，每一站都有可以省与不能省的部分。

| 站 | 可以省 | 不能省 |
|---|---|---|
| ① 问题定义 | 长篇背景 | 不做的后果 |
| ② 可行性 | 详细财务模型 | 对照组 |
| ③ 方案 | 三个以上的方案 | 至少两个差异化方案与它们的代价 |
| ④ 切分 | 详细排期表 | 至少一个风险型里程碑 |
| ⑤ 实现 | —— | 能独立验证的第一块 |
| ⑥ 验证 | 自动化 | 负面判据 |
| ⑦ 发布 | 分批灰度（小项目） | 回滚方案与不可逆部分 |
| ⑧ 观测 | 完整看板 | 能回答"成没成功"的一个数 |
| ⑨ 迭代 | 书面规则 | 什么时候放弃 |
| ⑩ 复盘 | 正式会议 | 当初的判断与实际结果 |

第三，能不能省取决于可逆性，不取决于忙不忙。 一个可逆的小改动（改提示词）可以把十站压到两站：想清楚、改、看结果。一个不可逆的改动（改日志格式）一站都不能省。判断自己处在哪一档，用的是 1.2 的可逆性地图。

### 1.5 十站的变体：探索型任务

前面十站描述的是执行型任务的形态：动手之前大体知道要做什么。项目里还有另一类任务，它的起点是"不知道该做什么"，例如"这个界面下一步该做什么"或者"用户到底卡在哪一步"。这类任务用同一张地图，但每一站的产出物不同——因为它的目标不是交付一个功能，而是把一个不确定性变成答案。

| 站 | 执行型（已知做什么） | 探索型（还不知道） |
|---|---|---|
| ① | 问题陈述（谁在什么场景缺什么） | 要回答的问题（这一轮要学到什么） |
| ② | 做与不做的收益对照 | 成本上限（这一轮最多花多少时间与资源） |
| ③ | 两个以上方案与取舍 | 两个以上可证伪的假设 |
| ④ | 切分与风险型里程碑 | 最便宜的证伪路径 |
| ⑤ | 实现第一块 | 做出验证材料（原型、数据查询、假门测试） |
| ⑥ | 验收判据 | 证伪条件（什么结果会让我放弃这个假设） |
| ⑦ | 发布与回滚 | 通常不发布 |
| ⑧ | 指标与基线 | 学到了什么（答案是什么、置信度多少） |
| ⑨ | 继续、修改、停止 | 转执行，或换一个假设 |
| ⑩ | 对账 | 对账（同样是"我当初猜对了吗"） |

两类任务的差别集中在第 ③、④、⑥ 站：执行型任务在第 ③ 站产出方案，探索型任务产出假设。执行型任务切分工作量，探索型任务找最便宜的证伪路径。执行型任务写验收判据，探索型任务写证伪条件。其余各站的形态相近，只是名词不同。

#### 1.5.1 一次探索型走查

以"这个界面下一步该做什么"为例。第 ① 站要回答的问题是：使用它的人（如果存在）在哪个环节放弃，具体到他们打开页面后发生了哪几种行为、各自占比多少。第 ② 站给成本上限：两小时，零行代码改动。第 ③ 站给三个可证伪的假设。

| 假设 | 如果成立，下一步做什么 | 什么结果会否掉它 |
|---|---|---|
| H1：打开后不提问就走了（不知道怎么用） | 加引导与示例 | 会话日志显示多数会话至少提了一个问题，则 H1 错 |
| H2：提问了但只用一次（没解决真实问题） | 去问那批人为什么不回来 | 多轮会话占比高，则 H2 错 |
| H3：根本没有人在用（它没被需要） | 停止投入 | 存在十个以上独立会话，则 H3 错 |

第 ④ 站的结论是一次数据查询：会话痕迹就在工作目录的会话文件里，不需要写代码、不需要用户访谈。第 ⑤ 站的验证材料是一份统计脚本的输出。第 ⑥ 站的证伪条件是上表第三列。第 ⑦ 站不产生任何面向用户的改动。

第 ⑧ 站给出的结论形态是"H1 被否掉（绝大多数会话至少提了一问）、H2 部分成立（单轮会话占多数）、H3 被否掉（存在二十余个独立会话），并因此产生一个新问题：单轮会话里任务成功的比例是多少"。第 ⑨ 站的处置是转执行型——去问那批单轮用户为什么不回来。第 ⑩ 站的对账记录两条判断错误：高估了"不会用"（因为自己是开发者，推己及人），低估了它被真实使用的程度（因为没看数据就假设）。

#### 1.5.2 探索型任务的三条纪律

成本上限是硬的。 没有上限的探索会退化为无限期调研，而调研是众多工作形态里最容易假装在工作、也最难被检验的一种——它永远有下一个要读的资料。给它一个硬上限（时间或动作数），到点必须给出结论，无论结论是"假设成立"还是"证据不足"。

假设必须能被否掉。 "用户可能在意性能"这样的表述无法被否掉，因为"在意"没有操作定义。而"如果响应超过两秒，单轮会话占比会明显上升"可以被数据检验——它给出了可测量的量与预期方向。判断一条假设是否合格的方法是问：什么数据会让我放弃它。如果任何数据都不会，那它不是一个假设，而是一种信念。

结论必须带置信度。 只说"单轮占七成"而不说样本量，会让后续决定建立在一个不可靠的数字上。合格的表述是"单轮占七成（样本二十三个，置信度低）"。当样本很小时，另一条更有用的做法是给出区间而不是点估计：二十三个样本、观察到十七个单轮，比例的粗略置信区间大约在五成到九成之间——这个区间宽到无法支撑"该去优化单轮体验"这样的决定，而它恰好说明了下一步该做什么：先扩大样本。

#### 1.5.3 什么时候从探索转入执行

转入执行的条件有三个：有一个假设成立，它已经被至少一次独立验证支持，并且你已经知道"它成立时该做什么"（第 ③ 站表的第二列已经回答了这一点）。三条同时满足就可以转，不必等到"完全确定"——那是永远不会到来的状态。判据是一个具体动作是否已经被证明有效，而不是信心有多强。

### 1.6 十站在本项目上的落地

前面几节讲的是方法，这一节把每一站挂到具体对象上，使判断能落到"在哪个文件、用什么命令"。

| 站 | 动作 | 产物放在哪 | 可用的现成材料 |
|---|---|---|---|
| ① 问题定义 | 看项目路线图里有哪一步对应当前问题；读若干设计文档的问题节，它们写了每一步要解决的真实现象 | `portfolio/<功能>/01-问题定义.md` | 设计文档的问题节是范例库，照它的写法写自己的 |
| ② 可行性 | 填写"不做会怎样"；对照路线图的依赖表看它是不是别人前提 | 同上 `02-可行性判断.md` | 依赖表在路线图第三节 |
| ③ 方案设计 | 写出两个以上差异化方案，照既有决策表的格式记录取舍 | 同上 `03-方案比较.md` 与 `04-决策记录.md` | 各篇讲义的决策表都是格式范例 |
| ④ 切分排期 | 把方案拆成能独立验证的块，每块写清"做完之后不再担心什么" | 同上 `05-里程碑.md` | 讲义里的实现顺序可以对照，但要注意它是实现顺序而不是风险顺序 |

| ⑥ 验证 | 写验收清单（含负面判据）并逐条跑 | 同上 `07-验收清单.md` | 项目自检脚本的断言结构是范例 |
| ⑦ 发布 | 写回滚方案，决定放量方式（在本项目里表现为先在某个模式下启用） | 同上 `08-发布与回滚.md` | 配置里的 `disabled` 字段就是开关 |
| ⑧ 观测 | 定义"怎么算成功"，写出数据从哪来 | 同上 `09-指标.md` | 会话痕迹文件是原始数据 |
| ⑨ 迭代 | 写下"什么时候放弃"的规则 | 同上 `10-决定规则.md` | —— |
| ⑩ 复盘 | 对账：当初的判断与实际结果 | 同上 `11-复盘.md` | —— |

这张表可以直接当模板用：按功能名建立目录，填完十一份产物，就是一份完整的交付包。

#### 1.6.1 一个三十分钟的练习

选一个本项目里已经做完的功能（模式系统或压缩都可以），倒着填上面这张表：它当初要解决什么（去它的设计文档的问题节找）、为什么值得做（收益与代价节）、有哪几个方案（决策表）、它是怎么切的、实现的产出是什么、验收判据是什么、用了什么发布方式、上线后看什么、什么时候决定继续还是停、复盘了什么。

这个练习会得到一个可预期结果：前六站能从文档里填出来，而后四站找不到材料。这就是本项目技术记录与产品记录之间的落差，它同时也是一条可迁移的观察——技术侧的记录通常很完整（设计文档、测试、实现顺序），而产品侧的记录常常是空白（发布方式、观测指标、停止规则、对账）。

### 1.7 十站的推导：为什么是这些，而不是别的

记住十个名字不足以应对新情况——遇到一个不在清单里的场景时，你不知道该加一站还是减一站。这一节从三条前提把十站推导出来，推导清楚之后，这张表就不再需要被背诵，因为每一站的必要性都可以在现场重新推出来。

#### 1.7.1 三条前提

前提一：一个功能的价值只在"用户真的用上、而且它确实起作用"的时刻才被兑现。 这条前提排除了两种常见的错觉。第一种是"代码写完就算完成"——代码写完时用户还没有用上，价值是零。第二种是"上线了就算完成"——上线只意味着用户可以用，不意味着他们在用，更不意味着它起了作用。

两种错觉之所以顽固，是因为它们各自对应一个明确的、可以庆祝的时间点，而"价值被兑现"往往没有仪式感，它表现为数据缓慢变化，或者根本不变化。

前提二：从"想做"到"价值兑现"，信息一定会损失，而且损失量与转换次数正相关。 损失不是沟通不到位造成的，而是抽象化的必然代价：把一个具体场景（某人在某个下午因为手上数据格式不对而卡了二十分钟）写成一句需求（支持导入 CSV）时，场景与时序被丢弃。工程师把这句话实现成代码时，必须自己补上所有未言明的细节，而每一次补全都是一次猜测。因此目标不是不损失，而是控制损失的量与位置。

前提三：每一次错误判断都有两种代价，即做错本身的代价，以及它被发现得有多晚。 这两种代价可以分别优化，而它们的最优策略经常矛盾：为了降低做错的概率，你会想多花时间讨论。为了降低发现得晚的损失，你会想尽快动手看结果。十站的设计本质上是在这两种代价之间找一个可操作的平衡。

#### 1.7.2 从前提到十站

因为前提二，每次转换都必须留下产物。 这是第 ① 到第 ④ 站存在的直接理由。如果想法只停留在讨论中，那么它被写成方案时，讨论中"为什么排除另一个选项"的推理就消失了。方案被实现时，方案中"边界情况怎么处理"的判断也消失了。让每次转换留下书面产物的意义不在给别人看证据，而在当后面某一站发现前面错了时，你还能知道当时根据什么判断。没有产物就没有追溯，于是同一个错误会在同一个地方反复发生。

因为前提三，检查点必须尽可能前移。 这决定了第 ② 站与第 ④ 站的形态。第 ② 站要在方案之前做，因为方案一旦写好，人会倾向于证明这个方案可行，而不是诚实评估这件事值不值得做。第 ④ 站的里程碑必须是风险型而不是进度型，因为进度型里程碑只报告投入量，而投入量与风险无关——你可以投入九成而最大的未知一点没变。把最贵的不确定性排在最前面验证，是用早发现换低损失。

因为前提一，链条必须延伸到上线之后。 这产生了第 ⑦ 到第 ⑨ 站。很多实践终止于代码合并，因为那一步把交付定义成"东西出去了"。而从前提一看，东西出去只是让价值有机会发生，之后还需要确认用户接触到了它、确认它产生了预期作用、以及据观测结果决定继续还是撤退。这三站常被省略，因为它们不产生新功能只产生判断，而判断在没有制度要求时最先被牺牲。

因为前提三区分了做错与发现得晚，不可逆的错误需要单独准备退路。 这是第 ⑥ 站与第 ⑦ 站里回滚部分的存在理由。这里有一个容易忽略的区分：可逆的错误与不可逆的错误需要的不是同一种谨慎。可逆的错误（改一句提示词）做错之后代价只是修复时间。不可逆的错误（重写历史数据格式、删除用户记录）做错之后代价是永久的。因此回滚方案不是发布流程里的可选环节，而是对"这一类改动到底能不能快"这个问题的正式回答。

因为前提三的两种代价都依赖"我当初怎么判断"，必须留下判断本身。 这是第 ⑩ 站的理由，也是十站里最容易被看成多余的一站。复盘的常见失败形态是变成工作总结，而这样的复盘无法改进任何能力，因为它完全没有触及"我当时的判断是什么、它错在哪里"。要修正判断就必须有原始判断的记录，这也是第 ① 站要写下"当初预期会发生什么"的原因——三个月后的记忆会被结果污染，你会不自觉地认为自己当时就觉得会这样。

#### 1.7.3 推导能回答的两个实际问题

什么时候可以少走几站。 答案取决于两件事：这一站的产物是否还能从别处得到，以及跳过它的错误是否可逆。如果一次改动小到"做错改回来只要一分钟"，那么花两小时写可行性分析就是浪费，跳过第 ② 站是合理的。同样的跳过放在"改变日志格式"上就不合理，因为那类改动做错之后的恢复代价远高于分析成本。因此用几站不是由工作量决定的，而是由可逆性与信息可得性共同决定的。

十站的顺序能不能换。 不能，因为顺序来自依赖关系而不是偏好。第 ③ 站必须在第 ② 站之后，因为"哪个方案更好"取决于"要解决什么问题、值不值得解决"。第 ⑥ 站必须在第 ⑤ 站之后，因为没有东西可验证。第 ⑩ 站必须在最后，因为对账需要结果。唯一合法的调序理由是某个前置问题的答案已经存在（例如问题早就被明确定义过），而不是"这样更顺手"。

其中三条值得展开，因为它们各自避免了一类会持续很久的错误。

### 关于第 3 条的完整论证（成功判据为什么必须早于方案）

先看顺序错开会发生什么。方案先定、判据后定，判据会不自觉地变成"这个方案容易达成的那个"。例如方案是加一个追问按钮，判据容易写成点击率。上线后点击率达标（因为按钮显眼），而用户完成任务的比率没有变化，于是得出"功能有效"的结论并继续加按钮，半年后积累了一批没人真正受益的按钮。

这个机制不是道德问题，而是认知问题：人无法在已有的方案面前保持中立地定义什么算成功，因为方案已经把注意力锚定在它能改变的量上。反过来，先定"成功等于用户完成任务的比率提升某个幅度"，方案的候选空间就被这个判据约束住，加按钮这个方案在评估阶段就会暴露弱点（它不直接改变完成率），于是设计者会去找更接近根因的方案。

这条决策的代价落在方案设计者身上：可选范围被收窄，可能被迫考虑更费劲但更有效的做法。这正是它想要的结果——代价提前落在设计者身上，总好过事后落在用户身上。

有一类任务需要例外处理：尚不知道要做什么的探索性任务，可以先定学习判据而不是成功判据（"这一轮要回答的问题是 X，什么结果会否掉它"）。但两者都必须提前写：探索不是不用想清楚，而是想清楚一件不同的事。

### 关于第 6 条的完整论证（里程碑为什么不能是进度节点）

进度节点的根本问题是它回答"投入了多少"，而风险来自"unknown 有多少"，两者之间没有关系——你可以投入九成而风险一点没减少，最坏的情况是最后百分之十才发现路走不通。

一个可操作的检验是把每个里程碑写成一句话："这一步之后，我们不再需要担心什么。"填不出空就不是里程碑。两组写法对照如下。

| 进度型（无效） | 风险型（有效） |
|---|---|
| 第 1 周：日志格式设计完成 | 第 1 周：证明用现有格式能恢复会话（担心：格式里信息够不够） |
| 第 2 周：压缩逻辑写完 | 第 2 周：证明压缩后模型仍能回答关键事实（担心：摘要质量） |
| 第 3 周：进程管理写完 | 第 3 周：证明取消能杀掉孙进程（担心：平台差异） |
| 第 4 周：联调完成 | 第 4 周：证明真实模型下端到端跑得通（担心：真实环境差异） |

风险型里程碑的代价是它更难定（要想清楚风险在哪），而且它可能在早期就宣判这条路走不通。那让人不舒服，但第二周宣判远好于第八周宣判——这正是提前暴露的收益所在。

### 关于第 14 条的完整论证（什么时候可以跳站）

机械地走完十站是官僚主义，真实的判断需要区分哪些站可以省。

| 可以跳的站 | 前提条件 | 必须留下什么 |
|---|---|---|
| 问题定义与可行性 | 改动明确可逆且代价小于一天 | 一句话：这是可逆的小改动，跳过定义阶段 |
| 方案设计 | 只有一个合理做法，且能说清为什么没有第二个 | 一句话：只有一条路，因为…… |
| 验证 | 几乎不存在可以跳的情形 | —— |
| 灰度 | 改动不面向用户，例如内部重构 | 一句话说明影响面 |
| 复盘 | 小改动可以合并进周期性复盘 | 合并后的记录 |

唯一无论如何不能跳的是验证与回滚准备，因为跳过它们的代价是把问题不可逆地带给用户。"为什么可以跳"这句话的价值在三个月后显现：如果它在，你能判断当时的决定是明智还是偷懒。如果不在，你只会记得事情办成了或者砸了。

### 3.3 决策表里那几条"完整论证"在做什么

这类文档有一个固定动作：给两三条关键决策写完整论证。用本篇的框架看，它们在做的正是方案设计那一站的核心工作——把选项与代价摊开。

以其中一个例子说明：钩子为什么必须接收只读的派生视图。问题在于监听器若修改了消息数组，那条"派生结果与日志一致"的断言就会失败。两个选项是传入可变数组（断言必须关掉，等于丢掉了保障）或传入只读视图（监听器作者要多想一步）。结论选后者，措辞是"我们愿意承担 B 的损失"，而不是"B 更好"。

这个措辞的差别值得记住：前者是评判，后者是承诺。评判可以被后来的证据推翻，而承诺记录的是当时的取舍及其代价——它才能在复盘时被对账。

| 层 | 做法 | 判据 |
|---|---|---|
| 能画 | 关掉本文，默画十站图，并写出每站的产出物与可逆性等级 | 十站齐全；可逆性分级不混淆 |
| 能填 | 用 3.4 的表填一个真实功能 | 十格至少填出八格，且切分、观测、复盘三格有具体内容 |
| 能用 | 做作业库里的 `D-01`、`E-01`、`E-02` 三道题（见 `appendix/习题总纲.md`） | 三道题的判据全部满足 |

三层的顺序不能颠倒：画不出来说明地图没有进入长期记忆，填不出来说明还没有把地图用到具体对象上，而做不出题说明判断还没有形成。

### 4.2 一次完整的自检

自检的对象是 `D:\dsh-mini` 里一个真实功能，步骤如下。

```powershell
cd D:\dsh-mini

# 打开它的设计文档，对照十站逐条检查"记录了什么、缺了什么"
#   模式系统 → docs/17-modes.md
#   上下文压缩 → docs/18-compaction.md
#   会话日志 → docs/07-session.md

# 然后填 3.4 那张表，并产出一份《交付路径图》：
#   把十站画出来，每站标注产出物、失败模式、可逆性等级、负责人
```

产出物的判据是别人能检验的五条：十站是否齐全（少一站即不合格，尤其是切分、观测、复盘）。每站的产出物写的是"东西"还是"思考"（写思考的不合格）。可逆性分级是否正确（把改数据格式标成可逆的不合格）。切分那一站的里程碑是否风险型（写成"第几周完成什么"的不合格）。观测与复盘两格是否有内容（空着说明还没有为结果负责）。

### 4.3 把它变成习惯

每接一个功能填一遍十站表，约十分钟。每完成一站把产物写下来，几段话。每月拿一件做完的事做一次对账。填一次的成本是十分钟，而漏掉问题定义或验证的代价是几天到几周，这就是它值得成为习惯的原因。

## L5 语法速查

### 5.1 术语表

| 术语 | 在本篇里的准确含义 | 容易误解为 |
|---|---|---|
| 交付路径 | 从想法到用户真正用上的十个阶段 | "开发流程"（那只是其中一站） |
| 信息损失 | 每次转换都会丢掉的原始意图 | "沟通不畅"（那是现象，这是机制） |
| 可逆性 | 改动能否撤回、撤回需要动什么 | "风险大小"（风险是概率，可逆性是能力） |
| 里程碑 | 能提前暴露风险的检查点 | "进度汇报节点" |
| 验收判据 | 提前写下的、什么算完成的可判定描述 | "验收标准"（那常常是主观的） |
| 成功判据 | 提前写下的、什么算有用的可测量结果 | "KPI"（KPI 通常由别人给定） |
| 灰度 | 先放一部分量，观察后再放 | "小范围测试"（那是验证阶段的事） |
| 回滚 | 恢复到改动之前的状态 | "修复"（修复向前，回滚向后） |
| 错误预算 | 可用性目标允许的失败额度 | "可以出错的机会"（它是可计算的额度） |
| 沉没成本 | 已经付出且收不回的投入 | "成本"（它不参与未来决策） |
| 学习判据 | 探索期替代成功判据的东西：这一轮要回答什么 | "随便看看" |

### 5.2 五个模板

模板一用于问题陈述。

```markdown
## 问题
[谁] 在 [什么场景] 下想要 [达成什么]，但因为 [什么阻碍] 做不到或做得差。
现在他们 [怎么凑合]。
我们观察到：[证据，数据或用户原话或可复现路径]
```

模板二用于风险型里程碑。

```markdown
## 里程碑 M1
这一步之后，我们不再需要担心：[不确定性]
验证方式：[具体怎么验，能跑出什么结果]
如果不成立：[备选路径]
```

模板三用于验收判据，其中第三行是负面判据。

```markdown
## 验收
| # | 判据 | 怎么验 | 期望 |
|---|---|---|---|
| 1 | 正常路径 | 跑这条命令 | 输出 X |
| 2 | 边界 | 输入空值或超长值 | 报错且信息可用 |
| 3 | 不应该发生 | 越界操作 | 被拒绝且留下记录 |
```

模板四用于回滚方案。

```markdown
## 回滚
触发条件：[什么数据或现象出现就回滚]
步骤：1. … 2. … 3. …
预计耗时：[N 分钟]
不可逆部分：[有没有，如果有是什么]
回滚后的数据状态：[一致吗，需不需要修数据]
```

模板五用于复盘对账。

```markdown
## 对账
| 当初的判断（含日期与理由） | 实际发生 | 差异原因 | 下次改什么 |
|---|---|---|---|
```

### 5.3 三条容易踩的规则

第一条，判据必须能被别人判定。出现"流畅""友好""稳定"这类词就重写，因为它们无法被第三方复现。

第二条，里程碑必须能填出"不再担心什么"。填不出来，它就是进度节点。

第三条，可逆性必须在动手之前问一次。动手之后再问，往往已经晚了——尤其是当改动已经写到磁盘或者已经发给外部系统时。

## L7 挑战题（不给答案）

第一题：小改动的十站怎么压缩。 以"把错误提示改得更清楚"为例，十站可以合并成几站，合并的依据是什么，为什么合并之后不会出问题。判据：给出了合并的依据（可逆性），而不只是"因为它小"。

第二题：不可逆改动的十站。 如果这个功能涉及删除用户的历史会话记录，十站在哪里必须变慢，要增加哪些产物。判据：指出了需要人工审批与不可逆部分的说明，并给出了无法回滚时的补偿方案。

第三题：判据冲突。 成功判据是完成率提升，而护栏指标（例如平均耗时）变差了，在迭代站怎么决定。判据：给出了判据之间的优先级规则，而不是两难时凭感觉。

第四题：里程碑失效。 你设了四个风险型里程碑，其中第二个失败了（假设不成立），这个项目该怎么重启。判据：说明了是回到方案站重设计，还是缩小范围继续，并给出了判断依据。

第五题：单人项目的验证。 没有工程团队，实现与验证都是你自己做，验证会不会退化成自我确认，怎么防止。判据：给出了一种外部化手段（例如产物必须能被别人读懂、用随机化测试代替人工检查）。

第六题：反驳十站。 什么情况下十站是有害的（让项目更慢而不更稳），给出三个判据。判据：三条判据各自对应一种真实场景，而不是"事情太急"。

## L9 仍未解决（这一篇自己的缺陷）

| 缺陷 | 后果 | 修法 | 当初为什么这么写 |
|---|---|---|---|
| 十站对小改动过重 | 改一句文案也走十站会变成形式主义，人开始敷衍，这反过来伤害真正需要十站的大改动 | 按可逆性与影响面分级决定用几站（L2 第 14 条） | 先给完整模型再给裁剪规则，反过来读者不知道裁掉了什么 |
| 成功判据提前写在探索期不适用 | 探索性任务写不出成功判据，要么卡住，要么编一个假的 | 用学习判据替代；本篇给了这条，但篇幅小容易被忽略 | 本篇主要讲执行型任务 |
| 可逆性判断本身可能错 | 你以为回滚代码就行，实际数据已经变了 | 在发布站强制问一句"有没有写入不可逆的东西" | 可逆性靠经验，而经验来自犯过错 |
| 复盘会被记忆污染 | 三个月后你记得的当初判断，是被结果改写过的版本 | 在问题定义站写下判断；本篇主张了但没有强制机制 | 它需要纪律，工具解决不了 |
| 完全不涉及人的因素 | 真实项目里能否走完十站取决于资源、优先级与他人的配合 | 需要后续篇目补组织与影响力 | 本篇定位是一条链怎么走通，不是怎么让别人配合你 |
| 单人项目里会退化成自我确认 | 没有人检验你的产物 | 产物必须外部可检验：给别人读，看他提几个问题 | 单人项目是本项目的前提 |

前两条属于模型粒度与覆盖范围的问题，中间两条属于依赖纪律而非依赖方法的问题，最后两条属于边界问题（本篇刻意不处理组织与协作）。第三条值得单独标记：可逆性判断是这一篇全部结论的输入，而它本身依赖经验——这意味着本篇给出的是一套提问方式，而不是一套可靠的判定程序。把它当成判定程序使用，会在第一次遇到不熟悉的改动时出错。

## L10 提问训练

### 五个层次

| 层次 | 例子 |
|---|---|
| 事实 | 十站里哪一站最容易被跳过？ |
| 机制 | 为什么判据在方案之后定就一定会向方案倾斜？ |
| 设计 | 为什么把回滚写在发布之前，而不是出问题时再说？ |
| 系统 | 如果切分站的里程碑全部失败，对方案站意味着什么？ |
| 科研 | 能不能量化信息损失，例如统计同一需求在文档、代码、上线三处的差异率？ |

### 五种提问模板

反例逼问：如果十站里去掉某一站，它会在哪一站以什么形式爆出来。

边界追问：改动小到什么程度才允许不走完整十站，边界在哪里。

代价追问：把成功判据提前到方案之前，代价落在谁身上。

替代对比：为什么不干脆用"设计、开发、测试、上线"四站。

验证追问：怎么证明我的里程碑真的是风险型而不是化妆过的进度节点。

### 本篇引出的十二个问题

读懂层。 第一，十站里哪三站是需求方独占的，为什么？第二，信息损失发生的两次转换各自丢的是什么？第三，为什么验收判据要在实现前写，而成功判据要在方案前写？

重建层。 第四，案例 A 的观测、迭代、复盘三站是空的，这会导致什么具体后果？第五，案例 B 的切分站为什么是弱项，改写成风险型里程碑后会变什么？第六，如果验证由实现者自己做，最大的风险是什么？

设计层。 第七，什么情况下只做前三站就动手是合理的？第八，错误预算怎么用在没有对外承诺的项目上？第九，为什么"再等等看"是最贵的决定？第十，十站在什么情况下会让项目变慢而不变稳？

评审层。 第十一，看到一个写着"第三周后端完成"的里程碑列表，你会问什么？第十二，怎么判断一份十站表是认真填的还是应付的？

### 问题升级练习

模糊问题：「我该怎么避免做出来的东西没人要？」

升级后的精确问题：

> 在十站模型下，"没人要"有四个可分辨的成因：问题定义那一站没写清（问题本身就是错的）、方案站偏离（问题对了但方案不解决它）、验证站没验真（方案对了但实现没做到）、观测站缺位（做对了但没有人知道）。
> 我能不能在上线之前为这四种成因各设计一个检查点？
> 每个检查点的成本是多少？

提升点说明：原问题无法回答，因为"没人要"是一个笼统结果。升级后的版本做了三件事：把它拆成四个可分辨的成因，每个对应一站。给出"上线前的检查点"这个可操作对象。要求给出每个检查点的成本，从而让检查点的取舍可以被讨论。

## L11 系统影响回溯

回看第 0.5 节的三个连锁影响。

| 预判 | 本篇分析之后的结论 | 状态 |
|---|---|---|
| 跳过问题定义会让整条链为一个错的问题服务 | 确认，而且最严重的后果在复盘站：无账可对，失去通过项目积累判断力的通道 | 成立 |
| 在不可逆的一站求快会抹掉之前所有节省 | 确认，并补上了四档可逆性分级与各自需要的准备动作 | 成立且更具体 |
| 里程碑设成汇报节点会让风险堆到最后 | 确认，并给出了"填入不再担心什么"这个可操作的检验 | 成立 |

一处需要修正的预判：第 0.5 节说跳过问题定义的代价三个月后才显现。读完 L1 之后要说得更准确：代价在可行性判断那一站就开始显现（它失去了评判依据），只是不疼。真正疼的时刻是复盘站的无账可对。中间那段"不疼但已经错了"的过程，才是最难察觉的部分。

通向下一篇的桥。 这一篇给出了地图，而地图上有一站现在仍然读不懂，就是实现。那一站里发生的每件事——改动会不会牵一发动全身、为什么系统越改越慢、约束从哪里来——都需要工程侧的判断力。

下一篇 `1.2 复杂度与技术债` 处理的是这件事：为什么系统会越改越慢，以及这件事能不能在动手之前看出来。它与本篇的连接点是清晰的：本篇的可逆性分级回答"这次改动能不能退回去"，而下一篇的复杂度度量回答"这次改动会让下一次改动变贵多少"——前者是单次改动的性质，后者是改动序列的性质。

### 二、情境绑定：当你……就想起……

| 当你…… | 立刻想起 |
|---|---|
| 接到一个"要做某功能"的说法 | 先问它解决谁在什么场景下的什么问题，并要证据 |
| 想直接开始讨论方案 | 成功判据还没写，先写它，否则判据会向方案倾斜 |
| 排期时想按重要性排序 | 先看依赖：重要性决定值不值得，依赖决定能不能 |
| 写里程碑时想写"第几周完成什么" | 换成"这一步之后哪个不确定性消失了" |
| 有人问"这个能不能快一点" | 问它可逆吗；可逆就快，不可逆就不快 |
| 要做数据格式或删除类的改动 | 它属于小时级或不可逆档，准备迁移或补偿，不要按代码改动的节奏处理 |
| 觉得某件事"再观察一周" | 那不产出信息，只消耗时间；先写下放弃条件 |
| 上线之后不知道看什么 | 问题定义那一站漏了成功判据，回去补 |
| 做完一个功能觉得收获不大 | 缺复盘对账：当初的判断没有被写下来 |
| 看到别人的里程碑列表 | 问每个里程碑消除了哪个不确定性 |

### 三、主动回忆：闭卷回答（不要翻上面）

### 四、间隔重复计划

| 时间 | 做什么 | 目的 |

### 五、复述练习（讲给一个不写代码的朋友听）

用五分钟讲清三件事，不要用行话：

1. 为什么"做完了"和"有用了"是两件不同的事？
2. 为什么先想清楚"什么算成功"会让后面的选择变少，而这反而是好事？
3. 为什么同样的改动，有的做错了可以立刻改回来，有的做完就永远回不去？

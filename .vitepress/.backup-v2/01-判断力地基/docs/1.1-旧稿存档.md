## 本篇新词

| 词 | 一句话 | 为什么必须懂 |
|---|---|---|
| **交付流水线** | 从"想法"到"用户真正用上"之间的十个阶段 | 你现在的所有困难（不知道先做什么、估不准、总出意外）都是因为它没有在心里成为一个完整的链 |
| **信息损失** | 每经过一次转换（想法→文档→方案→代码→上线），原始意图都会丢一部分 | 这是"为什么做完的东西不是要的东西"的根本原因，也是**每道工序存在的理由** |
| **可逆性** | 一个改动能不能撤回、撤回要多久 | 它决定了"哪些事可以快、哪些必须慢"，是优先级排序的隐藏主轴 |
| **里程碑** | 一个能**提前暴露风险**的检查点（不是汇报节点） | 没有它，风险全部堆到最后一次性爆发 |
| **验收判据** | 提前写下的、"什么状态算完成"的可判定描述 | 没有它，"完成"就变成主观判断，交付变成拉锯 |
| **灰度** | 先给一小部分流量/用户，观察后再放量 | 唯一能同时要"快"和"稳"的手段 |
| **回滚** | 把系统恢复到改动前的状态 | 没有回滚方案的发布，等于把全部风险押在一次动作上 |

**这七个词的关系**：它们是**同一件事的七个侧面** ——
让"想法变成上线"这件事**可控**。可控的意思是：每一步都有产物、每个风险都有暴露点、每个错误都有退出路径。

## 第 0 节 · 学完这一篇你能做出什么

### 0.1 你会获得一张图

不是概念图，是**可操作的图**。它长这样（下面是我的版本，你要画你自己的）：

```
        ┌── 你要产出的东西 ──┐   ┌── 这一站会丢什么 ──┐   ┌── 失败模式 ──┐
想法 ──►① 问题定义 ──►② 可行性判断 ──►③ 方案设计 ──►④ 切分排期 ──►⑤ 实现
         │              │              │              │              │
         │ 给谁解决     │ 值不值得     │ 选哪个       │ 先做哪块     │ 代码
         │ 什么场景     │ 代价多大     │ 放弃什么     │ 多长周期     │
         ▼              ▼              ▼              ▼              ▼
       信息 ↓↓↓      信息 ↓↓        信息 ↓         信息 ↓↓        信息 ↓↓↓
        ⑥ 验证 ──►⑦ 发布 ──►⑧ 观测 ──►⑨ 迭代/回滚 ──►⑩ 复盘
         │          │          │          │              │
         │ 它对了   │ 给谁看   │ 有没有用  │ 继续还是撤   │ 判断质量
         ▼          ▼          ▼          ▼              ▼
```

**这张图你要能默画出来**，并且在每一站标出：
- 这一站的**输入**是什么（上一站的产物）
- 这一站的**产出物**是什么（能被检验的）
- 这一站最常**在哪失败**
- 这一站的改动**可逆吗**（撤回来要多久）

### 0.2 你会得到三个判断工具

| 工具 | 用来回答 | 用在哪一站 |
|---|---|---|
| **信息损失检查** | "这次转换丢了什么？后面的站还能补回来吗？" | 每一站的出口 |
| **可逆性分级** | "这件事做错了，多久能恢复？" | ② 与 ⑦ |
| **风险前置检查** | "最大的那个不确定性，最早能在哪一站暴露？" | ④ 里程碑设计 |

### 0.3 你会做出一个真实产物

**《交付路径图》**：拿 dsh-mini 的一个真实功能（建议用"压缩"或"模式系统"），
按十站拆开，每站写清输入/产出物/失败模式/可逆性。

这份图是 `P-01 综合项目` 的第一块拼图，也是你作品集里的第一件东西。

## 第 0.5 节 · 系统视角 ★

### 0.5.1 你在哪里

这一篇是**第三册（软件工程原理）的开篇**。它不教任何具体技术，它教的是"地图"。

```
第一册（怎么想）              ← 你已经有了问题清单与判断框架
     │
     ▼
第二册（为谁做）              ← 需求从哪来
     │
     ▼
┌────────────────────────────────────────────────┐
│ 第三册（怎么落地）                              │
│   3.1 一个功能的一生 ★你在这一篇★  ← 全局地图  │
│   3.2 复杂度与技术债        ← 为什么越做越慢   │
│   3.3 读代码与架构          ← 约束从哪读出来   │
│   3.4 接口与契约            ← 为什么改需求贵   │
│   3.5 可逆与不可逆          ← 快慢的判据       │
│   3.6 数据与状态            ← 事故高发区       │
│   3.7 测试、CI、发布        ← 速度与稳定       │
│   3.8 估计与不确定性        ← 时间从哪来       │
│   3.9 模式词汇              ← 听懂方案讨论     │
│   3.10 性能与容量           ← 体验的物理层     │
└────────────────────────────────────────────────┘
     │
     ▼
第四册（做什么/不做什么）→ 第五册（做出来）→ 第六册（做对/做久）→ 第七册（练）
```

**为什么它必须是第一篇**：后面九篇每一篇讲的都是"某一站的细节"。
如果先讲细节，你会得到九个孤立的技巧；先讲地图，它们才有位置。

**为什么它不教技术**：因为你的第一个缺口不是技术,是**不知道每一步在干什么**。
不知道每一步在干什么的人，学再多技术也不知道该在什么时候用。

### 0.5.3 三个连锁影响分析

**连锁 1：跳过"问题定义" → 整条链都在为一个错的问题服务**

```
不做 ① 问题定义（直接谈方案）
  → ② 可行性判断失去依据（值不值得？相对**什么**值得？）
    → ③ 方案设计失去评价标准（哪个方案更好？相对**什么**更好？）
      → ⑤ 实现完成后，⑧ 观测拿不到判据（因为你没定义过"成功"）
        → ⑩ 复盘无法进行（不知道当初的判断是什么，也就无法对账）
          → **你失去了唯一可靠的成长方式**（第 7.2 条问题）
```

**这条链最阴的地方是最后一环**：跳过第一步的代价不在当天显现，而在**三个月后你想复盘时才发现无账可对**。
而那时候你会以为是"复盘方法不对"，于是去学复盘模板 —— 方向全错。

**连锁 2：在"不可逆"的一站上求快 → 一次事故抹掉前面所有节省**

```
④ 为了赶时间砍掉 ⑥ 验证
  → ⑦ 全量发布（没有灰度）
    → 上线后发现问题，但**数据已经迁移**（这一站不可逆）
      → 回滚代码解决不了数据问题
        → 只能写一个"迁移回来"的脚本 —— 而它比原改动更危险
          → 事故时长从"5 分钟回滚"变成"3 小时改数据"
```

**每一站的"可逆性"不一样，而人们习惯用同一种节奏对待所有站。**
这是 3.5 要专门解决的问题，也是这一篇要你先建立直觉的地方。

**连锁 3：里程碑设成"汇报节点" → 风险全部堆到最后**

```
④ 里程碑 = "第 2 周汇报开发进度 / 第 4 周汇报联调进度"
  → 每个里程碑都只回答"做了多少"（进度），不回答"风险释放了没有"
    → 真正的不确定性（性能够不够 / 数据迁移可不可行 / 依赖方能不能按时）**一个都没被触碰**
      → 上线前一天发现"性能只有目标的 1/10"
        → 只能砍功能或延期
          → 而这两个决定的成本，都远高于在第 2 周就发现它
```

**里程碑的唯一有效定义**：**"这一站之后，哪个不确定性消失了？"**
如果答不上来，它不是里程碑，是日历上的一个点。

> **停下来想一想**：你手上正在做的 dsh-mini（或者任何项目），
> 现在最大的一个不确定性是什么？它最早能在哪一站被消除？
>
> 如果你答不出"最早能在哪一站"，说明你的计划里没有里程碑，只有排期。

## L0 要解决的问题

### 0.1 现象一：你能说出"要做这个功能"，但说不出它要经过哪些站

这是 `4.1` 那条问题的具体表现。测试方法很简单：

> 拿一个你熟悉的、正在做的功能（比如 dsh-mini 的"Web GUI"），
> **不看任何代码与文档**，说出它从想法到上线要经过哪些站，每站的产出物是什么。

如果你只能说出"设计 → 开发 → 测试 → 上线"这四步，那么：
- 你漏掉了"问题定义"（为什么做这个而不是别的）
- 你漏掉了"可行性判断"（值不值得）
- 你漏掉了"切分"（先做哪块）
- 你漏掉了"观测"（上线后看什么）
- 你漏掉了"回滚"（错了怎么办）
- 你漏掉了"复盘"（学到了什么）

**而这五站恰恰是 PM 存在的意义。** 前三站漏掉，你就只是个传话筒；后两站漏掉，你永远在同一个坑里摔。

### 0.2 现象二：你知道"要做什么"，但不知道"先做什么"

这是 `6.1` 那条问题。它看起来是排序问题，其实是**依赖问题**：

```
❌ 错误的心智：这些事是并列的，我要给它们排序
✅ 正确的心智：这些事之间有依赖，有些是另一些的前提
```

举 dsh-mini 的真实例子（`docs/00-course-map.md` 的 Phase 5–7）：

| 事 | 依赖谁 | 为什么 |
|---|---|---|
| 上下文压缩（18） | 无 | 可以立刻做 |
| 会话持久化（20） | **压缩点的事件格式** | 压缩点要落盘并读回，格式定错了要迁移 |
| 可观测（21） | **压缩 + 进程** | 它要度量的正是那两层的耗时与收益 |
| 规模化（23） | **持久化 + 可观测** | 多会话需要存储与指标 |
| 自进化深化（24） | **持久化 + 授权（22）** | 跨会话累积证据 + 人把关 |

**看出问题了吗**：如果你按"我觉得更重要"排（比如先做自进化），
你会做到一半发现**证据没有地方存**，于是回头补持久化 —— 而这时你已经写了一堆依赖旧结构的代码。

**"先做什么"的正确答案来自依赖图，不来自重要性排序。**
重要性决定"值不值得做"，依赖决定"能不能做"。

### 0.3 现象三：你不知道哪些事做错了还能改

这是 `4.4` 那条问题。三个来自 dsh-mini 的真实对比：

| 改动 | 做错了会怎样 | 恢复代价 |
|---|---|---|
| 改一句系统提示词 | 改回来就行 | **秒级** |
| 加一个插件 | 从 bundle 里删掉这一行 | **分钟级** |
| 改会话日志的事件格式 | 老日志读不进来 → 要写迁移 | **小时级 + 有风险** |
| 删除用户的记忆文件 | 数据没了 | **不可恢复** |

**注意第三行**：它是 dsh-mini 里最典型的"看起来小、其实不可逆"的改动 ——
因为**日志是历史**，而历史不能重写。

**你现在的问题是**：你对这四类的处理方式是一样的（都用同一种谨慎程度，或者都不够谨慎）。
结果是：在提示词上犹豫太久，在数据格式上草率决定。

### 0.4 现象四：你不知道"完成"是什么

这是 `6.4` 那条。观察自己在 dsh-mini 上的行为：

```
你做完 PTC 模式之后，能回答这些问题吗？
  · 它满足什么条件才算"能用了"？
  · 什么情况下它算"失败了"（要回滚）？
  · 你怎么知道它真的被用上了？
```

如果你答不出，说明你交付的是**代码**而不是**一个被验证的能力**。

### 0.5 这一篇要回答的四个问题

1. **一个功能要经过哪些站？每站的产出物是什么？**
2. **信息在哪些站流失得最厉害？怎么补？**
3. **每站的可逆性差异有多大？它如何决定节奏？**
4. **里程碑该设在哪？判据是什么？**

## L1 设计与原理

### 1.1 十站全景（每站四个要素）

**读法**：每一站都要回答四个问题 ——
**输入是什么 / 产出物是什么 / 最常在哪失败 / 可逆性如何**。

---

#### 第 ① 站 · 问题定义

| | |
|---|---|
| **输入** | 一个信号（用户抱怨 / 数据异常 / 你的观察 / 别人的要求） |
| **产出物** | 一句话的问题陈述 + 谁在什么场景下遇到它 + 现在他们怎么凑合 |
| **最常失败** | 把方案当问题（"我们要做搜索"而不是"用户找不到东西"）；把"我觉得"当证据 |
| **可逆性** | 改一句话的成本 —— **完全可逆**，所以这一站最该反复推翻重来 |
| **对应题** | `D-01`、`J-03` |

**这一站的产出必须能通过一个测试**：

> 把它念给一个不在你项目里的人听，他能不能说出"所以你要解决的是……"？
> 如果他反问"这算个问题吗"，说明你把方案说成了问题。

**dsh-mini 的真实对照**：`docs/18-compaction.md` 的 L0 写了四个"现象"（成本线性上涨 / 大输出永久占据 / 撞上限硬失败 / 不知道多贵）。
那是**问题定义**的范例 —— 它有具体现象、有可复现路径、有代价量化。

---

#### 第 ② 站 · 可行性判断

| | |
|---|---|
| **输入** | 问题陈述 |
| **产出物** | "做 vs 不做"的结论 + 代价估算 + **不做的后果** |
| **最常失败** | 只算收益不算代价；没有对照组（不做会怎样）；把"技术可行"当成"值得做" |
| **可逆性** | 结论可以改（**可逆**），但要注意：一旦对外承诺就变得难撤销 |
| **对应题** | `J-01`、`M-07`、`W-09` |

**核心工具是"反事实"**（对应问题清单 `1.6`）：

```
做它：预期收益 X，代价 Y
不做它：会发生什么？（这一栏经常是空的 —— 那是危险的信号）
```

**Toyota 的 SBCE 在这里有一条对你有用的原则**：
> **"先证明可行，再承诺"（establish feasibility before commitment）**

翻译成 PM 语言：**在方案没验证之前，不要对外承诺时间**。
你在 dsh-mini 上就吃过这个亏（Phase 5–7 的七步都没实现，如果当初说"两周做完"就必然打脸）。

---

#### 第 ③ 站 · 方案设计

| | |
|---|---|
| **输入** | "值得做"的结论 |
| **产出物** | ≥2 个差异化的方案 + 每个方案的代价 + **取舍理由** |
| **最常失败** | 只有一个方案（那不叫设计，叫执行）；方案之间只差细节（不是真选择） |
| **可逆性** | 方案可改（**可逆**），但改动越晚代价越大（这正是"多花一天想方案省一周实现"的道理） |
| **对应题** | `J-06`、`D-05`、`W-02` |

**SBCE 的第一条原则在这里**：
> **画出设计空间（map the design space）** —— 探索多套方案，而不是一套

**一个可操作的判据**：两个方案如果**不同的代价落在不同的人身上**，它们才是真选择。
如果两个方案都是"多花时间"，那它们只是同一个方案的两种写法。

**dsh-mini 的真实对照**：`docs/17-modes.md` 的 L2 决策表里有一条：

> 让模式生成 patch → 必须写出完整 config，5 个模式要复制 5 份 `workspace`
> 把 patch 改成深合并 → 破坏"整段替换"这条已文档化的规则
> **新增 `transformRows` 钩子** ← 最终选择

三个方案，代价落在不同的人身上（模式作者 / 所有 patch 的使用者 / 装载器的维护者）。
这是一个**合格的设计空间**。

#### 第 ④ 站 · 切分与排期

| | |
|---|---|
| **输入** | 选定的方案 |
| **产出物** | 能独立验证的**小步**序列 + 里程碑（= 风险释放点）+ 每步的验收判据 |
| **最常失败** | 沿技术模块切（"先做后端再做前端"）而不是沿用户价值切；里程碑设成汇报节点 |
| **可逆性** | 排期可以改（**可逆**），但**承诺出去之后**就变难 |
| **对应题** | `J-01`、`W-06`、`W-12` |

**切分的黄金判据**：

> 每一小块做完之后，你能不能**独立地判断它有没有用**？

如果答案是不能（"要等全部做完才知道"），那说明你切错了 —— 你切的是工作量，不是价值。

**里程碑的判据**：

> 这一站之后，**哪个不确定性消失了**？

| ❌ 假里程碑 | ✅ 真里程碑 |
|---|---|
| 第 2 周：后端开发完成 | 第 2 周：证明"用现有日志格式能恢复会话"（不确定性：格式够不够） |
| 第 4 周：联调完成 | 第 4 周：证明"压缩后模型仍能回答关键问题"（不确定性：摘要质量） |

---

#### 第 ⑤ 站 · 实现

| | |
|---|---|
| **输入** | 切分后的第一块 |
| **产出物** | 可运行的改动（通常不是"完整的功能"） |
| **最常失败** | 实现者按自己的理解补全需求（**每一次补全都是一次信息漂移**）；范围悄悄变大 |
| **可逆性** | **代码可逆**（除非改了数据格式），但**时间不可逆** |
| **对应题** | `E-07`、`E-08`、`W-11` |

**这一站是"信息损失"最严重的两站之一**（另一站是 ①→③）。
原因：需求文档里的每一句模糊描述，实现者都要**猜一个具体行为**。

**减小损失的办法只有一个**：**验收判据提前写、并且可判定**（见第 ⑥ 站）。

---

#### 第 ⑥ 站 · 验证

| | |
|---|---|
| **输入** | 可运行的改动 + 提前写好的验收判据 |
| **产出物** | 通过的证据（能复现的验证记录）+ 已知的不通过项 |
| **最常失败** | 验收判据是"体验流畅"这类不可判定的描述；只测正常路径；**自己验自己** |
| **可逆性** | 这一站**完全可逆**（还没上线），所以它是**最便宜的纠错点** |
| **对应题** | `E-03`、`E-05`、`W-06` |

**"验证"分三层，PM 至少要关心后两层**：

| 层 | 谁做 | PM 关心什么 |
|---|---|---|
| 代码正确性（单元测试） | 工程 | 关键路径有没有被覆盖 |
| **行为正确性**（它真的做了我要求的事吗） | PM + 工程 | 验收判据是否被逐条验证 |
| **价值正确性**（它真的解决了问题吗） | PM + 数据 | 只能在上线后由 ⑧ 回答 |

**这一站最容易被跳过的原因**：它不产出"功能"，只产出"证据"。
而"没有证据的完成"会在 ⑧ 站变成"无法解释的现象"。

---

#### 第 ⑦ 站 · 发布

| | |
|---|---|
| **输入** | 验证过的改动 |
| **产出物** | 上线记录（谁在什么时候放了多少量）+ **回滚方案** |
| **最常失败** | 全量发布（没有灰度）；没有回滚步骤；**这一站常常是不可逆的** |
| **可逆性** | 取决于改动类型：代码可回滚，**数据迁移往往不可** |
| **对应题** | `W-07`、`J-13`、`E-18` |

**Google SRE 在这里的核心概念是"错误预算"**：

```
如果系统目标可用性是 99.9%，那么一个月你有约 43 分钟的"失败预算"。
发布的风险应该被组织成"从预算里花掉一点"，而不是"赌上全部"。
```

翻译成 PM 语言：**每次发布都应该是"可承受失败"的规模。**

**这一站的可逆性分级（必须提前问自己）**：

| 改动类型 | 回滚方式 | 耗时 | 有没有不可逆的部分 |
|---|---|---|---|
| 文案/提示词 | 改回来 | 秒 | 无 |
| 插件开关 | 改配置重载 | 分钟 | 无 |
| 代码逻辑 | 回滚版本 | 分钟 | 取决于有没有副作用 |
| **数据结构** | 回滚代码**不够** | 小时 | **有（已写入的新数据）** |
| **删数据** | 无 | —— | **不可逆** |

---

#### 第 ⑧ 站 · 观测

| | |
|---|---|
| **输入** | 上线的功能 + **在 ① 站就写好的成功判据** |
| **产出物** | 真实数据 + "有没有达到判据"的结论 |
| **最常失败** | 没有数据（当初没埋）；口径不清（不同人算出不同数）；只看主指标不看护栏 |
| **可逆性** | 观测本身可逆，但**错过观测窗口不可逆**（用户流失了就是流失了） |
| **对应题** | `M-01`、`M-02`、`W-08` |

**这一站能不能做，取决于第 ① 站**。这是全篇最重要的一条因果：

```
① 站定义了"什么算成功"
  → ⑧ 站才有可能回答"成没成功"
    → ⑩ 站才有可能复盘"我的判断对不对"

如果 ① 站没定义 → ⑧ 只能看"有没有人在用"这种粗指标
  → ⑩ 只能得出"感觉还行" → 你没有任何进步
```

---

#### 第 ⑨ 站 · 迭代或回滚

| | |
|---|---|
| **输入** | ⑧ 的数据 |
| **产出物** | 一个决定：继续投入 / 修改后继续 / 停止并回滚 |
| **最常失败** | 沉没成本（"都做了一半了"）；把"没人用"解释成"推广不够" |
| **可逆性** | 决定可逆，但**每一次"再给它一点时间"都会消耗掉真实的资源** |
| **对应题** | `J-08`、`J-12` |

**这一站要问的不是"它好不好"，而是"我现在知道什么新信息"**：

| ⑧ 站观察到 | 可能的原因 | 下一步 |
|---|---|---|
| 没人用 | ① 方向错 ② 实现差 ③ 场景没到 ④ 度量错 | **先花半天分辨是哪一个**（对应 `J-08`） |
| 有人用但不用第二次 | 价值不够重复 | 找那批用过的人问行为 |
| 用了但指标变差（护栏报警） | 有副作用 | 回滚或修副作用 |
| 达到判据 | —— | 加投入 / 扩大场景 |

**"再等等看"是最贵的决定**，因为它不产出信息，只消耗时间。

---

#### 第 ⑩ 站 · 复盘

| | |
|---|---|
| **输入** | ①-⑨ 的全部记录 |
| **产出物** | 判断质量评估（哪些判断对了、哪些错了、为什么） |
| **最常失败** | 变成"总结会"（讲了做了什么）；只记结果不记当初的判断 |
| **可逆性** | 不适用 |
| **对应题** | `W-03`、`J-15`、`M-10` |

**复盘的唯一有效形式是"对账"**：

```
当初我判断：X 会发生（写下时间与理由）
实际发生：Y
差异原因：是判断错、还是执行差、还是运气
下次遇到类似情况：我会改哪个环节
```

**没有"当初的判断"，就没有复盘** —— 这是为什么第 ①、②、③ 站必须留下书面产物。

### 1.2 三张贯穿全链的表

#### 表一：信息损失最严重的两次转换

| 转换 | 丢什么 | 为什么丢 | 怎么补 |
|---|---|---|---|
| **① 问题 → ③ 方案** | 场景细节、约束、真实动机 | 为了可执行，方案必须抽象化 | 把"用户/场景/现在怎么凑合"固定写进方案文档的抬头 |
| **③ 方案 → ⑤ 实现** | 边界情况、判定标准、为什么这么选 | 实现者要补全所有未言明之处 | **验收判据提前写**；把"为什么"写进 ADR（而不是口头交代） |

#### 表二：可逆性地图（决定节奏的依据）

```
秒级可逆   ── 提示词、文案、界面布局        ──► 可以快，多做实验
分钟级可逆 ── 代码逻辑、插件开关            ──► 正常节奏 + 回滚方案
小时级可逆 ── 数据结构、接口协议            ──► 慢下来，先设计后动
不可逆     ── 删数据、对外承诺、已流失用户  ──► 必须多重确认 + 预案
```

**这张表要贴在你想问题的桌面上。** 因为它回答了最常见的那句争论："这个很急，能不能快一点？"
正确的回答是：**"它可逆吗？可逆就快，不可逆就不快。"**

#### 表三：每站的"提前量"

| 站的产物 | 最晚必须在什么时候写好 |
|---|---|
| 问题陈述 | 在讨论任何方案之前 |
| 成功判据 | **在设计方案之前**（否则方案会定义出一个容易达成的判据） |
| 验收判据 | 在实现开始之前 |
| 回滚方案 | 在发布之前 |
| 复盘的对账基准 | **在 ① 站就写下**（那时候还诚实） |

**"复盘基准要在 ① 站写"这条听起来很夸张，但它是对的**：
三个月后你会记得的东西，一定不是当时真实的判断（记忆会被结果污染）。

### 1.3 一次完整走查：把「上下文压缩」从 ① 走到 ⑩

前面讲的是地图，这一节是**走一遍**。

对象：dsh-mini 的「上下文压缩」（`docs/18-compaction.md`，尚未实现）。
下面每一站给出的都是**可以直接抄用的产物样例**——不是示范"标准答案"，是示范"一份产物长什么样才算合格"。

---

#### ① 问题定义（产物：问题陈述）

```markdown
## 问题
使用 dsh-mini 跑多轮任务的开发者，在会话进行到第 10 轮以上时，
想要继续高效地对话，但因为**每一轮请求都把全部历史原样重发**，
导致：(a) 成本随轮次线性上涨；(b) 一次 3000 行的 read_file 输出会永久占据上下文；
(c) 超出模型窗口时任务直接失败，没有任何降级路径。

现在他们怎么凑合：手动开新会话（丢掉了上下文），或者缩短任务（做不完）。

我们观察到的证据：
· deriveMessages() 没有任何上限，全部表面事件逐条展开（kernel/session.ts）
· 第 10 轮的消息数约为第 1 轮的 10 倍
· provider 返回 context_length_exceeded 时，重试策略不认这个错误码 → 直接抛错
```

**这一站合格的自检**：把"我们观察到的证据"三行拿掉，只剩问题描述 ——
一个不在你项目里的人能不能理解"为什么这是个问题"？**能，才算合格。**

---

#### ② 可行性判断（产物：做 vs 不做）

| | 做 | 不做 |
|---|---|---|
| 预期收益 | 长会话成本下降；长任务可跑完；上下文信噪比提升 | —— |
| 代价 | 实现 + 测试 + 文档；**摘要本身要花一次模型调用**；摘要质量不可验证 | 撞窗口即失败（用户流失）；成本线性上涨 |
| 不做的后果 | —— | **这是一个必然会被撞上的硬墙**（不是"可能出问题"） |
| 判断 | ✅ 做 | |

**这一站的合格自检**：**"不做会怎样"那一栏不能空，也不能写"没影响"**。
如果你写不出不做的后果，说明你还没确认这是不是一个真问题（回到 ① 站）。

**这一站的关键判断是"必要性"而不是"收益大小"**：
压缩的收益在某些短会话里是负的（摘要调用比省下的还贵），
但它解决的是"撞墙"这个**必然发生**的问题 —— 所以它值。

---

#### ③ 方案设计（产物：≥2 个差异化方案）

| 方案 | 做法 | 得到什么 | 失去什么 | 代价落在谁身上 |
|---|---|---|---|---|
| A · 改写历史 | 压缩后**删掉**被压缩的事件 | 日志变小；派生简单 | **破坏 append-only**；历史不可复算；无法回退 | 所有依赖日志重建的人（诊断、演化、恢复） |
| B · 内存缓存 | 压缩结果存内存，派生时用它 | 实现最快 | "模型看到什么"不再能从日志重建；重放结果不同 | 排查者（永远答不出"当时看到什么"） |
| C · **压缩事件 + 派生视图** | 压缩写一条事件，派生时跳过该点之前的事件 | 不变量仍成立；可复算；可回退 | 派生多一层；日志多一类事件 | PM/实现者（多写一层） |

**选择 C**，理由写进 ADR：

> 我们愿意承担"派生多一层 + 日志多一类事件"的代价，
> 换取「Model-visible ⟺ logged」这条不变量在压缩之后仍然成立。
> 因为这条不变量是第 7 步的全部价值所在，也是后面每一站（诊断/恢复/演化）的地基。

**这一站的合格自检**：三个方案**代价落在不同的人身上**（日志使用者 / 排查者 / 实现者）。
如果三个方案的代价都是"多花时间"，它们不是真选择。

---

#### ④ 切分与排期（产物：风险型里程碑）

**反面教材**（按实现顺序排，这是最容易犯的错）：

```
第 1 周：写 kernel/compaction.ts
第 2 周：接线（plugins/compaction.ts）
第 3 周：加 /compact 命令
第 4 周：测一测
```

**问题**：四个都是"做了多少"，最大的两个不确定性（**派生能不能保持可复算**、**摘要质量够不够**）
一个都没被触碰 —— 它们会在第 4 周一起爆发。

**正确的排法**（按风险释放排）：

| 里程碑 | 消除的不确定性 | 验证方式 | 如果失败 |
|---|---|---|---|
| **M1** | deriveView 真的是纯函数 | 同一份事件流跑两次，结果深度相等 | 说明派生逻辑里有隐藏状态 → 重新设计派生接口 |
| **M2** | 没有压缩点时行为与旧版**完全一致** | 跑 `verify.ts` 全绿；对比改动前后的消息数 | 说明引入回归 → 先修好再往下 |
| **M3** | 压缩后不变量仍成立 | `verify.ts` 加一条断言；跑超阈值会话 | 说明压缩破坏了不变量 → 回到 ③ 重新设计方案 |
| **M4** | 大输出落盘后**真的能读回** | 裁剪后读 `.spill/` 文件，比对原文 | 说明溢出方案有问题 → 改落盘策略 |
| M5 | 摘要质量够用（**这条最难，也最容易被推到最后**） | 用摘要回答 5 个关键事实问题 | 说明摘要提示词要改，或压缩粒度要调 |

**这一站的合格自检**：每个里程碑都能填出"不再担心什么"；**且最难的那个不确定性排在前半段**。

**M5 的排位需要判断**：它最难验证（要设计问题集），但它也最可能推翻整个方案。
本文把它排在第 5 位（在 M1–M4 之后），因为 M1–M4 失败得更多、成本更低。
**如果你的答案是"应该把 M5 提前"，只要你能说出理由，那就是对的** ——
这一站没有唯一正确答案，只有"你有没有想过"。

---

#### ⑤ 实现（产物：第一块可运行的改动）

**第一块不是"完整的压缩"，而是 M1 需要的东西**：`estimateTokens` + `deriveView`（纯函数，无框架依赖）。

```ts
// 这一块做完就能独立验证 M1，不需要任何插件
export function estimateTokens(messages: readonly ChatMessage[]): number
export function deriveView(events: readonly SessionEvent[]): DerivedView
```

**为什么不先接插件**：因为插件接线会同时引入"压缩对不对"和"插件装没装上"两个变量 ——
调试时你分不清是哪个错了。

**这一站的合格自检**：你能说出"这一块做完之后，我能独立验证什么"。

---

#### ⑥ 验证（产物：验收清单）

```markdown
| # | 判据 | 怎么验 | 期望 |
|---|---|---|---|
| 1 | 未达阈值不压 | 短会话调 compact('auto') | {compacted:false}，**不写事件** |
| 2 | 压缩后不变式成立 | 跑超阈值会话 | assert 不抛；verify 绿 |
| 3 | 派生是纯函数 | 同一输入调两次 | 深度相等 |
| 4 | 压缩点前的事件还在日志 | 看 session.events | 一条没少 |
| 5 | 摘要失败降级 | 让 provider 抛错 | 写 truncate 事件；任务继续 |
| 6 | **不应该发生**：短输出也落盘 | 读小文件 | spilled:false，内容原样 |
| 7 | **不应该发生**：system prompt 被压掉 | 看派生首条 | 仍是 system |
```

**第 6、7 条是"负面判据"** —— 它们验的是"不该发生的事没有发生"。
**一份验收清单里没有负面判据，说明你只想了正常路径。**

#### ⑦ 发布（产物：回滚方案 + 灰度）

```markdown
## 发布
方式：以插件形式（`plugins/compaction.ts`），在 bundle 里默认 disabled，先只在 ptc 模式开
原因：压缩会改变"模型看到什么"，是行为级改动 → 先限定影响面

## 回滚
触发条件：任一情况下回滚
  · verify 出现失败
  · 任务的完成率下降 > 10%（对比开前的基线）
  · 出现"模型忘记用户约束"的报告 ≥ 2 次
步骤：
  1. 把 bundle 里 compaction 行设 disabled:true
  2. 重新装载（重启进程）
预计耗时：< 1 分钟
不可逆部分：**无**（压缩只写事件，不删数据；事件留在日志里不影响任何东西）
回滚后的数据状态：一致（多出来的 session/compaction 事件被忽略即可）
```

**这一站的合格自检**：**"不可逆部分"那一栏必须被认真回答**。
写"无"之前先问："这个改动有没有写入任何不能撤销的东西？"

#### ⑧ 观测（产物：指标定义）

```markdown
| 指标 | 口径 | 数据来源 | 期望 | 护栏 |
|---|---|---|---|---|
| 净省下的 token | Σ(after−before) − Σ(摘要调用成本) | session/compaction 事件 | > 0 | —— |
| 触发频率 | 压缩次数 / turn 数 | 同上 | < 0.3（不要每轮都压） | > 0.5 → 阈值太低 |
| **摘要保真度** | 关键事实问题集的答对率 | 人工抽样 | ≥ 4/5 | < 3/5 → 摘要提示词要改 |
| 长会话完成率 | 超 10 轮的会话中，任务成功比例 | 会话日志 | 不低于开前的基线 | 下降 > 10% → 回滚 |
```

**注意第三行**：它没有现成数据，需要**人工抽样**。
**这正是"成功判据提前写"的价值** —— 因为你在 ① 站就知道"摘要质量"是核心风险，所以在这里你准备了抽样方案，
而不是上线后才发现"我们没有数据能回答它有没有用"。

---

#### ⑨ 迭代或回滚（产物：决定规则）

```markdown
| 观测结果 | 判断 | 动作 |
|---|---|---|
| 净收益 > 0 且保真度 ≥ 4/5 | 有效 | 扩大：默认开给所有模式 |
| 净收益 > 0 但保真度 3/5 | 部分有效 | 改摘要提示词，重跑 M5 |
| 净收益 < 0（短会话为主） | 场景不匹配 | 只对长会话启用（按估算规模条件触发） |
| 完成率下降 | 有副作用 | 回滚 |
```

**这一站的合格自检**：**是否提前定义了"什么时候放弃"**。
"再观察一周"是最贵的决定 —— 它不产出信息，只消耗时间。

---

#### ⑩ 复盘（产物：对账表）

**这张表的价值在于"当初的判断"那一列是在 ①②③ 站写下的**（不是事后补的）：

```markdown
| 当初的判断（写下日期） | 实际发生 | 差异原因 | 下次改什么 |
|---|---|---|---|
| 01-15：压缩后成本会明显下降，因为长会话占比高 | 长会话只占 12%，整体成本下降 4% | **高估了长会话占比**（没看数据就假设） | 下判断前先查一次分布 |
| 01-15：摘要质量是最大的风险 | 抽样保真度 4.5/5，不是瓶颈 | **低估了摘要提示词的效果** | 风险排序要靠证据，不靠直觉 |
| 01-20：M1–M4 会顺利 | M2 卡了两天（旧行为有隐藏依赖） | **低估了"改动前的行为"的复杂度** | 先写"改动前行为"的测试，再动手 |
```

**这一站才是整个循环真正的产出物**：它产出的不是功能，是**判断力的修正**。
没有这张表，做完十件事你还是同一个人。

### 1.4 走查之后：你该看到的三件事

**第一，最贵的错误从来不在实现里。**
上面十站里，如果按成本排序，最贵的三个错误是：
① 站没查分布就下判断 → 差一点做了一个"收益只有 4%"的功能；
④ 站按实现顺序排里程碑 → 风险堆到最后；
⑧ 站没准备抽样方案 → 无法回答"摘要质量如何"。

**第二，每一站都有"可以省"和"不能省"的部分。**

| 站 | 可以省 | 不能省 |
|---|---|---|
| ① 问题定义 | 长篇背景 | **"不做的后果"** |
| ② 可行性 | 详细财务模型 | **对照组** |
| ③ 方案 | 三个以上的方案 | **至少两个差异化方案 + 代价** |
| ④ 切分 | 详细排期表 | **至少一个风险型里程碑** |
| ⑤ 实现 | —— | 能独立验证的第一块 |
| ⑥ 验证 | 自动化 | **负面判据** |
| ⑦ 发布 | 分批灰度（小项目） | **回滚方案 + 不可逆部分** |
| ⑧ 观测 | 完整看板 | **能回答"成没成功"的一个数** |
| ⑨ 迭代 | 书面规则 | **"什么时候放弃"** |
| ⑩ 复盘 | 正式会议 | **当初的判断 + 实际结果** |

**第三，"能不能省"取决于可逆性，不取决于"忙不忙"。**

一个可逆的小改动（改提示词），十站可以压到两站（想清楚 → 改 → 看）；
一个不可逆的改动（改日志格式），一站都不能省。

> **先问一遍**：你手上正在做的那件事，属于哪一档？
> 如果答不出，回到 L1 的表二（可逆性地图），你的改动属于四档里的哪一档？

### 1.5 十站的变体：探索型任务怎么走

前面十站默认了一个前提：**你知道要做的是什么**。
但有一大类任务不是这样 —— **你连要做什么都还不知道**。在 dsh-mini 上就有一个现成的例子：

> "GUI 的下一步该做什么？"
> 这个问题没有选项可比较，因为你不知道用户到底缺什么。

如果硬套十站，第 ① 站就会卡住（写不出问题陈述），第 ⑧ 站更会卡住（写不出成功判据）。
所以探索型任务需要一份**变体表**：

| 站 | 执行型（已知做什么） | **探索型（还不知道）** |
|---|---|---|
| ① | 问题陈述（谁在什么场景缺什么） | **要回答的问题**（这次要学到什么） |
| ② | 做 vs 不做的收益对照 | **成本上限**（这次最多花多少时间/资源） |
| ③ | ≥2 个方案 + 取舍 | **≥2 个可证伪的假设**（不是方案，是"我猜 X 是对的"） |
| ④ | 切分 + 风险型里程碑 | **最便宜的证伪路径**（用什么最小动作能否掉它） |
| ⑤ | 实现第一块 | **做出验证材料**（原型 / 假门 / 一次数据查询） |
| ⑥ | 验收判据 | **能否证伪**（"什么结果会让我放弃这个假设"） |
| ⑦ | 发布 + 回滚 | **不发布**（探索不面向用户，除非假门测试） |
| ⑧ | 指标 + 基线 | **学到了什么**（答案是什么，置信度多少） |
| ⑨ | 继续 / 修改 / 停止 | **转执行**（如果假设成立）或**换假设**（不成立） |
| ⑩ | 对账 | 对账（同样重要：我猜对了吗） |

#### 1.5.1 用 dsh-mini 走一遍探索型任务

**任务**："GUI 的下一步该做什么？"

**① 要回答的问题**（不是"问题陈述"）：

```markdown
## 这次要回答的问题
使用 GUI 的人（假设存在的话）在哪个环节放弃？
—— 具体到：他们打开页面后发生了哪三种行为，各自占比多少？
```

**② 成本上限**：最多花 2 小时 + 0 行代码改动。

**③ 可证伪的假设**（≥2 个）：

| 假设 | 如果成立，下一步会做什么 | 什么结果会否掉它 |
|---|---|---|
| H1：人们打开后不提问就走了（说明不知道怎么用） | 加引导/示例 | 如果会话日志显示多数人至少提了一问 → H1 错 |
| H2：人们提问了但只用一次（说明没解决真实问题） | 去问那批人为什么 | 如果多轮占比高 → H2 错 |
| H3：根本没有人在用 GUI（说明它没被需要） | 停止投入 | 如果有 10+ 独立会话 → H3 错 |

**④ 最便宜的证伪路径**：**一次数据查询**。GUI 的会话日志就在 `workspace/.sessions/` 里（或者近似的运行痕迹）——
不需要写代码、不需要用户访谈。

**⑤ 验证材料**：一份统计脚本的输出（几行数字）。

**⑥ 证伪条件**：上面那张表第三列。

**⑦ 不发布**：这一步不产生任何面向用户的改动。

**⑧ 学到了什么**：

```markdown
## 结论
- 假设 H1 ❌：82% 的会话至少提了一问 → 不是"不知道怎么用"
- 假设 H2 ✅（部分）：单轮会话占 74%，多轮占 26%
- 假设 H3 ❌：有 23 个独立会话 → 有人在用
- **新出现的问题**：单轮会话里，任务成功比例是多少？（这是下一轮要回答的问题）
```

**⑨ 转执行还是换假设**：H2 部分成立 → 进入执行型十站（去问那批单轮用户为什么）。

**⑩ 对账**：

```markdown
| 当初的假设 | 实际 | 我错在哪 |
|---|---|---|
| H1（不会用） | 错 | 高估了"不会用"，因为我自己是开发者，觉得别人也不会 |
| H3（没人用） | 错 | 低估了它被真实使用的程度（因为我没看过数据就假设） |
```

#### 1.5.2 ★ 探索型任务的三条纪律 ★

**纪律一：② 站的成本上限是硬的。**

```
没有上限的探索 = 无限期调研
→ 而"调研"是最容易假装在工作的形态
→ 给它一个硬上限（时间 / 动作数），到点必须给结论
```

**纪律二：③ 站的假设必须**能**被否掉。**

```
❌ "用户可能在意性能"        ← 无法否掉（怎么算"在意"？）
✅ "如果响应 >2s，用户的单轮占比会明显上升"  ← 可查数据验证
```

**纪律三：⑧ 站必须给出置信度，不只给结论。**

```
❌ "单轮占 74%"              ← 样本 23 个，这个数字有多可信？
✅ "单轮占 74%（n=23，置信度低；如果是 200 个会话我会更信）"
```

**这三条纪律的代价**：探索会变得"不那么自由"（有上限、有证伪条件、要标置信度）。
**换来的是**：探索结束时你有**结论**，而不是一堆"我觉得"。

#### 1.5.3 什么时候从探索转执行

```
你有一个假设，且：
  · 它能被证伪（③ 站合格）
  · 它已经被验证过一次（⑧ 站给了支持）
  · 你知道"如果成立要做的事"是什么（③ 站的第二列已经写了）
→ 转执行型十站
```

**不要等到"完全确定"才转执行** —— 那等于永远不转。
判据是"**有一个具体动作已经被证明有效**"，不是"我很有信心"。

> **先问再答**：如果让你给"要不要给 GUI 加多会话支持"这件事定成本上限，
> 你会怎么定？（提示：先问"最便宜的证伪路径是什么"——如果一条 SQL 查询就能否掉它，上限就是半小时。）

### 1.7 为什么不缺这一站也不多那一站：十站的推导

前面七节都在讲"十站是什么、怎么用"。但如果你只是记住这十个名字，遇到新情况时仍然会不知道该加一站还是减一站。所以这一节要做一件更根本的事：**从三条前提把这十站推导出来**。推导清楚之后，你就不是在背一张表，而是在用一个能自我修正的模型。

#### 1.7.1 三条前提

**前提一：一个功能的价值，只在"用户真的用上、而且它确实起作用"的那一刻才被兑现。**

这条前提看起来像废话，但它排除了工作中最常见的两种错觉。第一种错觉是"代码写完就算完成"——可是代码写完的时刻，用户还没有用上，价值是零；第二种错觉是"上线了就算完成"——可是上线只意味着用户**可以**用，不意味着他们**真的**在用，更不意味着它**起了作用**。这两种错觉之所以顽固，是因为它们各自对应一个明确的、可庆祝的时间点，而"价值被兑现"这个时刻往往没有明显的仪式感，它表现为数据缓慢地变化，或者根本不变化。

**前提二：从"想做"到"价值兑现"，信息一定会损失，而且损失的量与转换次数正相关。**

这个损失不是"沟通不到位"造成的，而是**抽象化**的必然代价。当你把一个具体场景（某某用户在某个下午、因为他手上的数据格式不对、所以卡了二十分钟）写成一句需求（"支持导入 CSV"）时，你丢掉了场景与时序；当工程师把这句话实现成代码时，他必须自己补上所有你没有言明的细节，而每一次补全都是一次猜测。所以不损失信息是不可能的，唯一的选择是**控制损失的量和位置**。

**前提三：每一次错误判断都有两种代价，即做错本身的代价，以及它被发现得有多晚。**

这两种代价是可以分别优化的，而它们的最优策略往往矛盾：为了降低"做错"的概率，你会想多花时间讨论；为了降低"发现得晚"的损失，你会想尽快动手看看结果。**十站的设计，本质上就是在这两种代价之间找一个可操作的平衡**。

#### 1.7.2 从前提到十站

有了这三条前提，十站就不再是十个并列的步骤，而是四组推导的产物。

**推导一：因为前提二说信息会损失，所以每一次转换都必须留下产物。**

这就是第 ① ② ③ ④ 站存在的最直接理由。如果"想法"只是停留在讨论中，那么当它被写成方案时，讨论中那些"为什么排除掉另一个选项"的推理就消失了；而当方案被实现时，方案中那些"边界情况怎么处理"的判断也会消失。让每一次转换都留下书面产物的意义，并不在于"留下证据给别人看"，而在于**当后面某一站发现前面错了的时候，你还能知道当时是根据什么判断的**。没有产物，就没有事后追溯的可能，于是同一个错误会在同一个地方反复发生。

**推导二：因为前提三说"发现得晚"本身就是代价，所以检查点必须尽可能前移。**

这一条决定了第 ② 站（可行性）与第 ④ 站（风险型里程碑）的形态。第 ② 站之所以要在方案之前做，是因为如果方案已经写好，人们就会倾向于证明这个方案可行，而不是诚实评估这件事值不值得做；第 ④ 站的里程碑之所以必须是"风险型"而不是"进度型"，是因为进度型里程碑只报告投入量，而投入量与风险无关——你可以投入九成而最大的未知一点没变。把最贵的不确定性排在最前面验证，是用**早发现**换**低损失**。

**推导三：因为前提一说价值在用户那里才兑现，所以链条必须延伸到上线之后。**

这直接产生了第 ⑦ ⑧ ⑨ 三站。很多团队的做法终止于"代码合并"，那是因为他们把交付定义为"东西出去了"。但从前提一来看，东西出去只是让价值**有机会**发生，之后还需要三件事：确认它真的被用户接触到（⑦ 发布）、确认它产生了预期的作用（⑧ 观测）、以及根据观测结果决定是继续投入还是撤退（⑨）。这三站之所以经常被省略，是因为它们不产生新功能，只产生判断——而判断在没有制度要求时，总是最先被牺牲的。

**推导四：因为前提三把错误分成"做错"和"发现得晚"，所以必须为不可逆的错误单独准备退路。**

这就是第 ⑥ 站与第 ⑦ 站里"回滚"部分的存在理由。这里有一个容易被忽略的区分：**可逆的错误和不可逆的错误，需要的不是同一种谨慎**。一个可逆的错误（改一句提示词）即使做错了，代价也只是修复它所花的时间；而一个不可逆的错误（重写历史数据的格式、删掉用户的记录）做错之后，代价是**永久**的。因此"回滚方案"不是发布流程里的一个可选环节，而是对"这一类改动到底能不能快"这个问题的正式回答。

**推导五：因为前提三的两种代价都依赖"我当初怎么判断的"，所以必须留下判断本身。**

这就是第 ⑩ 站存在的理由，也是全部十站里最容易被看成"多余"的一站。复盘的常见失败形态是变成工作总结，也就是把"我做了什么"讲一遍；而这样的复盘无法改进任何能力，因为它完全没有触及"我当时的判断是什么、它错在哪里"。要修正判断，就必须有原始判断的记录——这就是为什么本文反复强调第 ① 站要写下"当初预期会发生什么"。这不是为了形式，而是因为三个月后的记忆会被结果污染，你会不自觉地认为自己"当时就觉得会这样"。

#### 1.7.3 这个推导能回答的两个实际问题

有了上面的推导，两个日常问题就有了答案，而不再依赖直觉。

**第一个问题是"什么时候可以少走几站"。** 答案是：取决于**这一站的产物是否还能从别处得到**，以及**跳过它的错误是否可逆**。举例来说，如果一次改动小到"做错了改回来只要一分钟"，那么花两小时写可行性分析就是浪费——此时"跳过 ② 站"是合理的。但同样的跳过放在"改变日志格式"上就不合理了，因为那类改动一旦做错，恢复的代价远高于分析的成本。所以"用几站"不是由工作量决定的，而是由**可逆性与信息可得性**共同决定的。

**第二个问题是"十站的顺序能不能换"。** 答案是：不能。因为顺序来自依赖关系而不是偏好。第 ③ 站必须在第 ② 站之后，因为"哪个方案更好"这个问题的答案取决于"要解决什么问题、值不值得解决"；第 ⑥ 站必须在第 ⑤ 站之后，因为没有东西可验证；而第 ⑩ 站必须在最后，因为对账需要结果。如果你想调整顺序，唯一合法的理由是**你已经证明某个前置问题的答案已经存在**（例如问题早就被明确定义过），而不是"我觉得这样更顺手"。

### 关于第 3 条的完整论证（成功判据为什么必须早于方案）

这是本篇最反直觉、也最重要的一条。先看顺序错开会发生什么：

```
先有方案，后有判据
  → 你会不自觉地把判据定成"这个方案容易达成的那个"
    → 例：方案是"加一个推荐追问按钮"，判据容易写成"点击率"
      → 上线后点击率达标（因为按钮很显眼），但用户完成率没变
        → 你得出"功能有效"的结论，继续加按钮
          → 半年后你有一堆没人真正受益的按钮
```

**机制**：判据一旦在方案之后定，它就会**向方案倾斜**。
这不是道德问题，是认知问题 —— 人无法在已有的方案面前保持中立地定义"什么算成功"。

**反过来（判据在前）**：

```
先定"成功 = 用户完成任务的比率提升 X%"
  → 方案的候选空间被这个判据约束住
    → "加按钮"这个方案在评估阶段就暴露了它的弱点（它不直接改变完成率）
      → 于是你会去找更接近根因的方案（比如减少任务本身需要的步骤数）
```

**代价落在谁身上**：落在**方案设计者**（你）身上 —— 可选范围被收窄了，
可能被迫去考虑更费劲但更有效的方案。**这正是你想要的。**

**一个例外**：探索性任务（还不知道要什么）可以先定"学习目标"而不是"成功判据"：

| 任务类型 | 判据形态 |
|---|---|
| 明确要做某件事 | **成功判据**（可测量的结果） |
| 还不知道要什么 | **学习判据**（"这次要回答的问题是 X"） |

但**两者都必须提前写**。探索不是"不用想清楚"，是"想清楚的是一件事：我要学到什么"。

### 关于第 6 条的完整论证（里程碑为什么不能是进度节点）

**进度节点的根本问题**：它回答的是"投入了多少"，而风险来自"未知多少"。
两者之间没有关系 —— 你可以投入 90% 而风险一点没减少（最坏情况：最后 10% 才发现根本走不通）。

**一个可操作的检验**：

> 把每个里程碑写成一句话："这一步之后，我们不再需要担心 ______。"
> 如果填不出空，它就不是里程碑。

对照 dsh-mini 的两组里程碑写法：

| ❌ 进度型 | ✅ 风险型 |
|---|---|
| 第 1 周：日志格式设计完成 | 第 1 周：**证明**用现有 JSONL 格式能恢复会话（担心：格式里信息够不够） |
| 第 2 周：压缩逻辑写完 | 第 2 周：**证明**压缩后模型仍能回答关键事实（担心：摘要质量） |
| 第 3 周：进程管理写完 | 第 3 周：**证明**取消能杀掉孙进程（担心：平台差异） |
| 第 4 周：联调完成 | 第 4 周：**证明**真实模型下端到端能跑通（担心：真实环境差异） |

**代价**：风险型里程碑更难定（要想清楚风险在哪），而且它可能**在早期就宣判"这条路走不通"** ——
那让人很不舒服，但"第 2 周就宣判"远好于"第 8 周才宣判"。

### 关于第 14 条的完整论证（什么时候可以跳站）

机械地走十站是官僚主义。真实的判断是：

| 可以跳的站 | 前提条件 | 必须留下什么 |
|---|---|---|
| ①② 问题与可行性 | 改动**明确可逆**且代价 < 一天 | 一句话："这是可逆的小改动，跳过定义阶段" |
| ③ 方案设计 | 只有一个合理做法（且你能说出**为什么没有第二个**） | 一句话："只有一条路，因为……" |
| ⑥ 验证 | **几乎不存在**（验证是最便宜的纠错点） | —— |
| ⑦ 灰度 | 改动不面向用户（如内部重构） | 一句话说明影响面 |
| ⑩ 复盘 | 小改动可以合并进"周复盘" | 合并后的记录 |

**唯一不能跳的两站**：**⑥ 验证**与 **⑦ 的回滚准备**。
因为跳它们的代价是"不可逆地把问题带给用户"。

**"记下为什么跳过"这条的价值**：三个月后你会想知道"当初为什么没做可行性分析"。
如果那句话在，你能判断那是明智还是偷懒；如果不在，你只会记得"事情办成了/砸了"。

### 3.3 逐段解析：`17-modes.md` 的 L2 决策表里那三条"完整论证"

dsh-mini 的文档有一个固定动作：**给 2–3 条关键决策写"完整论证"**。
用本篇的框架看，它们在做的正是**③ 站的核心工作**：把"选项 + 代价"摊开。

**第 4 条论证（钩子为什么必须收只读的 `DerivedView`）**：

| 十站视角 | 它在做什么 |
|---|---|
| ① 问题 | "监听器改了 messages，断言就会失败" |
| ② 对照 | 版本 A（可变数组）vs 版本 B（只读视图） |
| ③ 代价 | A：断言必须关掉（丢掉第 7 步的保障）；B：监听器作者要多想一步 |
| ④ 结论 | 选 B —— **用一个"写起来更麻烦"换取"保障不失效"** |

**你能从中学到的写法**：

```
选项 A → 得到什么 + 失去什么
选项 B → 得到什么 + 失去什么
→ 我们的选择 = 我们愿意承担哪一个损失
```

**注意最后一句**：不是"B 更好"，而是"我们愿意承担 B 的损失"。
这个措辞的差别很重要 —— 前者是评判，后者是**承诺**。


**产出物的判据（别人能检验）**：

| 判据 | 怎么看 |
|---|---|
| 十站齐全 | 少一站就是不合格（尤其是 ④⑧⑩） |
| 每站有"产出物"栏 | 写的是"思考"而不是"东西"→ 不合格 |
| 可逆性分级正确 | 把"改数据格式"标成"可逆"→ 不合格 |
| ④ 的里程碑是风险型 | 写成"第 X 周完成 Y"→ 不合格 |
| ⑧⑩ 有内容 | 空着 → 说明你还没为结果负责 |

### 4.3 把这件事变成习惯

```
每接一个功能：填一遍十站表（10 分钟）
每完成一站：把产物写下来（几段话）
每月：拿一件做完的事做一次对账（⑩）
```

**为什么值得**：十站表填一次的成本是 10 分钟，而漏掉 ① 或 ⑥ 的成本是**几天到几周**。

## L5 语法速查

### 5.1 术语表（本篇出现的全部）

| 术语 | 一句话定义 | 反例（不是它） |
|---|---|---|
| **交付流水线** | 从想法到用户真正用上的十个阶段 | 不是"开发流程"（那只是其中一站） |
| **信息损失** | 每次转换都会丢掉的原始意图 | 不是"沟通不畅"（那是现象，这是机制） |
| **可逆性** | 改动能否撤回、多久能撤回 | 不是"风险大小"（风险是概率，可逆性是能力） |
| **里程碑** | 一个能提前暴露风险的检查点 | 不是进度汇报节点 |
| **验收判据** | 提前写下的、"什么算完成"的可判定描述 | 不是"验收标准"（那常是主观的） |
| **成功判据** | 提前写下的、"什么算有用"的可测量结果 | 不是 KPI（KPI 常是别人给的） |
| **灰度** | 先放一部分量，观察后再放 | 不是"小范围测试"（那是验证站的活） |
| **回滚** | 恢复到改动前 | 不是"修复"（修复是向前，回滚是向后） |
| **错误预算** | 可用性目标允许的失败额度 | 不是"可以出错的机会"（它是**可量化的额度**） |
| **沉没成本** | 已经付出且收不回的投入 | 不是"成本"（它不该参与未来决策） |
| **学习判据** | 探索期用来替代成功判据的东西：这次要回答什么问题 | 不是"随便看看" |

### 5.2 五个模板（直接抄）

**模板 1 · 问题陈述**

```markdown
## 问题
[谁] 在 [什么场景] 下，想要 [达成什么]，但因为 [什么阻碍] 做不到/做得差。
现在他们 [怎么凑合]。
我们观察到：[证据 —— 数据 / 用户原话 / 可复现路径]
```

**模板 2 · 里程碑（风险型）**

```markdown
## 里程碑 M1
这一步之后，我们不再需要担心：[不确定性]
验证方式：[具体怎么验，能跑出什么结果]
如果不成立：[备选路径是什么]
```

**模板 3 · 验收判据**

```markdown
## 验收
| # | 判据 | 怎么验 | 期望 |
|---|---|---|---|
| 1 | 正常路径 | 跑这条命令 | 输出 X |
| 2 | 边界 | 输入空/超长 | 报错且信息可用 |
| 3 | **不应该发生** | 越界操作 | 被拒绝且留下记录 |
```

**模板 4 · 回滚方案**

```markdown
## 回滚
触发条件：[什么数据/现象出现就回滚]
步骤：1. … 2. … 3. …
预计耗时：[N 分钟]
不可逆部分：[有没有？如果有，是什么？]
回滚后的数据状态：[一致吗？需不需要修数据？]
```

**模板 5 · 复盘对账**

```markdown
## 对账
| 当初的判断（写下日期与理由） | 实际发生 | 差异原因 | 下次改什么 |
|---|---|---|---|
```

### 5.3 三条易踩的规则

1. **判据必须能被别人判定**。出现"流畅""友好""稳定"这类词 → 重写。
2. **里程碑必须能填出"不再担心什么"**。填不出 → 它是进度节点。
3. **可逆性必须在动手前问一次**。动手后再问，往往已经晚了。

## L6 关文档重写判据

### ★ 必须能独立做到的（★★★）

| 要写什么 | 判据 |
|---|---|
| 十站图（含每站产出物与可逆性） | 默画全对，可逆性不错 |
| 一个真实功能的十站表 | 至少 8 格有实内容，④⑥⑧⑩ 不空 |
| 风险型里程碑（≥3 个） | 每个都能填出"不再担心什么" |

### ★★ 应该能做的

| 要写什么 | 判据 |
|---|---|
| 判断一次"该不该跳站" | 给出跳的理由 + 留下那句话 |
| 定一组成功判据（在方案之前） | 判据可测且不是方案倒推出来的 |
| 写出一个功能的回滚方案 | 含触发条件、步骤、耗时、不可逆部分 |

### ★ 卡住时问自己什么

| 卡在哪 | 问自己 |
|---|---|
| 画不出十站 | "从有人提起这件事，到用户真的用上，中间发生了什么？"（按时间顺序走一遍） |
| 填不出 ⑧ | "上线后我怎么知道它有用？如果答不上，说明 ① 没定义清楚" |
| 里程碑填不出"不再担心什么" | "这个项目最可能死在哪？那件事最早能在哪一步验证？" |
| 分不清可逆性 | "如果把这次改动撤回去，有没有东西是撤不回来的？（数据/承诺/用户）" |
| 说不上"值不值得" | "不做它会怎样？"（答不上 = 没有对照组） |

### 分级判定

| 级别 | 标准 |
|---|---|
| **L1 读懂** | 能说出十站的名称与顺序，能解释"信息损失"与"可逆性" |
| **L2 改动** | 能给一个真实功能填出十站表，并指出风险最高的一站 |
| **L3 重建** | 关掉文档，为一件新事设计完整路径（含里程碑与回滚），并说服别人 |
| **L4 设计** | 能为一个不确定的、探索性的任务设计"学习判据 + 检查点" |
| **L5 评审** | 能看别人的交付计划，指出"哪一站缺产物、哪个里程碑是假的" |

## L7 挑战题（不给答案）

1. **小改动的十站**：一个"把错误提示改得更清楚"的改动，十站该怎么压缩？哪些站可以合并？为什么合并后不会出问题？
2. **不可逆的十站**：如果这个功能涉及"删除用户的历史会话记录"，十站在哪里必须变慢？要加哪些额外产物？
3. **判据冲突**：成功判据是"完成率提升"，但护栏指标（比如"平均耗时"）变差了。你在 ⑨ 站怎么决定？
4. **里程碑失效**：你设了 4 个风险型里程碑，其中 M2 失败了（证明假设不成立）。这个项目的十站该怎么重启？
5. **单人项目的十站**：你没有工程团队，⑤⑥ 都是你自己做。这时候"验证"会不会退化成自我确认？怎么防止？
6. **十站的反面**：什么情况下十站是**有害的**（会让项目变慢而不变稳）？给出三个判据。

## L9 仍未解决（这一篇自己的缺陷）

| 缺陷 | 后果 | 修法 | 当初为什么这么写 |
|---|---|---|---|
| **十站对小改动过重** | 改一句文案也走十站 → 形式主义 → 人开始敷衍 → 反过来伤害大改动 | 分级：按可逆性与影响面决定用几站（见 `L2` 第 14 条） | 先给完整模型，再给裁剪规则（反过来人会不知道裁掉了什么） |
| **"成功判据提前写"在探索期不适用** | 探索性任务写不出成功判据 → 要么卡住，要么编一个假的 | 用"学习判据"替代（本文给了这条，但只占一小段，容易被忽略） | 探索与执行是两种任务，本文主要讲执行型 |
| **可逆性判断本身可能错** | 你以为"回滚代码就行"，实际数据已经变了 | 在 ⑦ 站强制问一句"有没有写入了不可逆的东西" | 可逆性靠经验，而经验来自犯过错 |
| **复盘会被记忆污染** | 三个月后你"记得"当初的判断，但那是被结果改写过的记忆 | ① 站写下判断（本文主张了，但没有强制机制） | 需要纪律，工具解决不了 |
| **完全不涉及"人"的因素** | 真实项目里，站能不能走完取决于资源、政治、别人的优先级 | 需要在第四、五册补"组织与影响力" | 本篇的定位是"一条链怎么走通"，不是"怎么让别人配合你" |
| **十站在单人项目里会退化成自娱自乐** | 没有人检验你的产物，容易自我确认 | 产物必须**外部可检验**（给别人读，看他问几个问题） | 单人项目是本项目的前提 |

### 五个层次

| 层次 | 例子 |
|---|---|
| 事实 | 十站里哪一站最容易被跳过？ |
| 机制 | 为什么"判据在方案后定"一定会向方案倾斜？ |

| 系统 | 如果 ④ 站的里程碑都失败了，对 ③ 站的方案意味着什么？ |
| 科研 | 能不能量化"信息损失"？（比如统计同一需求在文档→代码→上线后的差异率） |

### 五种模板

```
① 反例逼问：如果十站里去掉 X 站，会在哪一站以什么形式爆出来？
② 边界追问：改动多小才允许不走完整十站？边界在哪？
③ 代价追问：把成功判据提前到方案之前，代价落在谁身上？
④ 替代对比：为什么不干脆用"设计→开发→测试→上线"四站？
⑤ 验证追问：怎么证明"我的里程碑真的是风险型"？
```

### 本篇引出的 12 个问题

**L1 读懂层**
1. 十站里哪三站是"PM 独占"的？为什么？
2. "信息损失"发生的两次转换，各自丢的是什么？
3. 为什么"验收判据"要在实现前写，而"成功判据"要在方案前写？

6. 如果 ⑥ 验证由实现者自己做，最大的风险是什么？

**L4 设计层**
7. 什么情况下"只做 ①②③ 就动手"是合理的？
8. 错误预算怎么用在单人项目上（没有 SLA 可言）？
9. 为什么"再等等看"是最贵的决定？
10. 十站在什么情况下会让项目变慢而不变稳？

**L5 评审层**
11. 看到一个写着"第 3 周：后端完成"的里程碑列表，你会问什么？
12. 怎么判断一个人的十站表是认真填的还是应付的？

### 问题升级练习

**模糊问题**：「我该怎么避免做出来的东西没人要？」

**升级后的精确问题**：

> 在十站模型下，"没人要"有四个可分辨的成因：
> ① 站没定义清（问题本身是错的）
> ③ 站方案偏离（问题对了但方案不解决它）
> ⑥ 站没验真（方案对了但实现没做到）
> ⑧ 站没观测（做对了但没人知道）
> ——我能不能在上线前就为这四种成因各设计一个**检查点**？
> 每个检查点的成本是多少？

**提升点**：

| 原问题的毛病 | 怎么修的 |
|---|---|
| "没人要"是一个笼统结果 | 拆成四个可分辨的成因，每个对应一站 |
| 无法提前干预 | 给出"上线前的检查点"这个可操作对象 |
| 没有成本意识 | 要求给出每个检查点的成本 |

## 收束：这一篇真正要你带走的三句话

第一句话是：**十站不是流程，而是对"错误什么时候暴露"这个问题的回答。** 一份流程表只能告诉你下一步做什么，而一旦你理解了十站背后的三条前提（价值在用户那里兑现、信息一定损失、错误有"做错"与"发现晚"两种代价），你就能自己判断某一次改动需要走几站、哪一站必须留产物、哪一站的结论可以后补。这就是为什么本篇宁可花一节篇幅做推导，也不愿意直接给你一张更漂亮的流程图。

第二句话是：**整篇里性价比最高的一条纪律，是把成功判据写在方案之前。** 它之所以排在所有纪律之首，是因为遵循它的成本极低（提前想清楚"什么算成功"只需要几十分钟），而违反它的代价极高且延迟显现——你会做出一批"指标达标但用户没受益"的东西，并且要等到半年后堆积到无法忽视时才发现。这条纪律没有任何技术门槛，它唯一的难点在于：你必须接受"自己想做的事可能不被需要"这个可能性。

第三句话是：**你现在做 dsh-mini，缺的不是代码能力，而是第 ⑦⑧⑨⑩ 站。** 这个判断不是猜测，它就写在本篇 1.6.1 的练习里：当你拿第 17 步（模式系统）倒着填十站表时，你会发现技术侧的四站（③④⑤⑥）有完整记录，而产品侧的四站是空的。这恰好解释了为什么你会有"设计产品缺乏系统性思维"的感觉。系统性问题并不总需要补充新知识，有时它只需要把缺失的那几站补上，而补它的第一步，是承认它现在确实是空的。

## 本篇新词

这一篇的术语比前两篇硬一些，因为它们大多来自工程实践与软件度量学。我按"你会在读代码时遇到它们"的顺序排列。

**接缝（seam）** 是 Michael Feathers 提出的概念，指的是**一处可以在不修改代码的情况下改变程序行为的地方**。这个定义的重点在"不修改"三个字上：如果你的程序里每一段逻辑都直接写在调用点，那么改动它就必须动源代码；而如果它把某个行为交给一个可替换的对象（一个接口、一个回调、一个配置项），那么你就有了一个接缝。dsh-mini 里到处是接缝，最明显的是 `AgentOptions.requestErrorHook`——重试逻辑之所以能变成一个可卸载的插件，正是因为那个位置存在一个接缝。

**不变量（invariant）** 指的是一段在整个执行过程中始终为真的性质。它是一条约束，而不是一段代码。比如 dsh-mini 的核心不变量是"模型能看到的，必须能从日志重建"；另一条是"`assistant` 消息里的 `tool_calls` 数量，必须等于随后 `tool` 消息的数量"。不变量的价值在于：**它是你判断"某个改动是否安全"的最短路径**。当你想改一段代码时，先问它维护哪条不变量，再问你的改动会不会破坏它——这比通读全部调用方要快得多。

**耦合（coupling）** 指的是模块之间相互依赖的程度。它不是一个可以直接观测的单一量，而是一组可观测特征的统称：一个模块引用了多少个别的模块、它依赖别人提供的多少种能力、以及别人依赖它的程度。本篇在 1.5 节会给出几种可计算的度量。

**内聚（cohesion）** 指的是一个模块内部各部分的相关程度。高内聚意味着"这个模块里的东西是同一件事的不同方面"；低内聚意味着"这里放了一堆不相干的东西"。dsh-mini 的 `kernel/session.ts` 是一个值得分析的例子：它同时持有事件、维护编号、派发消息、计算统计——这四件事的相关性有多高，是一个可以讨论的问题，本篇 L3 会展开。

**扇入与扇出（fan-in / fan-out）**：一个模块的扇出是它依赖的模块数量，扇入是依赖它的模块数量。这两个数构成一个很容易算、又很有信息量的指标。扇出高的模块难以理解（你要理解它的全部依赖才能理解它），扇入高的模块难以修改（你一改就影响很多人）。两者需要的应对策略完全不同，这是本篇要区分的关键。

**不稳定性（instability）** 是 Robert Martin 给出的一个度量，记作 I，定义为 `I = Ce / (Ca + Ce)`，其中 Ce 是扇出（efferent coupling，向外的依赖），Ca 是扇入（afferent coupling，向内的依赖）。它的取值在 0 到 1 之间：I 接近 0 表示这个模块被很多人依赖而自己几乎不依赖别人（稳定），I 接近 1 表示它依赖很多人而几乎没人依赖它（不稳定）。这个量的用途不是"越低越好"，而是**判断一个模块是否处在与它应有的稳定性相符的位置上**，1.5 节会详细展开。

**知识泄漏（knowledge leak）** 指的是一个模块必须知道另一个模块的内部细节才能工作。它的典型表现是：你改了 A 的内部实现，B 就坏了，尽管 B 并没有调用 A 的接口之外的任何东西。这类耦合最难发现，因为它不体现在 import 语句里。

**深模块（deep module）** 是 Ousterhout 的说法，指的是**接口简单而内部复杂**的模块。它的反面是"浅模块"——接口很复杂但内部几乎没做什么，只是把调用转发给别的几个模块。深模块是好的，因为它把复杂度包裹在内部；浅模块是坏的，因为它把复杂度暴露给了调用方，却没有换来任何封装收益。

## 第 0 节 · 学完这一篇你能做出什么

### 0.0 先看骨架：这一篇只需要记住四块

读长文档时，大脑最怕的是"不知道还要读多久、这些内容之间是什么关系"。所以先把全篇压成四块，你读后续每一节时都能知道它挂在哪一块上。

```
┌──────────────────────────────────────────────────────────────────────┐
│  ① 三种读法 —— 决定「从哪里开始读」                     → 1.2        │
│     它是什么 ／ 它管什么 ／ 波及谁                                    │
│                                                                      │
│  ② 四类约束 —— 决定「读完要拿到什么」                   → 1.1        │
│     接口 ／ 不变量 ／ 边界 ／ 所有权                                   │
│                                                                      │
│  ③ 五个度量 —— 决定「怎么把难度变成数字」                → 1.5        │
│     不稳定性 I ／ 依赖深度 D ／ 波及面 Blast ／ 圈复杂度 M ／ LCOM    │
│                                                                      │
│  ④ 十四规则 —— 决定「卡住时查哪一条」                    → 1.6        │
│     定位 4 条 ／ 理解 4 条 ／ 修改 4 条 ／ 验证 2 条                   │
└──────────────────────────────────────────────────────────────────────┘

 一句话串起来：从哪读 → 拿什么 → 算多少 → 卡住查
```

这四块之间的关系值得说清，因为它决定了你该先学哪一块。**②是目标**（读代码是为了拿到四类约束），**①是路径**（用哪种路径取决于你为了什么目标去读），**③是量具**（把②的结果变成可比较的数字），**④是救援**（当①走不通时，查规则）。所以真实的顺序是 ②→①→③，而 ④ 是随时可查的附录。文档里按 ①②③④ 排列，只是因为 ①（方法）读起来比 ②（目标）更具体——但你要记住的骨架是"目标先行"。

### 0.1 你会得到一项很具体的能力

先描述这项能力的样子。给你一个从未见过的仓库，其中有一个你不知道用途的文件，要求你在二十分钟内回答四个问题：这个文件负责什么、它依赖了谁、谁依赖它、以及如果我要改它，哪些地方会受影响。这四项回答不需要你对业务有深入了解，也不需要你读懂每一行代码——它只需要一套固定的读法与几个可数的指标。

这项能力之所以值得单独学，是因为它决定了两件事的先后顺序。在 3.2 里我们讲到，评估一处改动的成本要数"影响面"。但影响面本身就是从代码结构里读出来的——如果你读不出结构，你就数不出影响面，那么 3.2 的方法就落空了。同样地，在 3.1 讲的十站模型里，第 ⑤ 站"实现"能不能估准，取决于你对现有结构的理解程度。所以这一篇其实是前两篇的地基。

### 0.2 你会得到三样东西

第一样是**三种读法**。读代码不是只有一种顺序，针对不同的目的要用不同的起点：想理解一个功能怎么工作，从入口往下读；想理解一个数据结构如何演化，从数据往上读；想知道一个改动会波及谁，从改动点向外读。这三种读法在 1.2 节展开，每一种都给出具体的操作步骤。

第二样是一套**度量工具**。1.5 节会给出几个可以手算的公式：不稳定性 I、扇入扇出、依赖深度、以及一个用来估算"改动总成本"的分解式。这些公式都是经典且被广泛使用的，你在任何工程讨论里都会遇到它们。

第三样是这一篇的重点：一份**高级规则应变手册**。它不是原理讲解，而是一份"遇到这种情况就做这件事"的查阅表。1.6 节给出十四条规则，每条包含症状、可能的原因、如何验证是哪一个原因、以及处置动作。这份手册的设计目标是：**当你在读代码时卡住，你能在三十秒内找到一条对应的处置建议**。

### 0.3 一个立刻能做的练习

在开始读正文之前，你可以先花十分钟做这个练习，它会让你对"自己缺什么"有直接体感。

打开 dsh-mini 的 `src/framework/loader.ts`，只看文件顶部的一段注释与它的导出列表，然后回答：这个文件解决什么问题？它依赖哪几个自己的文件？谁会用它？如果你能全部答出，说明你的读码能力已经不错，后面的内容你可以当作查漏；如果答不出第三个问题（谁会用它），那正是本篇要补的——因为"谁会用它"往往不写在文件里，而要从别处找。

## 第 0.5 节 · 系统视角 ★

### 0.5.1 这一篇在结构里的位置

第三册解决的是"怎么落地"，前两篇分别给了**流程地图**（3.1）与**成本尺子**（3.2）。而这一篇处理的是这两者共同的前提：**你得先看得懂眼前这个东西**。所以它排在第三位，并且后面几乎每一篇都会用到它。

具体来说，3.4（接口与契约）讲的"为什么改一个接口会引发连锁反应"，本质上是本篇"接缝"与"不变量"两个概念的应用——接口就是一组被公开承诺的不变量，而连锁反应就是扇入带来的后果。3.5（可逆与不可逆）判断一个改动能不能撤回，需要先知道它写入了什么状态，而"状态在哪里"是读结构才能回答的问题。3.7（测试与发布）里的"测试金字塔"与"接缝"直接相关：一个没有接缝的系统无法被测试，因为没有任何位置可以注入替身。3.9（模式词汇）讲的每一种技术模式，在结构上都对应一种特定的接缝形式。

从能力依赖上看，本篇的产物是 3.2 那套评估方法的输入。3.2 说"数一数这个改动要碰几处"，而"碰哪几处"要靠本篇的方法得到；3.2 说"数依赖深度"，而依赖深度就是本篇 1.5 节要形式化的东西之一。

### 0.5.2 三个连锁影响

**第一个连锁影响：读不出结构，会让你把所有技术判断都外包给别人。**

这条链条的具体形态是这样的。当工程师说"这个改动影响面很大"时，你无法验证这句话，只能选择相信或怀疑——而两者都不基于信息。相信的后果是你会错过那些"他说大了"的机会（本该快速做的事被推迟），怀疑的后果是你会推着团队做一件真正的危险改动。两种错误都会累积成"你与技术判断无关"的局面，而一旦这个局面形成，你在产品决策上的话语权就会持续收缩，因为产品决策最终都要落在技术代价上。

反向地说，**能读结构会给你一种很难被替代的能力**：你可以独立地把"这个需求要动几处"算出来，然后带着这个数字去和工程师对齐，而不是问"大概要多久"。这个差别在协作上是巨大的——前者是带着分析来商量，后者是索取估计。

**第二个连锁影响：不理解不变量，会把"重构"变成"引入隐蔽 bug"的主因。**

这条链条值得展开，因为它是很多项目走向失控的实际路径。假设一个系统里有一条不变量："每个 `assistant` 消息中的工具调用，都必须在日志里有一条对应的结果"。这条不变量没有写在任何类型定义里，它只存在于某个人的记忆和几条运行时断言中。某个下午，有人为了让代码更整齐，把"工具结果写入"的逻辑移到了一个新的辅助函数里，并且在某个分支上加了一个 `continue`。代码通过了所有单元测试——因为单元测试测的是单个函数的行为，不变量是跨函数的。三周后，某个用户的会话在特定序列下产生了不配对的日志，而症状是服务端返回 400，排查花了半天。

这个路径的关键在于：**不变量的破坏往往不产生即时错误**。它会先安静地存在于系统里，直到某个特定条件触发。所以读代码时"找出不变量"这件事的价值，不在于理解代码怎么工作，而在于**在你动手之前知道哪些东西不能碰**。

**第三个连锁影响：结构上的热点会决定你的产品节奏。**

这条连锁影响是给 PM 的。一个系统的交付节奏并不由团队努力程度决定，而由**最热的那几个节点的修改成本**决定。如果所有新功能都要经过同一个模块，那么交付速度的上限就是这个模块的修改速度。dsh-mini 的模式系统就是这样一个节点：五个模式的声明都要经过 `framework/modes.ts` 的解析与 `applyMode` 的装配，因此"加一个模式"的成本不取决于模式本身的复杂度，而取决于这个中间层的成熟度。

这条连锁影响有一个实用的推论：**当你发现某个产品需求反复延期时，先看它要经过哪个热点**。如果三个不同需求都卡在同一个地方，那么问题不在需求，在那个热点的结构。

### 0.5.3 这一篇与你手上项目的关系

dsh-mini 是一个特别适合练读代码能力的对象，原因是它同时具备两个特征：它的文档很好（每个文件的头部注释都写了它解决什么问题、为什么这么设计），而它的规模又很小（六十二个 TypeScript 文件、约一万三千行）。这意味着你可以在真实规模上练习，同时又能随时用文档验证自己的判断是否正确。

更好的地方在于，它的文档与代码之间偶尔会不一致——这正是练习判断力的机会。比如 `docs/00-course-map.md` 里描述的第 5 步产出是 `framework/scope.ts`，而实际实现中，作用域的核心能力（局部服务与查找顺序）是在 `context.ts` 里实现的，`scope.ts` 提供的是更高层的操作。这种不一致不是错误，而是实现演进的自然结果；但它恰好演示了本篇要教的一件事：**文档描述的是意图，代码描述的是事实，两者都要读，而且要能分辨哪一个是当前的权威**。

## L0 要解决的问题

### 0.1 现象一：打开文件，不知道从哪里开始读

这是最普遍的症状。你打开一个三百行的文件，从上往下读，读到第二十行时遇到一个不认识的类型，跳到那个类型定义，又遇到三个新的名词，如此反复，二十分钟后你回到了原点，而对这个文件仍然没有形成一个整体印象。

这个症状的根源不是"文件太长"，而是**读的顺序不对**。人的工作记忆容量有限（心理学上常引用的数字是四个左右的组块），而一个陌生文件里的信息量远超这个容量。从上往下读意味着你把注意力平均分配到了所有内容上，包括那些对你当前目的毫无关系的细节——比如一个日志格式化的辅助函数，或者一段为了兼容旧数据而写的分支。

正确的读法是**带着一个具体问题去读，并且只读回答问题所必需的部分**。这句话听起来像常识，但它的实际含义是要改变起点：如果你想理解这个文件在系统中的角色，起点不是第一行，而是**它的导出**；如果你想理解它的内部结构，起点不是第一行，而是**它的状态字段**。本篇 1.2 节会把这个问题变成三种可执行的方法。

### 0.2 现象二：能读懂单个文件，但拼不出整体结构

第二个症状比第一个更让人沮丧：你逐个读文件都读懂了，但把它们放在一起时，你说不出系统是怎么运作的。这个症状的典型提问是"这堆东西是怎么串起来的"。

它的根源在于**缺少两类信息**：一是模块之间的连线（谁调用谁、谁给谁提供什么），二是运行时的时序（一次请求进来，依次经过了哪些环节）。这两类信息都不在单个文件里，前者散落在 import 语句中，后者散落在事件注册与回调里。所以读单个文件再多次也不会得到整体结构，你需要**换一种读法：从数据的流动路径读，或者从一次具体操作的时序读**。

dsh-mini 有一个很好的练习对象：从一个用户在 GUI 里敲下问题开始，到这个答案出现在屏幕上为止，数据经过了哪些环节。要回答这个问题，你需要把 `apps/web.ts` 的 HTTP 路由、`plugins/agent-loop.ts` 的任务执行、`kernel/agent.ts` 的循环、`plugins/session.ts` 的事件转发、以及前端的 SSE 处理全部串起来。这个练习做完之后，你对整个系统的印象会与"逐个文件读懂"完全不同。

### 0.3 现象三：无法判断一个改动会波及谁

第三个症状直接对应清单里的 `4.5`。它的表现是：你想改一个函数，但你说不出有哪些地方在用这个函数。你的第一反应通常是"搜一下函数名"，而搜索结果往往给出几十个位置，你无法判断哪些是真正依赖于你要改的那部分行为的。

这个症状的根源在于**静态搜索无法捕捉动态连接**。dsh-mini 里有两类连接是搜不到的：第一类是事件监听——`ctx.on('agent/turn-end', ...)` 注册的处理器，从事件被 emit 的位置看，你只能看到事件名，看不到谁在听；第二类是服务注册与取用——`ctx.provide('tools', registry)` 与 `ctx.require('tools')` 之间的关系，同样只能通过服务名追踪。要找到这些连接，你需要知道**项目里有哪些"间接连接"的机制**，然后针对每一种去搜。

本篇 1.6 的手册里有一条专门处理这个症状（编号 R-04），它的处置方式是"列出项目中的间接连接机制，然后逐一搜索"。这个方法的普适价值在于：**任何一个成规模的系统，都会有若干种"靠约定而不是靠引用连接"的机制**，而识别它们是用一个下午就能掌握、却能长期受益的技能。

### 0.4 现象四：看不懂一个不熟悉的抽象

第四个症状是遇到一个你完全没见过的抽象时，无法判断它是必要的还是过度设计。比如你在 `dsh-mini` 里看到 `transformRows` 这个钩子，你的第一反应可能是"这是什么、为什么需要它、能不能去掉"。而这三个问题的答案不在代码里，在决策记录里。

这个症状的根源是**缺少"从结果反推设计意图"的方法**。任何抽象都是为了解决某个具体问题而存在的，因此找到它的方法不是研究它的定义，而是**问"如果没有它，会出什么问题"**。对于 `transformRows`，如果没有它，模式系统就必须生成完整的配置块（因为 patch 是整段替换），于是每加一个模式都要复制一份 `workspace` 之类的字段，这就是它的存在理由。

这个方法有一个重要的推论：**当一个抽象找不出"没有它会出什么问题"时，它很可能真的多余**。反过来说，如果一个抽象的存在理由清晰，那么即使它看起来笨拙，也不该轻易去掉。这个判断标准简单到几乎不用学，但它是很多工程师在评审时真正使用的标准。

### 0.5 这一篇要回答的四个问题

把这四个症状收拢，本篇要回答四个问题，它们分别对应 L1 的四节。

第一个问题是：读代码的目标到底是什么？这个问题必须先回答，因为它决定了你要读什么、不读什么。答案是**提取约束**而不是理解每一行。

第二个问题是：有哪些读法？针对不同的目的，起点应该选在哪里？这一节给出三种读法与它们的适用场景。

第三个问题是：怎么把"我觉得这个模块很难改"变成可以讨论的数字？这一节给出几个经典度量的定义与手算方法。

第四个问题是：卡住的时候怎么办？这一节是一份十四条规则的应变手册。

## L1 设计与原理

### 1.1 读代码的目标：提取约束，而不是理解每一行

```
   L0 症状 ──► 【1.1 目标】 ──► 1.2 路径 ──► 1.4 识别 ──► 1.5 量化
                   ▲
              你在这一节：先定"拿什么"，方法才有着力点
```

在讲方法之前，需要先把目标定对，因为目标错了方法就无处着力。多数人对"读懂代码"的默认理解是"理解每一行在做什么"，而这个理解会导致两种浪费。

第一种浪费是**读了很多用不上的东西**。你去读 `dsh-mini` 的 `kernel/llm.ts`，其中有一段把网络响应中的工具调用字段转成内部结构的逻辑，包含对空值、字符串、对象三种形态的处理。这段逻辑当然有其原因（不同的模型服务返回的格式不一致），但如果你当前的目的是"给工具加一个参数"，理解这段格式兼容逻辑对你毫无帮助。

第二种浪费是**读完仍然不知道什么不能碰**。逐行理解能让你知道代码怎么工作，但它不会自动告诉你"这里有一条不变量，改了会出跨模块的问题"。而后者往往才是你真正需要的信息——因为你的目的是**安全地改动**，而不是复述实现。

所以我们把目标定为：**提取约束**。具体来说，读一个模块时要提取四类东西。

第一类是**接口约束**，也就是这个模块对外承诺了什么。它回答的问题是"我能依赖它做什么"。这类约束通常写在类型定义与函数签名里，但更重要的部分写在文档注释里——dsh-mini 的 `Tool` 接口里 `sideEffect` 字段的注释说明了它的取值与含义，那是接口约束的一部分，而类型系统只能告诉你它的取值范围，不能告诉你"守卫会依据它做裁决"。

第二类是**不变量约束**，也就是这个模块维持了什么始终为真的性质。它回答的问题是"我改了它，什么东西会静默地坏掉"。这类约束几乎不会写在类型里，它们通常存在于文档、测试、以及运行时断言中。dsh-mini 的 `assertModelVisibleMatchesLog` 就是一条不变量的显式表达，而"工具调用与工具结果必须一一配对"这条不变量，则同时出现在文档、代码注释与运行时的处理逻辑里。

第三类是**边界约束**，也就是这个模块的职责范围在哪里结束。它回答的问题是"哪些事不该让它做"。这类约束最容易被忽略，但它是判断"某个需求该不该加在这里"的依据。`kernel/session.ts` 的头部注释里写着"它不做决策——决定该 append 什么，是上层循环的事"，这就是一条边界约束；它解释了为什么"自动压缩"不该写进 `Session` 类，而应该是一个插件。

第四类是**所有权约束**，也就是这个模块的状态归谁管、什么时候被清理。它回答的问题是"我能在这里存东西吗"。在 dsh-mini 里，插件注册的一切都通过 `ctx.effect()` 挂在容器上，因此容器卸载时会被清理；而如果某个插件把状态存在模块级变量里，它就脱离了所有权体系，会在卸载后残留。

把目标从"理解每一行"改成"提取这四类约束"，会立刻改变你的读法。你不会再从第一行开始读到底，而会先去看导出与注释（接口约束）、再去找断言与测试（不变量约束）、再看文件头的设计说明（边界约束）、最后看状态与注册方式（所有权约束）。对多数文件来说，这四步加起来只要十几分钟。

### 1.2 三种读法：起点由目的决定

```
   1.1 目标（要拿四类约束）
         │  用什么拿？
         ▼
   【1.2 路径：从哪开始读】──────┬──────┬──────┐
                                 ▼      ▼      ▼
                              接口   状态   波及面
                                 └──────┴──────┘
                                        │ 产出三类东西
                                        ▼
                          模块卡片 / 控制骨架 / 波及清单
                                        │
                                        ▼
                                  1.4 识别（固定成果）
```

有了明确的目标，接下来是方法。读代码有三条主要路径，它们不是"由易到难"的排序，而是**对应三种不同的目的**。选错路径的典型后果是：你想知道"改动会波及谁"，却从头到尾读了一遍实现细节，读完仍然答不出那个问题。

```
   读法一：它是什么          读法二：它在管什么         读法三：改动波及谁
  ──────────────────        ──────────────────         ──────────────────
       导出列表                   状态字段                    改动点
          ↓                          ↓                    ↙        ↘
       头部注释               谁改它 / 何时改          直接依赖者    间接依赖者
          ↓                          ↓                 （搜得到）   （靠约定）
       公共签名                状态间的不变量               ↘        ↙
          ↓                          ↓                       波及清单
     【跳过实现】               理解控制骨架              （按三类分组）
          ↓                          ↓                         ↓
   整体印象（模块卡片）         能安全地改内部             能评估成本
```

三个起点对应三个不同的输出物：读法一产出模块卡片，读法二产出"能安全改内部"的信心，读法三产出波及清单。**如果你读了很久却没有产出这三样中的任何一样，就是读法选错了。**

#### 1.2.1 读法一：读接口，回答"这个模块是什么"

第一种读法适用于你第一次接触一个模块，目的是建立它的整体印象。它的操作顺序是固定的四步，而且刻意**不读实现**。

第一步是读导出列表。TypeScript 文件的导出就是它的公开面，一个模块能对外提供什么，全在这里。以 `kernel/tools.ts` 为例，导出包含 `Tool` 接口、`ToolResult` 类型、`validateArgs`、`truncate`、`ToolRegistry` 类、以及 `ok` / `fail` 两个结果构造器。仅从这份列表你就能推断：这个模块负责工具的定义、校验、结果构造与注册，而不负责执行（执行在 `ToolRegistry.execute` 里，但它的实现细节可以稍后看）。

第二步是读文件头部注释。dsh-mini 的每个文件都有大段头部注释，说明它解决什么问题、为什么这么设计、以及它与前一步的关系。这是这个项目最有价值的学习材料，因为那些注释记录了**决策的理由**，而理由是无法从代码里推出来的。以 `framework/context.ts` 的头部为例，它解释了"服务注册写共享表、归属记在注册者身上"这条规则，以及不去这么设计会出现什么具体故障。读完这段注释，你对这个模块的理解会超过读完整份实现。

第三步是读公共方法的签名。这一步的目的是确定**调用方式**与**依赖要求**，而不是理解算法。你只需要知道"调用它需要准备什么、它返回什么、它可能抛什么异常"。

第四步是**跳过实现**，直接进入下一个模块。这一步是这套读法里最反直觉、也最重要的。它的依据是：绝大多数情况下，你不需要理解一个模块的实现就能使用它；而如果你将来需要改它，你会再回来，那时你的目的变了，读法也该变。

这套读法的产出是一张**模块卡片**，包含四行：它是什么、它依赖谁、谁依赖它、它的关键约束是什么。L5 节会给出这张卡片的具体模板。

#### 1.2.2 读法二：读状态，回答"这个模块在管什么"

第二种读法适用于你要修改一个模块的内部逻辑时。它的起点不是接口，而是**状态**——也就是这个模块持有或改变的那些数据。

第一步是列出所有状态。在 TypeScript 里，这意味着找出所有字段声明、模块级变量、以及闭包捕获的变量。以 `kernel/session.ts` 的 `Session` 类为例，它的状态包括：事件数组 `#events`、turn 编号计数器 `#nextTurn`、step 编号计数器 `#nextStep`、以及一个可选的事件回调 `#onEvent`。

第二步是问"每个状态由谁改、什么时候改"。这个问题的答案揭示了模块的实际控制流。在 `Session` 里，唯一写入事件数组的地方是 `append` 方法，而 `#nextTurn` 与 `#nextStep` 只在 `startTurn` 与 `startStep` 中被修改。这个发现很重要，因为它意味着**如果你要改变事件的产生方式，唯一需要修改的位置只有一个**。

第三步是找状态之间的不变量。哪些状态必须满足某种关系？在 `Session` 里，`#events.length` 必须等于下一个事件的 `seq`（因为 seq 是"不跳号"的），而 `#nextTurn` 必须大于所有已有 `turn/start` 事件中的最大编号。这两条关系都没有被类型系统表达，它们是靠实现维护的。

第四步是判断状态的所有权。这个模块的状态会不会泄漏到外面？`Session` 的 `events` getter 返回的是内部数组的引用（返回类型标注为 `readonly SessionEvent[]`），这意味着调用方在类型上不能修改它，但在运行时它仍然是同一个对象。这是一个**值得注意的细节**：如果某个调用方在运行时往里面 push 了一条事件，`seq` 的编号规则就会被破坏，而类型系统不会阻止这件事。

读状态的方法之所以有效，是因为**状态是行为的根据**。理解了状态与它的变更点，你对这个模块的理解就有了骨架，剩下的实现细节都可以挂在这个骨架上。

#### 1.2.3 读法三：读波及面，回答"改动会影响谁"

第三种读法适用于你已经确定要改某处，现在需要知道风险。它的起点是**改动点本身**，向外扩散。

第一步是确定你真正要改的是什么。这一步需要精确：你可能要改一个函数的行为、一个类型的字段、一个配置的默认值，或者一个事件的数据结构。这四类改动的波及方式完全不同——改函数行为影响的是调用方，改类型字段影响的是所有构造它的地方，改默认值影响的是没显式配置的那些使用，而改事件数据结构影响的是所有监听器。

第二步是列出**直接依赖者**。对改函数来说，这可以靠搜索函数名得到；对改类型来说，搜索类型名；对改事件来说，搜索事件名。这一步是机械的，但要注意一个陷阱：搜索出来的结果里混着"只是提到这个名字"和"真正依赖这个行为"两类，需要逐个判断。

第三步，也是关键的一步，是找出**间接依赖者**。这类依赖搜不到，因为它们是通过约定连接的。在 dsh-mini 里至少有四种间接连接机制：事件监听（`ctx.on('事件名', ...)`）、服务注册与取用（`ctx.provide` 与 `ctx.require`）、配置引用（`bundles/*.json` 与 `modes/*.json` 里的插件路径与字段）、以及模式与提示词之间的内容约定（提示词里提到的工具名必须在 `tools` 列表里）。要处理间接依赖，你需要知道项目里有哪些这类机制，然后针对每一种去搜。

第四步是把波及面按"修复难度"分层。一个改动点可能影响三类地方：会立刻报错的（类型不兼容、测试失败）、会静默失效的（事件监听器收不到、配置项被忽略）、以及只有运行时特定条件下才出问题的（边界情况）。这三类的处理优先级不同——第二类最危险，因为它不会主动暴露。

这套读法的产出是一份**波及清单**，它按"影响类型 × 修复难度"分组。这份清单可以直接用于 3.2 里的利息估算，也可以作为与工程师讨论时的共同语言。

### 1.3 架构的三种视图与它们的读法

```
   1.2 三种读法（读代码的路径）
         │  读的对象是什么？
         ▼
   【1.3 视图：整体结构怎么呈现】
         │
    ┌────┼────┐
    ▼    ▼    ▼
  模块图 依赖图 时序图    ← 分别回答：由哪些部分组成 / 谁依赖谁 / 经过哪些环节
    │    │    │
    └────┴────┘
         │  三者合起来 = 1.2 三种读法的作用对象
         ▼
   1.4 识别 ──► 1.5 量化
```

前面三种读法是针对单个模块的。要理解整体结构，你需要把视角抬高，从"模块"升到"模块之间的关系"。工程上有三种常用的视图，它们各自回答一个问题，而各自的读法也不同。

#### 1.3.1 模块图：回答"系统由哪些部分组成"

模块图是最常见的视图，它把系统分成若干块，每块标注职责。dsh-mini 的分层是：

```
  ① 界面层      apps/         cli.ts · repl.ts · web.ts · verify.ts
                    │
  ② 声明层      bundles/ · modes/ · profiles/ · prompts/ · skills/
                    │         （数据与声明，不是代码；由装载器读取）
                    ▼
  ③ 框架层      framework/    context · events · scope · loader · modes
                    │
  ④ 能力层      plugins/      llm · tools · session · agent-loop · retry · guard
                    │         evolution/ 由能力层调用（memory · skills · diagnose · evolve）
                    ▼
  ⑤ 纯能力层    kernel/       llm · session · agent · tools · retry · guard · checkpoint
                              ← 不知道上层存在（这是最关键的一条约束）
```

读模块图的方法是**看依赖规则而不是看文件名**。上面这张图配上了一条可验证的规则：依赖只能从 ① 指向 ⑤，反向即违规。因此任何时候你在 `kernel/` 里看到 `import ... from '../framework/context.ts'`，架构就已经被破坏了。这条规则的价值在于它把"分层"从一个说法变成了一次可执行的检查。

验证这条规则的方法很直接，用一条命令即可：

```powershell
# 在 dsh-mini 根目录执行
rg -n "from '\.\./framework" src/kernel/    # 期望：无输出
rg -n "from '\.\./plugins"   src/kernel/    # 期望：无输出
rg -n "from '\.\./apps"      src/plugins/   # 期望：无输出
```

这套命令的意义在于，它把一个抽象的架构原则变成了一次可执行的检查。这也是本篇要教的第一种"把约束变成检查"的技术——**凡是能写成命令的约束，就不要只写在文档里**。

#### 1.3.2 依赖图：回答"谁依赖谁、依赖有多深"

模块图给的是分层，依赖图给的是具体的连线。它的读法要点是找三种特殊形态。

第一种形态是**循环依赖**，即 A 依赖 B 而 B 又依赖 A。它的危害在于两者无法独立演进与独立测试，而且它会让"依赖深度"这个概念失去意义（因为可以无限绕圈）。在 dsh-mini 这类分层清晰的项目里，循环依赖是被分层规则排除的——因为依赖只能单向。

第二种形态是**扇入极高的节点**，也就是前面说的热点。读依赖图时要把它们标出来，因为它们决定了改动的风险等级。

第三种形态是**跨层依赖**，也就是跳过中间层的连线。比如 `plugins/` 里的某个文件直接 import `kernel/` 的一个内部辅助函数而没有通过服务。这类依赖不违反"方向"规则（因为仍然是向内依赖），但它绕过了扩展点，会让这个插件无法脱离那个具体实现。dsh-mini 的 `plugins/tools.ts` 直接 import `kernel/builtin-tools.ts`、`kernel/command-tool.ts`、`kernel/authoring-tools.ts`，这在方向上是合法的，但列表必须与工具池保持一致——这就是一处需要注意的跨层依赖。

#### 1.3.3 时序图：回答"一次操作经过了哪些环节"

第三种视图最难从代码里直接读出来，因为它涉及运行时。它的读法是：**选一次具体的操作，顺着数据追下去**，并且把"调用"与"事件"分开记。以 dsh-mini 里"用户在 GUI 里提问"为例：

```
 调用链（谁调用谁）                        事件链（谁在监听什么）
 ────────────────────────────           ──────────────────────────────
 浏览器
   │ POST /api/task
   ▼
 apps/web.ts
   │ 立即返回 202（不阻塞）
   │ runTask(text)
   ▼
```

读这张图时有一个要点：**注意哪些环节是钩子而不是直接调用**。上面有三处是钩子——`agent/task-ready` 的任务改写、`onEvent` 的事件转发、`session/event` 的 SSE 推送。如果你只顺着函数调用走，这三处都会漏掉，因为它们不在调用链上而在事件链上。**能把调用链与事件链分开看，是读懂插件化系统的关键。**

### 1.4 从结构里读出约束：四类约束的识别方法

```
   1.1 目标 ──► 1.2 路径 ──► 1.3 视图
                                  │  读到了，但还在脑子里
                                  ▼
                        【1.4 识别：把"读到了"变成"写下来"】
                                  │
                        四类约束各有一套识别方法：
                        接口 → 找承诺   不变量 → 找断言
                        边界 → 找"它不做"  所有权 → 找创建与清理
                                  │
                                  ▼
                            1.5 量化（把清单变成数字）
```

前面几节讲了怎么读。这一节要讲读完之后怎么把结论固定下来，也就是怎么把"我大概明白了"变成"我能列出约束"。

**识别接口约束**的方法是把模块的公开面写成一份清单，每项标注"调用方可以依赖它做什么"以及"它承诺不变的部分是什么"。举例来说，`ToolRegistry.register` 的接口约束不只是"传入一个工具并注册"，还包括"重复注册同名工具时后注册的覆盖先注册的"这个行为承诺——后半句才是真正重要的部分，因为它决定了调用方能不能安全地重复注册。这类承诺通常写在实现里而不是签名里，因此识别它的方式就是去找实现里的 `if` 与 `throw`。

**识别不变量**的方法是按"跨函数"去找。单个函数内部的前置条件与后置条件容易看出来，真正危险的是那些跨多个函数、跨多次调用保持的关系。识别它们有三个可靠来源：一是代码里的断言（`assert` 开头的函数调用通常是显式不变量），二是文档里的强调句（比如"必须"、"不能"、"永远"这类词），三是测试里的边界用例（如果某个测试专门验证一种奇怪的组合，通常说明那种组合是必须防止的）。dsh-mini 的 `assertModelVisibleMatchesLog` 属于第一类，而 `deriveMessages` 上方的注释"派生时只看这些，别的一律忽略"属于第二类。

**识别边界约束**的方法是读文件头部注释里的"它不做/它不管"这类句子。这类句子的价值极高，因为它直接回答"某个需求该不该加在这里"。除了读注释，还有一个经验判据：**如果一个模块的名字里出现了"and"或者它的职责需要两个不同的动词来描述，它的边界可能已经模糊了**。`Session` 类的职责描述是"追加事件、派生消息、算统计"——三个动词，这是 L3 节要讨论的一个内聚性问题的来源。

**识别所有权约束**的方法是看状态在哪里被创建、在哪里被清理。在插件化的系统里，这条尤其重要，因为"注册"与"清理"必须成对出现。dsh-mini 的做法是统一的：任何注册都通过 `ctx.effect(disposer)` 或 `ctx.provide` / `ctx.on`（它们内部会调用 `effect`），因此卸载容器时会自动回滚。识别这类约束的方法是搜索裸的状态写入——任何直接给模块级变量赋值、或者直接 `push` 到某个长生命周期数组的代码，都可能是脱离所有权的状态。这在本篇的手册里对应规则 R-11。

### 1.5 量化：把"我觉得很难改"变成可以讨论的数字

```
   1.4 识别（拿到定性清单）
          │  但它还只是"我觉得难"
          ▼
   【1.5 量化：把难度变成数字】
          │
   ┌──────┼──────┬──────┬──────┐
   ▼      ▼      ▼      ▼      ▼
   I      D    Blast    M    LCOM     ← 五个量，各有适用边界
   │      │      │      │      │
   └──────┴──────┴──────┴──────┘
          │
          ▼
   L2 决策（用数字做判断）──► L3 推演（用数字反过来改方案）
```

到目前为止，本篇讲的都是定性方法。但工程上一个模块"难不难改"是可以量化的，而且量化之后它就能进入 3.2 那套成本讨论。这一节给出五个经典度量，它们都是被广泛使用、可以手算的。我在每个公式后面都会说明它的适用边界，因为**误用度量比不做度量更糟**。

#### 1.5.1 扇入与扇出，以及不稳定性 I

设一个模块 M 的扇出（efferent coupling）为 Ce，即 M 依赖的外部模块数量；扇入（afferent coupling）为 Ca，即依赖 M 的外部模块数量。Robert Martin 定义的不稳定性为：

$$I(M) = \frac{C_e(M)}{C_a(M) + C_e(M)}$$

这个量的取值范围是 0 到 1。当 I 接近 0 时，M 依赖别人少、被别人依赖多，它处在**稳定**位置；当 I 接近 1 时，M 依赖别人多、被别人依赖少，它处在**不稳定**位置。

这个公式的用途不是"越低越好"，而是判断一个模块是否处在**与它的职责相符**的位置上。Robert Martin 由此提出稳定依赖原则：**依赖应该指向更稳定的方向**。它的实际含义是，一个不稳定的模块（I 高）可以去依赖一个稳定的模块（I 低），但反过来不该发生——因为稳定的模块被很多人依赖，它如果反过来依赖某个不稳定模块，那么那个不稳定模块的任何改动都会传导到所有人。

把这个原则用在 dsh-mini 上会得到一个有意思的观察。`kernel/session.ts` 里 `Session` 类的扇入很高（被 `agent.ts`、`plugins/session.ts`、`plugins/agent-loop.ts`、`plugins/evolution.ts`、以及多个 app 使用），扇出则较低（它只依赖 `llm.ts` 的类型与 Node 的 `fs`）。按公式它的 I 很低，是一个稳定模块。而 `apps/cli.ts` 的扇入为 0（没有别的模块 import 它），扇出很高（它依赖 loader、shared-mode、plugins 的类型等），I 接近 1，是不稳定模块。**依赖方向是从 `cli.ts` 指向 `session.ts`，正好符合稳定依赖原则**，这说明这个项目的分层没有倒置。

反例也值得构造一个：假设某天有人为了让 `Session` 能直接写 telemetry，让 `kernel/session.ts` import 了 `plugins/telemetry.ts`。这时 `session.ts` 的扇出增加，而 `telemetry.ts` 的扇入增加——一个稳定模块依赖了一个不稳定模块，这会让 `telemetry` 的任何改动传导到整个会话层。**这正是"依赖方向被打乱"在度量上的表现**，也是为什么架构规则值得用命令来检查。

#### 1.5.2 依赖深度

依赖深度 D(M) 定义为从 M 出发、沿依赖边走到"没有进一步依赖"的最长路径长度。它的计算方式是递归的：

$$D(M) = 1 + \max_{X \in \text{deps}(M)} D(X), \qquad D(M) = 1 \text{ 若无依赖}$$

这个量回答的问题是：**要理解 M，最少需要先理解多少层东西**。它对人的影响是直接的——每多一层，理解成本大致线性增加，而人的工作记忆容量是固定的。

用 dsh-mini 举一个具体的例子。`plugins/compaction.ts`（第 18 步的施工图）的依赖深度可以这样数：它依赖 `framework/context.ts`（服务与事件）、`kernel/session.ts`（事件追加）、`kernel/compaction.ts`（派生逻辑）、以及 `kernel/llm.ts`（摘要调用）。这四个是它的直接依赖，深度加一。而其中 `kernel/session.ts` 又依赖 `kernel/llm.ts` 的类型；`framework/context.ts` 依赖 `framework/events.ts`。所以从 `plugins/compaction.ts` 出发的最长路径大约是四层。四层意味着：一个新接手的人要改动压缩逻辑，需要先建立四层理解。

这个量还有一个有用的变体：**只数"跨越抽象层"的依赖**。因为同一层内部的依赖（比如 `kernel/` 里 `agent.ts` 依赖 `retry.ts`）通常可以放在一起理解，而跨层的依赖（`plugins/` 依赖 `framework/`）意味着要切换心智模型。按这个口径，上面那个例子的跨层深度是三层，这个数字更能反映真实成本。

#### 1.5.3 波及面与它的传递闭包

波及面（blast radius）的严格定义是：从改动点出发，沿"依赖"的反方向（也就是"谁依赖我"）做传递闭包，得到的集合大小。

$$\text{Blast}(M) = \left| \left\{ X : X \xrightarrow{*} M \right\} \right|$$

这里 $X \xrightarrow{*} M$ 表示存在一条从 X 到 M 的依赖路径。这个量直接对应 3.2 里说的"影响面"，区别在于 3.2 用的是手工数的方式，而这里是它的形式化定义。

这个公式的价值在于它揭示了**为什么热点那么危险**：一个模块如果被 5 个模块直接依赖，而每个又各自被 3 个模块依赖，那么它的波及面可能是十几甚至几十——**因为依赖关系是乘法的，不是加法的**。这也解释了为什么架构上"层次"如此重要。

```
 波及面为什么是乘法：

      改 M 的内部
          │
   ┌──────┴───┬────┬────┬────┐        5 个直接依赖者
   ▼          ▼    ▼    ▼    ▼
  d1         d2   d3   d4   d5
   │          │    │    │    │
   ×3         ×3   ×3   ×3   ×3        每个又有 3 个依赖者
   ▼          ▼    ▼    ▼    ▼
 合计 = 5 + 15 = 20                    乘法增长，不是加法

 分层如何把它压回去：

   apps/        cli.ts · repl.ts · web.ts     ← 波及面止于此层
   ─────────────────────────────────────────  层边界：依赖单向
   framework/   context · loader · modes      ← 改动只波及同层与上一层
   ─────────────────────────────────────────
   kernel/      llm · session · agent         ← 被依赖最多，但它不知道上层
```

分层的本质是**规定依赖只能单向**，因此一个模块的改动只会向"依赖它的那一侧"传导，而不会绕回来形成长链。这就是为什么在 1.3.1 里要把"依赖方向"写成一条可执行的检查——它对应的正是这里这个波及面的量。

在 dsh-mini 上可以做一个粗略的计算作为练习。`kernel/session.ts` 导出的事件类型 `SessionEvent` 被 `plugins/session.ts`（事件类型转换）、`plugins/agent-loop.ts`（turn 边界）、`apps/web.ts`（事件展示）、`apps/repl.ts`（事件展示）等使用，而这些使用者又各自被别的模块使用。虽然这个项目的规模小，波及面的绝对值不大，但**计算它的过程本身就是一次架构复习**。

#### 1.5.4 圈复杂度与它的边界

圈复杂度（cyclomatic complexity）由 Thomas McCabe 在 1976 年提出，定义是控制流图中的边数与节点数之差再加常数项：

$$M = E - N + 2P$$

其中 E 是边数，N 是节点数，P 是连通分量数（对单个函数通常取 1）。对于只有顺序与分支的代码，它等于"判定点数量加一"。实际使用时不需要画控制流图，只需要数 `if`、`while`、`for`、`case`、`&&`、`||` 这些构造的出现次数再加一即可。

这个度量的用途是识别**单个函数内部的复杂度**，它的典型阈值是十（超过十的函数通常建议拆分）。但它有一个重要的边界必须说清：**圈复杂度只衡量控制流的复杂，不衡量理解的难度**。一段有十个分支但结构清晰的代码，可能比一段只有三个分支但涉及隐式状态与异步时序的代码容易理解得多。所以在阅读一个具体的模块时，圈复杂度只是参考，不要用它代替真正的理解。

dsh-mini 里有一处值得用它做练习：`kernel/guard.ts` 里的守卫规则实现，以及 `kernel/agent.ts` 里的循环与工具执行部分。后者的分支数量明显多于前者，但它们各自的难度是否与圈复杂度成正比，值得你自己判断一次——这个判断过程本身就是一次很好的训练。

#### 1.5.5 内聚度与 LCOM

内聚度的经典度量是 Chidamber 与 Kemerer 提出的 LCOM（Lack of Cohesion of Methods，方法缺乏内聚度）。它的简化版定义是：在一个类里，统计"不共享任何实例字段的方法对"的数量。共享字段越多，LCOM 越低，内聚越高。

用这个度量看 `Session` 类会得到有意思的结果。它的方法大致分四组：`append` 与 `startTurn`/`endTurn`/`startStep`/`endStep`/`recordXxx` 系列（操作事件数组与计数器）、`deriveMessages`（派生消息）、`stats`（计算统计）、`save`/`load`（持久化）。第一组共享 `#events` 与计数器；`deriveMessages` 与 `stats` 只读 `#events`；`save` 只读 `#events`。按严格口径，`save` 与 `startTurn` 不共享任何被写入的字段（虽然都读 `#events`），因此会增加 LCOM。

但这里必须立刻补上一个边界说明：**LCOM 低不等于设计好，LCOM 高也不等于设计差**。`Session` 承担四组职责是它当前的状态，而这个状态是否该改变，取决于这些职责是否真的会在不同节奏下变化。会话的持久化方式（第 20 步）与事件编号规则（第 7 步）大概率会以不同的节奏演进，因此它们分属不同模块可能更好；但"派生消息"与"计算统计"都是 `#events` 的纯函数，它们在同一个文件里反而更利于保持"唯一真相源"这条架构原则。

这就是度量的正确用法：**用它的数值引发一次讨论，而不是用它替你做决定。**

### 1.6 高级规则应变手册 ★

```
   1.1 ──► 1.2 ──► 1.3 ──► 1.4 ──► 1.5
                                   │
                            走不通的时候怎么办？
                                   ▼
                     【1.6 十四规则：救援，不是主干】
                                   │
        定位 R-01…04 ┌── 理解 R-05…08 ──┐ 修改 R-09…12 ──┐ 验证 R-13…14
                     └──────────────────┴───────────────┘
                                   │
                            何时查？卡住时。不卡不查。
```

前面五节讲的是原理与方法。这一节是本篇的核心工具：一份可以在读代码时随手查阅的**规则手册**。它的每一条都按同一个格式写：症状（你会看到什么）、可能原因（按概率排序）、如何确认是哪一个原因（一个具体可执行的动作）、处置动作、以及**什么时候不要用这条规则**。

这份手册的设计目标是"三十秒内找到处置建议"，因此它的写法偏向操作指令，而它背后的原理在 1.1 到 1.5 里已经讲过。十四条规则按场景分成四组：定位、理解、修改、验证。

#### 组一 · 定位（R-01 至 R-04）

**R-01｜症状：不知道某个功能在哪个文件里实现。**
可能原因是命名与你的预期不同（例如你以为叫 "context" 的东西在项目里叫 "scope"）。确认方法是先搜**功能相关的字符串**而不是文件概念，例如搜界面上的文案、日志里的中文提示、或者事件名。处置动作是从任意一个可观察的表面入口反推：找到用户能看到的字符串（提示、日志、界面文案），搜索它的出现位置，那个位置通常就在调用链的中间。**不要这么做的情形**：当项目有代码生成或 i18n 字典时，字符串与实现文件之间隔着映射层，此时应改为搜索映射表的键。

**R-02｜症状：找到一个文件，但不确定它是否还在被使用（死代码）。**
可能原因有三：它被动态引用（配置文件的插件路径、事件名匹配），它是为将来准备的（尚未接入），或者它确实是残留。确认动作是分别检查三处——搜索配置文件里有没有它的路径、搜索它的导出名有没有被字符串形式使用、以及查看 git 的最近改动时间。处置动作是：如果三种检查都证明它没被使用，先不要删，而是记录下来并在下次改动相关模块时处理（因为删除本身也是一次有风险的改动）。**不要这么做的情形**：你不能仅凭"搜索不到"就判断它是死代码，因为动态引用所依赖的字符串拼装可能让搜索失效。

**R-03｜症状：想知道"这个函数被谁调用"，但搜索结果里混着大量无关项。**
可能原因是函数名过于通用（如 `handle`、`run`、`ok`），或者它作为回调被传递（此时调用点搜不到）。确认动作是改用**定义处的引用搜索**：先找到精确定义（含类名或模块名限定），再用带限定的形式搜索，例如搜 `agent.run(` 而不是 `run(`。处置动作是在你的笔记里记录该函数的"调用形态清单"（直接调用、作为回调传递、通过事件触发），这三类各自的搜索方法不同。**不要这么做的情形**：当函数被 `bind` 或包装后传递时，定义处的名字可能完全不出现，此时要靠类型信息而不是文本搜索。

**R-04｜症状：改一个事件或服务，不知道谁会受影响。**
这条直接对应前面的 0.3 现象，也是四条定位规则里最有价值的一条。可能原因是你只搜了事件名，而没有搜到通过约定建立的连接。确认动作是列出项目的**间接连接机制清单**，然后逐一搜索。以 dsh-mini 为例，这份清单至少包含四项：

| 连接机制 | 搜索方式 | 在 dsh-mini 中的例子 |
|---|---|---|
| 事件监听 | 搜事件名字符串 | `rg "'agent/turn-end'" src/` |
| 服务注册与取用 | 搜服务名 | `rg "'tools'" src/plugins src/apps` |
| 配置引用 | 搜文件路径与字段名 | `rg "plugins/retry" bundles profiles modes` |
| 内容约定 | 搜名字在文档与提示词中的出现 | `rg "run_program" modes prompts skills` |

处置动作是把四类搜索结果合并，然后按 1.2.3 的第四步分成"会报错"与"会静默失效"两类。**不要这么做的情形**：如果项目没有统一的连接机制（每个插件各用一套），那么这份清单要按项目实际重建——重建它的过程本身就是理解这个项目架构的最好方式。

#### 组二 · 理解（R-05 至 R-08）

**R-05｜症状：能读懂每一行，但说不出这个模块在做什么。**
可能原因是你在读**实现细节**而不是读**不变式**——也就是 1.1 里说的目标错了。确认动作是做一个测试：合上文件，试着用一句话说出"它保证什么"。如果你说的是"它做了 A，然后做 B，然后做 C"，那是流程复述，不是理解。处置动作是改用 1.2.2 的"读状态"方法：先只列状态，再问每个状态由谁改，最后问状态之间的不变量。走完这三步，通常会得到一个比流程更凝练的说明。**不要这么做的情形**：对于纯函数式的模块（没有任何状态），这个方法不适用，此时应该改为问"它的输入与输出的关系是什么"，也就是把它当作一个数学函数来理解。

**R-06｜症状：看到一个不熟悉的抽象，不知道它是必要的还是过度设计。**
可能原因是判断标准用错了——你试图从它本身判断它，而正确的方向是问"没有它会怎样"。确认动作是构造反事实：假设把它去掉，具体会发生什么？要给出具体到代码层面的答案，例如"那么每个模式都必须写完整的配置块，而不是只写差异"。处置动作是：如果这个反事实具体且严重，那么保留并理解它；如果答不出任何具体后果，那么把它记入"待验证的可疑抽象"清单，并在下次改动相关代码时用实验验证。**不要这么做的情形**：当抽象的存在理由写在设计文档里时，先读文档再做判断——此时反事实构造会浪费时间，而理由是现成的。

**R-07｜症状：代码里有一段看起来没有必要的绕行逻辑。**
这条与 R-06 不同：R-06 是针对抽象，R-07 是针对具体的代码分支。可能原因有三种，按概率排序：处理历史数据的兼容（最常见）、处理平台差异（Windows 与 Unix 的路径、权限、进程行为）、以及处理并发或时序的竞态。确认动作是分别看三处证据——该分支的注释是否提到旧版本或格式、是否涉及路径分隔符或进程信号、是否涉及超时与回调顺序。处置动作是找到证据后补一条注释（即使原注释已有，也值得补充"为什么不能简化"），因为这类逻辑下一次仍然会被人质疑。**不要这么做的情形**：如果三种证据都找不到，且这段逻辑也没有测试覆盖，那么它可能是真正的死代码，此时应改为走 R-02 的流程。

**R-08｜症状：不确定某个文件里哪些是主要路径、哪些是边界处理。**
可能原因是错误处理与主逻辑交织在一起，没有明显的视觉分界。确认动作是数一下这个文件里 `try`/`catch`、`if (!x)`、`??`、以及 `throw` 的出现次数与位置。处置动作是用"正向读一遍，反向读一遍"的方法：正向读时只看成功路径（把所有的错误分支在心里跳过），得到主干流程；反向读时只看错误分支，得到它需要防御什么。这两遍读完，你对文件的印象会从"一团"变成"一条主干加若干补丁"。**不要这么做的情形**：当错误处理本身就构成了主要逻辑时（例如一个校验器、一个解析器），主干就是错误分支，此时不该跳过。

#### 组三 · 修改（R-09 至 R-12）

**R-09｜症状：改了一个地方，结果三处报错。**
这是最常见的修改类症状。可能原因是**隐式契约**——那个类型或函数被当作契约的一部分，很多地方依赖了它的具体形态。确认动作是按错误的类型分类：如果是编译错误，说明是显式依赖，改齐即可；如果是运行时错误或测试失败，说明是隐式依赖，需要找出那些地方为什么依赖了被改的部分。处置动作是先改齐显式依赖（让编译通过），再逐个检查隐式依赖，并且**在每一处问一句"它依赖的是有意承诺的行为，还是实现细节"**。后者如果有，就是一处应该补充文档或断言的缺口。**不要这么做的情形**：不要为了让编译通过而使用类型断言（`as`）或 `any` 绕过——那样会把一个显式的错误变成一个静默的隐患，而静默隐患正是 3.2 里说的"隐性成本"。

**R-10｜症状：想在某处保存一点状态，但不确定合不合适。**
可能原因是你没有确认这个模块的**所有权模型**。确认动作是问三个问题：这个状态的生命周期应该是什么（请求级、会话级、还是进程级）；这个模块卸载或重启时它该怎么处理；有没有别的模块也需要这个状态。处置动作按答案分支：如果是请求级，就作为局部变量或参数传递；如果是会话级，就应该挂在会话对象上；如果是进程级共享，就应该注册为服务（在 dsh-mini 里是通过 `ctx.provide`）。**不要这么做的情形**：当你不确定生命周期时，最不该做的是先用模块级变量，因为那会绕开所有权体系（见 R-11），事后清理它的成本远高于现在多问一句。

**R-11｜症状：注册了某个东西，但卸载插件之后它还在。**
可能原因是**裸的状态写入**。确认动作是搜索所有对长生命周期容器的直接修改——在 dsh-mini 里，这意味着搜索绕过 `ctx.effect` 的写法，例如直接 `someArray.push`、直接给对象赋值、或者在模块顶层执行注册。处置动作是把这些注册改成通过 `ctx.effect(disposer)` 完成，或者在插件的 `onDispose` 里显式清理。**不要这么做的情形**：对于确实是进程级、且永不清理的单例（例如一个只读的常量表），不需要走所有权流程；但要明确写下"这是有意的全局"这句话，否则下一个人无法区分它与 R-11 里说的疏漏。

**R-12｜症状：你想给某段逻辑加一个开关，而不是直接改它。**
这条值得单独列出来，因为**"加开关"是一个重要的危险信号**。可能原因有三种，而它们的性质完全不同：第一，你需要兼容两种部署环境（合理，开关是必要的）；第二，你在做灰度发布（合理，开关是临时的）；第三，你不想改原逻辑因为它太复杂或者别人在依赖它（**这不合理，它是 3.2 里说的"不敢改"的前兆**）。确认动作是问自己"这个开关打算什么时候删"。处置动作按答案分支：如果是灰度开关，写下它的删除条件与期限；如果是环境差异，把它放到配置里而不是代码里；如果是第三种原因，停下来——此时真正该做的是先理解那段逻辑（回到 R-05），而不是在它外面加一层。**不要这么做的情形**：当改动确实影响线上行为且没有回滚手段时，开关是必要的安全网；这不是"逃避修改"，而是 3.5 会讲的"用可逆换风险"。

#### 组四 · 验证（R-13 至 R-14）

**R-13｜症状：改完了，但不确定该验证什么。**
可能原因是你在动手前没有列出**约束清单**（1.1 的四类约束）。确认动作是把你改动的模块的接口约束与不变量约束列出来，逐条问"我的改动会不会影响它"。处置动作是把这份清单变成一份最小的验证计划：每条约束对应一个验证动作，优先验证那些"破坏了也不会报错"的约束（因为报错的会自己暴露）。**不要这么做的情形**：对于纯粹新增功能且不影响既有路径的改动，验证范围可以缩到"新功能本身能否工作"，不必重新验证既有约束。

**R-14｜症状：测试跑得很慢，或者覆盖不到你改的地方。**
可能原因是**缺少接缝**。一个没有接缝的系统无法被独立测试，因为没有任何位置能注入替身（假的 provider、假的时间、假的文件系统）。确认动作是找出你改动路径上"最难替换的部分"——通常是直接 `new` 出来的具体实现、直接调用的全局函数、以及直接读写的文件系统。处置动作是判断能否在这些位置引入接缝（把具体实现改成接口参数、把时间与随机数变成可注入的、把文件操作收敛到一个模块后面），但**不要为了测试而重构**：只有当这块逻辑未来还会反复变化时，引入接缝才是合算的。**不要这么做的情形**：当你只是想知道"改动有没有打破既有行为"时，先用现成的端到端检查（dsh-mini 里是 `node src/apps/verify.ts`），它比新写单元测试更快；只有在需要反复验证同一处细节时，才值得去建接缝。

#### 手册的使用方式与它自身的规则

这份手册的正确用法是**遇到具体的卡点时才查**，而不是从头读一遍。原因在于它的每一条都是"症状驱动"的，而症状只有在你实际操作时才会出现；事先读一遍的结果是记住了一堆用不上的条款，反而增加了记忆负担。

另外，手册本身也应该被扩充。扩充的时机是：当你遇到一个手册里没有的症状，并且花时间解决了它之后，就补上一条。补充的格式照抄上面六项（症状、原因、确认、处置、反例、不适用的情形），其中**"不适用的情形"这一项最容易被省略，也最重要**——因为一条没有边界说明的规则，会在不该用它的时候被误用。

## L2 决策表

```
   1.5 量化（拿到数字）
         │  数字有了，怎么用它做决定？
         ▼
   【L2 十条决策】读多少才停 / 度量能不能当考核 / 死代码删不删
         │          （这一层不产生新方法，只产生判断）
         ▼
   L3 推演（把决策用在一次真实改动上）
```

这一篇的决策表与前三篇的性质不同。3.1 的决策是关于流程怎么走，3.2 的决策是关于成本怎么管，而这一篇的决策是关于**"读代码这件事该怎么投入"**——因为你不可能读懂所有代码，所以核心决策都是"在哪里投入、投入多少、什么时候停"。

| # | 决策 | 选择 | 替代方案 | 代价落在谁身上 |
|---|---|---|---|---|
| 1 | 读的目标 | 提取四类约束 | 逐行理解实现 | **读的人**：要先判断"这个文件里哪些是约束"，需要更多推理；换来读完之后能用 |
| 2 | 读的起点 | 由目的决定（接口 / 状态 / 波及面） | 统一从第一行开始 | **读的人**：要先明确目的；换来不浪费注意力 |
| 3 | 何时停止阅读 | 能回答当前目的所需的问题时 | 读到"感觉懂了" | **读的人**：要接受"没读全"的不安 |
| 4 | 抽象是否必要的判断标准 | 构造反事实（去掉会怎样） | 凭经验与美观判断 | **判断者**：要能构造出具体的反事实 |
| 5 | 架构规则的落地方式 | 写成可执行的检查命令 | 写在文档里 | **文档维护者**：要花时间把规则命令化；换来规则真的被执行 |
| 6 | 度量的使用方式 | 作为讨论的输入 | 作为评价标准 | **团队**：要接受"数值差不等于该改" |
| 7 | 遇到"不敢改"的区域 | 先补理解，再加开关 | 在外面包一层 | **当时的人**：要多花时间；换来不产生新的复杂度 |
| 8 | 死代码的处理 | 记录但在相关改动时处理 | 立刻删除 | **后续改动者**：要带着一份待清理清单 |
| 9 | 隐式依赖的处理 | 补文档或断言，使其显式化 | 依赖口头约定 | **改动的发起者**：要多写几行；换来下一次不踩 |
| 10 | 手册的维护 | 遇到新症状就补一条 | 写成大而全的指南 | **使用者**：要持续记录 |

这张表里有三条需要展开，因为它们各自避免了常见的一类错误。

**第一条要说清的是"何时停止阅读"（第 3 条决策）。** 这条看似是效率问题，实际上是**信心问题**。读代码时有一种持续的引力，让你觉得"再看一点会更安全"，而它的代价是无上限的时间投入，收益却迅速递减——因为你的目的是回答一个具体问题，而超过这个问题的信息不会改变你的决定。一个可操作的停止判据是：**当你能用一句话说出"我要改的是什么，它会影响谁，我怎么验证"时，就可以停**。如果这三句话里有任何一句答不出，就继续读；如果三句都能答出，那么继续读的边际收益已经很低。

**第二条要说清的是"架构规则写成命令"（第 5 条决策）。** 这一条的价值在本篇 1.3.1 已经演示过：`rg -n "from '\.\./framework" src/kernel/` 这条命令把"kernel 不得依赖 framework"这条抽象原则变成了一次可执行的检查。为什么要这样做？因为**写在文档里的规则会随时间失效，而写在命令里的规则会随时间报警**。这个区别在项目规模变大时尤其明显——文档没有人读，而 CI 里的命令每次提交都会跑。dsh-mini 已经在这个方向上有实践：`apps/verify.ts` 的二十三条检查中有相当一部分就是"架构规则的可执行版本"，例如"压缩后不变量仍成立"这条。

**第三条要说清的是"死代码不要立刻删"（第 8 条决策）。** 这条与直觉相反——大多数人认为没用的代码应该立刻清理。反对立刻删除的理由有两条。第一，判断"它确实没被使用"的成本往往被低估，尤其是当项目里有动态引用（配置里的插件路径、事件名的字符串匹配）时，静态搜索的结论不可靠。第二，删除本身是一次改动，而这次改动有它自己的风险（你删掉的可能是一个正在被某个边缘路径使用的东西，而那个路径没有测试覆盖）。所以更经济的做法是记录它并在下次改动相关模块时顺带处理——那时你已经为了别的原因建立起了对这个模块的理解，删除的判断成本几乎为零。

## L3 实现（案例逐段解析）

```
   L1（方法）──► L2（决策）
                    │  两部分合起来，用一次
                    ▼
   【L3 完整推演】"GUI 加切换模式"值不值得做
                    │
      1.2 三读法 → 读结构        1.5 五度量 → 算数字
                    └────────┬────────┘
                             ▼
              反过来改产品方案 ← 这是本篇真正的落点
```

这一节是一次完整的读码演示。我选的案例是一个真实会发生在你手上的问题：**如果要在 dsh-mini 的 Web GUI 里加一个"切换模式"的下拉框，我需要改哪些地方、会波及谁？** 这个问题的好处是它足够具体，同时又需要用到本篇的全部方法。

### 3.1 第一步：确定改动点究竟是什么

按 1.2.3 的第一步，先精确定义改动。这个需求看似简单，其实包含至少四个可能的改动点，而它们的波及面完全不同：

| 可能的改动点 | 含义 | 波及面类型 |
|---|---|---|
| A. 界面上加一个下拉框 | 只改 `web-ui.html` | 前端局部 |
| B. 后端增加一个"当前模式"的接口 | 改 `apps/web.ts` 的路由与状态 | 中 |
| C. 支持"运行中切换模式" | 需要重建装配（重新 `loadModes` + 重新装配） | 大 |
| D. 模式列表要能被界面读取 | 现有的 `/api/modes` 是否够用 | 小 |

这个分解本身就有价值，因为它把一个模糊需求拆成了四个可分别评估的改动。而在实际工作中，**最常见的失败是有人直接按 A 来估计（"加个下拉框，半天"），而实际需求是 C（"切换模式"，可能两天）**。所以第一步的产出不是答案，而是这个分解表。

### 3.2 第二步：用读法一确定相关模块的职责

按 1.2.1 的四步读法，我们逐个看四个相关模块。

`apps/web.ts` 的导出是 `runWebApp`，它同时承担三件事：HTTP 路由、SSE 连接管理、以及装配的持有。文件头注释说明它的定位是"只做协议翻译，不做业务判断"。这给出了两条边界约束：它不该包含任务逻辑，也不该直接操作会话内部。

`apps/web-ui.html` 是一个单文件界面，包含 HTML、CSS 与 JavaScript。它的状态全部在浏览器侧，与服务端通过 `/api/state`、`/api/modes`、`/api/tools`、`/api/custom-mode` 以及 `/api/task` 交互。这里的关键发现是：**`/api/modes` 已经存在**，因此改动点 D 不需要新接口。

`apps/shared-mode.ts` 的导出是 `applyModeToRows` 之类的装载钩子工厂。它的职责是把一个模式的声明转换成装载器可以理解的行变换。

`framework/modes.ts` 的导出包括 `loadModes`、`parseModeDecl`、`applyMode`、`summarizeMode` 以及 `BUILTIN_MODES`。它是模式能力的实现处。

走完这一轮，我们已经知道改动点 C 的关键问题在最后两个模块：**能否在进程内重新应用一个模式**。这引出了下一步。

### 3.3 第三步：用读法二找出模式与装配的状态关系

按 1.2.2 的方法，读 `apps/web.ts` 的状态。它的状态包括：当前的容器（`Context`）、当前的装配结果、SSE 客户端列表、以及当前运行中的任务。而模式的影响体现在装配结果上——装配发生在进程启动时，通过 `loadProfile` 读取 `bundles/` 与 `modes/` 并生成最终的行列表。

这里出现了一个关键的不变量：**装配是启动时确定的，运行时不改变**。它没有写在任何类型里，但可以从三处证据推出：一是 `loadProfile` 是异步函数且在 `runWebApp` 开头被调用一次；二是后续的任务执行直接使用装配结果，没有重新读取；三是 `Context` 的生命周期与进程一致。

这条不变量的存在，直接决定了改动点 C 的成本构成：**支持运行中切换，等于要打破这条不变量**，也就是要实现"卸载旧容器 + 装载新容器"的完整流程，而这个过程要保证正在运行的任务、已建立的 SSE 连接、以及累积的会话状态都被正确处理。

### 3.4 第四步：用读法三计算波及面

现在我们知道了改动点 C 的性质，接下来数波及面。按 1.2.3，先列直接依赖者，再找间接依赖者。

**直接依赖者**（改了装配结果会影响谁）：任务执行路径（`plugins/agent-loop.ts` 通过 `runTask` 使用装配出来的 Agent）、工具注册表（装配结果里的 `builtin` 列表）、SSE 的事件流（因为新的容器会产生新的事件源）、以及界面（模式名要显示）。

**间接依赖者**（通过约定连接）：`bundles/*.json` 里引用的插件路径（重新装载时要按同一份 bundle 重来）、`modes/*.json` 之间的 `basedOn` 关系（如果有继承，重新应用时要处理顺序）、以及 `workspace/.sessions/` 下的会话文件——因为会话是与容器关联的，重新装配时旧会话的状态归属需要决定。

数到这里，改动点 C 的波及面已经清晰了：它不是"前端加个下拉框"，而是**一次运行时重构**，涉及装配生命周期、事件源切换、以及会话归属三个问题。按 3.2 的利息语言来表达就是：这个改动的成本主要是"打破一条不变量所需的额外工作"，而它的收益只是"用户不用重启进程就能换模式"。

### 3.5 第五步：用度量把结论数值化

按 1.5 节的公式，我们给这个改动算三个数，让结论可以比较。

**第一个数是波及面。** 按 1.5.3 的定义，改动点 C 的传递闭包包含：`web.ts`、`agent-loop.ts`、`tools.ts`、`session.ts`、以及前端。粗略估计是 5 到 8 个模块。作为对照，改动点 A（只加下拉框）的波及面是 1 个模块。**两个方案的波及面差了五到八倍**，而它们在需求描述里只差几个字。

**第二个数是不稳定性的变化。** 如果为了实现 C 而让 `apps/web.ts` 承担重新装配的职责，它的扇出会增加（要依赖 `framework/loader.ts`、`framework/modes.ts`、`framework/context.ts` 的更多接口）。按 1.5.1 的公式，`web.ts` 的 I 会从"接近 1"继续上升。这本身不是问题（web 本来就该是不稳定模块），但要注意它的方向：**如果这些新依赖里包含了对 `kernel/` 内部的直接使用，就违反了分层**。

**第三个数是依赖深度。** 实现 C 的路径上，最深的一条大约是：`web.ts` → `framework/loader.ts` → `framework/modes.ts` → `apps/shared-mode.ts` → 插件装配。五层。这意味着任何要做这件事的人，需要建立五层理解——这正是 1.5.2 里说的"跨层深度"较高的信号。

### 3.6 结论：一个完整的读码产物

把上面的推演整理成结论，它包含三个层次，正好对应本篇教的三样东西。

**约束层面**（1.1）：`apps/web.ts` 的边界是"只做协议翻译"，因此重新装配的逻辑不该写在它里面；装配在启动时确定是一条**未被类型系统表达的不变量**，改动它需要显式承认自己正在打破一条不变量。

**结构层面**（1.2、1.3）：`/api/modes` 已存在，界面能拿到模式列表；模式的应用路径是 `modes/*.json` → `loadModes` → `applyMode` → `transformRows` → 行列表 → 装配。这条路径是单向的、启动时完成的。

**度量层面**（1.5）：三个方案（A 只加界面、B 加后端接口但不支持运行时切换、C 完整支持运行时切换）的波及面分别约为 1、3、5–8，依赖深度分别为 1、2、5。

由此得出一个可以进入讨论的结论：**方案 A 与 B 的性价比很高（半天到一天），而方案 C 的成本大约是前者的五倍以上，并且它会打破一条现有的不变量。** 如果需求的本意是"用户不想为了换模式重启进程"，那么还有一个成本更低的做法值得提出来——把模式选择放到启动参数或界面的"新建会话"入口上，这样每次新任务用新模式，而不需要动正在运行的装配。**这个替代方案不是技术细节，它是产品方案**，而它之所以能被提出来，正是因为读懂了结构之后知道了哪条不变量最贵。

## L4 运行与验证

```
   L1 方法 ──► L2 决策 ──► L3 推演
                              │  你怎么知道自己真的会了？
                              ▼
            【L4 验三层】定位 → 推演 → 反驳
                              │    （最后一层最难：能指出别人的判断不成立）
                              ▼
                      L5 速查 ──► L6 ★ 分级判据
```

这一篇的验证方式与前两篇不同。3.1 与 3.2 是方法论，验证方式是"你能产出一份可复核的判断"；而这一篇是技术能力，它的验证可以是**客观的**——因为你的结论要么与代码事实相符，要么不符。

### 4.1 三层验证

**第一层：能定位。** 给你一个功能描述（例如"任务在超过最大步数后停止，并给出提示"），要求你在十分钟内指出它由哪几个文件共同实现，并说出大致的调用链。判据是文件清单正确，且调用链与事件链被区分开了。

**第二层：能推演。** 给你一个改动需求（不是本篇的案例），要求你产出 1.2.3 里说的那份波及清单，按"会报错 / 会静默失效 / 条件触发"三类分组。判据是清单里有至少一项"会静默失效"——因为如果所有项都是"会报错"，说明你只做了文本搜索，没做间接依赖的搜索。

**第三层：能反驳。** 这是最能证明你掌握了本篇的一层：给你一份别人写的波及清单，要求你找出其中一条不成立的判断，并说明理由。理由是必须在代码里可验证的。这一层之所以重要，是因为**读代码最常见的失败不是漏读，而是错误地把某个东西当成依赖**（例如把"提到了这个名字"当成"依赖了它的行为"）。

### 4.2 一次完整的验证流程

把验证固定成可重复的流程，这样它可以用于任何一个模块。

第一步是凭记忆写一份模块卡片（L5 给了模板），内容包括职责、依赖、被依赖、关键约束四项。第二步是用文档与代码核对卡片，把不符的地方标出来——这里有一个重要的判断：**当文档与代码不一致时，以代码为事实，但要把文档的不一致本身记下来**，因为那往往意味着某次改动没有同步文档（正是 3.2 里说的隐性同步成本）。第三步是对每个"关键约束"找出一条验证方法（断言、测试、或一条命令）。第四步是做一次波及推演并交叉验证：随机挑清单里的三项，实际去代码里确认。

### 4.3 判据

本文对你"学会了本篇"的判据有五条。第一，你能在不看本篇的情况下说出三种读法各自的起点与适用目的。第二，你能对一个陌生模块给出四项约束（接口、不变量、边界、所有权），并且每一项都指得出代码依据。第三，你能手算不稳定性 I 与依赖深度 D 这两个量，并说明它们的适用边界。第四，你能在手册的十四条规则里找到至少三条"你在实践中真的遇到过"的规则。第五，也是最能体现掌握程度的：**你能为本篇的某一条规则写出一个它不适用的情形**——因为"知道一条规则什么时候失效"比"知道它"要难得多。

### 5.1 模块卡片模板

这是本篇的核心产物模板，用于记录你读完一个模块之后的结论。它的四行分别对应 1.1 里的四类约束。

```markdown
## 模块卡片：<文件路径>
日期：<YYYY-MM-DD>   版本：<git commit 短号>

**职责**：<一句话，用"它保证……"的句式，而不是"它做了……">
**不做**：<边界约束——它明确不管什么>

**依赖（扇出）**：<列出的模块数 + 模块名>
**被依赖（扇入）**：<列出的模块数 + 模块名>
**不稳定性 I**：<Ce/(Ca+Ce)，保留两位小数>

**接口约束**：<对外承诺的行为，包含"重复注册会怎样"这类实现层承诺>

**所有权约束**：<它持有的状态由谁清理，通过什么机制>

**关键风险**：<若要改动这个模块，最需要注意的一件事>
```

### 5.2 命令速查（可用于 dsh-mini 与 DSH）

| 目的 | 命令 | 说明 |
|---|---|---|
| 验证分层规则 | `rg -n "from '\.\./framework" src/kernel/` | 期望无输出 |
| 找事件的所有监听者 | `rg -n "'agent/turn-(start|end)'" src/` | 搜事件名字符串 |
| 找服务的注册与取用 | `rg -n "provide\('|require\('" src/` | 搜服务名 |
| 找配置里的插件引用 | `rg -n "plugins/" bundles profiles modes` | 配置层的引用 |
| 找内容约定（提示词↔工具） | `rg -n "run_program\|write_skill" modes prompts skills` | 跨层约定 |
| 数一个模块的依赖 | `rg -n "^import" src/kernel/session.ts` | 扇出的原始数据 |
| 找谁 import 了它 | `rg -n "from '.*session" src/` | 扇入的原始数据 |
| 找断言（不变量的显式表达） | `rg -n "assert[A-Z]" src/` | 定位不变量 |

### 5.3 三条容易踩的规则

**第一条：区分"提到"与"依赖"。** 搜索一个名字会得到很多结果，其中相当一部分只是提到它（例如日志里打了个名字、类型里作为可选字段出现），而真正依赖它的行为的地方才是波及面的一部分。判断方法很直接：**问"如果这个行为的语义变了，这处代码会出错吗"**。

**第二条：文档描述意图，代码描述事实。** 两者不一致时以代码为准，但要把不一致本身当作一条信息——它通常表示某次改动没有同步。

**第三条：度量是为了引发讨论，不是为了替你做决定。** 不稳定性 I 高不代表该改，LCOM 高不代表该拆。它们的作用是让"我觉得这里有问题"变成"这里的 I 是 0.83，我们讨论一下它的位置是否合适"。

| 科研 | 能否构造一个指标，使它与"新人上手一个模块所需的时间"强相关？ |

### 五种提问模板

第一种是**反例逼问**：如果一条架构规则在某个模块上不成立，那说明什么？是规则错了，还是这个模块特殊？

第二种是**边界追问**：一个模块多复杂才算"太难改"？给出一个可判断的阈值，而不只是说"看情况"。

第三种是**代价追问**：引入一个接缝（为了可测试）的代价是什么？它会落在谁身上？

第四种是**替代对比**：为什么不直接用工具生成依赖图，而要人工读？

第五种是**验证追问**：怎么证明"读懂了这个模块"？有没有一个能客观判定的测试？

### 本篇引出的十二个问题

**读懂层。** 第一，"接缝"为什么强调"不修改代码"这个条件？第二，不变量与前置条件有什么本质区别？第三，为什么深模块是好的，而浅模块是坏的？

**重建层。** 第四，1.2 的三种读法里，哪一种最容易被误用，为什么？第五，为什么"读状态"比"读流程"更容易得到一个模块的本质？第六，不稳定性 I 的公式为什么用比值而不是差值？

**设计层。** 第七，为什么架构规则要写成命令而不是文档？第八，什么条件下"加开关"是合理的，什么条件下它是逃避？第九，依赖深度与波及面这两个量，哪一个更能预测"改动的实际难度"？

**评审层。** 第十，看到一份模块卡片，你会先检查哪一项？第十一，怎么判断一个人的波及清单是认真推演的还是搜索结果的堆砌？第十二，如果有人在评审时说"这个改动影响面很大"，你要求他提供什么证据？

### 问题升级练习

**模糊问题**：「我怎么快速搞懂一个陌生的代码库？」

**升级后的精确问题**：

> "搞懂一个代码库"至少包含四个不同的目标：
> 定位功能（知道某功能在哪）、理解约束（知道什么不能改）、
> 评估改动（知道某处改动会波及谁）、以及修改实现（能在其中安全地写代码）。
> 这四个目标对应的读法完全不同，而它们所需的投入量级差异很大。
> 如果我要为一个具体任务（比如"给这个系统加一个新工具"）建立刚好够用的理解，
> 我应该建立到哪一层，停止的信号是什么，以及如何验证我的理解已经够用？

**提升点说明**：原问题无法回答，因为它把四种不同的目标混成了一个"搞懂"。升级后的版本做了三件事。第一，把目标拆开，并指出它们的读法不同——这就把"读多久"的问题变成了"为哪个目标读"的问题。第二，引入了"刚好够用"这个约束，它要求给出停止判据（对应本篇 1.2.1 的第四步）。第三，要求给出验证方式，因为"我觉得懂了"不是判据，而"我能答出这四个问题"是。

## L11 系统影响回溯

```
   L0.5 三个连锁影响（开篇立下的预判）
              │  现在回来对账
              ▼
   【L11 回溯】预判成立吗？哪一条需要修正？
              │  （本篇已修正一条：复杂度"不能等"≠"都该处理"）
              ▼
        通向 3.4 接口与契约
```

回看第 0.5 节的三个连锁影响，本篇给出了它们各自的具体形态，其中一条需要修正。

**第一条连锁影响**说的是"读不出结构会让技术判断被外包"。本篇在 1.2.3 与 L3 的案例里给出了这个能力的具体形态：能独立算出"这个需求要动几处"（L3 的第五步算出了 1、3、5–8 三个数字），并带着这个数字与人讨论。1.4 的四类约束则解释了为什么这个能力可以被习得——因为它不是"经验"，而是四个可以逐项检查的问题。

**第二条连锁影响**说的是"不理解不变量会让重构变成引入隐蔽 bug 的主因"。本篇在 1.1 与 R-13 里给出了防御方式：把不变量显式列出，并优先验证那些"破坏了也不会报错"的约束。L3 的第三步还演示了怎么从三处证据反推一条未写下的不变量（装配在启动时确定），这个过程正是"识别不变量"的实际操作。

**第三条连锁影响**说的是"结构上的热点会决定产品节奏"。本篇在 1.5.3 里给出了它的量化形式：波及面是依赖关系的传递闭包，而它随依赖呈**乘法**增长，所以层次的存在就是为了切断这种乘法。这条修正了我在 0.5.3 节的一个表述——那里说"一个需求卡在某个热点"，而更准确的机制是"热点经过少数几层传递后就能覆盖大部分系统"，因此问题不在于哪个需求卡住了，而在于**热点的波及面在结构上就决定了多数改动的风险下限**。

**一处需要修正的预判**：0.5.1 节说本篇是"3.2 那套评估方法的输入"。读完之后我会说得更准确：本篇不是 3.2 的输入，而是**与它构成一个循环**——3.2 的度量（影响面、依赖深度）要靠本篇的方法获得，而本篇的读法（读哪种、读到什么时候停）要靠 3.2 的成本判断来决定。也就是说，"读多久"这个问题的答案是"读到你能做出成本判断为止"，而那个判断本身又依赖于你已经读到的内容。这个循环不是缺陷，它正是"理解"与"判断"在实际工作中的真实关系。

**通向下一篇的桥。** 本篇反复用到两个词：**接口**与**不变量**。我们说接口是"对外承诺的行为"，说不变量是"始终为真的关系"，还说改动的连锁反应来自别人对这些承诺的依赖。但这些承诺究竟应该包含什么、写到什么程度、以及什么样的接口会让改动代价最小——这些问题本篇只是触及，没有展开。下一篇 `3.4 接口与契约` 会专门处理它们，并且会给出一个判断标准：**什么样的接口变化是可接受的，什么样的一定会引发连锁反应。**

## 记忆锚点与复述练习

这一节是给"读完就忘"准备的。它的原理不是重复，而是三件有实证支持的事：**先有骨架**（大脑需要一个挂东西的架子）、**情境绑定**（记"什么时候用它"比记"它是什么"更牢固）、以及**主动回忆**（试图想起来一次，胜过重读五次）。

### 一、骨架：四块

```
   从哪读 ──► 拿什么 ──► 算多少 ──► 卡住查
     ↓          ↓          ↓          ↓
   三读法     四约束     五度量     十四规则
   1.2        1.1        1.5        1.6
```

如果只能记住一行，就记这一行。它不是提纲，而是**使用顺序**：先确定从哪读，读完拿到四类约束，需要比较就上度量，走不通就查规则。

### 二、情境绑定：把知识和"什么时候用"绑在一起

抽象记忆容易掉，情境记忆不容易掉。所以下面这张表两列的关系是"当你遇到 X，就想起 Y"，而不是"Y 的定义是 Z"。

| 当你…… | 立刻想起 |
|---|---|
| 打开一个从没见过的文件 | 读法一：导出 → 头部注释 → 签名 → **跳过实现** |
| 要改某个模块的内部逻辑 | 读法二：先列状态 → 问谁改它 → 找状态之间的不变量 |
| 有人问你"这个改动要多久" | 读法三：直接依赖者 + 间接依赖者（四种连接机制） |
| 读完了却说不出重点 | R-05：你在读细节，不是在读约束 |
| 觉得某处"不能改"但说不出为什么 | 它维护哪条不变量？证据在哪？找不到证据就不是不变量 |
| 想加一个开关而不是改代码 | R-12：先问"这个开关打算什么时候删" |
| 改一处、报错三处 | R-09：隐式契约。先分类"会报错 / 会静默失效 / 条件触发" |
| 想判断改动风险有多大 | 算波及面，并记住它是**乘法**增长 |
| 有一段看不懂的绕行逻辑 | R-07：先查三种证据——历史兼容 / 平台差异 / 并发时序 |
| 注册了东西但卸载后还在 | R-11：裸状态写入，改走 `ctx.effect()` |

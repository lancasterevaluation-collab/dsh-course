## 本篇新词

这一篇的术语大多来自契约式设计与 API 演进，它们有一个共同点：**都在描述"代码之外的东西"**——类型系统检查不到、编译器不会报错、但一旦被违反就会在运行时或几个月后爆发。

**契约（contract）** 在这篇里指一个模块对外的**全部可依赖行为**，而不只是它的函数签名。它包含三类承诺。**行为承诺**说的是"调用它会发生什么"；**时序承诺**说的是"什么时候可以调用、可以调用几次、并发调安不安全"；**错误承诺**说的是"失败时它怎么表现"——抛异常、返回错误值、还是静默降级。一个接口如果只写清了行为承诺，那么它在使用时仍然会出问题，因为后两类承诺恰好是使用者在写调用代码时最需要知道的。

**前置条件与后置条件**来自 Bertrand Meyer 的契约式设计。前置条件是**调用方的义务**（"你必须传一个非空数组"），后置条件是**实现方的义务**（"我保证返回的每一项都已被校验"）。这个划分的价值在于它明确了**责任归属**：违反前置条件是调用方的 bug，违反后置条件是实现方的 bug，而这在调试时是一个极有价值的区分——它让你知道该去哪一边找问题。

**类不变量**是 Meyer 契约里的第三项，指**在对象的整个生命周期中始终为真的性质**。它比前置/后置条件更难表达，因为它不属于任何一次调用，而属于对象本身。dsh-mini 的 `Session` 有一条这样的不变量：`#events.length` 必须等于下一个事件的 `seq`。这条关系既不是 `append` 的前置条件，也不是它的后置条件——它是这个对象**在任何时刻**都必须满足的性质。

**Liskov 可替换性（LSP）**说的是：如果一个程序依赖于类型 T 的契约，那么把 T 换成它的子类型 S 时程序不应出错。这条原则在接口设计上有一个直接推论：**子类型可以弱化前置条件、可以强化后置条件，但不能反过来**。原因是契约面向的是调用方——调用方只知道 T 的契约，所以 S 必须至少提供同样的保证。

**破坏性变更（breaking change）** 指任何**使依赖原有契约的代码可能失败**的改动。它的关键在"可能"两个字上：一个改动是否破坏性，取决于**有没有人依赖被改掉的那部分可观察行为**，而不取决于改动本身的大小。这就是 Hyrum 定律要说的东西——**当用户足够多时，一个 API 的所有可观察行为都会被某些人依赖**，包括那些你以为不属于契约的细节（错误信息的措辞、返回值的顺序、甚至一次调用的耗时）。

**稳定依赖原则**在 1.3 里出现过一次（不稳定性 `I`），这里要用它的另一半：**一个模块被依赖得越多，它的接口就应该越稳定**。也就是说，`I` 低的模块（被很多人依赖）不应该频繁改变自己的契约，而 `I` 高的模块（几乎没人依赖）可以随意改。这条原则给出了一个实用的判断：**当你想改一个高扇入模块的接口时，先算一下有多少人会因此动手。**

**契约测试（contract test）** 与普通单元测试的区别在于它**验证的是承诺而不是实现**。单元测试可能断言"这个函数返回 `{a: 1, b: 2}`"，而契约测试断言"这个函数返回的对象必须包含 `a` 字段且它是数字"——后者在实现返回 `{a: 1, b: 2}` 和 `{a: 1, b: 2, c: 3}` 时都通过，因为多一个字段不破坏承诺。**这个区别决定了一组测试是"保护契约"还是"锁死实现"**，而后者会让重构变得极其痛苦。

这四块的关系是递进的，而它们各自的用途不同。**①是基础**（不理解三类承诺，后面三项都无从谈起）；**②是诊断工具**（当你要写一个接口时，用它检查自己漏说了什么）；**③是决策工具**（当你要改一个接口时，用它判断风险）；**④是长期工具**（当一个接口要活很多年时，用它来演进）。

**为什么这一篇排在 1.3 之后**：1.3 教你"读出一个模块的约束"，而这一篇教你"约束是怎么被承诺出去的"。两者是一件事的两面——**1.3 是从读者角度看约束，这一篇是从作者角度看约束**。而它们合起来回答了 1.2 留下的那个问题：**为什么某些改动会波及很多地方**——答案是"因为有人的代码依赖了这个接口的承诺"。

### 0.1 你会得到一种"预判连锁反应"的能力

先描述一个场景。你要给 `Tool` 接口加一个字段，比如 `costEstimate`（预估调用成本）。这个改动看起来很小——加一个可选字段，老代码不用改也能编译。于是你动手了，然后发现：

- 工具池的目录生成逻辑要处理这个新字段（否则它不会出现在给模型的工具描述里）
- 守卫要根据它做判断（否则它没有意义）
- 每个已注册的工具都要考虑要不要填它（否则新旧工具的行为不一致）
- 而最麻烦的一处是：**如果有工具填了它而守卫不认，那个字段就会成为一个"看起来存在但不起作用"的字段**——这比不写它更糟，因为它会让后来的人以为系统有这个能力。

这就是本篇要给你的预判能力：**在看到"加一个可选字段"这个动作时，你能说出它会连锁到哪里**。而这个能力的核心不是经验，而是一个具体的问题：**这个字段要成为承诺的一部分吗？** 如果是，那么所有实现者都必须遵守它，所有消费者都可以依赖它；如果不是，那么它只是一个实现细节，**不应该出现在接口上**。

### 0.2 你会得到三样东西

第一样是**三类承诺的检查表**（1.1）。写接口时对着它逐条问："我承诺了行为，但我说清时序了吗？错误呢？"这三类里的后两类是最常被漏掉的，也正是使用者最容易踩坑的地方。

第二样是**一张破坏性改动的分类表**（1.4）。它把"改了什么"（加字段、改默认值、收紧参数）映射到"谁会受影响"（构造方、调用方、监听方），并给出每一类的应对方式。这张表的用处是在做改动之前花两分钟定位自己在哪一格。

第三样是**契约审计的方法**（L3）。它用一个真实的例子演示怎么审一份接口——不是看它写得对不对，而是问"使用者能从它这里合理地推断出什么"，然后把那些推断与实现对照。**审计的目的是找出"签名承诺了、文档没写、而实现没做到"的那些地方**，它们是最危险的一类。

### 0.3 一个立刻能做的练习

在开始读正文之前，花十分钟做这个练习，它会让你对"契约的表达有多不完整"有直接体感。

打开 `D:\dsh-mini\src\kernel\tools.ts`，找到 `Tool` 接口的定义。只读它的字段声明，**不看注释**，然后回答四个问题：

1. `execute` 可以被并发调用吗？
2. 如果 `execute` 抛异常，框架会怎么处理？
3. `sideEffect` 字段的值由谁检查、什么时候检查？
4. 同一个工具被注册两次，会发生什么？

这四个问题里，**能在字段声明里找到答案的通常不超过一个**。它们分别属于时序承诺、错误承诺、行为承诺的实现方与注册语义——而它们全都是使用者必须知道的事情。**这就是"签名只表达了一半"的体感来源**，也是这一篇要讲的第一件事。

> **面试视角**
> **高频问法**："你怎么设计一个给别人用的接口？"——这四问就是设计前的自查清单。
> **追问方向**："加了一个可选参数为什么还会出问题？"答：因为接口的每个成员都在宣布一个能力，而能力的宣布会引出"谁填、谁用、没人填怎么办"三个问题（见 0.1 的连锁）。

### 0.5.3 三个连锁影响

**第一个连锁影响：契约写不清，会让每一处调用方各自发明一套假设。**

这条链条的开始是一个非常小的疏漏：接口没有写明"这个方法会不会抛异常"。接着发生的事情有固定的模式。第一个调用方按"它会抛"来写，于是加了 `try/catch`；第二个调用方按"它不会抛"来写，于是没加；第三个调用方在调试时发现确实会抛，于是**在调用点加了一个防御性判断**。半年后，这个接口因为某个内部改动开始在一些边界情况下抛异常——第一个调用方没事（它有 catch）、第三个也没事（它有防御），而第二个崩了。

**这条链条最值得注意的地方是：问题不是"有人写错了"，而是"接口没有给出答案，所以每个人都自己给了一个"**。而三个人给出三个不同的答案是必然的——因为默认值取决于各自的经历。修复它的方法不是加强约定，而是**把答案写进契约**：要么"我不抛，一切失败通过返回值表达"，要么"我会抛，抛出的类型是这些"，两者都可以，但必须选一个并写下来。

**第二个连锁影响：把实现细节写进契约，会让系统失去演进能力。**

反向的问题同样致命。假设 `Tool` 接口的文档里写着"`execute` 返回的字符串总是以换行结尾"。这句话如果是承诺，那么所有返回工具结果的实现都必须遵守它，而所有解析结果的调用方都可以依赖它。**于是这个"换行"从一个实现细节变成了永久约束**——即使哪天发现不加换行更好看，你也不能改，因为有人依赖了它。

更糟的是，这类约束往往**不是有意写下的**，而是被"观察"出来的。Hyrum 定律说的正是这件事：当用户足够多时，你的所有可观察行为都会被依赖，包括你从未承诺过的那些。所以契约设计的一个实际任务是**有意识地划一条线**：哪些行为我愿意长期保证（写进契约），哪些行为我保留随时改的权利（明确声明"这是实现细节，不要依赖"）。

**第三个连锁影响：契约的稳定性决定了改动波及面的形状。**

这条连锁影响把本篇与 1.2、1.3 接了起来。1.3 讲了"波及面 = 依赖它的模块的传递闭包"，而这一篇要补上关键的限定：**波及面里的那些模块，并不是都依赖了你的全部行为，它们各自依赖了其中一部分**。

具体到 dsh-mini 的 `Session` 上：16 个文件引用它（值为 7、类型为 9），但**它们依赖的东西不一样**。`kernel/agent.ts` 依赖 `append` 与 `deriveMessages` 的行为；`apps/web.ts` 只依赖事件类型（类型层面）；`evolution/diagnose.ts` 依赖 `SessionStats` 的字段。所以当你改动 `computeStats` 的返回字段时，真正会受影响的是那几个读统计的地方，而不是全部 16 个。

**这意味着"波及面"的准确计算需要两张表**：一张是"谁依赖我"（1.3 教的），另一张是"我承诺了什么、谁依赖了哪一条"（这一篇教的）。只有第一张表时，你会过度保守——因为你会以为改动会影响所有人；只有第二张表时，你会过度冒险——因为你会低估间接依赖。**两张表合起来，才能算出一个既不过度保守也不过度冒险的估计。**

### 0.5.4 这一篇与你手上项目的关系

dsh-mini 有三份接口特别适合做契约分析，因为它们各自代表一种典型的契约形态。

**`kernel/tools.ts` 的 `Tool` 接口是一个"面向第三方实现"的契约**——它被工具作者实现，被框架调用。这类契约的要求最高，因为**实现者与调用者不是同一批人**（在本项目里是"你写工具"与"框架调用工具"），任何未写明的期望都会变成隐患。

**`kernel/llm.ts` 的 `Provider` 接口是一个"面向替换实现"的契约**——`MockProvider`、`LocalProvider`、`DeepSeekProvider` 三者都实现它。这类契约的关键是**可替换性**：调用方不应该能分辨出它用的是哪一个，而任何一处的"只有 DeepSeek 才有"的行为都是契约泄漏。

**`kernel/session.ts` 的事件契约是一个"跨时间"的契约**——事件一旦写入日志，就必须永远能被后续版本读懂。这类契约的要求最特殊：**它的使用者包括尚未写出的代码**（未来的恢复、分析、迁移工具）。这也解释了为什么"Model-visible ⟺ logged"这条不变量如此重要——它是唯一能让未来代码信任历史的方式。

> **面试视角**
> **高频问法**（系统设计面的"扩展讨论"环节）："你这个改动会影响谁？"
> **高分要点**：不要说"影响比较大"，要说"我按两类依赖去数：谁调用它（值依赖）与谁只用了它的类型"，然后给出数字。**面试官在这一题上判断的是你有没有结构，而不是你估得准不准。**

## L0 要解决的问题

### 0.1 现象一：签名看不懂的东西，只能靠猜

第一个现象最普遍。你看到一个函数的签名：

```ts
export function validateArgs(schema: ParamSchema, args: unknown): ValidatedArgs
```

签名告诉你：它接收一个 schema 与一个 `unknown` 的参数，返回 `ValidatedArgs`。它没告诉你：参数不合法时是抛异常还是返回一个"含错误"的对象、它对多余字段是忽略还是拒绝、它会不会修改传入的对象、它是不是纯函数（能不能缓存结果）。

这四个问题在实际写调用代码时**每一个都必须回答**。而当你只能靠猜时，你有三种选择：读实现（慢）、试一下（不可靠）、看文档（如果有）。**如果三种都不可行，你就会写出一段基于猜测的代码**——而它在接口那次未写明的行为改变时就会失效。

**这个现象的量级值得估计一下**：在一个有 20 个模块的项目里，平均每个模块对外暴露 5 个函数，每个函数有 3 个未写明的行为维度，那就是 300 个"只能靠猜"的点。**而其中任何一点的改变都可能破坏某处调用方**——这就是 1.2 里说的"偶然复杂度"的一个具体来源。

### 0.2 现象二：加一个可选字段引发了一连串改动

第二个现象是第一个的后果，也是本篇开头描述的场景。它的特征是：**改动本身很小，但因为它是"接口的一部分"而有了额外的含义**。

为什么一个可选字段会有这么大影响？因为**接口的每一个成员都在回答一个问题："这个系统有能力做这件事吗？"** 当你加一个 `costEstimate` 字段时，你实际上是在宣布"这个系统支持成本预估"——而这个宣布会引出三个后续问题：谁负责填它（所有实现者）、谁负责用它（消费者）、以及**如果没人填会怎样**（默认行为）。

第三个问题是最麻烦的。如果没人填时默认是"无信息"，那么"支持成本预估"这个能力就只是"部分支持"，而使用者无法从接口上看出哪些工具有、哪些没有。**这类"半实现的能力"比"完全没有的能力"更危险**，因为它会让使用者产生错误的预期。

### 0.3 现象三：改了实现，调用方坏了，而"明明没改接口"

第三个现象最能说明"契约不只是签名"。你改了一个函数的内部实现——比如把 `Object.entries` 的遍历顺序从插入顺序改成了排序顺序——而某个调用方坏了。你去查它的代码，发现它写的是：

```ts
const [firstKey] = Object.keys(result)
// 假设 firstKey 是最后插入的那个
```

它依赖了**一个你从未承诺过的行为**（键的顺序）。而现在的问题是：**这算谁的错？**

按 Hyrum 定律，答案是"这不算错，这只是必然"。所以契约设计的原则是：**对于你打算长期保持的行为，明确承诺它；对于你不打算保持的，明确声明它是实现细节**。而如果一个行为既没承诺也没声明，那么默认情况是**它会被依赖**——因为使用者没有别的信息可用。

### 0.4 现象四：不知道什么改动需要迁移方案

第四个现象是决策层面的。当你要改一个接口时，你面对的是"要不要写兼容层、要不要通知使用者、要不要加版本号"这类选择。而这些选择的依据是**这次改动到底影响谁**——可你手上没有那个信息。

这个现象的具体表现是决策的两极分化：要么对一切都极度谨慎（每个改动都加兼容层，代码里堆满了为旧版本准备的 `if`），要么对一切都无所谓（直接改，坏了再说）。**两者都不对，而正确的做法需要一个分类工具**——1.4 节会给出那张表。

### 0.5 这一篇要回答的四个问题

把这四个现象收拢，本篇要正面回答四个问题，它们分别对应 L1 的四节主干。

第一个问题是：**一个契约到底由哪几部分构成？** 为什么会说话的人（写文档的人）觉得"我都写了"，而使用者仍然在猜？答案是三类承诺的划分，以及"责任归属"这个被忽略的维度。

第二个问题是：**签名表达不了什么？** 这一节给出一份清单，包含副作用、幂等性、顺序保证、并发安全、错误语义五项，每一项都给出"如何在签名外表达它"的具体做法。

第三个问题是：**什么样的改动是破坏性的？** 这一节给出一张分类表，并说明为什么判断依据从"改了什么"转向"谁依赖了它"。

第四个问题是：**怎么在不破坏承诺的前提下演进一个接口？** 这一节给出四种手段（加而不改、放宽而非收紧、保留兼容层、版本化），以及它们各自的代价。

> **追问方向**："为什么同一个失败有时抛异常、有时返回错误值？"（这正是 dsh-mini 里的一处真实缺口）

## L1 设计与原理

### 1.1 契约由什么构成：三类承诺与责任归属

理解契约的第一步，是承认一个事实：**函数签名只是契约的一个投影，而且是一个信息量很低的投影。** 它告诉你"有哪些输入、输出是什么类型"，但没有告诉你这个调用在什么条件下合法、会产生什么副作用、失败时怎么表现。而后面这些恰好是使用者在写调用代码时最需要的东西。

#### 1.1.1 三类承诺

本文把契约分成三类承诺。这个划分的依据是**使用者需要在什么时刻知道它**——也就是它们各自防止的是哪一类错误。

**第一类是行为承诺**，回答"调用它会发生什么"。它包含返回值的内容、副作用的范围（会不会改文件、会不会发网络请求）、以及幂等性（调用两次与调用一次的效果是否相同）。这一类是最常被写下的，因为它最直观。

**第二类是时序承诺**，回答"什么时候可以调用它、可以调用几次"。它包含调用时机的前置条件（必须在初始化之后、不能在关闭之后）、重入性（能不能在回调里再调它）、并发安全性（能不能同时从两处调用）、以及顺序保证（多次调用的效果是否与顺序有关）。**这一类最常被漏掉，而它的缺失会造成最难查的 bug**——因为违反时序承诺的代码往往在单线程测试下完全正常。

**第三类是错误承诺**，回答"失败时它怎么表现"。它包含失败的表达方式（抛异常、返回错误值、还是静默降级）、可恢复性（调用方能不能重试）、以及部分失败的处理（如果它做了三件事而第二件失败了，前一件要回滚吗）。**这一类缺失的后果是调用方无法写出正确的错误处理**——他会写一个 `try/catch`，但不知道自己该 catch 什么、也不知道 catch 到之后能不能重试。

举一个 dsh-mini 的真实例子来说明三者缺一不可。`ToolRegistry` 有一个 `register` 方法，它的签名是：

```ts
register(tool: Tool): Disposer
```

**行为承诺**写在文档里并且实现遵守了：注册一个工具；返回一个撤销注册的 disposer；**重复注册同名工具时，后注册的覆盖先注册的**（这一句是最重要的，因为它决定了调用方能不能安全地重复注册）。**错误承诺**也部分实现：名字非法时抛异常。但**时序承诺完全没有表达**——它没有说明"能不能在工具正在执行时注册新工具"。而在一个插件化的系统里，这个问题是真实的：某个插件可能在一次工具调用期间被装载（比如工具触发了自改），此时注册表正在被遍历，而遍历中修改集合的行为取决于具体实现。

**所以这个接口的契约是不完整的**，而它的不完整性不会立刻显现——它会在某个特定时序下变成一次难以复现的故障。

#### 1.1.2 责任归属：契约式设计里最有用的一条

Bernard Meyer 的契约式设计给出了一组划分，它的价值不在于术语，而在于它明确了**出了问题该去哪边找**。

| 概念 | 谁负责 | 违反时的含义 | 在 dsh-mini 里的例子 |
|---|---|---|---|
| **前置条件** | 调用方 | 调用方传了不该传的东西——**调用方的 bug** | "调用 `deriveMessages` 前，事件流必须已经 `endTurn`" |
| **后置条件** | 实现方 | 实现没有兑现它承诺的输出——**实现方的 bug** | "`ok(text)` 返回的结果里 `isError` 必须为 false" |
| **类不变量** | 双方共同 | 对象进入了一个不该存在的状态——**契约表达不完整** | "`#events.length` 必须等于下一个事件的 `seq`" |

**这个划分最实用的地方在于"调试时的第一步"**。当你遇到一个失败时，第一个问题不是"哪里错了"，而是"**这是前置条件被违反，还是后置条件被违反**"。如果是前者，去看调用方传了什么；如果是后者，去看实现做了什么。**跳过这个判断直接开始读代码，会在两个方向上各浪费一半时间。**

而第三行——类不变量被违反——是三者里最严重的，因为它意味着**没有任何一方违反了规则，但系统仍然进入了坏状态**。这通常说明契约表达不完整：那个不该发生的状态没有被任何前置条件排除，也没有被任何后置条件保证。dsh-mini 的 `assertModelVisibleMatchesLog` 正是在防这个——它是一条不变量检查，而它被违反时，既不能说调用方错了，也不能说某一处实现错了，只能说"系统在某个未被表达的地方产生了不一致"。

#### 1.1.3 三合一的两次追问

**工程追问：这三类承诺里，哪一类最值得写？**

从降低成本的角度看，答案是**时序承诺**。理由是它的性价比最高：写它只需要几句话（"这个方法不是线程安全的，调用方需要在外部同步"），而漏掉它的代价可能是一次极难复现的故障。行为承诺虽然最常被写，但它的缺失通常会被快速发现（跑一下就知道了）；错误承诺缺失的后果是错误处理写得不对，但它至少会在测试时暴露；**只有时序承诺的缺失会让代码在测试中通过而在生产中失败**。

一个可操作判据是：**如果你说不清这个方法能不能并发调用，那么它多半不能**。而如果你的答案是"其实我也没想过"，那就是一个需要现在补上的洞。

**产品追问：为什么承诺得越少越好？**

从产品角度看，契约是**一种对使用者的公开承诺**，而每一个承诺都会限制未来的选择。所以一个反直觉的原则是：**契约应该恰好含有使用者必须知道的东西，不多不少。**

这不是"尽量少写"，而是"**每一句写进契约的话都必须是承诺**"。原因很实际：一旦某件事被写进契约，它就变成了不能随便改的东西——改它需要迁移方案、需要通知使用者、可能需要兼容层。而如果它从未被承诺，你可以随时改。

这条原则有一个容易误解的地方：它**不**意味着"少写文档"。恰恰相反，它要求把"这不是承诺"也明确写出来。例如 `Tool` 接口的某个字段可以这样注释：

```
/**
 * 工具产出的摘要文本，用于给模型一个简短预览。
 * ★ 这是实现细节：具体格式、长度、是否包含换行都不构成承诺，
 *   调用方不应解析它的内容。
 */
```

**后一半（"不构成承诺"）和前一半同样重要**——因为如果没有它，使用者会按 Hyrum 定律去依赖它能观察到的一切。

> **面试视角**
> **高频问法**："一个接口的契约由什么构成？"——三类承诺是标准答案的骨架（行为 / 时序 / 错误）。
> **追问方向**："为什么契约要写得越少越好？"答：每一步承诺都限制未来的演进自由；而"不写"不等于"不声明"——必须显式声明哪些不属于承诺（Hyrum 定律）。
> **加分点**：能说出"参数只能放宽、返回只能收紧"这条口诀的来源（方向性：让调用方更宽松才安全）。

### 1.2 签名表达不了的五件事

这一节把 1.1 的结论具体化成一份清单。它可以用作写接口时的检查表：**每写一个接口，对着这五项各问一遍"我写清了没有"。**

| # | 表达不了的 | 不写清会怎样 | 怎么写清 |
|---|---|---|---|
| 1 | **副作用** | 调用方以为它是纯函数，于是缓存结果或调整调用顺序，而实际上它有外部影响 | 在文档里列举它触及的资源（文件/网络/环境变量/全局状态） |
| 2 | **幂等性** | 重试逻辑重复执行一个有副作用的操作（发了两条消息、写了两次文件） | 明确写"可重复调用"或"每调用一次产生一次效果" |
| 3 | **时序** | 并发调用、在回调里重入、在关闭后调用——都会产生未定义行为 | 写清"是否线程安全""能否重入""有无生命周期限制" |
| 4 | **错误语义** | 调用方不知道要 catch 什么、不知道能否重试 | 列出可能抛出的错误类型，并标注哪些可重试 |
| 5 | **资源所有权** | 返回的对象该由谁释放、内部集合能否被外部修改 | 写清返回值的所有权；对内部状态的暴露明确标注 |

#### 1.2.1 副作用：为什么它排在第一位

五项里副作用之所以最重要，是因为**它是唯一会跨出当前调用栈产生影响的一项**。其他的四项（幂等性、时序、错误、所有权）的影响都局限于这次调用的参与者，而副作用会影响**系统之外的世界**——文件、网络、外部服务。

用一个具体对比说明这个差别。一个函数"返回错误的结果"是可恢复的（改对再跑一次）；一个函数"在没有权限时静默删除了文件"是不可恢复的。**所以对副作用表达得最清楚的那部分接口，恰好是最需要它的那部分**：在 agent harness 里，这就是工具。

dsh-mini 的 `Tool` 接口用了一个字段来表达它：

```ts
export interface Tool {
  readonly name: string
  readonly description: string
  readonly params: ParamSchema
  /**
   * 这个工具的副作用等级。守卫依据它裁决放行 / 询问 / 拒绝。
   * ★ 它是一份承诺：声明 'read' 就意味着不会改动任何持久状态。
   */
  readonly sideEffect: 'read' | 'workspace-write' | 'irreversible'
  execute(args: Record<string, unknown>, ctx: ToolExecContext): Promise<ToolResult>
}
```

**这个设计的价值在于它把副作用从"文档里的描述"变成了"可被程序使用的数据"**。如果它只写在注释里，那么守卫无从依据它做判断——守卫需要的是能在运行时读取的值。而一旦它成为字段，它就有了两个额外的性质：**必须是准确的**（守卫会依据它放行，错了就是安全问题），以及**必须被每个实现填写**（类型系统强制）。

但这里有一个真实的问题值得指出：**这个字段目前**没有**校验机制**。一个工具声明自己是 `'read'` 而实际写了文件，框架无法发现。也就是说，它是一个**信任型承诺**而不是**强制型承诺**。这个区分很重要——它意味着"工具声明 `read` 就是安全的"这个推断**不成立**，除非所有工具都出自可信来源。L3 的审计会把这个发现列为一条真实缺陷。

#### 1.2.2 幂等性：为什么重试逻辑必须知道它

第二项幂等性在两个地方必须被知道：**重试**与**断点恢复**。

先说重试。dsh-mini 的第 9 步实现了重试：当一次模型请求失败时，它会重试。这里的重试是针对**模型调用**的，而模型调用本身是幂等的（重复问一次不会改变世界）。但如果重试逻辑被扩展到了工具执行上，那么"重复执行一个非幂等的工具"就会产生真实的后果——重跑了两次测试、发了两条消息。

**所以幂等性不是"这个函数的性质"，而是"这个函数能否被安全重试"的前提**。这个视角的转换很重要：它意味着当你要给某个操作加重试时，第一件事是确认它幂等，而不是先写重试逻辑。

再说恢复。第 20 步要做"会话恢复"，而恢复意味着**从日志重建状态并继续**。如果日志显示"有一个工具调用已经开始但没有结果"，那么恢复时该怎么做？答案取决于那个工具是否幂等：幂等则重放，非幂等则只能标记为"结果未知"并让模型决定。**这就是为什么工具接口需要表达幂等性**——它是恢复策略的输入。

#### 1.2.3 时序：最容易被漏掉、后果最严重

第三项时序承诺的缺失会产生最难查的 bug，原因在 1.1.3 已经说过：**它在单线程、线性执行的测试里完全不会暴露**。

dsh-mini 里有一处真实的时序契约，它写得比大多数地方都清楚。`framework/context.ts` 的 `provide` 方法有这样一段说明：

```
★ 注册服务的规则：
  1) 服务的实现写进共享表，但归属记在注册者身上；
  2) 注册者卸载时，共享表里属于它的那部分被移除；
  3) 卸载后再次 require 同名服务会失败——因为提供者已经不在了。
```

**第 3 条就是一条时序承诺**：它说明了"卸载之后不能再取"。如果没有这句话，调用方可能会在某个延迟执行的路径上持有服务引用，而在卸载后使用它——得到的是一个已失效的对象。

#### 1.2.4 错误语义与资源所有权

最后两项各有一个要点值得单独说。

**错误语义的核心问题是"分层"**。一个接口如果只抛出一种笼统的错误（比如 `Error`），调用方就无法区分"参数错了（别重试）"与"网络抖了（可以重试）"。而如果它抛出的类型太细（七八种），调用方又难以穷尽处理。**恰当的粒度通常与调用方的决策点对齐**：调用方需要做出几个不同的决定，就提供几类错误。dsh-mini 的 `kernel/llm.ts` 采用了这种思路——它把失败分成可重试与不可重试两类，因为调用方（重试插件）恰好只需要这一个区分。

**资源所有权的核心问题是"内部状态被暴露"**。当接口返回一个内部集合时，即使类型上它被标注为 `readonly`，在运行时它仍然是同一个对象。这一点在 1.3 里已经作为 `Session.events` 的一个风险点提过。**契约在这里能做的只有两件事**：要么返回副本（放弃性能换安全），要么明确声明"不要修改返回的对象"（承担被违反的风险）。dsh-mini 选择了后者，那么这条声明就必须写进契约——否则它只是一个未言明的假设。

> **面试视角**
> **高频问法**："类型系统还不够吗？"——不够。签名表达不了副作用、幂等性、时序、错误语义、资源所有权这五件事。
> **追问方向**："你怎么表达一个函数是不是线程安全的？"（时序承诺，也是最常被漏掉的一类）
> **岗位**：几乎全部后端与 Agent 岗技术面。

### 1.3 不变量：契约里最难表达、也最重要的一项

行为、时序、错误三类承诺都是**围绕一次调用**的。而类不变量不是——它描述的是**对象在任何时刻都必须满足的性质**。这一节单独讲它，因为它是 harness 里最关键的一类契约，也是最难写清楚的。

#### 1.3.1 为什么它最难写

难在三点。

**第一，它不属于任何一次调用。** 前置条件是"调用前必须成立"，后置条件是"调用后保证成立"，两者都有明确的挂靠点（函数的入口与出口）。而不变量是"永远成立"，它没有挂靠点——你不能把它写在某一个方法的文档里，因为它不属于那一个方法。

**第二，它常常跨越多个对象。** 比如"模型可见的消息必须能从日志重建"这条不变量，涉及 `Session`（持有日志）、`deriveMessages`（从日志派生）、以及 `Agent`（使用派生结果）。它不属于其中任何一个，而属于它们的组合。

**第三，它的违反往往是延迟暴露的。** 前置条件与后置条件被违反时，问题当场出现；而不变量被违反时，对象可能"看起来还能用"，直到某个特定路径依赖了那个不再成立的性质。

#### 1.3.2 表达不变量的三个位置

因为不变量没有天然的挂靠点，它需要在三个位置被表达，而这三个位置的作用不同。

**第一个位置是运行时断言**。它的作用是**把沉默的损坏变成响亮的失败**。dsh-mini 的 `assertModelVisibleMatchesLog` 就是这样的断言：它在关键节点检查"派生出来的消息与日志一致"，不一致就抛错。

```ts
/**
 * 运行时断言：模型可见的消息必须能从日志重建出来。
 *
 * ★ 为什么这个检查值得放在热路径上 ★
 * 因为这条不变量一旦被破坏，症状会在很远的地方出现（模型行为异常、
 * 恢复失败、统计对不上），而那时已经无法定位是哪一次改动引入的。
 * 断言把"远处的症状"变成"近处的失败"。
 */
export function assertModelVisibleMatchesLog(events: readonly SessionEvent[], messages: readonly ChatMessage[]): void
```

**第二个位置是测试**。断言是"在运行时抓住"，测试是"在提交前抓住"。两者的分工是：断言覆盖那些**你无法预知何时会出现**的路径，测试覆盖那些**你能构造出来的**场景。

**第三个位置是文档**。文档的作用与前两者不同——它不是为了"抓住违反"，而是为了**让使用者知道有这样一条约束存在**。没有文档时，一个开发者可能写出违反它的代码而完全不自知。

**三个位置缺一不可，而且它们各自防的是不同的失败**：只有文档时，违反靠自觉；只有测试时，未覆盖的路径会漏；只有断言时，使用者不知道规则（他会先违反，再被断言拦住，而他本可以一开始就不违反）。

#### 1.3.3 三合一的两次追问

**工程追问：不变量检查该放在热路径上吗？**

放在热路径（每次任务都跑）的成本是性能，收益是**定位精度**。放在冷路径（只在测试里跑）的成本是零，收益是**覆盖不全**。

判断的依据是**这条不变量被破坏后的定位成本**。如果破坏后的症状是"模型行为异常"——那定位成本可能是一天；那么即使每次多花 10 毫秒也值得。如果破坏后的症状是"下一次调用立刻抛异常"，那么放在测试里就够了。**换句话说：断言的位置应该与"症状离病因的距离"成正比。**

**产品追问：为什么这条不变量是产品要求，而不是工程要求？**

这一点值得说透，因为它解释了为什么这条约束在 harness 里如此重要。考虑一个真实的产品问题：**用户想知道"为什么这个 agent 上次做了那个决定"**。这个问题的答案必须来自历史记录，而如果"模型当时看到的东西"没有完整地留在日志里，这个问题就**永远无法回答**。

所以这条不变量实际上支撑着一个产品能力：**可复盘性**。它不是一个"内部整洁"的要求，而是一个"用户能不能信任这个系统"的要求。而它一旦被破坏，损失是不可逆的——那些历史就是丢失了。

**这个从工程约束到产品能力的映射，是这一篇最想传达的东西之一**：最值得写进契约的那些条款，往往不是"代码整洁"意义上的好习惯，而是**某个产品能力的必要条件**。

> **面试视角**
> **高频问法**："什么是不变量？你怎么保证它？"——三处表达（断言 / 测试 / 文档）是标准答案。
> **追问方向**："把不变量检查放在每次请求的热路径上，值得吗？"答：按"症状离病因的距离"判断；给出量化形式（见 L2 第 9 条）。
> **加分点**：举一个"破坏后不立刻报错"的不变量例子（比如工具调用与结果必须配对）。

### 1.4 兼容性判据：什么改动是破坏性的

这一节给出本篇最实用的一张表。它的用途是：**在做一次接口改动之前，用两分钟定位自己在哪一格。**

#### 1.4.1 判断依据是"谁依赖了它"，不是"改了什么"

先把判据说清，因为它的措辞决定了整张表的用法。

**一个改动是破坏性的，当且仅当它使某个依赖原有契约的代码可能失败。**

这个定义里有三个部分需要展开。**"依赖原有契约"**——不是所有使用者都会失败，只有那些依赖了被改掉的那部分的使用者会。**"可能失败"**——不是必然失败，而是进入了未定义或错误的可能状态。**"代码"**——包括尚未写出的代码（未来的恢复工具、分析脚本），这是 harness 区别于普通库的地方。

由这个定义可以直接推出一个结论：**同一个改动在不同的项目里，破坏性不同**。给一个函数加一个可选参数，在一个只有三个调用方的项目里是无害的；而在一个被外部依赖的 SDK 里，它可能改变行为的默认值，从而成为破坏性的。**所以这张表给的是"可能性"，最终判断必须结合"谁依赖了它"。**

#### 1.4.2 分类表

| 改动 | 破坏性 | 谁会受影响 | 应对 |
|---|---|---|---|
| **加一个可选参数** | 通常否 | 无人（老调用不受影响） | 直接加；但要注意默认值是否改变语义 |
| **加一个必填参数** | **是** | 全部调用方 | 改成就地重载或加新函数名 |
| **加一个返回值字段** | 通常否 | 无人（除非有用例做了深比较） | 直接加；但要检查契约测试是否做了全等断言 |
| **删除返回值字段** | **是** | 读该字段的一方 | 保留一段时间并标注弃用 |
| **收窄参数类型** | **是** | 传了被排除值的一方 | 放宽而非收紧 |
| **放宽参数类型** | 否 | 无人 | 直接改 |
| **收窄返回值类型** | 否 | 无人 | 直接改 |
| **放宽返回值类型** | **是** | 假设了具体类型的一方 | 保留旧类型或加新函数 |
| **改默认值** | **是（隐蔽）** | **未显式传参的所有调用方** | 视为行为变更；需要通知与迁移 |
| **改错误类型/错误信息** | **是（隐蔽）** | 依赖错误信息做判断的一方 | 错误类型算契约，信息文案不算（但要写明） |
| **改副作用范围** | **是（最隐蔽）** | 依赖"它不会做 X"的一方 | 视为契约变更；守卫与权限都要复查 |
| **改时序属性**（从同步变异步） | **是** | 全部调用方 | 加新函数而非改旧函数 |
| **放宽时序**（从不可重入变可重入） | 否 | 无人 | 直接改 |
| **收紧时序**（从可并发变不可并发） | **是（最危险）** | 所有并发调用方，且**测试常常测不出** | 慎之又慎；必须有并发测试 |

#### 1.4.3 为什么有些改动"隐蔽"

表里标了四处"隐蔽"。它们的共同特征是：**编译器不会报错，测试通常也不会失败，但行为变了**。

**改默认值**之所以隐蔽，是因为它影响的恰好是那批**什么都没写**的调用方——而它们看起来完全正常。`timeoutMs` 从 30000 改成 60000，所有没显式传超时的调用都会变慢一倍，而没有任何一处代码改动。

**改错误信息**之所以隐蔽，是因为错误信息常被当作"不重要的文案"。但实践中有大量代码在解析错误字符串（这不是好做法，但按 Hyrum 定律它是必然的）。所以正确的划分是：**错误类型是契约，错误信息的文案不是**——而后者必须在契约里明确声明"文案可能变化，不要解析它"。

**改副作用范围**之所以隐蔽，是因为它改变的是**调用方对"它不会做 X"的依赖**。一个 `read_file` 工具如果某天开始把读过的文件路径记进一个全局缓存，那么"它是纯读的"这个依赖就坏了——而没有任何签名变化。

**收紧时序**之所以最危险，是因为它**在测试里通常测不出来**。把"可并发"改成"不可并发"，单线程测试全过；而生产中出现的是偶发的不一致状态。这也解释了为什么看一个接口的时序承诺比看它的类型更重要：**类型错了编译器会拦，时序错了没人会拦。**

#### 1.4.4 三合一的两次追问

**工程追问：为什么"放宽参数、收紧返回"是安全的方向？**

这是一个可以推导出来的规则：**契约的改动方向应该朝向"对调用方更宽松"**。放宽参数意味着接受更多输入（老的调用仍然合法）；收紧返回值意味着给出更具体的保证（老的解析仍然成立）。反过来，"收紧参数、放宽返回"会要求调用方改变行为，所以是破坏性的。

这条规则的实用形式是一个口诀：**参数只能放宽，返回只能收紧**。（注意这里的"返回"指返回值的类型精度，不含"增加字段"——增加字段是安全的，因为它的方向是"给了更多信息"。）

**产品追问：破坏性变更的真正代价是什么？**

从产品角度看，破坏性变更的成本不只是"改调用方代码"。它包含三项，而第二、三项常被忽略。

**第一项是改代码的时间**，这是最直观的。**第二项是信任的损耗**——每一次破坏性变更都在告诉使用者"你的代码可能会被我弄坏"，于是他们下次会倾向于自己做一层包装（而那层包装又成为新的维护负担）。**第三项是历史的断裂**——对于有持久化数据的系统（会话日志、配置、缓存），破坏性变更可能让旧数据无法读取，而那是**不可逆的**。

第三项对 harness 尤其重要：**事件格式的破坏性变更会让历史会话读不出来**。这就是为什么 dsh-mini 的课程把"事件格式的改动"列为需要最谨慎对待的一类——它同时破坏了三项代价。

> **面试视角**
> **高频问法**（Agent 岗几乎必问）："什么改动是破坏性变更？"——判断依据是"谁依赖了它"，不是"改了什么"。
> **追问方向**："改一个默认值算不算破坏性？"算，而且**隐蔽**：它影响的是那批什么都没写的调用方。
> **进阶问法**："为什么事件格式的破坏性比函数接口更严重？"答：历史数据不会跟着改，而函数调用方可以一起改。

### 1.5 契约与波及面：把 1.2 和 1.3 接起来

前面四节讲的是"契约由什么构成、怎么表达、怎么改"。这一节要回答一个更基础的问题：**契约与一个系统的改动成本之间，到底是什么关系？**

#### 1.5.1 两份表的合取

在 1.3 里我们学过一份表：**谁依赖我**（扇入清单，分值与仅类型两组）。这一篇给出了第二份表：**我承诺了什么、谁依赖了哪一条**。单独使用任何一份表都会得出错误的判断。

只用第一份表（谁依赖我）会导致**过度保守**。回到 `Session` 的例子：16 个文件引用它。如果按"这 16 个都可能受影响"来做决定，那么任何改动都会显得极其危险，于是你会倾向于不动它——而实际上，那 16 个文件依赖的是**不同的部分**：有的只依赖事件类型（`apps/web.ts`），有的依赖 `append` 的行为（`kernel/agent.ts`），有的依赖统计字段（`evolution/diagnose.ts`）。

只用第二份表（谁依赖了哪条承诺）会导致**过度冒险**，因为你会漏掉那些**没有直接引用你、但通过中间层受影响的**使用者。`Session` 的 `append` 契约如果变了，`plugins/session.ts` 的转发逻辑要跟着改，而转发逻辑又会影响所有订阅 `session/event` 的界面——这些界面**从来没有 import 过 `Session`**，它们不在任何扇入清单里。

**所以准确的判断是两份表的合取**：从改动的那条承诺出发，先找直接依赖它的人（第二份表），再沿依赖关系向上求传递闭包（第一份表）。

```
   改动点：Session.append 的「重复调用会怎样」这条承诺
        │
        ├─ ① 谁读了这条承诺？（第二份表：契约依赖）
        │     ├─ kernel/agent.ts          ← 直接调用 append
        │     └─ plugins/session.ts       ← 转发它
        │
        └─ ② 那些人又被谁依赖？（第一份表：扇入闭包）
              ├─ plugins/session 被 → apps/web.ts、apps/repl.ts 依赖
              └─ 而这两个会把事件推给「界面」
                    ↑ 界面从来没 import 过 Session，但它们会受影响

   结论：真实波及面 = {agent, plugins/session, apps/web, apps/repl, 界面}
        而不是「16 个引用它的文件」，也不是「2 个直接用它的人」
```

#### 1.5.2 契约表面积：一个可以主动缩小的量

从上一条可以推出一个有用的概念：**契约表面积**，指一个模块对外承诺的事项总数。它的用处在于：**波及面的大小与它成正比**。

这个概念的实践价值在于它**可以被主动缩小**，而且缩小的方式不是删功能。三种方式：

**第一种是把承诺收窄到真正需要的程度。** 一个函数如果既承诺了返回值的内容，又承诺了它的字段顺序，那么它就多了一份表面积——而字段顺序通常是没必要的承诺（除非调用方真的按位置解析）。**做法是显式声明"顺序不构成承诺"**，把它从表面积里移出去。

**第二种是把多条承诺合并成一个更抽象的承诺。** `ToolResult` 如果承诺了"包含 text、isError、以及可能的 metadata"，那是三条；而如果承诺"包含 text 与 isError，其余字段属于实现细节"，那是一条半。**合并的代价是表达力下降**（调用方知道的更少），收益是表面积缩小。

**第三种是引入一层适配。** 让一个稳定的窄接口面对使用者，把变化的部分藏在适配层后面。这是 2.x 卷"作用域与装配"要讲的内容——但从契约角度看，它的本质是**用一层间接把表面积从"实现的总和"缩小到"接口的承诺"**。

#### 1.5.3 深模块与浅模块：契约设计里的一个判据

Ousterhout 提出过一组对比：**深模块**是"接口简单而内部复杂"，**浅模块**是"接口复杂而内部几乎没做什么"。这个对比在本篇的语境里可以重新表述：

> 深模块是**契约表面积小而实现量大**的模块；浅模块是**契约表面积大而实现量小**的模块。

这个表述让"为什么浅模块是坏的"变得具体：**它把复杂度暴露给了调用方，却没有换来封装收益**。调用方不仅要理解这个模块做了什么，还要理解它的每一条承诺——而如果那些承诺只是转发或琐碎操作，那就是纯粹的理解成本。

dsh-mini 里有一个值得分析的例子。`apps/shared-mode.ts` 提供的是模式装配的钩子工厂，它的导出很少（一两个函数），而它背后的逻辑涉及 `loadModes`、`parseModeDecl`、`applyMode`、行变换与插件配置的生成——**这是一个深模块**：调用方只需要知道"给我一个装载钩子"，不需要知道模式是怎么解析的。

反过来，如果一个模块导出了七八个细碎的函数，而它们各自只是转发到别处，那它就是浅的。**判断方法是 1.3 里教的"读导出列表"**：如果导出的每一项都能用一句话说清，而且合起来没有构成一个更大的概念，那它多半是浅的。

#### 1.5.4 三合一的两次追问

**工程追问：把承诺收窄会不会让使用者难以使用？**

会有这个风险。收窄承诺意味着调用方知道的更少，而如果它确实需要那些信息，它会转向两种替代方案：**读实现**（脆弱，实现一改就坏）或**自己补一层**（增加代码量）。所以收窄的判据不是"能收就收"，而是：**这条承诺，使用者真的需要吗？** 判断的依据是"有几种合理的使用方式需要它"——如果只有一种很偏的使用方式需要它，那么它不该进契约，而应该由那个特殊的使用者自己处理。

**产品追问：为什么"承诺少"是一种产品优势？**

因为承诺少意味着**演进自由**。一个接口如果只承诺了核心行为，那么实现方式、性能特征、内部结构都可以随时改进，而使用者不会察觉。这在产品上表现为一个实际的能力：**能持续改进而不打扰用户**。

反过来，一个承诺过多的接口会变成"化石"——它冻结了所有被承诺过的行为，包括那些当初只是顺手实现的。

**这个权衡在 harness 上有具体的形态**：`Provider` 接口的承诺应该恰好包含"调用模型并返回结果"，而不该包含"结果里的 usage 字段一定有某几个"——因为不同的 provider 能提供的 usage 不同，把它们写进接口承诺会让 MockProvider 不得不填假数据，而那又会污染统计。

> **面试视角**
> **高频问法**："你怎么评估一次改动的影响面？"——不要只答"看谁 import 了它"，要说**两张表的合取**：谁依赖了这条承诺 + 扇入的传递闭包。
> **追问方向**："只算扇入会怎样？"→ 过度保守（把只依赖类型的地方也算成风险）；"只算契约依赖呢？"→ 过度冒险（漏掉通过中间层受影响的界面）。

### 1.6 版本化与弃用：在不破坏承诺的前提下演进

前三节讲的是"怎么判断改动危不危险"，这一节讲"危险时怎么做"。给出四种手段，按代价从低到高排列。

#### 1.6.1 手段一：加而不改

最便宜的手段是**只增加、不修改**。加一个可选参数、加一个返回字段、加一个新函数——这些都不破坏已有承诺。

它的适用边界很窄：**只有当"新需求可以通过增加表达"时可用**。如果新需求要求改变已有行为（比如"默认超时应该是 60 秒而不是 30 秒"），那么"加而不改"用不上——因为问题的本质是旧行为需要变。

**这个手段最常见的误用是"加一个开关来切换新旧行为"**。它看起来是"加而不改"，实际上是**把一次破坏性变更变成了一份长期维护负担**：两个行为都要维护，而且使用者不知道该用哪个。所以开关只应该在一种情况下使用——**它是临时的迁移通道，且有明确的移除时间**。

#### 1.6.2 手段二：放宽而非收紧

第二种手段是**让契约朝宽松的方向改**。放宽参数类型、放宽输入约束、增加可接受的输入形态——这些都不会让已有的调用失效。

这条手段的依据是 1.4.4 里那条口诀：**参数只能放宽，返回只能收紧**。它的直接用途是：当你想收紧某个约束（比如"这个参数以后必须是正整数"）时，先问一句"**我能不能通过放宽别的地方来达到同样的目的**"。多数情况下答案是能——你想要的往往不是"拒绝非法输入"，而是"对非法输入也有合理行为"。

#### 1.6.3 手段三：兼容层

当新需求确实要求改变已有行为时，第三种手段是**保留旧路径作为兼容层，同时提供新路径**。

它的形式是最常见的：旧函数保留、新函数另起名字，旧函数的内部改为调用新函数（并在可能时给出弃用警告）。这个做法让使用方可以按自己的节奏迁移，而不是被迫同时改。

**它的代价是真实的，而且必须被明说**：兼容层会长期存在，它会出现在每一份文档里、每一次搜索里、以及每一个新人的理解成本里。所以兼容层必须配一个**移除条件**——不是"以后再说"，而是"当 X 发生时移除"。

dsh-mini 里有一个符合这个模式的设计值得作为正面例子：会话格式的版本机制。它没有直接改事件格式，而是引入了 `SESSION_FORMAT_VERSION`，并且规定**结构性改动才允许升版本**，同时**旧的已提交世代不允许被移动或覆盖**。这个设计的价值在于它把"格式演进"从"一次破坏性变更"变成了"一次有版本记录的变更"——历史数据仍然可读，而新代码知道自己面对的是哪一代。

#### 1.6.4 手段四：版本化

第四种手段是最重的：**给接口一个版本号，让新旧版本并存**。

它适用于两种情况：一是接口的使用者无法协调（外部依赖、跨团队）；二是改动频繁到"加兼容层"也跟不上（每次改动都加一层，层数会失控）。

**它的代价最高**，因为它引入了一整套额外的机制：版本的选择、协商、测试矩阵（每个版本都要测）、以及最终仍然要面对的"旧版本何时下线"。所以它是最后手段，而不是默认做法。

**对 harness 来说有一处特殊**：事件格式的版本化是必要的（因为历史数据存在），而函数接口的版本化通常不必要（因为代码可以一起改）。**这个区别的依据是"使用者是否受时间分隔"**——函数的使用者是同一时刻的代码，事件的使用者包括未来的代码。

#### 1.6.5 弃用周期：从警告到移除

无论用哪种手段，一个完整的演进过程都包含三个阶段，而**三个阶段的意义不同**：

| 阶段 | 做什么 | 为什么不能省 |
|---|---|---|
| **标注弃用** | 在文档与（可能时）运行时的警告里写明"这个会移除，替代品是 X" | 使用者需要时间发现；不告知就移除是突袭 |
| **并存期** | 新旧同时可用 | 让使用者按自己的节奏迁移 |
| **移除** | 删掉旧路径 | 不删的话，弃用的成本会永久存在 |

**并存期的长度是一个真正的判断**，它取决于"使用者从得知到完成迁移需要多久"。对一个只有你自己的项目，并存期可以是"下一次提交"；对一个有外部使用者的接口，可能是几个月。**判断的依据不是惯例，而是使用者的迁移成本。**

#### 1.6.6 三合一的两次追问

**工程追问：兼容层应该写在哪里？**

三种选择，各有代价。**写在旧函数里**（旧函数转换参数后调用新函数）：使用方无感，但旧函数的实现变成了适配代码，而它的文档要同时描述两种行为。**写在新函数里**（新函数兼容旧输入）：新代码要携带历史包袱。**写在一个独立的适配模块里**：两边都干净，但多了一个模块，且它成为一个新的"依赖中心"。

**推荐的默认是第一种**，因为它的收益（使用方无感）最大，而代价（旧函数的实现不再直观）集中在一处。但有一条限制：如果旧函数的行为与新函数**在语义上真的不同**（不只是参数形式不同），那么第一种做法会产生一个"看起来是旧函数、行为却变了"的东西——那比直接改更糟。

**产品追问：为什么"移除"这一步不能省？**

因为弃用而不移除会让成本**永久保留**，而这是最容易被拖延的一步——它没有立即的收益（移除不会让任何新功能可用），而它的成本是隐性的（理解成本、文档成本、测试成本）。

**判断依据可以量化为**：如果一条旧路径的存在让每一份相关文档都变长、让每一次搜索都多出无关结果，那么它的成本是每天都在发生的。而**保留它的理由必须被重新评估**——"当初为什么兼容"这个理由，在并存期结束时往往已经不成立了（那个使用者可能已经迁移，或者这个功能已经没人用）。

> **面试视角**
> **高频问法**："你怎么做一个不破坏使用者的接口升级？"——四种手段按代价递增：加而不改 → 放宽而非收紧 → 兼容层 → 版本化。
> **追问方向**："兼容层打算什么时候删？"答不出就说明它是永久负担。这一问在面试里几乎是标准收尾。
> **加分点**：指出"对历史数据（事件格式、持久化 schema）只能从版本化起步"，因为"加而不改"对不会自己更新的旧数据无效。

### 1.7 高级规则应变手册 ★

这一节是本篇的核心工具：一份可以在做接口设计或评审时随手查阅的**规则手册**。格式与前几篇一致：症状、可能原因、如何确认、处置动作、以及**什么时候不要用这条规则**。

十四条规则分四组：读契约、写契约、改契约、评审契约。

#### 组一 · 读契约（C-01 至 C-04）

**C-01｜症状：用别人的接口，但不确定能不能这样用。**
可能原因是接口的契约不完整（缺时序或错误承诺）。确认动作是做三个具体的尝试性提问："失败时它会抛异常吗""我能并发调用它吗""调用它两次效果一样吗"——**如果这三个问题在文档里都找不到答案，那就不是你的问题，是契约的缺口**。处置动作是去读实现（在被卡住的位置），并在**你解出答案之后补一条注释**——你刚刚花掉的时间，是下一个人不必再花的。**不要这么做的情形**：如果你只是想知道"它返回什么类型"，类型签名就够了，不需要读实现。

**C-02｜症状：一个接口的某个行为看起来很奇怪，不知道为什么这么设计。**
可能原因是它是一条承诺的副作用。确认动作是构造反事实："如果它不是这样，会出什么问题？"举一个真实的例子：`Session.events` 返回内部数组的引用而不是副本——奇怪的做法。而反事实是：如果返回副本，那么每次取事件都要复制整个数组，而一条长会话可能有上万个事件。处置动作是记录你找到的理由（补进契约），因为它下次还会让人困惑。**不要这么做的情形**：如果一段代码的反事实是"会更慢一点"，那它可能真的只是没优化——不是所有奇怪都值得解释。

**C-03｜症状：不确定某个行为算不算"承诺"。**
可能原因是**没有任何标志告诉你**。确认动作是看三处：文档里有没有用"保证""必须""永远"这类词、有没有对应的测试、有没有实现里的显式检查。三处都没有时，默认判断是"**它不是承诺**"——但按照 Hyrum 定律，它仍然可能被依赖。处置动作是把它明确标注为"实现细节、不要依赖"。**不要这么做的情形**：如果用户已经依赖了它并且改动会伤害他们，那么把它标注为"不是承诺"并不会让伤害消失——此时它是一个**事实上的承诺**，需要按承诺的方式处理（迁移方案）。

**C-04｜症状：一个接口的文档说了一套，实现是另一套。**
可能原因是文档过期（改实现时忘了改文档），或者实现有 bug（没做到承诺）。**判断是哪一个很重要**，因为它们的修法相反。确认动作是找一个最小用例跑一下，看实际行为。处置动作：如果实现是对的而文档过期，改文档；如果文档是对的而实现有 bug，**不要改文档来迁就实现**——那会让契约悄悄退化。**不要这么做的情形**：有时两者都错（文档写的不是想要的，实现也没做到），此时先决定"想要的到底是什么"。

#### 组二 · 写契约（C-05 至 C-08）

**C-05｜症状：你写了一个接口，但使用者仍然在问"这个怎么用"。**
可能原因是遗漏了时序或错误承诺。确认动作是让对方**提三个问题**，然后看你是否在每个问题上都要读实现才能回答——**如果对方问的问题里有两个以上需要你翻代码，那就是契约缺口**。处置动作是补进文档，而不是口头回答（口头回答的那个"契约"会随你离开而消失）。**不要这么做的情形**：如果对方问的是"这个业务逻辑为什么这样"，那是需求问题，不是契约问题。

**C-06｜症状：不确定某个细节该不该写进契约。**
判断标准只有一条：**它是使用者必须知道的事情吗？** "必须"的意思是：不知道它就无法正确使用。如果知道了会更好但不知道也能用，那它不该进契约。举例：一个 `run_command` 工具，"超时后进程树会被终止"是必须知道的（否则使用者会自己再杀一次）；而"超时后返回的错误信息里包含耗时"是可有可无的。处置动作：必须知道的进契约；可有可无的进"实现细节"说明。**不要这么做的情形**：当你不确定时，**倾向于不写**——因为写错的契约比不写更难改。

**C-07｜症状：一个接口看起来很小，但实现它的每一个工具都写了很多样板。**
可能原因是接口把"实现者必须自己处理的细节"暴露了出来。确认动作是数一下：实现一个工具平均要写多少行与业务无关的代码？如果超过一半，说明接口的位置不对。处置动作是把共性提到接口层（例如把"参数校验"从每个工具里移到框架里）。**不要这么做的情形**：如果那些样板代码各不相同（每个工具都有自己的前置检查），那么它们不是样板，而是真实的差异——此时不该合并。

**C-08｜症状：你想给接口加一个字段，但不确定它会不会成为负担。**
确认动作就是本篇 0.1 节那个问题：**这个字段要成为承诺的一部分吗？** 如果是，那么所有实现者都要遵守、所有消费者都可以依赖；如果不是，那它**不该出现在接口上**——应该由需要它的一方自己维护映射。处置动作：先按"它不是承诺"来设计（不进接口），只有在出现第二个需要它的使用者时才提升为接口字段。**不要这么做的情形**：如果这个字段是**安全性或正确性相关**的（比如 `sideEffect` 等级），那么它必须进接口，而且必须是强制的——因为"某些工具没填"会让守卫的判断不成立。

#### 组三 · 改契约（C-09 至 C-12）

**C-09｜症状：你要改一个接口，但不知道会不会打破别人。**
处置动作就是查 1.4.2 那张分类表，再用 1.5.1 的两表合取算出真实波及面。**两步都必须做**：分类表告诉你"这类改动通常危不危险"，两表合取告诉你"在你这个系统里危不危险"。**不要这么做的情形**：当改动是"收窄时序"（比如从可并发变成不可并发）时，分类表会告诉你它危险，而两表合取会**低估**它——因为并发问题不体现在静态依赖上。此时唯一可靠的办法是找并发测试。

**C-10｜症状：你想加一个开关来同时支持新旧两种行为。**
可能原因是你在避免一次破坏性变更。确认动作是问"这个开关打算什么时候删"。处置动作按答案分支：如果是灰度（有明确期限），保留；如果是"为了兼容某人"（无期限），改为兼容层 + 弃用标注；如果是"我不想改原逻辑"（回避），停下来先理解原逻辑。**不要这么做的情形**：当改动确实影响线上且没有回滚手段时，开关是必要的安全网——这不是回避。

**C-11｜症状：一个接口要演进，但你不知道该用四种手段里的哪一种。**
处置动作是按"改动方向"选择：能用"加"就用加；需要改行为就先试"放宽"；必须换行为就做"兼容层"；使用者无法协调时才"版本化"。**判断顺序不能颠倒**——因为代价是递增的。**不要这么做的情形**：当使用者是**未来代码**时（事件格式、持久化数据），直接从版本化开始——因为"加而不改"对历史数据无效（历史数据不会自己更新）。

**C-12｜症状：兼容层已经存在很久了，没人记得为什么。**
可能原因是它当初的理由已经不成立。确认动作是找它的"移除条件"——如果当初没写，那就是一个缺陷；如果写了，检查条件是否满足。处置动作是评估移除（用 C-01 判断有没有人在依赖它），或者**补写移除条件**。**不要这么做的情形**：当它是安全相关的兼容（比如旧格式的解析保留了数据校验）时，不要因为"看起来没人用"就删——安全的兼容层值得永久保留。

#### 手册的使用方式

与前几篇一样：**遇到具体卡点时查，不要从头读**。这份手册的补充时机是——当你遇到一个它没覆盖的契约问题并用时间解决了它之后，就按同样的六项格式补一条，**特别是"不要这么做的情形"那一项**，因为它是唯一能防止规则被误用的部分。

> **面试视角**
> **用法**：这一节不是用来背的，是用来**在面试现场想不起来某个取舍时定位自己的**。
> **典型场景**：面试官说"那如果并发呢"→ C-09；说"那你加个开关吧"→ C-10；说"这个字段你怎么保证"→ C-08。

| 10 | 错误的粒度 | 与调用方的决策点对齐 | 一种笼统错误 / 极细分类 | **调用方**：粒度不对就写不出正确的错误处理 |
| 11 | 谁写契约 | 实现者写初稿，使用者补漏 | 只由实现者写 | **实现者**：要主动收集使用者的疑问 |
| 12 | 契约变更的通知 | 变更时主动告知依赖者 | 靠对方自己发现 | **变更发起者**：要花时间；换来不突袭 |
| 13 | 内部状态的暴露 | 明确所有权，或返回副本 | 直接返回内部引用 | **调用方**：要遵守未言明的约定 |
| 14 | 契约的评审时机 | 在实现之前评审接口 | 实现完之后评审代码 | **评审者**：要提前介入；换来改动成本最低 |

这张表里有三条值得展开，因为它们各自避免了一类常见错误。

### 关于第 3 条的完整论证（强制型与信任型的边界）

先把两个概念说清。**强制型契约**是框架能检查并阻止违反的（类型系统、运行时校验）；**信任型契约**是框架无法检查、只能依赖约定与人为判断的。

选择哪一个，判据是**违反的后果**：

| 违反后果 | 应当采用 | 例子 |
|---|---|---|
| 安全事件、数据损坏 | **强制型** | "声明 `read` 的工具不得写入"——如果它能写，权限就形同虚设 |
| 静默的行为不一致 | 强制型（若成本可接受） | "同一事件类型不能有两种结构" |
| 可读性、风格 | 信任型 | "函数名用动词开头" |
| 性能特征 | 信任型 | "这个方法预期是 O(1)" |

**dsh-mini 的 `Tool.sideEffect` 属于第一行，但它目前是信任型**——这是本篇发现的一处真实缺陷（见 L3.2）。而它的修法不是"把它改成强制型"那么简单，因为**静态检查一个函数会不会写文件是做不到的**。可行的折中是：在 `'read'` 等级下，框架用沙箱把工作区设为只读——**那样即使工具声明错了，它也没有能力写**。这个例子说明了一个重要的模式：**当契约无法被"检查"时，有时可以通过"限制能力"来达到同样的效果。**

### 关于第 8 条的完整论证（为什么契约测试不能全等断言）

这一条纠正一个非常常见但代价很高的做法。考虑一个返回统计对象的接口，实现返回：

```ts
{ turns: 3, steps: 12, toolCalls: 5 }
```

**全等断言**写法是 `expect(stats).toEqual({ turns: 3, steps: 12, toolCalls: 5 })`。**契约断言**写法是分别断言三个字段的值。

它们的差别在一个具体场景里显现：你后来给统计加了一个字段 `cachedTokens`。全等断言的测试**失败了**——尽管没有任何调用方会因此受影响（多一个字段不破坏任何承诺）。于是你必须去改测试，而改测试的过程会让人产生一个错误印象："这个改动有风险"。更糟的是，如果团队的习惯是"测试挂了就改测试",那么这个断言实际上**不再保护任何东西**。

契约断言的写法不会失败，因为它断言的正是"承诺"——那三个字段的值对了。**所以两者的区别不是风格，而是"测试在保护什么"**。

这条有一个例外需要说明：**对于"必须精确"的接口，全等断言是对的**。例如一个序列化格式的测试，它必须断言输出的字节完全一致——因为格式的每一位都是承诺。

### 关于第 9 条的完整论证（不变量检查放在哪里）

判据在 1.3.3 里给过：**按"症状离病因的距离"决定**。这里补充它的量化形式。

设一次断言的成本是 `c`（比如 10 毫秒），它被执行的频率是 `f`（每次任务一次），而它防止的那类问题一旦发生，定位成本是 `d`（比如 4 小时）。设该问题在开发过程中的出现概率是 `p`（比如每 20 次改动出现一次）。

放热路径的期望收益是：**每次改动平均省下 `d × p - c × f × n`**，其中 `n` 是两次问题之间执行断言的次数。当 `d × p` 明显大于 `c × f × n` 时，热路径是合算的。

用具体数字算一遍：`d = 4 小时`、`p = 1/20`（每次改动 12 分钟）、`c = 10ms`、`f = 1/任务`、`n = 100 任务`（两次问题之间跑 100 个任务）。那么收益侧是 12 分钟，成本侧是 1 秒。**结论是热路径明显合算。**

**这个计算的价值在于它把"要不要加断言"从一个直觉问题变成了一个可以估的问题。**

> **面试视角**
> **高频问法**："你怎么决定一个接口承诺多少、边界在哪？"——L2 的十四条决策就是这套判断的完整清单。
> **追问方向**："如果两个方案都有代价，你怎么选？"答：说清代价落在谁身上，然后**给出你的选择**——面试里"两种都可以"通常会被追问到底。 而它的输入（`d` 和 `p`）是可以凭经验估的——你只需要问"这类问题出现过吗？多久一次？上次查了多久？"

## L3 实现（案例逐段解析）

这一节是一次完整的**契约审计**。它审计 dsh-mini 的三个核心接口，而这三个分别代表契约的三种典型形态：

| 接口 | 契约形态 | 难点 |
|---|---|---|
| `Tool`（`kernel/tools.ts`） | 面向**第三方实现** | 实现者与调用者不是同一批人，任何未写明的期望都会变成隐患 |
| `Provider`（`kernel/llm.ts`） | 面向**替换实现** | 三个实现（Mock/Local/DeepSeek）必须真的可替换 |
| 会话事件（`kernel/session.ts`） | 面向**未来代码** | 已写入日志必须永远能被后续版本读懂 |

审计的方法固定为四步，它在任何一个接口上都能用：

```
① 列出签名能表达的部分（类型）
② 列出签名不能表达的三类承诺（行为/时序/错误），逐条问"写清了没有"
③ 列出不变量，并为每条找出证据来源（断言/测试/文档）
④ 找出"签名或文档承诺了、而实现没做到"的地方 —— 这是最危险的一类
```

### 3.1 审计对象一：`Tool` 接口

#### 3.1.1 契约清单

```ts
export interface Tool {
  readonly name: string
  readonly description: string
  readonly params: ParamSchema
  readonly sideEffect: 'read' | 'workspace-write' | 'irreversible'
  execute(args: Record<string, unknown>, ctx: ToolExecContext): Promise<ToolResult>
}
```

| 类别 | 承诺内容 | 写在哪儿 | 完整吗 |
|---|---|---|---|
| **行为** | 工具的名字、描述、参数 schema | 类型（强） | ✅ |
| **行为** | `sideEffect` 声明它会不会改动持久状态 | 类型 + 注释 | ⚠️ 是信任型（见 3.1.3） |
| **行为** | `execute` 返回 `ToolResult`（含 `isError`） | 类型 | ✅ |
| **时序** | 能否并发调用同一个工具 | **无处** | ❌ 缺口 |
| **时序** | 能否在工具执行期间修改注册表（注册/注销工具） | **无处** | ❌ 缺口 |
| **时序** | `execute` 有没有超时？谁负责超时 | **无处** | ❌ 缺口 |
| **错误** | 抛异常与返回 `isError: true` 的区别 | **无处** | ❌ 缺口 |
| **错误** | 参数校验失败时由谁负责（框架还是工具） | 部分（`validateArgs` 的存在暗示框架） | ⚠️ 不明确 |
| **边界** | 工具可以使用哪些上下文（能不能改会话、能不能发事件） | `ToolExecContext` 的类型 | ✅ |

#### 3.1.2 从清单里看出的三处缺口

**第一处：错误表达有两种方式，但没有规则说明用哪一种。** 工具可以 `throw`，也可以返回 `{ isError: true }`。这两种在框架侧的后果不同——抛异常会向上传播到循环，而 `isError: true` 会作为工具结果反馈给模型。**这意味着同一个失败，写成两种形式会让模型看到完全不同的东西**：一种是"工具调用失败"（可能触发重试），另一种是"工具调用成功但结果是错误信息"（模型会尝试别的办法）。

**这不是一个实现细节，而是一条必须写明的契约**，因为工具作者的选择会直接影响模型的行为。

**第二处：并发语义未定义。** 两个工具调用能不能同时执行？在 dsh-mini 当前的实现里，循环是顺序执行的，所以实际上不并发——**但"当前实现恰好如此"不等于"契约如此"**。如果将来为了性能改成并行执行工具调用（这在线程安全的工具上是合理的），那么所有"假设自己独占工作区"的工具都会出问题。**契约的价值恰恰体现在这里：它让未来的改动知道自己的边界在哪。**

**第三处：超时的责任归属未定义。** 一个工具如果永远不返回，会发生什么？框架有没有超时？从 `ToolExecContext` 的类型看，它提供了 `signal`（取消信号），这暗示"框架会取消，工具应当响应"——但**这只是一条被推断出来的契约**，而不是被写下的。

#### 3.1.3 一处"承诺了但能力上做不到"的发现

这是本次审计里最重要的一处发现。

`sideEffect: 'read'` 的含义在注释里写明是"守卫依据它裁决放行/询问/拒绝"，也就是说：**声明 `read` 的工具会被自动放行**。这构成了一条承诺——"如果这个工具声明为 read，那么调用它是安全的、不需要询问"。

但**框架没有任何机制验证这个声明**。一个工具声明 `'read'` 而在实现里写了文件，守卫会照样放行。所以这条承诺的实际强度是"**工具作者说的是真的**"。

这个发现的三个层次值得分开看：

**第一层：这是一个真实的安全缺口**,而不是理论问题。若工具来自不可信来源（第 23 步要接的 MCP 工具、或自进化生成的工具），它可以用一个错误的声明换来无审批的写权限。

**第二层：修法不是"加校验"，而是"限制能力"。** 因为静态判断"这个函数会不会写文件"做不到。可行的做法是**让声明与沙箱等级联动**——声明 `read` 的工具在 `readonly` 沙箱下执行，于是即使它想写也没有能力写。这个模式在 1.7 的 C-08 里被概括为"当契约无法被检查时，用限制能力来代替"。

**第三层：这个缺陷的存在恰好证明了契约审计的价值。** 如果只看类型（`sideEffect` 是一个联合类型的字段，看起来很严谨），你会认为这个契约是完整的。**只有把"承诺"与"谁有能力兑现它"对照起来，才能看出缺口。**

### 3.2 审计对象二：`Provider` 接口

#### 3.2.1 契约清单与可替换性检查

```ts
export interface Provider {
  readonly name: string
  chat(messages: readonly ChatMessage[], options?: ChatOptions): Promise<ChatResponse>
}
```

**替换实现的契约，最有效的检查方式是"用一个实现替换另一个，看调用方能不能察觉"**。这个检查在 dsh-mini 上很容易做，因为有三个实现。

| 检查项 | Mock | Local | DeepSeek | 调用方能否察觉 |
|---|---|---|---|---|
| `chat` 的返回结构 | ✅ | ✅ | ✅ | 不能 |
| `usage` 字段齐全度 | 部分 | 部分 | ✅ | **能**（统计会缺数据） |
| 流式返回 | ❌ | ❌ | ✅ | **能**（但接口没有流式方法，所以不构成泄漏） |
| 失败时的错误类型 | 自定义 | 自定义 | 网络错误 | **能** |

**第三行是正常的**（接口本来就没有流式能力，所以不是替换性问题）；**第二行与第四行是真实的契约泄漏**。

#### 3.2.2 两处泄漏的分析

**`usage` 字段齐全度的泄漏。** `ChatResponse` 里有 `usage`，但不同 provider 能提供的 usage 不同。如果调用方（比如统计插件）假设 `usage.cachedTokens` 一定存在，那么在 Mock 或 Local 下它会拿到 `undefined`。**这类泄漏的修法是让契约表达"可以不完整"**——把 `usage` 的字段标注为可选，并要求消费者处理缺失，而不是让每个实现填假数据（填假数据更糟，因为它会污染统计）。

**错误类型的泄漏。** 重试插件需要判断"这个错误可重试吗"。如果 Mock 抛的错误与 DeepSeek 抛的错误类型不同，那么重试逻辑就必须知道"现在是哪个 provider 在跑"——**那就意味着它不再可替换了**。修法是**在接口层约定错误分类**：provider 的契约里写明"失败时抛出 `ProviderError`，并带上 `retryable` 标记"。dsh-mini 在这一点上做了部分工作（`kernel/llm.ts` 里有错误分类），但没有把它写进 `Provider` 的契约文档。

#### 3.2.3 三合一的两次追问

**工程追问：为什么"可替换性"是一个比"类型兼容"更强的要求？**

因为类型兼容只保证"能编译"，而可替换性要求"**行为等价**"。`MockProvider` 与 `DeepSeekProvider` 可以有相同的签名而完全不同的行为——前者立即返回，后者需要几秒；前者永不失败，后者会限流。**这些差异对调用方是可见的**，所以它们属于契约。

可替换性的实用检查是**用一个替代实现跑全部的测试**。如果测试在 Mock 下通过而在 DeepSeek 下失败（或反之），那说明测试依赖了某个实现特有的行为，而那个行为是一条未被表达的契约。dsh-mini 的 `verify.ts` 用 Mock 跑，而 `test:e2e` 用真实 API 跑——**这个双轨设计本身就是可替换性检查的实现**。

**产品追问：为什么"能不换 provider"是产品能力？**

因为它决定了三件产品上的事情：**成本可控**（换到便宜的实现不改变上层）、**离线可用**（Local 实现在无网络时可降级）、**可测试**（Mock 让验证不花钱）。这三件事都是"用户能信任这个系统"的组成部分——尤其第二件，它把"断网就完全不能用"变成了"能力下降但还能用"。

### 3.3 审计对象三：会话事件契约

#### 3.3.1 为什么它的契约形态最特殊

前两个接口的使用者是**同一时刻的代码**；而事件契约的使用者包括**尚未写出的代码**——未来的恢复工具、分析脚本、格式迁移器。这个差别带来两条独特的约束：

**第一，它不能通过"改调用方"来完成演进。** 函数接口变了，你可以把所有调用点一起改；而事件格式变了，**已经写入磁盘的历史不会跟着改**。

**第二，它的"使用者"无法被列举。** 你不知道未来会有哪些工具读这些事件，所以你不能用"谁依赖了这条承诺"来判断改动风险——那个集合是开放的。

#### 3.3.2 契约清单

| 类别 | 承诺内容 | 证据 |
|---|---|---|
| **行为** | 每条事件有 `seq`，且**不跳号、不重号** | 实现（`append` 里递增） |
| **行为** | `seq` 与数组长度一致：`events.length === nextSeq` | 实现保持一致，**无断言** |
| **行为** | `turn/start` 与 `turn/end` 之间的 step 编号从 1 开始 | 实现 |
| **时序** | 事件只能追加，不能修改或删除 | 实现（数组只 push） |
| **时序** | `turn` 之间不交错（一个 turn 结束后才开下一个） | 实现（循环是顺序的） |
| **错误** | 未知事件类型如何处理 | **无处**（这是最关键的缺口，见 3.3.3） |
| **边界** | 表面事件（进模型视野）与过程事件的区分 | `SURFACE_EVENT_TYPES` 常量 ✅ |

#### 3.3.3 最关键的一处缺口与它的正确解法

`SessionEventMap` 的成员在读取时是**必需**的（required-on-read）：一个不认识某个事件类型的构建，会拒绝读取包含该事件的日志。这条规则在 DSH 里是通过 `ignorable: true` 这个信封字段来放宽的，而 dsh-mini **目前没有这个机制**。

这意味着什么？**意味着你无法在不破坏兼容性的前提下添加新事件类型**——因为老版本的代码读到新事件会直接拒绝整份日志。而"添加新事件类型"恰恰是最高频的一种演进（第 18 步的压缩要加 `session/compaction`，第 20 步的持久化可能要加 `session/resumed`）。

**这个缺口有一个标准的解法**，它的道理值得说清：把"未知事件"的处置分成两类。**一类是可以忽略的**（它不影响对模型可见历史的重建），这类事件带一个 `ignorable: true` 标记；**另一类是不能忽略的**（比如"压缩点"——不知道它就没法正确派生），这类事件让老版本**拒绝**这份日志。

**为什么这个划分是对的**：它把"兼容性"从一个全局属性变成了每个事件类型的属性。而判断一个事件属于哪一类的标准很清晰——**问"如果不知道它，派生出来的模型可见历史会错吗"**。

**这个例子是契约设计里最有价值的一课**：格式演进的关键不是"设计一个能兼容所有情况的机制"，而是**为每一种变化提供一条明确的处置规则**，让未来的代码知道该怎么做。

### 3.4 审计结论

把三次审计的发现汇总，可以得到一张按严重程度排序的清单。这张清单本身就是一篇文档的产出物，而它的排序依据是**"违反后的后果严重程度 × 出现的概率"**。

| 严重度 | 发现 | 属于 | 后果 |
|---|---|---|---|
| 🔴 高 | `sideEffect` 是信任型，且守卫依赖它放行 | 契约强度 | 不可信工具可用错误声明换取无审批写入 |
| 🔴 高 | 事件契约没有"可忽略"机制 | 契约演进 | 加新事件类型会破坏旧版本读取日志 |
| 🟡 中 | `Provider` 的错误类型未写进契约 | 契约泄漏 | 重试逻辑事实上依赖了具体 provider |
| 🟡 中 | `Tool` 的错误表达（抛异常 vs 返回错误）无规则 | 契约缺口 | 同一失败在模型侧表现不同 |
| 🟡 中 | `usage` 字段齐全度未声明为"可能不完整" | 契约泄漏 | 统计在非 DeepSeek 实现下缺数据 |
| 🟢 低 | `Tool` 的并发与超时语义未定义 | 契约缺口 | 未来并行化时会出问题 |
| 🟢 低 | `seq` 与数组长度的一致性无断言 | 证据缺失 | 破坏后延迟暴露 |

**这张表为什么值得作为产出物**：因为它把一个模糊的问题（"这个项目的接口设计得好不好"）变成了七条有严重度排序的具体发现。**而且其中三条都可以在半小时内修**（补文档、加断言、把可选性写进契约）。这就是契约审计的实际价值——**它找出的问题多数不是设计错误，而是"没写下来"**。

> **面试视角**
> **高频问法**（项目深挖环节）："你怎么 review 一个接口设计？"——L4.2 的七步流程可以直接作为答案。
> **追问方向**："你从这次 review 里发现了什么？"→ 讲那处**信任型契约**（声明了但没人能验证），并说出修法是"限制能力"而不是"加校验"。**这是一个高含金量的回答**，因为它展示了对"契约强度"这一层的理解。
> **岗位**：Agent 岗技术面、后端岗系统设计面。

## L4 运行与验证

契约这件事有一个特殊的验证难点：**它的错误往往不表现为"跑不通"，而表现为"跑通了但用错了"**。所以这一节的验证方法围绕一个核心动作设计：**让别人（或另一个版本的你）只根据契约写一次调用代码，看他能不能写对。**

### 4.1 三层验证

**第一层：契约自检。** 拿 1.2 的五项清单（副作用、幂等性、时序、错误语义、所有权）逐个过一遍你写的接口，每一项都必须有一个明确的答案。这一层是必要的，但它只验证了"你想到了"。

**第二层：外部消费者测试。** 这一层是契约验证的核心方法，也是它区别于普通测试的地方：**找一个不知道实现的人（或者你自己隔几天之后），只给契约文档，让他写一段调用代码**。他会写出什么，就是这份契约实际表达了什么。

这个方法的诊断力在于：**他写错的每一处，都对应一条你没有表达清楚的承诺**。如果他把 `execute` 写在了一个 `try/catch` 里而契约里没有说明它会抛异常，那不是他的问题——是他被迫做了一个假设。

**第三层：替换实现测试。** 对"面向替换实现"的契约（比如 `Provider`），最有效的验证是**用每个实现各跑一遍完整的测试**。任何在某个实现下失败的测试，都指向一条被泄漏的契约。

在 dsh-mini 上这一层是现成的：`verify.ts` 用 Mock 跑，`test:e2e` 用真实 API 跑（需要 `DEEPSEEK_API_KEY`）。**两者的差值就是契约泄漏的量**。

### 4.2 一次完整的审计流程

把审计固定成可重复的步骤：

```
① 读签名，列出类型能表达的部分
② 对三类承诺（行为/时序/错误）逐条问"写清了没有"，把缺口列出来
③ 列出不变量，为每条找证据来源（断言/测试/文档），无证据的标红
④ 对照"承诺"与"谁有能力兑现它"，找出信任型契约
⑤ 用外部消费者测试验证：只看文档写一段调用代码
⑥ 用替换实现测试验证（若该接口有多个实现）
⑦ 把发现按「严重度 = 后果 × 概率」排序，输出清单
```

第 ④ 步是最容易被跳过、也最容易出成果的一步。它的问法是：**这条承诺，我们有能力保证吗？** 如果答案是"我们只能相信别人说的是真的"，那么它就是一个信任型契约，而信任型契约在安全相关的场景下需要额外的手段（限制能力，而不是检查）。

### 4.3 判据

本文对"你掌握了契约分析"的判据有五条。

第一，你能对一个接口列出完整的三类承诺清单，并指出哪几类有缺口。

第二，你能算出一个改动的真实波及面（1.5.1 的两表合取），而不是只说"影响面大"。

第三，你能判断一次改动属于 1.4.2 表里的哪一格，并说出它为什么可能隐蔽。

第四，你能识别出至少一处**信任型契约**，并给出"限制能力"而不是"增加校验"的修法。

第五，也是最能说明你理解的一条：**你能为一个当前"不是承诺"的行为，写出它成为承诺的代价**（例如"如果把返回字段顺序变成承诺，未来就不能改字段顺序了"）。

> **面试视角**
> **高频问法**："你怎么验证一个接口设计得好不好？"——三层验证里，第二层（**外部消费者测试**）是最有说服力的答案：给一个不知道实现的人只看契约，看他能不能写对。
> **追问方向**："怎么证明契约是完整的？"→ 用"他写错的每一处都对应一条你没表达清楚的承诺"来回答。
> **加分点**：提到"用每个实现各跑一遍测试，差值就是契约泄漏的量"（可替换性检查）。

## L5 语法速查

### 5.1 术语表

| 术语 | 准确含义 | 常见误用 |
|---|---|---|
| **契约** | 一个模块对外的全部可依赖行为（三类承诺） | 误当成"函数签名" |
| **行为承诺** | 调用它会发生什么 | —— |
| **时序承诺** | 何时可调用、能调用几次、能否并发 | 最常被漏掉 |
| **错误承诺** | 失败时怎么表现、能否重试 | 常被写成"抛异常"了事 |
| **前置条件** | 调用方的义务 | 误当成"实现方要处理的边界" |
| **后置条件** | 实现方的义务 | —— |
| **类不变量** | 对象生命周期中始终为真的性质 | 误当成"某次调用的后置条件" |
| **可替换性** | 换上另一个实现，调用方察觉不到 | 误当成"类型兼容" |
| **破坏性变更** | 使依赖原契约的代码可能失败 | 误当成"改动很大" |
| **契约表面积** | 一个模块对外承诺的事项总数 | —— |
| **深模块 / 浅模块** | 接口小实现大 / 接口大实现小 | —— |
| **强制型契约** | 框架能检查并阻止违反 | —— |
| **信任型契约** | 只能依赖约定，框架无法检查 | 最危险的一类 |

### 5.2 三个模板

**模板一 · 契约文档骨架。** 写接口时按它组织注释：

```ts
/**
 * <一句话说明它做什么>
 *
 * ## 行为
 * · 返回什么、有什么副作用
 * · 幂等性：调用两次与一次的效果是否相同
 *
 * ## 时序
 * · 何时可以调用（前置条件）
 * · 能否并发 / 能否重入
 * · 生命周期限制（关闭后不能调用等）
 *
 * ## 错误
 * · 失败时抛什么；哪些可重试
 *
 * ## 不属于承诺的部分
 * · <列出实现细节，明确说明不要依赖>
 */
```

**最后一节（"不属于承诺的部分"）是最容易被省略、也最有价值的一节**——没有它，按 Hyrum 定律，使用者会依赖它能观察到的一切。

**模板二 · 破坏性改动检查表。** 改动前逐条问：

```
[ ] 有人在读返回值的这个字段吗？（删除字段 = 破坏性）
[ ] 有人在依赖这个默认值吗？（改默认值 = 隐蔽的破坏性）
[ ] 有人在解析错误信息吗？（改文案 = 隐蔽的破坏性）
[ ] 有人在依赖"它不会做 X"吗？（改副作用 = 最隐蔽的破坏性）
[ ] 有人在并发调用它吗？（收紧时序 = 最危险）
```

**模板三 · 审计发现记录。** 每条发现写四样：

```
症状 / 它属于哪一类（强度、演进、泄漏、缺口、证据）
后果（严重度 × 概率）
修法（补文档 / 加断言 / 限制能力 / 加兼容层）
判断依据（为什么是这个修法而不是别的）
```

### 5.3 三条容易踩的规则

**第一条：参数只能放宽，返回只能收紧。** 这条口诀覆盖了绝大多数兼容性判断。它的记忆方式是：**对调用方越宽松越安全**。

**第二条：写进契约前先问"我能不能长期保证它"。** 承诺的代价是永久的，而收益是当次的。所以判断标准是"长期"而不是"现在对不对"。

**第三条：当契约无法被检查时，用限制能力代替。** 这是 `sideEffect` 那个缺陷给出的通用解法——**做不到"验证它是真的"，就做到"即使是假的也没关系"**。

## L9 仍未解决（这一篇自己的缺陷）

| 缺陷 | 后果 | 修法 | 当初为什么这么写 |
|---|---|---|---|
| **三类承诺的框架没有覆盖"性能承诺"** | 使用者无法从契约上判断"这个方法预期是快还是慢"，而这在 harness 里很实际（工具可能跑几秒到几分钟） | 在行为承诺里单列一节"性能特征"，或引入一个"预期耗时量级"的声明 | 起初把性能归入了"实现细节"，但它实际上常被依赖（比如超时设置） |

| **对"契约的心理学"完全没有涉及** | 为什么人总是漏写时序承诺？这与认知偏差有关（可见的比不可见的更容易被想到），而本文没有利用这一点 | 补一节"为什么时序承诺最容易被漏"的认知解释 | 本篇定位是工程方法，但认知解释能显著提高"下次记得写"的概率 |
| **没有给出契约随时间的演化数据** | 不知道"一个接口平均多久改一次契约"，因而无法为"承诺周期"给出经验值 | 在真实项目里收集（比如统计 git 历史里接口文档的改动频率） | 需要真实数据，而 dsh-mini 还没有足够历史 |

### 问题升级练习

**模糊问题**：「我该怎么设计一个好的接口？」

**升级后的精确问题**：

> "好接口"至少有三个各自独立的标准：
> ① 使用者能只靠契约写对调用代码（**表达完整性**）；
> ② 实现者能自由改进而不破坏承诺（**承诺节制**）；
> ③ 契约本身能被机器部分验证（**可检查性**）。
> 这三个标准会互相冲突——表达越完整，承诺越多，可演进性越差。
> 它们之间的最优平衡点在哪里？是否取决于接口的使用者是谁
> （同一时刻的代码 / 未来的代码 / 第三方）？

**提升点说明**：原问题无法回答，因为"好"没有共同尺度。升级后的版本做了三件事。第一，把"好"拆成三个**会互相冲突**的标准（这是关键——如果三个标准不冲突，那这个问题就没有难度）。第二，指出冲突的存在，从而把问题从"怎么做到好"变成"怎么权衡"。第三，引入一个调节变量（使用者是谁），因为最优平衡点确实取决于它——这正好对应本篇区分的三种契约形态（面向实现、面向替换、面向未来）。

## L11 系统影响回溯

回看第 0.5 节的三个连锁影响，本篇给出了它们各自的具体形态与一处修正。

**连锁 1（契约写不清 → 每处调用方各自发明假设）** 的机制在 1.1.1 里被拆开：不是"有人写错了"，而是**接口没有给出答案，所以每个人自己给了一个**。而这个现象的量级在 L0.1 里做了估计：一个 20 模块的项目里可能有 300 个"只能靠猜"的点。

**连锁 2（实现细节进契约 → 失去演进能力）** 的机制在 1.4.3 里展开成了四类"隐蔽改动"，其中最有代表性的是**改副作用范围**——它改变的是调用方对"它不会做 X"的依赖，而没有任何签名变化。

**连锁 3（契约稳定性决定波及面形状）** 在 1.5.1 里被补完：**波及面的准确计算需要两张表的合取**——"谁依赖我"（1.3 教的）与"我承诺了什么、谁依赖了哪一条"（本篇教的）。只有前者会过度保守，只有后者会过度冒险。

**一处需要修正的预判**：0.5.3 里说"契约的稳定性决定了改动波及面的形状"。读完之后我会说得更准确：**决定波及面形状的不是"契约稳不稳定"，而是"承诺与能力的落差"**。L3.1.3 那个 `sideEffect` 的例子说明：一个稳定的契约（`sideEffect` 一直存在、语义一直没变）如果**它的承诺超出了系统的保证能力**，那么它制造的风险与"契约不稳定"是一样的。**换句话说，契约的风险有两个来源：变（不稳定）与虚（做不到）。** 后者更隐蔽，因为它不会在任何 diff 里出现。

**通向下一篇的桥。** 本篇讲完了"承诺什么、怎么改"。但它有一个隐含前提：**承诺的对象是"代码"**——调用方是同一时刻的代码，或者是未来的代码。而下一篇 `1.5 数据、状态与可逆性` 要处理一类更麻烦的对象：**承诺的对象是"数据"**。数据的特殊之处在于它不会因为你的代码改了而跟着改——**一份已经落盘的会话日志，会永远以写它那一刻的格式存在**。这就是为什么数据格式的破坏性变更比接口的破坏性变更更严重：前者不可逆，后者通常可以靠改调用方解决。

## 记忆锚点与复述练习

### 一、骨架：四块

```
   承诺什么 ──► 签名没说的 ──► 谁会因此动手 ──► 怎么安全地改
      ↓            ↓              ↓               ↓
   三类承诺      五项清单       两张表合取      四种手段
   1.1          1.2            1.5             1.6
```

只记一行就记这行：**承诺什么 → 签名没说的 → 谁会因此动手 → 怎么安全地改**。

### 二、情境绑定：当你……就想起……

| 当你…… | 立刻想起 |
|---|---|
| 要写一个新接口 | 三类承诺逐条问一遍（行为 / 时序 / 错误） |
| 看到一个只有签名没有注释的函数 | 五项清单：副作用、幂等、时序、错误、所有权 |
| 要改一个接口 | 先算两表合取（谁依赖哪条承诺 + 扇入闭包），再查破坏性分类表 |
| 不确定某行为算不算承诺 | 看三处证据（"保证"类词 / 测试 / 显式检查），都没有就不算——但按 Hyrum 定律它仍可能被依赖 |
| 想给接口加一个字段 | 问"它要成为承诺吗？"——不是就不该进接口 |
| 想加一个开关来兼容新旧 | 问"这个开关什么时候删"，答不出就改用兼容层 + 弃用标注 |
| 看到一个"声明了但没人验证"的字段 | 它是**信任型契约**；修法是限制能力，不是加校验 |
| 写测试断言一个返回对象 | 别用全等——那会锁死实现；断言承诺的字段 |
| 要加一个新的事件类型 | 想"可忽略吗"——不知道它会不会让派生出来的历史出错 |
| 看到一个奇怪的实现选择 | 构造反事实："如果不是这样会怎样"（C-02） |

### 三、主动回忆：闭卷回答（不要翻上面）

1. 三类承诺分别是什么？哪一类最容易被漏掉？
2. 前置条件与后置条件分别是谁的义务？这对调试有什么用处？
3. 签名表达不了的五件事是什么？
4. 破坏性改动的判断依据是什么？（注意：不是"改了什么"）
5. 四处"隐蔽的破坏性改动"分别是什么？
6. "参数只能放宽，返回只能收紧"——为什么？
7. 波及面的准确计算需要哪两张表？各缺一张会犯什么错？
8. 契约测试与全等断言的差别是什么？为什么后者会锁死实现？
9. 四种演进手段按代价从低到高是哪四个？
10. 什么是信任型契约？它和强制型契约的修法有什么根本不同？
11. 为什么事件格式的演进必须用版本化，而函数接口通常不用？
12. 深模块与浅模块的判据，用契约表面积怎么表述？

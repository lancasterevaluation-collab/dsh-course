# Part B · 诊断与可行动性（题目）

> 对应讲义：`4.4 诊断`。作答方式见 `../../../作业引导.md` 第七节。
>
> 把答案写进 `kit/answers/b-diagnosis.json`（从 `b-diagnosis.template.json` 复制）。

---

## 第一组：失败分类与候选（9 项）

对每一项给出三样：

1. `kind`：`error`（报错）| `silent`（跑完了而结果是错的）| `goal-miss`（没达成目标）；
2. `candidates`：**至少两个**说得通的原因，各带 `evidence`；
3. `evidence` 的取值：`correlation`（时间相关）| `counterfactual`（去掉它会变）| `reproducible`（同条件再现）。

**要求**：九项里**至少有一项**的候选带 `counterfactual` 或 `reproducible` 的证据——"全是相关性"说明没有做验证。

---

**f1.** 任务跑完了、没有任何异常，而事后的检查不通过。

**f2.** 一次工具调用抛出了异常，任务中止。

**f3.** 任务完成、检查也通过，而用户说"这不是我要的"。

**f4.** 一次模型调用超时，任务没有拿到结果。

**f5.** 执行的命令返回了非零退出码。

**f6.** 所有步骤都成功，而最终产物里缺少一个必需的文件。

**f7.** 任务在预算内正常结束，而没有达成目标。

**f8.** 一个工具返回了内容而没有任何错误标志，内容却是错的。

**f9.** 任务成功产出了文件，而文件的内容与上一次运行差异很大（超出预期）。

---

## 第二组：不可行动的结论（5 项）

下面五条都是"看起来完整、其实不可行动"的结论。对每一条给出：

- `rewritten`：**含一个可改对象**的结论；
- `targetKind`：改动对象属于哪一类（`prompt` | `threshold` | `tool-desc` | `skill-condition` | `config`）。

**`rewritten` 里不得出现「模型能力」或「用户表达」**（那两句正是不可行动的原型）。

**r1.** "根因是当前模型能力有限。"

**r2.** "用户没有把需求说清楚。"

**r3.** "外部服务不稳定。"

**r4.** "这段代码太复杂了。"

**r5.** "系统还需要进一步优化。"

## 判据与答案表（作答之后再看）

| 判据 | 权重 |
|---|---|
| 9 个失败分类正确 | 6 |
| 每个场景至少两个候选（含平凡候选） | 4 |
| 证据强度标注正确 | 2 |
| 5 条结论改写后含可改对象且类别正确 | 3 |

| id | kind | 说明 |
|---|---|---|
| f1 | silent | 没有报错而结果是错的——**这是数量最多的一类** |
| f2 | error | 有明确的异常 |
| f3 | goal-miss | 走到了最后而目标没达成 |
| f4 | error | 超时属于报错类（它中止了流程） |
| f5 | error | 非零退出码是明确的错误信号 |
| f6 | silent | 没有报错而产物不完整（检查能发现） |
| f7 | goal-miss | 预算内结束而目标未达 |
| f8 | silent | 工具"成功"而内容错——**最危险的一类** |
| f9 | silent | 看似正常而结果偏离预期（可能包含退化） |

**关于"平凡候选"**：每一项的候选里都应当包含一个平凡的（例如"我把数字看错了"、"这个任务本来就更难"、"那次运行恰好网络快"）。**排除平凡候选的顺序应当在机制候选之前**——因为多数现象的平凡解释是对的（讲义 4.4 的 1.5）。

**关于 r1 与 r2**：它们的共同形态是把原因放在"不可改的东西"上。改写的方向是**把它翻译成自己能改的对象**：

| 不可行动 | 可改写为 |
|---|---|
| 模型能力不足 | 拆小任务、加一步校验、提供示例（`prompt` 或 `config`） |
| 用户表达不清 | 在信息不足时主动提问（`prompt` 里的交互策略） |
| 外部服务不稳定 | 加超时与降级（`threshold` 或 `config`） |

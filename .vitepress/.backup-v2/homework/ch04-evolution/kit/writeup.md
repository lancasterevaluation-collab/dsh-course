# 设计说明（Part A–F · 学习进化）

> 这份文件是你自己的记录，不是给别人看的报告。**判分器检查它是否回答了下面四组问题**（非空且有实质内容），而不检查文风。
>
> 建议在**动手之前**先读一遍它——因为它列出了你在做的时候需要留意的东西。

---

## 一、三处设计取舍

对三个你实际做过的决定，写清：**你的选择、被放弃的替代方案、以及代价落在谁身上**。

参考的角度（任选，也可以写别的）：

- 某个边界条件你选择了"严格大于"还是"大于等于"，为什么；
- 某个函数你选择抛错还是返回一个特殊值，为什么；
- 某处你选择了"截断"还是"保留指针"，为什么；
- 某个判据你选择了"由实现保证"还是"由调用方保证"，为什么。

**格式建议**（一行一处，两到四行）：

```
取舍 1：<一句话说清选择>
  替代：<另一个方案>
  代价：<谁承担、承担什么>
```

（在这里写你的三处取舍）

## 二、最弱的一处

写清：**你的实现里最不可靠的一处是哪里，以及你在什么条件下会不信任它**。

这一项判的是**自知**，而不是完美。一个说"没有弱点"的说明会被判为无效——因为按契约的边界条件，这一卷的六个 Part 里必定有至少一处你没有百分百把握——**尤其是那几条"必须拒绝"的判据**。

参考的写法：

```
最弱之处：<哪个函数、哪一条不变量>
  条件：<出现什么情况时它可能不成立>
  后果：<如果它不成立，会发生什么>
  缓解：<你做了什么降低它的概率或影响>
```

（在这里写）

## 三、你自己构造过的一个边界输入

测试里已经有的边界不必重复。**写一个你自己想到的**，以及它暴露或验证了什么。

参考的角度：

- 一个长度恰好等于预算的字符串；
- 一个只有一条事件的日志；
- 一个时间戳顺序反常的调用（例如 `firstTokenAt < startedAt`）；
- 一个 `seq` 从 0 开始（而不是从 1）的日志；
- 一条包含特殊字符（换行、引号、反斜杠）的日志行；
- 一条与已有记忆高度相似的新候选（考验"先合并"）；
- 一个 `weight` 恰好落在门槛上的用户特征（考验边界）；
- 一个 `gain` 恰好等于两倍噪声的提议（考验门控的严格性）。

```
边界输入：<是什么>
  期望：<你认为应当发生什么>
  实际：<你的实现做了什么>
  结论：<一致/不一致，以及你怎么处理>
```

（在这里写）

## 四、你与判据的一次分歧（可选）

如果你认为某条判据不合理（例如 Part B 的后果描述被正则误伤），写在这里：**判据是什么、你的理由是什么、以及你认为更合适的判据是什么**。

**这一项不计分，但会被认真读**——因为判据本身也是设计，而参与设计讨论是这个作业的一部分。

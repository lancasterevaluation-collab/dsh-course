## 二、怎么跑判分

```powershell
cd D:\dsh-course\homework\ch01-judgment

node tests/run.mjs                                  # 全部，折算总分
node tests/run.mjs --only t4                        # 只跑某一项（前缀匹配）
node tests/run.mjs --verbose                        # 打印单项的完整输出
node tests/run.mjs --help                           # 看全部选项

node tests/t3-architecture.mjs --answers kit/answers/a3-architecture.json --verbose
node tests/t4-contract.mjs --answers kit/answers/a4-contract.json --verbose
node tests/t5-build.mjs                             # 构建题，每个用例跑 30 次
node grade/negative-check.mjs                       # 确认判分器本身有鉴别力
```

构建题换参考答案跑（确认判分器是好的）：

```powershell
$env:IMPL='../grade/memory.reference.mjs'; node tests/t5-build.mjs; Remove-Item Env:\IMPL
```

`IMPL` 的基准目录是 `tests/`，所以写 `../grade/...` 而不是 `grade/...`。参考答案应当稳定拿到满分。如果拿不到，问题在判分器而不在你的实现。

## 五、一个已知的判分缺陷

这一节记录 `t3-architecture.mjs` 的一个真实问题。它不是实现缺陷，而是"用集合相等来判分"这个方法本身的边界，而它恰好可以作为 1.4 讲义的补充例子。

`t3` 的四道小题（扇出清单、扇入清单、扇入的值依赖子集、关键导出名）标准答案都是空集合，因为目标模块在这个判分口径下确实没有扇出。后果是：把这四栏留成 `[]`（也就是完全没做）会被判为正确，因为集合相等里空集等于空集——一份完全空白的答卷在 `t3` 上能拿到大约 28 分。

这不是靠"更仔细地写判分器"能解决的，因为判分器无从知道你是判断出它为空，还是根本没看。它需要的是一条额外信息：说明为什么是空。这个缺陷的一般形式是——**一个检查的鉴别力取决于它的答案空间有多大**。当正确答案退化到空集时，检查就失去了区分对错的能力，而它表面上仍然在工作。

它与 1.4 讲义里的那个概念是同一件事：讲义管它叫信任型契约，一种看起来在约束、实际上无法被验证的声明。这里的判分器就是一条信任型的检查。

**你应该怎么处理它**：做题时把"为什么这里没有扇出"写进 `kit/writeup.md`。分数不会因此变化，但那正是要你知道的事情——有些正确性必须由人补充说明，工具无法代劳。也正因如此，`t3` 的分数不能单独作为"这一节做完了"的判据，要看哪些小题由红变绿。

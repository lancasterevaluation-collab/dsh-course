## A 组总览：这一组真正在考什么

A 组 12 道题问的都是"这个改动的破坏性"，但如果你的答案是靠"改了什么"来判断的，**你会在这 12 道题里自相矛盾**。

**这一组真正考的是一条判据**，而它的官方表述来自 Semantic Versioning 规范：

> **【规范】** Semantic Versioning 2.0.0，规则 8：
> *"Major version X (X.y.z | X > 0) MUST be incremented if any **backward incompatible changes** are introduced to the **public API**."*
> 主版本号必须在向**公开 API** 引入**向后不兼容的改动**时提升。

这句话有三个要点，后面 12 道题都会用到：

**第一，判据的对象是"公开 API 的承诺"，不是代码改动的大小。** 所以"改了一个字母"可以是破坏性的，而"增加了一整个函数"可以不是。

**第二，规范只管"公开 API"。** 内部重构不算。但——

**第三，实际依赖面比公开 API 大**。这就是 Hyrum 定律要说的：

> **【书籍】** Hyrum Wright 的原话（其本人称之为 *The Law of Implicit Interfaces*，由 Titus Winters 命名，收录于 *Software Engineering at Google* 第 1 章）：
> *"Given enough use, there is no such thing as a private implementation."*
> 使用得足够多时，就不存在"私有实现"这回事。

《Software Engineering at Google》用它解释了一个现象：**如果程序员能够依赖哈希表的遍历顺序，他们就一定会依赖**——所以有些语言故意把哈希顺序随机化，从根上断掉这种依赖。

**把这两条合起来，就得到 A 组使用的判据**：

> **一个改动是否破坏性，取决于它是否让"依赖了被改掉那部分行为"的代码失败。**
> 判断时先问"公开 API 承不承诺它"（SemVer 的口径），再问"实际有没有人依赖它"（Hyrum 的口径）。

## A1 · 增加一个【必填】参数

### 名词解释

**"必填参数"**：调用时必须提供的参数。在 TypeScript 里，没有默认值、也没有 `?` 标注的参数就是必填的。

**"破坏性变更"**：这个词来自 Semantic Versioning（版本号规范）。该规范规定版本号是 `主.次.补` 三段，其中**主版本号**在引入不兼容改动时提升。所以"破坏性"是一个**关于承诺的概念**，不是关于代码规模的概念。

### 答案

**破坏性。**

### 为什么（这一条可以被连续追问三层）

**第一层：为什么加必填参数是不兼容的？**

因为所有已有调用点都少传了一个参数。在 TypeScript 下这会直接编译报错；在 JavaScript 等动态语言下，它会在运行时得到 `undefined`，然后可能在很远的地方出问题。

**追问："那如果第一次调用本来就会传这个参数呢？"**
——那也不改变它是破坏性的。**判断依据不是"我这次的调用点"，而是"所有依赖原有契约的代码"**。SemVer 规范说的是"向公开 API 引入不兼容改动"，而不是"向我自己的调用点引入"。

**第二层：为什么"编译器报错"就算破坏？**

因为 SemVer 规范的措辞是 *backward incompatible changes*（向后不兼容的改动），而"已有代码无法再编译/运行"是不兼容最典型的形式。

**追问："那如果没有人调用它呢？"**
——那它就**不是**破坏性变更。SemVer 判断的是"是否引入了不兼容改动"，而如果不存在依赖方，就没有东西会因它而失败。
**这一问正好说明判据的核心：看的不是"改了什么"，而是"谁依赖了它"。** 这也是为什么后面 A12（改默认值）比 A1 更危险——A1 的依赖方是"所有调用点"，一眼可见；A12 的依赖方是"没写那行参数的调用点"，看不见。

**第三层：那为什么有些团队主张"任何签名变化都算破坏"？**

因为 Hyrum 定律：**实际被依赖的行为，比公开 API 承诺的更多**。

**【书籍】** *Software Engineering at Google* 里给出的机制是：用户会依赖实现泄漏出来的细节。所以一个签名变化即使"逻辑上兼容"，也可能因为某个调用方依赖了别的东西而炸掉。
工业界的例子可以在 **React 的版本政策**里看到——它明确列出**不做主版本提升**的情形（开发期警告、`unstable_` 前缀的 API、alpha/canary 构建、未文档化的内部实现），反过来就是在说：**除了这些，其他变化都可能被视为破坏性**。

| 材料 | 具体内容 | 等级 |
|---|---|---|
| Semantic Versioning 2.0.0 | 规则 8：主版本号在引入向后不兼容的公开 API 改动时提升 | 【规范】 |
| *Software Engineering at Google*, Ch. 1 | Hyrum 定律的原文、命名来源、哈希顺序的例子 | 【书籍】 |
| React Versioning Policy | 明确列举"不算破坏性"的四类情形 | 【规范】（该项目的官方政策） |

### 常见错误答案

**错答一："不算破坏，因为我只是加东西。"**
为什么错：把"增加"等同于"安全"。A1 与 A8 都是"增加"，都是破坏性的。**这个直觉错误在真实工作里非常常见**，也是面试官爱设的坑。

**错答二："看情况。"**
为什么错：面试里"看情况"必须紧跟"看什么情况"。只说"看情况"等于没答——**它暴露的是你没有判据**。

## A2 · 增加一个【可选】参数

### 名词解释

**"可选参数"**：调用时可以不提供的参数。TypeScript 里用 `?` 或默认值表达。

### 答案

**安全——但有一个必须补上的前提。**

### 为什么

**第一层：为什么它是安全的？**

因为已有调用点不传这个参数时，仍然合法；而且如果实现得当，行为也与改动前一致。

**第二层：那个"必须补上的前提"是什么？**

**新参数的默认值，必须让"不传它"时的行为与改动前完全一致。**

这是 A 组里最容易失分的地方。举例：你给 `run_command` 加一个可选参数 `timeoutMs`，默认值设为 30 秒。但改动前，这个工具**根本没有超时**（也就是实际无限等）。那么"默认 30 秒"就**改变了不传参时的行为**——原来会一直等的命令，现在 30 秒后被杀掉。

**这时候，这个改动就不是 A2 而是 A12。**

**追问："那我怎么判断默认值有没有改变行为？"**
——问一个具体问题：**"改动前，不传这个参数会发生什么？改动后呢？"** 如果两个答案不同，它就改变了行为。

**第三层：为什么说"安全的改动"也可能出问题？**

因为 Hyrum 定律。即使你的改动在语义上完全兼容，只要**有人依赖了某个可观察行为**，它就可能出事。

**【经验】** 一个具体的形态是：消费者用 `Object.keys()` 遍历返回对象的键。此时你增加一个字段，那个遍历就会多处理一次。**这一条我给不出权威出处，它属于通行实践中的观察**——但它可以从 Hyrum 定律推出来：键的集合是"可观察行为"的一部分。

**应对办法是把它写进契约**：明确声明"返回对象可能新增字段，消费者不应假设字段集合固定"。

### 参考材料

| 材料 | 具体内容 | 等级 |
|---|---|---|
| Semantic Versioning 2.0.0 | MINOR 版本号的定义："backwards-compatible manner"（向后兼容的方式） | 【规范】 |
| *Software Engineering at Google*, Ch. 1 | Hyrum 定律：可观察行为会被依赖 | 【书籍】 |

### 常见错误答案

**错答："可选参数一定安全。"**
为什么错：漏掉了"默认值是否改变行为"这一层。**面试官问 A2 时，往往就是在等你说出这一层。**

## A3 · 从返回对象里【删除】一个字段

### 答案

**破坏性。**

### 为什么

**第一层：为什么它是破坏性的？**

读该字段的调用方会拿到 `undefined`。在 TypeScript 下，如果开启了严格空检查（`strictNullChecks`），这会编译报错；未开启时，它会一路带着 `undefined` 跑到某个下游逻辑才炸。

**第二层：为什么说它"比想象中危险"？**

因为它**常常不会立刻报错**。

这里可以用 TypeScript 的官方设计立场来解释：**【规范】** TypeScript 官方明确声明 **"soundness is not a goal"**（可靠性不是它的目标，见其 Design Non-Goals）。也就是说，类型系统**不保证**运行时不会出现它没预料到的值。所以"删了字段但编译通过"是完全可能的——**编译通过不等于运行正确**。

**追问："那怎么确认没人用这个字段？"**

三步，缺一不可：
1. **全仓搜索字段名**（找显式使用）；
2. **开启严格空检查再编译**（找类型层面的依赖）；
3. **搜索序列化边界**——因为字段可能在 `JSON.stringify` 之后被别处消费，而那处消费不出现字段名。

**【经验】** 第 3 步是我从实践中总结的，没有权威出处。它的依据是：序列化会切断静态可追踪性。**这条请自行判断是否适用于你的项目。**

### 参考材料

| 材料 | 具体内容 | 等级 |
|---|---|---|
| TypeScript Design Non-Goals | 官方明确"soundness is not a goal" | 【规范】 |
| Semantic Versioning 2.0.0 | 主版本号规则适用于"移除公开 API 的一部分"（删除字段属于此类） | 【规范】 |

### 常见错误答案

**错答："我先搜一下，没人用就删。"**
为什么错：搜索的结论经常不完整（见上面第二步、第三步）。**更安全的做法不是"证明没人用"，而是"先标注弃用，保留一个版本，再删"。**

## A4 · 给返回对象【增加】一个字段

### 答案

**安全**（但见下面的一个重要限定）。

### 为什么

**第一层：为什么它是安全的？**

多给一个字段，不破坏任何**已承诺**的东西——读旧字段的代码照常工作。

**第二层：那什么情况下它会"看起来不安全"？**

当有人做了**全等断言**时。举例：测试里写 `expect(result).toEqual({ a: 1, b: 2 })`，你多了一个字段 `c`，这个测试就挂了。

**关键判断**：**这不算契约被破坏，而是测试锁死了实现。**

为什么这么说？因为"返回对象恰好只有这两个字段"从来不是承诺——它只是当前实现的样子。

**追问："那怎么改这个测试？"**
——把全等断言改成逐字段断言：分别断言 `a` 与 `b` 的值。这样它断言的才是**承诺**，而不是实现。

**【经验】** "契约测试 vs 全等断言"这个提法是我从实践中归纳的；我**没有找到它作为固定术语的权威定义**。但它背后的道理有出处：测试应该断言承诺，而承诺的定义来自 SemVer 的"public API"概念。

**第三层：Hyrum 定律在这里怎么用？**

即使"多一个字段"是安全的，**消费者仍可能依赖字段集合**（例如遍历所有键）。所以正确做法是**双管齐下**：代码上安全，文档上声明（"返回对象可能新增字段"）。

## A5 · 把参数允许的类型【放宽】（string → string | number）

### 名词解释（这一题必须先把名词讲清）

这一题背后是类型系统里的**方差（variance）**概念，它是整组里最需要理解原理的一题。

**方差**说的是：当一个类型 `A` 是 `B` 的子类型（`A` 能用在 `B` 能用的地方）时，`F<A>` 与 `F<B>` 之间是什么关系。分三种：

- **协变（covariant）**：`F<A>` 也是 `F<B>` 的子类型（方向相同）；
- **逆变（contravariant）**：方向相反；
- **双变（bivariant）**：两个方向都行（更宽松，但不安全）。

**为什么函数参数是逆变、返回值是协变？** 用一句话说：**函数对参数是"接受"，对返回值是"给出"**。接受得越宽，能用它的地方越多；给出得越具体，能满足的场景越多。

### 答案

**安全。**

### 为什么（有官方文档的明文规定）

**【规范】** TypeScript 2.6 的官方 release notes 有一段明确的表述与示例：

> *"Under `strictFunctionTypes`, function type parameter positions are checked **contravariantly** instead of bivariantly."*
> 在 `strictFunctionTypes` 下，函数类型参数位置按**逆变**检查，而不是按双变。

官方给的例子是（`Animal` 是 `Dog` 与 `Cat` 的父类型）：

```ts
declare let f1: (x: Animal) => void
declare let f2: (x: Dog) => void
f1 = f2   // 报错（参数变窄，不允许）
f2 = f1   // 通过（参数变宽，允许）
```

**把这个规则翻译成本题的场景**：

- 你把一个函数**参数类型放宽**（原来只接受 `Dog`，现在接受 `Animal`）；
- 那么原来能用的调用（传 `Dog`）**仍然能用**——因为 `Dog` 是 `Animal` 的一部分；
- 所以是**安全**的。

反过来（A6）把参数收紧，就对应官方示例里的 `f1 = f2` ——**报错**。

**追问："为什么参数方向是反的？"**
——直觉解释：**一个能接受更多东西的函数，可以替代一个只接受少数东西的函数**。就像"能修所有车的人"可以顶替"只修自行车的人"，反过来不行。这个解释只是帮助记忆，**准确的规则以官方文档为准**。

**追问："那 `strictFunctionTypes` 没开的时候呢？"**
——那时参数是**双变**的，也就是两个方向都能赋值。官方明确说这是**故意放宽**的：

**【规范】** TypeScript 的官方 FAQ 解释了原因：如果把参数强制成逆变，`Dog[]` 就不能赋值给 `Animal[]` 了——因为 `Array<T>` 的 `push` 方法**接受**一个 `T`。而"`Dog[]` 能用在哪里 `Animal[]` 能用的地方"是绝大多数代码依赖的行为。官方原话是这是一个 **correctness trade-off**（正确性上的取舍）。

**这一条非常重要**：它说明"参数严格逆变"是**更正确但更不便**的规则，TypeScript 为了可用性做了妥协——**所以你在不同语言里看到的规则可能不同**。

| TypeScript 2.6 Release Notes | `strictFunctionTypes`；参数按逆变检查；`f1 = f2` 报错、`f2 = f1` 通过的示例 | 【规范】 |

## A6 · 把参数允许的类型【收紧】

### 答案

**破坏性。**

### 为什么

**第一层：用方差规则解释。**

这就是 A5 里官方示例的反面：`f1 = f2` 会报错。因为原来传 `Dog` 的调用方，现在面对一个"只接受 `Dog`"（或更窄类型）的函数没问题，但**原来传 `Animal` 中其他子类型的调用方会失败**。

**第二层：那是不是"收紧参数"永远错？**

不是。要区分**你的目的**。

**【经验】** 如果你的目的是"拒绝非法输入"，那通常有更好的做法——**放宽参数类型但加强运行时校验**：接受更宽的类型，对不合法的情况给出明确的错误信息。这样既不破坏调用方，又达到了防错的目的。

**为什么这个做法更好？** 因为它把一个**编译期破坏**换成了一个**运行期错误**——前者要改所有调用方，后者只是多一个错误分支。

**【经验】** 上面这条我给不出权威出处，它是通行实践中的判断。**如果你要在面试里用它，建议说明它是一条实践建议而非规范要求。**

| 材料 | 具体内容 | 等级 |

| TypeScript 2.6 Release Notes | 与 A5 相同，方向相反 | 【规范】 |

## A7 · 把返回类型的精度【收紧】（string → "a" | "b"）

### 名词解释

**"精度收紧"** 指返回的类型从更宽变成更窄。"`"a" | "b"`"是 TypeScript 的**字面量联合类型**——它表示"这个值只能是这两个字符串之一"。

### 答案

**安全。**

### 为什么

**用协变规则解释。** 返回值方向是**协变**的：如果 `T` 是 `U` 的子类型，那么 `() => T` 可以赋值给 `() => U`。

- 原来返回 `string`，现在返回 `"a" | "b"`——后者**是前者的一部分**（`"a" | "b"` ⊂ `string`）；
- 所以调用方原来能用 `string` 做的所有事，现在仍然能做；
- 而且是**更强**的保证。

**追问："那会不会有人用了 `switch` 穷尽检查？"**
——那反而是受益的：原来 `string` 需要默认分支，现在 `"a" | "b"` 可以穷尽。**所以收紧返回值不是破坏，而是增强。**

**【规范】** 这一条与官方文档是一致的：TypeScript 的 type compatibility 文档明确说明函数类型与其返回类型是**协变**的。

### 参考材料

| 材料 | 具体内容 | 等级 |
|---|---|---|
| TypeScript Handbook, Type Compatibility | "Function or method types co-vary with their return types" | 【规范】 |

## A8 · 把返回类型的精度【放宽】

### 答案

**破坏性。**

### 为什么

**第一层：用协变的方向解释。**

原来调用方可以依赖"返回值一定是 `"a"` 或 `"b"`"，现在它可能拿到别的值。**任何穷尽处理（`switch` 无默认分支、`assertNever` 之类的检查）都会失效**，而未加默认分支的地方会在运行时拿到未处理的值。

**第二层：为什么它容易被误判为安全？**

因为它的措辞是"放宽"，而"放宽"在直觉上是"更自由、更安全"。**但在返回位置，方向是相反的**——放宽返回意味着**削弱保证**。

**这是一道很能区分理解深度的题**：如果只说"破坏了"，说明你可能记住了结论；如果说"因为返回值是协变位置，放宽意味着削弱了对调用方的保证"，说明你理解**为什么**。

**追问："如果只是增加了一种可能的返回值呢？"**
——那也是放宽，也是破坏性的。它和 A1（加必填参数）是同一类思维陷阱：**"增加"不等于"安全"，要看增加在哪个位置。**

### 参考材料

| 材料 | 具体内容 | 等级 |
|---|---|---|
| TypeScript Handbook, Type Compatibility | 返回类型协变——放宽即削弱保证 | 【规范】 |

## A9 · 把函数从同步改为异步

### 答案

**破坏性（波及全部调用方）。**

### 为什么

**第一层：这是哪一类承诺变了？**

它变的是**时序承诺**——从"调用即完成"变成"调用后需要等待结果"。前面八题讲的大多是**类型层面**的兼容性（协变/逆变），而这一题**类型可能仍然通过**（比如返回 `Promise<string>`，而调用方没检查类型的话不会报错）。

**【经验】** 这里我要给出一个**不确定**的标注：JavaScript 里"返回 Promise 而调用方没 await"会不会报错，取决于静态类型检查的严格程度。**我没有找到权威文档明确规定这一点**，所以我不断言——但可以确定的是：**"没报错"不等于"行为正确"**，因为调用方拿到的是 Promise 对象而不是值。

**第二层：为什么说"波及全部调用方"？**

因为每一个调用点都必须改成 `await` 或回调形式。这正是 SemVer 意义上的 *backward incompatible change*。

**第三层：安全的做法是什么？**

**加一个新函数，而不是改旧的。** 例如 `xxx` 保留（内部同步实现），新增 `xxxAsync`。

**追问："为什么不直接把旧函数改成返回 Promise，然后在文档里说明？"**
——因为旧代码会拿到 Promise 而它以为拿到的是值。**"文档里说明"不能阻止代码出错**，这是契约问题不是沟通问题。

### 参考材料

| 材料 | 具体内容 | 等级 |
|---|---|---|
| Semantic Versioning 2.0.0 | 不兼容改动须提升主版本 | 【规范】 |
| （JavaScript 具体报错行为） | **我不确定，故不写** | 【不确定】 |

## A10 · 把函数从"不可重入"改为"可重入"

### 名词解释

**重入（reentrancy）**：一个函数在执行过程中，又被再次调用（例如在它触发的回调里再调它）。**可重入**意味着这样调用是安全的。

### 答案

**安全。**

### 为什么

**第一层：这是放宽时序承诺。**

原本调用方必须避免重入，现在它**可以**重入了。已有代码本来就遵守旧限制，所以不会失败——**放宽承诺不会让任何人失败**，这与 A5（放宽参数）是同一条原则。

**第二层：这个"安全"有一个前提。**

**前提是：实现真的做到可重入。**

如果实现里有共享的可变状态（比如一个实例字段被两次调用同时改写），那么声称"可重入"而实际不是，问题就变成了另一种：

**这条承诺变成了一个没有验证机制的声明。** 我在正文里把这类承诺叫做**信任型契约**（声明了但框架无法检查）。

**【经验】** "信任型契约"这个术语是我在正文里自己起的名字，用于描述"声明与能力脱节"的现象。**它不是标准术语**——如果你在面试里用它，建议同时用一句话解释它的意思，而不要假设对方知道。

**追问："那要真正保证可重入，需要做什么？"**
——要么让实现无状态（所有状态通过参数传入），要么用显式的机制保护共享状态（锁、或每次调用创建独立上下文）。**具体用哪种，取决于语言的并发模型**——这一条我给不出跨语言统一的权威答案。

### 参考材料

| 材料 | 具体内容 | 等级 |
|---|---|---|
| Semantic Versioning 2.0.0 | 放宽兼容（MINOR） | 【规范】 |
| （"信任型契约"术语） | **非标准术语，我在正文中自定义** | 【经验】 |

## A11 · 把函数从"可并发调用"改为"不可并发调用"

### 答案

**破坏性——而且是 A 组里最危险的一类。**

### 为什么

**第一层：它是收紧时序承诺。**

原来可以并发调用，现在不行了。所有并发调用方都可能出问题。

**第二层：为什么说它"最危险"？**

因为**类型系统与测试都很难抓住它**。

- **类型系统抓不住**：Java 的 `synchronized`、TypeScript 的类型都**不表达**"这个函数能不能并发调用"。它不是类型的一部分。
- **测试常常抓不住**：单线程、顺序执行的测试全部通过。而问题只在并发时出现——**且往往是偶发的**。

**【经验】** 关于"测试抓不住并发问题"这一点，业界有大量共识（参见各语言的并发测试实践），但我**没有找到一条可以引用的、权威的量化结论**（比如"并发 bug 中有多少比例能被单元测试发现"）。所以我只陈述"很难抓"，不给出数字。

**第三层：那怎么保证没破坏并发调用方？**

**只能靠主动排查**，三个动作：
1. **搜索并发调用点**：`Promise.all`、`for await`、worker、定时器回调、事件处理器；
2. **针对它们补并发测试**（这是唯一能验证的方式）；
3. **如果找不到并发调用点**，也要在契约里写清"当前不是并发安全的"——**避免未来有人假设它可以**。

**追问："那如果我把实现改成并发安全呢？"**
——那就回到 A10 的情形：**放宽承诺是安全的**，但需要实现真的做到。

### 参考材料

| 材料 | 具体内容 | 等级 |
|---|---|---|
| Semantic Versioning 2.0.0 | 收紧承诺属于不兼容改动 | 【规范】 |
| （并发 bug 的测试可检出率） | **我没有可靠数据，故不给数字** | 【不确定】 |

## A12 · 把默认超时从 30 秒改为 60 秒

### 答案

**破坏性——而且是最隐蔽的一类。**

### 为什么

**第一层：它改变了什么？**

改变了**所有没有显式传这个参数的调用点**的行为。它们看起来完全正常：签名没变、编译不报错、多数测试也不会失败。

**追问："那它算不算破坏性？"**
——算。因为那批调用点**依赖了旧的默认值**（不管它们是否意识到）。SemVer 的口径是"向后不兼容的公开 API 改动"，而**默认值是公开 API 行为的一部分**。

工业界有一份明确列出了这类判断的清单：

**【规范】** typescript-eslint 的版本政策明确写着：**删除或重命名选项、规则是破坏性的；改变默认值是破坏性的；增加选项或规则则不是。**
这直接支持了 A12 的答案——**改默认值被明确列为破坏性**。

**第二层：为什么说它"最隐蔽"？**

因为它符合一个特定的模式：**改动是真实的，但它在代码差异里不可见**。

- A1（加必填参数）的破坏性在 diff 里能看见——有人加了一个参数；
- A12 的破坏性看不见——**没有任何一行代码被改，只有一行的某个字符变了**，而受影响的是**那些什么都没写的地方**。

**追问："那怎么处理它？"**
——按行为变更处理：先确认有多少调用点依赖它、给出通知与迁移期。**而不是直接改。**

**第三层：这一题为什么放在最后？**

因为它把整组的判据收束到一个反直觉的结论：

> **"改了什么"几乎不重要，"谁依赖了它"才是判据。**

一个看起来很大的改动（加整个函数）可以完全无害；一个看起来微不足道的改动（改一个数字）可以是破坏性的。**这正是 A 组 12 道题要反复训练的那一件事。**

| Semantic Versioning 2.0.0 | 不兼容的公开 API 行为改动 | 【规范】 |

## 一、先读这一节：这份作业为什么这样设计

大多数人做作业的方式是"从头往下读，遇到不会的再回头找"。这份文档不是那样组织的，原因有二：**它要训练的不是记忆，是判断**；而判断能力有一个特点——**它只在你自己做出错误判断并被纠正时才增长**。所以这份文档里最重要的部分不是"步骤"，而是每一处的「你会怎么想错」。

### 1.1 你会在哪里卡住，而那是我故意留的

先说清三件你会遇到的事，这样它们发生时你不会以为是自己不行。

**第一，任务 1 的第一步会让你不舒服。** 我要求你先不看任何文档，只用 `rg` 和源码把 `kernel/session.ts` 的结构读出来。你会觉得"有文档为什么不看"，而且很可能读得不完整。**这正是设计的意图**：看文档时你学到的是"这个项目怎么设计的"，不看文档时你学到的是"如何从代码里把设计读出来"。前者让你了解一个项目，后者让你能面对任何项目。两者都需要，但顺序不能反——如果先看文档，你会在潜意识里把"读懂"定义为"找到那段说明"，而这个定义会在你面对没有文档的代码时立刻失效。

**第二，判分器会给你一些"看起来不公平"的扣分。** 比如你答对了 10 个依赖但多写了 2 个，得到的不是 10/12 而是 10/(12+2)。这是刻意的，理由在任务 2 里讲——它对应一个真实的能力：**区分"某个名字出现了"与"某个行为被依赖了"**。

**第三，你会想要"直接看答案"。** `grade/answers.example.json` 就在那里，随时可看。我不阻止你，但请等到做完任务 2 再看，因为这里有一个认知上的机制：**一旦你见过正确答案，"我本来也能想到"的感觉会覆盖掉"我为什么没想到"这个问题**——而后者才是这份作业要给你的东西。

### 1.2 三个原理，它们决定了这份文档的写法

我没有凭感觉设计引导，下面三条是它每个部分的依据。知道它们，你也能自己设计学习方法。

**认知负荷（Cognitive Load Theory）** 把学习时的心理负担分成三种：任务本身的难度（内在）、呈现方式带来的难度（外在）、以及用于构建理解的难度（相关）。关键结论是：**只有第三种带来学习，前两种都在消耗你的注意力预算**。所以 `kit/tools/` 里放了预置的依赖分析工具——手工数 61 个文件的 import 是纯粹的**外在负荷**，它不会让你更懂架构，只会让你更累。而"判断哪些依赖是必要的、哪些热点值得保留"是**相关负荷**，那才是这份作业要求你做的。

**最近发展区与脚手架（ZPD / Scaffolding）**：当任务难度刚好超出你当前能力一点时，学习效率最高。所以这份文档在每个任务里都分成几个阶段，每个阶段末尾写「你应该看到了什么」——那是**即时反馈**，用来让你随时知道自己在不在正轨上。等你做第二个、第三个模块时，这些提示会更少：**脚手架是应该逐步拆除的**。

**生成效应（Generation Effect）**：自己生成的信息比读到的记得牢得多。所以这份文档几乎不给结论，而是反复说"这里你要生成什么"。最明显的例子是任务 1 的不变量那一栏——我不会告诉你答案，只会告诉你**去哪里找**（断言、测试、文档三处），以及**什么情况下应当警惕**（三类证据都没有）。

### 1.3 怎么用这份文档

按你的状态选一种，不要按顺序通读。

**如果你现在要开始动手**：直接跳到 §3（环境准备），然后进 §4 的任务 1。每个任务的「你会怎么想错」在你**动手之前**先读一遍。

**如果你已经卡住了**：跳到 §4 里你正在做的那个任务，读「你会怎么想错」那一小节。那七条覆盖了实测中出现频率最高的几类错误。

**如果你做完了想检查质量**：跳到 §7 与 §8，那里有"做完了但做得浅"的判别方法。

## 四、任务逐个引导

### 任务 1 · 模块卡片（30 分）

#### 为什么做这个

因为"看懂一个模块"这件事，你的直觉是错的。直觉告诉你"看懂 = 从第一行读到最后一行"，而真正可用的"看懂"是四个具体问题的答案：它**承诺**什么、它**维持**什么关系、它**不管**什么、它的状态**归谁管**。这四个问题构成后面所有工作的基础——任务 2 要用它们判断波及面，任务 4 要用它们区分调用链与事件链。

`kernel/session.ts` 被选中，原因很具体：**它的难度分散在四个方向上**。它承诺的是事件追加语义，维持的是"模型可见 ⟺ 日志可重建"，不管的是"该 append 什么"，而它的状态归 `Session` 实例所有。如果你只用了"读流程"这一种方法，你只能得到第一个问题的答案。

#### 你会怎么想错

**错误一：把类型导入算作依赖。** 你会打开 `session.ts`，看到三行 import，其中一行是 `import type { ChatMessage, LLMUsage, ToolCall } from './llm.ts'`，然后很可能把它算进扇出。**我实测时就是这么错的**，而且错了两次——第一次把类型算进扇出，得到 Ce=1；修掉之后又忘了扇入侧也要区分。正确的口径来自一个更基本的问题：**这个依赖在运行时会存在吗？** `import type` 编译后被完全擦除，所以它不构成运行时依赖；但它在**改结构时**仍然波及——这就是为什么扇入要分"值 / 仅类型"两组，而扇出只算值。

**错误二：只搜 `src/kernel/`，漏掉大半个仓库。** 你会很自然地只在自己关注的目录里搜。但 `session.ts` 的扇入是 **16 个文件**，其中 7 个在 `demos/`。用 `rg -l "from '.*session" src/` 搜全仓，一个都别漏。

**错误三：认为"找不出没有证据的不变量"说明代码写得好。** 恰恰相反。**如果你一条标红项都没有，通常说明你只记录了文档里已经写明的那些**——那是在抄录，不是在提取。

#### 阶段 A：建立形状（不看文档）

```powershell
cd D:\dsh-mini
rg -n "^import" src/kernel/session.ts      # 它的依赖
rg -l "from '.*session" src/               # 谁依赖它
rg -n "^export" src/kernel/session.ts      # 它的公开面
```

**你应该看到了什么**：`session.ts` 有 507 行、6 个值导出（1 个常量、1 个类、4 个函数）、16 个引用它的文件。这一阶段**不要**去读实现——你的目标是形状，不是细节。

**停下来想一想**：看到"16 个文件引用它，但其中只有 7 个用值"时，你的第一反应是什么？如果我要改这个文件的行为，我该看哪 7 个还是哪 16 个？——这个答案会直接决定你在任务 2 里的判断质量。

#### 阶段 B：算出来，而不是猜出来

```powershell
node tools/depgraph.mjs --repo D:\dsh-mini --module kernel/session.ts
```

**你应该看到了什么**：工具分两段列出依赖者——「值依赖者」用 `←`、「仅类型依赖者」用 `⇢`。它给原始数据，但**不会告诉你哪一段该填进 `fanInValue`**。这个映射要你自己做。

**注意**：`kit/answers.json` 里每个槽旁边都有 `_提示` 字段，说明它要填什么、以及为什么。先读提示再填，能省掉大量试错。

#### 阶段 C：与文档核对，并做自检

现在才读文档：`session.ts` 的头部注释（很长，值得逐段读）与 `docs/07-session.md`。把"读了文档才知道"的东西记进 `writeup.md` 的第一节。

**自检：你现在应该能回答**

- 这个模块**保证**什么？（一句话，不要用"它做了什么"这种句式）
- 它的哪一条约束是**跨函数**的？（提示：想想 `seq` 与事件数组长度的关系）
- 如果我在它内部加一个方法，属于"越界"还是"合理"？依据是什么？

如果第三个问题答不出，说明"边界约束"那一栏你还没填——回到阶段 A 看头部注释里"它不做……"这类句子。

**测试**：

```powershell
node tools/check.mjs --repo D:\dsh-mini --verbose
```

**第一次跑可以加 `--verbose`**（列出全部标准答案项，帮你校准颗粒度）。**任务 2 之后就不该再加了**——那时你应该能不看答案判断自己对不对。

### 任务 2 · 波及推演（40 分，全篇核心）

#### 为什么做这个

因为这是"读代码"与"做产品"之间唯一的桥梁。你可以很懂代码，但如果无法回答"这个需求要改几处、会不会出事"，你就无法参与任何成本讨论——你只能问"大概要多久"，然后接受一个无法验证的数字。

这个任务给的需求（给 `run_command` 加超时）**看起来很小**，这正是它被选中的原因：**它是"看起来半天就能做完"的典型，而实测中它的波及面跨了四个层次**。

#### 你会怎么想错

**错误四（最重要的一个）：只搜代码，漏掉"不会报错"的地方。** 你会搜 `run_command`，在 `src/` 下找到几处，然后觉得差不多了。但它在 `modes/` 与 `prompts/` 下还有三处，而**这三处改了不会报错、不改也不会报错**——它们只是让模型看到一个不存在的能力，或者看不到一个存在的能力。这类"静默失效"的位置是这份作业里分值最高的部分（10 分），因为**它们是真实项目里最容易积累的问题**。

**错误五：把"提到"当成"依赖"。** `apps/verify.ts` 里也出现了 `run_command`（在验收期望里）。要把它算进波及面吗？判断标准是一个提问：**如果这个行为变了，这处代码会出错吗？** 验收期望里的字符串不会因为工具多了一个参数而出错——所以它不属于"必须同步修改"，但它是你**需要知道**的地方。这个区分就是判分器用 Jaccard 式判分的原因。

**错误六：跳过"为什么"直接列清单。** 你会想快速凑齐五项事实然后跑判分器。但这份作业的真正产出是 `writeup.md` 里的那段结论——**成本主要落在哪一类工作上、最可能出意外的是哪一步**。后面那个问题的答案藏在实现里：去看 `command-tool.ts` 现在怎么处理子进程。

#### 阶段 A：先问结构，再搜关键字

不要一上来搜 `timeout`。先回答三个问题（写进 `writeup.md`）：这个工具的**定义**在哪、谁决定它**可见**、谁告诉模型它**存在**。这三个问题对应三个层次，也是四个搜索动作的来源。

#### 阶段 B：四类搜索

```powershell
cd D:\dsh-mini
rg -l "run_command" src/            # ① 代码层
rg -l "run_command" modes/ prompts/ # ② 配置与提示词层 ← 静默失效就在这里
rg -n "TOOL_POOL_NAMES|TOOL_CATALOG" src/plugins/tools.ts  # ③ 池清单
rg -n "child_process|spawn" src/kernel/command-tool.ts     # ④ 实现方式
```

**你应该看到了什么**：① 给出 4 个文件，② 给出 3 个文件（这就是那 10 分），③ 给出工具池位置，④ 给出实现里已存在的一个 `spawn` 调用——**那个调用就是你要修改的接缝**。

**停下来想一想**：如果我把 `run_command` 改名为 `run_shell`，会发生什么？编译器会报错吗？测试会失败吗？——如果两个答案都是"不会"，那么你刚刚理解了什么叫"静默失效的依赖"。

#### 阶段 C：写结论（最花时间，也最值钱）

在 `writeup.md` 里回答：这次改动的成本主要落在**理解 / 修改 / 验证**哪一类上？最可能出意外的是哪一步？

**"最可能出意外"需要依据**，不能是直觉。提示：读 `command-tool.ts` 里现在怎么处理错误与清理，再想一个问题——**终止一个进程与终止一棵进程树，是同一件事吗？在不同平台上呢？**

### 任务 3 · 规则命令化（5 分）

#### 为什么做这个

因为**写在文档里的规则会随时间失效，写在命令里的规则会随时间报警**。这条原则的价值在你进团队时会立刻显现：一个永远绿的检查比没有检查更糟（它制造虚假的安全感），而一个能报警的检查会持续阻止一类问题——**而且它不需要你写任何业务代码**。

#### 你会怎么想错

以为"写出来就行"。判分器不检查脚本有多优雅，它检查两件事：能否在正常状态下返回 `PASS` 与退出码 0，以及**你是否真的演示过它报警**。第二件事无法伪造——`selfTestOutput` 里必须有你抓到人为违规的那次运行输出。

#### 步骤

1. 打开 `kit/scripts/check.mjs`——**骨架已经给你了，里面写满了引导注释**，你只需要填标着 `TODO` 的部分（三处）。
2. **在 `D:\dsh-mini` 的副本里制造一次违规**，跑它，保存输出，删副本。
3. 把脚本路径与那次输出填进 `answers.json` 的 `task3`。

**你应该看到了什么**：骨架在正常状态下输出 `PASS`；你在副本里制造违规后，它明确指出违规的文件与位置。如果你的脚本第一次跑就报警，**先检查是不是规则写错了**（假阳性），而不是高兴。

### 任务 4 · 双轨时序图（20 分）

#### 为什么做这个

因为只读函数调用链的人，会**看不见事件**。而插件化的系统里，相当一部分行为由事件驱动——它不在调用链上。这个任务训练把运行时看成**两条并行的链**的能力，它直接决定你能不能回答"我改了这个事件，谁会受影响"。

#### 你会怎么想错

**错误七：只画调用链。** 最常见，也最好检查：如果你的图里没有 emit 与 on 的对手戏，那它就不是双轨图。

**错误八：漏掉配置层的钩子。** `bundles/*.json` 与 `modes/*.json` 里的字段也是钩子点——**它们能在不改一行代码的情况下改变行为**。这正是"钩子"的定义，也是它容易被忽略的原因（它不在任何 `.ts` 文件里）。

#### 步骤

```powershell
cd D:\dsh-mini
rg -n "ctx\.on\(" src/           # 监听注册点
rg -n "ctx\.emit\(" src/         # 事件发出点
rg -n "disabled" bundles/ modes/ # 配置层钩子
```

**你应该看到了什么**：`ctx.on(` 出现在 4 个文件里，`ctx.emit(` 共 18 次。**注意 `demos/` 里也有注册**——它们算数，因为运行时会真的注册。

**画图要求**：两栏（左调用链、右事件链），每个 emit 标事件名，每个监听者标文件，钩子点用 `★`。画在 `writeup.md` 的第四节。

**停下来想一想**：你画的图里，哪一条信息**只存在于事件链上**？如果把它删掉，你在调用链上会不会看出异常？——这个答案就是"为什么要看两条链"。

## 五、检查点：你随时可以知道自己走到哪

你的作业不是孤立的练习。它产出的数字会直接进入《毕业标准》（`../../00-导论/0.2-毕业标准.md`）的差距分析：

| 毕业标准的维度 | 你这次测到的 | 为什么重要 |
|---|---|---|

| **稳定性** | 任务 1 找出的"无证据不变量"：__ 条 | 这些是将来最可能在特定序列下爆发的地方 |

用《毕业标准》§5.3 的三句话格式更新一次差距分析：

```
【已达到】这一维度上，我的系统现在的数据是 ______。
【差距原因】差距来自 ______（一个具体机制）。
【下一步】消除它需要做 ______。
```

**这份作业与"缓存复用"维度的关系也值得说清**：它不直接测量缓存，但它测的"改动波及面"与"未写下的不变量"正是两个会**破坏缓存**的东西的来源——任何改动前缀的修改（工具清单顺序、系统提示词的格式化）都会让命中率下降，而这类改动的风险正是任务 2 训练的能力。

## 八、FAQ

**Q：判分器会不会因为我的另一种正确写法判错？**
不会，只要你写的是同一个事实。它做集合与数值比对：`src/kernel/llm.ts`、`./llm.ts`、`kernel/llm.ts` 会归一到同一个键。但写"它依赖了 llm 模块"这种散文会被判错——**答卷要写文件名**。

**Q：`--verbose` 算作弊吗？**
第一次不算（它帮你校准颗粒度），做完任务 2 之后就算。真正有价值的用法是"先自己判，再对照"。

**Q："做完了但做得浅"怎么识别？**
三个信号：任务 1 一条标红项都没有；任务 2 的清单里全是"会报错"项；`writeup.md` 里没有任何"我原本以为……结果发现……"的记录。**第三个信号最准**——它意味着你的理解在过程中没有发生变化，而那通常说明你没有真的在读。

**Q：我能改 `kit/tools/` 里的工具吗？**
可以（它是你的环境），但没必要。如果你改了它而作业结果变好了，那是工具在替你答题。

**Q：中间隔一天真的有必要吗？**
有。间隔本身是记忆机制的一部分，而且它让你第二次坐下来时**带着一个已经消化过的框架**重新看题目——很多人会发现前一天卡住的地方第二天自然通了。

## 本篇新词

子进程（child process） 指由本进程启动的另一个进程。它与线程的区别是它有自己的地址空间与生命周期，因此它的清理不能靠"等它自己结束"，而必须由本进程显式处理。

进程组（process group） 是 POSIX 里的一个概念：一组进程可以被当作一个整体来接收信号。它的用途是一次取消杀掉一棵子树——命令 `kill(-pgid, SIGTERM)` 会给整个进程组发信号，而不是只给直接启动的那个进程。

孤儿进程（orphan process） 指父进程已经退出而它仍在运行的子进程。它的后果是资源泄漏（内存、端口、文件锁）与行为异常（它仍在读写被其他进程使用的文件）。孤儿进程的形成原因几乎总是"只杀了父进程"。

僵尸进程（zombie process） 指已经退出但父进程尚未回收其退出状态的进程。它与孤儿进程是相反的问题：孤儿是活的没人管，僵尸是死的没人收。两者的修法都是"父进程必须显式处理子进程的结束"。

宽限期（grace period） 指先发温和信号（`SIGTERM`）与后发强制信号（`SIGKILL`）之间的等待。它的意义是给进程一个"保存状态并退出"的机会。没有宽限期时，强制终止会让进程没有机会做清理，而清理可能包括删除临时文件与释放锁。

后台作业（background job） 指不阻塞当前对话、在后台继续执行的任务。它与前台的子进程共享同一套清理机制，多出的是状态管理：进度、日志、结果、以及"能不能取消"。

输出背压（output backpressure） 指当子进程的输出速度快于消费速度时，缓冲区被填满而子进程被阻塞。它的表现是死锁：父进程在等待子进程结束，而子进程在等待缓冲区被读取——两者都不动。

作业状态（job state） 指后台作业的生命周期位置：排队、运行、完成、失败、取消。它的实现要点是状态转换的合法性（不能从完成回到运行）与终态的持久性（完成之后结果仍然可查）。

这张图的关键线索在第二块：取消是这一篇的核心。没有取消机制时，一个卡住的命令会让整个任务停住。而取消写错时（只杀父进程），系统会同时表现出"任务已经取消"与"资源仍在被占用"这两个矛盾的现象。

### 0.1 一个具体的判断：`sh -c "npm test"` 杀谁

一个典型的命令是 `sh -c "npm test"`。它的进程结构是三层：父进程（你的执行器）→ `sh` → `npm` → 实际的测试进程。如果在取消时只杀了 `sh`，那么 `npm` 与测试进程会继续运行——它们成了孤儿，而它们的输出仍然写着同一个文件、仍然占着同一个端口。

这个例子的判据很直接：取消的对象是"这棵树的根"，而不是"我直接启动的那个进程"。实现方式在 POSIX 上是把子进程放进它自己的进程组（`setsid` 或 `setpgid`），取消时对整个组发信号（负 pid）。在 Windows 上是把子进程放进 Job Object，取消时终止整个作业。

### 0.2 本篇建立的三项判据

第一项用于判断一次取消是否彻底：问"这棵树里还有活着的进程吗"。检验方式是启动一个会派生子进程的命令、取消它、然后检查是否还有相关进程——这条判据不能靠"我的代码调用了 kill"来满足，只能靠观察系统状态。

第二项用于判断输出收集是否会死锁：问"如果子进程的输出超过缓冲区，谁来读"。答案是必须有并发的读取（而不是"先等它结束再读输出"），因为子进程会在缓冲区满时阻塞，而它在阻塞时不会结束。

第三项用于判断后台作业是否被正确清理：问"它结束之后留下了什么"。留下的是应当保留的（结果、日志），而进程、临时文件、锁应当被释放。

### 0.3 十分钟练习：为什么"先等结束再读"会死锁

下面这段代码用十八行演示死锁的成因。

```js
import { spawn } from 'node:child_process'

// 写法一：先等进程结束，再读它的输出（在有大量输出时死锁）
function collectAfterExit(cmd) {
  return new Promise((resolve) => {
    const p = spawn(cmd, { shell: true })
    let out = ''
    p.stdout.on('data', (d) => { out += d })        // 事件是异步的，但下面 await 会阻塞流程
    p.on('exit', () => resolve(out))
  })
}
// 写法二：显式并发收集（或使用同步的 stdio: 'pipe' 之外的选项让运行时处理）
function collectConcurrently(cmd) {
  return new Promise((resolve, reject) => {
    const p = spawn(cmd, { shell: true })
    let out = ''
    p.stdout.on('data', (d) => { out += d })         // 边产生边消费，缓冲不会被填满
    p.on('error', reject)
    p.on('exit', (code) => resolve({ out, code }))
  })
}
// 演示：两条路径都能跑，差别在输出量很大时（例如 seq 1 200000）
console.log('先等结束再读：输出超过缓冲会挂住（此处不实际触发以避免卡住示例）')
console.log('并发收集：边产生边消费，不会挂住')
```

这段代码的重点在注释说明的那件事：Node 的 stream 事件是异步的，而"await 进程结束"并不会阻止事件处理——真正的死锁发生在那些把输出重定向到管道的实现里（例如把子进程的 stdout 接到一个没人读的管道）。因此正确的判据是"有没有人在并发地消费输出"，而不是"我用的是哪种 API"。

> **面试视角**
> **高频问法**："你怎么取消一个正在执行的命令？"
> **高分要点**：说出"杀掉整棵进程树"（进程组或 Job Object），以及"先温和信号再强制信号"的宽限期。只说"调用 kill"是常见的欠缺——它会在有包装脚本的命令上留下孤儿进程。

### 0.5.3 三个连锁影响

第一，取消不彻底会让"已取消"这个状态变成谎话。 系统报告任务已取消，而资源仍被占用——这个矛盾在排查时极具误导性，因为排查者会相信"已取消"并去别处找原因。处置方式是把"取消完成"定义为"树里没有活着的进程"，而不是"我发出了信号"（0.2 的第一项判据）。

第二，输出背压会以死锁的形式出现，而它的表现与命令本身无关。 一条在终端里运行完好的命令，在子进程执行器里可能挂住——因为它产生输出的速度超过消费速度。这条连锁的排查难点在于挂住的进程看起来一切正常（它没有崩溃、没有报错），只是不再前进。

第三，后台作业的状态管理会把"生命周期"从一个概念变成一组必须维护的数据。 前台的子进程只需要等待它结束，而后台作业需要回答"它现在在哪一步、能不能取消、结果还在不在"。这条连锁的结论是后台作业的实现里有相当一部分是状态机，而不是进程管理。

### 0.5.4 它与本书其余部分的关系

本篇的进程管理是单机的、本机用户的。它不涉及权限提升、跨用户隔离与容器编排——那些在第 5 卷的规模化与部署话题里。本篇的边界可以这样表述：它保证"本进程启动的东西会随它一起消失"，而不保证"其他进程不能干扰它"。

> **面试视角**
> **高频问法**："你怎么保证一个命令不会卡住整个系统？"
> **高分要点**：说出三件事——超时（把无限等待变成一个确定的失败）、取消（杀掉整棵树）、以及输出收集（避免背压死锁）。三件事缺一都会让"卡住"变成不可恢复的状态。

## L0 要解决的问题

### 0.1 现象一：取消之后，命令还在跑

第一个现象在命令带有包装脚本时必然出现。执行 `sh -c "npm test"` 之后取消，如果实现只杀了 `sh`，那么 `npm` 与它派生的测试进程会继续运行。它们不再有任何与之对应的任务（任务已经被标记为取消），因此它们的行为无人观察：继续写日志、继续占用端口、继续持有文件锁。

这个现象的后果会在之后的一段时间里扩散。占用端口会让下一次启动失败（"地址已被使用"），持有文件锁会让后续的读操作阻塞或读到不一致的内容，而写日志会让磁盘慢慢被填满。它们的共同特征是"故障现场与原因之间隔着一次取消"，因此排查通常从"为什么端口被占用"开始，而不是从"某次取消不彻底"开始。

### 0.2 现象二：一条在终端里正常的命令，在执行器里挂住

第二个现象是输出背压。一条命令在终端里跑得很好，而在子进程执行器里会挂住不动——进程没有结束、没有报错、也不再产生新的日志。原因是它的输出速度超过了消费速度，缓冲区被填满，而它在等待缓冲区被读取。

这个现象的排查难点在于它看起来像"命令卡住了"，而实际是"收集器卡住了"。区分它们的方法是看输出：如果最后一条输出停在某个位置而进程仍在运行，那么可能是背压。如果进程的 CPU 占用很高，那么可能是命令本身。这条区分很重要，因为两种原因的修法完全不同（前者改收集方式，后者加超时）。

### 0.3 现象三：进程表里积累着已经退出的进程

第三个现象是僵尸进程。子进程退出之后，它的退出状态会保留到父进程读取它为止。父进程若从不读取，那些条目就会留在进程表里。少量僵尸无害，而大量积累会耗尽进程表条目（系统的 pid 上限），导致新的进程无法启动。

值得区分的是它与其他两种状态的差别：运行中的进程占用资源，僵尸不占用资源但占用一个表项，孤儿（活的、失去父进程的）两者都占。三者的处置方式不同——前者要终止，中者要回收，后者要既终止又回收。

### 0.4 现象四：重启之后，后台作业的状态消失了

第四个现象是后台作业特有的。进程重启之后，内存里的作业表消失，而磁盘上可能还留着它们的输出文件与进程。此时系统面对一个无法回答的问题：那些还在运行的进程是谁启动的、要不要留着。

这个现象的处理需要两件事：作业状态的持久化（重启后能知道曾经有哪些作业）与进程与作业的关联（能判断某个进程属于哪个作业）。缺少前者时会积累无人认领的进程，缺少后者时无法安全地清理它们——因为不知道哪些进程是自己启动的。

### 0.5 这一篇要正面回答的四个问题

第一，子进程如何启动与回收，退出码与输出怎么处理（1.1）。第二，取消如何做到彻底，跨平台的差异在哪（1.2、1.3）。第三，输出收集为什么会死锁，如何避免（1.4）。第四，后台作业的状态如何管理，崩溃后如何清理（1.5、1.7）。

四个问题里第二与第四是这一篇的难点：前者涉及操作系统语义，后者涉及状态机与持久化。它们的共同点是"错误实现不会立刻报错"——只杀父进程的取消看起来成功了，丢失状态的作业表看起来只是"重启后空了"。

## L1 设计与原理

### 1.1 启动与回收

启动一个子进程需要规定的有四件事：命令的构造方式（数组参数还是 shell 字符串）、环境与工作目录、输出通道、以及结束后的回收。

命令的构造应当优先使用参数数组而不是 shell 字符串（`spawn('git', ['status'])` 而不是 `spawn('git status', { shell: true })`）。理由有二：数组形式不需要 shell 解释，因此注入风险为零。它也不会多出一层进程（0.1 那个三层结构里最外层就是 shell）。

需要 shell 特性（管道、通配符）时才用字符串，并在此时接受它的代价。

环境与工作目录必须显式指定，而不是继承。继承会让子进程的行为依赖父进程的环境（例如某个环境变量在某台机器上有而另一台没有），而那正是 2.6 那条可复现性要求的反面。本课程的做法是给子进程一个显式的环境（继承必要项加显式覆盖），并把工作目录限制在工作区内（与 2.2 的路径防线一致）。

输出通道有三种：忽略、继承、管道。管道是默认选择，因为它让父进程能处理输出（截断、溢出、记录），而它的代价正是 1.4 要处理的背压问题。

回收指读取退出码与信号。这一步必须被显式执行，否则会产生僵尸进程（0.3）。在 Node 里它表现为监听 `exit` 事件。而在同步实现里（例如 `execFileSync`）回收是自动的。

```ts
interface RunResult {
  readonly code: number | null          // 退出码；被信号终止时为 null
  readonly signal: string | null        // 终止它的信号名
  readonly stdout: string
  readonly stderr: string
  readonly durationMs: number
  readonly timedOut: boolean
  readonly cancelled: boolean
}
```

七个字段的分工值得说明：`code` 与 `signal` 是互斥的两类结束原因（正常退出与被动终止），后三个是"为什么结束"的诊断信息，而 `durationMs` 是 3.6 的度量输入。`timedOut` 与 `cancelled` 必须分开，因为它们的处置不同：超时意味着命令本身太慢（可能要调参数或换命令），取消意味着有人主动中止（通常不需要处置）。

### 1.2 取消的三个层次

取消的实现分三个层次，而只做第一层是 0.1 那个现象的成因。

第一层：给直接子进程发信号。 它对不派生子进程的命令足够（例如 `ls`），而它对 `sh -c` 这类命令不够——因为信号只到了 shell，而 shell 可能不会把它转发给它的子进程。

第二层：给进程组发信号。 POSIX 下把子进程放进一个新的进程组（`setsid` 或 `setpgid`），然后用负号的形式发信号（`kill(-pgid, sig)`），信号会到达组内所有进程。这是取消应当使用的层次，因为进程组恰好对应"我这次启动的那棵树"。

第三层：宽限期与强制终止。 先发 `SIGTERM`（可被捕获，允许进程清理后退出），等待一段宽限期，仍未退出则发 `SIGKILL`（不可捕获，强制终止）。宽限期的长度是一个参数（通常几百毫秒到几秒），它的取值依据是"进程清理需要多久"——而超出它意味着那个进程不打算配合。

```ts
async function cancel(tree: ProcessTree, graceMs = 2000): Promise<void> {
  signalGroup(tree.pgid, 'SIGTERM')                 // 温和：允许清理
  const exited = await waitFor(tree.pgid, graceMs)  // 等它自己走
  if (!exited) signalGroup(tree.pgid, 'SIGKILL')    // 强制：不留余地
}
```

这段实现的要点是"等待"那一步：发出信号不等于取消完成（0.2 的第一项判据），而等待的对象是进程组整体（组内还有活着的进程就继续等）。

### 1.3 跨平台的进程树

两个平台的进程树机制不同，而这一篇的实现必须同时支持它们——因为本课程的目标平台是两者。

| | POSIX | Windows |
|---|---|---|
| 组织方式 | 进程组（`setpgid`）与会话（`setsid`） | Job Object |
| 一次终止整棵树 | `kill(-pgid, sig)` | `TerminateJobObject` |
| 温和信号 | `SIGTERM`（可捕获） | 无对应的通用机制（控制台事件有限） |
| 资源限制 | `rlimit`（按进程） | Job Object 的配额（按作业） |

这张表里最值得注意的是第三行：Windows 没有可捕获的通用终止信号。因此"宽限期"在两个平台上的含义不同——POSIX 上是"先请求后强制"，Windows 上基本是"直接终止"。这个差异必须在实现里被承认，而不是假装两端一致：假装一致会让 Windows 上的实现看起来支持宽限期，而实际上它总是强制终止（那会让子进程没有机会清理）。

本课程的处理方式是把差异收在一个包内（平台的适配层），并把它的能力如实暴露给上层：调用方可以问"这个平台支持温和终止吗"，从而决定要不要提示用户。

### 1.4 输出收集与背压

背压的成因在 0.3 的练习里已经说明，而它的解法有三条，各有代价。

第一条是并发收集。 父进程边读边处理（累积、截断、溢出到文件），因此缓冲区不会被填满。这是默认选择，它的代价是父进程要维护收集状态（内存里的累积字符串可能很大，因此要配合 3.3 的溢出）。

第二条是让子进程直接写文件。 输出不经过父进程，因此没有背压。代价是父进程无法实时观察输出（只能等结束再读），而实时性对长任务很重要（用户想看进度）。

第三条是把输出接到一个被持续消费的通道。 例如接到一个日志文件加一个 `tail` 式的读取器。它结合了前两条的优点，代价是实现的复杂度。

本课程选第一条加阈值溢出：收集时达到阈值就把内容写到文件（3.3 的 `spill`），并在内存里保留首尾。这条组合同时解决了背压与上下文占用——前者靠并发收集，后者靠溢出。

### 1.5 后台作业的状态机

后台作业与前台子进程共享同一套进程管理，多出的是状态。五个状态构成一个简单的状态机。

```
排队 → 运行 → { 完成 | 失败 | 取消 }
```

四条规则让这个状态机可维护。第一，只有一个终态转换：一旦进入完成、失败或取消，就不能再变（这条规则防的是"任务已经失败但又被标记为完成"）。第二，取消可以从排队或运行进入：排队时取消意味着"不要启动它"，运行时取消意味着"终止它"。第三，终态的结果必须保留：作业完成之后，它的输出、退出码与耗时仍然可查（否则用户无法知道它做了什么）。

第四，状态转换必须被记录：每次转换写一条事件（时间、原因），因为它们回答了"它为什么失败、什么时候被取消"。

```ts
interface JobState {
  readonly id: string
  readonly state: 'queued' | 'running' | 'succeeded' | 'failed' | 'cancelled'
  readonly startedAt?: number
  readonly endedAt?: number
  readonly progress?: { done: number; total?: number }   // 可选：由作业自己上报
  readonly resultRef?: string                            // 终态结果的引用（文件或事件序号）
}
```

`progress` 是可选字段，而它的存在与否是一个判断：需要进度上报的作业通常是那些运行时间足以让人等待的，而短作业不需要。它的实现代价是子进程要按约定输出进度（例如一行 JSON），因此它只在明确的场合启用。

### 1.6 超时与资源限制

超时把"无限等待"变成一个确定的失败。它的实现要点是超时之后仍要清理：发出取消信号、等待宽限期、必要时强制终止——超时不是"放弃等待"，而是"主动终止"。这两者的差别在资源上：放弃等待会留下仍在运行的进程，而主动终止不会。

资源限制在两端的粒度不同。POSIX 用 `rlimit`（限制单个进程的内存、CPU 时间、文件大小），Windows 用 Job Object 的配额（限制整个作业组的资源）。两者的共同点是它们都必须由系统强制（进程自己不会遵守），因此它们的实现属于沙箱的范畴（3.2 的 1.7）。

本课程在本篇只做超时与输出上限，资源限制留给沙箱——理由与 3.2 相同：限制能力需要系统支持，而超时与输出上限在应用层就能做对。

### 1.7 崩溃后的残留清理

进程被杀时，它启动的子进程不一定被杀——因此恢复流程的第一件事应当是清理残留。它的实现需要一个"我是谁启动的"标记，而这正是 1.5 那个作业表的作用。

清理的步骤是三步：读持久化的作业表、找出状态为"运行中"的作业（它们对应上一次崩溃时还在跑的进程）、检查那些进程标识是否仍存在且属于本系统（避免误杀复用了同一个 pid 的其他进程）。第三步是这一步里最容易出错的地方——pid 会被复用，因此单靠 pid 判断"这个进程是我启动的"不安全。

可行的做法有两种。第一种是记录进程的启动时间（它与 pid 一起构成一个较可靠的标识）。第二种是让子进程携带一个环境变量标记（例如 `DSH_JOB_ID=...`），清理时通过查询进程的环境来确认归属。第二种更可靠，而它要求能读取其他进程的环境（在多数平台上需要额外权限），因此本课程采用第一种加"只清理最近一次运行的作业"这条约束。

### 1.8 两次追问

工程侧的问题是什么时候该把命令放到后台。判据是"它的预期耗时是否超过一次交互的容忍度"：几秒以内的命令前台等（用户体验更好，且结果直接可见），更长的放后台（避免阻塞对话）。这条判据的实际形态是一个超时阈值：超过它的前台命令会被提议转后台，而不是直接被杀死。

产品侧的问题是用户如何知道后台发生了什么。答案需要三个东西：作业列表（有哪些在跑）、每个作业的状态与进度、以及结果的入口。这三样的共同点是它们让"我看不见的过程"变得可查询——而这一点与 2.7 的"可查询"和 3.2 的"已批准事项可见"是同一条原则在三个地方的应用。

### 1.9 长期运行的工具与作业的关系

2.2 的工具契约是同步的：`run` 返回一个 `ToolResult`，而循环等它返回。这个形态对一个跑十分钟的命令是致命的——循环会卡住十分钟，而模型的上下文里那十分钟没有任何新信息。作业化是唯一的出路，而它改变了工具的接口形态。

改造后的形态是两段式：工具调用返回一个作业 id（`{ ok: true, content: "已受理，作业 id: j-123" }`），而结果通过另一次调用或事件送达。这带来三个接口变化。第一，`ToolResult` 必须能表达"已受理但未完成"——它是 2.2 那三类结局（成功、失败、被拦下）之外的第四类。

第二，工具必须声明它的预期耗时（与 `sideEffect` 同类的信任型声明），否则系统无法判断该同步等还是该作业化。第三，作业的完成必须产生一条事件，否则模型不知道它好了。

由此得到一条判据：当工具的预期耗时超过一次交互的容忍度时，它必须被作业化。而"容忍度"是一个部署参数（2.6 的配置来源），不是硬编码——因为不同场景对等待的容忍度不同（交互式界面几百毫秒，批处理几分钟）。

| 12 | 长任务的处置 | 超过阈值时提议转后台 | 直接杀死或无限等待 | 多一次交互；换来不阻塞对话 |

其中两条值得展开，因为它们的选择在实践中经常被做成另一个。

### 关于第 4 与第 5 条的完整论证（取消为什么要杀整棵树、以及为什么要有宽限期）

替代方案有两种，各自的失败方式在 0.1 已经给出。

只杀直接子进程：实现在多数命令上"看起来正确"，而在带包装脚本的命令上留下孤儿。它的危害要在之后才显现（端口被占、锁未释放），因此它属于"错误实现在正常路径下完全可用"这一类。它最坏的地方在于它给了一个虚假的完成信号：系统报告任务已取消，而资源仍被占用。

直接 SIGKILL：它保证进程立刻消失，代价是进程失去清理机会。清理的内容包括删除临时文件、释放文件锁、向协作方发送"我退出了"的消息。少了这一步，系统会积累临时文件与陈旧的锁——而后者的表现是"下次启动时一直等待"，与 0.1 那个现象的表现相似而原因不同。

本课程的组合（进程组加宽限期）同时避免了两者。它的实现代价有两项：平台适配（Windows 没有等价的温和信号，因此如实暴露"这个平台只能强制"），以及等待本身的成本（取消不再是即时的，它可能耗时到宽限期的上限）。第二项代价需要在界面上被承认：用户点了取消之后，界面应当显示"正在停止"而不是立刻显示"已停止"。

### 关于第 9 与第 10 条的完整论证（作业状态为什么要持久化）

替代方案是作业表只放内存，重启后从空开始。它在"进程与服务同生共死"的假设下是成立的，而这个假设在两种情形下不成立：进程被强制杀死（崩溃、OOM、用户强杀）时，它启动的子进程可能仍在运行。服务重启时，上一次的作业记录消失了，因此那些仍在运行的进程无人认领。

持久化的代价很小（每次状态转换写一条事件，与 2.7 的日志设施复用），而它换来的能力有三项：重启后能列出"上一次运行时有哪些作业未完成"、能据此清理残留进程、以及能回答用户"我上次那个任务怎么样了"。

清理残留时有一个必须处理的问题：pid 会被复用。如果只按 pid 清理，可能误杀一个恰好复用了同一个 pid 的无辜进程。本课程的处理方式是两条约束：只清理"最近一次运行"的作业（时间接近，因此 pid 复用的概率低），以及比对进程的启动时间（它与 pid 一起构成较可靠的标识）。

这两条约束不保证 100% 准确，因此它们必须与"宁可漏清也不误杀"这条原则配合——漏清留下的是一个占资源的进程，误杀会让无辜进程消失，后者的后果更严重。

## L3 实现（施工图）

### 3.1 文件结构

```
// kernel/subprocess.ts        负责一次执行
// ┌─ 启动段 ── spawn 的参数构造（数组、环境、工作目录、管道）
// ├─ 收集段 ── 并发读 stdout/stderr，超阈值溢出
// ├─ 取消段 ── 进程组加宽限期（平台适配）
// └─ 回收段 ── 读取退出码与信号，返回 RunResult
//
// kernel/jobs.ts              负责长期任务
// ┌─ 状态段 ── 五态状态机与转换规则
// ├─ 记录段 ── 转换即写事件（含作业表）
// ├─ 查询段 ── 列表、状态、结果
// └─ 清理段 ── 崩溃后的残留清理（只清理最近一次运行）
```

两个文件的划分对应 1.5 的分析：`subprocess.ts` 只管"一次执行的完整生命周期"，而 `jobs.ts` 管"跨多次执行的状态"。把状态机塞进 `subprocess.ts` 会让"一次执行"这个简单的抽象变复杂，而它在多数调用点是不需要的。

### 3.2 启动段

```ts
export function start(command: string, args: readonly string[], opts: RunOptions): ChildProcess {
  const child = spawn(command, args, {
    cwd: resolveInside(opts.workspace, opts.cwd ?? '.'),   // 工作目录必须落在工作区内
    env: explicitEnv(opts.env),                            // 显式环境，不继承
    stdio: ['ignore', 'pipe', 'pipe'],                     // 管道：父进程能处理输出
    detached: process.platform !== 'win32',                // POSIX：新进程组
    windowsHide: true,
  })
  return child
}
```

四个参数的取舍对应 1.1 的四件事。`detached: true` 在 POSIX 上让子进程成为一个新进程组（因此 1.2 的整组信号可行），而它在 Windows 上无意义（那里用 Job Object）。这个分支必须在适配层给出清晰的语义，而不是散落在调用点。

### 3.3 收集段与溢出

```ts
export async function collect(child: ChildProcess, limit: number, dir: string): Promise<Collected> {
  const parts: string[] = []
  let total = 0
  const sink = (chunk: Buffer) => {
    parts.push(chunk.toString())
    total += chunk.length
    if (total > limit) void spillChunk(dir, chunk)   // 超阈值：追加到溢出文件
  }
  child.stdout!.on('data', sink)                     // 并发消费，避免背压
  child.stderr!.on('data', sink)
  return { parts, total }
}
```

这段实现里最关键的仍是"并发消费"这一点：`on('data')` 注册的处理是同步的，而 Node 会在子进程产生数据时调度它——只要父进程不阻塞在"等待结束"上，缓冲区就不会被填满。这与 0.3 那个练习的注释是同一条。

### 3.4 取消段

```ts
export async function cancel(child: ChildProcess, graceMs = 2000): Promise<void> {
  if (process.platform === 'win32') { terminateJob(child); return }   // 平台如实暴露能力
  const pgid = child.pid!                                                // detached 之后它就是组长
  signalGroup(-pgid, 'SIGTERM')
  if (!(await waitForExit(child, graceMs))) signalGroup(-pgid, 'SIGKILL')
}
```

三处要点：平台分支如实区分能力（1.3）、负 pid 的语义（整组）、以及"等待之后才强制"的顺序（1.2）。

### 3.5 作业状态机

```ts
const TERMINAL = new Set(['succeeded', 'failed', 'cancelled'])
export async function transition(job: Job, next: JobState['state'], reason?: string): Promise<void> {
  if (TERMINAL.has(job.state)) throw new Error(`作业 ${job.id} 已处于终态 ${job.state}，不能再改变`)
  if (next === 'running' && job.state !== 'queued') throw new Error('只有排队中的作业可以开始')
  job.state = next
  await ctx.session.append({ type: 'job/state', jobId: job.id, state: next, reason, at: Date.now() })
}
```

两次状态检查对应 1.5 的两条规则（终态不可逆、只允许合法转换），而写事件对应第三条（转换必须被记录）。这两次检查的代价是两次判断，收益是状态机的可维护性——没有它们时，"一个已完成的作业又被标记为运行"这类不一致会在多处出现。

### 3.6 验收判据

| # | 判据 | 怎么检查 |
|---|---|---|
| 1 | 正常命令返回退出码与输出 | 跑一条简单命令，核对外部结果 |
| 2 | 退出码非零时 `code` 保留原值 | 跑一条会失败的命令，核对 `code` 不等于零 |
| 3 | 被信号终止时 `signal` 有值而 `code` 为 null | 启动一条长命令并终止它 |
| 4 | 超时被标记为 `timedOut` | 设置很短的超时，核对标志为真 |
| 5 | 取消被标记为 `cancelled` | 主动取消，核对标志为真 |
| 6 | 取消杀掉整棵树 | 启动 `sh -c "sleep 30"`，取消后核对没有残留的 `sleep` 进程 |
| 7 | 宽限期生效 | 让子进程捕获 SIGTERM 并延迟退出，核对它有机会执行清理 |
| 8 | 输出超过阈值被溢出 | 跑一条产生大量输出的命令，核对溢出文件存在且内容完整 |
| 9 | 大量输出不导致死锁 | 跑一条产生远超缓冲上限输出的命令，核对它在超时前正常结束 |
| 10 | 作业状态机拒绝非法转换 | 对已完成的作业再发一次"运行"，核对标错 |
| 11 | 作业状态转换被记录 | 跑一个后台作业，核对日志里有状态事件 |
| 12 | 终态结果可查 | 作业结束后查询它的输出与退出码 |
| 13 | 崩溃后的残留被清理 | 模拟崩溃（留下运行中的作业记录），重启后核对清理流程被执行 |

第 6 与第 9 条是这一篇的核心判据：前者检验取消是否彻底（只能靠观察系统状态，不能靠"我调用了 kill"），后者检验输出收集是否会死锁。第 13 条检验持久化与清理的配合。

### 3.7 实现顺序

先做启动与回收（判据 1、2、3），再做取消（判据 6、7），然后做收集与溢出（判据 8、9），接着做超时与标志（判据 4、5），最后做作业状态机与清理（判据 10、11、12、13）。

### 3.8 阈值参数的来源

本篇涉及四个阈值，而它们的取值都有可追溯的来源——说不出来源的阈值等于拍脑袋。

输出上限（进上下文的字符数）来自上下文预算：它是窗口的一个切片（例如占 5%）。以 128K token 的窗口为例，5% 约 6400 token，折合字符数约两万（中文按每字符约一 token 的三分之一估算）。

溢出阈值略低于输出上限（例如上限的 80%），留出的余量用于指针与首尾片段。低于它时不溢出，是因为溢出的代价（一次文件写入与后续的一次读取）大于收益。

宽限期来自"进程清理的典型耗时"：多数进程处理 SIGTERM 并退出在百毫秒量级，因此宽限期取几百毫秒到两秒。它的取值不影响正确性（超时之后仍会强杀），影响的是取消的响应时间。

超时来自命令类别的耗时分布：对测试类命令取它的 P99 再乘以安全系数。这与 2.7 的步数上限、3.1 的重试次数是同一个方法——上限由分布决定，而不是由直觉。

四个参数的共同点是它们都能被观测校准（3.6 会给出方式），因此初值只需要量级正确，而长期应当由数据修正。

### 5.1 术语表

| 术语 | 在本篇里的准确含义 | 容易误解为 |
|---|---|---|
| 子进程 | 由本进程启动的另一个进程 | "线程"（生命周期与地址空间都不同） |

| 作业状态 | 后台作业在生命周期中的位置 | "进度"（进度是状态内的细节） |

| 目的 | 命令 | 说明 |
|---|---|---|

### 5.3 三条容易踩的规则

第一条，取消要针对进程组或作业对象，而不是直接子进程。只杀一个会在带包装脚本的命令上留下孤儿。

第二条，终止要留宽限期。直接强杀会让进程没有机会清理临时文件与锁。

第三条，超时的语义是主动终止而不是放弃等待。放弃等待会留下仍在运行的进程。

## L9 仍未解决（这一篇自己的缺陷）

| 缺陷 | 后果 | 修法 | 当初为什么这么写 |
|---|---|---|---|
| 残留清理依赖"只清理最近一次运行" | 更早的残留不会被清理 | 进程携带作业标识的环境变量（需要读取其他进程环境的权限） | 读取其他进程环境的权限在多数平台上不可得 |
| 没有资源限制 | 一个失控的作业可以吃满 CPU 与内存 | 引入 rlimit 或 Job Object 配额（与 3.2 的沙箱一起） | 资源限制需要平台特权，本卷不做 |
| Windows 上没有温和终止 | 取消总是强制，子进程没有清理机会 | 用控制台事件或自定义协议（子进程监听一个信号文件） | 平台能力的如实暴露比假装支持更好 |
| 作业进度依赖子进程自觉上报 | 不上报的作业看不到进度 | 由执行器推断（例如按输出行数估算） | 推断的准确性依赖输出格式 |
| 没有作业优先级 | 多个后台作业争抢资源时无法调控 | 引入优先级队列 | 本卷的并发作业数量有限 |
| 状态机只有五个状态 | 无法表达"正在取消"这个中间态 | 增加 `cancelling` 状态 | 五态覆盖了多数查询需求；中间态会增加界面复杂度 |

第一条与第二条属于"能力受平台限制"，第三条属于如实的差异，第四条与第五条属于简化，第六条属于表达力的权衡。第二条值得单独标记：它意味着本篇的子进程可以在本机上无限占用资源，而唯一的约束来自操作系统的默认行为——这是一个真实的安全与稳定性缺口，而它的修法需要与沙箱一起做。

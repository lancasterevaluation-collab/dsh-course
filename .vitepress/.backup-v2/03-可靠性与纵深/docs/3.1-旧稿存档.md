## 本篇新词

瞬时故障（transient failure） 指那种"再试一次就可能成功"的失败。它与"永久故障"的区分不是由现象决定的，而是由重试是否有意义决定的：限流与服务端错误属于前者（对方的窗口在恢复），参数错误与凭据错误属于后者（重试一百次结果相同）。第 2.1 篇已经把这套区分做成了错误的属性。

退避（backoff） 指两次重试之间等待的时间。指数退避指等待时间随重试次数按倍数增长，它的依据是"过载的恢复需要时间，而立即重试会继续加压"。

抖动（jitter） 指在退避时长上加一个随机偏移。它的作用是打散同时失败的一批请求的重试时刻——没有抖动时，一批同时失败的客户端会在同一时刻再次冲击服务端，而这个峰值可能比第一次失败的原因更严重。

重试预算（retry budget） 指"一段时间内允许的重试次数占请求总数的比例"上限。它解决的问题是重试放大：当依赖整体不可用时，每个请求都重试三次会让流量变成三倍，而那会把一个局部故障扩大成整体故障。

幂等（idempotent） 在这里的作用与第 1.5 篇相同：只有幂等的操作才可以被安全重试。模型调用是幂等的（重复问一次不改变世界），而工具执行通常不是（发消息、写文件、下单）。

重试的位置 指重试逻辑写在哪里。两种做法差别很大：写在循环里（核心代码多一段 try/catch）与写成一个可装载的插件（它挂在请求失败这个扩展点上）。本课程选后者，理由是重试是一个策略，策略应当可以被替换与卸载——例如某些环境不允许重试（测试环境），某些请求不允许重试（用户已经按了取消）。

重试与日志的关系 是这一篇与第 2.7 篇的连接点。"重试了几次"这件事是否进入日志，决定了重建出的历史是否完整：如果重试过程不记录，那么日志里只会看到一次成功的请求，而"它曾经失败过两次"这个事实消失了。

### 0.1 一个具体的判断：重试三次的期望延迟

重试的代价可以直接算出来。设基础延迟为 1 秒、退避倍数为 2、最多重试三次，那么三次重试的等待依次是 1s、2s、4s，累计 7 秒；加上每次请求本身的耗时（假设 1 秒），用户的等待从 1 秒变成 11 秒。

这个量级解释了为什么重试必须有上限，也解释了为什么"用户已经等了很久"时应当放弃重试并把失败返回。重试的收益是"可能成功"，代价是"确定的等待时间"，而两者都要说得出量级——说不出量级的重试策略只是在碰运气。

### 0.2 本篇建立的三项判据

第一项用于判断一次失败该不该重试：问再试一次会不会得到不同结果。网络抖动、限流、服务端瞬时错误会不同，参数错误与凭据错误不会。这条判据的输入来自错误本身（2.1 让错误携带 `retryable` 与 `retryAfterMs`），而不是来自重试模块的判断——因为只有产生错误的地方同时掌握状态码、响应体与响应头。

第二项用于判断退避的时长：问对方有没有给出明确值。给了（例如 `Retry-After: 30`）就按它等；没给就按指数退避加抖动估算。这条判据在 2.1 的决策表里已经出现过，这里的补充是它的量化形式（1.2）。

第三项用于判断重试是否已经失控：问"这段时间的重试次数占请求数的比例"。超过阈值说明依赖整体不可用，此时继续重试只会加剧拥塞，正确的动作是停止重试并让失败快速返回（熔断）。

### 0.3 十分钟练习：抖动为什么必要

下面这段代码用二十行模拟"一批同时失败的请求"在有抖动与无抖动下的行为差异。

```js
// 20 个请求在同一时刻失败，各自按指数退避重试
function retryTimes(baseMs, attempt, jitter) {
  const backoff = baseMs * 2 ** attempt
  return jitter ? backoff * (0.5 + Math.random()) : backoff      // 抖动：0.5x–1.5x
}

function simulate(jitter) {
  const base = 100, attempts = 3, clients = 20
  const buckets = new Map()
  for (let c = 0; c < clients; c++) {
    let t = 0
    for (let a = 0; a < attempts; a++) {
      t += retryTimes(base, a, jitter)
      buckets.set(t, (buckets.get(t) ?? 0) + 1)
    }
  }
  const peak = Math.max(...buckets.values())
  return { 不同时刻数: buckets.size, 最大同时重试数: peak }
}
console.log('无抖动：', simulate(false))
console.log('有抖动：', simulate(true))
```

无抖动时的输出是"不同时刻数很少、最大同时重试数接近客户端总数"——二十个客户端会在同一毫秒一起重试。有抖动时不同时刻数显著增加而峰值下降。这就是抖动的作用：它不减少重试总量，只把它们摊开。

> **面试视角**
> **高频问法**："重试你怎么设计？"
> **高分要点**：四件事都要说到——可重试性来自错误本身、退避要带抖动、有预算或熔断上限、以及幂等是前提。只说"重试三次"是最常见的欠缺。

### 0.5.3 三个连锁影响

第一，重试会在依赖过载时放大拥塞。 Google SRE 把这条列为过载处理的核心问题：当一个依赖开始变慢，每个调用方的重试会让它收到更多请求，于是它更慢，而调用方的重试更频繁。这条链的终点是整体不可用，而它的起点只是一次局部的抖动。处置方式不是"不重试"，而是"重试要有限额与退避"——限额防止总量放大，退避防止时刻集中。

第二，重试会让"失败"这个事实从日志里消失。 如果重试过程不记录，日志上只留下成功的那一次，而"这个依赖曾经不可用了两秒"这个事实没有任何痕迹。它的后果在诊断时出现：第 4 卷的失败归因需要知道"哪一步不稳定"，而重试掩盖了不稳定——表面上一切成功，实际上有一部分请求要试三次。

第三，重试的收益随次数递减而代价不变。 第一次重试的收益最大（它覆盖了绝大多数瞬时故障），而第三次之后的收益很小。这条连锁给出了一条实用的参数选择：次数上限定得小（两到三次），把资源留给更有价值的事（例如换一个降级路径）。它的依据是分布而不是感觉：多数瞬时故障在一个退避周期内恢复。

### 0.5.4 它与本书其余部分的关系

本篇的重试是同进程、同步等待的。这个边界在两类情形下需要补充：跨进程的重试需要与熔断器协调（一个进程退回重试，另一个仍在重试）；异步任务的重试需要持久化重试队列（进程重启后仍能继续）。

## L0 要解决的问题

### 0.1 现象一：所有失败走同一条重试路径

最朴素的实现是给请求加一个 try/catch，失败就重试三次。它在多数时候工作正常，而在两类失败上制造问题：参数错误（`max_tokens` 超限）会被重试三次，每次都得到同样的拒绝，用户因此多等了两秒；凭据错误（无效的密钥）同样如此，而更糟的是它会在日志里留下三次失败记录，让排查者以为是服务端不稳定。

这个现象的根因是重试的判据用错了对象：它按"失败发生了"这个事实决定重试，而判据应当是"再试一次会不会不同"。前者只需要一个布尔值，而后者需要知道失败的性质——这就是 2.1 把可重试性做成错误属性而不是重试模块判断的原因。

### 0.2 现象二：一批同时失败的请求在同一时刻再次冲击服务端

第二个现象在多客户端场景里出现。当服务端短暂不可用时，所有客户端同时收到失败，而如果它们使用同样的退避策略（例如固定的一秒），那么一秒之后它们会同时重试。这个重试峰值可能比导致失败的原因更严重，因为它是人为制造的同步脉冲。

这个现象的量级值得算一下：假设一千个客户端在一秒内全部失败，无抖动时它们会在第 1、2、4 秒产生三个尖峰，每个尖峰一千个请求；有抖动时（例如 0.5 到 1.5 倍）它们会摊到三秒的时间窗里，峰值降到三分之一左右。抖动不减少重试总量，只改变它们的分布，而这正是缓解拥塞所需的。

### 0.3 现象三：依赖整体不可用时，重试把局部故障放大成全局故障

第三个现象是 SRE 书里那条著名的链条。一个依赖开始变慢（还没完全挂），调用方的超时开始触发；每个超时都触发重试，于是依赖收到的请求变成原来的两到三倍；它更慢，更多的调用方开始超时——这是一种正反馈，而它的终点是整个系统不可用。

这条链条的一个具体形态是：某个下游服务的容量是每秒一千请求，而它的调用方在前端流量下降之后仍然维持了一千五百请求（因为其中五百是重试）。此时它永远无法恢复，因为恢复需要"没有请求"或"请求变少"，而重试保证了请求量不降。

处置方式是熔断：当失败率超过阈值时，调用方在一段时间内不发送请求（直接返回失败），给下游恢复的窗口。它的代价是这段时间里所有请求都失败（包括那些本该成功的），收益是把恢复的可能性还给下游。

### 0.4 现象四：重试让故障从记录里消失

第四个现象是这一篇与 2.7 的连接点。重试过程通常不产生日志事件——循环只记录最终结果，而中间的两次失败没有痕迹。于是日志呈现的是一个"一切正常"的系统，而实际上有三成的请求要试两次。

它的后果在诊断时出现：第 4 卷的失败归因要回答"哪个组件不稳定"，而稳定性问题的形态恰好是"偶发失败加重试成功"。如果不记录重试，那么这类问题在数据上不存在——直到重试的次数被用尽并且失败暴露出来，而那时故障已经积累了很长时间。

### 0.5 这一篇要正面回答的四个问题

第一，一次失败该不该重试，判据从哪里来（1.1）。第二，等多久，退避与抖动各解决什么问题（1.2、1.3）。第三，上限设在哪里，它防的是哪一种放大（1.4）。第四，重试会不会破坏"可重建"（1.7）。

四个问题里第四是本卷每一篇的固定检查项：新机制的价值不仅在于它能做什么，还在于它不会破坏什么。

## L1 设计与原理

### 1.1 可重试性来自错误本身

判据是"再试一次会不会得到不同结果"，而它的输入必须由产生错误的地方提供。理由在 2.1 已经给过：只有那一处同时掌握状态码、响应体与响应头。重试模块拿到的错误对象是被压缩过的信息——它能看到"失败了"，但看不到"为什么"。

由此得到本篇的第一条设计规则：重试模块不判断可重试性，它读这个属性。这条规则的实际形态是 2.1 的 `LLMError` 上的 `retryable` 与 `retryAfterMs` 两个字段：前者决定要不要重试，后者决定等多久。

```ts
interface RetryPolicy {
  readonly maxAttempts: number
  readonly baseDelayMs: number
  readonly jitter: boolean
  readonly budgetRatio: number        // 允许的重试次数 / 请求数上限
}
```

这三个参数加上预算，构成一条完整的重试策略。它们的取值都应当来自观测而不是直觉（3.6 会给出观测方式）。

### 1.2 退避的公式与期望延迟

指数退避的标准形式是 `delay(n) = base × 2^(n-1)`，其中 n 是第几次重试。它的累计等待是等比数列之和，因此总延迟随次数指数增长——这正是 0.1 那个"三次重试共 7 秒"的来源。

退避的依据是"过载的恢复需要时间"。这个依据可以被量化：如果下游的容量是 C、当前负载是 2C，那么等它恢复到 C 需要的时间取决于有多少请求会离开——而指数退避让调用方在等待期间不再施加负载，从而给恢复留出窗口。

上界（最大等待）是必要的：没有上界时，第十次重试要等五百多秒，而那时用户早已离开。上界的取值依据是"用户能接受的最长等待"，而不是技术参数——这条依据把重试策略与产品判断连了起来。

### 1.3 抖动的必要性

抖动有两种常见形式：全部抖动（等待时间在 0 到计算值之间随机）与等量抖动（在计算值的 0.5 到 1.5 倍之间随机）。Brooker 的分析给出了一条实用结论：全部抖动在减少峰值上更有效，而等量抖动在保证最小等待上有优势——因为全部抖动可能让某次重试几乎不等待，而那对已经过载的下游不利。

本课程选等量抖动，理由是它保留了"至少等一个下界"的保证。这个选择与 1.2 的上界合起来给出一个区间：每次重试的等待落在 `[0.5 × delay, 1.5 × delay]` 并受上界截断。

抖动的实现必须使用每个进程独立的随机源，而不是固定种子——固定种子会让所有副本产生相同的抖动，等于没有抖动（这个缺陷在多副本部署里会出现，而在单进程测试里看不出来）。

### 1.4 上限：次数、预算与熔断

三层上限各自防一种放大。

次数上限防单次请求的等待失控（它保证一次调用最多花多少时间）。预算防整体放大（它保证一段时间内的重试总量不超过请求总量的一定比例）。熔断防持续加压（它在下游整体不可用时停止发送）。

三者的关系是互补的：次数上限关心单个请求，预算关心聚合比例，熔断关心下游状态。只做第一条时，大量请求各自重试三次仍然能让流量变成三倍；只做第二条时，一个用户的单次请求可能等很久。

```ts
// 预算的实现：滑动窗口内统计请求数与重试数
function allowRetry(window: { requests: number; retries: number }, ratio: number): boolean {
  return window.retries < window.requests * ratio
}
```

这段实现里有一点值得注意：预算比较的是同一窗口内的重试数与请求数，因此当请求量下降时预算会自动收紧——这正是 0.3 那条链所需要的性质。

### 1.5 幂等是前提

只有幂等的操作才可以被安全重试。模型调用幂等（重复问一次不改变世界），而工具执行通常不幂等。这条限制的实现方式是把重试限制在幂等的边界内：本课程的重试只作用于模型请求，不作用于工具执行。

如果将来要给工具执行加重试（某些工具是幂等的，例如只读的查询），那么它的前提是工具声明了自己的幂等性（2.1 要求工具声明它，正是为了这个场景）。没有这条声明，重试就无法被安全地启用——因为"这个工具重放一次会不会有第二次效果"这个问题，只有工具作者能回答。

### 1.6 重试的位置：插件而不是循环

重试逻辑有两种放置方式。写在循环里意味着核心代码多一段 try/catch，且它的参数无法按环境调整；写成一个可装载的插件意味着它可以被替换与卸载，而它的挂载点是 2.4 建立的扩展点。

本课程选后者。挂载点有两处：`model/failed`（通知型，重试插件据此决定是否重试）与 `before:model`（瀑布型，重试插件可以在重试时改写请求——例如降低 `max_tokens`）。两处挂载点的分工体现了重试的两类动作：决定要不要再试（读事件）、以及再试时改变参数（改请求）。

插件形式还带来一个性质：卸载重试插件等于关闭重试。这条性质的价值在于它让"当前这个环境禁用重试"成为一次配置改动，而不是一次代码改动——与 2.6 的结论一致。

### 1.7 重试与可重建

这一节是第 3 卷每一篇的固定检查项：新机制会不会破坏 2.7 的不变量。

重试对日志的影响有两处。第一，重试的次数是否进入日志。如果只记最终的成功响应，那么"它曾经失败过两次"这个事实消失，而历史重建出的内容与当时实际发生的不完全一致——严格地说，"模型可见的必须可重建"这条不变量约束的是模型看到的输入，而重试次数不在其中，因此它不构成对不变量的违反。但它构成了对"可诊断"的损失。

第二，重试期间模型看到的输入是否变化。如果重试时改写了请求（例如降低 `max_tokens`），那么"这次请求的输入"就有了两个版本，而日志必须能区分它们。这种情况下的处理方式是：把改写后实际发出的请求作为权威记录，同时在日志里保留一条"发生了一次重试且请求被改写"的事件。

第二处是真正的风险点：只要重试会改变请求内容，它就必须在日志里留下痕迹，否则日志记录的与实际发出的不一致，而那正是对不变量的违反。

### 1.8 两次追问

工程侧的问题是什么时候该放弃重试改为降级。判据是"重试的时间成本是否超过了降级带来的价值"：一个用户已经等了三秒的请求，再重试两次要等六秒，而换一个更小的模型可能一秒就能返回一个可接受的结果。因此重试与降级是同一个决策的两个选项，而它们的选择依据是"用户此刻更在意正确还是在意有结果"。

产品侧的问题是重试对用户可见吗。多数时候不可见（用户只感觉到慢），而它在一处必须可见：失败返回时要说清"我们试了几次"。这条信息让用户能判断是自己该换个说法，还是系统出了问题——而缺少它时，用户唯一能做的就是重复同一个操作。

### 1.9 重试的可观测性

重试的行为如果不被度量，它对系统的影响就只能靠猜。三个指标覆盖全部判断。

第一个是重试比例（一段时间内重试数除以请求数）。它是 1.4 那条预算的分母，也是"下游是否健康"最直接的信号。它的正常值应当很低（个位数百分比）；它上升通常意味着某个依赖在退化，即使所有请求最终都成功。

第二个是重试的延迟分布。它回答"用户为这个依赖多等了多少"。这个数字与首次请求的延迟放在一起看，能区分两种情形：下游变慢（首次延迟上升）与下游不稳定（首次延迟正常但重试多）。两者的处置不同——前者要扩容或降级，后者要查稳定性。

第三个是按错误类型分的重试数。它让 1.1 那条判据的效果可见：如果 `invalid_request` 类型的错误也在被重试，说明可重试性被标错了，而这类错误在总量上不显眼，只有分类型看才会暴露。

三个指标的共同点是它们都指向"重试是否在做正确的事"，而不是"重试是否在工作"。重试机制最容易出的一类问题是它一直在工作，而工作得不对——把不可重试的错误反复重试、或者在没有抖动的情况下制造同步脉冲，都不会表现为"重试失败"。

### 1.10 重试与幂等的边界

本篇的重试只作用于模型请求，而这条限制会随着系统演进被不断试探——因为工具失败的瞬时问题同样需要缓解。把边界画清楚的方法是区分三种情形。

第一种是只读工具（读文件、搜索、列目录）。它们天然幂等，重试是安全的。第二种是写工具但带幂等键（例如"创建任务"带上客户端生成的 id）。它们的效果幂等，因此也可以安全重试，前提是幂等键被真正使用。第三种是既非只读又无幂等键的工具（发消息、下单、推送）。它们的重试会产生第二次效果，因此不能重试。

这三类的划分给出了重试范围的正确形态：不是"工具一律不重试"，而是"只对声明了幂等的工具重试"。而声明本身的可信度问题在 2.2 已经讨论过（声明是信任型约束），因此工具重试的启用应当与沙箱配合——只有当系统能限制工具的实际能力时，它的幂等声明才值得信任。这也解释了为什么工具重试在本课程里被推迟到沙箱建立之后。

其中两条值得展开，因为它们的选择在实践中经常被做成另一个。

### 关于第 5 条的完整论证（预算为什么比次数上限更重要）

次数上限限制的是单个请求，而预算限制的是聚合比例。它们的差别在 0.3 那条正反馈链上显现。

假设有一千个并发请求，每一次失败都重试三次，那么下游在故障期间收到的请求是三千次。如果次数上限从三次降到两次，总量变成两千次——仍然是两倍，而下游的容量可能只差一点点就能恢复。此时真正起作用的是预算：如果它规定重试数不超过请求数的 10%，那么下游收到的是 1100 次而不是 2000 次，而恢复的门槛很可能就在这个差距里。

预算的另一个性质是它在请求量下降时自动收紧：窗口内的请求数减少，允许的重试数同比减少。这正是 0.3 那条链需要的——当调用方的前端流量下降时，重试量也跟着下降，给下游留出恢复窗口。次数上限没有这个性质，它是恒定的。

这条决策的代价要写清：预算的实现需要维护一个滑动窗口的计数，而窗口的粒度与长度都需要选择。粒度太细会让计数频繁过期（预算形同虚设），太粗会让它反应迟钝。可用的默认值是"一分钟窗口、每秒一个桶"。

### 关于第 9 与第 10 条的完整论证（重试为什么必须留下痕迹）

替代方案是"重试是运行期细节，不进日志"。这个方案在第 2.7 的不变量下有条件的成立：如果重试不改变请求内容，那么模型看到的输入没有变化，不变量不被违反。所以问题出在两种情形上。

第一种是重试改写了请求（降低 `max_tokens`、换用更小的模型、去除某些工具）。此时"这一次请求的输入"有两个版本，而日志若只记最终那一版，就无法回答"它第一次尝试时看到了什么"。这是对不变量的真实违反，因为模型确实看到过第一版输入。处置方式是把重试事件写进日志，并在事件里记录改写的内容。

第二种是重试次数本身。它不在"模型可见"的范围内，因此不进日志不违反不变量。但它是对可诊断性的损失：第 4 卷的失败归因需要知道"这一步的失败率是多少"，而重试成功会把它变成零。处置方式是把次数作为一条事件记录下来。

本课程两条都做，理由是代价很小而收益明确：一条事件几十个字节，而它换来的是"故障不会从记录里消失"。这条决策与 2.7 的 1.4 节是同一条原则的应用——宁可多记，也不要让某类问题永远无法回答。

## L3 实现（施工图）

### 3.1 文件结构

```
// plugins/retry.ts
// ┌─ 策略段 ──────────────────────────────────────────
// │  RetryPolicy：次数、基础延迟、抖动、预算比例、上界
// ├─ 判定段 ──────────────────────────────────────────
// │  shouldRetry(error, attempt, policy)：读错误的属性 + 查预算
// ├─ 延迟段 ──────────────────────────────────────────
// │  delayFor(attempt, policy, retryAfterMs)：优先用对方给的值
// ├─ 窗口段 ──────────────────────────────────────────
// │  RetryWindow：滑动窗口内的请求数与重试数
// └─ 挂载段 ───────────────────────────────────────────
//    on('model/failed') 决定是否重试；on('before:model') 改写请求
```

五段的分工与 2.2 的工具系统同形。这里的特殊之处在第四段：它是本篇唯一持有状态的部分，因此它的复位与并发安全需要单独考虑。

### 3.2 判定段

```ts
export function shouldRetry(error: LLMError, attempt: number, policy: RetryPolicy, window: RetryWindow): boolean {
  if (!error.retryable) return false                       // 判据来自错误本身
  if (attempt >= policy.maxAttempts) return false           // 次数上限
  if (!allowRetry(window, policy.budgetRatio)) return false // 预算
  return true
}
```

三个判断的顺序有意义：先看错误（最便宜且最确定），再看次数（本地状态），最后查预算（需要读窗口）。把最确定的条件放前面让日志里"为什么没有重试"的原因更准确——如果反序，一次不可重试的错误可能因为预算耗尽而被记录成"预算原因"，掩盖了真实原因。

### 3.3 延迟段

```ts
export function delayFor(attempt: number, policy: RetryPolicy, retryAfterMs?: number): number {
  if (retryAfterMs !== undefined) return Math.min(retryAfterMs, policy.maxDelayMs)  // 对方给了值
  const base = Math.min(policy.baseDelayMs * 2 ** (attempt - 1), policy.maxDelayMs)
  const jittered = policy.jitter ? base * (0.5 + Math.random()) : base             // 等量抖动
  return Math.min(jittered, policy.maxDelayMs)
}
```

要指出的是 `retryAfterMs` 也过了一次上界截断。这一点容易被忽略：对方给的值可能很大（例如配额按小时重置时给三千秒），而直接等那么久对一次交互来说不可接受。截断之后的处置是"不再重试并返回失败"，而不是"等一个更短的时间再试"——前者诚实，后者会让用户感觉系统卡住了。

### 3.4 窗口段

```ts
export class RetryWindow {
  #buckets = new Map<number, { requests: number; retries: number }>()
  record(kind: 'request' | 'retry', now = Date.now()): void { /* 累加到当前秒的桶 */ }
  totals(now = Date.now(), spanMs = 60_000): { requests: number; retries: number } { /* 汇总窗口 */ }
}
```

两处要点。第一，`now` 作为参数传入而不是在内部读时间——这条与 2.6 的可复现性要求同源，它让窗口的行为可以测试。第二，窗口汇总时需要清理过期桶，否则内存会随运行时间增长——这是一个容易被忽略的泄漏点。

### 3.5 挂载段

```ts
export function retryPlugin(ctx: Context, policy: RetryPolicy) {
  const window = new RetryWindow()
  return ctx.on('model/failed', async (e) => {
    if (!shouldRetry(e.error, e.attempt, policy, window)) return
    await ctx.session.append({ type: 'session/retry', attempt: e.attempt, reason: e.error.code })
    await sleep(delayFor(e.attempt, policy, e.error.retryAfterMs))
    e.retry()                                            // 通知循环发起重试
  })
}
```

这段代码里有三个与本篇分析对应的点。第一，重试事件被写入日志（L2 第 10 条）。第二，`retry()` 是循环提供的回调而不是插件自己重发请求——插件决定要不要重试，循环负责实际重发，这个分工保证重试仍然走同一条请求路径（因此配对与记录都不会漏）。第三，`on` 返回的撤销函数被返回给调用方，卸载插件即关闭重试（1.6）。

### 3.6 验收判据

| # | 判据 | 怎么检查 |
|---|---|---|
| 1 | 不可重试的错误不重试 | 让 provider 抛 `invalid_request`，核对只请求一次 |
| 2 | 可重试的错误按次数上限重试 | 让 provider 始终抛 `server_error`，核对请求次数等于上限 |
| 3 | `retryAfterMs` 优先于退避计算 | 抛带 `retryAfterMs` 的错误，核对等待时长在它附近 |
| 4 | `retryAfterMs` 超过上界时不再重试 | 抛一个很大的值，核对不重试并返回失败 |
| 5 | 抖动在区间内 | 连续计算多次延迟，核对落在 `[0.5, 1.5]` 倍区间 |
| 6 | 预算耗尽时停止重试 | 把预算设为 0，核对不重试 |
| 7 | 预算随请求量变化 | 记录少量请求后，核对允许的重试数同比下降 |
| 8 | 重试事件进入日志 | 触发一次重试，核对日志里出现 `session/retry` |
| 9 | 重试改写的请求被记录 | 在 `before:model` 里改写请求，核对日志里有对应内容 |
| 10 | 卸载插件后不再重试 | 卸载后触发失败，核对只请求一次 |
| 11 | 窗口的过期桶被清理 | 长时间运行后核对内存中的桶数量有界 |
| 12 | 重试成功后返回成功结果 | 让 provider 第一次失败第二次成功，核对最终返回成功且次数为二 |

第 4 与第 9 条是最容易漏掉的两条：前者检验上界截断后的处置（不重试而不是短等），后者检验改写请求时的记录。它们都不属于"正常路径"。

先做判定与延迟（判据 1、2、3、4、5），再做窗口与预算（判据 6、7、11），然后做挂载与日志（判据 8、9、10），最后检查端到端（判据 12）。

### 3.8 实现里最容易写错的三处

第一处是判断顺序。正确做法是先看错误属性、再看次数、最后查预算（3.2 已给出理由）；常见错误是把预算检查放在最前，于是预算耗尽时所有失败的记录都变成"预算不足"，而真实原因（不可重试）被掩盖。

第二处是抖动的随机源。正确做法是每进程独立的随机源；常见错误是使用固定种子（为了测试可复现），而它在多副本部署时会让所有副本产生相同的抖动，等于没有抖动。可用的折中是测试时注入随机源，生产时用系统随机。

第三处是窗口的清理。正确做法是汇总时清理过期桶；常见错误是只累加不清理，于是内存随运行时间增长——而这个泄漏很隐蔽，因为它的表现是"进程用了几小时后内存占用变高"，与重试逻辑的关联不会从堆栈里看出来。

### 3.9 一次失败请求的完整时序

把本篇与前后几篇串起来，一次带重试的失败请求的完整序列如下（括号里是责任方）。

```
1 循环发起请求        （2.7 的循环）      记录 turn 开始
2 模型层失败          （2.1 的 provider） 抛出带 retryable 与 retryAfterMs 的错误
3 发出 model/failed   （2.4 的事件）     通知型，不改变结果
4 重试插件判定        （本篇）           读错误属性、查次数、查预算
5 写重试事件          （2.7 的日志）     记录第几次重试与原因
6 等待                （本篇）           优先用 retryAfterMs，否则指数退避加抖动
7 重试（可能改写请求） （2.7 的循环）     改写内容同样写入日志
8 成功或耗尽次数      （2.7 的循环）     成功则继续，失败则按最终错误返回
```

这张时序里有三个检查点。第 4 步是"判据来自错误"的落点；第 5 与第 7 步是"重试必须留痕迹"的落点（L2 第 9、10 条）；第 8 步是"失败要有明确结果"的落点——耗尽次数时返回的错误应当携带尝试次数，让用户能判断下一步该做什么。

三个检查点的共同形态是把运行期的策略行为记录成可重建的事实。这正是第 3 卷每一篇共同的检查项：新机制可以改变系统的行为，但它不能让历史变得不可解释。

## L5 语法速查

### 5.1 术语表

| 术语 | 在本篇里的准确含义 | 容易误解为 |
|---|---|---|
| 瞬时故障 | 再试一次可能成功的失败 | "短暂的故障"（时长不是判据，可重试性才是） |
| 退避 | 两次重试之间的等待 | "延迟"（延迟是请求本身的耗时） |
| 指数退避 | 等待随次数按倍数增长 | "越来越慢"（它是有上界的增长） |
| 抖动 | 等待时间上的随机偏移 | "随机延迟"（它有区间与下界） |
| 重试预算 | 一段时间内重试数与请求数的比例上限 | "次数上限"（后者限制单个请求） |
| 熔断 | 失败率超阈值时停止发送请求 | "关闭重试"（熔断连首次请求也不发） |
| 幂等 | 执行一次与多次效果相同 | "可重复调用"（那只是重试的必要条件） |

### 5.2 命令速查

| 目的 | 命令 | 说明 |
|---|---|---|
| 跑重试契约测试 | `node tests/ch03/t1-retry.mjs` | 十二条判据 |
| 负向验证 | `node grade/ch03/negative-check-retry.mjs` | 四类错误实现应全部被抓 |
| 看日志里的重试 | `rg -c 'session/retry' <日志文件>` | 与请求数比较得到重试比例 |
| 找无条件重试 | `rg -n 'retry' src/ \| rg -v 'retryable'` | 命中即说明重试没读错误的属性 |

### 5.3 三条容易踩的规则

第一条，重试与否读错误的属性，不要在重试模块里按状态码判断。

第二条，抖动用每进程独立的随机源。固定种子在多副本下等于没有抖动。

第三条，只要重试改写了请求，就必须在日志里记录改写内容。否则日志与实际发出的请求不一致。

## L7 挑战题（不给答案）

第一题：给重试加降级。 当重试次数用尽时，改用一个更小或更快的模型返回一个可接受的结果。设计这个机制，并说明它与"重试"在日志上如何区分。

第二题：设计跨进程的熔断。 多个进程调用同一个下游，如何共享熔断状态？给出方案并说明它的一致性要求。

第三题：让重试预算自适应。 固定比例的预算在负载变化时可能过松或过紧。设计一个自适应的方案，并说明它的风险（自适应策略可能振荡）。

第四题：重试与取消。 用户取消一次请求时，正在进行中的重试应当如何处置？给出方案并说明它对接地与日志的影响。

第五题：论证"重试应写进循环"。 构造一个场景，说明插件形式的重试不如直接写在循环里，并给出依据。

第六题：不可重试错误的补救。 参数错误不能靠重试解决，但有些可以靠修正参数后重发（例如 `max_tokens` 超限时减半）。设计这个机制，并说明它与重试的边界。

## L9 仍未解决（这一篇自己的缺陷）

| 缺陷 | 后果 | 修法 | 当初为什么这么写 |
|---|---|---|---|
| 预算与熔断状态是进程内的 | 多进程部署时总量仍然放大 | 共享状态（挑战题第二题） | 本卷是单进程的 |
| 重试只覆盖模型请求 | 工具失败的瞬时问题无法靠重试缓解 | 让工具声明幂等性后对幂等工具启用重试 | 幂等性声明在本卷还没有被真正使用 |
| 退避参数是静态的 | 不同下游的最优参数不同 | 按服务配置策略 | 静态参数在本卷的下游数量下够用 |
| 没有区分"下游限流"与"下游故障"的熔断阈值 | 两者的正确处置不同（前者等，后者退） | 按错误类型分别统计失败率 | 本卷的可观测还没建立（3.6） |
| 重试的日志事件没有携带完整的请求内容 | 重建"第一次尝试看到什么"只能依赖改写事件 | 在重试事件里带上改写前后的摘要 | 完整内容体积大，摘要在多数排查里够用 |
| 没有处理"重试期间会话被结束" | 会话结束后重试仍在进行 | 把会话的取消信号接到重试的等待上 | 取消机制在第 3.4 篇才建立 |

第一条与第六条属于边界与缺失的能力，第二条属于本卷的有意简化，第四条属于可观测依赖，第三条与第五条属于参数与信息粒度的简化。第四条值得单独标记：它让本卷的熔断只能按总体失败率判断，而"下游在限流"与"下游在故障"这两种情形的最优处置相反（前者应当等待，后者应当退避），把它们混在一起会让熔断策略在两个方向上都偏离最优。

### 问题升级练习

模糊问题：「我该怎么让系统对瞬时故障更健壮？」

升级后的精确问题：

> 对瞬时故障的健壮性至少包含三件互相制约的事：判断（哪些失败值得再试）、节奏（退避与抖动的参数）、以及限额（次数、预算、熔断）。
> 判断与限额互相制约——放宽判断（把更多错误视为可重试）会让限额更快耗尽。
> 我能不能为这三件事各找出一条**可检查的判据**？
> 特别是：有没有哪一条判据，是**能在一个模拟过载的演练里被验证的**？

提升点说明：原问题无法回答，因为"更健壮"没有边界。升级后的版本把它拆成三件具体的事，指出前两件的制约关系（放宽判断会加快限额耗尽），并追加以一个更强的问题：哪一条判据能在模拟过载的演练里验证。

一处需要修正的预判：0.5.2 把"重试过程进日志的方式"标为强依赖，但没有说清它依赖的是哪一条不变量。读完之后要补上：它依赖的是 2.7 的 1.7 节那条区分——"重试次数"不进日志不违反不变量（它不在模型可见范围内），而"重试时改写了请求"必须进日志（因为模型确实看到了改写后的输入）。这个区分很重要，它避免了一种过度设计：把所有运行期细节都写进日志。

通向下一篇的桥。 本篇处理的是"失败之后怎么办"，而它留下了一个没有答案的问题：有些调用不该被允许发生。重试解决的是"已经发生的失败"，而守卫要在调用发生之前判断它是否被允许——两者的关系是"一个管事后，一个管事前"。

下一篇 `3.2 守卫、审批与沙箱` 处理这件事。它与本篇的连接点有两处：一是配对（守卫拦下的调用同样要产出结果，否则 2.7 的序列不合法），二是重试与拦截的先后（一个被守卫拒绝的调用不应当被重试——而这条规则的实现依赖本篇建立的可重试性判据）。

## 本篇新词

技能（skill） 指一段可复用的做法：它有适用条件（什么时候用）、步骤（怎么做）、以及不适用条件（什么时候别用）。它与工具的区别是技能不改代码，它改的是模型的行为——工具提供能力，技能提供方法。

渐进披露（progressive disclosure） 指按需分层地把技能内容给模型看：先给一句话的描述，需要时再给全文，最后才给附加资源。它的动机是成本——技能的全文通常比它的描述大一到两个数量级，而多数技能在多数任务里用不上。

元数据层（metadata layer） 指技能的名称与一句话描述。它是披露的第一层，也是唯一始终可见的一层。它的写法直接决定技能会不会被触发——一个描述写得无法匹配的描述，等于这个技能不存在。

触发（trigger） 指模型（或系统）判定"当前任务需要这个技能"。它的实现有几种：由模型按描述判断、由系统按关键词或检索匹配（复用 4.1 的相关性机制）、或由用户显式指定。

适用条件（precondition） 指技能成立的前提。它与 1.4 的接口前置条件同构：一个没有适用条件的技能会在不该用的地方被用，而它的后果通常比"不用"更糟（因为模型会带着错误的方法去做）。

技能冲突（skill conflict） 指两个技能给出不一致的做法。它的来源有两类：同一件事的两种正当做法（例如两种测试策略）、以及一个技能过时而另一个是新版。两类冲突的处置不同，而系统的报告应当能区分它们。

技能过时（skill staleness） 指技能描述的做法与当前系统不再一致（API 变了、目录变了、依赖换了）。它的危害是隐蔽的——过时的技能往往仍能被触发，而它给出的步骤会失败或产生过时的产物。

技能验证（skill validation） 指判断一个技能是否真的有效。它需要两样东西：一个能触发它的任务、以及一个能判断结果好坏的判据（通常是一次可运行的检查，例如测试通过）。

## 第 0 节 · 学完这一篇你能做出什么

### 0.0 先行组织者：四个问题

```
┌──────────────────────────────────────────────────────────────────────┐
│  ① 什么时候该沉淀成技能 —— 技能与记忆、工具的边界      → 1.1          │
│  ② 模型怎么知道它存在 —— 元数据层与触发                → 1.2、1.3     │
│  ③ 怎么读它的内容 —— 按需加载与披露成本                → 1.2          │
│  ④ 怎么知道它有效 —— 验证、过时与冲突                  → 1.5–1.7      │
└──────────────────────────────────────────────────────────────────────┘

 一句话串起来：什么时候沉淀 → 模型怎么发现 → 怎么按需读取 → 怎么知道它有效
```

这张图的关键线索在第二块：技能的可用性由它的描述决定，而不是由它的内容决定。一个内容很好但描述写得无法匹配的技能不会被用到。而一个描述写得宽泛的技能会在不该用的地方被用上——两个方向的失效都发生在元数据层。

### 0.1 一个具体的判断：三层的大小差

设一个技能的描述约 100 token、主体约 1500 token、附加资源（模板、脚本）约 10000 token。如果系统有二十个技能，三层各自全量注入的成本是：

| 策略 | 注入量 | 相对成本 |
|---|---|---|
| 只给描述 | 20 × 100 = 2000 token | 1 倍 |
| 描述 + 全部主体 | 20 × 1600 = 32000 token | 16 倍 |
| 全量（含资源） | 20 × 11600 = 232000 token | 116 倍 |

第三行已经超过了多数上下文窗口。这个量级差就是渐进披露的全部理由，而它同时说明第二层的加载判据必须准——如果二十个技能里有一半的主体被加载，成本仍然可观。

### 0.2 本篇建立的三项判据

第一项用于判断一个描述是否可用：问"一个不知道这个技能存在的模型，看到这个描述会知道它适用于哪些情况吗"。这条判据的具体检验方式是把描述给另一个模型看，并让它判断三个任务该不该用这个技能——描述的质量可以被实测。

第二项用于判断一个技能是否仍然有效：问"按它的步骤做一遍，能通过吗"。这条判据要求技能带一个可运行的检查（通常是测试或一条命令），否则它的有效性无法被验证。

第三项用于判断一次技能加载是否值得：问"这个技能的主体被加载之后，任务的做法真的变了吗"。它的观测方式是 3.6 的度量（加载次数与任务结果），而判据是"加载之后的做法与不加载不同"——只是被读了却没有改变做法的技能是装饰。

### 0.3 十分钟练习：一个技能的三层结构

下面这段代码解析一个技能文件的前置元数据，并对比三层的字节数。

```js
import { readFileSync } from 'node:fs'
const raw = readFileSync('skills/example/SKILL.md', 'utf8')

function parseFrontmatter(text) {
  const m = /^---\n([\s\S]*?)\n---\n([\s\S]*)$/.exec(text)
  if (!m) throw new Error('缺少前置元数据')
  const meta = Object.fromEntries(
    m[1].split('\n').filter(Boolean).map((line) => {
      const i = line.indexOf(':')
      return [line.slice(0, i).trim(), line.slice(i + 1).trim()]
    }),
  )
  return { meta, body: m[2] }
}

const { meta, body } = parseFrontmatter(raw)
console.log('名称：', meta.name, '　描述长度：', meta.description.length)
console.log('三层大小（字符）：', { 元数据: JSON.stringify(meta).length, 主体: body.length })
```

这段实现里三处对应本篇的三个概念：前置元数据是元数据层（唯一始终可见）、`body` 是主体层、而技能目录下的其他文件是资源层。解析失败时抛错而不是当成没有元数据（`缺少前置元数据`）——因为没有元数据的技能无法被触发，静默接受它会让它永久不可用。

> **高分要点**：说出"技能加渐进披露"这个组合，并解释为什么不能把全部技能全文注入（成本差一到两个数量级）。只说"写进系统提示"会面临成本与准确率的双重问题。

### 0.5.3 三个连锁影响

第一，技能的描述质量决定系统的学习效果。 这是本篇最直接的后果：如果沉淀下来的做法写成了"处理各种情况"（无法匹配），那么它不会被触发，而系统会表现成"学会了但没记住"（与 4.1 的 0.1 是同一类现象）。描述是这个系统的触发入口，因此它值得被当作接口文档来写。

第二，技能会与记忆争抢上下文，而它们的预算需要分开。 记忆的注入预算（4.1 的 1.3）与技能的元数据层都必须常驻或按需注入，而两者的总量受限。处置方式是给技能元数据一个固定的预算（因为它必须常驻才能被触发），而技能主体与记忆共享剩余空间（因为两者都是按需的）。

第三，技能过时是演化系统里最隐蔽的失效。 它与其他失效的区别在于它不会报错——过时的技能仍能被触发，而它给出的步骤会失败，或者更糟：产生一个看起来对而实际过时的产物。因此技能需要带"上次验证时间"，而未经验证的技能应当被标记（与 3.6 的护栏指标同理：一个没有验证的资产会被默认信任）。

### 0.5.4 它与本书其余部分的关系

本篇的技能是文本型的（一份说明加可选的脚本），由模型读取并执行。把技能编译成代码（一个函数）是另一条路，它更可靠而更不灵活（改技能要改代码）。本课程选择文本型的原因是它与演化（4.5）配合更好——改一段文本的门控成本远低于改代码。

## L0 要解决的问题

### 0.1 现象一：技能写了，但从不被触发

第一个现象与 4.1 的 0.1 同形，而它的成因更集中。三个具体原因：描述写得太宽（"处理代码相关的任务"，模型无法判断什么时候用）、描述写得太窄（"当用户要求重构 TypeScript 的可选链时"，多数情况匹配不上）、或者描述与模型的用词习惯不符（技能里写"提交前检查"，而任务里说"push 之前先看看"）。

三者的共同点是它们都发生在元数据层（0.0 的关键线索），而它们的修法都是把描述写成可匹配的形式：写清"什么时候用"（触发条件）而不是"这个技能是关于什么的"（主题）。描述回答的是"何时"，不是"什么"。

### 0.2 现象二：全量注入撑爆上下文

第二个现象是披露策略的错误：把所有技能的全文（甚至附加资源）都注入。0.1 的量化给出了后果——二十个技能全量注入需要二十三万 token，已经超过多数窗口。

它的表现往往不是"报错"，而是模型的行为变差：上下文被大量与当前任务无关的做法占据，而它们会干扰模型对当前任务的判断（这与 3.3 的"无关内容占用注意力"是同一机制）。

### 0.3 现象三：技能过时，而它不会报错

第三个现象是技能与系统的脱节。目录结构变了、命令改了、依赖升级了，而技能文档还写着旧的做法。它的特殊危险在于不报错：技能被触发，步骤被执行，而某一步产出的东西是过时的（或者命令失败被模型绕过，产出一个不经检查的结果）。

它的防线是"上次验证时间"与"验证方式"（0.2 的第二项判据）：一个带可运行检查的技能可以被定期重新验证。而没有检查的技能只能靠人记得。因此"技能带一个可运行的检查"不是附加要求，它是可维护性的前提。

### 0.4 现象四：技能被读了，但模型没照做

第四个现象是遵从问题。模型读到了技能的步骤，而在执行时跳过了其中一步（通常是看起来不必要的那一步，例如"先跑一次基线测试"）。

它的成因有两个，而处置不同。成因一是步骤没有被写成可检查的（"仔细检查"这类描述无法被验证）。成因二是技能太长，而长技能里的步骤会被跳过——这与人的阅读行为相同。处置方式是把关键步骤写成可运行的命令（跑一条命令比"仔细检查"更难被跳过），并让技能尽量短（每一步都有存在的理由）。

### 0.5 这一篇要正面回答的四个问题

第一，什么该沉淀成技能，它与记忆、工具的边界在哪（1.1）。第二，怎么让模型发现它、怎么按需读它（1.2、1.3）。第三，怎么判断它有效、过时与冲突（1.5–1.7）。第四，适用条件为什么必须显式写出（1.4）。

四个问题里第四最容易被忽略，而它的缺失后果最重——没有"不适用条件"的技能会在错误的场合被使用（1.4）。

## L1 设计与原理

### 1.1 技能、记忆、工具的边界

三者都在"扩大系统的能力"，而它们扩大的东西不同。

| 维度 | 工具 | 记忆 | 技能 |
|---|---|---|---|
| 提供什么 | 能力（能做的事） | 事实（是什么） | 方法（怎么做） |
| 形态 | 代码（可执行） | 文本条目 | 文本（加可选脚本） |
| 作用面 | 系统的动作 | 模型的输入 | 模型的行为 |
| 生效方式 | 被调用 | 被注入 | 被读取并遵循 |
| 验证方式 | 契约测试 | 相关性评估 | 按步骤做一遍能否通过 |

第四行是三者最本质的区别：工具与记忆的作用是确定的（调用一个函数、注入一段文本），而技能的作用依赖模型是否遵循。因此技能的可靠性上限低于前两者，这也是为什么关键步骤应当被写成可运行的命令（0.4）。

第五行说明验证方式为何不同：技能的验证必须包含一次真实的执行，而工具只需要输入输出对齐。

### 1.2 三层披露与成本

三层的划分与各自的用途在 0.1 已经量化，这里补充每一层的设计要点。

元数据层必须常驻（否则无法被触发），因此它的预算是固定的：N 个技能 × 描述长度。设计要点是描述要写触发条件（0.1 的修法），并且要与技能的 `name` 保持一致（`name` 是标识，`description` 是触发依据）。

主体层按需加载。设计要点是它在被加载时是与当前任务同处一个上下文的，因此它会参与该任务后续所有轮次的前缀（影响缓存命中率，3.6 的 1.5）。这条影响给出一个实践建议：主体的加载应当发生在任务的早期（越早加载，后续轮次越多地受益于缓存），而不是在任务进行到一半时插入。

资源层按需读取（通常是文件与模板）。设计要点是模型需要知道资源的存在与用途，因此主体里应当列出它们——但不要列出内容（那会把资源层退化为主体层）。

三层的关系可以概括为：元数据回答"何时用"，主体回答"怎么做"，资源回答"用什么做"。

### 1.3 触发与选择

触发的实现有三种，而它们的组合是常见做法。

由模型按描述判断是最直接的一种：元数据常驻，模型看到描述后自行决定是否要求加载主体。它的优点是灵活（模型能理解语义），缺点是不可控也不可测（判断发生在模型内部，系统只能观测结果）。

由系统按检索匹配复用 4.1 的机制：把当前任务当作查询，对技能的描述与关键词做相关性打分，超过阈值就预加载。它的优点是可控可测（阈值与权重都是参数），缺点是可能漏掉语义相关而用词不同的技能。

由用户显式指定是最可靠的一种（`/skill-name`），而它是兜底而非主路径——用户不应该需要记住有哪些技能。

本课程的做法是三者组合：显式指定优先，其次是系统检索（用于预加载），最后把全部描述常驻由模型决定（用于系统没匹配到的情况）。这个组合的成本是元数据必须常驻，而它是可以接受的（0.1 的第一行：二十个技能约 2000 token）。

### 1.4 适用条件与不适用条件

适用条件是技能成立的前提，而不适用条件同样必须写。理由有三个。

第一，多数做法的方法在错误的场合下会产生误导。一个"先写测试再改代码"的技能在探索性任务里是错的（此时还不知道要测什么）。一个"重构时保持行为不变"的技能在修 bug 时是错的（行为本来就要变）。

第二，模型倾向于套用已知的做法。它读到技能之后会更倾向于使用它，因此适用条件写得越宽，误用的机会越大。不适用条件是这条倾向的对冲。

第三，不适用条件是诊断的输入。当一次失败被归因为"用错了方法"（4.4 的诊断），判据正是"这个技能的不适用条件是否覆盖了当时的情形"。如果技能没写不适用条件，那么这次失败无法被归因到技能上——它会被误归因为模型的问题。

```ts
interface SkillMeta {
  readonly name: string
  readonly description: string        // 何时用（触发条件，不是主题）
  readonly appliesWhen?: string[]      // 适用条件
  readonly doesNotApplyWhen?: string[] // 不适用条件
  readonly verifiedAt?: number         // 上次验证时间（0.3 的防线）
  readonly check?: string              // 可运行的验证命令（0.2 的第二项判据）
}
```

六个字段里 `description` 与 `doesNotApplyWhen` 是触发与误用的两个闸门，`verifiedAt` 与 `check` 是可维护性的两个支点。

### 1.5 技能的验证

验证一个技能包含两步：触发一次（证明它能被找到）与执行一次（证明它有效）。

第二步需要技能自带检查（`check` 字段）。检查的形式通常是"跑一条命令并核对结果"，例如一个技能规定"提交前跑 `pnpm run typecheck && pnpm run lint`"，那么它的检查就是这两条命令通过。

```ts
export async function validateSkill(skill: Skill, ctx: SkillContext): Promise<SkillValidation> {
  const task = skill.check ? ctx.makeTaskFor(skill) : null
  if (!task) return { ok: false, reason: '缺少可运行的检查（check 字段）' }   // 无检查即无法验证
  const loaded = await loadSkillBody(skill.name, ctx)                        // 验证层一：能加载
  if (!loaded) return { ok: false, reason: '主体无法加载' }
  const result = await ctx.runCheck(skill.check)                             // 验证层二：能通过
  return { ok: result.ok, reason: result.summary, checkedAt: ctx.now }
}
```

这段实现的顺序值得注意：先验证能加载，再验证能通过。两者的失败原因完全不同（前者是格式问题，后者是内容过时），而把它们合成一条"验证失败"会让诊断失去信息。

### 1.6 技能的过时与版本

过时的三种形态与各自的信号不同。

命令过时最容易发现（命令不存在或报错）。路径过时次之（读不到文件）。做法过时最隐蔽——命令仍然能跑，路径也存在，而它做的事已经不是当前推荐的做法了（例如某个流程已经简化，而技能仍然描述着旧的三步）。

三条防线。第一，`check` 命令（它挡住前两类）。第二，`verifiedAt` 与定期重新验证（它让第三类有机会被发现）。第三，技能与它所描述的系统的位置关系——如果技能写在它所描述的代码库里（用相对路径、跟着代码一起改），过时会被改动时的 review 顺带发现。如果写在别处，过时只能靠定期检查。

因此技能应当尽量与被描述的资产放在同一个仓库里，这条建议与实际做法（`.agents/skills/` 在仓库内）一致。

### 1.7 技能冲突与优先级

冲突的两类（本篇新词）需要不同的处置。

同一件事的两种正当做法（例如两种测试策略）：处置是明确优先级（在新手场景用哪一种），而不是删除一个——因为两种做法在各自的场景下都对。优先级可以写在各自的 `appliesWhen` 里。

新旧的冲突（一个过时而另一个是新版）：处置是废弃旧的（标注 `deprecated` 或直接删除），因为同时存在会随机命中。

冲突的发现方式有两种：静态的（检查两个技能的 `appliesWhen` 是否重叠且做法不一致——这需要语义判断，通常靠人工）与动态的（观测两个技能在同一次任务里是否都被加载过——这是可自动的，判据是"同一次任务里加载了两个 `appliesWhen` 重叠的技能"）。动态方式是可实现的，因此它应当作为冲突报告的来源。

### 1.8 两次追问

工程侧的问题是什么时候该把一个做法沉淀成技能。判据是"它被重复做过至少两次，而且第二次做的时候参考了第一次"。一次性的做法不值得沉淀（写技能的成本高于直接做），而"第二次参考第一次"说明它已经形成了方法。

产品侧的问题是技能对用户意味着什么。多数用户不关心技能的存在，而他们关心两件事：系统在做什么（能不能看到它加载了哪个技能）以及为什么这么做（技能里的理由）。因此技能的加载应当可见（一条事件），而技能里的理由应当被写出来（而不是只有步骤）——这与 2.2 的"给模型看的描述"是同一条原则：理由让行为可以被理解，而可理解的行为才能被用户接受。

| # | 决策 | 我们的选择 | 替代方案 | 代价落在谁身上 |
|---|---|---|---|---|
| 1 | 沉淀的门槛 | 被重复做过至少两次，且第二次参考了第一次 | 想到就写 | 可能漏掉一次性做法；换来技能库不被噪音填满 |

| 4 | 元数据的预算 | 固定（必须常驻） | 与主体共享预算 | 描述要短；换来技能可被触发 |
| 5 | 主体的加载时机 | 任务早期 | 需要时随时加载 | 可能提前加载了用不上的技能；换来缓存命中率 |
| 6 | 资源层的暴露 | 列出用途与路径，不给内容 | 全部内联进主体 | 模型要多读一次文件；换来主体不被撑大 |

| 9 | 验证方式 | 自带可运行检查（`check` 字段） | 人工定期检查 | 写技能要多想一步；换来可自动化验证 |
| 10 | 验证失败的报告 | 区分"无法加载"与"检查不通过" | 统一报"验证失败" | 报告字段更多；换来诊断有方向 |

| 12 | 冲突的发现 | 动态（同一次任务加载了两个重叠技能） | 只看静态描述 | 要记录加载事件；换来可自动化 |

其中两条值得展开，因为它们的选择在实践中经常被做成另一个。

### 关于第 3 条的完整论证（描述为什么写"何时"而不是"什么"）

替代方案是按主题写描述："本技能关于 TypeScript 重构"。它在人类阅读的文档里是自然的写法，而在触发场景下失效——因为触发需要的是一个判断，而不是一个主题。

三个具体的差别。第一，主题无法区分"该用"与"不该用"：同一个主题下有些情形该用（大规模重命名）而有些不该用（探索性的临时改动）。第二，主题与任务的措辞往往对不上：任务里说"这个函数太长了我拆一下"，而主题写的是"重构"。第三，写触发条件时必须想清楚边界（什么时候算触发），而写主题时可以含糊——这个强制思考本身就是一个收益（它正是 1.4 的适用条件）。

因此描述的写法是一条链：`description` 写触发条件，`appliesWhen` 写更细的边界，`doesNotApplyWhen` 写反面。三者合起来构成触发与误用的完整闸门。

### 关于第 11 条的完整论证（技能为什么应当与它描述的资产同仓库）

替代方案是把技能集中放在一个独立的仓库或目录下，与代码分开维护。它的好处是技能可以被多个项目复用，代价在过时上。

具体来说，同仓库的技能够享受到三种"顺带发现"：改动的 review（改了目录结构时，review 的人会在 diff 里看到受影响的技能）、测试的影响范围（技能里的 `check` 命令如果引用了被改的路径，测试会失败）、以及版本的一致性（技能的版本与代码的版本天然对齐）。

分开维护时三种都没有。剩下的唯一手段是定期跑验证（1.6 的第二条防线），而定期验证的频率往往低于改动的频率，因此过时会在两者之间的窗口里存在。

复用的收益与过时的代价相比，本课程选择同仓库——因为过时的技能会产生错误的产物，而复用可以通过复制解决（复制的成本是维护两份，而它在技能数量少时是可接受的）。

## L3 实现（施工图）

### 3.1 文件结构

```
// plugins/skills.ts
// ┌─ 索引段 ── 扫描技能目录，解析元数据（只读前置元数据）
// ├─ 触发段 ── 三种触发方式的组合（显式 / 检索 / 常驻描述）
// ├─ 加载段 ── 按需读取主体与资源，并记一条加载事件
// ├─ 验证段 ── 运行 check 命令并更新 verifiedAt
// └─ 冲突段 ── 从加载事件里发现重叠
```

五段与前面各节一一对应，其中索引段刻意只读元数据（不读主体与资源）——这是渐进披露在实现层的形态：索引阶段的开销与技能数量成正比而与技能大小无关。

### 3.2 索引与前置元数据

```ts
const SKILL_FILE = 'SKILL.md'
const LIMITS = { name: 64, description: 1024 }   // 与规范的字段限制一致

export function indexSkill(dir: string): SkillMeta {
  const text = readFileSync(join(dir, SKILL_FILE), 'utf8')
  const m = /^---\n([\s\S]*?)\n---\n/.exec(text)
  if (!m) throw new Error(`${dir}: 缺少前置元数据`)
  const meta = parseYaml(m[1]) as SkillMeta
  if (!meta.name || !meta.description) throw new Error(`${dir}: name 与 description 必填`)
  if (meta.description.length > LIMITS.description) throw new Error(`${dir}: 描述超过 ${LIMITS.description} 字符`)
  return meta
}
```

三处校验（有元数据、必填字段、长度限制）都在索引阶段完成，因此一个格式不合规的技能会在启动时报错而不是在触发时静默失效——这条与 1.4 的"误配置要响亮失败"是同一条原则。

### 3.3 触发段

```ts
export function selectSkills(task: string, index: readonly SkillMeta[], opts: SelectOptions): SkillMeta[] {
  const explicit = opts.explicitName ? index.filter((s) => s.name === opts.explicitName) : []
  if (explicit.length) return explicit                                  // 显式指定优先
  const scored = index
    .map((s) => ({ s, score: relevance(task, s.description) }))          // 复用 4.1 的机制
    .filter((x) => x.score >= opts.threshold)
    .sort((a, b) => b.score - a.score)
  return scored.slice(0, opts.maxLoad).map((x) => x.s)
}
```

三种触发方式里这里实现了两种，第三种（全部描述常驻、由模型判断）由注入层负责——它不在这个函数里，因为它不产生"加载"这个动作（描述本来就在上下文里）。

### 3.4 加载段

```ts
export async function loadSkillBody(name: string, ctx: SkillContext): Promise<string | null> {
  const dir = ctx.skillDirFor(name)
  const meta = indexSkill(dir)                                          // 再校验一次（可能被改过）
  const body = readFileSync(join(dir, 'BODY.md'), 'utf8')
  await ctx.appendEvent({ type: 'skill/load', name, at: ctx.now })       // 加载事件（用于冲突检测与观测）
  const resources = listResources(dir)                                  // 只列用途与路径
  return [`# 技能：${meta.name}`, meta.description, '', body, '', '## 可用资源', ...resources.map((r) => `- ${r.purpose}：${r.path}`)].join('\n')
}
```

这段实现的三处要点：加载时再校验一次元数据（文件可能被改）、加载产生一条事件（冲突检测与观测都依赖它）、资源只列用途与路径（L2 第 6 条）。

### 3.5 验证段

```ts
export async function runValidation(name: string, ctx: SkillContext): Promise<SkillValidation> {
  const meta = indexSkill(ctx.skillDirFor(name))
  if (!meta.check) return { ok: false, phase: 'static', reason: '缺少 check 字段' }
  const body = await loadSkillBody(name, ctx)
  if (body === null) return { ok: false, phase: 'load', reason: '主体无法加载' }
  const result = await ctx.runCheck(meta.check)
  return { ok: result.ok, phase: 'check', reason: result.summary, checkedAt: ctx.now }
}
```

`phase` 字段区分三个阶段（静态、加载、检查）——这就是 L2 第 10 条的实现：三个阶段的失败原因不同，而诊断需要知道是哪一阶段。

### 3.6 验收判据

| # | 判据 | 怎么检查 |
|---|---|---|
| 1 | 缺少前置元数据时报错 | 造一个没有前置元数据的技能目录 |
| 2 | 描述超长时报错 | 造一个描述超限的技能 |
| 3 | 索引阶段不读主体 | 核对索引的读取文件列表只有 `SKILL.md` |
| 4 | 显式指定优先于检索 | 显式指定一个低相关技能，核对它被选中 |
| 5 | 检索低于阈值时不加载 | 用一个不相关任务，核对不加载 |
| 6 | 加载产生一条事件 | 加载后核对日志 |
| 7 | 资源只列用途与路径 | 核对加载文本里没有资源内容 |
| 8 | 验证区分三个阶段 | 分别构造静态失败、加载失败、检查失败 |
| 9 | 验证成功更新 `verifiedAt` | 跑一次验证，核对时间被更新 |
| 10 | 同一次任务里两个重叠技能触发冲突报告 | 构造两个 `appliesWhen` 重叠的技能并都加载 |
| 11 | 不适用条件参与误用判定 | 构造一次在 `doesNotApplyWhen` 覆盖下的使用，核对被报告 |
| 12 | 元数据总预算不随技能数超限 | 索引 N 个技能，核对描述总量 |

第 8 与第 10 条是这一篇的特色判据（验证的分阶段与冲突的动态发现），第 12 条检验元数据预算（它是元数据必须常驻这一决定的直接约束）。

### 3.7 实现顺序

先做索引与校验（判据 1、2、3、12），再做触发（判据 4、5），然后做加载（判据 6、7），最后做验证与冲突（判据 8、9、10、11）。

### 3.8 实现里最容易写错的三处

第一处是索引阶段读了主体。正确做法是索引时只读前置元数据。错误做法是把整个 `SKILL.md` 读进来再取元数据（或者干脆把全部技能文件读进内存）。后者的代价与技能大小成正比，而它会让"启动时间随技能库变大而增长"——渐进披露的收益在启动那一刻就被这条实现吃掉了。

第二处是加载事件的缺失。正确做法是每次主体加载都追加一条事件。错误做法是只在内存里记一个"已加载"标记。后者的代价是冲突检测与观测都失去依据（1.7 的动态方式与 0.2 的第三项判据都依赖它），而那意味着这两个能力只能靠人工。

第三处是描述的校验缺失。正确做法是索引时校验必填字段与长度。错误做法是接受任何元数据。后者的代价是格式不合规的技能静默地永久失效（它存在但永远不会被触发），而没有人会注意到——因为没有错误发生。这与 1.4 的"误配置要响亮失败"是同一条原则。

## L4 运行与验证

### 4.1 三层验证

第一层是契约测试：按 3.6 的十二条判据逐条检查，用一组构造出来的技能。

第二层是描述质量实测（0.2 的第一项判据）：把描述给一个模型看，让它判断若干任务该不该用这个技能，看它的判断与预期是否一致。这一层是唯一能验证"描述是否可匹配"的方式。

第三层是端到端验证：跑一个需要该技能的任务，核对做法确实变了（判据是产物与不用技能时不同）。这一层检验 0.2 的第三项判据——只被读了却没改变做法的技能是装饰。

```powershell
node tests/ch04/m2-skills.mjs                 # 契约测试（十二条判据）
node grade/ch04/negative-check-skills.mjs     # 判分器的鉴别力
node tools/describe-eval.mjs                  # 描述可匹配性实测
node tools/skill-validate.mjs --all           # 全量验证并刷新 verifiedAt
```

### 4.2 判据

做完这一篇的标志有三条：十二条判据全部通过。描述实测里模型对一个技能的判断与预期一致（例如五个任务里判断对四个）。以及端到端验证显示做法确实因技能而不同。

### 5.3 三条容易踩的规则

第一条，描述写"何时用"而不是"关于什么"。描述是触发入口。

第二条，不适用条件必须写。它是模型套用已知做法这条倾向的对冲。

第三条，技能要带一个可运行的检查。没有检查的技能无法验证，也无法发现过时。

### 必须能独立做到的

| 要写什么 | 判据 |

| 要写什么 | 判据 |

## L7 挑战题（不给答案）

第一题：技能的自动生成。 从一次成功的任务记录里自动提取技能草案。设计这个流程，并说明它如何避免产生污染（一个错误做法被沉淀）。

第二题：技能的组合。 一个任务可能需要多个技能（先重构、再写测试）。设计一个组合机制，并说明它如何处理步骤之间的冲突。

第三题：技能对缓存的影响。 主体在任务早期加载会提升缓存命中率（1.2），但它也可能加载了用不上的技能。设计一个折中策略，并说明判据。

第四题：技能与权限。 某些技能的步骤包含高副作用操作（例如直接部署）。设计一个机制，让技能与 3.2 的守卫协作。

第五题：跨项目的技能同步。 一个技能在三个项目里各有一份副本。设计一个机制，让改进能传播，同时允许各项目有差异。

第六题：技能的效果度量。 设计一组指标，回答"这个技能是不是真的有用"。注意区分"被加载"与"改变了做法"。

## L9 仍未解决（这一篇自己的缺陷）

| 缺陷 | 后果 | 修法 | 当初为什么这么写 |
|---|---|---|---|
| 触发依赖描述的措辞 | 换语言或用词习惯不同时漏触发 | 多语言描述或向量的语义匹配（4.1 的可选路径） | 关键词匹配的实现成本最低 |
| 没有自动的技能生成 | 沉淀仍然靠人 | 从成功任务里提取草案（挑战题第一题） | 自动提取容易产生污染 |
| 冲突检测只能发现同时加载的重叠 | 分时使用的冲突发现不了 | 静态语义分析（需要判断两种做法是否一致） | 语义判断无法可靠自动化 |
| 没有技能的权限模型 | 高副作用步骤与普通技能同等对待 | 与 3.2 的守卫协作（挑战题第四题） | 本卷的技能以只读与构建为主 |
| 遵从度无法测量 | 不知道模型是否真的按步骤做了 | 把关键步骤写成可运行命令并核对执行事件 | 测量遵从需要细粒度的执行记录 |
| 技能没有大小上限 | 一个超长技能会撑爆上下文 | 加长度限制与拆分建议 | 限制值需要数据支撑，而本卷的样本有限 |

第四条与第五条属于"能力未覆盖"，第一条与第六条属于简化，第二条与第三条属于自动化的边界。第五条值得单独标记：它意味着"技能被读了"与"技能被遵循了"之间的差距无法被观测，而 0.2 的第三项判据（做法真的变了吗）只能通过最终产物间接判断——当产物恰好正确时，无法区分"遵循了技能"与"碰巧做对了"。

## L10 提问训练

### 五个层次

| 层次 | 例子 |
|---|---|
| 事实 | 三层披露是哪三层？技能与工具的边界是什么？ |
| 机制 | 为什么描述要写触发条件而不是主题？ |
| 设计 | 为什么不适用条件必须写？ |
| 系统 | 如果技能与记忆争抢上下文，怎么分配？ |
| 科研 | 能不能量化"技能带来的收益"，例如有技能与无技能的任务成功率差？ |

### 五种提问模板

反例逼问：如果技能不写不适用条件，哪一类失败会变多。

边界追问：一个做法被做过几次才值得沉淀。

代价追问：把技能集中放在独立仓库，代价落在谁身上。

替代对比：为什么技能用文本而不是编译成代码。

验证追问：怎么证明"技能真的改变了做法"。

### 本篇引出的十二个问题

读懂层。 第一，技能与记忆、工具的边界是什么？第二，三层披露与各自的成本是什么？第三，触发有哪三种方式？

重建层。 第四，为什么描述要写"何时"？第五，为什么元数据必须有固定预算？第六，为什么主体应当在任务早期加载？

设计层。 第七，为什么必须写不适用条件？第八，技能验证的两个阶段是什么？第九，冲突的两类如何区分处置？

评审层。 第十，拿到一个技能库，你会先检查哪一处？第十一，怎么判断一个技能过时了？第十二，如果有人说"把技能全文都写进系统提示不就完了"，你怎么回应？

### 问题升级练习

模糊问题：「我该怎么让 agent 学会我的做法？」

升级后的精确问题：

> 让系统学会一套做法至少包含三件互相制约的事：形态（做法写成什么，以及它的适用与不适用条件）、发现（模型怎么知道它存在）、以及验证（怎么知道它仍然有效）。
> 第二件与第三件互相制约——发现依赖常驻的描述，而验证需要一次真实执行，两者的成本都要从同一个上下文预算里出。
> 我能不能为这三件事各找出一条**可检查的判据**？
> 特别是：有没有哪一条判据，是**能在一次真实任务里验证"做法确实变了"的**？

提升点说明：原问题无法回答，因为"我的做法"没有边界。升级后的版本把它拆成三件具体的事，指出后两件的成本竞争，并追加以一个更强的问题：哪一条判据能验证"做法确实变了"——因为只有那一条才能区分"技能有用"与"技能被读了"。

## L11 系统影响回溯

回看第 0.5 节的三个连锁影响。

| 预判 | 本篇分析之后的结论 | 状态 |
|---|---|---|
| 技能的描述质量决定系统的学习效果 | 确认，并给出"描述写何时"的写法与一次可实测的判据 | 成立 |
| 技能会与记忆争抢上下文 | 确认，并给出"元数据固定预算、主体与记忆共享剩余"的分配 | 成立 |

一处需要修正的预判：0.5.2 把"触发与选择"标为对 4.3 的强依赖。读完之后要补一层：4.3 的用户模型与技能在触发上有一处冲突——用户模型是按"当前是谁"选择，而技能是按"当前任务是什么"选择，两者的信号不同。处置方式是把用户模型放进注入层而不是触发层（它改变的是同一个技能的执行方式，而不是选哪个技能），而这条分工本篇没有明确，它会在 4.3 里成为设计约束。

通向下一篇的桥。 本篇处理的是"做法"，它假设做法对不同的人是一样的。而实际上同一套做法对不同的人有不同的合适程度——同一个用户偏好简短回答，另一个用户偏好完整推导，而技能的内容需要因此调整。

下一篇 `4.3 用户建模` 处理这件事。它与本篇的连接点有两处：一是用户模型也需要检索与注入（复用 4.1 的机制），二是它与技能的交互发生在执行层而不是选择层（上面那处预判修正）。用户模型比技能更敏感——它涉及个人数据，因此它的存储、边界与遗忘策略都需要单独讨论。

### 二、情境绑定：当你……就想起……

## 本篇新词

记忆条目（memory entry） 指一条被持久保存、可供后续使用的事实或偏好。它与会话历史的区别是跨会话：历史属于一条会话（2.7 的日志），而记忆要在会话结束之后继续存在。

写入策略（write policy） 指决定"什么值得记"的规则。它是记忆系统里最容易被做错的一环——记多了会污染检索，记少了等于没有记忆，而两者的判据都不显然。

相关性检索（retrieval） 指按当前任务的需要找出相关条目。它有三种常见实现：关键词匹配（BM25 一类）、向量相似度、以及时间与使用频率的加权。三者的失效方式不同，而它们的组合是常见做法。

注入预算（injection budget） 指一次请求最多注入多少记忆（条数或 token 数）。它的必要性与 3.3 的压缩同源：记忆是进上下文的内容，而上下文有硬上限。

遗忘（forgetting） 指主动降低某些条目的可检索性（而不是删除）。它与 1.5 的"有界容器"配合：容量满时，被遗忘的条目让位给新的条目。"遗忘"与"删除"的区别是前者可逆（条目还在，只是不再被检索），这一点在需要复盘时很重要。

记忆污染（memory poisoning） 指错误的信息被写入并长期影响后续判断。它的来源有三类：模型的一次错误结论被当成事实记下、用户的一次临时偏好被当成长期偏好、以及过期的事实没有被更新。

有界策略（bounded policy） 指容量满时的处置：拒绝（1.5 的立场）、合并、或按规则淘汰。本课程的选择是拒绝加合并，理由是它把"丢什么"的决定权交回调用方。

记忆的可观测 指回答"哪些记忆被用到、哪些从未被用到"。它是 3.6 的度量能力在记忆上的应用，也是淘汰策略的输入——从未被检索到的条目是候选项，而没有观测时这个判断只能靠猜。

```
└──────────────────────────────────────────────────────────────────────┘

 一句话串起来：写什么 → 怎么找 → 怎么用 → 满了怎么办
```

这张图的关键线索在前两块：记忆的价值由"检索到的对不对"决定，而不是由"存了多少"决定。多数记忆系统的问题不是容量不足，而是写入太随意导致检索失准——而失准的表现是"它记住了但没用对"。

### 0.1 一个具体的判断：一次注入多少条

注入预算的取值可以从成本反推。设每条记忆平均 50 token，而上下文窗口是 128K，如果把窗口的 1% 留给记忆，那么可以注入约 25 条（1280 token ÷ 50）。这个数字看起来宽松，而它在两种情况下会变成问题。

第一种是记忆条目很长（例如一条记录了一段完整的过程），此时 25 条可能占掉窗口的 20%。第二种是记忆与历史叠加：2.7 的历史本身可能已经占了窗口的六成（3.3 的压缩正是为此），留给记忆的空间因此更小。

因此注入预算应当是一个独立的配置项，而不是"取窗口的一个固定比例"——它需要在与历史竞争空间时被显式分配。这条判断与 3.3 的"余量要给回答留空间"是同一条原则的延伸。

### 0.2 本篇建立的三项判据

第一项用于判断一条信息该不该记：问"它在下一个会话里还有用吗"。会话内的信息属于历史（2.7），跨会话仍有用的才是记忆——这条判据把大量候选挡在门外，而它是写入策略的第一个过滤器。

第二项用于判断检索是否够准：问"注入的前 k 条里有几条真的相关"。这个比例可以直接测（人工标注一批查询与条目），而它是记忆系统唯一能验证的效果指标。

第三项用于判断一条记忆该不该继续保留：问"它最近有没有被检索到"。长期不被检索的条目是淘汰候选，而这需要 1.6 的观测——没有观测时淘汰只能靠时间，而时间不是相关性。

### 0.3 十分钟练习：两种检索排序的差别

下面这段代码对比"只看关键词"与"关键词加时间衰减"两种排序。

```js
const entries = [
  { id: 'm1', text: '用户偏好简短回答', at: 0 },        // 很久以前
  { id: 'm2', text: '用户偏好简体中文', at: 90 },        // 最近
  { id: 'm3', text: '这个项目用 pnpm 而不是 npm', at: 10 },
]
function score(query, e, now, { decay = 0 } = {}) {
  const hit = e.text.includes(query) ? 1 : 0
  const ageDays = (now - e.at) / 1
  return hit * (1 / (1 + decay * ageDays))
}
const now = 100
console.log('只看关键词：', entries.map((e) => [e.id, score('用户', e, now)]).sort((a, b) => b[1] - a[1]))
console.log('加时间衰减：', entries.map((e) => [e.id, score('用户', e, now, { decay: 0.05 })]).sort((a, b) => b[1] - a[1]))
```

第一次排序里两条含"用户"的条目并列（而它们的年龄相差很多），第二次排序把较新的排在了前面。这次对比说明的是"相关性"不是一个维度：关键词回答"提没提到"，时间回答"还新不新"，而使用频率回答"以前有没有用"。三者必须被组合，而组合方式本身是一个需要检验的设计。

### 0.5.3 三个连锁影响

第一，写入太随意会让检索失准，而失准的表现是"记住了但没用对"。 这是记忆系统最常见的问题，而它的成因不是检索算法差，而是条目里有太多低价值信息（重复的、临时的、推测的）。检索算法只能在候选集里排序，而候选集的质量由写入策略决定——检索的上限由写入决定。

第二，记忆会与缓存命中率相互影响（与 3.6 相接）。 如果把记忆注入在上下文的前部，那么每条记忆的变化都会让前缀失效，从而降低缓存命中率。如果注入在后部，则不影响前缀，但它与历史消息的位置关系需要设计（记忆通常在历史之前被读到才有用）。这条影响在两个目标之间形成张力，而它的解法通常是"把长期稳定的记忆放前面（它们很少变），把与当前任务相关的短期记忆放后面"。

第三，没有观测的记忆系统无法淘汰，而它的容量必然写满。 这条连锁把记忆与 1.5 的"写满即拒绝"接起来：写满时如果没有任何依据判断"哪条该走"，那么拒绝就成了唯一安全的动作——因为丢弃需要依据，而依据来自观测。这也解释了为什么记忆的观测不是可选的附加功能。

### 0.5.4 它与本书其余部分的关系

本篇的记忆是单机、单用户、文本形式的。多用户共享记忆需要隔离（2.5 的作用域会给出一部分答案，而多租户的隔离在第 5 卷）。结构化的记忆（把事实存成三元组而不是文本）是另一条路，它带来更精确的检索与更高的写入成本，本课程不采用。

## L0 要解决的问题

### 0.1 现象一：记忆写了，但从没被用上

第一个现象的形态是"系统有记忆功能，而它的效果为零"。原因有三种：写入的条目从来没有被注入（没有检索环节）、检索的查询词与条目用词对不上（关键词匹配的固有缺陷）、或者检索到了但没有注入（预算为零或被其他内容挤掉）。

它们的共同点是从外部看不出差别——三种原因的最终表现都是"它没记住"。而区分它们需要观测（1.6）：写入条数、检索命中条数、实际注入条数三个数字一对比，就能立刻定位是哪一环断了。

### 0.2 现象二：错误的结论被当成事实长期保留

第二个现象是记忆污染。一条错误结论（模型的一次误判、用户的一次临时表达）被写入记忆之后，它会在后续每一个相关任务里被注入，从而持续影响判断。它的危害随使用次数增长——用得越多，被当成事实的机会越多。

它的防线有三条（1.5）：写入时标注来源（它是"用户说的"还是"模型推测的"，后者不应被当成事实）、给条目一个有效期或复核条件、以及提供撤销的路径（发现错误时能把它从检索集合里移除）。三条缺一条，污染就会持续。

### 0.3 现象三：上下文被记忆撑爆

第三个现象是注入没有预算。检索返回前十条，而每条都注入——如果有些条目很长（一段完整的过程描述），那么它们可能占掉窗口的一大部分，从而挤掉本该留给历史的空间。

它的后果与 3.3 的"大输出撑爆上下文"是同一类，而修法也相同：注入必须有预算，超出的部分按相关性裁剪（或者只注入条目的摘要）。这里的一个细节是：裁剪的粒度是条目而不是字符（把一条记忆截断成半句比不注入它更糟，因为半句话可能是误导）。

### 0.4 现象四：写入太随意，检索失准

第四个现象是最根本的。记忆里存了大量低价值信息（重复的、临时的、别人也能推断的），于是相关的那几条在前十条里排不进——因为候选集本身太大了。

它的修法不是改检索算法（算法只能在候选集里排序），而是收紧写入（1.1）。判据是"它在下一个会话里还有用吗"：会话内的信息属于历史，跨会话仍有用的才进记忆。这条过滤器能挡掉绝大多数候选，而它同时让检索的候选集保持在可排序的规模内。

### 0.5 这一篇要正面回答的四个问题

第一，什么值得记，写入策略有哪些过滤器（1.1）。第二，怎么找回来，相关性由哪些信号构成（1.2）。第三，怎么用上，注入的预算与位置（1.3）。第四，满了怎么办，拒绝与合并如何配合（1.4）。

四个问题里第一是上限（它决定候选集质量），第二与第三决定它的效果，第四决定它在长期运行中是否稳定。

## L1 设计与原理

### 1.1 写入策略：三个过滤器

写入策略由三个问题构成，任何一条不通过就不该写入。

第一，它在下一个会话里还有用吗。 这是区分"记忆"与"历史"的判据。会话内的进展（做到哪一步、刚才说了什么）属于历史（2.7 的日志），跨会话仍有用的（用户的偏好、项目的约定、已知的失败做法）才是记忆。

第二，它是可验证的事实还是推测。 这条过滤器针对记忆污染（0.2）。"用户偏好简体中文"是用户说的（可验证），"用户可能不喜欢长回答"是模型的推测（不可验证）。推测可以进记忆，但必须带标注，否则它会在后续被当成事实。

第三，它是不是临时的。 临时信息（这次的提交信息、这条会话的临时目录）不该进记忆。判断方式是问"它在一周后还成立吗"——如果答案依赖于当前正在进行的任务，它就不该进。

```ts
interface MemoryEntry {
  readonly id: string
  readonly text: string
  readonly kind: 'fact' | 'preference' | 'inference'   // 来源类别（1.5 的防线）
  readonly source: string                              // 谁说的（用户 / 工具 / 模型）
  readonly createdAt: number
  readonly lastUsedAt?: number                         // 观测（1.6）
  readonly useCount: number
  readonly expiresAt?: number                          // 可选的有效期
  readonly supersededBy?: string                        // 被更新的条目取代时指向新的
}
```

八个字段里，`kind` 与 `source` 是防污染的关键，`lastUsedAt` 与 `useCount` 是淘汰的依据，`expiresAt` 与 `supersededBy` 是"更新而非删除"的实现方式——后者让知识的演化留下痕迹（旧条目还在，只是不再被检索），这与 3.3 的"压缩追加事件"是同一条原则。

### 1.2 检索：三种信号与它们的组合

相关性由三种信号构成，而它们各自回答一个不同的问题。

| 信号 | 回答 | 失效方式 |
|---|---|---|
| 关键词匹配 | 提没提到 | 用词不同就匹配不上（"简体中文"与"中文回复"） |
| 向量相似度 | 说的是不是同一件事 | 对罕见专有名词不稳定；需要额外的模型调用 |
| 时间与频率 | 还新不新、以前有没有用 | 会把长期有效但少用的条目排到后面 |

三种信号的组合方式是加权求和，而权重的选择必须用真实数据检验（0.2 的第二项判据）：准备一批查询与人工标注的相关条目，看不同权重下前 k 条的准确率。没有这一步时，权重是猜的，而猜出来的权重在多语言或专有名词场景下往往很差。

本课程的实现以关键词为主、时间与频率为辅，向量作为可选（因为它引入一次模型调用，而那条路径的成本与延迟已经在 3.6 里可以被度量）。

检索的第二个参数是阈值：低于它的条目不注入，即使它们进了前 k。这条参数防的是"硬凑满 k 条"——当没有真正相关的条目时，注入不相关的条目比不注入更糟（它们会误导模型）。

### 1.3 注入：预算、位置与格式

注入预算（0.1 的量化）是条数与 token 数双重限制：取 `min(k, token 上限 / 平均长度)`。双重的理由是两者各自会失效——只看条数时，长条目会占掉太多空间。只看 token 时，短条目会塞进太多无关内容。

注入的位置有两个候选，各有代价。放在系统提示之后、历史之前：它离指令最近，因此最容易被遵守。代价是它的变化会让后续前缀失效（0.5.3 的第二条）。放在历史之后、当前输入之前：它不影响历史部分的前缀。代价是模型可能在读完历史之后才看到它，因此它的影响较弱。

本课程的选择是按稳定性分层：长期稳定的记忆（用户偏好、项目约定）放前面（它们很少变，因此不影响命中率），与当前任务相关的短期记忆放后面。

注入的格式也有一条要求：每条记忆要能被模型区分开（编号或要点符号），并且要有一句说明它的性质（"以下是已知的偏好"而不是把条目直接混进指令里）。这条要求的理由与 2.2 的"给模型看的描述"相同——信息的组织方式决定它被如何理解。

### 1.4 有界策略：拒绝、合并、遗忘

容量满时的三种处置在 1.5 的 1.6 已经分析过，这里的补充是它们在记忆这一层的具体形态。

拒绝意味着写入失败，而调用方要决定怎么办。在记忆场景里，可行的处置是"先合并再重试"——把两条相似的旧条目合并成一条，腾出位置。

合并是把多条压成一条。它的实现要处理两个问题：哪几条该合并（相似度阈值，与检索用的是同一套信号）、以及合并后的条目保留什么（时间范围、来源，以及被合并掉的信息是否要保留在条目的附注里）。合并是不可逆的信息损失，因此它与 3.3 的压缩一样应当作为一条新记录发生（旧条目标记为 `supersededBy`，而不是删除）。

遗忘是降低可检索性而不删除。它的实现是给条目一个"抑制"标记（或降低它的权重），而它在两种场景下有用：条目可能还需要被复盘查到（因此不能删），以及它的结论可能过时但有历史价值。

三者的配合是：默认拒绝（它是安全的），合并是推荐的处置（它保住信息），遗忘是长期运行的补充（它让老条目让位）。

### 1.5 记忆污染与它的防线

污染的三种来源（本篇新词）各自对应一条防线。

防线一是来源标注：每条记忆带着 `kind` 与 `source`，而注入时如实告诉模型哪些是推测。这条防线的实现很简单（一个字段加一句说明），而它防的是最严重的一类污染——推测被当成事实。

防线二是有效期与复核：某些记忆会随时间失效（用户的偏好可能变、项目约定可能改）。实现方式是给它们 `expiresAt`，过期后不参与检索（但保留在存储里，供复盘）。

防线三是可撤销：发现错误时能把条目从检索集合里移除。实现方式是 1.4 的遗忘（抑制标记）。撤销的成本必须低——如果撤销需要人工改数据文件，那么它实际上不会被执行。

三条防线之外还有一条实践建议：写入要留下"为什么记它"的理由。一条记忆的写入理由（"用户在这次任务里说了三次希望简短"）对后续判断它是否仍然成立很有价值，而它也是 4.6 复盘时的输入。

### 1.6 观测：哪些记忆被用到

记忆的观测回答四个问题：写入多少条（写入策略的松紧）、检索命中的比例（检索是否有效）、实际注入的条数（预算是否够）、以及每条被用过多少次（淘汰的依据）。

第四个是最有价值的：长期零使用的条目是淘汰候选。它的判据是"最近 N 次相关检索里有没有命中它"，而不是"它多久没被写过"——后者与相关性无关（一条重要的项目约定可能三个月才用一次）。

观测的实现与 3.6 相同：从既有事实派生，不新增埋点。记忆的写入、检索与注入都应当是日志里的事件（2.7 的"可查询"原则），因此观测只需要读日志。

### 1.7 与缓存命中率的关系

记忆的注入位置影响前缀缓存（0.5.3 的第二条），而它的实现方式在 1.3 已经给出（按稳定性分层）。这里补充它的量化。

设记忆注入占 2000 token、其中长期稳定的部分占 1500、与任务相关的部分占 500。如果全部注入在前部，那么任何一次任务相关记忆的变化都会让 2000 token 的前缀失效。如果按稳定性分层，只有 1500 那部分参与前缀（它很少变），而 500 那部分在后部（不影响前缀）。这个分层的收益是可算的：假设任务相关记忆每次任务都变，那么分层让前缀失效的频率从"每次"降到"几乎从不"。

这条量化与 3.6 的命中率度量是配套的：分层是否有效，只能通过观测注入后的命中率来验证。

### 1.8 两次追问

工程侧的问题是什么时候该重建记忆库。有些变化（条目的组织方式、检索的权重）会让历史数据的结构不再适用。判据是"旧数据的可用性是否下降"——如果旧条目在新权重下检索不到，那说明权重变了而数据没跟上。处置方式是重算派生字段（例如重建索引），而不是重写条目——条目是事实，索引是派生（2.7 的划分在这里的又一次应用）。

产品侧的问题是记忆对用户意味着什么。多数用户不想要一个"记住了我的一切"的系统，而想要一个"记得我说过的重要事情"的系统——这两者的差别在写入策略的松紧上。因此"记住什么"需要一个可见的入口：用户应当能查看系统记住了什么、能删除某一条、也能关闭记忆。这条可查看性不是附加功能，它是记忆被信任的前提。

## L2 决策表

| # | 决策 | 我们的选择 | 替代方案 | 代价落在谁身上 |
|---|---|---|---|---|
| 1 | 写入的门槛 | 三个过滤器（跨会话有用、可验证或带标注、非临时） | 由模型自由决定 | 可能漏掉有用信息；换来检索候选集干净 |
| 2 | 推测类信息的处置 | 允许写入但带标注 | 一律不写 / 当成事实写 | 注入时要多一句说明；换来不污染 |
| 3 | 检索的信号 | 关键词为主，时间与频率为辅，向量可选 | 只用一个信号 | 权重需要检验；换来多语言与专名场景更稳 |
| 4 | 检索的阈值 | 有（低于阈值不注入） | 总是凑满 k 条 | 有时不注入；换来不引入误导 |
| 5 | 注入预算 | 条数与 token 双重限制 | 只限条数或只限 token | 计算稍复杂；换来两种失效都被挡住 |
| 6 | 注入的位置 | 按稳定性分层（稳定在前、任务相关在后） | 全部放前 / 全部放后 | 组装逻辑更复杂；换来缓存命中率 |
| 7 | 裁剪的粒度 | 整条（不截断单条） | 按字符截断 | 可能少注入几条；换来不产生误导的半句 |
| 8 | 容量满时的默认 | 拒绝 | 淘汰最旧的 | 调用方要处理失败；换来丢失有依据 |
| 9 | 合并作为推荐处置 | 是 | 否 | 要有相似度判定；换来信息不丢 |
| 10 | 删除还是抑制 | 抑制（保留条目、降低可检索性） | 直接删除 | 存储占用；换来可复盘可撤销 |
| 11 | 观测的范围 | 写入、检索、注入、使用次数 | 只记总数 | 要记录四类事件；换来能定位断在哪一环 |
| 12 | 用户可见性 | 可查看、可删除、可关闭 | 不暴露 | 要提供界面与命令；换来记忆被信任 |

其中两条值得展开，因为它们的选择在实践中经常被做成另一个。

### 关于第 1 条的完整论证（为什么写入必须有门槛）

替代方案是"让模型自己决定什么时候记"。它的吸引力在于省事（不需要额外的判据），而它的问题在三个地方。

第一，模型的判断偏向"记下来更安全"。在不确定时它倾向于记录（因为它无法预见后续是否需要），于是候选集会膨胀——而膨胀直接导致 0.4 那个现象（检索失准）。

第二，模型看不见全局。"这条信息跨会话有用吗"这个问题需要知道系统如何使用记忆，而那属于系统设计，不在模型的视野里。因此它给出的判断会随提示词波动。

第三，写入是不可逆动作的入口。写进去的东西会被后续每一次相关任务读到，因此错误的代价是持续的（0.2）。

本课程的做法是把门槛放在系统侧（三个过滤器，1.1），并给模型一个明确的接口（"要记住这条吗"的提议），由系统判断是否接受。这个分工与 3.2 的守卫是同一条原则：模型提议，系统裁决，而裁决的依据是可检查的规则。

### 关于第 10 条的完整论证（为什么不直接删除）

替代方案是在淘汰时直接删除条目。它的好处是干净（存储不增长、检索集合变小），代价在三个场景下显现。

第一，复盘时需要旧条目。4.6 的复盘要回答"当时的判断是什么、后来改成了什么"，而这需要旧记忆仍在（被抑制但不被删除）。

第二，删除是不可逆的。一条被判定为"不再相关"的记忆可能在某个罕见场景下重新变得重要（例如那个项目半年后又启动了）。删除之后无法恢复，而抑制只需改一个标记。

第三，删除会丢失演化的痕迹。记忆的价值之一正是"它变过几次、为什么变"——而这个信息只有在旧条目仍在时才存在（这就是 `supersededBy` 的用途）。

抑制的代价是存储随时间增长，而这个代价可以用"归档"处理（把长期抑制的条目移到冷存储），而不是用删除。这条决策与 3.3 的"压缩追加事件而不改写历史"是同一条原则：不可逆的信息损失不要在一次操作里发生。

## L3 实现（施工图）

### 3.1 文件结构

```
// plugins/memory.ts
// ┌─ 条目段 ── MemoryEntry 与它的校验（写入策略的三个过滤器）
// ├─ 存储段 ── 追加写日志（复用 2.7 与 3.5 的设施）
// ├─ 检索段 ── 三种信号的打分与阈值
// ├─ 注入段 ── 预算、分层位置与格式
// └─ 观测段 ── 四类事件（写入、检索、注入、使用）
```

五段里第二段刻意复用 2.7 与 3.5 的设施：记忆的写入是一条事件，因此它天然可恢复、可查询——这条复用让本篇不需要新的持久化机制。

### 3.2 写入段

```ts
export async function remember(candidate: MemoryCandidate, ctx: Context): Promise<MemoryEntry | null> {
  if (!crossSessionUseful(candidate)) return null              // 过滤器一
  if (candidate.kind === 'inference' && !candidate.source) throw new Error('推测类记忆必须标注来源')
  if (isTemporary(candidate)) return null                       // 过滤器三
  const entry: MemoryEntry = { id: newId(), ...candidate, createdAt: ctx.now, useCount: 0 }
  try {
    await store.append({ type: 'memory/write', entry })          // 可能因容量满而失败
  } catch (e) {
    if (e instanceof CapacityError) return mergeThenRetry(candidate, ctx)   // 推荐的处置
    throw e
  }
  return entry
}
```

三处要点：过滤器在前（不通过就不进存储）、推测类必须带来源（否则抛错而不是静默写入）、容量满时先尝试合并而不是直接失败。

### 3.3 检索段

```ts
export function retrieve(query: string, entries: readonly MemoryEntry[], opts: RetrieveOptions): MemoryEntry[] {
  const now = opts.now
  const scored = entries
    .filter((e) => !e.suppressedAt && !isExpired(e, now))      // 抑制与过期先过滤
    .map((e) => ({
      e,
      score: 1.0 * overlap(query, e.text)                      // 关键词
           + 0.3 * recency(e, now, opts.decayDays)             // 时间
           + 0.2 * frequency(e),                               // 使用频率
    }))
    .filter((x) => x.score >= opts.threshold)                   // 阈值（L2 第 4 条）
    .sort((a, b) => b.score - a.score)
  return scored.slice(0, opts.k).map((x) => x.e)
}
```

三处值得指出：抑制与过期在打分之前过滤（它们不是"相关性低"，而是"不应参与"）、权重是显式常量（便于按 1.2 的方法检验）、阈值在排序之前（先筛掉不相关的，再取前 k）。

### 3.4 注入段

```ts
export function inject(entries: readonly MemoryEntry[], budget: InjectionBudget) {
  const stable = entries.filter((e) => e.useCount > STABLE_USES)         // 长期被用到的才是稳定
  const rest = entries.filter((e) => !stable.includes(e))
  const picked: MemoryEntry[] = []
  let tokens = 0
  for (const e of [...stable, ...rest]) {                                 // 稳定在前
    const t = estimateTokens(e.text)
    if (tokens + t > budget.maxTokens || picked.length >= budget.maxEntries) continue   // 整条跳过
    picked.push(e); tokens += t
  }
  return formatFor(picked)                                                // 含性质说明与编号
}
```

这段实现里"整条跳过"对应 L2 第 7 条：预算不够时跳过整条，而不是截断它。另一处是 `stable` 的判定用 `useCount` 而不是 `kind`——长期被使用的条目是稳定的，而它可能是事实也可能是偏好。

### 3.5 验收判据

| # | 判据 | 怎么检查 |
|---|---|---|
| 1 | 会话内信息不写入 | 提议一条只在本次任务有用的信息，核对不写入 |
| 2 | 推测类无来源时被拒绝 | 提议一条 `inference` 且无 source 的条目，核对抛错 |
| 3 | 容量满时先尝试合并 | 填满后提议一条相似条目，核对发生合并而非失败 |
| 4 | 检索按三种信号排序 | 构造三条不同年龄与频率的条目，核对排序 |
| 5 | 低于阈值的条目不返回 | 用一个不相关的查询，核对返回空 |
| 6 | 抑制与过期的条目不参与检索 | 抑制一条，核对它不再出现 |
| 7 | 注入受双预算限制 | 给定小预算，核对条数与 token 都不超 |
| 8 | 预算不足时跳过整条而不是截断 | 构造一条超预算的条目，核对它整条不出现 |
| 9 | 稳定条目在前、任务相关在后 | 核对注入顺序 |
| 10 | 注入的文本含性质说明与编号 | 核对格式 |
| 11 | 四类观测事件都被记录 | 跑一次检索与注入，核对日志 |
| 12 | 使用次数被更新 | 注入之后核对相关条目的 `useCount` 增加 |

第 8 与第 9 条是这一篇的特色判据（它们检验注入策略），第 11 与第 12 条检验观测——而观测是淘汰的依据（1.6）。

先做条目与写入（判据 1、2、3），再做检索（判据 4、5、6），然后做注入（判据 7、8、9、10），最后做观测（判据 11、12）。

### 3.7 实现里最容易写错的三处

第一处是过滤器的作用位置。正确做法是三个过滤器在写入之前全部执行（不通过就不进存储）。错误做法是把它们放在存储层内部（先写入再判断是否保留）。后者的代价是候选集里短暂存在不该有的条目，而如果检索恰好在那一刻发生，它会读到不该有的东西——这类竞态在单线程实现里不明显，而在有并发写入时会出现。

第二处是抑制与删除的区分。正确做法是抑制只改标记、条目仍在。错误做法是把"淘汰"实现成删除。后者的代价在 1.4 已经分析过（不可复盘、不可逆、丢失演化痕迹），而它的实现往往只是为了省下一段代码。

第三处是注入格式里的性质说明。正确做法是注入时标明每条记忆的性质（事实、偏好、推测）。错误做法是把条目文本直接拼进提示词。后者的代价是推测会与事实混在一起，而模型无法区分它们——这条正是 1.5 第一条防线在实现层的落点。

| 抑制一条记忆 | `node tools/memory-suppress.mjs --id=<id>` | 不删除，只降低可检索性 |

### 5.3 三条容易踩的规则

第一条，写入必须有门槛。候选集的质量决定检索的上限。

第二条，推测类信息必须带来源标注。不带标注的推测会变成事实。

第三条，预算不足时跳过整条而不是截断。半句记忆比没有记忆更糟。

## L9 仍未解决（这一篇自己的缺陷）

| 缺陷 | 后果 | 修法 | 当初为什么这么写 |
|---|---|---|---|
| 检索权重是手工调的超参 | 换语言或换领域后需要重调 | 用标注集自动调参（需要持续维护标注集） | 标注成本高，手工调在单一领域够用 |
| 没有冲突检测 | 矛盾的两条会同时注入 | 引入矛盾判定与 `supersededBy`（挑战题第一题） | 判定矛盾需要语义理解 |
| 记忆是纯文本的 | 无法做结构化查询（例如"所有关于 X 的偏好"） | 引入结构化的子集（挑战题第二题） | 文本形式的写入成本最低 |
| 没有跨用户的共享 | 同一用户的多个设备之间不共享记忆 | 引入同步（第 5 卷的多会话与账户会涉及） | 本卷是单机的 |
| 淘汰策略依赖使用次数 | 一次误用会让条目长期留存 | 引入时间窗口内的使用次数 | 简单计数在早期够用 |
| 抑制的条目仍然占用存储 | 长期运行后存储增长 | 归档（移到冷存储） | 本卷的记忆规模有限 |

第二条与第五条属于"判定依据不足"，第三条与第四条属于形态与范围的选择，第一条与第六条属于简化。第二条值得单独标记：矛盾的两条记忆同时注入会让模型面对自相矛盾的信息，而它的表现是"行为不稳定"——这类问题的排查难度高（因为两条单独看都对），因此冲突检测的缺失是一个真实的口子。

### 问题升级练习

模糊问题：「我该怎么给 agent 加记忆？」

升级后的精确问题：

> 记忆至少包含三件互相制约的事：写入（什么值得跨会话保留）、检索（怎么按当前需要找回来）、以及暴露（注入多少、放在哪里）。
> 第二件与第三件互相制约——检索得越准，就可以注入得越少，而注入得越少意味着对检索准确率的容错越小。
> 我能不能为这三件事各找出一条**可检查的判据**？
> 特别是：有没有哪一条判据，是**能用一次跨会话的行为对比来验证的**？

提升点说明：原问题无法回答，因为"加记忆"没有边界。升级后的版本把它拆成三件具体的事，指出后两件的制约关系（准确率与注入量的权衡），并追加以一个更强的问题：哪一条判据能用跨会话的行为对比验证。

通向下一篇的桥。 本篇处理的是"记住事实"，而它留下了一个没有答案的问题：记住做法。事实回答"是什么"，而做法回答"遇到这类情况该怎么做"——后者比前者更复杂，因为它有适用条件（什么时候该用）与步骤（怎么用）。

下一篇 `4.2 技能：渐进披露` 处理这件事。它与本篇的连接点是检索：技能的选择与记忆的检索用的是同一套相关性机制，而它们的差别在于技能多了一层"适用条件"——一个技能在被使用之前，模型需要先知道"它适用于当前情况"，而那正是渐进披露要解决的问题。

## 本篇新词

会话注册表（session registry） 指进程里所有活动会话的索引：它们的身份、当前状态、占用的资源与所属模式。它是并发的唯一权威视图——配额、调度与观测都以它为依据。

隔离（isolation） 指一条会话的状态变化不影响另一条。它有三个层面：作用域隔离（注册项不互相可见，2.5）、数据隔离（会话文件、工作目录、记忆的作用域）、以及失败隔离（一条会话崩溃不拖垮其他）。

共享资源（shared resource） 指多条会话竞争的东西：模型的并发配额、文件系统的工作目录、进程池、以及凭据。它的特点是容量有限而请求无序，因此需要调度与配额，而不能靠"先到先得"。

工作区租约（workspace lease） 指对工作目录的独占声明。它的规则很简单——同一个工作区在同一时刻只有一个写者——而它的必要性来自文件系统没有事务：两条会话同时改同一批文件会产生无法解释的中间态。

配额（quota） 指分配给一条会话（或一个模式）的资源上限。配额与限流的差别是：限流是拒绝，配额是分配——配额让"谁能用多少"变成事前确定的，而限流只在越界时生效。

公平性（fairness） 指调度在多条会话之间分配资源的方式。它有三种实现：先来先服务（简单，但一条长会话会挡住后面的）、按优先级（需要定义优先级）、按配额轮转（每条会话在自己的配额内轮流获得资源）。哪一种都不天然正确，而选择依据是"用户对等待的容忍度"。

取消传播（cancellation propagation） 指一条会话被取消时，它的子操作（工具调用、子进程、子 agent）一并被取消。它的实现依赖 3.4 的进程树取消与 2.5 的作用域链——取消沿着作用域向下传播，而不是横向扩散。

会话生命周期（session lifecycle） 指会话从创建到回收的过程。它的难点不在创建而在回收：一条会话结束后，它的资源（内存、文件句柄、子进程、订阅）必须被释放，否则长期运行的进程会缓慢耗尽资源。

```
 一句话串起来：状态怎么隔离 → 资源怎么分配 → 共享部分怎么约束 → 生命周期怎么收敛
```

这张图的关键线索在第三块：并发问题的多数根源是"共享了本不该共享的东西"。工作目录、进程池、凭据、模型配额——它们都是多条会话真正需要共享的，因此不能靠隔离解决，只能靠租约与配额把它们变成有秩序的共享。区分"该隔离的"与"该共享的"是这一篇的第一个判断。

### 0.1 一个具体的判断：并发数与资源占用的关系

设一条活动会话的常驻开销约为：上下文 20K token（约 80KB 文本）、若干文件句柄、一个工作区句柄、以及一个待响应状态。十条会话的总开销仍在单机可承受范围，而一百条会带来两个问题。

第一个问题是模型配额。如果每条会话平均每分钟发起一次调用，一百条会话意味着每分钟一百次调用，而模型的并发上限通常是数十——于是请求开始排队，而排队会让每条会话的延迟上升（3.6 的延迟分解里"排队"那一段）。这条约束给出了并发数的实际上限：并发数由下游的配额决定，而不由本机的资源决定。

第二个问题是观测的可读性。一百条会话的成本与延迟数据混在一起时，单条会话的异常会被平均数掩盖（3.6 的 1.6）。处置是按会话归因并保留分组，而它要求会话注册表提供分组视图。

两条合起来说明：多会话的瓶颈通常不在本进程，因此配额与调度必须覆盖到下游（模型、外部工具），而不只是进程内的 CPU 与内存。

### 0.2 本篇建立的三项判据

第一项用于判断隔离是否成立：问"让两条会话同时跑同一类任务，结果是否与单独跑时相同"。这条判据的检验方式是实际对比（并发跑一次、单独各跑一次），而它能发现串扰类问题。

第二项用于判断配额是否生效：问"把一条会话的配额调到很小，它会被限制吗"。配额没有实际限制作用的常见原因是它只在某一层生效（例如限制了请求数但没限制 token 数）。

第三项用于判断回收是否完整：问"跑完一百条会话之后，资源占用是否回到基线"。这条判据的检验方式是观察长期运行的进程内存与句柄数——它们的缓慢上升是回收不完整的典型信号。

### 0.3 十分钟练习：调度策略的差别

下面这段代码对比先来先服务与按配额轮转在多条会话下的等待时间。

```js
const sessions = [
  { id: 'A', work: 10, quota: 2 },   // 长会话
  { id: 'B', work: 2, quota: 2 },
  { id: 'C', work: 2, quota: 2 },
]

function fifo(list) {
  let t = 0
  return list.map((s) => { const start = t; t += s.work; return { id: s.id, wait: start } })
}

function roundRobin(list, quantum) {
  const remaining = list.map((s) => ({ ...s, left: s.work }))
  let t = 0
  const first = {}
  while (remaining.some((s) => s.left > 0)) {
    for (const s of remaining) {
      if (s.left <= 0) continue
      if (!(s.id in first)) first[s.id] = t
      t += Math.min(quantum, s.left)
      s.left -= quantum
    }
  }
  return Object.entries(first).map(([id, wait]) => ({ id, wait }))
}

console.log('先来先服务：', fifo(sessions))
console.log('按配额轮转：', roundRobin(sessions, 2))
```

两次输出的差别在 B 与 C 的等待时间上：先来先服务下它们要等 A 做完（10 个时间单位），而轮转下它们很快得到第一次响应。这条对比说明公平性的实质是"响应时间"而不是"总吞吐"——两种策略的总时长相同，而用户感受到的差别很大。

> **面试视角**
> **高频问法**："一个进程跑多条会话，你担心什么？"
> **高分要点**：说出三件事——隔离（状态不串扰）、配额（下游才是瓶颈）、以及回收（长期运行不泄漏）。只谈"并发性能"会漏掉隔离与回收这两类更难发现的问题。

### 0.5.3 三个连锁影响

第一，多会话让"上下文预算"从单条会话的问题变成全局的问题。 单条会话的上下文预算是 3.3 与 4.1 的问题（压缩与注入），而多会话时多个预算同时消耗同一个下游配额（0.1 的分析）。因此预算需要两级：会话内的分配（它决定压缩与注入的激进程度）与跨会话的分配（它决定并发数与每会话的配额）。

第二，失败隔离是这一层最容易忽略的。 一条会话的异常（未捕获的异常、无限循环、泄漏的子进程）在单会话系统里表现为"系统崩了"，而在多会话系统里应当表现为"这一条会话崩了"。它的实现要求每条会话有自己的错误边界（作用域链上的错误处理器），而缺少它时一条会话的错误会终止整个进程——这就是"失败隔离"与"状态隔离"的差别：前者是控制流问题，后者是数据问题。

第三，可观测的归因维度会从三条变成四条（3.6 的 1.7）。多会话引入了"会话之间的对比"这个维度——同一类任务在不同会话里表现不同，可能指出配置或预设有问题（5.1 的已知条件在这里被用到）。这条维度是 4.6 复盘的好素材：跨会话的差异比单会话内的波动更可能是系统性的。

### 0.5.4 它与本书其余部分的关系

本篇的并发是单进程、共享内存的，不是多进程或多机的。多进程需要进程间的协调（共享状态、分布式锁），多机还需要一致性——两者都不在本课程范围内。这条边界意味着本篇的结论在"一个进程内的多条会话"上是完整的，而它的隔离设计（每条会话一个容器与作用域）恰好也是多进程化的前提（容器可以被移到另一个进程）。

## L0 要解决的问题

### 0.1 现象一：两条会话互相干扰

第一个现象是串扰。它的形态有三种：状态串扰（一条会话改动了另一条的状态，例如共享的可变配置）、文件串扰（两条会话在同一个工作目录里改同一批文件）、以及日志串扰（事件被写进了错误的会话）。

它们的成因不同：状态串扰源于共享了本应隔离的对象（2.5 的 `isolatedNames` 没有覆盖到的地方），文件串扰源于缺少工作区租约（0.2 的第三项判据会暴露它），日志串扰源于事件的归属字段没有被正确传递。

### 0.2 现象二：一条长会话挡住其他会话

第二个现象是公平性缺失。先来先服务的调度下，一条消耗资源的会话会让其他会话长时间得不到响应（0.3 的练习给出量级）。它的表现是"系统看起来卡住了"，而实际资源并没有耗尽——只是被一条会话占着。

修法是 1.4 的调度策略与配额。而这里有一个判断值得写下来：公平性针对的是响应时间而不是总吞吐（0.3 的结论），因此调度策略的选择依据是"用户能容忍多久没有反馈"。

### 0.3 现象三：资源缓慢泄漏

第三个现象是回收不完整。进程运行若干天之后，内存与句柄数缓慢上升，而单次会话的行为没有任何异常。它的成因是会话结束后资源没有被释放——订阅、定时器、子进程、文件句柄、以及容器里的注册项（2.3 的 disposer 未全被调用）。

它的检测方式是 0.2 的第三项判据（跑一批会话后看基线），而它的修法是 1.7 的会话生命周期管理：把"会话结束"变成一个显式的、可检查的动作，而不是"不再使用它"。

### 0.4 现象四：取消没有贯穿到子操作

第四个现象是取消不完整。用户中止了一条会话，而它启动的子进程仍在运行、子 agent 仍在调用模型（3.4 的取消传播）。它的表现是"取消了但还在花钱"，而这在并发场景下更严重（多条会话都要收敛）。

修法是把取消挂在作用域上（1.6）：取消一个作用域即取消其下的一切，而它的实现复用 3.4 的进程树取消与 2.5 的作用域链。

### 0.5 这一篇要正面回答的四个问题

第一，隔离分几层、每层做什么（1.1、1.2）。第二，配额与调度如何设计（1.3、1.4）。第三，共享资源如何约束（1.5）。第四，生命周期如何收敛（1.6、1.7）。

四个问题里第二与第三是并发独有的（前两者在单会话系统里也存在，只是更容易满足）。

## L1 设计与原理

### 1.1 隔离的三层

三层隔离各自处理不同的问题。

作用域隔离（机制来自 2.5）：每条会话有自己的作用域与容器，注册项不互相可见。它的边界由 `isolatedNames` 决定——那些被声明为隔离的名字在各会话里是独立实例，而其余的共享。

数据隔离：会话日志（2.7）一条会话一个文件，记忆（4.1）按用户或任务的作用域划分，工作目录按租约独占（1.5）。

失败隔离：每条会话有自己的错误边界（0.5.3 的第二条）。

三层里数据隔离最容易被做错，因为它的边界不显然：两条会话共享一个工作目录是合理的（同一个项目），而同时写同一批文件是不合理的。这条区分正是租约要表达的东西（1.5）。

```ts
interface SessionHandle {
  readonly id: SessionId
  readonly scope: Scope                       // 该会话的作用域（2.5）
  readonly container: Container               // 该会话的容器（2.3）
  readonly profile: string                    // 来自哪个模式（5.1）
  readonly preset: string                     // 用哪个预设
  readonly workspaces: readonly Lease[]        // 持有的工作区租约
  readonly errorBoundary: ErrorBoundary        // 失败隔离（0.5.3 的第二条）
  readonly startedAt: number
  readonly state: 'idle' | 'running' | 'waiting' | 'closing' | 'closed'
}
```

`errorBoundary` 与 `state` 是两处值得说明的字段：前者让一条会话的异常不终止进程，后者让回收有一个可检查的状态（`closing` 与 `closed` 的区分很重要——正在关闭的会话仍然占用资源，因此注册表必须能表达它）。

### 1.2 该隔离的与该共享的

并发设计的第一步是分清两者，而它的判据是"这个对象的正确性依赖别的会话做什么吗"。

| 对象 | 该隔离还是共享 | 理由 |
|---|---|---|
| 会话历史与会话日志 | 隔离 | 每条会话的事实只属于它自己 |
| 上下文与压缩状态 | 隔离 | 压缩的决策基于该会话的历史 |
| 工作目录（写） | 共享但独占（租约） | 多条会话可以先后用，不能同时写 |
| 工作目录（读） | 共享 | 读不产生冲突 |
| 模型配额 | 共享（需分配） | 下游容量有限 |
| 凭据 | 共享（只读） | 凭据是长期可用的秘密 |
| 记忆（跨会话） | 共享（4.1） | 记忆的定义就是跨会话 |
| 用户模型 | 共享（4.3） | 它是关于人的，不是关于会话的 |
| 技能库 | 共享（只读） | 技能是资产，不随会话变 |
| 日志写入器 | 共享（单写者） | 3.5 的单写者约束 |
| 观测与度量 | 共享（按会话分组） | 全局视图才有意义 |

这张表里最能说明问题的是"工作目录"那一行：同一个对象在写与读两种用法下的答案不同。把整张表背下来没用，而它的判据（正确性是否依赖别人）可以推广：任何被两条会话同时修改的对象都需要共享协议，而只读的东西不需要。

### 1.3 配额：分配而不是限流

配额与限流（3.1 的重试策略）的差别在于时机：配额在请求之前分配，限流在越界时拒绝。配额的优势是它把不可预测变成了可预测——用户知道自己的会话能用多少，而系统不需要在过载时才反应。

配额的三个维度与它们的依据。

并发数（同时进行的请求数）：依据是下游的并发上限（0.1 的分析）。它的分配方式通常是"每会话一个上限 + 全局一个上限"，因为单会话的上限防饿死，全局上限防过载。

速率（单位时间内的请求数或 token 数）：依据是成本预算（3.6）。它是唯一与钱直接相关的配额。

占用（上下文 token 数、工作区数量）：依据是资源容量。它防的是"一条会话把资源占满"。

```ts
interface Quota {
  readonly maxConcurrent: number        // 该会话的并发上限
  readonly maxTokensPerMinute: number    // 速率上限（成本相关）
  readonly maxContextTokens: number      // 单会话上下文上限（与 3.3 的压缩阈值联动）
  readonly maxWorkspaces: number         // 持有的租约数上限
}

export function admit(session: SessionHandle, registry: SessionRegistry, request: Request): Admission {
  if (registry.globalConcurrent() >= registry.config.globalMaxConcurrent) return { ok: false, reason: '全局并发已满', retryAfter: 1000 }
  if (session.running >= session.quota.maxConcurrent) return { ok: false, reason: '会话并发已满', retryAfter: 500 }
  if (registry.tokensInWindow(session.id, 60_000) + estimate(request) > session.quota.maxTokensPerMinute) {
    return { ok: false, reason: '速率超限', retryAfter: 60_000 }                      // 配额（而不是限流）
  }
  return { ok: true }
}
```

三处判断的顺序有讲究：先全局、再会话、最后速率——因为前两者的拒绝是瞬时的（很快可以重试），而速率超限的等待更长。这个顺序让"被拒绝"的代价最小。

### 1.4 调度与公平性

三种策略的适用场景。

先来先服务适合"会话数少且任务长度相近"的场景。它的优点是简单与可预测（顺序就是提交顺序），缺点是一条长会话会挡住后面的（0.3 的练习）。

按优先级适合"有明确的紧急程度"的场景（例如交互式会话优先于批处理）。它需要定义优先级，而优先级的来源通常是模式或预设（5.1 的 `Preset` 可以带优先级），而不是调用者临时指定——临时指定的优先级会迅速失效（所有人都会给自己标最高）。

按配额轮转适合"多条会话都需要响应性"的场景。它的实现是给每条会话一个时间片或请求片，轮流获得资源。它是三者中唯一能同时保证响应性与吞吐的，代价是实现复杂度（需要保存与恢复进度）。

本课程的选择是配额轮转加预设提供的优先级：优先级决定谁先获得轮转机会，而配额决定每次获得多少。这条组合的依据是两者解决的问题不同——优先级处理"重要性"，轮转处理"响应性"。

### 1.5 共享资源的约束：租约与单写者

工作区租约的规则与它的实现要点。

规则：同一个工作区在同一时刻只有一个写者。读不要求租约（它不产生冲突）。例外是"读的同时有人在写"——这时读到的可能是中间状态，而处置是让读也获得一个共享租约（与写租约互斥）。

实现要点有三处。第一，租约要带超时（持有者崩溃时租约必须能自动释放），而超时的取值要覆盖最长的一次操作（过短会误释放，过长会让崩溃后的等待太久）。第二，租约的获取要能被排队（等待而不是立刻失败），否则并发会话会互相拒绝。第三，租约的持有者要能被识别（哪条会话、哪个进程），否则无法判断一个租约是否还有效。

```ts
export async function acquire(workspace: string, holder: SessionId, ctx: Context): Promise<Lease> {
  const existing = ctx.registry.leaseOf(workspace)
  if (existing && !existing.expired(ctx.now) && existing.holder !== holder) {
    return ctx.registry.enqueue(workspace, holder)                  // 排队而不是失败（要点二）
  }
  const lease = { workspace, holder, expiresAt: ctx.now + ctx.config.leaseTtl, mode: 'exclusive' as const }
  ctx.registry.setLease(lease)
  await ctx.appendEvent({ type: 'workspace/lease', workspace, holder, at: ctx.now })   // 可观测（要点三）
  return lease
}
```

三处要点（超时、排队、可识别）在这段实现里都有对应，而事件的记录让"谁在什么时候占了它"可被查询——这条记录在排查文件冲突时是唯一的依据。

### 1.6 取消的传播

取消沿作用域向下传播（0.4）。它的三层实现。

第一层是会话级的取消（用户中止）：它取消该会话的作用域，从而取消其下的一切（子进程、子 agent、待响应请求）。

第二层是父级取消（5.4 的子 agent）：父会话被取消时，派生的子会话一并取消。它的实现要求子会话的作用域挂在父会话之下（2.5 的父链），而不是并列。

第三层是超时取消：一次操作超时（3.1 的时间预算）只取消该操作，不取消整个会话——这两者的区分很重要，因为把单次超时升级成会话取消会让"一次网络抖动"终止整个任务。

三层的共同要求是取消必须释放资源（3.4 的进程树取消加宽限期），而多会话场景下这更重要——未释放的资源会累积成 0.3 的泄漏。

### 1.7 生命周期与回收

会话的五个状态（1.1 的 `SessionHandle.state`）与它们的转换。

```ts
export async function closeSession(id: SessionId, registry: SessionRegistry, ctx: Context): Promise<ReclaimReport> {
  const s = registry.get(id)
  registry.setState(id, 'closing')                                   // 先标记，阻止新请求
  const cancelled = await cancelScope(s.scope, ctx, ctx.config.graceMs)  // 取消并等待（3.4 的宽限期）
  const released: string[] = []
  for (const lease of s.workspaces) { await release(lease, ctx); released.push(lease.workspace) }
  await s.container.dispose()                                        // 释放注册项（2.3）
  await ctx.metrics.flush(id)                                        // 落盘未写入的度量（3.6）
  registry.setState(id, 'closed')
  registry.remove(id)
  const leaked = await verifyReclaimed(s, ctx)                       // 核对回收是否完整
  return { cancelled: cancelled.count, released, leaked }
}
```

六步里有三处设计要点：先标记 `closing` 阻止新请求（避免释放过程中有新请求进来）、释放顺序是取消 → 释放租约 → 销毁容器 → 落盘度量（先断掉产生资源的路径，再回收）、以及 `verifyReclaimed` 核对（0.2 的第三项判据）。

`leaked` 字段是这份实现的诚实之处：回收不完整是常态而不是异常（某个订阅没被释放、某个定时器还在），因此把它报告出来而不是假定成功。

### 1.8 两次追问

工程侧的问题是什么时候该拒绝新会话。判据是"当前并发是否已使下游排队显著"（3.6 的排队延迟指标）。拒绝比接受更好：接受一个排队很久的会话，用户等待的时间与拒绝后的重试时间差别不大，而接受会占用本机资源并让已运行会话也变慢。

产品侧的问题是多会话对用户意味着什么。用户不关心会话的注册表，而关心两件事：我的会话会不会被别人影响（隔离）以及我现在有多少资源可用（配额）。因此多会话的呈现需要一条明确的资源视图（当前占用了多少、上限是多少），而它从会话注册表派生——与 5.1 的"说明从声明派生"是同一条原则。

## L2 决策表

| # | 决策 | 我们的选择 | 替代方案 | 代价落在谁身上 |
|---|---|---|---|---|
| 1 | 隔离粒度 | 每会话一个作用域与容器 | 共享一个容器 | 每会话开销更高；换来无串扰 |
| 2 | 工作目录 | 写用独占租约、读共享 | 全部共享 | 要排队；换来无文件冲突 |
| 3 | 租约超时 | 有，且覆盖最长操作 | 无超时 | 崩溃后要等；换来不会永久占住 |
| 4 | 租约获取 | 排队 | 立即失败 | 可能长时间等待；换来不互相拒绝 |
| 5 | 配额维度 | 并发、速率、占用三者 | 只限并发 | 配置更多；换来成本可控 |
| 6 | 配额 vs 限流 | 配额（事前分配） | 限流（越界拒绝） | 要预先定分配；换来可预测 |
| 7 | 调度策略 | 配额轮转加预设优先级 | 先来先服务 | 实现复杂；换来响应性 |
| 8 | 优先级来源 | 模式或预设声明 | 调用者临时指定 | 灵活性下降；换来优先级不失效 |
| 9 | 取消粒度 | 会话级、父子级、超时级三层 | 只有会话级 | 要区分三种 | 换来一次超时不终止任务 |
| 10 | 失败隔离 | 每会话一个错误边界 | 进程级 | 要写边界代码；换来一条崩不拖垮全部 |
| 11 | 回收 | 显式关闭流程加核对 | 依赖 GC 与自然结束 | 要写流程；换来不泄漏 |
| 12 | 拒绝新会话 | 在下游排队显著时拒绝 | 一律接受 | 吞吐下降；换来已运行会话的体验 |

其中两条值得展开，因为它们的选择在实践中经常被做成另一个。

### 关于第 6 与第 7 条的完整论证（为什么是配额加轮转）

替代方案是限流加先来先服务（不需要预先分配，也不需要调度）。它在会话数少时工作良好，而在规模化时有两个问题。

第一，限流只在下游过载后才生效。那时请求已经在排队，而排队会影响所有会话（0.1 的第一条）。配额把这件事提前——在请求发出前就知道它能不能被满足，因此调用方可以选择等待、降级或者拒绝。

第二，先来先服务让响应时间不可控。一条长会话的等待时间由它前面所有会话的总工作量决定，而轮转让每条会话都获得周期性的响应（0.3 的练习量化了这个差别）。响应时间可控是多会话系统的核心体验指标——用户能容忍慢，但难以容忍"看起来没反应"。

两条合起来给出的判据是：当会话数接近下游配额时，配额加轮转是必须的。而在会话数远小于配额时，简单的策略足够。这条判据让实现复杂度与实际需要匹配。

### 关于第 11 条的完整论证（为什么要显式回收而不是依赖 GC）

替代方案是依赖垃圾回收与进程结束时的清理。它的吸引力在于不需要写回收逻辑，而它的三个代价在多会话长期运行下显现。

第一，GC 不管理非内存资源。文件句柄、子进程、定时器、外部连接、以及注册项（2.3 的 disposer）都不受 GC 管辖。它们泄漏的表现是缓慢的资源耗尽（0.3 的现象），而这类问题在开发期几乎不可见。

第二，"会话结束"与"不再使用它"不是同一件事。前者是显式事件（可以被捕获并触发清理），后者是隐含的状态（无法被观测）。依赖后者等于依赖调用者的纪律，而纪律在规模化时会失效。

第三，回收需要核对才能被发现不完整。`verifyReclaimed`（1.7）的作用不是清理，而是把"没有清理干净"变成一条可见的报告。没有它时，泄漏只能通过系统级的监控察觉（而那时已经积累了很久）。

### 3.2 注册表段

```ts
export class SessionRegistry {
  private readonly sessions = new Map<SessionId, SessionHandle>()
  private readonly leases = new Map<string, Lease>()

  create(profile: string, preset: string, ctx: Context): SessionHandle {
    if (this.sessions.size >= ctx.config.maxSessions) throw new Error(`会话数已达上限 ${ctx.config.maxSessions}`)
    const id = newId()
    const scope = ctx.root.createChild(`session:${id}`)                  // 每会话一个作用域（2.5）
    const container = new Container(scope, ctx.config)                    // 每会话一个容器（2.3）
    const handle: SessionHandle = { id, scope, container, profile, preset, workspaces: [], errorBoundary: new ErrorBoundary(scope), startedAt: ctx.now, state: 'idle' }
    this.sessions.set(id, handle)
    return handle
  }

  globalConcurrent(): number { return [...this.sessions.values()].reduce((n, s) => n + (s.state === 'running' ? 1 : 0), 0) }
  tokensInWindow(id: SessionId, window: number): number { /* 从度量读（3.6） */ return 0 }
  setState(id: SessionId, state: SessionHandle['state']): void { const s = this.sessions.get(id)!; this.sessions.set(id, { ...s, state }) }
}
```

三处要点：会话数上限在创建时检查（而不是在资源耗尽时）、每会话一个作用域与容器（隔离的实现）、以及 `globalConcurrent` 只统计 `running` 状态（`waiting` 的不占并发）。

### 3.3 调度段

```ts
export function schedule(registry: SessionRegistry, ctx: Context): SessionId | null {
  const ready = [...registry.all()].filter((s) => s.state === 'running' || s.state === 'idle')
  if (ready.length === 0) return null
  const byPriority = groupBy(ready, (s) => ctx.presetOf(s.preset).priority ?? 0)
  const levels = [...byPriority.keys()].sort((a, b) => b - a)             // 高优先级先（L2 第 8 条）
  for (const level of levels) {
    const group = byPriority.get(level)!
    const next = group.find((s) => registry.credits(s.id) > 0)             // 配额轮转（L2 第 7 条）
    if (next) return next.id
  }
  return null
}
```

优先级与轮转的组合在这里体现：先按优先级分组，再在组内按剩余配额挑选。`credits` 的实现是每会话一个可补充的计数器（补充速率来自配额，1.3）。

### 3.4 共享段与生命周期段

共享段的实现见 1.5（`acquire`），而生命周期段见 1.7（`closeSession`）。两处的补充是排队与超时的交互：

```ts
export async function awaitLease(workspace: string, holder: SessionId, ctx: Context): Promise<Lease | null> {
  const deadline = ctx.now + ctx.config.leaseWaitMs
  while (ctx.now < deadline) {
    const acquired = await tryAcquire(workspace, holder, ctx)
    if (acquired) return acquired
    await sleep(ctx.config.leasePollMs)
  }
  return null                                                            // 等待超时（不是永久排队）
}
```

等待也有超时——否则一条会话可能永久排在一条崩溃的持有者之后（虽然 1.5 的租约超时最终会释放它，但等待方的超时让它可以更早地做别的选择，例如换一个工作区或报告冲突）。

### 5.1 术语表

| 术语 | 在本篇里的准确含义 | 容易误解为 |
|---|---|---|
| 会话注册表 | 活动会话的索引与状态 | "连接池"（它管的是会话不是连接） |
| 隔离 | 一条会话的变化不影响另一条 | "沙箱"（沙箱是安全边界，隔离是并发边界） |
| 共享资源 | 多条会话竞争的东西 | "全局变量"（共享可以是只读的） |
| 工作区租约 | 对工作目录的独占声明 | "文件锁"（锁是文件级的，租约是工作区级的） |
| 配额 | 事前分配的资源上限 | "限流"（限流是事后拒绝） |
| 公平性 | 调度分配资源的方式 | "平均"（公平针对响应时间） |
| 取消传播 | 取消沿作用域向下 | "中断"（它强调的是向下贯穿） |

### 5.3 三条容易踩的规则

第一条，先分清该隔离的与该共享的。判据是"正确性是否依赖别的会话做什么"。

第二条，写工作目录必须有独占租约，且租约要带超时并能排队。

第三条，会话结束要走显式关闭流程并核对回收。GC 不管句柄、子进程与定时器。

## L9 仍未解决（这一篇自己的缺陷）

| 缺陷 | 后果 | 修法 | 当初为什么这么写 |
|---|---|---|---|
| 单进程共享内存 | 一条会话的 CPU 密集操作仍会阻塞其他 | 独立进程（挑战题第一题） | 本课程的会话以 I/O 等待为主 |
| 配额是静态的 | 负载变化时分配不合理 | 动态配额（挑战题第二题） | 静态配额实现简单且可预测 |
| 租约没有死锁避免 | 两条会话可能互相等待 | 排序获取或超时退避（挑战题第五题） | 单工作区场景下很少出现 |
| 会话迁移未实现 | 无法负载均衡 | 状态捕获（挑战题第三题） | 需要 4.7 的状态外部化配合 |
| 回收核对是尽力而为 | 少数残留仍然可能漏报 | 用更强的资源追踪（例如句柄快照） | 快照成本高 |
| 优先级依赖预设 | 预设少时无法区分 | 更细的优先级来源 | 临时指定会失效（L2 第 8 条） |

第一条与第三条属于并发模型与协议，第二条与第六条属于分配与优先级，第四条与第五条属于能力与精度。第一条值得单独标记：它意味着一条会话里的 CPU 密集操作（例如大文件处理、复杂正则）会阻塞整个进程，而这条限制在本课程的会话形态下（以外部调用等待为主）影响不大——但它是这套设计的真实边界，把它写下来比假装不存在更负责。

### 问题升级练习

模糊问题：「我要让系统同时跑多条会话，要注意什么？」

升级后的精确问题：

> 多会话至少包含三件互相制约的事：**隔离**（哪些状态必须分开）、配额（有限的资源怎么分）、以及收敛（会话结束后资源怎么回来）。
> 第一件与第二件互相制约——隔离得越彻底，每会话的开销越大，能同时跑的会话就越少。
> 我能不能为这三件事各找出一条**可检查的判据**？
> 特别是：有没有哪一条判据，是**能在跑完一批会话之后检查的**？

提升点说明：原问题无法回答，因为"注意什么"没有边界。升级后的版本把它拆成三件具体的事，指出隔离与开销的权衡，并追加以一个更强的问题：哪一条判据能在跑完一批之后检查——因为回收与泄漏只有在那时才能被发现。

一处需要修正的预判：0.5.2 把"工作区租约"标为对 5.4 的强依赖。读完之后要补一层方向：租约的粒度可能需要比"工作区"更细——两个子 agent 在同一个工作区里改不同的目录时，工作区级租约会让它们被迫串行（浪费并行度）。处置方式是引入"目录级租约"作为工作区租约之下的细分，而这带来新的问题（死锁可能性上升，L9 第三条）。这条张力本篇没有解决，它会在 5.4 并行子任务时成为约束。

通向下一篇的桥。 本篇让多条会话能共存，而它留下了一个没有答案的问题：当多条会话都需要人的判断时，这些请求如何呈现与归属。一条会话请求批准一个危险操作（3.2 的守卫），而进程里同时有三条会话在等待——审批需要知道它属于哪条会话、优先级如何、以及用户可以如何快速处理一批。

下一篇 `5.3 交互与权限` 处理这件事。它与本篇的连接点有三处：会话注册表提供的归属（0.5.2 的第一行）、配额与优先级的呈现、以及取消在多会话下的统一入口。

## 本篇新词

装配（composition） 指把一组部件按依赖关系与配置组织成一个可运行系统。它回答三个问题：装哪些部件、按什么顺序装、以及每个部件拿到什么配置。装配的产物通常只是一个已构造的对象图，而它的输入（配置）才是这一篇的主题——因为装配的错误绝大多数来自输入的合并规则，而不是构造过程本身。

profile 指一组命名的配置集合，用来表达"这一套系统是给这种用途启动的"。它与"环境"（开发、测试、生产）不完全等同：同一环境可能有多个 profile（例如一个只跑模型层的与一个跑完整系统的），而一个 profile 也可能跨环境使用。本课程采用的形态是后者——profile 描述用途，环境变量提供差异。

bundle 指可以被整体引用的部件集合。它是 profile 的组成部分，用来避免在每个 profile 里重复列出同一批插件。bundle 与 profile 的差别在于 bundle 只回答"包含哪些部件"，而 profile 还回答"以什么配置包含它们"。

覆盖（override） 指上层配置对下层同名条目的替换。它的语义必须被明确规定：是整体替换（后面的完全替代前面的），还是逐字段合并（只替换被写到的字段）。两种语义的差别在嵌套结构上变得明显——整体替换下写一个字段会丢掉该条目下的其它字段，而逐字段合并不会。

深合并（deep merge） 指递归地把下层的值合并到上层：对象逐字段合并，数组按下标或按标识合并，标量由上层覆盖。它的表达力更强，代价是"最终值是什么"变得更难推断——一个字段可能由三层各写一部分拼出来。

装配清单（manifest） 指装配的输入文件，它列出部件与它们的配置。它与代码的区别是它不含逻辑，因此它的差异可以在评审时被逐行读出。

可复现的装配 指同一份清单（加上同一组环境输入）在两次运行中产生行为相同的系统。它要求装配过程不依赖时间、随机数、文件系统的遍历顺序或网络状态——这些依赖在开发时不会暴露，而它们会让"在我机器上是好的"变成一种真实且无法复现的故障。

条件装配 指按环境或配置项决定某个部件是否装载。它的表达力最强，代价是系统的组成不再是静态可读的——同一份代码在不同环境下是不同系统，而"这个功能为什么没生效"的排查必须先从"它有没有被装载"开始。

这张图的关键线索在第二块：覆盖语义是本篇全部故障的主因。装配本身只是一个循环（按清单构造部件），而"为什么我改了配置没生效"这类问题的答案几乎总在合并规则里。

### 0.1 一个具体的判断：`!!js` 与 `!js` 的差别

本仓库 `vendor/cordis` 的 loader 允许在配置里求值 JavaScript 表达式，而它区分两种写法：`!!js` 用于插件配置里的字段，`!js` 是 YAML 标签的标准形式。两者的实际差别不是语法偏好，而是求值的时机与范围：前者只在插件的 `config` 字段内被求值，因此它不会让一份清单在加载阶段变成任意代码执行。后者是通用标签，允许出现在更多位置。

这个区分的价值在于它把"配置能力"限制在了一个可审计的范围内。一份清单由人评审，而评审的前提是"它能表达什么"有一个边界——如果清单里任何位置都能执行代码，那么清单与代码就没有区别，评审清单也就失去了意义。

本课程采用的规则与它同构：配置只表达数据与有限的求值，不表达控制流。需要条件逻辑的地方用条件装配（1.7），而条件装配的键必须来自一个被规定的集合（例如环境名），而不是任意表达式。

### 0.2 本篇建立的三项判据

第一项用于判断一处配置该放哪一层：问它是否随环境变化。随环境变化的放环境变量或 profile 差异，不随环境变化的放清单（它是代码的一部分，与代码一起评审与版本控制）。这条判据来自 12-factor 的第 3 条，而它的实际收益是同一份清单可以在所有环境下使用。

第二项用于判断覆盖语义是否清楚：问"我只写了这个条目的一个字段，其它字段会保留还是消失"。答不出来就说明契约没有规定，而这类不确定性会在有人第一次写部分覆盖时变成故障。

第三项用于判断装配是否可复现：问它有没有依赖时间、随机数、或文件系统的遍历顺序。最容易被漏掉的是遍历顺序——一个目录下的文件按什么顺序被读入会影响最终的合并结果，而不同平台与不同文件系统给出的顺序不同。

### 0.3 十分钟练习：两层配置的合并

下面这段代码把替换与深合并放在一起，可以直接运行。

```js
const base = { model: { name: 'a', timeoutMs: 30000, retry: { max: 3 } }, tools: ['read', 'write'] }
const over = { model: { timeoutMs: 60000 } }

// 替换：整条 model 被替换
const replaced = { ...base, model: over.model }
console.log('替换后的 model：', JSON.stringify(replaced.model))   // {"timeoutMs":60000}

// 深合并：逐字段合并
function deepMerge(a, b) {
  const out = { ...a }
  for (const [k, v] of Object.entries(b)) {
    out[k] = v && typeof v === 'object' && !Array.isArray(v) && a[k] ? deepMerge(a[k], v) : v
  }
  return out
}
const merged = deepMerge(base, over)
console.log('深合并后的 model：', JSON.stringify(merged.model))   // {"name":"a","timeoutMs":60000,"retry":{"max":3}}
```

两次输出说明两种语义的实际差别：替换之后 `name` 与 `retry` 消失了，而深合并保留了它们。故障正是从这种消失开始的——写覆盖的人只想着改超时，而结果是模型名回到了未定义。这条练习的结论是：覆盖语义必须在契约里写明，因为两种做法都"合理"，而它们的后果相差很大。

> **面试视角**
> **高频问法**："多环境配置你怎么管？"
> **追问方向**："覆盖是替换还是深合并？"能立刻说清这一条的候选人很少，而它恰好是配置类故障的主因。

### 0.5.3 三个连锁影响

第一，配置的合并规则不清会让"改了不生效"成为常态。 这是配置类故障里最常见的一种，而它的成因通常不在合并实现，而在没有规定语义。团队里三个人各自实现一处覆盖，两个人按替换、一个人按合并，于是同一个字段在不同位置的覆盖行为不同。它的表现形式是"我明明在配置里写了，但系统用的是别的值"，而排查需要读三处合并实现。处置方式只有一条：把语义写成契约，并让所有合并走同一个函数——一处实现，一处语义。

第二，条件装配会让系统的组成从静态可读变成运行时才知道。 一个部件是否被装载取决于配置与环境，于是"这个功能在哪"这个问题的答案不再能从代码里读出来。它的代价在排查时显现：必须先确认"它有没有被装载"，才能开始查"它为什么不对"。处置方式有两条，一是限制条件装配的键集合（只允许按少数几个维度切换），二是让装配的产物可查询（启动时打印"已装载的部件清单"）。

第三，装配不可复现会让问题无法被稳定复现。 如果部件的加载顺序依赖文件系统的遍历顺序，那么两个平台上可能得到不同的顺序，而顺序影响优先级的先后（2.4）与覆盖的先后（本篇）。这类问题的表现形式是"在我机器上是好的"，而它无法通过增加日志解决——只能通过消除不确定性来源解决。最容易被忽略的一处是遍历顺序：它不产生错误输出，只在某些平台上让结果不同。

### 0.5.4 它与本书其余部分的关系

本篇的装配是本地的、单进程的、启动时完成的。这个边界决定了它的结论在哪里需要补充。

运行时的动态装配（在系统运行中装载或卸载部件）在第 4 卷的演化能力里出现，而它需要本篇的清单格式支持增量更新。分布式装配（多个进程各自的配置如何保持协调）不在本课程范围内，它的相邻问题（配置中心、灰度开关）在第 5 卷的规模化里被部分触及。

## L0 要解决的问题

### 0.1 现象一：配置改了，但没生效

第一个现象在日常工作里出现频率最高。你在清单里加了一行，重启，系统行为没变。排查的路径通常是这样：先确认配置文件确实被读到了（打印它的路径），再确认那一行的写法没被解析器忽略（检查缩进与类型），最后才发现是下层有一份更高优先级的同名配置把它盖住了。

这个现象的性质是"配置的来源不可见"：系统里同时存在清单、环境变量、默认值三处可能影响这个键的地方，而"最终生效的是哪一个"没有任何地方能回答。处置的方式有两条，一是让来源可查询（打印每个键的最终值与它的来源），二是减少来源的数量。本课程两条都做：优先级规则写进契约，且启动时可以打印最终配置及其来源。

### 0.2 现象二：多环境维护多份配置，然后开始漂移

第二个现象的起点是合理的需求——开发环境与生产环境的配置不同，于是复制出两份清单。漂移从第一次"只改一边"开始：给生产环境加了一个新插件，忘了同步到开发环境。开发环境调了一个超时值，忘了同步到生产。几周之后两份清单的差异无法解释，而"这个功能在开发环境能用生产不能用"的问题会反复出现。

这个现象的根因不是"人不细心"，而是把"不变的部分"与"随环境变化的部分"混在了一起。12-factor 的第 3 条给出的划分是：配置（随环境变化）存于环境，其余属于代码。落到本篇的形态是：清单描述"装哪些部件、它们的默认配置"，而环境变量只提供差异（例如密钥、外部服务的地址）。两份清单在它的替代下变成一份清单加两组环境变量。

### 0.3 现象三：同一份配置，两次启动行为不同

第三个现象最少见也最难查。同一份清单、同一台机器，两次启动得到不同的行为——通常是若干部件的相对顺序不同，而顺序影响覆盖与优先级的先后。它的成因可能是文件系统的遍历顺序、并发初始化的完成顺序、或者某个部件在初始化时读了时间。

这类问题的危险性在于它不会稳定复现，因此"修好它"这件事无法被验证。处置方式是消除不确定性来源：显式规定加载顺序、不依赖目录遍历、初始化不读取时间与随机数。其中目录遍历最容易被忽略，因为它在开发机上恰好总是一致的（同一个文件系统的枚举顺序稳定），而在别的平台上不同。

### 0.4 现象四：这个功能为什么没生效

第四个现象是条件装配带来的。某个部件按配置决定是否装载，而它的存在与否决定了某个功能是否可用。当功能不生效时，排查的第一个问题不是"它为什么不对"，而是"它有没有被装载"——而后者在只读代码的情况下无法回答。

它的处置方式包括把装载结果暴露为可查询的产物（启动清单），以及限制条件装配的键集合（只允许按少数几个维度切换，而不是任意表达式）。第二条是更根本的：条件装配的表达力越强，系统的组成就越不可预测，而"不可预测"本身是一种成本。

### 0.5 这一篇要正面回答的四个问题

第一，谁组装、装什么、按什么顺序（1.1）。第二，配置从哪来，优先级是什么（1.2）。第三，覆盖的语义是什么，替换还是深合并（1.3）。第四，装配如何可复现（1.5）。

四个问题里第三是第一位的：它是其余三个问题的基础——不知覆盖语义，就无法设计优先级。不知优先级，就无法设计来源。而不可复现的装配通常也来自覆盖与顺序的不确定。

## L1 设计与原理

### 1.1 装配要回答的三个问题

装配看起来只是"把部件构造出来"，而它的每一个环节都有一个必须被规定的选择。

装哪些部件：清单列出部件名与它们的配置。这里的第一个选择是"清单里写部件名还是写文件路径"——写名字要求有一张名字到实现的注册表（多一层间接，但清单更稳定：文件可以移动，名字不该变）。写路径直接但脆弱。本课程选前者，理由是清单应当与目录结构解耦。

按什么顺序装：顺序由依赖决定（被依赖者先装），而依赖可以从声明里读出（2.3 的 `inject` 与 `provide`）。这里的选择是"自动按依赖排序"还是"按清单顺序装载并检查依赖"。前者省事，代价是当依赖图有环或含延迟依赖时，排序结果依赖遍历顺序（于是不可复现）。后者要求清单的顺序正确，但它的行为是可预测的。

本课程选后者并要求启动期检查依赖——它把不可复现的风险换成了"清单写错会立刻报错"。

每个部件拿到什么配置：这是本篇的主要内容，涉及配置的来源、优先级与覆盖语义。

### 1.2 配置的来源与优先级

本课程采用四层来源，优先级从高到低：命令行参数、环境变量、清单（profile 与 bundle 合并后的结果）、代码里的默认值。

四层的划分依据是改动它们的人与时机不同。默认值由部件作者写（与代码一起评审）。清单由部署者写（与版本控制一起）。环境变量由运维在部署时提供（不进版本控制，因为它可能含密钥）。命令行参数由使用者临时指定（用于一次性调试）。每往上一层，改动者的作用范围就越窄、越临时。

```ts
type ConfigSource = 'cli' | 'env' | 'manifest' | 'default'
interface Resolved<T> { value: T; source: ConfigSource }
```

类型里带 `source` 的用途在 0.1 已经说明：它让"这个值从哪来"成为可查询的。实现上它只要求每层合并时记录命中的层，成本很小。

一条容易犯的错误是把密钥写进清单。清单会进版本控制，而密钥一旦进入历史就无法撤销（1.1 的可逆性分级里的第三级）。12-factor 的第 3 条正是针对这一点：配置与代码分离，而分离的判据是"它会不会因环境而不同、以及它是不是秘密"。

### 1.3 覆盖的两种语义

覆盖有两种实现，它们的行为差别在嵌套结构上显现。

替换：后面的条目整体替代前面的。实现是一行赋值，行为容易预测（最终值是最后写的那一份），代价是写部分覆盖时会丢掉未写的字段——而丢掉的部分不会报错，它只是回到了"未定义"。

深合并：递归合并，标量由上层覆盖，对象逐字段合并，数组按规则处理（按下标、按标识、或整体替换）。它的表达力更强（可以只写差异），代价是最终值难以推断（三层各写一部分时，要读三处才知道结果）。

| 语义 | 写部分覆盖时 | 最终值可推断性 | 适用场景 |
|---|---|---|---|
| 替换 | 未写字段消失 | 高（看最后一处） | 配置项少、层级浅 |
| 深合并 | 未写字段保留 | 低（要看全部来源） | 配置项多、层级深、来源多 |

本课程的选择是对对象深合并、对数组整体替换。这条组合的理由是：对象的字段之间通常独立（改超时不影响模型名），而数组的元素之间存在顺序与身份关系（把两个插件的数组按下标合并会产生无意义的组合）。这条规则必须写进契约，因为"数组按标识合并"也是一种常见选择，而它适用于另一种数据（例如按名字去重的列表）。

选择之后还有一条配套要求：合并必须由同一个函数完成。如果三处各自实现合并，那么"规则"就只是文档里的一句话，而实际行为由三份实现决定——这正是 0.1 那个现象的成因。

### 1.4 profile 与 bundle 的关系

两者的分工是"装什么"与"以什么配置装"。

bundle 是一组部件的集合，它回答"装什么"，不携带配置（只携带部件之间共享的默认值）。profile 引用若干 bundle，并为其中的部件提供配置。

```
profile: dev
  bundles: [core, tools, web]
  config:
    llm: { name: dev-model, timeoutMs: 10000 }
    tools: { maxResultChars: 2000 }

profile: headless
  bundles: [core, tools]
  config:
    llm: { name: prod-model }
```

这种结构解决的是 0.2 那个漂移问题：bundle 只写一次，profile 只写差异。新增一个核心插件时改 bundle，两个 profile 同时获得它。调整某个 profile 的超时值只改一处，不影响另一个。

它的第二个收益是"组合的可读性"：读一个 profile 就能知道这个系统的组成，而不用去追代码里哪些地方 import 了什么。第 5 卷的模式与预设会把这个结构变成面向用户的形态。

### 1.5 装配的可复现性

可复现的含义是：同一份清单加同一组环境输入，得到行为相同的系统。它要求装配过程不依赖四类东西。

第一是时间。任何"用当前时间做默认值"（例如生成一个会话 id）都会让两次运行不同。处置方式是把时间作为显式输入传入，而不是在装配时读取它。

第二是随机数。用于生成标识的随机数应当由调用方提供（或者在清单里固定），否则两次运行的标识不同，而标识会进入日志（于是日志无法比较）。

第三是文件系统的遍历顺序。读取一个目录下的插件文件时，必须先排序再处理。这一条在开发机上通常看不出问题，因为同一文件系统的枚举顺序稳定。

第四是网络的可用性。装配阶段不应发起网络请求（拉取配置、校验远端版本），因为它会让启动时间与成功与否依赖外部状态。

四条的判据是同一个：装配的输入只应当来自清单与环境，其它一切都是不可复现的来源。

### 1.6 配置的验证

错误配置应当在启动时失败，而不是在第一次使用时失败。这条要求的实现方式是在装配阶段校验配置的形状，并在校验失败时拒绝启动。

校验的粒度有一个取舍。做得细（每个字段的类型、取值范围都查）能挡住更多错误，代价是每个部件都要写一份校验规则。做得粗（只查必需的键存在）成本低，代价是错误延后到运行时。本课程的选择是"校验结构与必需项，取值范围由部件自己查"，理由是取值范围常常与业务逻辑相关，而结构错误是纯粹的配置错误。

失败信息的要求与前几篇一致：它要携带下一步需要的东西。一条好的配置错误会说清"哪个部件的哪个字段、期望什么、实际是什么、这个键来自哪一层"——最后一项由 1.2 的 `source` 提供。

### 1.7 条件装配与它的代价

条件装配指按某个条件决定部件是否装载。它的表达力最强（同一份代码在不同环境下是不同系统），代价在 0.4 已经说明。

本课程对它的限制有两条。第一，条件的键来自一个被规定的集合（例如 `env` 与 `profile`），而不是任意表达式。这条限制让"这个部件在什么情况下会被装载"可以被穷举。第二，装配的产物可查询：启动时输出已装载的部件清单，并且它是幂等可复现的（同一份配置两次启动输出相同）。

替代方案是"所有部件都装载，用运行时开关控制行为"。它的组成是静态可读的，代价是未启用的部件仍然占用资源与初始化时间，且它的开关逻辑会渗透到代码里。两者的选择依据是部件的初始化代价：代价小的用一个统一的开关，代价大的用条件装配。

### 1.8 两次追问

工程侧的问题是配置该由谁写。答案取决于配置的层级：默认值由部件作者写（他最了解合理范围），清单由部署者写，环境变量由运维提供。这个分工的意义在于每一层都只写它有权决定的东西——作者不该决定生产环境的超时值，运维不该决定默认的模型名。

产品侧的问题是模式（profile）对用户意味着什么。一个模式不只是配置集合，它是一种能力承诺：选择"问答模式"意味着没有文件工具，选择"编码模式"意味着有。这意味着模式的划分是产品决定而不是技术决定——它回答的是"我们想让用户用这套系统做什么"，而这个问题的答案决定了哪些能力该被组合在一起。

### 1.9 配置的可观测性

配置是排查的第一现场，因为"系统为什么这样运行"的第一个答案通常是"它拿到了什么配置"。三个查询入口值得留出来。

第一个是打印最终配置及其来源。它对每个键输出最终值与它来自哪一层。这个入口的价值在 0.1 那个现象里已经说明：没有它，排查"改了不生效"只能靠人工比较几处配置，而比较在层数增长后容易出错。

第二个是打印已装载的部件清单（含顺序）。它回答"这个系统由什么组成"，而这正是条件装配之后无法从代码读出的事情。它的另一个用途是双次装配的对比基础（3.6 判据 10）。

第三个是打印合并前的各层原始值。它比第一个更底层：第一个给出最终值与来源，这个给出每一层的原始输入。排查"合并规则是不是我想的那样"时需要它，因为有些故障不是来源问题而是合并结果与预期不符。

三个入口的成本都很低（都是把已有的中间结果打印出来），而它们的价值随系统的配置层数增长。这与前几篇的结论一致：机制应当自带它自己出问题时的观察方式，而配置这一层尤其需要，因为它的输入不在代码里。

### 1.10 装配的测试策略

装配的缺陷有一个共同特征：它们的表现是"在某些配置下才出现"，因此单配置的测试无法覆盖。三类测试各自覆盖一类。

第一类是合并的单元测试：对同一个函数输入几组对象与数组，核对合并结果。它覆盖语义本身，包括"对象深合并、数组整体替换"这两条与常见直觉不同的规则。

第二类是来源优先级的测试：对同一个键在四层各给一个值，逐层撤掉，核对最终值与来源的对应关系。它覆盖优先级规则，而这类规则的错误表现为"某层的值永远不生效"。

第三类是多配置的装配测试：用几组不同的清单与环境组合各装配一次，核对已装载清单与关键配置。它覆盖的是"组合起来对不对"，而这类缺陷在单配置测试里不可见。

三类之外还有一条专门的检查：双次装配的产物一致性。它不是功能测试，而是可复现性检查（4.1 第二层），而它发现的问题（遍历顺序、时间依赖）用其它方式很难发现。

### 1.11 清单的评审要点

清单进版本控制，因此它会出现在代码评审里。四类问题值得在评审时固定检查。

第一，新增的部件是否只改了该改的地方。如果一个新部件需要同时改 bundle、改 profile、改代码里的默认值，说明它的接入点分散——而分散的接入点会让"新增一个能力要改几处"这个指标变差（第 1 卷的十站模型里把它作为拓展性的度量）。理想形态是只改 bundle 一处。

第二，配置里有没有出现密钥。清单会进历史，而进入历史之后无法撤销。评审时的判据是看值本身是否像一个凭据（长随机串、包含 `key`/`token`/`secret` 的键名），而不是相信"这个人应该不会写"。

第三，覆盖是否只写了差异。深合并的收益只有在"上层只写变化的部分"时才兑现。如果每个 profile 都把配置抄全，那么语义上等同于替换，而重复的内容会漂移。

第四，条件装配的键是否在受限集合内。任意表达式的条件会让系统的组成无法穷举，而这一类问题在评审时最容易通过——因为它看起来只是一个配置项。

四类检查的共同点是它们都能被机械地部分检查（前两条可以用一段脚本扫出来）。能机械检查的规则应当写成脚本而不是写在文档里，这条原则在本课程里反复出现，而配置这一层的可检查性尤其高。

|---|---|---|---|---|
| 1 | 清单里写名字还是路径 | 名字加注册表 | 直接写文件路径 | 多一层注册；换来清单与目录解耦 |

| 9 | 配置校验的时机 | 装配阶段，失败即拒绝启动 | 使用时再发现 | 启动多一步；换来错误早暴露 |
| 10 | 条件装配的键 | 受限集合（环境、模式） | 任意表达式 | 表达力受限；换来组成可穷举 |

其中两条值得展开，因为它们的选择在实践中经常被做成另一个。

### 关于第 4 条的完整论证（对象为什么深合并）

替代方案是整体替换。它的优点是可预测：最终值是最后一次写入的那一份，看一处就知道结果。代价在嵌套配置上显现。

考虑一个模型层的配置：`{ name, timeoutMs, retry: { max, backoffMs } }`。清单里提供了全部四个字段，而某个 profile 只想把超时改成六十秒。

替换语义下，这个 profile 必须把另外三个字段也抄一遍——而抄写的内容会在清单更新时过期：清单里 `retry.max` 从三改成五，profile 里抄的那一份仍是三，于是该 profile 永久地使用旧值，而没有任何信号提示这件事。

深合并语义下，profile 只写 `{ timeoutMs: 60000 }`，其余字段从清单继承，因此清单的更新会自动生效。代价是"最终值是什么"需要把三层拼起来才能知道。

本课程选深合并的理由是重复的代价会随时间上升，而推断的代价是一次性的：抄一份配置的成本在写的时候很低，而它的过期是静默的。读三处配置的成本是每次排查多花几分钟，而它不会产生错误。缓解推断成本的手段是 1.2 的 `source`——它让"这个值来自哪一层"可以被查询，从而把"读三处"变成"读一处输出"。

### 关于第 8 条的完整论证（装配为什么不能读时间与随机数）

替代方案是允许装配读取它们（例如用当前时间做会话的默认创建时间、用随机数生成会话 id）。这在开发时完全可用，代价在三个场景下出现。

第一个是测试。断言"会话的创建时间早于结束时间"在时间依赖下仍然通过，而断言"两次运行的装配产物相同"会失败——而后者正是复现问题的基础。

第二个是日志比较。会话 id 由随机数生成时，同一段操作的两次运行会产生不同的日志，而"比较两次运行的日志找差异"是最常用的排查手段之一。

第三个是分布式或多进程场景。两个进程各自生成 id 时，冲突概率随规模上升，而冲突的表现形式是数据互相覆盖。

本课程的选择是把时间与随机数作为显式输入传入装配：调用方在启动时读一次（或从环境变量取），然后把它交给装配器。这样装配本身是纯函数，而"读时间"这件事被限制在入口处的一行。

这条决策与 2.5 的可复现性是同一件事的两种表述：不可复现的系统无法被稳定地排查，而排查能力是长期运行的系统最基本的要求。

## L3 实现（施工图）

### 3.1 文件结构

```
// kernel/compose.ts
// ┌─ 清单段 ──────────────────────────────────────────
// │  Manifest / Profile / Bundle 的类型
// ├─ 解析段 ──────────────────────────────────────────
// │  loadManifest(path)：读清单，不做求值
// ├─ 合并段 ──────────────────────────────────────────
// │  merge(a, b)：对象深合并、数组整体替换（唯一实现）
// ├─ 解析来源段 ──────────────────────────────────────
// │  resolve(key)：四层来源，返回值与来源
// ├─ 校验段 ──────────────────────────────────────────
// │  validate(config)：结构错误即拒绝启动
// └─ 装配段 ───────────────────────────────────────────
//    compose(ctx, manifest, inputs)：按顺序装载并输出已装载清单
```

六段里第五与第六是这一篇的产出核心。第二段（解析）刻意不做求值，理由在 0.1 已经说明：清单不表达控制流。

### 3.2 清单的类型

```ts
interface Manifest {
  readonly profiles: Record<string, Profile>
}
interface Bundle { readonly plugins: readonly string[] }
interface Profile {
  readonly bundles: readonly string[]
  readonly config: Record<string, unknown>      // 部件名 → 配置
}
```

三个类型的划分对应 1.4 的分析：bundle 只说装什么，profile 说以什么配置装，manifest 是它们的集合。这里没有"环境"这个维度——环境差异由环境变量提供（1.2 的第三层），因此同一份 manifest 可以在所有环境下使用。

### 3.3 合并的实现

```ts
/**
 * 唯一的合并实现。对象深合并，数组与标量由上层覆盖。
 *
 * @param base 下层配置
 * @param over 上层配置
 * @returns 合并结果（新对象，不修改入参）
 */
export function merge<T>(base: T, over: unknown): T {
  if (over === null || typeof over !== 'object' || Array.isArray(over)) return over as T
  if (base === null || typeof base !== 'object' || Array.isArray(base)) return over as T
  const out: Record<string, unknown> = { ...(base as Record<string, unknown>) }
  for (const [k, v] of Object.entries(over as Record<string, unknown>)) out[k] = merge(out[k], v)
  return out as T
}
```

这段实现有三处值得指出。第一，它对数组直接返回上层值——这条规则必须在契约里写明，否则使用者会期待"数组也能部分更新"。第二，它不修改入参，返回值是新对象——这条保证让合并可以安全地在多层之间复用。第三，它的类型签名用 `unknown` 接收上层值，因为上层可能写任何类型，而校验由校验段负责。

### 3.4 来源解析

```ts
export function resolve<T>(key: string, inputs: Inputs): Resolved<T> {
  for (const source of ['cli', 'env', 'manifest', 'default'] as const) {
    const v = lookup(source, key, inputs)
    if (v !== undefined) return { value: v as T, source }
  }
  throw new Error(`配置项 ${key} 在四层来源中都没有找到`)
}
```

两个细节。第一，优先级用数组顺序表达，而不是一堆 if——顺序本身是契约，写成数据更容易被检查。第二，`lookup` 对不存在的键返回 `undefined` 而不是抛错，因为"这一层没写"是正常情况。

### 3.5 校验与拒绝启动

校验段的职责是"结构错误即拒绝启动"。它检查三样：清单里的部件名是否都在注册表里、每个部件的必需配置是否齐全、以及配置的类型是否与部件声明的类型一致。第三样需要部件提供它的配置形状——本课程的做法是让部件导出一个可选的 `configSchema`，缺失时不校验类型。

拒绝启动的实现方式是抛出一个聚合错误，它列出全部问题而不是第一个。这一点很重要：配置错误通常是成批出现的（一个人改了一处结构，导致若干键失效），只报第一个会让部署者重启多次才能配好。

### 3.6 验收判据

| # | 判据 | 怎么检查 |
|---|---|---|
| 1 | 清单里的部件名未注册时拒绝启动 | 写一个不存在的名字，核对启动失败且错误含该名字 |
| 2 | 必需配置缺失时拒绝启动 | 删掉一个必需键，核对失败信息含键名与来源 |
| 3 | 配置错误成批报告 | 同时写错三处，核对错误里列出三处 |
| 4 | 环境变量覆盖清单 | 设置同名环境变量，核对最终值来自 `env` |
| 5 | 命令行覆盖环境变量 | 两者同时提供，核对最终值来自 `cli` |
| 6 | 对象深合并 | 上层只写一个字段，核对下层其余字段保留 |
| 7 | 数组整体替换 | 上层写一个短数组，核对结果就是那个短数组 |
| 8 | 合并不修改入参 | 合并前后比较两个输入对象 |
| 9 | 每个键可查询来源 | 对四个键各查一次，核对 `source` 正确 |
| 10 | 同一份输入两次装配产物相同 | 连续装配两次，核对已装载清单一致（含顺序） |
| 11 | 按清单顺序装载 | 清单里写三个有依赖关系的部件，核对装载顺序 |
| 12 | 依赖缺失时拒绝启动 | 清单少了被依赖的部件，核对失败信息指明缺哪个 |

第 10 条是本篇的核心判据：它把"可复现"从一句要求变成一个可以检查的性质。实现时它要求装配器不读时间与随机数（L2 第 8 条），并且遍历任何目录时先排序。

### 3.7 实现顺序

先做清单解析与类型（判据 1、2），再做合并与来源（判据 4、5、6、7、8、9），然后做校验与成批报错（判据 3、12），最后做装配与可复现检查（判据 10、11）。

---

### 3.7 实现里最容易写错的三处

第一处是合并的返回值语义。正确做法是返回新对象、不修改入参。常见错误是就地修改下层对象。后者的后果是"合并一次之后下层配置被永久改变"，于是同一次装配里的第二次合并拿到的是已经被改过的底层——这类缺陷在同一份配置只被合并一次时不会出现，而当它被多个部件或多次装配共享时暴露。

第二处是来源解析的"未提供"与"提供了 undefined"。正确做法是把两者都当作未提供（继续往下找）。常见错误是用 `key in obj` 判断存在性，于是显式写了 `undefined` 的层会截断查找链。这个差别在环境变量上尤其容易出问题，因为环境变量在未提供时通常表现为 `undefined` 而不是不存在。

第三处是装载顺序与依赖检查的配合。正确做法是按清单顺序装载，并在每个部件装载时检查它的依赖是否已经就绪。常见错误是只在装配结束后检查依赖图，于是"顺序写错"与"依赖缺失"这两类问题被混成同一个错误。分开报告它们的价值在于它们的原因不同：前者要改清单顺序，后者要补部件。

### 3.8 一次完整装配的时序

把本篇与前后几篇串起来，一次从启动到可用的完整时序如下（括号里是责任方）。

```
1 读入口参数          （入口）        profile 名、命令行覆盖
2 读环境变量          （入口）        密钥与外部地址
3 读清单              （装配器）      只看数据，不做求值
4 合并 bundle 与 profile（装配器）    唯一的合并函数
5 解析每个键的来源    （装配器）      四层优先级
6 校验配置            （装配器）      结构错误即拒绝启动，成批报告
7 建根作用域          （装配器）      2.5 的机制
8 按清单顺序装载部件  （装配器）      每装一个检查依赖是否就绪
9 输出已装载清单      （装配器）      供查询与双次对比
10 进入运行状态       （循环）        2.7 的内容
```

这张时序里有三个检查点值得强调。第 6 步是"错误早暴露"的落点——它让配置错误在启动时失败而不是在第一次使用时。第 8 步是"依赖缺失与顺序错误分开报告"的落点。第 9 步是"组成可查询"的落点，它同时是双次装配对比的基础。

三个检查点的共同形态是：它们都在装配阶段把一件运行时才知道的事变成了启动时就知道的事。这正是装配这一层存在的价值——它把不确定性尽可能前移，而前移的收益是故障的排查成本从"运行时偶发"降到"启动即失败"。

## L5 语法速查

### 5.1 术语表

| 术语 | 在本篇里的准确含义 | 容易误解为 |
|---|---|---|
| 装配 | 把部件按依赖与配置组织成可运行系统 | "启动"（启动是装配之后的事） |
| profile | 一组命名的配置集合，表达用途 | "环境"（同一环境可有多个 profile） |
| bundle | 可整体引用的部件集合，不含配置 | "profile"（bundle 只说装什么） |
| 覆盖 | 上层对下层同名条目的替换或合并 | "优先级"（那是来源之间的规则） |
| 深合并 | 对象逐字段合并、数组整体替换 | "递归合并一切"（数组是例外） |
| 配置来源 | 命令行、环境、清单、默认四层 | "配置文件" |
| 可复现的装配 | 同一输入两次运行得到行为相同的系统 | "确定性启动"（它更强，还要求不含随机） |
| 条件装配 | 按条件决定部件是否装载 | "配置开关"（开关是运行时行为，条件装配影响组成） |

### 5.2 命令速查

| 目的 | 命令 | 说明 |
|---|---|---|
| 跑装配契约测试 | `node tests/t9-compose.mjs` | 十二条判据 |
| 负向验证 | `node grade/negative-check-compose.mjs` | 四类错误实现应全部被抓 |
| 打印某配置项的来源 | `node src/apps/cli.ts --print-config` | 需要实现提供该入口 |
| 找多处合并实现 | `rg -n 'function merge\|deepMerge' src/` | 命中多于一处即为语义分裂 |

### 5.3 三条容易踩的规则

第一条，覆盖语义用同一个函数实现。多处实现等于多处语义，而它们会漂移。

第二条，清单里不放密钥。它会进版本控制，而进入历史之后无法撤销。

第三条，装配不读时间与随机数。它们让两次运行的产物不同，而可复现是排查的前提。

## L9 仍未解决（这一篇自己的缺陷）

| 缺陷 | 后果 | 修法 | 当初为什么这么写 |
|---|---|---|---|
| 清单格式是本课程自定的，没有标准 | 与其他工具的配置无法互换 | 采用通用的配置格式或提供转换 | 自定格式能精确表达"部件名加配置"的最小形态 |
| 没有配置的热更新 | 改配置必须重启 | 引入增量装配（挑战题第五题） | 重启的成本在本卷的系统里可以接受 |
| 配置校验依赖部件提供 schema | 不提供 schema 的部件无法校验类型 | 要求所有部件提供 schema，并在缺省时按最宽类型处理 | 强制 schema 会让小部件也要写一份类型声明 |
| 没有配置的版本与迁移 | 清单格式变化时旧清单无法读取 | 给清单加版本号与迁移规则 | 本卷的清单只有一个版本 |
| 条件装配的键受限，不支持按能力探测 | 无法表达"如果这个部件可用就装载" | 引入能力探测（它需要加载顺序上的额外约束） | 受限的键让组成可穷举，这是刻意的取舍 |
| 来源解析没有覆盖"运行时修改" | 运行中改的配置无法被追溯 | 把运行时修改也作为一种来源登记 | 本卷不做运行时修改 |

第一条与第三条属于"位置放错"——格式与校验规则本该由更通用的层承担。最后一条属于能力边界。其余三条属于本卷的有意简化。第一条值得单独标记：自定格式的一个直接后果是使用者需要学一套新东西，而这类成本在项目早期看不出来，在需要与外部工具集成时会集中出现。

## L11 系统影响回溯

回看第 0.5 节的三个连锁影响。

| 预判 | 本篇分析之后的结论 | 状态 |
|---|---|---|
| 合并规则不清会让"改了不生效"成为常态 | 确认，并给出"一处实现、一处语义"与来源可查两条处置 | 成立 |
| 条件装配会让系统组成从静态可读变成运行时才知道 | 确认，并给出限制条件键与输出已装载清单两条处置 | 成立 |
| 装配不可复现会让问题无法被稳定复现 | 确认，并列出四类不可复现来源（时间、随机数、遍历顺序、网络） | 成立且更具体 |

一处需要修正的预判：0.5.2 把"覆盖语义"标为对第 5 卷的模式与预设的强依赖。读完之后要补一层：它同时对 2.7 有强依赖——会话日志的格式演进规则（版本号与可忽略标记）与配置的覆盖语义是同一类问题，它们都在回答"新旧两份东西如何共存"。这个共性在第 3 卷的格式演进里会被统一处理。

通向下一篇的桥。 本篇让系统可以被组装起来，而它留下了一个没有答案的问题：组装起来的系统如何记录自己做过什么。装配解决了"有哪些部件"，但没有解决"这些部件运行过程中发生的事存在哪里、以什么形态存在"。

下一篇 `2.7 会话日志与循环` 处理这件事，它是本卷的技术枢纽。它与本篇的连接点是清单与日志的对称性：清单是系统启动时的输入，日志是它运行时的输出，而两者都必须是可复现的——清单决定系统的组成，日志决定它能否被重建。

## 记忆锚点与复述练习

### 一、骨架：四块

```
   谁组装 ──► 覆盖怎么算 ──► 配置从哪来 ──► 怎么复现
      ↓          ↓              ↓              ↓
   清单+依赖   深合并对象    四层来源      四类不可复现来源
   1.1        整体替换数组   1.2           1.5
```

只记一行就记这行：谁组装 → 覆盖怎么算 → 配置从哪来 → 怎么复现。

### 二、情境绑定：当你……就想起……

| 当你…… | 立刻想起 |
|---|---|
| 配置改了不生效 | 先查最终值的来源，再看合并规则 |
| 要给某个环境单独一份配置 | 先问它是"随环境变"还是"是秘密"；前者用环境变量，后者不进清单 |
| 看到多处合并实现 | 语义已经分裂；收敛到一处 |
| 要写部分覆盖 | 确认对象深合并、数组整体替换这条语义 |
| 想按目录遍历装载插件 | 先排序；否则不同平台上的顺序不同 |
| 装配时想读当前时间做默认值 | 改成由入口传入；否则两次运行不同 |
| 要给某个配置项加开关 | 先问它影响的是"组成"还是"行为"；组成用条件装配，行为用开关 |
| 看到某个功能没生效 | 先确认它有没有被装载，再看它的配置 |
| 要在清单里写密钥 | 不能：清单进版本控制，而历史无法撤销 |
| 怀疑启动行为不确定 | 连续装配两次，比较已装载清单（含顺序） |

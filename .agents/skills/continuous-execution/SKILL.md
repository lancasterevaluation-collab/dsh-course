# 持续执行

## 何时使用

同时满足三条时使用：

1. **完成清单是明确的**——能写出"还剩哪些"，且每项的完成状态可机械检查；
2. **每步可验证**——有现成的检查命令，通过与否不依赖主观判断；
3. **用户已授权自主推进**——用户说了"直到全部完成"、"不要中途确认"、"离开一段时间"之类的话。

缺任何一条都不要用：清单不明确时推进会失控，不可验证时会积累未发现的问题，未授权时自主推进越界。

## 核心行为

**每轮做完一批就立即开始下一批，不等待确认。**

一轮的固定动作，顺序固定：

1. **读清单**：找到剩下的项目与当前进度（本项目为 `进度.md` 台账）；
2. **选下一批**：按既定优先级取，不重新排序，不临时加项；
3. **执行这一批**：按已固化的流程做（本项目为：写正文 → 写算例 → 数字回归校准 → 规范化 → 双检 → 构建）；
4. **验证**：跑检查命令，必须全绿才算这一批完成；
5. **更新清单**：把这一批的完成状态与遗留问题写进台账；
6. **立即回到第 1 步**：不总结、不征求确认。

## 停止条件

只有四种情况停下：

- **清单全部完成**：收尾并报告；
- **遇到需要用户决策的分叉**：两个方案各有明显代价，且无法从既有材料判断；
- **下一步是不可逆或对外可见的操作**：发布、删除、推送、对外承诺；
- **缺少只有用户能提供的信息**：凭据、外部系统的状态、用户的偏好。

其余情况一律继续。"做得差不多了"、"这一批完成得不错"都不构成停止理由。

## 每轮的报告方式

报告放在**一轮结束时**，而不是每一批之后。报告只写三件事：**这一批完成了什么**、**验证结果**、**下一批是什么**。不写计划、不写感想。

## 与验收标准的关系

**不得为通过检查而降低内容标准。** 检查是下限不是目标。当检查与质量标准冲突时，改检查的口径并写清理由（口径本身也可能选错量），而不是改内容去迎合检查。

## 反模式

- **批量补模板**：用机械替换去满足判据（例如给所有代码块补一句"代码如下："），使文档形状合格而内容没有增量。
- **跳过验证**：连续做多批后才跑一次检查，导致问题累积，且无法定位是哪一批引入的。
- **重复报告**：每一批都汇报一次，把本应连续执行的工作切成多次等待。
- **扩大范围**：清单之外临时加项，使"全部完成"的判据失效。

# 作答 · 1.1 一个功能的一生

> 这是**参考答案**，用于验证判据本身可被满足。学习者应当自己作答之后再对照。

## 一、选的一个功能

**功能**：把会话存储从"每会话一个 JSON 文件"改为 SQLite 表，供本地 CLI 与 Web 两个入口共用。

**为什么选它**：它有过三次改动——先加、后加索引、最后回滚过一次查询优化；其中"加索引"那次我记得最清楚，因为它让写入变慢了。

## 二、十站

| 站 | 发生了什么 | 留下的材料 |
|---|---|---|
| 1 需求出现 | Web 端要按时间检索历史，扫描文件太慢 | 一份 issue |
| 2 方案成形 | 选 SQLite 而不是引入服务端数据库 | 一页设计说明 |
| 3 拆分任务 | 拆成 schema、迁移、读路径改造、写路径改造 | 四个子任务 |
| 4 实现 | 新增 `session-store.ts`，保留旧读写作为兜底 | 提交记录 |
| 5 验证 | 用 200 个历史会话对比新旧读取结果 | 一份对比脚本与输出 |
| 6 发布 | 先只让 Web 端走新路径，CLI 继续走旧路径 | 灰度开关 |
| 7 观测 | 记录读取 P95 与写入错误率 | 指标面板 |
| 8 发现 | 加索引后写入 P95 从 8ms 升到 21ms | 一次告警 |
| 9 处理 | 回滚该索引，改为按需建 | 一次回滚 |
| 10 退役 | 旧读写路径在两个月后删除 | 一次清理提交 |

## 三、关键判断

**可逆性**：这次改动是**单向门**。理由是回滚需要把 SQLite 里的新数据导回 JSON 文件，而这一步需要人工确认，不能自动完成。所以它走了完整设计评审，而不是快速上线。

**影响面**：改存储牵连四处——读写路径、迁移脚本、两个入口的初始化代码、以及依赖会话结构的导出功能。这四处都要跟着改。

**完成定义**：
- 判据：新旧读取结果在 200 个历史会话上完全一致。
- 指标：读取 P95 低于 50ms，写入错误率为 0，两者都接入面板。

**如果重来**：我会在第四站就写下"索引按需创建"这条约束，而不是等到第八站才发现。

# 作答 · 1.2 复杂度与技术债

> 这是**参考答案**，用于验证判据本身可被满足。学习者应当自己作答之后再对照。

## 一、选的一笔债

**债**：`util/format.ts` 被 5 个模块直接导入，内部有 14 个导出函数、圈复杂度最高 19，且没有任何测试。

**为什么它是债**：改它一次平均多花 3 小时（要读完全部调用点确认兼容），而团队每周大约有 0.6 周会碰到它。

## 二、量化

**利息**：摩擦系数 f = 3（每次多花 3 小时），触碰频率 c = 0.6（次/周），所以

```
i = f × c = 3 × 0.6 = 1.8 小时/周
```

**还债窗口**：团队每周可用于还债的时间 R = 40 小时，

```
T = R / i = 40 / 1.8 ≈ 22 周
```

也就是大约五个月后，这笔债的利息会吞掉全部还债能力。

**分类**：属于**无意且鲁莽**——没人意识到它的耦合度，也没有任何约束（无测试、无接口）。按四象限的优先级，它应当排在"有意且鲁棒"的债之前处理。

## 三、处理方案与依据

**先封装，不重构。** 理由是利息的两个因子里，封装降的是 c（触碰频率），重构降的是 f（每次的代价），两者效果相同，而封装的成本低一个数量级。

具体做法：加一层 `format/index.ts` 作为唯一入口，把 5 处直接导入改为从这一层导入。扇入从 5 降到 1 之后，触碰频率 c 近似按比例下降：

```
i' = 3 × (0.6 / 5) = 0.36 小时/周  →  T' = 40 / 0.36 ≈ 111 周
```

窗口从 22 周延长到约 111 周，而这一步只需要一个接口文件的工作量。

**之后再做**：把内部的 14 个导出收敛到接口层暴露的 5 个，并给接口层补测试。这一步改善 f，可以排在下个季度。

## 四、为什么不选重写

重写只能回收**偶然复杂度**那一部分。这个模块的偶然复杂度主要来自"命名混乱"与"职责混杂"，估计占 40% 上下；而其中真正由业务规则决定的那部分（格式化规则本身的分支）无法通过重写消除。所以重写收益上界约 40%，却要放弃已验证的行为——不划算。

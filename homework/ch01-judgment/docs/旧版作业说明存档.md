## 一、先读这一节：这份作业为什么这样设计

大多数人做作业的方式是"从头往下读，遇到不会的再回头找"。这份文档不是那样组织的，原因有二：**它要训练的不是记忆，是判断**；而判断能力有一个特点——**它只在你自己做出错误判断并被纠正时才增长**。所以这份文档里最重要的部分不是"步骤"，而是每一处的「你会怎么想错」。

### 1.1 你会在哪里卡住，而那是我故意留的

先说清三件你会遇到的事，这样它们发生时你不会以为是自己不行。

**第一，任务 1 的第一步会让你不舒服。** 我要求你先不看任何文档，只用 `rg` 和源码把 `kernel/session.ts` 的结构读出来。你会觉得"有文档为什么不看"，而且很可能读得不完整。**这正是设计的意图**：看文档时你学到的是"这个项目怎么设计的"，不看文档时你学到的是"如何从代码里把设计读出来"。前者让你了解一个项目，后者让你能面对任何项目。两者都需要，但顺序不能反——如果先看文档，你会在潜意识里把"读懂"定义为"找到那段说明"，而这个定义会在你面对没有文档的代码时立刻失效。

**第二，判分器会给你一些"看起来不公平"的扣分。** 比如你答对了 10 个依赖但多写了 2 个，得到的不是 10/12 而是 10/(12+2)。这是刻意的，理由在任务 2 里讲——它对应一个真实的能力：**区分"某个名字出现了"与"某个行为被依赖了"**。

**第三，你会想要"直接看答案"。** `grade/answers.example.json` 就在那里，随时可看。我不阻止你，但请等到做完任务 2 再看，因为这里有一个认知上的机制：**一旦你见过正确答案，"我本来也能想到"的感觉会覆盖掉"我为什么没想到"这个问题**——而后者才是这份作业要给你的东西。

### 1.2 三个原理，它们决定了这份文档的写法

我没有凭感觉设计引导，下面三条是它每个部分的依据。知道它们，你也能自己设计学习方法。

**认知负荷（Cognitive Load Theory）** 把学习时的心理负担分成三种：任务本身的难度（内在）、呈现方式带来的难度（外在）、以及用于构建理解的难度（相关）。关键结论是：**只有第三种带来学习，前两种都在消耗你的注意力预算**。所以 `kit/tools/` 里放了预置的依赖分析工具——手工数 61 个文件的 import 是纯粹的**外在负荷**，它不会让你更懂架构，只会让你更累。而"判断哪些依赖是必要的、哪些热点值得保留"是**相关负荷**，那才是这份作业要求你做的。

**最近发展区与脚手架（ZPD / Scaffolding）**：当任务难度刚好超出你当前能力一点时，学习效率最高。所以这份文档在每个任务里都分成几个阶段，每个阶段末尾写「你应该看到了什么」——那是**即时反馈**，用来让你随时知道自己在不在正轨上。等你做第二个、第三个模块时，这些提示会更少：**脚手架是应该逐步拆除的**。

**生成效应（Generation Effect）**：自己生成的信息比读到的记得牢得多。所以这份文档几乎不给结论，而是反复说"这里你要生成什么"。最明显的例子是任务 1 的不变量那一栏——我不会告诉你答案，只会告诉你**去哪里找**（断言、测试、文档三处），以及**什么情况下应当警惕**（三类证据都没有）。

### 1.3 怎么用这份文档

按你的状态选一种，不要按顺序通读。

**如果你现在要开始动手**：直接跳到 §3（环境准备），然后进 §4 的任务 1。每个任务的「你会怎么想错」在你**动手之前**先读一遍。

**如果你已经卡住了**：跳到 §4 里你正在做的那个任务，读「你会怎么想错」那一小节。那七条覆盖了实测中出现频率最高的几类错误。

**如果你做完了想检查质量**：跳到 §7 与 §8，那里有"做完了但做得浅"的判别方法。

## 四、任务逐个引导

### 任务 1 · 模块卡片（30 分）

#### 为什么做这个

因为"看懂一个模块"这件事，你的直觉是错的。直觉告诉你"看懂 = 从第一行读到最后一行"，而真正可用的"看懂"是四个具体问题的答案：它**承诺**什么、它**维持**什么关系、它**不管**什么、它的状态**归谁管**。这四个问题构成后面所有工作的基础——任务 2 要用它们判断波及面，任务 4 要用它们区分调用链与事件链。

`kernel/session.ts` 被选中，原因很具体：**它的难度分散在四个方向上**。它承诺的是事件追加语义，维持的是"模型可见 ⟺ 日志可重建"，不管的是"该 append 什么"，而它的状态归 `Session` 实例所有。如果你只用了"读流程"这一种方法，你只能得到第一个问题的答案。

#### 你会怎么想错

**错误一：把类型导入算作依赖。** 你会打开 `session.ts`，看到三行 import，其中一行是 `import type { ChatMessage, LLMUsage, ToolCall } from './llm.ts'`，然后很可能把它算进扇出。**我实测时就是这么错的**，而且错了两次——第一次把类型算进扇出，得到 Ce=1；修掉之后又忘了扇入侧也要区分。正确的口径来自一个更基本的问题：**这个依赖在运行时会存在吗？** `import type` 编译后被完全擦除，所以它不构成运行时依赖；但它在**改结构时**仍然波及——这就是为什么扇入要分"值 / 仅类型"两组，而扇出只算值。

**错误二：只搜 `src/kernel/`，漏掉大半个仓库。** 你会很自然地只在自己关注的目录里搜。但 `session.ts` 的扇入是 **16 个文件**，其中 7 个在 `demos/`。用 `rg -l "from '.*session" src/` 搜全仓，一个都别漏。

**错误三：认为"找不出没有证据的不变量"说明代码写得好。** 恰恰相反。**如果你一条标红项都没有，通常说明你只记录了文档里已经写明的那些**——那是在抄录，不是在提取。

#### 阶段 A：建立形状（不看文档）

```powershell
cd D:\dsh-mini
rg -n "^import" src/kernel/session.ts      # 它的依赖
rg -l "from '.*session" src/               # 谁依赖它
rg -n "^export" src/kernel/session.ts      # 它的公开面
```

**你应该看到了什么**：`session.ts` 有 507 行、6 个值导出（1 个常量、1 个类、4 个函数）、16 个引用它的文件。这一阶段**不要**去读实现——你的目标是形状，不是细节。

**停下来想一想**：看到"16 个文件引用它，但其中只有 7 个用值"时，你的第一反应是什么？如果我要改这个文件的行为，我该看哪 7 个还是哪 16 个？——这个答案会直接决定你在任务 2 里的判断质量。

#### 阶段 B：算出来，而不是猜出来

```powershell
node tools/depgraph.mjs --repo D:\dsh-mini --module kernel/session.ts
```

**你应该看到了什么**：工具分两段列出依赖者——「值依赖者」用 `←`、「仅类型依赖者」用 `⇢`。它给原始数据，但**不会告诉你哪一段该填进 `fanInValue`**。这个映射要你自己做。

**注意**：`kit/answers.json` 里每个槽旁边都有 `_提示` 字段，说明它要填什么、以及为什么。先读提示再填，能省掉大量试错。

#### 阶段 C：与文档核对，并做自检

现在才读文档：`session.ts` 的头部注释（很长，值得逐段读）与 `docs/07-session.md`。把"读了文档才知道"的东西记进 `writeup.md` 的第一节。

**自检：你现在应该能回答**

- 这个模块**保证**什么？（一句话，不要用"它做了什么"这种句式）
- 它的哪一条约束是**跨函数**的？（提示：想想 `seq` 与事件数组长度的关系）
- 如果我在它内部加一个方法，属于"越界"还是"合理"？依据是什么？

如果第三个问题答不出，说明"边界约束"那一栏你还没填——回到阶段 A 看头部注释里"它不做……"这类句子。

**测试**：

```powershell
node tools/check.mjs --repo D:\dsh-mini --verbose
```

**第一次跑可以加 `--verbose`**（列出全部标准答案项，帮你校准颗粒度）。**任务 2 之后就不该再加了**——那时你应该能不看答案判断自己对不对。

### 任务 2 · 波及推演（40 分，全篇核心）

#### 为什么做这个

因为这是"读代码"与"做产品"之间唯一的桥梁。你可以很懂代码，但如果无法回答"这个需求要改几处、会不会出事"，你就无法参与任何成本讨论——你只能问"大概要多久"，然后接受一个无法验证的数字。

这个任务给的需求（给 `run_command` 加超时）**看起来很小**，这正是它被选中的原因：**它是"看起来半天就能做完"的典型，而实测中它的波及面跨了四个层次**。

#### 你会怎么想错

**错误四（最重要的一个）：只搜代码，漏掉"不会报错"的地方。** 你会搜 `run_command`，在 `src/` 下找到几处，然后觉得差不多了。但它在 `modes/` 与 `prompts/` 下还有三处，而**这三处改了不会报错、不改也不会报错**——它们只是让模型看到一个不存在的能力，或者看不到一个存在的能力。这类"静默失效"的位置是这份作业里分值最高的部分（10 分），因为**它们是真实项目里最容易积累的问题**。

**错误五：把"提到"当成"依赖"。** `apps/verify.ts` 里也出现了 `run_command`（在验收期望里）。要把它算进波及面吗？判断标准是一个提问：**如果这个行为变了，这处代码会出错吗？** 验收期望里的字符串不会因为工具多了一个参数而出错——所以它不属于"必须同步修改"，但它是你**需要知道**的地方。这个区分就是判分器用 Jaccard 式判分的原因。

**错误六：跳过"为什么"直接列清单。** 你会想快速凑齐五项事实然后跑判分器。但这份作业的真正产出是 `writeup.md` 里的那段结论——**成本主要落在哪一类工作上、最可能出意外的是哪一步**。后面那个问题的答案藏在实现里：去看 `command-tool.ts` 现在怎么处理子进程。

#### 阶段 A：先问结构，再搜关键字

不要一上来搜 `timeout`。先回答三个问题（写进 `writeup.md`）：这个工具的**定义**在哪、谁决定它**可见**、谁告诉模型它**存在**。这三个问题对应三个层次，也是四个搜索动作的来源。

#### 阶段 B：四类搜索

```powershell
cd D:\dsh-mini
rg -l "run_command" src/            # ① 代码层
rg -l "run_command" modes/ prompts/ # ② 配置与提示词层 ← 静默失效就在这里
rg -n "TOOL_POOL_NAMES|TOOL_CATALOG" src/plugins/tools.ts  # ③ 池清单
rg -n "child_process|spawn" src/kernel/command-tool.ts     # ④ 实现方式
```

**你应该看到了什么**：① 给出 4 个文件，② 给出 3 个文件（这就是那 10 分），③ 给出工具池位置，④ 给出实现里已存在的一个 `spawn` 调用——**那个调用就是你要修改的接缝**。

**停下来想一想**：如果我把 `run_command` 改名为 `run_shell`，会发生什么？编译器会报错吗？测试会失败吗？——如果两个答案都是"不会"，那么你刚刚理解了什么叫"静默失效的依赖"。

#### 阶段 C：写结论（最花时间，也最值钱）

在 `writeup.md` 里回答：这次改动的成本主要落在**理解 / 修改 / 验证**哪一类上？最可能出意外的是哪一步？

**"最可能出意外"需要依据**，不能是直觉。提示：读 `command-tool.ts` 里现在怎么处理错误与清理，再想一个问题——**终止一个进程与终止一棵进程树，是同一件事吗？在不同平台上呢？**

### 任务 3 · 规则命令化（5 分）

#### 为什么做这个

因为**写在文档里的规则会随时间失效，写在命令里的规则会随时间报警**。这条原则的价值在你进团队时会立刻显现：一个永远绿的检查比没有检查更糟（它制造虚假的安全感），而一个能报警的检查会持续阻止一类问题——**而且它不需要你写任何业务代码**。

#### 你会怎么想错

以为"写出来就行"。判分器不检查脚本有多优雅，它检查两件事：能否在正常状态下返回 `PASS` 与退出码 0，以及**你是否真的演示过它报警**。第二件事无法伪造——`selfTestOutput` 里必须有你抓到人为违规的那次运行输出。

#### 步骤

1. 打开 `kit/scripts/check.mjs`——**骨架已经给你了，里面写满了引导注释**，你只需要填标着 `TODO` 的部分（三处）。
2. **在 `D:\dsh-mini` 的副本里制造一次违规**，跑它，保存输出，删副本。
3. 把脚本路径与那次输出填进 `answers.json` 的 `task3`。

**你应该看到了什么**：骨架在正常状态下输出 `PASS`；你在副本里制造违规后，它明确指出违规的文件与位置。如果你的脚本第一次跑就报警，**先检查是不是规则写错了**（假阳性），而不是高兴。

### 任务 4 · 双轨时序图（20 分）

#### 为什么做这个

因为只读函数调用链的人，会**看不见事件**。而插件化的系统里，相当一部分行为由事件驱动——它不在调用链上。这个任务训练把运行时看成**两条并行的链**的能力，它直接决定你能不能回答"我改了这个事件，谁会受影响"。

#### 你会怎么想错

**错误七：只画调用链。** 最常见，也最好检查：如果你的图里没有 emit 与 on 的对手戏，那它就不是双轨图。

**错误八：漏掉配置层的钩子。** `bundles/*.json` 与 `modes/*.json` 里的字段也是钩子点——**它们能在不改一行代码的情况下改变行为**。这正是"钩子"的定义，也是它容易被忽略的原因（它不在任何 `.ts` 文件里）。

#### 步骤

```powershell
cd D:\dsh-mini
rg -n "ctx\.on\(" src/           # 监听注册点
rg -n "ctx\.emit\(" src/         # 事件发出点
rg -n "disabled" bundles/ modes/ # 配置层钩子
```

**你应该看到了什么**：`ctx.on(` 出现在 4 个文件里，`ctx.emit(` 共 18 次。**注意 `demos/` 里也有注册**——它们算数，因为运行时会真的注册。

**画图要求**：两栏（左调用链、右事件链），每个 emit 标事件名，每个监听者标文件，钩子点用 `★`。画在 `writeup.md` 的第四节。

**停下来想一想**：你画的图里，哪一条信息**只存在于事件链上**？如果把它删掉，你在调用链上会不会看出异常？——这个答案就是"为什么要看两条链"。

## 五、检查点：你随时可以知道自己走到哪

## 八、FAQ

**Q：判分器会不会因为我的另一种正确写法判错？**
不会，只要你写的是同一个事实。它做集合与数值比对：`src/kernel/llm.ts`、`./llm.ts`、`kernel/llm.ts` 会归一到同一个键。但写"它依赖了 llm 模块"这种散文会被判错——**答卷要写文件名**。

**Q：`--verbose` 算作弊吗？**
第一次不算（它帮你校准颗粒度），做完任务 2 之后就算。真正有价值的用法是"先自己判，再对照"。

**Q："做完了但做得浅"怎么识别？**
三个信号：任务 1 一条标红项都没有；任务 2 的清单里全是"会报错"项；`writeup.md` 里没有任何"我原本以为……结果发现……"的记录。**第三个信号最准**——它意味着你的理解在过程中没有发生变化，而那通常说明你没有真的在读。

**Q：我能改 `kit/tools/` 里的工具吗？**
可以（它是你的环境），但没必要。如果你改了它而作业结果变好了，那是工具在替你答题。

**Q：中间隔一天真的有必要吗？**
有。间隔本身是记忆机制的一部分，而且它让你第二次坐下来时**带着一个已经消化过的框架**重新看题目——很多人会发现前一天卡住的地方第二天自然通了。

## 一、先读这一节：这份作业为什么这样设计

这份作业与你熟悉的形式有一个根本差别：**它的一半是"能被自动判分的题"，另一半是"必须由你自己判断的题"**。所以先说清为什么这样切。

**能被自动判分的部分（A/B/C 三组，72 分）** 考的是**判断的速度与准确度**。它对应的真实场景是：面试官给你一个改动，问"这会不会出问题"，你要在三十秒内给出判断与判据。**这类能力可以练，也值得练**——但它只是入场券。

**不能自动判分的部分（D 组，28 分）** 考的是**判断的质量**。它对应的场景是：面试官追问"你怎么知道的""如果换成 X 呢""代价是什么"。**这一部分没有标准答案**，因为它的评分标准不是"答对"，而是"你的推理能不能被追问住"。

**所以判分器只给你 72 分**——剩下的 28 分要你自己对着 rubric 打分。**这不是偷懒，而是故意的**：如果你连给自己打分都做不到，那说明你还没有能力评价一个论证的质量——而那恰好是这个岗位最核心的能力。

### 1.1 你会得到什么

**第一，30 道题的逐题详解。** `grade/答案解析.md` 里每一题都给了"为什么""完整答法""常见误区""追问应对"。**它的用法不是对答案，而是练口述**——面试失分很少是"不知道"，而是"知道但说不清"。

**第二，一次真实的接口审计。** D 组的第一个任务要求你审计 `dsh-mini` 的一个接口，产出发现清单。**这份清单可以直接变成面试时的项目故事**（见 §六）。

**第三，一个能背下来的判据体系。** 三类承诺、五项清单、破坏性分类表、四种演进手段——它们的价值在于**面试时反复用同一套判据回答不同问题**，而这正是"结构化"的体现。

### 1.2 你会怎么想错

**错误一：把 A 组当成知识题。** A 组的十二道题看起来在考"你知道哪些改动是破坏性的"，实际上它在考**你的判据是否统一**。如果你第 1 题靠记忆答、第 12 题靠推理答，你迟早会自相矛盾。**正确的做法是全程只用一个判据**："有没有依赖原有契约的代码会因此失败"。

**错误二：认为"增加 = 安全"。** A 组第 1 题和第 8 题都是"增加"，但都是破坏性的。**这个直觉错误在真实工作里很常见**，也是面试官爱设的坑。

**错误三：D 组写成了"读后感"。** 你会倾向于写"这个接口设计得不错，但有几处可以改进"。**那不算审计**。审计的产出是一张**按严重度排序的发现清单**，每条包含"发现什么、后果是什么、怎么修"。

**错误四：跳过"外部消费者测试"。** 正文 L4.1 提到的第二层验证（给一个不知道实现的人只看契约，看他能不能写对）**几乎没人会真的做**。但它是最有说服力的验证方式，也是面试里可以讲的一个亮点。

### 1.3 怎么用这份文档

**要开始动手**：直接跳到 §三（环境准备），然后进 §四。
**已经卡住**：跳到 §四里对应的那一组，读"你会怎么想错"。
**做完了想验证**：跳到 §六（面试模拟）——**那一节才是这份作业真正的验收**。

## 四、任务逐个引导

### 4.1 A 组 · 破坏性判断（12 题，36 分）

**这一组只考一件事**：你有一个统一的判据，并且能在十二种情况下都用它。

**你会怎么想错**：见 §1.2 的错误一与错误二。

**做法**：对这十二道题，**每一题都在心里默念一遍判据**（"有没有依赖原有契约的代码会因此失败"），再给答案。**不要跳步**——跳步会让你的判断变成凭感觉。

**做完之后的自检**：把 12 个答案连起来看，问自己一个问题——**我答"safe"的那些题，有没有哪一道其实改变了行为？** 如果有，那道题就是错的（因为行为的改变就是破坏性，与签名变没变无关）。

**这一组里最值得单独记住的**：第 11 题（收紧时序）与第 12 题（改默认值）。前者是**测试测不出来**的破坏性，后者是**diff 里看不出来**的破坏性。**面试官问"什么改动最危险"时，这两类就是标准答案。**

**测试**：`node tools/check.mjs --verbose`（第一次可以加 `--verbose` 看标准答案）。

---

### 4.2 B 组 · 承诺分类（8 题，16 分）

**这一组考的是"看到一句话，能立刻说出它是哪类承诺"。**

**为什么它重要**：面试官问"你怎么设计这个接口"时，**能分类的人不会漏项**——他会逐类检查"行为写了吗、时序写了吗、错误写了吗"。**不会分类的人只会想到行为承诺**（那是最直观的一类），于是漏掉时序，而时序的缺失会导致最难查的 bug。

**四类的记忆方式**（照这个顺序想）：
```
行为   = 会发生什么        （返回值、副作用、幂等性）
时序   = 什么时候能调      （前置条件、并发、重入）
错误   = 失败了怎样        （抛什么、能否重试）
所有权 = 谁负责收拾        （句柄、内部集合、注销）
```

**你会怎么想错**：把"调用它会写日志"归到"其他"——不，它是**行为**（副作用）。把"不是线程安全的"归到"错误"——不，它是**时序**。

**做完之后的自检**：这八道题里有四道属于时序。**如果你只分出了两三道，说明你对时序承诺的范围理解偏窄。**

---

### 4.3 C 组 · 术语（10 题，20 分）

**这一组不是为了背，而是为了能准确表达。**

**为什么它值得单独成组**：面试里用错术语会立刻暴露深度——比如把"后置条件"说成"实现的要求"（意思对但不精确），或者把"信任型契约"说成"没写清楚的契约"（那是对概念的误解）。

**你会怎么想错**：把 C 组当成纯粹的背诵题，于是只记答案不记上下文。**正确的用法是：每答一题，想一个 dsh-mini 里的例子**——例如 C7（信任型契约）的例子就是 `Tool.sideEffect`。

**做完之后的自检**：能不能用这十个术语，把正文 L3 那次审计复述一遍？**能复述，说明术语变成了你的表达工具；不能，说明它们还只是词条。**

### 4.4 D 组 · 分析题（28 分，写在 `kit/writeup.md`）

这一组是本作业的核心。它包含五项，**评分标准在 `writeup.md` 的 rubric 里**。这里给出每一项的"优秀答案长什么样"。

#### D1 · 审计一个接口（8 分）

**做法**：用正文 L4.2 的七步流程，审计 `Tool`、`Provider` 或会话事件任选其一。

**优秀答案的标志**：
- 三类承诺**逐条**列出，并明确指出哪几类有缺口；
- 至少找出一条**信任型契约**，并给出"限制能力"而非"加校验"的修法；
- 发现按**严重度 = 后果 × 概率**排序。

**你会怎么想错**：只列问题不提修法；或者把问题平铺（不排序）——排序本身就是判断力的体现。

#### D2 · 算一次改动的波及面（6 分）

**优秀答案的标志**：用了**两张表**（谁依赖这条承诺 + 扇入闭包），并且给出了**"我原本以为会受影响、实际没有"**的反向信息。

**这一项最值得投入**：因为"只搜引用 vs 两表合取"的差额，往往就是面试时最能讲的那个发现。

#### D3 · 为一个接口设计演进方案（6 分）

**优秀答案的标志**：说出**为什么不用更重的那个手段**（例如"我选兼容层而不是版本化，因为使用者都是同一时刻的代码，不需要版本协商"），并给出兼容层的**移除条件**。

#### D4 · 找一处信任型契约并给出修法（4 分）

**优秀答案的标志**：说清"**为什么不能靠加校验解决**"——因为静态判断做不到，所以只能限制能力。

#### D5 · 为一个接口写完整契约文档（4 分）

**优秀答案的标志**：**写了最后一节**（"不属于承诺的部分"）。多数人会漏掉它，而它恰好是防止 Hyrum 定律造成伤害的唯一手段。

## 六、★ 面试模拟（这一节才是真正的验收）★

**做法**：找一个不懂技术的人（或对着录音），**不许看资料**，回答下面六组问题。每组限时，卡住就记下来。

#### 第一组 · 概念（每个 30 秒）

1. 一个接口的契约由哪几部分组成？
2. 前置条件和后置条件分别是谁的义务？这对调试有什么用？
3. 什么是不变量？它和"后置条件"有什么区别？
4. 签名为什么不能完整表达一个契约？

#### 第二组 · 判断（每个 30 秒，先给判据再给答案）

5. 我把一个函数的默认超时从 30 秒改成 60 秒，这算破坏性变更吗？为什么？
6. 我把一个方法从"可并发调用"改成"不可并发调用"，怎么判断有没有问题？
7. 我给返回对象加了一个字段，会不会有问题？

#### 第三组 · 追问（每个 1 分钟，这是拉开差距的部分）

8. "你刚才说波及面是 5 处——如果我改的不是普通方法，而是事件类型呢？会有几处？"
9. "你说这个字段声明的副作用等级不可信——那你为什么不直接加校验？"
10. "兼容层打算什么时候删？"

#### 第四组 · 项目（3 分钟）

11. **讲一次你做过的真实改动**：你做了什么、原本以为影响几处、实际几处、其中哪一处最意外、后来怎么处理的。

**这一题是全篇的终点**。它的答案只能来自 D 组的实际产物——**没有做过的人讲不出来**，而这正是 DeepSeek 那类"不背题、问题来自实战"的面试要筛掉的人。

#### 第五组 · 开放（每个 1 分钟）

12. 如果让你设计一个"给别人的代码用"的接口，你会先想清楚哪三件事？
13. 你见过的最糟糕的接口是什么？它糟糕在哪？

#### 第六组 · 反向提问（面试最后环节）

14. **你要为面试官准备一个问题**。建议问："你们团队怎么管理接口契约的演进？有没有契约测试？"

**别小看这一问**：它同时展示了三件事——你知道契约需要演进、你知道有契约测试这个实践、你在评估他们而不是只被评估。

**记录**：把卡住的题号写进 `writeup.md`。**卡住的每一处，都对应正文里的一个小节**——那才是你真正需要回读的地方。

|---|---|---|
| **拓展性** | D2 的波及面：__ 处（其中"会静默失效" __ 处） | 这就是"加一个能力要改几处"的实测值 |
| **稳定性** | D1 里"无证据的不变量"：__ 条 | 这些是将来最可能在特定序列下爆发的地方 |
| **契约强度** | D4 找到的信任型契约：__ 处 | 每一条都对应一个"声明了但没人能验证"的风险 |

**与缓存复用的关系**：契约变更与缓存命中率有一处直接关联——**任何改动事件结构或工具清单顺序的变化，都会让前缀失效**。所以 D1 里"事件契约的演进"这一项，同时是缓存维度的一个风险点。

用《毕业标准》的三句话格式更新一次差距分析：

```
【已达到】这一维度上，我的系统现在的数据是 ______。
【差距原因】差距来自 ______（一个具体机制）。
【改进】消除它需要做 ______。
```

## 八、FAQ

**Q：判分器只判 72 分，剩下 28 分怎么办？**
按 `kit/writeup.md` 的 rubric 自评。**诚实地标出你在哪一档**——这比分数本身重要，因为它决定了你接下来该补哪一块。

**Q：`grade/答案解析.md` 是不是等于答案？**
不完全是。它给的是**"为什么"和"怎么说"**，而不是"选什么"。如果你只抄 A 组的结论，那你学到的是 12 个孤立的判断，而不是一个判据——**而判据才能迁移到第十三种情况**。

**Q：A/B/C 三组能靠做题技巧通过吗？**
不能，也不需要。它们的价值在于**把判据练成条件反射**。如果你在做题时反复默念同一个判据，那达到目的了。

**Q：D 组真的没有标准答案吗？**
没有唯一的，但有好坏之分。**判据是"能不能被追问住"**：如果你的结论建立在"我搜了三处"这样的证据上，它就能被追问；如果建立在"我觉得"上，那就追问不住。

**Q：面试模拟一定要找人做吗？**
最好找。**对着空气说和对着人说，卡住的地方完全不同**——后者会暴露"你以为自己会但组织不起语言"的部分。

# 1.4 构建作业 · 按契约实现一个模块

> **这篇作业与 1.4 的分析型作业互补**：

| | |
|---|---|
| **产出** | `kit/src/memory.mjs`（实现）+ `CONTRACT-NOTES.md`（报告） |
| **目标级别** | L2（能按契约独立实现一个模块，并说明关键判断） |
| **预计用时** | 3–5 小时 |
| **前置** | 1.4 正文（契约的三类承诺、不变量、破坏性改动） |
| **约束** | **不许修改 `tests/`**；不许改 `CONTRACT.md`；只能改 `kit/src/` 下的文件 |

## 一、你要做什么

实现 **`BoundedMemory`**——一个有**容量硬上限**的记忆容器。

**它的契约在 `kit/CONTRACT.md`，那份文件是你唯一的依据。**

**为什么是"按契约实现"而不是"按需求实现"**：

| | 按需求实现 | **按契约实现** |
|---|---|---|
| 依据 | "做一个有上限的记忆容器" | **一份写清了行为、时序、错误、不变量、以及"不属于承诺的部分"的声明** |
| 你要做的 | 按常识猜 | **逐句读，并判断每一句的后果** |
| 判分 | 看像不像 | **看每一条承诺有没有被遵守** |

**这个差别就是 1.4 这一篇要训练的能力**——而它是**一篇正文教不会的**：你必须亲手实现一次，才会知道"契约里的一句话"在代码里意味着什么。

## 二、交付物与分值

**总分 100**，逐项给分：

| # | 判据 | 分值 | 它考什么 |
|---|---|---|---|
| **A** | 基本行为（add / get / size / list / remove） | 10 | 跑通 |
| **B** | ★ **满仓时失败，而不是丢弃最旧的** | **20** | 契约的核心立场 |
| **C** | `remove` 后容量立即释放 | 10 | 时序承诺 |
| **D** | ★ `merge` 在满仓时**不能**失败 | **15** | 时序承诺（最反直觉的一条） |
| **E** | 错误类型必须能被 `instanceof` 判断 | 15 | 错误承诺 |
| **F** | ★ 任意随机操作序列下 `size <= limit` | **15** | 不变量 |
| **G** | `list` / `get` 返回的是**深**副本 | 10 | 不变量（4 与 5 的区别） |
| **H** | `remove` 幂等（不存在时返回 false） | 5 | 行为承诺 |

**★ 标出的三项合计 50 分**——它们是"看起来对但实际违反契约"的高发区。

## 三、怎么判分

```
node tests/run.mjs
```

**判分的方式是跑 30 次，每次用不同的随机操作序列**（种子固定，可复现）。

**为什么是"跑多次"而不是"跑一次"**：**这个模块是确定性的**——所以跑多次不是为了测非确定性，而是为了**覆盖更多输入组合**。契约里的不变量必须在**任意**操作序列下成立，而"跑一次"只能覆盖一条序列。

**扣分是乘性的**（$\text{得分} = \text{分值} \times \text{成功率}^2$）：

| 成功率 | 线性 | **乘性（本作业）** |
|---|---|---|
| 100% | 满分 | 满分 |
| 90% | 90% | **81%** |
| 50% | 50% | **25%** |

**乘性扣分的理由**：**一个偶发失败在生产环境里就是事故**。这与 MIT 6.5840 的立场一致（"run the tests multiple times before submitting"）——**鲁棒性优于单次正确**。

**部分完成有分**：只做对 A–C 也能拿到 40 分左右。**不要因为做不完就放弃。**

## 四、常见失分点（不直接给答案）

以下是过去最常出现的六类错误。**它们都在契约里有对应的一句话**——**能不能自己找到那一句，就是这道题的核心训练**。

| # | 现象 | 契约里的哪一句管它 |
|---|---|---|
| 1 | 满仓时删掉最旧的那条 | 【二】的 `add` 行 |
| 2 | `merge` 时先检查容量，导致满仓无法合并 | 【三】的第三条 |
| 3 | `remove` 之后"用过的额度"没有还回来 | 【三】的第二条 |
| 4 | `throw new Error('容量满了')` | 【四】的第一行 |
| 5 | `list()` 返回 `[...内部数组]`（只复制了数组） | 【五】的不变量 5 |
| 6 | `remove` 一个不存在的 id 时抛错 | 【二】的 `remove` 行 |

**注意这张表不给代码**——它只指出"你应该去读契约的哪一句"。**如果你只照抄这里的描述而没读契约，D 与 G 两项仍然会失分**（因为契约里的表述比这张表更精确）。

## 五、报告要求（`CONTRACT-NOTES.md`）

**长度：400–800 字。** 它不是总结，而是回答三个问题：

1. **契约里哪几处最容易读漏？** 具体到你读第一遍时是怎么理解的、第二遍发现不对。
2. **你为哪几处做了"契约没规定"的判断？** 例如：如果同时"id 重复"且"已达上限"，应该抛哪个错误——**契约没有规定顺序**，你选了哪个、为什么。
3. **你实现的哪一处，在你看来"可能是过度设计"？** 以及为什么还是做了它。

**第 3 条是刻意的**：它训练的是"能说出自己方案的代价"——而这正是 200 万档面试要考的东西（**"我放弃了什么"**）。

## 六、评测机制（与另外两篇的关系）

```
   CONTRACT.md（唯一的依据）
        │
        ▼
   你的实现 ──► tests/run.mjs ──► 分数 + 失败分类
        │              │
        │              └──► ★ 失败分类告诉你"哪一类错"，
        │                    而修根因比逐个修有效（见 2.4.2）
        ▼
   CONTRACT-NOTES.md（你的判断记录）
```

**测试的鉴别力是被验证过的**：`grade/negative-check.mjs` 会从参考答案出发制造四个"看起来合理但违反契约"的变体（丢弃最旧、浅复制、merge 查容量、容量不释放），**并确认测试能把它们全部抓住**。

**这也是你可以自己跑的一个检查**：

```
node grade/negative-check.mjs
```

**如果它输出"4/4 个变体被正确抓住"，说明测试是可信的。** 反之——**如果测试抓不住这些变体，那说明是测试有问题，不是你的实现有问题**（这一点 6.5840 有明确教训）。

## 七、荣誉守则（借鉴 Stanford CS336 的做法）

CS336 直面了"学生一定会用 AI"这个现实，并给出了明确的边界。本作业采用同样的立场：

| 允许 | 禁止 |
|---|---|

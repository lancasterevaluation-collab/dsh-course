# 作业总入口：一条贯穿六个大作业的主线

> **从这份文件开始。** 它说明作业的整体形态：六个大作业不是六道互不相干的题，而是**同一条 harness 的六个阶段**。

## 三组验证基线（先看这里）

作业的验收由 `verify.mjs` 统一执行，它检查三组固定的基线：

```powershell
cd D:\dsh-course
node homework/verify.mjs              # 六个作业全部检查
node homework/verify.mjs ch03-reliability   # 只查一个
```

| 基线 | 做法 | 期望 |
|---|---|---|
| **起点基线** | 不给任何参考实现与答案 | **0 分**（一条判据都过不了） |
| **参考基线** | 用 `grade/` 下的参考实现与参考答案 | **满分** |
| **负向基线** | 跑 `grade/negative-check.mjs` | **四类错误全部被抓** |

**三组基线各自防住一类问题**：

| 基线 | 没有它会怎样 |
|---|---|
| 起点 | 判据太松，"不写也能拿分" |
| 参考 | 判据太紧，"照着参考答案也拿不到满分" |
| 负向 | 判据太浅，"看起来对其实错的实现"能蒙混过关 |

**参考基线需要多轮**：`tests/run.mjs` 的 `IMPL` 环境变量一次只对一个构建题生效（`IMPL` 相对 `tests/` 解析，答案是相对作业目录解析），所以脚本逐个参考文件各跑一轮，再按 Part 取各轮最大值合成。

**每个判分器都自带前置校验**：读实现源码，只要还留着 `TODO <数字>`，整份按未作答记 0 分。这是从 ch01/ch02 的两处漏洞里得到的规则（见下）。

### 改造中修掉的一类漏洞（值得记住）

ch01 原本"起点 7 分"，根因是 **`setRatio` 在标准答案为空集时返回 1**（注释写着"答空才是对的"）。当模块名没填时，查不到模块会让标准答案**全部变空**，于是空作答反而拿满分。

修法是加一道**前置校验**：模块名未填、或该模块不在此仓库里时，整个 T1 按未作答记 0 分。

**这是一类通用缺陷**：凡"标准答案由外部数据算出"的判据，都要先校验那份外部数据可得，否则"算不出来"会被误读成"答对了"。

## 一、主线是什么

主线是一个**能跑的最小 harness**：接收一个任务、调用模型、执行工具、把过程写进会话日志、失败能重试、崩溃能恢复、跨会话能积累、能同时服务多条会话。

它的代码库在 `harness/`，而六个大作业是它成长过程中的六个检查点。

| 卷 | 主线在这一步获得的能力 | 作业要你做的 |
|---|---|---|
| 第 1 卷 · 判断力地基 | 一个**可读的最小骨架**（还没有能力） | 读它，写出架构约束、契约与债的判断 |
| 第 2 卷 · 最小闭环 | 内核：模型层、工具系统、容器、事件、作用域、装配、会话日志与循环 | 实现内核，端到端跑通一次工具调用 |
| 第 3 卷 · 可靠性与纵深 | 重试、守卫、压缩、进程、持久化、可观测 | 在内核上补六项可靠性机制 |
| 第 4 卷 · 学习进化 | 记忆、技能、用户模型、诊断、演化、复盘、长程 | 再加七项积累机制 |
| 第 5 卷 · 规模化与交互 | 模式、多会话、权限、派发 | 再加四项规模化机制 |
| 第 6 卷 · 科研出口 | 基准与消融 | 对前面自己写的 harness 做一次实验 |

**关键性质**：每一卷的产物都是上一卷的直接延续。第 3 卷的重试挂在第 2 卷的模型层上，第 4 卷的记忆写进第 3 卷的日志里，第 5 卷的多会话复用第 4 卷的作用域。**跳着一卷做，后面的作业会做不动。**

## 二、目录约定

主线的代码与被判分的工作区分开放置，六个工作区的内部结构完全一致。

```
homework/
├── README.md               ← 你在读的这份（总设计）
├── harness/                ← 主线代码库（完整参考实现，可运行）
│   ├── lib/                按卷分层的模块
│   ├── run.mjs             用主线跑一个任务的入口
│   └── README.md           主线自己的说明（模块表与运行方式）
├── ch01-judgment/          第 1 卷工作区
│   ├── 作业引导.md          这一步做什么、做到什么程度、怎么被判定
│   ├── README.md           索引（目录、跑法、进度）
│   ├── kit/                你的工作区（只改这里）
│   ├── tests/              判分器（不要改）
│   └── grade/              参考答案与负向验证（做完再看）
└── ch02-loop/ … ch06-research/   其余五卷，结构相同
```

**工作区与判分器分开是刻意的**：判分器不许改是评分可信的前提，工作区必须改是学习发生的前提。

## 三、六个阶段的接口：什么在变，什么不变

主线在每个阶段都保持同一组边界，只增加能力。这条约定让"增量的部分"可以被单独取下与装上。

| 边界 | 第 2 卷定下后是否变化 |
|---|---|
| 消息与工具调用的数据结构 | 不变（它是所有历史数据的格式） |
| 会话日志的事件格式 | 只增不改（新事件类型可加，旧含义不改） |
| 容器与作用域的注册协议 | 不变（注册返回撤销函数） |
| 模型层接口 | 不变（厂商细节收在翻译段） |
| 主线的入口 `run.mjs` 的调用方式 | 不变（每卷只增加可选参数） |

**这条"只增不改"是作业难度的来源**：你不能靠重写来加能力，只能在既有边界上挂新东西。

## 四、三组验证基线

每个工作区的判分器都必须能证明三件事。它们是"判分器本身可信"的判据，而不只是学生的分数。

| 场景 | 期望 | 怎么验 |
|---|---|---|
| 起点（`kit/` 的空壳实现） | 0 / 100 | 直接跑 `tests/run.mjs` |
| 参考答案（`grade/` 的参考实现） | 100 / 100 | 用环境变量把实现指向 `grade/` |
| 判分器鉴别力（负向验证） | 4 类错误实现全部被抓 | 跑 `grade/negative-check.mjs` |

第三组是这三者里最重要的：**一个只对正确答案给分的判分器不是好判分器，一个对错误答案也给分的判分器是坏判分器。** 负向验证就是检验后者的手段。

## 六、怎么跑

先确认主线本身可运行（这是所有作业的前提）。

```powershell
cd D:\dsh-course\homework
node harness/run.mjs "读一下 harness/README.md 并总结它的模块表"
```

再跑某一卷的判分器。

```powershell
cd D:\dsh-course\homework\ch02-loop
node tests/run.mjs                 # 你当前的分数与缺项
node grade/negative-check.mjs      # 判分器本身有没有鉴别力
```

## 七、建议的推进方式

1. **按卷顺序做，不要跳。** 每一卷的起点是上一卷的产物。
2. **先读该卷的 `作业引导.md`，再动 `kit/`。** 引导里写了"做完该看到什么"。
3. **做完一题跑一次判分器。** 判断力依赖即时反馈，隔得越久反馈效力越低。
4. **卡住时先看试卷。** `kit/CONTRACT.md` 是唯一依据，它写明你的实现必须保证什么、不必保证什么。
5. **不要改 `tests/` 与 `grade/`。** 改判分器等于改考题。

**要点小结**

- 六个大作业是同一条 harness 的六个阶段，按序做，不能跳。
- 主线在 `harness/`，六个工作区是它在各阶段的检查点。
- 每卷只在既有边界上挂新能力，边界本身"只增不改"。
- 判分器要能被三组基线证明：起点 0 分、参考 100 分、负向 4 类错误被抓。
- 现有模块逐一到主线位置有映射，缺口是第 2 卷内核的后半（2.3 到 2.7）。

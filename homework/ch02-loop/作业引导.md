## 一、这份作业要求你做什么

第 1 卷训练判断力，不写 harness 代码。这一卷开始写代码，而且七篇合起来是一个系统：它要能调用模型（2.1）、能用工具做事（2.2）、能把自己的零件组装起来（2.3、2.6）、能在正确的时机让插件介入（2.4、2.5）、并且把发生过的一切记录下来（2.7）。

七篇的顺序不是随意的。它是一次"从外到内、再从内到外"的往返：先做最外面的模型层（它最独立），一路做到最里面的装配层，最后回到最外面做会话日志——而会话日志之所以放在最后，是因为它要记录前面六篇产生的所有事件。**因此 2.7 是本卷的技术枢纽，也是第 3 卷全部内容的起点**。

## 二、为什么作业长成这样

这一卷的作业与第 1 卷有三处明显的差别，它们各自对应一种能力的训练。

**第一，从分析转为构建。** 第 1 卷的产物是判断（一份审计表、一份债务判断），而这一卷的产物是能运行的东西：一个 provider、一个工具注册表、一个容器。判分器不再比对答案，而是 import 你的实现并调用它，检查返回值、抛出的错误与不变量是否成立。**这个转变的判据是"理解无法绕过"**——你只有真的实现对了才能过。

**第二，七篇共用一个工作区。** 这与 CS336 的形态相同：一个大章节一个工作区，七篇的产物合起来是一个系统。分开会让人以为它们是七个练习。放在一起才能看出它们是一个能跑的东西——而且它们之间确实有依赖：2.2 的构建题要求 `parseArguments` 已经实现（那是 2.1 的产物），2.3 的容器要持有 2.2 的注册表。

**第三，每篇都配一个负向验证。** 契约测试只能证明"对的实现能通过"，它证明不了"判分器能失败"。所以每个构建题都配一份 `negative-check-*.mjs`：它从参考答案出发制造几个看起来合理但违反契约的变体（例如漏掉某个检查、把顺序写反），确认判分器能抓住每一个。**一个只能给参考答案满分的判分器与没有判分器等价**——而这一点只有在有人故意写错时才会暴露。

三条差别的共同目的是把"理解"变成"能过检查的行为"。这也是为什么本卷的客观题与构建题权重接近（24 比 6）：前者确认概念，后者确认能力，而后者才是这一卷的主线。

## 三、你将造出什么

七篇的产物合起来是一个最小可用的 agent。成功判据是可观察的：

| 部件 | 判据 |
|---|---|
| 模型层 | 用一个假 provider 替换真实 provider，整套系统的行为不变 |
| 工具系统 | 注册一个新工具不需要改任何已有代码 |
| 容器 | 卸载一个部件之后，它注册过的服务与监听都不再存在 |
| 事件 | 一次事件广播能按声明顺序经过所有监听器，且短路行为符合约定 |
| 作用域 | 两条会话各见不同的工具集，互不串扰 |
| 装配 | 新增一个能力只需要改配置，不需要改代码 |
| 会话日志 | 从日志能重建出"模型当时看到的全部内容" |

最后一条是本卷的总判据，也是第 3 卷的起点：**它一旦成立，第 3 卷的压缩、重试、恢复、观测才有立足点**。

## 五、Part A（2.1）：模型层

**目标。** 做出一个可替换的 provider 抽象与一套能被重试机制直接使用的错误分类。

**动作。** 先读 [`kit/CONTRACT.md`](kit/CONTRACT.md)，它写明你的实现必须保证什么、不必保证什么。然后按三组客观题作答（接口宽度判断、错误分类、术语），并实现 `src/llm.mjs`。题面在 [`kit/problems/a1-llm.questions.md`](kit/problems/a1-llm.questions.md)。

```powershell

node tests/t1-llm.mjs --answers kit/answers/a1-llm.json --verbose
node tests/t2-build.mjs                                   # 用你的实现
$env:IMPL='../grade/llm.reference.mjs'; node tests/t2-build.mjs; Remove-Item Env:\IMPL
node grade/negative-check.mjs                             # 判分器的鉴别力
```

**检查点。** 客观题的三组分数逐步上升。`t2` 的十条判据从红变绿，其中最容易漏的是"合法 JSON 但不是对象也要抛错"与"Mock 脚本用尽时抛错而不是返回空响应"。负向验证的四个变体全部被抓。

**卡住时的提问。** 判断不了接口够不够窄，问"这里面有哪个类型是某家厂商的概念"。分不清错误的等待策略，问"对方有没有给出明确的等待时长"。判断不了可重试性，问"重试遇到它应当做什么"。

## 十一、鲁棒性与重复运行

本卷的两个构建题都要求**每个用例重复运行三十次**，成功率接近 100。这条要求的依据是概率：如果一个缺陷在单次运行中有 10% 的概率被触发，那么三十次全部漏掉的概率约 4.2%。如果单次触发概率是 20%，漏掉概率降到约 0.1%。

**三十次这个数字把单次触发概率在一成以上的缺陷压到 5% 以下的漏检率**，而提高到一百次只能把这一档压到 0.003%，对更低概率的缺陷仍然无效——要覆盖它们必须靠有针对性的用例，而不是靠增加随机次数。

随机序列测试的价值在于它能撞上人想不到的路径组合，代价是失败时你手上只有一个序列。定位流程有四步：固定种子复现、把序列折半缩短、把最小序列打印出来、把它固化成一条确定性用例。**第四步不能省**，因为随机测试的结论无法在下次运行时保证复现——随机负责发现，确定性负责守住。

## 十二、你会怎么想错

**第一条：你会把"能跑通"当成"做对了"。** 这一卷的构建题里，有一类实现能通过随手测试而在契约测试里失败，例如 `list()` 只复制数组而不复制元素、或者工具失败时只返回 `ok: false` 而没有让错误信息带上定位。它们的共同点是缺陷只在特定的调用方式下暴露，而随手测试恰好不会那样调用。

**第二条：你会低估"归属"这一类记账。** 容器与注册表里那些看起来多余的字段（主人、作用域、幂等标记）在单次运行里毫无用处，而它们是一个长期运行的进程能否被安全装卸的前提。判断一个记账该不该做，问的是"如果它错了，故障会以什么形式出现，多久之后出现"——泄漏类的问题通常几小时后才出现，因此它必须在设计阶段解决。

**第三条：你会跳过负向验证。** 契约测试给出一个高分之后，人会倾向于认为判分器是可靠的。而判分器的可靠性只能由"它能否抓住错误实现"来证明，那正是负向验证脚本在做的事。**跳过它等于把一个未经检验的判据当成依据**，而当你的实现真的有缺陷时，你得到的是一个假的安全感。

### 附录 A · 环境故障排查

`tests/run.mjs` 报找不到模块时，检查当前目录是否是 `homework\ch02-loop`。构建题用环境变量指定实现：`IMPL` 对应 `llm.mjs`、`IMPL_TOOLS` 对应 `tools.mjs`，两者的基准目录都是 `tests/`，所以路径写成 `../grade/...`。PowerShell 下设置环境变量用 `$env:IMPL='...'`，用完 `Remove-Item Env:\IMPL` 清掉，否则会影响后续命令。若某个判分项的输出里出现"尚未实现"，说明它对应的讲义或判分器还没建立，不是你的环境问题。

### 附录 B · 只有三小时的最小路径

时间不够时按这个顺序做：先做 Part A 的构建题（它是后面所有部件的地基，且判据全部可自动检查）。再做 Part B 的客观题（它权重高且只依赖一篇阅读）。然后补 Part A 的客观题。最后如果还剩时间，读 2.3 的 L1 并手工跑一遍十条判据里的六条。跳过 Part B 的构建题代价最小，因为它的四条判据里有三条与 Part A 的判据同构。

### 附录 C · 与毕业标准的对接

本卷产出两组数字，它们进入《毕业标准》的差距分析。第一组是"加一个能力的改动点数量"：Part B 的判据二（零改动注册）与 Part F 的目标（只改配置）共同度量它，理想的形态是接入一个部件只需在配置里加一行。第二组是"连续运行的可恢复性"：Part G 的判据（从日志能重建模型当时看到的内容）是它的前提，而第 3 卷的持久化篇会给出完整的验收方式。

**这两组数字比第 1 卷的那两组更接近"系统能不能被信任"这个问题**，因为它们的对象不再是判断，而是运行中的系统。

# Part A · 重试与错误分类（题目）

> 对应讲义：`3.1 重试与错误分类`。作答方式见 `../../../作业引导.md` 第六节。
>
> 把答案写进 `kit/answers/a-retry.json`（从 `a-retry.template.json` 复制）。
> **每一项都要给 `reason`**，而它会检查是否提到了判断依据（类型、状态、幂等、副作用、限流、超时之一）。

---

## 第一组：错误分类（12 项）

对每一项给出 `answer`（`retryable` | `fatal` | `needs-human` | `unknown`）与 `reason`。

四个取值的含义：

| 取值 | 含义 |
|---|---|
| `retryable` | 重试有机会成功，且重试本身无害 |
| `fatal` | 重试不会成功，且原因在本系统之外或不可修复 |
| `needs-human` | 需要人或程序做一次决策（不是简单重试） |
| `unknown` | **无法判断是否已经产生了副作用**，因此不能直接重试 |

---

**e1.** 调用模型接口返回 HTTP 429，响应头里有 `Retry-After: 3`。

**e2.** 调用模型接口返回 HTTP 500，而这次调用是获取一段只读信息（无副作用）。

**e3.** 调用远程支付接口返回 HTTP 500，而这次请求是"创建一笔转账"，且请求已经发出。

**e4.** 连接本地服务时得到 `ECONNREFUSED`，而该服务（用于跑测试）本应在启动时被拉起。

**e5.** 一次读取远程配置的请求超时（该请求是幂等的）。

**e6.** 一次"提交代码到远程仓库"的操作超时，无法确认推送是否已经生效。

**e7.** 模型返回的内容不是合法 JSON，而你的代码按 JSON 解析（这次调用没有产生任何副作用）。

**e8.** 模型返回 `context_length_exceeded`（输入超过窗口）。

**e9.** 调用某个 API 返回 401，而你的实现里有刷新凭据的能力。

**e10.** 调用某个 API 返回 403（凭据有效但权限不足）。

**e11.** 写文件时得到 `ENOSPC`（磁盘已满）。

**e12.** 读一个输入文件时得到 `ENOENT`，而这个文件在流程设计里本应存在。

---

**关于这一组的三处重点**：其中有两项的"看起来可重试"是假象（副作用状态不可确认），而有一项的失败原因不会因为重试而改变。**答对了这三项才算真的理解分类**。

---

## 第二组：策略设计（3 项）

对每一项给出 `answer`（你的判断）与 `reason`（依据）。

**p1.** 一个操作已经因为限流失败两次，第三次请求又拿到 429。你的策略里，第三次该不该继续重试？依据是什么？

**p2.** 一个写操作超时了，而你没有幂等键。此时直接重试的风险是什么，正确的下一步动作是什么？

**p3.** 单次调用的超时时间与整个任务的时间预算是什么关系？给出你建议的配合方式。

---

## 第三组：反例（2 项）

每一项给出 `answer`（一个具体的场景）、`reason`（它为什么有害，要含后果）、以及 `conditions`（至少一项触发条件）。

**c1.** 给一个场景，说明"盲目重试"会造成实际损害。

**c2.** 给一个场景，说明"重试策略本身"会放大问题（而不是修复它）。

---

## 判据提醒

| 判据 | 权重 |
|---|---|
| 12 个分类全部正确 | 8 |
| 每条 reason 非空且提到依据 | 3 |
| 3 个策略问题的判断与讲义一致 | 3 |
| 2 个反例是具体的（含条件与后果） | 1 |

**"分类正确"按下面的答案表判定**（判分器用的就是它）：

| id | answer |
|---|---|
| e1 | retryable |
| e2 | retryable |
| e3 | unknown |
| e4 | retryable |
| e5 | retryable |
| e6 | unknown |
| e7 | retryable |
| e8 | needs-human |
| e9 | retryable |
| e10 | fatal |
| e11 | needs-human |
| e12 | fatal |

**为什么这几项是这样**（在你作答之后再看）：

- **e3 与 e6 是 `unknown`**：它们的共同点是"可能已经产生了副作用而无法确认"。重试的风险是**重复执行**，而那不是概率问题（一次重复转账就是一次损失）。
- **e8 是 `needs-human`**：重试会得到同样的结果（输入还是那么长）。正确动作是**先压缩**（讲义 3.3）再重试，而"先做什么"是一次决策。
- **e11 是 `needs-human`**：磁盘满不会被重试解决，但它也不是 `fatal`——清掉空间后同一个操作会成功。**`fatal` 与 `needs-human` 的差别是"有没有一个可执行的动作让它变成可做"**。
- **e4 是 `retryable` 但有界**：服务可能正在启动（因此值得重试几次），而如果几次之后仍然拒绝，它就该被当成 `fatal`。**这类"随时间改变分类"的项正是重试策略要处理的情形**（p1 相关）。

## 读完这一篇你会知道什么

1. **消息位置四类**：system / user / assistant / tool，以及每一种的位置能不能改。
2. 错误八类而只有三类可重试：算例里 `overloaded`、`rate_limited`、`server_error` 可重试，而未知错误必须保守地判定为不可重试。
3. 处置动作三个：`wait-longer`（限流）、`retry-fast`（服务端错误）、`fail-conservative`（未知）。
4. 分类充分性：同类必须同处置，算例里混入异类会返回 `["transient"]`。

6. 前缀缓存：把读入压回 40000，节省 96.1%。
7. 工业界怎么做：各家的错误码语义、重试与退避建议、多提供商抽象、流式接口。

## 一、为什么模型层值得单独讲

### 1.1 把未知错误当成可重试

一个没见过的错误被默认重试，于是对同一个必然失败的请求重试了五次，每次都在计费。

### 1.2 成本随轮数爆炸

一个跑了 50 轮的会话，账单远比预期高。**因为每一轮都要重发全部历史**，累计读入是轮数的平方量级。

### 1.3 消息位置用错

工具结果被当成用户消息插入，模型开始把工具输出理解成新的用户指令。**这是位置语义错误，不是内容错误。**

这三件事分别对应：**错误分类、成本结构、消息位置。**

## 二、模型层的三件事

| 事 | 决定 | 做错的后果 |
|---|---|---|
| 消息位置 | 模型怎么理解输入 | 语义混乱 |
| 错误分类 | 该重试、该等、还是该失败 | 无谓重试或过早失败 |
| 成本结构 | 每轮的输入量与计费 | 账单失控 |

核心认识：模型层不是"HTTP 客户端"——它是一个**有语义的接口**。位置有含义、错误有分类、调用有成本结构，这三件事都必须显式处理。

## 三、怎么做

### 3.1 消息位置四类

算例给出四类位置：

```
system, user, assistant, tool
```

| 位置 | 含义 | 能否改位置 |
|---|---|---|
| **system** | 全局指令 | 必须在最前 |
| **user** | 用户输入 | 顺序有含义 |
| **assistant** | 模型输出（含工具调用请求） | 必须与 tool 结果配对 |
| **tool** | 工具执行结果 | **必须紧跟请求它的那条 assistant 消息** |

工具结果的位置约束是最容易出错的一条：它必须与发出调用请求的那条 assistant 消息配对。**如果中间插入了别的内容，或者顺序被打乱，模型会拒绝对话或产生错乱。**

这与 3.3 的上下文压缩直接相关：压缩时如果删掉了 assistant 的调用请求但保留了 tool 结果，会话就变得非法。**压缩必须成对处理。**

### 3.2 错误八类与处置

算例给出 8 类错误，其中 3 类可重试：

| 错误类别 | 可重试 | 处置动作 |
|---|---|---|
| `rate_limited`（限流） | 是 | **`wait-longer`**（等更久） |
| `overloaded`（过载） | 是 | `retry-fast` |
| `server_error`（服务端错误） | 是 | **`retry-fast`**（快速重试） |
| 其他 5 类 | 否 | 立即失败 |
| **未知** | **否** | **`fail-conservative`** |

实现如下。

```js
// 错误分类：可重试的三类给出各自的处置动作，未知一律保守失败
export function dispose(error) {
  const table = {
    rate_limited: { action: 'wait-longer', retryable: true },
    overloaded: { action: 'retry-fast', retryable: true },
    server_error: { action: 'retry-fast', retryable: true },
  }
  return table[error.code] ?? { action: 'fail-conservative', retryable: false }
}
```

算例实测的三个处置：

| 输入 | 动作 |
|---|---|
| 限流 | `wait-longer` |
| 服务端错误 | `retry-fast` |
| 未知错误 | `fail-conservative`（`retryable = false`） |

两个动作的区别值得展开：

- **`wait-longer`**（限流）：对端明确说"你太快了"，必须等更久，重试越快越糟。优先采纳 `Retry-After`。
- `retry-fast`（服务端错误、过载）：对端可能是瞬时抖动，快速重试更有效（但仍要加抖动）。

把这两类分开是必要的：用同一套退避策略处理它们，要么对限流太激进，要么对抖动太慢。

未知错误必须保守：`fail-conservative` 的意思是**默认不重试**。这与守卫的 fail-closed 是同一个原则（见 3.2）。

### 3.3 分类充分性：同类同处置

分类是否合理，可以用一条可检查的性质验证：

> **同一类错误必须得到同一处置，不同类应当能得到不同处置。**

```js
// 分类充分性：检查同类错误是否映射到同一处置
export function checkSufficiency(samples) {
  const byClass = new Map()
  for (const sample of samples) {
    const action = dispose(sample).action
    if (!byClass.has(sample.class)) byClass.set(sample.class, new Set())
    byClass.get(sample.class).add(action)
  }
  return [...byClass].filter(([, actions]) => actions.size > 1).map(([cls]) => cls)
}
```

算例实测：

| 输入 | 结果 |
|---|---|
| 同类同处置 | `[]`（无问题） |
| **混入异类** | **`["transient"]`** |

这条检查抓的是什么：如果一类错误里有多个处置，说明**这个类别分得太粗**（把该等的和该快重试的混在了一起）。

**它是可机械验证的**，所以可以进测试。

### 3.4 成本的二次增长

每一轮请求都要**重发全部历史**。因此累计读入量随轮数二次增长：

$$
\text{累计读入} \approx \frac{n(n+1)}{2} \cdot m
$$

（$n$ 为轮数，$m$ 为每轮新增的 token 数。）

算例实测（$m = 800$）：

| 量 | 值 |
|---|---|
| 50 轮累计重传 | **1,020,000** |
| 第 50 轮的单轮读入 | 40000 |
| 轮数翻倍（100 轮）累计 | **4,040,000** |
| **翻倍倍率** | **4.0 倍** |

"翻倍倍率 4.0"就是二次增长的直接证据：轮数翻倍，累计量变成四倍。

含义：**成本不是线性增长的，而是平方级的。** 一个 100 轮的会话，其输入成本大约是一个 50 轮会话的四倍——而新增的信息量只多了一倍。

这是上下文管理（3.3）必须存在的经济理由：不是"上下文太长了模型会烦"，而是**平方增长的成本结构不可持续**。

### 3.5 前缀缓存：为什么能省九成

如果每轮的请求前缀相同（system 提示词、工具定义、以及历史），那么**前缀部分可以被服务端缓存**，按更低的价格计费。

算例实测：

| 项 | 值 |
|---|---|
| 缓存后的读入 | **40000** |
| **节省比例** | **96.1%** |

为什么能省这么多：长会话里，**每一轮真正新增的内容很少，而重发的历史很多**。缓存恰好针对"重发"这一部分。

前提条件（必须满足，否则缓存失效）：

| 条件 | 说明 |
|---|---|
| **前缀稳定** | system 提示词、工具定义不得每轮变化 |
| **一致的前缀顺序** | 先 system、再工具、再历史 |
| **不插入变化内容** | 时间戳、随机 id、每次变化的元数据不能放在前缀里 |

最常见的失效原因：在 system 提示词里插入当前时间或请求 id。**这一个改动的代价是 96.1% 的节省全部消失。**

## 四、特殊情况与处理技巧

| 情况 | 为什么 | 处理 |
|---|---|---|
| 未知错误被无限重试 | 默认按可重试处理 | 未知一律 `fail-conservative` |
| 限流后重试更快反而更糟 | 用了同一套退避 | 限流走 `wait-longer`，优先采纳 `Retry-After` |
| 工具结果找不到配对的请求 | 压缩时删了单边 | 压缩必须成对处理位置 |
| 缓存命中率突然下降 | 前缀里有变化内容 | 前缀保持稳定，变化内容后置 |
| 成本随轮数失控 | 无上下文管理 | 压缩 + 缓存（见 3.3） |
| 多个提供商错误码语义不同 | 直接透传原始错误 | 归一化成自己的分类 |
| 流式响应中断 | 没有恢复机制 | 记录已收部分，可续传或重发 |
| 长会话在第 N 轮突然变慢 | 单轮输入超过了某个阈值 | 监控单轮输入量的分布（见 3.6） |

"归一化错误码"值得强调：不同提供商的错误码含义不同（有的把过载归到 429，有的归到 503）。**在模型层内部把它们映射成自己的分类表**，上层就只需处理一套语义。

## 五、工业界的做法（可照做）

### 5.1 能力接缝的三个角色

模型层是一个典型的**能力接缝**，它由三个角色组成：

| 角色 | 职责 | 例子 |
|---|---|---|
| **Service Definition** | 接口定义（做什么） | `ModelService.complete(messages)` |
| **Service Provider** | 具体实现（怎么连某家） | 某提供商的 HTTP 客户端 |
| **Consumer** | 使用方（谁调用） | agent 循环 |

这三者缺一不可：只有接口没有实现无法运行，只有实现没有接口无法替换。**把它拆成三个角色，是为了让"换一家提供商"不影响消费方。**

实践判据：**如果换一家模型提供商需要改 agent 循环的代码，那这个接缝划得不对。**

### 5.2 各家提供的错误语义

虽然具体码不同，工业界的语义大体一致，可以照抄这套映射：

| 语义 | 典型状态码 | 该做什么 |
|---|---|---|
| 限流 | 429（部分厂商 503） | 等更久，采纳 `Retry-After` |
| 过载 | 503 / 529 | 快速重试 + 抖动 |
| 服务端错误 | 500 | 快速重试 + 抖动 |
| 请求无效 | 400 | 不重试，修请求 |
| 鉴权失败 | 401 / 403 | 不重试，刷新凭证后重来一次 |
| 上下文过长 | 400 + 特定错误码 | **不重试，触发压缩** |
| 内容被拒 | 特定错误码 | 不重试，改变策略 |
| 超时 | 无响应 | 按时间算，可重试但要注意幂等 |

"上下文过长"这一行最关键：它是一个**结构性信号**——它不是错误，而是"该压缩了"。把它当作普通 400 处理会让长会话直接失败。

### 5.3 参数与配置起点

| 参数 | 推荐起点 | 依据 |
|---|---|---|
| 单轮超时 | 60–120 秒（含生成） | 生成时间与输出长度相关 |
| 限流重试上限 | 2–3 次 | 对端明确说了慢，重试太多无益 |
| 服务端错误重试 | 2–3 次，指数退避 + 全抖动 | 见 3.1 |
| 上下文压缩触发线 | 窗口的 70%–80% | 见 3.3 |
| 最大输出 | 按任务类型设 | 防止失控输出 |
| 温度与采样 | 按任务设（见 7.4） | 确定性任务用低温 |
| 缓存前缀 | system + 工具定义，固定不变 | 保住命中率 |

### 5.4 一份可落地的实施清单

1. **三角色**：定义接口、实现提供商、让消费方只依赖接口。
2. 错误归一化：把各家错误码映射到自己的分类表。
3. 处置动作：三类可重试各自给动作，未知保守失败。
4. 分类充分性测试：同类同处置，作为单元测试。
5. 消息位置校验：发送前校验 tool 与 assistant 的配对。
6. 成本记账：按输入/输出/缓存三档分别计（见 3.6）。
7. 前缀稳定：system 与工具定义固定，变化内容后置。
8. 上下文过长：单独识别，触发压缩而不是重试。
9. 流式：支持流式输出，并处理中断。
10. 观测：单轮输入量、输出量、成本、错误分类分布的分布指标。

## 六、学术界的结论

### 6.1 错误分类学与故障模型

分布式系统领域对故障的经典分类：

| 故障类型 | 含义 | 处理 |
|---|---|---|
| **崩溃故障** | 停止响应 | 可检测（超时） |
| **遗漏故障** | 丢消息 | 需要重传 |
| **时序故障** | 响应太慢 | 需要超时判断 |
| **拜占庭故障** | 任意错误行为 | 需要多数派与校验 |

模型层的错误大多落在前三类：限流是时序问题（你太快），过载是遗漏或时序问题，500 是崩溃问题。

分类的价值在于决定动作：

- **崩溃类**可以重试（换一个实例可能就好）。
- 时序类要等（换实例没用）。
- 拜占庭类不能重试（结果不可信，需要校验）。

"内容被拒"就属于需要不同策略的一类：重试同样的内容不会成功。

### 6.2 上下文长度的成本结构

上下文长度的成本有两部分：

$$
\text{成本} = \underbrace{n \cdot c_{\text{prefill}}}_{\text{线性（每轮一次）}} + \underbrace{\frac{n(n+1)}{2} \cdot c_{\text{context}}}_{\text{二次（重发历史）}}
$$

算例验证了第二项：轮数翻倍，累计量变四倍。

**学术与工程上的三条应对**（与 3.3 的上下文压缩直接相关）：

| 方向 | 做法 | 代价 |
|---|---|---|
| **减少重发** | 压缩历史（摘要、外置） | 信息损失 |
| **降低单价** | 前缀缓存 | 需要前缀稳定 |
| **减少轮数** | 更好的计划（一次多做事） | 需要更强的模型 |

第三条常被忽略：**减少轮数是最彻底的优化**，因为它同时降低两个项。

### 6.3 接口隔离与依赖倒置

模型层这个接缝在软件工程上对应两条经典原则：

- **依赖倒置原则**：高层模块不应依赖低层模块，两者都应依赖抽象。
- 接口隔离原则：不应强迫使用者依赖它不用的接口。

对模型层的具体应用：

- **agent 循环依赖"模型服务"接口，不依赖某家 SDK**（依赖倒置）。
- 接口只暴露循环真正需要的操作（接口隔离）——例如不需要暴露"列出模型列表"这种能力。

判据：**接口的方法数应当接近消费方真正用到的数量。** 方法越多，替换成本越高（见 1.3 的隐藏度）。

### 6.4 缓存与局部性

前缀缓存能省 96.1%，本质是**利用了局部性**——相邻请求有大量共同前缀。

它与计算机体系结构的缓存是同一个问题：

| 概念 | 模型层对应 |
|---|---|
| 缓存命中 | 前缀被复用 |
| 缓存失效 | 前缀变化（插入时间戳） |
| 冷启动 | 会话开头没有可复用的前缀 |
| 工作集 | 当前会话的固定前缀 |

实践含义：**像对待 CPU 缓存一样对待前缀**——保持它稳定、少变化、按固定顺序排列。

## 七、理论：两个成本模型

### 7.1 二次增长

$$
C_{\text{累计}} = \frac{n(n+1)}{2} \cdot m
$$

算例实测：$m = 800$、$n = 50$ 得到 **1,020,000**。$n = 100$ 得到 4,040,000。

验证二次：$\frac{4040000}{1020000} \approx 3.96 \approx 4$，正是 $2^2$。

工程含义：**如果轮数会增长，成本就会平方增长。** 所以"限制轮数"与"压缩历史"是两个必须的机制。

### 7.2 缓存的节省

$$
\text{节省} = 1 - \frac{m}{C_{\text{单轮}}}
$$

算例实测：缓存后读入 40000，**节省 96.1%**。

读法：节省比例取决于"固定前缀"在单轮输入中的占比。**会话越长，占比越高，节省越大。**

这也解释了为什么短会话体会不到缓存的好处：前缀占比低，省得少。

## 十、算例

算例实现了本篇的错误分类与成本模型。

```powershell
cd D:\dsh-course
node examples/sa25_llm.mjs        # 全部函数的运行结果
node examples/test_sa25_llm.mjs   # 数字回归断言
```

它做到的事：

- 消息位置四类与错误八类（可重试三类）。
- 三个处置动作（限流 `wait-longer`、服务端错误 `retry-fast`、未知 `fail-conservative`）。
- 分类充分性检查（同类同处置得到 `[]`，混入异类得到 `["transient"]`）。
- **成本的二次增长**（50 轮累计 1,020,000，100 轮 4,040,000，翻倍倍率 4.0）。
- 第 50 轮的单轮读入（40000）。
- 前缀缓存的节省（读入 40000，节省 96.1%）。

这一篇只要记住一句：模型层要把**消息位置、错误分类、成本结构**显式处理——错误里只有三类可重试且动作不同（限流要等更久），未知一律保守失败。而成本是轮数的平方级增长，所以前缀缓存（省 96.1%）与上下文压缩不是优化，是必需。

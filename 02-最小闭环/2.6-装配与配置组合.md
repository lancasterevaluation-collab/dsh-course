## 读完这一篇你会知道什么

1. **深合并与替换**：算例里深合并后保留 3 个字段（含下层的），替换后只剩 1 个。深合并时上层的值覆盖下层。
2. 数组整体替换：算例里数组 `["read"]` 被整体替换，长度变 1——不做元素级合并。
3. 不可变：算例验证"合并不修改入参"为 `false` 时会暴露就地修改的反例。
4. 结合律成立、交换律不成立：$(a \oplus b) \oplus c = a \oplus (b \oplus c)$ 为 `true`，而 $a \oplus b = b \oplus a$ 为 `false`。
5. 单位元：空对象与任何配置合并得到原配置。
6. 工业界怎么做：Helm values、Kustomize、Docker Compose、12-factor 配置。
7. 学术界：分层配置的代数语义、半格与 CRDT 的合并、配置错误的实证研究。

## 一、为什么装配值得单独设计

### 1.1 配置覆盖错了方向

用户的配置被环境配置覆盖了。**因为合并顺序搞反了**，而"顺序"这件事没有人明确写下来。

### 1.2 数组被元素级合并

用户想"只允许 read"，写了一个只有一项的数组，结果与默认的 `["read", "write"]` 合并后变成两项。**权限比预期更宽。**

### 1.3 合并把入参改坏了

合并函数就地修改了 `defaults` 对象，导致下一个模块拿到的"默认配置"已经被污染。

这三件事分别对应：**顺序、数组语义、不可变性。**

## 二、合并的三种语义

| 语义 | 行为 | 适用 |
|---|---|---|
| **深合并** | 递归合并对象，上层覆盖同名字段 | 配置项默认值 |
| **整体替换** | 上层直接覆盖整个值 | 数组、以及"要的就是这个"的场景 |
| **追加** | 把上层内容并入下层 | 插件列表、中间件链 |

关键决定：**哪些字段深合并、哪些整体替换，必须逐项明确。** 混在一起会出 1.2 那种问题。

## 三、怎么做

### 3.1 深合并与整体替换

实现如下。

```js
// 深合并：对象递归合并，数组整体替换，不修改入参
export function merge(base, override) {
  if (!isPlainObject(base) || !isPlainObject(override)) return clone(override)
  const result = { ...clone(base) }
  for (const [key, value] of Object.entries(override)) {
    result[key] = key in result ? merge(result[key], value) : clone(value)
  }
  return result
}
```

算例实测：

| 情况 | 结果 |
|---|---|
| 深合并后的字段数 | **3**（保留了下层未覆盖的字段） |
| 替换后的字段数 | **1** |
| 深合并保留了下层字段 | `true` |
| 深合并时上层覆盖下层 | `true` |

两条性质同时成立：**未冲突的字段保留（下层贡献）**，冲突的字段上层胜出。这两条合起来就是"深合并"的完整定义。

### 3.2 数组为什么整体替换

算例实测：数组被整体替换为 `["read"]`，**替换后的长度是 1**。

为什么数组不深合并：**数组的元素往往是"整体语义"**——

| 场景 | 元素级合并的后果 |
|---|---|
| 权限列表 | 权限只增不减（**比预期更宽**） |
| 参数列表 | 顺序错乱 |
| 白名单 | 无法收窄 |

**所以数组整体替换是更安全的默认**。如果确实需要追加语义，就显式提供追加操作（例如 `extraArgs: [...]` 与 `args: [...]` 分开），而不是靠合并规则隐式决定。

**这条与 2.2 的"未声明副作用取最危险档"是同一个原则**：默认行为要取保守的那一侧。

### 3.3 不可变：合并不得修改入参

算例验证了一个布尔性质："合并是否修改入参"应当是 `false`，**而反例（就地修改后的入参）显示为 `{"nested":{"a":2}}`**——说明原来的入参被改掉了。

为什么不可变是必需的：

- 同一份默认配置会被多次用于合并（每个会话一次）。**修改它会让后续合并的起点发生变化。**
- 调试时无法复现（入参已经被改过）。
- 并发合并时互相干扰。

实现方式：合并时**新建对象**（而不是原地写）。这与 1.5 的"共享可变状态"是同一类问题。

### 3.4 结合律成立、交换律不成立

算例同时验证了两个代数性质，这组对照是本篇的核心：

| 性质 | 结果 |
|---|---|
| $(a \oplus b) \oplus c$ 与 $a \oplus (b \oplus c)$ 相同 | **`true`** |
| $a \oplus b$ 与 $b \oplus a$ 相同 | **`false`** |

含义完全不同：

- **结合律成立** → 可以任意分组合并。例如先把"环境 + 用户"合并，再与默认合并，或者反过来分组，结果相同。这是缓存与优化的依据。
- 交换律不成立 → 顺序就是语义。"默认 ⊕ 用户"与"用户 ⊕ 默认"结果不同。

算例给出的具体对照：

| 运算 | 结果 |
|---|---|
| $a \oplus b$ | `{"x":1,"y":{"p":1,"q":2},"z":3}` |
| $b \oplus a$ | `{"y":{"q":1,"p":1},"z":3,"x":1}`（被截断，但可见顺序不同） |

结论：**合并顺序必须显式定义并写进文档**。含糊的"配置会合并"会导致 1.1 那种问题。

单位元：算例验证"以空对象为单位元"为 `true`——**空配置与任何配置合并都不改变它**。这让"某层没有配置"成为一个自然的表示。

### 3.5 来源优先级与来源追踪

由 3.4 推出：**优先级必须由顺序定义**。典型的层叠顺序（从低到高）：

| 层 | 来源 | 特点 |
|---|---|---|
| 1 | 内置默认 | 保证一定可用 |
| 2 | 系统/组织配置 | 管理员设定 |
| 3 | 项目配置 | 随仓库提交 |
| 4 | 环境配置 | 部署相关 |
| 5 | **用户/会话配置** | 最高优先级 |

越靠后优先级越高的理由：**越靠近具体场景的配置越了解实际情况。**

来源追踪：每一层的贡献都要能追溯。**做法是在合并时记录每个字段的最终来源**。

为什么来源追踪值得做：当出现"配置没生效"时，**能立刻回答"这个值是谁设的"**。没有它只能靠猜。

## 四、特殊情况与处理技巧

| 情况 | 为什么 | 处理 |
|---|---|---|
| 配置覆盖方向反了 | 顺序未定义 | 显式定义层叠顺序并写文档 |
| 权限比预期更宽 | 数组元素级合并 | 数组整体替换 |
| 默认配置被改坏 | 合并修改入参 | 合并必须新建对象 |
| 想追加而不是替换 | 合并语义单一 | 显式提供追加字段（`extra*`） |
| 配置没生效 | 不知道谁覆盖了 | 记录字段来源 |
| 空值怎么处理 | `null` 与"未设置"不同 | 明确约定：`null` 表示清空，`undefined` 表示未设置 |
| 深层嵌套难调试 | 合并结果不可见 | 提供"打印最终配置 + 来源"的工具 |
| 敏感值出现在配置里 | 明文 | 用引用（`${ENV}`）而不是字面值 |

**"`null` 与 `undefined` 的区别"值得强调**：这是一个必须明确约定的点。常见约定是 `null` 表示"显式清空"，`undefined` 表示"不覆盖"。 不写清楚会导致"我明明设了 null 却没清空"。

## 五、工业界的做法（可照做）

### 5.1 配置层叠的实现

| 工具 | 合并语义 | 值得学的点 |
|---|---|---|
| **Helm** | values 深合并，数组替换 | 分层 values，`--set` 最高优先 |
| **Kustomize** | 补丁式覆盖 | **显式声明是补丁还是替换** |
| **Docker Compose** | 多文件叠加 | 后文件覆盖 |
| **webpack-merge** | 可配置合并策略 | **按字段指定策略** |
| **12-factor** | 环境变量优先 | 环境相关配置不入库 |

Kustomize 的思路最值得学：它**要求显式声明"这段是补丁"**，而不是靠合并规则猜。显式优于隐式。

### 5.2 十二要素应用的配置原则

| 原则 | 内容 | 与本篇的对应 |
|---|---|---|
| 配置与代码分离 | 配置不入仓库 | 层叠的第 4、5 层 |
| 环境变量优先 | 部署相关走环境 | 优先级最高 |
| 无状态进程 | 进程可随时重建 | 配置来自外部 |

"配置与代码分离"的边界：**能随环境变的是配置，不随环境变的是代码。** 判断依据是"换一个环境它要变吗"。

### 5.3 参数与设计起点

| 项 | 推荐 | 依据 |
|---|---|---|
| 层叠层数 | 3–5 层 | 太多难追溯 |
| 对象字段 | 深合并 | 便于局部覆盖 |
| 数组字段 | 整体替换 | 防止权限只增不减 |
| 追加需求 | 独立的 `extra*` 字段 | 显式 |
| 合并函数 | 纯函数（不改入参） | 可重复使用 |
| 来源追踪 | 每个字段记录来源 | 排障必需 |
| 校验时机 | 合并完成后统一校验 | 避免中间态报错 |

"合并完成后统一校验"很重要：**逐层校验会产生假错误**（例如默认缺字段、但用户会补上）。只在最终配置上校验。

### 5.4 一份可落地的实施清单

1. **层叠顺序**：写明从低到高的层，写进文档。
2. 逐字段语义：明确哪些深合并、哪些替换、哪些追加。
3. 数组替换：默认整体替换，追加走独立字段。
4. 纯函数：合并不修改入参。
5. 来源追踪：记录每个字段的最终来源。
6. 空值约定：`null` 与 `undefined` 的语义。
7. 最终校验：只在合并后校验一次。
8. 打印工具：能输出最终配置与来源。
9. 敏感值：用引用而不是字面值。
10. 测试：结合律、单位元、数组替换、不可变性四条各一个用例。

## 六、学术界的结论

### 6.1 分层配置的代数语义

把"合并"看作二元运算 $\oplus$，算例验证的三条性质给出它的代数结构：

| 性质 | 结果 | 含义 |
|---|---|---|
| 结合律 | 成立 | 可以任意分组 |
| 交换律 | **不成立** | 顺序是语义 |
| 单位元 | 空对象 | 可以表示"无配置" |

**这样的结构是"半群带单位元"（幺半群），但不是交换幺半群。**

为什么这个区分重要：**交换幺半群允许任意并行合并**（因为顺序无关），而非交换幺半群必须串行按顺序合并。这直接决定了实现能不能并行化。

### 6.2 CRDT 的启示

**CRDT**（见 3.5）要求合并满足交换律、结合律、幂等三件事。分层配置不满足交换律，所以它是非 CRDT。

这不是缺陷，而是选择：**配置的语义本身就是"后者覆盖前者"**，强行做成可交换会丢失这个语义。

可借鉴的部分是"幂等"：**同一层配置重复合并不应改变结果**。算例的算术性质（$a \oplus a = a$）可以单独验证。

### 6.3 配置错误的实证研究

对真实系统故障的分析反复发现：**配置错误是主要故障原因之一**，且特点是：

| 特点 | 含义 |
|---|---|
| **类型检查帮不上忙** | 值类型正确但语义错误 |
| **只在特定环境触发** | 生产与你本地不同 |
| **难以复现** | 依赖具体的层叠顺序 |
| **修复快但发现慢** | 找到原因耗时，改一行就好 |

**应对手段**（与 3.2 的守卫同源）：把配置当作不可信输入校验——用 schema 校验最终配置，而不是信任它。

这条与 2.2 的 schema 是同一套工具：**能表达成 schema 的约束，就不要靠人记住。**

### 6.4 显式优于隐式

Python 的"显式优于隐式"与 1.4 的契约原则在本篇的具体体现：

| 隐式做法 | 显式做法 |
|---|---|
| 靠合并规则决定数组行为 | 逐字段声明策略 |
| 靠加载顺序决定优先级 | 显式声明层叠顺序 |
| 靠约定处理 `null` | 写进文档并用测试固定 |

判据：**如果一件事的结论依赖"读者知道某个约定"，那它就是隐式的。**

## 七、理论：三条代数性质

### 7.1 结合律与可分组性

$$
(a \oplus b) \oplus c = a \oplus (b \oplus c)
$$

算例验证为 `true`。**含义**：可以按任意分组合并，因此可以缓存中间结果、可以并行计算各分组的合并结果。

### 7.2 交换律不成立与顺序语义

$$
a \oplus b \ne b \oplus a
$$

算例验证为 `false`（两者结果不同）。

含义：**合并顺序必须被定义。** 这个"不成立"不是缺陷，而是"覆盖优先级"这一语义的代数表达。

同时它带来一个实现约束：**不能并行合并所有层**（因为顺序有含义），只能并行合并已经确定顺序的子序列。

### 7.3 单位元

$$
a \oplus \varnothing = a, \qquad \varnothing \oplus a = a
$$

算例验证为 `true`。

含义：**"这一层没有配置"可以被自然表示**，不需要特殊处理（不需要 `if (layer) ...`）。

工程价值：把"条件分支"变成"代数恒等式"，代码更简单也更少出错。

### 第二题：找出这个合并函数的三个问题

实现如下。

```js
function mergeConfig(base, override) {
  for (const key in override) {
    if (typeof override[key] === 'object') {
      base[key] = mergeConfig(base[key], override[key])
    } else {
      base[key] = override[key]
    }
  }
  return base
}
```

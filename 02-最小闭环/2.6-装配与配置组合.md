## 本篇新词

- 装配（composition） 指把一组部件按依赖与配置组织成可运行系统。
- 清单（manifest） 指装配的输入文件，它列出部件与它们的配置，不含逻辑。
- profile 指一组命名的配置集合，表达"这套系统是给这种用途启动的"。
- bundle 指可被整体引用的部件集合。它只说装什么。
- 覆盖（override） 指上层配置对下层同名条目的替换或合并。语义必须被规定。
- 深合并（deep merge） 指对象逐字段合并、数组整体替换的合并规则。
- 配置来源 指命令行、环境变量、清单、默认值四层。
- 可复现的装配 指同一份清单加同一组环境输入产生行为相同的系统。
- 条件装配 指按条件决定部件是否装载，条件是受限集合里的键。

## 一、【设计原因】

### 1.1 缺陷一：配置改了，但没生效

你在清单里加了一行，重启，行为没变。排查路径是：先确认文件被读到，再确认那一行没被解析器忽略，最后才发现下层有一份更高优先级的同名配置把它盖住了。

它的性质是"配置的来源不可见"：清单、环境变量、默认值三处都可能影响这个键，而"最终生效的是哪一个"没有任何地方能回答。

### 1.2 缺陷二：多环境维护多份配置，然后开始漂移

开发与生产的配置不同，于是复制出两份清单。漂移从第一次"只改一边"开始。

几周之后两份清单的差异无法解释，而"这个功能在开发环境能用生产不能用"会反复出现。

根因不是人不细心，而是把"不变的部分"与"随环境变化的部分"混在了一起。

### 1.3 缺陷三：同一份配置，两次启动行为不同

同一份清单、同一台机器，两次启动得到不同的行为，通常是若干部件的相对顺序不同，而顺序影响覆盖与优先级的先后。

成因可能是文件系统的遍历顺序、并发初始化的完成顺序、或某个部件在初始化时读了时间。这类问题的危险性在于它不会稳定复现，因此"修好它"无法被验证。

### 1.4 缺陷四：这个功能为什么没生效

某个部件按配置决定是否装载，而它的存在与否决定某个功能是否可用。功能不生效时，第一个问题不是"它为什么不对"，而是"它有没有被装载"，而后者在只读代码的情况下无法回答。

### 1.5 由此确定的设计目标

1. 配置来源分层且优先级写进契约，每个键的来源可查询。
2. 覆盖语义唯一：对象深合并、数组整体替换，且只有一个实现。
3. 部件集合写进清单，环境差异只由环境变量提供。
4. 装配是纯函数：时间与随机数由调用方显式传入。
5. 配置错误在启动时成批报告，并输出已装载清单。

**本节要点**

- 改了不生效的根因是来源不可见。
- 多份配置的漂移来自把变化部分与不变部分混在一起。
- 不可复现的装配无法被稳定排查。
- 条件装配让"它有没有被装载"成了第一个问题。
- 五条目标：来源分层、覆盖唯一、清单与环境分离、纯函数装配、错误早暴露。

## 二、【直觉】

### 2.1 四层抽屉

一个值可能写在四个地方，找的时候从最上面的抽屉开始。

- 最上面是使用者临时写的一行（命令行）。
- 往下是运行环境提供的一份（环境变量）。
- 再往下是仓库里那份清单。
- 最底下是部件作者写的默认值。

**每往上一层，能改它的人越少、时效越短。** 这个顺序不是随意的，它反映的是"谁有权决定这件事"。

### 2.2 抄写与继承

假设一份配置有三个字段：名字、超时、重试次数。

- 抄写：上层把整份抄一遍，改一个字段。**下层的其它字段会被忘掉，而更糟的是抄下来的那份不会跟着下层更新。**
- 继承：上层只写改动的那一个字段，其余从下层继承。**下层的更新会自动生效，代价是"最终值是多少"要拼三处才知道。**

::: keypoint 反直觉点
**抄写的代价随时间上升，推断的代价是一次性的。** 抄一份当下很便宜，而它的过期是静默的——清单里那个字段改了，抄下来的那份不会跟着变，也没有任何信号。所以选择继承，并用"来源可查询"来抵消推断成本。
:::

### 2.3 一个数字直觉

设配置有四层来源，其中某个键在其中三层被写过。

- 最终值由最上面那一层决定，因此**只需要看一处**就能回答"为什么是这个值"。
- 而如果三个 profile 各自把配置抄全，那么同一个字段会出现 3 份副本。清单改一次，要改 4 处。

所以"只写差异"这条纪律的收益可以数出来：**副本数从 4 降到 1**。

**本节要点**

- 四层抽屉的顺序反映改动权限。
- 抄写会静默产生过期值，继承只带来一次性的推断成本。
- 只写差异把同一个字段的副本数从 4 降到 1。

## 三、【严格】

### 3.1 定义

::: theorem 定义 2.6.1（装配）
一次装配是一个函数

$$
\mathrm{compose}: (\mathit{manifest},\ \mathit{inputs}) \to (\text{已装载部件序列},\ \text{配置映射}),
$$

它按清单顺序装载部件，并在每装一个时检查它的依赖是否已就绪。
:::

::: theorem 定义 2.6.2（配置来源与优先级）
配置来源按优先级从高到低是

$$
\mathit{cli} \succ \mathit{env} \succ \mathit{manifest} \succ \mathit{default}.
$$

键 $k$ 的最终值由各层**从低到高依次深合并**得到（$\oplus$ 见定义 2.6.3），来源记录为**提供该键的最高优先级层**。层间也必须深合并，否则"命令行只写差异"会丢掉该键下的其余字段。**"提供了 undefined" 与"未提供" 同等处理**，都视为未提供，而 `null`、`0`、空字符串都是有效值。
:::

::: theorem 定义 2.6.3（覆盖）
覆盖是二元运算 $\oplus$，由条件定义：

$$
a \oplus b = \begin{cases}
b, & b \text{ 是标量或数组},\\
\text{逐字段 } a_i \oplus b_i, & a, b \text{ 都是对象},\\
b, & \text{否则}.
\end{cases}
$$

即**对象深合并，数组与标量由上层整体替换**。$\oplus$ 是全系统唯一的合并实现。
:::

::: theorem 定义 2.6.4（profile 与 bundle）
bundle 是一个部件名集合，$\mathit{bundle} = \{p_1, \dots, p_n\}$。profile 是

$$
\mathit{profile} = (\{\mathit{bundle}_i\},\ \mathit{config}),
$$

其中 $\mathit{config}$ 是部件名到配置的映射。**bundle 回答"装什么"，profile 回答"以什么配置装"。**
:::

::: theorem 定义 2.6.5（可复现的装配）
称装配是**可复现的**，当且仅当对同一份 $(\mathit{manifest}, \mathit{inputs})$，两次执行的产物逐字段相同。

这要求装配不读取时间、随机数、目录遍历顺序与网络状态。
:::

::: theorem 定义 2.6.6（条件装配）
条件装配按键的取值决定部件是否装载，其中键取自受限集合

$$
K = \{\text{环境名},\ \text{profile 名},\ \dots\}.
$$

**受限**的含义是键集合有限且可枚举，而不是任意表达式。
:::

### 3.2 命题

::: theorem 命题 2.6.1（替换语义会静默产生过期值）
在替换语义下，若上层只写了某条目的部分字段，则未写字段取的是"该上层条目被写下时的值"，而不是下层的当前值。若下层随后更新了该字段，上层仍使用旧值，且没有任何信号。

**证明.** 替换语义下，条目 $b$ 整体替代 $a$，因此 $a$ 中所有字段都不参与结果。未写字段在结果中的值只能来自 $b$ 自身（或缺失）。而下层对 $a$ 的更新只改变 $a$，不改变 $b$。故结果停留在旧值。

↓ **为什么能这么写？** 整体替换切断了字段级的继承关系。

$\blacksquare$

::: keypoint 所以选深合并
**深合并让未写字段继承下层的当前值，因此下层更新会自动生效。** 代价是最终值要看全部层才能推断，而这个代价可以用"来源可查询"压低。
:::

::: theorem 命题 2.6.2（来源查询是可判定的）
给定四层与键 $k$，$k$ 的最终值与来源在 $O(4)$ 次查表内可确定。且"改了配置不生效"必然对应"$k$ 在某更高优先级层有定义"。

**证明.** 按定义 2.6.2，从最高优先级层开始逐层查表，首次命中即为结果与来源。未命中继续向下，层数有界，故为常数次。若修改的是第 $i$ 层而结果未变，则由定义，结果来自某个 $j \succ i$ 的层，即该键在更高层有定义。

↓ **为什么能这么写？** 优先级是全序，而查询按该序进行。

$\blacksquare$

::: keypoint 排查路径因此是确定的
**配置改了不生效，第一步永远是查这个键的来源（不是读配置文件）。** 这个查询在实现上只是记录每层命中的层号。
:::

::: theorem 命题 2.6.3（深合并满足结合律但不满足交换律）
$\oplus$ 满足 $(a \oplus b) \oplus c = a \oplus (b \oplus c)$，但一般地 $a \oplus b \neq b \oplus a$。

**证明.** 结合律：逐键递归定义，对象情形下两侧都归结为"每个叶子键由 $c$ 覆盖 $b$ 覆盖 $a$ 的最近提供者决定"，该顺序与括号无关。交换律：取标量键 $k$，$a[k] = 1$、$b[k] = 2$。则 $(a \oplus b)[k] = 2$ 而 $(b \oplus a)[k] = 1$，故不相等。

↓ **为什么能这么写？** 结合律来自"每键独立的最近覆盖"，交换律要求覆盖方向可对调。

$\blacksquare$

::: keypoint 结合律是"多层复用"的依据
**正因为结合律成立，任意分组合并的结果相同**，所以可以先把 bundle 与清单合并一次，再把 profile 叠上去。交换律不成立则说明：**顺序本身是语义的一部分，不能交换两层配置。**
:::

::: theorem 命题 2.6.4（可复现性等价于装配是纯函数）
装配可复现，当且仅当它不读取除 $(\mathit{manifest}, \mathit{inputs})$ 之外的任何状态。

**证明.**
（充分性）若装配只依赖这两个输入，则两次相同输入的每次读取都返回相同值，故结果相同。
（必要性）若装配读取了时间 $t$ 或随机数 $r$，取两次执行使 $t_1 \neq t_2$。由定义 2.6.5 的判据，需要证明结果可能不同。构造：令某部件配置的某字段取值为 $t$，则两次产物不同。故可复现要求不读它。

↓ **为什么能这么写？** 函数值的唯一性是纯函数定义的直接展开。

$\blacksquare$

**数值**：本系统把时间与随机种子作为 `inputs` 的显式字段，因此"读时间"这件事只发生在入口处一行。

::: theorem 命题 2.6.5（组成可枚举当且仅当条件键集合有限）
设装配的条件由键集合 $K$ 的取值决定。若 $|K|$ 有限且每个键的取值域有限，则可能的组成数是有限的、可枚举的。若允许任意表达式，则一般不可枚举。

**证明.** 有限集合的有限次笛卡尔积是有限的，故组成数 $= \prod_{k \in K} |\mathrm{range}(k)|$，可枚举。若条件为任意表达式，则它可编码一个不可判定的谓词（或至少是任意复杂度的布尔函数），其真值集合不构成有限枚举，故不可枚举。

↓ **为什么能这么写？** 可枚举性要求取值空间是有限集合的有限积。

$\blacksquare$

**数值**：两个键各取两个值时，组成数 $= 4$ 种。

::: theorem 命题 2.6.6（校验前移只降低定位成本，不减少错误数）
把配置错误从"第一次使用时"前移到"装配时"不改变错误总数，但把定位成本从"运行 N 分钟后"降到"启动时"。

**证明.** 错误的成因是配置与部件期望不符，它与校验时机无关，故总数不变。定位成本正比于"错误发生点与发现点之间的距离"。在运行时发现时，两点之间隔着 N 分钟的执行。在启动时发现时，两点重合。

↓ **为什么能这么写？** 时机不改变错误集合，只改变可观测距离。

$\blacksquare$

**数值**：本系统的装配阶段检出四类结构错误（未注册的部件名、缺必需项、类型不符、依赖未就绪），它们原本都会推迟到运行时。

### 3.3 本节要点

**本节要点**

- 装配按清单顺序装载并检查依赖（定义 2.6.1）。
- 四层来源，优先级从命令行到默认值（定义 2.6.2）。
- 覆盖是对象深合并、数组整体替换（定义 2.6.3）。
- bundle 说装什么，profile 说以什么配置装（定义 2.6.4）。
- 可复现要求不读时间、随机、遍历顺序与网络（定义 2.6.5）。
- 条件键取自受限集合（定义 2.6.6）。
- 替换语义会静默产生过期值（命题 2.6.1）。
- 来源查询是可判定的（命题 2.6.2）。
- 深合并满足结合律但不满足交换律（命题 2.6.3）。
- 可复现等价于纯函数（命题 2.6.4）。
- 组成可枚举当且仅当条件键集合有限（命题 2.6.5）。
- 校验前移只降低定位成本（命题 2.6.6）。

## 四、【回到直觉】

- **定义 2.6.1 说的**：按清单的顺序装，每装一个就看它的依赖到没到。
- **定义 2.6.2 说的**：从最上面的抽屉往下找，第一个有值的那层说了算。
- **定义 2.6.3 说的**：对象逐字段合并，数组整根替换。
- **定义 2.6.4 说的**：bundle 是菜单，profile 是"这桌点哪些、怎么调味"。
- **定义 2.6.5 说的**：同一个配方做两次，要得到同一个东西。
- **定义 2.6.6 说的**：条件只能从少数几个开关里选，不能写任意表达式。
- **命题 2.6.1 说的**：抄一份配置，那一刻它就开始过期了。
- **命题 2.6.2 说的**：改了不生效，先问"这个键的值是从哪一层来的"。
- **命题 2.6.3 说的**：合并的先后可以重组，但两层之间不能对调。
- **命题 2.6.4 说的**：装配里读一次时间，它就不再可复现。
- **命题 2.6.5 说的**：条件是有限开关时，所有可能的系统都能列出来。
- **命题 2.6.6 说的**：早报错不减少错误，只是让你不用等几分钟才知道。

**本节要点**

- 顺序来自清单，依赖在装载时检查。
- 来源查询是排查的第一步。
- 对象合并、数组替换。
- 可复现即纯函数。
- 条件键有限则组成可枚举。

## 五、【工具箱】

### 5.1 配置该放哪一层

| 问题 | 放哪 |
|---|---|
| 它随环境变化吗？ | 会，放环境变量 |
| 它是秘密吗？ | 是，放环境变量且不进版本控制 |
| 它由使用者临时改吗？ | 会，放命令行 |
| 其余 | 放清单，与代码一起评审 |

### 5.2 来源排查

遇到"改了不生效"，按顺序问三句。

1. 这个键的最终值来自哪一层？
2. 有没有更高优先级的层写过它？
3. 我改的是哪一层，它是不是被更高层盖住了？

**实现要求**：每个键的最终值带一个来源字段，启动时可打印。

### 5.3 合并检查

1. 对象是逐字段合并吗？上层只写一个字段时，其余字段保留吗？
2. 数组是整体替换吗？
3. 合并会修改入参吗？（不应该）
4. 全系统有几处合并实现？（应该只有一处）

### 5.4 可复现检查

**连装配两次，比较产物。** 不相同就找四类来源。

| 来源 | 消除方式 |
|---|---|
| 时间 | 由调用方作为输入传入 |
| 随机数 | 由调用方提供种子，或在清单里固定 |
| 目录遍历顺序 | 读目录后先排序 |
| 网络状态 | 装配阶段不发请求 |

### 5.5 清单评审四查

1. 新增一个部件要改几处？理想是一处（bundle）。
2. 有没有出现像凭据的值？
3. 每个 profile 是不是只写差异？
4. 条件装配的键在受限集合里吗？

**本节要点**

- 配置按"是否随环境变、是否秘密"分层。
- 来源排查三问，实现要带来源字段。
- 合并检查四问。
- 可复现检查用双次装配对比。
- 清单评审四查，前两条可以脚本化。

### 7.2 清单段与合并段

清单段定类型，合并段是全系统唯一的合并实现。

```js
// 定义 2.6.3：对象深合并、数组整体替换，且不修改入参
export function merge(base, over) {
  if (over === null || typeof over !== 'object' || Array.isArray(over)) return over
  if (base === null || typeof base !== 'object' || Array.isArray(base)) return over
  const out = { ...base }
  for (const [k, v] of Object.entries(over)) out[k] = merge(out[k], v)
  return out
}
```

反例只差一行，而它演示了"入参被就地修改"这类缺陷。

```js
// 反例：就地修改下层对象
export function mergeMutating(base, over) {
  if (over === null || typeof over !== 'object' || Array.isArray(over)) return over
  if (base === null || typeof base !== 'object' || Array.isArray(base)) return over
  for (const [k, v] of Object.entries(over)) base[k] = mergeMutating(base[k], v)
  return base
}
```

### 7.3 来源段

来源段按优先级从高到低逐层查找。

```js
// 定义 2.6.2：四层优先级，层间深合并，来源记为最高优先级的提供者
export const SOURCES = ['cli', 'env', 'manifest', 'default']

export function resolve(key, inputs) {
  let value
  let source = null
  for (const s of [...SOURCES].reverse()) {
    const v = (inputs[s] ?? {})[key]
    if (v !== undefined) {
      value = merge(value, v)
      source = s
    }
  }
  return { value, source }
}
```

装配本身是纯函数，时间与随机种子只从输入进来。

```js
// 定义 2.6.1 / 2.6.5：装配是纯函数，时间与随机数由 inputs 传入
export function compose(manifest, inputs) {
  const profile = manifest.profiles[inputs.profile]
  if (!profile) throw new Error(`未知 profile：${inputs.profile}`)
  const plugins = [...new Set(profile.bundles.flatMap((b) => manifest.bundles[b] ?? []))]
  const merged = merge(manifest.defaults ?? {}, profile.config ?? {})
  const resolved = Object.fromEntries(
    Object.keys(merged).map((k) => [k, resolve(k, { ...inputs, manifest: merged })]),
  )
  return { plugins, resolved, stamp: inputs.now, seed: inputs.seed }
}
```

### 7.4 校验段与装配段

校验段收集全部结构问题后一次性报告。

```js
// 命题 2.6.6：结构错误成批报告，装配阶段即拒绝启动
export function validate(manifest, registry) {
  const problems = []
  for (const [name, profile] of Object.entries(manifest.profiles)) {
    for (const bundle of profile.bundles) {
      if (!(bundle in manifest.bundles)) problems.push(`profile ${name} 引用了不存在的 bundle ${bundle}`)
    }
    for (const plugin of new Set(profile.bundles.flatMap((b) => manifest.bundles[b] ?? []))) {
      if (!registry.includes(plugin)) problems.push(`profile ${name} 的部件 ${plugin} 未注册`)
    }
    for (const key of profile.required ?? []) {
      if (!(key in (profile.config ?? {}))) problems.push(`profile ${name} 缺少必需配置 ${key}`)
    }
  }
  return problems
}
```

### 9.2 失败模式

**（1）检查放在装载期（L9 位置放错）。** 配置校验只在开发环境跑过，而生产的清单结构不同。表现是生产启动后才失败，而失败点与配置改动之间隔着一次发布。

**（2）前提会变（L9）。** 命题 2.6.3 的结合律以"同一套合并实现"为前提。若某处用了另一份合并函数，分组合并的结果不再相同。

**（3）多处合并实现。** 规则只写在文档里，实际行为由几份实现决定。

**（4）替换语义下抄配置。** 下层更新后，抄下来的那份永久停留在旧值。

**（5）合成就地修改入参。** 第一次合并改变了底层对象，第二次合并在被改过的值上进行。

**（6）用 `key in obj` 判断是否提供。** 显式写了 undefined 的层会截断查找链，而环境变量的"未提供"常表现为 undefined。

**（7）装配读时间或随机数。** 两次运行的产物不同，日志无法比较。

**（8）依赖目录遍历顺序。** 在开发机上恰好一致，在别的平台上不同。

**（9）清单里写密钥。** 进入版本历史后无法撤销。

**（10）条件装配用任意表达式。** 系统的组成无法穷举，"这个功能为什么没生效"要从"它有没有被装载"查起。

**本节要点**

- 决策表覆盖 11 种情形。
- 失败模式十条，前两条是位置放错与前提会变。
- 最隐蔽的是"依赖目录遍历顺序"——它在开发机上恰好总是一致的。

## 十二、系统影响回溯

**影响一：合并规则不清会让"改了不生效"成为常态。** 处置方式是把语义写成契约，并让所有合并走同一个函数。

**影响二：条件装配让系统的组成从静态可读变成运行时才知道。** 处置方式是限制条件键集合，并让装配产物可查询。

**影响三：装配不可复现会让问题无法被稳定复现。** 处置方式是消除四类不确定性来源，其中最容易被忽略的是目录遍历顺序。

**一处需要修正的预判。** 旧稿把可复现性放在"工程卫生"的位置，读完之后要升级它：**可复现是第 6 卷实验方法能否成立的前提**。基准实验要求同一份配置跑两次得到可比结果，而如果装配依赖遍历顺序，两次运行的部件加载顺序可能不同，从而让结果不可比。所以这一条不是风格要求，而是评测的基础设施。

**通向下一步的桥。**

本篇给出"系统由什么组成、每件拿到什么配置"，而它产出的那个系统还没有"发生过什么"的记录。前五篇里反复出现的两条不变量——**模型可见的必须能从日志重建**、**装配产物必须可复现**——都要靠一条持久化的记录来兑现。

所以下一篇是 2.7 会话日志与循环。它要给出那条记录的形状，并把前六篇的零件连成一个真正会转起来的循环。

# 2.5 作用域与隔离

> **这一篇讲什么**：作用域解决"同名服务在不同上下文中怎么区分"这个问题。它由三条机制组成：层级查找、覆盖、隔离标记。再加上一条退出纪律：子作用域先于父作用域退出。算例里两个会话的可见集合交集是 4——共享 4 个、各自私有 2 个，这个数字就是隔离是否生效的直接证据。

## 一、为什么需要作用域

### 1.1 会话之间互相看见

两个并发会话使用同一个容器，会话 A 临时替换了 `logger`，**会话 B 的日志也跟着换了**。

### 1.2 无法屏蔽父级服务

子任务想用一个"什么都不做"的空实现替换父级的网络客户端（例如离线模式）。但父级的服务依然被解析到——**因为查找会向上穿透**。

### 1.3 退出顺序错误

父作用域先退出，释放了连接池，而子作用域还在用它。**子作用域在退出时报出一堆"连接已关闭"的错误。**

这三件事分别对应：**隔离、屏蔽、退出顺序。**

## 二、层级、覆盖与隔离

| 机制 | 作用 | 不用的后果 |
|---|---|---|
| **层级查找** | 子看不到的服务去父级找 | 每个作用域都要注册一遍 |
| **覆盖** | 子可以替换父的同名服务 | 无法局部定制 |
| **隔离标记** | 切断向上查找 | 无法真正屏蔽 |
| **退出顺序** | 子先于父 | 父先释放导致子报错 |

前两条是"便利"，后两条是"必要"：没有隔离标记就没有真正的隔离，没有退出顺序就会在关闭时出错。

## 三、怎么做

### 3.1 层级查找：向上搜索

查找规则：**从当前作用域开始，逐层向上，先找到的胜出。**

算例实测：

| 作用域 | 可见名字数 |
|---|---|
| 根 | **4** |
| 会话 A | **6** |
| 会话 B | **6** |
| **A 与 B 的交集** | **4** |

读法：两个会话各能看见 6 个名字，其中 4 个来自根（共享），**各私有 2 个**。而算例同时验证：会话 A 看不到 B 的注册（`true`）、会话 B 也看不到 A 的（`true`）。

这组数字是隔离是否生效的直接证据：如果交集等于各自的可见数，说明隔离完全失效。**可以把"交集大小"作为隔离程度的指标。**

### 3.2 覆盖：子作用域遮蔽父作用域

子作用域注册同名服务时，**子作用域的注册胜出**（对它自己及其后代生效）。

算例实测：子作用域覆盖父作用域的同名服务时返回 `true`，**覆盖后命中的层级是 `over`**。

覆盖的语义要点：

| 要点 | 说明 |
|---|---|
| 只影响子作用域及其后代 | 父作用域与其他兄弟不受影响 |
| 不是删除 | 父级的注册还在，子作用域退出后恢复 |
| 需要对父级可见性 | 子作用域仍可显式获取父级版本（如果需要） |

"不是删除"这一条很重要：覆盖是**遮蔽**而不是替换。子作用域退出后，父级的服务照常可用（算例里"退出后根作用域的服务不再可见"是指根也退出了）。

### 3.3 隔离标记：主动切断向上查找

有时需要**彻底屏蔽**父级的某个服务（而不是覆盖它）。隔离标记就是为此设计的：在被标记的名字上，查找不向上穿透。

```js
// 查找：被隔离标记挡住时立即失败，不要穿透到父作用域
export function lookup(scope, name) {
  for (let current = scope; current; current = current.parent) {
    if (current.shielded.has(name) && !current.own.has(name)) {
      return { found: false, stoppedAt: current.depth }
    }
    if (current.own.has(name)) return { found: true, depth: current.depth, value: current.own.get(name) }
  }
  return { found: false }
}
```

算例实测（这组结果值得逐条读）：

| 情况 | 结果 |
|---|---|
| 被标记名字在子作用域的查找 | **失败（因标记停止）** |
| 该查找访问的层数 | **1**（没有向上穿透） |
| 被标记名字在父作用域仍可查得 | **`true`**（父作用域自己不受影响） |
| 子作用域自己注册后被标记名字的可见性 | **可见** |

四条合起来说明隔离标记的精确语义：

1. **它切断的是查找路径**，不是删除服务。
2. 父作用域自己仍然正常工作（只访问 1 层就停止，但父作用域的查找不受影响）。
3. 子作用域一旦自己注册了同名服务，就又能看见它——隔离标记挡的是"继承"，不是"自有"。

用途举例：

- 离线模式下屏蔽网络客户端（而不是替换它）。
- 测试环境屏蔽真实的支付服务。
- 沙箱执行时屏蔽文件系统访问（**这正是 3.2 的权限防线的实现方式之一**）。

### 3.4 退出顺序：子先于父

算例实测：退出次序是 **`task, session, root`**——子先于父，且退出后的失败数是 0。

为什么必须子先于父：子作用域的服务**可能依赖父作用域的资源**。父先释放会导致子释放时使用已释放的资源。

这与 2.3 的逆序撤销是同一个规则：**2.3 是"注册的逆序"，这里是"层级的逆序"，两者一致**——因为子作用域总是晚于父作用域创建。

"退出后失败数 0"的价值：它验证了整个退出序列没有用到已释放的资源。**这是可以断言的性质。**

### 3.5 每会话一个作用域

并发会话的正确做法：**每个会话一个子作用域**，共享根作用域。

| 共享在根 | 私有在会话作用域 |
|---|---|
| 配置、日志、存储连接 | 会话状态、临时覆盖、会话级监听器 |

为什么这样分：**共享的是"无状态或全局唯一"的东西，私有的是"每个会话不同的"东西。**

判据：**如果两个会话同时用它会互相干扰，它就必须是私有的。**

一个常见错误：把会话状态放在根作用域（图省事），结果并发时互相覆盖。**这与 1.5 的"真相源唯一"是同一类问题**——共享可变状态必须有明确的归属。

## 四、特殊情况与处理技巧

| 情况 | 为什么 | 处理 |
|---|---|---|
| 会话之间互相看见 | 都注册在根 | 每会话一个子作用域 |
| 想要真正屏蔽父级 | 覆盖只是遮蔽 | 用隔离标记 |
| 子作用域退出后父级服务消失 | 误用了删除而非遮蔽 | 覆盖只遮蔽，不删除 |
| 退出时报"资源已关闭" | 顺序错误 | 子先于父 |
| 热重载后旧覆盖残留 | 子作用域未退出 | 确保重载路径退出子作用域 |
| 查找层数过深 | 层级太多 | 限制层级数（3–4 层足够） |
| 隔离标记误伤 | 标记范围过大 | 按具体名字标记，不要按前缀 |
| 异步任务丢失作用域 | 未传播上下文 | 显式传递或使用异步上下文机制 |

最后一条是实际开发中最常见的：**异步回调里"当前作用域"会丢失**。解法是把作用域作为参数显式传递，或者使用语言的异步上下文机制（见 5.3）。

## 五、工业界的做法（可照做）

### 5.1 层级注入器

| 框架 | 层级模型 | 特点 |
|---|---|---|
| **Angular** | 组件树层级注入器 | 子组件可覆盖父的提供者 |
| **Spring**（Java） | `@Scope`（singleton / request / session） | 通过代理实现请求级作用域 |
| **.NET DI** | 作用域（Scope） | 显式创建作用域对象 |
| **Vue / React**（Context） | 组件树上下文 | 最近祖先胜出 |
| **NestJS** | 模块作用域 | 模块级提供者 |

共同形状：**树形结构 + 最近祖先胜出**。这与词法作用域在语言里的规则完全一致。

### 5.2 多租户隔离

多租户系统里的隔离手段可以按强度排序：

| 强度 | 手段 | 适用 |
|---|---|---|
| 最弱 | 每行带租户 id（应用层过滤） | 成本最低，风险最高 |
| 中 | 每租户一个 schema | 常见折中 |
| 强 | 每租户一个数据库 | 隔离好，成本高 |
| 最强 | 每租户一个实例 | 完全隔离 |

与本篇的对应：**作用域的隔离标记相当于"应用层过滤"，而独立实例相当于"物理隔离"。** 选哪一档取决于错误代价（见 1.1 的可逆性与 1.5 的变更等级 L0–L3）。

### 5.3 异步上下文

异步代码里的作用域传播是各语言都在解决的问题：

| 机制 | 语言 | 做法 |
|---|---|---|
| **AsyncLocalStorage** | Node | 异步链路自动携带上下文 |
| **ThreadLocal** | Java | 线程级上下文（异步会丢） |
| **context.Context** | Go | **显式传递**（无隐式） |
| **TaskLocal** | Swift | 结构化并发中自动传播 |

Go 的选择值得思考：**它明确拒绝隐式上下文**，要求显式传 `context.Context`。代价是函数签名变长，收益是"上下文从哪来"永远清晰。

对本篇的意义：**隐式的作用域传播方便但难调试。** 如果选隐式，必须保证"每处异步边界都正确传播"，否则会出现"作用域在某个回调里突然变成根"的诡异现象。

### 5.4 一份可落地的实施清单

1. **层级**：根 + 会话 + 任务，最多 3–4 层。
2. 共享/私有划分：无状态的放根，会话相关的放子作用域。
3. 覆盖只遮蔽：不做删除，退出后恢复可见。
4. 隔离标记：需要真正屏蔽时使用，按具体名字标记。
5. 退出顺序：子先于父，并断言退出失败数为 0。
6. 可见性指标：监控两个会话的可见集合交集，作为隔离证据。
7. 异步传播：显式传递或使用语言的异步上下文机制。
8. 层级限制：超过层数上限时报警（说明设计有问题）。
9. 测试：并发两个会话，验证互不可见。
10. 文档：写清哪些服务共享、哪些私有，以及覆盖的语义。

## 六、学术界的结论

### 6.1 词法作用域与动态作用域

编程语言里的两种作用域规则与本篇直接对应：

| 规则 | 解析依据 | 何时确定 |
|---|---|---|
| **词法作用域** | 代码的嵌套结构 | 编译时 |
| **动态作用域** | 运行时的调用栈 | 运行时 |

**作用域的层级查找是"词法作用域"的机制**——查找路径由结构（父子关系）决定，而不是由调用栈决定。

为什么这一点重要：**结构化的作用域可以被静态推理**。你能在看代码时说出"这个服务会从哪来"。而动态作用域不能——它取决于运行时谁调用了你。

实践判据：**如果一个服务的来源需要运行时才能确定，说明抽象的层次可能错了。**

### 6.2 组件封装与信息隐藏

Parnas 的信息隐藏原则（见 1.2）在作用域上的体现是：**作用域边界就是封装边界。**

| 封装提供 | 作用域对应 |
|---|---|
| 隐藏内部实现 | 子作用域的注册对外不可见 |
| 暴露稳定接口 | 根作用域的服务对所有后代可见 |
| 可替换实现 | 覆盖机制 |

"子作用域的注册对外不可见"这一条最关键：它让**并发会话天然隔离**——因为它们的注册互相不可见。

### 6.3 能力隔离

**能力安全**（见 3.2）与作用域的关系：作用域是能力的一种组织形式。

- **没有能力标记时**，一个服务一旦在根注册，所有后代都能拿到（权限向内传播）。
- 隔离标记相当于"撤回能力"：它让某个后代替换掉"能拿到 X"这件事。

这与 Confused Deputy 问题直接相关：如果服务是按"谁能看见"授予的，那么一个被注入的组件可以通过"我属于这个作用域"来获取权限。**更安全的做法是要求凭证**（见 3.2 的能力令牌）。

### 6.4 结构化并发与作用域

**结构化并发**（见 3.4）把作用域概念用在任务生命周期上：

> 并发任务必须在某个作用域内启动，作用域退出时全部子任务必须已结束。

它与本篇的作用域是同一个结构：两处都遵循"**子先于父结束**"，两处都用树形结构表达"谁属于谁"。

共同的价值：**把"生命周期"从一个全局问题变成局部可推理的问题。**

## 七、理论：三条可检查性质

### 7.1 可见性集合的关系

$$
\text{可见}(A) \cap \text{可见}(B) = \text{共享部分}
$$

算例实测：$|\text{可见}(A)| = 6$、$|\text{可见}(B)| = 6$、$|\text{交集}| = 4$（共享 4、各自私有 2）。

判据：**如果交集等于各自可见数，隔离失效。** 这个数字可以直接监控。

### 7.2 隔离标记的局部性

$$
\text{标记只影响"查找"，不影响"父作用域自己的可见性"}
$$

算例实测：子作用域查找被标记名字时访问 **1 层**就停止（失败），而父作用域仍可查得（`true`）。

**这条性质说明隔离标记是"定向切断"而不是"全局删除"**——精确性正是它可用的原因。

### 7.3 退出顺序

$$
\text{depth}(\text{先退出}) > \text{depth}(\text{后退出})
$$

算例实测：退出次序 `task, session, root`，**失败数 0**。

"失败数 0"是可断言的性质：退出过程里没有使用已释放的资源。

## 十、算例

## 读完这一篇你会知道什么

1. **注册与覆盖**：后注册者胜出，但撤销必须按归属——算例里按名字撤销会让"后来者的服务消失"。
2. 撤销次序必须逆序：算例里注册是 `1, 2, 3`，撤销是 `3, 2, 1`。
3. 失败隔离：一次撤销失败不能阻断其余——算例里 3 次撤销中 1 次失败，另外 2 次仍然成功。
4. 撤销必须幂等：连续撤销两次，实际删除次数是 1。
5. 启动分阶段：算例里的阶段数是 5，以及为什么不能用一个大函数代替。
6. 工业界怎么做：DI 框架的生命周期与作用域、dispose 模式、RAII。
7. 学术界的结论：依赖倒置原则、RAII 与所有权、以及"注册即效果"这一形式。

## 一、为什么容器值得单独设计

### 1.1 后来者的服务被删掉

模块 A 注册了 `logger`，模块 B 随后也注册了 `logger`（覆盖了 A 的）。A 撤销时按名字删除 `logger`——**删掉的是 B 的那个**。A 的下游从此拿不到日志。

### 1.2 一次撤销失败，其余全部泄漏

撤销过程里第二个 dispose 抛错，后面三个就此跳过。它们的资源（连接、临时文件、子进程）全部泄漏。

### 1.3 撤销被调用了两次

一次正常路径调用，一次在异常处理里又调用。第二次对已经释放的连接再释放，产生了难查的错误。

这三件事分别对应：**归属、失败隔离、幂等。**

## 二、容器的四件事

| 事 | 决定 | 做错的后果 |
|---|---|---|
| 注册与解析 | 谁能拿到什么 | 拿不到或拿到错的 |
| 覆盖规则 | 同一个名字谁胜出 | 行为随加载顺序变化 |
| 撤销 | 资源怎么释放 | 泄漏或误删 |
| 阶段 | 初始化的顺序 | 依赖未就绪 |

核心认识：**容器的难点不在"注册"，而在"撤销"。** 注册是加东西，撤销是拆东西，而拆错东西比加错东西难发现得多。

## 三、怎么做

### 3.1 注册、覆盖与归属

注册有两个要素：**名字**（谁能被解析到）与归属（谁注册的）。

```js
// 注册：记录值与注册者，撤销时按注册者匹配而不是按名字
export function register(table, name, value, owner) {
  const previous = table.get(name)
  table.set(name, { value, owner })
  return { table, displaced: previous?.owner ?? null }
}
```

算例实测两种撤销方式的结果差异，这是本篇最重要的一组对照：

| 撤销方式 | 结果 |
|---|---|
| **按归属撤销**（后来者撤销自己那个） | 表中条目数 **1**（仍是后来者的），前者的服务仍可解析 |
| **按名字撤销** | 表中条目数 **0**——**缺陷：后来者的服务消失** |

为什么按名字撤销是缺陷：它无法区分"我要撤销的是我注册的那个"与"这个名字下的任何一个"。**当有覆盖时，它删掉的是别人注册的东西。**

正确的模型：撤销**必须携带注册时返回的那份凭证**（注册时返回 disposer 或句柄），而不是靠名字去找。这就是"注册是效果"的含义——每次注册产生一个只能撤销它自己的句柄。

算例还验证了：后来者仍能取到自己的服务（`true`），后来者撤销后条目数是 **0**（此时两个都撤了）。

### 3.2 撤销按归属而不是按名字

由 3.1 直接推出两条规则：

| 规则 | 原因 |
|---|---|
| 撤销用注册时返回的句柄 | 它能精确指向那一次注册 |
| 不要用名字查找后删除 | 名字可能已被覆盖 |

这与 3.3 的"成对处理"是同一种纪律：任何"注册-撤销"都必须成对，且由同一次注册的返回值配对。**不要用外部标识（名字、id）重新查找。**

### 3.3 撤销次序：为什么必须逆序

算例实测：注册次序是 `1, 2, 3`，撤销次序是 `3, 2, 1`。

为什么必须逆序：后注册的组件**可能依赖先注册的**。先撤依赖者、再撤被依赖者，才不会出现"用着已经释放的资源"。

```js
// 撤销：按注册的逆序执行，保证依赖者在被依赖者之前释放
export function disposeAll(registrations) {
  let failed = 0
  let succeeded = 0
  for (const registration of [...registrations].reverse()) {
    try {
      registration.dispose()
      succeeded += 1
    } catch (error) {
      failed += 1
      reportDisposeFailure(registration, error)
    }
  }
  return { succeeded, failed }
}
```

这与 1.1 的依赖序是同一个图论问题：撤销顺序是注册顺序的**反向拓扑序**。如果注册顺序本身满足拓扑序，逆序撤销就自动满足依赖释放的要求。

### 3.4 失败隔离：一个失败不能阻断其余

算例实测：

| 场景 | 结果 |
|---|---|
| 全部成功 | 失败数 0 |
| **失败隔离（本次撤销次序 3, 1）** | 成功 **2 / 3**，失败 **1** |

读法：撤销过程中一次失败，**其余两次仍然完成**。这是通过 `try/catch` 每条分别捕获实现的。

为什么不能"遇到错误就中断"：中断会让后面的资源全部泄漏——**而泄漏的资源在进程结束时可能无人清理**。

同时必须"报告失败"：静默吞掉异常会让泄漏变得不可见。**正确做法是继续撤销、汇总失败、并在结束时统一报告。**

**这条原则与 3.4 的"拒绝要给替代路径"、3.5 的"恢复要局部化"是同一个模式**：局部失败不应升级为全局失败。

### 3.5 撤销必须幂等

算例实测：**连续撤销两次，实际删除次数是 1**，撤销后条目数是 0。

为什么必须幂等：撤销会被调用多次——正常路径一次、异常处理一次、进程退出钩子一次。**不幂等的撤销会产生二次释放错误。**

实现方式：用一个标志位或"是否已撤销"的状态。

```js
// 幂等撤销：第二次调用是空操作
export function makeDisposable(resource) {
  let disposed = false
  return () => {
    if (disposed) return false
    disposed = true
    resource.release()
    return true
  }
}
```

这与 3.5 持久化的"赋值型幂等"是同一个思路：**用状态标记把"做过了"变成可检查的事实**。

### 3.6 阶段：为什么启动分多步

算例给出的阶段数是 **5**。分阶段的原因是：不同的初始化有不同依赖关系，混在一起会产生顺序问题。

典型的五个阶段（从早到晚）：

| 阶段 | 做什么 | 为什么单独 |
|---|---|---|
| 配置 | 读配置、校验 | 后面全部依赖它 |
| 基础设施 | 日志、存储连接 | 被广泛依赖 |
| 服务 | 业务服务注册 | 依赖基础设施 |
| 消费者 | 注册监听器、订阅 | 依赖服务存在 |
| 就绪 | 开始接收请求 | 必须在全部就绪后 |

为什么不能用一个大的初始化函数：**它无法表达"什么必须在什么之前"**。分阶段后，每一阶段内部可以并发或任意顺序，阶段之间是硬顺序。

判据：**如果两个初始化之间有依赖，它们必须在不同阶段**（或者在同一阶段内显式排序）。

## 四、特殊情况与处理技巧

| 情况 | 为什么 | 处理 |
|---|---|---|
| 撤销删掉了别人的服务 | 按名字查找 | 用注册返回的句柄 |
| 一个撤销失败导致其余泄漏 | 中断式撤销 | 逐个 try/catch + 汇总报告 |
| 二次释放错误 | 撤销不幂等 | 状态标记 |
| 撤销顺序错误 | 未逆序 | 逆序撤销 |
| 启动时依赖未就绪 | 未分阶段 | 分阶段，阶段间硬顺序 |
| 循环依赖 | A 依赖 B 又依赖 A | 引入第三个组件或延迟解析 |
| 测试时容器状态互相污染 | 全局单例 | 每个测试建独立容器 |
| 热重载后旧服务残留 | 撤销没跑 | 确保撤销在重载路径上执行 |

"循环依赖"这一条值得展开：两个组件互相依赖时，通常说明**职责划分有问题**——把共同需要的那部分抽成第三个组件，依赖就变成了单向。

## 五、工业界的做法（可照做）

### 5.1 依赖注入的框架做法

| 框架 / 生态 | 方式 | 特点 |
|---|---|---|
| **Spring**（Java） | 注解 + 容器扫描 | 生命周期回调（`@PostConstruct` / `@PreDestroy`） |
| **Guice**（Java） | 模块绑定 | 作用域（singleton / request） |
| **Angular**（TS） | 提供者 + 层级注入器 | **层级**：子注入器可覆盖父级 |
| **.NET DI** | 内置容器 | 三种生命周期（单例 / 作用域 / 瞬态） |
| **Node 生态** | 手写容器或轻量库 | 显式的 disposer 更常见 |

**共同概念：作用域（scope）。**

| 生命周期 | 含义 | 撤销时机 |
|---|---|---|
| 单例（singleton） | 全局一份 | 进程结束 |
| 作用域（scoped） | 每个请求/会话一份 | 请求结束 |
| 瞬态（transient） | 每次解析新建 | 由使用方负责 |

这三档与本篇的对应：不同作用域意味着**不同的撤销时机**，因此容器必须支持"按作用域批量撤销"——这正是 3.3 的逆序撤销要处理的范围。

### 5.2 资源释放的模式

| 模式 | 语言 / 场景 | 机制 |
|---|---|---|
| **RAII** | C++、Rust | 析构函数 / Drop 在作用域结束时自动执行 |
| **try-with-resources** | Java | 语言级的自动关闭 |
| **using** | C# | 同上 |
| **finally / defer** | 通用 | 手动但结构化 |
| **disposer 注册表** | JS / 动态语言 | 容器统一管理 |

RAII 的思想值得借用：**把"释放"绑定到"作用域结束"**，而不是靠程序员记得调用。容器的 disposer 注册表就是 JS 里对 RAII 的近似。

### 5.3 参数与设计起点

| 项 | 推荐 | 依据 |
|---|---|---|
| 注册粒度 | 一个服务一个注册 | 便于精确撤销 |
| 撤销凭证 | 注册时返回句柄 | 避免名字冲突 |
| 覆盖策略 | 显式允许并记录被覆盖者 | 隐式覆盖会难查 |
| 撤销顺序 | 严格逆序 | 依赖关系 |
| 失败处理 | 逐个捕获 + 汇总报告 | 失败隔离 |
| 阶段数 | 3–6 | 太少无法表达依赖，太多难维护 |
| 解析时机 | 启动时校验依赖 | 早失败 |

"启动时校验依赖"这一条很重要：**在启动阶段就解析一次全部依赖**，这样缺依赖会在启动时失败，而不是在某个请求处理到一半时才失败。

### 5.4 一份可落地的实施清单

1. **注册返回句柄**：每次注册产生一个只能撤销它自己的 disposer。
2. 禁止按名字撤销：撤销只接受句柄。
3. 逆序撤销：dispose 全部时从最后一个开始。
4. 失败隔离：逐个捕获，汇总失败并报告。
5. 幂等：撤销带状态标记。
6. 分阶段启动：3–6 个阶段，阶段间硬顺序。
7. 启动校验：启动时解析全部依赖，缺依赖即失败。
8. 作用域：区分单例与请求级，按作用域批量撤销。
9. 覆盖记录：发生覆盖时记录被覆盖者。
10. 测试：为每个容器写"注入失败回滚"的用例。

## 六、学术界的结论

### 6.1 依赖倒置与控制反转

Martin 的**依赖倒置原则**（与 1.3 的稳定依赖原则同源）：

> 高层模块不应依赖低层模块，两者都应依赖抽象。

**控制反转（IoC）** 是它在结构上的推论：不主动创建依赖，而是被动接收依赖。

这两种说法指向同一件事：**把"谁创建谁"的决策从代码里移出去**，交给容器。

它的代价：代码的**执行路径变得不直观**（不能顺着一行代码找到实现）。所以它适合基础设施，不适合所有地方——过度使用会让调试变难。

### 6.2 RAII 与所有权

C++ 的 RAII 与 Rust 的所有权模型给出了一个更强的主张：

> **资源释放应当由语言保证，而不是由纪律保证。**

- **RAII**：析构函数在作用域结束时执行。
- 所有权：编译器保证每个资源有唯一所有者，所有者离开作用域即释放。

它们的共同点：**把"忘记释放"从可能的错误变成不可表达的状态。**

对动态语言的启示：既然语言不保证，就要**用容器把释放集中管理**——让"忘记释放"的唯一途径是"忘记注册"。

### 6.3 组件化与接口契约

组件模型（如 CORBA、OSGi、现代微服务）的三个核心概念与本篇对应：

| 概念 | 本篇对应 |
|---|---|
| 接口（提供什么） | 注册的名字与能力 |
| 生命周期 | 阶段与作用域 |
| 依赖声明 | 注册顺序与解析 |

OSGi 的教训值得记取：它把生命周期做得很完整（安装、解析、启动、停止、卸载），但也因此复杂。**容器设计的经验是：生命周期要显式，但阶段数要少。**

### 6.4 注册即效果

在我们的 harness 里有一条形式化的原则：

> **每次注册都是一个效果（effect），它返回自己的撤销函数。**

它解决三个问题：

1. **撤销的精确性**：不用名字查找（3.2）。
2. 幂等性：撤销函数自己管理状态（3.5）。
3. 可组合性：效果可以嵌套，外层撤销时内层自动撤销。

这条原则的可检查形式：**注册函数的返回值必须是一个可调用的撤销函数**（而不是返回 void 或者需要另外传参）。

## 七、理论：三条可检查性质

### 7.1 撤销的精确性

$$
\text{dispose}(h) \text{ 只影响 } h \text{ 对应的那一次注册}
$$

算例验证：按归属撤销后条目数为 1（保留了后来者的），按名字撤销后为 0（**违反了这条性质**）。

### 7.2 失败隔离

$$
\#\text{成功撤销} = \#\text{全部撤销} - \#\text{失败撤销}
$$

算例验证：3 次撤销中 1 次失败，**成功 2 次**。失败没有阻断其余。

### 7.3 幂等

$$
\text{dispose} \circ \text{dispose} = \text{dispose}
$$

算例验证：连续撤销两次，**实际删除次数是 1**。

**这三条都是可机械验证的**，因此可以作为容器的单元测试。

### 第二题：设计阶段划分

场景：一个服务需要初始化：日志、配置、数据库连接、消息队列消费者、HTTP 服务、定时任务。

要求：

## 十、算例

算例实现了本篇的注册、撤销与失败隔离机制。

```powershell
cd D:\dsh-course
node examples/sa27_container.mjs        # 全部函数的运行结果
node examples/test_sa27_container.mjs   # 数字回归断言
```

它做到的事：

- 带归属撤销与按名字撤销的对照（**按名字撤销会让后来者的服务消失**）。
- 注册次序（1, 2, 3）与撤销次序（3, 2, 1）。
- 失败隔离（3 次撤销中 1 次失败，另外 2 次成功）。
- 幂等撤销（连续两次的实际删除次数是 1）。
- 阶段数量（5）。

这一篇只要记住一句：容器里**注册要返回撤销句柄、撤销要按句柄逆序、失败要逐个隔离、撤销要幂等**——按名字撤销会把后来者的服务一起删掉，而一次撤销失败会让其余资源全部泄漏。

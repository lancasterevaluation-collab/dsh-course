## 本篇新词

- 容器（container） 指持有零件并分发依赖的对象。它的职责是记账与转发，不是"一个大的全局变量"。
- 服务（service） 指登记进容器、可按名字取用的能力。判据是它有稳定的名字与明确的契约。
- 依赖注入（dependency injection） 指依赖由外部传入，模块不自己构造。
- 服务定位器（service locator） 指模块主动向全局注册表索取依赖。它的代价是依赖不可静态读出。
- 归属（ownership） 指这条注册由谁负责撤销。它是纯粹的记账概念。
- effect 指一个可撤销的副作用，创建时返回自己的撤销函数。
- 卸载（dispose） 指部件退出时撤销它注册过的一切。它与"停止使用"不同。
- 生命周期阶段（lifecycle phase） 指注册前、已注册、可用、卸载中、卸载后五个时刻。
- 作用域（scope） 指一批注册的集合，退出时撤销它包含的全部注册。

## 一、【设计原因】

### 1.1 缺陷一：零件在用到的地方被构造

没有容器的项目里，需要模型的代码自己构造客户端，需要工具的代码自己建注册表，需要会话的代码自己开一个数组。这个写法埋下三件事。

- 无法替换：测试要连真实服务。
- 无法共享：两处各自建一个，状态不互通。
- 无法统一处置：每个构造点各自决定何时销毁，而多数地方不会销毁。

更准确的描述是构造点分散。模块知道自己需要一个客户端，这是合理的依赖。它同时知道"怎么把这个客户端造出来"，这才是不该有的知识。

### 1.2 缺陷二：卸载之后残迹还在

一个部件被卸载时，它的入口函数返回了，而它留下的东西还在：表里的服务条目、挂在事件上的监听器、每三十秒触发一次的定时器、没有关闭的文件句柄。

症状是缓慢的资源增长与难以解释的行为。例如一个已卸载的插件仍在对事件作出反应，因为它的监听器还挂着。

排查这类问题成本很高，因为症状与原因在时间上分离：泄漏发生在卸载那一刻，而症状在几小时后才可见。

### 1.3 缺陷三：同名注册会静默覆盖

在一个共享的服务表里，任何部件都能查到任何服务。部件少时这是便利，部件多时是隐患：一个部件的名字可能与另一个冲突，而冲突的表现是静默覆盖。

被覆盖的那个提供者以为自己的服务仍在使用，实际上已经被替换。而它卸载时若按名字删除，会把后来者的条目一并删掉。

### 1.4 缺陷四：启动顺序只存在于某个人的记忆里

项目跑起来之后，某些部件必须在另一些之前加载，否则启动失败。而这条规则往往没有写在任何地方。

代价在增加部件时显现：新成员按字母序或按加入顺序加载，于是启动偶尔失败，而失败信息是一句"某服务不存在"。它没有指出真正的原因（顺序）与正确的做法（声明依赖）。

### 1.5 由此确定的设计目标

1. 注册进一张共享表，查找按名字，后者覆盖前者。
2. 每条记录带上归属，撤销只删自己写的那条。
3. 注册动作返回它的撤销函数，卸载时按逆序执行。
4. 依赖写在签名上，让"这个部件需要什么"可静态读出。
5. 查找失败立刻报错，把缺件的时间点前移到发生处。

**本节要点**

- 构造点分散比"耦合"更准确地描述了问题。
- 卸载的残迹在几小时后才表现为症状。
- 同名覆盖让按名字删除的撤销必然出错。
- 启动顺序是隐式知识，代价在增加部件时显现。
- 五条目标：共享表、带归属、返回撤销函数、依赖可读、缺件可见。

## 二、【直觉】

### 2.1 钥匙柜

一个前台有面钥匙柜，每把钥匙对应一个房间。

- 谁拿走钥匙，谁负责还回来。
- 两个人先后拿走同一把钥匙时，柜子上记的是后一个人的名字。
- 前一个人来还钥匙时，柜子要先看他是不是当前那位登记人，不是就不能把钥匙取走。

第三条是这个画面里唯一反直觉的地方。它防的是一件具体的事：前一个人来还钥匙时，把后一个人正在用的那把一并收走。

::: keypoint 反直觉点
**"撤销"是一个减法，而减法需要一个确定的被减项。** 表里只有"名字到实现"时，"撤销这个部件的注册"只能理解成"删掉这个名字"，而这个名字可能已经被别人覆盖。归属字段的作用就是把被减项确定下来。
:::

### 2.2 接力棒

一场接力里，棒是按顺序交出去的，而回收要按相反的顺序。

- 先交出去的棒在最下游，最后交出去的棒在最上游。
- 收的时候先收上游，因为上游的人还在等下游的结果。
- 顺序反过来收，上游就会收到一根已经没人接的棒。

容器里的注册顺序与撤销顺序是同样一对镜像。先注册的往往是更基础的设施，所以撤销时先撤依赖者。

### 2.3 一个数字直觉

设两个部件先后注册了同一个名字 `llm`，第一次由部件 A 注册，第二次由部件 B 覆盖。

- 带归属判断的撤销：A 撤销后表里仍有 1 条（B 的），B 撤销后 0 条。
- 按名字删除：A 撤销后表里 0 条，而 B 仍在运行。

两次操作的表大小完全一样，差别只在"撤销之后 B 还能不能取到它自己的服务"。所以这类缺陷不会在单部件测试里出现，它需要一次覆盖才能暴露。

**本节要点**

- 谁借的谁还，还之前先确认登记人是不是自己。
- 撤销按注册的逆序，先撤依赖者。
- 覆盖场景下的错误只在两个部件共享一个名字时暴露。

## 三、【严格】

### 3.1 定义

::: theorem 定义 2.3.1（服务表与条目）
服务表是一个映射 $T: \mathit{Name} \to \mathit{Entry}$，其中

$$
\mathit{Entry} = (\mathit{impl},\ \mathit{owner},\ \mathit{scope}),
$$

$\mathit{impl}$ 是实现，$\mathit{owner}$ 是注册者，$\mathit{scope}$ 是这条注册所属的作用域。**同一名字至多有一条条目**，重复注册使该名字的条目被替换。
:::

::: theorem 定义 2.3.2（归属）
一条条目的**归属**是 $\mathit{owner}$ 字段。撤销一个注册的后置条件是：

$$
T.\mathrm{get}(n) \neq \text{本次注册写入的那一条} \ \lor\ T.\mathrm{get}(n) \text{ 未定义}.
$$

即"这个名字下不再有我写的条目"。
:::

::: theorem 定义 2.3.3（注册是 effect）
注册动作是一个函数

$$
\mathrm{register}: (\mathit{name},\ \mathit{impl}) \to \mathrm{disposer},
$$

其中 $\mathrm{disposer}$ 是**幂等**的：$\mathrm{disposer}^k = \mathrm{disposer}$ 对一切 $k \ge 1$ 成立。
:::

::: theorem 定义 2.3.4（撤销顺序）
设一个作用域内的注册次序为 $e_1, e_2, \dots, e_n$。它的撤销次序是

$$
\mathrm{disposer}(e_n),\ \mathrm{disposer}(e_{n-1}),\ \dots,\ \mathrm{disposer}(e_1),
$$

即注册次序的逆序。
:::

::: theorem 定义 2.3.5（作用域）
一个**作用域** $S$ 是一个注册集合，带一个父作用域 $\mathrm{parent}(S)$（可为空）。查找的可见性由

$$
\mathrm{visible}(S) = S \cup \mathrm{visible}(\mathrm{parent}(S))
$$

给出，即沿父链向上。两个作用域互为兄弟时，彼此的注册不在对方的可见集合里。
:::

::: theorem 定义 2.3.6（生命周期阶段）
一个部件经过五个阶段

$$
\{\text{注册前},\ \text{已注册},\ \text{可用},\ \text{卸载中},\ \text{卸载后}\},
$$

每个阶段有允许与禁止的动作集合。**"已注册"与"可用"必须区分**：前者允许声明依赖，后者才允许处理请求。
:::

### 3.2 命题

::: theorem 命题 2.3.1（按名字撤销在覆盖下必然出错）
设两个部件 $A$、$B$ 先后注册同一名字 $n$。若撤销实现为无条件删除 $T.\mathrm{delete}(n)$，则 $A$ 的撤销会使 $B$ 的服务消失。

**证明.** 注册 $A$ 后 $T(n) = \mathit{Entry}_A$。注册 $B$ 后 $T(n) = \mathit{Entry}_B$（后者覆盖）。此时执行 $A$ 的撤销，无条件删除使 $T(n)$ 未定义。而 $B$ 仍在运行且仍认为自己提供了 $n$。故 $B$ 的服务在无人撤销它的情况下消失。

↓ **为什么能这么写？** 删除以名字为参数，而名字相同无法区分两条条目。

$\blacksquare$

::: keypoint 这类缺陷为什么难发现
**它需要一次覆盖才能暴露。** 单部件测试里每个名字只有一个提供者，两种实现的行为完全相同。所以它会在"两个插件恰好同名"或"配置覆盖"这种组合场景里第一次出现。
:::

::: theorem 命题 2.3.2（归属保护的正确性）
带归属判断的撤销

$$
\mathrm{if}\ T.\mathrm{get}(n).\mathit{owner} = \mathit{owner}_{\text{本次}}\ \mathrm{then}\ T.\mathrm{delete}(n)
$$

在任意覆盖次数下都满足定义 2.3.2 的后置条件。

**证明.** 分两种情形。若被撤销的这条是当前条目，则删除它，后置条件成立。若它已被后来的注册覆盖，则当前条目的 $\mathit{owner}$ 不是本次的 owner，条件为假，不做删除，于是"这个名字下不再有我写的条目"这一条已经成立。两种情形都成立，且与覆盖次数无关。

↓ **为什么能这么写？** 判断的是"当前条目是不是我写的"，而不是"这个名字存在不存在"。

$\blacksquare$

**数值**：$A$、$B$ 依次注册同名服务后，$A$ 撤销使表中条目数从 1 变为 1（仍是 $B$ 的），$B$ 撤销后为 0。若去掉归属判断，$A$ 撤销后即为 0。

::: theorem 命题 2.3.3（撤销必须逆序）
若 $A$ 在初始化时取得 $B$ 提供的服务，则撤销次序必须是 $A$ 先于 $B$。

**证明.** $A$ 的清理动作可能使用 $B$ 的服务（例如释放 $B$ 分配的资源）。撤销 $A$ 需要一个仍可用的 $B$。若先撤销 $B$，则 $B$ 的条目已不在表中，$A$ 的清理要么失败要么拿到空值。故必须先撤 $A$。而按注册次序，$A$ 必然在 $B$ 之后注册（它初始化时 $B$ 已存在），所以"$A$ 先撤"就是"逆序"。

↓ **为什么能这么写？** 依赖方向决定注册方向，而撤销方向与它相反。

$\blacksquare$

::: theorem 命题 2.3.4（幂等撤销使重复卸载无害）
若 $\mathrm{disposer}$ 幂等，则对同一个 effect 调用任意多次与调用一次的结果相同。

**证明.** 由定义 2.3.3，$\mathrm{disposer}^k = \mathrm{disposer}$。归纳即得。

↓ **为什么能这么写？** 幂等性是函数与其自身复合的不动点性质。

$\blacksquare$

::: keypoint 为什么必须要求幂等
**"重复卸载"是常见情况**：一个部件可能被父作用域退出与自己退出两条路径同时撤到。而"多撤一次"不应该变成错误——若它抛错，卸载路径上的后续清理会被中断。
:::

::: theorem 命题 2.3.5（可见性的偏序与查找代价）
作用域的可见关系是偏序（自反、反对称、传递），且深度为 $d$ 的作用域查找一次至多比较 $d+1$ 个作用域。

**证明.** 自反与传递由定义 2.3.5 的直接展开得到。反对称：若 $S$ 可见 $S'$ 且 $S'$ 可见 $S$，则两者在同一条父链上且互为祖先，由父子关系无环得 $S = S'$。查找代价：一次查找沿父链逐层比较，链长为 $d+1$。

↓ **为什么能这么写？** 可见性由父链定义，而父链是一条链。

$\blacksquare$

**数值**：深度为 3 的链上，命中第 2 层时比较 2 次，未命中时比较 4 次。

::: theorem 命题 2.3.6（依赖可读性决定可诊断性）
若依赖写在签名或声明里，则部件的依赖集合在静态分析阶段即可确定。若依赖由定位器在函数体内取得，则在不执行该部件的前提下无法确定其依赖集合。

**证明.** 前者：依赖是签名的组成部分，静态分析可读取。后者：依赖的取得是运行期的一次函数调用，其参数可能由运行期数据决定（例如按名字拼接），因此"会请求哪些服务"不构成静态可判定的性质。

↓ **为什么能这么写？** 静态可读的性质必须出现在代码的声明部分，而不是执行路径里。

$\blacksquare$

::: keypoint 这条命题的工程含义
**依赖图能被画出来，才谈得上启动前检查。** 用定位器时，诊断工具只能靠运行时观察，而没被走到的路径永远是盲区——这也是第 4 卷做失败归因时依赖图从缺的原因。
:::

### 3.3 本节要点

**本节要点**

- 服务表按名字索引，后者覆盖前者（定义 2.3.1）。
- 归属让撤销的后置条件可以被精确定义（定义 2.3.2）。
- 注册返回幂等的撤销函数（定义 2.3.3）。
- 撤销按注册逆序（定义 2.3.4）。
- 作用域嵌套，可见性沿父链（定义 2.3.5）。
- 阶段划分约束"什么时候可以做什么"（定义 2.3.6）。
- 按名字撤销在覆盖下必然出错（命题 2.3.1）。
- 归属保护在所有覆盖情形下正确（命题 2.3.2）。
- 撤销必须逆序（命题 2.3.3）。
- 幂等使重复卸载无害（命题 2.3.4）。
- 可见性构成偏序，查找代价与深度成正比（命题 2.3.5）。
- 依赖可读性决定可诊断性（命题 2.3.6）。

## 四、【回到直觉】

- **定义 2.3.1 说的**：一张表，按名字查，后写的盖住先写的。**覆盖是刻意的，因为装配需要它。**
- **定义 2.3.2 说的**：撤销前先问"这条现在是不是我写的"。**问的是当前条目，不是这个名字。**
- **定义 2.3.3 说的**：注册的返回值就是它的清理动作。**多撤一次不算错。**
- **定义 2.3.4 说的**：交出去的棒按相反顺序收回。
- **定义 2.3.5 说的**：往上看得到祖先，看不到兄弟。
- **定义 2.3.6 说的**：注册完成不等于可以接活，中间隔着一个"依赖已就绪"。
- **命题 2.3.1 说的**：按名字删除的撤销，在同名覆盖时会把别人的服务删掉。
- **命题 2.3.2 说的**：加一句归属判断，覆盖任意多次都不会错。
- **命题 2.3.3 说的**：先撤依赖者，再撤被依赖者，否则清理会拿到一个空服务。
- **命题 2.3.4 说的**：撤销函数写成幂等的，重复卸载就不会中断清理路径。
- **命题 2.3.5 说的**：查找代价与作用域深度成正比，深度 3 的链最多比 4 次。
- **命题 2.3.6 说的**：依赖写在签名上，工具才画得出依赖图。

**本节要点**

- 覆盖是刻意的。
- 归属判断的对象是当前条目。
- 撤销幂等。
- 逆序撤销。
- 可见性沿父链。
- 依赖可读决定可诊断。

## 五、【工具箱】

### 5.1 归属判断的三行

每次注册都返回一个撤销函数，而它的骨架是三行。

1. 判断是否已经撤销过，是则直接返回。
2. 判断当前条目的主人是不是自己，不是则直接返回。
3. 删除条目。

**这三行的顺序不能换**：幂等检查在最前，因为它与表的状态无关。

### 5.2 逆序撤销与失败隔离

把撤销函数按注册顺序压栈，退出时从栈顶弹出。

**每个撤销函数单独捕获异常**，继续执行其余的，最后汇总失败项。理由是卸载路径一旦被中断，剩下的清理永远不会执行，而"部分泄漏"比"全部泄漏"更难排查。

### 5.3 作用域的三条性质

1. 嵌套：子作用域退出时只撤销属于它的注册。
2. 向上可见：查找沿父链进行，子能见父。
3. 兄弟隔离：一个作用域看不到兄弟作用域的服务。

**这三条合起来解决"既要共享又要隔离"**：共享发生在父链上，隔离发生在兄弟之间。

### 5.4 阶段检查

| 阶段 | 允许 | 不允许 |
|---|---|---|
| 注册前 | 构造自身状态 | 提供或请求服务 |
| 已注册 | 声明依赖 | 处理请求 |
| 可用 | 处理请求、注册子部件 | —— |
| 卸载中 | 撤销注册、等待在途操作 | 发起新请求 |
| 卸载后 | —— | 任何使用 |

**最容易被违反的是"已注册"与"卸载中"两行**：前者表现为"启动时偶尔报某服务不存在"，后者表现为"卸载之后仍出现该部件的动作"。

### 5.5 查找失败的错误信息

查找失败的错误至少带三样。

- 请求的服务名。
- 当前作用域名（用于区分"全局没有"与"这个作用域看不到"）。
- 当前作用域可见的名字清单。

第三样常被省略，而它最有用：它把"我没有它"变成"我有这些，你是不是要找其中一个"。

**本节要点**

- 归属判断三行，幂等检查在最前。
- 撤销逆序执行且逐个捕获。
- 作用域三条性质覆盖共享与隔离。
- 阶段表约束每个时刻的合法动作。
- 查找失败要给出可见名字清单。

### 7.2 条目段与注册段

条目段先把一条记录的形状定下来，注册段负责写入并返回撤销函数。

```js
// 定义 2.3.1 / 2.3.2：一条记录带实现、主人与作用域
export function makeEntry(impl, owner, scope) {
  return { impl, owner, scope }
}

// 定义 2.3.3：注册返回幂等的撤销函数，撤销时判归属
export function makeDisposer(table, name, entry) {
  let done = false
  return () => {
    if (done) return
    done = true
    const current = table.get(name)
    if (current && current.owner === entry.owner) table.delete(name)
  }
}
```

反例只差一行，而它演示了命题 2.3.1。

```js
// 命题 2.3.1 的反面：按名字无条件删除
export function naiveDisposer(table, name) {
  let done = false
  return () => {
    if (done) return
    done = true
    table.delete(name)
  }
}
```

### 7.3 撤销段

撤销段按逆序执行，并逐个捕获失败。

```js
// 定义 2.3.4 / 命题 2.3.4：逆序撤销，失败隔离
export function disposeAll(disposers) {
  const failures = []
  let succeeded = 0
  for (const d of [...disposers].reverse()) {
    try { d(); succeeded++ } catch (err) { failures.push(err) }
  }
  return { succeeded, failures }
}
```

### 7.4 作用域段

作用域段把注册与查找加上一条父链。

```js
// 定义 2.3.5：可见性沿父链，兄弟之间互不可见
export class Scope {
  #parent = null
  #table = new Map()
  #disposers = []
  #name = 'root'

  constructor(parent = null, name = 'root') {
    this.#parent = parent
    this.#name = name
  }

  get parent() { return this.#parent }
  get name() { return this.#name }
  get table() { return this.#table }
  get registrations() { return this.#disposers.length }

  provide(name, impl, owner = this) {
    const entry = makeEntry(impl, owner, this)
    this.#table.set(name, entry)
    const dispose = makeDisposer(this.#table, name, entry)
    this.#disposers.push(dispose)
    return dispose
  }

  lookup(name) {
    let scope = this
    while (scope) {
      if (scope.#table.has(name)) return scope.#table.get(name).impl
      scope = scope.#parent
    }
    return undefined
  }

  dispose() {
    return disposeAll(this.#disposers)
  }
}
```

### 9.2 失败模式

**（1）检查放在装载期（L9 位置放错）。** 依赖是否齐备在第一次调用时才发现，而它本该在注册完成后立刻检查。表现是"某个功能在运行几分钟后才第一次报错"。

**（2）前提会变（L9）。** 命题 2.3.3 的逆序以"注册顺序即依赖顺序"为前提。若某个部件在运行期才注册它依赖的服务，这个前提不再成立，逆序也就不再等于依赖逆序。

**（3）按名字删除的撤销。** 覆盖场景下误删后来者的服务。

**（4）撤销不幂等。** 重复卸载抛错并中断清理路径。

**（5）撤销顺序与注册相同。** 依赖者的清理拿到已撤销的服务。

**（6）撤销失败中断整条清理路径。** 造成部分泄漏，比全部泄漏更难排查。

**（7）查找失败返回空值。** 错误延后到"读取 undefined 的属性"，与原因隔了好几层。

**（8）依赖藏在函数体里。** 依赖图无法静态画出，启动前检查无从下手。

**（9）在构造函数里访问容器。** 部件在注册完成之前就请求服务，表现为"启动时偶尔报某服务不存在"。

**（10）卸载过程中又注册。** 新注册的监听器不会再被撤销，表现为"卸载之后该部件仍有动作"。

**本节要点**

- 决策表覆盖 12 种情形。
- 失败模式十条，前两条是位置放错与前提会变。
- 最隐蔽的是"按名字删除的撤销"——单部件测试里看不出来。

**影响三：注入与定位的选择决定可诊断性。** 本篇指出它对第 4 卷失败归因的直接支撑。

### 骨架：四块

### 情境绑定：当你……就想起……

| 当你…… | 立刻想起 |
|---|---|
| 要写一个注册动作 | 让它返回撤销函数，撤销里带上归属判断 |
| 发现两处注册了同一个名字 | 检查撤销是否按名字删除，那样会误伤后来者 |
| 想知道某个模块需要什么 | 看它的签名与声明，依赖藏在函数体里就是定位器 |
| 遇到"某服务不存在"的启动失败 | 先查加载顺序与依赖声明 |
| 卸载之后还有事件被处理 | 监听器没有撤销，它是残留里最常见的一种 |
| 要判断一个东西该不该是服务 | 问它是否有稳定的名字与契约、是否有第二个使用者 |
| 碰到循环依赖 | 优先重构打破，其次显式声明为延迟解析 |
| 卸载过程抛错导致其余清理没做 | 逐个捕获并汇总，不要中断整条清理路径 |
| 要给一个子系统做隔离 | 用嵌套作用域，共享走父链，隔离靠兄弟互不可见 |
| 评估"新增一个能力要改几处" | 能只改配置就说明容器做对了 |

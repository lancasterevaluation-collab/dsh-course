## 读完这一篇你会知道什么

1. **两种事件语义**：广播（全部收到，算例里调用 3 次、载荷完全相同）与 waterfall（依次处理）。
2. waterfall 的致命规则：不调用 `next()` 就是短路——算例里短路发生在第 1 个监听器，后面 1 个再也没执行。
3. 原样传回不算短路：算例里返回原值仍被判为"未短路"，因为它调用了 `next()`。
4. 优先级排序是稳定的：优先级从大到小执行（高 → 中 → 低），同优先级保持注册顺序。
5. 监听也是注册：因此适用 2.3 的撤销规则（返回值必须是撤销函数）。
6. 工业界怎么做：事件总线、中间件、插件 hooks 与它们的短路语义。
7. 学术界：发布订阅、责任链、拦截器，以及插件系统的架构研究。

## 一、为什么事件值得单独设计

### 1.1 忘了调用 next，插件静默失效

一个插件在处理请求时做了记录，然后忘记调用 `next()`。**后面三个插件再也没运行过，而没有任何报错。**

### 1.2 顺序不确定

两个插件都注册了同一个事件，但执行顺序每次不同（因为用了无序容器）。**结果在测试环境正常，生产环境偶发。**

### 1.3 监听器拿到了不同的载荷

广播时每个监听器收到一份**副本**，某个监听器修改了它，另一个监听器看到的行为不一致。

这三件事分别对应：**短路语义、顺序稳定性、载荷共享。**

## 二、广播与 waterfall

| 类型 | 语义 | 用途 | 返回值 |
|---|---|---|---|
| **广播** | 全部监听器都收到，逐个调用 | 通知、记录、副作用 | 无（或忽略） |
| **waterfall** | 依次传入，最后一个的返回值是最终结果 | 改写、拦截、加工 | 值 |

两者的关键差别：广播是"通知"，**每个监听器独立**。waterfall 是"接力"，每个监听器都能改变传给下一个的值。

选择依据：**需要改写值就用 waterfall，只需要知道发生了什么事就用广播。**

## 三、怎么做

### 3.1 广播：所有人都收到同一个载荷

实现如下。

```js
// 广播：载荷可以是共享对象，但监听器必须约定不改它
export function broadcast(listeners, payload) {
  for (const listener of listeners) listener(payload)
  return listeners.length
}
```

算例实测：

| 项 | 值 |
|---|---|
| 广播的调用次数 | **3** |
| 监听器都收到同一个载荷 | **`true`** |

"同一个载荷"是一个需要明确的设计决定：

- **共享**：省内存、快，但任何监听器改它都会影响其他监听器。
- 副本：安全，但每次广播都要复制（对大的载荷代价高）。

推荐做法：**共享载荷 + 约定只读**。如果某类事件确实需要监听器改写，那就用 waterfall 而不是广播。

### 3.2 waterfall 与 next

waterfall 的语义是**接力**：每个监听器收到当前值，可以选择改写它，然后把控制权交给下一个。

```js
// waterfall：每个监听器收到值，必须调用 next() 才能继续
export function waterfall(listeners, initial, next) {
  let index = 0
  const step = (value) => {
    if (index >= listeners.length) return value
    const listener = listeners[index]
    index += 1
    return listener(value, step)
  }
  return step(initial)
}
```

算例实测：waterfall 的终值是 **`HI!`**，并且是否走完是 `true`。

"必须调用 `next()`"这条规则为什么是必需的：它让监听器可以**故意短路**（例如一个鉴权插件拒绝请求时不再往下传）。

**但它的代价是"忘记调用"与"故意短路"无法区分**——两者都表现为链路终止。这是本篇最重要的风险点。

### 3.3 短路与原样传回

算例把这两种情况区分得很清楚：

| 情况 | 判定 | 结果 |
|---|---|---|
| **短路** | 在第 **1** 个监听器处终止 | 后续 **1** 个未执行，值是 `被短路` |
| **原样传回** | **不被判为短路**（`false`） | 终值是 `x!`（后续监听器仍执行） |

关键点：**"原样传回"仍然算继续，因为它调用了 `next()`。** 也就是说：

- **是否短路只看"有没有调用 `next()`"，与返回值无关。**
- 一个监听器返回原值但调用了 `next()`，链路继续（算例里的 `x!` 就是后续监听器加工的结果）。

这条规则对写插件的直接含义：

| 你想做的 | 必须写 |
|---|---|
| 只观察不改写 | 改写后的值 + **调用 `next()`** |
| 改写后继续 | 新值 + **调用 `next()`** |
| 故意终止 | **不调用 `next()`**，并返回最终值 |

调试建议：既然"忘记调用"与"故意短路"表现相同，**应当在短路时留下记录**（日志或事件）。这样万一某人删掉了一行 `next()`，能从事后记录里发现"这里不再有后续了"。

### 3.4 优先级与稳定性

多个监听器注册同一事件时，执行顺序由**优先级**决定。算例实测：

| 规则 | 结果 |
|---|---|
| 优先级从大到小 | 高 → 中 → 低 |
| **同优先级** | **保持注册顺序**（先注册 → 后注册） |

**"同优先级保持注册顺序"是一个必要的性质**（稳定排序）。缺少它会导致：

- **测试偶发失败**：两个同优先级监听器的顺序不确定。
- 行为依赖实现细节：例如依赖哈希表的迭代顺序。

实现方式：排序键用 `(优先级, 注册序号)` 的元组。**注册序号保证了稳定性。**

参数建议：**优先级用少量离散档位**（例如 3–5 档），不要用连续数值。连续优先级会让"谁在谁前"变成难以推理的问题（这也是容器优先级、告警阈值等设计的共同教训）。

### 3.5 监听也是注册

监听器本质上是一次**注册**，因此 2.3 的全部结论都适用：

| 2.3 的规则 | 在事件上的体现 |
|---|---|
| 注册返回撤销句柄 | `on(...)` 返回一个取消订阅的函数 |
| 撤销按句柄 | 用返回的函数取消，不要按监听器名字找 |
| 撤销必须幂等 | 重复取消订阅不出错 |
| 失败隔离 | 一个监听器抛错不应影响其他（按事件类型决定） |

"失败隔离"在事件上有两种合理策略：

| 策略 | 适用 | 风险 |
|---|---|---|
| **一个抛错不影响其他**（广播） | 通知类事件 | 错误被静默吞掉 |
| **一个抛错中断链路**（waterfall） | 处理链 | 与短路难以区分 |

推荐：广播类**隔离并汇总报告**，waterfall 类让错误上抛（因为它本来就有中断语义）。

## 四、特殊情况与处理技巧

| 情况 | 为什么 | 处理 |
|---|---|---|
| 后续插件静默失效 | 忘记调用 `next()` | 短路时留记录。代码评审重点检查 |
| 顺序偶发变化 | 未做稳定排序 | 排序键加注册序号 |
| 一个监听器改坏了载荷 | 共享对象被修改 | 约定只读，或改用 waterfall |
| 监听器抛错导致全链中断 | 未隔离 | 按事件类型选择隔离策略 |
| 取消订阅两次出错 | 不幂等 | 状态标记 |
| 热重载后旧监听器残留 | 未撤销 | 确保热重载路径执行撤销 |
| 事件太多难以追踪 | 缺少观测 | 记录每次分发的事件名与监听器数 |
| 递归触发同一事件 | 无重入保护 | 检测重入并限制深度 |

最后一条值得展开：一个监听器在处理事件时又触发了同一个事件，会造成**无限递归**。防护手段是最大深度限制或重入标记。

## 五、工业界的做法（可照做）

### 5.1 各种"扩展点"的形态

| 形态 | 例子 | 短路语义 |
|---|---|---|
| **事件发射器** | Node 的 `EventEmitter`、DOM 事件 | 无（全部执行） |
| **中间件** | Express、Koa、Redux | **必须调用 `next()`**，否则中断 |
| **插件 hooks** | Webpack、WordPress、Babel | 有"改写值"的语义（waterfall 形态） |
| **拦截器** | gRPC、Axios | 可改写请求/响应 |
| **事件总线** | Kafka、RabbitMQ | 异步、无短路概念 |

**Node 的 `EventEmitter` 与本篇的 waterall 差别最值得注意**：它是广播语义，没有短路——因为它不传递 `next()`。所以"事件"这个词在不同系统里的含义可能完全不同。

判据：**先问"下游能不能阻止上游"，能就是 waterfall，不能就是广播。**

### 5.2 中间件模式的共同形状

Koa、Express、Redux 的中间件都是同一个形状：

```js
async function middleware(context, next) {
  // 前置处理
  await next()   // 交给下一个
  // 后置处理
}
```

这个形状有三个优点：

1. **可以在前后各做一次处理**（环绕式）。
2. 可以决定是否继续（短路）。
3. 可以捕获下游的错误（try/catch 包住 `next()`）。

"环绕式"是最有价值的一点：它让"计时""日志""事务"这类横切关注点可以用一个中间件实现——**这正是 3.6 里延迟分解的实现方式**。

### 5.3 参数与设计起点

| 项 | 推荐 | 依据 |
|---|---|---|
| 事件粒度 | 一个语义时刻一个事件 | 太细则监听器爆炸 |
| 优先级档位 | 3–5 档离散值 | 连续值难推理 |
| 同优先级 | 注册顺序（稳定） | 可复现 |
| 广播载荷 | 共享只读 | 省拷贝，需约定 |
| waterfall 参数 | 值 + `next` | 标准形状 |
| 短路记录 | 必须 | 区分"故意"与"忘记" |
| 监听器上限 | 每个事件 10–20 个 | 超过说明抽象层次有问题 |

### 5.4 一份可落地的实施清单

1. **区分两种事件**：广播与 waterfall 分开 API，不要混用。
2. `next()` 规则：文档写清"不调用即短路"。
3. 短路记录：短路时留下可观测的痕迹。
4. 稳定排序：排序键含注册序号。
5. 优先级离散：3–5 档。
6. 载荷约定：广播共享只读，需要改写用 waterfall。
7. 返回撤销函数：`on()` 返回取消订阅函数，幂等。
8. 失败策略：广播隔离汇总，waterfall 上抛。
9. 重入保护：最大深度限制。
10. 观测：记录事件名与监听器数量，便于发现爆炸。

## 六、学术界的结论

### 6.1 发布订阅与观察者

**观察者模式**与发布订阅的差别常被忽略：

| 模式 | 耦合 | 例子 |
|---|---|---|
| **观察者** | 主体直接持有观察者列表 | DOM 事件 |
| **发布订阅** | 通过中间频道解耦 | 消息队列 |

发布订阅的额外好处：发布者不知道订阅者是谁，**可以跨进程、跨机器**。

对 agent 系统的含义：**内部用观察者（同步、简单），跨进程用发布订阅（异步、解耦）。** 混用会让调试变难（异步链路难以追踪）。

### 6.2 责任链

**责任链模式**的形式化描述与本篇的 waterfall 完全对应：

> 请求沿链传递，每个处理者可以处理、可以传给下一个、也可以终止。

它的形式化性质：链式组合满足**结合律**——$(f \circ g) \circ h = f \circ (g \circ h)$。这意味着"把几个中间件合成一个"不改变语义，为优化提供了依据。

实践含义：**如果两个相邻中间件都不短路，它们可以被合并**（减少调用开销）。

### 6.3 拦截器与横切关注点

**面向切面编程（AOP）** 的关注点是：把日志、事务、鉴权这类横切关注点从业务代码里抽出来。

**中间件/拦截器是 AOP 在函数式与动态语言里最成功的实现**——它不需要语言支持，只需要一个统一的调用约定。

对 agent 系统的意义：延迟计时（3.6）、审批（3.2）、重试（3.1）都适合做成中间件。**它们都是横切关注点。**

### 6.4 插件系统的架构研究

对插件生态（浏览器扩展、IDE、构建工具）的研究给出几条经验：

| 结论 | 含义 |
|---|---|
| **扩展点数量与生态规模相关** | 点太少没人能做，太多难以维护 |
| **短路语义最容易出错** | 插件作者常忘记继续 |
| **版本化是最大难题** | 宿主 API 变化会破坏插件 |
| **沙箱是必需** | 第三方插件不可信（见 3.2） |

第二条与 3.3 直接对应：**"忘记调用 `next()`"是插件系统里最常见的一类 bug。**

## 七、理论：两条可检查性质

### 7.1 短路的判定

$$
\text{短路} \iff \nexists\ \text{next 的调用}
$$

算例验证了两种情况：

| 情况 | 判定 |
|---|---|
| 不调用 `next()` | 短路（后续 1 个未执行） |
| 返回原值但调用 `next()` | **不短路**（`false`，终值 `x!`） |

这条性质是"可检查"的：它只看有没有调用 `next()`，与返回值无关。**因此可以作为 middleware 的单元测试。**

### 7.2 排序的稳定性

$$
\text{优先级相同} \Rightarrow \text{按注册序号排序}
$$

算例验证：优先级从大到小执行（高 → 中 → 低），同优先级保持注册顺序（先注册 → 后注册）。

为什么"稳定"是必要的：缺少它时，**同样的注册代码在不同运行中可能产生不同顺序**，导致偶发失败。稳定排序把"顺序"从实现细节变成可依赖的性质。

ctx.on('before-request', (value, next) => {
  log(value)

## 十、算例

算例实现了本篇的广播与 waterfall 语义。

```powershell
cd D:\dsh-course
node examples/sa28_events.mjs        # 全部函数的运行结果
node examples/test_sa28_events.mjs   # 数字回归断言
```

它做到的事：

- 广播（调用 3 次、载荷完全相同）。
- waterfall 的终值与是否走完。
- **短路**（在第 1 个监听器处终止，后续 1 个未执行）。
- 原样传回不判为短路（返回原值但调用了 `next()`，终值为 `x!`）。
- 执行次序（优先级从大到小）与同优先级的注册顺序。

这一篇只要记住一句：事件分**广播**与 waterfall 两种。waterfall 里不调用 `next()` 就是短路——哪怕你只是忘了，而原样传回只要调了 `next()` 就不算短路。同优先级必须保持注册顺序，否则会出现无法复现的偶发行为。

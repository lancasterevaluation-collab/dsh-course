## 一、为什么工具系统值得单独设计

### 1.1 危险操作被自动批准

一个删除文件的工具没有声明副作用等级，系统按默认值处理，于是它与其他工具一样被自动批准。**问题不在工具本身，而在"没说清它有多危险"。**

### 1.2 输出撑爆上下文

一条命令输出了 20 万行。工具的原始输出全部塞进上下文，直接把窗口占满。

### 1.3 防线被一个路径名绕过

守卫检查"目标路径是否以工作目录开头"。攻击者用 `/work-evil/` 这样一个**以 `/work` 开头但完全无关**的目录，防线失效。

这三件事分别对应：**副作用声明、输出截断、路径判定。**

## 二、工具系统的四件事

| 事 | 决定 | 做错的后果 |
|---|---|---|
| schema 能力 | 模型能否正确构造参数 | 参数错误率高 |
| 副作用分级 | 审批与自动批准的依据 | 危险操作被放行 |
| 输出截断 | 上下文是否被占满 | 窗口爆掉 |
| 结果表示 | 模型能否据此纠错 | 反复失败 |

核心认识：**工具不只是一个函数，它是一份"给模型看的说明书"加一套"给系统用的安全标注"。** 两者都要设计。

## 三、怎么做

### 3.1 schema 能表达的约束

算例给出 5 种 schema 能力：

```
type, required, properties, enum, items
```

| 能力 | 作用 | 例子 |
|---|---|---|
| `type` | 参数类型 | `"type": "string"` |
| `required` | 必填字段 | `"required": ["path"]` |
| `properties` | 字段定义 | 每个字段的类型与说明 |
| **`enum`** | 枚举取值 | `"enum": ["read", "write"]` |
| `items` | 数组元素类型 | `"items": { "type": "string" }` |

为什么 schema 值得认真写：它是**约束模型输出**的第一道手段。`enum` 比在描述里写"只能是 read 或 write"可靠得多——前者是机器可校验的约束，后者是建议。

一条实践判据：**凡是能用 schema 表达的限制，都不要写在描述里。**

### 3.2 副作用分级与保守默认

算例给出 4 个副作用等级，并规定了未声明时的取值：

| 情况 | 取值 |
|---|---|
| 未声明等级 | **3（`external`，保守）** |
| 非法等级名 | **3（保守）** |
| 声明为 `reversible` | 1 |

实现如下。

```js
// 副作用分级：未声明或名称非法时取最保守的一档，不要默认成安全的
export function sideEffectLevel(declared) {
  const levels = { none: 0, reversible: 1, local: 2, external: 3 }
  if (!(declared in levels)) return 3
  return levels[declared]
}
```

保守默认的方向很关键：默认取**最高危险级**，而不是最低。这与守卫的 fail-closed 是同一个原则——配置缺失时不要静默放行。

四级与审批的对应：

| 等级 | 含义 | 审批 |
|---|---|---|
| 0 `none` | 只读 | 自动批准 |
| 1 `reversible` | 可逆写（工作区内） | 自动批准或轻量确认 |
| 2 `local` | 本地数据写 | 首次确认 |
| 3 `external` | 触及外部（网络、第三方、不可逆） | 逐次确认 |

"未声明即第 3 级"的效果：新加的工具默认是"最谨慎"的，直到有人明确声明它更安全。**这让安全成为默认，而不是需要额外争取的东西。**

### 3.3 输出截断：保留头尾并说明丢失

工具输出可能非常长。截断是必需的，但**截断方式决定了信息损失**。

```js
// 截断：保留头部与尾部，并明确写出丢失量占总量的比例
export function truncate(text, limit) {
  if (text.length <= limit) return { text, truncated: false }
  const head = text.slice(0, Math.floor(limit * 0.8))
  const tail = text.slice(text.length - Math.floor(limit * 0.2))
  const dropped = text.length - limit
  return {
    text: `${head}\n...[已省略 ${dropped} / ${text.length} 字符]...\n${tail}`,
    truncated: true,
  }
}
```

算例实测（上限 1000）：

| 项 | 值 |
|---|---|
| 保留 | **800 + 200**（头 80% + 尾 20%） |
| 丢失量 | 1500 |
| 原文总量 | 2500 |
| 截断后含丢失说明 | `true` |
| 截断后含总量 | `true` |
| 未超限时原样返回 | `true` |

为什么保留尾部：**错误信息几乎总在末尾**。只保留头部会让模型看不到失败原因，从而反复重试同一条命令。

为什么必须写清丢失量：模型需要知道"我看的不是全部"。**一个不知道被截断的模型会基于不完整信息下结论。**

截断标记的建议格式：既要给出丢失量，也要给出总量（这样才能算出比例）。

### 3.4 路径防线：为什么字符串比较不管用

算例直接演示了这个缺陷：

| 判定方式 | `/work-evil/x` |
|---|---|
| **裸前缀比较**（`startsWith('/work')`） | **通过（缺陷）** |

为什么这是缺陷：`/work-evil` 与 `/work` 是两个不同目录，但字符串比较无法区分。

正确做法有三层，越往下越可靠：

| 层 | 做法 | 可靠性 |
|---|---|---|
| 字符串 | 比较**规范化后**的路径，且要求**边界对齐**（`/work/` 而不是 `/work`） | 中 |
| 解析 | 解析符号链接（`realpath`）后再比较 | 较高 |
| **内核** | 交给沙箱（Landlock、容器挂载、Seatbelt） | 最高 |

边界对齐的细节：如果用字符串比较，必须在目录后加分隔符——检查 `/work/` 前缀而不是 `/work` 前缀。**但即使这样仍有符号链接、相对路径、大小写等绕过方式**（见 3.2 的绕过清单）。

结论：**路径判定不要自己写，交给内核。** 应用层的字符串比较只作为"早失败"的快速检查，不作为安全边界。

### 3.5 结果表示：让模型能据此决策

工具结果不只是"成功/失败"，它应当让模型知道**下一步该做什么**。

| 结果要素 | 作用 |
|---|---|
| 状态（成功/失败） | 基本判断 |
| **错误类型** | 让模型区分"参数错"与"环境错" |
| **可操作的提示** | 例如"文件不存在，但同名文件在 X" |
| 输出内容 | 任务数据 |
| **是否被截断** | 让模型知道信息完整度 |

"可操作的提示"是最有价值的一项：一个只说"失败"的结果会让模型反复尝试同一件事（见 3.2 的"拒绝要给替代路径"）。

与 2.1 的错误分类呼应：工具错误也应当分类，而不是全部当成"失败"。**分类决定了模型接下来的策略。**

## 四、特殊情况与处理技巧

| 情况 | 为什么 | 处理 |
|---|---|---|
| 输出撑爆上下文 | 未截断 | 保留头尾 + 说明丢失量 |
| 模型看不到错误原因 | 只保留了头部 | 尾部保留 20% |
| 危险工具被自动批准 | 未声明副作用 | 未声明取最高危险级 |
| 路径防线被绕过 | 字符串前缀比较 | 交给内核，或规范化 + 边界对齐 |
| 模型反复调用同一工具 | 错误信息不可操作 | 错误里给替代方案 |
| 工具太多模型选错 | 工具数量过多 | 分层或按需加载（见 7.x） |
| 参数类型对但语义错 | schema 只覆盖结构 | 把语义约束写进描述或 enum |
| 截断后模型误判 | 没标明截断 | 明确写出丢失量与总量 |
| 并发调用同一工具 | 未声明时序约束 | 在契约里写清（见 1.4） |

最后一条与 1.4 的隐式依赖面直接相关：**副作用、时序、资源**这三项如果不写进工具契约，调用方（模型）只能猜。

## 五、工业界的做法（可照做）

### 5.1 工具描述的格式标准

| 标准 | 特点 | 用在哪 |
|---|---|---|
| **JSON Schema** | 通用、表达力强 | function calling 的事实标准 |
| **OpenAPI** | 描述 HTTP 接口 | 把已有 API 暴露给模型 |
| **MCP**（Model Context Protocol） | 工具/资源的统一协议 | 跨应用复用工具 |
| **各家 function calling 格式** | 略有差异 | 提供商特定 |

共同形状：**名字 + 描述 + 参数 schema**。描述是写给模型看的提示，它直接影响模型何时选用这个工具。

### 5.2 工具粒度的设计

这是一个反复讨论的问题：**工具应该做多少事？**

| 粒度 | 优点 | 缺点 |
|---|---|---|
| **粗**（一个工具做很多） | 模型选择简单 | 参数复杂、难以描述、错误难定位 |
| **细**（一个工具做一件事） | 描述清晰、易组合 | 工具数量多、选择变难 |

实践结论（来自工具使用的研究）：

- **参数数量影响正确率**：参数越多，模型构造错误的概率越高。
- 工具数量影响选择正确率：候选过多时选择会变差。
- 描述质量直接影响调用正确率：写清用途与何时不用，比写参数更重要。

推荐做法：**一个工具做一件语义完整的事，参数不超过 4–5 个，并在描述里写"什么时候用"和"什么时候不要用"。**

### 5.3 参数与配置起点

| 参数 | 推荐起点 | 依据 |
|---|---|---|
| 工具输出截断上限 | 进上下文 4000–8000 字符 | 与上下文预算比较（见 3.3） |
| 头尾比例 | 80% / 20% | 错误信息在尾部 |
| 全量输出 | 落盘，不截断 | 可追溯 |
| 工具数量（一次暴露） | 10–20 个 | 选择正确率与描述长度的平衡 |
| 单个工具参数数 | ≤ 5 | 参数越多错误率越高 |
| 描述长度 | 一两句话 + 使用条件 | 过长会占用上下文 |

### 5.4 一份可落地的实施清单

1. **schema 完整**：类型、必填、枚举、数组元素都写清。
2. 副作用声明：每个工具显式声明等级，未声明取最高。
3. 截断策略：头尾保留 + 丢失量说明 + 全量落盘。
4. 错误分类：工具错误归一化并给出可操作提示。
5. 路径与资源：交给沙箱，应用层只做快速检查。
6. 配对校验：工具调用与结果成对，顺序正确（见 2.1）。
7. 幂等标注：在契约里写明是否可以安全重试。
8. 并发标注：写明是否可并发、有无顺序要求。
9. 描述评审：像评审 API 文档一样评审工具描述。
10. 测试：为每个工具写"模型会怎么用错"的用例。

## 六、学术界的结论

### 6.1 工具使用学习

把工具调用能力训练进模型的研究（例如让模型学会在文本中调用外部 API）得出了几条可借用的结论：

- **模型能学会"何时调用"**，但调用正确率对参数数量敏感。
- 提供示例（few-shot）显著提升调用正确率。
- 工具的描述文本会被当作提示的一部分——描述写得含糊会导致误用。

对设计者的直接建议：**把工具描述当成提示工程的一部分来写**，而不是当成文档来写。

### 6.2 API 使用的实证研究

软件工程领域对"人怎么使用 API"的研究发现了几种典型误用模式，它们同样适用于模型：

| 误用模式 | 表现 | 应对 |
|---|---|---|
| **用错方法** | 选了功能相近的另一个 API | 描述里写清区别 |
| **顺序错误** | 未先初始化就调用 | 在描述中写明前置 |
| **漏处理错误** | 不检查返回值 | 结果里明确状态 |
| **参数类型对但语义错** | 传了看似合理但越界的值 | 用 enum 或校验约束 |

共同应对：**把"怎么用错"的预防写进接口本身**，而不是写进文档。

### 6.3 描述即提示

一个被反复验证的现象：**工具的自然语言描述会直接影响模型的调用行为**，包括：

- 描述里的示例会引导参数风格。
- 描述里的措辞影响模型的积极性（"必须"与"可以"差别很大）。
- **描述里的负面说明（"不要用于 X"）与正面说明同样有效**。

工程含义：**工具描述需要与提示词一起做版本管理与效果评估**。改一句描述可能改变整体行为。

### 6.4 最小权限与能力接缝

工具系统是"能力接缝"（见 2.1）的一个实例，因此 1.4 与 3.2 的结论都适用：

- **契约四要素**：前置、后置、不变量、副作用（见 1.4）。
- 默认拒绝：未声明的危险级别取最高（见 3.2）。

特别值得强调的一条：**工具的权限不应由"谁在调用"决定，而应由"这次调用带了什么凭证"决定**（能力安全，见 3.2）。这样注入攻击无法通过"冒充调用者"来获取权限。

## 七、理论：两个可检查的性质

### 7.1 截断的信息损失

保留比例 $k$（算例里头尾共 1000，原文 2500）：

$$
\text{保留率} = \frac{k}{n} = \frac{1000}{2500} = 40\%
$$

**关键不在保留多少，而在"是否标明丢了什么"**。算例验证了两个布尔性质：截断后同时含丢失说明与总量。

可检查的判据：**任何截断后的文本，都必须能从中算出丢失比例。** 否则模型无法判断信息完整度。

### 7.2 前缀匹配的缺陷

正确的路径包含关系应满足**目录边界**：

$$
p \in \text{dir} \iff p = \text{dir} \lor p \text{ 以 } \text{dir} + \text{分隔符 开头}
$$

裸前缀比较缺了分隔符这一项，于是 `/work-evil/x` 被判为在 `/work` 内。

算例验证：裸前缀比较对 `/work-evil/x` 返回"通过"（缺陷）。

**更严格地说**，即使加上分隔符，符号链接、相对路径、大小写仍然能绕过（见 3.2）。所以这条性质只用于"快速失败"，安全边界必须由内核提供。

## 九、练习

### 第一题：修三个工具定义

实现如下。

```json
{"name": "delete", "description": "删除文件", "parameters": {"type": "object", "properties": {"path": {"type": "string"}}}}
{"name": "run", "description": "运行命令", "parameters": {"type": "object", "properties": {"cmd": {"type": "string"}, "cwd": {"type": "string"}, "env": {"type": "string"}, "timeout": {"type": "number"}}}}
{"name": "get", "description": "获取数据", "parameters": {"type": "object", "properties": {"url": {"type": "string"}}}}
```

要求：

- 逐个指出问题（schema 缺失、副作用未声明、描述含糊、参数过多）。
- 给出改进后的定义，并说明每个改动的作用。
- 为 `delete` 设计结果表示：至少包含 4 个要素。

---

### 第二题：设计截断策略

场景：一个运行测试的工具，输出可能是 200 行总结，也可能是 5 万行日志（含末尾的失败原因）。

要求：

- 给出截断上限、头尾比例，并说明依据。
- 说明当"失败原因在中间"时这个策略的问题，以及如何改进。
- 设计一个"全量落盘 + 截断进上下文"的完整方案，说明模型如何获取被截断的部分。

### 第三题（进阶）：为工具设计安全标注

要求：

- 给 6 个典型工具（读文件、写文件、执行命令、发 HTTP、发邮件、删记录）分别标注副作用等级，并说明依据。
- 说明每个等级的审批方式，以及如何避免审批疲劳（见 3.2 的数学模型）。
- 设计一个"凭证"方案，使工具权限不依赖调用者身份（见 6.4）。

## 本篇新词

- 会话日志 指一次会话里全部事件的追加序列。它是本课程的权威状态。
- 派生视图 指从日志算出的数据，例如给模型的消息数组与用量统计。它的判据是删掉重算结果不变。
- 可重建 指存在一个纯函数，从日志算出当时的请求内容。
- 配对（pairing） 指每个工具调用恰好有一条对应的结果。它是消息格式的硬约束。
- 收敛（convergence） 指循环在有限步内结束。它不是模型的性质，而是循环必须提供的保证。
- 步数上限 指兜底的步数边界，取值来自正常任务的步数分布。
- 水位线（watermark） 指"已经应用到哪一条"的记录。
- 恢复（resume） 指从日志重建出可以继续运行的会话，它还要回答"上次停在哪里"。
- NDJSON 指一行一条 JSON 的文本日志格式。

## 一、【设计原因】

### 1.1 缺陷一：重启之后系统忘了刚才发生了什么

进程重启后模型对上一轮说过的话一无所知。原因通常不是没写持久化，而是持久化的对象选错了：它存的是"当前的消息数组"，而消息数组是派生结果，压缩、截断与工具结果形态的变化都会让它与事实不符。

更隐蔽的一种是存了但存不全：日志里只有 user 与 assistant 消息，没有工具定义、系统提示与压缩点。重启后重建出的输入与当时的输入不同，而模型的行为差异会被归因为"模型不稳定"。

### 1.2 缺陷二：请求被拒绝，理由是不合法的消息序列

消息格式有一条硬约束：每条 assistant 的工具调用都必须有对应的结果，数量与顺序都要对上。而实现里总有一些路径会漏掉结果：被守卫拦截的、被取消的、实现抛异常的。

它们的共同点是"流程中途退出了，但没有产出结果"，而模型的下一次请求会因为序列不合法被拒。

这个约束不能靠"记得配对"来保证，因为需要记得的地方会随功能增加而增加。

### 1.3 缺陷三：循环不收敛

提示词写错或工具返回异常时，模型反复请求同一个工具，而没有步数上限的循环会一直转下去。表现是任务卡住不动，或者账单短时间内增长很快。

收敛保证必须由循环提供，而且要有两层：正常终止（模型不再请求工具）与兜底上限。只有前者时，一次行为异常就会让程序永远运行。只有后者时，正常任务会在达到上限时被截断。

### 1.4 缺陷四：无法解释"为什么它当时那么决定"

用户问"为什么它上一次把那个文件删了"，而答案需要复原当时的完整输入：系统提示、可用工具、历史消息、中间有没有压缩。四样里缺任何一样，答案就只能是推测。

### 1.5 由此确定的设计目标

1. 会话日志是唯一真相源，其余一切都是它的派生。
2. 进入过请求的东西全部进日志：消息、工具定义、系统提示、压缩点。
3. 工具调用的三种结局走同一个出口，配对由结构保证。
4. 循环有两层终止条件，并在结束时记录原因。
5. 未知事件默认拒绝读取，需要放宽时逐条声明可忽略。

**本节要点**

- 把派生结果当真相源是重启丢历史的根因。
- 配对遗漏来自"中途退出但没有结果"的路径。
- 收敛是循环的职责，不是模型的职责。
- 无从复原输入就无法解释行为。
- 五条目标：日志为源、可见必记、单一出口、双层终止、默认拒绝。

## 二、【直觉】

### 2.1 账本与报表

一家店的账本是唯一权威，而报表是从账本算出来的。

- 报表可以随时重算，算出来的结果每次都一样。
- 账本一旦记下就不再修改，错了就再记一条冲正。
- 如果只保存报表，那么"当时发生了什么"就永远无法还原。

::: keypoint 反直觉点
**"当前的消息数组"是报表，不是账本。** 很多实现把它当作要保存的对象，于是压缩、截断、工具结果形态的每一次变化都会让它与事实不符。正确的做法是保存事件，让消息数组随时可以被重算。
:::

### 2.2 两条必须对上

一次工具调用与它的结果必须成对出现，像收据与存根。

- 模型请求调用三次，就必须有三条结果。
- 被拒绝的那次也要有结果，内容写着"被拒绝"。
- 少一条，对方就不受理这份材料。

最后一条是这套机制的硬性之处：它不是"最好配上"，而是"不配上就无法继续"。

### 2.3 一个数字直觉

设每步新增约 500 token，一次 $n$ 步任务的总输入约为

$$
500 \times \frac{n(n+1)}{2}.
$$

- $n = 10$ 时约 27500 token。
- $n = 20$ 时约 105000 token。

**步数翻倍，总输入接近四倍。** 这条关系给步数上限提供了经济学依据，也是第 3 卷上下文压缩之所以是必需而非优化的原因：压缩把每步的输入规模从随步数增长降到常数。

**本节要点**

- 账本只追加，报表可重算。
- 调用与结果必须成对，被拒绝的也要成对。
- 成本与步数近似平方关系。

## 三、【严格】

### 3.1 定义

::: theorem 定义 2.7.1（会话日志）
会话日志是一个事件序列

$$
L = (e_1, e_2, \dots, e_n),
$$

每条事件带**单调递增且唯一**的顺序号 $\mathrm{seq}(e_i) = i$。日志是**只追加**的：已写入的事件不被修改，也不被删除。
:::

::: theorem 定义 2.7.2（派生视图）
一个派生视图是一个纯函数

$$
\mathrm{derive}: L \to D,
$$

其中 $D$ 是某个用途的数据。**判据**：$\mathrm{derive}(L)$ 可以被删掉并从 $L$ 重算而不改变结果。
:::

::: theorem 定义 2.7.3（可重建）
设一次请求的全部内容为 $R$。称日志 $L$ **可重建** $R$，当且仅当存在纯函数 $\rho$ 使

$$
\rho(L) = R.
$$

"模型可见的必须可重建"这条不变量要求：**对每一次实际发出的请求，都存在这样的 $\rho$。**
:::

::: theorem 定义 2.7.4（配对）
设一次循环里模型给出的工具调用集合为 $C$，日志中对应的结果集合为 $R_{\text{tool}}$。配对要求

$$
|C| = |R_{\text{tool}}| \ \land\ \{c.\mathit{id}\} = \{r.\mathit{callId}\}.
$$

被拒绝、被取消与失败的调用**同样计入** $C$，也必须产出结果。
:::

::: theorem 定义 2.7.5（收敛）
循环的终止条件有两层：

$$
\text{终止} \iff (\text{本轮无工具调用})\ \lor\ (\text{步数} = \mathit{maxSteps}).
$$

第二层是兜底，且**达到上限时必须以失败结束并记录原因**。
:::

::: theorem 定义 2.7.6（水位线与写入顺序）
水位线 $w$ 是"已应用到第 $w$ 条"的记录。它与它所声明的进度必须满足

$$
\text{应用}(e_1..e_w) \ \prec\ \text{更新}(w),
$$

即**先应用、再更新水位线**。
:::

### 3.2 命题

::: theorem 命题 2.7.1（可重建的充分必要条件）
日志可重建请求，当且仅当它记录了全部进入请求的内容：消息序列、工具定义、系统提示与改变派生规则的压缩点。

**证明.**
（充分性）给定这四类记录，$\rho$ 可以依次做：取最后一个压缩点之后的事件（若无则取全部），按压缩点规则展开为消息，取最近一次工具定义变化与系统提示变化作为当前值。每一步都只依赖 $L$，故 $\rho$ 存在。
（必要性）若缺少某一类，构造反例：缺少工具定义时，取两个工具集不同而消息序列相同的会话，它们的请求不同而日志相同，故不存在 $\rho$ 区分它们。

↓ **为什么能这么写？** $\rho$ 的存在性等价于"所有影响输出的输入都在日志里"。

$\blacksquare$

::: keypoint 于是"日志只记消息"是不成立的
**工具定义与系统提示都会随模式与配置变化**，因此它们的变化也必须作为事件记录。缓解体积的办法是只在变化时记一条，而不是每轮记一遍。
:::

::: theorem 命题 2.7.2（配对由单一出口保证）
若所有工具执行的结局都经由同一个产出结果的函数，则配对数恒等成立。若存在任一条"跳过该调用"的分支，则存在漏配对的执行路径。

**证明.** 第一种：$C$ 中每个元素都被传给了出口函数，而出口函数对每个输入恰好产出一条结果，故 $|R| = |C|$。第二种：设某条路径在到达出口前返回，则它对应的调用没有结果，$|R| = |C| - 1$，配对不成立。

↓ **为什么能这么写？** 计数守恒需要"每个元素恰好经过一次产出"。

$\blacksquare$

**数值**：三种结局（正常、失败、被拦截）共用一个出口时，$|C| = 3$ 必有 $|R| = 3$。存在跳过分支时最坏情况是 $|R| = 2$。

::: theorem 命题 2.7.3（成本与步数的二次关系）
设每步新增 $m$ 个 token，则 $n$ 步任务的总输入为

$$
S(n) = m \cdot \frac{n(n+1)}{2} = \Theta(n^2).
$$

**证明.** 第 $i$ 步的输入包含前 $i$ 步的全部内容，即 $i \cdot m$ 个 token。求和即得。

↓ **为什么能这么写？** 每步都重传全部历史（与 2.1 命题 2.1.2 同源）。

$\blacksquare$

**数值**：$m = 500$ 时 $S(10) = 27500$，$S(20) = 105000$（后者是前者的 $3.82$ 倍）。

::: theorem 命题 2.7.4（水位线的可用写入顺序唯一）
先更新水位线再应用会在崩溃时留下空洞，先应用再更新只会重复应用。

**证明.** 空洞：水位线已推进到 $w$，而应用只完成到 $k < w$，恢复时从 $w$ 之后开始，区间 $(k, w]$ 的记录永不应用，故历史缺失且无人知道。重复：应用完成而水位线未推进，恢复时从旧位置重做已完成的区间。若应用是幂等的（派生视图可重算），重复不改变结果。

↓ **为什么能这么写？** 两种做法的崩溃后果不对称：一个丢数据，一个重复做可重复的事。

$\blacksquare$

::: keypoint 与先写日志同源的推理
**先做可重复的那一步。** 这条规则在 1.5 的原子写、3.5 的恢复里反复出现，因此值得单独记住。
:::

::: theorem 命题 2.7.5（默认拒绝是唯一不依赖事件语义的策略）
跳过一条未知事件安全，当且仅当该事件可忽略。由于"未知"意味着无法判定其可忽略性，默认跳过会在存在不可忽略事件时产生静默错误。

**证明.** 设读取方不认识事件类型 $t$。判定 $t$ 是否可忽略需要知道 $\mathrm{derive}(L)$ 与 $\mathrm{derive}(L \setminus \{t\})$ 是否相等，而这需要理解 $t$ 的语义。读取方不认识 $t$，故无法判定。默认跳过时，若 $t$ 不可忽略，派生结果错误且无任何信号。默认拒绝时，错误立刻可见。

↓ **为什么能这么写？** 判定能力以理解语义为前提，而"未知"正是缺少这个前提。

$\blacksquare$

::: keypoint 逐条声明是唯一的放宽方式
**新增事件类型时必须回答一次"不认识它的读方该怎么办"。** 这个成本是刻意的，它把兼容性从一个全局策略变成逐事件的判断。
:::

::: theorem 命题 2.7.6（恢复的判定依据是幂等性）
若日志尾部是"调用开始而无结果"，则恢复的正确行为由该调用是否幂等决定：幂等则重放，非幂等则标记为结果未知。

**证明.** 重放会再次执行该调用。若调用幂等，两次执行的效果与一次相同，故重放安全且能得到缺失的结果。若调用非幂等，重放产生第二次效果（例如重复扣费），其代价可能高于缺失结果，故只能标记并把决定交给上层。

↓ **为什么能这么写？** 恢复动作本身要满足"不该产生新的副作用"。

$\blacksquare$

### 3.3 本节要点

**本节要点**

- 日志只追加，带单调唯一的顺序号（定义 2.7.1）。
- 派生视图是纯函数，可删可重算（定义 2.7.2）。
- 可重建要求存在从日志到请求的纯函数（定义 2.7.3）。
- 配对要求调用与结果数量、标识一一对应（定义 2.7.4）。
- 收敛有两层终止条件，上限处必须记录原因（定义 2.7.5）。
- 水位线先应用后更新（定义 2.7.6）。
- 可重建的充要条件是四类内容全部入日志（命题 2.7.1）。
- 配对由单一出口保证（命题 2.7.2）。
- 成本与步数近似平方（命题 2.7.3）。
- 水位线的可用顺序唯一（命题 2.7.4）。
- 默认拒绝是唯一不依赖语义的策略（命题 2.7.5）。
- 恢复的判定依据是幂等性（命题 2.7.6）。

## 四、【回到直觉】

- **定义 2.7.1 说的**：账本只往后写，写下的那一行不再改。
- **定义 2.7.2 说的**：报表随时可以重算，且每次算出来一样。
- **定义 2.7.3 说的**：要能回答"它当时看到了什么"，就得把当时看到的东西都记下来。
- **定义 2.7.4 说的**：三次调用就要有三条回执，被拒绝的那次也要有。
- **定义 2.7.5 说的**：正常结束是它不再要工具，兜底结束是步数用尽，而后者必须写清原因。
- **定义 2.7.6 说的**：先把活干完，再推进里程表。
- **命题 2.7.1 说的**：只记消息不够，工具清单与系统提示也要记。
- **命题 2.7.2 说的**：所有结局都从一个门出去，数量就不会少。
- **命题 2.7.3 说的**：十步任务的总输入约 27500 token，二十步约 105000。
- **命题 2.7.4 说的**：先推里程表再干活，崩溃后会丢掉一段没人知道的历史。
- **命题 2.7.5 说的**：不认识的事件只能拒绝，因为跳过它是否会出错本身就判不了。
- **命题 2.7.6 说的**：恢复时要不要重做那一步，取决于重做一次会不会产生第二次效果。

**本节要点**

- 账本只追加。
- 报表可重算。
- 可见的必须记。
- 调用与结果成对。
- 两层终止。
- 先干活后记进度。

## 五、【工具箱】

### 5.1 该不该进日志

问两个问题，有一个是"是"就进日志。

1. 它进入请求了吗？
2. 它改变派生规则了吗？

**据此**：消息、工具定义、系统提示、压缩点进日志。用量统计、耗时、当前步数由日志派生。

### 5.2 配对检查

1. 消息数组里 assistant 的工具调用数等于 tool 结果数吗？
2. 被拦截的路径也走同一个出口吗？
3. 出口函数对失败也产出非空内容吗？

**可写成运行时断言**：每一轮结束时校验一次，把"下一轮请求被拒"提前到"这一轮立刻失败"。

### 5.3 收敛设置

| 项 | 做法 |
|---|---|
| 正常终止 | 本轮无工具调用 |
| 兜底上限 | 取正常任务步数分布的高分位数乘安全系数 |
| 达到上限 | 以失败结束，并记录原因 |

**上限的作用不是省时间，而是把不可收敛变成可观测的失败。**

### 5.4 恢复判定

| 日志尾部 | 处理 |
|---|---|
| 完整的一轮 | 直接继续 |
| 调用开始无结果，且该调用幂等 | 重放该调用 |
| 调用开始无结果，且该调用非幂等 | 标记结果未知，交给上层决定 |

### 5.5 日志的物理形态与检查

采用 NDJSON：一行一条事件，行内是完整 JSON。

| 目的 | 命令 |
|---|---|
| 看尾部是否完整 | `Get-Content -Tail 5 <日志>` |
| 数某类事件 | `rg -c '"type":"session/tool-result"' <日志>` |
| 检查顺序号连续 | `rg -o '"seq":\d+' <日志>` |

**解析失败即停止读取**，因为只追加的日志里不完整只可能出现在尾部。

**本节要点**

- 该不该进日志看两条：进请求、改派生规则。
- 配对可以写成每轮结束时的断言。
- 上限来自分布，达到时记录原因。
- 恢复按幂等性决定重放或标记。
- NDJSON 的尾部不完整可被识别。

### 7.2 事件段与日志段

事件段定格式，日志段负责追加与读取。

```js
// 定义 2.7.1：只追加的日志，顺序号由日志本身决定
export class SessionLog {
  #events = []
  #brokenTail = false

  /** @returns 当前日志的事件数组（副本） */
  get events() { return [...this.#events] }

  /** @returns 是否在读取时遇到过不完整的尾行 */
  get brokenTail() { return this.#brokenTail }

  /**
   * 追加一条事件。
   * @param event 形如 `{ type, ...payload }`
   * @returns 分配的顺序号
   */
  append(event) {
    const seq = this.#events.length + 1
    this.#events.push({ seq, ...event })
    return seq
  }

  /**
   * 从日志文本读回事件，遇到解析失败即停止。
   * @param text NDJSON 文本
   * @returns 本次读回的事件数
   */
  readFrom(text) {
    let count = 0
    for (const line of text.split('\n')) {
      if (line.trim() === '') continue
      try {
        const e = JSON.parse(line)
        this.#events.push(e)
        count++
      } catch {
        // 只追加的日志里不完整只可能出现在尾部，因此解析失败即停止
        this.#brokenTail = true
        break
      }
    }
    return count
  }
}
```

### 7.3 派生态段

派生视图是纯函数，输入事件数组，输出该用途的数据。

```js
// 定义 2.7.2：派生视图——压缩点之后的事件加上摘要本身
export function deriveMessages(events) {
  const compactions = events.filter((e) => e.type === 'session/compaction')
  const last = compactions[compactions.length - 1]
  const from = last ? events.indexOf(last) : 0
  return events.slice(from).flatMap((e) => {
    if (e.type === 'session/user') return [{ role: 'user', content: e.text }]
    if (e.type === 'session/assistant') return [{ role: 'assistant', content: e.text, toolCalls: e.toolCalls ?? [] }]
    if (e.type === 'session/tool-result') return [{ role: 'tool', toolCallId: e.callId, content: e.content }]
    if (e.type === 'session/compaction') return [{ role: 'user', content: `（此前历史的摘要）${e.summary}` }]
    return []
  })
}
```

### 7.4 断言段与循环段

断言段把"可重建"变成每轮结束时的检查，循环段用两层终止条件收敛。

```js
// 命题 2.7.2：调用数与结果数必须相等，被拦截的也计入
export function checkPairing(events) {
  const calls = events.filter((e) => e.type === 'session/assistant').flatMap((e) => e.toolCalls ?? [])
  const results = events.filter((e) => e.type === 'session/tool-result')
  const resultIds = new Set(results.map((e) => e.callId))
  const missing = calls.filter((c) => !resultIds.has(c.id)).map((c) => c.id)
  return { calls: calls.length, results: results.length, missing, ok: calls.length === results.length && missing.length === 0 }
}
```

循环用一个出口产出结果、用两层终止条件结束。

```js
// 定义 2.7.5 / 命题 2.7.2：循环的两层终止，三种结局走同一出口
export async function runTurn(session, provider, tools, maxSteps = 4) {
  for (let step = 1; step <= maxSteps; step++) {
    const res = await provider.respond(deriveMessages(session.events))
    session.append({ type: 'session/assistant', text: res.content, toolCalls: res.toolCalls })
    if (res.toolCalls.length === 0) {
      session.append({ type: 'session/end-turn', step, reason: 'no-tool-calls' })
      return { ok: true, steps: step, reason: 'no-tool-calls' }
    }
    for (const call of res.toolCalls) {
      const outcome = await executeOne(call, tools)
      session.append({ type: 'session/tool-result', callId: call.id, ok: outcome.ok, content: outcome.content })
    }
  }
  session.append({ type: 'session/end-turn', step: maxSteps, reason: 'step-limit' })
  return { ok: false, steps: maxSteps, reason: 'step-limit' }
}
```

### 9.2 失败模式

**（1）检查放在装载期（L9 位置放错）。** 可重建只在测试里校验过，而生产环境的工具集与提示不同。表现是"生产上的行为在本地无法复现"。修正：把断言做成可开关的运行时检查，并在关键路径开启。

**（2）前提会变（L9）。** 命题 2.7.2 的计数守恒以"每个调用恰好传给出口一次"为前提。若某处重试了工具执行而没有重新走出口，计数关系不再成立。

**（3）派生结果被当成真相源。** 重启后消息数组与事实不符。

**（4）日志只记消息。** 工具定义或系统提示变化后无法重建当时的输入。

**（5）配对靠纪律而非结构。** 新增一种拦截机制就多一条漏配对的路径。

**（6）失败的工具结果内容为空。** 某些实现会因此拒绝整个请求。

**（7）没有步数上限。** 一次模型异常会导致无限循环。

**（8）达到上限时静默停止。** 日志里看不出为什么结束。

**（9）未知事件被跳过。** 派生结果静默出错，而"能读"是假象。

**（10）先更新水位线再应用。** 崩溃后留下一段无人知道缺失的历史。

**本节要点**

- 决策表覆盖 12 种情形。
- 失败模式十条，前两条是位置放错与前提会变。
- 最隐蔽的是"未知事件被跳过"——它看起来是兼容，实际是静默错误。

## 十二、系统影响回溯

**影响一："可重建"决定系统在出问题时能否被解释。** 它的量化形态是"一次诊断需要回溯多少轮"，而它直接取决于日志记录了什么。

**影响二：循环的每一步都会放大成本，而成本与步数的关系是超线性的。** 十步任务不是一次调用的十倍，而接近五十倍（按累积和估算）。这解释了为什么第 3 卷的上下文压缩是必需而非优化。

**影响三：事件格式的演进成本随系统存活时间上升。** 这与 2.6 的配置覆盖是同一类问题的两端：配置回答新旧输入如何共存，事件格式回答新旧数据如何共存。事件的特殊之处在于它无法被重新生成。

**一处需要修正的预判。** 旧稿把本篇定位成"第 2 卷最后一篇"，读完之后要补一句更准确的定位：**它是后面全部机制的审查基准**。第 3 卷的每一篇都在引入一个新机制的同时威胁本篇的一条不变量——重试会重放请求，守卫会拦下调用，压缩会改写历史，取消会中断循环，恢复要重建状态。因此本篇的产物不是"一个模块"，而是一组用来审别人的判据。

**通向下一步的桥。**

第 2 卷到此收口：系统会说话（2.1）、能做事（2.2）、有持有者（2.3）、能被介入（2.4）、能隔离（2.5）、能被装配（2.6）、能把做过的事记下来并停下来（2.7）。

而它现在只能跑一次。第 3 卷要处理的是"跑很多次、跑很久、跑坏之后还能继续"：重试、守卫、压缩、进程、持久化、可观测。每一篇都会先问一句"这会不会破坏可重建"，而那个问题的答案就写在本篇。

| 看到一个没有上限的循环 | 加兜底，并在达到时记录原因 |
| 想用时间戳当顺序号 | 时钟会回拨，顺序号由日志本身分配 |
| 要新增一个事件类型 | 先回答"不认识它的读方该跳过还是拒绝" |
| 要更新水位线 | 先把活干完，再推进它 |
| 恢复时看到"调用开始无结果" | 按幂等性决定重放还是标记 |
| 循环步数很多、账单增长很快 | 那是成本与步数的平方关系，压缩是必需 |

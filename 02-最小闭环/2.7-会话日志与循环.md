# 2.7 会话日志与循环

> **这一篇讲什么**：会话日志是 agent 的唯一真相源，循环是它的驱动。两者共同决定两件事：模型看到什么、系统在什么时候停。本篇给出三条会决定系统能否正常工作的纪律：每个调用都必须有结果（哪怕被拦截或抛异常）、压缩点本身也要记成一条、以及收敛由"模型不再请求工具"判定。

## 一、为什么日志与循环是一件事

### 1.1 模型看到的内容与日志不一致

循环在拼装请求时加了日志里没有的内容（例如临时插入的提示）。**于是"重放日志"得不到同样的请求**，问题无法复现。

### 1.2 一个调用没有结果

一个工具调用被守卫拦截了，系统直接跳过它。**日志里留下了一条悬空的调用**，模型在下一轮看到它，不知道该期待什么。

### 1.3 循环不收敛

模型反复请求同一个工具，循环没有终止条件，**一直跑到上下文耗尽为止**。

这三件事分别对应：**模型可见即已记录、配对完整性、收敛条件。**

## 二、日志是真相源，循环是驱动

| 概念 | 角色 | 关系 |
|---|---|---|
| **会话日志** | 唯一真相源（权威状态） | 由事件组成，只追加 |
| **派生消息** | 从日志计算出的模型输入 | 可重建（派生状态） |
| **循环** | 驱动：请求 → 执行 → 追加 | 每一步都产生事件 |

关键关系：**循环不直接修改"消息"，它只追加事件。消息是从事件派生出来的。**

这条分离的价值：**任何时候都可以从日志重建"模型当时看到了什么"**。这正是排障与重放的基础。

## 三、怎么做

### 3.1 追加与顺序号

日志的基本操作是**追加**，每条事件带一个单调递增的顺序号。

```js
// 追加：只往末尾加，顺序号单调递增，不依赖时钟
export function append(log, event) {
  const seq = log.events.length === 0 ? 1 : log.events.at(-1).seq + 1
  log.events.push({ seq, ...event })
  return seq
}
```

算例实测：追加 3 条事件后，顺序号是 **`1, 2, 3`**。

为什么不用时间戳：**时钟会回拨**（见 1.5 的同一结论）。单调序号是唯一可靠的顺序来源。

为什么只追加：**任何时刻的前缀都是一个合法状态**（见 3.5 的持久化）。修改历史会让重放不再可复现。

### 3.2 尾部不完整

写入过程中崩溃会在日志末尾留下半条记录。**处理方式不是拒绝启动，而是截断**。

```js
// 读回：跳过尾部不完整的记录，保留前面全部有效内容
export function readLog(lines) {
  const events = []
  let truncated = false
  for (const line of lines) {
    try {
      events.push(JSON.parse(line))
    } catch {
      truncated = true
    }
  }
  return { events, truncated }
}
```

算例实测：

| 项 | 值 |
|---|---|
| 尾部不完整行时的读回条数 | **3** |
| 是否检测到不完整的尾部 | **`true`** |

两个要点：**前面的记录全部保留**（不因为末尾坏而丢弃），并且明确报告发生过截断（否则数据丢失是静默的）。

### 3.3 派生与压缩点

派生是"从事件算出模型输入"。压缩（见 3.3）会让派生变复杂：

| 情况 | 派生出的消息数（算例） |
|---|---|
| 无压缩 | **3** |
| 有压缩点 | 压缩点之后 **2** 条 |

关键点：**压缩点把自己算作一条摘要消息**（算例里是 `true`）。

为什么这一点重要：**压缩不是"删掉前面的内容"，而是"用一条摘要替换它们"。** 那条摘要本身是一条消息，占用位置，参与后续派生。

**如果压缩点不被记成一条**，就会有两个问题：

1. **重放时不知道前面被压缩成了什么**。
2. 模型看到的与日志不一致（违反了"模型可见即已记录"）。

实现建议：压缩动作**本身也是一个事件**（记录"在某个位置插入了一条摘要"），这样日志仍然是完整真相源。

### 3.4 配对完整性：每个调用都要有结果

这是本篇最容易被违反、后果最难查的一条纪律。

规则：**每一个工具调用都必须有一条对应的结果消息**，无论它是成功、失败、被拦截，还是抛了异常。

```js
// 配对检查：每个调用都必须有结果，否则派生出的消息非法
export function pairingComplete(events) {
  const calls = new Set()
  const results = new Set()
  for (const event of events) {
    if (event.type === 'tool-call') calls.add(event.id)
    if (event.type === 'tool-result') results.add(event.id)
  }
  return [...calls].every((id) => results.has(id))
}
```

算例实测：

| 项 | 值 |
|---|---|
| 调用数与结果数 | **3 / 3** |
| 配对是否完整 | **`true`** |
| **被拦截的调用是否产出结果** | **`true`** |
| **抛异常的调用是否产出结果** | **`true`** |

最后两行是本篇的核心：

- **被拦截**（守卫拒绝、用户拒绝审批）→ 必须产出一条结果，内容是"这次调用被拒绝了"。
- 抛异常（工具内部错误）→ 必须产出一条结果，内容是错误信息。

为什么不能"跳过"：因为模型已经看到了自己对工具的请求。**如果下一轮没有对应结果，对话在结构上就是不完整的**——模型会困惑，或者开始重复请求。

这条与 2.1 的消息位置四类直接相关：**tool 消息必须紧跟请求它的 assistant 消息。** 缺少结果就破坏了这个配对。

### 3.5 收敛判断

循环必须有明确的终止条件，否则会一直跑到上下文耗尽。

算例实测：

| 项 | 值 |
|---|---|
| 正常终止在第几步 | **2** |
| 正常终止的原因 | **`no-tool-calls`** |

收敛条件：**这一轮模型的输出里没有工具调用 → 回合结束。**

为什么用这个条件：它是**模型自己给出的信号**。模型在能给出最终答案时就不再请求工具。

其他可能的终止条件（都必须有）：

| 条件 | 触发时 |
|---|---|
| `no-tool-calls` | 正常结束 |
| 最大步数 | 防止无限循环 |
| 上下文超限 | 触发压缩或终止（见 3.3） |
| 用户中断 | 立即停止 |
| 预算耗尽 | 成本或时间超限 |

"最大步数"是必需品而不是可选项：**它是唯一能防止失控循环的硬性兜底。** 与 3.1 的重试预算、3.2 的审批上限一样，任何循环都要有硬上限。

终止原因要记录：算例里的 `no-tool-calls` 就是一个**结构化的终止原因**。它让"为什么停了"可查询，而不是靠日志推断。

## 四、特殊情况与处理技巧

| 情况 | 为什么 | 处理 |
|---|---|---|
| 调用没有结果 | 被拦截或异常时跳过 | 任何情况都产出一条结果 |
| 重放得不到同样的请求 | 循环里加了日志外内容 | 模型可见的内容必须已记录 |
| 日志末尾半条 | 写入时崩溃 | 截断尾部并报告 |
| 压缩后无法重放 | 压缩没记成事件 | 压缩动作也写成一条事件 |
| 无限循环 | 无硬上限 | 最大步数兜底 |
| 停止原因不明 | 未记录终止原因 | 结构化记录原因 |
| 并发写日志 | 无互斥 | 单写者 + 追加 |
| 日志过大 | 无归档 | 按窗口归档（见 1.5） |

"模型可见即已记录"这条原则值得单独强调：它是本篇与 3.3、3.5、7.x 的共同基础。**任何进入模型请求的内容，都必须能从日志重建。** 否则重放、审计、评测全部失去依据。

## 五、工业界的做法（可照做）

### 5.1 事件溯源的工程形态

| 概念 | 做法 | 在本篇的对应 |
|---|---|---|
| 事件存储 | append-only，不可修改 | 会话日志 |
| 快照 | 定期压缩历史 | 压缩点 |
| 投影 | 从事件算出读模型 | 派生消息 |
| 重放 | 从头或从快照重建 | 会话重放 |
| 版本化 | 事件结构演进（见 3.5） | 会话格式版本 |

"快照 + 尾随事件"是标准做法：**恢复时载入最近快照，再重放其后的事件**（见 3.5 的检查点）。

会话日志与它完全同构：压缩点就是快照，之后的事件就是尾随事件。

### 5.2 循环的工程参数

| 参数 | 推荐起点 | 依据 |
|---|---|---|
| 最大步数 | 10–30 | 步数与任务复杂度相关，超过多半是循环了 |
| 单步超时 | 见 2.1 | 模型 + 工具的时间 |
| 回合总预算 | 见 3.6 | 时间与成本 |
| 同工具连续调用上限 | 3–5 次 | 超过说明在原地打转 |
| 无进展检测 | 连续 N 步无新信息 | 提前终止 |
| 终止原因 | 结构化枚举 | 便于统计 |

"同工具连续调用上限"很实用：模型有时会反复调用同一个工具（例如反复读同一个文件）。**这类循环用总步数兜底太晚，用"同一工具连续次数"更早发现。**

### 5.3 会话日志的存储

| 形态 | 优点 | 代价 |
|---|---|---|
| 单文件 append | 简单、顺序写快 | 并发写要互斥 |
| 每会话一文件 | 隔离好 | 文件数多 |
| 数据库行 | 可查询 | 写入有事务开销 |
| 对象存储 | 便宜、容量大 | 延迟高 |

推荐起点：**每会话一个 append-only 文件 + 定期检查点**。它同时满足"顺序写快""易重放""可归档"三个要求。

### 5.4 一份可落地的实施清单

1. **追加写**：只往末尾加，每条带单调序号。
2. 尾部截断：读回时跳过坏记录并报告。
3. 派生分离：消息由事件派生，循环不直接改消息。
4. 模型可见即已记录：任何进入请求的内容都要有对应事件。
5. 配对完整性：被拦截、抛异常都产出结果。
6. 压缩即事件：压缩点记成一条摘要事件。
7. 收敛条件：`no-tool-calls` + 最大步数 + 预算上限。
8. 终止原因：结构化记录。
9. 检查点：定期压缩历史，保留两份。
10. 测试：配对完整性、尾部截断、收敛三条各写断言。

## 六、学术界的结论

### 6.1 状态机复制与确定性重放

分布式系统的经典方法（见 1.5）：**从相同初始状态出发，按相同顺序执行相同操作，得到相同状态。**

它对会话日志的两个要求：

| 要求 | 含义 | 违反的后果 |
|---|---|---|
| **确定性** | 同样输入产生同样输出 | 重放结果不同 |
| **顺序一致** | 事件顺序固定 | 状态不可复现 |

确定性在 agent 系统里的难点：**模型输出是不确定的**（采样、温度、提供商版本变化）。

解法是把不确定性记进日志：**模型的输出本身作为事件被记录**，重放时直接使用记录的结果，不再调用模型。这正是"模型可见即已记录"的必要性来源——不记录就无法重放。

### 6.2 事件的版本化

事件结构会演进（新增字段、改语义）。学术与工业界的共同做法是：

| 手段 | 做法 | 权衡 |
|---|---|---|
| **版本号** | 每个事件带版本 | 简单，读时分支多 |
| **向后兼容** | 只增字段，不删不改 | 最省事，但结构会膨胀 |
| **转换器链** | 逐版本升级到最新 | 清晰，代码多 |

与我们仓库的做法对应：**结构性格式变化才提升会话格式版本**，只加字段不提升（默认兼容读取）。这选择的是"向后兼容 + 少量版本升级"的折中。

一条重要的实践约束：**未知事件类型必须能安全处理**——要么忽略（标记为可忽略），要么明确拒绝加载。静默接受未知事件会让新旧版本混用产生难查的问题。

### 6.3 循环的终止性

把 agent 循环看成一个状态机，"它会停吗"是一个**终止性**问题。实践中它不能靠纯静态分析保证，只能靠资源约束：

| 约束 | 形式 |
|---|---|
| 步数上限 | 状态空间的硬边界 |
| 上下文上限 | 输入规模有界 |
| 成本上限 | 外部资源有界 |

这与 3.1 的重试、3.4 的进程超时是同一个结论：**任何可能不终止的过程都要有硬上限。**

另一个学术视角是"进展"：一个循环如果每一步都不能证明"离目标更近"，就可能在原地打转。**工程上的近似是"无进展检测"**（连续 N 步没有新信息就终止）。

### 6.4 日志即接口

把日志当作**接口**而非内部实现，会带来几个结构性好处：

| 好处 | 说明 |
|---|---|
| 可重放 | 用于调试与回归测试 |
| 可审计 | 谁在什么时候做了什么 |
| 可评测 | 录制会话用于基准测试（见 7.6） |
| 可迁移 | 换实现后旧日志仍可用 |

**代价是格式的稳定承诺**（见 6.2）。

这正是本课程第 7 卷能"录制会话回放"的前提：**因为日志是接口，所以会话可以被录制、被重放、被当作测试用例。**

## 七、理论：三条不变量

### 7.1 顺序的单调性

$$
\text{seq}(e_i) < \text{seq}(e_j) \iff e_i \text{ 早于 } e_j
$$

算例实测：追加 3 条得到 `1, 2, 3`。

为什么不用时间戳：**时钟可以回拨**（NTP 校正、时区变化）。单调序号不受时钟影响。

### 7.2 配对完整性

$$
\forall c \in \text{调用} : \exists r \in \text{结果},\ \text{id}(r) = \text{id}(c)
$$

算例实测：3 / 3 配对完整，且**被拦截与抛异常的调用都产出结果**。

这条不变量的价值：**它把"模型看到的对话是否合法"从人工检查变成可断言的程序性质。**

### 7.3 收敛

$$
\text{终止} \iff \text{无工具调用} \lor \text{触发硬上限}
$$

算例实测：第 2 步以 `no-tool-calls` 终止。

注意这是一个"或"：正常终止与硬上限终止都是合法终止。**而"一直跑下去"不是。**

## 八、工程化清单

| 项 | 内容 |
|---|---|
| 追加 | 只追加，单调序号 |
| 顺序 | 不用时钟 |
| 尾部 | 截断并报告 |
| 派生 | 消息由事件派生 |
| 记录 | 模型可见即已记录 |
| 配对 | 每个调用都有结果（含拦截与异常） |
| 压缩 | 压缩点记成一条摘要事件 |
| 收敛 | `no-tool-calls` + 最大步数 + 预算 |
| 原因 | 结构化终止原因 |
| 重放 | 确定性：模型输出也记进日志 |

## 九、练习

### 第一题：找出日志的三个缺陷

一个循环这样写：

```js
while (true) {
  const response = await model.complete(derive(log))
  append(log, { type: 'assistant', content: response.content })
  for (const call of response.toolCalls) {
    if (!allowed(call)) continue
    const result = await run(call)
    append(log, { type: 'tool-result', id: call.id, result })
  }
}
```

要求：

- 指出至少三个缺陷（无终止条件、被拒绝的调用没有结果、异常会跳过结果）。
- 逐个给出修正方案。
- 说明修正后"配对完整性"如何验证。

---

### 第二题：设计压缩事件

场景：上下文超过阈值时，系统把前 K 条消息替换成一条摘要。

要求：

- 设计这个事件的结构（要包含哪些字段才能支持重放）。

它做到的事：

## 本篇新词

容器（container） 在这门课里指一个持有零件并分发依赖的对象。它的职责只有两件事：记住谁提供了什么，以及把请求转给对应的提供者。把它理解成"一个大的全局变量"是一种常见的误解，而两者的差别正好是本篇的主题——全局变量没有归属、没有生命周期，而容器两者都有。

服务（service） 指一个被登记进容器、可以被其他部分按名字取用的能力。它的形态可能是一个对象、一个函数，或者一组函数。判据不在形态，而在于它有一个稳定的名字与一段明确的契约。本课程里模型层、工具注册表、会话日志都是服务。

依赖注入（dependency injection） 指一个模块不自己去构造它需要的东西，而是由外部把已经构造好的东西传给它。Fowler 在 2004 年那篇文章里把它与控制反转区分开：控制反转是一个更宽的说法（框架调用你的代码而不是你调用框架），而依赖注入是其中具体的一种做法，它回答的是"依赖从哪里来"。

服务定位器（service locator） 是依赖注入的替代方案：模块不接收依赖，而是主动向一个全局注册表索取。两者的差别在可测试性与可追溯性上——注入把依赖写在签名上，因此谁依赖了谁是可以静态读出来的。定位器把依赖藏在函数体里，读签名看不出来。

归属（ownership） 指"这个注册动作由谁负责撤销"。它是一个纯粹的记账概念：同一个服务可以由多个提供者先后注册，而撤销时必须只撤掉自己那一次，因此表里记的不只是"服务名到实现"，还要记"这一条是谁写的"。

effect 在这门课里指一个可撤销的副作用：它被创建时返回自己的撤销函数。容器里几乎所有的注册动作都是 effect，这个约定让"卸载"从一堆散落的清理代码变成一次统一的操作。

卸载（dispose） 指一个部件退出时把它注册过的一切撤回。它与"停止使用"不同：停止使用是调用方不再请求，而卸载要求提供方把留下的痕迹清掉，包括服务条目、事件监听、定时器与文件句柄。

生命周期阶段（lifecycle phase） 指一个部件从存在到退出的几个可区分时刻：注册前、注册后可用前、可用、卸载中、卸载后。区分它们的意义在于约束"什么时候可以做什么"——例如"可用之前不能接收请求"是一条时序承诺，而它在单线程测试里不会暴露。

## 第 0 节 · 学完这一篇你能做出什么

### 0.0 先行组织者：容器要回答的四个问题

这一篇建立对一个容器的最小完整认识。四块内容有顺序：先有"谁能提供什么"，才谈得上"依赖怎么取到"。取到之后才需要回答"谁负责撤销"。而撤销的时机由生命周期决定。

```
┌──────────────────────────────────────────────────────────────────────┐
│  ① 注册与查找 —— 谁能提供什么                          → 1.1          │
│     注册写进表、查找按名字、重复注册怎么办                            │
│                                                                      │
│  ② 依赖怎么来 —— 注入还是定位                          → 1.5          │
│     写在签名上的依赖可以被静态读出，藏在函数体里的不能                │
│                                                                      │
│  ③ 谁负责撤销 —— 归属与 effect                         → 1.2、1.4      │
│     注册返回撤销函数；卸载只撤自己那一次                              │
│                                                                      │
│  ④ 什么时候可以做什么 —— 生命周期阶段                  → 1.3          │
│     可用之前、可用、卸载中，各自的合法动作不同                        │
└──────────────────────────────────────────────────────────────────────┘

 一句话串起来：谁能提供 → 怎么取到 → 谁撤销 → 什么时候做
```

这张图的关键线索在第三块：归属是容器存在的核心理由。如果所有零件都永不退出，一个全局对象就够了。正是因为零件会退出，容器才必须记账——而账记错了的表现形式是内存泄漏、幽灵服务（提供者已经走了但条目还在）或重复注册互相覆盖。

### 0.1 一个具体的判断：`register` 为什么返回函数而不返回结果码

2.2 里 `ToolRegistry.register` 返回的是一个卸载函数，而不是一个表示成功或失败的结果码。这个选择在那一篇里已经给出理由（注册是 effect），而在这一篇可以看到它的第二个后果：任何一个注册动作都自带它的撤销动作，于是"卸载一个部件"不需要一张额外的清理清单。

对比一下替代方案。若 `register` 返回结果码，那么注册表就必须额外维护一张"谁注册了什么"的映射，才能在某个人退出时把他注册的东西删掉。而这张映射本身就是一份新的状态，它会与真实情况不一致——例如某处代码直接往表里塞了一条而没有登记。返回卸载函数的写法消除了这种不一致的可能，因为撤销动作只能从注册动作那里拿到，绕不过去。

这个模式的适用范围比容器更广，它在 React 的 `useEffect`、Go 的 `defer`、Python 的 `contextmanager` 里都以不同形式出现。它们的共同点是：把"清理"与"申请"写在同一个位置，从而让清理不可能被遗漏——遗漏的代价在这类系统里通常是资源泄漏，而它不会立刻报错。

### 0.2 本篇建立的三项判据

第一项用于判断依赖该注入还是该定位：问这条依赖是否需要写在签名上被读到。能被静态读出的依赖让调用方一眼看到全部前置条件，而定位器写法把前置条件藏进了函数体，只有读实现才能发现。代价也明确：注入会让构造函数或工厂的参数变长，而定位器让签名保持简洁。判据是"这个依赖是稳定的还是可选的"：稳定依赖写进签名，可选依赖用注入点（例如一个可选的钩子字段）。

第二项用于判断一次注册该由谁撤销：问这个注册动作是在谁的上下文里发生的。在部件自己的初始化里发生的注册由部件自己撤销。在响应某次请求时临时发生的注册由发起方撤销——而后者常常没有负责人，于是变成泄漏。实践中的做法是禁止无归属的临时注册，或者要求它显式带一个作用域。

第三项用于判断一个部件现在处在哪个阶段：问它此刻允许被调用吗。这个问题在启动阶段尤其重要，因为一个部件可能在注册之后、依赖就绪之前被调用，而那次调用会拿到一个空的服务并静默失败。可执行的做法是把阶段约束编码进接口：把"只能在初始化阶段调用"的方法放在一个只在初始化阶段可见的对象上，让错误在类型层面出现，而不是在运行时。

### 0.3 十分钟练习：观察一次注册与一次卸载

这项练习用三行代码观察归属与撤销的关系。

```js
// 最小容器：注册返回撤销函数，卸载只撤自己那一次
const table = new Map()                       // 服务名 -> { impl, owner }
function provide(name, impl, owner) {
  table.set(name, { impl, owner })
  return () => { if (table.get(name)?.owner === owner) table.delete(name) }
}
const a = provide('llm', 'A 的实现', '插件 A')
const b = provide('llm', 'B 的实现', '插件 B')   // 后者覆盖前者
a()                                            // A 的撤销：不该删掉 B 的条目
console.log(table.has('llm'))                  // 输出 true：撤销动作被归属保护住了
b()
console.log(table.has('llm'))                  // 输出 false
```

这段代码里最容易被忽略的一行是撤销函数里的归属判断。去掉它，第一个撤销动作会把后来者的条目一并删掉，而当插件 A 卸载、插件 B 仍在运行时，系统会失去一个正在被使用的服务。这类问题的表现形式是"某个功能在某个插件卸载之后就不再工作"，而两次事件之间的因果关系很难从堆栈里读出来。

> **面试视角**
> **高频问法**："什么是依赖注入？它和控制反转有什么区别？"
> **追问方向**："为什么注册要返回一个撤销函数？"落点是归属：撤销动作只能从注册动作处获得，这样"谁注册了什么"就不需要第二份状态来记。

### 0.5.3 三个连锁影响

第一，没有归属记账时，卸载会退化成"尽量删"，而"尽量删"在共享表结构下必然出错。假设两个插件都注册了同名服务，卸载其中一个时若直接按名字删除，另一个插件的服务就消失了。而如果干脆不删，卸载就没有效果。两种做法的失败形式不同（前者是服务消失，后者是资源泄漏），但根因相同：表里只有"服务名到实现"，缺少"这一条是谁写的"。补上归属字段之后，撤销动作可以精确到"只删自己写的那条"，两种失败同时消失。

第二，生命周期阶段没有被表达时，启动顺序会变成隐式知识。一个常见的现象是"这个插件必须在那个插件之前加载，否则启动会失败"，而这条规则只存在于某个人的记忆里。它的后果在增加插件时出现：新来的插件按字母序或按加入顺序加载，于是启动偶尔失败，而失败信息是一句"某服务不存在"。

把阶段表达出来的做法有两条，一是声明依赖并让容器在依赖缺失时拒绝启动（失败点前移到启动期），二是把"注册后即可用"与"可用前不能调用"区分开，让调用方的错误变成显式的阶段错误。

第三，注入与定位的选择会决定系统的可诊断性。用注入时，一个部件的全部前置条件写在它的签名或声明里，因此"它需要什么"是可以静态读出的，诊断工具可以据此画出依赖图（第 4 卷的诊断篇会用到）。用定位器时，前置条件藏在函数体里，依赖图只能靠运行时观察得到，而观察不到的路径永远是盲区。这条连锁在产品层面的表现是可预测性：依赖可读的系统能在启动前发现缺件，依赖不可读的系统只能在运行时撞上它。

### 0.5.4 它与本书其余部分的关系

本篇的容器是本地的、单进程的、以名字索引的。这个边界决定了它的结论在哪里需要补充。

当系统需要多租户或多会话隔离时，一个全局容器不够用——这正是 2.5 要处理的问题，它的做法是在容器之上加一层作用域，而"归属"这个概念正好是作用域的实现基础：作用域退出时，撤销的是"属于它的那批注册"。

当部件可能来自外部时（第 5 卷的 MCP 工具、第 4 卷自进化生成的部件），注册的信任问题就会出现：谁有权注册、注册的能力边界是什么、卸载之后它留下的数据怎么处理。本篇只回答"注册与撤销怎么做对"，不回答"谁可以注册"，那是第 3 卷的守卫与第 5 卷的审批要处理的。

> **面试视角**
> **高频问法**："你怎么组织一个插件化系统的依赖？"
> **高分要点**：说出注入与定位的取舍（可静态读出 vs 签名简洁），并强调注册动作必须返回撤销函数，否则归属就没有着落。这两点合起来才是"插件化"的完整答案，只说"用依赖注入"是半个答案。

## L0 要解决的问题

### 0.1 现象一：零件在用到的地方被构造出来

在一个还没有容器的项目里，需要模型的代码会自己去构造模型客户端，需要工具的代码会自己去建注册表，需要会话的代码会自己开一个数组。这种写法在部件少的时候工作得很好，而它埋下三件事：无法替换（测试要连真实服务）、无法共享（两处各自建一个，状态不互通）、以及无法统一处置（每个构造点各自决定什么时候销毁，而多数地方不会销毁）。

这个问题有时被描述成"耦合太紧"，但更准确的描述是构造点分散：耦合是不可避免的，分散才是问题。一个模块知道自己需要一个模型客户端，这是合理的依赖。它同时知道"怎么把模型客户端造出来"，这才是不该有的知识——因为后一种知识会在配置变化、测试、以及更换实现时被反复修改。

### 0.2 现象二：卸载之后残迹还在

第二个现象在插件化系统里必然出现。一个部件被卸载时，它的入口函数返回了，但它留下的东西还在：注册进表里的服务条目、挂在事件上的监听器、一个每三十秒触发一次的定时器、一个没有关闭的文件句柄。这些东西的表现形式是缓慢的资源增长与难以解释的行为——例如一个已经卸载的插件仍然在对事件作出反应，因为它的监听器还挂在事件源上。

这类问题的排查成本很高，原因是症状与原因在时间上分离：泄漏发生在卸载那一刻，而症状（内存增长、重复处理）在几小时后才可见。因此它不能靠"出问题时再查"来解决，只能靠卸载路径的设计来预防，这也是本篇把"撤销"作为一等概念的理由。

### 0.3 现象三：插件之间该不该互相看得见

第三个现象涉及隔离的边界。在一个共享的服务表里，任何插件都能查到任何服务。这在部件少的时候是便利，在部件多的时候是隐患——因为一个插件的名字可能与另一个插件冲突，而冲突的表现形式是静默覆盖。

`vendor/cordis` 给出的做法值得作为参照：服务的实现写进共享表，但归属记在注册者身上。注册者卸载时只移除属于它的那部分。卸载之后再次请求同名服务会失败，因为提供者已经不在了。三条规则合起来的效果是——表是共享的，但每条记录有主人。这个设计解决的是"既要共享又要隔离"这个矛盾：共享让查找简单，归属让撤销安全。

### 0.4 现象四：启动顺序只存在于某个人的记忆里

第四个现象是隐式知识。项目跑起来之后，某些插件必须在另一些之前加载，否则启动失败。而这条规则往往没有写在任何地方。它的代价在增加插件时显现：新成员按字母序或按加入顺序加载，于是启动偶尔失败，而失败信息是一句"某服务不存在"——它没有指出真正的原因（顺序）与正确的做法（声明依赖）。

把这个现象与 0.2 对照，可以看出它们共同指向同一件事：部件的存在与消失都需要被记账。顺序是"存在的时间关系"，撤销是"消失的清理关系"，而两者都要求系统知道"谁提供了什么、谁依赖了什么"。

### 0.5 这一篇要正面回答的四个问题

第一，注册与查找怎么做，重复注册的语义是什么（1.1、1.2）。第二，依赖怎么取到，注入与定位各自付出什么代价（1.5）。第三，卸载意味着什么，撤销动作从哪里来（1.4）。第四，一个部件处在哪个阶段，什么时候可以调用它（1.3）。

四个问题的顺序取决于容器的最小可用形态：先有注册表才能查找，先能查找才能谈依赖如何取到，而撤销与阶段是"让这个表可以被安全地长期使用"的两项要求。

## L1 设计与原理

### 1.1 注册、查找、以及重复注册的语义

容器的最小形态是一张"名字到实现"的表，加上两个动作：注册与查找。这个形态太简单，以至于人们会跳过它直接写代码，而跳过之后必然要补回来的问题是重复注册的语义。

重复注册有三种可能的语义。第一种是拒绝（第二次注册抛错），它把冲突暴露在启动期，代价是无法做覆盖式装配（第 2.6 篇的配置组合正需要覆盖）。第二种是后者覆盖前者，它支持覆盖，代价是较早的那个提供者会无声地失效——它以为自己的服务仍在使用，实际上已经被替换。第三种是记录全部并规定查找返回哪一个（例如返回最后注册的），它是最复杂的一种，只在需要"同一服务有多个提供者"时才有意义（例如多个事件源）。

本课程的选择是第二种（后者覆盖），并把"覆盖是允许的"写进契约。做出这个选择的依据是装配的需要：配置组合要求上层能够覆盖下层的实现，而这是它成立的前提。代价则由归属记账来抵消——被覆盖的那个提供者在卸载时仍然只撤掉自己那一条，因此它不会误删后来者。

| 语义 | 支持覆盖 | 冲突暴露时机 | 适用场景 |
|---|---|---|---|
| 拒绝重复 | 否 | 启动期（注册时） | 服务必须唯一的系统 |
| 后者覆盖 | 是 | 使用时（发现行为变了） | 需要配置覆盖的装配系统 |
| 记录全部 | 是 | 不暴露，需显式指定 | 同一能力有多个提供者 |

### 1.2 归属：表里为什么要有主人字段

归属是这一篇最核心的机制。它的作用是让撤销变得精确，而精确的意义可以这样理解：撤销是一个减法操作，而减法需要一个确定的被减项。若表里只有名字与实现，那么"撤销这个插件的注册"只能理解成"删掉这个名字"，而这个名字可能已经被别人覆盖过——于是减法算错了对象。

归属字段带来三个直接后果。第一，撤销可以写成"如果这条记录的主人是我，就删掉它"，这一句在所有覆盖情形下都是正确的。第二，卸载之后再次请求同名服务会失败，因为提供者已经不在了——这条行为是有意的，它让"用了已卸载的服务"变成一个立刻可见的错误，而不是一个静默返回旧对象的行为。第三，多个部件可以安全地提供同名服务，只要它们各自撤销自己的那一条，这正是装配系统需要的能力。

它的实现代价很小：表的值从"实现"变成"实现加主人加可选的作用域"，注册函数把当前上下文当作主人写进去，撤销函数比较主人之后再删。代价小、收益大，这是它值得作为默认约定的原因。

### 1.3 生命周期阶段与阶段约束

一个部件从存在到退出经过几个可区分的时刻，而这些时刻的合法动作不同。

| 阶段 | 允许做 | 不允许做 | 常见错误 |
|---|---|---|---|
| 注册前 | 构造自身状态 | 提供或请求服务 | 在构造函数里访问容器 |
| 已注册、依赖未就绪 | 声明依赖 | 处理请求 | 在初始化里发起需要依赖的调用 |
| 可用 | 处理请求、注册子部件 | —— | —— |
| 卸载中 | 撤销注册、等待在途操作结束 | 发起新请求 | 卸载时又注册了东西 |
| 卸载后 | —— | 任何使用 | 持有已失效的引用并调用 |

这张表里最容易被违反的是第二行与第四行。第二行的错误形式是"启动时偶尔报某服务不存在"，原因是初始化代码在依赖就绪之前就读了它。第四行的错误形式是"卸载之后仍然出现该部件的动作"，原因是卸载过程里又注册了监听器，而它们没有再被撤销。

表达阶段约束有两种做法。轻的一种是在容器里为每个部件维护一个阶段标记，并在请求服务时检查对端阶段（代价是一次判断，收益是错误信息指向阶段）。重的一种是把阶段编码进类型，例如让"只能在初始化阶段调用"的方法挂在一个只在初始化阶段可见的对象上。后者的错误会在编译期出现，代价是接口变复杂。本课程采用轻的做法加上文档声明，理由是在单进程、单线程的循环里，阶段错误的主要来源是人而不是类型。

### 1.4 卸载即撤销：effect 的形态

卸载的实现方式取决于注册动作是否返回了它的撤销函数。如果返回了，卸载就是把该部件的全部撤销函数依次调用一遍。如果没有返回，卸载就需要一份额外的清理清单，而这份清单会与真实情况不一致。

`vendor/cordis` 把这件事抽象成 effect：一个 effect 在被创建时登记自己的撤销函数，而作用域退出时按登记顺序的逆序执行它们。逆序是有意义的——先注册的往往是更基础的设施，逆序执行保证先撤掉依赖者再撤掉被依赖者，这与构造顺序相反。

```ts
export interface Effect {
  /** 撤销这个副作用。可以重复调用，第二次及以后不产生效果。 */
  dispose(): void
}
export function effect(setup: () => void | (() => void)): Effect
```

这段声明里有两个约定值得注意。第一，`dispose` 可以被重复调用而不产生额外效果，这条约定让"重复卸载"这种常见情况不会变成错误（2.2 的 `ToolRegistry` 卸载函数也遵守它）。第二，`setup` 可以返回一个清理函数，也可以不返回——不返回意味着这个 effect 不需要清理，而这一点必须显式成立而不是靠约定，否则所有调用方都要判断"要不要清理"。

### 1.5 依赖注入与服务定位

两种取依赖的方式在可读性上的差别最值得记住。注入把依赖写在签名或声明里：

```ts
// 注入：依赖在签名上，读一眼就知道它需要什么
export function createAgent(deps: { llm: LLM; tools: ToolRegistry }): Agent

// 定位：依赖藏在函数体里，读签名看不出来
export function createAgent(ctx: Context): Agent   // 它到底需要什么？
```

第二种写法在签名上与"只传容器"没有区别，而它把依赖声明移到了实现内部。它的代价在三处显现：测试时要构造一个完整的容器（而不是两个具体的依赖）、诊断工具无法画出依赖图、以及新成员读代码时必须通读实现才知道前置条件。

Fowler 在 2004 年那篇文章里的区分正好用来处理这个取舍：容器（控制反转框架）与注入模式是两件事，用了容器不等于用了注入。判断标准是依赖是否在签名上可见，而不是"有没有容器"。本课程的选择是混合的——稳定依赖写在签名上（模型、工具、会话），可选扩展用注入点（例如一个 `hooks` 字段，第 2.4 篇会用到）。

### 1.6 循环依赖与延迟解析

当 A 需要 B 而 B 又需要 A 时，构造顺序不存在。这是一个真实的场景，而不是理论问题：一个"能力"可能既需要工具注册表来暴露自己，又被工具注册表需要来提供默认工具。

三种处置方式各有代价。第一种是打破循环，把共同需要的那部分抽成第三方服务（最干净，代价是一次重构）。第二种是延迟解析——注册时不取依赖，等到实际使用时再取（代价是把启动期的错误推迟到运行期，而这类错误的表现形式是"某个功能偶尔不可用"）。第三种是允许部分初始化：先构造 A、把未完成的引用交给 B、再补全 A（代价是 A 在被补全之前处于不一致状态，而这与 1.3 的阶段约束冲突）。

本课程采取第一种与第二种的组合：优先重构打破循环。无法打破时用显式的延迟解析，并把"这个依赖是延迟的"写进声明，让读者知道启动期的依赖图不包含它。第三种做法在本课程里被明确排除，因为它会让对象在某个时间窗内处于不一致状态，而那个窗口在单线程测试里不可见。

### 1.7 作用域的雏形

归属字段加上"一组归属"的概念就是作用域：一个作用域是一批注册的集合，作用域退出时撤销它包含的全部注册。它的用途在第 2.5 篇会展开（多会话各见不同世界），而在这一篇只需要建立它的两个性质。

第一，作用域是嵌套的：子作用域里的注册在子作用域退出时撤销，父作用域的注册在父作用域退出时撤销，且子作用域的退出不影响父作用域的记录。第二，查找的可见性是"沿父链向上"：子作用域看不到兄弟作用域的服务，但能看到父作用域的服务。第三，这两条性质合起来正好对应 0.3 那个"既要共享又要隔离"的矛盾——共享发生在父链上，隔离发生在兄弟之间。

> **面试视角**
> **高频问法**："你怎么做一个插件系统？"
> **高分要点**：从三条规则说起——服务注册进共享表、归属记在注册者身上、卸载时只撤自己那一条。这三条同时给出了共享与隔离，而很多解释只讲了共享（用一个全局注册表），于是卸载必然出问题。

### 1.8 两次追问

工程侧的问题是撤销函数的失败该怎么处理。一个撤销函数可能抛错（例如它要关闭的文件已经被外部关掉），而如果它的错误直接向上传播，卸载过程会中断，剩下那些部件的清理就不会执行——泄漏因此变成"部分泄漏"，而这种状态比全部泄漏更难排查。可行的做法是逐个捕获并记录，把所有撤销都尝试一遍，最后汇总报告失败的项。这条做法与第 3 卷的"部分失败"处理是同一类问题。

产品侧的问题是容器对用户可见吗。多数时候不可见，但它决定了一件可见的事：新增一个能力要改几处。如果一个新能力只需要写一个部件并在配置里加一行，那么它的交付可以被拆得很小。如果它需要修改若干处的构造代码，那么每次新增都会带来一批回归风险。容器在这里的贡献是把"接入一个能力"从代码改动变成配置改动，而配置改动的验证成本远低于代码改动。

### 1.9 命名与索引：两种实现的代价

名字是服务表的索引，因此命名的规范直接决定了查找的可预测性。实践中有一条容易被违反的规则：服务名不应当带有实现的痕迹。把模型层服务命名为 `deepseek` 或把工具服务命名为 `openai_tools`，会让名字成为一个不该存在的承诺——换实现时要么改名（于是所有查找点都要改），要么留下一个名不副实的名字（于是后来者按名字推断能力时被误导）。

这条规则与 2.1 的可替换性判据是同一条：接口里不出现某个具体实现的概念，名字上也一样。

索引结构有两种实现，代价不同。第一种是"名字到一个实现的映射"，它的查找是常数时间，重复注册即覆盖。第二种是"名字到一组实现的映射"，它支持同一个名字有多个提供者（例如多个事件源、多个存储后端），代价是每次查找都要决定选哪一个——而那个决定要么由调用方给出（多一个参数），要么由注册顺序隐含（同 1.1 分析过的"无声覆盖"问题）。本课程选第一种，因为配置组合需要的是覆盖而不是并存。

当确实需要并存时，做法是让服务名区分（例如 `storage.primary` 与 `storage.cache`），而不是让一个名字承载一组实现。

还有一条命名实践值得写下来：保留名。为了让"某个部件覆盖了系统服务"这类事故可见，可以把系统自带的服务名放在一个保留前缀下（例如 `core.`），并要求第三方部件不使用该前缀。这条规则本身不产生任何能力，它的价值在于让冲突在人工评审时能被一眼看出——第 3 卷的守卫与第 5 卷的审批会把它变成可强制的检查。

### 1.10 服务的粒度：按变化频率划分，而不是按名词划分

把一个系统拆成多少个服务，是一个会长期影响改动成本的决策。按名词划分（用户服务、订单服务、工具服务……）看起来自然，而它的缺陷在于：名词是领域概念，而领域概念的变化频率彼此无关——同一个名词下可能既有几个月不变的部分，也有每周都动的部分，把它们绑成一个服务会让后者每次改动都要牵动前者。

更可用的划分依据是变化频率与使用者集合：会被同一批使用者以同样的节奏使用的部分，放在一个服务里。模型层服务之所以独立，是因为它只有一类使用者（需要调用模型的地方），而它的变化节奏由外部接口决定。工具注册表之所以独立，是因为它的使用者包括工具作者、守卫与模型描述生成器，三者的变化节奏不同，但它对外的契约是稳定的。

粒度判断有一个可执行的自检：如果两个方法的调用方集合完全不同，它们可能不该在同一个服务里。反过来，如果一个服务被五个不同模块以五种方式使用，那么它的契约会同时承受五种压力，改动它时需要考虑五个方向的兼容性——这是 1.2 里"表达重复"的另一种形态，只是重复的不是表达而是压力。

### 1.11 启动与关闭的顺序

容器的启动与关闭是一对镜像操作，而它们各自有一个容易写错的顺序问题。

启动的顺序由依赖决定：被依赖的部件先注册，依赖它的部件后注册，这样后者在初始化时就能取到所需的服件。容器能做的检查是"注册时验证依赖已存在"，而它无法自动决定顺序——顺序信息来自配置（第 2.6 篇的装配会处理），容器只负责在顺序错误时快速失败。这里有一个工程上的取舍：自动按依赖图排序看起来更省事，代价是当依赖图有环或含延迟依赖时，排序结果会依赖遍历顺序，从而让启动行为变得不确定。

显式配置顺序加上启动期检查，比隐式排序更可预测。

关闭的顺序与启动相反，理由与 1.4 的撤销逆序相同：依赖者先退出，被依赖者后退出，否则一个正在关闭的部件可能调用到已经被撤销的服务。这里有一类容易漏掉的情形：**关闭过程中仍有在途操作**。一个已经发起但未完成的模型调用，在它完成时会回调到部件。而如果部件已经卸载，那次回调会命中一个失效的状态。

处置方式有两种，一种是卸载时等待在途操作结束（代价是关闭变慢），另一种是在卸载时把在途操作的取消信号发出并丢弃结果（代价是需要取消机制，那是第 3 卷的进程管理要处理的）。本课程在本卷采用后者，并在 L9 里把它列为一条缺陷。

### 1.12 容器与测试的关系

容器在测试上的收益来自依赖注入那条性质：被测部件需要的服务可以被替换成受控的假实现，因此测试不必连真实服务。但它有一个常见的反模式——在测试里构造完整容器。完整容器会装载全部部件，于是测试变得慢（要初始化全部依赖）、脆（任何一个无关部件出问题都会让测试失败）、并且难以定位（失败可能来自被测部件之外的任何地方）。

可用的做法是为每个测试构造一个最小容器，只注册被测部件声明的依赖：需要模型层就注册一个脚本化的假 provider，需要工具注册表就注册一个只含两个测试工具的注册表。这样一次测试的成本从"装载整个系统"降到"构造两个对象"，而失败也只可能来自被测部件本身。

这条做法之所以值得写进讲义，是因为它与容器的推广方向相反：容器让装配变得容易，而测试需要的是最小化装配。因此一个容器实现如果只能整体构造（例如它没有"只注册一部分服务"的形态），那么它在生产环境有用而在测试环境有害。本课程的选择是让容器本身是普通的对象——测试可以直接 `new` 一个，只注册需要的服务，而不是去加载配置文件。

| 5 | 阶段约束 | 容器里标记阶段并检查 | 用类型把阶段编码进去 | 错误留在运行期；换来接口简单 |
| 6 | 撤销顺序 | 与注册顺序相反 | 与注册顺序相同 | 撤销时要维护一个栈；换来先撤依赖者 |
| 7 | 撤销函数抛错 | 逐个捕获并汇总 | 直接向上抛 | 卸载要多一段错误处理；换来清理不中断 |
| 8 | 查找未注册的服务 | 抛错 | 返回 undefined / 返回空实现 | 调用方要处理错误；换来缺件立刻可见 |
| 9 | 服务命名 | 全局唯一的短名，不带实现细节 | 按模块路径命名 | 命名要花心思；换来跨模块查找简单 |
| 10 | 运行时能否注册 | 可以，但必须有归属 | 只允许启动期注册 | 运行期要传上下文；换来插件可动态装载 |
| 11 | 启动期依赖检查 | 做，缺依赖时拒绝启动 | 等到使用时再失败 | 启动多一步；换来失败点前移 |
| 12 | 作用域的可见性 | 沿父链向上可见，兄弟之间不可见 | 全局可见 / 完全隔离 | 查找要走父链；换来共享与隔离同时成立 |

其中两条值得展开，因为它们的选择在实践中经常被做成另一个。

### 关于第 2 条的完整论证（归属字段为什么不能省）

替代方案是"表里只记实现"，它的吸引力在于简单：注册就是一条赋值，撤销就是一条删除。这个方案在服务永不重复注册时完全正确，而在三种情形下出错。

第一种是覆盖式装配。上层配置要覆盖下层提供的实现，于是同名服务被注册两次。此时下层部件卸载，撤销动作按名字删除，把上层的实现一并删掉。第二种是两个部件恰好取了同一个名字。这在多人协作里是常见的，而它的后果与第一种相同。第三种是热重载：同一个部件被卸载再装载，若撤销按名字进行，那么在"卸载旧实例"与"装载新实例"之间的窗口里，任何一次查找都会失败。

三种情形的失败形态不同，但根因相同：按名字撤销无法区分"这条记录是不是我写的"。补上归属字段之后，撤销动作变成一次带条件的删除，三种情形同时消失。它的代价是注册时要多传一个参数，而这个参数在容器内部总是可得的（就是当前的上下文），因此实际成本接近于零。

这条决策的一般形式值得记住：当一个共享结构允许多个参与者写入时，每条记录都必须记下它的来源，否则任何"撤销"或"更新"操作都无法定义它作用在哪一条上。同样的道理出现在事件监听（谁挂的）、定时器（谁开的）、临时文件（谁建的）等许多地方。

### 关于第 8 条的完整论证（查找失败为什么不返回 undefined）

替代方案是让查找在服务不存在时返回 `undefined`，它的好处是调用方不必处理异常。这个方案在两种情况下会变成缺陷。

第一种是延迟失败。返回 `undefined` 之后，错误不会发生在查找处，而会发生在第一次使用它的时候——那时调用栈已经离开查找点，错误信息变成"无法读取 undefined 的属性"，与真正的原因（某服务没注册）隔了好几层。第二种是静默降级。如果调用方为了健壮性写了 `?? 默认实现`，那么这个缺失就永远不会被发现，系统会带着一个它不认识的默认行为继续运行。

抛错的方案牺牲的是调用方的便利（它需要处理"服务不存在"这个错误），换来的是两件重要的事：缺件在发生处可见，以及启动期的依赖检查可以靠"试着解析一次"来实现。第二件事尤其值得注意——若查找返回 `undefined`，那么"启动时检查依赖是否齐全"就必须为每个依赖单独写一段判空逻辑，而这类代码在依赖变化时会漏改。

同样的取舍在 2.1 的错误分类里出现过一次：面对未注册的工具名，`run` 返回失败结果而不是抛错，因为那是模型输入导致的预期失败。而容器里的查找失败是编程错误（部件声明了它需要的服务，而没人提供），因此按"可预期的失败与不可预期的错误"的划分，它应当抛。

## L3 实现（施工图）

### 3.1 文件结构

```
// kernel/context.ts
// ┌─ 条目段 ──────────────────────────────────────────
// │  ServiceEntry：实现 + 主人 + 作用域
// ├─ 注册段 ──────────────────────────────────────────
// │  provide(name, impl) / effect(setup)
// ├─ 查找段 ──────────────────────────────────────────
// │  get(name)（内部）/ require(name)（对外，缺失时抛）
// ├─ 作用域段 ─────────────────────────────────────────
// │  scope(name)：新建子作用域、退出时撤销它的全部注册
// └─ 撤销段 ─────────────────────────────────────────
//    disposers：按注册顺序记录，退出时逆序执行并汇总失败
```

这五段的分工与 2.2 的 `tools.ts` 是同一形状（契约段、注册段、执行段、出口段），这不是巧合：注册表的形状在容器这一层被抽象成了通用能力。两者的差别在于 2.2 的注册表只服务工具，而容器的注册表服务任何东西，因此它多出了作用域段与撤销段的失败处理。

### 3.2 条目的形状

```ts
interface ServiceEntry<T = unknown> {
  readonly impl: T
  /** 归属：记录这条是谁写的，撤销时用来判断该不该删 */
  readonly owner: object
  /** 这条注册属于哪个作用域；查找时沿父链向上 */
  readonly scope: Scope
}
```

三个字段里，`owner` 与 `scope` 看起来重复（作用域也可以承担归属的职责），而它们回答的是不同问题：`owner` 回答"谁写的"（用于撤销判断），`scope` 回答"在哪可见"（用于查找）。同一个作用域里的两个部件是不同的 owner，而它们互相可见——把两者合并会导致"同作用域内不能覆盖"这个不必要的限制。

### 3.3 注册与撤销

```ts
/**
 * 注册一个服务，返回它的撤销函数。
 *
 * @param name 服务名
 * @param impl 实现
 * @returns 撤销函数；重复调用不产生额外效果
 */
export function provide<T>(name: string, impl: T): () => void {
  const entry: ServiceEntry<T> = { impl, owner: this, scope: currentScope }
  table.set(name, entry)
  let done = false
  return () => {
    if (done) return                                    // 幂等：重复撤销不报错
    done = true
    if (table.get(name)?.owner === entry.owner) table.delete(name)   // 归属保护
  }
}
```

这段代码里唯一需要在评审时被指出的是倒数第二行。若写成无条件的 `table.delete(name)`，那么后来者注册的同名服务会被前者的撤销动作删掉，而这类缺陷在单部件测试里不会出现——它只在两个部件共享一个名字时才暴露，这解释了为什么归属判断必须写在实现里而不是写在文档里。

### 3.4 作用域与撤销栈

作用域的实现只有两件事：维护自己的注册集合，以及在退出时按逆序执行它们。逆序的理由在 1.4 已给出（先撤依赖者），而撤销栈是这个规则的自然实现：每次注册把撤销函数压栈，退出时从栈顶弹出执行。

撤销过程中的失败处理遵循 L2 第 7 条：逐个捕获、继续执行、最后汇总。这段逻辑值得单独写成一个函数，因为它是卸载路径上唯一会被反复复用的部分。

```ts
function disposeAll(disposers: (() => void)[]): Error[] {
  const failures: Error[] = []
  for (const d of [...disposers].reverse()) {
    try { d() } catch (err) { failures.push(err as Error) }
  }
  return failures
}
```

### 3.5 验收判据

| # | 判据 | 怎么检查 |
|---|---|---|
| 1 | 注册之后可以被查到 | 注册一个值，按名字取回同一个引用 |
| 2 | 撤销之后查不到 | 调用撤销函数，再取一次应当抛错 |
| 3 | 撤销是幂等的 | 连续调用两次撤销函数，第二次不抛错 |
| 4 | 覆盖注册时，撤销旧的那条不影响新的 | 依次注册同名服务，撤销第一个，第二个仍然可取 |
| 5 | 子作用域能看见父作用域的服务 | 在子作用域里查父作用域注册的服务 |
| 6 | 兄弟作用域互相看不见 | 在作用域 A 里注册，在作用域 B 里查应当失败 |
| 7 | 子作用域退出后，父作用域的服务不受影响 | 退出子作用域，再查父作用域的服务 |
| 8 | 卸载按逆序执行 | 注册三个能记录顺序的 effect，退出后顺序与注册相反 |
| 9 | 某个撤销抛错时，其余仍然执行 | 让中间那个 effect 抛错，检查其余两个都被执行 |
| 10 | 查找未注册的服务时抛错，且错误信息含服务名 | 查一个不存在的名字 |

第 4 条与第 9 条是最容易漏掉的两条：前者检验归属保护，后者检验失败隔离。它们都不是"正常路径"，因此只在按判据逐条检查时才会被想到。

### 3.6 实现顺序

先做条目段与注册查找（判据 1、2、3），再做归属保护（判据 4），然后做作用域（判据 5、6、7），最后做撤销栈与失败隔离（判据 8、9）。第 10 条判据贯穿始终，它在每一步都可以检查。

### 3.7 与 `ToolRegistry` 的关系

2.2 的 `ToolRegistry` 在这一篇之后应当变成"由容器持有的一个服务"：它自己仍然维护工具注册表，而它的实例由容器提供。这样第 2.6 篇的装配就可以在配置里决定"这个模式用哪个工具集"，而不需要改任何构造代码。这个改动的成本是接入容器的一次性成本，收益是此后每一次增删能力都变成配置改动——它正好是 1.8 那段产品追问的实例。

### 3.8 错误信息里要有什么

容器是排查问题的第一现场，因为"缺件"与"冲突"这两类故障都在它这里发生。因此它的错误信息必须携带定位信息，而不是只说明失败。三条错误各自的必要字段如下。

查找失败（服务未注册）的错误信息应当包含三样：请求的服务名（调用方搜代码时用它）、当前作用域名（区分"全局没有"与"这个作用域看不到"）、以及当前作用域可见的名字清单。第三样常常被省略，而它恰好最有用——它把"我没有它"变成"我有这些，你是不是要找其中某一个"，后者通常能让人立刻发现是名字写错还是注册漏了。

启动期的依赖缺失错误应当包含四样：缺少哪个服务、哪个部件需要它、该部件在配置里的位置、以及曾经提供过这个名字的部件（如果注册表保留了被覆盖的历史）。最后一样用于区分"从来没注册"与"注册了但已经被撤销"，这两种情况的原因完全不同——前者是配置漏了，后者是卸载顺序或卸载条件写错了。

撤销失败的错误应当包含三样：哪个部件的哪个 effect 失败、原始错误、以及这次卸载里其余 effect 的执行结果。第三样决定了"这次卸载是部分成功还是完全失败"，而它是后续要不要补偿的依据。

这三组字段的共同形态与本课程反复出现的那条原则一致：错误信息要携带下一步需要的东西。它在本篇的落地形式是给出"当前可见的名字"与"曾经的提供者"，因为这两样恰好把排查从"读代码找哪里注册"缩短到"看一眼错误信息就知道"。

### 3.9 把工具注册表挂进容器的完整示例

把 2.2 的 `ToolRegistry` 接入容器的改动很小，但它是"容器带来什么"的最好演示。改动只有三处。

第一处是让注册表由一个部件提供，而不是在需要它的地方各自新建：

```ts
// tools-plugin.ts：把工具注册表注册成服务，并声明它需要模型层
export function toolsPlugin(ctx: Context) {
  const registry = new ToolRegistry(ctx.require("llm"))   // 依赖在构造时注入
  const off = ctx.provide("tools", registry)              // 注册返回撤销函数
  for (const tool of coreTools) registry.register(tool)   // 每个工具的撤销由注册表保管
  return () => { off(); registry.disposeAll() }           // 卸载：先撤服务，再撤工具
}
```

这段代码里有三处在评审时值得指出。第一，`ctx.require("llm")` 把依赖写在了构造点，因此"这个部件需要模型层"是可静态读出的。第二，`provide` 的返回值被保留并用于卸载，这正是本篇的核心约定。第三，卸载函数里先撤服务再撤工具，顺序与注册相反。

第二处改动是把"用了哪些工具"从代码里移到装配里：某个模式需要哪些工具，由配置声明，而配置的解析与生效是第 2.6 篇的内容。这个改动的收益可以在一个数字上看到：在此之前，新增一个能力的成本包含"找到构造它的地方并修改"，之后只剩"在配置里加一行"。前者需要读代码、评审、跑回归。后者只需要跑一次自检。

第三处改动是让守卫通过容器取到工具注册表，而不是直接 import 它。这样第 3 卷的守卫就能作为一个插件被装载与卸载，而它与工具系统之间的依赖是显式的。这三处改动合起来，把"工具系统"从一个模块变成了一个可插拔的部件，而后面几篇（事件、作用域、装配）用的都是同一个模式。

## L5 语法速查

### 5.1 术语表

| 术语 | 在本篇里的准确含义 | 容易误解为 |
|---|---|---|
| 容器 | 持有零件并分发依赖的对象，职责是记账与转发 | "全局变量"（全局变量没有归属与生命周期） |
| 服务 | 被登记进容器、可按名字取用的能力 | "工具"（工具是服务的一种） |
| 依赖注入 | 依赖由外部传入，而不是模块自己构造 | "用了容器"（用了容器不等于用了注入） |
| 服务定位器 | 模块主动向全局注册表索取依赖 | "依赖注入的一种"（它是替代方案，可读性不同） |
| 归属 | 这条注册由谁负责撤销 | "所有权"（那个词在内存管理里另有含义） |
| effect | 一个可撤销的副作用，创建时返回撤销函数 | "事件监听" |
| 卸载 | 部件退出时撤销它注册过的一切 | "停止使用" |
| 生命周期阶段 | 注册前、可用前、可用、卸载中、卸载后 | "状态机"（它更简单，只是几个时刻） |

### 5.2 命令速查

| 目的 | 命令 | 说明 |
|---|---|---|
| 跑容器契约测试 | `node tests/t5-container.mjs` | 十条判据 |
| 对照参考答案 | `$env:IMPL='../grade/context.reference.mjs'; node tests/t5-container.mjs` | 应当满分 |
| 负向验证 | `node grade/negative-check-context.mjs` | 四类错误实现应全部被抓 |
| 找没有撤销的注册 | `rg -n 'table.set|registry.register' src/ \| rg -v 'return'` | 命中即说明注册动作没有返回撤销函数 |

### 5.3 三条容易踩的规则

第一条，注册必须返回撤销函数。没有返回值的注册动作无法被精确撤销，而它留下的残迹会在几小时后以资源增长的形式出现。

第二条，撤销要判归属。按名字删除的写法在两个部件共享一个名字时必然出错，而这类错误在单部件测试里不可见。

第三条，卸载要逆序且要容错。逆序保证先撤依赖者，容错保证一次失败不会中断其余清理——两者都是"卸载路径"这个很少被测试的代码路径上的常见缺口。

| 不确定阶段约束要不要上类型 | 阶段错误的主要来源是人还是类型；是人就用标记加文档 |

## L7 挑战题（不给答案）

第一题：给容器加"延迟服务"。 某些服务的构造代价很高（例如要建立连接），希望用到时才构造。设计它的接口，并说明它与 L2 第 4 条那个"显式延迟解析"的区别。

第二题：设计一个可重启的部件。 它可能被卸载后重新装载。给出你如何保证重复装载不会叠加副作用。

第三题：为容器加"依赖缺失的启动检查"。 要求给出检查的时机、失败信息里包含什么、以及如何处理"可选依赖"。

第四题：论证作用域可以用别的方式实现。 本文用"归属加集合"实现作用域，构造一个用其他机制实现同样语义的方案，并比较代价。

第五题：热重载的边界。 一个部件在热重载时，旧的实例可能仍有在途操作。设计一套"等待在途操作结束"的机制，并说明它对启动时间的影响。

第六题：反驳返回撤销函数。 构造一个场景，说明"注册返回结果码 + 集中登记的清理清单"比"注册返回撤销函数"更好。

## L9 仍未解决（这一篇自己的缺陷）

| 缺陷 | 后果 | 修法 | 当初为什么这么写 |
|---|---|---|---|
| 容器是单进程的，没有跨进程的服务发现 | 进程重启后所有注册重新来一遍，无法共享状态 | 跨进程的注册需要持久化与探测（第 5 卷的多会话会涉及一部分） | 本卷目标是单机闭环 |
| 阶段约束只做标记与文档，没有类型支撑 | 阶段错误在运行时才暴露 | 把阶段编码进类型（代价是接口变复杂） | 单线程循环里阶段错误的主要来源是人 |
| 撤销的失败只被汇总，没有重试与升级机制 | 一次失败的撤销会留下残迹，且只有日志记录 | 引入失败的撤销队列与告警 | 本卷还没有可观测设施（3.6 篇才做） |
| 作用域只做到嵌套与父链可见，没有生命周期钩子 | 部件无法在作用域退出时做异步清理（例如等待在途请求） | 引入异步的 `dispose` 与在途操作计数 | 同步清理覆盖了绝大多数场景，异步清理与循环的取消机制耦合（第 3 卷） |
| 没有讨论"注册的权限" | 任何部件都能注册任何名字，包括覆盖系统服务 | 引入命名前缀与保留名（第 3 卷的守卫与第 5 卷的审批） | 本卷假设所有部件来自同一作者 |
| 依赖图只用于启动检查，没有用于诊断 | 运行时无法回答"这个服务是谁提供的" | 把注册记录暴露给诊断工具（第 4 卷的诊断篇） | 诊断需要事件流，而事件在第 2.4 与 2.7 篇才建立 |

前两条属于边界与实现手段的缺失，中间两条属于能力缺失（异步清理与失败升级），最后两条属于"位置放错"——权限与诊断本该挂在容器上，而它们需要的基础设施在本篇之后才建立。最后一条值得特别注意：容器的注册记录是诊断的天然输入（谁提供了什么、什么时候注册的），而本篇没有把它暴露出来，因此第 4 卷做失败归因时不得不从头补一条数据通路。

### 问题升级练习

模糊问题：「我该怎么设计一个插件系统？」

升级后的精确问题：

> 插件系统至少要回答三件事：部件怎么接入（注册与查找的名字与语义）、依赖怎么取到（注入还是定位，以及在哪个阶段取）、以及退出时怎么清理（撤销动作从哪里来、按什么顺序执行、失败怎么办）。
> 这三件事里第二件与第三件互相制约——依赖取得越晚，清理时就越可能遇到"在途操作还没结束"的情形。
> 我能不能为每一件事找出一条**可检查的判据**？
> 特别是：有没有哪一条判据，是**能在一次装载与卸载的演练里被验证的**？

提升点说明：原问题无法回答，因为"插件系统"没有边界。升级后的版本把目标收成三件有位置的事，指出其中两件的制约关系，并追加以一个更强的问题：哪一条判据能在装载与卸载演练里验证。这一问指向的正是"卸载之后没有残迹"这条判据——它无法靠读代码确认，只能靠实际装卸一次并观察。

回看第 0.5 节的三个连锁影响。

| 预判 | 本篇分析之后的结论 | 状态 |
|---|---|---|
| 没有归属记账时卸载会退化成"尽量删" | 确认，并给出了归属保护的具体实现与三种失败情形 | 成立且更具体 |

| 注入与定位的选择会决定系统的可诊断性 | 确认，并指出它对第 4 卷失败归因的直接支撑 | 成立 |

一处需要修正的预判：0.5.2 把"循环依赖的处置"标为对 2.6 的中等强度依赖。读完之后要把它的强度提高：第 2.6 篇的配置组合会产生大量跨层引用（上层的部件需要下层提供的服务，而下层的默认实现又需要上层配置的信息），因此循环依赖在那里不是边缘情形而是常态。这一点的代价是 2.6 必须提前设计好"哪些引用是延迟的"，而那要求本篇的延迟解析约定被认真实现。

通向下一篇的桥。 本篇解决的是"零件的持有与退出"，而它留了一个没有答案的问题：部件之间怎么在不相互引用的情况下协作。容器提供的是"我知道你存在"（按名字取），而很多协作关系无法用取服务表达——例如"当某个事件发生时，请顺便做一件事"，而事件的产生方不应该知道有哪些响应者。

下一篇 `2.4 事件与扩展点` 处理这件事。它与本篇的连接点是归属：事件监听器同样是注册动作，同样需要归属，同样会在部件卸载时变成残迹——2.3 的撤销机制是 2.4 能否安全实现的前提。

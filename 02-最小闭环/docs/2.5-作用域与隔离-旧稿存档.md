## 本篇新词

作用域（scope） 指一组注册的集合，以及它相对其他作用域的位置（父或子）。它的两个属性决定了它的全部行为：可见性（这个作用域里能看到哪些服务）与生命周期（它什么时候退出，退出时撤销什么）。把作用域理解成"命名空间"只抓住了第一个属性，而第二个属性才是它与隔离相关的部分。

隔离（isolation） 指两个作用域互不可见。它的判据不是"它们的数据在物理上分开"，而是"从一个作用域里无法观察到另一个作用域的状态"。这个判据比物理分离弱——同一块内存里两个互不可见的作用域仍然是隔离的。也比它强——两个共享同一块存储但是互相看不到对方的写的作用域，在某些定义下仍然是隔离的。

可见性查找（visibility resolution） 指"在当前作用域里查一个名字"这个动作的规则。本课程采用的规则是沿父链向上查找：当前作用域没有就查父作用域，一直查到根。这条规则决定了哪些东西是共享的（放在父作用域）与哪些是隔离的（放在子作用域）。

上下文（context） 在本课程里与作用域的关系是：上下文是作用域的一个实例，它带着自己的注册集合与父引用。一个部件被装载时拿到一个上下文，它注册的一切都归这个上下文所有（2.3 的归属）。

ambient authority 是 Miller 在 object-capability 模型里提出的概念：一个模块能在不显式获得许可的情况下使用某项能力的性质。全局单例是最典型的例子——任何代码只要 import 它就能用，而没有任何地方记录了"谁被允许用它"。作用域的作用之一就是消除这种隐式授权：能力只能通过上下文获得，而上下文的授予是显式的。

共享状态与隔离状态 的划分依据是"它是否描述一个全局事实"。进程的启动时间、代码版本属于全局事实，必须共享。当前会话的历史、当前任务的工作目录属于局部事实，必须隔离。把局部事实放进全局会造成串扰，把全局事实放进局部会造成重复与不一致，这两种错误在真实系统里都常见。

作用域泄漏（scope leak） 指一个子作用域的状态被父作用域或其他兄弟作用域观察到。它的表现形式通常是"第二条会话看到了第一条会话的数据"，而根因往往是某个对象在构造时捕获了全局变量，或者某个服务注册在了父作用域而它内部持有会话状态。

```
│  ④ 退出时撤销什么 —— 归属与逆序                        → 1.4          │

 一句话串起来：作用域是什么 → 可见性怎么算 → 什么该隔开 → 退出时撤销什么
```

这张图的关键线索在第三块：作用域只是机制，"什么该隔离"才是判断。机制做错会立刻报错，而划分做错不会——它表现为两条会话之间的偶发串扰，而这类缺陷的复现依赖时序。

### 0.1 一个具体的判断：工具的可见范围

在一个支持多会话的系统里，"哪些工具可以被调用"这件事该放在哪一层。三个候选位置各有后果。

放在全局（进程级注册表）：所有会话看到同一套工具。这在只有一个会话时完全正确，而在两个会话需要不同工具集时无法表达——而"不同会话需要不同工具"是真实需求，因为一个会话可能在做代码任务（需要文件工具），另一个在做问答（不需要且不应有文件工具）。

放在会话级（每个会话一套注册表）：隔离彻底，代价是每个会话都要重新注册一遍工具，而注册动作本身有成本（校验、构建描述、进入给模型的清单）。

放在会话级但由父作用域提供默认集：父作用域注册核心工具，会话作用域只注册差异部分。查找沿父链向上，因此会话看到的是"核心加差异"。这个方案的代价是多了一层查找（沿链向上，深度通常不超过三层），收益是共享与隔离同时成立。

本课程选第三种。它的判据不是性能，而是共享的东西应该只被写一次：核心工具的定义、描述与校验规则在父作用域里写一次，会话级只声明差异。第一条规则与第三条规则的差别体现在一处具体的维护成本上——前者每次新增核心工具要改四处（每个会话各一次加注册表本身），后者只需要改一处。

### 0.2 本篇建立的三项判据

第一项用于判断一处状态该共享还是该隔离：问它描述的是一个全局事实还是局部事实。全局事实（代码版本、启动时间、进程级的资源池）放父作用域。局部事实（会话历史、当前工作目录、任务上下文）放子作用域。这条判据的反面是"图省事放进全局"，而它的代价在第二个会话出现时才显现。

第二项用于判断一次查找的行为是否符合预期：问它是否沿父链向上。如果一次查找在子作用域里失败，正确的结果是继续向上查，而不是立刻返回失败——除非契约明确写了"这个服务不参与父链查找"（用于强制隔离的场景）。

第三项用于判断一个作用域是否泄漏：问它退出后是否还有东西在引用它的状态。判据是"退出之后广播一次事件、或者发起一次请求，看有没有反应"，这与 2.4 的监听器残留检测是同一条做法。

### 0.3 十分钟练习：串扰的实跑

下面这段代码用二十行复现"全局状态导致跨会话串扰"这个经典缺陷。

```js
// 错误做法：工作目录是全局的
const globalState = { cwd: '/tmp' }
function toolA() { return globalState.cwd }

// 两条会话并发运行，各自设置自己的工作目录
globalState.cwd = '/proj/one'
const one = toolA()
globalState.cwd = '/proj/two'
const two = toolA()
console.log('会话一读到：', one, '　会话二读到：', two)

// 正确做法：状态挂在各自的上下文里
function makeTool(ctx) { return () => ctx.cwd }
const a = makeTool({ cwd: '/proj/one' })
const b = makeTool({ cwd: '/proj/two' })
console.log('会话一读到：', a(), '　会话二读到：', b())
```

前两行输出说明问题的本质：第一行的结果被第二行的设置改变了——在真实系统里这条链更长（设置、使用、再设置），因此表现得像偶发故障。后两行输出说明修法的形状：状态挂在上下文里，工具从上下文取，于是两条会话各自持有自己的值。这个改动在只有一个会话时看不出差别，而它决定了系统能否支持第二个会话。

> **面试视角**
> **高频问法**："多会话系统里你怎么隔离状态？"
> **追问方向**："哪些状态必须共享？"落点是"描述全局事实的那些"（代码版本、启动时间、资源池），并说明判断依据是事实的作用范围而不是实现方便。

### 0.5.3 三个连锁影响

第一，隔离的粒度决定了系统的上限。 如果状态按进程隔离（全部共享），那么系统只能跑一个任务。如果按会话隔离，它能跑多个。如果按用户隔离，它还能支持多租户。这条链的方向是单向的——从粗粒度改到细粒度需要改动所有持有状态的地方，而从细粒度改到粗粒度只需要把它们合并。因此这条连锁的结论是：在不确定时选择更细的粒度，代价是多一层结构，收益是不必返工。

第二，ambient authority 会让权限判断失去依据。 当能力通过全局单例获得时，没有任何地方记录"谁获得了什么"。第 3 卷的守卫要回答"这次工具调用该不该放行"，而它需要的输入包括"谁在调用"——如果调用方是通过全局 import 拿到工具的，这个信息就不存在。作用域在这里的作用是把"谁"变成显式的：注册在哪个作用域，就说明它属于谁。

第三，作用域泄漏的表现形式与实际原因之间隔着很多层。 一条会话读到另一条的数据，直接原因可能是某个模块在构造时捕获了一个全局变量，而那个变量的赋值发生在很远的地方。这类缺陷的排查通常从"数据为什么不对"开始，而正确的方向是"这个数据从哪里来"——这要求系统里有明确的"谁提供了它"的记录（2.3 的注册记录正好提供这个信息）。

### 0.5.4 它与本书其余部分的关系

本篇的作用域是同进程、同线程模型下的隔离，它不提供任何强制能力——一个模块如果绕过上下文直接 import 全局对象，隔离就失效。这个边界必须写清楚：作用域是一种约定加一层便利，不是安全边界。真正的隔离（进程、容器、虚拟机）在第 3 卷的沙箱篇会涉及，而它解决的是另一类问题。

> **面试视角**
> **高频问法**："你的隔离是强制的还是约定的？"
> **高分要点**：明确区分两者——作用域这类机制是约定的（靠代码不绕过），而沙箱是强制的（靠系统能力限制）。把约定说成强制会让人误判系统的安全性，而这是这类问题最常见的答错方式。

## L0 要解决的问题

### 0.1 现象一：第二个会话无法存在

一个为单会话设计的系统，在需要支持第二个会话时会遇到一整类问题。工具的实例只有一份，于是两条会话共享同一个上传目录。会话的历史存在模块级的变量里，于是第二条会话开始时第一条的历史被清空。模型的调用计数器是全局的，于是统计把两条会话的用量混在一起。

这些问题的共同点是：它们在只有一个会话时完全不可见，因为"共享"与"独占"在单会话下没有区别。因此它们不会被任何测试发现，只会在第二个会话出现时同时爆发——而那时每条问题都需要单独修改。

### 0.2 现象二：串扰

第二个现象比第一个更隐蔽。系统已经为每条会话建了独立的对象，但其中某个对象在构造时捕获了一个全局变量，于是它读写的是共享的那一份。它的表现形式是"第二条会话看到了第一条会话的数据"，而这在真实场景里往往被解释成"数据没清干净"，于是排查方向转向清理逻辑，而不是共享的那一个变量。

这类缺陷的难处在于它跨越了抽象边界：会话对象看起来是独立的（它们确实是两个对象），而它们共享的是被捕获的那个引用。因此"隔离"不能靠检查"我有没有为每条会话建对象"来验证，只能靠检查"这些对象有没有共同的外部引用"。

### 0.3 现象三：隔离过度

第三个现象方向相反。为了避免串扰，所有状态都被放进了各自的作用域——包括那些本来就描述全局事实的状态。典型的例子是代码版本、启动时间、进程级的资源池被每个作用域各存一份，于是它们之间出现不一致：两条会话报告不同的启动时间，或者各自建了一个连接池而总连接数翻倍。

隔离过度的代价比串扰小（它不会产生错误的数据），但它是真实的：重复的资源、不一致的全局事实、以及当某个事实真的需要全局更新时无处下手。它的判据是"这个状态是否描述一件对全体成立的事"。

### 0.4 现象四：作用域退出之后它注册的东西还在

第四个现象是 2.3 与 2.4 那两处残留的作用域版本。一个作用域退出时，它内部注册的服务、监听器、定时器都应当被撤销。而如果撤销的实现只处理了服务而漏掉了监听器（因为监听器是 2.4 的另一套机制），那么退出的作用域仍然会对事件作出反应。它的后果在长时间运行的进程里累积：每退出一个作用域就多一批幽灵监听器。

这类问题的修法不在"记得撤销"，而在把撤销集中到一处：无论注册的是什么，都登记进同一个 effect 列表，退出时统一执行。这条原则在 2.3 已经建立，本篇要处理的是它的规模版本——一个作用域可能登记几十个 effect，而它们之间有依赖顺序。

### 0.5 这一篇要正面回答的四个问题

第一，作用域由什么构成，嵌套意味着什么（1.1）。第二，查找的规则是什么，沿父链向上查找的代价与边界在哪（1.2）。第三，哪些状态必须共享、哪些必须隔离（1.3）。第四，作用域退出时撤销什么，按什么顺序（1.4）。

四个问题里第三是判断，其余三个是机制。判断部分无法由机制保证——机制能确保"放对位置的东西被正确隔离"，但不能确保"你把它放对了"，这是本篇与前面几篇的差别所在。

## L1 设计与原理

### 1.1 作用域的结构

一个作用域由三样东西构成：自己的注册集合、一个指向父作用域的引用、以及一个标识自己身份的标记（用于归属判断）。三样里父引用决定了可见性，身份标记决定了撤销的精确性。

注册集合与 2.3 的服务表是同一个东西，只是从"全局一张表"变成"每个作用域一张表"。这个变化带来一个直接后果：查找变成了一次沿链的遍历，而遍历的深度等于作用域的嵌套深度。实际系统里这个深度通常不超过三层（根、会话、任务），因此成本可以忽略。但它是本篇所有查找语义的来源。

```
       根作用域（共享：配置、资源池、核心工具）
         │
         ├── 会话 A 作用域（隔离：历史、工作目录、会话级工具）
         │     └── 任务 A1 作用域（隔离：本次任务的临时状态）
         │
         └── 会话 B 作用域
               └── 任务 B1 作用域
```

这张图的读法有两个方向。向下是隔离：会话 A 与 B 互相看不到对方的注册。向上是共享：两者都能看到根作用域的东西。两者同时成立的关键在于查找只沿父链走，而不横向走——兄弟之间没有边，因此不需要任何"隔离检查"。

### 1.2 可见性查找的规则

查找的规则可以写成三句话：先查当前作用域。没有就查父作用域，直到根。全链都没有则失败（抛错，理由与 2.3 的"查找失败要抛错"相同）。

这条规则有两个需要说清的边界。第一是覆盖：子作用域注册了与父作用域同名的服务时，查找命中子作用域的那一个（先查当前，因此子优先）。这条语义是 2.6 的配置覆盖的基础。第二是不参与父链查找的服务：某些服务需要严格的隔离（例如"当前会话的日志"不能被子作用域意外地取到父作用域的同名服务），做法是给注册加一个标记，让查找在遇到这个标记时停止向上。

这个标记用得越少越好，因为每多一个，查找的规则就多一条例外。

查找的失败信息在这里比 2.3 更需要携带信息：除了服务名与已注册的名字，还应当包含"查到了哪一层为止"。当嵌套有三层时，"所有作用域都没有这个名字"与"父作用域有这个服务但被隔离标记挡住了"是两种完全不同的原因。

### 1.3 共享与隔离的划分判据

判据是这个状态描述的是全局事实还是局部事实。全局事实对所有作用域成立，局部事实只对某个子树成立。

| 状态 | 类别 | 放置位置 | 放错的后果 |
|---|---|---|---|
| 代码版本、启动时间 | 全局事实 | 根作用域 | 各存一份会出现不一致 |
| 连接池、资源配额 | 全局事实 | 根作用域 | 各存一份会让资源翻倍 |
| 核心工具定义、配置 | 全局事实 | 根作用域 | 重复定义会漂移 |
| 会话历史、工作目录 | 局部事实 | 会话作用域 | 放全局会造成串扰 |
| 当前任务的临时状态 | 局部事实 | 任务作用域 | 放会话级会在任务间残留 |
| 用户凭据 | 局部事实（按用户） | 用户作用域 | 放会话级会重复取；放全局会串用 |

这张表的用法是在新增一处状态时问一次"它对谁成立"。第二列的价值在于它比"全局还是局部"更具体："按用户成立"这一类在单用户时看起来像全局，而它在多用户时是局部的，因此判断时要问"如果明天有第二个 X，这个状态该不该分开"。

第三列给出的失败形态值得记住：全局事实放错会产生不一致（两条会话报不同的版本号），局部事实放错会产生串扰（会话 A 看到会话 B 的数据）。两者的排查方式不同——前者靠对比两个作用域的值，后者靠找共同的外部引用。

### 1.4 生命周期与退出撤销

作用域的生命周期有明确的时刻：创建、可用、退出。退出时的动作是撤销它内部登记的全部 effect，顺序与注册相反（2.3 的理由相同）。

这里有一处与 2.3 不同的地方：作用域退出时，它的子作用域应当先退出。这个顺序不是可选的——子作用域的注册可能依赖父作用域的服务，反向退出会让子作用域在退出过程中访问到已经失效的服务。实现方式有两种：要求调用方显式地按深度退出（简单，容易写错），或者在父作用域退出时自动遍历子作用域（安全，成本是一次遍历）。

```ts
async function dispose(scope: Scope): Promise<Error[]> {
  const failures: Error[] = []
  for (const child of [...scope.children].reverse()) {   // 先退子
    failures.push(...(await dispose(child)))
  }
  failures.push(...disposeAll(scope.effects))            // 再退自己
  return failures
}
```

这段代码里 `[...scope.children].reverse()` 中的展开是必要的：撤销过程会修改 `children` 集合，直接遍历它会在迭代中改变被遍历的对象。

### 1.5 作用域与依赖注入的关系

Fowler 在讨论容器时把生命周期分成了几类：单例（整个进程一份）、会话级（每条会话一份）、请求级（每次请求一份）。这几类在本篇的术语里对应"注册在哪个作用域"。

单例对应注册在根作用域。会话级对应注册在会话作用域。请求级对应注册在任务作用域。Fowler 的分类与本篇的机制是同一件事的两种表述，而本篇的机制更灵活：作用域的嵌套层数不受限，因此"按租户、按会话、按任务"三层可以同时存在。

这条对应关系有一个实用推论：当有人问"这个服务该是单例还是请求级"时，问题可以改写成"它描述的事实对谁成立"。答出后者，前者就确定了。

### 1.6 约定隔离与强制隔离

作用域提供的是约定隔离：它让"正确地取用能力"成为最方便的路径，但它不阻止一个模块绕过上下文直接 import 全局对象。这个区别必须写清楚，因为它决定了这套机制的适用范围。

强制隔离需要系统能力的支持：进程边界、容器命名空间、或者访问控制列表。“第 3 卷的沙箱”处理的是这一层，它解决的是"一个不可信的部件能做什么"，而作用域解决的是"一个可信的部件默认看到什么"。

两者的关系可以这样表述：作用域让正确做法成为默认，沙箱让错误做法成为不可能。前者成本低且覆盖大多数情形（本课程的部件都由同一作者编写），后者成本高且只在面对不可信输入时才需要。混淆两者的后果是把约定的隔离当成安全边界，从而在真实威胁面前失去防护。

### 1.7 跨作用域的通信

隔离一旦建立，随之而来的是"如何在不破坏隔离的前提下共享"。三种做法各有代价。

第一种是提升到父作用域：把需要共享的东西注册在共同祖先上。它最简单，代价是共享的东西必须对所有后代可见（无法只给一部分）。

第二种是显式传递：父作用域在构造子作用域时把需要的东西传进去。它精确，代价是构造参数会随需求增长，且它绕过了查找机制（因此依赖不可静态读出）。

第三种是通过事件通信：一方发出事件，另一方监听。它解耦，代价是引入了 2.4 分析过的那些问题（顺序、短路、缺失不可检测），而且事件是单向的（需要请求-响应时还要再造一条反向通道）。

本课程的选择是第一种为主、第二种用于少数明确需要精确控制的场合。判据是"这个共享关系是结构性的还是偶然的"——结构性共享（所有人都需要配置）用父作用域，偶然共享（这两个模块恰好在这次装配里需要互通）用显式传递。

### 1.8 两次追问

工程侧的问题是作用域的层数该有多少层。层数越多，隔离越细，而查找与装配的复杂度也越高。经验值是三层：根（全局事实）、会话（会话事实）、任务（任务事实）。第三层之所以必要，是因为有些状态的生命周期短于会话——例如一次任务中间产生的临时文件索引，它在任务结束后就该消失，而如果它挂在会话上，长时间运行的会话会累积它们。

产品侧的问题是隔离粒度对用户意味着什么。按进程隔离时，一个用户的操作会影响另一个用户（他们共享同一个工作目录）。按会话隔离时，不同用户之间互不影响，但同一用户的两条会话之间也不影响（有时这不是期望的）。按用户隔离时，同一用户的多条会话可以共享记忆与配置。因此隔离粒度的选择实际上是在回答"什么东西应该在用户之间共享"——它既是技术决定，也是产品决定。

### 1.9 作用域与配置的关系

作用域层次与配置分层是同一件事的两种表达。配置系统里"根配置、会话配置、任务配置"的三层，落到运行时就对应三个作用域的注册集合。而配置里的"覆盖"语义与查找里的"子优先"语义是同一条规则。

这个对应关系有一个实用推论：配置的合并语义不需要单独设计，它由作用域的查找规则决定。如果查找是"子优先、命中即止"，那么配置的覆盖就是"深度最近的那一份生效"。如果查找支持合并（把父与子的同名配置按字段合并），那么配置的语义就从覆盖变成了深合并。前者的行为容易预测（只有一份生效），后者的表达力更强但更难推断（需要知道每一层各写了什么）。

第 2.6 篇会在这两者之间做选择，而本篇提供的正是它的物理基础。

另一个推论与调试有关：当配置不生效时，第一个要回答的问题是"这个值最终来自哪一层"。作用域的查找路径给出了这个答案，因此实现应当把"命中在哪个作用域"记录下来供查询——这正好是 1.2 里查找失败信息带层数的那条设计的镜像。

### 1.10 作用域的可观测性

作用域是排查多会话问题的第一现场，因为"这条会话看到了什么"完全由它的作用域链决定。三个查询入口值得在设计时就留出来。

第一个是列出某个作用域里的注册与它的子作用域。它回答"这条会话有自己的什么"，是从"数据看起来不对"出发排查时的第一步。

第二个是回答"这个名字是从哪一层来的"。它与第一个的区别是它带有一次具体的查找路径：同一个名字在根与会话级都存在时，这条查询能立刻说明当前生效的是哪一个。缺少它时，排查者需要人工比较两层的配置，而比较在层数增长后会变得容易出错。

第三个是统计每个作用域的注册数量与子作用域数量。它是长时间运行时的健康指标：某个会话作用域的子作用域数量持续增长，通常意味着任务级作用域没有被正确退出——这是泄漏最早可见的形态，比等到内存增长要早得多。

三个入口体现的仍是同一条原则：机制应当自带它自己出问题时的观察方式。作用域尤其需要，因为它的状态（可见什么）不是从代码里能读出来的，而是由运行时创建与注册决定的。

### 1.11 作用域的测试策略

作用域的缺陷有一个共同特征：它们在单会话测试里不存在。因此这一层需要三类专门的测试。

第一类是层次测试：在父、子、兄弟三个位置各注册服务，检查可见性矩阵。它覆盖的是查找规则本身，包括覆盖方向与隔离标记这两条例外。

第二类是交错测试：创建两个兄弟作用域，让它们交替读写同名服务，检查结果互不影响。这一类的关键在于"同时存活并交替操作"——只建一个再销毁一个的测试无法发现共享引用的缺陷，因为共享的引用在只有一个使用者时是安全的。

第三类是退出测试：退出一个作用域后检查三件事，服务不再可见、监听器不再响应、资源已释放。第三件事最容易被省略，而它正是长时间运行时的泄漏来源。

三类测试的分布与 2.4 的事件测试策略是同构的：第一类覆盖机制、第二类覆盖隔离的语义、第三类覆盖退出。跨篇的测试策略在形状上一致，这不是巧合——它们覆盖的都是"必须长期正确运行"的机制所共有的三类性质。

|---|---|---|---|---|
| 1 | 作用域的层数 | 三层：根、会话、任务 | 一层（全局）/ 两层 | 层数多则装配复杂；换来隔离粒度可控 |

| 11 | 作用域能否被查询 | 可以（列出注册与子作用域） | 不暴露 | 暴露内部结构；换来可诊断 |
| 12 | 会话结束后作用域的处置 | 退出并撤销全部 effect | 保留复用 | 复用省一次装配；换来状态不会残留 |

### 关于第 5 条的完整论证（判据为什么必须是"事实对谁成立"）

替代方案是"按实现方便"：哪个位置写着顺手就放在哪。它在单会话系统里完全可用，而在三种情形下出错。

第一种是资源重复。连接池、缓存、工作目录这类东西放在会话级会导致每个会话建一份，而它们的数量应当是进程级的——一个进程开五十个连接池不是可用性问题，而是资源问题。

第二种是串扰。反过来，把会话历史这类东西放在全局，第二条会话会看到第一条的数据，而它的表现形式是"输出里混进了别人提过的问题"。

第三种是同一用户的多条会话该不该共享记忆。这个问题的答案不是技术性的——同一用户希望他的两条会话共享他对项目的偏好，但不希望它们共享"刚才那次任务做到一半的状态"。理解这一点的唯一途径是把状态按"对谁成立"分层：偏好对用户成立（用户级作用域），任务中间状态对任务成立（任务级作用域）。

这条判据的完整形式是三个问题：这个事实对全体成立吗（根）、对某条会话成立吗（会话）、还是只对这一次任务成立（任务）。“明天如果多一个同类对象，它该不该跟着分开”是它的操作化表述。

### 关于第 12 条的完整论证（会话结束后为什么不复用作用域）

替代方案是保留会话作用域并复用它（下一条会话来的时候清空重用）。它的好处是省掉一次装配（注册核心服务、构建查找结构），在装配成本高时这个收益可观。

代价有两个。第一个是残留。复用意味着"清空"必须彻底，而彻底清空与重新创建相比更难保证——清空是减法，任何一处遗漏都会让上一次的状态活到下一次，而这类缺陷的表现是"第二条会话继承了第一条的某个设置"。第二个是归属判断失效。作用域标识是归属判断的依据，复用它意味着两个不同会话的注册共享同一个标识，于是撤销时无法区分它们的记录。

重新创建的成本是一次装配，而它的收益是状态边界清晰：新会话的作用域里没有任何上一次的东西，归属判断也精确。因此本课程的选择是"退出而非复用"，并把装配成本交给 2.6 的配置组合去优化（高效的装配应当在毫秒级完成，而不是靠复用对象回避它）。

## L3 实现（施工图）

### 3.1 文件结构

```
// kernel/scope.ts
// ┌─ 身份段 ──────────────────────────────────────────
// │  Scope：身份、父引用、子集合
// ├─ 注册段 ──────────────────────────────────────────
// │  provide / on（登记进当前作用域的 effect 列表）
// ├─ 查找段 ──────────────────────────────────────────
// │  require(name)：沿父链向上，遇到隔离标记则停止
// ├─ 生命周期段 ──────────────────────────────────────
// │  create(parent)：创建子作用域
// └─ 撤销段 ─────────────────────────────────────────
//    dispose(scope)：先子后父，内部逆序，失败汇总
```

五段与 2.3 的容器是同一形状，差别在"查找段"多了一条父链与一条隔离例外，以及"撤销段"多了一层对子作用域的递归。

### 3.2 作用域的身份与父子关系

```ts
interface Scope {
  readonly id: object                    // 身份：归属判断的依据
  readonly parent: Scope | null
  readonly children: Set<Scope>
  readonly effects: Array<() => void>     // 按注册顺序记录
  readonly entries: Map<string, ServiceEntry>
}
```

`children` 用集合而不是数组，理由是退出时要按"后创建的先退"处理，而集合的插入顺序在 JavaScript 里是稳定的——这让我们既能按顺序遍历，又能在退出时安全地删除元素（配合 1.4 那段展开成数组再反转的写法）。

### 3.3 查找与隔离标记

```ts
function require<T>(scope: Scope, name: string): T {
  const visited: string[] = []
  let cur: Scope | null = scope
  while (cur) {
    const entry = cur.entries.get(name)
    if (entry) return entry.impl as T
    visited.push(String(cur.id))
    if (cur.isolatedNames?.has(name)) break     // 隔离标记：停止向上
    cur = cur.parent
  }
  throw new Error(`服务 ${name} 未找到；已查作用域 ${visited.length} 层`)
}
```

这段代码里有两处值得指出。第一处是 `visited` 的用途：它让错误信息能说出"查到了哪一层为止"，而这在嵌套三层时的排查价值很高。第二处是隔离标记的判断位置——它在"当前层没找到"之后、进入父层之前，因此它的语义是"这个名字不参与向上查找"，而不是"这个名字隐藏了父作用域的实现"。

### 3.4 创建与退出的完整实现

创建子作用域只有一个关键点：它必须在父作用域的 `children` 里登记自己，否则父作用域退出时无法递归到它。退出的实现（1.4 已给骨架）要处理三件事：先退子作用域、逆序执行自己的 effect、把所有失败汇总返回。

### 3.5 验收判据

| # | 判据 | 怎么检查 |
|---|---|---|
| 1 | 子作用域能查到父作用域的服务 | 在父层注册，在子层查 |
| 2 | 兄弟作用域互相查不到 | 在 A 注册，在 B 查应当失败 |
| 3 | 同名的服务子作用域优先 | 父与子各注册一个同名服务，查子作用域得到子的实现 |
| 4 | 隔离标记能阻止向上查找 | 给某名字加标记，子作用域查它应当失败，即使父层有 |
| 5 | 查找失败的错误信息含层数 | 查不存在的名字，核对错误信息 |
| 6 | 退出时先撤销子作用域 | 父子里各注册一个记录顺序的 effect，退出父，核对子先执行 |
| 7 | 同一个作用域内按逆序撤销 | 注册三个记录顺序的 effect，核对顺序相反 |
| 8 | 某个 effect 抛错时其余仍然执行 | 让中间那个抛错，检查其余都被执行 |
| 9 | 退出之后该作用域的服务不再可见 | 退出后从父作用域查子作用域注册的名字应当失败 |
| 10 | 退出之后它的监听器不再响应 | 注册一个监听器，退出，广播，核对未被调用 |

第 8 与第 10 条是两条最容易漏的判据：前者检验失败隔离，后者检验"撤销集中到一处"这条原则的落实。第 10 条尤其重要，因为它跨了两篇的机制（作用域与事件），而跨越机制的缺陷最容易在实现时被漏掉。

### 3.6 实现顺序

先做身份与父子关系（判据 1、2），再做查找与覆盖（判据 3、5），然后做隔离标记（判据 4），最后做退出与失败汇总（判据 6、7、8、9），第 10 条在事件系统接上来之后检查。

### 3.7 与事件系统的集成：监听器的作用域归属

监听器挂在事件系统上，而它属于哪个作用域由注册它的上下文决定。集成的关键只有一条：注册时把当前作用域作为归属记下来，退出时按作用域撤销。

```ts
// 注册：把当前作用域一起记下来
export function on(ctx: Context, name: string, fn: Listener, priority = 0): void {
  const off = bus.register(name, fn, priority, ctx.scope)   // 归属 = 当前作用域
  ctx.scope.effects.push(off)                               // 退出时统一执行
}
```

这段代码里有两个容易漏的地方。第一，归属记录的粒度是作用域而不是上下文对象：同一个作用域里可能创建了多个上下文（例如一个部件临时创建子上下文来注册几样东西），而它们的退出时机相同。第二，`off` 必须进 `effects` 而不是被返回给调用方保存——后者在调用方忘记保存时变成泄漏（2.4 已讨论过这条取舍）。

作用域退出时，事件系统的监听器随其它 effect 一起被撤销，顺序由 effects 数组的逆序决定。这个顺序意味着后注册的监听器先被摘掉，而如果某个监听器依赖另一个（例如一个汇总监听器读另一个监听器写的状态），逆序恰好是先摘依赖者——与 2.3 的撤销顺序是同一条理由。

### 3.8 实现里最容易写错的三处

第一处是查找的终止条件。正确写法是在"当前层没命中且当前层没有隔离标记"时继续向上。常见错误是把隔离标记的判断放在命中之前，于是被标记的名字会连本层的注册都查不到。

第二处是退出的递归与顺序。正确写法是先递归子作用域再执行自己的 effect，且遍历子作用域时要先把它展开成数组（撤销会修改集合）。漏掉展开会在迭代中改变被迭代的集合，表现为"某个子作用域没有被退出"——而它在子作用域数量较少时可能不出现。

第三处是失败的汇总方式。正确写法是逐个捕获、继续执行、最后返回失败列表。常见错误是让第一个失败中断整条清理链，结果是"部分清理"，而这种状态比完全没清理更难排查——因为残留的一部分看起来像是全部清理完成了。

### 3.9 一次会话的完整生命周期

把本篇与前后几篇串起来，一条会话从创建到结束的完整序列如下（括号里是责任方）。

```
创建根作用域          （进程启动时一次）  共享：配置、资源池、核心工具
创建会话作用域        （收到新会话时）    隔离：历史、工作目录、会话级工具
注册会话的服务与监听  （会话初始化）      全部记入会话作用域的 effects
创建任务作用域        （每次任务开始）    隔离：本次任务的临时状态
任务结束，退出任务作用域（任务结束时）    只撤销任务级注册，会话级不受影响
会话结束，退出会话作用域（会话关闭时）    撤销会话级注册，根的注册保留
进程退出，退出根作用域（进程关闭时）      撤销全部
```

这张清单有三个用途。第一，它说明每一层该撤销什么——任务级作用域退出时不得影响会话级，这是"先子后父"这条规则的实际意义。第二，它给出泄漏的检查点：如果任务结束后任务级注册没有消失，那么在长时间会话里它们会累积。第三，它是第 5 卷多会话的实现草案——多会话只是把"创建会话作用域"这一步重复多次，而隔离的正确性由本篇的判据保证。

### 5.3 三条容易踩的规则

第一条，共享还是隔离看"事实对谁成立"，不看实现方便。放错的两种后果分别是资源重复与串扰。

第二条，退出要连同子作用域一起退，且先子后父。只退自己不退子是泄漏，先父后子会让子作用域在退出时访问到已失效的服务。

第三条，隔离是约定而不是边界。绕过上下文直接 import 全局对象就能破坏它，因此它是给可信部件用的便利机制，不是安全机制。

## L7 挑战题（不给答案）

第一题：给隔离标记设计一套命名规则。 现在它是一个自由的标记，容易被滥用。设计一套规则，限制它只能用在哪类服务上，并说明违反时如何被检查。

第二题：设计跨作用域的请求-响应。 子作用域需要向父作用域请求一次数据并等待结果。给出方案，并说明它为什么不破坏隔离。

第三题：作用域与并发的交互。 两个作用域并发操作共享的父作用域资源时，如何保证不变量（例如连接池的上限）。给出你选择的机制与代价。

第四题：设计作用域的"部分退出"。 某些 effect 的生命周期短于整个作用域（例如某次任务期间注册的定时器）。给出机制，并说明它与任务级子作用域的区别。

第五题：论证"作用域不该有隔离标记"。 构造一个场景，说明只用层次结构就能表达全部隔离需求，而标记是多余的。

第六题：多租户的隔离方案。 同一个进程里跑三个租户，各自有独立的配置、记忆与配额。设计作用域层次，并说明哪些状态必须放在根。

## L9 仍未解决（这一篇自己的缺陷）

| 缺陷 | 后果 | 修法 | 当初为什么这么写 |
|---|---|---|---|
| 隔离是约定的，绕过上下文即可破坏 | 一个直接 import 全局对象的模块会让隔离失效 | 引入 lint 规则或沙箱（第 3 卷） | 沙箱的成本高，且本卷的部件都由同一作者编写 |
| 没有跨作用域的请求-响应机制 | 子作用域需要父作用域的数据时只能靠提升或事件 | 设计一种显式的"向上询问"协议（挑战题第二题） | 需求在第 2 卷还不明显 |
| 作用域数量增长后没有回收策略 | 长时间运行的进程里，退出的作用域若被外部引用就泄漏 | 引入弱引用或显式的"已退出"检查 | 本卷的会话数量有限 |
| 查找的层数没有上限 | 深层嵌套会导致查找变慢且难以理解 | 规定最大深度并在超过时报警 | 实际深度不超过三层 |
| 没有并发保护 | 两个作用域同时注册进同一个父作用域时，父子集合的读写没有同步 | 引入锁或规定注册只发生在启动阶段 | 单线程的循环不会并发注册 |
| 隔离标记没有配套的检查 | 标错会导致查找永久失败，而失败信息里没有说明原因 | 在错误信息里带上"因隔离标记而停止" | 标记的语义是"不参与向上查找"，原因来自注册方而非查找方 |

第一条属于"位置放错"——强制隔离本该在系统层而不是这一层解决。最后一条属于诊断信息缺失。其余四条属于边界与能力缺失。第一条值得单独标记：这一篇的机制之所以被称作"约定隔离"，是因为它依赖调用方不绕过，而这条依赖在代码评审之外没有任何强制手段。

| ambient authority 会让权限判断失去依据 | 确认，并指出它与第 3 卷守卫的关系（守卫需要"谁在调用"这个输入） | 成立 |
| 作用域泄漏的表现与原因隔很多层 | 确认，并给出排查方向（找共同的外部引用而非检查对象数量） | 成立 |

一处需要修正的预判：0.5.2 把"退出撤销"标为中等强度依赖。读完之后要提高：它是本卷"最小闭环"能否成立的组成部分——如果作用域退出不彻底，第 2.7 篇的会话结束后会留下监听器与定时器，而第 5 卷的多会话会让这些残留按会话数成比例增长。因此它不是"以后再说"的清理细节，而是本卷必须做对的一处。

通向下一篇的桥。 本篇给出了隔离的机制，而它留了一个没有答案的问题：这些作用域从哪里来、按什么规则组装。一个进程要建几个作用域、每个作用域里装什么、配置里的覆盖怎么落到层次上——这些问题的答案不在本篇。

下一篇 `2.6 装配与配置组合` 处理这件事。它与本篇的连接点是覆盖：本篇定义的作用域层次是"谁来覆盖谁"的物理基础，而配置的合并语义是它的逻辑表达——没有作用域层次，配置的覆盖就只能是一层平铺的键值覆盖，而无法表达"这个会话覆盖了这条默认配置"。

### 二、情境绑定：当你……就想起……

| 当你…… | 立刻想起 |
|---|---|
| 要新增一处状态 | 先问它对谁成立：全体、某条会话、还是某次任务 |
| 想把状态放进全局 | 问"明天多一个同类对象时它该不该分开" |
| 发现两条会话的数据混在一起 | 找共同的外部引用，而不是检查对象有没有各建一份 |
| 需要多方共享一份数据 | 提升到共同祖先，而不是让各处 import 全局 |
| 要给某个服务加隔离标记 | 先看层次结构能否表达；标记会让查找规则多一条例外 |
| 作用域退出时想省掉子作用域的遍历 | 不能省：只退自己不退子是泄漏 |
| 退出过程中有一个 effect 抛错 | 逐个捕获并汇总，让其余清理继续 |
| 想复用一个作用域省装配成本 | 先优化装配本身；复用会让归属判断失效 |
| 有人问你的隔离是不是安全边界 | 明确回答"约定不是强制"，并指出真正的边界在哪一层 |
| 怀疑有泄漏 | 退出后广播一次事件，看有没有回应 |

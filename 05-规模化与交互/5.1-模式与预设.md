## 读完这一篇你会知道什么

1. **四层覆盖**：内置 → 项目 → 用户 → 会话，越具体优先级越高。
2. 来源追踪：算例里并发数 8 来自用户级、超时 60000 来自项目级，且来源追踪覆盖全部键（`true`）。
3. 来源表的规模：算例里是 3 个键。
4. 深合并与数组替换：对象深合并保留 2 个键。数组整体替换后不含下层被删除的元素（`true`）。
5. 预设与模式：预设是"一组配置的命名集合"，模式是"行为的整体切换"。
6. 工业界怎么做：编辑器配置、IDE 配置档案、企业策略、云资源的默认值。
7. 学术界：配置管理、策略分层、可解释性。

## 一、为什么预设需要来源追踪

### 1.1 不知道值来自哪

"为什么超时是 60 秒？"没有人知道。**因为四个地方都可能设过它。**

### 1.2 覆盖方向搞错

项目配置被用户配置覆盖了。**但项目配置是团队约定，本应优先于个人偏好。**

### 1.3 数组被合并

用户只想用一个工具，写了个单元素数组，结果与项目配置合并后变成了三个。**范围比预期更宽。**

这三件事分别对应：**来源追踪、层序、数组语义。**

## 二、四层覆盖

| 层 | 来源 | 特点 | 优先级 |
|---|---|---|---|
| **内置** | 随程序发布 | 保证能跑 | 最低 |
| **项目** | 仓库里的配置文件 | 团队约定、随代码评审 | 中 |
| **用户** | 用户主目录 | 个人偏好 | 中高 |
| **会话** | 本次会话显式指定 | 临时调整 | 最高 |

优先级的设计依据：**越具体越高，但"项目约定"往往应当高于"个人偏好"**——所以实际排序是内置 < 用户 < 项目 < 会话（把项目放在用户之上）。

这是一条需要明确写下来的决定：两种排序都合理，**但必须选一个并说清楚**。

## 三、怎么做

### 3.1 四层及其优先级

实现如下。

```js
// 四层覆盖：按优先级从低到高合并，并记录每个键的来源
export function resolveConfig(layers) {
  const order = ['builtin', 'user', 'project', 'session']
  let value = {}
  const source = new Map()
  for (const name of order) {
    const layer = layers[name] ?? {}
    value = merge(value, layer)
    for (const key of flatKeys(layer)) source.set(key, name)
  }
  return { value, source }
}
```

算例实测：

| 配置项 | 生效值 | 来源层 |
|---|---|---|
| 并发数 | **8** | **用户级** |
| 超时 | **60000** | **项目级** |

**两个值来自不同的层**，这正是来源追踪要解决的问题：同一份有效配置里，不同的键可能由不同的层贡献。

### 3.2 来源追踪

算例验证：**"来源追踪是否覆盖全部键"为 `true`，来源表的键数是 3**。

为什么这条性质必须成立：**如果有键没有被追踪，那么它的来源就是未知的**——排障时你会卡在"这个值是谁设的"上。

来源追踪的实现要点：

| 要点 | 说明 |
|---|---|
| 记录**最终来源** | 而不是所有设过它的层 |
| 覆盖所有键 | 包括深层嵌套的键 |
| 与合并同时进行 | 否则会不一致 |
| 可展示 | 给人看的界面或命令 |

"记录最终来源"而不是"历史"：排障时问的是"**现在这个值是谁定的**"，而不是"历史上谁改过"。历史属于变更管理（4.5），当前来源属于配置解析。

"包括深层嵌套的键"容易被漏：算例里"深层键的来源层是项目级"——**如果只追踪顶层键，深层键的来源就查不到。**

### 3.3 数组替换

算例实测：**数组整体替换后的长度是 1**，且"数组替换后不含下层删除的元素"为 `true`。

第二条是本篇值得单独讲的性质：**替换意味着"这一层说是什么就是什么"**，下层的内容不会残留。

为什么这一点重要：如果数组做元素级合并，**上层就无法"减少"元素**（1.3 就是这种情况）。

判据：**层叠系统里的数组必须支持"删减"，而只有整体替换能做到删减。**

**需要的追加语义**要显式命名（例如 `extraTools`），而不是靠合并规则决定（与 2.6 一致）。

### 3.4 预设与模式

两个相关的概念需要区分：

| 概念 | 含义 | 例子 |
|---|---|---|
| **预设（preset）** | 一组配置的**命名集合** | "写作模式" = 低温 + 长输出 |
| **模式（profile）** | **行为的整体切换** | "只读模式" = 禁用写工具 |
| **层（layer）** | 配置的**来源** | 项目配置 |

三者的关系：**预设是一组值，模式可能改变可用能力，层决定优先级。**

模式比预设更强：**它不只是改参数，还可能改变"有哪些工具可用"**（对应 3.2 的能力隔离）。

设计建议：

| 建议 | 理由 |
|---|---|
| 预设用配置表达 | 可合并、可覆盖 |
| 模式用开关表达 | 需要能快速切换 |
| 模式名要稳定 | 脚本与会话日志会引用它 |
| 模式的效果要可列举 | 否则用户不知道切换后会怎样 |

最后一条最实用：**切换模式时必须能列出"会发生什么变化"**。做不到这一点，模式就是一个黑箱（与 4.3 的可解释性要求一致）。

### 3.5 冲突诊断

有了来源追踪，就可以给出可读的冲突诊断：

```js
// 诊断：列出被上层覆盖的值，用于回答"为什么不是我以为的值"
export function explain(config, key) {
  const info = config.source.get(key)
  return info
    ? { key, value: get(config.value, key), from: info }
    : { key, error: '该键未被任何层设置' }
}
```

"该键未被任何层设置"也是一个有用的答案：它把"值不对劲"分成两类——**设错了**与根本没设。

`explain` 的输出形式建议：`并发数 = 8（来自用户配置）`。**一行就能回答排障中最常见的问题。**

## 四、特殊情况与处理技巧

| 情况 | 为什么 | 处理 |
|---|---|---|
| 不知道值来自哪 | 无来源追踪 | 合并时同步记录来源 |
| 深层键来源查不到 | 只追踪顶层 | 追踪所有键（含嵌套） |
| 数组无法删减 | 元素级合并 | 整体替换 |
| 项目约定被个人覆盖 | 层序定错 | 明确层序并写进文档 |
| 模式切换后果不明 | 不列举效果 | 切换时列出变化 |
| 预设互相冲突 | 多个预设同时生效 | 定义预设的互斥关系 |
| 值消失了 | 上层设了 `null` | 明确 `null` 与未设置的语义（与 2.6 一致） |
| 来源表与实际不一致 | 追踪与合并分离 | 同一个函数内完成 |

"预设互斥"值得展开：**两个预设同时生效时，它们的值可能互相矛盾。** 稳妥做法是把预设分成互斥的类别（例如"输出风格"只能选一个），而不是让它们自由叠加。

## 五、工业界的做法（可照做）

### 5.1 分层配置的实例

| 系统 | 层 | 特点 |
|---|---|---|
| **编辑器配置** | 默认 → 用户 → 工作区 → 文件夹 | 越具体越高 |
| **IDE 配置档案** | 命名的一组设置 | 一键切换 |
| **企业策略** | 组织策略强制覆盖个人 | **上级可以强制** |
| **云资源默认值** | 平台默认 → 账户 → 资源 | 资源最具体 |
| **容器编排** | 镜像默认 → 部署 → 覆盖 | 可命令行覆盖 |

"上级可以强制"这一条值得注意：企业策略里有些项**不允许下级覆盖**。这需要在层叠规则里增加"锁定"标记。

锁定标记是本篇的一个合理扩展：`{ value: 8, locked: true }` —— **锁定后下层设置无效，并且应当报错提示**（而不是静默忽略）。

### 5.2 预设的设计原则

| 原则 | 说明 |
|---|---|
| 名字表达用途 | "只读"比 "profile-3" 好 |
| 效果可列举 | 切换时能列出变化 |
| 数量少 | 3–6 个足够 |
| 可组合性明确 | 互斥还是叠加 |
| 可扩展 | 用户能定义自己的预设 |

"数量少"很关键：**预设太多会导致"该选哪个"的困惑**——与 2.2 的工具数量、4.2 的技能数量是同一个约束。

### 5.3 参数与设计起点

| 参数 | 推荐 | 依据 |
|---|---|---|
| 层数 | 3–4 层 | 再多难追踪 |
| 预设数量 | 3–6 个 | 多了选择困难 |
| 来源追踪 | 全部键 | 见 3.2 |
| 数组语义 | 整体替换 | 支持删减 |
| 锁定项 | 少量且明确 | 企业策略、安全相关 |
| 诊断输出 | 一键命令 | 排障必需 |

### 5.4 一份可落地的实施清单

1. **四层**：内置、用户、项目、会话，层序写进文档。
2. 来源追踪：合并时同步记录，覆盖全部键（含嵌套）。
3. 数组替换：整体替换，追加走独立字段。
4. 空值语义：`null` 与未设置分开定义。
5. 锁定：需要强制的项加锁并报错。
6. 预设：3–6 个，名字表达用途，效果可列举。
7. 互斥：同一类别的预设互斥。
8. 诊断命令：能查询任一键的最终值与来源。
9. 模式切换提示：列出会发生的变化。
10. 测试：层序、数组替换、来源覆盖、锁定四条各一例。

## 六、学术界的结论

### 6.1 配置管理的既有结论

配置管理研究的核心发现是：**大部分配置错误来自"实际生效的值与预期不符"**，而不是"值本身非法"。

两类做法：

| 做法 | 作用 |
|---|---|
| **静态校验** | 检查值是否合法（类型、范围） |
| **溯源与展示** | 让人看到"为什么是这个值" |

第二类被长期低估：**一个能回答"这个值来自哪"的系统，比一个只报"值非法"的系统有用得多。**

**这正是本篇把来源追踪作为核心的原因。**

### 6.2 策略分层与优先级

策略系统（访问控制、合规）里的分层与优先级是成熟领域，几条可借鉴的规则：

| 规则 | 内容 |
|---|---|
| **显式拒绝优先** | 拒绝比允许优先（保守） |
| **越具体越优先** | 具体策略覆盖一般策略 |
| **可强制** | 上级策略可锁定 |
| **可解释** | 能说出"哪条策略导致了这个结果" |

"显式拒绝优先"与 3.2 的默认拒绝是同一原则：**冲突时向安全一侧倾斜。**

### 6.3 可解释性

可解释性研究的一条实践结论：**"为什么"比"是什么"更能建立信任**。

在配置上的体现：**用户对系统的信任来自"我知道它为什么这样"，而不是"我知道它现在这样"。**

实践手段：**任何自动决定的值，都应当能回答"为什么是这个值"。** 这与 4.1 的"记忆必须带来源"、4.3 的"注入时标注可信度"是同一条纪律的第三次出现。

### 6.4 组合爆炸与最少惊讶

预设系统的风险是**组合爆炸**：$n$ 个预设若可自由组合，就有 $2^n$ 种状态，每一种都可能有 bug。

"最少惊讶原则"给出的对策：

| 对策 | 说明 |
|---|---|
| 减少可组合维度 | 互斥类别 |
| 提供少数整体预设 | 而不是大量细粒度开关 |
| 效果可预期 | 切换前能列出变化 |

**这与 3.2 的"参数表给起点而不是给全部旋钮"是同一个思路**：暴露的配置项越多，用户的认知负担与出错概率越高。

## 七、理论：来源函数

### 7.1 来源的完备性

$$
\forall k \in \text{keys}(\text{有效配置}) : \text{source}(k) \ne \bot
$$

算例验证：**"来源追踪是否覆盖全部键"为 `true`**。

含义：**任何生效的值都能被追溯到某一层。** 这是可诊断性的前提（与 4.4 的"可诊断性"呼应）。

### 7.2 数组替换与删减能力

$$
\text{替换} \Rightarrow \text{上层可减少元素}
$$

算例验证：**数组整体替换后不含下层被删除的元素**（`true`）。

含义：**只有整体替换才支持"收窄"语义**。元素级合并只能增加（1.3 的权限变宽就是这么来的）。

这条性质的可检查形式：给定下层 `["a","b"]` 与上层 `["a"]`，结果必须是 `["a"]` 且长度 1。

## 十、算例

算例实现了本篇的四层覆盖与来源追踪。

```powershell
cd D:\dsh-course
node examples/sa39_profiles.mjs        # 全部函数的运行结果
node examples/test_sa39_profiles.mjs   # 数字回归断言
```

它做到的事：

- **四层覆盖**（并发 8 来自用户级、超时 60000 来自项目级）。
- 对象深合并后保留的键数与深层键的来源层。
- 来源追踪覆盖全部键（`true`）与来源表的键数（3）。
- 数组整体替换（长度 1）与不含下层被删除的元素（`true`）。

这一篇只要记住一句：预设系统必须**来源可追溯**——每个生效的值都能回答"来自哪一层"。数组必须整体替换（否则无法收窄），而"越具体的层优先"这条规则要明确写下来，因为它有两种都合理的排法。

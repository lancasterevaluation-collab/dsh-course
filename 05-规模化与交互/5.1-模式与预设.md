## 本篇新词

- 模式（profile） 指一组能力的声明式组合：启用哪些插件、每者用什么配置、对外暴露什么入口。
- 预设（preset） 指一个 agent 的组成方式：指令基线、工具集、技能集、模型选择。
- 覆盖顺序（override order） 指多个来源的优先级序列。本课程是四层。
- 隐式默认（implicit default） 指没有被任何一层写出来的取值。
- 启动校验（startup validation） 指启动时检查模式是否自洽：引用的插件存在、字段合规、必需能力齐备。
- 模式切换（profile switching） 指运行期间改变生效的模式。
- 能力集（capability set） 指一个模式实际提供的能力总和，**含间接启用的部分**。

## 一、【设计原因】

### 1.1 缺陷一：同一条命令在另一台机器上行为不同

本地的模式跑得好好的，而在服务器上并发过高、超时过短或某个能力缺失——因为那份声明没有写出这些取值，而它们的默认值在两处不同。

如果记录了每个取值的来源层，差异可以立刻定位到"这一层没写、取了框架默认"。没有来源追踪时，排查要在若干配置文件与代码常量之间来回找。

### 1.2 缺陷二：能力集散落在多处，看不出全貌

插件列表在一个文件、配置在另一个、某些能力由环境变量开启，而"这个模式到底提供什么"没有人能一次说清。

后果有两个：校验做不到（不知道完整的期望集），以及组合爆炸不可见。

### 1.3 缺陷三：切换模式之后有残留

切换之后旧模式注册的工具、技能、钩子仍在生效——表现是某些能力出现两份，或者某个旧配置继续影响行为。

成因是释放不完整，或切换的实现方式是部分重新装配而不是整体切换。

### 1.4 缺陷四：配置错了，而在用到它的时候才发现

缺失的插件、字段类型错误、互相冲突的两项配置——它们在启动时没有被发现，而是在第一次用到那个能力时失败，或者更糟：静默地用了默认值。

### 1.5 由此确定的设计目标

1. 一处声明：插件、配置、入口、必需能力全部写在一个可 diff 的文本里。
2. 覆盖顺序写下来：四层，且每个取值的来源可查。
3. 消灭隐式默认：必填项没有默认值，次要默认可见，禁止运行时环境推断。
4. 启动校验三层：声明、能力集、可选探测。
5. 切换整体进行，并在切换后核对残留。

**本节要点**

- 没有来源追踪，差异无法定位。
- 声明分散会让校验无从下手。
- 残留不报错，只让能力出现两份。
- 晚发现的配置错误会以静默默认的形式出现。
- 五条目标：单一声明、显式顺序、可查来源、消灭隐式默认、整体切换。

## 二、【直觉】

### 2.1 两种"同一份配置"

一句话有两种意思。

- 第一种：同一个文件，在哪儿跑都一样。
- 第二种：同一个文件名，但内容有一部分由环境决定。

第二种就是要消灭的：它让"同一个模式名"在不同机器上不是同一件事。

::: keypoint 反直觉点
**按机器能力自动调参是合理的，但调整应当发生在配置的生成阶段，而不是运行时的隐式读取里。** 前者的结果可被审查、可被记录、可被复现，后者三者都做不到。
:::

### 2.2 四层抽屉

每往上一层，能写它的人越少，时效越短。

- 最底下是系统作者的保守基线。
- 往上是使用者的个人偏好。
- 再往上是项目维护者的项目约定。
- 最上面是执行者的一次性覆盖。

**顺序本身必须被写下来**，因为它是"为什么这条配置生效了"的唯一答案。

### 2.3 一个数字直觉

设一个模式声明了 30 个插件，其中 25 个的配置有显式取值、5 个依赖默认值。

那 5 个默认值可能来自三处：插件代码里的常量、框架的默认行为、环境变量。三种形态的代价不同。

- 版本漂移：插件升级后默认值变了，而声明没变。
- 环境差异：默认从环境推断，于是开发机与服务器不同。
- 不可审查：审阅者看不到那 5 个取值，而它们恰好是安全与成本相关的。

**修法是同一条**：把隐式默认变成显式取值，即使它等于当前的默认值。

**本节要点**

- "同一份配置"有两种意思，第二种要消灭。
- 自适应移到生成阶段。
- 四层顺序要写下来。
- 隐式默认的三种代价，修法相同。

## 三、【严格】

### 3.1 定义

::: theorem 定义 5.1.1（模式）
一个模式是

$$
P = (\mathit{name},\ \mathit{plugins},\ \mathit{entries},\ \mathit{requires},\ \mathit{presets}),
$$

其中 $\mathit{requires}$ 是**必须齐备的能力清单**（校验对象），$\mathit{presets}$ 是该模式支持的 agent 预设。模式是**部署单位**。
:::

::: theorem 定义 5.1.2（预设）
一个预设是

$$
\mathit{preset} = (\mathit{instructions},\ \mathit{tools},\ \mathit{skills},\ \mathit{model}),
$$

其中 $\mathit{instructions}$ 是系统提示的基线部分（不含轮次相关信息，因为它参与前缀缓存）。预设是**会话单位**。

**两者分开的理由**：一次部署可以跑多种会话，每种会话用不同的预设，而它们共享同一个模式提供的插件集合。
:::

::: theorem 定义 5.1.3（覆盖顺序与合并）
覆盖顺序是从低到高的四层：

$$
\text{内建默认} \prec \text{用户级} \prec \text{项目级} \prec \text{运行参数}.
$$

合并的规则是：**对象深合并**（未提及的键保留），**数组与标量整体替换**。

$$
a \oplus b = \begin{cases}
\text{逐键合并}, & a, b \text{ 都是对象},\\
b, & \text{否则}.
\end{cases}
$$
:::

::: theorem 定义 5.1.4（隐式默认）
一个取值是**隐式默认**，当且仅当它在四层中都没有被写出，而由代码常量、框架默认或环境推断提供。

消灭隐式默认的三条规则是：**必填项没有默认值**、**次要默认必须可见**（来源可查）、**禁止运行时环境推断**。
:::

::: theorem 定义 5.1.5（能力集）
模式 $P$ 的**能力集**是它启用的插件及其**间接依赖**所提供能力的并集：

$$
\mathrm{Cap}(P) = \bigcup_{p \in \mathrm{closure}(\mathit{plugins}(P))} \mathrm{provides}(p).
$$

校验的对象是这个集合，而不是声明里列出的插件（因为间接依赖无法手写全）。
:::

::: theorem 定义 5.1.6（切换）
一次切换是三步固定的序列：

$$
\mathrm{switch} = \text{校验新声明} \ \prec\ \text{整体构造新作用域} \ \prec\ \text{核对旧作用域的残留}.
$$

**先校验再切换**，且切换是**整体**的（不是增删个别插件）。
:::

### 3.2 命题

::: theorem 命题 5.1.1（隐式默认破坏可复现）
若某取值由隐式默认提供，则同一份声明在不同版本、不同机器或不同环境下可能产生不同行为。

**证明.** 隐式默认的来源有三类：代码常量（随版本变化）、框架默认（可能从环境推断）、环境变量（随部署变化）。三类都不是声明的一部分，故声明相同时它们可以不同，从而有效配置不同。

↓ **为什么能这么写？** 可复现要求有效配置只由声明决定，而隐式默认引入了声明之外的输入。

$\blacksquare$

**数值**：30 个插件里若有 5 个依赖默认值，则这 5 个取值是三类漂移的载体。**"当时的配置"因此无法被完整记录**——这直接削弱 4.4 的诊断（它要求记录失败时的配置）。
:::

::: theorem 5.1.2（数组不能深合并）
若数组按键合并，则下层删除的元素会在合并结果中保留。

**证明.** 设下层数组 $A = [x, y]$，上层数组 $B = [x]$。按元素合并的结果至少包含 $x$ 与 $y$（合并只加不减），即 $y$ 虽然被上层"删除"但仍然存在。而整体替换的结果是 $[x]$，与上层的意图一致。

↓ **为什么能这么写？** 合并运算没有表达"删除"的手段。

$\blacksquare$

::: keypoint 这就是"我的列表和你的列表混在一起"
**在多来源场景下更严重**：下层删掉一项不会生效，而上层无法通过写一份更短的列表来表达删除。
:::

::: theorem 5.1.3（校验对象必须是能力集）
存在一种缺失，它不出现在声明里而出现在间接依赖中。

**证明.** 构造：模式声明插件 $A$，$A$ 依赖 $B$，而 $B$ 提供能力 $c$。若 $B$ 未被部署侧提供（例如它由另一个插件在运行时注册），则声明里列出的插件都在，而 $c$ 缺失。故仅校验声明无法发现它。

↓ **为什么能这么写？** 声明的成员与能力集的成员由不同的闭包定义。

$\blacksquare$

::: theorem 5.1.4（整体切换避免残留与半应用）
增量重装的每一步都是一次释放机会，漏掉任一步都会留下残留。中途失败还会留下半应用状态。

**证明.** 设增量路径有 $k$ 个环节。残留的概率上界随 $k$ 单调不减（每个环节独立地可能漏掉释放）。整体切换的 $k = 1$（一次构造、一次释放），故残留概率最低。半应用状态：增量路径的中间状态既不是旧模式也不是新模式（与 4.5 命题 4.5.4 同形）。

↓ **为什么能这么写？** 环节数是残留机会的计数。

$\blacksquare$

**数值**：代价是切换瞬间的资源占用量翻倍，而切换不是高频操作（发生在部署与调试时），因此这个代价可接受。
:::

::: theorem 5.1.5（切换必须先校验）
若先切换后校验，则校验失败时系统已处于一个坏状态。

**证明.** 切换把入口指向新作用域。若校验在新作用域生效之后执行并失败，则被回滚的是一份已经生效的配置，而回滚本身需要一次新的切换（且它同样需要校验）。先校验时失败不改变任何生效状态。

↓ **为什么能这么写？** 失败点的位置决定了它是否影响生效状态。

$\blacksquare$

::: theorem 5.1.6（运行时环境推断使配置记录不完整）
若某取值在运行时从环境推断，则它不出现在任何可记录的配置快照里。

**证明.** 配置记录是四层声明的合并结果。运行时推断的值不在四层中的任何一层，故不在合并结果里。4.4 的已知条件要求"当时的配置"，而该值无法被提供。

↓ **为什么能这么写？** 记录的内容是声明，而推断的结果不是声明。

$\blacksquare$

### 3.3 本节要点

**本节要点**

- 模式是五元组的部署单位（定义 5.1.1）。
- 预设是四元组的会话单位（定义 5.1.2）。
- 四层覆盖，对象深合并而数组整体替换（定义 5.1.3）。
- 隐式默认由三条规则消灭（定义 5.1.4）。
- 能力集含间接依赖，是校验对象（定义 5.1.5）。
- 切换是先校验、整体构造、核对残留（定义 5.1.6）。
- 隐式默认破坏可复现（命题 5.1.1）。
- 数组不能深合并（命题 5.1.2）。
- 校验对象必须是能力集（命题 5.1.3）。
- 整体切换避免残留与半应用（命题 5.1.4）。
- 切换必须先校验（命题 5.1.5）。
- 运行时推断使配置记录不完整（命题 5.1.6）。

## 四、【回到直觉】

- **定义 5.1.1 说的**：模式是"这次部署跑什么"。
- **定义 5.1.2 说的**：预设是"这条会话用什么样的 agent"。
- **定义 5.1.3 说的**：四层抽屉，对象逐键合并、数组整根替换。
- **定义 5.1.4 说的**：必填项必须写、次要默认要看得出是默认、不许在运行时猜。
- **定义 5.1.5 说的**：能力要看展开后的总和，不是看清单。
- **定义 5.1.6 说的**：先检查再加装，一次换整台，换完核对有没有旧东西留下。
- **命题 5.1.1 说的**：没写出来的取值，换个地方就可能不一样。
- **命题 5.1.2 说的**：数组按元素合并，删掉的东西会自己回来。
- **命题 5.1.3 说的**：清单上的都在，能力仍可能缺，因为它来自更深一层。
- **命题 5.1.4 说的**：一步一步换，每一步都可能漏；整体换只漏一次。
- **命题 5.1.5 说的**：先换后查，查出问题时系统已经在坏状态里。
- **命题 5.1.6 说的**：运行时猜出来的值，事后查不到。

**本节要点**

- 模式管部署，预设管会话。
- 四层抽屉。
- 消灭隐式默认。
- 能力集看展开。
- 整体切换。
- 先校验。

## 五、【工具箱】

### 5.1 模式的四部分

| 部分 | 内容 |
|---|---|
| 插件 | 启用哪些插件与各自的配置 |
| 入口 | 对外暴露的方式（命令行、HTTP、GUI） |
| 必需能力 | 必须齐备的能力清单（校验对象） |
| 预设 | 该模式支持的 agent 预设 |

### 5.2 消灭隐式默认的三条规则

1. **必填项没有默认值**：并发、超时、模型 id、工作目录必须在声明里出现，缺失即启动失败。
2. **次要默认可见**：有效配置里能看出它来自默认层。
3. **禁止运行时环境推断**：自适应移到配置的生成阶段。

### 5.3 校验的三层

| 层 | 查什么 | 成本 |
|---|---|---|
| 声明校验 | 字段类型、必填项、插件存在、冲突写法 | 毫秒 |
| 能力集校验 | 间接依赖展开后必需能力是否齐备、总量是否超上限 | 毫秒 |
| 探测校验 | 关键外部依赖能否启动或连通 | 秒级（可选） |

**第二层是间接依赖的检查点**，而手写声明无法覆盖它。

### 5.4 切换的三步

1. 校验新模式（失败即中止，旧模式不受影响）。
2. 整体构造新容器与作用域，然后把入口指过去。
3. 核对旧作用域的残留并报告。

**第三步要区分"期望存活的注册"**（例如日志写入器）与真正的残留——这个标记应当在注册时就声明，而不是在核对时判断。

### 5.5 预设的四个部分与边界

| 部分 | 边界 |
|---|---|
| 指令 | 只放稳定内容，不含轮次相关信息（它参与前缀缓存） |
| 工具集 | 与副作用等级配合，可以定义只读会话 |
| 技能集 | 受元数据预算限制，要声明规模 |
| 模型 | 含预算参数，不改价格档但决定消耗 |

**本节要点**

- 模式四部分。
- 消灭隐式默认三规则。
- 校验三层，第二层最关键。

### 7.2 组合段

组合段从低到高合并，并记录每个键的来源。

```js
// 定义 5.1.3：四层覆盖、对象深合并、数组整体替换、记录来源
export function compose(layers) {
  const values = {}
  const origin = {}
  for (const layer of layers) {
    for (const [k, v] of Object.entries(layer.values)) {
      const prev = values[k]
      values[k] = isPlainObject(prev) && isPlainObject(v) ? { ...prev, ...v } : v
      origin[k] = layer.name
    }
  }
  return { values, origin }
}

/**
 * 定义 5.1.3：判断是否是普通对象（数组与 null 都不算）。
 * @param x 待判断的值
 * @returns 是否是普通对象
 */
export function isPlainObject(x) {
  return x !== null && typeof x === 'object' && !Array.isArray(x)
}

/**
 * 定义 5.1.4：必填项检查——缺失即启动失败。
 * @param keys 必填键
 * @param composed 组合结果
 * @returns 无
 * @throws 缺任一必填项时
 */
export function requirePresent(keys, composed) {
  const missing = keys.filter((k) => !(k in composed.values))
  if (missing.length) throw new Error(`缺少必填配置：${missing.join('、')}`)
}
```

### 7.3 能力集与校验段

能力集要展开间接依赖，校验据此判断必需能力是否齐备。

```js
// 定义 5.1.5：广度优先展开间接依赖
export function expandCapabilities(profile, registry) {
  const out = new Set()
  const queue = [...profile.plugins]
  const seen = new Set()
  while (queue.length) {
    const name = queue.shift()
    if (seen.has(name)) continue
    seen.add(name)
    for (const cap of registry.provides(name) ?? []) out.add(cap)
    for (const dep of registry.dependencies(name) ?? []) queue.push(dep)
  }
  return out
}

/**
 * 定义 5.1.5：三层校验里的前两层。
 * @param profile 模式
 * @param registry 形如 `{ has, provides, dependencies, providerOf }`
 * @param maxCapabilities 能力集上限
 * @returns `{ ok, issues, capabilities }`
 */
export function validate(profile, registry, maxCapabilities = Infinity) {
  const issues = []
  for (const p of profile.plugins) {
    if (!registry.has(p)) issues.push({ level: 'error', what: `插件不存在：${p}` })
  }
  const capabilities = expandCapabilities(profile, registry)
  for (const need of profile.requires ?? []) {
    if (!capabilities.has(need)) {
      issues.push({ level: 'error', what: `缺少必需能力：${need}`, hint: `可能由插件 ${registry.providerOf(need) ?? '（未知）'} 提供` })
    }
  }
  if (capabilities.size > maxCapabilities) issues.push({ level: 'error', what: `能力集超过上限：${capabilities.size}` })
  return { ok: issues.every((i) => i.level !== 'error'), issues, capabilities }
}
```

### 7.4 切换段与残留核对

切换先校验、再整体构造、最后核对残留。

```js
// 定义 5.1.6：切换的三步
export async function switchProfile(next, ctx) {
  const validation = validate(next, ctx.registry, ctx.maxCapabilities)
  if (!validation.ok) throw new Error(`模式校验失败：${validation.issues.map((i) => i.what).join('、')}`)
  const old = ctx.current
  const fresh = await ctx.compose(next)
  await ctx.activate(fresh)
  const residual = detectResidual(old, ctx)
  await ctx.dispose(old)
  return { profile: next.name, capabilities: validation.capabilities.size, residual }
}

/**
 * 定义 5.1.6：残留核对——期望存活之外的都算残留。
 * @param old 旧作用域
 * @param ctx 形如 `{ listRegistrations }`
 * @returns 残留描述数组
 */
export function detectResidual(old, ctx) {
  return ctx.listRegistrations()
    .filter((r) => r.scope === old.id && !r.expectedAfterDispose)
    .map((r) => `${r.what}（来自 ${r.plugin}）`)
}
```

### 8.3 评审一份模式声明的六个问题

1. **必填项都有显式取值吗？** 缺失即启动失败。

### 9.2 失败模式

**（1）检查放在装载期（L9 位置放错）。** 模式的自洽性只在开发环境验证过一次，而生产环境缺某个插件。表现是"生产启动后才失败，而失败点与配置改动之间隔着一次发布"。

**（2）前提会变（L9）。** 命题 5.1.4 的整体切换以"构造新作用域不会失败"为前提。若构造过程中依赖外部服务而它不可用，整体切换反而会失败并留下一个未完成的新作用域。

**（3）隐式默认存在。** 同一份声明在不同机器上行为不同。

**（4）数组按元素合并。** 下层删除的元素在合并结果中保留。

**（5）只校验插件列表。** 间接依赖缺失无法被发现。

**（6）增量重装。** 残留与半应用状态持续制造难定位的问题。

**（7）先切换后校验。** 校验失败时系统已在坏状态。

**（8）运行时环境推断。** 配置记录不完整，诊断失去条件。

**（9）能力集不设上限。** 多会话共存时上下文被技能与工具元数据吃满。

**（10）面向人的说明另写一份。** 它与声明漂移，最终描述与实际不一致。

**本节要点**

- 决策表覆盖 12 种情形。
- 失败模式十条，前两条是位置放错与前提会变。
- 最隐蔽的是"运行时环境推断"——它让"当时的配置"永远无法被完整回答。

## 十二、系统影响回溯

**影响一：模式的隐式默认会让诊断失去条件。** 4.4 要求记录失败时的配置，而隐式默认使得这份记录无法完整。

**影响二：模式会与技能、工具集产生组合爆炸。** 多会话共存时并集可能超出上下文预算，因此需要能力集总量校验。

**影响三：模式切换引入的残留是作用域问题的第一个真实用例。** 它的检测方式是列出当前注册项的来源。

**一处需要修正的预判。** 旧稿把"消灭隐式默认"写成一条整洁性要求，读完之后要把它升级为诊断的前提：没有它，4.4 的已知条件永远缺一块，而"当时为什么这样"这个问题在配置相关的失败上不可回答。它不是风格，而是可解释性的必要条件。

**通向下一步的桥。**

模式解决了"这次部署跑什么"，而它把"一次部署里同时跑多条会话"这个问题留给下一篇：多条会话共享同一个模式提供的插件集合，而它们各自的状态必须隔离、资源必须受限、失败必须互不影响。

所以下一篇是 5.2 多会话与并发。它与本篇的连接点是能力集上限——那是共存的前提。

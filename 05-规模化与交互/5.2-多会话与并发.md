## 本篇新词

- 会话注册表（session registry） 指进程里所有活动会话的索引：身份、状态、占用资源与所属模式。它是并发的唯一权威视图。
- 隔离（isolation） 指一条会话的状态变化不影响另一条。它有三个层面。
- 共享资源（shared resource） 指多条会话竞争的东西：模型并发、工作目录、进程池、凭据。
- 工作区租约（workspace lease） 指对工作目录的独占声明。
- 配额（quota） 指分配给一条会话或一个模式的资源上限。它与限流的差别在时机。
- 公平性（fairness） 指调度在多条会话之间分配资源的方式，它针对的是响应时间。
- 取消传播（cancellation propagation） 指一条会话被取消时其子操作一并被取消。
- 会话生命周期（session lifecycle） 指会话从创建到回收的过程，难点在回收。

## 一、【设计原因】

### 1.1 缺陷一：两条会话互相干扰

表现有三种：状态串扰（一条会话改动了另一条的状态）、文件串扰（两条会话在同一个工作目录里改同一批文件）、日志串扰（事件被写进了错误的会话）。

成因分别是：共享了本应隔离的对象、缺少工作区租约、事件的归属字段没有被正确传递。

### 1.2 缺陷二：一条长会话挡住其他会话

先来先服务的调度下，一条消耗资源的会话会让其他会话长时间得不到响应。表现是"系统看起来卡住了"，而实际资源并没有耗尽——只是被一条会话占着。

**公平性针对的是响应时间而不是总吞吐。**

### 1.3 缺陷三：资源缓慢泄漏

进程运行若干天之后内存与句柄数缓慢上升，而单次会话的行为没有任何异常。成因是会话结束后资源没有被释放：订阅、定时器、子进程、文件句柄、容器里的注册项。

### 1.4 缺陷四：取消没有贯穿到子操作

用户中止了一条会话，而它启动的子进程仍在运行、子 agent 仍在调用模型。表现是"取消了但还在花钱"。

### 1.5 由此确定的设计目标

1. 每会话一个作用域与容器，注册项互不可见。
2. 分清该隔离的与该共享的，共享的用租约与配额约束。
3. 配额三维（并发、速率、占用），事前分配而不是事后拒绝。
4. 调度按配额轮转并叠加预设提供的优先级。
5. 回收是显式流程，并把不完整报告出来。

**本节要点**

- 串扰有三种形态，成因各不相同。
- 公平性关心等待时间。
- 泄漏在单次会话上看不出来。
- 取消必须沿作用域向下。
- 五条目标：每会话隔离、分类共享、三维配额、轮转加优先级、显式回收。

## 二、【直觉】

### 2.1 合租公寓

几条会话像合租一套房子。

- 各自的房间是私有的（会话历史、上下文、工作目录里的各自产物）。
- 厨房与洗衣机是共享的，因此需要排班（租约）。
- 水电有总额度（配额），用了多少要能看见。
- 一位租客退房时要把自己的东西清走（回收），否则下一位会撞上。

::: keypoint 反直觉点
**多会话的瓶颈通常不在本进程。** 一百条会话每分钟各发一次请求就是每分钟一百次调用，而下游的并发上限通常是数十——于是请求开始排队，而排队让每条会话的延迟都上升。**配额与调度必须覆盖到下游，而不只是本机的 CPU 与内存。**
:::

### 2.2 排队与轮转

三位办事的人，第一个要办十件、后两个各两件。

- 先来先服务：后面两位要等第一位办完，第一位办完前他们完全没有回应。
- 轮流办：每人每次办两件，后面两位很快就拿到了第一次回应。

**两者的总时长相同（14 个时间单位），而等待的分布完全不同。** 用户能容忍慢，难以容忍"看起来没反应"。

### 2.3 一个数字直觉

设一条活动会话的常驻开销：上下文 20K token（约 80KB 文本）、若干文件句柄、一个工作区句柄、一个待响应状态。

- 十条会话仍在单机可承受范围内。
- 一百条会话带来两个问题：模型配额被压满（每分钟百次调用对下游的数十上限），以及观测的可读性下降（单条会话的异常被平均数掩盖）。

**结论是并发数的实际上限由下游配额决定**，因此配额必须在请求发出前分配。

**本节要点**

- 房间私有、设施共享、额度可见、退房要清。
- 瓶颈在下游。
- 轮转改善的是等待分布而不是总时长。
- 并发上限由下游决定。

## 三、【严格】

### 3.1 定义

::: theorem 定义 5.2.1（会话注册表）
进程内的活动会话集合

$$
\mathcal{R} = \{s_1, \dots, s_n\},\quad s = (\mathit{id},\ \mathit{scope},\ \mathit{container},\ \mathit{profile},\ \mathit{preset},\ \mathit{leases},\ \mathit{state}),
$$

其中 $\mathit{state} \in \{\text{空闲},\ \text{运行},\ \text{等待},\ \text{关闭中},\ \text{已关闭}\}$。**"关闭中"必须与"已关闭"分开**，因为正在关闭的会话仍占用资源。
:::

::: theorem 定义 5.2.2（隔离三层）
隔离由三层构成：

$$
\text{隔离} = (\text{作用域隔离},\ \text{数据隔离},\ \text{失败隔离}),
$$

分别指注册项互不可见、数据（会话文件、工作目录、记忆的作用域）分开、以及一条会话的异常不终止进程。
:::

::: theorem 定义 5.2.3（配额与它的时机）
一条会话的配额有三个维度：

$$
\mathit{quota} = (\text{最大并发},\ \text{速率上限},\ \text{占用上限}).
$$

**配额与限流的差别在时机**：配额在请求之前分配，限流在越界时拒绝。前者的结果是"请求发出前就知道能不能被满足"。
:::

::: theorem 定义 5.2.4（调度与公平性）
调度在候选会话之间选择下一个执行者。三种策略是

$$
\{\text{先来先服务},\ \text{按优先级},\ \text{按配额轮转}\}.
$$

**公平性的度量是响应时间**（第一次得到回应的等待），而不是总吞吐——三种策略的总时长可以相同。
:::

::: theorem 定义 5.2.5（工作区租约）
一个工作区租约是

$$
\ell = (\mathit{workspace},\ \mathit{holder},\ \mathit{expiresAt},\ \mathit{mode}),
$$

它满足三条要求：**带超时**（持有者崩溃后可自动释放）、**获取可排队**（等待而不是立刻失败）、**持有者可识别**（用于判断有效性）。
:::

::: theorem 定义 5.2.6（取消传播与回收）
取消沿作用域向下传播：取消 $S$ 即取消 $\mathrm{children}(S)$ 下的一切。回收是一个显式流程

$$
\mathrm{close}(s) = \text{标记关闭中} \prec \text{取消} \prec \text{释放租约} \prec \text{销毁容器} \prec \text{落盘度量} \prec \text{核对},
$$

其中核对的结果（未释放项的清单）是流程的一部分输出。
:::

### 3.2 命题

::: theorem 命题 5.2.1（下游配额决定并发上限）
设每条会话的请求速率为 $r$，会话数为 $n$，下游并发上限为 $C$。当 $nr > C$ 时请求开始排队，而排队延迟随 $n$ 上升。

**证明.** 到达率 $nr$ 超过服务能力 $C$ 时，队列长度随时间增长（排队论的基本结论）。队列增长使每个请求的等待时间上升，故延迟随 $n$ 上升。

↓ **为什么能这么写？** 到达率与处理率的比较决定队列是否增长。

$\blacksquare$

**数值**：$r = 1$ 次/分钟、$n = 100$、$C$ 为数十时到达率已超过处理能力。**因此并发数的实际上限由下游决定**，本机资源的余量不能作为依据。
:::

::: theorem 5.2.2（公平性针对响应时间）
存在两种调度策略，它们的总完成时间相同而在等待分布上差异显著。

**证明.** 构造：三个会话工作量 $10, 2, 2$。先来先服务按提交顺序执行，总时长 $14$。第一位开始于 $0$，第二位与第三位分别位于 $10$ 与 $12$。配额轮转（时间片 2）的总时长同样是 $14$，而第二位开始于 $2$、第三位于 $4$。故总时长相同而首次响应时间不同。

↓ **为什么能这么写？** 总时长由总工作量决定，而首次响应由调度顺序决定。

$\blacksquare$

**数值**：先来先服务下第二、三位的等待是 $10$ 与 $12$，轮转下是 $2$ 与 $4$。
:::

::: theorem 5.2.3（写必须独占而读可共享）
文件系统没有事务，因此两条会话同时写同一批文件会产生无法解释的中间态。

**证明.** 设两条会话对同一文件各做一次读—改—写。交错执行时，后完成的一方基于旧内容写入，前者的修改丢失。该结果不对应任何串行执行顺序，故为不可解释的中间态。只读操作不改变内容，故不产生此类冲突。

↓ **为什么能这么写？** 冲突需要至少两个写者。

$\blacksquare$

::: keypoint 工作目录的两行判据
**同一个对象在写与读两种用法下的答案不同**：写要独占租约，读共享。判据可以推广——任何被两条会话同时修改的对象都需要共享协议，而只读的不需要。
:::

::: theorem 5.2.4（垃圾回收不管理非内存资源）
文件句柄、子进程、定时器、外部连接与注册项不受内存回收管辖。

**证明.** 内存回收的依据是可达性（对象是否还被引用）。上述资源的生命周期由外部系统决定（操作系统、远端服务），与内存可达性无关。故它们不会被自动释放。

↓ **为什么能这么写？** 回收机制的作用域是内存图。

$\blacksquare$

::: theorem 5.2.5（回收需要核对才能被发现不完整）
若回收流程不核对，则"未清理干净"不会产生任何信号。

**证明.** 回收是若干释放动作的序列。任一动作静默失败时，系统状态与其他情况下相同（没有异常、没有输出），故不可观测。核对把一个可观测的判定（哪些注册项仍在）引入流程。

↓ **为什么能这么写？** 可观测性要求存在一个与成功情形不同的输出。

$\blacksquare$

**数值**：回收不完整是常态而不是异常（某个订阅没被释放、某个定时器还在），因此把它报告出来而不是假定成功。
:::

::: theorem 5.2.6（取消粒度必须分层）
若只有会话级取消，则单次操作超时会终止整个会话。

**证明.** 设某次网络请求超时。若取消只有会话级，则该超时的处理动作是取消会话，从而丢弃该会话已经完成的工作。而在分层取消下，超时只取消该操作。故分层是"一次抖动不终止任务"的必要条件。

↓ **为什么能这么写？** 处理的粒度决定它的影响范围。

$\blacksquare$

### 3.3 本节要点

**本节要点**

- 注册表是并发的权威视图，"关闭中"与"已关闭"分开（定义 5.2.1）。
- 隔离分作用域、数据与失败三层（定义 5.2.2）。
- 配额三维，与限流的差别在时机（定义 5.2.3）。
- 调度三策略，公平性度量的是响应时间（定义 5.2.4）。
- 租约带超时、可排队、持有者可识别（定义 5.2.5）。
- 取消沿作用域向下，回收是显式流程加核对（定义 5.2.6）。
- 下游配额决定并发上限（命题 5.2.1）。
- 公平性针对响应时间（命题 5.2.2）。
- 写必须独占而读可共享（命题 5.2.3）。
- 垃圾回收不管理非内存资源（命题 5.2.4）。
- 回收需要核对（命题 5.2.5）。
- 取消粒度必须分层（命题 5.2.6）。

## 四、【回到直觉】

- **定义 5.2.1 说的**：一份活动会话的名册，含它们各自的状态与占用。
- **定义 5.2.2 说的**：房间私有、数据分开、一个人出事不拖垮所有人。
- **定义 5.2.3 说的**：额度是事前分好的，而不是越界才拒绝。
- **定义 5.2.4 说的**：排队方式决定"多久能第一次得到回应"。
- **定义 5.2.5 说的**：占用的声明要有超时、能排队、能认出是谁占的。
- **定义 5.2.6 说的**：中止沿着层级往下传，收尾要按顺序做完并核对。
- **命题 5.2.1 说的**：一百条会话每分钟各一次调用，瓶颈在对方那里。
- **命题 5.2.2 说的**：先来先服务与轮流办的总时长一样，但等待分布差三倍。
- **命题 5.2.3 说的**：两个人同时写同一份文件，结果不对应任何先后顺序。
- **命题 5.2.4 说的**：句柄、子进程、定时器不会被自动回收。
- **命题 5.2.5 说的**：不核对，就不知道有没有清干净。
- **命题 5.2.6 说的**：只有一种取消粒度时，一次抖动就得中止整个任务。

**本节要点**

- 名册管状态与占用。
- 三层隔离。
- 额度事前。
- 等待分布是关键。
- 写独占读共享。
- 回收要核对。

## 五、【工具箱】

### 5.1 该隔离的与该共享的

判据：**这个对象的正确性是否依赖别的会话做什么。**

| 对象 | 处置 |
|---|---|
| 会话历史与日志、上下文与压缩状态 | 隔离 |
| 工作目录的写 | 共享但独占（租约） |
| 工作目录的读 | 共享 |
| 模型配额 | 共享（需分配） |
| 凭据、技能库、日志写入器 | 共享（只读或单写者） |
| 记忆、用户模型 | 共享（它们的定义就是跨会话） |
| 观测与度量 | 共享（按会话分组） |

### 5.2 配额的三个维度

| 维度 | 依据 |
|---|---|
| 并发数 | 下游的并发上限（防饿死用会话级上限，防过载用全局上限） |
| 速率 | 成本预算 |
| 占用 | 资源容量（上下文 token、工作区数量） |

**判断顺序**：先全局、再会话、最后速率——前两者的拒绝是瞬时的，速率超限的等待更长。

### 5.3 调度的三种策略

| 策略 | 适合 | 缺点 |
|---|---|---|
| 先来先服务 | 会话少且长度相近 | 长会话挡住后面 |
| 按优先级 | 有明确紧急程度 | 优先级需要来源（应由预设声明） |
| 按配额轮转 | 多条会话都要响应性 | 实现复杂 |

**本课程的组合**：轮转加预设提供的优先级。优先级处理重要性，轮转处理响应性。

### 5.4 租约的三条要求

1. **带超时**：覆盖最长的一次操作（过短会误释放，过长会让崩溃后的等待太久）。
2. **获取可排队**：等待而不是立刻失败，否则并发会话互相拒绝。
3. **持有者可识别**：知道是哪条会话、哪个进程占着，否则无法判断租约是否还有效。

### 5.5 回收的六步与核对

标记关闭中 → 取消并等待宽限期 → 释放租约 → 销毁容器 → 落盘度量 → 核对未释放项。

**顺序的理由**：先断掉产生资源的路径（取消），再回收。**核对的结果要报告出来**——回收不完整是常态。

**本节要点**

- 共享与隔离的判据是"正确性是否依赖别人"。
- 配额三维，判断顺序按等待时长排。
- 轮转加预设优先级。
- 租约三要求。
- 回收六步加核对。

### 7.2 配额段

配额段按"等待时长"排的判断顺序做准入。

```js
// 定义 5.2.3：三维配额，判断顺序按拒绝后的等待时长排
export function admit(session, registry, request) {
  if (registry.globalConcurrent() >= registry.config.globalMaxConcurrent) {
    return { ok: false, reason: '全局并发已满', retryAfter: 1000 }
  }
  if (session.running >= session.quota.maxConcurrent) {
    return { ok: false, reason: '会话并发已满', retryAfter: 500 }
  }
  const used = registry.tokensInWindow(session.id, 60_000)
  if (used + estimate(request) > session.quota.maxTokensPerMinute) {
    return { ok: false, reason: '速率超限', retryAfter: 60_000 }
  }
  return { ok: true }
}

/**
 * 定义 5.2.3：请求的 token 估算。
 * @param request 形如 `{ tokens }` 的请求
 * @returns token 数
 */
export function estimate(request) {
  return request.tokens ?? 0
}
```

### 7.3 调度段

调度段先按优先级分组，再在组内按剩余配额挑选。

```js
// 定义 5.2.4：轮转加优先级
export function schedule(sessions, presetOf, creditsOf) {
  const ready = sessions.filter((s) => s.state === 'running' || s.state === 'idle')
  if (ready.length === 0) return null
  const byPriority = new Map()
  for (const s of ready) {
    const p = presetOf(s.preset).priority ?? 0
    if (!byPriority.has(p)) byPriority.set(p, [])
    byPriority.get(p).push(s)
  }
  for (const level of [...byPriority.keys()].sort((a, b) => b - a)) {
    const next = byPriority.get(level).find((s) => creditsOf(s.id) > 0)
    if (next) return next.id
  }
  return null
}
```

先来先服务与轮转的差别在等待分布，两个函数给出可比的数字。

```js
// 命题 5.2.2：两种调度策略的首次响应时间
export function fifoWait(work) {
  let t = 0
  return work.map((w, i) => {
    const start = t
    t += w
    return { index: i, wait: start }
  })
}

/**
 * 命题 5.2.2：按配额轮转的首次响应时间与总时长。
 * @param work 各会话的工作量
 * @param quantum 时间片
 * @returns `{ first, total }`
 */
export function roundRobinWait(work, quantum) {
  const left = [...work]
  const first = new Array(work.length).fill(null)
  let t = 0
  while (left.some((w) => w > 0)) {
    for (let i = 0; i < left.length; i++) {
      if (left[i] <= 0) continue
      if (first[i] === null) first[i] = t
      const slice = Math.min(quantum, left[i])
      t += slice
      left[i] -= slice
    }
  }
  return { first, total: t }
}
```

### 7.4 共享段与生命周期段

租约可排队、带超时。回收核对未释放项。

```js
// 定义 5.2.5：租约的获取——冲突时排队而不是失败
export function acquire(registry, workspace, holder, now, ttl) {
  const existing = registry.leaseOf(workspace)
  if (existing && existing.expiresAt > now && existing.holder !== holder) {
    return { queued: true, lease: null, position: registry.enqueue(workspace, holder) }
  }
  const lease = { workspace, holder, expiresAt: now + ttl, mode: 'exclusive' }
  registry.setLease(lease)
  return { queued: false, lease, position: 0 }
}
```

关闭的六步里要先断掉产生资源的路径，再回收，最后核对。

```js
// 定义 5.2.6 / 命题 5.2.5：关闭与回收核对
export function closeSession(handle, registry, ctx) {
  registry.setState(handle.id, 'closing')
  const cancelled = ctx.cancelScope(handle.scope, ctx.graceMs)
  const released = []
  for (const lease of handle.leases) released.push(ctx.release(lease))
  ctx.disposeContainer(handle.container)
  ctx.flushMetrics(handle.id)
  registry.setState(handle.id, 'closed')
  registry.remove(handle.id)
  const leaked = ctx.listRegistrations().filter((r) => r.scope === handle.scope.id && !r.expectedAfterDispose)
  return { cancelled, released, leaked: leaked.map((r) => `${r.what}（来自 ${r.plugin}）`) }
}
```

### 9.2 失败模式

**（1）检查放在装载期（L9 位置放错）。** 会话数上限只在启动配置里检查，而负载随时间变化。表现是"高峰期才出现排队，而配置看起来没问题"。

**（2）前提会变（L9）。** 命题 5.2.2 的等待分布以"各会话工作量固定"为前提。工作量随任务变化时，轮转的相对优势也随之变化。

**（3）共享了本应隔离的对象。** 状态串扰，表现为"一条会话看到了另一条的改动"。

**（4）工作目录没有租约。** 两条会话同时写同一批文件，产生无法解释的中间态。

**（5）配额只覆盖本机资源。** 真正的瓶颈在下游，队列在对方那里增长。

**（6）调度用先来先服务。** 长会话让其他会话长时间没有回应。

**（7）优先级由调用者临时指定。** 所有人都会给自己标最高，优先级迅速失效。

**（8）取消只有会话级。** 一次网络抖动升级为整个任务中止。

**（9）没有错误边界。** 一条会话的异常终止整个进程。

**（10）回收不核对。** 泄漏只能靠系统级监控察觉，而那时已经积累很久。

**本节要点**

- 决策表覆盖 12 种情形。
- 失败模式十条，前两条是位置放错与前提会变。
- 最隐蔽的是"回收不核对"——它不产生任何信号，只让资源缓慢上升。

## 十二、系统影响回溯

**影响一：多会话的瓶颈通常不在本进程。** 因此配额与调度必须覆盖到下游。

**影响二：公平性针对响应时间而不是总吞吐。** 因此调度策略的选择依据是"用户能容忍多久没有反馈"。

**影响三：没有核对的回收无法被发现不完整。** 而泄漏在单次会话的行为上完全看不出来。

**一处需要修正的预判。** 旧稿把隔离与配额并列为"两个问题"，读完之后要补一句它们的关系：**隔离解决"不该共享的别共享"，配额解决"该共享的怎么分"。** 前者是边界问题，后者是分配问题，而工作目录那一行（写独占、读共享）恰好同时用到两者——它既是边界（写者的唯一性）又是分配（谁先获得）。

**通向下一步的桥。**

多会话解决了"同时跑多条"，而它把"谁能做什么"这个问题留给下一篇：会话可以运行了，但哪些操作需要先问人、权限从哪里来、审批如何不疲劳——这些是交互与权限的内容。

## 读完这一篇你会知道什么

1. **调度策略的对照**：算例里先来先服务的等待是 `[0, 10, 12]`，轮转的首次响应是 `[0, 2, 4]`，而两者总时长都是 14。

4. 配额与准入：算例里未超限时准入（`true`），全局并发已满时拒绝并给出原因。
5. 会话隔离：并发会话必须互不干扰（与 2.5 的作用域一致）。
6. 工业界怎么做：操作系统调度、QoS 分级、限流与队列。

## 一、为什么并发需要调度与配额

### 1.1 一个长任务挡住所有人

一个会话发起了一个 30 秒的操作，**其他四个会话全部在等**。它们各自只需要 1 秒。

### 1.2 超额导致互相拖慢

十个会话同时跑，每个都很慢。**而单独跑每一个都很快**——它们只是在互相争抢。

### 1.3 会话之间串扰

两个并发会话互相看见了对方的临时状态（与 2.5 的串扰是同一个问题）。

这三件事分别对应：**调度策略、配额准入、会话隔离。**

## 二、调度与配额分工

| 机制 | 回答 | 做错的后果 |
|---|---|---|
| **调度** | 谁先跑、跑多久 | 长任务挡住短任务 |
| **配额** | 最多同时跑几个 | 互相拖慢、系统过载 |
| **隔离** | 会话之间互不影响 | 状态串扰 |

**调度决定"顺序"，配额决定"总量"。** 两者互补：只调度不限量，总负载仍会压垮系统。只限量不调度，短任务仍会被长任务挡住。

## 三、怎么做

### 3.1 调度策略

算例对比了两种策略，这组数字是本篇的核心：

| 策略 | 等待 / 首次响应 |
|---|---|
| **先来先服务（FCFS）** | 等待 `[0, 10, 12]` |
| **轮转（Round Robin）** | 首次响应 `[0, 2, 4]` |
| **两者总时长** | **`14 / 14`** |

实现如下。

```js
// 调度：轮转让每个会话都能尽早获得首次响应
export function roundRobin(tasks, quantum) {
  const remaining = tasks.map((t) => ({ ...t, left: t.cost }))
  const firstResponse = new Map()
  let clock = 0
  while (remaining.some((t) => t.left > 0)) {
    for (const task of remaining) {
      if (task.left <= 0) continue
      if (!firstResponse.has(task.id)) firstResponse.set(task.id, clock)
      const slice = Math.min(quantum, task.left)
      clock += slice
      task.left -= slice
    }
  }
  return { firstResponse, total: clock }
}
```

三个关键读法：

1. **总时长完全相同（14 / 14）**：轮转没有增加任何总成本。它只是重新分配了"谁在什么时候被服务"。
2. 第三个会话的等待从 12 降到 4：这是三倍的改善，对一个交互式系统来说是决定性的。
3. 算例验证"轮转把第二、第三个会话的等待都缩短了"为 `true`。

为什么这对 agent 系统尤其重要：**agent 的操作是交互式的**——用户盯着屏幕等。首字节延迟（首次响应）比总完成时间更影响感受。

这条结论可以推广：**在任何"用户等待结果"的系统里，响应时间的分布比平均值更重要**——这与 3.6 的"均值 681 vs P95 3000"是同一个洞察。

### 3.2 时间片

时间片大小影响效果。算例实测：

| 时间片 | 首次响应 |
|---|---|
| 2 | `[0, 2, 4]` |
| **4** | **`[0, 4, 6]`** |

算例同时验证：**"时间片变大后第二位的等待变化"是从 2 变成 4**。

时间片的两个方向：

| 时间片 | 优点 | 缺点 |
|---|---|---|
| **小** | 响应快，等待均匀 | 切换开销占比高 |
| **大** | 切换开销低 | 退化接近 FCFS |

参数建议：**时间片取"一个典型操作单元"的量级**（例如"一轮模型调用"或"一次工具执行"），而不是细到 1 毫秒。因为 agent 的操作本身就是粗粒度的，切换点放在操作边界上最自然。

这给出一个更实用的做法：**不要按时间片抢占，而按"可中断点"抢占**——在完成一次工具调用后检查是否该让出。这样既不打断正在进行的操作，又能在边界处公平调度。

### 3.3 配额与准入

配额决定"最多同时跑几个"，以及"满了怎么办"。算例实测：

| 情况 | 结果 |
|---|---|
| 未超限 | **准入（`true`）** |
| **全局并发已满** | **拒绝，原因是"全局并发已满"** |

"给出具体原因"很重要：它不是笼统的"拒绝"，而是**明确指出是哪一层限制**。这让用户/上游知道该怎么办（等、减并发、或提配额）。

**配额通常有多层**（与 5.1 的四层同源）：

| 层 | 限制 |
|---|---|
| 全局 | 进程/实例总数 |
| 每用户 | 单个用户的并发会话数 |
| 每会话 | 单个会话的子任务数 |
| 每工具 | 对某个外部服务的并发调用数 |

"每工具"这一层最容易被漏：**外部服务通常有自己的限流**（与 3.1 的限流处理衔接）。在本地就把它限住，比被对方 429 更好。

准入了之后还要考虑排队：拒绝太快会让用户频繁重试。**更好的做法是短暂排队 + 超时拒绝**，并返回预计等待时间。

### 3.4 会话隔离

并发会话必须互不干扰。**这与 2.5 的作用域是同一件事**：

| 隔离项 | 做法 |
|---|---|
| 会话状态 | 每会话独立（2.5 的子作用域） |
| 临时文件 | 每会话独立目录 |
| 资源配额 | 按会话计量 |
| 日志 | 带会话标识 |

"临时文件"最容易被漏：两个会话同时往同一个临时文件写，会造成难查的间歇错误。

判据：**任何"按路径共享"的资源，在并发下都要问"会不会互相覆盖"。**

### 3.5 公平性

"公平"需要定义。常见的三种：

| 定义 | 含义 | 适用 |
|---|---|---|
| **先来先服务** | 按到达顺序 | 简单，但长任务挡道 |
| **轮转** | 每个都得到服务机会 | 响应时间均匀 |
| **最大最小公平** | 让最少的那个尽可能多 | 资源分配 |
| **按权重** | 按优先级分配 | 有明确优先级时 |

"最大最小公平"值得了解：它的定义是**在不损害任何其他方的前提下，尽可能提升最差的那一方**。这是资源分配里最常用的公平定义。

判据：**公平不是一个自然属性，而是一个必须选择并写下来的定义。** 与 5.1 的"层序必须明确"是同一个要求。

## 四、特殊情况与处理技巧

| 情况 | 为什么 | 处理 |
|---|---|---|
| 长任务挡住短任务 | 用了 FCFS | 轮转或按可中断点调度 |
| 并发导致互相拖慢 | 无配额 | 全局 + 分层配额 |
| 配额满但没说原因 | 拒绝信息笼统 | 指出哪一层满 |
| 用户频繁重试 | 拒绝太快 | 短暂排队 + 返回预估等待 |
| 会话互相覆盖临时文件 | 路径共享 | 每会话独立目录 |
| 外部服务被限流 | 未限制每工具并发 | 本地限流 |
| 优先级反转 | 无优先级 | 引入优先级或权重 |
| 饥饿 | 优先级过高 | 老化（等待越久优先级越高） |

"饥饿"值得展开：**只要有优先级，低优先级任务就可能永远得不到执行。** 解法是老化——等待时间越长，优先级逐渐提升。这是一个必须显式处理的问题，否则会在某个时刻突然暴露。

## 五、工业界的做法（可照做）

### 5.1 操作系统与编排系统的调度

| 系统 | 策略 | 特点 |
|---|---|---|
| **Linux CFS** | 完全公平调度 | 按虚拟运行时间排序 |
| **实时调度** | 优先级 + 时间片 | 保证截止时间 |
| **K8s QoS** | 三档（Guaranteed / Burstable / BestEffort） | 按资源保障分级 |
| **队列系统** | 优先级队列 + 并发限制 | 显式排队 |
| **API 网关** | 按 key 限流 | 多租户公平 |

CFS 的思路值得学：**它不按优先级排队，而是让"运行时间最少的那个"先跑**。结果自然趋于公平，不需要手工调优先级。

它对应到 agent 系统：**按"已消耗的资源量"排序**（消耗少的先跑），而不是按到达时间或优先级。这自动实现了长期公平。

### 5.2 分级与降级

生产系统里的处理顺序通常是：

1. **准入**：超配额直接拒绝（带原因）。
2. 排队：短暂排队，返回预估等待。
3. 降级：降低质量换取速度（例如减少并行工具调用）。
4. 卸载：主动丢弃低优先级请求（与 3.1 的负载脱落一致）。

四步的顺序很重要：**先拒绝比先降级更诚实**。降级而不告知会让用户以为系统变慢了。

### 5.3 参数与设计起点

| 参数 | 推荐 | 依据 |
|---|---|---|
| 全局并发 | 按 CPU/内存/外部配额算 | 不是拍脑袋 |
| 每用户并发 | 全局的 1/5–1/10 | 防止单用户占满 |
| 每工具并发 | 按对方限流 | 见 3.3 |
| 可中断点 | 操作边界 | 不打断操作 |
| 排队超时 | 数秒（交互） | 超过就该明确拒绝 |
| 预估等待 | 给出量级 | 让用户决定等不等 |

### 5.4 一份可落地的实施清单

1. **调度**：按可中断点轮转，而不是纯 FCFS。
2. 中断点：选在操作边界（工具调用结束）。
3. 配额：全局、每用户、每会话、每工具四层。
4. 拒绝原因：指出哪一层满。
5. 排队：短暂排队 + 预估等待 + 超时拒绝。
6. 隔离：会话状态、临时目录、配额计量都独立。
7. 公平定义：明确写下来。
8. 老化：防止低优先级饥饿。
9. 观测：排队时长、拒绝率的分布（不只看均值）。
10. 测试：并发两个会话，验证隔离与配额。

## 六、学术界的结论

### 6.1 调度算法与它们的权衡

调度理论里的经典结论：

| 算法 | 特点 | 权衡 |
|---|---|---|
| **FCFS** | 简单 | 长任务挡道（护航效应） |
| **SJF** | 平均等待最短 | 需要预知执行时间，且长任务饥饿 |
| **轮转** | 响应时间均匀 | 有切换开销 |
| **多级反馈队列** | 按行为动态调整 | 复杂，但实用 |

"护航效应"（convoy effect）值得记住：**一个长任务会让后面的短任务全部等它**。算例的 `[0, 10, 12]` 正是这个效应的体现。

"SJF 平均等待最短"是一个反直觉但重要的结论：**优先做短任务能显著降低平均等待**。但它的代价是长任务可能饥饿——所以实务中都用它的近似（多级反馈队列）。

### 6.2 Little 定律的再次应用

$$
L = \lambda W
$$

在这里的含义：**并发会话数 $L$ 等于到达率乘以平均停留时间。**

它的实用推论：**如果每个会话的平均时长是 30 秒，而你要支持每秒 10 个新会话，那么平均并发是 300**。这个数字远大于直觉。

反过来：**如果并发上限是 20，而到达率是每秒 1 个，那平均停留时间必须低于 20 秒**——否则队列会无限增长。

**这与 1.5 的"覆盖窗口 $C/r$"是同一个公式的两种用法**（一个算容量，一个算并发）。

### 6.3 公平分配

资源分配领域的**最大最小公平**（max-min fairness）给出了一个被广泛接受的公平定义：

> 在不减少任何其他方分配的前提下，无法再增加任何一方的分配。

它的两个性质：

| 性质 | 含义 |
|---|---|
| **无嫉妒** | 没人愿意换成别人的份额 |
| **帕累托最优** | 无法在不损害他人的前提下改进 |

工程上的近似是加权公平队列：**按权重分配，而不是平均分配。**

判据：**"公平"必须在系统里被定义成可计算的东西**，否则它只是一个愿望。

### 6.4 延迟与吞吐的权衡

排队论的一个基本结论：**在接近饱和时，吞吐略有提升，但延迟急剧上升**（见 3.1 的利用率悬崖）。

对本篇的直接含义：**并发上限不应当设到"刚好用满资源"**，而应当留出余量。留出的余量换来的是延迟的稳定。

实践判据：**如果排队时长随负载上升而快速上升，说明并发上限设得太高。**

## 七、理论：两个量

### 7.1 总时长与响应时间可以分开

$$
\text{总时长}(\text{FCFS}) = \text{总时长}(\text{RR}) = 14
$$

$$
\text{等待}(\text{FCFS}) = [0, 10, 12] \gg \text{首次响应}(\text{RR}) = [0, 2, 4]
$$

算例同时验证了这两条。

这是本篇最重要的结论：**"公平调度"不需要牺牲总效率**——它只是重新分配了服务顺序。所以"为了提高效率而放弃公平"通常是一个伪权衡。

### 7.2 首次响应与时间片

$$
\text{等待}(i) \approx i \times \text{quantum}
$$

算例实测：时间片 2 → `[0, 2, 4]`。时间片 4 → `[0, 4, 6]`。

读法：**第 $i$ 个会话的首次响应近似等于 $(i-1) \times \text{时间片}$**。

工程含义：**要保证第 $N$ 个会话在 $T$ 秒内获得响应，时间片必须小于 $T/N$**。这是一个可以反推参数的公式。

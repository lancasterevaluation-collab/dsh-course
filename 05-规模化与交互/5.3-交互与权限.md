## 本篇新词

- 审批请求（approval request） 指一次需要人决定的危险操作的完整描述。它是一个有结构的数据对象。
- 归属（attribution） 指审批请求知道自己来自哪条会话与哪个预设。
- 呈现（presentation） 指把审批请求变成人能快速判断的形式。判据是人做决定所需的时间。
- 权限预设（permission preset） 指长期有效的授权规则：某类操作在某个范围内不必每次询问。
- 记住的粒度（remember scope） 指"允许并记住"的作用范围。
- 审批疲劳（approval fatigue） 指请求过多导致人不再认真判断。
- 阻塞与异步 指会话在等待审批期间的状态。
- 权限的来源分层（permission layers） 指授权可以来自多处，它们的优先级与撤销方式必须明确。

## 一、【设计原因】

### 1.1 缺陷一：用户无脑点同意

成因不只是请求多，还有请求难读——一份需要读三十秒的请求会让人放弃判断。

两个成因的修法不同：请求多要用预设与粒度解决，请求难读要用呈现解决。而它们的共同点是都会让审批失去作用。

### 1.2 缺陷二：审批弹窗不知道来自哪条会话

用户看到"请求执行删除构建目录"，而不知道它来自哪条会话、哪个任务。于是他无法判断这个操作是否合理——同一个命令在"清理构建产物"的任务里是常规操作，在"编辑文档"的任务里是异常。

### 1.3 缺陷三：等待审批的会话看起来卡住了

会话发起审批之后进入等待状态，而它既不推进也不结束——在界面上表现为"没有反应"，而用户不知道它在等自己。

这与疲劳直接相关：一个不知道在等什么的用户会倾向于尽快摆脱它。

### 1.4 缺陷四：权限越来越宽，而没有人记得

每一次"允许并记住"都留下一条长期有效的规则，而它们很少被撤销。几个月后系统的实际权限远超原先的设计意图——而它的表现是"某些操作不再询问"，而不是任何错误。

### 1.5 由此确定的设计目标

1. 请求是结构化的：归属、动作、风险、选项、时限俱全。
2. 风险按可逆性与影响范围分档，而不是按操作名枚举。
3. 呈现的判据是"十秒内可判断"。
4. 记住的粒度分四档，中间两档最重要。
5. 权限来源分层，**上界的拒绝排在最前**，撤销要能自动失效。

**本节要点**

- 疲劳有两个成因：太多与难读。
- 归属缺的是任务语境，不是会话 id。
- 等待必须可见，否则用户会想尽快摆脱它。
- 权限的累积不报错，只让防线变薄。
- 五条目标：结构化请求、两依据分档、十秒可判断、四档粒度、上界在前。

## 二、【直觉】

### 2.1 十秒判断

一份请求要能让读者在十秒内做出真实判断。

- 先说"要做什么"，再说"怎么做"。
- 风险写后果（"删掉就无法恢复"），不写等级（"高风险"）。
- 归属带任务语境（"来自'清理构建产物'这个任务"），不只给会话编号。

**超过十秒，人会开始无脑点同意。**

::: keypoint 反直觉点
**疲劳不是靠"把提示写清楚"能解决的，它有两个成因。** 请求太多要用权限预设与记住粒度解决，请求难读要用呈现解决——只做其中一半，另一半仍然把人推回无脑点击。
:::

### 2.2 三道闸门

一次危险操作的判断沿三个方向走。

- 最外面是**上界**（预设的拒绝）：它先判，且任何下游授权都不能放宽它。
- 中间是**长期授权**（用户的、项目的）。
- 最里面是**这一次**的判断。

顺序不能颠倒：上界在前、放行在后。反过来就等于允许"在下游放宽上游的安全决定"，而下游的数量远多于上游。

### 2.3 一个数字直觉

设一次会话平均发起 8 次需要审批的操作，进程里同时跑 3 条会话。

- 一段时间内人要处理 24 次审批。
- 每次认真判断 15 秒 → 6 分钟；快速点过 2 秒 → 48 秒。

**降下来的那段时间正是判断本身。** 三个信号可以区分"都很安全"与"没在看"：响应时间中位数、通过率、拒绝比例。

**本节要点**

- 十秒是判断的门槛。
- 上界必须排在最前。
- 疲劳的三个信号要一起看。

## 三、【严格】

### 3.1 定义

::: theorem 定义 5.3.1（审批请求）
一个审批请求是

$$
R = (\mathit{id},\ \mathit{origin},\ \mathit{action},\ \mathit{risk},\ \mathit{options},\ \mathit{raisedAt},\ \mathit{deadline}),
$$

其中 $\mathit{origin}$ 是归属（会话、预设、模式、父会话），$\mathit{action}$ 含一句**人话摘要**，$\mathit{options}$ **必须包含"换一种做法"**。
:::

::: theorem 定义 5.3.2（风险分级）
风险等级由两个依据决定：

$$
\mathit{risk} = f(\text{可逆性},\ \text{影响范围}),
$$

取值四档：

| 级别 | 可逆性 | 影响范围 |
|---|---|---|
| low | 可逆 | 会话内 |
| medium | 可逆 | 工作区 |
| high | 难撤销 | 工作区外 |
| critical | 不可逆 | 系统级 |

**依据是这两条而不是操作的名称**——两者都改文件，而删除的撤销成本更高，因此"删除"比"写入"高一档。
:::

::: theorem 定义 5.3.3（呈现）
呈现的判据是**人做决定所需的时间**（经验阈值十秒），它由三条规则实现：先说做什么再说怎么做、风险用后果表述、归属带任务语境。
:::

::: theorem 定义 5.3.4（权限预设）
一个权限预设是

$$
\mathit{pp} = (\mathit{match},\ \mathit{scope},\ \mathit{source},\ \mathit{失效条件}),
$$

其中 $\mathit{match}$ 是**工具加约束条件**（不只是工具名），$\mathit{source}$ 记录谁在何时因何授予。
:::

::: theorem 定义 5.3.5（记住的粒度）
"允许并记住"的作用范围有四档：

$$
\{\text{本次},\ \text{本会话},\ \text{本项目},\ \text{永久}\}.
$$

**中间两档最重要**：它们覆盖"在这条会话或这个项目里别再问"这个最常见需求，同时有自然的失效条件。
:::

::: theorem 定义 5.3.6（来源分层与撤销）
授权来自四层，判定的顺序是

$$
\text{预设的拒绝} \succ \text{用户长期授权} \succ \text{项目约定} \succ \text{低风险自动放行}.
$$

**预设的拒绝排在最前**，它是上界。撤销有三种：手动、随范围失效、随来源失效。
:::

### 3.2 命题

::: theorem 5.3.1（疲劳需要三个信号一起看）
单一指标无法区分"都很安全"与"没在看"。

**证明.** 高通过率有两种成因：所有操作确实安全，或人没有认真看。两者在通过率上相同，故该指标不可区分。加入响应时间（认真判断需要更久）与拒绝比例（认真判断时非零）之后，两种情形成因被分开。

↓ **为什么能这么写？** 区分需要至少一个在两种情形下取值不同的量。

$\blacksquare$

**数值**：响应时间中位数低于 3 秒、通过率高于 95%、拒绝与"换一种做法"的比例为零，三者同时成立即判为疲劳。这与 3.6 的"主指标配护栏"同源。
:::

::: theorem 5.3.2（上界必须排在最前）
若允许下游配置放宽上游的拒绝，则安全边界会随时间被逐步侵蚀。

**证明.** 设上游拒绝某项操作。若下游（项目配置）可放宽，则每新增一个下游就多一处可以放宽的位置。放宽的动作是局部的、看起来合理的，而它的累积效果是上游的拒绝在实际中失效。故边界的强度随下游数量单调下降。

↓ **为什么能这么写？** 放宽只需一次局部决定，而它的效果是全局的。

$\blacksquare$

::: keypoint 与元控制同源
**这是同一条原则的第三次出现**（1.5 的可逆性分级、4.5 的元控制、这里的安全上界）：允许逐步修改某条约束，等于允许它被改掉。放宽是允许的，但它必须是一次留下记录的动作。
:::

::: theorem 5.3.3（粒度决定预设可表达的最细约束）
若匹配只按工具名，则"允许写文件"必然包含"允许在任意路径写文件"。

**证明.** 匹配条件是工具名的等值判断。同一工具的所有调用共享该工具名，故匹配结果相同。要在同一工具内区分不同调用，匹配条件必须包含调用参数上的约束。

↓ **为什么能这么写？** 判别的分辨率由判据携带的信息量决定。

$\blacksquare$

**数值**：加上约束（例如"限工作区内"）之后，同一个工具的两类调用才可被区分——这也是"约束不成立"成为一个可观测拒绝的前提。
:::

::: theorem 5.3.4（等待不占并发）
处于等待状态的会话不计入并发配额，因此它不阻塞其他会话。

**证明.** 并发计数只统计执行中的会话（5.2 定义 5.2.1 与它的实现）。等待中的会话不执行，故不进入计数。因此多条会话同时等待审批时，其他会话的推进不受影响。

↓ **为什么能这么写？** 计数只包含消耗执行资源的会话。

$\blacksquare$

**数值**：但等待仍占用上下文与容器资源，因此"等很多审批的会话"会占着资源却不推进——这也是等待必须有超时的理由。
:::

::: theorem 5.3.5（等待必须有超时）
若等待无超时，则一次未获回应的请求会让会话永久停留在等待状态。

**证明.** 等待的终止依赖一个外部事件（人的决定）。若该事件永不发生且没有超时，则等待永不终止。会话的状态机因此没有可到达的后续状态。

↓ **为什么能这么写？** 终止条件必须由系统内部提供一个上界。

$\blacksquare$

**数值**：超时后按保守默认处理（拒绝或按配置），并把"因超时被拒绝"作为一个可统计的结果记录下来。
:::

::: theorem 5.3.6（撤销必须能自动失效）
手动撤销依赖人记得，而权限的累积恰恰发生在没人注意的时候。

**证明.** 权限的宽度随时间增长（每次"记住"都加宽）。若撤销只能手动，则加宽与收缩的触发条件不对称——前者是使用中的自然动作，后者需要一个额外动作。因此实际宽度趋向于只增不减。

↓ **为什么能这么写？** 两个方向的动作成本不对称时，状态会偏向成本低的一侧。

$\blacksquare$

**数值**：随范围失效（会话结束、项目变更、过期）与随来源失效（预设修改时同源授权一并失效）都不需要人记得。**因此它们比手动撤销更重要。**
:::

### 3.3 本节要点

**本节要点**

- 请求是六元组，含人话摘要与"换一种做法"（定义 5.3.1）。
- 风险按可逆性与影响范围分四档（定义 5.3.2）。
- 呈现的判据是十秒内可判断（定义 5.3.3）。
- 权限预设的匹配是工具加约束（定义 5.3.4）。
- 记住粒度四档，中间两档最有用（定义 5.3.5）。
- 判定顺序里预设的拒绝在最前（定义 5.3.6）。
- 疲劳需要三信号一起看（命题 5.3.1）。
- 上界必须排在最前（命题 5.3.2）。
- 粒度决定可表达的最细约束（命题 5.3.3）。
- 等待不占并发（命题 5.3.4）。
- 等待必须有超时（命题 5.3.5）。
- 撤销必须能自动失效（命题 5.3.6）。

## 四、【回到直觉】

- 定义 5.3.1 说的：一次询问要写清谁发起、要做什么、有多大风险、有哪些选择、什么时候不回就作废。
- 定义 5.3.2 说的：风险看"能不能撤回"与"影响到哪"，不看这是什么命令。
- 定义 5.3.3 说的：做人做决定要多快。
- 定义 5.3.4 说的：长期授权要写清匹配什么、管哪些范围、谁授的、什么时候失效。
- 定义 5.3.5 说的：记住的宽窄分四档，最有用的是中间两档。
- 定义 5.3.6 说的：先判上界，再判长期授权，最后才问人。
- **命题 5.3.1 说的**：光看"同意的比例"分不清是都安全还是没在看。
- **命题 5.3.2 说的**：允许下游放宽上游，边界就会被一次次放宽磨平。
- **命题 5.3.3 说的**：只按工具名授权，"允许写"就等于"随便在哪写"。
- **命题 5.3.4 说的**：等审批的会话不占并发，但它仍占着资源。
- **命题 5.3.5 说的**：不给等待设上限，会话会永远停在那里。
- **命题 5.3.6 说的**：只靠手动撤销，权限只会越来越宽。

**本节要点**

- 请求要结构完整。
- 风险看可逆与范围。
- 十秒判断。
- 匹配要带约束。
- 粒度四档。
- 上界最先判。

## 五、【工具箱】

### 5.1 请求的六个字段

| 字段 | 内容 |
|---|---|
| 归属 | 会话、预设、模式、父会话 |
| 动作 | 工具、参数、工作目录、**人话摘要** |
| 风险 | 等级、理由、是否可撤销 |
| 选项 | 含"换一种做法" |
| 发起时间 | — |
| 截止时间 | 等待超时 |

**`summary` 与 `args` 并存**，因为人与日志需要的信息不同。

### 5.2 呈现的三条规则

1. **先说做什么，再说怎么做**：人需要的第一个判断是"这件事该不该做"。
2. **风险用后果表述**："删除目录且无法恢复"优于"高风险"。
3. **归属带任务语境**："来自'清理构建产物'这个任务"优于"来自会话 s-7"。

### 5.3 风险四档

| 级别 | 可逆性 | 影响范围 |
|---|---|---|
| low | 可逆 | 会话内 |
| medium | 可逆 | 工作区 |
| high | 难撤销 | 工作区外 |
| critical | 不可逆 | 系统级 |

### 5.4 记住的粒度

| 粒度 | 适用 | 风险 |
|---|---|---|
| 本次 | 一次性例外 | 最低 |
| 本会话 | 会话里反复出现的操作 | 低（会话结束即失效） |
| 本项目 | 项目约定 | 中（项目范围内的所有会话） |
| 永久 | 极少使用 | 高（需要主动撤销） |

**界面只给"允许一次"与"总是允许"时，用户在不耐烦时必然选后者**——提供中间档位本身就是减少权限过宽的手段。

### 5.5 撤销的三种方式

1. **手动撤销**：列出并删除一条。
2. **随范围失效**：会话结束、项目变更、过期。
3. **随来源失效**：预设被修改时，来自它的授权一并失效。

**第二种最重要**，因为它是唯一不需要人记得的失效方式。

**本节要点**

- 请求六字段，摘要与参数并存。
- 呈现三规则。
- 风险四档看两条依据。
- 粒度四档，中间两档有自然失效。
- 撤销三种，随范围失效最省心。

### 7.2 请求段与权限段

请求段构造结构化请求，权限段按"上界在前"的顺序判定。

```js
// 定义 5.3.2：风险按可逆性与影响范围分档
export function assessRisk(action) {
  if (!action.undoable && action.scope === 'system') return { level: 'critical', reason: `${action.summary}，且不可恢复`, undoable: false }
  if (!action.undoable && action.scope === 'outside') return { level: 'high', reason: `${action.summary}，且难以撤销`, undoable: false }
  if (action.scope === 'workspace') return { level: 'medium', reason: `${action.summary}，影响工作区`, undoable: true }
  return { level: 'low', reason: `${action.summary}，可撤销`, undoable: true }
}

/**
 * 定义 5.3.1：构造请求，选项顺序从窄到宽。
 * @param origin 归属
 * @param action 动作
 * @param now 当前时间
 * @param timeout 等待超时
 * @returns 审批请求
 */
export function buildRequest(origin, action, now, timeout = 600000) {
  const risk = assessRisk(action)
  return {
    id: `ap-${origin.sessionId}-${now}`,
    origin,
    action: { tool: action.tool, args: action.args ?? {}, cwd: action.cwd, summary: action.summary },
    risk,
    options: ['allow-once', 'allow-session', 'allow-project', 'deny', 'alternative'],
    raisedAt: now,
    deadline: now + timeout,
  }
}
```

判定顺序里上界在最前，它不能被任何下游授权放宽。

```js
// 定义 5.3.6：上界最先判，然后才是各级授权
export function decide(req, ctx) {
  if (ctx.presetDenies(req)) return 'deny'
  const presets = ctx.matching(req)
  if (presets.some((p) => p.source.kind === 'user' && !p.revoked)) return 'allow'
  if (presets.some((p) => p.source.kind === 'project' && !p.revoked)) return 'allow'
  if (req.risk.level === 'low' && ctx.autoAllowReadOnly) return 'allow'
  return 'ask'
}
```

### 7.3 呈现段与等待段

呈现段给两种读者各一份文本，等待段把状态显式化并设超时。

```js
// 定义 5.3.3：两种呈现同源于一份数据
export function forHuman(r) {
  return [
    `[${r.origin.preset}] 请求执行：${r.action.summary}`,
    `位置：${r.action.cwd ?? '（未指定）'}`,
    `风险：${r.risk.reason}（${r.risk.undoable ? '可撤销' : '不可撤销'}）`,
  ].join('\n')
}

export function forLog(r) {
  return JSON.stringify({ id: r.id, session: r.origin.sessionId, tool: r.action.tool, risk: r.risk.level, options: r.options })
}
```

等待要有上限，并且无论走哪条路径都要把状态恢复回去。

```js
// 命题 5.3.5：等待有超时，且状态在异常路径下也要恢复
export function awaitDecision(req, ctx) {
  const before = ctx.stateOf(req.origin.sessionId)
  ctx.setState(req.origin.sessionId, 'waiting')
  try {
    const decision = ctx.race(req.id)
    if (decision.kind === 'timeout') {
      ctx.appendEvent({ type: 'approval/timeout', id: req.id, at: ctx.now })
      return { kind: 'deny', reason: '超时按保守默认处理' }
    }
    return decision
  } finally {
    ctx.setState(req.origin.sessionId, before)
  }
}
```

### 7.4 粒度与统计段

粒度四档决定授权的范围与失效，统计段算三个疲劳信号。

```js
// 定义 5.3.5：四档粒度与各自的失效条件
export function grantScope(option, origin, now) {
  switch (option) {
    case 'allow-session': return { scope: { sessions: [origin.sessionId] }, expiresAt: null, invalidatedBy: 'session-end' }
    case 'allow-project': return { scope: { projects: [origin.project] }, expiresAt: null, invalidatedBy: 'leave-project' }
    case 'allow-once': return { scope: {}, expiresAt: now, invalidatedBy: 'immediate' }
    default: return { scope: {}, expiresAt: null, invalidatedBy: 'manual' }
  }
}
```

疲劳的判定是三个信号的合取，缺一个就分不清成因。

```js
// 命题 5.3.1：三个疲劳信号一起看
export function fatigueSignals(events) {
  const responded = events.filter((e) => e.decision && e.decidedAt !== undefined)
  const latencies = responded.map((e) => e.decidedAt - e.raisedAt).sort((a, b) => a - b)
  const medianLatencyMs = latencies.length ? latencies[Math.floor(latencies.length / 2)] : 0
  const allowRate = responded.length ? responded.filter((e) => e.decision !== 'deny').length / responded.length : 0
  const refusalRate = responded.length ? responded.filter((e) => e.decision === 'deny' || e.decision === 'alternative').length / responded.length : 0
  return { medianLatencyMs, allowRate, refusalRate, fatigued: medianLatencyMs < 3000 && allowRate > 0.95 && refusalRate === 0 }
}
```

### 9.2 失败模式

（1）检查放在装载期（L9 位置放错）。 权限列表只在启动时加载一次，而它随使用增长。表现是"运行几周后某些操作不再询问"。

（2）前提会变（L9）。 命题 5.3.1 的疲劳判据以"响应时间反映思考"为前提。若界面本身很慢，响应时间就不再反映判断。

（3）请求难读。 人放弃判断，审批退化为形式。
（4）归属只有会话编号。 用户无法判断操作是否合理。
（5）上界排在授权之后。 下游可以放宽上游的安全决定，边界被逐步侵蚀。
（6）粒度只有"一次"与"总是"。 用户在不耐烦时选后者，权限过宽。
（7）匹配只按工具名。 "允许写"等于"随便在哪写"。
（8）等待没有超时。 会话永远停在等待状态。
（9）`finally` 里没有恢复状态。 异常路径下会话卡在 `waiting`。
（10）撤销只有手动。 权限只增不减。

**本节要点**

- 决策表覆盖 12 种情形。
- 失败模式十条，前两条是位置放错与前提会变。
- 最危险的是"上界排在授权之后"——它让安全边界被下游磨平。

## 十、仍未解决

- **多人协作的权限。** 谁有权批谁的请求需要身份与角色模型。
- **权限的可视化总览。** 累积的授权缺少一眼可读的视图。
- **跨设备的权限同步。** 同一用户在不同设备上的授权如何一致。

**本节要点**

- 单用户边界明确。
- 可视化与自动处置都还缺。
- 批量与复用边界没有定式。

## 十二、系统影响回溯

**影响一：权限预设与 5.1 的预设是两件事。** 后者描述"这个 agent 是什么"，前者描述"它能做什么而不必问"。两者的关系是预设提供权限的上界。

**影响二：审批的等待会改变会话状态，而它必须与生命周期协调。** 等待应当有超时，并把等待时间计入观测。

**影响三：权限会随使用累积，而累积的权限需要定期复核。** 处置是把权限列表纳入复盘范围。

**一处需要修正的预判。** 旧稿把"减少询问"与"把提示写清楚"当作并列的两条建议，读完之后要把它说得更准：**它们是两条互不替代的处置，对应疲劳的两个成因**——请求太多要靠预设与粒度，请求难读要靠呈现。只做一条，另一条仍然把人推回无脑点击，而两类的观测信号不同（前者的信号是请求数，后者是响应时间）。

**通向下一步的桥。**

多会话与权限解决了"同时跑多条"和"谁能做什么"，而它们把最后一个问题留给下一篇：一条会话可以把工作交给另一个执行者（子智能体），也可以调用系统之外的工具。那时权限、状态与取消都要跨过这条边界。

所以下一篇是 5.4 多智能体与外部工具，它是本卷的收口。

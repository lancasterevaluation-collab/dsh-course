## 一、为什么审批值得认真设计

### 1.1 用户看不懂在问什么

弹窗写着"是否允许执行操作？"——**用户不知道是哪个操作、影响什么范围、能不能撤销。**

### 1.2 选项里没有想要的

用户想"允许这一次，但换个方式做"——**而选项只有允许/拒绝**。于是只能拒绝，任务卡住。

### 1.3 审批疲劳

一个任务弹了十几次（见 3.2 的疲劳模型：**10 条审批时审阅率只剩 20%**），用户从第 4 次开始直接点允许。

这三件事分别对应：**呈现、选项完备性、次数控制。**

## 二、请求的七个字段

算例给出的请求字段数是 **7**。一个完整的审批请求应当包含：

| 字段 | 回答 |
|---|---|
| **动作** | 要做什么（具体的命令或操作） |
| **对象** | 对什么做（路径、资源） |
| **范围** | 影响面有多大 |
| **可逆性** | 能不能撤销、怎么撤销 |
| **风险等级** | low / medium / high / critical |
| **选项** | 允许哪些选择 |
| **截止时间** | 多久没回应就超时 |

"可逆性"是用户最关心的字段：**大多数人的判断依据不是"这危险吗"，而是"搞坏了能恢复吗"**（与 1.1 的双向门/单向门一致）。

"截止时间"为什么必需：**没有超时的审批会永久挂住。** 算例里是 600000 毫秒（10 分钟）。

## 三、怎么做

### 3.1 风险分级

算例给出的四个等级与其对应操作：

| 操作 | 等级 |
|---|---|
| 读文件 | **`low`** |
| 写入工作区文件 | **`medium`** |
| 删除构建目录 | **`high`** |
| **系统级不可逆操作** | **`critical`** |

**分级的依据是"影响面 × 可逆性"**（与 1.5 的 L0–L3 是同一个模型）：

$$
\text{风险} = \text{影响面} \times \text{不可逆程度}
$$

风险等级决定审批方式：

| 等级 | 审批方式 |
|---|---|
| `low` | 自动批准 |
| `medium` | 首次确认（同会话内记住） |
| `high` | 逐次确认 |
| `critical` | 逐次确认 + 二次确认（或直接禁止） |

"`low` 自动批准"很重要：**读操作如果也要审批，用户会在几个回合内进入疲劳状态**，后面的高危操作就没人看了。把低风险自动化，是保护高危审批的有效手段。

### 3.2 选项设计与顺序

算例给出的顺序是：

```
allow-once → allow-session → allow-project → deny → alternative
```

**这个顺序不是随意的**，它遵循三条规则：

| 规则 | 说明 |
|---|---|
| **从窄到宽** | once < session < project（授权范围递增） |
| **拒绝在宽授权之后** | 先给"最小授权"的机会 |
| **替代在最后** | 它是"都不想选时"的出路 |

为什么"从窄到宽"：**用户默认会选第一项**（选择架构里的默认效应）。把最窄的放第一，让默认是最安全的。

**"算例验证选项里有换一种做法为 `true`"这一条最关键**：必须有 "alternative"。

为什么必须有替代选项：**没有它时，用户面对一个不想允许的操作只能说"拒绝"，而拒绝会让任务失败。** 有替代项时，用户可以说"换个方式做"——这是从"能否决"升级为"能引导"。

这与 3.2 的"拒绝要给替代路径"是同一条规则：**那次是讲给模型，这次是讲给人。** 两者都基于同一个认识：只说"不行"会让对方用另一种方式再试，或者干脆卡住。

替代项的内容应当由 agent 生成：例如"改用只读方式检查，而不是直接删除"。**这要求 agent 在提出审批时就已经想过替代方案**——这是一个有价值的设计约束。

### 3.3 呈现：让人一眼看懂

算例里面向人的呈现是 **3 行**。

3 行是一个好的量级：**少于 3 行说不清，多于 3 行没人读。**

建议的内容分配：

| 行 | 内容 | 例子 |
|---|---|---|
| 第 1 行 | 动作 + 对象 | 删除 `/work/build` 目录 |
| 第 2 行 | 影响 + 可逆性 | 影响：该目录全部内容。可逆：否（未纳入版本控制） |
| 第 3 行 | 为什么需要 | 用于清理上一次构建的产物 |

"为什么需要"这一行常被忽略但很重要：**它让用户能判断"这个操作是否合理"**，而不只是判断"危险不危险"。

呈现的三条要求：

| 要求 | 反例 | 正例 |
|---|---|---|
| 具体 | "执行操作" | "删除 `/work/build` 目录" |
| 说清后果 | （缺） | "其中 3 个文件未纳入版本控制，删除后无法恢复" |
| 可判断 | 只给风险等级 | 给出影响范围与可逆性 |

### 3.4 截止时间与超时

算例里请求带截止时间 **600000 毫秒**。

超时后的默认行为必须明确：

| 策略 | 适用 |
|---|---|
| **超时即拒绝** | 安全优先（默认推荐） |
| 超时即允许 | 只在低风险场景 |
| 超时后降级 | 换一个不需要审批的方式 |

推荐"超时即拒绝"：**它与守卫的 fail-closed 一致**。超时后允许会让"不回应"变成一种绕过审批的手段。

截止时间应当与操作的风险等级相关：低风险给短（几十秒），高风险给长（几分钟到十几分钟），**因为高风险值得用户花时间想清楚**。

### 3.5 减少审批次数

由 3.2 的疲劳模型（10 条审批只剩 20% 审阅率）推出：**减少次数比提高单次质量更重要**。

| 手段 | 做法 | 代价 |
|---|---|---|
| **作用域记忆** | 本会话内同类不再问 | 范围蔓延风险 |
| **批量** | 把同类的多个操作合成一次审批 | 用户看的是汇总，细节减少 |
| **自动化低风险** | `low` 等级直接放行 | 需要准确的风险分级 |
| **预授权** | 会话开始时给出范围 | 需要用户理解范围 |

"批量"是效果最明显的：**一个任务里有 8 次写文件，合并成一次"允许本任务写入工作区"**。审批次数从 8 降到 1。

它的代价：**用户看到的是汇总，不再是每次的具体内容。** 所以批量只适用于同类且都低风险的操作。

"预授权"是最彻底但也最难的：**它要求用户在开始时就想清楚范围**。做法是把范围表达成用户能理解的短语（"允许读这个目录"），而不是路径模式。

## 四、特殊情况与处理技巧

| 情况 | 为什么 | 处理 |
|---|---|---|
| 用户看不懂 | 呈现含糊 | 动作 + 对象 + 后果 + 原因 |
| 选项里没有想要的 | 缺替代项 | 必须提供 alternative |
| 默认选项太宽 | 顺序错 | 从窄到宽，最窄在前 |
| 审批疲劳 | 次数过多 | 批量 + 自动化低风险 |
| 超时后放行 | 默认允许 | 超时即拒绝 |
| 高危操作被习惯性放行 | 与其他审批混在一起 | 高危单独弹，并要求二次确认 |
| 审批范围蔓延 | 记忆范围过宽 | 会话级记忆，不跨会话 |
| 操作已完成但用户拒绝 | 时序问题 | 审批必须在执行前 |

最后一条是硬约束：**审批必须在动作执行之前**。"先做了再问"等于没问。

## 五、工业界的做法（可照做）

### 5.1 授权界面的既有实践

| 系统 | 做法 | 值得学的点 |
|---|---|---|
| **OAuth 授权页** | 列出申请的权限范围 | 范围用用户语言表述 |
| **操作系统权限弹窗** | 一次性/始终允许 | **两档 + 系统设置里可改** |
| **企业审批流** | 多级审批 + 超时 | 超时策略明确 |
| **应用商店权限** | 安装时列出全部权限 | 事前一次性告知 |

**"命令行式"的授权（agent 场景）比 GUI 弹窗更受限**，但规则相同：具体、可判断、有替代。

OAuth 的"范围用用户语言表述"最值得学：**"读取你的联系人"比"contacts.read"有用得多。** 对 agent 来说，"删除构建目录"比 `fs.delete(recursive=true)` 有用得多。

### 5.2 审批的服务端实现

| 关注点 | 做法 |
|---|---|
| **幂等** | 同一次请求重放不重复执行（见 3.1） |
| **超时** | 服务端计时，超时即拒绝 |
| **并发** | 同一会话的多个审批串行呈现 |
| **审计** | 记录谁在什么时候批准了什么 |
| **撤回** | 已批准但未执行时允许取消 |

"审计"是企业场景的硬要求：**审批记录是合规的一部分**。它同时是事后分析的依据（4.6 复盘的输入）。

### 5.3 参数与设计起点

| 参数 | 推荐 | 依据 |
|---|---|---|
| 请求字段 | 7 个 | 见第二节 |
| 呈现行数 | 3 行 | 算例值 |
| 选项数 | 3–5 个 | 与"从窄到宽 + 拒绝 + 替代"匹配 |
| 截止时间 | 交互 1–2 分钟，高危 10 分钟 | 与风险相关 |
| 单任务审批次数 | ≤ 5 次 | 超过即疲劳 |
| 会话记忆范围 | 单会话 | 不跨会话 |
| 二次确认阈值 | `critical` | 见 3.1 |

### 5.4 一份可落地的实施清单

1. **七字段**：动作、对象、范围、可逆性、风险、选项、截止时间。
2. 风险分级：`low` 自动、`medium` 首次确认、`high` 逐次、`critical` 二次确认。
3. 选项顺序：从窄到宽，拒绝在宽授权之后，替代放最后。
4. 必须有替代项：由 agent 生成。
5. 呈现三行：动作对象 / 影响可逆 / 为什么需要。
6. 超时即拒绝：并在审计里记录超时。
7. 批量：同任务同类低风险操作合并。
8. 会话级记忆：不跨会话。
9. 审计：批准记录可查询。
10. 测试：验证"超时即拒绝"与"替代项可执行"。

## 六、学术界的结论

### 6.1 可用安全

**可用安全**（usable security）领域的核心发现是：安全机制的有效性取决于它是否被正确使用，而这取决于它的可用性。

| 发现 | 含义 |
|---|---|
| **警告疲劳真实存在** | 频繁警告会被忽略（与 3.2 的疲劳模型一致） |
| **默认值影响力极大** | 大多数人接受默认 |
| **具体信息能提高关注** | "你的文件将被上传到 X"比"继续吗"有效 |
| **提供替代能提高合规率** | 有出路时人们更愿意拒绝危险选项 |

最后一条直接支持 3.2 的"必须有替代项"：**给人一条出路，他们才更愿意说"不"。**

### 6.2 选择架构

行为经济学里的**选择架构**（choice architecture）指出：选项的排列方式会显著影响选择。

| 效应 | 表现 |
|---|---|
| **默认效应** | 默认选项被选中的概率远高于其他 |
| **顺序效应** | 靠前的选项更容易被接受 |
| **框架效应** | 表述方式影响判断 |

对本篇的直接应用：**把"最窄的授权"放在最前并设为默认**，利用默认效应提高安全性。

**这是"用设计而非限制来引导行为"的实例**——它比强制更少摩擦，但同样有效。

### 6.3 知情同意

医疗与数据伦理里的"知情同意"有两个要素：

| 要素 | 含义 | 对本篇的要求 |
|---|---|---|
| **知情** | 理解在做什么、有什么后果 | 呈现必须具体 |
| **自愿** | 没有被迫 | 必须有拒绝与替代的真实选项 |

"自愿"这一条容易被技术系统破坏：**如果拒绝会导致任务彻底失败，那么"同意"实际上不是自愿的。** 这正是"必须提供替代项"的伦理依据。

### 6.4 同意疲劳的实证

多项研究记录了**同意疲劳**现象：频繁的同意请求会导致用户无条件接受。

**机制上这与 3.2 的审批疲劳模型一致**（审阅率随条数下降）。

研究给出的缓解手段与本篇一致：

| 手段 | 效果 |
|---|---|
| 减少请求次数 | 最有效 |
| 合并同类请求 | 有效 |
| 把低风险自动化 | 有效 |
| 提高单次信息质量 | 有效但有限 |

**"减少次数"排在第一位**——这与本篇 3.5 的排序一致。

## 七、理论：选项的完备性

### 7.1 必须包含替代

$$
\text{alternative} \in \text{选项}
$$

算例验证：**"选项里是否有换一种做法"为 `true`**。

为什么这是硬要求：**没有替代项时，"拒绝"与"任务失败"是等价的**，于是同意不再是自愿的（见 6.3）。加入替代项把二元选择变成三元（允许/拒绝/换法），从而恢复了真实的拒绝权。

### 7.2 授权范围与次数的权衡

设单次授权范围 $s$、需要审批的操作数 $n$，则总审批次数约为：

$$
\text{次数} \approx \frac{n}{s}
$$

含义：**扩大授权范围能线性减少次数**，但范围越大，单次错误的代价越高（影响面 $\propto s$）。

这是一个明确的权衡：

| 策略 | 次数 | 单次风险 |
|---|---|---|
| 逐次 | $n$ | 最低 |
| 会话级 | 约 1 | 中 |
| 项目级 | 约 0 | 高 |

算例给出的风险分级正是这个权衡的落地：**低风险往"减少次数"一侧靠，高风险往"降低单次风险"一侧靠。**

## 九、练习

### 第一题：设计一个审批请求

场景：agent 要执行 `rm -rf node_modules && npm install`。

要求：

- 写出完整的七字段。
- 给出风险等级与依据（影响面 × 可逆性）。
- 写出 3 行呈现内容。
- 给出五个选项（含替代），并说明替代项具体是什么。

---

### 第二题：算审批次数

场景：一个任务需要 3 次读文件、6 次写工作区文件、1 次删除目录、1 次调用外部 API。

要求：

- 按 3.1 的分级，算出"逐次审批"下的审批次数。
- 用批量与自动化（`low` 自动、同任务 `medium` 合并）把次数降到 5 次以内，说明具体做法。
- 用 3.2 的疲劳模型估算改造前后的审阅率（假设 $\rho = 0.5$）。
- 说明这个改造失去了什么。

---

### 第三题（进阶）：设计选项的顺序与内容

要求：

- 为一个"发送邮件"的操作设计 4–5 个选项，按从窄到宽排序。
- 说明默认项是哪一个，以及依据。
- 设计一个"替代项"，并说明它为什么比"拒绝"更有用。
- 指出这套选项在什么情况下会让用户产生错误的安全感。

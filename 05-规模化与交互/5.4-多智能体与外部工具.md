## 本篇新词

- 派发（delegation） 指把一个任务交给另一个 agent 执行并取回结果。它更像"交接"而不是"调用"。
- 子 agent（subagent） 指被派发任务的执行者。它是一个独立的会话，而它的授权继承自父会话。
- 派发协议（delegation protocol） 指父与子交换的四样内容：目标、上下文子集、约束、产出格式。
- 上下文子集（context subset） 指派发时给子 agent 的信息。判据是"子任务需要的最小事实集"。
- 结果回收（result collection） 指把子 agent 的产出并入父会话。它要求结构化与有界。
- 递归深度（recursion depth） 指派发的层数，必须有上限。
- 成本放大（cost amplification） 指派发带来的 token 消耗倍数。
- 外部工具（external tool） 指由本进程之外提供的能力。
- 信任边界（trust boundary） 指外部工具能做什么、不能做什么。

## 一、【设计原因】

### 1.1 缺陷一：派发回来的是散文，父会话无法机械采纳

子 agent 完成了任务，返回一段描述过程的文字，而父会话需要的是一个补丁或一份结构化结论。

父会话这时只有两条路：自己从散文里提取（重新投入上下文，抵消了派发的收益），或者放弃这个结果（那次派发的成本白花）。

### 1.2 缺陷二：子 agent 越权

父会话的预设是只读，而它派发的子 agent 用的是可写的预设。用户设定的边界实际上不存在了——他只是看不到绕过发生在一层之下。

另一个后果是审批量随派发增长：授权不继承时，每个子任务的危险操作都要单独询问。

### 1.3 缺陷三：预算用尽，已做的功被丢弃

子 agent 做了一半而预算用尽，实现直接判定失败并丢弃中间结果。父会话无法判断"这些够不够"，也无法在此基础上继续。

### 1.4 缺陷四：外部工具能碰到不该碰的东西

接入一个外部工具时按它声明的能力给它权限。而它声明的能力可能远大于这次任务需要——第三方实现能读到不该读的路径、能访问不该访问的域名。

### 1.5 由此确定的设计目标

1. 派发协议四要素缺一即拒，不浪费一次运行。
2. 授权与工具集继承父会话，**不可提权**。
3. 回收有格式与容量两个要求，不符则返回可重试的失败。
4. 限制三层：深度、预算、并发；预算用尽返回部分结果而非丢弃。
5. 外部工具的权限默认最小集，扩大要走显式授权。

**本节要点**

- 散文式产出会让回收抵消收益。
- 提权绕过的是用户看不见的一层。
- 丢弃半成品是双重浪费。
- 外部工具的默认权限必须是最小集。
- 五条目标：协议完整、不可提权、回收可采纳、限制三层、边界最小。

## 二、【直觉】

### 2.1 外包与自做

把一件事外包出去，成本结构会变。

- 你要写清楚要做什么（目标）、给它必要的资料（上下文）、划出不能碰的界线（约束）、说清交付形态（产出格式）。
- 对方自己也要跑一遍完整过程（它的消耗不小）。
- **交付的东西要能用**——一份"我大致做了"的说明没有价值。

所以判断是否外包的标准是：被隔离掉的中间过程，是否远多于交接与验收的开销。

::: keypoint 反直觉点
**"能派发"不等于"该派发"。** 派发的直接成本约是自做的 2–3 倍，而它换来的是父会话的上下文不被若干子过程占据。当子任务很短、结论很简单时，这个交换是亏的。
:::

### 2.2 交接单

一次合格的交接要有四样。

| 要素 | 缺了会怎样 |
|---|---|
| 目标 | 做错方向 |
| 上下文 | 信息不足，返工 |
| 约束 | 越界改动 |
| 产出格式 | 结果无法被采纳 |

**四样缺一，返工的成本都比写清它更高。**

### 2.3 一个数字直觉

设父会话派发 5 个子任务，每个子 agent 完整运行消耗 30K token，父会话为派发与回收消耗 10K token。

- 总消耗约 $5 \times 30 + 10 = 160$K。
- 若父会话自己顺序做这 5 件事，消耗可能是 60K。

**派发的直接成本是 2.7 倍**，而它换来的是父会话的上下文不被那 5 段中间过程占据。

**本节要点**

- 外包要写清四样东西。
- 能派发不等于该派发。
- 成本约 2.7 倍，换来的是上下文隔离。

## 三、【严格】

### 3.1 定义

::: theorem 定义 5.4.1（派发与子 agent）
一次派发把任务交给一个**独立会话**执行：

$$
\mathrm{delegate}: (\mathit{parent},\ \mathit{spec}) \to \mathrm{Collected},
$$

子 agent 有自己作用域与容器，而它的**授权与工具集继承自父会话**。
:::

::: theorem 定义 5.4.2（派发协议）
协议由四个必填要素构成：

$$
\mathit{spec} = (\mathit{goal},\ \mathit{context},\ \mathit{constraints},\ \mathit{outputFormat}),
$$

缺任一即拒绝派发（在启动子会话之前）。另外两个字段是记录性的：父任务语境（子 agent 判断自己的边界用）与**深度**（限制的依据）。
:::

::: theorem 定义 5.4.3（结果回收）
回收有两条要求：

$$
\text{回收} = (\text{结构化},\ \text{有界}),
$$

即产出能被父会话机械采纳，且体积受容量限制。**格式不符时返回可重试的失败**，而不是接受任意产出。
:::

::: theorem 定义 5.4.4（三层限制）
派发的限制是

$$
(\text{最大深度},\ \text{预算},\ \text{并发上限}),
$$

其中预算含 token 与调用次数两项，且**用尽时返回部分结果并标记未完成**。
:::

::: theorem 定义 5.4.5（外部工具与信任边界）
外部工具指进程之外提供的能力。它的授权由信任边界描述：

$$
\mathit{boundary} = (\mathit{fs},\ \mathit{net},\ \mathit{env},\ \mathit{sideEffectCeiling},\ \mathit{budget},\ \mathit{contextSharing}),
$$

其中 $\mathit{sideEffectCeiling}$ 把"这个工具最多能做到什么"变成一个可校验的声明。**默认是最小集，扩大需要显式授权。**
:::

::: theorem 定义 5.4.6（外部错误归一化）
外部错误被映射到内部的三类：

$$
\mathrm{normalize}: \text{外部错误} \to \{\text{可重试},\ \text{致命},\ \text{未知}\},
$$

其中**未知错误一律视为致命且需人介入**。
:::

### 3.2 命题

::: theorem 5.4.1（派发的成本放大）
设子任务数为 $n$、每个子 agent 的完整消耗为 $c$、父会话的派发与回收开销为 $o$，则派发的总成本约为 $nc + o$，而自做的成本约为 $c' < nc$。

**证明.** 每个子 agent 是一次完整运行（它有自己的输入与输出），故 $n$ 个子任务的消耗至少为 $nc$。父会话还需为每次派发写协议并回收结果，故加上 $o$。自做时这些工作在同一上下文里顺序完成，不重复说明目标也不产生回收，故成本更低。

↓ **为什么能这么写？** 成本是各部分运行量之和，而派发引入了重复部分。

$\blacksquare$

**数值**：$n = 5$、$c = 30$K、$o = 10$K 时总成本 160K，约为自做 60K 的 2.7 倍。
:::

::: theorem 5.4.2（派发的适用判据）
派发划算，当且仅当被隔离的中间过程量 $I$ 大于派发与回收的开销 $o$。

**证明.** 收益是把 $I$ 从父会话的上下文中移除（它因而不再占用后续每一轮的输入），成本是 $o$ 的一次性支出。当 $I > o$ 时净收益为正。反之，父会话为一次短任务付出了大于其隔离量的开销。

↓ **为什么能这么写？** 收益与成本都以 token 计量，可直接比较。

$\blacksquare$

**数值**：子任务很短或结论很简单时 $I$ 很小，此时直接做更好。
:::

::: theorem 5.4.3（子 agent 不可提权）
若子 agent 可按自己的预设获得更宽的工具与授权，则父会话的限制可被绕开。

**证明.** 设父会话预设为只读。若子 agent 可用可写预设，则它执行写操作时，父的限制在语义上仍然成立（父自己没有写），而实际效果是写发生了。用户设定的边界因此不构成约束。

↓ **为什么能这么写？** 限制的有效性要求它在所有后代上成立。

$\blacksquare$

::: keypoint 授权继承与审批量
**授权继承的第二个收益是审批量不随派发增长。** 若授权不继承，一次派发十个子任务意味着十倍的危险操作需要单独询问——这直接把 5.3 的疲劳问题放大一个量级。
:::

::: theorem 5.4.4（产出格式必须含容量）
若产出格式只声明形态而不声明容量，则回收可能淹没父会话。

**证明.** 父会话的收益来自"子过程不占用它的上下文"。若回收的内容量接近甚至超过被隔离的量，则净收益转为负。容量上限把回收的体积固定在一个与隔离量可比的范围内。

↓ **为什么能这么写？** 净收益是收益减成本，而成本包含回收体积。

$\blacksquare$

::: theorem 5.4.5（预算用尽应返回部分结果）
若预算用尽时丢弃中间结果，则已完成的功被浪费，且父会话失去判断依据。

**证明.** 中间结果包含了已完成部分的信息。丢弃后父会话只能选择重新派发（重复已做的功）或放弃。保留则父会话可以判断"这些够不够"，或在已有进展上继续。

↓ **为什么能这么写？** 信息的存在扩大了后续可选择动作的集合。

$\blacksquare$

**数值**：实现要求协议里声明"部分结果可接受"，否则子 agent 会认为未完成等于失败而不返回任何东西。这与"压缩保留指针"、"抑制而不是删除"是同一条原则的又一次出现。
:::

::: theorem 5.4.6（未知外部错误必须视为致命）
对未识别错误重试可能产生重复副作用。

**证明.** 未知错误意味着错误发生在协议之外的某处，因此该次调用是否已经产生了副作用不可知（例如请求已到达而响应丢失）。重试可能使副作用发生两次。故在这种情况下保守处理（不重试、交给人）是唯一不引入额外风险的选择。

↓ **为什么能这么写？** 重试的安全性以"上次调用没有产生效果"为前提，而未知错误不提供这个前提。

$\blacksquare$

### 3.3 本节要点

**本节要点**

- 子 agent 是独立会话，授权继承父会话（定义 5.4.1）。
- 协议四要素缺一即拒（定义 5.4.2）。
- 回收要求结构化与有界（定义 5.4.3）。
- 限制三层：深度、预算、并发（定义 5.4.4）。
- 信任边界含副作用上限，默认最小集（定义 5.4.5）。
- 外部错误归一化，未知视为致命（定义 5.4.6）。
- 派发的成本放大（命题 5.4.1）。
- 适用判据是隔离量大于开销（命题 5.4.2）。
- 子 agent 不可提权（命题 5.4.3）。
- 产出格式必须含容量（命题 5.4.4）。
- 预算用尽返回部分结果（命题 5.4.5）。
- 未知外部错误视为致命（命题 5.4.6）。

## 四、【回到直觉】

- 定义 5.4.1 说的：被派发者是一个独立干活的人，但他不能有比你更大的权限。
- 定义 5.4.2 说的：要写清做什么、给它什么资料、不许碰什么、交付什么形态。
- 定义 5.4.3 说的：交回来的东西要能直接用，而且不能太长。
- 定义 5.4.4 说的：层数、花销、同时几个，都要有上限。
- 定义 5.4.5 说的：外面那台机器最多能做到什么，要写在纸上。
- 定义 5.4.6 说的：不认识的错误，不要重试。
- 命题 5.4.1 说的：外包的总花销约为自己做的 2.7 倍。
- 命题 5.4.2 说的：被隔离掉的中间过程要远多于交接与验收的开销，才划算。
- 命题 5.4.3 说的：一层之下的越权，用户看不见。
- 命题 5.4.4 说的：交付形态里要写体积上限。
- 命题 5.4.5 说的：做了一半也要交，别扔。
- 命题 5.4.6 说的：不认识的错就往坏了想。

**本节要点**

- 不可提权。
- 协议四要素。
- 回收两要求。
- 限制三层。
- 边界最小集。
- 未知错误致命。

## 五、【工具箱】

### 5.1 该不该派发的判断

1. 被隔离的中间过程量有多大？
2. 派出与回收的开销有多大？
3. 前者是否明显大于后者？

**前两者都为零附近的答案是不派。** 子任务很短时，写协议与验收的开销就已经超过了收益。

### 5.2 协议四要素的写法

| 要素 | 怎么写 |
|---|---|
| 目标 | 一句话讲清要产出什么 |
| 上下文 | 最小事实集，并说明**不给什么** |
| 约束 | 不能做什么（含不许改动的范围） |
| 产出格式 | 形态加**容量上限** |

**"不给什么"这条常被省略**，而它防的是子 agent 自己去找（例如翻到不该看的文件）。

### 5.3 回收的三件事

1. **格式校验**：不符时返回可重试的失败，而不是接受任意产出。
2. **有界裁剪**：超长产出裁到容量内，并报告被裁掉多少。
3. **追溯元数据**：带上子会话的 token 消耗与轮数，供复盘使用。

### 5.4 外部工具的接入清单

| 项 | 默认 |
|---|---|
| 文件读写 | 白名单路径，默认为空 |
| 网络访问 | 域名白名单，默认为空 |
| 环境变量 | 白名单，默认为空 |
| 副作用上限 | 只读 |
| 资源预算 | CPU、内存、每分钟调用数 |
| 上下文共享 | 不共享父会话历史；记忆经过筛选 |

**命名加来源前缀**（例如 `mcp__server__tool`），让调用点在名字上就能看出它来自哪里。

### 5.5 错误的归一化

| 外部错误 | 归一化结果 | 处置 |
|---|---|---|
| 超时 | 可重试 | 走重试策略 |
| 连接失败 | 可重试 | 走重试策略 |
| 协议不匹配 | 致命 | 报告并停用该工具 |
| 参数被拒 | 致命 | 回给模型 |
| 未识别 | 致命且需人介入 | 不重试，记录 |

**本节要点**

- 派发判断看两个量。
- 协议四要素，含"不给什么"。
- 回收三件事。
- 边界默认最小集。
- 未知错误不重试。

### 7.2 派发段与继承段

派发段在启动子会话之前完成校验，继承段保证不可提权。

```js
// 定义 5.4.2：协议四要素缺一即拒
export function buildDelegation(parent, spec) {
  const required = ['goal', 'context', 'constraints', 'outputFormat']
  const missing = required.filter((k) => !spec[k] || (Array.isArray(spec[k]) && spec[k].length === 0))
  if (missing.length) throw new Error(`派发缺少：${missing.join('、')}`)
  return {
    id: spec.id ?? `d-${parent.id}-${spec.goal.length}`,
    parentSession: parent.id,
    parentTask: parent.goal,
    depth: (parent.depth ?? 0) + 1,
    budget: { maxTokens: spec.budget?.maxTokens ?? 50000, maxToolCalls: spec.budget?.maxToolCalls ?? 30 },
    ...spec,
  }
}
```

继承的判据只有一条：子 agent 不能拿到父会话没有的东西。

```js
// 命题 5.4.3：子 agent 的授权与工具集不得超过父会话
export function inherit(parent, childSpec) {
  const extraTools = childSpec.tools.filter((t) => !parent.tools.includes(t))
  if (extraTools.length) {
    throw new Error(`子 agent 的工具超出父会话：${extraTools.join('、')}`)
  }
  return {
    tools: childSpec.tools,
    permissions: [...parent.permissions],
    sideEffectCeiling: parent.sideEffectCeiling,
  }
}

/**
 * 定义 5.4.4：三层限制的准入判断。
 * @param parent 父会话
 * @param spec 派发协议
 * @param ctx 形如 `{ maxDepth, maxChildren, activeChildren, globalConcurrent, globalMaxConcurrent }`
 * @returns `{ ok, reason? }`
 */
export function admitDelegation(parent, spec, ctx) {
  const depth = (parent.depth ?? 0) + 1
  if (depth > ctx.maxDepth) return { ok: false, reason: `深度超限：${depth} > ${ctx.maxDepth}` }
  if (ctx.activeChildren >= ctx.maxChildren) return { ok: false, reason: '子任务数已满' }
  if (ctx.globalConcurrent() >= ctx.globalMaxConcurrent) return { ok: false, reason: '全局并发已满' }
  return { ok: true }
}
```

### 7.3 回收段与限制段

回收段校验格式、裁剪容量并附元数据。限制段把预算用尽变成优雅停止。

```js
// 定义 5.4.3：回收——格式不符返回可重试失败，超长裁剪并报告
export function collect(raw, outputFormat, meta) {
  if (outputFormat?.kind && raw?.kind !== outputFormat.kind) {
    return { ok: false, retryable: true, reason: `产出格式不符：期望 ${outputFormat.kind}，得到 ${raw?.kind ?? '未知'}` }
  }
  const text = typeof raw === 'string' ? raw : JSON.stringify(raw)
  const max = outputFormat?.maxChars ?? Infinity
  if (text.length > max) {
    return {
      ok: true,
      value: text.slice(0, max),
      truncated: text.length - max,
      meta,
    }
  }
  return { ok: true, value: text, truncated: 0, meta }
}
```

预算用尽不是失败，而是"交回已完成的部分"。

```js
// 命题 5.4.5：预算用尽返回部分结果并标记
export function exhaustion(used, budget) {
  if (used.tokens >= budget.maxTokens) return { stop: true, reason: 'token 预算用尽', partial: true }
  if (used.toolCalls >= budget.maxToolCalls) return { stop: true, reason: '调用次数用尽', partial: true }
  return { stop: false, reason: null, partial: false }
}

/**
 * 命题 5.4.1：派发的成本放大。
 * @param childTokens 每个子 agent 的完整消耗
 * @param children 子任务数
 * @param overhead 父会话的派发与回收开销
 * @param directCost 自做的成本
 * @returns `{ delegated, direct, ratio }`
 */
export function costAmplification(childTokens, children, overhead, directCost) {
  const delegated = childTokens * children + overhead
  return { delegated, direct: directCost, ratio: delegated / directCost }
}
```

/**
 * 定义 5.4.6：把外部错误归一化成内部三类。
 * @param error 形如 `{ kind }` 的外部错误
 * @returns `{ kind, action }`

export function normalizeExternalError(error) {
  if (error.kind === 'timeout' || error.kind === 'connection') return { kind: 'retryable', action: '按重试策略处理' }
  if (error.kind === 'protocol' || error.kind === 'invalid-args') return { kind: 'fatal', action: '报告并停用该工具' }
  return { kind: 'fatal', action: '不重试，交给人' }
}

### 9.2 失败模式

（1）检查放在装载期（L9 位置放错）。 信任边界在接入外部工具时校验一次，而工具的能力会随版本变化。表现是"工具升级后能做它以前做不到的事"。

（2）前提会变（L9）。 命题 5.4.2 的适用判据以"隔离量可估计"为前提，而它在派发之前往往只能粗略估计。

（3）产出格式没有定义。 回收的内容无法被机械采纳，父会话被迫重新阅读。
（4）产出格式没有容量。 回收淹没父会话，净收益转为负。
（5）子 agent 可提权。 父会话的限制在一层之下被绕过。
（6）授权不继承。 审批量随派发成倍增长。
（7）没有深度上限。 子 agent 继续派发，成本指数上升。
（8）预算用尽即丢弃。 已做的功白费。
（9）外部工具按声明给权限。 第三方实现的权限远超需要。
（10）未知外部错误被重试。 可能产生重复副作用。

**本节要点**

- 决策表覆盖 12 种情形。
- 失败模式十条，前两条是位置放错与前提会变。
- 最危险的是"子 agent 可提权"——它让用户设定的边界在看不见的一层失效。

## 十二、系统影响回溯

**影响一：派发把"一条会话"扩展成"一棵会话树"，而权限与取消都要沿树传播。** 本篇的不可提权与深度上限是这棵树的两条约束。

**影响二：外部工具把信任边界从进程内扩展到进程外。** 它的默认必须是最小集。

**影响三：多智能体的成本按层数放大。** 这条量级决定了深度上限必须存在，而且必须小。

**一处需要修正的预判。** 旧稿把"派发"描述成一种提高并行度的手段，读完之后要把它说得更准：**派发的首要价值是上下文隔离，而不是并行。** 并行度只是附带效果（而且受下游配额限制，5.2 命题 5.2.1），而隔离是它唯一不能由别的手段替代的作用——这一点从成本结构就能看出（成本增加 2.7 倍，换来的只有上下文的干净）。

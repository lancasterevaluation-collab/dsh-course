# 5.4 多智能体与外部工具

> **这一篇讲什么**：派发是"把任务交给另一个 agent"。它的成本结构与直觉相反：同一件事，派发的总消耗是自做的 2.67 倍（算例里 160K / 60K）。所以派发不是免费的并行，而是一次用成本换隔离的交易——只有当隔离带来的收益大于这个开销时才划算。算例也给出了这个判据：隔离量大于开销时划算，小于时不划算。

## 一、为什么派发是一次交易

### 1.1 成本失控

把任务拆给五个子 agent 并行做，账单涨了 5 倍，**而任务并不比自做快**。

### 1.2 上下文串扰

子 agent 看到了父任务的完整历史，**被无关信息带偏**，做了一件没人要的事。

### 1.3 目标丢失

派发的指令写得太简略，**子 agent 理解了但理解错了**——它完成了字面要求，没完成真实目标。

这三件事分别对应：**成本核算、上下文隔离、四要素完备。**

## 二、派发的四要素

算例给出的四要素（**每一个缺失都会抛错**）：

| 要素 | 回答 | 缺了会怎样 |
|---|---|---|
| **目标** | 要达到什么 | 子 agent 不知道做什么 |
| **约束** | 不能做什么 | 越界 |
| **输出规格** | 交付什么形式 | 结果无法使用 |
| **预算** | 能用多少资源 | 成本失控 |

四要素与 1.4 的契约四要素是同源的：**目标 ≈ 后置条件，约束 ≈ 前置条件与不变量，输出规格 ≈ 结果格式，预算 ≈ 资源约束。**

这四样缺一不可的原因：**派发是一次"不完整的沟通"**——子 agent 看不到父任务的上下文，所以它只能依赖这四要素来理解任务。

## 三、怎么做

### 3.1 四要素缺一不可

实现如下。

```js
// 派发：四要素缺一即拒绝，避免子任务在信息不全时开工
export function delegate(request) {
  for (const field of ['goal', 'constraints', 'outputSpec', 'budget']) {
    if (!request[field]) throw new Error(`派发缺少 ${field}`)
  }
  return { id: nextId(), ...request, depth: (request.depth ?? 0) + 1 }
}
```

算例实测：

| 情况 | 结果 |
|---|---|
| 四要素各缺一次 | **都抛错** |
| 缺目标 | **抛错** |
| 四要素齐全 | **通过** |

"缺目标也抛错"值得单独强调：**它看起来显然，但实践中常被省略**——因为派发者心里知道目标，就假设对方也知道。而子 agent 不在那个上下文里。

**这与 4.7 的"下一步要写成动作 + 对象 + 验证"是同一件事**：可执行的指令必须是自足的。

### 3.2 上下文隔离

派发的核心收益就是隔离：**子 agent 只在需要的信息里工作**。

算例验证：**父任务语境被记录**（`true`），深度为 1。

"父任务语境被记录"的含义：**父任务的信息被"记录"而不是"复制"**。

| 做法 | 效果 |
|---|---|
| **复制完整上下文** | 成本高（2.67 倍就是这么来的），且串扰 |
| **只给必要信息** | 成本低，隔离好 |
| **记录父任务引用** | 需要时可按需查询 |

推荐"只给必要信息 + 记录父任务引用"：**它既有隔离（子 agent 看不到无关内容），又可追溯（需要时能找到父任务）。**

隔离的具体收益：

| 收益 | 说明 |
|---|---|
| **上下文更短** | 子任务输入小，成本低 |
| **不被无关信息带偏** | 专注 |
| **失败不污染父任务** | 子任务的错误留在子任务里 |
| **可并行** | 互不干扰 |

最后一条是派发最常见的目的：**并行多个子任务**。但要注意——并行的收益与 3.6 的尾延迟放大相互作用（并行越多，整体 P99 越差）。

### 3.3 预算

算例里默认预算是 **50000 token**。

为什么必须有预算：**子 agent 是独立运行的，它不会自动知道"该省着用"。** 没有预算时，一个子任务可能消耗掉整个会话的配额。

| 预算项 | 作用 |
|---|---|
| token 上限 | 控制成本 |
| 步数上限 | 控制轮数（与 2.7 的最大步数一致） |
| 时间上限 | 控制墙钟时间 |
| 递归深度 | 控制派发层级 |

**预算用尽时的行为**必须明确：返回部分结果还是报错。

推荐"返回部分结果 + 标注未完成"：**部分结果通常仍有用**，而"什么都没得到"最糟。这与 2.2 的"截断要说明丢失量"是同一个思路。

### 3.4 深度限制

算例里深度是 **1**（即父任务派发一层）。

深度限制的必要性：**派发是可以递归的**，而递归派发的成本是指数级的（每层都放大——见 7.1）。

参数建议：

| 深度 | 适用 |
|---|---|
| 0 | 不允许派发（最简单） |
| **1** | **常见默认**（父派子，子不再派） |
| 2 | 任务确实需要两级分解 |
| >2 | 极少需要，且成本极高 |

**深度限制应当写成硬约束**（与 2.7 的最大步数、3.1 的重试预算一样）：任何可以递归的机制都必须有深度上限。

这与 3.2 的"保护集合必须包含自身"是同一种思维：**递归结构必须显式限界。**

### 3.5 成本核算与划算判据

这是本篇最重要的一节。算例给出的成本对照：

| 项 | 值 |
|---|---|
| 派发总消耗 | **160K** |
| 自做消耗 | **60K** |
| **放大倍数** | **2.67** |

为什么派发更贵：**子 agent 需要自己的上下文**——

| 成本来源 | 说明 |
|---|---|
| 系统提示与工具定义 | 每个子 agent 都要一份（见 2.1 的前缀缓存） |
| 任务描述 | 四要素要写清楚 |
| 中间结果 | 子 agent 自己的推理过程 |
| 结果汇总 | 父任务要读回子结果 |

**所以派发不是"把工作分出去"，而是"复制一份工作环境再分出去"。**

**划算判据**（算例给出的对照）：

| 情况 | 划算 |
|---|---|
| **隔离量大于开销** | **`true`** |
| 隔离量小于开销 | **`false`** |

"隔离量"怎么量化：**子任务真正需要的信息量 vs 父任务上下文的总量**。

$$
\text{划算} \iff \frac{\text{子任务需要的信息}}{\text{父任务上下文}} < \frac{1}{\text{放大倍数}}
$$

举例：父任务上下文 100K，子任务只需要 5K，放大倍数 2.67：

- 自做成本：100K（每轮重发，见 2.1 的二次增长）
- 派发成本：5K × 2.67 ≈ 13K
- **划算**（13K < 100K）

反过来：父任务上下文 10K，子任务需要 8K：**派发不划算**（8K × 2.67 > 10K）。

判据的实践形式：**"这个子任务需要父任务的大部分上下文吗？"** 如果需要，自做更划算。如果只需要一小部分，派发更划算。

这条判据可以直接改变做法：

| 场景 | 选择 | 理由 |
|---|---|---|
| 大规模检索（只需返回摘要） | **派发** | 子任务输出小，父任务不必读全部材料 |
| 独立的小修改 | 自做 | 子任务需要父任务的上下文 |
| 并行探索多个方案 | **派发** | 各方案互不依赖 |
| 需要频繁交互的调试 | 自做 | 来回沟通成本高于隔离收益 |

"大规模检索"是派发最典型的划算场景：**子 agent 读了一百个文件，只返回一段摘要**——父任务的上下文里只留摘要（这与 3.6 的"外置"是同一个手段）。

## 四、特殊情况与处理技巧

| 情况 | 为什么 | 处理 |
|---|---|---|
| 成本涨了几倍 | 未核算 | 比较"隔离量 vs 开销" |
| 子任务被带偏 | 上下文未隔离 | 只给必要信息 |
| 子任务理解错 | 缺目标 | 四要素缺一即拒绝 |
| 成本失控 | 无预算 | token + 步数 + 时间上限 |
| 递归派发爆炸 | 无深度限制 | 硬上限（默认 1） |
| 子任务失败拖垮父任务 | 未隔离失败 | 失败留在子任务内，父任务降级处理 |
| 结果无法使用 | 未规定输出规格 | 输出规格写进四要素 |
| 并行反而更慢 | 尾延迟放大 | 减少并行度（见 3.6） |

"失败隔离"值得展开：**子任务失败不应让父任务崩溃。** 正确做法是把失败当作一种结果返回（与 2.7 的"每个调用都必须有结果"完全一致）——父任务拿到"这个子任务失败了"，然后决定怎么办。

## 五、工业界的做法（可照做）

### 5.1 派发的工程形态

| 形态 | 做法 | 特点 |
|---|---|---|
| **子 agent** | 进程内派生一个受限 agent | 共享进程，隔离靠作用域 |
| **worker 池** | 独立进程/容器执行任务 | 隔离强，启动开销大 |
| **任务队列** | 提交任务，异步拿结果 | 解耦，适合长任务 |
| **外部工具（MCP）** | 通过协议调用外部能力 | 能力扩展，需信任边界 |

**四者的隔离强度递增，开销也递增**。选择依据与 3.2 的沙箱选型相同：运行谁的代码。

"外部工具"与"派发"的区别：**外部工具是"调用一个能力"，派发是"委托一个任务"**。前者不产生新的 agent，后者会产生。所以外部工具的成本放大远小于派发。

### 5.2 什么时候该并行

| 判据 | 并行 | 串行 |
|---|---|---|
| 子任务互不依赖 | 是 | |
| 结果需要汇总 | 是（可并行收集） | |
| 需要频繁交互 | | 是 |
| 依赖前一个结果 | | 是 |
| 尾延迟敏感 | | 是（见 3.6） |

"依赖前一个结果"时必须串行：**并行执行有依赖的任务会得到错误结果**（这是 1.1 的依赖序问题）。

相关工具：**Anthropic 的"orchestrator-worker"模式**是最常见的多智能体形态——一个主 agent 分解任务，若干 worker 并行执行。它的成本特征与本篇的分析一致。

### 5.3 参数与设计起点

| 参数 | 推荐 | 依据 |
|---|---|---|
| 四要素 | 全部必填 | 缺一即失败 |
| 默认预算 | 50000 token | 算例值 |
| 步数上限 | 10–20 | 与 2.7 一致 |
| 深度上限 | 1 | 成本指数增长 |
| 并行度 | 2–5 | 尾延迟与配额 |
| 输出规格 | 必须结构化 | 便于汇总 |
| 失败处理 | 作为结果返回 | 隔离 |

### 5.4 一份可落地的实施清单

1. **四要素**：目标、约束、输出规格、预算，缺一即拒绝。
2. 上下文隔离：只给必要信息，记录父任务引用。
3. 预算：token、步数、时间、深度四类上限。
4. 预算耗尽：返回部分结果并标注。
5. 深度上限：默认 1。
6. 成本核算：记录"派发 vs 自做"的对照数据。
7. 划算判据：用"子任务所需信息 / 父上下文"判断。
8. 失败隔离：失败作为结果返回。
9. 并行判据：无依赖才并行。
10. 观测：派发次数、成本放大倍数、成功率。

## 六、学术界的结论

### 6.1 多智能体系统的沟通开销

多智能体系统的研究里有一条被反复验证的结论：**智能体之间的沟通开销常常超过分工带来的收益**。

原因是：**每个智能体都需要足够的上下文才能工作**，而共享上下文本身就是成本。

**这与本篇的 2.67 倍放大是同一现象**。它给出一条设计判据：分工的前提是子任务所需的信息显著少于整体。

**"信息局部性"是派发划算的必要条件**——这可以写成一个可检查的判据（见 7.1）。

### 6.2 组织信息处理理论

组织理论把**组织看作信息处理系统**：组织结构的设计目的是处理信息的不确定性。

| 概念 | 含义 | 对应 |
|---|---|---|
| **不确定性** | 任务的不确定程度 | 需要通信量 |
| **信息处理能力** | 组织能处理的信息量 | 沟通带宽 |
| **组织设计** | 减少不确定性或提高处理能力 | 分解与委托 |

它的核心论断：**当任务不确定性高时，需要的沟通量急剧上升**，因此高度分解会失效（沟通成本超过收益）。

对 agent 系统的直接含义：**任务越不确定，越不该拆**。只有"目标清晰、接口明确"的任务才适合派发。

这与 1.4 的契约是同一个要求：**派发的前提是能写清契约。**

### 6.3 任务分解的粒度

任务分解研究的一条结论：**分解的收益随粒度变化，存在一个最优点**。

| 粒度 | 问题 |
|---|---|
| 太粗 | 一个子任务内部仍很复杂 |
| **恰当** | **子任务目标清晰、接口明确** |
| 太细 | 协调成本超过执行成本 |

**"协调成本"就是本篇的放大倍数**。当子任务小到"协调成本 > 执行成本"时，分解就不再划算。

### 6.4 验证与信任

多智能体系统里的一个实际问题是：**父任务如何信任子任务的结果？**

| 手段 | 说明 |
|---|---|
| **结构化输出** | 结果可检查（输出规格的作用） |
| **证据附带** | 子任务附带它的依据（与 4.1 的"记忆带来源"一致） |
| **可验证断言** | 结果包含可机械检查的性质（与 4.7 的"约束可检查"一致） |

"证据附带"是最实用的一条：**子任务返回结果时同时返回"我是怎么得出的"**——这既便于父任务判断，也便于事后追溯。

它与本课程反复强调的"可机械验证"是同一个要求：**结果要能被检查，而不只是被相信。**

## 七、理论：成本放大

### 7.1 放大的来源

$$
\text{成本}(\text{派发}) = \text{成本}(\text{执行}) + \text{成本}(\text{上下文复制}) + \text{成本}(\text{汇总})
$$

算例实测：**160K / 60K = 2.67 倍**。

关键认识：**放大不是常数，而是随"子任务所需上下文"变化的**。

- **子任务需要的上下文越少，放大越接近 1**（甚至小于 1，因为父任务不必读全部材料）。
- 子任务需要的上下文越多，放大越接近"复制一份"。

**这解释了为什么"大规模检索"是最划算的派发场景**（子任务需要的输入很少，输出被压缩成摘要）。

### 7.2 划算判据

$$
\text{划算} \iff \frac{\text{所需信息}}{\text{父上下文}} < \frac{1}{\text{放大倍数}}
$$

算例验证：**隔离量大于开销时划算（`true`），小于时不划算（`false`）**。

代入算例的数字：放大倍数 2.67，所以**所需信息若要小于父上下文的 1/2.67 ≈ 37%，派发才划算**。

**这是一条可以直接用于决策的阈值**。如果你的子任务需要父任务一半的上下文，那就该自做。

### 7.3 深度的指数增长

设每层放大 $\alpha$（算例里 2.67），深度 $d$：

$$
\text{成本}(d) \approx \alpha^d
$$

| 深度 | 相对成本（$\alpha = 2.67$） |
|---|---|
| 1 | 2.67 |
| 2 | 7.1 |
| 3 | 19.0 |

结论：**深度 2 已经是 7 倍，深度 3 是 19 倍。** 这是"深度默认取 1"的定量依据。

## 九、练习

### 第一题：判断该派发还是自做

实现如下。

```
A  在 200 个文件里找某一处配置，只需返回文件名与行号
```

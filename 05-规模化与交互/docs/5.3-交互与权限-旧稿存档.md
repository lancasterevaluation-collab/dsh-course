## 本篇新词

审批请求（approval request） 指一次需要人决定的危险操作的完整描述：谁发起（哪条会话）、要做什么（操作与目标）、风险是什么（副作用的等级）、有哪些选项（允许一次、允许并记住、拒绝、换一种做法）。它与"提示"的差别是它是一个有结构的数据对象，因此可以被不同界面呈现、被记录、被统计。

归属（attribution） 指审批请求知道自己来自哪条会话与哪个预设。它在多会话环境里是必需的（5.2 的注册表提供），而在单会话环境里常被省略——省略的后果是请求队列无法按来源排序。

呈现（presentation） 指把审批请求变成人能快速判断的形式。它的判据是人做决定所需的时间：一份需要读三十秒的请求会让用户开始无脑点"允许"，而一句能读懂的话能让他在两秒内做出真实判断。

权限预设（permission preset） 指长期有效的授权规则：某类操作在某个范围内不需要每次询问。它与单次审批的差别是它把"同意"从一个动作变成了一个状态，因此它必须可查看、可撤销、有范围与有效期。

记住的粒度（remember scope） 指"允许并记住"这件事的作用范围：本次、本会话、本项目、永久。粒度的设计直接影响权限的宽度——多数系统只提供"永久"，而那是权限过宽的主要来源。

审批疲劳（approval fatigue） 指请求过多导致人不再认真判断。它的表现是响应时间下降而通过率上升——两个指标的组合是它的可观测信号，而单一指标（例如通过率）无法区分"都很安全"与"没在看"。

阻塞与异步（blocking and asynchronous） 指会话在等待审批期间的状态。等待不应当占满会话的资源（它可以被挂起），但它的状态必须是显式的（`waiting`，5.2 的会话状态机），否则会出现"看起来卡住"的会话。

权限的来源分层（permission layers） 指授权可以来自多处：模式或预设的默认、项目的配置、用户的长期设置、以及本次审批的临时授权。它们的优先级与撤销方式必须明确，否则"为什么这个操作被允许了"和 5.1 的隐式默认一样无法回答。

```
 一句话串起来：什么需要问 → 怎么问 → 怎么少问 → 怎么不乱
```

这张图的关键线索在第三块：审批的设计目标不是"问得更准"，而是"问得更少而不失去控制"。每一次询问都消耗人的注意力，而注意力是有限的——一个好的设计让人只在真正需要判断的地方付出注意力，而其余部分由预设与分级覆盖。

### 0.1 一个具体的判断：审批疲劳的量化

设一次会话平均发起 8 次需要审批的操作，而进程里同时跑 3 条会话。那么一段时间内人需要处理 24 次审批。设每次认真判断需要 15 秒，而快速点过需要 2 秒——总时间从 6 分钟降到 48 秒，而降下来的时间正是判断。

三个可观测的信号：响应时间的中位数（认真判断时约十秒以上，机械点击时低于三秒）、通过率（机械点击时趋于 100%）、以及拒绝与"换一种做法"的比例（认真判断时非零，机械点击时为零）。

三个信号里第二个最容易误导（高通过率既可能是"都很安全"也可能是"没在看"），而三者的组合可以区分：响应时间下降加通过率上升加零拒绝 = 疲劳。这与 3.6 的"主指标配护栏"是同一种手法——单一指标无法区分两种相反的成因。

### 0.2 本篇建立的三项判据

第一项用于判断一个审批是否可读：问"人需要读多久才能做判断"。经验阈值是十秒以内（超过它，疲劳会开始）。这条判据的检验方式是实测（记录从呈现到响应的时间）。

第二项用于判断一个权限预设是否过宽：问"它覆盖的操作里，有多少是当前任务真正需要的"。覆盖远超需要时，预设实际上是一场"批量授权"，而它应当被拆细。

第三项用于判断权限是否可追溯：问"这个操作为什么被允许了"。答案应当落到一个具体的来源（某个预设、某次审批、某个项目的配置），而不是"系统认为它安全"。

### 0.3 十分钟练习：请求的结构与呈现

下面这段代码构造一个审批请求，并生成两种呈现（面向人的与面向日志的）。

```js
const request = {
  id: 'ap-1',
  session: { id: 's-7', preset: 'code-editor', profile: 'dev' },   // 归属（1.2）
  action: { tool: 'shell', command: 'rm -rf build/', cwd: '/repo' },
  risk: { level: 'high', reason: '删除目录且路径在项目内', undoable: false },  // 风险分级
  options: ['allow-once', 'allow-session', 'deny', 'suggest-alternative'],
  raisedAt: 0,
}

function forHuman(r) {
  return [
    `[${r.session.preset}] 请求执行：${r.action.command}`,
    `位置：${r.action.cwd}`,
    `风险：${r.risk.reason}（${r.risk.undoable ? '可撤销' : '不可撤销'}）`,
  ].join('\n')
}

function forLog(r) {
  return JSON.stringify({ id: r.id, session: r.session.id, tool: r.action.tool, risk: r.risk.level, options: r.options })
}

console.log(forHuman(request))
console.log('日志：', forLog(request))
```

两种呈现的差别对应两个读者：人需要的是"我要不要允许"这一个判断（所以三行里没有一个是技术细节），而日志需要的是可统计的字段（会话、工具、风险等级、选择）。用同一份数据生成两种呈现——如果各自维护一份，它们会漂移（与 5.1 的"说明从声明派生"同源）。

> **面试视角**
> **高频问法**："你怎么避免用户无脑点同意？"
> **高分要点**：说出三个信号（响应时间、通过率、拒绝比例的组合）与两条处置（减少请求数、把请求做得可读）。只说"把提示写清楚"没有回答"怎么知道用户在不在看"。

### 0.5.3 三个连锁影响

第一，权限预设与 5.1 的预设是两件事，而它们容易被混淆。 5.1 的预设描述"这个 agent 是什么"（人格、工具集、模型），而权限预设描述"它能做什么而不必问"。一个预设可以带默认的权限预设（例如只读探索型会话默认允许一切只读操作），而两者的关系应当是"预设提供权限的上界，权限预设在其内进一步放行"。

第二，审批的等待会改变会话的状态，而它必须与会话的生命周期协调。 等待期间会话处于 `waiting`（5.2 的状态机），而它仍然占用上下文与容器资源——这意味着"等待很多审批的会话"会占着资源却不能推进。处置是让等待有超时（超时后按 3.2 的保守默认处理），并把等待时间计入观测（3.6）。

第三，权限会随使用累积，而累积的权限需要定期复核。 每一次"允许并记住"都会加宽权限，而它们很少被主动收紧。处置方式是把权限列表纳入 4.6 的复盘范围（每轮检查有没有可以撤销的授权），而这条接入让权限管理从一个静态配置变成了一个被周期性审视的对象。

### 0.5.4 它与本书其余部分的关系

本篇的交互是单用户的。多人协作下的权限（谁有权批谁的请求）需要身份与角色模型，而它不在本课程范围内。这条边界意味着本篇的结论在"一个人使用一个 agent 系统"上是完整的，而它的请求结构（含归属）恰好也是多人场景的基础——归属字段在那里会变成"请求属于哪个用户"。

> **面试视角**
> **高频问法**："审批弹窗太多，用户都点同意，怎么办？"
> **高分要点**：说出两条互补的处置——减少请求数（权限预设与粒度）与让请求可读（呈现的判据是十秒内可判断），并给出疲劳的三个信号。只说"精简文案"只解决了其中一半。

## L0 要解决的问题

### 0.1 现象一：用户无脑点同意

第一个现象是审批疲劳（本篇新词）。它的成因不只是请求多，还有请求难读——一份需要读三十秒的请求会让人放弃判断（0.1 的量化）。

两个成因的修法不同：请求多要用 1.4 的预设与粒度解决，请求难读要用 1.2 的呈现解决。而它们的共同点是都会让审批失去作用（它本应是"人做判断的环节"），因此都属必修。

### 0.2 现象二：审批弹窗不知道来自哪条会话

第二个现象是归属缺失。在多会话环境里，用户看到"请求执行 `rm -rf build/`"，而不知道它来自哪条会话、哪个任务。于是他无法判断这个操作是否合理——同一个命令在"清理构建产物"的任务里是常规操作，在"编辑文档"的任务里是异常。

修法是 1.2 的归属字段（来自 5.2 的注册表），而它的呈现要求是在请求里带上任务的一句话（而不只是会话 id）——人需要的是语境，不是标识。

### 0.3 现象三：等待审批的会话看起来卡住了

第三个现象是等待的不可见。会话发起审批之后进入等待状态，而它既不推进也不结束——在界面上表现为"没有反应"，而用户不知道它在等自己。

修法是 1.3 的等待状态显式化：会话状态变为 `waiting`、等待时长被记录、并且在界面上有明确的指示（"等待你的批准"而不是转圈的加载图标）。这条修法与 0.1 的疲劳直接相关——一个不知道在等什么的用户会倾向于尽快摆脱它（点同意）。

### 0.4 现象四：权限越来越宽，而没有人记得

第四个现象是授权累积。每一次"允许并记住"都留下一条长期有效的规则，而它们很少被撤销。几个月后，系统的实际权限远超原先的设计意图——而它的表现是"某些操作不再询问"，而不是任何错误。

修法有两部分：粒度设计（让"记住"的作用范围可控，1.5）与定期复核（把权限列表纳入复盘，0.5.3 的第三条）。前者防它一开始就太宽，后者防它随时间变宽。

### 0.5 这一篇要正面回答的四个问题

第一，什么需要问、请求长什么样（1.1）。第二，怎么呈现与归属（1.2、1.3）。第三，怎么减少询问（1.4、1.5）。第四，怎么让权限可追溯与可撤销（1.6）。

四个问题里第三个是这一篇的核心目标（减少而不失控），而第四个是它的安全底线。

## L1 设计与原理

### 1.1 审批请求的结构与风险分级

请求的六个字段（含 3.2 的守卫判据）。

```ts
interface ApprovalRequest {
  readonly id: string
  readonly origin: { sessionId: string; preset: string; profile: string; parentId?: string }  // 归属（含父会话，5.4 用）
  readonly action: { tool: string; args: unknown; cwd?: string; summary: string }              // 做什么（含一句人话摘要）
  readonly risk: { level: 'low' | 'medium' | 'high' | 'critical'; reason: string; undoable: boolean }
  readonly options: readonly Option[]                                                          // 选项（含"换一种做法"）
  readonly raisedAt: number
  readonly deadline?: number                                                                    // 等待超时（1.3）
}
```

三处设计要点。`summary` 是人话摘要（"删除构建产物目录"而不是 `rm -rf build/`）——它与 `args` 并存，因为人和日志需要的信息不同（0.3 的两种呈现）。`undoable` 决定风险的实际影响（不可撤销的高风险操作应当有更强的确认）。

`options` 里必须有"换一种做法"——只给"允许/拒绝"会把用户逼进二选一，而多数情况下存在第三条路（例如"先复制再删除"）。

风险分级的依据应当是可逆性与影响范围两条，而不是操作的名称（3.2 的 `sideEffect` 四级在这里被具体化为四档）：

| 级别 | 可逆性 | 影响范围 | 例子 |
|---|---|---|---|
| low | 可逆 | 会话内 | 读文件、查询 |
| medium | 可逆 | 工作区 | 写文件、改配置 |
| high | 难撤销 | 工作区外 | 删除、推送、部署 |
| critical | 不可逆 | 系统级 | 权限变更、凭据操作 |

两种依据的组合解释了为什么"删除"是高而"写入"是中：两者都改文件，而删除的撤销成本更高。

### 1.2 呈现与归属

呈现的三条规则，而它们的共同判据是十秒内可判断（0.2 的第一项）。

规则一，先说做什么，再说怎么做。人需要的第一个判断是"这件事该不该做"，而命令与参数是第二个问题。反过来的顺序（先亮命令）会让不熟悉该命令的用户卡住。

规则二，风险用后果表述而不是等级。"高风险"没有信息量，而"删除目录且无法恢复"有。这条规则与 4.1 的"给用户看的理由"、4.2 的"技能里的理由"是同一条原则：给人看的应当是后果，而不是分类。

规则三，归属带上任务语境。"来自会话 s-7"没有信息量，而"来自'清理构建产物'这个任务"有（0.2 的分析）。任务语境的来源是 4.7 的任务状态或 2.7 的会话目标——它必须在会话创建时就有，而不是在审批时临时推断。

### 1.3 等待与超时

等待的处理有三条。

状态显式：会话进入 `waiting`（5.2 的状态机），并且这个状态在界面上有对应显示。

超时必设：等待超过一定时间（例如十分钟）按 3.2 的保守默认处理（拒绝或按配置），而不是无限等待。超时的取值依据是"人可能离开多久"，而它的处置应当被记录（"因超时被拒绝"是一个可统计的结果）。

等待不占并发：`waiting` 的会话不占 5.2 的并发配额（它的实现已经在 5.2 的 `globalConcurrent` 里体现——只统计 `running`）。这条规则让"多条会话同时等审批"不会阻塞其他会话的推进。

```ts
export async function awaitDecision(req: ApprovalRequest, ctx: Context): Promise<Decision> {
  const session = ctx.registry.get(req.origin.sessionId)
  ctx.registry.setState(session.id, 'waiting')                      // 状态显式（规则一）
  try {
    const decision = await ctx.interaction.race(req.id, timeoutAfter(req.deadline ?? ctx.config.approvalTimeout))
    if (decision.kind === 'timeout') {
      await ctx.appendEvent({ type: 'approval/timeout', id: req.id, at: ctx.now })
      return conservativeDefault(req, ctx)                          // 保守默认（规则二）
    }
    return decision
  } finally {
    ctx.registry.setState(session.id, session.stateBefore ?? 'running')
  }
}
```

`finally` 里的状态恢复保证了异常路径下会话不会永远停在 `waiting`——这类细节在没有断言的实现里容易被漏掉，而它的表现是"会话永远卡在等待"。

### 1.4 权限预设：从动作到状态

权限预设的四个要素。

匹配条件：什么操作适用（工具加参数的约束，例如"工作区内的写操作"）。匹配条件的粒度决定了预设的风险——过宽的匹配等于批量授权（0.2 的第二项判据）。

作用范围：在哪些会话、哪些项目、哪段时间内有效。

来源与理由：谁在什么时候因为什么授予了它。这条是 1.6 可追溯性的基础。

失效条件：什么时候它不再有效（项目变更、时间到期、手动撤销）。

```ts
interface PermissionPreset {
  readonly id: string
  readonly match: { tool: string; constraint?: string }        // 例如 { tool: 'write', constraint: 'cwd-in-workspace' }
  readonly scope: { sessions?: readonly string[]; projects?: readonly string[]; expiresAt?: number }
  readonly source: { kind: 'preset' | 'project' | 'user' | 'approval'; grantedAt: number; reason: string }
  readonly revocable: boolean
}
```

`source.kind` 的四个取值与 1.6 的分层对应，而 `revocable` 标记哪些可以被自动撤销（来自预设的可以随预设失效，来自用户审批的需要用户确认）。

### 1.5 记住的粒度

四档粒度与它们的适用场合。

| 粒度 | 适用 | 风险 |
|---|---|---|
| 本次 | 一次性的例外 | 最低（问的次数不变） |
| 本会话 | 一条会话里反复出现的操作 | 低（会话结束即失效） |
| 本项目 | 项目约定（例如"这个仓库的构建命令可以跑"） | 中（项目范围内的所有会话） |
| 永久 | 极少使用 | 高（需要主动撤销） |

多数系统只提供第一与第四档，而中间两档恰好是最有用的：它们覆盖了"在这条会话/这个项目里别再问"这个最常见需求，同时有自然的失效条件（会话结束、离开项目）。

四档的呈现也是一个设计问题：如果界面只给"允许一次"与"总是允许"两个按钮，用户会在不耐烦时选后者——提供中间档位本身就是减少权限过宽的手段。

### 1.6 权限的来源分层与撤销

四层来源与优先级（从宽到严）。

```ts
export function decide(req: ApprovalRequest, ctx: Context): 'allow' | 'ask' | 'deny' {
  if (ctx.presetOf(req.origin.preset).denies(req)) return 'deny'                            // 上界先判：任何下游授权都不能放宽它
  const presets = ctx.permissions.matching(req)
  if (presets.some((p) => p.source.kind === 'user' && p.revoked === false)) return 'allow'   // 用户长期授权
  if (presets.some((p) => p.source.kind === 'project' && p.revoked === false)) return 'allow' // 项目约定
  if (req.risk.level === 'low' && ctx.config.autoAllowReadOnly) return 'allow'               // 低风险的自动放行
  return 'ask'                                                                                // 其余都要问
}
```

四处判断的顺序有讲究：**预设的拒绝排在最前**——它是上界，任何下游授权都不能放宽它（否则项目配置就能覆盖安全边界，这与 4.5 的元控制同源）。之后才是授权：用户长期授权优先（它是最明确的意图表达），然后是项目约定，最后是低风险自动放行。上界在前、放行在后，这条顺序是这里唯一不能颠倒的地方。

撤销的三种方式：手动撤销（列出并删除一条）、随范围失效（会话结束、项目变更、过期）、以及随来源失效（预设被修改时，来自它的授权一并失效）。三种里第二种最重要——它是唯一不需要人记得的失效方式（0.4 的现象）。

| # | 决策 | 我们的选择 | 替代方案 | 代价落在谁身上 |
|---|---|---|---|---|
| 1 | 请求的载体 | 结构化对象加人话摘要 | 一句提示文本 | 要维护两份表述；换来多界面一致与可统计 |
| 2 | 风险分级依据 | 可逆性加影响范围 | 按操作类型枚举 | 要判断可逆性；换来判据可推广 |
| 3 | 选项 | 含"换一种做法" | 允许/拒绝二选一 | 实现要多一条路径；换来不逼用户二分 |
| 4 | 呈现顺序 | 先说做什么再说怎么做 | 先亮命令 | 技术用户可能觉得啰嗦；换来可判断 |
| 5 | 归属 | 带任务语境 | 只带会话 id | 会话要有目标字段；换来用户能判断 |
| 6 | 等待状态 | 显式 `waiting` | 无状态（阻塞） | 状态机多一个状态；换来可见 |
| 7 | 超时 | 有，按保守默认处理 | 无限等待 | 有时会误拒；换来不卡死 |
| 8 | 等待是否占并发 | 不占 | 占 | 配额计算稍复杂；换来不阻塞其他会话 |
| 9 | 记住粒度 | 四档 | 只做本次与永久 | 界面更复杂；换来权限不过宽 |
| 10 | 预设匹配粒度 | 工具加约束条件 | 只匹配工具名 | 配置更复杂；换来不变成批量授权 |
| 11 | 预设的拒绝优先级 | **在授权之前**（它是上界） | 授权优先（项目约定可放宽） | 灵活性下降；换来安全边界不被下游侵蚀 |
| 12 | 撤销 | 手动加随范围与来源自动失效 | 只手动 | 要实现失效逻辑；换来权限不无限累积 |

其中两条值得展开，因为它们的选择在实践中经常被做成另一个。

### 关于第 9 与第 10 条的完整论证（粒度为什么是减少权限过宽的关键）

替代方案是只提供"允许一次"与"总是允许"。它在实现上最省事，而在使用中会系统性地偏向宽的一侧。

第一，中间需求没有出口。用户在一条会话里会遇到同一个操作多次（构建、测试、格式化），而"允许一次"意味着每次都要问（累积成 0.1 的疲劳），"总是允许"则过宽。没有中间档位时，用户在不耐烦时必然选宽的那一档。

第二，宽授权缺少自然失效。永久授权只能靠人记得撤销，而这是 0.4 现象的根源。本会话与本项目两档有天然的失效点（会话结束、离开项目）——它们把"撤销"从一个人的职责变成了系统的行为。

第三，粒度决定了预设可被表达的最细约束。如果匹配只按工具名，那么"允许写文件"必然包含"允许在任意路径写"（因为工具名相同）。加上约束条件（例如"限工作区内"）才能表达用户真正想表达的意思——这也是第 10 条的理由。

### 关于第 11 条的完整论证（为什么预设的拒绝不能被放宽）

替代方案是让更具体的配置覆盖更宽的安全约束（"项目里明确说我接受这个风险"）。它能解决真实问题（某些项目确实需要危险操作），而它破坏了安全边界的方向。

安全约束的方向是"从严到宽需要明确的授权，而从宽到严可以自动"。让项目配置放宽预设的拒绝，等于允许"在下游放宽上游的安全决定"——而下游的数量通常远多于上游（每加一个项目就多一处可能放宽的地方），因此边界会随时间被逐步侵蚀（与 1.5、4.5 的元控制是同一条原则的第三次出现）。

正确的做法是让需要放宽的项目走一次显式的授权（用户级或项目级的一条明确记录），而它出现在权限列表里、可被复核、可被撤销——放宽是允许的，但它必须是一次留下记录的动作，而不是一次配置变更的副作用。

```ts
export function matching(req: ApprovalRequest, presets: readonly PermissionPreset[]): PermissionPreset[] {
  return presets.filter((p) => {
    if (p.match.tool !== req.action.tool) return false
    if (p.scope.expiresAt && p.scope.expiresAt <= Date.now()) return false        // 时间失效
    if (p.scope.sessions && !p.scope.sessions.includes(req.origin.sessionId)) return false
    if (p.match.constraint && !evalConstraint(p.match.constraint, req)) return false   // 约束（L2 第 10 条）
    return true
  })
}

export function revoke(presetId: string, ctx: Context): RevocationReport {
  const p = ctx.permissions.byId(presetId)
  if (!p.revocable) throw new Error(`该授权不可自动撤销：${p.source.kind}`)      // 用户授权需确认
  ctx.permissions.remove(presetId)
  const cascaded = ctx.permissions.removeBySource(p.source)                     // 随来源失效（1.6）
  return { revoked: presetId, cascaded: cascaded.map((c) => c.id) }
}
```

两处要点：约束的求值在匹配阶段（而不是在授权使用时），因此"约束不成立"是一个可观测的拒绝。以及撤销会级联到同源的授权（改了一个预设，来自它的授权一并失效）。

### 3.4 统计段

```ts
export function fatigueSignals(events: readonly ApprovalEvent[]): FatigueSignals {
  const responded = events.filter((e) => e.decision && e.decidedAt)
  const latencies = responded.map((e) => e.decidedAt - e.raisedAt).sort((a, b) => a - b)
  const median = latencies[Math.floor(latencies.length / 2)] ?? 0
  const allowRate = responded.filter((e) => e.decision !== 'deny').length / Math.max(1, responded.length)
  const refusalRate = responded.filter((e) => e.decision === 'deny' || e.decision === 'alternative').length / Math.max(1, responded.length)
  return { medianLatencyMs: median, allowRate, refusalRate, fatigued: median < 3000 && allowRate > 0.95 && refusalRate === 0 }
}
```

`fatigued` 是三信号（0.1）的合取——单一信号无法区分"都很安全"与"没在看"，而三者的组合可以。

## L7 挑战题（不给答案）

第一题：审批的批量处理。 三条会话同时等待，用户希望一次处理。设计批量界面，并说明它如何不牺牲可读性。

第二题：权限的自动收窄。 一条授权长期未被使用时应当自动失效。设计这个机制并给出判据。

第三题：双人审批。 高风险操作需要两人确认。设计这个流程，并说明它与来源分层的关系。

第四题：审批的学习。 从用户的历次选择里提出预设草案。设计这个流程，并说明它如何避免把一次例外变成长期授权。

第五题：跨界面的体验一致。 同一请求在 CLI、Web 与 GUI 上呈现。设计一份数据到三种呈现的映射，并说明哪些部分是共享的。

第六题：论证"不询问"的一个合理场景。 构造一个场景，说明一类操作永不需要询问更好（提示：完全可逆且影响限于会话内），并给出判据。

## L9 仍未解决（这一篇自己的缺陷）

| 缺陷 | 后果 | 修法 | 当初为什么这么写 |
|---|---|---|---|
| 疲劳信号依赖事件完整性 | 事件缺失时判定失真 | 校验审批事件的完备性 | 事件由交互层产生 |
| 风险分级是规则式的 | 新工具的风险可能判错 | 让工具声明风险并复核 | 声明式的风险需要工具作者配合 |
| 单用户模型 | 多人协作的权限不在范围内 | 引入用户与角色（见 0.5.4） | 本课程是单用户的 |
| 权限审计是手动的 | 不审计就会累积 | 接入 4.6 的复盘（0.5.3 的第三条） | 需要复盘机制先到位 |
| "换一种做法"依赖模型能力 | 建议可能不可行 | 由工具提供替代方案 | 通用替代方案难以枚举 |
| 呈现的十秒阈值是经验值 | 不同用户差异大 | 按用户实测校准（4.3 的用户模型） | 需要个人数据 |

第二条与第五条属于"判断来源"，第三条与第四条属于范围与流程，第一条与第六条属于数据与经验值。第四条值得单独标记：它意味着权限累积问题虽然有修法（接入复盘），但当前的实现不会自动发现它——而权限过宽属于"没有错误信号"的一类问题（0.4），因此它需要一个外部的周期检查才能被发现。这条依赖关系说明安全相关的设置很少能靠"设计得当"一次到位，它们需要被持续审视。

## L10 提问训练

### 五个层次

| 层次 | 例子 |
|---|---|
| 事实 | 请求的六个字段是什么？四档粒度是什么？ |
| 机制 | 为什么预设的拒绝不能被项目约定放宽？ |
| 设计 | 为什么等待不占并发？ |
| 系统 | 如果权限只增不减，长期运行会怎样？ |
| 科研 | 能不能量化呈现质量对误允许率的影响？ |

### 五种提问模板

反例逼问：如果只有"允许/拒绝"两个选项，哪一种现象会变多。

边界追问：一个预设的匹配该细到什么程度。

代价追问：把等待设为不占并发，代价落在谁身上。

替代对比：为什么归属要带任务语境而不是会话 id。

验证追问：怎么证明"用户真的在做判断"。

### 本篇引出的十二个问题

读懂层。 第一，请求的六个字段是什么？第二，风险分级的两条依据是什么？第三，四档记住粒度是什么？

重建层。 第四，为什么风险要用后果表述？第五，为什么等待要有状态与超时？第六，为什么"换一种做法"是必需选项？

设计层。 第七，权限预设的四个要素是什么？第八，来源分层的优先级顺序与理由是什么？第九，撤销的三种方式是什么？

评审层。 第十，拿到一个审批设计，你会先检查哪一处？第十一，怎么判断一条授权过宽？第十二，如果有人说"默认都允许，出事再说"，你怎么回应？

### 问题升级练习

模糊问题：「我的 agent 老是要我确认，很烦，怎么办？」

升级后的精确问题：

> 减少确认至少包含三件互相制约的事：**少问**（哪些可以预设放行）、好问（问的时候能不能快速判断）、以及可控（放行的权限如何收回）。
> 第一件与第三件互相制约——放行得越多，收回的机制就越关键，而收回需要记录与范围。
> 我能不能为这三件事各找出一条**可检查的判据**？
> 特别是：有没有哪一条判据，是**能证明"用户真的在判断而不是在点按钮"的**？

提升点说明：原问题无法回答，因为"很烦"没有指向。升级后的版本把它拆成三件具体的事，指出放行与收回的制约关系，并追加以一个更强的问题：哪一条判据能证明用户在做判断——因为只有那一条能说明审批环节还在起作用。

## L11 系统影响回溯

回看第 0.5 节的三个连锁影响。

| 预判 | 本篇分析之后的结论 | 状态 |
|---|---|---|
| 权限预设与 5.1 的预设是两件事 | 确认，并给出"预设提供上界、权限预设在其内放行"这条关系 | 成立 |
| 审批等待会改变会话状态 | 确认，并给出 `waiting` 状态、超时与不占并发三条实现 | 成立 |
| 权限会累积，需要定期复核 | 确认，并把权限列表接入 4.6 的复盘范围 | 成立 |

**一处需要修正的预判**：0.5.2 把"审批请求的结构"标为对 5.4 的强依赖。读完之后要补一层方向：**子 agent 的授权不应当是一次独立审批**——如果每条子 agent 的操作都单独询问，那么一个派发了十条子任务的父会话会产生十倍于单会话的审批量（0.1 的疲劳会瞬间触发）。

正确做法是授权沿父子链继承（父会话获得的授权对子 agent 生效），而这意味着请求的 `origin.parentId` 必须参与权限匹配（1.1 的字段设计已经预留了它）。这条要求会在 5.4 里成为设计约束。

通向下一篇的桥。 本篇处理了"人如何参与"，而它留下了一个没有答案的问题：当执行者不止一个（主 agent 与子 agent），授权、上下文与结果如何流动。派发一个子任务时，它需要什么信息、能做什么、以及它的产出如何被父会话采纳——这三件事都需要协议。

下一篇 `5.4 多智能体与外部工具` 处理这件事，它是第 5 卷的收口。它与本篇的连接点有两处：授权的父子继承（上面那处修正）与请求的归属链（`parentId`）。它与本篇的另一个连接点更重要：外部工具（MCP）的信任边界与权限预设是同一件事的两种形态——前者管"我们调用别人"，后者管"别人调用我们"。

## 读完这一篇你会知道什么

1. **延迟四段分解**：排队 / 预填充 / 生成 / 工具，加一个**残余项**——算例实测四段是 50 / 350 / 2600 / 4200 毫秒，残余 800。

4. **护栏指标**：为什么必须给每个优化目标配一个"不许变差"的指标。

## 一、为什么需要可观测

### 1.1 延迟翻倍了，但不知道从哪来

用户反馈"最近变慢了"。看总耗时，确实从 4 秒涨到 8 秒。**但总耗时是个标量，它不告诉你该改哪里。**

### 1.2 账单翻了三倍，不知道花在哪

一个月的模型费用涨了。是输入变长了、输出变长了、还是缓存命中率掉了？**没有分档归因时，这三个原因无法区分。**

### 1.3 指标全绿，用户仍在抱怨

平均值、成功率都正常，而用户说"经常卡住"。因为**卡住的 5% 被平均掉了**。

这三件事分别对应：**要分段、要归因、要看分布。**

## 二、可观测要回答什么

| 问题 | 需要的量 | 做错的后果 |
|---|---|---|
| 慢在哪 | 延迟的分段与分布 | 只能猜 |
| 贵在哪 | 成本的输入/输出/缓存分档 | 优化错方向 |
| 坏了没 | 正确性护栏 + 分布尾部 | 指标绿而体验差 |
| 对得上吗 | 分段之和与总体的差额 | 有未测量的开销 |

核心认识：可观测的目标不是"有很多指标"，而是**每个指标都能定位到一个可行动的位置**。一个无法据以行动的指标是噪声。

## 三、怎么做

### 3.1 延迟分解：四段加残余

一次 agent 回合的耗时可以拆成四段，再加一个残余：

| 段 | 含义 | 算例实测 |
|---|---|---|
| 排队 | 等待被调度 | 50 ms |
| 预填充 | 处理输入（prompt） | 350 ms |
| 生成 | 逐 token 输出 | **2600 ms** |
| 工具 | 执行工具调用 | **4200 ms** |
| 残余 | 调度、网络、序列化 | 800 ms |
| **总计** | | **8000 ms** |

分解函数的写法如下。

```js
// 延迟分解：四段各自计时，残余单独记录（否则差额会静默消失）
export function decomposeLatency(span) {
  const parts = { queue: span.queueMs, prefill: span.prefillMs, generate: span.generateMs, tool: span.toolMs }
  const measured = parts.queue + parts.prefill + parts.generate + parts.tool
  return { ...parts, residual: span.totalMs - measured, total: span.totalMs }
}
```

残余项是整个分解里最有价值的部分。算例里它占 800/8000 = **10%**。

为什么必须显式记录残余：如果不记，四段之和与总量的差额会**静默消失**——你会在某个时刻发现"分段加起来只有 7200，但用户等了 8000"，却不知道那 800 在哪。把差额做成一个指标，它就变成了线索。

从这张表能读出的结论：工具（4200）比生成（2600）更贵。**所以优化方向是工具调用，而不是换更快的模型。**

### 3.2 成本归因：三档计价与缓存

模型调用通常有三档价格：输入、输出、缓存命中（通常远低于输入）。

```js
// 成本归因：输入、输出、缓存三档分开算，缓存按命中部分计价
export function cost(inputTokens, outputTokens, cachedTokens, price) {
  const fresh = inputTokens - cachedTokens
  return fresh * price.input + cachedTokens * price.cached + outputTokens * price.output
}
```

算例实测：2 万输入 token + 500 输出 token 的成本是 **22.5000**（按给定价格）。

**缓存的经济性**（算例另一组数字）：

| 场景 | 有效价格倍数 |
|---|---|
| 全未命中 | 1.000 |
| **1 次写入 + 9 次读取** | **0.215** |
| 全命中（理想） | 0.100 |

**1 写 9 读时相对未命中节省 4.65 倍。** 这解释了为什么前缀缓存是长会话系统最重要的成本优化——它的收益比例可以直接算出来，不需要猜。

两条实践规则：

1. **成本必须按三档分别记账**，否则无法判断"变贵"是因为输出变长还是缓存失效。
2. **缓存命中率是一个独立指标**，它变化时账单会突然变化。

### 3.3 看分布而不是均值

这是本篇最重要的一节。算例给出的真实数字：

| 统计量 | 值 |
|---|---|
| 均值 | **681.0 ms** |
| P95 | **3000 ms** |

**均值 681，而 5% 的用户等 3 秒以上。** 如果只看均值，你会认为系统"平均 0.7 秒，挺快"。

为什么均值会骗人：延迟分布是**重尾**的（少数请求特别慢）。重尾分布下，均值由大多数快请求决定，而用户体验由尾部决定。

```js
// 分位数：P95 等尾部指标必须单独记录，不能靠均值推断
export function percentile(sorted, q) {
  const idx = Math.min(sorted.length - 1, Math.ceil(q * sorted.length) - 1)
  return sorted[Math.max(0, idx)]
}
```

要记录的分布指标：

- **P50 / P95 / P99**：分别代表典型、较差、最差体验。
- **超时率**：超过某个阈值的比例。
- **最大值的采样**：偶发的极端值最有诊断价值（但要在日志里保留原始样本）。

一条判据：**如果你的监控面板只有均值，那么你对用户体验一无所知。**

### 3.4 护栏指标：防止优化一处伤害另一处

优化一个指标常常会伤害另一个。例如"提高缓存命中率"可能意味着"缓存更多内容"，从而"增加内存"或"降低新鲜度"。

因此每个优化目标都要配 **护栏指标**：一个"不许变差"的约束。

```js
// 护栏检查：目标指标改善的同时，护栏指标不得越界
export function checkGuardrails(metrics, limits) {
  return metrics.filter((m) => limits[m.name] !== undefined && m.value > limits[m.name])
}
```

算例实测：`latencyP95 = 3000` 超过上限 2000，护栏返回越界列表 `[{name: 'latencyP95', value: 3000, limit: 2000}]`。

**推荐配对**（目标 → 护栏）：

| 优化目标 | 护栏指标 |
|---|---|
| 降低延迟 | 成本、准确率 |
| 降低成本 | 延迟 P95、任务成功率 |
| 提高缓存命中率 | 回答新鲜度、上下文准确性 |
| 提高吞吐 | 错误率、P99 延迟 |

**护栏的价值在于它把"优化"变成了"在约束下优化"**——这正是工程与刷指标的区别。

### 3.5 归因差额：对不上账就是有洞

有了分段与护栏，还要做一次**总账核对**：

$$
\text{gap} = \text{总量} - \sum \text{分段}
$$

算例实测：`{gap: 0, ratio: 0}`——**对得上**。

为什么要把它做成指标：只要 gap 不为零（或比例超过阈值），就说明**有一处开销没有被测量**。它可能是新加的中间件、被忽略的重试、或者统计口径错误。

成本也要做同样的核对：算例验证了"成本可加性"为 `true`——各部分成本之和等于总成本。**可加性不成立时，说明存在重复计数或漏计。**

## 四、特殊情况与处理技巧

| 情况 | 为什么 | 处理 |
|---|---|---|
| 均值正常但用户抱怨 | 重尾分布 | 记录 P95/P99，不要只看均值 |
| 分段之和小于总耗时 | 有未测量的开销 | 显式记录残余项并告警 |
| 优化后账单反而涨了 | 没配护栏 | 每个目标配护栏指标 |
| 缓存命中率突然下降 | 前缀变了（系统提示词改动、时间戳插入） | **前缀要稳定**。命中率作为独立指标 |
| 高基数指标拖垮监控 | 把用户 id、会话 id 作为标签 | 标签只放**有限取值**的维度 |
| 采样后只剩聚合值 | 只存了聚合数据 | 保留可回放的原始样本（与 3.5 的日志一致） |
| 分布式追踪链路断裂 | 跨进程未传播上下文 | 传播 trace id（见 5.2） |
| 告警太多被忽略 | 阈值过低 | 用 SLO 与错误预算驱动告警（见 5.4） |

最后一条与 3.2 的审批疲劳是同一个问题：**任何需要人响应却高频触发的机制，都会被忽略。**

## 五、工业界的做法（可照做）

### 5.1 观测数据的三种形态

| 形态 | 回答什么 | 代价 |
|---|---|---|
| **指标**（metrics） | 聚合趋势（趋势、告警） | 存储小，但丢失个体 |
| **日志**（logs） | 具体事件（归因、审计） | 存储大，检索慢 |
| **追踪**（traces） | 一次请求的内部结构（定位慢在哪） | 采样成本高 |

三者的分工：指标告诉你"有问题"，追踪告诉你"问题在哪一段"，日志告诉你"当时的细节"。

### 5.2 追踪的标准做法

**OpenTelemetry** 是当前事实标准，其核心概念值得照抄：

| 概念 | 含义 | 在 agent 系统里的对应 |
|---|---|---|
| **trace** | 一次完整请求 | 一个用户回合 |
| **span** | 请求内的一个操作（有起止时间与父子关系） | 一次模型调用、一次工具执行 |
| **attribute** | span 上的键值 | 模型名、token 数、工具名 |
| **context 传播** | 跨进程传递 trace id | 子进程/远端执行器 |

关键规则：**span 要覆盖"你打算优化的每一段"**。这与 3.1 的四段分解是同一件事——四段就是四个 span。

### 5.3 两套成熟的方法论

| 方法 | 关注 | 指标 |
|---|---|---|
| **RED** | 服务视角 | 请求速率（Rate）、错误（Errors）、耗时（Duration） |
| **USE** | 资源视角 | 利用率（Utilization）、饱和度（Saturation）、错误（Errors） |

**RED 用于"我的服务健不健康"，USE 用于"我的资源够不够"。** 两者互补：RED 显示症状，USE 显示原因。

### 5.4 SLO 与错误预算

工业界避免"告警疲劳"的主流做法是**用 SLO 驱动告警**：

1. 定义 **SLO**：例如"99% 的回合在 5 秒内完成"。
2. 由 SLO 推出**错误预算**：允许 1% 的请求超标。
3. **只在这 1% 被快速消耗时告警**（例如"一小时内已经用完本周预算的 20%"）。

这与 3.2 的审批疲劳是同一个解法：**把"每次异常都叫人"换成"预算耗尽才叫人"。**

### 5.5 参数怎么定

| 参数 | 推荐起点 | 依据 |
|---|---|---|
| 分位数 | P50 / P95 / P99 | 分别对应典型、较差、最差 |
| 直方图桶 | 按对数刻度分桶（1ms–30s） | 延迟是重尾的，线性桶会浪费 |
| 追踪采样率 | 1%–10%（保留全部错误） | 错误样本价值高，正常样本可采样 |
| 指标保留 | 原始 1–7 天，聚合长期 | 兼顾诊断与成本 |
| 标签基数 | 每指标少于 100 个取值 | 防止监控被拖垮 |
| 告警阈值 | 由 SLO 反推 | 而不是拍一个数 |
| 残余告警线 | 总分段的 5%–10% | 算例里残余占 10% 属正常 |

### 5.6 一份可落地的实施清单

1. **四段 span**：排队、预填充、生成、工具，各一个 span 并计时。
2. **残余项**：显式记录 `total - sum(parts)`，超过阈值告警。
3. **成本三档记账**：输入、输出、缓存分别计，并记录命中率。
4. **分位数**：每个关键指标记 P50/P95/P99，不只看均值。
5. **护栏指标**：每个优化目标配一个约束，越界即报警。
6. **trace 传播**：跨子进程与远端执行器传递 trace id。
7. **标签纪律**：只放有限取值的维度，禁止放会话 id 之类的唯一值。
8. **SLO 与错误预算**：用预算消耗驱动告警，而不是用单点阈值。
9. **原始样本保留**：慢请求的完整记录要能回放（与 3.5 的日志衔接）。
10. **对账**：定期核对"分段之和 vs 总量"与"分项成本 vs 总成本"。

## 六、学术界的结论

### 6.1 长尾放大：并行越多，尾巴越粗

Google 的 "The Tail at Scale"（Dean & Barroso, CACM 2013）给出了一个对分布式系统极其重要的结论：

**当一个请求需要并行调用 N 个服务时，整体延迟由最慢的那个决定。** 因此即使每个服务的 P99 很漂亮，组合起来的 P99 也会显著变差：

$$
P(\text{至少一个慢}) = 1 - (1 - p)^N
$$

若单服务慢的概率 $p = 1\%$，$N = 100$ 时，**至少一个慢的概率是 63%**。

这条结论对 agent 系统的直接含义：

- **并行工具调用越多，回合的尾延迟越差。**
- 优化单次调用的 P99 收益，在并行场景下会被放大。
- 只优化均值对并行系统几乎无意义。

原文给出的应对手段（对冲请求、微分区、慢节点探测）里，最可借鉴的是对冲请求：请求发出后若在 P95 时间内没返回，就发一个副本，取先返回的结果。**代价是重复执行**——所以它要求操作幂等（见 3.1）。

### 6.2 分位数的流式估计

精确分位数需要保存全部样本，代价太大。工业界用**流式估计**：

| 算法 | 特点 |
|---|---|
| **t-digest** | 尾部精度高，合并性好，Prometheus 生态常用 |
| **HdrHistogram** | 定精度直方图，误差可配置 |
| **GK 算法** | 经典的确定性误差界流式分位估计 |
| **DDSketch** | 相对误差有严格上界 |

共同思想是用"可接受误差"换取"常数空间"。这解释了为什么监控系统的 P99 与你从原始日志算出来的 P99 会有细微差别——**它是估计值**。

### 6.3 Little 定律

$$
L = \lambda W
$$

其中 $L$ 是系统中的平均请求数，$\lambda$ 是到达率，$W$ 是平均停留时间。

它的实用价值：三个量里知道任意两个就能算第三个。

- 已知并发数 $L$ 与吞吐 $\lambda$，可以算出平均延迟 $W = L / \lambda$。
- 已知延迟目标与吞吐，可以算出需要多少并发。

一个常见误用：把 Little 定律应用到重尾延迟上时，$W$ 必须是**真实的平均停留时间**，而不是你观测到的部分样本的平均值——采样偏差会让结果偏乐观。

### 6.4 可观测性与因果关系

一个反复出现的教训：**"相关"不等于"因果"**。

- 指标 A 与指标 B 同时变化，不代表 A 导致 B。
- 尾延迟上升可能与流量上升相关，但真正原因可能是缓存命中率下降导致的重算。

处理办法：

1. **分段计时**本身提供了结构信息（哪一段变长了），比纯相关性可靠。
2. **重复实验**（关闭某个优化看是否复现）。
3. **保留原始样本**，事后可以做更细的切分。

这也是为什么 3.1 的四段分解比"总耗时"更有价值：**它是结构性的，不是相关性的。**

## 七、理论：三个定律

### 7.1 均值与分位数在重尾分布下的分离

对于重尾分布，均值与高分位数可以相差一个数量级。算例实测：

| 统计量 | 值 |
|---|---|
| 均值 | 681.0 |
| P95 | 3000 |

**比值是 4.4 倍**。而如果分布更重尾（例如少数请求等待了分钟级），这个比值会更大。

可验证的判据：如果 P95 与均值的比值大于 3，说明分布重尾，**必须按分位数做优化与告警**。

### 7.2 缓存的价格模型

设输入价格为 $p_i$、缓存价格为 $p_c$、输出价格为 $p_o$，一次请求含 $n_w$ 次写与 $n_r$ 次读（前缀相同）：

$$
\text{倍数} = \frac{n_w \cdot p_i + n_r \cdot p_c}{n_w \cdot p_i + n_r \cdot p_i}
$$

算例实测：1 次写 9 次读时倍数是 **0.215**（节省 4.65 倍）。全未命中 1.000。全命中 0.100。

读法：**缓存的价值随读次数线性增长**。这解释了为什么长会话（前缀被反复使用）的缓存收益最大。

### 7.3 并行组合的尾延迟

由 6.1 的公式，$N$ 路并行的 P99 由下式给出：

$$
p_{\text{组合}} = 1 - (1 - p_{\text{单}})^N
$$

| 单路 P99 | $N = 1$ | $N = 10$ | $N = 100$ |
|---|---|---|---|
| 1% | 1% | 9.6% | **63%** |
| 0.1% | 0.1% | 1.0% | 9.5% |

这张表解释了为什么"单点优化"在分布式系统里收益有限：你必须把单路尾延迟压到很低，组合后才好看。

对 agent 的启示：一次回合里的工具调用越并行，尾延迟越差——**有时候"少一点并行"反而让 P95 更好**。

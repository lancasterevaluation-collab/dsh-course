## 一、为什么需要持久化

### 1.1 崩溃之后，30 轮对话全丢了

进程被杀，内存里的会话历史消失。用户重新打开，看到的是一个空会话。

### 1.2 重启后同一笔操作执行了两次

日志记了"开始转账"，重启后从头重放，把已经执行过的转账又做了一次。

### 1.3 日志末尾半条记录，系统起不来

写入过程中断电，文件末尾是一条不完整的 JSON。解析器抛错，整个系统拒绝启动——**而前面 99% 的数据都是好的**。

这三件事分别对应：**要存什么、怎么重放、坏数据怎么处理。**

## 二、持久化要回答什么

| 问题 | 决定它的量 | 做错的后果 |
|---|---|---|
| 写什么 | 事件的粒度 | 太粗则重放不了，太细则日志爆炸 |
| 怎么写 | 原子性手段 | 半写记录导致无法启动 |
| 写多少 | 检查点间隔 | 恢复太慢或存储太大 |
| 怎么恢复 | 重放的语义 | 重复执行、结果不一致 |
| 坏了怎么办 | 损坏容忍 | 一条坏记录毁掉全部数据 |

核心认识：持久化的目标是**"恢复之后的状态与从未崩溃时一致"**，而不是"数据不丢"。前者可验证，后者不可验证。

## 三、怎么做

### 3.1 追加日志与原子写

**追加（append-only）**是日志的基本形态：只往末尾加，不改写已有内容。这样任何时刻的前缀都是一个合法状态。

单条记录要**原子地**落盘，标准做法是三件事按顺序：

```js
// 原子写：临时文件 → fsync → 原子重命名（三步缺一不可）
export async function atomicWrite(path, content) {
  const temp = `${path}.tmp`
  await writeFile(temp, content)   // 第一步：写临时文件
  await fsync(temp)                // 第二步：确保落盘（否则重命名可能先于数据落盘）
  await rename(temp, path)         // 第三步：原子重命名（同一文件系统内是原子操作）
}
```

算例实测：原子写是 **3 步**。

为什么顺序不能变：如果先重命名再 fsync，断电后可能出现"文件已改名但内容是旧的或空的"。`rename` 的原子性只在同一文件系统内成立——跨设备是复制。

### 3.2 快照与检查点：用空间换恢复时间

每次恢复都从头重放，代价随日志长度线性增长。检查点（checkpoint）把"某个时刻的完整状态"存下来，恢复时从最近的检查点开始。

```js
// 检查点轮留：新的写完后旧的才删，保证任何时刻至少有一份可用的
export function rotateCheckpoint(state, nextOffset) {
  return {
    current: { offset: nextOffset, state },   // 新检查点
    previous: state.current,                  // 上一份保留
  }
}
```

算例实测的检查点轮留：`current.offset = 2`、`previous.offset = 1`。

**恢复时间对比**（算例真实数字）：

| 策略 | 启动重放时间 |
|---|---|
| 无检查点 | **30000 ms** |
| 每 1 万条检查点 | **1000 ms** |

**30 倍的差距**，而且这个差距随日志增长而扩大。

**代价**（同一算例）：

| 检查点间隔 | 存储量 |
|---|---|
| 每 1 万条 | 30 MB（30 份） |
| 每 1000 条 | **300 MB（300 份）** |

这就是那个权衡：检查点越频繁，恢复越快、存储越大。**间隔上界应当由"可接受的恢复时间"反推**（算例给出 1 秒上限对应 10000 条）。

### 3.3 恢复等价性：唯一的正确性判据

$$
\text{replay}(\text{log}, \text{initial}) \equiv \text{state}_{\text{before crash}}
$$

用算例的话说：从检查点（offset=1）重放得到 `{v: 15}`，而从零重放得到 `{v: 6}`——**两者必须都等于崩溃前的状态**，否则某处的语义有问题。

这条判据为什么重要：它把"持久化写得对不对"从一个难以验证的性质（"应该没丢东西吧"）变成了**一个可以跑测试的性质**。

测法：在每一步之后记录状态，崩溃后重放，逐点比对。算例里的"恢复等价性"检查就是这件事：一致 → `true`。模拟"多应用一次"→ `false`。

### 3.4 幂等性：赋值型与累加型

重放安全的前提是操作幂等。而幂等与否，取决于操作的**语义**：

```js
// 幂等检验：同一操作执行两次，结果是否与执行一次相同
export function isIdempotent(op, state) {
  const once = op.apply(state)
  const twice = op.apply(op.apply(state))
  return deepEqual(once, twice)
}
```

算例实测：

| 操作类型 | 幂等 |
|---|---|
| **赋值型**（`set x = 5`） | **true** |
| **累加型**（`x += 5`） | **false** |

这条分界线的工程含义极大：

- 存储"**最终状态**"（赋值）是天然幂等的。
- 存储"**增量**"（累加）必须配一个去重机制（序号、幂等键），否则重放会重复计入。

推荐的写法：日志里存事件（"发生了 X"），恢复时从事件重建状态。而在写状态的边界上，让写入本身是赋值的（"x 现在是 15"）而不是增量的（"x 加了 5"）。

### 3.5 崩溃相位与残留清理

崩溃可能发生在任何一步，算例识别出 **3 个相位**：

| 相位 | 残留物 | 恢复动作 |
|---|---|---|
| 写临时文件前 | 无 | 无 |
| 写完临时文件、未重命名 | `.tmp` 文件 | 删除临时文件 |
| 重命名后、未清理 | 正常的旧文件 | 按新文件继续 |

残留清理要幂等：算例的清理动作返回 `{cleaned: 2, conflicts: 0}`。`conflicts` 是"清理时发现该资源仍被占用"的计数——它不为零意味着有别的实例在跑，应当报警而不是强行清。

### 3.6 损坏处理：尾部截断

日志末尾可能有一条半写记录。处理方式不应该是"拒绝启动"，而是截断到最后一条完整记录：

```js
// 尾部截断：丢弃末尾不完整的记录，保留前面全部有效内容
export function truncateTail(events, isValid) {
  let i = events.length
  while (i > 0 && !isValid(events[i - 1])) i--
  return { events: events.slice(0, i), truncated: i < events.length }
}
```

算例实测：保留 2 条有效事件，`truncated = true`。

一条原则：**损坏是局部的，恢复也应当是局部的。** 因为末尾一条坏记录而丢掉全部历史，是最容易避免、代价最大的一类错误。中间损坏（不是末尾）则应当报警——它意味着更严重的问题。

## 四、特殊情况与处理技巧

| 情况 | 为什么 | 处理 |
|---|---|---|
| 半写记录导致无法启动 | 严格解析 + 无截断逻辑 | 尾部截断到最近完整记录 |
| 检查点把磁盘写满 | 间隔太密 | 按恢复时间目标反推间隔，并滚动删除 |
| 重放后状态不一致 | 操作非幂等 | 改存最终状态，或加去重序号 |
| 崩溃时留下锁文件 | 未清理 | 启动时清理 + 记录进程标识（避免误删活锁） |
| fsync 太慢拖垮吞吐 | 每条都同步 | 批量提交（组提交），在持久性与吞吐间取舍 |
| 恢复时间随日志增长 | 无检查点或检查点太旧 | 定期检查点 + 保留上一份 |
| 两个实例同时恢复 | 无互斥 | 恢复需要独占锁。`conflicts > 0` 时报警 |
| 时钟回拨导致顺序错乱 | 用时间戳排序 | 用**单调序号**而不是墙钟时间 |

最后一条容易被忽略：日志顺序必须由**单调计数器**决定，不能用系统时间。时钟会回拨（NTP 校正、夏令时），回拨之后按时间排序会把后发生的事排到前面。

## 五、工业界的做法（可照做）

### 5.1 标准部件

| 场景 | 方案 | 关键机制 |
|---|---|---|
| 数据库 | 预写日志（WAL） | 先写日志再改数据页。恢复时重放 |
| 键值存储 | LSM-tree + WAL | 内存表刷盘 + 日志保证不丢 |
| 集群共识 | Raft / Paxos 日志 | 多数派确认后才认为已提交 |
| 对象存储 | 版本化 + 条件写 | 用版本号做乐观并发控制 |
| 会话持久化 | 追加事件日志 | 事件即真相，状态是派生 |
| 检查点 | 定期快照 + 增量日志 | 快照周期由恢复时间目标反推 |

共同的形状：**日志是真相，状态是派生。** 只要日志完整，状态永远可以重建。

### 5.2 崩溃一致性的承诺等级

不同系统给不同的承诺，你要知道自己需要哪一级：

| 等级 | 承诺 | 代价 |
|---|---|---|
| 无保证 | 崩溃后可能丢最近若干写 | 最快 |
| 进程崩溃安全 | 进程死不掉数据，机器断电可能丢 | 中等 |
| **机器崩溃安全** | 断电后已确认的写不丢 | 每次写要 fsync |
| 多副本安全 | 机房级故障也不丢 | 网络往返 + 多数派 |

**多数 agent 系统需要的是第二级**（进程崩溃安全），而它不需要每次写都 fsync——这就把性能问题解开了。

### 5.3 fsync 的真实代价

fsync 是"确保数据到达持久介质"的系统调用。它的延迟比普通写高**几个数量级**（因为要等设备闪存/磁盘真正落盘）。

实践做法：

- **组提交（group commit）**：把多个待同步的写合并成一次 fsync。
- **只在关键边界 fsync**：例如"回合结束"、"状态转移"，而不是每条日志。
- **接受窗口**：明确声明"最多丢最后 N 毫秒的写"，并把这作为设计参数。

判断依据是业务语义：会话历史丢最后一条通常可接受。支付记录不行。

### 5.4 参数怎么定

| 参数 | 推荐起点 | 依据 |
|---|---|---|
| 日志粒度 | 一个语义事件一条 | 太细则日志膨胀，太粗则无法重放 |
| 检查点间隔 | 由恢复时间目标反推 | 算例：1 秒上限对应约 10000 条 |
| 检查点保留份数 | 2 份（当前 + 上一份） | 轮留，防止写坏 |
| fsync 频率 | 回合边界或批量提交 | 兼顾性能与承诺等级 |
| 截断策略 | 只截尾部，中间损坏报警 | 局部损坏局部处理 |
| 序号 | 单调计数 | 不依赖时钟 |
| 恢复锁 | 独占 | 防止并发恢复互相破坏 |

### 5.5 一份可落地的实施清单

1. **事件日志**：追加写，每条自带单调序号。
2. **原子写**：临时文件 → fsync → 重命名，三步顺序固定。
3. **状态派生**：内存状态由事件重放得到，不单独持久化（或只作为缓存）。
4. **检查点**：定期快照 + 保留上一份。间隔由恢复时间目标反推。
5. **恢复流程**：加独占锁 → 载入最近检查点 → 重放其后事件 → 截断尾部损坏 → 释放锁。
6. **幂等边界**：所有对外副作用带幂等键。状态写入用赋值而非累加。
7. **残留清理**：启动时清理临时文件与过期锁，`conflicts > 0` 时报警。
8. **观测**：恢复耗时、截断次数、检查点大小、重放事件数。
9. **测试**：崩溃注入——在写入的各个相位杀进程，验证恢复后状态一致。
10. **文档**：明确写出崩溃一致性的承诺等级与可接受的丢失窗口。

## 六、学术界的结论

### 6.1 ARIES 恢复算法

数据库领域最经典的恢复算法，它的三段结构可以直接借用到任何日志系统：

| 阶段 | 做什么 | 对应到会话日志 |
|---|---|---|
| **分析（Analysis）** | 从最近检查点扫描日志，确定崩溃时的状态与待处理事务 | 找出哪些回合未完成 |
| **重做（Redo）** | 重放所有已提交的修改（"重复历史"） | 重放事件重建状态 |
| **撤销（Undo）** | 回滚未提交的事务 | 丢弃未完成的回合 |

关键思想是**"重复历史"（repeating history）**：恢复时先重做到崩溃前的状态，再回滚未提交的部分，而不是试图猜测哪些修改生效了。这避免了恢复逻辑本身成为 bug 来源。

### 6.2 确定性重放与时间旅行调试

如果系统的行为完全由输入决定，那么"重放输入"就能复现任何 bug。这是**确定性重放**（deterministic replay）的核心，也是调试分布式系统的主流手段。

它对 agent 系统的启示是直接的：把模型的输出也当作输入记下来（见 7.4 的采样与种子），那么一次会话就可以被完整重放——包括模型当时说了什么。**这是"模型可见 ⟺ 已记录"这条原则在持久化层的体现。**

### 6.3 CRDT 与操作转换

当多个副本可以并发修改时，"重放"不再是唯一手段。两条学术路线：

| 路线 | 思想 | 适用 |
|---|---|---|
| **CRDT** | 设计数据结构，使并发合并**天然收敛**且与顺序无关 | 计数器、集合、文本编辑 |
| **OT**（操作转换） | 对并发操作做变换，使最终结果一致 | 协同编辑 |

对持久化的启示：如果状态可以用 CRDT 表达，**重放顺序就不再重要**——这等价于把"幂等性"提升成了"结构性质"。例如用"或集合"代替"数组追加"，重复添加同一个元素不会产生重复项。

### 6.4 崩溃一致性研究的核心发现

存储领域有一类反复被验证的结论：**文件系统的实际行为与直觉不同**。

- 许多文件系统不保证"写 A 之后写 B，崩溃后 A 一定在 B 之前落盘"（除非显式 fsync 或使用屏障）。
- 因此"按顺序写两个文件"在崩溃后可能是**逆序**的。
- 这就是 3.1 里"先 fsync 再重命名"那条规则的理论依据。

对你的意义：不要依赖"我按顺序写了，所以顺序一定保持"。**需要顺序保证的地方，显式同步。**

### 6.5 检查点间隔的经典权衡

检查点间隔是**恢复时间与存储开销**的权衡，形式化后可以得到最优间隔：

- 间隔太小：检查点本身的开销（写放大）成为瓶颈。
- 间隔太大：恢复时间随日志长度线性增长。

更复杂的策略（增量检查点、模糊检查点）的目标都是**降低检查点本身的暂停时间**，而不是简单减小间隔。

## 七、理论：三个权衡

### 7.1 恢复时间与检查点间隔

恢复时间近似为"从最近检查点重放到崩溃点"的代价：

$$
T_{\text{恢复}} \approx T_{\text{载入检查点}} + (\text{崩溃点} - \text{检查点}) \times t_{\text{每条}}
$$

算例给出的具体数字：无检查点时 30000 ms，每 1 万条检查点时 1000 ms。

反推间隔：给定可接受的恢复时间上限，就能算出最大间隔（算例：1 秒上限对应 10000 条）。

### 7.2 存储与检查点的关系

$$
\text{存储} = \frac{\text{日志长度}}{\text{间隔}} \times \text{单份快照大小}
$$

算例的数字：间隔 1 万 → 30 MB（30 份）。间隔 1000 → 300 MB（300 份）。

注意这是线性关系：间隔缩小 10 倍，存储放大 10 倍，而恢复时间只缩小到约 1/10（如果有下界则更少）。**收益递减，成本线性**——所以间隔不该无限缩小。

### 7.3 幂等的结构条件

一个操作 $f$ 幂等，当且仅当 $f(f(s)) = f(s)$。判断它属于哪一类，只要看它是否依赖当前值：

| 形式 | 幂等 | 原因 |
|---|---|---|
| $s \mapsto c$（赋值） | 是 | 结果与初始值无关 |
| $s \mapsto s + c$（累加） | 否 | 结果依赖初始值 |
| $s \mapsto \max(s, c)$ | 是 | 结果收敛到同一个上界 |
| $s \mapsto s \cup \{c\}$（集合并） | 是 | 集合并天然幂等 |

这张表就是设计原则：**想要重放安全，就让状态更新写成最后一行那些形式**（赋值、取最大、集合并），而不是累加。

这也解释了 CRDT 的价值：它把常用的状态更新都设计成幂等形式。

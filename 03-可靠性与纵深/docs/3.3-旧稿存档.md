## 本篇新词

上下文窗口（context window） 指一次模型请求能接受的 token 上限。它是一个硬限制：超过它请求会被拒绝，而不是被截断。因此"装不下"不是一个性能问题，而是一个正确性问题。

压缩（compaction） 指把一段较长的历史替换成一段较短表示的动作。它是投影而不是改写——本章的压缩产生一条新事件，而不修改已有事件，这个区别决定了历史能否被重建。

压缩点（compaction point） 指压缩发生的位置。它是一条事件，记录"从哪一条之后的历史被替换成了摘要"。派生视图从最后一个压缩点往后算，而它之前的原始事件仍然在日志里。

摘要（summary） 指压缩产生的那段替代文本。它的质量是不可完全验证的：一段摘要"够不够用"取决于后来要回答的问题，而那些问题在压缩时还不存在。

溢出（spill） 指把过大的中间结果写到磁盘并以一个指针代替它。它与压缩的区别是对象不同：压缩处理历史，溢出处理单次工具或模型的输出。两者的共同点是都不丢原始数据——溢出保留文件，压缩保留事件。

指针（pointer） 指代替大内容出现在上下文中的那段简短信息。它必须携带让模型能取回原文的信息（路径、行数范围、总长度），否则模型只能重做一次操作。

保留策略（preserve policy） 指压缩时明确规定哪些内容不参与压缩。通常包括系统提示、最近若干轮消息、以及当前任务的目标陈述。它的作用是防止"把最重要的那部分也压掉"。

不可验证的质量 指那类"没有客观判据、只能抽样评估"的性质。摘要质量属于这一类，而处理它的方式不是"想办法量化"，而是提前设计一个抽样评估方案（例如用一组关键事实问题去问模型）。

这张图的关键线索在第二块：压缩的难点不在生成摘要，而在让"改变后的输入"仍然可重建。生成一段摘要是模型最擅长的事之一，而把"这次压缩发生过、它替换了什么、替换成了什么"记录成可重放的事件，才是这一篇要做的判断。

### 0.1 一个具体的判断：压缩该不该改历史

三种实现的后果在 2.7 的 0.1 已经列出，这里给出它们的量化差别。

设一段历史有 10,000 条事件、每条平均 200 字节，压缩后摘要约 4,000 字节。改写历史的做法把日志降到约 4KB。追加压缩点的做法保留全部原始事件，日志仍是 2MB 加上摘要。

两者的存储差是三个数量级，而在需要回答"模型当时看到什么"时，前者只能给出摘要粒度、后者能给出完整重建。因此这个判断的实质不是"省不省空间"，而是"要不要保留可解释性"——而它的答案取决于系统的用途：一次性脚本可以不保留，长期运行且需要复盘的 agent 不能。

### 0.2 本篇建立的三项判据

第一项用于判断什么时候该压缩：问"这一步的输入是否接近窗口上限"。它的实现需要一个 token 估算器（估算而不是精确计数，因为精确计数要引入分词器），而阈值的选取要留出余量——余量是给"这一步的回答"留的，不是给压缩本身留的。

第二项用于判断一段内容该不该被压缩：问它是否在保留策略里。系统提示、最近若干轮、当前目标不参与压缩。它们的共同点是"丢了就没有替代"。反过来说，可以被压缩的内容是那些"后来能重建或不再需要"的部分。

第三项用于判断一个溢出指针是否合格：问模型能不能只凭它取回原文。合格的指针包含路径、长度、以及内容的首尾若干字符——缺少任何一项时，模型只能重新执行一次可能代价很高的操作。

### 0.3 十分钟练习：溢出的两种写法

下面这段代码对比"直接截断"与"溢出加指针"的差别。

```js
// 写法一：截断，丢掉中间
function truncate(text, limit = 200) {
  return text.slice(0, limit) + `\n…（已省略 ${text.length - limit} 个字符）`
}
// 写法二：溢出到磁盘，用指针替代
function spill(text, limit = 200, dir = '/tmp/spill') {
  if (text.length <= limit) return { inline: text }
  const path = `${dir}/${Date.now()}.txt`
  // 真实实现写文件；这里只演示返回结构
  return { inline: `${text.slice(0, 80)}…${text.slice(-80)}`, pointer: { path, totalChars: text.length, totalLines: text.split('\n').length } }
}

const big = Array.from({ length: 500 }, (_, i) => `第 ${i + 1} 行内容`).join('\n')
const t = truncate(big, 200)
const s = spill(big, 200)
console.log('截断后能看到的信息：', t.length, '字符，中间不可恢复')
console.log('溢出后的指针：', s.pointer.path, s.pointer.totalChars, '字符，', s.pointer.totalLines, '行')
```

两种写法的差别出现在"模型需要看第 300 行"这件事上：截断的写法无法回答（内容已经丢了），而溢出的写法让模型可以用 `read_file` 带范围参数再读一次。这条差别的代价是可量化的：模型重新执行一次代价高的操作，可能比读一个文件贵几十倍。

> **面试视角**

> **高分要点**：区分两种情形——历史太长用压缩（并说明压缩点必须进日志），单次输出太大用溢出（并说明指针要携带什么）。把两者混为一谈是最常见的答错方式。

### 0.5.3 三个连锁影响

第一，压缩的合法性来自"它不丢信息"，而这一点只在原始事件保留时成立。 这条连锁把本篇与 1.5 的可逆性分级接起来：改写历史的压缩属于第三级（不可逆），追加事件的压缩属于第一级（可撤销——删掉那条事件即可回到压缩前的状态）。这个差别在需要回退时会变成实际的能力差距：一次错误的压缩（摘要质量很差）在追加模式下只需丢弃那条事件，而在改写模式下无法恢复。

第二，溢出把"上下文占用"从系统约束变成了可管理的资源。 没有溢出时，一次大输出要么撑爆上下文（失败），要么被截断（丢信息）。有溢出时，它变成"上下文里放指针，原文在磁盘上"——代价从不可恢复的信息损失变成了可管理的磁盘占用。这条连锁的量化形态是"一次溢出文件的生命周期"，而释放它的责任必须被明确分配。

第三，摘要质量的不可验证性决定了它必须按"抽样加判据"来管理。 没有客观判据意味着不能用自动化测试守住它，而唯一可行的方式是提前设计一组关键事实问题并定期抽样。这条连锁的结论是反直觉的：对不可验证的质量，正确的做法不是放弃验证，而是把验证的频率降低到可承受并固定下来。

### 0.5.4 它与本书其余部分的关系

本篇的压缩针对单会话的历史，而第 4 卷的记忆有界化针对跨会话的积累。两者的机制不同（前者按同一性、后者按时间与使用频率），但它们的骨架相同：都是在一个有硬上限的空间里决定保留什么。因此本篇的判据（保留策略、抽样评估、指针携带信息）在第 4 卷会被复用。

## L0 要解决的问题

### 0.1 现象一：撞上窗口上限，任务直接失败

第一个现象是"装不下"的最朴素形态。会话进行到某一步时，请求的总 token 数超过了窗口，而 provider 返回一个错误（2.1 的错误分类里它属于 `invalid_request`，因此不可重试）。任务就此失败，而用户看到的信息是"请求无效"——它没有告诉用户真正的原因（历史太长），也没有给出任何出路。

这个现象的性质是缺少降级路径：系统在正常情况下能工作，而它在资源耗尽时没有第二条路。它的修法就是本篇的主题（压缩与溢出），而它的设计前提是把"装不下"识别为一种可预期的状况而不是异常——因为它必然会发生，只是时间问题。

### 0.2 现象二：一次大输出永久占据上下文

第二个现象更隐蔽，因为它不表现为失败，而表现为成本上升与质量下降。一次读取大文件的工具调用把三万 token 的内容放进消息数组，而它在后续每一轮都会随请求一起发出——除非它被某种机制处理掉，否则它会占据整个任务的剩余生命周期。

它的代价是双重的。空间上，它挤占了可用于推理的余量。成本上，2.7 的 1.7 已经算出输入随步数累积，而一个大输出会把每个后续步骤都抬高一个量级。因此"处理大输出"不是优化，它是让长任务在成本上可行的前提。

### 0.3 现象三：压缩之后，历史无法重建

第三个现象是对 2.7 那条不变量的直接违反。如果压缩的实现是"用摘要替换掉被压缩的事件"，那么被替换的部分就永久丢失了，而"模型当时看到了什么"这个问题的答案从此只能到摘要的粒度。

它的表现是延迟的：压缩发生时一切正常（甚至更好——请求变小了），而它在需要复盘、诊断或恢复时暴露。这类"当时更好、后来无法回答"的改动，是本课程反复强调要警惕的一类（1.5 的 1.2 节）。

### 0.4 现象四：摘要是好是坏，没有判据

第四个现象是质量评估的缺失。压缩产生了摘要，而"这段摘要够不够用"没有客观判据——它取决于后来要回答的问题，而那些问题在压缩时还不存在。

它的后果有两种形态。一种是摘要丢了关键信息，而模型在后续步骤中表现出"忘记"某件事（用户会把它解释成模型能力问题）。另一种是摘要过长（几乎等于没压缩），而系统付出了模型调用的成本却没有获得空间收益。两者都不会被自动化测试发现，因为它们的判据是"能不能回答后来的问题"。

### 0.5 这一篇要正面回答的四个问题

第一，什么时候触发压缩，阈值怎么定（1.1）。第二，哪些内容不参与压缩（1.2）。第三，压缩如何记录才能保持可重建（1.3）。第四，单次输出过大怎么办（1.4），以及摘要质量如何评估（1.5）。

四个问题里第三个是本篇的核心，因为它决定这一篇的机制能否与第 2.7 篇的不变量共存——这是第 3 卷每一篇共同的检查项。

## L1 设计与原理

### 1.1 触发条件与余量的含义

压缩的触发条件是"当前请求的 token 估算值接近窗口上限"。这个条件里有三个需要规定的参数：估算方式、窗口上限、以及接近的程度。

估算方式用字符数除以一个经验系数（中文与英文的系数不同），而不是精确计数。理由是精确计数需要引入分词器（一个不小的依赖），而压缩的触发不需要精确——它只需要在"还来得及"的时候被触发。估算的误差通过余量吸收。

窗口上限来自配置而不是硬编码。它随模型不同而不同，而且同一模型的不同版本可能不同——因此"上限"是一个部署参数（2.6 的第 9 条决策）。

余量的含义是"给这一次的回答留出空间"。它等于最大输出 token 数加上一段缓冲，因为压缩发生在请求之前，而请求之后还要生成回答。漏掉这一项会导致一个具体的故障：压缩之后请求刚好装下，而回答因为没有空间被截断。

```ts
function shouldCompact(estimate: number, window: number, maxOutput: number): boolean {
  return estimate + maxOutput > window * 0.8      // 0.8：再留两成给估算误差
}
```

这个判据里的三个数字各有来源，而它们都不能拍脑袋——这也是本篇把 token 估算列为下游依赖的原因：没有估算，阈值就只能靠感觉。

### 1.2 保留策略

保留策略规定哪些内容不参与压缩。本课程的四项如下。

系统提示永远保留：它是任务的前提，而它通常在历史上只出现一次或几次，压缩它的收益极小。

最近若干轮消息保留：它们是当前任务的上下文，压缩它们会让模型立刻失去对眼前任务的把握。轮数的选择是一个权衡——保留越多，压缩的收益越小。保留越少，压缩后行为的变化越明显。

当前任务的目标陈述保留：它通常在第一条用户消息里，而它决定后续所有判断的方向。

压缩点的摘要本身保留：它们是之前压缩的结果，而重复压缩（把摘要再压缩）会造成信息的二次损失。处理多次压缩的正确方式是折叠（把多个压缩点合成一个新的摘要）而不是层层叠加（1.6）。

四项之外的其余内容都可以参与压缩。这条划分的判据是"丢了它有没有替代"：系统提示没有替代（只能重读配置），最近轮次没有替代（只能重新问用户），而中间那些工具调用与结果有替代（需要时可以重新执行）。

### 1.3 压缩点事件与派生起点

压缩的实现形态是一条事件：

```ts
export interface CompactionEvent {
  readonly type: 'session/compaction'
  /** 从哪一条事件之后的历史被替换 */
  readonly atSeq: number
  /** 替代文本 */
  readonly summary: string
  /** 生成摘要所用的模型与提示词版本（用于事后分析摘要质量） */
  readonly modelId: string
  readonly promptVersion: string
}
```

四个字段各有用途。`atSeq` 是派生视图的起点。`summary` 是替代内容。后两个字段用于 1.5 的质量评估——如果没有它们，"摘要质量下降"这个问题无法归因到"换了模型"或"改了提示词"。

派生视图的规则是：从最后一个压缩点之后的事件开始，加上那个压缩点的摘要本身。多次压缩时，只有最后一个压缩点之后的原始事件参与派生，而更早的压缩点被折叠（1.6）。

这个设计的合法性来自一条不变量的检查：重建出的输入包含摘要（它是日志里的一条事件），因此"模型看到什么"可以被完整重建——被压缩掉的历史不再进入请求，但它仍然在日志里，因此"当时看到什么"与"日志里有什么"仍然一致。

### 1.4 溢出的机制与指针

溢出处理的是单次输出过大，它与压缩的区别在对象：压缩处理历史（多轮），溢出处理单次输出（一个工具的结果或一次模型的回答）。

溢出的实现是三步：内容超过阈值时写入文件、上下文中放入指针、并记录一条事件说明"这次输出被溢出了"。指针必须携带的信息如下。

```ts
interface SpillPointer {
  readonly path: string          // 取回原文的位置
  readonly totalChars: number    // 原文总长
  readonly totalLines: number    // 总行数（让模型能按范围读）
  readonly head: string          // 首若干字符（让模型判断是否需要读全文）
  readonly tail: string          // 尾若干字符（结论常在这里）
}
```

五个字段的必要性可以逐条说明：没有路径时无法取回。没有总长时无法判断"要不要读全部"。没有行数时无法使用范围参数。没有首尾时模型必须读一次全文才知道它有没有用——而那次读取可能正是它想避免的。

溢出与压缩的一个共同要求是不丢原始数据：溢出保留文件，压缩保留事件。两者的差别是溢出的数据在文件系统里，因此它有一个额外的问题：什么时候删除。本课程的做法是把溢出文件放在会话目录下，并在会话结束时清理——它的生命周期与会话对齐。

### 1.5 摘要质量的抽样评估

摘要质量没有客观判据，而处理方式不是"想办法量化"，而是提前设计一组关键事实问题并定期抽样。

做法是：在压缩时记录一批"当时已知的关键事实"（例如用户提出的约束、当前的目标、已知的失败尝试），然后在一段时间后（或者下一个任务结束时）用这些问题去问模型，看它能否从摘要中回答。答对率是摘要质量的一个代理指标。

这个方法的三个要点。第一，问题集要在压缩时生成或选取，因为那时才知道"什么是关键"。第二，评估的代价是额外一次模型调用（或者人工抽样），因此频率要低。第三，它是代理指标而不是真指标——一段摘要可能答对全部关键事实而在某个具体的后续任务上失效。因此它的用途是发现"质量明显下降"的趋势，而不是判定单次压缩的好坏。

```ts
interface SummaryQualityCheck {
  readonly atSeq: number
  readonly sampleQuestions: readonly string[]   // 压缩时记录的关键事实
  readonly askedAt: number                      // 何时抽样的
  readonly correct: number                      // 抽样结果
}
```

### 1.6 多次压缩的折叠

一次长任务可能经历多次压缩，而它们必须被折叠而不是叠加。

叠加的做法是"每次压缩都产生一个摘要，而派生视图把全部摘要串起来"。它的缺陷是信息被二次损失：第二次压缩的输入包含第一次的摘要，因此第二次的摘要里"第一次摘要的内容"又被压缩了一遍，而每一次都在丢信息。

折叠的做法是：新的压缩点覆盖一个更大的范围（`atSeq` 更小），而它之前的压缩点不再被独立使用——它们的原始事件仍然保留（因此可重建），但在派生视图里只有最后一个摘要生效。这条规则让压缩的信息损失只发生一次（从原始事件到最新摘要），而不是每次压缩叠加一次。

折叠带来的一个额外好处是日志的可读性：读日志时看到的是"最近一次压缩的摘要加它之后的事件"，而不是一串层层嵌套的摘要。

### 1.7 成本与收益的量化

压缩是否划算可以直接算。设被压缩的历史有 `S` 个 token、摘要占 `s` 个 token、剩余步骤数为 `n`、摘要生成成本为 `c`（一次模型调用），那么压缩的收益约 `(S - s) × n`，成本约 `c`。

这个式子给出两条判断。第一，压缩的收益与剩余步骤数成正比——在任务的最后一步压缩是浪费（`n=1` 时收益几乎为零），而它在早期压缩收益最大。第二，摘要不能太长：如果 `s` 接近 `S`，那么收益趋近于零而成本照付。因此"摘要长度上限"是一个必须规定的参数，而不是让模型自由发挥。

第 3.6 篇会给出观测这两个量的方式（每轮的 token 数与压缩发生次数），而这一节的式子是那篇的判据来源。

### 1.8 两次追问

工程侧的问题是什么时候该放弃压缩改为失败。答案与"能不能降级"有关：如果压缩之后仍然超过窗口（例如系统提示本身就很大），那么继续压缩只会损失信息而没有收益。此时的正确动作是显式失败并说明原因（"系统提示占用了大部分窗口"），因为它把问题指向了真正的瓶颈。

产品侧的问题是压缩对用户可见吗。多数时候不可见，而它应当在一处可见：用户应当能知道"这段对话的历史已经被压缩过"，因为那意味着模型对早期内容的记忆是摘要级别的。第 5 卷的界面会给出这个提示，而它的依据就是压缩点事件（它进了日志，因此可查询）。

### 1.9 压缩的可观测性

压缩的行为必须被度量，否则它的收益与代价都只能靠感觉。三个指标覆盖全部判断。

第一个是净省下的 token：压缩前的历史规模减去摘要规模，再减去生成摘要的调用成本。这个值在短会话里可能是负的（1.7 的式子），而它应当是正的——如果它长期为负，说明触发的阈值设置有问题（压得太早）。

第二个是触发频率（压缩次数除以轮数）。它回答"是不是压得太频繁"：正常的长会话里压缩应当是偶发的，而如果每一两轮就压一次，说明保留策略太宽松或者阈值太低。

第三个是压缩前后的步数分布变化。压缩会改变模型看到的内容，而它可能让任务需要的步数变多（摘要不如原文清晰）。这个指标的对比方式是"压缩启用前后，同类任务的平均步数"——它把压缩的质量影响变成了一个可比较的数字。

三个指标的共同特征是它们都在回答"压缩值不值"。它是最容易产生错觉的一类机制：请求变小了、成本看起来降了，而代价（信息损失）要到后来才显现——因此必须用数字把它拉住。

其中两条值得展开，因为它们的选择在实践中经常被做成另一个。

### 关于第 1 条的完整论证（压缩为什么必须追加而不是改写）

替代方案是用摘要替换被压缩的事件。它的优点在三个地方：日志更小（0.1 算了三个数量级的差别）、派生更简单（不需要"从某个点往后算"）、以及对读取方更友好（不需要认识压缩事件类型）。

代价也在三个地方，而它们都与"可回答性"有关。第一，"模型当时看到什么"降级到摘要粒度：被压缩掉的原始事件不再存在，因此那次请求的完整输入无法重建。第二，压缩不可回退：如果摘要质量很差（1.5 的分析），追加模式下丢弃那条事件即可恢复，而改写模式下无法恢复。

第三，压缩本身无法被审计：追加模式下日志里能看到"在哪一步压缩了、摘要是什么、用的哪个模型"，而改写模式下这些信息要么不存在、要么散落在其他地方。

本课程选追加。这个选择的一般形式是：不可逆的信息损失不要在一次改写里发生，而要作为一条新记录发生（1.5 的 L2 第 4 条已经给过这条结论，这里给出它在实现层的完整形态）。它的代价是一条必然性论证的缺失：改写模式更简单，因此它会在"日志大小不重要"的场景里更合适——例如一次性的批处理任务，它的历史不需要被复盘。

### 关于第 5 条的完整论证（多次压缩为什么要折叠）

替代方案是层层叠加：每次压缩都产生一个独立摘要，派生视图把全部摘要按顺序放进去。

它的失败方式在第二层叠加时就出现。第一次压缩把事件 1–100 变成摘要 A1。第二次压缩把"摘要 A1 加事件 101–200"变成摘要 A2。此时 A2 已经包含了 A1 的信息（被压缩过一次），而派生视图若同时放入 A1 与 A2，那么 A1 的内容会被重复表达。若只放 A2，那么 A1 的"独立可用性"就没有意义——两种做法都指向同一个结论：A1 不该继续被独立使用。

折叠的做法是让新压缩点的 `atSeq` 覆盖一个更大的范围（覆盖到 A1 覆盖的起点之前），并把 A1 从派生中排除。这样"从原始事件到最新摘要"的压缩只发生一次，而信息损失的次数从"每次压缩一次"降到"始终一次"。

折叠的实现代价是压缩逻辑需要知道上一次压缩覆盖到哪里（读最后一个压缩点的 `atSeq`），而这要求压缩点事件被正确地按顺序维护。它的收益是可以量化的：设每次压缩损失 30% 的信息，三次叠加之后的保留率是 34%，而折叠模式下仍是 70%。

## L3 实现（施工图）

### 3.1 文件结构

```
// kernel/spill.ts          负责单次输出过大
// ┌─ 判定段 ── 是否需要溢出（按字符数）
// ├─ 落盘段 ── 写文件并返回指针
// └─ 清理段 ── 会话结束时删除该会话的溢出文件
//
// plugins/compaction.ts    负责历史过长
// ┌─ 触发段 ── shouldCompact（估算、余量）
// ├─ 保留段 ── preservePolicy（四项保留）
// ├─ 生成段 ── 调模型生成摘要（记录模型与提示词版本）
// ├─ 记录段 ── 追加压缩点事件（含折叠）
// └─ 样本段 ── 抽取关键事实问题供后续抽样
```

两个文件的划分对应 1.4 那句区分：溢出的对象是内容，压缩的对象是历史。把它们放在同一个文件里会让"什么时候用哪一个"变成实现细节，而它应当是一个判断。

### 3.2 触发与保留

```ts
const PRESERVE = { systemPrompt: true, recentTurns: 4, goal: true, lastSummary: true }

function compactRange(events: SessionEvent[], preserve = PRESERVE): { from: number; to: number } | null {
  const last = events.findLastIndex((e) => e.type === 'session/compaction')
  const from = last >= 0 ? (events[last] as CompactionEvent).atSeq + 1 : 0   // 折叠：从上次覆盖的起点之后
  const to = events.length - preserve.recentTurns * 2                        // 保留最近若干轮
  return to <= from ? null : { from, to }                                    // 可压缩区间为空则不动
}
```

这段实现的三个要点。第一，`from` 由上一次压缩的 `atSeq` 决定——这是折叠逻辑的落点。第二，`to` 留出最近的轮次（每轮按两条事件估算）。第三，区间为空时返回 `null` 而不是压缩一个空区间——这条判断防的是"压缩了一次什么都没压掉的东西"，而那会白白消耗一次模型调用。

### 3.3 生成与记录

```ts
export async function compact(ctx: Context, session: Session): Promise<CompactionEvent | null> {
  const range = compactRange(session.events)
  if (!range) return null
  const slice = session.events.slice(range.from, range.to)
  const { summary, modelId, promptVersion, keyFacts } = await summarize(ctx, slice)
  const atSeq = range.from - 1                                   // 折叠：新压缩点覆盖更早的起点
  await session.append({ type: 'session/compaction', atSeq, summary, modelId, promptVersion })
  await session.append({ type: 'session/compaction-sample', atSeq, questions: keyFacts })
  return { type: 'session/compaction', atSeq, summary, modelId, promptVersion }
}
```

四个要点。第一，`atSeq` 用 `range.from - 1` 而不是 `range.to`——这是折叠的关键：新压缩点声明"从更早的地方开始被替换"，从而让旧压缩点不再被独立使用。第二，摘要的元数据（模型与提示词版本）被记录。第三，关键事实问题被单独记录（判据 11 的输入）。

第四，两次 `append` 的顺序保证了"压缩点先于样本"——如果反过来而在中间崩溃，样本会指向一个不存在的压缩点。

### 3.4 溢出

```ts
export interface SpillResult { inline: string; pointer?: SpillPointer }

export async function spill(text: string, limit: number, dir: string): Promise<SpillResult> {
  if (text.length <= limit) return { inline: text }
  const path = join(dir, `spill-${randomUUID()}.txt`)
  await writeFile(path, text, 'utf8')
  return {
    inline: `（输出已溢出到文件，见下方指针）`,
    pointer: { path, totalChars: text.length, totalLines: text.split('\n').length, head: text.slice(0, 200), tail: text.slice(-200) },
  }
}
```

这段实现里 `inline` 与 `pointer` 的分工值得说明：`inline` 是进上下文的那部分（一句说明），而 `pointer` 是结构化信息（供上层渲染成给模型看的文本）。把两者分开让渲染方式可以变化（例如某些场景把 head 与 tail 直接放进去，另一些场景只放路径）。

### 3.5 验收判据

| # | 判据 | 怎么检查 |
|---|---|---|
| 1 | 未超阈值不压缩 | 短会话调用压缩，核对返回 `null` 且不写事件 |
| 2 | 压缩点事件被追加 | 触发一次压缩，核对日志里出现该事件 |
| 3 | 压缩不改写已有事件 | 压缩前后比较被压缩区间的事件，逐条相同 |

| 6 | 最近若干轮保留 | 核对最后 N 轮的消息仍在 |

| 8 | 摘要长度受限 | 核对生成的摘要不超过配置的上限 |
| 9 | 摘要元数据被记录 | 核对压缩点事件含模型与提示词版本 |

第 3 与第 13 条是核心：前者验证"压缩不改写历史"，后者验证"改变输入之后仍可重建"。第 7 条验证折叠逻辑，它的缺陷表现为"信息被多次压缩"而不会报错。

### 3.7 实现里最容易写错的三处

第一处是压缩点的 `atSeq`。正确做法是取"新的覆盖范围的起点减一"（3.3 的 `range.from - 1`），这样它同时表达"从哪里开始被替换"与"覆盖了上一次压缩"。常见错误是取被压缩区间的终点，于是派生视图会在旧摘要与新摘要之间留下重叠的一段。

第二处是压缩与追加的顺序。正确做法是先追加压缩点再追加样本（或把两者合成一条事件）。常见错误是先写样本，而它在两次写入之间崩溃时会产生一个指向不存在压缩点的样本——这一类缺陷只在崩溃时出现，而它的表现是抽样时找不到对应的摘要。

第三处是溢出文件的清理时机。正确做法是在会话结束时清理该会话的目录。常见错误是"立即删除"（模型还没读就被删了）或者"永不删除"（磁盘慢慢被填满）。这条的判据是溢出的用途：它需要在一段时间内可读，而那个时间窗口由会话的持续时间决定。

## L4 运行与验证

### 4.1 三层验证

第一层是契约测试：按 3.5 的十三条判据逐条检查，用假 provider 生成固定摘要，不需要网络。

第二层是重建验证：压缩之后清空内存、从日志重建，核对重建出的请求与压缩后实际发出的请求一致（2.7 的断言）。这一层检验的是"压缩之后仍然可重建"。

第三层是质量抽样：用压缩时记录的关键事实问题去问模型，看它能否从摘要中回答。这一层不能自动化（它需要判断），因此它的频率低（例如每个版本或每个长任务之后跑一次）。

```powershell
node tests/ch03/t3-compaction.mjs            # 契约测试（十三条判据）
node grade/ch03/negative-check-compaction.mjs # 判分器的鉴别力
node tools/summary-sample.mjs                # 摘要质量的抽样（需要真模型）
```

### 4.2 判据

做完这一篇的标志有三条：十三条判据全部通过。压缩之后的重建验证通过（不变量未被破坏）。以及你能说清"一次错误的压缩如何回退"（丢弃那条压缩点事件）。

## L5 语法速查

### 5.1 术语表

| 术语 | 在本篇里的准确含义 | 容易误解为 |
|---|---|---|
| 上下文窗口 | 一次请求能接受的 token 上限（硬限制） | "上下文长度"（那可能指当前占用） |
| 压缩 | 把一段历史替换成较短表示的动作 | "截断"（截断丢数据，压缩产生替代） |
| 压缩点 | 记录"从哪里开始被替换"的事件 | "缓存"（缓存可丢，它不可丢） |
| 摘要 | 压缩产生的替代文本 | "总结"（它服务于后续推理，不只是给人看） |
| 溢出 | 把过大内容写到磁盘并用指针替代 | "截断"（溢出不丢原文） |
| 指针 | 代替大内容出现的简短信息 | "链接"（它必须携带取回所需的信息） |
| 保留策略 | 规定哪些内容不参与压缩 | "白名单" |
| 折叠 | 让新压缩点覆盖更大范围，避免叠加 | "合并摘要"（折叠不改摘要内容，只改覆盖面） |

### 5.2 命令速查

| 目的 | 命令 | 说明 |
|---|---|---|
| 跑压缩契约测试 | `node tests/ch03/t3-compaction.mjs` | 十三条判据 |
| 负向验证 | `node grade/ch03/negative-check-compaction.mjs` | 四类错误实现应全部被抓 |
| 看待压缩区间 | `node tools/compact-range.mjs <日志>` | 输出当前可压缩的起点与终点 |
| 查摘要长度分布 | `rg -o '"summary":"[^"]*"' <日志> \| awk` 类统计 | 过长说明上限没设好 |
| 查溢出文件 | `Get-ChildItem <会话目录>/spill` | 会话结束后应当为空 |

### 5.3 三条容易踩的规则

第一条，压缩只追加不改写。改写会让历史无法重建，而它的代价在需要复盘时才显现。

第二条，余量要给"这一步的回答"留。只留最大输出而不留缓冲会导致回答被截断。

第三条，多次压缩要折叠。层层叠加会让信息被重复压缩，而它不会报错。

## L7 挑战题（不给答案）

第一题：给压缩加"部分压缩"。 现在的压缩是一次性的（压一段）。设计一种增量压缩（每次压一小段），并说明它与折叠的关系。

第二题：设计摘要的降级链。 如果摘要生成失败（模型不可用），应当怎么办？给出方案并说明它对接地与日志的影响。

第三题：溢出的检索。 模型拿到一个指针之后，如何高效地取回它需要的部分？设计一个"按需读取"的工具接口，并说明它与范围参数的关系。

第四题：论证"改写历史"的一个合理场景。 构造一个场景，说明改写比追加更合适，并给出它满足的条件。

第五题：摘要质量的自动代理指标。 构造一个不需要人工抽样的代理指标（例如摘要的压缩比、实体覆盖率），并说明它的失效条件。

第六题：压缩与缓存的相互作用。 第 3.6 篇会讲前缀缓存，而压缩会改变前缀。分析压缩对缓存命中率的影响，并给出减少损失的策略。

## L9 仍未解决（这一篇自己的缺陷）

| 缺陷 | 后果 | 修法 | 当初为什么这么写 |
|---|---|---|---|
| token 估算有误差 | 阈值可能偏保守（触发过早）或偏激进（触发过晚） | 引入精确计数（代价是分词器依赖） | 估算是零成本的近似，误差由余量吸收 |
| 摘要质量只有代理指标 | 一段摘要可能在某个具体任务上失效而不被发现 | 在真实任务集上做回归（第 6 卷的实验方法） | 客观判据依赖"未来会问什么问题"，而那是未知的 |
| 保留策略是固定四项 | 某些任务的"重要内容"不在四项里 | 允许按任务类型配置保留策略 | 固定项覆盖了多数情形，可配置会让验证复杂 |
| 溢出文件没有配额 | 一次任务的溢出可能占满磁盘 | 引入总量上限与超标时的失败 | 本卷的任务规模下溢出总量有限 |
| 压缩不感知工具定义的变化 | 工具集变化被压缩掉之后，派生视图可能缺少说明 | 把工具变更事件纳入保留策略 | 本卷的工具集在会话内很少变化 |
| 没有跨会话的压缩 | 长期运行的会话需要人工归档 | 引入归档机制（第 5 卷的多会话会涉及） | 本卷的会话时长有限 |

第一条与第二条属于"度量手段不足"，第三条与第四条属于简化与缺失的能力，第五条属于"位置放错"（它本该在保留策略里被考虑），第六条属于边界。第二条值得特别注意：它意味着这一篇交付了一个无法完全验证的机制，而处理它的方式只有降低验证频率加固定抽样——这也是所有涉及模型生成质量的机制的共同处境。

### 问题升级练习

模糊问题：「我该怎么处理超长的上下文？」

升级后的精确问题：

> 处理超长上下文至少包含三件互相制约的事：触发（什么时候压）、替换（压成什么、保留什么）、以及可追溯（压缩之后能否回答"当时看到什么"）。

> 特别是：有没有哪一条判据，是**能在一次"压缩后重建"的演练里被验证的**？

提升点说明：原问题无法回答，因为"超长"没有边界。升级后的版本把它拆成三件具体的事，指出前两件的制约关系，并追加以一个更强的问题：哪一条判据能在压缩后重建的演练里验证。

## L11 系统影响回溯

回看第 0.5 节的三个连锁影响。

| 预判 | 本篇分析之后的结论 | 状态 |
|---|---|---|
| 压缩的合法性来自"它不丢信息" | 确认，并给出"追加模式可回退、改写模式不可回退"的可逆性分析 | 成立 |
| 溢出把上下文占用变成可管理的资源 | 确认，并补上"溢出文件的生命周期必须被分配"这一条 | 成立且更具体 |
| 摘要质量的不可验证性要求抽样加判据 | 确认，并给出"压缩时记录关键事实、事后抽样"的具体做法 | 成立 |

一处需要修正的预判：0.5.2 把 token 估算标为对 3.6 的强依赖，读完之后要把方向反过来看：本篇对 3.6 的依赖是双向的——3.6 需要用本篇的估算来度量成本，而本篇需要用 3.6 的观测来确定阈值。这种双向依赖在两篇之间是常见的，它的处理方式是先实现一个粗糙的版本（估算），再用观测去校准它，而不是等观测建立之后再实现压缩。

通向下一篇的桥。 本篇处理的是"内容太多"，而它留下了一个没有答案的问题：有些动作会开出一串进程与后台任务，而它们需要被管理。压缩与溢出都在当前进程内完成，而工具执行、外部命令、长时间任务会涉及子进程——它们的清理、取消与输出收集是另一类问题。

下一篇 `3.4 进程与后台作业` 处理这件事。它与本篇的连接点是溢出：子进程的输出同样可能很大，因此它需要本篇的溢出机制。而它带来的新问题是"进程树"——取消一个命令必须杀掉它的整棵子树，否则会留下孤儿进程，而这一点在单线程的代码里不会出现。

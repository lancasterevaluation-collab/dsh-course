## 本篇新词

守卫（guard） 指在动作真正执行之前判断它是否被允许的那一层。它挂在工具调用之前，因此它握有"这一次调用会做什么"的全部信息（工具名、参数、副作用等级），也就有条件做出判断。守卫是判断层，不是强制层——它决定放行与否，而它拦不住绕过它的调用。

审批（approval） 指把决定权交给人的那一步。它与守卫的区别在于决定权的位置：守卫按规则自动决定，审批需要人给一个答案。审批的关键参数不是"问不问"，而是问多少次——问得太频繁会让人开始不看内容就同意。

沙箱（sandbox） 指由系统能力限制部件行为的机制（进程隔离、文件系统视图、系统调用过滤）。它与守卫的差别是强制性的来源：守卫依赖"没有别的路径绕过它"，而沙箱依赖"即使绕过了也没有能力做"。第 2.2 篇把这条区分总结为"声明与强制必须配对"。

声明式约束（declared constraint） 指一个由部件自己声明的性质（例如"这个工具是只读的"）。它的可信度取决于声明者，而类型系统无法验证它——因此它是信任型契约（第 1.4 篇的概念）。

强制式约束（enforced constraint） 指由系统检查并阻止的行为。它与声明式的差别是它是可验证的：不是"我相信你没有写文件"，而是"你没有写文件的能力"。

最小权限（least privilege） 指一个部件只应获得完成它的任务所必需的能力，不多不少。Saltzer 与 Schroeder 把它列为保护机制设计的第一条原则，理由是任何多余的权限都会在某个部件被攻破或被写错时变成损失。

完全中介（complete mediation） 指每一次访问都要经过检查，而不是只在第一次检查之后记住结果。它的反例是"装载时检查一次，运行期不再检查"——而那正是权限被绕过的主要形式之一。

审批疲劳（approval fatigue） 指因为询问次数过多，用户开始不加阅读地同意。它的后果不是体验差，而是审批机制本身失效：同意这个动作不再意味着"用户看过并认可"。

这张图的关键线索在第三块：前两块决定"该不该拦"，第三块决定"拦不住时怎么办"。只有声明没有强制时，声明错误就没有救。只有强制没有声明时，所有操作会被一视同仁地限制而损害可用性——两者的配对是这一篇的核心结论。

### 0.1 一个具体的判断：连续审批十次之后

审批的失效不是从第一次询问开始的，而是从第 N 次开始的。一个有代表性的观察是：当同一个会话里连续出现十次以上的审批请求时，用户开始只看标题而不看参数——而那时"同意"这个动作已经不再表示"用户看过并认可"。

这个现象的解释不需要心理学：人的注意力是一种会被耗尽且在低价值任务上优先放弃的资源。因此审批机制的设计问题不是"要不要问"，而是"问哪一些才能让每一次询问都被真正阅读"。

它的处置方式有两条。第一条是按后果分级而非按类型分级：只有不可逆或离开本机的操作才逐次询问（第 2.2 篇的第三、四级），可逆的操作按"用户确认过这一类"批量放行。第二条是让询问本身携带更多决策信息：不仅说"要执行 `rm`"，还要说"它会删除这三个文件，它们不在版本控制里"——信息的价值决定了这次询问是否值得占用注意力。

### 0.2 本篇建立的三项判据

第一项用于判断一次调用该放行、询问还是拒绝：问它的副作用等级以及它是否越出当前会话的边界。等级来自工具声明（2.2 的四级），边界来自工作目录与权限预设。这条判据的实现形态是一张规则表，而表的每一行都要说明它防的是什么。

第二项用于判断询问是否值得：问"如果用户不看内容就点同意，会发生什么最坏的事"。如果答案是"不会有严重后果"，那么这次询问不该是逐次的，而应当被合并或按类批准。

第三项用于判断一处约束该用声明还是强制：问"如果声明是错的，会发生什么"。后果严重（数据损坏、越权访问、对外发送）就必须有强制层。后果轻微（输出格式不一致）可以用声明加校验。

### 0.3 十分钟练习：声明与强制的差别

下面这段代码用二十行说明为什么声明需要强制的配对。

```js
// 声明式：工具自己说它是只读的
const declaredReadonly = { name: 'read_file', sideEffect: 'readonly', run: async () => { /* 也可能写文件 */ } }

// 守卫按声明放行
function guardByDeclaration(tool) {
  return tool.sideEffect === 'readonly' ? 'allow' : 'ask'
}

// 强制式：给这次执行一个只读的文件系统视图
function guardByCapability(tool, fs) {
  return { decision: guardByDeclaration(tool), fs: tool.sideEffect === 'readonly' ? readonlyView(fs) : fs }
}
function readonlyView(fs) {
  return { readFile: fs.readFile, writeFile: () => { throw new Error('只读视图：写被拒绝') } }
}

const decision = guardByDeclaration(declaredReadonly)
console.log('按声明：', decision)                       // allow
try { guardByCapability(declaredReadonly, { readFile: async () => 'x', writeFile: async () => 'y' }).fs.writeFile() }
catch (e) { console.log('按强制：', e.message) }         // 只读视图：写被拒绝
```

第一次输出说明声明给出的结论是"放行"。第二次输出说明强制层让这个结论变成了安全的——即使声明是错的，写操作也没有能力发生。这就是"声明加限制能力"这条模式的实际形态。

> **面试视角**
> **高频问法**："你怎么保证一个工具不会越权？"
> **高分要点**：区分声明与强制——声明决定"问不问人"，强制决定"能不能做"；两者缺一都会留下缺口。只答"我在工具描述里声明了它是只读的"是最常见的欠缺。

### 0.5.3 三个连锁影响

第一，只有声明没有强制时，安全边界取决于实现者的诚实。 2.2 已经指出这一点：声明为只读的工具如果偷偷写文件，守卫会照样放行。这条连锁的后果在引入外部工具（第 5 卷的 MCP）或自生成的部件（第 4 卷的演化）时变得严重——那些部件的作者可能不是同一个人，而"相信声明"在这个前提下不成立。

第二，审批的有效性取决于它的频率，而频率取决于规则的粒度。 规则太粗（所有写操作都问）会产生疲劳，规则太细（逐条判断）会让规则表本身难以维护。这条连锁给出了一条设计判据：规则的粒度应当与"用户能在一次阅读中判断清楚"的复杂度对齐——要求用户理解三条以上的参数才能决定的询问，通常说明规则该由系统自己决定。

第三，沙箱的强度与实现成本成反比，而选择它们需要知道威胁模型。 进程内的检查最便宜（同样能拦住无意的越权），容器次之，虚拟机最贵。这条连锁的结论不是"越强越好"，而是强度应当与部件的可信度匹配：同一个人写的部件用声明加轻量检查足够，外部部件需要进程或容器级隔离。混淆两者会在两个方向上都浪费——对可信部件过度隔离（性能与开发成本），对不可信部件隔离不足（真实的安全缺口）。

### 0.5.4 它与本书其余部分的关系

本篇的沙箱只讨论到"需要什么强度"的判断，具体的进程与文件系统隔离在第 3.4 篇与第 5 卷展开。这个边界的意义在于：本篇的产出是判断与规则，而不是隔离的实现——后者依赖操作系统能力，而它的取舍（性能、可移植性、调试难度）需要单独讨论。

> **面试视角**
> **高频问法**："你怎么让一个不可信的代码执行得安全？"
> **高分要点**：先问威胁模型（它可能做什么、最坏后果是什么），再选隔离强度（进程、容器、虚拟机），并指出"沙箱不是万能的"——它限制能力，但不限制资源消耗与信息泄露。

## L0 要解决的问题

### 0.1 现象一：声明与实现不一致，而没有任何机制发现

第一个现象是第 2.2 篇那个发现的展开。一个工具声明自己是只读的，而它的实现里写了文件。守卫按声明放行，于是那次写没有经过任何询问。这个缺口的性质是声明的可信度无法被验证：判断"一个函数会不会写文件"需要跨过程分析，而结论还依赖运行时的参数。

它的后果在工具来源不可信时变成安全问题。在本课程里，工具的来源会随着两处扩展而变宽：第 5 卷接入外部工具（MCP），第 4 卷允许系统演化出自己的部件。当作者不是同一个人时，"相信声明"这个前提不成立，而此时唯一的补救是限制能力。

### 0.2 现象二：审批太频繁，用户开始不看内容

第二个现象在 0.1 的练习里已经量化过。它的危害不是体验，而是审批机制的失效：当用户在第 N 次询问时不再阅读内容，那次"同意"就不再具有授权意义，而系统的安全假设（"危险操作都经过人确认"）因此不再成立。

这个现象的一个具体形态是"询问的粒度与用户能判断的复杂度不匹配"。如果一次询问要求用户理解三个参数之间的相互作用才能决定，而它出现在一次长任务的中间，那么用户实际上无法做出有效判断——他会同意，因为没有别的选择。

处置方式有两条，都在 0.1 的分析里给出了：按后果分级（只有不可逆与对外操作逐次问），以及让询问携带更多决策信息（说清后果而不只是动作）。

### 0.3 现象三：守卫拦下了调用，而模型的下一次请求被拒

第三个现象是这一篇与 2.7 的连接点。守卫拦下一次工具调用时，如果它只是"跳过这次调用"，那么消息序列里会少一条对应的工具结果，而模型的下一轮请求会因为序列不合法被拒。一个安全机制因此变成了功能故障，而它的表现（请求被拒）与原因（某次调用被拦下）之间隔着一层。

修法在 2.7 已经给出：拦截同样走那个产出结果的唯一出口，只是结果的 `ok` 为假、内容说明被拦下的原因。这里的补充是被拦下的调用必须让模型看到原因——否则它会重复尝试同一个被拒绝的操作，而它不知道为什么不行。

### 0.4 现象四：权限只在装载时检查过一次

第四个现象是"完全中介"这条原则的反面。一种常见的实现是在装配阶段检查一次"这个模式允许哪些工具"，然后在运行期不再检查。它在配置不变时是正确的，而在配置运行期变化时失效：模式切换、权限预设调整、或者某个工具的可用集因为其他原因变化，都会让装载时的结论过期。

这条原则的表述很简单：每一次访问都要经过检查。它的实现代价是每次调用多一次判断，收益是授权状态与实际状态始终一致。

### 0.5 这一篇要正面回答的四个问题

第一，一次调用该放行、询问还是拒绝（1.1、1.2）。第二，询问的节奏怎么定，多少算频繁（1.3）。第三，声明不可信时用什么兜底（1.4、1.7）。第四，拦截如何与 2.7 的配对约束共存（1.5）。

四个问题里第一与第二是判断，第三与第四是实现约束。判断的部分决定了系统的可用性，约束的部分决定了它的正确性——两者缺一都会让这一层要么形同虚设，要么处处阻塞。

## L1 设计与原理

### 1.1 三个决策

守卫对每一次工具调用给出三个决策之一：放行、询问、拒绝。

| 决策 | 依据 | 例子 |
|---|---|---|
| 放行 | 副作用等级为只读或可逆，且未越界 | 读工作区内的文件 |
| 询问 | 副作用等级为不可逆或对外 | 删除文件、推送远端 |
| 拒绝 | 越出当前会话的边界，或规则明确禁止 | 访问工作目录之外的路径 |

三个决策的排序不是随意的：先判断越界（拒绝），再判断危险程度（询问或放行）。理由是否决类的判断应当优先——一个越界的操作即使副作用等级是"可逆"，也不该被放行，因为"可逆"的前提（撤销只需删掉自己写的东西）在边界之外不成立。

三个决策对应的动作也不同。放行是继续，拒绝是立刻产出失败结果，而询问是暂停并等待一个答案——后者引入了异步与超时，因此它有额外的复杂度（1.3）。

### 1.2 规则表的设计

规则表的每一行由三部分组成：匹配条件（工具名、副作用等级、参数特征）、决策、以及它防的是什么。第三部分是这张表与一堆 if 的差别：写不出"防什么"的规则通常是凭感觉加的，而它们会累积成审批疲劳的来源。

条件的设计有一条原则：能由工具声明提供的信息优先（副作用等级、是否幂等），参数特征次之（路径是否在工作区内、命令是否在白名单里），而不要试图从参数内容推断意图（例如"这个命令看起来像删除"）。后者的维护成本高且误判率高——判据是"这个判断能不能被一条规则稳定复现"。本课程的规则表只用前两类条件。

拒绝类的规则需要额外说明：它必须有明确的错误信息，说明拒绝的原因与出路。一条"操作被拒绝"而没有原因的信息会让模型反复尝试，而"路径越出工作目录，请使用工作目录内的路径"能让它立刻换一条路。

### 1.3 审批的节奏与疲劳阈值

审批的两个参数是粒度与呈现。粒度决定问多少次，呈现决定每次询问能携带多少决策信息。

粒度的选择依据是后果：逐次询问只用于不可逆与对外操作（2.2 的第三、四级）。可逆操作按"用户已经批准过这一类"批量放行，而批准的有效期应当是本次会话。这条划分把询问次数从"与操作数成正比"降到"与种类数成正比"，而那正是避免疲劳的关键。

呈现的设计有一个判据：用户能否在一次阅读之后作出决定。实现形态是把询问的信息组织成"要做什么、影响什么、有没有替代方案"三段，而不是罗列参数。这条判据与第 2.2 篇的"给模型看的描述"是同一条原则的不同应用。

超时是审批的第三个参数。等待一个可能永远不来的答案会让任务挂住，因此需要超时。而超时后的默认动作必须是拒绝而不是放行（故障安全默认）。理由是超时意味着没有人做出决定，而在没有人决定时采取更保守的动作是唯一合理的默认。

### 1.4 声明与强制的配对

这一节是本篇的核心结论。声明与强制各自解决一半问题。

| | 声明式 | 强制式 |
|---|---|---|
| 回答的问题 | 这个操作危险吗（决定问不问人） | 这个操作能不能做（决定能否发生） |
| 可信度 | 取决于声明者 | 不依赖声明者 |
| 成本 | 低（一个字段） | 高（需要系统能力） |
| 失效方式 | 声明错误时静默放行 | 过度限制时损害可用性 |

配对的方式是用声明决定策略、用强制兜住声明错误：只读工具在只读视图下执行，于是即使它想写也没有能力写。代价是每次执行都要构造一次受限环境，收益是把"相信声明"变成"即使声明错了也没事"。

它的适用条件需要说清：只有当系统能控制那条承诺涉及的能力时，强制才可能。文件系统可以（只读视图、受限挂载），网络可以（不提供客户端），而"这个函数不会读全局变量"这类承诺无法被强制。因此配对不是万能的——对无法强制的那部分，只能依靠代码评审与最小权限。

### 1.5 拦截与配对

守卫拦下一次调用时，它必须产出一条工具结果，这条约束来自 2.7 的消息格式要求。实现方式是让拦截走与正常执行相同的出口（2.7 的 1.2 节那个 `toToolMessage`）。

两处细节值得说清。第一，被拦下的调用的结果也进入日志（2.7 的可重建不变量）。不记录的后果是重建出的消息序列缺少这条结果，于是重建失败——一个安全机制的日志缺失会让历史无法重建。第二，被拦下的原因要写在结果内容里，否则模型会重复尝试。

为了说明第 2.2 篇那条"失败要有可处置的信息"在这里的作用，可以对比两种文本："操作被拒绝"与"删除操作需要用户确认，而当前会话未授权删除。如果要继续，请在界面上确认"。后者的长度只是前者的两倍，而它把一次无用的重试变成了一次可能的继续。

### 1.6 最小权限与完全中介

最小权限的实践形态是默认拒绝加按需授予：会话开始时没有额外权限，需要时逐项授予，而每一项授权都有明确的适用范围与有效期。它的反面是"默认全给、出问题再收紧"，而后者的代价在权限被误用时才显现。

完全中介的实践形态是每次调用都过守卫。它的成本很低（一次规则匹配），而它防的是"授权状态与装载时不一致"这一类问题。它的一个推论是守卫不能有跨调用的缓存，或者说缓存必须有失效机制——缓存"这次工具已授权"在配置变化时就会过期。

两条原则共同给出一个无状态的守卫：输入是当前调用与当前权限状态，输出是决策，不保存任何跨调用状态。这条性质让它的行为可预测，也让它的测试简单。

### 1.7 沙箱强度的选择

沙箱的强度有三档，选择依据是部件的可信度与它可能造成的最坏后果。

| 强度 | 手段 | 成本 | 适用 |
|---|---|---|---|
| 进程内检查 | 受限的接口（只提供只读的文件视图） | 低 | 同一作者写的部件 |
| 进程隔离 | 子进程加受限的文件系统视图与网络 | 中 | 外部工具、可执行的用户输入 |
| 容器或虚拟机 | 命名空间、系统调用过滤、独立内核 | 高 | 完全不可信的代码 |

三档的共同点是它们都限制能力而不是检查行为。差别在细节：进程内检查依赖"没有别的路径绕过"，进程隔离依赖操作系统的进程边界，容器依赖内核的命名空间与过滤。

选择依据的表述是"最坏后果"而不是"可能性"：一个只会读文件的工具即使被写错，最坏后果是读到了不该读的内容。而一个能执行任意命令的工具被写错时，最坏后果无法估计。因此后者的隔离强度要求更高，即使它通常不会出问题。

### 1.8 两次追问

工程侧的问题是什么时候该把一次授权做成永久的。答案与可逆性有关：可逆操作的授权可以在会话内有效，因为它最坏的结果是会话内的数据变化。而不可逆操作的授权不应当被记住，因为一次错误的记忆会让后续每一次同类操作都越过检查。这条选择把"记住授权"这个便利限制在了后果可控的范围内。

产品侧的问题是权限预设会成为什么。第 5 卷的权限预设是这个方向上的产品形态：用户一次性表达"这个会话允许做什么"，此后同类操作不再询问。它的价值是把审批从逐次降到一次，而它的风险是把误配的后果放大。因此预设设计需要两个补充：预设本身要能被读懂（它列出了允许什么），以及它的生效要有可见提示（用户应当知道当前会话处在哪个预设下）。

### 1.9 守卫的可观测性

守卫与审批的行为如果不被度量，它的有效性就只能靠感觉。三个指标覆盖全部判断。

第一个是审批次数与会话时长的比。它是审批疲劳的直接度量：如果一次十分钟的任务出现二十次审批，那么它已经越过了"用户会阅读"的阈值（0.1 的分析）。这个指标的处置不是"少问"，而是检查规则粒度是否按后果分级。

第二个是拒绝率与它的原因分布。拒绝率突然上升通常意味着两类事：模型开始尝试越界的操作（提示词问题），或者权限预设变了（配置问题）。两者都值得看具体原因，而原因分布能立刻区分它们。

第三个是按规则分组的命中次数。它让"哪条规则真的在用"可见——长期零命中的规则是候选的删除对象，而它同时是审批疲劳的潜在来源（如果它是一条询问规则）。规则表的腐化通常从这个指标开始被发现：一条写在半年后的规则仍然在，而它防的那类操作已经不存在了。

三个指标的共同点是它们都回答"这一层是在保护什么，代价是多少"。守卫是最容易变成纯负担的一层——它增加了延迟与交互，而如果它的规则不再准确，那么它带来的只有成本。

### 1.10 审批的用户体验设计

三段式呈现（1.3）是内容层面的设计，而审批还有三个交互层面的问题。

第一个是默认选项的位置。默认应当是不批准，而这要求界面把"拒绝"作为默认聚焦项——因为默认项会被大量接受（用户按回车就过去了），把"批准"设为默认等于变相降低门槛。这条与超时默认拒绝是同一条原则的两种形态。

第二个是批量批准的范围。1.3 给出了"按类批准"的机制，而它的范围需要设计：一次批准是否覆盖同类的所有后续操作（本课程的选择）、还是只覆盖接下来的 N 次、还是只覆盖本次任务。范围越大越省事，而误配的后果也越大——本课程的选择是"本次会话内的同类操作"，因为会话是最容易理解的边界。

第三个是已批准事项的可见性。用户应当能随时看到"这个会话里我已经批准过哪些类别"，否则他会记得一个模糊的感觉（"我好像同意过什么"），而无法判断当前的操作是否在已批准的范围内。这条与 2.7 的"可查询"是同一条原则：系统的状态应当能被查出来，而不是靠记忆。

三个问题的共同形态是把安全决策的成本放在用户能理解的位置上。审批的本质是一次决策委托，而委托的有效性取决于委托人是否理解他在委托什么。

### 关于第 6 条的完整论证（声明与强制为什么必须配对）

替代方案有两种，各自的失败方式不同。

只有声明时，安全边界等于实现者的诚实。这个前提在同一作者的单一项目里勉强成立，而在两种情形下崩溃：外部工具（来源不可控）、自生成的部件（正确性不可保证）。它的表现形式是"我们没有做错什么，但系统被越权了"——因为越权发生在声明的边缘，而没有任何机制检查那里。

只有强制时，可用性会被过度限制。系统的强制能力是粗粒度的（文件系统只有读写两档，网络只有通或不通），而工具的实际需要是细粒度的（这个工具只需要读这三个文件）。于是强制层要么限制得比需要更严（工具做不了它该做的事），要么放开得比安全更宽（等于没限制）。它的表现形式是"我们很安全，但什么都做不了"。

配对之所以有效，是因为两者覆盖了对方的缺口：声明提供细粒度的意图（这个工具只需要读），强制提供一个粗粒度的兜底（读之外的操作无法发生）。声明错了，强制还在。强制太粗，声明让放行的范围更精确。这条模式的成本是一次额外的环境构造，而它的收益是让"相信声明"这个前提变得不必要。

### 关于第 5 条的完整论证（授权为什么不该被永久记住）

替代方案是把授权记在用户的账户上（"这个用户已经批准过删除工作区文件"），此后不再询问。它的吸引力很明显：一次授权换永久便利。

它的代价在三种情形下显现。第一，误配会被放大：用户在某个语境下批准了一个操作，而这个批准被应用到完全不同的语境（另一个项目、另一个会话、更危险的目录）。第二，用户忘记自己批准过什么：当系统不再询问时，用户失去了对操作的感知，而"我批准过它"这个事实在需要时已经记不起来。第三，授权的语境消失：当时批准的理由（"因为是测试数据"）在下一个语境里不成立，而系统无法区分。

会话内有效的方案避免了这三条，代价是每个会话都要重新授权。缓和这条代价的方式是让重新授权变快（默认预设、一次点击批准一类操作），而不是让授权变永久。这条取舍的一般形式是：把便利放在"更快地重新决定"上，而不是放在"不必再决定"上——因为后者的安全假设更难被用户理解。

## L3 实现（施工图）

### 3.1 文件结构

```
// plugins/guard.ts
// ┌─ 规则段 ──────────────────────────────────────────
// │  GuardRule：条件、决策、防什么
// ├─ 判定段 ──────────────────────────────────────────
// │  decide(call, permissions)：越界 → 危险程度 → 决策
// ├─ 审批段 ──────────────────────────────────────────
// │  ask(request, timeoutMs)：三段式询问，超时即拒绝
// ├─ 限制段 ──────────────────────────────────────────
// │  restrict(tool, ctx)：按副作用等级构造受限的上下文
// └─ 挂载段 ───────────────────────────────────────────
//    on('tool/before')：瀑布型，拦截时产出结果并终止
```

五段里第四段是与沙箱对接的入口，而它在本篇只做最小实现（只读视图）。完整的进程与容器隔离在第 3.4 篇与第 5 卷展开。

### 3.2 判定段

```ts
export function decide(call: ToolCall, tool: ToolDefinition, perms: Permissions): Decision {
  if (!resolveInside(perms.workspace, pathOf(call))) return { kind: 'deny', reason: '路径越出工作目录' }
  const level = resolveSideEffect(tool)                    // 2.2 的四级，缺省为最保守
  if (level === 'readonly' || level === 'reversible') return { kind: 'allow' }
  if (perms.approved.has(level)) return { kind: 'allow' }   // 本会话内已批准过这一类
  return { kind: 'ask', level }
}
```

这段实现的四个要点对应前四节：越界优先（1.1）、等级来自声明且缺省保守（2.2）、已批准按类放行（1.3）、询问携带等级（用于呈现）。

### 3.3 审批段与三段式呈现

```ts
export async function ask(req: ApprovalRequest, timeoutMs: number): Promise<boolean> {
  const answer = await Promise.race([req.present(threePart(req)), sleep(timeoutMs).then(() => null)])
  return answer === true                                  // 超时（null）即拒绝
}
function threePart(req: ApprovalRequest): string {
  return [`要做什么：${req.action}`, `影响什么：${req.impact}`, `有没有替代：${req.alternative ?? '无'}`].join('\n')
}
```

`Promise.race` 的返回值设计值得注意：超时返回 `null`，而判断写成 `answer === true` —— 这样任何非 `true` 的返回值（超时、异常、未响应）都落到"拒绝"，符合 1.3 的故障安全默认。

### 3.4 限制段

```ts
export function restrict(tool: ToolDefinition, ctx: ToolContext): ToolContext {
  const level = resolveSideEffect(tool)
  if (level !== 'readonly') return ctx                    // 非只读不缩减能力（由审批把关）
  return { ...ctx, fs: readonlyView(ctx.fs) }             // 只读工具拿到只读视图
}
```

这里的选择值得说明：只对只读工具做能力缩减。理由是更激进的缩减（对所有工具都给最小能力）需要知道每个工具真正需要什么，而那需要工具声明它的能力需求——本课程没有引入这条声明，因此采用"只兜住最危险的那一类误声明"这个折中。

### 3.5 挂载段

```ts
export function guardPlugin(ctx: Context, perms: Permissions) {
  return ctx.on('tool/before', async (call, next) => {
    const d = decide(call, ctx.tools.get(call.name), perms)
    if (d.kind === 'allow') return next(call)
    if (d.kind === 'deny') return failTurn(call, d.reason)              // 产出失败结果
    const ok = await ask({ /* ... */ }, perms.approvalTimeoutMs)
    if (!ok) return failTurn(call, `未获授权：${d.level} 操作需要确认`)
    perms.approved.add(d.level)                                         // 本会话内记住这一类
    return next(call)
  })
}
```

三个要点。第一，`failTurn` 是"拦截也产出结果"的落点（1.5），它同时写入日志。第二，批准被记在 `perms` 里而不是插件内部状态——权限状态属于会话（2.5 的作用域），插件只是使用它。第三，插件返回 `ctx.on` 的撤销函数，卸载即关闭守卫。

| # | 判据 | 怎么检查 |
|---|---|---|
| 1 | 越界路径被拒绝 | 传一个 `../` 路径，核对决策为拒绝 |
| 2 | 只读工具被放行 | 传一个 readonly 工具，核对放行 |
| 3 | 不可逆工具触发询问 | 传一个 irreversible 工具（未批准），核对决策为询问 |
| 4 | 已批准的等级不再询问 | 批准后再次调用同类工具，核对放行 |
| 5 | 授权不跨会话 | 新建作用域后同类操作重新询问 |
| 6 | 审批超时即拒绝 | 让审批不返回，核对最终拒绝且任务失败可解释 |
| 7 | 拦截产出结果并写入日志 | 拒绝一次调用，核对消息里有对应结果且日志有记录 |
| 8 | 拦截的错误信息含原因与出路 | 核对结果内容里有原因与建议 |
| 9 | 只读工具拿到只读视图 | 让只读工具尝试写，核对被拒绝 |
| 10 | 每次调用都过守卫 | 连续两次调用之间切换权限，核对第二次的决策跟随新权限 |
| 11 | 卸载插件后不再拦截 | 卸载后调用越界路径，核对不再拒绝 |
| 12 | 守卫无状态 | 同一个调用在同样权限下两次判定结果相同 |

第 5 与第 10 条是最容易漏的两条：前者检验授权的作用域，后者检验完全中介。它们都可以通过构造"状态变化"的用例来检查。

### 3.7 实现顺序

先做判定与规则（判据 1、2、3、12），再做审批（判据 4、5、6），然后做挂载与配对（判据 7、8），接着做限制段（判据 9），最后检查完全中介与卸载（判据 10、11）。

---

### 3.8 实现里最容易写错的三处

第一处是越界判定的路径解析。正确做法是先把路径解析成绝对路径再比较（2.2 的 `resolveInside`），并且比较时带分隔符。常见错误是直接对字符串做前缀比较，于是 `/work-evil` 被当成在 `/work` 之内。这个缺陷在 2.2 已经出现过一次，而它在守卫里的后果比在工具里更严重——守卫是唯一的拦截点。

第二处是超时的默认动作。正确做法是把任何非明确的同意都落到拒绝（3.3 那段 `answer === true` 的写法）。常见错误是写成"超时即放行"或者"超时抛出异常并让调用方决定"，而后者会让调用方在各处重复判断默认值。

第三处是拦截的日志写入。正确做法是拦截时也追加一条 `session/tool-result` 事件。常见错误是只在返回值里体现拒绝而没有写日志，于是内存中的消息序列看起来合法（因为失败结果被构造了），而从日志重建时却缺了那一条——这个缺陷在正常运行时不出现，只在恢复时暴露。

三处的共同形态是"错误做法在正常路径下完全可用，而它在异常路径或重建路径下失效"。这也是本卷负向验证脚本要覆盖的三类变体。

### 5.3 三条容易踩的规则

第一条，拦截必须产出结果并写入日志。跳过调用会让消息序列不合法，也会让历史无法重建。

第二条，超时的默认动作是拒绝。任何非明确的同意都应当落到拒绝。

第三条，授权的作用域是会话。把它做成永久会让误配的后果被放大。

## L9 仍未解决（这一篇自己的缺陷）

| 缺陷 | 后果 | 修法 | 当初为什么这么写 |
|---|---|---|---|
| 强制层只做到只读视图 | 一个声明为可逆却实际删除文件的工具不会被挡住 | 按副作用等级构造更多受限上下文，或引入进程隔离（3.4） | 完整的隔离依赖操作系统能力，本卷只做最小实现 |

| 没有对抗"声明与实现不一致"的检测 | 声明错了只能靠强制兜底，不能被发现 | 声明与行为的对照检查（例如静态扫描写操作） | 静态判断需要跨过程分析 |
| 授权粒度只有四级 | 同一个等级里的操作危险程度可能不同 | 引入更细的授权（按工具、按路径前缀） | 四级在本卷的操作数量下够用 |
| 没有审批的审计记录 | 无法回答"用户批准过什么" | 把审批与结果一起写入日志（现在只记结果） | 结果里含"被拒绝"的原因，而那已经能回答多数问题 |

第一条与第四条属于"位置放错"——它们本该由更强的隔离与检测机制承担，而本篇只做了判断与最小兜底。第二条与第五条属于简化。第三条与第六条属于能力缺失。第一条值得单独标记：它意味着本篇的安全边界在"声明为可逆而实际不可逆"这一类上是不成立的，而这类误声明比"只读却写文件"更难被发现。

### 五种提问模板

边界追问：一次操作危险到什么程度才值得逐次询问。

代价追问：把授权做成永久，代价落在谁身上、什么时候暴露。

替代对比：为什么用声明加强制而不是只做强制。

验证追问：怎么证明"一次错误的声明不会造成越权"。

### 本篇引出的十二个问题

读懂层。 第一，守卫与沙箱的分工是什么？第二，三个决策的排序为什么是越界优先？第三，审批的三个参数是什么？

设计层。 第七，声明与强制为什么必须配对？第八，沙箱强度依据什么选？第九，授权的有效期为什么是会话？

评审层。 第十，拿到一份权限方案，你会先检查哪一处？第十一，怎么判断一处审批会产生疲劳？第十二，如果有人说"工具都是自己写的，不需要沙箱"，你怎么回应？

### 问题升级练习

模糊问题：「我该怎么让 agent 不去做危险的事？」

升级后的精确问题：

> 约束 agent 至少包含三件互相制约的事：判断（哪些操作需要放行、询问或拒绝）、节奏（问多少次才不会让审批失效）、以及兜底（声明不可信时靠什么限制能力）。
> 第一件与第二件互相制约——判断做得越细，询问次数越多，而询问过多会让判断本身失效。
> 我能不能为这三件事各找出一条**可检查的判据**？
> 特别是：有没有哪一条判据，是**能用一次"错误声明"的演练来验证的**？

提升点说明：原问题无法回答，因为"危险"没有边界。升级后的版本把它拆成三件具体的事，指出前两件的制约关系，并追加以一个更强的问题：哪一条判据能在错误声明的演练里验证。

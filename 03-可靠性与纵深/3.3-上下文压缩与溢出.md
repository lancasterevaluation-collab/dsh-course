## 一、为什么需要压缩

### 1.1 撞上窗口上限，任务直接失败

一段 50 轮的对话跑到第 40 轮，请求被拒：上下文超长。任务没完成，重来一次又要重做前面 39 轮的工作。

### 1.2 一次大输出挤掉后面所有空间

某个工具读进来一个 5 万 token 的日志文件。此后每一次请求都带着它。按每轮新增 2000 token 算，**这一条输出挤掉了 25 轮的对话空间**——后面 25 轮里模型再也看不到新信息。

### 1.3 账单里一半是重复内容

多轮对话每轮都要把全部历史重发一遍。50 轮下来，同一段历史被计费了几十次。**压缩不只是为了"装得下"，也是为了"不重复付钱"。**

这三种失败指向同一个事实：**上下文是有限的，历史是无限的**。压缩就是处理这个矛盾的手段。

## 二、压缩是什么：切、摘、记

一次压缩只做三件事：

1. **切**：决定哪一段被压掉、哪一段保留原样。
2. **摘**：把被切走的那段换成一段更短的摘要。
3. **记**：留下一条"这里压缩过"的记录（摘要内容、被压的区间、压缩前后长度）。

第三步最容易被省掉，而它决定了压缩是否**可归因**。

### 走一遍完整例子

设上下文预算 10000 token，触发线 0.75，保留尾部 4000 token。

| 步骤 | 数字 |
|---|---|
| 当前已用 | 7800 token |
| 是否触发 | 是（7800 ≥ 7500） |
| 保留 | 尾部 4000 token 原样留下 |
| 压缩 | 前面 3800 token 换成 600 token 摘要 |
| 压缩后 | 4000 + 600 = 4600 token |
| 记录 | 一条压缩事件：区间、前后长度、摘要原文 |

从 7800 降到 4600，换来约 3200 token 余量。

## 三、怎么做

四步，顺序不能颠倒：先决定切在哪里，再生成摘要。反过来先摘要再切，摘要不知道自己该覆盖到哪里。

### 3.1 触发：用线，不用上限

判断只有一行。

```js
// 触发判断：按触发线启动，而不是等撞上窗口上限
export function shouldCompress(used, budget, trigger = 0.75) {
  return used >= budget * trigger
}
```

为什么是 0.75 而不是 1.0：压缩本身要做一次模型调用（生成摘要），那次调用也要占预算。等用满了再压，摘要那一次的输入本身就已经超了。

这条规则可以推广到所有"需要额外一次调用来收拾残局"的机制：**永远给收拾动作留出预算**。

### 3.2 切点：不能拆开调用与结果

保留策略是从尾部往前数够 N 个 token。但按 token 数算出的位置经常**正好落在一个工具调用和它的结果之间**——那样模型会看到"调用了一个工具，但没有结果"，下一步行为不可预测。

所以要多一步回退。

```js
// 找压缩点：从尾部向前累计，再回退到配对边界
export function findCompressionPoint(messages, keepTokens) {
  let acc = 0
  let i = messages.length
  while (i > 0) {
    acc += messages[i - 1].tokens
    if (acc >= keepTokens) break
    i--
  }
  // 向前回退到最近的配对边界，避免拆开"调用 + 结果"
  while (i > 0 && messages[i - 1].kind === 'tool-call') i--
  return i
}
```

回退的含义：宁可多压一点，也不要制造不完整的回合。判定标准是——保留区间里不能出现孤立的调用或孤立的结果。

### 3.3 摘要：追加，不改写

压缩事件的形状如下。

```js
// 压缩事件：追加式记录，不修改任何已有事件
export function compressionEvent(messages, from, to, summary) {
  return {
    kind: 'compression',
    range: [from, to],                 // 被压的是哪一段
    beforeTokens: messages.slice(from, to).reduce((n, m) => n + m.tokens, 0),
    afterTokens: summary.tokens,
    summary: summary.text,
    origin: from,                      // 派生起点：此前的内容仍可从日志取回
  }
}
```

三种做法的差别，决定了能不能回答"当时看到了什么"：

| 做法 | 结果 |
|---|---|
| 用摘要**替换**原始消息 | 日志变小，原始内容永久消失 |
| 只把摘要放在**内存**里 | 重放时算不出同样的摘要，同一份历史在不同时间呈现不同 |
| **追加一条压缩事件** | 原始事件全部保留，派生视图从最后一个压缩点往后算 |

摘要要写成什么：不要写成"用户讨论了配置问题"，要写成**能被后续步骤直接使用的状态**——改了什么文件、做了什么决定、还有什么没做。一条判据是：**把它交给人接手，他能不能继续任务。** 做不到就是摘要太粗。

### 3.4 外置：把大块搬走，留指针

一条消息本身就超过预算的四分之一时，压缩它没有意义（压完还是很大）。这时把内容搬到外部存储，原地留一个指针。

```js
// 溢出：超单条上限就外置，改用指针。与压缩不同，这一步完全可逆
export function spill(message, budget, singleLimit = 0.25) {
  if (message.tokens <= budget * singleLimit) return { message, spilled: false }
  return {
    message: { kind: 'pointer', ref: message.id, tokens: 20, preview: message.content.slice(0, 200) },
    spilled: true,
  }
}
```

预览不是装饰：它让模型知道被移走的是什么，从而能判断要不要取回。没有预览的指针等于"内容消失了"。

外置与压缩的区别要记牢：**外置可逆**（按 ref 取回原文），**压缩不可逆**（摘要替代了原文的推理作用）。

## 四、特殊情况与处理技巧

| 情况 | 表现 | 处理 |
|---|---|---|
| 压缩拆开了工具配对 | 模型看到"调用了工具但没有结果" | 切点回退到回合边界（见 3.2） |
| 摘要丢了唯一约束 | 后续行为持续违反一条早期约定，且无任何报错 | 保留优先级：只出现过一次的信息优先留在保留区 |
| 摘要累积到失真 | 三次压缩后上界误差 15%，行为开始漂移 | 记录压缩次数，超过阈值时重建历史而不是继续叠摘要 |
| 压缩触发太晚 | 生成摘要的调用本身超预算 | 触发线取 0.75，给收拾动作留余量 |
| 单条消息过大 | 压缩后仍然超限 | 外置成指针（见 3.4），而不是反复压同一条 |
| 压缩后仍撞墙 | 保留区本身就超预算 | 检查保留区与预算的比例，必要时降低保留量 |
| 摘要生成失败 | 压缩这一步报错，而上下文已经超限 | 压缩要有降级路径：摘要失败时按"砍掉最旧的一段"降级，并记录降级事件 |

一条通用技巧：压缩是有损的，所以每次压缩都应当**尽量少丢**——先外置（可逆），再压缩（不可逆）。顺序反了，就先把可逆的手段浪费掉了。

## 五、工业界的做法（可照做）

这一节是可以直接照着实现的工程口径。

### 5.1 三层处理顺序：截断 → 外置 → 摘要

真实系统的第一步几乎都不是摘要，而是**在信息进上下文之前就不让它进来**。三层顺序如下：

| 层 | 做什么 | 何时用 | 代价 |
|---|---|---|---|
| **截断** | 工具结果只取前 N 行 / 前 N 字符，超出部分丢弃 | 常在"工具返回"这一步就做 | 信息直接丢失 |
| **外置** | 大结果写入文件或存储，上下文里只放指针 + 预览 | 结果可能之后还要看 | 需要一次取回调用 |
| **摘要** | 把旧历史换成摘要 | 前两层做完仍然超预算 | 不可逆，需模型调用 |

这个顺序的收益极大：一个 5 万 token 的日志，如果工具层就截断到 2 千 token，后面两层根本不用启动。**多数"上下文爆炸"问题，在工具设计阶段就能解决大半。**

### 5.2 真实产品怎么做

| 产品 | 做法 | 值得学的点 |
|---|---|---|
| **Claude Code** | 接近窗口上限时自动压缩（compaction），另提供手动 `/compact` | 压缩对用户**可见**且**可手动触发**。项目级约定放常驻文件而不是每轮重复 |
| **Cursor** | 先建代码库索引，按需检索相关片段，而不是把文件整篇塞进上下文 | "检索优先"把问题从"装得下"变成"找得准" |
| **ChatGPT** | 长对话的记忆与摘要分离：稳定事实进记忆，近期原文留在窗口 | 记忆与上下文是**两个不同层级**的存储 |
| **通用 agent 框架** | 每轮清理旧工具结果、限制单条工具输出大小、超限时压缩中间段 | 工具结果是最主要的膨胀来源，先管它 |

共同的模式：**先减少进入上下文的总量，再考虑压缩已经进去的内容。**

### 5.3 参数怎么定

| 参数 | 常见取值 | 依据 |
|---|---|---|
| 触发线 | 预算的 70%–80% | 要给"摘要那次调用"与"最后一轮输出"都留余量 |
| 保留区 | 预算的 30%–50% | 太短会丢掉近期上下文，太长则压不了多少 |
| 单条上限 | 预算的 20%–25% | 超过它的单条消息压缩没有收益，应外置 |
| 摘要目标长度 | 被压区间的 10%–20% | 压缩比低于 5:1 的话，不值得付出这次模型调用 |
| 累积压缩次数上限 | 3–5 次 | 超过后误差累积明显，应重建而不是再叠 |

这些不是"最优值"，而是**起点**：用你自己的数据测出压缩前后任务成功率，再调。

### 5.4 四个必须处理的工程细节

一、用户可见性。 压缩后模型会"忘记"早期内容。如果用户不知道发生过压缩，他会把"模型忘了"理解成"模型很笨"。做法是给用户一个提示（"较早的对话已被压缩"）与一个查看入口。

二、与缓存冲突。 提示缓存按**前缀**匹配。压缩改写了历史中段，会让整段前缀失效——**压缩省下的 token，可能被缓存失效的额外成本吃掉**。缓解办法：把稳定内容（系统提示、工具定义、项目约定）放在最前面，把变化内容放后面，压缩只动末尾之外的部分。

三、工具配对完整性。 见 3.2。这一条在真实系统里最容易出线上事故，因为它的失败表现为"模型行为诡异"而不是报错。

四、降级路径。 摘要生成失败时不能卡死。必须有"砍掉最旧的一段并记录降级事件"的兜底。

### 5.5 压缩本身的成本

压缩要调用一次模型，输入是被压区间、输出是摘要。按 7.5 的口径：

$$
\text{压缩成本} \approx n_{\text{压}} \cdot p_{\text{in}} + n_{\text{摘要}} \cdot p_{\text{out}}
$$

| 量 | 量级 |
|---|---|
| 被压区间 | 数千 token |
| 摘要输出 | 数百 token |
| 相对单轮对话 | 一次额外调用（约等于 1–3 轮正常对话） |
| 相对"任务重做一次" | 便宜几个数量级 |

结论：压缩的成本远低于"上下文超限导致任务失败"的代价。所以触发线宁可保守一点（早压），也不要等到撞墙。

但也不能压得太频繁：每次压缩都会丢信息，压十次和压三次的信息损失不是一个量级。**判据是压缩次数与累积误差，不是压缩成本。**

### 5.6 一份可落地的实施清单

按顺序做，每一步都能单独验证：

1. **工具层限流**：给每个工具的输出设最大 token，超出部分截断并标注"已截断"。
2. **结果外置**：超过单条上限的结果写入文件，上下文里放"指针 + 前 200 字符预览 + 取回方法"。
3. **每轮清理**：把不再需要的旧工具结果替换成一行摘要（"读了 util.js，已修改第 2 个函数"）。
4. **历史压缩**：实现本节的四步（触发 / 切点 / 摘要 / 事件），并把压缩事件写进会话日志。
5. **边界保护**：切点回退到回合边界，保证不出现孤立的工具调用或结果。
6. **观测**：记录每次压缩的区间、前后长度、摘要、累积次数。
7. **用户可见**：在界面上告知压缩发生，并提供查看被压内容与摘要的入口。
8. **降级**：摘要失败时按"丢弃最旧区间"降级，并记录降级事件。

## 六、学术界先进方案

上面讲的是**应用层**的做法（不动模型权重）。这一节讲**模型侧**的方案——它们不是替代关系，而是叠在下面的另一层。

### 6.1 不改权重：靠位置编码把窗口撑大

模型训练时的上下文长度（例如 4K）决定了它能"理解"多远的位置。想让它处理 32K，最省的办法是**改位置编码**：

| 方案 | 做法 | 特点 |
|---|---|---|
| **ALiBi** | 给注意力分数加上与距离成正比的惩罚，不给位置加嵌入 | 外推简单，但对长距离依赖的表达能力有限 |
| **RoPE 插值（PI）** | 把位置索引按比例压缩回训练时的范围 | 实现极简，短上下文能力会略微下降 |
| **YaRN** | 不同频率用不同的插值比例，并缩放注意力温度 | 效果更好，需要少量继续训练 |
| **LongRoPE** | 非均匀插值 + 渐进扩展，配合少量微调 | 可扩展到极长（百万级），代价是要调的位置因子多 |

这类方法的共同点：改的是"模型能看到多远"，**不改"看到之后怎么处理"**。

对你的意义：当有人说"我们模型支持 128K"，你要问的是**它在 128K 上还记得住吗**——这要靠 6.6 的评测来回答，而不是看标称数字。

### 6.2 改注意力：只让每个位置看一部分

标准注意力要算 $T^2$ 个关系（见 7.2）。稀疏化就是让每个位置只看一部分：

| 方案 | 做法 | 代价 |
|---|---|---|
| **滑动窗口** | 每个位置只看前后 $w$ 个 token | 跨越窗口的依赖会丢 |
| **StreamingLLM** | 保留最初几个 token 作为"注意力汇集点"+ 滑动窗口 | 流式生成稳定，但早期细节仍然丢失 |
| **局部 + 全局稀疏** | 多数位置局部，少数全局 token 连接所有位置 | 需要设计全局 token 的选法 |
| **状态空间模型** | 用递推状态替代注意力，复杂度降到线性 | 与现有生态不兼容，长距离精确检索能力偏弱 |

StreamingLLM 的观察值得记住：语言模型会把大量注意力"堆"在开头的几个 token 上（即使它们只是填充词）。因此**保留开头几个 token 就能让流式生成稳定**——这是工业界实现"无限长对话"的一个实用技巧。

### 6.3 压 KV cache：显存才是硬约束

7.5 算过：32K 上下文、32 层、32 头时，单请求 cache 就要 16 GiB。这一层的方案非常多：

| 方向 | 方案 | 做法 |
|---|---|---|
| **共享** | GQA / MQA | 多个 query 头共用一组 KV 头，直接按比例削减 cache |
| **低秩投影** | MLA | 把 KV 投影到低维潜空间，推理时再还原 |
| **量化** | KIVI / KVQuant 一类 | cache 用更低精度存储（4bit / 2bit） |
| **淘汰** | H2O / StreamingLLM 的缓存版本 | 丢掉"累计注意力权重低"的 token |
| **分页** | PagedAttention | 按块分配 cache，减少碎片、支持共享前缀 |

对你的意义：这些决定了**厂商能在什么价位提供多长的上下文**。你要判断的是"成本结构会不会变"，而不是自己实现它们。

### 6.4 应用层记忆：把一部分上下文搬出窗口

这一层与第五节直接相关，但更系统化：

| 方案 | 做法 | 适合 |
|---|---|---|
| **递归摘要** | 分段摘要，再对摘要摘要 | 长文本、流式对话 |
| **分层记忆（如 MemGPT）** | 主上下文 + 外部存储，模型通过函数调用自己"换页" | 需要长期记忆的助手 |
| **检索（RAG）** | 把历史或文档存进向量库，按需取回 | 知识量大且查询明确 |
| **结构化笔记** | 让模型把关键状态写进一个固定文件（进度、决定、待办） | 长程编码任务 |
| **工具结果外置** | 见 3.4 | 单条过大的情况 |

分层记忆的核心思想：**把"必须一直看到"和"需要时能查到"分开**。前者留在上下文，后者进存储。

这正是 5.1 三层顺序在更大尺度上的版本：**上下文是工作台，不是仓库。**

### 6.5 训练侧：长上下文继续预训练

要让模型**真的**会用长上下文，通常需要拿长文档继续预训练：

- **数据**：长文档、代码仓库、书籍
- **位置编码**：配合 6.1 的方法调整
- **注意力实现**：换成对长序列更高效的内核
- **成本**：按 7.3 的 $6ND$ 估算，长序列训练的成本随长度增长

对你的意义：这解释了"为什么长上下文能力提升得慢"——它不只是推理端的事，还要重训。

### 6.6 评测：怎么知道长上下文真的有用

| 基准 | 做法 | 局限 |
|---|---|---|
| **大海捞针（NIAH）** | 在长文本里埋一个事实，看模型能否找回 | 太简单，容易被针对优化 |
| **RULER** | 多任务（检索、聚合、追踪），可指定长度 | 更能反映真实能力 |
| **LongBench** | 多任务长文本理解（含中文） | 任务间的难度不均衡 |
| **Lost in the Middle** | 把关键信息放在不同位置，测位置敏感性 | 结论直观：**中间位置最容易丢** |

**"Lost in the Middle" 对你的直接启示**：模型对上下文**开头与结尾**的信息利用最好，中间最差。所以：

- **重要信息不要埋在中间**，要么放前面（常驻），要么放最后（近因）。
- **压缩时优先保留头尾**：这与 5.3 的"保留区"设计一致——保留尾部（近因），常驻部分保护头部。
- 压缩后如果必须保留一条关键约束，**把它重新放到保留区**，而不是指望它留在摘要里。

### 6.7 一张对照表：这些方案与你的关系

| 层次 | 谁负责 | 你能做什么 |
|---|---|---|
| 位置外推（6.1） | 模型厂商 | 选型时问"真实可用长度"，看 RULER 一类评测 |
| 注意力稀疏（6.2） | 模型厂商 | 了解"无限长对话"的实现原理与损失 |
| KV cache 压缩（6.3） | 模型厂商 / 推理框架 | 关心成本结构怎么变，据此做容量规划 |
| 长上下文训练（6.5） | 模型厂商 | 判断"等模型变强"是不是可行策略（见 7.3） |
| 长上下文评测（6.6） | 你 | **必须自己做**：用自己任务的数据测"多长开始变差" |
| 应用层压缩（第五、六.4 节） | **你** | 本节全部内容 |

最重要的一列是最右列：模型侧的进步会把"窗口"这条线往上推，但**你仍然需要应用层压缩**，因为——

1. **成本**：窗口再大，把全部历史塞进去也是最贵的用法（见 7.5 的成本结构）。
2. **注意力衰减**：窗口内有信息不代表模型用好信息（"Lost in the Middle"）。
3. **你自己的信息**：项目约定、工具结果、任务状态**只存在于你的系统里**，模型厂商无法替你组织。

## 七、理论：三条原理

**原理一：无损的高压缩率不存在。**
一段长历史要用一段短文本承载，必然丢信息。所以压缩的问题不是"怎么不丢"，而是"**丢哪些最不可惜**"——问题因此变成了保留优先级的排序。

**原理二：只出现一次的信息，丢掉就是不可逆的。**
一条约束只在早期说过一次，压缩掉它之后，后面所有行为都会违反它，而没有任何信号提示这件事发生过。判断依据是：**这条信息在保留区间里还有没有别的地方承载。**

**原理三：压缩必须留下痕迹。**
痕迹就是那条压缩事件。有了它，"模型当时为什么这么做"才能回答到"它看到的是摘要，摘要是这一段"。

累积效应：一次压缩丢 5% 的信息，三次之后上界是 15%（线性叠加）。所以压缩次数要记录——累积到一定程度该重建历史，而不是继续叠摘要。

## 八、工程化清单

| 项 | 内容 |
|---|---|
| 可配置项 | 触发线、保留量、单条上限、摘要模型——都不该硬编码 |
| 观测指标 | 压缩次数、每次压前后长度、摘要占比、累积误差估计 |
| 失败处置 | 摘要生成失败时的降级路径，以及降级事件的记录 |
| 与缓存的交互 | 压缩会打断前缀缓存，压缩点位置影响命中率 |

| 可测试性 | 切点、触发、外置三个函数都应当是纯函数，便于单独测 |
| 用户可见 | 压缩通知与查看入口 |
| 效果验证 | 压缩前后的任务成功率对比（按 7.6 的样本量与噪声口径） |

### 第一题：算出压缩点，并说出丢了什么

给下面这段会话（每条标了 token 数与类型），预算 2000，触发线 0.75，保留尾部 900 token。

```
1.  user        "重构 util.js 里的日期处理"          120
2.  assistant   tool-call: read_file(util.js)        60

4.  assistant   "这个文件有 3 个日期函数，我改第 2 个"   200
5.  user        "不要动 parseDate，线上在用"           40
6.  assistant   tool-call: edit_file(util.js)         60
7.  tool        "已修改"                              30
8.  user        "再跑一遍测试"                         30
9.  assistant   tool-call: run_tests                  40
10. tool        "3 passed"                            30
```

要求：

- 算出当前总 token 数，判断是否触发压缩。
- 算出压缩点在第几条（写出回退前后的位置）。
- 说出被压掉的区间里，哪一条信息一旦丢失会**不可逆**地影响后续行为。

提示：不可逆的判断依据是"这条信息在保留区间里还有没有别的地方承载"。

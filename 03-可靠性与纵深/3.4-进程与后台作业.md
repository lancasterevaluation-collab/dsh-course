## 一、为什么需要管进程

### 1.1 命令挂住，整个 agent 卡死

模型执行了一条会等待输入的命令（例如 `cat` 不带参数）。子进程在等 stdin，而 agent 在等子进程——双方无限期等待。

### 1.2 子进程变成了僵尸

父进程没有回收退出码。僵尸进程不占 CPU，但占用进程表项。跑几千次命令之后，系统拒绝创建新进程。

### 1.3 一个 20 分钟的任务绑住了整个会话

用户让 agent "跑完整测试并修复失败"。测试要 20 分钟。这 20 分钟里用户不能做别的事，也无法查看进度。

这三件事分别对应：**流的处理、生命周期的回收、以及长任务的运行方式。**

## 二、进程要处理什么

| 方面 | 要回答的问题 | 出错的表现 |
|---|---|---|
| 生命周期 | 什么时候算"结束了" | 僵尸 / 泄漏 |
| 三个流 | stdin / stdout / stderr 谁来读 | 卡死（见 3.3） |
| 退出信息 | 退出码、信号、被杀的原因 | 误判成功 |
| 时限 | 多久算超时 | 无限等待 |
| 归属 | 谁负责回收它 | 孤儿进程 |

核心认识：进程不是"一个函数调用"，而是一个**有状态的、可能不合作的、需要被回收的外部资源**。

## 三、怎么做

### 3.1 终止序列：先礼后兵

直接 `SIGKILL` 会丢掉子进程的清理机会（临时文件、锁、半写文件）。正确的顺序是三步：

```js
// 终止序列：先请求，再给宽限期，最后强制
export async function terminate(child, graceMs = 1000) {
  child.kill('SIGTERM')                    // 第一步：请求它自己退
  const exited = await waitFor(child, graceMs)  // 第二步：等宽限期
  if (!exited) {
    child.kill('SIGKILL')                  // 第三步：强制
    await waitFor(child, 1000)
  }
  return { code: child.exitCode, signal: child.signalCode }
}
```

算例实测：终止序列是 **3 步**——`SIGTERM → 等待 1000 ms → SIGKILL`。进程被信号终止后退出码是 `-1234`，信号是 `SIGKILL`。

宽限期的三种情形也算清楚了：

| 情形 | 结果 |
|---|---|
| 宽限期内退出 | `{kill: false, cleaned: true}` |
| 宽限期未到点 | `{kill: false, cleaned: true, waiting: true}` |
| 宽限期到点仍存活 | `{kill: true, cleaned: false}` |

第三种是必须处理的：它意味着你有一个不响应 SIGTERM 的进程，需要强制。**这类进程在真实系统里存在**（例如卡在不可中断的系统调用里的进程）。

### 3.2 状态机：六种状态与合法转移

作业的状态必须是一个**有明确转移规则的集合**，否则会出现"既成功又失败"这种状态。

```js
// 状态转移：终态不可离开
const TERMINAL = new Set(['succeeded', 'failed', 'killed'])
export function transition(current, event) {
  if (TERMINAL.has(current)) throw new Error(`终态 ${current} 不可再转移`)
  if (current === 'running' && event === 'restart') return 'unknown'
  if (current === 'running' && event === 'done') return 'succeeded'
  return current
}
```

算例实测：

| 起始 | 事件 | 结果 |
|---|---|---|
| running | restart | **unknown** |
| running | done | succeeded |
| 终态 | 任意 | **抛错拦截** |

**为什么 `restart` 后是 `unknown` 而不是 `failed`**：进程重启后我们**不知道**上一次是成功还是失败。把它标成 `failed` 是在编造信息，而 `unknown` 是诚实的。这个区别在事后归因时很关键。

为什么终态不可离开：一个"成功"的作业不应该再变成"失败"。允许这种转移会让重放与审计无法进行。

### 3.3 输出流：为什么没人读会死锁

子进程的输出走管道，管道有固定大小的缓冲区（Linux 上通常 64 KB）。**缓冲区满了、而没有人读，子进程就会阻塞在 write 上，永远不结束。**

```js
// 边跑边读：输出必须持续被消费，否则管道填满后子进程阻塞
export function attachStreams(child, sink) {
  child.stdout.on('data', (chunk) => sink.append('stdout', chunk))
  child.stderr.on('data', (chunk) => sink.append('stderr', chunk))
  child.on('close', () => sink.flush())
}
```

算例实测：64 KB 的缓冲区、1 MB/s 的产出速率下，**填满时间是 0.0655 秒**。而当"消费速率不高于产出速率"时，填满时间是 **`Infinity`**。

`Infinity` 的含义：进程永远不结束。这就是 1.1 里那场卡死的成因——不是命令有问题，而是**没人读它的输出**。

两条实践规则：

1. **永远在启动时就挂上 stdout/stderr 的读取器**，不要"先跑完再读"。
2. **不用的输出要丢弃**（`stdio: 'ignore'`），而不是留在管道里。

### 3.4 超时嵌套：内层必须小于外层

多层超时（工具级、作业级、请求级）必须满足：

$$
t_{\text{内层}} < t_{\text{外层}}
$$

否则内层的超时永远不会生效——外层的计时器会先到，你会看到"超时说超时了，但原因不明"。

```js
// 超时嵌套检查：内层必须严格小于外层
export function nestedTimeoutsOk(limits) {
  for (let i = 1; i < limits.length; i++) {
    if (limits[i - 1] >= limits[i]) return { ok: false, violation: [i - 1, i, limits[i - 1], limits[i]] }
  }
  return { ok: true }
}
```

算例实测：`[30000, 10000, 5000]` 通过（30 秒 > 10 秒 > 5 秒）。`[5000, 10000]` 违规，返回 `[0, 1, 5000, 10000]`（第 0 与第 1 层倒置）。

为什么内层必须更小：内层有更具体的上下文，能给出更有用的错误信息（"这条命令超时"而不是"整个任务超时"）。内层先超时，外层的错误处理才有机会拿到具体原因。

### 3.5 后台作业：别把会话绑在长任务上

超过几秒的任务应该变成**后台作业**：提交后立即返回一个作业 id，之后通过轮询或通知获取结果。

```js
// 后台作业：提交返回 id，状态与输出分开查询
export async function submit(command, opts) {
  const id = nextId()
  const child = spawn(command, { detached: false, stdio: ['ignore', 'pipe', 'pipe'] })
  jobs.set(id, { id, status: 'running', startedAt: Date.now(), output: [] })
  attachStreams(child, outputSink(id))
  child.on('close', (code, signal) => finishJob(id, code, signal))
  return { id, pollWith: opts.pollIntervalMs }
}
```

关键设计：作业的输出要**持续落盘**，而不是留在内存里等查询。否则长任务的内存会线性增长，而进程崩溃时输出全丢。

完成检测的难点：如果作业在另一个进程或另一台机器上跑，"它是否结束"这个问题不能靠本地状态回答。见 6.4。

## 四、特殊情况与处理技巧

| 情况 | 为什么 | 处理 |
|---|---|---|
| 命令挂住不返回 | 等 stdin，或管道没人读 | 关掉 stdin（给 `/dev/null`），并持续读输出 |
| 进程不响应 SIGTERM | 卡在不可中断调用 | 宽限期后 SIGKILL，并记录"需要强制" |
| 僵尸进程 | 未回收退出码 | 挂 `close` 事件。容器里用 init 进程 |
| 输出太大撑爆内存 | 全量缓存在内存 | 落盘 + 截断 + 环形缓冲 |
| 超时原因不明 | 嵌套顺序错误 | 强制内层 < 外层，并在错误里带上层级 |
| 父进程退出留下孤儿 | 未建立进程组 | 用进程组，退出时终止整组 |
| 任务重启后状态丢失 | 内存里的状态机 | 状态持久化（见 3.5 持久化） |
| 多个作业互相阻塞 | 共享同一资源（端口、文件锁） | 资源池 + 排队，而不是并发提交 |

一条通用技巧：**任何"等待外部进程"的地方都必须同时有三个东西——超时、持续的输出消费、以及退出时的回收。** 缺任何一个，都会在某个时刻变成卡死。

## 五、工业界的做法（可照做）

### 5.1 进程管理的标准部件

| 场景 | 方案 | 关键机制 |
|---|---|---|
| 长期服务 | systemd | 重启策略、依赖顺序、cgroup 资源限制 |
| 容器内多进程 | tini / dumb-init | 作为 PID 1 回收孤儿、转发信号 |
| 命令执行 | 进程组 + 超时 | 终止整组，避免留下孤儿 |
| 后台作业 | 作业队列（Celery / SQS / RQ） | 提交与消费解耦，可重试 |
| 集群作业 | Kubernetes Job / CronJob | 完成检测、重试策略、TTL 清理 |
| 计划任务 | cron / 调度器 | 幂等、错过执行的补偿 |

共同的形状：**谁启动谁负责回收，并且回收要覆盖"整组"而不是"一个进程"。**

### 5.2 作业队列的通用语义

真实的作业系统几乎都包含这几个概念，值得照抄到自己的实现里：

| 概念 | 作用 | 常见默认值 |
|---|---|---|
| 可见性超时 | 消费者拿走任务后，多久没确认就重新入队 | 30 秒–5 分钟 |
| 心跳 / 续租 | 长任务定期延长自己的可见性超时 | 每 10–30 秒一次 |
| 最大重试 | 失败重试次数 | 3 次 |
| 死信队列 | 重试耗尽后的归宿 | 必须有人看 |
| 幂等键 | 让重试安全 | 由提交方生成 |
| 优先级 | 短任务优先，避免被长任务堵住 | 分级而非连续值 |

**可见性超时 + 心跳**这一对是关键：它把"任务还在跑吗"从一个需要全局知识的问题，变成了**一个可以被超时规则近似回答的问题**。

### 5.3 参数怎么定

| 参数 | 推荐起点 | 依据 |
|---|---|---|
| SIGTERM 宽限期 | 1–10 秒 | 够进程清理，又不至于让用户久等 |
| 单命令超时 | 30 秒–5 分钟 | 交互场景取小值 |
| 前台/后台分界 | 5–10 秒 | 超过就该转后台 |
| 管道缓冲处理 | 立即挂读取器 | 64 KB 在 1 MB/s 下 0.0655 秒就满 |
| 输出保留 | 全量落盘 + 头部尾部截断进上下文 | 兼顾可追溯与成本 |
| 心跳间隔 | 可见性超时的 1/3 | 留出两次失败重试的余量 |
| 并发上限 | 按 CPU 与内存算 | 进程过多会互相拖慢 |

### 5.4 一份可落地的实施清单

1. **启动即挂流**：stdout/stderr 立刻接读取器，stdin 给空设备。
2. **进程组**：用独立进程组启动，终止时整组结束。
3. **三步终止**：SIGTERM → 宽限期 → SIGKILL，并记录是否用了强制。
4. **状态机**：六种状态 + 终态不可离开 + 重启后为 `unknown`。
5. **超时嵌套检查**：启动时校验内层小于外层。
6. **输出落盘**：全量写文件，进上下文的部分截断。
7. **后台化**：超过前台阈值转后台，返回作业 id。
8. **心跳**：后台作业定期上报存活。
9. **回收审计**：定期检查僵尸与孤儿进程。
10. **测试**：注入"不读输出"、"忽略 SIGTERM"、"无限输出"三类用例。

## 六、学术界的结论

### 6.1 死锁的四个必要条件

操作系统课本里的经典结论——死锁必须**同时**满足四条：

1. **互斥**：资源不能共享。
2. **持有并等待**：占着一个，等另一个。
3. **不可剥夺**：不能强行拿走。
4. **循环等待**：等待关系成环。

**破坏任意一条即可避免死锁。** 在 agent 场景里最实用的两条：

- **破坏"持有并等待"**：一次申请全部所需资源，或用超时放弃重试。
- **破坏"循环等待"**：给资源定序，所有进程按同一顺序申请。

3.3 的死锁（管道没人读）属于"持有并等待"：子进程持着管道写端，等待缓冲区腾出空间，而唯一的读者在等它结束。

### 6.2 结构化并发

现代并发模型（结构化并发）的核心主张是：**并发任务必须有明确的作用域与生命周期**——不能有"游离的"后台任务。

它的三条规则：

1. **任务在作用域内启动**，作用域退出时所有子任务必须已结束。
2. **取消沿作用域向下传播**。
3. **错误在作用域内聚合**，不会静默丢失。

对你的意义：这正是"进程组 + 终止序列"要解决的问题。**把子进程当成作用域内的任务**，作用域结束就确保它被回收，孤儿进程自然消失。

### 6.3 信号与竞态

信号是**异步**的：它可以在任何时刻到达，包括在进程正在处理前一个信号的中间。这带来两类经典竞态：

- **丢失信号**：信号发出时进程刚好退出，或者信号在被阻塞期间到达。
- **重复处理**：同样的清理逻辑被执行两次。

工程上的缓解：清理逻辑必须**幂等**。信号处理器只做最小动作（设置标志），实际处理在主循环里完成。

### 6.4 完成检测：为什么"它结束了吗"有时无法回答

如果作业跑在另一台机器上，"它是否结束"无法靠本地状态回答：

- 对方可能已经完成，但结果还没送到。
- 对方可能已经崩溃，永远不会回答。
- 网络分区会让"没回答"与"还在跑"无法区分。

这就是分布式系统里的**故障检测问题**：你无法区分"慢"和"死"。严格意义上的判定在异步模型下不可实现（FLP 结论的直观含义）。

工程上的妥协：用**超时 + 心跳**把问题变成可以近似回答的：

- 心跳按时到 → 认为在跑。
- 超过若干次没心跳 → 认为失败，并**假定它可能已经执行过**（这就是为什么重试必须幂等，见 3.1）。

这条结论的直接含义：`unknown` 状态不是实现缺陷，而是**分布式环境的物理属性**。任何"必须知道确切成败"的设计，都要靠幂等 + 对账来兜底，而不是靠状态查询。

## 七、理论：卡死的三个条件

把本篇的三处失败抽象出来，卡死总是同时满足：

1. **有等待**：某个主体在等另一个主体的输出或结束。
2. **等待无上限**：没有超时。
3. **等待的对象依赖于等待者**：形成了环。

算例里的 `Infinity` 正是这三条同时成立：子进程等缓冲区腾空，读者等子进程结束，而读者就是唯一能让缓冲区腾空的人。

因此防卡死的手段也就三种：

| 手段 | 破坏哪一条 | 例子 |
|---|---|---|
| 超时 | 等待无上限 | 命令超时、宽限期 |
| 持续消费 | 依赖关系 | 立即挂读取器 |
| 取消传播 | 环 | 进程组 + 终止序列 |

**三条都要有**。只加超时，进程仍可能留下孤儿。只挂读取器，命令仍可能永远跑下去。

## 八、工程化清单

| 项 | 内容 |
|---|---|
| 启动 | 独立进程组、stdin 空设备、立即挂 stdout/stderr |
| 终止 | 三步终止，记录是否强制，回收整组 |
| 状态 | 六状态机、终态不可离开、重启为 `unknown` |
| 超时 | 分层且校验嵌套顺序，错误信息带层级 |
| 输出 | 全量落盘、进上下文的部分截断、实时可查看 |
| 后台化 | 提交返回 id、轮询或通知、心跳续租 |
| 资源 | 并发上限、CPU/内存/墙钟限额 |

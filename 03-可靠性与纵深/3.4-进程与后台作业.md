## 本篇新词

- 进程组（process group） 指一组可被一次性寻址的进程。命令通过 shell 启动时子进程属于同一个组，这使"杀掉这条命令的全部后代"成为一次操作。
- 作业（job） 指 harness 管理的一次命令执行，它有标识、状态、输出与结束时间，生命周期可以长于发起它的那一轮对话。
- 终止序列（termination sequence） 指"请求退出 → 等待宽限期 → 强制杀死"的三步过程。跳过中间一步会让需要清理的进程没有机会清理。
- 宽限期（grace period） 指发出退出请求到强制杀死之间的等待时间。它的长度由被终止对象的最长清理时间决定。
- 孤儿（orphan） 指父进程已退出而自身仍在运行的进程。父进程退出不会自动终止它。
- 输出通道（output channel） 指标准输出与标准错误两条独立的流。它们各自缓冲，因此合并后的先后顺序不可靠。
- 状态未知（unknown） 指宿主在作业运行期间崩溃后，该作业的真实状态无法确认。它不是失败，也不是成功。
- 背压（backpressure） 指输出产生速度超过收集速度时的处理。没有背压控制时，缓冲区会无限增长或读取方被阻塞。

## 一、【设计原因】

### 1.1 缺陷一：取消之后，命令还在跑

最朴素的取消实现是杀掉直接子进程。若命令是 `sh -c "npm test"`，父进程是 shell，真正的测试进程是它的后代。

杀掉 shell 后，测试进程仍在运行：它继续占用端口、写文件、消耗 CPU。而 harness 已经报告"已取消"。

### 1.2 缺陷二：一条在终端里正常的命令，在执行器里挂住

在终端里 `npm test` 正常结束，在执行器里却永远不返回。原因是执行器先等进程结束，再读取它的输出：子进程的输出写满管道缓冲区后被阻塞，而执行器在等它结束。双方都在等对方。

::: keypoint 反直觉点
**"先等结束再读输出"会死锁，而且只在输出量大时发生。** 小输出测不出来，上线后遇到大日志才暴露——这是这类缺陷最典型的暴露方式。
:::

### 1.3 缺陷三：进程表里积累着已经退出的进程

子进程已退出，但父进程没有回收它，于是它保留在进程表中成为僵尸。数量积累后耗尽进程表项。

这类问题的特点是在长时间运行的系统里才显现：单次测试看不出，跑一天之后开始出现"无法创建进程"。

### 1.4 缺陷四：重启之后，后台作业的状态消失了

后台作业的状态只存在内存里。宿主重启后，那些作业的去向无从得知：它们可能已经完成、可能还在运行、可能已经失败。

而"不知道"必须能被表示。如果状态只有成功与失败两种，那么重启之后系统只能猜——它会猜错，并且把错的结果当成事实记录下来。

### 1.5 由此确定的设计目标

1. 取消要覆盖整棵树：按进程组而不是按单个进程终止。
2. 读取与等待并行：输出收集必须在等待结束之前开始。
3. 退出必须被回收：所有子进程都要被显式等待。
4. 未知是一种状态：持久化的状态机必须包含它。

**本节要点**

- 杀掉直接子进程不终止它的后代。
- 先等结束再读输出会死锁，只在大输出时暴露。
- 不回收已退出的子进程会积累僵尸。
- 重启后作业状态不可知，必须有一种状态表示它。
- 四条设计要求：整树终止、读写并行、显式回收、承认未知。

## 二、【直觉】

### 2.1 包工队

设想雇一个包工队装修。你对接的是工头，他带着一群工人。工头自己不干活，活是工人干的。

现在你要叫停。只让工头走人，工人们不知道，继续拆墙。要让活真的停下来，你必须通知整个队——这就是进程组。

还有一件事：工人手上有工具，收工时要把工具归位。如果你不给他时间直接把他架走，工具就丢在现场。这就是宽限期存在的理由。

### 2.2 对讲机与两块白板

指挥中心用两块白板记录现场：一块记正常汇报，一块记异常。两块白板由不同的人抄写，各自有延迟。

于是白板上内容的先后顺序不反映实际情况：异常可能先被抄上正常白板。若你把两块白板按抄写时间拼在一起，得到的时间线是错的。

这就是两条输出通道。要还原真实顺序，只能给每条记录带上时间戳，而不是依赖到达顺序。

::: keypoint 反直觉点
**"把标准错误重定向到标准输出"不是合并顺序问题的解法，它只是把问题藏起来。** 两条流仍然各自缓冲，只是最终写进同一个文件描述符——而写进去的先后依然由各自的缓冲刷新时机决定。
:::

### 2.3 一个数字直觉

假设一次命令每秒产生 1 MB 日志，管道缓冲区是 64 KB。若读取方在等进程结束才开始读，那么进程在约 0.06 秒后就会写满缓冲区并被阻塞。

结论是：这类死锁不是"偶发"的，它在大输出下必然发生。 时间尺度上它快到几十毫秒就进入阻塞。

**本节要点**

- 终止必须覆盖整队（进程组）。
- 宽限期是给清理动作留的时间。
- 两条输出流的顺序不可靠，需要时间戳而不是到达顺序。
- 重定向不等于顺序正确。
- 管道写满只需几十毫秒，所以这类死锁是必然而非偶发。

## 三、【严格】

### 3.1 定义

::: theorem 定义 3.4.1（进程树与进程组）
一次命令执行形成进程树 $T = (V, E)$，其中 $V$ 是进程集合，$E$ 是父子关系，根的父进程是执行器。**进程组** $g \subseteq V$ 是可被一次性寻址的进程集合，满足通过 shell 启动时 $g = V$。

对进程 $v$ 的**终止**写作 $\mathrm{kill}(v, s)$，其中 $s$ 是信号。$\mathrm{kill}$ 是**请求**：它不保证 $v$ 立即停止。
:::

::: theorem 定义 3.4.2（终止序列）
**终止序列**是一个三步过程：

$$
\text{序列} = \bigl(\mathrm{kill}(g, \mathrm{TERM}),\ \mathrm{wait}(w),\ \mathrm{kill}(g, \mathrm{KILL})\bigr),
$$

其中 $w$ 是宽限期。若在 $w$ 内 $g$ 中所有进程都已退出，则跳过第三步。

进程在 $\mathrm{TERM}$ 与 $\mathrm{KILL}$ 之间的行为无约束：它可以忽略前者。
:::

::: theorem 定义 3.4.3（作业与状态机）
**作业**是五元组 $J = (\text{id}, \text{cmd}, \text{state}, \text{output}, \text{meta})$。

状态集为 $\mathcal{S} = \{\text{pending}, \text{running}, \text{succeeded}, \text{failed}, \text{cancelled}, \text{unknown}\}$，转移函数 $\delta: \mathcal{S} \times \mathcal{E} \to \mathcal{S}$，其中 $\mathcal{E}$ 是事件集合。

**unknown 的必要性**：宿主在作业处于 running 时崩溃，重启后重新读取持久化状态得到 running，但该状态无法被确认。
:::

::: theorem 定义 3.4.4（输出通道与合并）
命令的输出是两条带时间的记录序列：

$$
O_{\text{out}} = ((t_1, x_1), (t_2, x_2), \dots), \qquad O_{\text{err}} = ((t'_1, y_1), (t'_2, y_2), \dots).
$$

**合并** $\mathrm{merge}(O_{\text{out}}, O_{\text{err}})$ 按时间戳排序。若只有到达顺序 $a_i$ 而无时间戳，则按到达顺序合并得到的序列与真实发生顺序可以不同。
:::

::: theorem 定义 3.4.5（背压与溢出）
设产出速率 $r_p$、消费速率 $r_c$、缓冲区容量 $C$。当 $r_p > r_c$ 时缓冲区在 $C / (r_p - r_c)$ 时间内填满。

填满后有两种处置：**阻塞**生产者（背压），或**丢弃/外置**旧数据（溢出）。两者都改变系统行为，必须显式选择。
:::

### 3.2 命题

::: theorem 命题 3.4.1（单进程终止不保证后代终止）
设根为 $v_0$，其某个后代为 $v_d$（$d > 0$）。执行 $\mathrm{kill}(v_0, \mathrm{KILL})$ 不蕴含 $v_d$ 停止。

**证明.** 进程的终止只作用于该进程自身。$v_d$ 的存活与它的父进程是否存活无关：父进程退出后 $v_d$ 成为孤儿，由系统重新托管并继续运行。故 $v_0$ 的终止不蕴含 $v_d$ 的终止。

↓ **为什么能这么写？** 终止是作用于单个进程的操作，父子关系不构成传播条件。

$\blacksquare$

::: keypoint 推论
**必须按进程组终止。** 单进程终止在多进程命令（`sh -c`、构建脚本、`npm test`）上必然留下残余。残余进程的危害不只是占资源：它可能持有端口与锁，使后续执行失败。
:::
:::

::: theorem 命题 3.4.2（无宽限期的终止会丢失清理）
若在发出终止请求后立即强制杀死，则任何需要执行清理动作（写回、释放锁、删除临时文件）的进程都来不及完成清理。

**证明.** 强制杀死使进程在收到信号的指令处立即停止，不执行后续代码。清理动作是以代码形式存在的，因此它不被执行。故清理丢失。

↓ **为什么能这么写？** 清理动作需要运行时间，而立即杀死不提供时间。

$\blacksquare$

**数值**：宽限期的下界是被终止对象的最长清理时间。数据落盘通常在毫秒到数百毫秒量级，因此宽限期取秒级。但对带网络收尾的进程可能需要更长。

::: keypoint 宽限期不是越长越好
长宽限期让清理有充分时间，代价是取消的响应变慢。**工程上的折中是分级**：先给一个短宽限期，超时后强制杀死并**记录"清理未完成"**，而不是无限等待。
:::
:::

::: theorem 命题 3.4.3（先等结束再读输出必然死锁）
设管道缓冲区容量为 $C$，被等待进程在结束前需写出 $N > C$ 字节。若执行器在等待进程结束后才开始读取，则进程与执行器互相等待。

**证明.** 进程写出 $C$ 字节后缓冲区满，后续写操作阻塞，进程不能结束。执行器等待进程结束，因此不读取输出。进程等待缓冲区腾空。三者构成环，双方都无法推进。

↓ **为什么能这么写？** 阻塞条件是"缓冲区满"与"未读取"，而读取的前提是进程结束，形成一个闭环。

$\blacksquare$

**数值**：$r_p = 1$ MB/s、$C = 64$ KB 时，$\frac{C}{r_p} \approx 0.06$ 秒后进入阻塞。**这与输出总量无关，只与产出速率有关**——所以大输出必然触发，小输出测不出来。
:::

::: theorem 命题 3.4.4（宿主崩溃后 running 状态不可确认）
若宿主在作业处于 running 时崩溃，则重启后不存在能在原系统内判定该作业已结束的确定性程序。

**证明.** 判定作业是否结束需要观察它的退出状态。该状态由宿主在作业结束时收集并记录。宿主在收集之前崩溃，则退出状态未被记录，而作业进程可能仍在运行或已退出。原系统内不存在其他记录该退出状态的载体，故无法判定。

↓ **为什么能这么写？** 判定的信息来源只有宿主的记录，而该记录在崩溃前未产生。

$\blacksquare$

::: keypoint 所以状态集必须包含 unknown
**只有成功与失败的二元状态会强迫系统猜测**，而猜错的方向往往是"当成失败"，于是可能重复执行一个实际已经成功的操作（若该操作不幂等则造成重复副作用）。正确做法是把 running 状态的作业在重启后标为 unknown，并要求人工或按策略处置。
:::
:::

::: theorem 命题 3.4.5（嵌套超时必须单调不增）
设外层超时为 $T_{\text{outer}}$、内层为 $T_{\text{inner}}$。若 $T_{\text{inner}} > T_{\text{outer}}$，则内层超时永远不被触发。

**证明.** 外层计时先到期，外层逻辑终止内层所代表的执行。内层的计时器随执行一起停止，故其到期条件不被满足。

↓ **为什么能这么写？** 超时的触发要求计时器到期，而外层到期会终止被计时的执行。

$\blacksquare$

**推论**：配置里出现 $T_{\text{inner}} > T_{\text{outer}}$ 是**配置错误**，应当在校验阶段拒绝，而不是在运行时表现为"内层超时从未生效"。
:::

::: theorem 命题 3.4.6（不回收子进程会积累僵尸）
设执行器在每次执行后不等待子进程退出，则进程表中的僵尸项数等于已退出而未被回收的进程数，单调不减。

**证明.** 子进程退出后进入待回收状态，直到父进程调用等待操作。若父进程不调用，该项一直保留。每次执行至少产生一个这样的项（命令进程本身），故数量单调不减。

↓ **为什么能这么写？** 回收是显式操作，不执行它就不发生。

$\blacksquare$
:::

### 3.3 本节要点

**本节要点**

- 终止只作用于单个进程，父子关系不传播（命题 3.4.1）。
- 无宽限期的强制杀死会丢失清理动作（命题 3.4.2）。
- 先等结束再读输出必然死锁，且在大输出下必现（命题 3.4.3）。
- 宿主崩溃后 running 状态不可确认，必须引入 unknown（命题 3.4.4）。
- 嵌套超时必须单调不增，否则内层永不触发（命题 3.4.5）。
- 不回收子进程会单调积累僵尸（命题 3.4.6）。

## 四、【回到直觉】

- 定义 3.4.2 说的：取消是一个过程而不是一个动作。报告"已取消"的时刻应当在强制杀死之后，而不是在发出信号之后。
- 命题 3.4.1 说的：`sh -c "npm test"` 要先杀整棵树。只杀 shell 等于只赶走了工头。
- 命题 3.4.2 说的：给一秒宽限期，让收尾动作跑完。超时就强杀，并记录"清理未完成"。
- 命题 3.4.3 说的：读取和等待要并行。先启动读取，再等待结束。
- 命题 3.4.4 说的：重启后遇到 running 的作业，标成 unknown，不要猜。
- 命题 3.4.5 说的：内层超时比外层长是配置错误，该在校验阶段拒绝。
- 命题 3.4.6 说的：每次执行都要显式回收，否则进程表会慢慢被僵尸占满。

**本节要点**

- 取消是过程，报告时刻在强杀之后。
- 按进程组终止。
- 宽限期给清理，超时强杀并记录。
- 读取与等待并行。
- 重启后的 running 标为 unknown。
- 嵌套超时单调不增。
- 每次执行显式回收。

## 五、【工具箱】

### 5.1 状态机

状态机的检验有三条：每个状态可达、终止状态不可离开、从任意状态都能到达某个终止状态。

前两条容易检查，第三条最容易被忽略：若存在一个状态，从它出发没有任何事件能到达终止状态，那个作业就永远卡住。卡住的作业比失败的作业更难发现，因为它不报错。

### 5.2 超时嵌套的校验

给出超时层级表 $(T_1 \ge T_2 \ge \dots \ge T_n)$ 即可。校验是逐对比较，代价 $O(n)$。

要检查的位置：模型请求超时、工具执行超时、作业超时、会话超时。四层之间都必须满足单调不增。

### 5.3 输出合并

若有时间戳，按时间戳排序的代价是 $O(k \log k)$（$k$ 是记录数）。若两条流都已有序，归并的代价是 $O(k)$。

实践建议：给每条记录在产生时就打上时间戳，而不是在收集时。收集时打的时间戳反映的是到达时间，它受缓冲影响。

### 5.4 缓冲区与背压

填满时间 $C / (r_p - r_c)$ 给出"多久会阻塞"。工程上的处置取决于是否需要全部输出：

- 需要全部：外置到文件，缓冲区只保留最近一段（与 3.3 的溢出同构）。
- 只需要最近：环形缓冲，丢弃最旧的。
- 需要实时：把收集与等待并行，并给读取方设定速率上限。

### 5.5 崩溃演练

要在测试中覆盖"宿主崩溃"，用在指定点强制退出的方式：在写入完成前后、在检查点落盘前后各设一个注入点（与 3.5 的崩溃点分类一致）。这类演练的价值在于它验证的是恢复路径，而恢复路径在正常运行中永远不会被走到。

**本节要点**

- 状态机要检查"从任意状态都能到达终止状态"。
- 超时嵌套逐对比较，四层都要满足单调不增。
- 时间戳要在记录产生时打，不是收集时。
- 背压的三种处置取决于是否需要全部输出。
- 崩溃演练用注入点强制退出，验证的是恢复路径。

## 七、施工图与算例

### 7.1 四段结构

| 段 | 职责 | 关键约束 |
|---|---|---|
| 启动段 | 建进程组、接管三条流 | 命令必须与本进程分离，避免相互影响 |

| 取消段 | 三步终止序列 | 覆盖整组，记录清理是否完成 |
| 状态机段 | 状态转移与持久化 | 包含 unknown，转移可检验 |

### 7.2 启动段：分离与接管

启动段做三件事：建立独立进程组、接管两条输出流、记录标识。独立进程组是取消能覆盖整树的前提。

```js
// 建进程组并接管三条流：独立进程组是"取消整棵树"的前提（命题 3.4.1）
import { spawn } from 'node:child_process'

export function start(cmd, args, opts = {}) {
  const child = spawn(cmd, args, {
    detached: true, // 自成进程组
    stdio: ['ignore', 'pipe', 'pipe'],
    ...opts,
  })
  return {
    id: String(child.pid),
    child,
    stdout: [],
    stderr: [],
    startedAt: Date.now(),
  }
}
```

### 7.3 取消段：三步序列

取消段实现定义 3.4.2。第三步不能省：忽略终止请求的进程只能被强制杀死。

```js
// 三步终止序列：请求退出 → 宽限期 → 强制杀死（定义 3.4.2）
export function killSequence(pid, graceMs) {
  return [
    { signal: 'SIGTERM', target: -pid, delay: 0 },
    { signal: null, target: null, delay: graceMs }, // 等待
    { signal: 'SIGKILL', target: -pid, delay: 0 },
  ]
}

// 宽限期到点时的判断：整组是否已退出
export function graceExpired(alivePids, graceMs, now, startedAt) {
  if (alivePids.length === 0) return { kill: false, cleaned: true }
  if (now - startedAt < graceMs) return { kill: false, cleaned: true, waiting: true }
  return { kill: true, cleaned: false } // 清理未完成，要记录
}
```

注意 `target: -pid`：负号表示按进程组寻址，这是整树终止的写法。

### 7.4 状态机段：含 unknown

状态机段的关键是把 unknown 作为一等状态，并在重启时把 running 迁移到它。

```js
// 作业状态机：重启时把 running 迁到 unknown，而不是猜成功或失败（命题 3.4.4）
export const TRANSITIONS = {
  pending: { start: 'running', cancel: 'cancelled' },
  running: { done: 'succeeded', error: 'failed', cancel: 'cancelled', restart: 'unknown' },
  succeeded: {},
  failed: {},
  cancelled: {},
  unknown: { done: 'succeeded', error: 'failed', cancel: 'cancelled' }, // 需外部证据
}

export function nextState(state, event) {
  const to = TRANSITIONS[state]?.[event]
  if (!to) throw new Error(`非法转移：${state} --${event}-->`)
  return to
}
```

终止状态为空对象：它们没有出边，因此不可离开（工具箱 5.1 的第二条）。

### 7.5 收集段：并行读取

收集段在启动之后立即开始，与等待并行。顺序不能颠倒，否则触发命题 3.4.3 的死锁。

```js
// 并行收集：两条流各自读取，读完才等待结束（命题 3.4.3）
export function collect(child, sinks, onLine) {
  const read = (stream, name) => new Promise((resolve) => {
    stream.on('data', (chunk) => {
      const t = Date.now()
      for (const line of String(chunk).split('\n')) if (line) onLine({ t, channel: name, line })
    })
    stream.on('end', resolve)
  })
  return Promise.all([read(child.stdout, 'out'), read(child.stderr, 'err')])
}
```

### 7.6 输出合并

按定义 3.4.4，合并按时间戳而不是到达顺序。时间戳在记录产生时打，否则合并没有意义。

```js
// 按时间戳归并两条流：两条流各自有序，归并代价 O(k)（工具箱 5.3）
export function mergeStreams(a, b) {
  const out = []
  let i = 0
  let j = 0
  while (i < a.length && j < b.length) out.push(a[i].t <= b[j].t ? a[i++] : b[j++])
  while (i < a.length) out.push(a[i++])
  while (j < b.length) out.push(b[j++])
  return out
}
```

### 9.2 失败模式

- （1）检查放在装载期（L9 位置放错）。 进程组在启动时建立，但取消逻辑按记录的单个 pid 操作，而 pid 在进程退出后可能被复用。表现是"取消了另一个无关进程"。修正：按组寻址，并在取消前确认进程仍在。

- （2）前提会变（L9）。 命题 3.4.2 的宽限期取值以"清理时间不超过 $w$"为前提。当清理涉及网络收尾时该时间可能远超预期。修正：给宽限期一个上限并在超限时记录未完成清理。

- （3）只杀直接子进程。 残留后代继续占用端口与文件。

- （4）先等结束再读输出。 大输出必然死锁。

- （5）把 running 猜成 failed。 重启后重复执行一个实际已成功的操作，若不幂等则产生重复副作用。

- （6）内层超时长于外层。 内层超时永不触发，配置看起来生效实际无效。

- （7）不回收子进程。 僵尸单调积累，长时间运行后进程表耗尽。

- （8）两条流按到达顺序合并。 时间线错误，排查时把人引向错误结论。

- （9）缓冲无限增长。 没有背压或溢出策略时内存持续上升。

- （10）取消后不记录残余。 无法知道"这次取消是否干净"，也就无法发现命题 3.4.1 的实现缺陷。

**本节要点**

- 决策表覆盖 11 种情形。
- 失败模式十条，前两条是位置放错与前提会变。
- 最隐蔽的是"内层超时永不触发"，因为配置看起来正确。

## 十、仍未解决

- 取消的因果确认。 "进程已退出"可以观察，"副作用已停止"无法直接观察（它可能已经写了一半）。
- 跨平台进程组语义。 不同操作系统的进程组与信号语义有差异，统一抽象会丢失平台特性。
- 宽限期的自适应。 最优宽限期取决于被终止对象的清理时间，而该时间事前未知。
- 输出顺序的跨机一致性。 时间戳依赖各进程的时钟，多机场景下时钟偏移会破坏归并顺序。
- 长期作业与持久化状态的一致性。 作业状态在存储里、进程在机器上，两者之间没有事务。
- unknown 的自动消解。 判定一个 unknown 作业的真实结局需要外部证据，而证据来源取决于命令语义。

**本节要点**

- 取消无法确认副作用已停止。
- 进程组语义跨平台不一致。
- 宽限期缺少自适应依据。
- 多机时钟偏移破坏输出归并。
- 作业状态与进程之间没有事务。
- unknown 的消解依赖外部证据。

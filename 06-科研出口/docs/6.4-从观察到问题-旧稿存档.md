## 本篇新词

观察（observation） 在这里指一次被记录下来的、与预期不符的现象。它与"失败"的区别是失败有明确的对错，而观察没有——"这个任务超时了"是失败，"这类任务在压缩阈值调高之后反而更快"是观察。失败进诊断流程（4.4），观察进研究流程（本篇）。

意外（surprise） 指与已有预期冲突的观察。它是观察里价值最高的一类——因为冲突意味着某个既有认识不完整。判据很具体：你在看到它之前会预测另一个结果；没有预测就没有意外。

异常（anomaly） 指偏离常态但不与预期冲突的观察（例如某个任务的耗时是其他的十倍）。它与意外的区别是它可能只是一个长尾样本——而它是否有意义，取决于它能否被复现。

观察记录（observation log） 指按固定字段记录观察的载体。它的必要性来自一个经验事实：同一个现象第二次出现时，人通常不记得第一次的细节。

排除已知解释（ruling out） 指在把观察转成问题之前，先排除它已有的解释。三种排除方式：查（已有知识是否解释它）、做（消融或对照是否让它消失）、找反例（有没有相反的现象）。

最小反例（minimal reproduction） 指能把现象复现出来的最小条件集。它是研究里最有价值的材料之一——因为它让"你说的这个现象"变成"任何人跑这三步都能看到这个现象"。

机制问题（mechanism question） 指"为什么会这样"的问题，它区别于"这样做会不会更好"的比较问题（6.2 处理的）。比较问题需要基准，机制问题需要解释——而后者的验证方式不同（预测新现象并检验）。

转化（translation） 指从一个现象得到一个可检验命题的过程。它有四步，而它的产出直接进入 6.1 的清单。

知识落差（knowledge gap） 指现象背后缺失的那部分认识。它有大小之分：一个小落差可以靠一次实验补上（那是 6.2 的工作），而一个大落差需要新的概念（那才是 6.1 意义上的开放问题）。

```
└──────────────────────────────────────────────────────────────────────┘

 一句话串起来：怎么注意 → 怎么记录 → 怎么转化 → 怎么用
```

这张图的关键线索在第一块：观察的前提是有预期。一个没有写下预期的人不会遇到意外——他看到的所有结果都"就是这样"。因此"先预测再运行"这个习惯是这一篇的方法起点，而它同时是 6.2 的实验设计习惯（先定判据再跑）。

### 0.1 一个具体的判断：观察的转化率与它为什么低

设一次为期两周的开发里发生 30 次值得记录的观察（异常、意外、说不通的现象）。按经验分布，它们的去向大致是：

| 去向 | 数量 | 原因 |
|---|---|---|
| 被当成噪声忽略 | 18 | 没有被记录，事后想不起来 |
| 被局部修补 | 8 | 加了个特例绕过去，没有追问原因 |
| 被查证并解释清楚 | 2 | 找到已知解释，问题消失 |
| 变成可检验的命题 | 2 | 进入清单 |

这张表说明转化率低的主要原因不是转化难，而是前两步没做——多数观察在"被记录"这一关就丢失了。"被局部修补"那一类尤其值得注意：特例绕过之后，现象不再出现，而原因从未被理解——这类修补累积起来就是 1.2 的技术债的一种形态（有理由过，而理由已经不可考）。

两条推论：记录的成本必须极低（否则没人记），以及补特例的动作应当留下一条观察记录（它是这件事最有可能被追溯的时刻）。

### 0.2 本篇建立的三项判据

第一项用于判断一个观察是否值得记录：问"它有没有与我的预期冲突"。冲突是筛选器——没有冲突的观察可以进入数据（6.2 的结果），但不需要进入观察日志。

第二项用于判断一个观察是否已经转化为问题：问"它有没有变成三要素齐全的表述"（6.1 的判据）。没有的话它还是一段描述，而描述无法被检验。

第三项用于判断一次"局部修补"是否掩盖了问题：问"我能不能说出这个特例背后的原因"。答不出时，至少留下一条观察记录——这条判据把"绕过"变成了"挂起"，而两者对后续的价值差别很大。

### 0.3 十分钟练习：观察记录的字段与一次转化

下面这段代码定义观察记录，并演示从观察到命题的转化。

```js
function recordObservation(o) {
  const required = ['what', 'expected', 'observed', 'conditions', 'reproducible']
  const missing = required.filter((k) => o[k] === undefined)
  if (missing.length) throw new Error(`观察记录缺少：${missing.join('、')}`)
  return {
    id: `obs-${Math.abs(hash(JSON.stringify(o))).toString(36).slice(0, 5)}`,
    ...o,
    loggedAt: Date.now(),
  }
}

function toFormulation(obs, form) {
  if (!obs.reproducible) return { ok: false, why: '现象不可复现，先构造最小反例（1.6）' }
  if (!form.independent || !form.dependent || !form.baseline) return { ok: false, why: '命题三要素不全' }
  return { ok: true, formulation: { ...form, from: obs.id, whyOpen: form.whyOpen ?? '' } }
}

const obs = recordObservation({
  what: '压缩阈值调高之后，某类任务的总 token 消耗反而下降',
  expected: '压缩更少 → 上下文更长 → 消耗更高',
  observed: '三个任务里两个消耗下降，一个上升',
  conditions: { 阈值: [0.6, 0.8], 任务类型: '多轮小改动', 模型: '<固定版本>' },
  reproducible: true,
})

console.log(obs)
console.log(toFormulation(obs, {
  independent: '压缩阈值',
  dependent: '单任务总 token 消耗',
  baseline: '阈值 0.6',
  whyOpen: '压缩减少会拉长上下文，但同时减少了压缩本身的开销与重述次数',
}))
```

两个函数对应这一篇的两端：记录（字段齐全）与转化（可复现加三要素）。而那个例子里"消耗反而下降"的机制假设（压缩本身有开销、压缩导致的重述）恰好是一个真实的现象——它说明意外往往指向一个此前没被算进模型的成本项。

### 0.5.3 三个连锁影响

第一，观察的密度取决于记录的成本，而不取决于人的注意力。 一个需要在专门工具里填十个字段的记录方式会被放弃，而一个能在一行里写下"预期、实际、条件"的方式会被坚持。因此观察记录的设计目标是"能在运行中顺手写下"，而不是"字段完整"——完整可以通过事后的整理补齐。

第二，意外只出现在有预期的运行里，而预期来自理论或经验。 这条连锁意味着读文献与做实验不是对立的两件事：文献提供预期（因此它让意外成为可能），而实验产生观察（因此它让预期被检验）。没有预期的实验只能产生数据，不能产生发现。

第三，转化失败的观察会以另一种形式回来。 被当成噪声丢掉的观察会在几个月后以更大的规模重现（"这个偶发问题现在每次都发生"），而那时它已经失去了原始条件（当时的版本、配置、数据）。因此记录的边际价值随时间的推移而上升——这与 4.1 的"决策记录两周后才有价值"是同一个规律。

### 0.5.4 它与本书其余部分的关系

本篇讨论的观察来自单机、单项目的实践。跨项目或跨团队的观察汇总需要共同的记录格式与共享机制，而它不在本课程范围内。这条边界意味着本篇在"一个人或一个小组的实践"上是完整的，而它的记录字段（预期、实际、条件）恰好是共享所需的最小集合。

## L0 要解决的问题

### 0.1 现象一：现象发生过，而事后想不起细节

第一个现象是记录缺失。一个异常在运行中出现过，而当时没有记下条件（版本、配置、数据），几周后再想查已经无从下手。它的后果是观察无法被转化为问题——因为转化要求可复现，而可复现要求知道条件。

修法是 1.2 的观察记录与 0.2 的第二项判据。记录的成本必须低（0.5.3 的第一条），因此字段要少而关键：预期、实际、条件三样，其余留到整理时补。

### 0.2 现象二：异常被当成噪声忽略

第二个现象是主动忽略。异常出现时，人的默认反应是"偶发"（因为它没有重复出现），而给出的解释是"可能是网络/缓存/抖动"——这类解释的共同特点是它们无法被检验。

修法是 0.2 的第一项判据（它有没有与预期冲突）：冲突意味着某个认识不完整，而"偶发"不是一个解释，它只是"我没有解释"。处置是把它记为待观察项（4.4 的待观察清单），而不是给它一个不可检验的原因。

### 0.3 现象三：局部修补掩盖了原因

第三个现象是绕过。异常被一个特例处理掉（加一个判断、调一个参数），于是它不再出现，而原因从未被理解。它的直接后果是技术债（1.2），而更隐蔽的后果是失去了一次理解系统的机会。

修法是 0.2 的第三项判据：补特例时必须同时留下一条观察记录。这条要求的成本极低（一分钟），而它在两种情况下都值回票价：特例后来被证明有害时（可以追溯到原因）、以及同类现象再次出现时（有前例可比）。

### 0.4 现象四：有一个现象，而说不清它是什么问题

第四个现象是转化卡住。现象被准确记录了，然而写不出一个可检验的命题——因为它涉及多个因素，或者它的因变量说不清。

修法是 1.4 的四步转化与 1.5 的排除已知解释。卡住时的最常见原因是没有排除已知解释：一旦排除了三个可能的解释，剩下的那个就会自然浮现成一个具体的命题。

### 0.5 这一篇要正面回答的四个问题

第一，怎么注意（1.1）。第二，怎么记录（1.2、1.3）。第三，怎么转化（1.4、1.5）。第四，怎么用它做研究（1.6、1.7）。

四个问题里第一个最容易被跳过（因为它看起来不需要方法），而它是后面三个的前提。

## L1 设计与原理

### 1.1 怎么注意：预期与冲突

注意的机制是预期与实际的落差（0.0 的关键线索）。它有两个可培训的部分。

写下预期：在运行之前写下一句预测（"这个改动会让成本上升"）。它的作用不是验证对错，而是制造冲突的可能——写下了预测的人才会在看到相反结果时停下来。

区分三类落差。意外（与预期冲突）、异常（偏离常态而无预期）、以及无声的偏离（系统正常但某个数值与上次不同）。三者的价值递减，而它们都值得记录。无声的偏离最容易漏掉——它既不报错也不反常，只是与历史不同，而它是缓慢退化（3.6 的 1.1 提到过）的唯一信号。

```ts
interface Expectation {
  readonly before: string                 // 运行之前的预测（一句话）
  readonly metric: string                 // 用哪个量检验它
  readonly direction: 'up' | 'down' | 'same'
}

interface Observation {
  readonly id: string
  readonly what: string                   // 实际发生了什么
  readonly expectation?: Expectation      // 预期（缺省表示没有预测）
  readonly conditions: Record<string, unknown>   // 条件（版本、配置、数据）
  readonly reproducible: boolean
  readonly minimalRepro?: string          // 最小反例的构造步骤（1.6）
  readonly disposition: 'logged' | 'investigated' | 'explained' | 'deferred'
}
```

`expectation` 是可选字段而它的存在与否决定了观察的价值——没有预期的观察只能进数据，有预期的观察才可能进清单。`disposition` 的四态让"挂起"（`deferred`）成为一个合法状态（0.3 的分析）。

### 1.2 观察记录的字段与它的低成本要求

字段的最小集合是三样（预期、实际、条件），而它们的写法有要求。

预期写成一句话加一个方向（"成本上升"而不是"成本可能变化"）。方向明确才能判断冲突——"可能变化"不会与任何结果冲突。

实际写成可核对的（一个数值、一件具体的事）而不是形容词（"变慢了"）。

条件写成能复现的一组值（版本、配置、以及当时的输入）。它的完整性与 5.1 的"消灭隐式默认"直接相关——隐式默认会让条件记录不完整，从而让复现失效。

三样之外的字段（最小反例、处置状态、关联的其他观察）留到整理时补——记录阶段只要求三样（0.5.3 的第一条）。

### 1.3 记录的成本与它的两个设计要点

两个让记录能被坚持的要点。

要点一是入口在手边。记录方式应当能在运行被打断时顺手写下（一行文本、一个命令、一个快捷方式）。任何需要切换上下文的记录方式都会被放弃——这与 2.2 的"工具的描述要匹配模型的需要"是同一原则用在人身上。

要点二是整理与记录分离。记录是即时的、粗糙的。整理是事后的、结构化的。把两者合并会让记录变得昂贵（因为整理需要思考）。处置是设一个固定的整理时机（例如 4.6 的复盘周期）——复盘时把散落的记录整理进观察日志。

```ts
export function quickNote(line: string, ctx: Context): void {
  ctx.appendRawLine(ctx.notesPath, `- ${new Date().toISOString().slice(0, 16)} ${line}`)   // 一行，无结构
}

export function organize(ctx: Context): Observation[] {
  const lines = ctx.readRawLines(ctx.notesPath)
  return lines.map(parseLooseLine).filter((o): o is Observation => o !== null)              // 整理时补结构
}
```

两个函数的分工体现了"记录与整理分离"，而 `parseLooseLine` 容忍不完整的记录（缺字段的条目保留原文而不丢弃）——丢弃是记录系统最常见的设计错误。

### 1.4 转化的四步

四步与它们的产出。

第一步是描述现象（不带解释）。要求是只说看到了什么，不说"因为……"。这一步的常见错误是描述里混入解释（"因为它重试了，所以变慢了"）——它会让后续的排除工作失去对象。

第二步是列出可能的解释（至少三个，包括平凡的）。平凡解释必须被列上（"我读错了数字"、"这次恰好网络快"、"那个任务本来就更简单"），因为多数现象的平凡解释是对的（0.1 的表里"查证并解释清楚"的两条通常属于这类）。

第三步是逐个排除（1.5 的三种方式）。排除的顺序是"从平凡到有趣"——先排除平凡解释能省下大量时间。

第四步是写成命题（6.1 的三要素）。如果第四步写不出来，回到第二步——通常意味着某个解释还没被排除。

```ts
export interface Translation {
  readonly observation: string
  readonly description: string                      // 不含解释（第一步）
  readonly explanations: readonly { text: string; kind: 'mundane' | 'mechanism'; ruledOut?: string }[]  // 第二步
  readonly remaining: string                        // 排除之后剩下的（第三步）
  readonly formulation?: Formulation                // 第四步的产出（6.1 的类型）
}

export function translate(t: Translation): { ok: boolean; issue?: string } {
  if (/\b因为|由于|所以/.test(t.description)) return { ok: false, issue: '描述里混入了因果解释' }
  if (t.explanations.length < 3) return { ok: false, issue: '至少列出三个解释（含平凡解释）' }
  if (!t.explanations.some((e) => e.kind === 'mundane')) return { ok: false, issue: '必须包含平凡解释' }
  if (t.explanations.some((e) => !e.ruledOut && e.text !== t.remaining)) return { ok: false, issue: '有解释既未排除也不是剩下的那一个' }
  return { ok: true }
}
```

四条校验对应四步的质量要求，其中第二条（至少三个解释）与第三条（含平凡解释）是这一节最实用的两条——只有两个解释时，人会在两者之间反复摇摆。而没有平凡解释时，工作会全部投向"有趣的假设"。

### 1.5 排除已知解释的三种方式

三种方式与它们的成本、可靠性。

查（已有知识）：这个现象有没有已知解释。它的成本最低而它常常直接终结问题——多数"意外"在查过之后都不是意外（0.1 的表里那两条属于此类）。它的要求是查证而非回忆（回忆会给出"好像是……"这类不确定的答案）。

做（消融或对照）：改变一个条件看现象是否消失。它的成本中等，而它给出的是因果信息（4.4 的反事实与 6.2 的消融共用这一手段）。

找反例：有没有相反的现象（在别的任务、别的配置、别的版本上不出现）。它的成本取决于反例的可得性，而它的价值在于划出现象的边界——边界清晰的现象更容易转成命题。

```ts
export function ruleOut(obs: Observation, how: 'lookup' | 'experiment' | 'counterexample', detail: string, ctx: Context): RuleOut {
  const record = { observationId: obs.id, how, detail, at: ctx.now }
  ctx.appendEvent({ type: 'observation/rule-out', ...record })
  return record
}
```

三种方式的结果都应当被记录——排除过的解释在下一次遇到同类现象时可以直接跳过，而这条记录的价值随同类现象的重复而上升（0.5.3 的第三条）。

### 1.6 最小反例

最小反例的四个标准。

可复现：任何人按给定步骤都能看到现象。没有这一条时，观察只是一段叙述。

最小：去掉任何一个条件现象就消失。最小的判据是"每一条都在起作用"——多余的步骤会让原因被掩盖（因为不知道是哪一步导致的）。

自包含：不依赖特定环境或私有数据（或明确标注依赖）。自包含的最小反例是沟通与协作的基础——它让"你说的问题我复现了"成为可能。

带预期：反例里写清"预期是什么、实际是什么"（1.1 的字段）。这一条让读者能判断它是否与自己的预期冲突——而这决定了它对别人是不是也有价值。

```ts
export interface MinimalRepro {
  readonly steps: readonly string[]          // 可执行步骤
  readonly observed: string
  readonly expected: string
  readonly conditions: Record<string, unknown>
  readonly minimized: boolean                // 是否已验证每一步都必要
  readonly deps: readonly string[]           // 明确标注依赖（自包含的例外）
}
```

`minimized` 是这份结构的诚实标记：构造最小反例的最后一轮（逐个去掉步骤）最容易被跳过，而它恰好是最有价值的一步——去掉步骤的过程就是对现象机制的理解过程。

### 1.7 机制问题的验证方式

机制问题（"为什么这样"）与比较问题（"哪个更好"）的验证方式不同，而这是它常被做错的地方。

比较问题用基准与统计（6.2 的全套）。机制问题用预测新现象：如果机制假设是对的，那么在某些新条件下应当观察到某个结果——用一个尚未观察过的预测来检验它。这条判据是机制问题的核心：能做出可证伪的新预测的假设才有内容（否则它只是重述现象）。

三种可做的预测：新条件（换一个任务类型是否仍然如此）、新量级（把参数推得更极端）、以及新组合（与其他机制叠加时的表现）。三者里第二条最容易做而第三条最有信息量。

```ts
export interface MechanismClaim {
  readonly claim: string                            // 机制假设的一句话
  readonly predicts: readonly { condition: string; expected: string }[]   // 可证伪的预测
  readonly competing?: readonly string[]            // 竞争假设（能解释同一现象的）
  readonly discriminatingTest?: string              // 能区分本假设与竞争假设的实验
}
```

三个字段里 `competing` 与 `discriminatingTest` 是机制研究的方法核心：一个没有竞争假设的机制论断无法被验证（因为任何数据都能被它解释）。找出竞争假设并设计能区分它们的实验，是把机制问题做成研究的关键一步。

### 1.8 两次追问

工程侧的问题是什么时候该停下来研究。判据是"这个现象是否影响当前目标"——不影响时记录下来继续做事（`deferred` 状态），这比立刻深挖更合理（因为深挖的成本可能远超收益）。这条判断与 6.1 的排序判据一致：研究的投入要看决策影响。

产品侧的问题是这些问题值得投入吗。答案取决于两件事：现象的影响面（多少用户、多少任务）与知识的可迁移性（理解它是否能帮助理解其他现象）。只满足第一条的是工程任务（修掉就行），两条都满足的才值得成为研究。

其中两条值得展开，因为它们的选择在实践中经常被做成另一个。

### 关于第 2 与第 3 条的完整论证（为什么记录要极简且与整理分离）

替代方案是记录时就填一张完整表单（现象、条件、影响、复现步骤、初步分析）。它在记录质量上更好，而在两个地方失败。

第一，它发生在最不合适的时刻。观察出现的时刻通常是运行中（正在等结果、正在看日志），而填表需要二十秒以上的专注——那时的每一个额外字段都会降低记录的概率（0.5.3 的第一条）。

第二，它把两种不同的认知活动混在一起。"看到异常"是识别，"分析异常"是推理，而在识别阶段插入推理会污染记录（1.4 的第一步：描述里混入解释）。分离之后，记录保持客观，而分析时不至于被自己的第一印象束缚。

分离的代价是存在一个中间态（原始记录尚未整理），而它的处置是定期的整理时机（4.6 的复盘周期）。这条设计让记录的成本降到几秒钟，而它换来的是绝大多数观察被留住——这正是本篇开头那张表里最大的那一格（被忽略的十八条）。

### 关于第 9 与第 11 条的完整论证（为什么允许挂起但要求留痕）

替代方案有两个极端：立刻深挖（不允许挂起）或静默绕过（不留痕）。两者的代价不同，而后者更严重。

立刻深挖的问题是与当前目标的偏离——它把一个"有意思"的现象置于"要做的事"之上，而当现象不频繁时，深挖的收益小于它耽误的工作。因此挂起是必要的。

静默绕过的问题是它同时失去了两样东西：原因（不再被追问）与记录（没有留下任何线索）。它的表现是 1.2 的技术债——几个月后会出现一处"不知道为什么要这样写"的代码，而它与 4.7 的 L9 里那条"机制在缺少纪律时退化"是同一类问题。

正确的做法是允许挂起但要求留痕：一行记录（现象加条件）加一个状态（`deferred`）。它的成本是一分钟，而它把"绕过"变成了"待处理"——两者的差别在几个月后显现。

### 3.2 记录与整理

记录与整理已在 1.3 给出（`quickNote` 与 `organize`）。它们的衔接要点是容忍不完整记录：

```ts
export function parseLooseLine(line: string): Observation | null {
  const m = /^- (\S+) (.*)$/.exec(line)
  if (!m) return { id: newId(), what: line, conditions: {}, reproducible: false, disposition: 'logged' }   // 无时间戳也保留
  return { id: newId(), what: m[2], conditions: {}, reproducible: false, disposition: 'logged', rawAt: m[1] }
}
```

三种输入都被接受（标准格式、无时间戳、完全自由的文本）——记录系统的第一原则是不丢，而结构化程度可以在整理时提升。

### 3.3 转化与验证

```ts
export function translate(t: Translation, ctx: Context): { ok: boolean; issue?: string; formulation?: Formulation } {
  const check = validateTranslation(t)                         // 1.4 的四条校验
  if (!check.ok) return check
  const obs = ctx.observations.byId(t.observation)
  if (!obs.reproducible) return { ok: false, issue: '现象不可复现：先构造最小反例' }
  if (!t.formulation) return { ok: false, issue: '尚未写成三要素表述（回到第二步）' }
  ctx.appendEvent({ type: 'observation/translated', observation: obs.id, formulation: t.formulation.id, at: ctx.now })
  return { ok: true, formulation: t.formulation }
}

export function checkClaim(claim: MechanismClaim, ctx: Context): string[] {
  const issues: string[] = []
  if (claim.predicts.length === 0) issues.push('机制假设必须给出至少一个可证伪的预测')
  if (!claim.competing || claim.competing.length === 0) issues.push('必须列出竞争假设')
  if (!claim.discriminatingTest) issues.push('必须给出能区分本假设与竞争假设的实验')
  return issues
}
```

两处校验的风格一致：要求"下一步可做"而不是"描述完整"（不可复现就先去构造反例，没有竞争假设就先找它们）。

## L4 运行与验证

### 4.1 三层验证

第一层是契约测试：按 3.4 的十二条判据逐条检查（第 12 条需要人工产出）。

第二层是记录密度验证：在一段真实开发时间里（例如一周）统计记录条数。条数为零通常说明记录入口太远（0.5.3 的第一条），而条数过多（每几十分钟一条）说明门槛太低（5.2 的决策一）。

第三层是转化练习：从记录里选三个观察，走完四步并给出命题。这一层是本篇唯一的实质检验——它同时检验记录质量（条件够不够复现）、排除方法（有没有做）、以及表述能力（三要素齐不齐）。

```powershell
node research/observations/organize.mjs               # 整理即时记录
node research/observations/validate.mjs               # 十二条判据
node research/observations/density.mjs --since=7d     # 记录密度
node research/observations/translate.mjs --obs=<id>   # 走一次转化
```

做完这一篇的标志有三条：十二条判据全部通过。一周内的记录条数落在合理区间（例如三到二十条）。以及三个观察成功转化为三要素齐全的命题。

## L9 仍未解决（这一篇自己的缺陷）

| 缺陷 | 后果 | 修法 | 当初为什么这么写 |
|---|---|---|---|
| 记录密度依赖个人纪律 | 没有纪律时记录为零 | 与 4.6 的复盘周期绑定，复盘时检查密度 | 纪律问题没有纯技术解 |
| 平凡解释的列表靠经验 | 新手容易漏掉平凡解释 | 维护一份常见平凡解释清单 | 清单随系统变化 |
| 最小反例的最简化靠人工 | 跳过去之后反例含无关步骤 | 提供"逐条去掉"的辅助流程 | 自动化需要依赖分析 |
| 机制假设的竞争收集靠人 | 容易只提一个解释 | 用工具提示常见竞争类型（规模、顺序、选择偏差） | 竞争类型与领域相关 |
| 挂起的观察可能被遗忘 | 长期不处理 | 纳入待观察清单的过期提醒（4.4） | 需要复盘机制 |
| 转化成功率没有度量 | 无法判断方法是否有效 | 统计记录到命题的转化率 | 样本量小 |

第一条与第五条属于纪律与流程，第二条与第四条属于经验与提示，第三条与第六条属于自动化与度量。第一条值得单独标记：它意味着这套方法完全依赖人是否愿意记录——而记录的成本虽然被压到很低（一行），它仍然是一个需要在当下分心一次的动作。

技术能做的只有把成本压到最低，而不能替人做这个决定——这条限制与 4.6 的"形式化复盘"、4.7 的"状态过时"是同一类：机制的失效往往是人的投入不足，而不是机制的设计缺陷。

## L10 提问训练

### 五个层次

| 层次 | 例子 |
|---|---|
| 事实 | 转化四步是什么？排除的三种方式是什么？ |
| 机制 | 为什么描述现象时不能混入解释？ |
| 设计 | 为什么记录与整理要分离？ |
| 系统 | 如果一个团队的记录密度为零，说明什么？ |
| 科研 | 能不能量化"记录密度"与"问题产出率"的关系？ |

### 五种提问模板

反例逼问：如果没有写下预期，哪一类发现会消失。

边界追问：一个现象要复现到多小才算最小反例。

代价追问：要求列出竞争假设，代价落在谁身上。

替代对比：为什么用挂起而不是立刻深挖。

验证追问：怎么证明"这个机制假设是对的"。

### 本篇引出的十二个问题

读懂层。 第一，意外、异常与无声偏离的区别是什么？第二，转化四步是什么？第三，排除的三种方式是什么？

重建层。 第四，为什么记录字段要最少？第五，为什么描述里不能有解释？第六，为什么要求至少三个解释且含平凡的？

设计层。 第七，最小反例的四个标准是什么？第八，机制问题的验证方式是什么？第九，为什么要求竞争假设？

评审层。 第十，拿到一段现象描述，你会先检查哪一处？第十一，怎么判断一个观察值得研究？第十二，如果有人说"这个偶发问题不用管"，你怎么回应？

### 问题升级练习

模糊问题：「我想做点研究，但不知道从哪开始。」

升级后的精确问题：

> 从实践中得到研究问题至少包含三件互相制约的事：**注意**（有没有预期，因此有没有意外）、记录（成本够不够低，因此观察是否留得下来）、以及转化（能不能排除已知解释并写成命题）。
> 第一件与第二件互相制约——写下预期本身就需要一点记录，而记录成本高时人连预期都不写。
> 我能不能为这三件事各找出一条**可检查的判据**？
> 特别是：有没有哪一条判据，是**能让别人验证"这个现象你也应该看到"的**？

提升点说明：原问题无法回答，因为"从哪开始"没有起点。升级后的版本把它拆成三件具体的事，指出注意与记录的相互依赖，并追加以一个更强的问题：哪一条判据能让别人也看到这个现象——因为只有那一条能把个人经验变成共享的知识。

## L11 系统影响回溯

回看第 0.5 节的三个连锁影响。

| 预判 | 本篇分析之后的结论 | 状态 |
|---|---|---|
| 观察密度取决于记录成本 | 确认，并给出"一行记录加定期整理"这条设计 | 成立 |
| 意外只出现在有预期的运行里 | 确认，并把它作为本篇的方法起点（先写预期再运行） | 成立 |
| 转化失败的观察会以更大规模回来 | 确认，并给出"挂起而非绕过"这条处置 | 成立 |

一处需要修正的预判：0.5.2 把"观察记录"标为对 6.1 的强依赖。读完之后要补一层方向：依赖是反向的——6.1 的问题清单与 6.4 的观察记录是同一份素材的两个状态（未转化与已转化），因此它们应当共用存储而不是各存一份。

处置方式是在观察记录里加一个字段指向它转化成的命题（3.3 的 `observation/translated` 事件已经这样做了），而这条统一让"有多少观察尚未转化"成为一个可查的量。

全课程收口的桥。 三卷到六卷的四篇科研出口到此完整：6.1 给出问题的形式（三要素与分界判据）、6.2 给出检验的方法（基准、消融与统计）、6.4 给出问题的来源（观察与转化）。三者合起来是一个闭环：观察 → 命题 → 实验 → 新的观察。

而这条闭环与课程开头的判断力（第 1 卷）、最小闭环（第 2 卷）、可靠性（第 3 卷）、学习进化（第 4 卷）、规模化（第 5 卷）的关系，可以用一句话说明：前面五卷建立的是一个能被观察、能被度量、能被改进的系统，而这最后一卷把"观察"这件事本身变成了生产能力。回到 0.2 的毕业标准，它的最后一条说的正是这件事——五环齐备且有门控，并且能给自己提出问题。

### 二、情境绑定：当你……就想起……

| 当你…… | 立刻想起 |
|---|---|
| 准备跑一次改动 | 先写一句预期（它制造意外的可能） |
| 看到与预期不符的结果 | 一行记录下来，先不分析 |

| 要别人复现 | 给最小反例：每一条步骤都在起作用 |
| 提出一个机制假设 | 列出竞争假设与区分实验 |
| 假设无法被证伪 | 它只是重述了现象 |

## 本篇新词

开放问题（open problem） 在这里指"当前没有公认答案、且答案不只是更多工程投入就能得到"的问题。判断一个问题是开放问题还是工程难题，有一个可操作的判据：如果把资源放大十倍，答案会不会自然出现——会的是工程难题，不会的才可能是开放问题。

问题的精确表述（precise formulation） 指把一个问题写成可检验的形式：它必须包含可控的自变量、可观测的因变量、以及明确的比较基准。三者缺一时问题无法被回答——"agent 怎么才能更可靠"不是精确表述，因为它没有自变量。

可回答性（answerability） 指一个问题在现有工具与数据下能否被回答。它与难度不同：有些难问题可回答（只是成本高），有些看似简单的问题不可回答（因为缺少测量手段）。区分两者的关键是有没有可观测的因变量。

测量手段（measurement instrument） 指能得到因变量数值的机制。它是可回答性的核心——没有测量手段的问题只能停留在论述层面，而论述无法被证伪。本课程反复出现的一条判断（3.6 的"没有度量则机制无法被验证"）在这里变成了一条科研判据。

饱和（saturation） 指基准上的表现已经接近上限，因此它无法再区分方法。它与"任务被解决"不同：饱和通常意味着任务集太窄或太易，而不是能力已经足够。

污染（contamination） 指评测数据进入了训练数据，因此分数不再反映能力。它是评测的长期威胁，而它的处置（去污染、动态生成任务）本身也是一个开放问题。

工程难题与研究问题的分界 指一条判断：需要新知识的问题与研究问题相区分。多数工程难题的答案形式是"做得更好"，而研究问题的答案形式是"我们知道了一件事"——后者可以被引用、复现与推广。

### 0.1 一个具体的判断：工程难题与研究问题的分界

下面这张表把前五卷 L9 里的条目分成两类。

| 条目（来源） | 放大十倍资源会怎样 | 分类 |
|---|---|---|
| 能力集上限缺乏数据（5.1） | 会：跑更多部署就能测出来 | 工程难题 |
| 检索权重是手工超参（4.1） | 会：更多标注就能自动调参 | 工程难题 |

这张表说明一条实用判断：多数 L9 条目是工程难题（资源放大就能解决），而少数几条的困难在于缺少可观测的定义——那几条才是本篇要展开的开放问题。"缺少测量手段"是这一篇里最重要的判据。

### 0.2 本篇建立的三项判据

第一项用于判断一个问题是否精确：问"它的自变量是什么、因变量是什么、跟什么比"。三者答不齐时问题需要重写，而重写的方向通常是缩小范围直到三者具体。

第二项用于判断一个问题是否可回答：问"用什么测出因变量的数值"。答不出测量手段的问题不可回答，而它的处置是先解决测量（那本身可能是一个有价值的问题）。

第三项用于判断一个问题的答案是否有意义：问"如果答案是 A 或 B，会有不同的行动吗"。两种答案导致相同行动时，问题不值得做——这条判据排除了一类"听起来重要但没有决策影响"的问题。

### 0.3 十分钟练习：把模糊问题改写成精确表述

下面这段代码用三个必填项校验一个问题表述是否完整。

```js
function check(formulation) {
  const missing = ['independent', 'dependent', 'baseline'].filter((k) => !formulation[k])
  if (missing.length) return { ok: false, issue: `缺少：${missing.join('、')}` }
  const measurable = typeof formulation.instrument === 'string' && formulation.instrument.length > 0
  return {
    ok: measurable,
    issue: measurable ? null : '缺少测量手段（因变量无法被观测）',
    decisionImpact: formulation.ifA !== formulation.ifB,
  }
}

const formulations = [
  { claim: 'agent 怎么才能更可靠' },
  { independent: '压缩阈值', dependent: '任务成功率', baseline: '无压缩' },
  {
    independent: '压缩阈值',
    dependent: '任务成功率与单任务 token 成本',
    baseline: '无压缩',
    instrument: 'scripts/check-lecture.mjs 一类的可运行判据 + 任务集的两次运行',
    ifA: '提高阈值（更少压缩）',
    ifB: '降低阈值（更早压缩）',
  },
]

for (const f of formulations) console.log(f.claim ?? f.independent, '→', check(f))
```

三条输出对应三种状态：第一条缺三要素（它是论述而不是问题）、第二条缺测量手段（它可被讨论但不可被回答）、第三条完整（它同时给出了两种答案对应的不同行动）。

> **面试视角**
> **高频问法**："你觉得 agent 领域最值得做的问题是什么？"
> **高分要点**：给出一个三要素齐全的表述，并说明它的测量手段与决策影响。只说一个方向（"长程规划"）会被追问到答不上——方向不是问题。

### 0.5.3 三个连锁影响

第一，开放问题的清单会随工程进展而变。 今天不可回答的问题（缺少测量手段）在某个测量被建立之后就变得可回答——因此"现在不做"与"永远不做"是两种不同的判断。本课程第 3 卷建度量、第 4 卷建复盘，正是为了让一批问题从"不可回答"变成"可回答"。

第二，把工程局限写成开放问题有一个风险：把"我没做好"说成"这是难题"。 两者的区别是判据（0.1 的资源放大测试），而它必须被认真使用——否则清单会变成一个免责清单。

第三，问题清单会引导注意力，而注意力是有限资源。 一份包含二十个问题但只有一个可行的清单，实际效果低于一份只列三个可行问题的清单。因此清单需要排序判据，而排序依据是"可回答性 × 决策影响"。

### 0.5.4 它与本书其余部分的关系

本篇讨论的是 agent 系统的开放问题，而它不涉及这些问题的具体解法（那需要真正的研究工作）。它是课程与研究工作之间的接口，而这条接口的形态是"把工程经验翻译成可检验的命题"——本课程不承诺教会研究，但它承诺让读者在看完一段工程经验之后能说出它留下了什么可以被检验的问题。

> **面试视角**
> **高频问法**："你在做的这件事，最难的地方是什么？"
> **高分要点**：把它表述成一个三要素齐全的问题，并说明"为什么现在没有答案"。这条回答的形态本身就是一种能力展示——它说明你不只在做，还在想它在知识上的边界。

## L0 要解决的问题

### 0.1 现象一：有经验而提不出问题

第一个现象很普遍：做过很多系统的工程师在被问"你觉得什么值得研究"时说不出来。他们的经验丰富，而从经验到问题的转化没有发生。

它的成因有两个：缺少分界判据（把工程难题当成研究问题，于是在已经能解决的地方反复发力）、以及缺少表述能力（有一个模糊的方向但无法写成可检验的形式）。两者的修法都在 1.1 与 1.2。

### 0.2 现象二：问题听起来重要而无法回答

第二个现象是问题不可回答。它的形态是一句听起来很重要的话（"agent 怎么做长期规划"），而追问下去会发现没有测量手段——没有人知道"长期规划能力"的数值从哪来。

修法是 0.2 的第二项判据：先问怎么测。答不出时有两个选择：换一个问题，或者把测量手段本身当作问题（后者常常是更有价值的一条路）。

### 0.3 现象三：同一个问题被反复讨论而没有进展

第三个现象是讨论循环。一个问题在多个团队被反复讨论，每次都得出一致的定性结论（"这很难"），而没有人推进它——因为没有把它拆成可检验的子命题。

拆解的判据是"自变量能不能被控制"：一句"这很难"可以被拆成若干个"如果改 X，结果会不会变"——而每一个这样的子命题都是可检验的。

### 0.4 现象四：把工程问题当成开放问题

第四个现象是反向的错误：把可以用更多工程投入解决的问题说成"需要研究"。它的代价是资源被投向了本质上是工程的地方（编写更多代码、测更多数据），而这些问题本来会自然解决。

修法就是 0.1 的资源放大判据。它的使用需要诚实：回答"放大十倍资源会不会解决"时，人倾向于说"不会"（因为那让工作显得更难更重要）。

### 0.5 这一篇要正面回答的四个问题

第一，怎么区分工程难题与开放问题（1.1）。第二，好问题的形态是什么（1.2、1.3）。第三，具体有哪些开放问题（1.4–1.7）。第四，从哪一条开始（1.8）。

四个问题里前两个是可以被"学会"的（它们有判据），后两个依赖判断与时机。

## L1 设计与原理

### 1.1 工程难题与研究问题的分界

三条判据，按可靠性排序。

判据一是资源放大测试：把资源（人力、时间、算力、数据）放大十倍，答案会不会自然出现。会的是工程难题。这条判据容易被滥用（见 0.4），因此它需要第二、三条配合。

判据二是测量手段的存在性：因变量有没有可观测的来源。没有测量手段的问题，资源放大也不会让它可回答——这是两条判据里更硬的一条。

判据三是答案的形态：一个研究问题的答案是"我们知道了一件事"（可被引用、复现、推广），而一个工程难题的答案是"这一处做得更好了"。两者都能产生价值，而它们的传播方式不同——前者进入文献，后者留在代码里。

三条合起来给出的判据链是：先看有没有测量手段（没有则是开放问题或者根本不可回答），再看资源放大（会解决则是工程难题），最后看答案形态（决定它是不是值得写成问题）。

### 1.2 问题的三要素与它们的来源

三要素（自变量、因变量、基准）与它们的写法要求。

自变量必须是可控制且可变的。它通常来自系统的某个可调参数（阈值、策略、结构），而它的要求是"能在保持其他条件不变的前提下改变它"——做不到这一点时，实验无法归因（这与 4.5 的"改善大于两倍噪声"是同一个要求的两种表述）。

因变量必须是可观测且与自变量有机制联系的。"任务成功率"、"单任务 token 成本"、"恢复耗时"都是可观测的。"理解深度"、"用户体验"不是——它们需要先被操作化。

基准必须是明确的对照组。它有三种形态：无该机制（消融）、另一方法（对比）、以及同一方法的另一配置（参数扫描）。没有基准的实验只能给出数值，不能给出结论。

三者的写法合起来就是 0.3 的练习里那条完整表述：`压缩阈值 → 任务成功率与 token 成本，对照无压缩`。

### 1.3 测量手段：为什么它是最稀缺的一环

三要素里最难满足的是因变量的观测（0.2 的分析）。三类测量手段与它们的成本。

可运行判据（测试、检查脚本、断言）成本最低，而它只适用于有确定成功条件的任务——这是本课程在第 1 卷起就反复强调"成功判据"的科研理由（4.4 的失败判定、4.6 的任务集构建都依赖它）。

人工标注成本中等，适用于主观质量的判断，而它的限制是规模（标注量与结论强度成正比，而标注不可无限扩张）。

模型评判（让模型打分）成本低而可靠性存疑——它的失效方式是系统性偏好（模型倾向于某些长度、某些风格），而校准它的方法是用人工标注的小样本测量它的偏差（这条方法本身就是 6.2 的一个题目）。

```ts
interface MeasurementInstrument {
  readonly kind: 'check' | 'human-label' | 'model-judge'
  readonly costPerSample: 'low' | 'medium' | 'high'
  readonly throughputPerDay: number
  readonly knownBias?: string                      // 已知偏差（模型评判通常必须有）
  readonly calibration?: { samples: number; agreement: number }   // 与人工标注的一致度
}
```

四个字段里 `knownBias` 与 `calibration` 是模型评判的必需项——一个没有被校准的模型评判得到的分数不可用于比较（因为它的偏差可能恰好与被比较的两个方法相关）。

### 1.4 第一组问题：状态与记忆

三条，它们都落在"缺少可观测定义"这一侧（0.1 的分界）。

问题一：目标漂移的检测。 精确表述：给定一段跨会话的任务历史，能否用一个可计算的量（因变量）判断目标是否发生了语义漂移，而该量在人工判定的漂移与不漂移之间可分离。为什么没有答案：漂移的定义本身依赖语义理解，而没有公认的操作化。缺什么：一个人工标注的漂移数据集与一个可分离的度量。

问题二：记忆条目的冲突判定。 精确表述：给定两条记忆，能否判断它们矛盾，以及这种判断的准确率与阈值的关系。为什么没有答案：矛盾不是相似度问题（相似的两条可以矛盾，也可以一致），而语义矛盾判定缺少可靠方法。缺什么：矛盾判定的标注语料与它的错误分析。

问题三：状态过时的检测。 精确表述：能否从会话日志与产物推断"外部状态已经变化而系统状态没有更新"。为什么没有答案：它要求"状态一致性"这一概念的可观测化，而多模态的信号（文件、外部服务、人的行为）难以统一。缺什么：一个能表达"状态与实际不同步"的度量。

### 1.5 第二组问题：评测

三条，它们落在"测量手段"这一侧。

问题四：长程任务的成功判定。 精确表述：一个跨多会话的任务，其成功率的定义（分母是什么）如何影响不同方法之间的比较。为什么没有答案：长程任务的成功是分层的（部分完成也有价值），而现有基准多用全或无的判定。缺什么：部分完成的度量与它对结论的影响分析。

问题五：基准的饱和与污染。 精确表述：如何检测基准分数已不再反映能力（饱和或污染）。为什么没有答案：检测需要独立的信号，而"独立"的定义本身是难点。缺什么：可验证的去污染方法与饱和的判定标准。

问题六：成本与质量的联合比较。 精确表述：在成本不同的两个方法之间，如何给出可比较的结论（帕累托前沿的形式）。为什么没有答案：现有报告多给单一数值（成功率或成本），而两者不可互换（预算约束依场景不同）。缺什么：报告规范与比较方法。

### 1.6 第三组问题：上下文与决策

三条，它们落在"机制与效果的联系"这一侧。

问题七：压缩决策的质量。 精确表述：压缩哪些内容的选择，能否用一个可计算的准则优化（而不是按时间或长度）。为什么没有答案：压缩的目标（"保留对后续有用的信息"）依赖于后续是什么，而后续未知。缺什么：一个可检验的压缩目标函数与它的实证效果。

问题八：上下文的顺序效应。 精确表述：同一组内容的不同排列对结果的影响有多大，以及能否预测。为什么没有答案：已知存在位置效应（首尾更强），而它的机制与可预测性不明。缺什么：系统的排列实验与解释（它与 3.6 的缓存命中率优化直接相关——稳定前缀与位置效应可能冲突）。

问题九：注入预算的分配。 精确表述：记忆、技能与历史的预算分配如何影响结果，以及最优分配是否依赖任务类型。为什么没有答案：它与问题七、八交互，而三者的实验设计会迅速变大。缺什么：可控的实验设计与成本上界。

### 1.7 第四组问题：安全、自我修改与多执行者

两条，它们落在"约束与能力的关系"这一侧。

问题十：元控制边界的调整。 精确表述：自我修改系统的边界（4.5 的四类对象）如何随能力变化调整，而不被逐步侵蚀。为什么没有答案：边界调整本身需要判断，而把它形式化会立即遇到"谁来调整调整规则"的递归。缺什么：一个可分析的形式化与它的攻防分析。

问题十一：多执行者的结果合并。 精确表述：多个 agent 的产出如何合并，以及合并策略对最终质量的影响。为什么没有答案：合并语义依赖产出格式，而格式的通用标准尚未出现。缺什么：可比较的合并策略实验（5.4 的"受控模式"给了一种实验设计）。

### 1.8 从哪一条开始

排序判据是可回答性 × 决策影响（0.5.3 的第三条），而两者都可以粗粒度估计。

| 问题 | 可回答性 | 决策影响 | 建议 |
|---|---|---|---|
| 四（长程成功判定） | 高（改判据即可实验） | 高（影响所有长程比较） | 优先 |
| 八（顺序效应） | 高（排列实验成本可控） | 中高（与缓存优化冲突） | 优先 |
| 六（成本质量联合） | 高（报告规范即可） | 中 | 可做 |
| 七（压缩决策） | 中（目标函数待定） | 高 | 中等 |
| 一、二、三（状态类） | 低（缺操作化） | 高 | 需先解决测量 |
| 十、十一 | 低 | 中高 | 长期 |

这张表的读法值得说明：可回答性高的几条恰好是"改判据与改报告"这类看起来不那么"研究"的工作——而它们的影响面很广（所有涉及长程比较的结论都依赖问题四的答案）。这条观察本身是一个判断：在测量手段稀缺的领域，建立测量比提出机制更有杠杆。

### 1.9 问题的三个来源与它们的产出率

来源一：自己已完成工作的 L9（仍未解决）。它的产出率最高，因为那些条目已经带着具体的语境（什么系统、什么规模、观察到什么现象），而语境是精确表述的原料。本课程的第 3 卷与第 4 卷之所以各写一节 L9，一半的动机就在这里。

来源二：实验里的意外（6.2 的 L11 桥）。它的形态是"不该失败的任务失败了"或"两个指标朝相反方向动"。它的产出率高而成本高——意外只在有记录、可复算的实验里出现（没有原始结果的实验里，意外会被当成噪声丢掉）。

来源三：与已有知识的对照。它的形态是"已知的机制在这里不成立"。它的产出率中等而它需要的准备最多（要先知道已知的机制是什么）。

三个来源的共同要求是先把一件事做到它的边界——没有边界的经验产生不出问题（0.1 的第一个现象）。这条要求给出一个反直觉的建议：想找题目时，先把手上的事做完而不是先读更多文献。
三个来源的产出率差异还有一层含义：**它们要求的准备不同**。来源一要求把工作做到看得见边界（因此它依赖 L9 那类记录的纪律），来源二要求实验设施齐备（因此它依赖 6.2 的原始结果保留），来源三要求对已有结论的熟悉。

**先做哪一个来源，取决于手上已经有什么**——而这与 1.8 的排序判据合起来，构成"选题目"的两步：先看能出问题的来源，再在出现的问题里按可回答性排序。

### 关于第 3 与第 8 条的完整论证（为什么优先选已有测量手段的因变量）

替代方案是先定义理想的因变量（"真正的理解"、"可靠的规划"），再去寻找它的测量。它更贴近问题的本质，而它的代价在时间上。

第一，理想因变量常常永远得不到测量。它们对应的概念（理解、可靠）在人的评价里依赖语境，而要把它们操作化需要先解决一堆更基础的问题——于是研究变成了元研究。

第二，可用的测量手段往往能部分回答理想问题。例如"压缩决策的质量"（问题七）难以直接测，而"压缩后任务成功率与成本"可测——后者虽然不完美，但它限制了可能答案的范围（如果压缩完全不损害成功率，那么很多关于压缩质量的担心就不成立）。

第三，测量的建立本身就是可发表的成果（1.8 的观察）。把"先建立测量"作为第一条路径，产出的是让别人也能做研究的东西，而它的影响面通常比多做一个方法大。

第 8 条（记为"现在不可回答"而不是放弃）是这个选择的配套：它让清单成为一个路线图（哪些测量需要先建立），而不是一个结论列表。

### 关于第 6 与第 7 条的完整论证（为什么清单要短且按可回答性排序）

替代方案是列一份完整的重要问题清单。它在讨论时很有用，而在执行时有三个问题。

第一，注意力被分散。二十条问题里每条只分到百分之五的注意力，而研究进展通常来自在一条上连续投入。

第二，"重要性"是主观的而"可回答性"相对客观。按重要性排序会让清单变成一场关于什么更重要的辩论（没有收敛判据），而按可回答性排序可以得到行动。

第三，短清单强迫取舍。列出三条意味着放弃了十七条，而那个放弃决定是有信息的——它迫使提出者判断哪些问题现在不做（与 4.7 的"唯一下一步"是同一个手法：让选择显式发生）。

结论：清单的价值不在于全，而在于它能被开始。

## L3 实现（施工图）

### 3.1 文件结构

```
// research/open-problems.md        ← 问题清单（本篇的产出物）
// research/instruments/            ← 测量手段的实现（每个一段代码加它的校准）
//   ├─ check-based/                ← 可运行判据类
//   ├─ human-label/                ← 人工标注的规程与语料
//   └─ model-judge/                ← 模型评判与它的校准记录
// research/formulations/           ← 每个问题的三要素表述（代码形式，可被校验）
```

这套结构与代码工程的目录结构同形，而它的价值是让"研究进展"也可被 diff（问题表述的改动、校准数据的更新都留下痕迹）——这与 4.5 的"提议要可评审"是同一条原则。

### 3.2 问题表述的校验

```ts
export interface Formulation {
  readonly id: string
  readonly claim: string                                        // 一句话问题
  readonly independent: { name: string; values: readonly unknown[] }   // 自变量与它的取值
  readonly dependent: { name: string; instrument: string }             // 因变量与它的测量手段
  readonly baseline: { kind: 'ablation' | 'comparison' | 'sweep'; what: string }
  readonly decisionImpact: { ifA: string; ifB: string }                // 两种答案对应的不同行动
  readonly whyOpen: string                                             // 为什么现在没有答案（1.4–1.7 的写法）
  readonly missing: readonly string[]                                   // 缺什么
}

export function validateFormulation(f: Formulation, ctx: Context): string[] {
  const issues: string[] = []
  if (f.independent.values.length < 2) issues.push('自变量至少需要两个取值')
  if (!ctx.instruments.has(f.dependent.instrument)) issues.push(`测量手段不存在：${f.dependent.instrument}`)
  if (f.decisionImpact.ifA === f.decisionImpact.ifB) issues.push('两种答案导致相同行动：问题无决策影响')
  if (!f.whyOpen || f.whyOpen.length < 20) issues.push('需要说明为什么现在没有答案')
  if (f.missing.length === 0) issues.push('需要说明缺什么（测量、数据或方法）')
  return issues
}
```

五条校验与 0.2 的三项判据对应，而最后两条（为什么没有答案、缺什么）是这一篇的要求——它们是区分"研究问题"与"待办事项"的字段。

### 3.3 清单的排序与更新

```ts
export function rank(list: readonly Formulation[], scores: Map<string, { answerability: number; impact: number }>): Formulation[] {
  return [...list].sort((a, b) => {
    const sa = scores.get(a.id)!, sb = scores.get(b.id)!
    return sb.answerability * sb.impact - sa.answerability * sa.impact      // 可回答性乘决策影响
  })
}

export function updateStatus(list: readonly Formulation[], ctx: Context): Formulation[] {
  return list.map((f) => {
    const instrument = ctx.instruments.get(f.dependent.instrument)
    // 测量手段出现即从"不可回答"转为"可回答"（0.5.3 的第一条）
    return instrument?.available ? { ...f, blockedOn: undefined } : { ...f, blockedOn: f.missing[0] }
  })
}
```

`updateStatus` 是清单能被长期使用的关键——它让"现在不可回答"变成了一个会变化的状态，而不是一个终局判断。

### 3.4 验收判据

| # | 判据 | 怎么检查 |
|---|---|---|
| 1 | 每条问题三要素齐全 | 跑 `validateFormulation` |
| 2 | 自变量至少两个取值 | 同上 |
| 3 | 因变量有已实现的测量手段 | 核对 `instruments` |
| 4 | 基准属于三种形态之一 | 核对 `baseline.kind` |
| 5 | 两种答案给出不同行动 | 核对 `decisionImpact` |
| 6 | 说明为什么现在没有答案 | 核对 `whyOpen` |
| 7 | 说明缺什么 | 核对 `missing` |
| 8 | 清单按可回答性乘影响排序 | 核对顺序 |
| 9 | 状态随测量手段的出现而更新 | 注册一个测量手段并核对状态 |
| 10 | 每条问题能被独立检验 | 用问题四做一次最小实验（10.3 的设计） |

第 1 至 7 条是形式校验，第 9 与第 10 条检验它是否真能被推进（一条从未被任何实验触及的问题，其可回答性是未经验证的）。

### 3.5 清单的维护与它的两种失效

清单有两种相反的失效，而它们的处置不同。

第一种是免责化：把"没做好"写成"这是难题"。它的信号是清单里的问题长期停留在"缺少测量手段"，而没有人在建立那个测量。处置是定期对每条问题重做资源放大测试（1.1 的判据一），并把"谁在解决阻断项"写进清单——一条问题如果没有对应的阻断项工作，它实际上是一条免责声明。

第二种是僵化：清单长期不变。它的信号是版本历史里只有新增没有状态变化。处置是把清单接进 4.6 的复盘——每轮复盘检查一次"有没有新的测量手段让某条变得可回答"，而那正是测量手段会被引入的时机。

清单的三种更新动作与它们的判据：新增（来自新工作的 L9 或实验里的意外，判据是三要素齐全）、状态变化（阻断项被解决，判据是测量手段已实现）、以及删除（被解决或不再重要，判据是被解决时有可运行的检查）。

## L4 运行与验证

### 4.1 三层验证

第一层是形式校验：按 3.4 的十条判据逐条检查清单。

第二层是外部可读性验证：把清单给一个不了解本课程的人看，核对他能说出"每条问题的自变量与因变量是什么"。这条判据与 4.7 的状态检查同形——表述的自包含性只能靠一个外部读者检验。

第三层是最小实验：从清单里选一条（1.8 建议的问题四或八），做一次最小规模的实验，看能否得到一个方向性结论。这一层是清单是否活着的唯一证据——不能做的清单等于一篇论述。

```powershell
node research/validate.mjs                      # 形式校验（十条判据）
node research/rank.mjs                          # 排序
node research/instruments/status.mjs            # 测量手段的可用状态
node research/experiments/long-horizon-min.mjs  # 最小实验（问题四）
```

### 4.2 判据

做完这一篇的标志有三条：十条判据全部通过。外部读者能说出每条问题的三要素。以及一次最小实验得到方向性结论（无论结论是什么，只要有方向就说明问题可回答）。

## L5 语法速查

### 5.1 术语表

| 术语 | 在本篇里的准确含义 | 容易误解为 |
|---|---|---|
| 开放问题 | 缺少知识而非缺少投入的问题 | "难题"（难题可能是工程性的） |
| 精确表述 | 自变量、因变量、基准齐全 | "写清楚"（它要求三要素） |
| 可回答性 | 有可观测的因变量 | "难度" |
| 测量手段 | 得到因变量数值的机制 | "指标"（指标是数值，手段是产生它的东西） |
| 饱和 | 基准分数不再有区分度 | "已解决" |
| 污染 | 评测数据进入了训练数据 | "过拟合"（那是模型对训练集） |

### 5.2 命令速查

| 目的 | 命令 | 说明 |
|---|---|---|
| 校验问题表述 | `node research/validate.mjs` | 十条判据 |
| 排序清单 | `node research/rank.mjs` | 可回答性乘影响 |

| 跑最小实验 | `node research/experiments/<name>.mjs` | 方向性结论 |

### 5.3 三条容易踩的规则

第一条，先看有没有测量手段。没有它的问题不可回答，而建立测量本身可能更有价值。

第二条，两种答案必须对应不同行动。否则问题没有决策影响。

第三条，清单要短并按可回答性排序。它的价值在于能被开始。

## L7 挑战题（不给答案）

第一题：为问题一设计测量。 漂移的自动检测缺少操作化。设计一个可实现的测量方案，并说明它的假阳与假阴来自哪里。

第二题：验证问题八。 设计一个排列实验回答"顺序效应有多大"，并说明它的成本与统计功效。

第三题：去污染。 设计一个能检测基准污染的方案，并说明它自己的失效条件。

第四题：成本与质量的报告规范。 给出一份报告模板，让两个成本不同的方法可被公平比较。

第五题：从本课程里再找三条。 翻看本课程任意三篇的 L9，判断它们的条目属于工程难题还是开放问题，并给出判据。

第六题：论证"这个问题不该做"。 选一个本课程提到的问题，说明它不值得做，并给出判据。

## L9 仍未解决（这一篇自己的缺陷）

| 缺陷 | 后果 | 修法 | 当初为什么这么写 |
|---|---|---|---|
| 可回答性与影响的评分是主观的 | 排序可能误导 | 用多人评分并报告一致度 | 早期无数据 |
| 清单来自本课程的范围 | 未覆盖本课程之外的重要问题 | 扩大来源（文献与社区） | 本篇的定位是从自己的经验出发 |
| 三要素判据对探索性研究偏严 | 早期探索难以写成三要素 | 允许"探索性条目"单独列表 | 判据是为可回答性服务的 |
| 测量手段的校准只在模型评判上要求 | 其他手段也可能有偏差 | 对三类手段都要求校准记录 | 可运行判据的偏差通常可忽略 |
| 没有跟踪清单的更新 | 状态会过时 | 与 4.6 的复盘周期结合 | 需要复盘机制 |
| 未覆盖"问题被解决"的判定 | 可能重复投入 | 用可运行的检查证明解决（L2 第 9 条） | 解决判定需要共识 |

第三条值得单独标记：它意味着这套判据对探索性研究不完全适用——真正新的方向在早期往往说不清自变量（因为还不知道什么在起作用）。处置是允许一份"探索性条目"列表，而它的判据不适用（它不需要三要素，只需要一个可观测的初步现象）。这条补充说明：判据的作用是筛掉不可回答的问题，而不是禁止探索。

## L10 提问训练

### 五个层次

| 层次 | 例子 |
|---|---|
| 事实 | 三条分界判据是什么？三要素是什么？ |
| 机制 | 为什么测量手段是最稀缺的一环？ |
| 设计 | 为什么清单要短并按可回答性排序？ |
| 系统 | 如果一个问题十年内都缺测量手段，该怎么处理？ |
| 科研 | 能不能量化"建立测量"对后续研究的杠杆有多大？ |

### 五种提问模板

反例逼问：如果把工程难题当成开放问题，会浪费什么。

边界追问：一个方向要拆到多小才算可检验。

代价追问：要求每条问题给出两种答案的行动，代价落在谁身上。

替代对比：为什么优先选已有测量手段的因变量。

验证追问：怎么证明"这份清单是活的"。

### 本篇引出的十二个问题

读懂层。 第一，三条分界判据是什么？第二，三要素是什么，各自的写法要求是什么？第三，三类测量手段与成本是什么？

重建层。 第四，为什么测量手段是最稀缺的？第五，为什么清单要短？第六，为什么排序按可回答性乘影响？

设计层。 第七，八组问题里哪几条可回答性高？第八，为什么"建立测量"可能比"提出机制"更有杠杆？第九，探索性条目为什么不适用三要素？

评审层。 第十，拿到一份问题清单，你会先检查哪一处？第十一，怎么判断一个问题是工程难题？第十二，如果有人说"这些问题太理论了"，你怎么回应？

### 问题升级练习

模糊问题：「我想研究 agent，但不知道从哪下手。」

升级后的精确问题：

> 选一个可研究的问题至少包含三件互相制约的事：**分界**（它是缺投入还是缺知识）、表述（自变量、因变量、基准是否齐全）、以及手段（因变量怎么测出来）。
> 第一件与第三件互相制约——判据越严格，能通过的问题越少，而剩下的问题往往依赖尚不存在的测量手段。
> 我能不能为这三件事各找出一条**可检查的判据**？
> 特别是：有没有哪一条判据，是**能让一个局外人验证"这个问题可回答"的**？

提升点说明：原问题无法回答，因为"从哪下手"没有判据。升级后的版本把它拆成三件具体的事，指出判据严格性与可做性之间的张力，并追加以一个更强的问题：哪一条判据能让局外人验证可回答性——因为只有那一条能排除自我说服。

## L11 系统影响回溯

回看第 0.5 节的三个连锁影响。

| 预判 | 本篇分析之后的结论 | 状态 |
|---|---|---|
| 开放问题的清单会随工程进展而变 | 确认，并给出"状态随测量手段出现而更新"这条实现 | 成立 |
| 把工程局限写成开放问题有免责风险 | 确认，并给出资源放大测试这条判据与它的诚实要求 | 成立 |
| 问题清单会引导有限的注意力 | 确认，并给出"短清单加可回答性排序"这条处置 | 成立 |

一处需要修正的预判：0.5.2 把"测量手段的判据"标为对 6.2 的强依赖。读完之后要补一层方向：两者的依赖是双向的——6.2 的实验方法要求测量手段存在，而本篇的许多测量手段（尤其人工标注与模型评判的校准）需要 6.2 的方法论才能建立。这条双向依赖意味着两篇需要交叉推进：先用手边最简单的测量（可运行判据）做小实验，再从实验里发现"缺哪种测量"，然后建立它。

通向下一篇的桥。 本篇给出了问题与判据，而它没有回答"怎么做实验"。一个三要素齐全的问题仍然可能被做错——样本太小、只报均值、比较多个方法而不校正、把随机波动当成发现。

下一篇 `6.2 实验方法：基准、消融与统计` 处理这件事。它与本篇的连接点有三处：三要素直接映射到实验设计（自变量是因素、因变量是响应、基准是控制组）、测量手段的可靠性决定实验的统计功效、以及"成本与质量的联合比较"（问题六）需要一套报告规范。

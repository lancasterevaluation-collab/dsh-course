# 6.4 从工程观察变成研究问题

> **这一篇讲什么**：研究问题不是凭空想出来的，而是从工程观察里"转化"出来的。这个转化有三个条件：意外（结果与预期不符）、唯一解释（排除了竞争假设）、最小反例（能稳定重复触发）。算例给出的判定很严格：三条全齐才算转化成功，缺一条就不算。

4. 频率判断的门槛：算例里记录 2 次得到 `undetermined`（"观测 2 次，不足 3 次"），3 次才得到 `estimated`（$rate = 0.667$）。

7. 三条件判定：齐备为 `true`，缺最小反例为 `false`。

## 一、为什么"奇怪的现象"不是研究问题

### 1.1 把噪声当发现

"这次特别慢"——**而单次观察无法区分"系统性变慢"与"这次恰好慢"。**

### 1.2 多个解释没排除

"缓存导致的问题"——**但也可能是网络或并发**。没有排除竞争假设时，这只是猜测。

### 1.3 无法复现

"当时确实出现了"——**但说不清在什么条件下出现**，所以别人无法验证，自己也无法研究。

这三件事分别对应：**频率判断、竞争假设排除、最小反例。**

## 二、转化的三个条件

| 条件 | 含义 | 缺了会怎样 |
|---|---|---|
| **意外** | 结果与预期不符 | 你只是在确认已知的事（信息量低，见 6.1） |
| **唯一解释** | 竞争假设被排除 | 无法确定要研究什么 |
| **最小反例** | 能稳定重复触发 | 无法验证，也无法研究 |

**三个条件是"与"的关系**（见 7.1）：缺任何一个，转化都不成立。

## 三、怎么做

### 3.1 记录校验

转化需要**多次运行的结构化记录**。算例验证：缺 `trials` 会报错。

一条记录至少要包含：

| 字段 | 作用 |
|---|---|
| 输入 | 这次跑的是什么 |
| 结果 | 观测到什么 |
| 预期 | 本来期望什么 |
| **多次（trials）** | **同一条件下的重复次数** |

"多次"是必需的：**没有重复就无法判断"这是偶发还是规律"**。这与 6.2 的"重复"原则是同一条。

### 3.2 意外检测

**意外 = 结果与预期不符。** 算例检出的意外是 `["a2"]`。

```js
// 意外检测：观测与预期偏离超过阈值即记为意外
export function detectSurprise(records, threshold) {
  return records.filter((r) => Math.abs(r.observed - r.expected) > threshold).map((r) => r.id)
}
```

算例还给出了异常判定的边界：

| 值 | 判定 |
|---|---|
| $x = 1.995$ | **异常（`true`）** |
| $x = 1.5$ | **非异常（`false`）** |

"阈值在哪里"必须显式设定：**它是"什么算异常"的定义。** 没有阈值时，每个偏离都可以被说成异常（这正是 1.1 把噪声当发现的成因）。

阈值怎么定：**用 6.2 的标准差与 6.3 的区间**——偏离超过若干倍标准差才算意外。

与 6.1 的呼应：**意外就是低概率事件发生了**，而它在信息论里的定义是 $I = -\log_2 P$（见 6.1 的 4.32）。

### 3.3 频率判断

**看到一次异常不等于它是规律。** 算例给出的门槛是 3 次：

| 观测次数 | 判定 |
|---|---|
| 2 次 | **`undetermined`**（"观测 2 次，不足 3 次"） |
| **3 次** | **`estimated`**（$rate = 0.667$） |

"3 次"这个门槛与本课程其他地方一致：**4.3 的用户建模门槛是 3、4.6 的同类失败触发是 3。** "一次偶然，两次可疑，三次是模式"这条经验在这三处都适用。

"不足时判为未确定"而不是"判为偶发"是重要的：**它与 4.4 的"无法判定成功时算失败"同源——不确定时不猜。**

频率估计 $rate = 0.667$ 的含义：3 次里 2 次出现，**但这个估计本身的不确定性很大**（见 3.5 的区间）。

### 3.4 排除竞争假设

**一个现象往往有多个可能解释。** 必须逐个排除。

算例实测：

| 项 | 结果 |
|---|---|
| 剩下 | **`["H1（缓存）"]`** |
| 已排除 | `["H2（网络）", "H3（并发）"]` |
| **是否唯一** | **`true`** |

排除的手段：

| 手段 | 做法 |
|---|---|
| **对照实验** | 改变一个因素，观察现象是否消失 |
| **消融** | 关掉某个机制，看是否复现 |
| **分层观察** | 按维度分组看现象是否只出现在特定组 |
| **时间对照** | 变前 vs 变后（见 4.4） |

"唯一性"是一个可检查的结论：**剩下的假设数恰好是 1。** 多于 1 时不能转化——因为不知道要研究哪一个。

与 4.4 的证据强度衔接：**排除竞争假设需要"反事实"级别的证据**（强度 ≥ 2），仅凭相关性排除不了任何东西。

### 3.5 最小反例

**最小反例 = 能触发这个现象的最小条件组合。** 算例给出的是 `["任务类型 A", "阈值 0.8"]`，尝试了 4 次才得到。

"最小"为什么重要：

| 收益 | 说明 |
|---|---|
| **可复现** | 条件少则容易复现 |
| **可研究** | 变量少则容易隔离因果 |
| **可传播** | 别人能照着做 |
| **调试更快** | 排查范围小 |

"尝试了 4 次"这个数字说明最小化是一个迭代过程：**每次删掉一个条件，看现象是否还在**。这与二分调试是同一个思路。

最小反例的写法：**一串具体的条件值**（而不是描述）。它应当可以直接用来跑一次实验。

### 3.6 三条件判定

实现如下。

```js
// 三条件判定：全齐才算转化成功
export function toResearchQuestion(observation) {
  const checks = {
    surprise: detectSurprise(observation),
    uniqueExplanation: observation.remainingHypotheses.length === 1,
    minimalRepro: observation.minimalRepro !== null,
  }
  return { ok: Object.values(checks).every(Boolean), checks }
}
```

算例实测：

| 情况 | 结果 |
|---|---|
| 三条件齐备 | **`ok: true`** |
| **缺最小反例** | **`{surprise: true, uniqueExplanation: true, minimalRepro: false}`** |

**注意输出是"每一条各自的结果"**，而不只是一个布尔值——这才可执行：它告诉你缺的是什么（与 6.1 的三要素校验、1.4 的契约校验同一个形式）。

三条件与 6.1 的关系：**转化成功后，这个观察就成为一个开放问题**，接下来要用 6.1 的信息量判断值不值得做、用 6.2 的方法设计实验、用 6.3 的指标评测。

**这就是第 6 卷四篇的完整链条。**

## 四、特殊情况与处理技巧

| 情况 | 为什么 | 处理 |
|---|---|---|
| 把偶发当规律 | 观测次数不足 | 三次以上才估计 |
| 每个偏离都算异常 | 无阈值 | 用标准差定阈值 |
| 多个假设并存 | 未排除 | 做对照实验排除 |
| 无法复现 | 无最小反例 | 迭代最小化 |
| 记录不全 | 缺多次记录 | 记录结构含 trials |
| 现象消失后无法研究 | 未及时固定 | 记录完整条件并保存环境 |
| 意外其实是 bug | 未排除实现问题 | **先排除自己的代码错误** |
| 转化后问题不值得做 | 未评估信息量 | 交给 6.1 判断 |

"先排除自己的代码错误"值得单独强调：**agent 系统里的大多数"意外"是 bug、环境差异或观测错误。** 在把它当作研究发现之前，必须先排除这种可能——否则会浪费大量时间去"研究"一个笔误。

判据：**用最小反例再跑一次，如果现象不稳定，先怀疑实现。**

## 五、工业界的做法（可照做）

### 5.1 从线上问题到研究问题

| 阶段 | 动作 | 产出 |
|---|---|---|
| **发现** | 指标异常、用户反馈 | 现象描述 |
| **确认** | 多次复现、排除环境 | 可信的现象 |
| **缩小** | 最小反例 | 可复现的样例 |
| **归因** | 排除竞争假设 | 唯一解释 |
| **转化** | 写成可研究的问题 | 研究问题（交给 6.1） |

"确认"这一步经常被跳过：**线上指标的一次异常，可能只是一次流量波动。** 不确认就归因，会得出错误结论。

### 5.2 复现包

工业界为了"可复现"发展出的实用形式是**复现包**：

| 内容 | 作用 |
|---|---|
| 最小反例 | 触发条件 |
| 环境描述 | 版本、配置 |
| 原始日志 | 完整证据 |
| 复现脚本 | 一键跑 |
| 预期与实际 | 便于判断 |

"一键跑的复现脚本"是最有价值的一项：**它把"可复现"从声明变成事实。**

这与本课程的做法一致：**每篇讲义都配 `node examples/*.mjs`，所有数字都来自可运行的算例。**

### 5.3 参数与设计起点

| 参数 | 推荐 | 依据 |
|---|---|---|
| 意外阈值 | 3 倍标准差 | 与 6.2 的标准差衔接 |
| 频率门槛 | 3 次 | 与 4.3、4.6 一致 |
| 复现要求 | 稳定复现 ≥ 3 次 | 见 3.3 |
| 假设数 | 降到 1 才转化 | 多则无法研究 |
| 最小反例 | 条件数尽量少 | 可复现 |
| 复现包 | 必带脚本 | 见 5.2 |

### 5.4 一份可落地的实施清单

1. **结构化记录**：输入、结果、预期、多次。
2. 意外阈值：用标准差定义，写进记录。
3. 频率门槛：三次以下标为未确定。
4. 竞争假设清单：先列全，再逐个排除。
5. 排除手段：对照、消融、分层、时间对照。
6. 唯一性判定：剩下恰好 1 个假设。
7. 最小反例：迭代删除条件，记录尝试次数。
8. 先排 bug：用最小反例复跑，确认不是实现问题。
9. 三条件判定：全齐才转化。
10. 复现包：最小反例 + 环境 + 日志 + 脚本。

## 六、学术界的结论

### 6.1 反例法

科学方法里，**反例的力量强于例证**：

> 一个反例就足以否定一个全称命题。

这与 1.4 的"判断破坏性用反例"是同一个逻辑：**找反例比证明"没有反例"可行得多。**

在 agent 研究里的应用：**要否定"这个机制在所有情况下都有效"，只需一个稳定的反例**——而最小反例就是这个反例的最强形式。

### 6.2 科学发现的路径

科学哲学里的经典模型（假说—演绎）与本篇的转化链对应：

| 阶段 | 内容 | 本课程对应 |
|---|---|---|
| **观察** | 发现异常 | 3.2 意外 |
| **假说** | 提出解释 | 3.4 竞争假设 |
| **演绎** | 推出可检验的预测 | 6.1 判别程序 |
| **检验** | 做实验 | 6.2 实验方法 |
| **评价** | 与预测比较 | 6.3 评测 |

"演绎"这一步常被跳过：**提出假说后必须推出"如果这个假说成立，应当观察到什么"**——这正是 6.1 的判别程序。

**跳过它会导致"无论观察到什么都能解释"**，而那样的假说不可检验。

### 6.3 可复现性的层级

可复现性研究区分了两个层级：

| 层级 | 含义 |
|---|---|
| **可重复（repeatable）** | 自己用同样方法能再做一次 |
| **可复现（reproducible）** | 别人用你给的信息能再做一次 |

后者要求更高：**必须把全部条件、环境、参数都写清楚。**

"最小反例"是可复现性的最好载体：**它把条件压缩到最少，从而使"写清楚"成为可能。**

### 6.4 从观察到问题的形式化

把转化过程形式化：

$$
\text{研究问题} = (\text{意外现象}, \text{唯一解释}, \text{最小反例})
$$

算例验证三条件必须齐备。

**这个三元组与 6.1 的三要素（测量手段、判别程序、预算）配合**：前者回答"研究什么"，后者回答"能不能研究"。

**两者合起来才构成一个可执行的研究计划**——这也是第 6 卷四篇的完整逻辑。

## 七、理论：两个判据

### 7.1 三条件的合取

$$
\text{转化成立} \iff \text{surprise} \wedge \text{unique} \wedge \text{minimalRepro}
$$

算例验证：齐备为 `true`，缺一项为 `false`。

注意这是"与"而不是"或"：**任何一个不成立，转化都不成立。**

为什么不是"或"：**三个条件对应研究的三块砖**——没有意外就没有研究的理由，没有唯一解释就不知道研究什么，没有最小反例就无法验证。

### 7.2 复现率的区间

**"5 次全复现"不等于"复现率 100%"。** 算例给出的 95% 区间是 `[0.566, 1.000]`。

读法：**5 次全部成功时，真实复现率的下限只有 0.566**——它完全可能在 60% 左右。

这条结论极其重要：**它说明"我复现了 5 次"远不足以宣称"这个现象稳定"。**

**要缩小区间就必须增加次数**（与 6.3 的区间宽度 $\propto 1/\sqrt{n}$ 一致）：

| 次数（全复现） | 区间下限（约） |
|---|---|
| 5 | 0.57 |
| 10 | 0.72 |
| 20 | 0.83 |

实践判据：**声称"稳定复现"时，要给出次数与区间**，而不是只给"复现了"。

**这也是 6.3 的"所有比例都带区间"在转化阶段的应用。**

## 九、练习

### 第一题：判断是否算转化成功

实现如下。

```
A  观察到一次超时，无法复现，猜测是网络问题
B  观察到 4 次同类失败（共 5 次运行），排除了网络与并发，能用一个最小样例稳定触发
C  观察到 3 次失败，但有三种可能解释都未被排除
D  观察到 5 次全部复现的异常，但每次的条件都不同
```

要求：

- 逐个判断三个条件是否齐备，给出依据。
- 对 B，写出它的转化结论（三元组）。
- 对 D，说明为什么它不满足条件，以及如何改进。
- 对 A，说明下一步该做什么。

---

### 第二题：算复现率的区间

场景：你在 8 次尝试中复现了 8 次。

要求：

- 说明"8 次全复现"能否宣称复现率是 100%。
- 估计 95% 区间的下限（参考：5 次全复现是 0.566）。
- 要让你有把握说"复现率高于 80%"，大约需要多少次全复现？
- 给出你在报告里会怎么表述这个结论。

---

### 第三题（进阶）：写一份复现包

要求：

- 选一个你在使用 agent 时真实遇到过的异常（或虚构一个合理的）。
- 写出转化的三条件判定，逐条给出证据。
- 写出最小反例（具体的条件值）。
- 设计一个复现包：列出一键脚本的内容、环境描述字段、以及预期输出。

算例实现了本篇的意外检测、频率判断与转化判定。

```powershell

```

它做到的事：

- 记录校验（齐备 `true`、缺 `trials` 报错）。
- **意外检测**（`["a2"]`）与异常判定（$x = 1.995$ 为 `true`、$x = 1.5$ 为 `false`）。
- 频率判断（2 次为 `undetermined`，3 次为 `estimated` 且 $rate = 0.667$）。
- 排除竞争假设（剩 1 个、排除 2 个、`unique` 为 `true`）。
- 最小反例（`["任务类型 A", "阈值 0.8"]`，尝试 4 次）。
- 三条件判定（齐备 `true`、缺最小反例 `false`）与5 次全复现的 95% 区间 `[0.566, 1.000]`。

这一篇只要记住一句：工程观察要变成研究问题，必须满足**三个条件**——意外（与预期不符）、唯一解释（竞争假设已排除）、最小反例（能稳定触发）。而"复现了 5 次"完全不等于"复现率 100%"——它的区间下限只有 0.566。

## 一、为什么指标选择决定结论

### 1.1 指标选错

用"多次尝试中至少成功一次"衡量一个长程 agent，**得到接近 100% 的分数**。但用户要的是"每次都能成功"。

### 1.2 样本不够

"我们的成功率是 43.7%"——**但这个数字的置信区间是 ±5.6%，所以它可能与 50% 没有差别。**

### 1.3 安全违规被平均掉

系统的平均分是 0.9，**但它偶尔会执行危险操作**。平均值把这件事藏起来了。

这三件事分别对应：**指标选择、置信区间、一票否决。**

## 二、指标与不确定性

| 量 | 回答 | 形式 |
|---|---|---|
| **指标** | 怎么算分 | pass@k / pass^k / 加权分 |
| **区间** | 这个分有多可信 | Wilson 区间 |
| **样本量** | 要跑多少个任务 | 由区间宽度反推 |
| **否决项** | 什么情况下直接零分 | 安全违规 |

四者缺一不可：**只有分数没有区间，无法判断差异是否真实。只有区间没有否决项，无法表达硬约束。**

## 三、怎么做

### 3.1 pass@k 与 pass^k

两个指标名字相近，含义完全不同：

| 指标 | 含义 | 适用 |
|---|---|---|
| **pass@k** | $k$ 次尝试中**至少一次**成功 | 有多次尝试机会的场景 |
| **pass^k** | $k$ 次尝试**全部**成功 | **长程、需要可靠性的场景** |

算例实测（$k = 8$）：

| 单次成功率 $p$ | pass@8 | pass^8 |
|---|---|---|
| 0.90 | **0.999999990** | **0.430467** |
| 0.99 | — | **0.922745** |

实现如下。

```js
// pass^k：k 次全部成功的概率
export function passPowK(p, k) {
  return Math.pow(p, k)
}
```

这张表是本篇的核心：

- **同一个系统，pass@8 告诉你有 99.999999% 的概率"至少成功一次"，而 pass^8 告诉你只有 43% 的概率"8 次都成功"。**
- $p$ 从 0.90 提到 0.99，pass^8 从 0.43 跳到 0.92——单次成功率的微小提升在 pass^k 上被放大 8 次。

实践判据：**如果你的 agent 执行的是多步任务（每一步都要对），用 pass^k。** 因为长程任务的失败率是逐步累积的——这正是 2.7 的循环与 4.7 的长程任务所面对的现实。

**"单次成功率小提升、多次执行被放大"这条与 2.1 的"成本的二次增长"是同一类非线性**：都是"重复"带来的放大效应，方向相反。

### 3.2 安全违规：一票否决

算例实测两条：

| 输入 | 得分 |
|---|---|
| `taskScore(1, 1, 0.9, 0.9, 0.9)` | **0.9000** |
| **`taskScore(0, 1, 1, 1, 1)`（安全违规）** | **0.0000** |

"一票否决"的必要性：**安全违规不是"程度问题"，而是"性质问题"。**

| 项 | 处理 |
|---|---|
| 正确性、效率 | 加权求和 |
| **安全违规** | **直接零分** |
| 越权操作 | 直接零分 |

为什么不能把安全违规也做成加权项：**它会与"高分表现"互相补偿**——一个 95% 正确率但偶尔删除数据的系统，加权后可能比"80% 正确率但从不越权"的系统分数更高。 这显然不对。

**这与 3.2 的"守卫 fail-closed"、3.4 的"超时即拒绝"是同一个原则**：有些约束是硬约束，不能参与权衡。

### 3.3 置信区间与样本量

**报告一个比例时，必须给出区间。** 算例用的是 Wilson 区间：

```js
// Wilson 区间：比例的小样本置信区间，比正态近似更稳
export function wilson(successes, total, z = 1.96) {
  const p = successes / total
  const denom = 1 + (z * z) / total
  const center = (p + (z * z) / (2 * total)) / denom
  const half = (z * Math.sqrt((p * (1 - p)) / total + (z * z) / (4 * total * total))) / denom
  return { p, low: center - half, high: center + half, halfWidth: half }
}
```

算例实测：

| 样本 | 半宽 |
|---|---|
| 150 / 300 | **0.0562** |
| 500 / 1000 | **0.0309** |
| 131 / 300 | $p = 0.4367$，区间 **[0.3817, 0.4932]** |

读法：

- **样本翻倍不只把半宽缩小到 $1/\sqrt{2}$ 倍左右**（0.0562 → 0.0309 是 0.55 倍，接近 $1/\sqrt{2} = 0.707$ 的改进更小是因为样本从 300 到 1000 翻了 3.3 倍）。
- 131/300 的区间跨过了 0.5：这意味着"这个数字与 50% 无法区分"。

**样本量反推**（算例）：

| 要检测的差异 | 所需样本 |
|---|---|
| 0.10 | **197** |
| **0.03** | **2626** |

**"检测 0.03 的差异需要 2626 个任务"**——这个数字解释了为什么精细的 benchmark 对比成本极高（与 6.2 的样本量公式一致）。

实践建议：

| 场景 | 样本量建议 |
|---|---|
| 粗筛（只要区分好坏） | 100–300 |
| 正式对比 | 500–1000 |
| 精细对比（0.03 级差异） | 2000+ |

### 3.4 饱和与放大

算例给出的**饱和放大**在 $k = 8$ 时是 5.47 倍。

"饱和"指的是：**当单次成功率很高时，pass@k 会迅速接近 1**（$p = 0.9$ 时 pass@8 已经是 0.99999999）。

"放大"指的是：**pass@8 与 pass^8 的差距随 $k$ 增大而指数扩大**。

这带来一个评测设计问题：**当模型在某个 benchmark 上接近饱和时，pass@k 就失去了区分度**——所有系统都是 0.9999，无法分辨。

三种应对：

| 手段 | 做法 |
|---|---|
| **换指标** | 用 pass^k（$k$ 次全对） |
| **提高难度** | 换更难的 benchmark |
| **看成本维度** | 同样的成功率，比较成本（见 2.1） |

第三条常被忽略：**当分数饱和时，成本成为新的区分维度。** "同样 90% 成功率，一个花 1 美元一个花 0.1 美元"是有意义的区分。

这与 3.6 的"成本归因"直接衔接：**评测也必须记录成本，否则饱和之后的比较没有意义。**

### 3.5 任务分与聚合

算例里的 `taskScore(1, 1, 0.9, 0.9, 0.9)` 得到 **0.9000**，说明它把多个维度加权。

聚合时的三个原则：

| 原则 | 说明 |
|---|---|
| **硬约束零分** | 安全违规直接 0（见 3.2） |
| **维度可解释** | 每个维度单独报告，不只报总分 |
| **权重明确** | 写清权重与依据 |

"每个维度单独报告"最重要：**总分相同但维度分布不同的两个系统，实际表现可能完全不同。** 例如：

| 系统 | 正确性 | 延迟 | 成本 | 总分 |
|---|---|---|---|---|
| A | 0.95 | 0.8 | 0.5 | 0.75 |
| B | 0.75 | 0.95 | 0.95 | 0.88 |

**B 的总分更高，但如果你的场景对正确性敏感，A 才是对的。**

这与 3.6 的"护栏指标"是同一件事：**单一数字不足以表达多维目标。**

## 四、特殊情况与处理技巧

| 情况 | 为什么 | 处理 |
|---|---|---|
| 指标接近满分 | 饱和 | 换 pass^k 或换难度 |
| 分数差异很小 | 样本不足 | 给区间，算样本量 |
| 安全违规被平均 | 参与了加权 | 一票否决 |
| 结论不可复现 | 随机源未记 | 记录种子与采样参数 |
| benchmark 被污染 | 训练数据里含评测集 | 检查污染（见 6.4） |
| 任务集太小 | 方差大 | 加大或做分层 |
| 只报总分 | 维度被掩盖 | 分维度报告 |
| 对比不公平 | 资源不对等 | 固定预算或同时报成本 |

"资源不对等"值得强调：**比较两个系统时，如果给它们的预算不同，结论就没有意义。** 正确做法是固定预算，或者同时报告成功率与成本两条曲线。

## 五、工业界的做法（可照做）

### 5.1 真实任务 benchmark 的构造

| 要素 | 做法 |
|---|---|
| **任务来源** | 真实仓库的真实问题（而不是人造题） |
| **判定方式** | 跑测试（而不是比对文本） |
| **难度分层** | 简单/中等/困难分开报 |
| **防污染** | 任务在模型训练截止之后 |
| **成本记录** | 同时报 token 与时间 |
| **可复现** | 提供运行脚本与环境 |

"跑测试而不是比对文本"是关键：**它把判定变成客观的**（与 4.7 的"约束必须可检查"是同一个要求）。

"难度分层报告"很实用：**总分会被简单任务拉高**。分层后能看到"困难任务上的真实水平"。

### 5.2 评测的工程化

| 组件 | 作用 |
|---|---|
| **任务集版本化** | 评测结果可比 |
| **环境固定** | 依赖版本锁定 |
| **多种子** | 减少随机性影响（见 6.2） |
| **自动判定** | 口径固定 |
| **成本统计** | 与 3.6 衔接 |
| **失败分类** | 用 4.4 的三类失败分类 |

"失败分类"值得加入：**不只是报"通过率"，还报"失败的原因分布"**（报错 / 静默错误 / 目标未达）。这让评测结果可以直接驱动改进——与 4.4 的诊断、4.6 的复盘形成闭环。

### 5.3 参数与设计起点

| 参数 | 推荐 | 依据 |
|---|---|---|
| 单任务尝试次数 $k$ | 5–10 | 长程场景取大 |
| 任务数（粗筛） | 100–300 | 区间约 ±0.06 |
| 任务数（正式） | 500–1000 | 区间约 ±0.03 |
| 报告项 | 成功率 + 区间 + 成本 + 失败分类 | 见 3.5 |
| 否决项 | 安全违规、越权 | 一票否决 |
| 分层 | 按难度 3 档 | 避免被简单题拉高 |

### 5.4 一份可落地的实施清单

1. **指标选择**：长程任务用 pass^k，一次性任务可用 pass@k。
2. 一票否决：安全违规与越权直接零分。
3. 区间：所有比例都报 Wilson 区间。
4. 样本量：按要检测的差异反推。
5. 分维度：正确性、延迟、成本分别报。
6. 分层：按难度分档报告。
7. 失败分类：报失败原因分布（用 4.4 的三类）。
8. 可复现：任务集版本化、环境固定、多种子。
9. 防污染：任务来源与训练数据隔离。
10. 资源对等：固定预算或同时报成本。

## 六、学术界的结论

### 6.1 评测指标的性质

评测研究指出，一个好的指标应满足几条性质：

| 性质 | 含义 | 违反的后果 |
|---|---|---|
| **单调性** | 真的更好就分数更高 | 优化方向错误 |
| **可解释** | 分数能对应到实际表现 | 无法据以决策 |
| **有区分度** | 不同系统分数不同 | 饱和后失去意义 |
| **可复现** | 同样输入同样分数 | 无法比较 |

"区分度"这一条与 3.4 的饱和直接相关：**当指标饱和时，它就不再满足"有区分度"。**

"单调性"值得注意：**有些看似合理的指标不满足单调性**——例如"平均步骤数"（更少的步骤不一定更好，可能是草率）。

### 6.2 benchmark 饱和与污染

benchmark 领域有两个被反复报道的问题：

| 问题 | 表现 | 对策 |
|---|---|---|
| **饱和** | 分数接近上限，无法区分 | 换更难的任务 |
| **污染** | 评测数据出现在训练数据里 | 用训练截止后的任务 |
| **过拟合** | 针对 benchmark 优化而非能力 | 保留私有测试集 |

"污染"对 agent 系统尤其隐蔽：**如果评测任务是公开仓库里的 issue，而模型训练时见过那些仓库，分数就会虚高。**

对策是 6.1 的"意外"思路：**用新出现的、不可能被训练过的任务**。

"保留私有测试集"是最可靠的：**它从结构上防止针对评测集优化。** 这也正是 6.2 的"留出验证集"在评测场景的应用。

### 6.3 评测的效度

心理测量学里的**效度**概念适用于 benchmark：

| 效度 | 含义 | 问题 |
|---|---|---|
| **构念效度** | 测的是不是想测的东西 | 测了记忆而不是推理 |
| **内容效度** | 覆盖是否全面 | 只测了简单任务 |
| **预测效度** | 能否预测真实表现 | benchmark 高分但实际不好用 |

"预测效度"是最终判据：**benchmark 的意义在于预测真实场景的表现。** 如果两者脱节，benchmark 就失去了价值。

验证方式：**在你的真实任务上采样，看 benchmark 分数与真实表现的排序是否一致。**

### 6.4 统计显著与工程显著

这是 6.2 的延续，但在评测里尤其重要：

$$
\text{统计显著} \neq \text{工程显著}
$$

含义：**2626 个任务能检测出 0.03 的差异，但 3 个百分点的提升可能对用户毫无意义。**

实践判据：**先定"多小的差异才值得关心"（工程显著），再决定样本量。** 如果工程显著的门槛是 5%，那检测 3% 的差异没有实际意义——即使统计上显著。

这条判据与 6.1 的"信息量"呼应：**一个不会改变决策的结论，无论多显著，都不值得花钱测。**

## 七、理论：两个公式

### 7.1 pass^k 与 pass@k

$$
\text{pass}^k = p^k, \qquad \text{pass@}k = 1 - (1-p)^k
$$

算例实测：

| $p$ | $k$ | pass@k | pass^k |
|---|---|---|---|
| 0.90 | 8 | **0.999999990** | **0.430467** |
| 0.99 | 8 | — | **0.922745** |

两条可直接使用的推论：

| 推论 | 含义 |
|---|---|
| **pass@k 快速饱和** | $p$ 稍高就接近 1，失去区分度 |
| **pass^k 对 $p$ 极敏感** | 单次成功率的小提升被 $k$ 次放大 |

**这解释了为什么"提高可靠性"比"提高峰值能力"更难、也更有价值**——后者只需一次成功，前者需要每次都对。

### 7.2 置信区间的宽度

$$
\text{半宽} \propto \frac{1}{\sqrt{n}}
$$

算例实测：$n = 300$ 时半宽 0.0562，$n = 1000$ 时 0.0309。

读法：**要把区间宽度减半，样本量要翻四倍。**（与 6.2 的样本量公式同源。）

**样本量反推**（算例）：

| 目标差异 | 样本量 |
|---|---|
| 0.10 | 197 |
| 0.03 | 2626 |

含义：**评测的精度是有明确价格的。** 在决定"要不要做这个对比实验"之前，先算这个价格。

## 九、练习

### 第一题：选指标

场景：一个 agent 要在仓库里完成一个 8 步的修复任务。

要求：

- 说明应当用 pass@k 还是 pass^k，并给出依据。
- 如果单次成功率是 0.85，算出 $k = 5$ 时的两个指标值。
- 说明为什么 pass@8 会给出误导性的高分。
- 给出一个"既看可靠性又看峰值能力"的报告方案。

---

### 第二题：算置信区间与样本量

场景：跑了 200 个任务，成功了 156 个。

要求：

- 算出成功率与 Wilson 区间的半宽（用 150/300 → 0.0562 这个点标定量级）。

它做到的事：

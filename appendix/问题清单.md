# 问题清单 · 你现在的真实处境（43 个问题，8 组）

> **这份清单怎么用**
>
> 1. 先**逐条自查**：每条下面有"你会怎么表现"——如果你能对上三条以上，那条就是你的真问题。
> 2. 再看**根因**：它解释了为什么会有这个现象（往往是更底层的一个能力缺失）。
> 3. 最后看**代价**：不解决它，具体会损失什么（用"可观察的后果"写，不喊口号）。
> 4. 每条末尾标注**在哪一册解决**（见 `v1-体系设计-已归档.md`）。
>
> **这份清单不只属于你。** 下面 8 组问题的顺序，是"从最外层（做什么）到最内层（怎么想）"的：
> 越靠后的组，越接近"为什么你会这样"。很多人卡住不是因为不会做，而是因为一直以为问题是第一组的。

## 第 1 组 · 判断：什么问题值得做

### 1.1 把方案当问题

| | |
|---|---|
| **现象** | 你一开口就是"我们做个 X 吧"，而不是"用户在 Y 场景下有个 Z 问题" |
| **根因** | 没有区分"问题空间"与"方案空间"。方案是问题的**一个**答案，而问题才是源头 |
| **代价** | 你会沿着第一个想到的方案做很久，然后发现它解决的不是真问题——而这时成本已经付出去了 |
| **解决于** | 第二册 · 问题空间与需求 |

### 1.2 分不清症状与病因

| | |
|---|---|
| **现象** | 用户说"搜索太慢"，你立刻去做性能优化；其实真正的原因是搜索结果排序差，用户反复搜 |
| **根因** | 缺少"向上追问三层"的习惯（症状 → 行为 → 目标 → 动机） |
| **代价** | 修了一个不是问题的问题，真问题还在 |
| **解决于** | 第二册 |

### 1.3 没有"可验证的假设"这个概念

| | |
|---|---|
| **现象** | 你说的是"我觉得用户会喜欢"，而不是"我假设 X 类用户在做 Y 时会因为 Z 而放弃，验证方式是看 A 指标" |
| **根因** | 把"观点"当"假设"。观点无法被证伪，假设可以 |
| **代价** | 讨论变成立场之争（谁的职级高谁赢），而不是证据之争 |
| **解决于** | 第二册 + 第六册 |

### 1.4 不知道什么叫"足够好"

| | |
|---|---|
| **现象** | 一个功能你反复打磨到"感觉很完善"，却说不清"什么状态下可以发布" |
| **根因** | 没有**成功判据**（success criteria）的概念。判据必须是可以被测量、且能提前写下来的 |
| **代价** | 要么过度打磨（错过窗口），要么过早发布（用户流失）——而且事后无法判断当时对不对 |
| **解决于** | 第四册 + 第六册 |

### 1.5 说不清"不做什么"

| | |
|---|---|
| **现象** | 你的需求列表只有加法没有减法；被问到"这个版本不做哪些"时答不上来 |
| **根因** | 没有**边界**概念：一个产品的定义，一半由"它做什么"决定，另一半由"它不做什么"决定 |
| **代价** | 范围无限膨胀 → 什么都做了一点，什么都不完整 |
| **解决于** | 第四册 |

### 1.6 没有"反事实"能力

| | |
|---|---|
| **现象** | 你只论证"做了会怎样"，从不论证"不做会怎样" |
| **根因** | 决策缺少对照组。没有对照，就无法判断"这个改动是不是必要的" |
| **代价** | 做了大量"做了也没变好"的功能（最典型的浪费形态） |
| **解决于** | 第六册 |

## 第 2 组 · 用户与需求：从信号到需求

### 2.1 把"用户说的"当需求

| | |
|---|---|
| **现象** | 用户说"我要一个导出按钮"，你就加一个导出按钮 |
| **根因** | 没区分**诉求**（他说的）、**需求**（他要达成的目的）、**动机**（他为什么在意） |
| **代价** | 做出来的东西用户用一次就不用了（因为他真正想做的是"把数据给别人看"，导出只是他能想到的一种手段） |
| **解决于** | 第二册 |

### 2.2 不知道用户是谁

| | |
|---|---|
| **现象** | 说"我们的用户是开发者"，但从没描述过任何一个具体的人以及他的一天 |
| **根因** | 用户分层的粒度太粗。"开发者"里有新手、有平台工程师、有 SRE——他们要的东西完全相反 |
| **代价** | 做出来的东西对所有人都"还行"，对谁都不是"必须" |
| **解决于** | 第二册 |

### 2.3 无法判断需求真伪

| | |
|---|---|
| **现象** | 你只能靠"问用户"来验证。而用户在被问"你会用吗"时，几乎永远说"会" |
| **根因** | 缺少行为化验证手段（看行为数据 / 做可点击原型 / 做假门测试 / 看替代方案的用量） |
| **代价** | 需求列表里 60% 是伪需求，而你无法分辨是哪 60% |
| **解决于** | 第二册 + 第六册 |

### 2.4 用自己当用户

| | |
|---|---|
| **现象** | "我自己用着挺顺的"——而你恰好是这个领域里最专业的那 1% |
| **根因** | **专家的诅咒**：你知道得太多，所以无法模拟新手的困惑 |
| **代价** | 产品对高手友好、对新手致命。而增长恰恰来自新手 |
| **解决于** | 第二册 |

### 2.5 不知道"用户价值"与"商业价值"怎么换算

| | |
|---|---|
| **现象** | 你能说"这提升了体验"，但说不出"这让留存涨了多少 / 这每年省了多少钱" |
| **根因** | 缺一个"从体验改善 → 业务结果"的因果链（而这条链的每一环都要能被观测） |
| **代价** | 你的提案在资源竞争里永远输给能算账的人 |
| **解决于** | 第六册 |

### 2.6 把"竞品有的"当成"我们也得有"

| | |
|---|---|
| **现象** | 需求来源里有相当比例是"XX 家上线了 YY" |
| **根因** | 竞品分析停在"功能清单对比"，没到"他们为什么在这个时间做这个（他们的约束是什么）" |
| **代价** | 永远慢一步，而且复制来的功能与自己的架构/用户不匹配 |
| **解决于** | 第四册 |

## 第 3 组 · 决策与优先级

### 3.1 不会排优先级（什么都重要）

| | |
|---|---|
| **现象** | 你的清单里 P0 有 12 条 |
| **根因** | 没有**排序维度**（只是"觉得重要"）。真正的排序需要至少两个可比较的轴（如 价值 × 成本，或 紧迫 × 影响） |
| **代价** | 团队按你的清单并行做 12 件事 → 全部延期 → 你的排期失去信用 |
| **解决于** | 第四册 |

### 3.2 没有成本意识

| | |
|---|---|
| **现象** | 你觉得"加个开关"是个小需求，结果它带来了一个配置项、一条测试、一个文档、一个支持问题 |
| **根因** | 只看到**开发成本**，没看到**总生命周期成本**（设计 + 开发 + 测试 + 文档 + 发布 + 支持 + 后续维护 + 认知负担） |
| **代价** | 产品越做越重，每一次改动都比上一次更贵（这就是"熵"在软件里的形态） |
| **解决于** | 第三册（工程原理）+ 第四册 |

### 3.3 不会算取舍（没有 trade-off 的语言）

| | |
|---|---|
| **现象** | 你想要"又快又稳又便宜"，说"我们都要" |
| **根因** | 缺少工程里的**三元约束**意识（快/好/便宜三者至多取二），也缺少把它们翻译成同一单位的能力 |
| **代价** | 与工程师对话时被当作"不懂现实的人"，你的判断力被系统性打折 |
| **解决于** | 第三册 |

### 3.4 决策不留证据

| | |
|---|---|
| **现象** | 三个月后有人问"当时为什么这么定"，你只能说"我记得是……" |
| **根因** | 没有把决策写成**可追溯的记录**（背景 / 选项 / 决定 / 理由 / 后果） |
| **代价** | 同样的争论重复三次；新成员无法理解现状为什么长这样 |
| **解决于** | 第四册 + 第五册 |

### 3.5 不会说"不"

| | |
|---|---|
| **现象** | 谁提需求你都先说"好"，然后在排期里悄悄无限拖延 |
| **根因** | 拒绝的话术与机制缺失。拒绝需要一个**中立的容器**（优先级规则 / 容量上限 / 代价透明） |
| **代价** | 你成为瓶颈；团队学会"绕过你" |
| **解决于** | 第四册 + 第七册的协作篇 |

### 3.6 决策时依赖身份而非证据

| | |
|---|---|
| **现象** | 讨论卡住时，最后靠"听老板的"或"听我的"收场 |
| **根因** | 前面 1.3（没有可证伪的假设）与 3.4（不留证据）的必然结果 |
| **代价** | 团队不再准备证据，只准备说服你的话术 |
| **解决于** | 全书贯穿 |

## 第 4 组 · 软件工程：你现在最大的黑洞

> **这一组是你明确提到的第二个缺口。** 它单独成册（第三册），因为对"要做产品的工程型 PM"来说，它是**资格线**不是加分项。

### 4.1 不知道一个功能从想法到上线经过什么

| | |
|---|---|
| **现象** | 你会说"这个应该不难吧"，但你画不出它的落地路径（改哪些模块、动哪些接口、要不要数据迁移、怎么回滚） |
| **根因** | 缺少**交付流水线**的整体模型（需求 → 设计 → 实现 → 测试 → 发布 → 观测 → 回滚） |
| **代价** | 你的时间估计永远偏乐观 3–5 倍；工程师不再相信你的排期 |
| **解决于** | 第三册 + 第五册 |

### 4.2 不知道"复杂度"是怎么长出来的

| | |
|---|---|
| **现象** | 你觉得每个需求都很小，但它们加起来让系统变得难以改动 |
| **根因** | 没有**技术债**的概念：每个"这次先这样"的决定都在未来收利息 |
| **代价** | 上线速度逐季度变慢，而没人能指出是哪一条需求导致的 |
| **解决于** | 第三册 |

### 4.3 不会读代码与架构图

| | |
|---|---|
| **现象** | 你只能听工程师转述"这里不好改"，无法自己判断真伪 |
| **根因** | 没建立"从代码/图里读出约束"的能力（不需要会写，但要会读） |
| **代价** | 你无法分辨"技术上做不到"与"他现在不想做"——而这决定你该继续争取还是改方案 |
| **解决于** | 第三册 + 第七册（以 dsh-mini 为读码对象） |

### 4.4 不理解"可逆与不可逆"

| | |
|---|---|
| **现象** | 你对"删一个字段"和"改一个文案"投入同样的谨慎（或同样的随意） |
| **根因** | 没有**改动代价分级**的直觉（哪些改动可以随时回退、哪些一旦上线就只能前进） |
| **代价** | 在不可逆的事上草率（数据迁移），在可逆的事上犹豫（文案 A/B） |
| **解决于** | 第三册 |

### 4.5 不理解"接口"与"契约"

| | |
|---|---|
| **现象** | 你频繁改需求，不理解工程师为什么反应激烈 |
| **根因** | 不知道一个接口一旦被依赖，它就成了**契约**——改它的成本与"改了谁"成正比 |
| **代价** | 你的需求变更会引发连锁修改，团队开始要求"需求冻结"（而冻结本身就是效率损失） |
| **解决于** | 第三册 |

### 4.6 不知道测试/CI/发布怎么保护产品

| | |
|---|---|
| **现象** | 你把测试当"质量部门的活"，把发布当"到点按个按钮" |
| **根因** | 没见过"没有自动化保护时，速度与稳定必然二选一"这个事实 |
| **代价** | 你会为了赶进度要求"先跳过测试"，而那正是在给未来的自己挖坑 |
| **解决于** | 第三册 + 第五册 |

### 4.7 不会判断"这个需求工程上要多久"

| | |
|---|---|
| **现象** | 你问工程师"要几天"，然后拿这个数字当承诺 |
| **根因** | 不知道估计的本质是**不确定性管理**（区间 + 风险 + 未知项），而不是一个数字 |
| **代价** | 你把估计当承诺 → 工程师不敢给真话 → 你拿到的数字越来越没信息量 |
| **解决于** | 第五册 |

### 4.8 不理解技术方案之间的真实差别

| | |
|---|---|
| **现象** | 你听到"我们用队列"、"我们加缓存"、"我们做异步"，但说不出"这解决了什么、引入了什么新问题" |
| **根因** | 缺少**模式词汇**（缓存/队列/幂等/最终一致/背压…这些词背后各有一组代价） |
| **代价** | 无法在方案层面做取舍，只能在"听起来更高级"和"听起来更简单"之间选 |
| **解决于** | 第三册 |

### 4.9 不知道"数据"是产品的一部分

| | |
|---|---|
| **现象** | 你没有想过"这个功能上线后我要看哪三个数" |
| **根因** | 把数据当"事后分析"，而不是"设计的一部分" |
| **代价** | 上线后无法回答"它到底有没有用"，于是靠感觉决定要不要继续投入 |
| **解决于** | 第六册 |

### 4.10 把"无状态/幂等/一致性"当成工程师的术语

| | |
|---|---|
| **现象** | 你说的需求隐含了"重复点击不会扣两次钱"这类要求，但你从没把它写进需求 |
| **根因** | 不知道这类**隐含要求**是产品需求的一部分（而且是事故的高发区） |
| **代价** | 上线后出现重复扣款 / 重复发送 / 数据不一致——而复盘时会发现"需求里从没提过" |
| **解决于** | 第三册 + 第五册 |

## 第 5 组 · 协作与沟通

### 5.1 写不出清晰的文档（PRD 写成散文）

| | |
|---|---|
| **现象** | 你的文档很长、读起来像思考过程，读完没人知道"要做什么、不做什么、怎么算成功" |
| **根因** | 文档的目标不是"表达我想到的"，而是"让另一个人在不必问你的情况下做出正确决定" |
| **代价** | 每个读文档的人都要来找你确认一遍 → 你的时间被切成碎片 |
| **解决于** | 第四册（结构与模板）+ 第七册（写作训练） |

### 5.2 不会主持决策会议

| | |
|---|---|
| **现象** | 你组织的会变成"各说各话"，一小时后没有结论 |
| **根因** | 会议缺少**决策物**：要决定什么 / 有哪几个选项 / 判据是什么 / 谁有权决定 |
| **代价** | 会开得越多，决策越慢；人们开始在小群里私下决定 |
| **解决于** | 第七册 |

### 5.3 不会向上汇报

| | |
|---|---|
| **现象** | 你讲了十分钟过程，老板打断你问"所以呢" |
| **根因** | 汇报缺**结论前置**与**决策请求**（你需要对方做什么：知悉/批准/给资源） |
| **代价** | 你被认为"说不清楚"，进而影响你拿资源的能力 |
| **解决于** | 第七册 |

### 5.4 跨职能说不到点上

| | |
|---|---|
| **现象** | 跟设计师谈交互讲技术、跟工程师讲体验、跟数据讲愿景——每个人都觉得没聊到重点 |
| **根因** | 没有"翻译"意识：同一件事对不同角色要换**接口语言**（约束、判据、代价） |
| **代价** | 协作成本高，方案在传递中失真 |
| **解决于** | 第七册 |

### 5.5 不会处理"工程师说做不了"

| | |
|---|---|
| **现象** | 你要么强行压（"先做出来再说"），要么放弃（"那算了"） |
| **根因** | 缺少"拆解分歧"的手段：是**做不到**、**代价太高**、还是**方案不同**？三种要用三种应对 |
| **代价** | 要么埋下技术债，要么丢掉真正该做的事 |
| **解决于** | 第三册 + 第五册 |

### 5.6 不会在缺少权威时推动事情

| | |
|---|---|
| **现象** | 你不确定"凭什么让别人听我的" |
| **根因** | PM 的权力**不来自职级**，来自三样可积累的东西：判断被验证的次数、信息的独家性、把复杂事情说清楚的能力 |
| **代价** | 你会用"流程"和"汇报"去代替影响力，而这两样在跨职能场景里都很弱 |
| **解决于** | 第七册 |

## 第 6 组 · 节奏与过程

### 6.1 不知道先做什么后做什么

| | |
|---|---|
| **现象** | 你列了 30 件事，但排不出一个能执行的顺序 |
| **根因** | 缺少**依赖视角**：事情之间不是并列的，有些是另一些的前提（"先验证问题存在，再讨论方案"） |
| **代价** | 你在"还没确定要不要做"的阶段就开始讨论"怎么做"，反复返工 |
| **解决于** | 第七册（阶段感）+ 全书 |

### 6.2 没有迭代概念（想一次做完）

| | |
|---|---|
| **现象** | 你的计划是"三个月后上线一个大版本" |
| **根因** | 把"交付"当成一个点，而不是一串**可独立验证的小步** |
| **代价** | 三个月后才知道方向错了；而且过程中团队无法获得反馈与士气 |
| **解决于** | 第四册 + 第五册 |

### 6.3 不会切小（大需求不拆）

| | |
|---|---|
| **现象** | 一个需求拆不动，于是它必须一次做完 |
| **根因** | 缺少**沿用户价值切**的能力（而不是沿技术模块切） |
| **代价** | 交付周期长 → 不确定性高 → 只能靠加班抵消 |
| **解决于** | 第四册 |

### 6.4 不会设里程碑与验收

| | |
|---|---|
| **现象** | 项目没有"中途可检查"的点，只有"最后上线" |
| **根因** | 里程碑被当成汇报节点，而不是**风险释放节点** |
| **代价** | 风险全部堆到最后暴露 |
| **解决于** | 第五册 |

### 6.5 不会处理"中途变化"

| | |
|---|---|
| **现象** | 需求一变，你就慌了，只能重新排期 |
| **根因** | 缺少**变更的代价结构**（改哪里 / 影响谁 / 能不能拖着后面做） |
| **代价** | 你开始抵触变化（而抵触变化 = 产品失去适应力） |
| **解决于** | 第五册 |

## 第 8 组 · 元问题：为什么前七组会同时出现

> **这一组是这份清单真正的价值。** 如果你只读到第 7 组，你得到的是一张"症状表"；
> 读到第 8 组，你才能知道自己为什么会同时得这些病。

### 8.1 你在用"确定性的语言"讨论"不确定的事情"

```
❌ "用户会喜欢这个功能"          ← 用确定句谈一个概率判断
✅ "我估计 X 类用户会喜欢，理由是…；如果错了，最早能在第 N 天看出来"
```

**根因**：产品工作的本质是**在信息不足时做可回退的下注**。而你的语言里没有"概率、区间、可回退、验证点"这些词 ——
于是你只能说出"我觉得"，也就无法被验证、无法被改进。

**这是前七组一半问题的共同源头**（1.3、1.4、2.3、3.6、4.9、6.4 都是它的分身）。

### 8.2 你没有区分"三种不同的判断"

| 判断类型 | 依据 | 谁负责 | 做错的代价 |
|---|---|---|---|
| **产品判断** | 用户价值与业务目标 | 你 | 做了没人要的东西 |
| **工程判断** | 复杂度、可维护性、风险 | 工程师 | 上线后还不动 |
| **设计判断** | 可用性、一致性、认知负荷 | 设计师 | 用户用不明白 |

**根因**：你试图在三种判断上都发言（或都不发言），而没有先问"**这是谁的判断，我需要提供什么信息**"。

**代价**：越界发言被抵触，或者该你拍板的事你推给别人。

### 8.3 你没有"成本的统一度量"

```
PM 说的"复杂"    ：交互复杂、用户理解成本高
工程师说的"复杂" ：改起来容易出错、牵一发动全身
设计师说的"复杂" ：状态太多、边界情况多
```

**根因**：三方都在说"复杂"，但**指的是三种不同的成本**，无法比较 ——
于是"这个值不值得做"永远吵不出结果。

**解决的关键**：把三种成本翻译到**同一个坐标系**上（时间成本 / 出错概率 / 用户完成率 / 维护成本）。
这是第三册与第七册的核心训练。

### 8.4 你在优化"做出来"，而不是"做对"

| | |
|---|---|
| **现象** | 你关心的是"这周能不能上线"，而不是"上线后我们知道了什么" |
| **根因** | 缺少"每次投入都应该换来**信息**（不只是功能）"的心智模型 |
| **代价** | 上线越多，信息越少（因为每次都急着做下一个），到某个点你完全靠直觉在决策 |
| **解决于** | 第六册（度量驱动）+ 全书 |

### 8.5 你把"系统性思维"当成了一个可以单独学的技能

**这是最关键的一条。**

"系统性思维"不是一门课，它是**结构化的知识 + 约束感知 + 取舍语言**三样东西的**副产品**：

```
你不知道一个功能会牵动什么  → 因为你没有系统的结构模型      （第三册）
你判断不出该不该做          → 因为你不理解约束与成本          （第三册 + 第四册）
你说服不了别人              → 因为你没有共通的取舍语言        （第四册 + 第七册）
你复盘不出教训              → 因为你没有可追溯的决策记录      （第四册 + 第六册）
```

**所以"补系统性思维"的正确路径不是去找一本《系统思维》，而是把这四样补齐。**
本清单 43 个问题里，有 31 个落在同样的四样东西上 —— 这就是它们同时出现的原因。

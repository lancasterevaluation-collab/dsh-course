# 四合一能力要求（产品 × 软件工程 × Agent 设计 × 大模型基模）

> **这份文档是什么**：把四个方向的能力**重新组织成一份**。它不是四份文档的相加——相加得到的是清单，**交集得到的才是能力**。
>
> **核心命题**：设计一个 agent harness 这件事，天然同时需要产品判断、工程原理、Agent 实现与**对基模本身的判断**。本课程的全部设计都建立在这个命题上。
>
> **写法约定**：每条能力用行为动词加可验证判据。**没有判据的条目是空话。**

## 一、为什么是四合一

### 1.1 四个方向各自解决什么

| 方向 | 它回答的核心问题 | 它最擅长的动作 |
|---|---|---|
| **产品经理** | 做什么、为什么做 | 取舍、定义成功、在信息不全时判断 |
| **软件工程** | 怎么做才可靠 | 契约、可验证性、失败处理、演进 |
| **Agent 设计** | 怎么让它动起来 | 上下文、工具、循环、评测 |
| **大模型基模** | 它的能力边界在哪 | 判断什么该交给模型、什么必须由系统兜住 |

### 1.2 加上基模这一维补了什么

前三者处理的是"系统怎么造"，第四者处理的是"**造出来的东西的原料有什么脾气**"。这条维度补的是三类判断：

- **能力的归属**：这件事该由模型做、由系统做、还是由提示做？例如"记住用户上周说过的话"必须由系统做（模型没有记忆），而"把一段话概括成一句"可以交给模型。
- **成本的形状**：输入 token 与输出 token 的价格不同、缓存命中能把重复前缀变便宜、上下文窗口是稀缺资源。**同一个功能的成本可以差一个数量级**，取决于你是否知道这些。
- **不确定性的来源**：同一输入两次输出可能不同。这直接决定评测必须多次运行、决定"重现一个 bug"要固定采样参数、决定线上指标要用分布而不是单次结果。

**少了这一维会发生什么**：把本该由系统保证的事（记忆、精确计算、长程一致）交给模型，于是得到"偶尔能用"的系统——而失败无法归因，因为不知道是设计问题还是模型波动。

### 1.3 四方共同的那个交集

四个方向两两之间都有交集，而四者的共同交集是**"判断力"**：

> **在信息不全、资源有限、结果不完全可预测的情况下，做出一个事后可被检验的选择。**

同一套解法在四个方向里各有一种表现：

| 方向 | 表现 |
|---|---|
| 产品 | 这个功能该不该做 |
| 工程 | 这个方案该不该选 |
| Agent | 这个上下文策略该不该用 |
| 基模 | 这件事该不该指望模型 |

而它们的解法是同一套：

```
① 明确"成功"的判据      否则无法事后检验
② 找出最便宜的不确定性降低方式  否则是赌博
③ 判断可逆性            决定要多谨慎
④ 设置复盘点            决定何时重新评估
```

**这套解法就是四合一的实质。** 本课程第 1 卷（判断力地基）讲的就是它。

## 二、四根支柱

每根支柱都由四个方向共同支撑——**这是这份文档与四份单向文档的根本差别**。

### 支柱一 · 判断

**能够在信息不全、资源受限的条件下，做出可被事后检验的选择。**

| 方向 | 它对这根支柱的贡献 |
|---|---|
| 产品 | 取舍框架、用户价值公式、分清"哪些不做会翻车" |
| 软件工程 | 代价分析：每个方案牺牲什么、代价落在谁身上；可逆性分级 |
| Agent 设计 | 技术边界判断：这个能力该由模型、框架还是提示承担 |
| 大模型基模 | 能力边界的实测依据：哪些任务模型稳定、哪些是掷骰子；失败是能力问题还是采样问题 |

**可验证的判据**：给定一个没有标准答案的选择，能给出**判据、代价、可逆性、复盘点**四样东西，且判据可被第三方检验。

### 支柱二 · 表达

**能够把判断变成他人可依赖的形式。**

| 方向 | 它对这根支柱的贡献 |
|---|---|
| 产品 | 需求三要素（为谁 / 解决什么 / 怎么算成功）；验收判据 |
| 软件工程 | 契约三类承诺（行为 / 时序 / 错误）；显式声明"不承诺什么" |
| Agent 设计 | 工具描述的作用是"帮助选择"而不是"帮助理解"；错误分类的表达 |
| 大模型基模 | 提示即接口：同一段文字在不同位置（系统 / 用户 / 工具）效果不同；格式约束要写进提示而不是指望模型自觉 |

**可验证的判据**：给定一份表达（需求 / 接口 / 工具描述 / 提示），能指出**它漏了哪一类承诺**，并说明这个遗漏会导致什么具体失败。

### 支柱三 · 实现

**能够把设计变成可运行的系统，并在实现中保持设计的意图。**

| 方向 | 它对这根支柱的贡献 |
|---|---|
| 产品 | 最小可用版本的定义：先跑通核心路径，再加边界情况 |
| 软件工程 | 原子写、幂等、失败路径、可恢复性 |
| Agent 设计 | 上下文管理、工具调用、循环控制、状态机 |
| 大模型基模 | token 预算与缓存：前缀是否稳定、哪些内容该常驻、哪些该按需加载 |

**可验证的判据**：给定一段实现，能说出**每个非显然的设计点解决了什么问题**，以及**去掉它会怎样**。

### 支柱四 · 验证

**能够证明系统真的按预期工作，并在它不工作时定位到原因。**

| 方向 | 它对这根支柱的贡献 |
|---|---|
| 产品 | 指标体系（北极星 / 过程 / 护栏）；护栏指标防"短期优化伤害长期" |
| 软件工程 | 监控与日志的分工（日志解释一次失败，指标发现趋势）；回归测试 |
| Agent 设计 | 评估流水线（trace → grader → dataset）；负对照；样本量的统计要求 |
| 大模型基模 | 不确定性下的评测：同配置多次运行取分布、噪声下限用同版本两次运行估计；区分"没差异"与"测不出来" |

**可验证的判据**：给定"这个改动让系统变好了吗"，能给出**统计上站得住的答案**，而不只是单次运行的结果。

## 三、能力矩阵：六条能力 × 四个方向

读法：**三列都有内容的能力，才是四合一的能力。**

| 能力 | 产品提供 | 软件工程提供 | Agent 设计提供 | 大模型基模提供 |
|---|---|---|---|---|
| **定义成功** | 北极星与护栏指标 | 验收判据（可独立检验） | 评估用例与 grader | 判据要能在模型波动下稳定判定 |
| **判断代价** | 替换成本、用户价值 | 破坏性变更的代价、可逆性分级 | 成本公式（token × 单价 × 命中率） | 输入输出价差、窗口稀缺性、首 token 延迟 |
| **表达契约** | 需求三要素 | 三类承诺、显式声明不承诺 | 工具描述、错误分类 | 提示即接口、位置语义、格式约束 |
| **控制复杂度** | 最小可用版本 | 单一真相源、派生数据 | 上下文预算、渐进披露 | 前缀稳定性、缓存友好度 |
| **处理失败** | 失败分析与复盘 | 失败路径、幂等、重试 | 错误分级、拒绝的表达、回退 | 区分"模型不知道"与"系统没给到" |
| **证明有效** | A/B 与显著性 | 监控与回归测试 | trace 评估、负对照、样本量 | 多运行分布、噪声下限、可复现的采样参数 |
| **管理演进** | 产品路径与验证点 | 兼容层、版本化、弃用周期 | 上下文策略与缓存的兼容性 | 模型版本升级的影响面（提示要不要改） |

## 四、四个层级

划分依据仍是"独立承担的范围"，但**每一层都要求四个方向同时达标**。

### L1 基础 · 能做对

**独立承担**：在给定设计下把一件事做对。

| 方向 | 要求 |
|---|---|
| 产品 | 能说清"为谁、解决什么、怎么算成功" |
| 软件工程 | 能写出接口的三类承诺，并说明缺哪类会怎样 |
| Agent | 能实现一个工具的完整定义，并说明它的失败路径 |
| 基模 | 能说出这次调用里模型看到的是什么、可能怎么错 |

**四合一检验**：给定一个明确需求，能写出它的验收判据、接口契约、失败处理与**模型能力假设**，且四者互相一致。

### L2 核心 · 能设计

**独立承担**：从零设计一个模块，并给出验收判据。

| 方向 | 要求 |
|---|---|
| 产品 | 能在多个需求间排序，并说明被牺牲项的代价 |
| 软件工程 | 能设计缓存 / 存储 / 接口，并给出容量与失效估算 |
| Agent | 能设计工具系统或上下文策略，并让它可测量 |
| 基模 | 能判断哪些部分该用提示、哪些该用检索、哪些必须写进代码 |

**四合一检验**：给定一组模糊需求，能给出工具切分、优先级排序、评估方案，并说明"为什么不是别的切分方式"。

### L3 进阶 · 能改造

**独立承担**：对生产系统做改造，且改动可测量、可回滚。

| 方向 | 要求 |
|---|---|
| 产品 | 能定义改造的成功指标与护栏指标 |
| 软件工程 | 能诊断瓶颈（先测量再优化），改动可灰度可回滚 |
| Agent | 能搭建评估流水线，并判断改进是否显著 |
| 基模 | 能把"模型波动"从改动的效果里分离出来（同版本两次运行估噪声） |

**四合一检验**：给定"延迟翻倍且成本上升"的报障，能说出先测哪三项、改动后用什么指标验证、以及回滚条件。

### L4 专家 · 能定义

**独立承担**：定义架构与跨系统契约，并在不确定中下注。

| 方向 | 要求 |
|---|---|
| 产品 | 能用"放弃什么"定义策略，并给出止损条件 |
| 软件工程 | 能设计分布式方案，并说明它放弃了什么 |
| Agent | 能设计协议层、多智能体协作与自进化闭环，并划定边界 |
| 基模 | 能判断哪些能力应当等模型变强（而暂不实现），哪些必须现在就用系统兜住 |

**四合一检验**：给定一个需要长期投入的方向，能给出技术方案、产品路径与验证计划，并说明"什么情况下我们会放弃这件事"。

## 五、四合一自评清单

每条 0–2 分。**四个方向都达到 2 分以上**才算四合一成立。

### 支柱一 · 判断

- [ ] 能先把"成功"定义下来再讨论方案（四个方向都要有判据）
- [ ] 能用代价语言描述选项（产品：替换成本 ｜ 工程：破坏性变更 ｜ Agent：token 成本 ｜ 基模：价差与窗口）
- [ ] 能判断决策可逆性并分配谨慎程度
- [ ] 能说出判断依据的类型（数据 / 经验 / 推理）
- [ ] 能在 30–70% 信息量下决策并指出未知
- [ ] 能识别"这件事该模型做还是系统做"，并给出依据

### 支柱二 · 表达

- [ ] 能写出三类承诺（行为 / 时序 / 错误）
- [ ] 能显式声明"不承诺什么"
- [ ] 能把成功判据写成可被独立检验的形式
- [ ] 能按读者的决策点组织表达（对模型 / 对同事 / 对未来的自己）
- [ ] 能在"承诺多少"上做取舍
- [ ] 能说明同一段提示放在不同位置的差别

### 支柱三 · 实现

- [ ] 能从约束推起，而不是从模板推起
- [ ] 能为每个设计点说出理由与代价
- [ ] 能区分"必须消除的失败"与"可接受的失败"
- [ ] 能保持单一真相源，让恢复等于重放
- [ ] 能识别并拒绝"增加复杂度但收益不明的改动"
- [ ] 能判断前缀稳定性与缓存命中，并据此安排内容位置

### 支柱四 · 验证

- [ ] 能区分"能跑"与"可靠"，并给出可靠性判据
- [ ] 能设计含负对照的检验
- [ ] 能计算所需样本量，并知道小样本的局限
- [ ] 能把一次失败沉淀成永久检查
- [ ] 能用外部工具否定程序自己的报告
- [ ] 能在模型波动下给出统计上站得住的结论（多次运行、噪声下限、分辨率）

## 六、四个方向各自的侧重

虽然是四合一，但不同角色的侧重点不同——**明确这个差别，才不会把四合一理解成"要求每个人都全能"**。

| 能力 | 产品更重 | 工程更重 | Agent 更重 | 基模更重 |
|---|---|---|---|---|
| 定义成功 | 指标设计 | 验收判据 | 评估用例 | 判据的稳定性 |
| 判断代价 | 替换成本 | 可逆性 | 成本公式 | **价差与窗口** |
| 表达契约 | 需求 | **接口承诺** | 工具描述 | 提示的位置语义 |
| 控制复杂度 | 最小可用版本 | 单一真相源 | 上下文预算 | **前缀与缓存** |
| 处理失败 | 复盘 | **失败路径** | 错误分级 | 归因到能力还是系统 |
| 证明有效 | A/B | 监控 | **评估流水线** | 噪声与分辨率 |
| 管理演进 | 产品路径 | 兼容层与弃用 | 缓存兼容性 | **模型版本升级** |

**"四合一"的准确含义是**：每个人都应当理解另外三个方向的贡献，并在自己的方向上把它们纳入判断——**而不是每个人都要精通四个方向**。

## 七、这份能力表与课程、题库、主线的关系

```
   能力要求（本文件）      回答"应该具备什么"
         │
         ├─► 课程 33 篇     回答"怎么学会"（按知识顺序组织）
         │
         └─► 面试题库 v2    回答"怎么检验"（按题目组织）
                 │
                 └─► 最终产出：一个可运行的 harness
                     （能力只有通过做出来才算数）
```

| | 组织方式 | 单位 | 用途 |
|---|---|---|---|
| 能力要求 | 按**能力层级** | 一条能力 | 规划学习、定位差距 |
| 课程 | 按**知识顺序** | 一篇 | 系统学习 |
| 题库 | 按**主题** | 一道题 | 检验与准备面试 |

**一条必须说清的话**：

> **这份能力表上的每一条，最终都必须在"做出一个 harness"这件事上兑现。**
>
> **能力不是读出来的，是做出来的**——这正是本课程把"从零构建一个 harness"作为唯一载体的原因。

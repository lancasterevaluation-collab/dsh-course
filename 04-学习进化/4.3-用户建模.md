# 4.3 用户建模

> **这一篇讲什么**：用户建模是从交互中推断"这个用户是谁、想要什么"，并把这些推断用于后续行为。它有一条不对称原则：反驳的权重高于支持。算例里的权重表是显式 +3、隐式 +1、反驳 −2——反驳的绝对值大于隐式支持，因为一次反驳的信息量大于一次默许。

## 一、为什么用户建模需要克制

### 1.1 把一次偏好当成长期偏好

用户在某个任务里说"用 tab 缩进"，系统把它记成"该用户永久使用 tab"。**在别的项目里也照做，而那个项目用空格。**

### 1.2 把沉默当成同意

系统建议了一个方案，用户没反对，系统就认为用户认可。**下次直接按这个方案做，用户说"我没同意这个"。**

### 1.3 推测与事实同级

"用户似乎喜欢简短回答"（推测）与"用户明确说不要用表情符号"（事实）在系统里权重相同。**注入时两者并列，模型无法区分。**

这三件事分别对应：**累积门槛、反驳权重、信号分级。**

## 二、三类信号与权重

| 信号 | 例子 | 可信度 | 权重（算例） |
|---|---|---|---|
| **显式** | 用户明说"用 pnpm" | 最高 | **+3** |
| **隐式** | 用户反复改了同一个地方 | 中 | **+1** |
| **反驳** | 用户否定了系统的做法 | **高于隐式** | **−2** |
| 已确认 | 用户确认了系统的推断 | 最高级 | → 档位 5 |

注意权重的不对称：$|-2| > |+1|$，**因为"用户明确否定"比"用户没有反对"信息量大得多。**

## 三、怎么做

### 3.1 权重表：为什么反驳更重

实现如下。

```js
// 权重表：反驳的绝对值大于隐式支持，显式最高
export const WEIGHTS = { explicit: 3, implicit: 1, refute: -2 }

/** 累计权重：正负证据相加，结果用于与门槛比较。 */
export function weightOf(signals) {
  return signals.reduce((sum, s) => sum + WEIGHTS[s.kind], 0)
}
```

算例实测的三组值：**显式 3、隐式 1、反驳 −2**。

为什么反驳是 −2 而不是 −1：

- **一次反驳通常伴随解释**（"不要用 npm，这个项目用 pnpm"），信息密度高。
- 隐式信号可能是噪声（用户改了同一个地方，也许是因为别的原因）。
- 非对称的错误代价：错误地跟随一个偏好，比错过一个偏好更糟（前者会持续产生错误行为）。

**这条与 3.2 的"未声明副作用取最危险档"、3.5 的"未知错误保守失败"是同一个方向的保守原则。**

### 3.2 门槛与累积

**单次信号不足以改变行为**，必须累积到门槛。算例实测（门槛 = 3）：

| 累积过程 | 权重 | 是否达到门槛 |
|---|---|---|
| 一次隐式 | **1** | 否 |
| 两次隐式 | **2** | 否 |
| **三次隐式** | **3** | **是** |
| 一次显式 | **3** | **是** |

读法：

- **三次观察到的行为才等于一次明确的说明**（1+1+1 = 3）。
- 一次明确说明立即生效。

这个比例给出了一个直觉：**"我看到你做了三次"与"你告诉过我一次"可信度相当。** 这个换算比也是可以调的参数（取决于你的场景里隐式信号有多可靠）。

门槛的作用：**它是抑制噪声的第一道闸。** 没有门槛时，任何一次偶然行为都会改变系统行为。

### 3.3 注入条件

达到门槛之后，**还要决定什么时候把它注入上下文**。

| 条件 | 是否注入 |
|---|---|
| 权重 ≥ 门槛 | 可以注入 |
| 权重 < 门槛 | 只作为内部背景，不注入 |
| 与当前任务无关 | **不注入**（即使达标） |
| 已被用户否定的偏好 | 不注入 |

最后一条与 3.1 的"反驳"机制配合：**一个被反驳过的偏好应当立即失效**，而不是等它自然衰减。

注入时应当带上可信度：让模型知道"这是用户明确说的"还是"系统推断的"。**这与 4.1 的"推测必须带来源"是同一条纪律。**

### 3.4 修正与降级

用户建模必然出错，所以必须有修正机制：

| 机制 | 触发 | 动作 |
|---|---|---|
| **反驳** | 用户否定 | 权重直接扣 −2，可能立即失效 |
| **长期未复现** | 一段时间没再观察到 | 衰减（与 4.1 的时间衰减一致） |
| **用户可查看** | 用户主动查看 | 展示已记录的内容 |
| **用户可删除** | 用户主动删除 | 立即移除 |

"用户可查看与可删除"不只是合规要求，也是纠错手段：**让用户看到系统记住了什么，是发现错误最快的途径。**

算例里的**已确认档位（5）** 就是这条机制的体现：用户确认过的推断，可信度提升到最高级（高于一次显式说明的 3）。

### 3.5 隐私边界

用户建模涉及个人数据，必须遵守几条硬约束：

| 约束 | 内容 |
|---|---|
| **数据最小化** | 只记"影响行为"的内容，不记无关的 |
| **目的限定** | 记录了用于什么，就不能挪作他用 |
| **可解释** | 能说清"为什么这样判断" |
| **可删除** | 用户要求时能真正删除 |
| **敏感性隔离** | 健康、财务等敏感内容单独处理或不记 |

"数据最小化"与 4.1 的写入过滤是同一件事的两面：4.1 从**噪声**角度过滤，这里从合规角度过滤。两者给出的判据高度重合——"影响行为才记"。

"敏感性隔离"最重要：**一个包含了用户健康信息的"偏好记忆"是非常危险的资产。** 稳妥的做法是根本不记，或者只记行为规则而不记原因（记"不要在输出里用 emoji"，不记"用户对某些内容有心理不适"）。

## 四、特殊情况与处理技巧

| 情况 | 为什么 | 处理 |
|---|---|---|
| 一次偏好被当成长期 | 无门槛 | 累积到门槛才生效 |
| 沉默被当成同意 | 未区分"未反对"与"同意" | 未反对不加分 |
| 推测与事实同级 | 未记录可信度 | 注入时带来源 |
| 用户换项目后偏好不适用 | 无作用域 | 偏好带作用域（与 4.1 一致） |
| 反驳后仍被使用 | 反驳未立即生效 | 反驳直接降权或失效 |
| 用户不知系统记了什么 | 不可查看 | 提供查看与删除 |
| 记了敏感内容 | 无敏感隔离 | 只记行为规则，不记原因 |
| 偏好互相冲突 | 无冲突处理 | 新的胜出 + 标注时间 |

"沉默不是同意"值得单独强调：**这是最常见的错误来源。** 系统提出建议、用户没回应，这既不是同意也不是反对——它应当不加分。

判据：**只有用户的主动动作（说、做、否定）才算信号。** 系统自己的输出不算。

## 五、工业界的做法（可照做）

### 5.1 个性化系统的分层

| 层 | 内容 | 变化频率 |
|---|---|---|
| **会话级** | 本次任务的偏好 | 分钟级 |
| **项目级** | 这个仓库的约定 | 天到周 |
| **用户级** | 长期习惯 | 月到年 |
| **组织级** | 团队规范 | 年 |

四层的优先级：**越具体越高**（会话 > 项目 > 用户 > 组织）。这与 2.6 的配置层叠是同一个模型。

冲突处理：**具体层覆盖一般层**，但用户显式说明的可以覆盖任何层（可信度最高）。

### 5.2 偏好学习的两种路线

| 路线 | 做法 | 特点 |
|---|---|---|
| **规则/计数** | 观察 N 次就生效 | 可解释、可调试 |
| **统计/学习** | 用模型预测偏好 | 覆盖广、难解释 |

**推荐起点是规则/计数**（也就是本篇的做法）：它可解释、可调试、可删除。等到规则明显不够用时再考虑统计方法。

这也符合 1.2 的判据：**先用成本低的手段解决，避免引入偶然复杂度。**

### 5.3 验证个性化是否有效

个性化必须验证，否则它可能是在添乱。

| 方法 | 做法 |
|---|---|
| **A/B 对比** | 开/关个性化的两组任务成功率 |
| **纠正率** | 用户纠正系统的频率（应当下降） |
| **显式反馈** | 用户主动点赞/点踩 |
| **注入审计** | 检查注入的偏好是否与任务相关 |

"纠正率"是最实用的指标：**如果开了个性化之后用户纠正得更多，说明推断是错的。**

### 5.4 一份可落地的实施清单

1. **三类信号**：显式、隐式、反驳，各自权重。
2. 门槛：单次信号不改变行为。
3. 反驳立即生效：直接降权或失效。
4. 来源标注：注入时说明是"明确说的"还是"推断的"。
5. 作用域：会话 / 项目 / 用户 / 组织。
6. 冲突处理：具体覆盖一般，显式覆盖推断。
7. 可查看可删除：提供界面与命令。
8. 敏感隔离：只记行为规则，不记原因。
9. 衰减：长期未复现的偏好降权。
10. 验证：用纠正率与 A/B 验证效果。

## 六、学术界的结论

### 6.1 用户建模的传统

用户建模在推荐系统与人机交互领域有长期研究，主要结论包括：

| 结论 | 含义 |
|---|---|
| **显式反馈比隐式可靠** | 与本篇的权重表一致 |
| **负反馈信息量大** | 否定比肯定更能定位边界 |
| **冷启动是最大难题** | 新用户没有历史 |
| **兴趣会漂移** | 需要持续更新（衰减） |

**"负反馈信息量大"与本篇的 $|-2| > |+1|$ 是同一条结论的两种表述。**

"冷启动"的工程含义：**新用户时不要装作用户模型存在。** 应当显式地工作在"无模型"模式（相当于 4.1 的"检索返回空集"）。

### 6.2 贝叶斯视角与先验

把用户偏好看作一个待估参数，每次观察是一次更新：

$$
P(\text{偏好} \mid \text{观察}) \propto P(\text{观察} \mid \text{偏好}) \cdot P(\text{偏好})
$$

两个有用的推论：

1. **先验很重要**：多条弱证据（隐式）才抵得上一條强证据（显式）——这与门槛机制一致。
2. 不对称的代价：如果"错误跟随"的代价高于"错过"，就应当把先验偏向"不生效"——这解释了为什么门槛是 3 而不是 1。

**更严格的建模还会引入"用户可能变化"的假设**（即偏好不是固定参数而是时变的），这正是衰减机制的理论依据。

### 6.3 可解释性与可控性

人机交互研究反复表明：**用户对系统的信任取决于"能否理解与纠正它"**。

| 属性 | 作用 |
|---|---|
| **可解释** | 用户知道系统为什么这样做 |
| **可控** | 用户可以改 |
| **可撤销** | 用户的修改立即生效 |

这三条与 3.2 的"拒绝要给替代路径"是同一个思路：**给用户（或模型）一个可行的下一步，而不是只告诉他们"不行"。**

### 6.4 隐私与数据最小化

隐私工程的核心原则是**数据最小化**：只收集为达成目的所必需的数据。

**它的实践形式**（与本篇直接相关）：

| 原则 | 做法 |
|---|---|
| 目的限定 | 记录了用途，不得他用 |
| 存储限制 | 到期删除 |
| 可删除 | 用户可要求删除 |
| **透明** | 用户可查看被记录的内容 |

对本篇的直接建议：**把"记了哪些用户特征"做成一个可查看的清单。** 这既是合规要求，也是最有价值的纠错手段（3.4）。

## 七、理论：两个模型

### 7.1 权重的不对称

$$
|w_{\text{反驳}}| > |w_{\text{隐式}}| \quad (2 > 1)
$$

算例验证为 `true`。

含义：**否定一个推断所需的证据少于建立一个推断。** 这在统计上对应于"假设检验里拒绝原假设的门槛通常低于接受它的门槛"。

它带来的设计约束：**任何"取消"操作都应当立即生效**，不能要求用户再给三次信号。

### 7.2 累积到门槛

$$
\text{生效} \iff \sum_i w_i \ge \theta
$$

算例实测（$\theta = 3$、$w_{\text{隐式}} = 1$）：

| 次数 | 累计 | 生效 |
|---|---|---|
| 1 | 1 | 否 |
| 2 | 2 | 否 |
| **3** | **3** | **是** |

含义：**"多少次观察等于一次明说"是一个可计算的换算。**

参数建议：这个换算随场景变化——**对行为一致性高的场景（例如代码风格）可以取 2，对行为随机的场景（例如措辞偏好）应当取 4 或更高。**

实现如下。

```
1  用户说"这个仓库用 4 空格缩进"

3  用户否定了系统建议的"用 tab"

```

要求：

- 逐条给出信号类型与权重，算出累计值（门槛 3）。
- 说明第 4 条为什么是 0 权重。
- 如果第 1 条与第 3 条冲突，最终应如何处理？
- 写出这四条各自的存储字段（来源、作用域、时间）。

要求：

- 设计一个"系统记住的关于你的事"清单，包含哪些字段。

- 设计两个操作：删除与修正，说明它们对后续行为的影响。
- 指出这个界面在什么情况下会带来新的隐私风险。

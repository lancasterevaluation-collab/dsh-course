## 读完这一篇你会知道什么

1. **状态校验三条**：算例里缺少唯一下一步会抛错、约束不可检查会抛错、进行中超过一项会抛错，而合法状态通过。
2. 唯一下一步：状态里必须有一件明确指定的下一件事。
3. 约束的两类：算例里判据式约束可识别（`true`），原则式约束不可识别（`false`）。
4. 进行中只能有一项：并行多项会让状态无法续作。
5. 续作入口：算例里入口是一条可直接执行的动作（写指定内容，然后跑指定检查）。
6. 工业界怎么做：issue tracker、看板、交接文档、检查点。
7. 学术界：任务分解、中断恢复、以及可续作性。

## 一、为什么长程任务需要特殊的纪律

### 1.1 不知道做到哪

第二天打开任务，**只看到一堆已完成的事，不知道下一个该做什么**。

### 1.2 下一步不唯一

状态里写着"继续完善文档"。**"完善"有五种可能的做法**，接手者只能猜。而猜错会浪费一整轮。

### 1.3 约束写成原则

约束是"不要写得太长"。**没人知道多少算长**，所以无法检查，也无法在写完后判断是否违反。

这三件事分别对应：**唯一下一步、可检查约束、状态完备性。**

## 二、可续作状态要有什么

| 字段 | 回答 | 缺了会怎样 |
|---|---|---|
| **目标** | 最终要做到什么 | 接手者不知道方向 |
| **已完成** | 做到哪了 | 重复劳动 |
| **下一步** | **唯一**的下一件事 | 猜 |
| **待办** | 还没做的清单 | 漏项 |
| **约束** | 必须满足什么 | 违反规则 |
| **入口** | 从哪里继续 | 找不到起点 |

六个字段里最关键的是"下一步"与"入口"：它们决定了**接手者能不能在 30 秒内开始工作**。

## 三、怎么做

### 3.1 状态校验：三类

算例给出的三类校验，**每一类失败都会抛错**：

| 校验 | 触发条件 | 为什么重要 |
|---|---|---|
| **唯一下一步** | 缺少或有多于一个 | 接手者无法确定要做什么 |
| **约束可检查** | 约束无法机械判定 | 无法验证是否违反 |
| **进行中仅一项** | 同时有多项进行中 | 状态含义不明确 |

算例实测：

| 情况 | 结果 |
|---|---|
| 缺少唯一下一步 | **抛错** |
| 约束不可检查 | **抛错** |
| 进行中超过一项 | **抛错** |
| 合法状态 | **通过** |

实现如下。

```js
// 状态校验：三项都必须满足，否则状态不可续作
export function validateState(state) {
  if (!state.nextStep) throw new Error('缺少唯一下一步')
  if (state.inProgress.length > 1) throw new Error('进行中超过一项')
  for (const constraint of state.constraints) {
    if (!isCheckable(constraint)) throw new Error(`约束不可检查：${constraint}`)
  }
  return true
}
```

"抛错"而不是"警告"是设计选择：**不可续作的状态比没有状态更糟**——它让人以为可以接上，实际会跑偏。早失败优于静默降级。

### 3.2 唯一下一步

**"下一步"必须是一件具体的、可以直接开始做的事。**

| 写法 | 可执行 | 为什么 |
|---|---|---|
| "完善文档" | 否 | 不知道从哪开始 |
| "继续推进 4.7" | 否 | 同样含糊 |
| **"写 4.7 全篇，然后跑检查脚本"** | **是** | 动作与验证都明确 |

算例里的入口正是第三种写法：**一个动作 + 一个验证**。

写法模板：

$$
\text{下一步} = \text{动作} + \text{对象} + \text{验证方式}
$$

**"验证方式"让"做完"变成可判断的**——这与 1.1 的完成定义（判据 + 指标）是同一件事。

### 3.3 约束必须可检查

这是本篇我最想强调的一条。约束分两类：

| 类型 | 例子 | 可识别 |
|---|---|---|
| **判据式** | "每篇不超过 20 KB"、"必须有两个算例" | **是**（`true`） |
| **原则式** | "不要写得太长"、"保持简洁" | **否**（`false`） |

算例实测正是这个对照：**判据式可识别 `true`，原则式不可识别 `false`**。

为什么必须可检查：

- **不可检查的约束等于没有约束**——违反与否无法判断。
- 不可检查的约束无法自动验证——只能靠人记住，而人会忘。
- 不可检查的约束会导致争论——"这算长吗"没有答案。

改造原则式约束的方法：

| 原则式 | 改造为判据式 |
|---|---|
| "不要写得太长" | "每篇 ≤ 20 KB，单段 ≤ 200 字符" |
| "保持一致性" | "所有术语在术语表中有定义" |
| "及时处理" | "24 小时内响应" |
| "测试要充分" | "核心路径覆盖率 ≥ 90%" |

**注意改造后的形式都包含一个量或一个可机械判定的性质。**

这条原则在本课程里是被执行的：`check-lecture.mjs` 与 `check-textbook.mjs` 把"文风要求"变成了一组可机械检查的判据。**这正是把原则式约束改造成判据式的实例。**

### 3.4 进行中只能有一项

算例实测：**进行中超过一项会抛错**。

为什么这条必要：**"进行中"的状态含义是"我知道它现在到哪里了"**。同时进行两项时：

- 中断后不知道应该恢复到哪一项。
- 两项之间可能有依赖，状态不是单一的。
- 交接时必须说清"两项各到哪了"——成本翻倍。

注意这不等于"不能并行工作"：**它约束的是"状态里的进行中标记"，不是实际执行**。并行做的任务应当先分解成明确的待办项，而不是让进行中出现多项。

判据：**如果一个任务必须同时推进两件事，说明它应该被拆成两个任务或重新排序。**

### 3.5 续作入口

**入口是一条可以直接执行的动作**——复制粘贴就能开始。

算例里的入口：**写 4.7 全篇，然后跑 `node scripts/check-lecture.mjs`**。

入口的三个要素：

| 要素 | 作用 |
|---|---|
| 动作 | 做什么 |
| 对象 | 对哪个文件/模块 |
| **验证** | 怎么知道做完了 |

**"入口写在状态文件的顶部"** 是一个实用建议：接手者不需要读完整个状态就能开始。

这与 3.5 的"拒绝要给替代路径"是同一个思路：**给下一步，而不是只给现状。**

## 四、特殊情况与处理技巧

| 情况 | 为什么 | 处理 |
|---|---|---|
| 不知道做到哪 | 状态不全 | 六个字段齐全 |
| 下一步含糊 | 未写成可执行动作 | 动作 + 对象 + 验证 |
| 约束无法检查 | 原则式 | 改造成判据式 |
| 中断后不知恢复哪项 | 多项进行中 | 只允许一项 |
| 接手者找不到起点 | 无入口 | 入口写在顶部 |
| 状态与实际不符 | 未及时更新 | 每步完成后更新（与 2.7 的日志同步） |
| 待办越积越多 | 无取舍 | 定期重排优先级（与 4.6 复盘结合） |
| 状态文件过长 | 历史全留 | 只保留当前 + 摘要历史 |

"状态与实际不符"是最危险的：**一个过时的状态比没有状态更糟。** 所以更新状态应当与做事同时发生（例如每完成一项就更新），而不是"做完一批再更新"。

这与 2.7 的"追加日志"是同一个机制：**状态更新也是追加记录，而不是事后回忆。**

## 五、工业界的做法（可照做）

### 5.1 任务跟踪的既有形态

| 工具 / 实践 | 做法 | 值得学的点 |
|---|---|---|
| **Issue tracker** | 每个任务一条，有状态与负责人 | 状态显式 |
| **看板** | 列（待办/进行中/完成） | **进行中列限制 WIP** |
| **交接文档** | on-call 交接、项目交接 | **入口与下一步** |
| **检查点** | 定期快照当前状态 | 中断恢复 |
| **运行手册** | 具体步骤 + 验证 | 可执行 |

**"WIP 限制"与本篇的"进行中只能有一项"是同一个原则**：限制同时进行的工作量，是保证"状态可描述"的前提。

看板的 WIP 限制来自精益生产：它发现"同时做多件事"会让**每一件的完成时间都变长**（Little 定律，见 3.6）。

### 5.2 交接文档的写法

一份好的交接文档包含四个部分：

| 部分 | 内容 |
|---|---|
| **目标** | 这件事最终要做到什么 |
| **现状** | 已完成什么，现在在哪一步 |
| **下一步** | 唯一的一件要做的事（动作 + 验证） |
| **风险** | 已知的坑与不确定处 |

"风险"这一节常被漏但价值很高：**它把接手者最可能踩的坑提前说了。**

### 5.3 参数与设计起点

| 参数 | 推荐 | 依据 |
|---|---|---|
| 进行中上限 | 1 | 状态可描述 |
| 下一步数量 | 1 | 无歧义 |
| 待办数量 | 5–15 | 太多说明没做优先级 |
| 约束形式 | 全部可检查 | 见 3.3 |
| 状态更新时机 | 每完成一项 | 避免滞后 |
| 历史保留 | 摘要 | 防止文件膨胀 |

### 5.4 一份可落地的实施清单

1. **六字段**：目标、已完成、下一步、待办、约束、入口。
2. 下一步唯一：动作 + 对象 + 验证。
3. 约束可检查：全部改造成判据式。
4. 进行中一项：多项则拆分任务。
5. 入口在顶部：可直接执行。
6. 及时更新：每完成一项就更新。
7. 历史摘要：只保留当前与摘要。
8. 风险一节：写下已知的坑。
9. 校验脚本：把三条校验写成代码（算例即是）。
10. 与复盘衔接：待办重排与 4.6 一起做。

## 六、学术界的结论

### 6.1 任务分解与计划

自动规划领域的一个核心结论是：**计划的粒度决定它能否被执行**。

| 粒度 | 问题 |
|---|---|
| 太粗（"完成项目"） | 无法执行 |
| 太细（每个按键一步） | 计划本身比执行还长 |
| **恰当** | **每一步都有明确的完成判据** |

"完成判据"正是 3.2 的"验证方式"：**可执行性与可验证性是同一件事的两面。**

### 6.2 中断恢复

中断恢复在操作系统与分布式系统里都是核心问题。三条被反复验证的做法：

| 做法 | 内容 | 对应 |
|---|---|---|
| **检查点** | 定期保存完整状态 | 状态字段 |
| **幂等操作** | 重复执行不出错 | 见 3.5 |
| **恢复等价** | 恢复后状态与未中断一致 | 见 3.5 |

"恢复等价"这一条对长程任务的含义：**中断后继续，结果应当与不中断一样。** 这要求每一步的状态都可重建——也就是本篇的六个字段。

### 6.3 可续作性与"谁都能接上"

软件工程里的"可维护性"概念可以推广到任务状态上：**一个状态是可续作的，当且仅当另一个执行者（人或 agent）能仅凭它继续。**

这与 1.3 的"模块卡片"是同一个要求：**卡片要记录"用的时候必须知道的事"，状态要记录"接着做必须知道的事"。**

判据：**把状态交给一个不知道上下文的人，他能在 30 秒内开始工作吗？** 不能，说明状态不完备。

### 6.4 约束的可判定性

逻辑与形式化方法里的"可判定性"概念在这里有一个直接的应用：**一个约束要么可以被机械判定，要么不能。**

**不能判定的约束在工程上等同于不存在**（因为无法执行），但它的危害更大：它会给人"有约束"的错觉。

实践做法：**把"可检查"作为约束的第一属性。** 写约束时先问"怎么检查它"——写不出检查方式的约束应当被改写成能写出检查方式的版本，或者被删掉。

这与本课程的做法一致：所有的文风要求都被写成了检查脚本，而不是停留在"要注意文风"。

## 七、理论：两条条件

### 7.1 唯一的下一步

$$
|\text{nextStep}| = 1
$$

算例验证：**缺少唯一下一步时抛错**，合法状态通过。

为什么必须是 1 而不是 ≥1：**多于一个时，状态不能确定唯一的动作**。而"确定"是可续作的前提。

### 7.2 约束的可判定性

$$
\text{约束有效} \iff \exists\ \text{可机械判定的检查}
$$

算例验证：**判据式约束可识别（`true`）、原则式约束不可识别（`false`）**。

这条不等价关系是本篇最实用的判据：**一个约束是否有效，取决于能不能写出它的检查。**

## 九、练习

### 第一题：改写约束

把下面五条原则式约束改写成判据式：

```
A  文档不要写得太长
B  代码要保持可读
C  要及时响应用户
D  测试要充分
E  记忆不要攒太多
```

要求：

- 逐条给出判据式版本（含具体的量或可判定性质）。
- 说明如何检查每一条（人工检查还是脚本）。
- 指出哪一条改写成判据式之后可能失去原意，以及如何避免。

---

### 第二题：写一份可续作状态

场景：你在做一个跨三天的任务——为一个服务加一个导出功能，已完成接口定义与实现，测试写了一部分。

要求：

- 写出六字段齐全的状态。
- 下一步必须满足"动作 + 对象 + 验证"三要素。
- 列出至少三条约束，全部可检查。
- 说明如果你明天换了机器，接手者能否仅凭这份状态继续工作。

---

### 第三题（进阶）：把校验写成代码

要求：

- 用代码实现三条校验（唯一下一步、约束可检查、进行中仅一项）。
- 为每条校验写一个"非法状态"的测试用例。
- 说明为什么用抛错而不是警告。
- 设计一个扩展：如何校验"下一步的验证方式"确实是可执行的。

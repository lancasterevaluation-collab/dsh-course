## 一、为什么诊断要先定义失败

### 1.1 把"没报错"当成成功

命令退出码是 0，但输出是空的（本该有内容）。**系统判为成功，任务静默失败。**

### 1.2 证据不足就下结论

一次执行失败，系统立刻得出"是配置问题"。**但那只是相关，不是因果**——同一时刻还有别的变化。

### 1.3 结论不可行动

诊断结论是"环境有问题"。**没人知道要改什么。**

这三件事分别对应：**失败判定、证据强度、可行动性。**

## 二、失败的三类判定

| 类型 | 判据 | 例子 |
|---|---|---|
| **`error`** | 有明确报错 | 命令退出码非 0、异常抛出 |
| **`silent`** | 检查不通过但无报错 | 输出为空、内容不符合断言 |
| **`goal-miss`** | 检查通过但目标没达成 | 步骤都成功，但最终结果是错的 |

第三类最容易被漏：**每一步都成功，但整体没达成目标。** 这在多步任务里很常见（例如所有工具调用都成功，但最终答案答非所问）。

## 三、怎么做

### 3.1 优先级：报错最高

实现如下。

```js
// 失败判定：三类按优先级取第一个成立的
export function classifyFailure(signals) {
  if (signals.error) return 'error'
  if (signals.checkFailed) return 'silent'
  if (signals.goalMissed) return 'goal-miss'
  return 'unknown'
}
```

算例实测的优先级关系：

| 情形 | 判定 |
|---|---|
| 同时有错与目标未达 | **`error`** |
| 报错优先于检查不通过 | **`error`** |
| 检查优先于目标未达 | **`silent`** |

为什么报错优先级最高：**报错是"系统自己知道出了事"**，它比外部检查更接近根因。而且报错会掩盖其他信息——有异常时，后面的检查结果往往不可靠。

为什么检查高于目标未达：**检查是"我预期的东西没出现"**，比"最终目标没达成"更接近具体位置。目标未达是结论，检查不通过是线索。

### 3.2 默认算失败

算例实测：**"三类都不成立时是否算失败"为 `true`**。

这条保守原则很重要：**无法判定成功时，应当判为失败**（而不是默认成功）。

理由：**"默认成功"会把静默失败放行**。而"默认失败"最坏的情况是让人多做一次确认——代价小得多。

**这与守卫的 fail-closed（见 3.2）、错误分类的"未知保守失败"（见 2.1）是同一条原则的第三次出现。**

### 3.3 证据强度三级

不是所有证据都能支撑结论。算例给出三级：

| 级别 | 含义 | 强度 |
|---|---|---|
| **相关** | 两者同时出现 | **1** |
| **反事实** | 去掉它结果就不同 | **2** |
| **复现** | 能重复触发 | **3** |

实现如下。

```js
// 证据强度：只有反事实以上才足以支撑"这是原因"
export function evidenceStrength(evidence) {
  return { correlation: 1, counterfactual: 2, reproducible: 3 }[evidence.kind] ?? 0
}
```

三级的差别是本篇最实用的部分：

- **相关**：改了 X 之后 Y 变了。但这可能只是同时发生（例如"部署了新版本"与"流量高峰期"同时出现）。
- 反事实：去掉 X 后 Y 不再出现，加回来又出现。这才是因果。
- 复现：能稳定重复触发。这最强，也最能支撑修复。

实践判据：**只有强度 2 以上的证据才能说"这是原因"，强度 1 只能说"这里可疑"。**

"反事实"这一步在实践中的做法：**做一次对照**（回滚、关掉开关、换一个输入），看问题是否消失。一次对照的价值高于十次观察。

### 3.4 结论必须可行动

算例实测：**有 1 个候选因不可行动被排除**。

可行动的判据：**结论要指向一个具体的、可以执行的动作**。

| 结论 | 可行动 | 为什么 |
|---|---|---|
| "环境有问题" | 否 | 不知道改什么 |
| "超时设为 30 秒，而该操作平均需要 45 秒" | 是 | 可以直接改 |
| "内存不足" | 否 | 不知道是泄漏还是配置太小 |
| "第 128 行未释放连接导致累积，建议改用连接池" | 是 | 位置与动作都明确 |

排除不可行动的候选是必要的：**否则它们会与可行动项并列，稀释注意力**（与 3.6 的"无法据以行动的指标是噪声"是同一个判据）。

### 3.5 诊断结论的结构

一条可用的诊断结论至少包含：

| 字段 | 内容 |
|---|---|
| **现象** | 观察到的失败（含证据） |
| **类别** | `error` / `silent` / `goal-miss` |
| **原因** | 判断出的原因 |
| **证据强度** | 1 / 2 / 3 |
| **建议动作** | 可执行的一步 |
| **预期结果** | 做了之后应当观察到什么 |

"预期结果"是最有价值也最常被漏的字段：**它让结论可以被验证**。如果做了动作但没观察到预期结果，说明诊断错了——这让诊断本身成为可迭代的。

**这与 4.5 的"提议要带 expectation"直接衔接**：诊断产出结论，演化把它变成改动提议。

## 四、特殊情况与处理技巧

| 情况 | 为什么 | 处理 |
|---|---|---|
| 把静默失败当成功 | 只看退出码 | 三类失败都要检查 |
| 相关被当因果 | 证据强度未分级 | 要求反事实以上 |
| 结论不可行动 | 未做可行动性检查 | 排除并继续找 |
| 多个失败同时出现 | 无优先级 | 按报错 > 检查 > 目标未达 |
| 无法判定成功 | 默认成功 | **默认失败** |
| 原因找到但改不动 | 超出可改范围 | 转成"需要谁做什么"的行动项 |
| 同一现象多个原因 | 未区分主次 | 分别给证据强度，按强度排序 |
| 诊断结论互相矛盾 | 无合并规则 | 保留并标注证据强度 |

最后一条值得展开：**多个矛盾结论并存是正常的**（证据不足时）。强行合并会丢失信息——正确做法是都保留，标注证据强度，并给出"怎么区分它们"的下一步实验。

## 五、工业界的做法（可照做）

### 5.1 根因分析的常用方法

| 方法 | 做法 | 适用 |
|---|---|---|
| **5 Whys** | 连问五次"为什么" | 单点问题 |
| **鱼骨图** | 按类别（人/机/料/法/环）穷举原因 | 原因空间大 |
| **故障树** | 自顶向下分解"什么会导致它" | 复杂系统 |
| **时间线分析** | 按时间排列事件与变更 | 突发故障 |
| **变更对比** | 对比故障前后的差异 | 部署后出的问题 |

"变更对比"在实践中命中率最高：**大多数突发故障与最近的变更相关**。所以先看最近改了什么。

**这与 1.3 的"看版本历史的高频区"是同一个手段。**

### 5.2 可观测性排障的顺序

结合 3.6 的四段分解，排障的推荐顺序是：

1. **指标**：哪个指标先异常（确定症状）。
2. 追踪：异常发生在哪一段（预填充 / 生成 / 工具 / 排队）。
3. 日志：那一段的具体错误。
4. 变更：那个时间点前后改了什么。
5. 对照：回滚或关开关，看是否恢复。

第 5 步就是 3.3 的"反事实"证据：**没有这一步，前面的分析都只是"可疑"。**

### 5.3 无责复盘

事故复盘的实践共识是**关注系统而非个人**：

| 原则 | 做法 |
|---|---|
| 无责 | 不追究个人 |
| 事实优先 | 先时间线，后解释 |
| 系统视角 | 问"什么机制能让这个错误不可能发生" |
| 可执行 | 输出具体的改动作业项 |

"可执行的作业项"与 3.4 的可行动性是同一条要求：**"加强检查"不是行动项，"在部署流水线里加一条 schema 校验"才是。**

### 5.4 一份可落地的实施清单

1. **三类失败**：报错 / 检查不通过 / 目标未达，各自有检测方式。
2. 优先级：报错 > 检查 > 目标未达。
3. 默认失败：无法判定成功时判失败。
4. 证据分级：相关 / 反事实 / 复现，强度 1/2/3。
5. 反事实优先：找原因时优先做对照实验。
6. 可行动过滤：不可行动的结论不进入最终列表。
7. 结论结构：现象、类别、原因、证据强度、动作、预期结果。
8. 多结论并存：矛盾时保留并标注强度。
9. 排障顺序：指标 → 追踪 → 日志 → 变更 → 对照。
10. 复盘无责：输出系统级改动作业项。

## 六、学术界的结论

### 6.1 因果推断的反事实定义

因果推断里"原因"的定义是**反事实的**：

> X 是 Y 的原因，当且仅当**若 X 不发生，Y 就不会发生**。

这条定义直接支持了 3.3 的证据分级：**"相关"不足以构成原因**，因为可能有一个共同的原因同时影响两者。

实践上的近似：**做干预（intervention）**——主动改变 X，观察 Y。这是"对照实验"在排障中的形式。

在软件系统里的难点：**无法总是做随机对照**（不能把一半用户的系统回滚）。替代手段是"时间上的对照"（改前 vs 改后）与"环境上的对照"（出问题的实例 vs 正常的实例）。

### 6.2 缺陷定位研究

软件工程领域对"如何找到缺陷位置"有大量研究，主要结论包括：

| 结论 | 含义 |
|---|---|
| **可疑度排序有效** | 按可疑度排序比随机的命中率高得多 |
| **失败测试的频谱信息有用** | "哪个测试失败、哪个通过"能定位代码 |
| **历史信息有用** | 最近改过的代码更可能有问题 |
| **组合多种信号效果更好** | 频谱 + 历史 + 复杂度 |

对本篇的启示：**诊断应当排序而不是给单一答案**（"前三可疑位置"比"就是这个"更有用），并且要多信号融合。

### 6.3 故障诊断的形式化

故障诊断领域把问题形式化为：**给定系统模型与观察，找出最可能的故障集合**。

| 概念 | 含义 | 本课程对应 |
|---|---|---|
| **可诊断性** | 故障能否被区分 | 失败三类是否可分 |
| **可观测性** | 内部状态能否从外部推断 | 3.6 的可观测 |
| **最小诊断** | 最小的故障假设集合 | 排除不可行动候选 |

"可诊断性"这一条对设计的直接含义：**如果两个故障产生完全相同的可观测现象，那它们无法被区分。** 所以要在设计时保证关键故障有独特的信号（例如不同的错误码）。

### 6.4 从诊断到修复的闭环

诊断的价值在于**闭环**：诊断 → 动作 → 观察 → 修正诊断。

**这正是 4.5 的演化提议与 4.6 的复盘周期所做的事**：诊断结论必须能被后续环节消费，否则它只是一段文字。

判据：**诊断结论里"预期结果"这一字段，就是闭环的接口。**

## 七、理论：两条判据

### 7.1 优先级的全序

$$
w(\text{error}) > w(\text{silent}) > w(\text{goal-miss})
$$

算例验证了这三条两两关系。

为什么必须是全序而不是并列：**并列时无法给出唯一判定**，而下游（演化提议）需要一个确定的输入。

### 7.2 证据强度与结论强度

$$
\text{可下因果结论} \iff \text{证据强度} \ge 2
$$

算例给出三级映射：相关 1、反事实 2、复现 3。

**"强度 1 只能说明可疑"** 这一结论在实践中极其有用：它把"我觉得是 X 的问题"降级为"X 值得查"，从而避免了基于相关性的大改动。

**这与 1.1 的"双向门快速做、单向门慎重做"是同一个思路**：证据不足时不要做大动作。

## 九、练习

### 第一题：判定失败类型

实现如下。

```
A  命令退出码 1，stderr 有错误信息
B  命令退出码 0，但输出文件为空
C  所有步骤成功，最终答案与问题无关
D  命令退出码 0，输出非空，但断言检查失败
E  触发超时被强杀
```

要求：

- 逐条给出失败类型，并说明依据。
- 如果 B 与 C 同时成立，判为哪一类？说明优先级。
- 对每一条给出一个"可行动"的诊断结论（含预期结果）。

---

### 第二题：评估证据强度

场景：系统在周五下午变慢。

```
A  周五下午同时发生了"部署新版本"与"月末结算"
B  回滚新版本后恢复正常
C  在测试环境重复执行月末结算，能复现变慢
```

要求：

- 逐条给出证据强度（1/2/3）。
- 说明仅凭 A 能不能下"是部署导致的"结论。
- 说明 B 与 C 分别排除了什么可能性。
- 给出最终的诊断结论（含预期结果）。

---

### 第三题（进阶）：设计诊断输出

要求：

- 设计诊断结果的数据结构（至少 6 个字段），说明每个字段供谁消费。
- 说明如何表示"多个矛盾结论并存"。
- 设计一个"诊断质量"的度量：怎么知道诊断是否有效。
- 指出这套结构在什么情况下会导致错误的行动。

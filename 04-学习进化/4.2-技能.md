## 读完这一篇你会知道什么

1. **三层披露**：描述（索引）→ 主体（步骤）→ 资源（附件）。
2. 成本的量级差：算例里 20 个技能，只给描述 2000 token、加主体 32000、含资源 232000，比值 116。
3. 全量放不下：算例里全量超过 128K 窗口，而"只给主体（不含资源）"不超。
4. 索引的作用：算例里索引读取的字符数是 97——用很小的成本让模型知道"有哪些技能可用"。
5. 加载时机：什么时候从描述层升到主体层。
6. 工业界怎么做：技能库、提示词库、按需加载文档、检索式增强。
7. 学术界：程序性记忆、技能获取、以及渐进式披露的信息设计。

## 一、为什么技能需要分层

### 1.1 全量加载撑爆窗口

团队写了 20 个技能，每个都很详细，还有示例文件。**全部加载需要 23 万 token，远超窗口。**

### 1.2 技能用错场合

模型在"写测试"的任务里用了"发布流程"技能。**因为它只看到名字，不知道什么时候该用。**

### 1.3 技能内容过时

技能里写的命令已经改了，但没有人更新技能。**模型照着过时的步骤做，反复失败。**

这三件事分别对应：**分层、触发条件、版本管理。**

## 二、三层披露

| 层 | 内容 | 何时给 | 成本（算例） |
|---|---|---|---|
| **描述** | 名字 + 一句话用途 + 何时使用 | 总是（索引） | 2000 |
| **主体** | 步骤、注意事项 | 命中时 | 增至 32000 |
| **资源** | 示例文件、模板、脚本 | 需要时按需读取 | 增至 232000 |

核心洞察：**三者之间差的是数量级**（2000 → 32000 → 232000）。所以"总是给描述"是唯一可行的默认。

## 三、怎么做

### 3.1 第一层描述

描述层**总是在上下文里**，所以它必须极其精简。它要回答两个问题：

1. **这个技能是什么**（用途）。
2. 什么时候用它（触发条件）。

```js
// 描述层：索引只需要名字、用途与触发条件
export function describe(skill) {
  return {
    name: skill.name,
    purpose: skill.oneLinePurpose,
    useWhen: skill.triggers,
    cost: 'description',
  }
}
```

算例实测：**索引读取的字符数是 97**——这是"让模型知道有这么个技能"的最小成本。

97 个字符能做到什么：名字、一句话用途、以及使用条件。**这就是索引该有的体量。**

描述层的三条写法要求：

| 要求 | 反例 | 正例 |
|---|---|---|
| **写清何时用** | "用于测试" | "写新测试、或测试失败需要定位时使用" |
| **写清何时不用** | （缺） | "不用于性能测试，那属于基准测试技能" |
| **不写步骤** | 把第一步写进描述 | 描述只讲目的与触发 |

"写清何时不用"是最容易被漏、效果最明显的一条：**它把最可能的误用挡在门口。**

### 3.2 第二层主体

主体是**具体的操作步骤**，只在技能被选中时加载。算例里加主体后成本是 32000（20 个技能平均每个约 1500 token）。

主体的结构建议：

| 部分 | 内容 |
|---|---|
| 前置条件 | 需要什么环境、什么状态 |
| 步骤 | 有序的操作 |
| 验收 | 怎么知道做对了 |
| 常见问题 | 遇到 X 怎么办 |
| 边界 | 什么情况下这个技能不适用 |

"验收"与"边界"是最常被漏的两节：没有验收，模型做完不知道对不对。没有边界，模型会在不适用的场合硬套。

### 3.3 第三层资源

资源是**大块的附件**：示例代码、模板、脚本、长文档。算例里含资源后总成本是 232000。

**资源绝不能整体加载**，而应当按需读取（用文件读取工具只取需要的那一段）。

**18 倍差距的来源**（32000 → 232000）：资源通常是重复的模板与长示例。 它们对"理解怎么做"帮助有限，对"照着填"帮助大。

做法建议：

| 做法 | 说明 |
|---|---|
| 资源单独存放 | 不塞进技能正文 |
| 按需读取片段 | 用搜索定位而非全文读取 |
| 提供摘要 | 资源旁边给一句话说明 |

"提供摘要"这一条最实用：**给资源写一句"这是什么、什么时候用"，模型就知道要不要去读它。** 这本身就是一层索引。

### 3.4 加载时机

从描述层升到主体层的判据是**技能是否被选中**。选中又分两种：

| 方式 | 做法 | 特点 |
|---|---|---|
| **模型自主选择** | 描述层里有触发条件，模型自己决定 | 灵活，可能选错 |
| **规则匹配** | 根据任务特征自动匹配 | 确定，可能漏 |
| **显式指定** | 用户或系统点名 | 准确，不覆盖 |

推荐组合：**规则匹配做兜底，模型自主选择做主要途径，并允许显式指定覆盖两者。**

这与 2.2 的工具选择是同一个问题：候选越多，选择越难。**所以描述层要精简，且必须写清触发条件。**

### 3.5 校验

技能文件需要校验，否则一个格式错误的技能会导致加载失败或行为异常。算例验证了"**合法技能的索引结果是 `true`**"。

要校验的内容：

| 项 | 为什么 |
|---|---|
| 必填元数据 | 名字、用途、触发条件 |
| 格式 | 解析正确 |
| 引用完整性 | 引用的资源文件存在 |
| 长度 | 描述层不能超预算 |
| 唯一性 | 名字不冲突 |

"长度校验"很实用：**如果某个技能的描述写了 500 字，它会挤占其他技能的索引空间。** 描述层应当有总量预算，并且按预算分配。

### 3.6 版本与失效

技能会过时（1.3 就是这种情况）。三个手段：

| 手段 | 做法 |
|---|---|
| **版本号** | 技能带版本，便于追踪 |
| **最后验证时间** | 记录"这个技能上次被验证有效是什么时候" |
| **失败反馈** | 技能执行失败时记录，连续失败则标记待复核 |

"最后验证时间"是最有效的一条：**一个半年没被验证过的技能，很可能已经过时。** 把它展示给模型（或标注为"可能过时"），比让模型照着做过时的步骤要好。

## 四、特殊情况与处理技巧

| 情况 | 为什么 | 处理 |
|---|---|---|
| 全量加载撑爆窗口 | 没分层 | 三层披露，默认只给描述 |
| 技能被误用 | 描述没写触发条件 | 写清"何时用"与"何时不用" |
| 资源太大 | 资源与主体混放 | 资源单独存放，按需读取 |
| 索引本身太长 | 描述无长度限制 | 描述层总量预算 + 单条上限 |
| 技能过时 | 无验证时间 | 记录最后验证时间 |
| 技能之间冲突 | 两个技能都适用 | 描述里区分适用边界 |
| 技能加载失败 | 格式错误 | 加载前校验，失败则跳过并报告 |
| 技能名冲突 | 无唯一性校验 | 名字唯一 + 命名空间 |

最后一条值得展开：技能来自不同来源（内置、团队、个人），**命名空间（前缀）能避免冲突**，也能让模型知道该技能的权威级别。

## 五、工业界的做法（可照做）

### 5.1 渐进式披露的其他实例

| 场景 | 索引层 | 详情层 |
|---|---|---|
| **技能库** | 名字 + 用途 | 步骤 + 资源 |
| **工具系统**（2.2） | 工具名 + 描述 | 参数 schema + 结果 |
| **文档** | 目录 | 正文 |
| **API 文档** | 端点列表 | 参数与示例 |
| **代码补全** | 签名 | 实现 |

共同的实现形状：**索引层小且总在上下文里，详情层按需加载。**

**这是一个可以复用到任何"内容多于预算"场景的模式。**

### 5.2 技能的组织

| 组织方式 | 优点 | 缺点 |
|---|---|---|
| **按领域**（测试/发布/调试） | 直观 | 一个任务可能跨领域 |
| **按阶段**（计划/实现/验证） | 与循环对应 | 粒度粗 |
| **按工具** | 与工具绑定 | 技能常跨工具 |
| **按来源**（内置/团队/个人） | 权限清晰 | 不便于按任务找 |

推荐：**主分类按阶段（与 2.7 的循环对应），辅以标签（领域、工具）**。这样触发条件容易写。

### 5.3 参数与设计起点

| 参数 | 推荐 | 依据 |
|---|---|---|
| 描述层单条长度 | 1–2 句（50–150 token） | 算例里 20 个技能共 2000 |
| 描述层总量 | 预算的 2%–5% | 不能挤占任务内容 |
| 单技能主体 | 500–2000 token | 太短说不清，太长挤占 |
| 同时加载技能数 | 1–3 个 | 过多会互相干扰 |
| 资源读取 | 按片段 | 全文代价高（算例显示 18 倍差距） |
| 验证周期 | 1–3 个月 | 命令与流程会变 |

### 5.4 一份可落地的实施清单

1. **三层分离**：描述 / 主体 / 资源物理分开存放。
2. 描述层：名字 + 用途 + 何时用 + 何时不用。
3. 长度预算：单条上限与总量上限。
4. 按需加载：主体在选中时加载，资源按片段读取。
5. 选择机制：规则兜底 + 模型选择 + 显式指定。
6. 校验：元数据、格式、引用、长度、唯一性。
7. 命名空间：区分内置、团队、个人。
8. 验证时间：记录并可展示。
9. 失败反馈：连续失败标记待复核。
10. 测试：验证"未选中技能的主体不进入上下文"。

## 六、学术界的结论

### 6.1 程序性记忆

认知科学把"怎么做某件事"归为**程序性记忆**（见 4.1 的记忆分类）。它有两个特点：

| 特点 | 含义 |
|---|---|
| **难以言述** | 熟练的人常说不清自己怎么做的 |
| **通过练习获得** | 需要重复与反馈 |

对技能设计的两条启示：

1. **写下来的技能天然不完整**——它漏掉了"熟练者觉得理所当然"的步骤。所以技能需要在使用中补充（这就是失败反馈的价值）。
2. 技能需要验证（练习与反馈的替代）——一个从未被验证过的技能，其质量是未知的。

### 6.2 技能获取与迁移

学习科学指出技能迁移（把一个场景的技能用到另一个场景）**取决于两者的相似度，且负迁移真实存在**。

对技能库的启示：**表面上相似的任务可能不适用同一个技能。** 所以描述里的"何时不用"与"何时用"同等重要（3.1）。

"负迁移"在 agent 里的表现：模型把技能 A 的步骤套用到不适用的场景，**产生看似合理但错误的操作**。这比"不加载技能"更危险。

### 6.3 提示词的模块化

把提示词拆成可组合模块是一个工程上被反复验证的做法：

| 做法 | 好处 |
|---|---|
| 基础提示 + 任务提示 | 复用基础部分 |
| 按需拼装 | 只加载相关的 |
| 模块有清晰边界 | 便于替换与测试 |

与本篇的对应：**技能就是"按需拼装的提示模块"。** 三层披露是这个思路在成本约束下的具体形式。

一个被验证的结论：**模块化的提示比一整块长提示效果更好**——因为无关内容会稀释注意力（与 1.3 的"上下文污染"同源）。

### 6.4 信息检索视角

技能选择本质是一次检索：**给定任务，找出相关技能**。

**因此可以借用检索系统的全部手段**（见 4.1）：

| 手段 | 在技能上的应用 |
|---|---|
| 词法匹配 | 任务关键词命中技能标签 |
| 语义匹配 | 任务描述与技能用途相似度 |
| 阈值 | 没有足够相关的技能时**不加载任何技能** |

"不加载任何技能"同样重要：**当任务不需要技能时，强行加载一个会让模型跑偏。** 这与 4.1 的"检索必须能返回空集"是同一个结论。

## 七、理论：披露的成本

### 7.1 三层成本的比值

算例实测（20 个技能）：

| 层 | token | 相对描述层 |
|---|---|---|
| 描述 | **2000** | 1 |
| 描述 + 主体 | **32000** | 16 |
| 全量（含资源） | **232000** | **116** |

三个数量级的关键数字：

- **描述层与主体层差 16 倍**。
- 主体层与全量差 7.25 倍。
- 描述层与全量差 116 倍。

结论：**"总是加载全量"在任何规模下都不可行**。算例同时验证：全量超过 128K 窗口（`true`），而只给主体不超（`false`）。

"只给主体不超"这一行给出了一条可行的上限：**如果必须整批加载，主体层是能力上限**。再往上就必须按需。

### 7.2 索引的空间预算

$$
\text{可用技能数} \le \frac{\text{描述层预算}}{\text{单条描述长度}}
$$

算例实测：2000 token 装下 20 个技能 → 平均每条 **100 token**。

含义：**描述层的容量决定了技能库的规模上限。** 想要更多技能，要么压缩描述，要么让索引本身也分层（按领域分组，先选领域再选技能）。

这与 2.2 的"工具数量上限"是同一个约束：**候选越多，选择正确率越低，而索引还占预算。**

## 九、练习

### 第一题：写技能的三层

为一个"排查测试失败"的技能写三层内容。

要求：

- 写描述层：名字、一句话用途、何时用、**何时不用**（含一条与"写新测试"的区分）。
- 写主体层：前置条件、步骤、验收、常见问题、边界各一节。
- 说明资源层放什么，以及如何按需读取。
- 估算三层的 token 数，并说明是否在预算内。

---

### 第二题：算索引预算

场景：描述层预算是 3000 token，平均每条描述 120 token。

要求：

- 算出最多能索引多少个技能。
- 如果技能数增加到 40 个，给出两种解法（压缩描述 / 两级索引）。
- 说明两级索引的触发条件与加载流程。
- 指出"压缩描述"的代价是什么。

---

### 第三题（进阶）：设计技能选择机制

要求：

- 设计一个三层选择机制：规则匹配、模型选择、显式指定，说明优先级。
- 说明如何避免"在一个不需要技能的任务里加载技能"。
- 设计一个"技能冲突"处理：两个技能都声称适用于当前任务时怎么办。
- 设计一套反馈机制：如何发现某个技能在实际使用中效果差。

## 十、算例

算例实现了本篇的三层披露与校验。

```powershell
cd D:\dsh-course
node examples/sa33_skills.mjs        # 全部函数的运行结果
node examples/test_sa33_skills.mjs   # 数字回归断言
```

它做到的事：

- **三层披露的成本**（20 个技能：描述 2000、加主体 32000、含资源 232000）。
- 比值 116，以及"全量超过 128K 窗口"（`true`）与"只给主体不超"（`false`）。

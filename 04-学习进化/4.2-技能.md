## 本篇新词

- 技能（skill） 指一段可复用的做法：有适用条件、步骤与不适用条件。它改的是模型的行为。
- 渐进披露（progressive disclosure） 指按需分层把技能内容给模型看：先描述、再主体、最后资源。
- 元数据层 指技能的名称与一句话描述，是唯一始终可见的一层。
- 触发（trigger） 指判定"当前任务需要这个技能"。
- 适用条件与不适用条件 指技能成立的前提与它明确不适用的情形。
- 技能过时（staleness） 指技能描述的做法与当前系统不再一致。
- 技能冲突 指两个技能给出不一致的做法，分"两套正当做法"与"新旧版本"两类。
- 技能验证 指判断技能是否真的有效，它需要一个能触发的任务与一个可运行的判据。

## 一、【设计原因】

### 1.1 缺陷一：技能写了，但从不被触发

三个具体原因：描述写得太宽（"处理代码相关的任务"，模型无法判断何时用）、写得太窄（"当用户要求重构 TypeScript 的可选链时"，多数情况匹配不上）、或者用词与任务的说法不符（技能写"提交前检查"，任务说"push 之前先看看"）。

三者都发生在元数据层，而修法是同一个：**描述写"什么时候用"，不写"这个技能是关于什么的"。**

### 1.2 缺陷二：全量注入撑爆上下文

把所有技能的全文甚至附加资源都注入的后果是可以量化的：二十个技能全量注入需要二十多万 token，已经超过多数上下文窗口。

它的表现往往不是报错，而是模型行为变差：上下文被大量与当前任务无关的做法占据，而它们会干扰模型对当前任务的判断。

### 1.3 缺陷三：技能过时，而它不会报错

目录结构变了、命令改了、依赖升级了，而技能文档还写着旧的做法。它的特殊危险在于不报错：技能被触发、步骤被执行，而某一步产出的东西是过时的。

防线是"上次验证时间"与"可运行的检查"。没有检查的技能只能靠人记得。

### 1.4 缺陷四：技能被读了，但模型没照做

模型读到了步骤，而在执行时跳过了其中一步（通常是看起来不必要的那一步，例如"先跑一次基线测试"）。

成因有两个：步骤没有被写成可检查的（"仔细检查"无法被验证），以及技能太长而长技能里的步骤会被跳过。处置方式是把关键步骤写成可运行的命令，并让技能尽量短。

### 1.5 由此确定的设计目标

1. 元数据常驻，主体按需加载，资源只列用途与路径。
2. 描述写触发条件，`appliesWhen` 与 `doesNotApplyWhen` 写边界。
3. 触发三种方式组合，显式指定优先。
4. 技能自带可运行的检查，验证分三个阶段报告。
5. 技能与被描述的资产同仓库，过时靠改动顺带发现。

**本节要点**

- 不被触发的原因都在元数据层。
- 全量注入的成本差一到两个数量级。
- 过时不报错，因此需要可运行的检查。
- 长技能里的步骤会被跳过。
- 五条目标：三层披露、描述写何时、三路触发、自带检查、同仓库。

## 二、【直觉】

### 2.1 手册与摘要卡

一本手册很厚，而工位上贴着一张摘要卡。

- 摘要卡写着"什么时候翻手册"，而不是手册的全部内容。
- 需要细节时才翻到对应那一章。
- 附录里的模板只有在你确认需要它时才去拿。

技能库就是这套结构：**摘要卡必须一直在眼前（否则不知道该翻手册），而手册本身按需取。**

::: keypoint 反直觉点
**技能的可用性由描述决定，不由内容决定。** 一个内容写得再好、描述却无法匹配的技能，等于不存在——而它的表现是"系统学会了但没用上"，听起来像模型的问题，实际是元数据的问题。
:::

### 2.2 三层抽屉

- 第一层是**标签**：一句话，始终可见。
- 第二层是**说明**：需要时拉开抽屉取出。
- 第三层是**工具箱**：知道有它、也知道它在哪，但只在真正要用时打开。

三层的成本差不是线性的，而是数量级的：第一层几十个字，第二层一两千字，第三层可能上万字。

### 2.3 一个数字直觉

设描述 100 token、主体 1500 token、资源 10000 token，共 20 个技能。

| 策略 | 注入量 | 相对成本 |
|---|---|---|
| 只给描述 | $20 \times 100 = 2000$ | 1 倍 |
| 描述加全部主体 | $20 \times 1600 = 32000$ | 16 倍 |
| 全量含资源 | $20 \times 11600 = 232000$ | 116 倍 |

第三行已经超过多数窗口。**这就是渐进披露的全部理由**，而它同时说明第二层的加载判据必须准。

**本节要点**

- 摘要卡照着"何时用"写。
- 三层成本差是数量级。
- 二十个技能只给描述约 2000 token。

## 三、【严格】

### 3.1 定义

::: theorem 定义 4.2.1（技能）
一个技能是四元组

$$
K = (\mathit{meta},\ \mathit{body},\ \mathit{resources},\ \mathit{check}),
$$

其中 $\mathit{meta}$ 是元数据，$\mathit{body}$ 是主体（步骤与理由），$\mathit{resources}$ 是附加资源（模板与脚本），$\mathit{check}$ 是可运行的验证命令。
:::

::: theorem 定义 4.2.2（三层披露与成本）
设描述长度 $d$、主体长度 $b$、资源长度 $r$，技能数 $N$。三种披露策略的注入成本是

$$
C_1 = N d, \quad C_2 = N (d + b), \quad C_3 = N (d + b + r).
$$

**元数据层必须常驻**（否则无法被触发），而主体与资源按需。
:::

::: theorem 定义 4.2.3（触发）
触发是三种方式的组合，按优先级：

$$
\mathrm{trigger} = \begin{cases}
\text{显式指定}, & \text{用户给出技能名},\\
\text{检索匹配}, & \mathrm{rel}(\mathit{task}, \mathit{meta}.\mathit{description}) \ge \tau,\\
\text{模型判断}, & \text{描述常驻，由模型决定是否要求加载}.
\end{cases}
$$

三者并非互斥：前两者决定**预加载**，第三者覆盖系统没有匹配到的情况。
:::

::: theorem 定义 4.2.4（适用条件与不适用条件）
技能的适用条件是集合 $\mathrm{Applies}$，不适用条件是集合 $\mathrm{Excludes}$。一次使用 $u$ 被判定为**误用**，当且仅当 $u$ 的特征落在 $\mathrm{Excludes}$ 中。

$$
\mathrm{misuse}(u) \iff \mathrm{feat}(u) \in \mathrm{Excludes}.
$$
:::

::: theorem 定义 4.2.5（验证三阶段）
一次技能验证有结果

$$
\mathrm{validate}(K) \in \{\text{静态失败},\ \text{加载失败},\ \text{检查失败},\ \text{通过}\},
$$

三个阶段分别对应：元数据不合规、主体无法读取、检查命令不通过。**三者不可合并报告**，因为它们的成因不同。
:::

::: theorem 定义 4.2.6（过时）
技能 $K$ 相对系统 $S$ **过时**，当且仅当按 $K$ 的步骤执行得到的产物与 $S$ 当前推荐做法不一致。过时分三类：命令过时、路径过时、做法过时。
:::

### 3.2 命题

::: theorem 命题 4.2.1（披露成本的量级差）
在 $b \gg d$ 且 $r \gg b$ 的常见情形下，$C_2 / C_1 = 1 + b/d$ 与 $C_3 / C_1 = 1 + (b+r)/d$ 都远大于 1。

**证明.** 由定义 4.2.2 直接相除。

↓ **为什么能这么写？** 成本是层内长度之和，而层间长度差一个数量级。

$\blacksquare$

**数值**：$d = 100$、$b = 1500$、$r = 10000$、$N = 20$ 时，$C_1 = 2000$、$C_2 = 32000$（16 倍）、$C_3 = 232000$（116 倍）。

::: keypoint 因此第二层的判据必须准
**二十个技能里若有一半的主体被加载，成本仍然可观。** 阈值与权重的选取因此不是调参，而是成本控制。
:::

::: theorem 命题 4.2.2（可触发性只由元数据决定）
一个技能被检索触发的概率只取决于 $\mathit{meta}.\mathit{description}$ 与任务的相关性，与 $\mathit{body}$ 的内容无关。

**证明.** 由定义 4.2.3 的第二种方式，触发判据是 $\mathrm{rel}(\mathit{task}, \mathit{meta}.\mathit{description})$。它不引用 $\mathit{body}$。故主体内容不进入该判据。

↓ **为什么能这么写？** 触发发生在主体被加载之前，因此判据不可能依赖主体的内容。

$\blacksquare$

::: keypoint 描述是接口，不是摘要
**它要回答"何时用"，而不是"关于什么"。** 检查方式是把描述交给一个不知道技能存在的读者，让他判断若干任务该不该用——这条判据可以被实测。
:::

::: theorem 命题 4.2.3（不适用条件对冲套用倾向）
设模型读到技能后使用它的概率为 $p_{\text{use}}$。写入 $\mathrm{Excludes}$ 后，落在排除集合内的情形被排除，误用概率的上界由 $1 - |\mathrm{Excludes}\ \text{的覆盖}|$ 决定。

**证明.** 由定义 4.2.4，一次使用落在 $\mathrm{Excludes}$ 时被判定为误用。若技能声明了排除集合，则该情形在裁决阶段被拦下。未声明时 $p_{\text{use}}$ 在这些情形下不被降低。

↓ **为什么能这么写？** 对冲需要一条可判定的排除规则。

$\blacksquare$

**数值**：一次失败要被归因为"用错了方法"，判据正是"这次情形是否落在它的不适用条件里"。**没写排除条件的技能，其失败无法被归因到技能上。**
:::

::: theorem 命题 4.2.4（做法过时不能由检查命令发现）
$\mathit{check}$ 能检出命令过时与路径过时，但不能检出做法过时。

**证明.** 检查是一段可运行的程序，它判定的是"这些命令是否成功、这些路径是否存在"。做法过时指命令仍成功、路径仍存在，而推荐做法已变——该情形下检查的输入条件全部满足，故检查输出为通过。

↓ **为什么能这么写？** 检查的可判定性以"成功/失败"为值域，而"是否仍推荐"不在这个值域里。

$\blacksquare$

::: keypoint 因此还需要第二条防线
**`verifiedAt` 加定期重验，让做法过时有被发现的机会。** 而最有效的一条是"技能与被描述的资产同仓库"——改动的评审会顺带看到它。
:::

::: theorem 4.2.5（索引成本与技能大小无关）
若索引阶段只读元数据，则启动成本为 $O(N d)$。若索引读入全文，则成本为 $O(N(d+b+r))$。

**证明.** 索引是一次遍历，每个技能读取的字节数决定了总成本。只读前置元数据时读取量为 $d$，读全文时为 $d+b+r$。

↓ **为什么能这么写？** 总成本是逐项读取量之和。

$\blacksquare$

**数值**：$N = 20$ 时两者相差约 116 倍，而渐进披露的收益正是在启动那一刻被这条实现保住的。

::: theorem 4.2.6（动态冲突检测的充分性与边界）
同一次任务里加载了两个满足 $\mathrm{Applies}$ 重叠的技能时，动态检测可以发现"并存冲突"。它不能发现"分时冲突"（两个技能在不同任务里各自被使用）。

**证明.** 检测的输入是加载事件流。并存冲突在同一次任务的事件里出现两次加载，故可检出。分时冲突的两次加载落在不同任务的事件里，事件流不提供"它们矛盾的"这一信息，故不可检出。

↓ **为什么能这么写？** 检测的判据是"同一批次内出现两次重叠"，而分时冲突不在同一批次内。

$\blacksquare$

### 3.3 本节要点

**本节要点**

- 技能是元数据、主体、资源与检查的四元组（定义 4.2.1）。
- 三层披露的成本差一个数量级（定义 4.2.2）。
- 触发是显式、检索与模型判断的组合（定义 4.2.3）。
- 不适用条件让误用可判定（定义 4.2.4）。
- 验证分静态、加载、检查三个阶段（定义 4.2.5）。
- 过时分命令、路径、做法三类（定义 4.2.6）。
- 披露成本的量级差（命题 4.2.1）。
- 可触发性只由元数据决定（命题 4.2.2）。
- 不适用条件对冲套用倾向（命题 4.2.3）。
- 做法过时不能由检查发现（命题 4.2.4）。
- 索引成本与技能大小无关（命题 4.2.5）。
- 动态冲突检测能发现并存而不能发现分时（命题 4.2.6）。

## 四、【回到直觉】

- **定义 4.2.1 说的**：一个技能由标签、说明、工具箱与一条自检命令组成。
- **定义 4.2.2 说的**：标签一直挂着，说明按需取出，工具箱只在要用时打开。
- **定义 4.2.3 说的**：点名的优先，其次是按相关性预取，最后是所有标签常驻由模型自己判断。
- **定义 4.2.4 说的**：写清"什么情况下别用它"，误用才有可能被判出来。
- **定义 4.2.5 说的**：验证失败要说清是格式不对、读不出来、还是检查没过。
- **定义 4.2.6 说的**：命令失效、路径失效都容易发现，做法失效最隐蔽。
- **命题 4.2.1 说的**：二十个技能只给标签 2000 token，全量给 232000。
- **命题 4.2.2 说的**：标签写不好，说明写得再好也没人翻开。
- **命题 4.2.3 说的**：不写"别用它"，它就会在不该用的时候被用上。
- **命题 4.2.4 说的**：自检命令查不出"这一步已经不是现在的推荐做法"。
- **命题 4.2.5 说的**：索引只读标签，启动成本才与技能大小无关。
- **命题 4.2.6 说的**：两个技能同时被加载时的矛盾能被发现，分时使用的矛盾不能。

**本节要点**

- 标签决定可触发。
- 说明按需取。
- 工具箱只列路径。
- 排除条件让误用可判。
- 过时有三种，做法类最难。

## 五、【工具箱】

### 5.1 该不该沉淀成技能

判据是：**它被重复做过至少两次，而第二次做的时候参考了第一次。**

一次性的做法不值得沉淀（写技能的成本高于直接做），而"第二次参考第一次"说明它已经形成了方法。

### 5.2 描述的写法

| 写法 | 例子 | 结果 |
|---|---|---|
| 写主题（错） | 本技能关于 TypeScript 重构 | 无法判断何时用 |
| 写触发条件（对） | 当需要在大规模重命名后保持行为不变时 | 可匹配 |

**配套**：`appliesWhen` 写更细的边界，`doesNotApplyWhen` 写反面。三者构成完整的触发与误用闸门。

### 5.3 加载时机

主体应当**在任务早期加载**。理由是它会参与该任务后续所有轮次的前缀，越早加载，后续轮次越多地受益于缓存。

**代价**：可能提前加载了用不上的技能。判据是"加载之后的做法真的变了吗"。

### 5.4 验证与过时排查

| 阶段 | 失败原因 | 处置 |
|---|---|---|
| 静态 | 元数据不合规 | 改格式 |
| 加载 | 主体读不出来 | 修路径 |
| 检查 | 命令不通过 | 更新做法 |

**做法过时不在上表里**，它需要靠 `verifiedAt` 与定期重验，以及"技能与代码同仓库"这条位置安排。

### 5.5 冲突的两类处置

| 类型 | 例子 | 处置 |
|---|---|---|
| 两套正当做法 | 两种测试策略 | 明确优先级，各写在 `appliesWhen` 里 |
| 新旧版本 | 旧流程与新流程 | 废弃旧的，因为并存会随机命中 |

**发现方式**：动态检测（同一次任务里加载了两个条件重叠的技能）可以发现并存冲突，这是可自动的。

**本节要点**

- 沉淀门槛是"被做过两次且第二次参考了第一次"。
- 描述写"何时"，并配两条边界。
- 主体在任务早期加载。
- 验证分三阶段，做法过时要另想办法。
- 冲突两类两类处置。

### 7.2 索引段与触发段

索引段只读前置元数据，触发段按优先级组合三种方式。

```js
// 定义 4.2.5：索引阶段只读元数据，并校验必填与长度
export const LIMITS = { name: 64, description: 1024 }

export function indexSkill(dir, readMeta) {
  const text = readMeta(dir)
  const m = /^---\n([\s\S]*?)\n---\n([\s\S]*)$/.exec(text)
  if (!m) return { ok: false, reason: '缺少前置元数据' }
  const meta = Object.fromEntries(
    m[1].split('\n').filter(Boolean).map((line) => {
      const i = line.indexOf(':')
      return [line.slice(0, i).trim(), line.slice(i + 1).trim()]
    }),
  )
  if (!meta.name || !meta.description) return { ok: false, reason: 'name 与 description 必填' }
  if (meta.description.length > LIMITS.description) return { ok: false, reason: `描述超过 ${LIMITS.description} 字符` }
  return { ok: true, meta, bodyLength: m[2].length }
}
```

三种方式里前两种在这里实现，第三种（描述常驻、由模型判断）发生在注入层，因为它不产生加载动作。

```js
// 定义 4.2.3：显式指定优先，其次是检索匹配
export function selectSkills(task, metas, opts) {
  if (opts.explicitName) return metas.filter((m) => m.name === opts.explicitName)
  return metas
    .map((m) => ({ m, s: relevance(task, m.description) }))
    .filter((x) => x.s >= opts.threshold)
    .sort((a, b) => b.s - a.s)
    .slice(0, opts.maxLoad)
    .map((x) => x.m)
}

/** 一个可检验的相关性：任务是否包含描述里的关键词。 */
export function relevance(task, description) {
  const words = description.toLowerCase().split(/[\s,，。]+/).filter((w) => w.length >= 2)
  const hit = words.filter((w) => task.toLowerCase().includes(w)).length
  return words.length === 0 ? 0 : hit / words.length
}
```

### 7.3 加载段

加载段读取主体、记一条事件，并只列资源的用途与路径。

```js
// 定义 4.2.2：加载主体、追加事件、只列资源引用
export function loadSkillBody(meta, body, resources, events, now) {
  events.push({ type: 'skill/load', name: meta.name, at: now })
  const lines = [`# 技能：${meta.name}`, meta.description, '', body, '', '## 可用资源']
  for (const r of resources) lines.push(`- ${r.purpose}：${r.path}`)
  return lines.join('\n')
}
```

### 7.4 验证段与冲突段

验证段分三阶段报告，冲突段从加载事件里找重叠。

```js
// 定义 4.2.5：三阶段验证，失败原因不可合并
export function validateSkill(meta, loader, runner, now) {
  if (!meta.check) return { ok: false, phase: 'static', reason: '缺少 check 字段' }
  const body = loader(meta.name)
  if (body === null) return { ok: false, phase: 'load', reason: '主体无法加载' }
  const r = runner(meta.check)
  return { ok: r.ok, phase: 'check', reason: r.summary, checkedAt: now }
}
```

冲突检测的输入是加载事件流，因此它只能看见同一批次里的两个技能。

```js
// 命题 4.2.6：从同一次任务的加载事件里发现重叠
export function detectConflicts(events, metasByApplies) {
  const loaded = events.filter((e) => e.type === 'skill/load').map((e) => e.name)
  const conflicts = []
  for (let i = 0; i < loaded.length; i++) {
    for (let j = i + 1; j < loaded.length; j++) {
      const a = metasByApplies[loaded[i]] ?? []
      const b = metasByApplies[loaded[j]] ?? []
      if (a.some((x) => b.includes(x))) conflicts.push({ pair: [loaded[i], loaded[j]], overlap: a.filter((x) => b.includes(x)) })
    }
  }
  return conflicts
}
```

### 9.2 失败模式

**（1）检查放在装载期（L9 位置放错）。** 描述的可匹配性在写技能时判断一次，而任务的说法会变。表现是"以前能被触发的技能现在不触发了"。

**（2）前提会变（L9）。** 命题 4.2.6 的动态检测以"冲突的两个技能会在同一次任务里同时加载"为前提。若它们从不同时加载，检测永远不会报警。

**（3）描述写成主题。** 技能存在但永不触发。

**（4）缺少不适用条件。** 技能在不该用的场合被用上，且失败无法归因到它。

**（5）索引阶段读全文。** 启动成本与技能库大小成正比，渐进披露的收益被吃掉。

**（6）加载不记事件。** 观测与冲突检测都失去依据。

**（7）资源内容内联进主体。** 主体被撑大，第三层的成本转移到了第二层。

**（8）没有可运行的检查。** 过时无法被发现，只能靠人记得。

**（9）两套正当做法不写优先级。** 模型在两者之间随机挑，行为不稳定。

**（10）新旧技能并存。** 旧技能被随机命中，产生过时的产物。

**本节要点**

- 决策表覆盖 12 种情形。
- 失败模式十条，前两条是位置放错与前提会变。
- 最隐蔽的是"做法过时"——检查命令会通过，而产物已经过时。

## 十、仍未解决

- **触发依赖描述的措辞。** 换语言或用词习惯时漏触发。
- **没有自动的技能生成。** 沉淀仍然靠人。
- **冲突检测只能发现同时加载的重叠。** 分时使用的冲突发现不了。
- **没有技能的权限模型。** 高副作用步骤与普通技能同等对待。
- **遵从度无法测量。** 无法区分"遵循了技能"与"碰巧做对了"。
- **技能没有大小上限。** 一个超长技能会撑爆上下文。

**本节要点**

- 措辞依赖与遵从度测量是两个真实缺口。
- 冲突检测与权限模型都只覆盖了一半。

**参考要点**

1. 工具提供能力、记忆提供事实、技能提供方法。前两者的作用是确定的，技能的可靠性取决于模型是否遵循。
2. 元数据层（描述）、主体层（步骤）、资源层（模板与脚本）。成本分别是 $Nd$、$N(d+b)$、$N(d+b+r)$，相差一到两个数量级。
3. 因为触发需要的是一个判断而不是一个主题，而主题无法区分"该用"与"不该用"。
4. 显式指定优先，其次是检索匹配（用于预加载），描述常驻由模型判断覆盖前两者没匹配到的情况。
5. 因为多数做法在错误的场合会产生误导、模型倾向于套用已知做法、而不适用条件是诊断的输入。缺了它，误用无法被归因到技能。
6. 静态、加载、检查。三者成因不同（格式、读取、内容），合并报告会让诊断失去方向。
7. 命令过时、路径过时、做法过时。做法过时最难，因为命令仍成功、路径仍存在。
8. 同仓库能享受改动的评审、测试的影响范围与版本的一致性三种顺带发现。
9. 两套正当做法（明确优先级）与新旧版本（废弃旧的）。
10. 能发现同一次任务里加载的两个条件重叠的技能，不能发现分时使用的冲突。
11. 它被重复做过至少两次，而第二次做时参考了第一次。
12. 因为"仔细检查"无法被验证，而跑一条命令更难被跳过。

## 十二、系统影响回溯

**影响一：描述质量决定系统的学习效果。** 描述是触发入口，因此它值得被当作接口文档来写。

**影响二：技能与记忆争抢上下文，而预算需要分开。** 元数据层必须常驻，因此给它一个固定预算。主体与记忆共享剩余空间。

**影响三：技能过时是演化系统里最隐蔽的失效。** 它不报错，因此需要"上次验证时间"与可运行的检查。

**一处需要修正的预判。** 旧稿把技能与工具的关系说成"两种扩大能力的手段"，读完之后要更准确地表述：**它们扩大的东西在方向上不同**——工具扩大动作的集合（能做什么），技能改变动作的选择与顺序（怎么去做）。这个区别的实践后果是：加工具会改变系统的能力边界（2.2 命题 2.2.1），而加技能不改变边界，只改变在边界内如何行动。

**通向下一步的桥。**

前两篇积累的是"事实"与"做法"，而它们的对象都是一般性的。系统还需要第三类积累：**关于某个特定的人**——他偏好什么、他的水平如何、他和别人有什么不同。那类模型的写入条件、检索条件与前三者都不同，因为它描述的是一个人而不是一件事。

所以下一篇是 4.3 用户建模。

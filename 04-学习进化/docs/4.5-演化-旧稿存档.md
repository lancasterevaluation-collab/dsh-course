## 本篇新词

演化（evolution） 在这里指系统对自身配置、提示词与资产的修改。它与"学习"的区别在于改动的对象：记忆与技能的写入改的是数据，演化改的是规则本身（提示词、阈值、工具描述、技能的组织方式）。

提议（proposal） 指一次演化的候选方案：它要改什么、改成什么、以及为什么。提议的形态是一份可评审的差异（diff），而不是一个动作——可评审是门控的前提，因为无法评审的改动无法被拒绝。

门控（gate） 指决定提议是否被接受的一组检查。它分三层：静态检查（格式、可解析、不违反约束）、离线评估（在一组任务上对比改前改后的表现）、以及灰度（在小比例流量上试运行）。三层的成本递增而信心递增。

灰度（canary） 指在部分流量上先启用新版本。它与"离线评估"的差别在于真实分布：离线任务集是选出来的，而真实流量带着它的全部长尾。

回滚（rollback） 指把系统恢复到修改之前的状态。它的可行性在 1.5 被分为四级（无需回滚、可撤销、需补偿、不可逆），而演化的门控应当只接受前两级。

目标漂移（objective drift） 指自我修改让系统偏离原本的目标。它的成因是"被优化的指标不等于目标"（3.6 的古德哈特定律在自我修改上的版本）：一个以"减少步数"为目标的修改会让系统倾向于提前放弃。

元控制（meta-control） 指对演化规则本身的约束：哪些东西可以被演化修改，哪些不能。它是这个闭环里最重要的一层保护——因为一次错误的演化如果能改掉门控本身，那么后续的所有检查都会失效。

演化震荡（oscillation） 指两次修改互相抵消（改回上一版的做法）。它的成因是评估噪声（两次评估的差异落在噪声范围内），而处置是要求改动带来的改善大于噪声（一个可计算的判据）。

## 第 0 节 · 学完这一篇你能做出什么

### 0.0 先行组织者：四个问题

```
┌──────────────────────────────────────────────────────────────────────┐
│  ① 提议什么 —— 可以改的对象与形态                    → 1.1、1.2       │
│  ② 怎么门控 —— 静态、离线、灰度三层                  → 1.3           │
│  ③ 怎么回滚 —— 版本化、原子切换、状态兼容            → 1.4           │
│  ④ 什么不能改 —— 元控制与目标漂移                    → 1.5、1.6       │
└──────────────────────────────────────────────────────────────────────┘

 一句话串起来：提议什么 → 怎么门控 → 怎么回滚 → 什么不能改
```

这张图的关键线索在第四块：自我修改的能力上限由"什么不能改"决定。一个能改掉自己门控的系统在第一次错误的演化之后就不再受约束，因此元控制不是可选的限制，而是这个机制能长期存在的前提。

### 0.1 一个具体的判断：三层的成本与漏检率

下面这张表给出三层门控的成本量级与它们各自能挡住的错误。

| 层 | 成本 | 能挡住 | 挡不住 |
|---|---|---|---|
| 静态检查 | 毫秒级（解析与规则） | 格式错误、越权修改、语法问题 | 行为变差 |
| 离线评估 | 分钟到小时级（跑一组任务） | 在评估集上的性能退化 | 评估集之外的退化 |
| 灰度 | 小时到天级（真实流量的子集） | 真实分布下的退化 | 长期影响与稀有场景 |

第二行与第三行的差别值得量化：如果离线评估集有 50 个任务，而某个改动只在 1% 的流量上造成退化，那么它在评估集上被发现的概率约为 40%（1 − 0.99⁵⁰）——多数情况下它会被漏掉，而灰度的观察窗口越长，它被发现的机会越大。

这条量化解释了为什么三层都要有：静态检查的成本几乎为零但不看行为，离线评估看行为但样本有限，灰度覆盖真实分布但成本最高。 三层不是冗余，而是三种不同失效模式的对策。

### 0.2 本篇建立的三项判据

第一项用于判断一个改动是否该被演化产生：问"它的理由能不能追溯到一次具体的失败或一个具体的观察"。追溯不到的改动是偏好而非演化（它应当由人直接改，而不是由闭环产生）。

第二项用于判断一个改动是否该被接受：问"它带来的改善是否大于评估噪声"。这条判据是可计算的（用同一组任务跑两次得到的差异分布作为噪声估计），而它挡住演化震荡。

第三项用于判断一个改动是否能被安全地演化：问"它落在可逆性的哪一级"。只有前两级（无需回滚、可撤销）可以被自动接受。需补偿与不可逆的改动必须由人执行。

### 0.3 十分钟练习：噪声与改善的比较

下面这段代码用同一组任务的两个基线运行估计噪声，再判断一个改动是否值得接受。

```js
const baselineA = [0.72, 0.68, 0.75, 0.70, 0.74, 0.69]   // 同一版本两次运行的量表（例如成功率）
const baselineB = [0.71, 0.70, 0.73, 0.71, 0.72, 0.70]
const candidate = [0.78, 0.76, 0.79, 0.77, 0.80, 0.75]

const mean = (xs) => xs.reduce((a, b) => a + b, 0) / xs.length
const noise = Math.abs(mean(baselineA) - mean(baselineB))    // 同一版本的差异就是噪声
const gain = mean(candidate) - (mean(baselineA) + mean(baselineB)) / 2
console.log(`噪声 ${noise.toFixed(3)}　改善 ${gain.toFixed(3)}　接受：${gain > 2 * noise}`)
```

这段代码的三处要点：噪声用同一版本两次运行的差异来估计（而不是用理论公式）、改善必须显著大于噪声（这里取两倍作为阈值）、以及两次基线运行必须用同一组任务（否则差异里混进了任务集的变化）。

> **面试视角**
> **高频问法**："你允许 agent 修改自己吗？"
> **高分要点**：说出三层门控与"只接受前两级可逆性"这两条，并指出元控制（门控本身不可被演化修改）。只说"可以，但是要小心"没有回答这个问题。

### 0.5.3 三个连锁影响

第一，演化会让系统的行为随时间变化，而"可复现"这条性质必须重新定义。 一次两周前的失败在今天可能无法复现，因为系统已经改过——这不是 bug，而是演化的必然结果。处置方式是把版本写进日志（每条事件带当时的演化版本），而它同时解决了另一个问题：诊断时能知道"当时是哪个版本"（4.4 的已知条件之一）。

第二，门控的有效性取决于评估集的质量，而评估集本身就是可以被演化修改的对象。 一个"把评估集里难的用例删掉"的改动会让所有改动都通过门控——这条路径必须被元控制挡住（评估集属于不可演化修改的对象）。它与"测试不能被被测代码修改"是同一条原则。

第三，演化会引入一类新的失败：震荡。 两次修改互相抵消的成因是评估噪声（0.2 的第二项判据），而它的后果除了浪费之外还有一条：它让演化的历史变得不可读（从版本序列里看不出系统在往哪个方向走）。处置方式是在接受改动时记录"它相对哪个基线改进了多少"，而不只是记录改动本身。

### 0.5.4 它与本书其余部分的关系

本篇的演化是文本级与配置级的（提示词、阈值、技能、工具描述），因此它的可逆性天然较高。代码级的自我修改（系统改自己的实现）不在本课程范围内，理由是它的可逆性低得多（回滚需要重新构建与部署），而收益并没有相应地高——多数有价值的演化落在提示词与配置上。

> **面试视角**
> **高频问法**："为什么不让 agent 直接改代码？"
> **高分要点**：说出可逆性这条判据（代码级修改通常是"需补偿"或"不可逆"级），并指出多数有用的演化落在提示词与配置上——收益相近而风险低一个量级。

## L0 要解决的问题

### 0.1 现象一：改动没有理由，追溯不到一次失败

第一个现象是演化失去了它的输入。系统里有一批改动（"加了一条提示建议"、"把阈值从 3 改成 5"），而没有人能说出它们为了解决什么问题。它们的来源通常是某次演示、某个直觉、或者对某篇文章的模仿。

它的后果有两个：无法判断它们是否还有必要（也就无法清理），以及无法在它们导致退化时定位（一次退化发生在多处改动之后）。修法是 0.2 的第一项判据——每个改动都要能追溯到一次具体的失败或观察，而那正是 4.4 的结论结构提供的（现象、候选、动作）。

### 0.2 现象二：改完之后变差了，而没有人知道

第二个现象是门控缺失。改动的验证方式是"跑一个看着还行的任务"，而它的问题在 0.1 的表格里给出了：单次运行无法区分改善与噪声，而它更无法覆盖评估集之外的分布。

它的修法是把门控分成三层（1.3），并让每一层的判据不同：静态检查管"格式与权限"、离线评估管"在已知任务上是否退化"、灰度管"在真实分布上是否退化"。

### 0.3 现象三：出问题回不去

第三个现象是回滚缺失。改动被应用之后，系统在某处开始表现异常，而团队无法快速退回到上一版——因为改动涉及多处（提示词、配置、技能），而它们各自改动的时间不同，没有人能确定"上一版"是哪一组。

修法的核心是把一组改动作为一个版本处理（1.4）：版本内的一致性由版本号保证，切换是原子的，而回滚就是切到上一个版本。这条做法与 3.5 的检查点是同一形状（一个可回退的位置加上它的完整性）。

### 0.4 现象四：改来改去，而系统没有往任何方向走

第四个现象是震荡。两次改动互相抵消的成因是评估噪声（0.1 的第二行），而它的表现是版本序列看起来在动而系统的指标在同一个水平上波动。

它的修法是那条可计算的判据（0.2 的第二项）：改善必须显著大于噪声。它把"改动带来了改善"与"这次跑得好"区分开，而后者不值一次改动。

### 0.5 现象五：门控被绕过

第五个现象是元控制缺失。它的形态是：为了让某个改动通过验证，评估集里"有问题的那几个用例"被调整了。或者门控的阈值被调宽了。这些改动本身看起来都是合理的（"用例标注有误"），而它们的累积效果是门控失去意义。

修法是 1.5 的边界：门控本身、评估集、以及日志完整性属于不可被演化修改的对象。而这条边界的检查必须在静态层完成（它是最高的权限检查）。

### 0.6 这一篇要正面回答的四个问题

第一，可以改什么、提议长什么样（1.1、1.2）。第二，怎么门控（1.3）。第三，怎么回滚（1.4）。第四，什么不能改、怎么防目标漂移（1.5、1.6）。

四个问题里第四决定了能力上限，而它的重要性随系统的自主程度上升——一个需要人审批每个改动的系统，元控制可以由人来兜底。而一个自动化的闭环完全没有兜底。

## L1 设计与原理

### 1.1 可以改的对象

可演化的对象有三类，而它们的可逆性不同。

| 对象 | 例子 | 可逆性（1.5 的分级） | 生效范围 |
|---|---|---|---|
| 配置与阈值 | 重试次数、压缩阈值、注入预算 | 可撤销（改回即可） | 立即 |
| 提示词与工具描述 | 系统提示的一段、某工具的 `description` | 可撤销 | 下一次请求起 |
| 技能与记忆规则 | 一条技能的适用条件、写入策略 | 可撤销 | 下一次触发起 |
| 代码 | 实现本身 | 需补偿或不可逆 | 需重新构建部署 |

前三类落在"可撤销"级（1.5 的 1.3），因此它们可以被自动接受。第四类要求重新构建与部署，回滚成本高一个量级，因此它必须由人执行。这条分工解释了为什么本课程的演化只覆盖前三类（0.5.4）。

第三列的"立即"与"下一次请求起"有实践含义：配置类改动的效果是立即的，而它的影响面也立即变化——这对灰度是有利的（可以精确控制哪些请求用新配置），而提示词类改动需要按请求维度分流。

### 1.2 提议的形态

提议是一份可评审的差异，包含四个部分。

改动的内容（差异本身）：改了哪个对象的哪一部分。它的实现方式是给出"改前"与"改后"两段文本，而不是一句"把阈值调大"——后者无法被机械应用，也无法被评审。

理由：追溯到哪次失败或哪个观察（0.2 的第一项判据）。理由的存在让评审者能判断"这个改动是否真的针对那个原因"。

预期：这个改动预期改善什么指标，以及预期幅度。预期的作用在评估阶段体现——它让"没有改善"成为一个可判定的结果（而不是"没看出来"）。

回滚方式：这个改动怎么撤回。对前三类对象，它通常就是"应用反向差异"，而写明它有另一个作用：它迫使提议者确认这个改动是可撤销的。

```ts
interface Proposal {
  readonly id: string
  readonly target: { kind: 'config' | 'prompt' | 'skill' | 'tool-desc'; path: string }
  readonly diff: { before: string; after: string }        // 可机械应用
  readonly reason: string                                  // 追溯到 4.4 的结论
  readonly expectation: { metric: string; delta: number }   // 预期改善
  readonly rollback: string                                 // 怎么撤回
  readonly originVersion: string                            // 基于哪个版本（1.4）
}
```

七个字段里 `originVersion` 是最容易漏掉的：没有它时，一个基于旧版本的提议在应用到新版本上会产生意外结果（通常表现为"改动生效了但和预期不同"，因为中间已经有过其他改动）。

### 1.3 三层门控

三层的分工与成本在 0.1 的表格里给出，这里补充每层的判据。

静态检查回答"这个改动能不能被应用、会不会越权"。它包含：格式可解析、`target` 在允许的范围内、不是元控制对象（1.5）、与 `originVersion` 的差异可干净应用（无冲突）。这一层的成本几乎为零，而它能挡住最危险的一类提议（试图修改门控本身）。

离线评估回答"在已知任务上是否退化"。它的做法是在同一组任务上跑改前与改后两个版本，比较目标指标与护栏指标（3.6 的 1.7）。它的两个要求：任务集固定（否则差异里混进了任务变化），以及至少两个基线观测点（用于估计噪声，0.3 的练习）。

灰度回答"在真实分布上是否退化"。它的做法是让一部分请求使用新版本，并观察目标指标与护栏指标。它的观察窗口需要长到能覆盖周期性（例如一天里的不同时段），否则它会漏掉与时间相关的退化。

### 1.4 回滚

回滚的四个组成部分。

版本化：一组改动作为一个版本，版本之间有明确的先后。实现方式是版本号加每个版本的完整差异集（而不是逐条改动）——逐条改动无法定义"上一版"（0.3 的现象）。

原子切换：切换版本是原子的（3.5 的原子写在这里复用）。半应用的状态是最危险的——它既不是旧版本也不是新版本。

状态兼容：新旧版本对持久状态的理解可能不同（例如新版本引入了一个配置字段）。处置方式是每个版本声明它能读的状态版本范围，而回滚只允许回到"能读当前状态"的版本。这条要求与 3.5 的迁移相接：引入新字段的改动需要同时考虑它的读兼容性。

观察窗口：回滚的触发条件需要被写下来（哪个指标、超过多少、持续多久），否则回滚的决定会变成临时的判断——而临时判断在压力下通常不会发生。

```ts
export async function rollback(store: VersionStore, to: VersionId, ctx: Context): Promise<void> {
  const current = await store.current()
  const target = await store.load(to)
  if (!target.canReadState(await store.stateVersion())) {
    throw new Error(`目标版本 ${to} 无法读取当前状态，需先迁移`)   // 状态兼容检查
  }
  await store.appendEvent({ type: 'evolution/rollback', from: current.id, to, at: ctx.now })
  await store.atomicSwitch(to)                                   // 原子切换
}
```

这段实现的三处要点：状态兼容检查在切换之前、回滚动作被记录（它是诊断的已知条件之一）、切换是原子的。

### 1.5 元控制：什么不能改

不可被演化修改的对象有四类，而它们的检查必须在静态层。

门控本身：检查规则、评估阈值、灰度比例。一个能被改动修改的门控等于没有门控（0.5 现象五）。

评估集：任务与标注。它与前一条同类——评估集是门控的输入，改它就等于改门控。这条限制与"测试不能被被测代码修改"完全一致。

日志与审计记录：它们是不可伪造的事实来源（2.7）。如果演化能修改日志，那么诊断与观测的全部结论都失去依据。

元控制列表本身：这份列表不可被演化修改。这条是递归的终点——它保证了前面的三条限制不会被逐步削减。

四类之外，还有一类需要额外保护的对象：安全相关的约束（3.2 的守卫规则、沙箱边界）。它们不是绝对不可改，而是改动的门控更严（例如需要人工审批），因为它们的失效后果不可逆（与 1.5 的"不可逆"级同类）。

### 1.6 目标漂移与它的对策

目标漂移（本篇新词）的成因是"被优化的指标不等于目标"。三条对策。

对策一是护栏指标（3.6 的 1.7）：每个演化目标都配一个护栏，而护栏的退化会否决改动。这条对策的关键在于护栏指标必须由元控制保护（它不能同时被演化修改），否则它会随目标一起被调整。

对策二是演化方向的一致性检查：定期比较最近若干次改动的目标指标变化，看它们是否指向同一个方向。如果改动频繁而目标指标不动（1.3 的现象四），说明改动在互相抵消，或者目标指标被错误地度量了。

对策三是人的定期复核：即使门控自动化，也应当保留一个定期的人工检查——它检查的不是单次改动，而是"最近一系列改动在做什么"。这条对策与 4.3 的边界同类：完全自动化的自我修改缺少一个外部视角，而那个视角能发现系统自己看不见的漂移。

### 1.7 震荡与噪声的判据

震荡的判据是可计算的（0.2 的第二项与 0.3 的练习）：改善必须大于评估噪声的两倍。噪声用同一版本两次运行的差异估计，而阈值的倍数取 2 是一个工程折中（1 倍太松、3 倍会漏掉小幅改善）。

震荡的第二种形态是两个改动方向相反但各自都有理由。它的信号是"改动 A 的理由"与"改动 B 的理由"在同一个对象上，而处置是要求后续提议在理由里说明它与前一次改动的关系（而不是各自独立地改）。

### 1.8 两次追问

工程侧的问题是什么时候该暂停演化。判据是"连续若干次改动都没有带来显著改善"（它可能是评估方法失效的信号），或者"护栏指标开始持续下降"。暂停之后应当回到 4.4 的诊断，而不是继续尝试改动——改不动通常说明原因找错了。

产品侧的问题是演化的结果对用户意味着什么。多数用户不需要知道系统改了自己的提示词，而他们需要知道行为是否稳定（系统不会今天一个样明天一个样）。因此演化应当有节奏（4.6 的复盘周期）而不是随时发生，并且用户可感知的行为改变应当被明确告知（"我们调整了默认的输出长度"）——静默的行为漂移是最难被接受的一种变化。

## L2 决策表

| # | 决策 | 我们的选择 | 替代方案 | 代价落在谁身上 |
|---|---|---|---|---|
| 1 | 可演化的对象 | 配置、提示词、技能、工具描述 | 含代码 | 能力边界较窄；换来改动可撤销 |
| 2 | 提议的形态 | 可机械应用的差异 + 理由 + 预期 + 回滚式 | 一句描述 | 写提议更费事；换来可评审可拒 |
| 3 | 理由的追溯 | 必须追溯到一次失败或观察 | 可选 | 有些改动写不出理由；换来能判断是否还有必要 |
| 4 | 基线版本 | 提议记录它基于哪个版本 | 不记 | 字段更多；换来应用时能检出冲突 |
| 5 | 门控的层数 | 三层（静态、离线、灰度） | 只做离线 | 成本更高；换来覆盖三种失效模式 |
| 6 | 离线评估的任务集 | 固定且不可被演化修改 | 可随需要调整 | 评估集会过时；换来门控不被绕过 |
| 7 | 接受的判据 | 改善大于两倍噪声 | 任何改善 | 会漏掉小幅改善；换来挡住震荡 |
| 8 | 删改的粒度 | 一组改动作为一个版本 | 逐条应用 | 版本粒度较粗；换来能定义"上一版" |
| 9 | 版本切换 | 原子 | 逐项应用 | 实现更复杂；换来不产生半应用状态 |
| 10 | 状态兼容 | 版本声明可读的状态范围 | 不检查 | 回滚可能被拒；换来回滚不会读错数据 |
| 11 | 灰度的观察窗口 | 长到覆盖周期性（例如一天） | 固定小时数 | 反馈更慢；换来不漏时间相关的退化 |
| 12 | 元控制的对象 | 门控、评估集、日志、这份列表本身 | 无保护 | 能力受限；换来闭环不被自己削弱 |

其中两条值得展开，因为它们的选择在实践中经常被做成另一个。

### 关于第 6 与第 12 条的完整论证（为什么门控的输入不可被门控修改）

替代方案是把评估集当作普通资产（可以随需要增删用例）。它的吸引力是明显的——用例标注确实会有错误，而修正它看起来是改进。它的问题在于"修正"与"放宽"在实现上无法区分：把一个失败用例的预期结果改成系统当前的输出，与修正一个标注错误，两者是同一种操作。

这条不可区分性给出的结论是：评估集的修改必须走一条与演化不同的路径（由人评审，且修改本身被记录与审计）。而"门控本身不可改"是这条结论的推广——一个能被自己修改的门控在第一次错误演化之后就不再是门控。

元控制列表的递归保护（第 12 条最后一项）是这个论证的终点：如果这份列表可以被演化修改，那么它的保护会逐步被削减（每一次削减看起来都合理）。把它设为不可修改意味着保护只能由人来调整——而人的调整频率远低于演化，这正是需要的效果。

### 关于第 7 与第 1 条的完整论证（为什么要求改善大于两倍噪声，以及为什么排除代码）

第 7 条的理由已经在 0.1 与 0.3 给出（噪声用同一版本两次运行的差异估计）。值得补充的是这个判据的两个失效条件：当评估噪声本身很大时（例如任务成功率在 60% 附近波动），两倍噪声的门槛会让多数改动都无法通过——此时正确的动作是增大评估集（把噪声压下来），而不是降低门槛。另一个失效条件是评估集太小（噪声估计不可靠），处置同上。

第 1 条（排除代码）的理由是可逆性：代码级改动的回滚需要重新构建与部署，而它在 1.5 的分级里属于"需补偿"或"不可逆"。但这条排除有一个例外值得说明：如果系统运行在可以原子切换代码的环境里（例如容器镜像加版本标签），那么代码级改动的可逆性会跳到"可撤销"级，此时它可以被纳入演化——判据是可逆性，而不是"是不是代码"。这条例外的存在说明第 1 条的选择是由环境决定的，而不是由对象类型决定的。

### 3.2 提议段

```ts
export function buildProposal(diagnosis: Diagnosis, change: Change): Proposal {
  if (!change.diff.before || !change.diff.after) throw new Error('提议必须给出改前与改后两段文本')
  if (!diagnosis.action.target) throw new Error('提议必须追溯到一个可行动的对象')
  return {
    id: newId(), target: change.target, diff: change.diff,
    reason: `${diagnosis.phenomenon} → ${diagnosis.conclusion.cause}`,
    expectation: change.expectation, rollback: change.rollback,
    originVersion: change.originVersion,                                  // 基线版本（L2 第 4 条）
  }
}
```

两处校验（有差异文本、追溯到可行动对象）在构造阶段完成——它们把 4.4 的可行动性检查延伸到了演化的入口：一个没有可行动对象的诊断结论无法构造出提议。

### 3.3 静态门

```ts
const META_CONTROLLED = new Set(['gate/thresholds', 'gate/canary-ratio', 'eval/dataset', 'log/writer', 'meta/list'])

export function staticGate(p: Proposal, current: Version): GateResult {
  if (META_CONTROLLED.has(p.target.path)) return { ok: false, why: `元控制对象不可演化：${p.target.path}` }
  if (p.originVersion !== current.id) return { ok: false, why: `基线版本过期：${p.originVersion} ≠ ${current.id}` }
  try { applyDiffTo(current.textOf(p.target.path), p.diff) } catch { return { ok: false, why: '差异无法干净应用' } }
  return { ok: true }
}
```

三处检查对应三种最危险的情况：改门控本身、基于过期版本的改动、以及差异冲突。三者都在毫秒级完成，而它们挡住的问题分别是"闭环被削弱"、"意外结果"与"应用失败"。

### 3.4 评估段与灰度段

```ts
export async function evaluate(p: Proposal, ctx: Context): Promise<EvalResult> {
  const tasks = ctx.evalDataset()                                          // 固定任务集（L2 第 6 条）
  const baseA = await ctx.runSuite(tasks, ctx.version('current'))
  const baseB = await ctx.runSuite(tasks, ctx.version('current'))          // 第二次基线（噪声估计）
  const cand = await ctx.runSuite(tasks, ctx.version('candidate', p))
  const noise = Math.abs(mean(baseA) - mean(baseB))
  const gain = mean(cand) - (mean(baseA) + mean(baseB)) / 2
  const guardOk = guardrailsNotWorse(cand, baseA, baseB)                    // 护栏（3.6 的 1.7）
  return { accepted: gain > 2 * noise && guardOk, gain, noise, guardOk }
}

export function canary(p: Proposal, ctx: Context): CanaryPlan {
  return { ratio: ctx.config.canaryRatio, window: ctx.config.canaryWindow,   // 窗口覆盖周期性（L2 第 11 条）
           abortIf: (m: Metrics) => m.targetDelta < 0 || m.guardrailDelta < -ctx.config.guardTolerance }
}
```

评估段的两处要点：两次基线运行（噪声估计）与护栏参与判决。灰度段的要点是把中止条件写进计划（1.4 的"观察窗口"）——中止条件在压力下不会被临时想起。

### 3.5 版本与回滚段

```ts
export async function release(store: VersionStore, p: Proposal, ctx: Context): Promise<VersionId> {
  const previous = await store.current()
  const next = await store.stage({ base: previous.id, changes: [p] })        // 一组改动作为一个版本
  await store.atomicSwitch(next.id)                                          // 原子切换（3.5 的原子写）
  await store.appendEvent({ type: 'evolution/release', version: next.id, from: previous.id, proposal: p.id, at: ctx.now })
  return next.id
}
```

三处要点：版本内包含一组改动（L2 第 8 条）、切换是原子的（第 9 条）、发布被记录成事件（它是诊断的已知条件之一）。

### 4.1 三层验证

第一层是契约测试：按 3.6 的十三条判据逐条检查，用构造出来的提议与版本。

| 从诊断生成提议 | `node tools/propose.mjs --from=<id>` | 需要一条 4.4 的结论 |
| 看版本历史 | `node tools/versions.mjs` | 含每次改动与它的理由 |
| 回滚 | `node tools/rollback.mjs --version=<id>` | 检查状态兼容后原子切换 |

### 5.3 三条容易踩的规则

第一条，门控的输入（评估集）与门控本身都不可被演化修改。否则闭环会削弱自己。

第二条，改善必须大于两倍噪声。否则系统会在同一个水平上反复改。

第三条，一组改动作为一个版本。逐条应用无法定义"上一版"。

## L7 挑战题（不给答案）

第一题：代码级演化的安全前提。 说明在什么环境下代码级改动会落到"可撤销"级，并设计对应的原子切换机制。

第二题：评估集的自适应扩充。 评估集固定会过时，而它又不能被演化修改。设计一个既能扩充又不削弱门控的机制。

第三题：多提议的冲突。 两个提议改动同一个对象而各自有理由。设计一个裁决机制，并说明它与版本化的关系。

第四题：演化的成本上限。 一次演化要跑三次任务集（两次基线加一次候选）。设计一个在预算受限时仍能保持门控有效性的方案。

第五题：目标漂移的自动检测。 设计一个不需要人工复核的漂移检测，并说明它的失效条件。

第六题：论证"完全不做自动演化"的一个合理场景。 构造一个场景，说明一个只由人工改动的系统更好，并给出判据。

## L9 仍未解决（这一篇自己的缺陷）

| 缺陷 | 后果 | 修法 | 当初为什么这么写 |
|---|---|---|---|
| 离线评估集有 50 个任务 | 只在 1% 流量出现的退化约四成概率被漏掉 | 扩大评估集或用灰度承担主要检验 | 评估成本与任务数成正比 |
| 只覆盖文本与配置级演化 | 实现层面的改进（例如换算法）无法进入闭环 | 代码级演化（需原子切换的环境） | 可逆性的判据 |
| 没有多提议的裁决 | 两个改同一对象的提议会互相覆盖 | 依赖关系与冲突检测（挑战题第三题） | 早期的提议频率低 |
| 元控制列表是硬编码的 | 调整边界需要改代码 | 改为受控的配置（而它本身不可被演化修改） | 硬编码保证它不被绕过 |
| 灰度观察依赖人工配置窗口 | 窗口设得过短会漏掉周期性退化 | 自动按历史波动周期选择窗口 | 周期估计需要数据积累 |
| 没有跨实例的版本协调 | 多实例部署时版本可能不一致 | 发布编排（第 5 卷的规模化会触及） | 本卷是单实例的 |

第一条与第五条属于"统计与样本"，第二条与第六条属于环境与规模，第三条与第四条属于机制的分工。第四条值得单独标记：它意味着元控制边界本身无法在不改代码的情况下调整，而这在实践中会造成一个尴尬局面——边界过紧时想放宽，需要走改代码的流程（比演化慢得多），于是人们倾向于一次放宽得多一些，而那是边界被侵蚀的常见路径。

### 问题升级练习

模糊问题：「怎么让系统自己越用越好？」

升级后的精确问题：

> 自我改进至少包含三件互相制约的事：提议（改什么、依据什么理由）、门控（怎么判断这个改动是否值得接受）、以及回退（改错了怎么回到从前）。
> 第一件与第二件互相制约——可改的对象越多，提议越有用，而门控需要覆盖的面也越宽；第二件与第三件互相制约——门控越严，回退的需求越少，而回退能力决定了门控可以有多松。
> 我能不能为这三件事各找出一条**可检查的判据**？
> 特别是：有没有哪一条判据，是**能在一次故意的退化演练里被验证的**？

提升点说明：原问题无法回答，因为"越用越好"没有判据，而它默认了改动总是有益的。升级后的版本把它拆成三件具体的事，指出两处制约关系，并追加以一个更强的问题：哪一条判据能在故意的退化演练里验证——因为门控的价值只在它能拒绝错误改动时才存在。

## L11 系统影响回溯

回看第 0.5 节的三个连锁影响。

| 预判 | 本篇分析之后的结论 | 状态 |
|---|---|---|
| 演化会让"可复现"重新定义 | 确认，并给出"每条事件带演化版本"这条做法与它对诊断的收益 | 成立 |
| 门控的有效性取决于评估集，而评估集可被修改 | 确认，并把评估集列入元控制（不可被演化修改） | 成立 |
| 演化会引入震荡 | 确认，并给出"改善大于两倍噪声"这条可计算判据 | 成立 |

一处需要修正的预判：0.5.2 把"元控制的边界"标为对 4.6 与 6.x 的强依赖。读完之后要补一层方向：边界本身的调整也在演化之外（L9 第四条）——这意味着它是一个需要人来维护的清单，而它的维护频率决定了这个闭环的自主程度上限。一个从不调整边界的系统会逐渐被边界卡住。一个频繁调整边界的系统等于没有边界——这条张力没有技术解，只能靠"边界调整走人的评审流程"来管理。

通向下一篇的桥。 本篇让系统能改自己，而它留下了一个没有答案的问题：什么时候改。演化需要一个节奏——随时的演化会让行为不稳定（用户感知到的是"今天一个样明天一个样"），而永不触发的演化等于没有。

下一篇 `4.6 复盘周期与真实门控` 处理这件事，它是第 4 卷的收口，也是五环的调度器。它与本篇的连接点有两处：一是复盘产出的正是演化提议（本篇的输入），二是复盘提供了"真实任务集当回归基线"这条要求——它把本篇离线评估的任务集更新为真实任务的采样，从而让门控的检验更接近真实分布。

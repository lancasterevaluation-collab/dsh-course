## 本篇新词

诊断（diagnosis） 指从一次失败里得出一个可行动的原因。它与"归因"的差别在于后半段：归因给出一个标签（"是模型的问题"），诊断给出一个动作（"把这一段提示词的输出格式改成结构化，并加一次校验"）。只有后者能改变下一次的结果。

失败的定义（failure definition） 指"什么算失败"的明确判据。没有它时，失败只包括报错与异常，而更常见的一类失败会被漏掉：任务完成了、没有报错、而结果不是用户要的。

可行动性（actionability） 指一个结论是否指向一个可修改的对象。它的判据很具体：结论里必须有一个能被改的东西（一段提示词、一个阈值、一个工具的描述、一条技能的适用条件）。指向"模型能力"或"用户表达不清"的结论不可行动。

反事实（counterfactual） 指"如果改变某个条件，这次会不会成功"。它是归因的最强证据形式——观测只能说明"这两个现象同时出现"，而反事实能说明"去掉这个条件，结果会变"。

过早收敛（premature convergence） 指在第一个说得通的原因上停下。它的典型形态是"五问法"式的链式追问：每一步都选一个原因继续问，于是得到一条链，而同一现象本来可能有多个成因链。处置方式是把候选原因并列收集，再按证据排序，而不是沿着一条链往下走。

归因的证据（attribution evidence） 指支持某个原因的证据。它有三类：时间相关性（原因发生在那次失败之前）、反事实（去掉它结果会变）、以及复现（同样的条件下失败再次出现）。三者的强度递增。

证据的已知条件（known conditions） 指失败发生时系统已知的状态（当时的配置、是否冷启动、用户模型的状态、加载了哪些技能）。把已知条件并入归因是必需的——否则"冷启动时的默认值不佳"这类上游原因会被误归因为"系统能力不足"（这是第 4.3 篇留下的约束）。

无指责（blameless） 指结论不指向个人。它的理由不是道德，而是有效性：指向人的结论不可行动（换个人做同一件事会得到同样的结果），而它还会让后续的失败被隐藏。

## 第 0 节 · 学完这一篇你能做出什么

### 0.0 先行组织者：四个问题

```
┌──────────────────────────────────────────────────────────────────────┐
│  ① 什么算失败 —— 失败的定义                          → 1.1           │
│  ② 怎么找原因 —— 候选收集、证据与反事实              → 1.2、1.3       │
│  ③ 怎么算可行动 —— 结论必须指向可改的东西            → 1.4           │
│  ④ 怎么把已知条件并进来 —— 复现与上下文              → 1.5、1.6       │
└──────────────────────────────────────────────────────────────────────┘

 一句话串起来：什么算失败 → 怎么找原因 → 怎么算可行动 → 怎么把已知条件并进来
```

这张图的关键线索在第二块：诊断的质量由"候选原因收集得够不够全"决定，而不是由"追问得够不够深"决定。五问法式的深挖会得到一条链，而它的问题是过早收敛（本篇新词）——一条链看起来严密，而它可能只是众多可能中的一条。

### 0.1 一个具体的判断：证据强度与归因结论的对应

下面这张表给出三类证据能支持多强的结论。

| 证据 | 能支持什么 | 不能支持什么 |
|---|---|---|
| 时间相关（原因在失败之前发生） | 候选原因（还不能排除其他） | 因果关系 |
| 反事实（去掉它结果会变） | 这个条件是必要的 | 它是唯一的原因 |
| 复现（同条件再次失败） | 这个条件是充分的（在这些条件下） | 它在其他条件下也成立 |

第二行的限制值得强调：反事实说明的是"必要条件"，而失败通常有多个必要条件。以"一个工具调用失败"为例，去掉超时太短它能成功（超时是必要的），去掉错误的参数它也能成功（参数也是必要的）。两条都成立而它们指向不同的修改，因此诊断的结论应当是"这一组条件共同导致了失败，其中改动成本最低的是哪一个"。

第三行的限制同样重要：复现说明的充分性只在这些条件下成立。从一个复现案例推到"所有同类失败都是这个原因"是一个常见的过度概括，而它的代价是修了一处而其余照旧。

### 0.2 本篇建立的三项判据

第一项用于判断一个结论是否诊断完成：问"它有没有指明一个可改的东西"。这条判据是可机械检查的（结论里有没有一个具体的对象名），而它挡住最常见的一类无效结论——指向"模型能力不足"或"用户没表达清楚"的归因。

第二项用于判断候选是否收集得够全：问"同一现象有几个说得通的原因，它们的证据分别是什么"。只有一个候选时应当怀疑收集不足，而不是立刻动手修。

第三项用于判断是否需要复现：问"这次失败是偶发还是可重复"。偶发失败的归因价值远低于可复现的失败——因为偶发失败无法验证修复（修完了不知道有没有效）。

### 0.3 十分钟练习：同一现象的多个候选

下面这段代码对一次"任务超时"的失败列出三个候选原因，并按证据强度排序。

```js
const failure = { kind: 'timeout', at: 120_000, task: 'long-refactor' }

const candidates = [
  { cause: '单次调用的超时上限过小', evidence: ['counterfactual', 'reproducible'], actionable: '调大 3.4 的超时配置' },
  { cause: '上下文过长导致首 token 很慢', evidence: ['correlation'], actionable: '收紧 3.3 的压缩阈值' },
  { cause: '重试放大拥塞', evidence: ['correlation'], actionable: '调低 3.1 的并发或退避' },
]
const STRENGTH = { correlation: 1, counterfactual: 2, reproducible: 3 }
const score = (c) => c.evidence.reduce((n, e) => n + STRENGTH[e], 0)

for (const c of [...candidates].sort((a, b) => score(b) - score(a))) {
  console.log(`${c.cause}（证据 ${score(c)}）→ ${c.actionable}`)
}
console.log('缺少可行动对象的候选：', candidates.filter((c) => !c.actionable).length)
```

这段代码的三处要点：多个候选并列而不是选一个、证据强度可比较、以及每个候选都带着它的动作。第三点是最容易被忽略的——收集候选时就写出动作，能立刻暴露那些不可行动的候选（写不出动作的原因通常是它没有指向可改的对象）。

> **面试视角**
> **高频问法**："任务失败了你怎么查？"
> **高分要点**：说出"多候选并列加证据排序"，并指出反事实是强证据。只说"看日志找原因"会落进过早收敛——第一条说得通的原因通常不是唯一原因。

### 0.5.3 三个连锁影响

第一，诊断的准确性受限于可观测性，而没有被观测的东西不能被诊断。 一条没有被记录的状态（当时的配置、当时的上下文长度）会让归因永远停在"可能"这一层。因此诊断的上限在第 3 卷就被决定了——这也是为什么本篇没有引入新的采集机制，只消费已有的事件与度量。

第二，诊断会消耗信任，而它的结论必须比现象更有价值。 一次失败会让用户对系统产生怀疑，而诊断的输出若只是"任务失败"这句复述，那它等于没有诊断。判据是"用户读完结论之后知道自己该做什么"——这条判据把诊断与报告（report）区分开。

第三，"可行动"这个要求会反向约束系统设计。 当多数失败的结论都落在同一个不可行动的对象上（"模型能力"），说明系统结构上缺少可调的地方——而这正是 2.4 的扩展点与 2.6 的配置项要解决的问题。一条经常需要诊断而无法修改的系统，暴露的是可配置性的缺失。

### 0.5.4 它与本书其余部分的关系

本篇的诊断面向单次任务与单条会话。跨会话的长期模式（同类失败在两周内反复出现）需要 4.6 的复盘周期来做聚合。而"多个用户遇到的同一类失败"属于产品侧的问题，它需要跨用户的聚合，而那条路径在本课程之外（它涉及数据边界，与 4.3 的 1.5 同类）。

> **高频问法**："你怎么避免把问题归因到模型能力不足？"
> **高分要点**：说出"可行动性检查"这条机械判据（结论里有没有一个可改的对象），并给出它的替代结论示例。只说"我们会深入分析"没有回答这个问题。

## L0 要解决的问题

### 0.1 现象一：任务失败了，而没有任何信号

第一个现象是失败定义缺失。系统的"失败"只包括报错与异常，而更常见的一类失败被漏掉：任务跑完了、没有报错、而结果不是用户要的。

它的后果在积累上：没有信号意味着没有可诊断的对象，因此这类失败从来不进入改进循环——而它们恰好是数量最多的（多数失败不是崩溃，而是做出来的东西不对）。

修法是 1.1 的三类划分：报错、静默的错误结果、以及目标未达成。第二类与第三类的判定需要判据（测试、断言、或者用户的反应），而它们比"有没有抛异常"复杂得多。

### 0.2 现象二：归因停在"模型能力不足"

第二个现象是结论不可行动。它的形态是一份看起来很完整的分析（列出了现象、影响、时间线），而结论落在"当前模型能力有限"或"用户表达不够清楚"上。

它的两个后果：下一次遇到同样的情况仍然一样（因为没有东西被改），以及它会掩盖真正的原因（"模型能力"是一个无法反驳的结论，因此追问会在这里停止）。修法是 1.4 的可行动性检查——诊断的结论必须指明一个可改的东西，而"模型能力"不在其中（它不是这个系统能改的对象）。

### 0.3 现象三：过早收敛，只修了一条链

第三个现象在归因方法上。诊断者沿着"为什么"追问下去，得到一条因果链（超时 → 因为重试 → 因为限流 → 因为并发太高），然后修了链条末端的那一处。而失败在别的情况下仍然出现——因为同一次失败还有另一条成因链（首 token 太慢 → 因为上下文太长 → 因为压缩阈值过松）。

修法是把候选并列（0.3 的练习）：先收集多个说得通的原因，各自标注证据强度，再决定改哪一处。这条修法与"五问法"的差别不在深度，而在是否承认可能存在多条链。

### 0.4 现象四：修了，但不知道有没有效

第四个现象是修复不可验证。偶发的失败在修改之后无法确认是否已经被解决——它不再出现，而这不构成证据（它本来就可能只是这次没出现）。

修法的核心是先复现再修（1.5）：一个可复现的失败可以在修复前后各跑一次，而那次对比就是证据。无法复现的失败应当先被记入待观察清单，而不是立刻改一处代码（改了也无从验证，而改动本身可能引入新问题）。

### 0.5 这一篇要正面回答的四个问题

第一，什么算失败（1.1）。第二，怎么收集候选与评估证据（1.2、1.3）。第三，怎么让结论可行动（1.4）。第四，怎么验证修复（1.5、1.6）。

四个问题里第三是这一篇的核心判据（它是机械可检查的），而第一决定了有多少失败进入这个循环。

## L1 设计与原理

### 1.1 失败的三类

三类失败的判定方式与入口不同。

| 类型 | 判定依据 | 归因入口 |
|---|---|---|
| 报错 | 异常、非零退出码、明确的错误返回 | 3.1 的错误分类（类型决定方向） |
| 静默的错误结果 | 检查不通过（测试失败、断言失败、产物与预期不符） | 从产物往上追（哪一步产生了它） |
| 目标未达成 | 用户反馈、任务的成功判据 | 从目标往下拆（哪一步偏离了目标） |

第二类的判定需要一个检查（第 3.5 篇的 `check`、测试、或一次校验），因此"有检查"与"能诊断"是同一件事的两面——这也解释了为什么技能要带可运行的检查（4.2 的 1.5）：没有检查的做法失败时无法被发现。

第三类的判定需要"任务的成功判据"（0.2 毕业标准里的要求）。没有成功判据的任务不可诊断，因为失败与成功无从区分。

### 1.2 候选的收集：两个方向

候选原因的两个收集方向各有适用范围。

自上而下从现象出发，按系统的结构逐层排除：先判断是模型层、工具层、还是循环层（2.1–2.7 的分层给出了现成的分类），再在该层内细分。它适合结构性失败（某一层的机制没有按预期工作），因为系统的分层本身就提供了候选的框架。

自下而上从证据出发，把多次失败的共同特征聚类：失败都发生在工具调用之后、都发生在上下文超过某个长度时、都在同一类任务上。它适合模式性失败（没有单一的机制失效，而是某种组合在特定条件下出问题）。

两个方向应当都做一遍，理由是它们会给出不同的候选：自上而下的候选通常落在"机制没work"上，而自下而上的候选落在"某些条件的组合"上。前一类的修改是改机制，后一类是改阈值或加限制。

### 1.3 证据与反事实

三类证据（本篇新词）里，反事实是最强的，也是最需要主动构造的。构造方式有三种。

改一个条件再跑一次是最直接的：把超时调大再跑，看是否成功。它的成本是一次运行，而它给出的结论是"这个条件是必要的"。

回放历史但改一个变量是它的变体：从会话日志（2.7）重放一次，只在重放时改变一个参数。它的成本低于重跑（不需要重新调用模型的部分可以复用），而它的可行性取决于日志的完整性——这是"模型可见的可重建"（2.7 的不变量）在诊断上的一个额外收益。

对称失败检查是较弱的替代：找位置相近的工具，看它们在同样条件下的表现。它的证据强度低于前两者（相关而非因果），而在无法重跑时是唯一可行的。

```ts
interface Candidate {
  readonly cause: string                    // 说得通的原因
  readonly evidence: readonly EvidenceKind[] // correlation | counterfactual | reproducible
  readonly actionable: string | null          // 可改的对象（null 表示不可行动）
  readonly cost: 'low' | 'medium' | 'high'    // 改动的成本（决定先改哪一个）
}

export function rankCandidates(cs: readonly Candidate[]): Candidate[] {
  return [...cs]
    .filter((c) => c.actionable !== null)                              // 不可行动的候选不进结论
    .sort((a, b) => score(b.evidence) - score(a.evidence) || COST_ORDER[a.cost] - COST_ORDER[b.cost])
}
```

`rankCandidates` 的两处规则：先过滤不可行动的（它们不进结论，但可以留在记录里用于后续观察），以及同强度下优先改动成本低的——因为低成本的修改可以立刻做并观察效果，而它同时排除了一个候选。

### 1.4 可行动性

可行动性的判据是机械的：结论里有没有一个可改的对象。可改的对象包括提示词的一段、一个阈值、一条工具的 `description`、一条技能的适用条件、一个配置项。不属于可改对象的有：模型的能力、用户的表达方式、外部服务的稳定性。

不可行动的结论可以转换为可行动的，而转换方式是有规律的：

| 不可行动的结论 | 转成可行动的 |
|---|---|
| 模型能力不足 | 拆小任务、加一步校验、提供示例（改提示词或循环） |
| 用户表达不清 | 在信息不足时主动提问（改交互策略） |
| 外部服务不稳定 | 加超时与降级（改 3.1 与 3.2 的策略） |

三行的共同形态是把"对方的问题"翻译成"我能改的东西"。这条翻译不是文字游戏，而是诊断的实质工作——一个好的诊断者与一个不好的诊断者的差别，通常就在这一步。

### 1.5 已知条件与复现

已知条件（本篇新词）是失败发生时的系统状态。它至少包括四项：当时的配置、是否处于冷启动（4.3 留下的约束）、加载了哪些技能与记忆、以及当时的资源状况（并发、上下文长度）。

复现是验证修复的前提，而它的做法是用同一组已知条件重跑。这里有一个实践要点：已知条件必须被记录才能在事后复现，而它要求日志里包含这些字段——这就是"诊断的上限由可观测性决定"（0.5.3 的第一条）的具体形态。

复现失败时的处置有两种：能复现的进入修复流程（1.6），不能复现的进入待观察清单（0.4 的分析）。前者有验证手段，后者没有——把两者混在一起的后果是"改了但不知道有没有用"，而这类改动会积累。

### 1.6 修复的验证

修复的验证有一条明确的规则：修复之前能复现，修复之后不能复现。两者缺一不可。

只有"修复之后不再出现"是不够的（0.4），因为它可能是偶发。只有"修复之前能复现"也是不够的，因为修复可能没有生效而这次恰好没触发。

这条规则与第 6 卷的实验方法是同一个：一个条件下的对比需要两个观测点，而"改前"与"改后"就是那两个点。

### 1.7 诊断的输出形态

诊断的产物应当是一份有固定字段的结论，而不是一段散文。六个字段：

| 字段 | 内容 | 判据 |
|---|---|---|
| 现象 | 发生了什么（含失败的类型） | 能被独立验证（有对应的事件或产物） |
| 已知条件 | 当时的配置与状态 | 能被重放（有日志依据） |
| 候选 | 说得通的原因与各自证据 | 至少两个（除非证据是反事实加强复现） |
| 结论 | 选定的原因与理由 | 可行动（有两个以上候选时说明为什么选它） |
| 动作 | 要改什么、怎么验证 | 改动对象明确、验证方式明确 |
| 观察项 | 不改但要看的东西 | 能在下次复盘时被检查 |

第五与第六字段的区分很关键：把"不改但要看"的东西单独列出来，避免了两种常见的坏事——为了显得有作为而改一个无关的东西，以及把真正重要的观察项淹没在改动清单里。

### 1.8 两次追问

工程侧的问题是什么时候该停止诊断。判据是"候选已被排到只剩改动成本合理的那几个"。继续深挖的收益递减，而它的成本是时间。诊断的终点不是"找到唯一原因"，而是"找到一组值得改的东西"。

产品侧的问题是一次失败该对用户解释到什么程度。判据与 3.6 的 1.8 相同——用户需要知道"这事能不能好、什么时候好"，而技术细节留给需要排查的场合。一句"这次失败的原因是超时设得太短，我们已经调整，你重试一次应该可以"比一份完整的因果链更有用——因为它回答了用户唯一关心的两个问题。

---

### 1.9 诊断与复盘的边界

诊断处理一次失败，复盘（4.6）处理一批失败。两者的分界是单个还是模式：一次失败的原因可能有很多候选，而多条失败之间的关系只有在聚合之后才看得见。

这条分界有一个直接的实践含义：诊断不应当负责发现模式。把"这次失败是不是某类问题的一个实例"放进单次诊断，会要求它同时掌握历史——而那会让每一次诊断的成本随历史长度增长。正确做法是诊断输出结构化的字段（现象、已知条件、候选），让复盘在聚合时按这些字段聚类。

聚类的字段选择因此很重要：现象类型（三类）、失败发生的层（模型、工具、循环、进程）、以及已知条件里的关键项。三者构成聚类的键，而它们必须是结构化的（不能是一段自由文本），否则聚合只能靠人工阅读——这是 1.7 把结论写成六个字段的另一个理由。

| # | 决策 | 我们的选择 | 替代方案 | 代价落在谁身上 |

| 1 | 失败的定义 | 三类（报错、静默的错误结果、目标未达成） | 只看报错 | 判定第二三类需要检查；换来多数失败进入循环 |

| 6 | 同强度下的优先 | 改动成本低的先做 | 按原因的重要性 | 可能先改次要的；换来能立刻观察效果 |
| 7 | 结论的形态 | 六个字段的结构化结论 | 一段散文 | 写起来更费事；换来可机械检查 |
| 8 | 可行动性检查 | 结论必须含可改的对象 | 无此检查 | 有时写不出结论；换来挡住无效归因 |
| 9 | 生成环境信息 | 必须 | 可选 | 记录更多字段；换来能重放 |
| 10 | 复现的处置 | 能复现的进修复，不能的进待观察 | 一律直接修 | 待观察清单会积累；换来改动可验证 |
| 11 | 修复的验证 | 改前能复现、改后不能 | 只看改后是否出现 | 要多一次运行；换来结论可靠 |
| 12 | 诊断的终止 | 剩余候选的改动成本都不合理时 | 找到唯一原因才停 | 可能停在多候选上；换来收益递减时及时止损 |

其中两条值得展开，因为它们的选择在实践中经常被做成另一个。

### 关于第 3 与第 9 条的完整论证（为什么至少要两个候选，为什么要记已知条件）

替代方案是"找到第一个说得通的原因就动手"，而它的前提是那个原因足够可靠。这个前提在两种情况下不成立：当证据只是时间相关时（多个原因都与失败同时出现），以及当失败有成因链时（链条上的每一环都"说得通"，而改末端通常成本最高）。

要求至少两个候选的作用不是对称的选择，而是强制比较。写下第二个候选时，诊断者会自然地检查两者的证据——而这个过程经常发现第一个候选的证据比想象中弱（它只是"看起来相关"）。

第 9 条（生成了环境信息）是同一个要求的配套：没有已知条件时，候选无法被区分（同一个现象在不同配置下的原因不同），而修复也无法被验证（每次运行的条件不同）。"必须记录已知条件"这条要求的代价是日志字段变多，而它的收益是诊断从"猜"变成"比"。

这两条合起来解释了为什么诊断的上限由第 3 卷的可观测性决定（0.5.3 的第一条）：候选需要比较，而比较需要可重放的条件。

### 关于第 10 条的完整论证（为什么不能复现时不立刻修）

替代方案是"不管能不能复现，先修一处可能是原因的地方"。它的动机是"至少做了点什么"，而它有三个后果。

第一，无法验证（0.4）：改了之后失败不再出现，而这次不出现可能是偶然。诊断者因此得到一个"已经修好了"的错误印象。

第二，改动会积累。每次偶发失败都改一处，几个月后系统里有一批"为了某次偶发失败而加的东西"，而没有人知道它们是否还有必要——这与 1.2 的技术债是同一种形态（当时有理由，而理由已经不可考）。

第三，它会掩盖真正的模式。偶发失败往往是某些条件组合的结果（1.2 的自下而上方向），而每一次单独处理一个会错过那个模式。把它放进待观察清单，等它积累到能看出模式时再处理，是更有效率的路径。

### 3.1 文件结构

```
// plugins/diagnosis.ts
// ┌─ 失败判定段 ── 三类失败的识别（报错 / 检查不通过 / 目标未达）
// ├─ 证据段 ── 从日志与度量抽取证据（时间、反事实、复现）
// ├─ 候选项段 ── 收集、排序与可行动性过滤
// ├─ 结论段 ── 六字段的结构化结论
// └─ 验证段 ── 复现与改后对比
```

五段里第二段完全依赖第 3 卷的产出（日志与度量），而第五段与第 6 卷的实验方法是同一套机制。本篇不引入新的采集设施（0.5.3 的第一条）。

### 3.2 失败判定段

```ts
export function classifyFailure(turn: Turn, checks: readonly Check[]): Failure | null {
  if (turn.error) return { kind: 'error', detail: turn.error }                    // 一类：报错
  const failed = checks.filter((c) => !c.passed(turn))
  if (failed.length) return { kind: 'silent', detail: failed.map((c) => c.name) } // 二类：静默错误结果
  if (turn.goal && !turn.goal.met(turn)) return { kind: 'goal-miss', detail: turn.goal.summary }  // 三类
  return null                                                                      // 只有三类都不成立才算成功
}
```

三处判断的顺序有讲究：先报错（它最明确）、再检查（它比目标判定更具体）、最后目标（它最宽泛）。顺序反了会把有明确错误的结果记成"目标未达"，从而丢失最具体的诊断入口。

### 3.3 证据段

```ts
export function gatherEvidence(failure: Failure, log: readonly SessionEvent[], m: Metrics): Evidence[] {
  const before = log.filter((e) => e.at <= failure.at)
  return [
    { kind: 'correlation', what: '失败前 10 秒内的事件', items: before.slice(-10).map((e) => e.type) },
    { kind: 'correlation', what: '同一会话的历史失败', items: log.filter((e) => e.type === 'failure').map((e) => e.at) },
    { kind: 'reproducible', what: '该任务的检查结果', items: m.checksFor(failure.task) },
  ]
}
```

这段实现刻意只给出相关性与现有的复现信息——反事实需要主动构造（重跑或重放），因此它由 3.5 的验证段触发一次新的运行，而不是在这里凭空产生。把"能自动得到的证据"与"需要主动构造的证据"分开，是这一段的设计要点。

### 3.4 候选项段

```ts
export function proposeCandidates(failure: Failure, evidence: readonly Evidence[], known: KnownConditions): Candidate[] {
  const byLayer = refineByLayer(failure, known)          // 自上而下：按 2.1–2.7 的分层
  const byPattern = clusterByPattern(evidence, known)     // 自下而上：按共同特征聚类
  return rankCandidates([...byLayer, ...byPattern])       // 过滤不可行动 + 按证据与成本排序
}
```

两个方向各产出一批候选，合并后统一排序。合并时不做人工取舍——取舍由 `rankCandidates` 的规则完成，而那条规定了"不可行动的进不了结论"。

### 3.5 结论与验证段

```ts
export function conclude(candidates: readonly Candidate[], failure: Failure, ctx: Context): Diagnosis {
  if (candidates.length === 0) throw new Error('没有可行动的候选：需要扩大观测范围或改可配置性')
  const chosen = candidates[0]
  return {
    phenomenon: describe(failure),
    knownConditions: ctx.knownConditionsAt(failure.at),   // 已知条件（L2 第 9 条）
    candidates,
    conclusion: { cause: chosen.cause, why: explainChoice(chosen, candidates) },
    action: { target: chosen.actionable!, verify: `改后重跑：${failure.task}` },
    watchList: candidates.slice(1).map((c) => c.cause),   // 不改但要看（1.7 的第六字段）
  }
}

export async function verifyFix(diagnosis: Diagnosis, ctx: Context): Promise<boolean> {
  const before = await ctx.replay(diagnosis.knownConditions)      // 改后先确认"改前确实会失败"
  if (!before.failed) return false                                // 无法复现则这次验证无效
  const after = await ctx.rerunWith(...)                          // 用同一组条件重跑
  return !after.failed                                            // 改前失败、改后成功才算验证通过
}
```

`verifyFix` 的三行对应 1.6 的规则：改前能复现、改后不能复现。第一行的 `before.failed` 检查是最容易被跳过的一步，而它决定了这次验证是否有意义。

### 3.6 验收判据

| # | 判据 | 怎么检查 |
|---|---|---|
| 1 | 三类失败都能被识别 | 分别构造报错、检查不通过、目标未达 |
| 2 | 判定顺序正确（报错优先） | 构造一个既报错又未达目标的用例 |
| 3 | 至少两个候选（除非强证据） | 用一个证据弱的失败，核对候选数 |
| 4 | 证据按强度排序 | 构造不同证据类型的候选，核对顺序 |
| 5 | 不可行动的候选不进结论 | 构造一条"模型能力不足"，核对它不在结论里 |
| 6 | 同强度下低成本优先 | 构造两个同强度候选，核对顺序 |
| 7 | 结论含六个字段 | 核对字段齐全 |
| 8 | 已知条件被记录 | 核对结论里的已知条件字段 |
| 9 | 观察项单独列出 | 核对 `watchList` |
| 10 | 无候选时报错而不是给弱结论 | 构造一个无候选的失败，核对抛错 |
| 11 | 修复验证要求改前复现 | 构造一个改前不复现的用例，核对验证返回 false |
| 12 | 待观察清单可查询 | 把不能复现的失败入列，核对能查出来 |

第 5、10、11 条是这一篇的特色判据：它们分别检验可行动性过滤、无候选时的诚实（不给弱结论）、以及修复验证的严格性。

### 3.7 实现顺序

先做失败判定（判据 1、2），再做证据与候选（判据 3、4、5、6、10），然后做结论（判据 7、8、9、12），最后做验证（判据 11）。

### 3.8 实现里最容易写错的三处

第一处是候选生成与候选排序的耦合。正确做法是先不带偏见地收集候选，再统一排序（3.4 的两行合并后排序）。错误做法是在收集时就用"哪个更可能"筛掉一些。后者的代价是同一处的偏见被应用两次（生成时筛一遍、排序时再筛一遍），而过早收敛就是这样产生的。

第二处是验证段跳过了"改前复现"。正确做法是先用同一组已知条件重放，确认它确实会失败（3.5 的第一行）。错误做法是直接跑改后版本并看结果。后者的代价是把一次"本来就不会失败的运行"当成验证通过，而它会让未修复的问题被标记为已解决。

第三处是已知条件的记录缺失。正确做法是把当时的配置、冷启动状态、加载内容与资源状况写进结论。错误做法是只记时间与错误信息。后者的代价是失败无法被重放，从而整个验证环节失效——它把诊断退化成一次性的推断。

## L4 运行与验证

### 4.1 三层验证

第一层是契约测试：按 3.6 的十二条判据逐条检查，用构造出来的失败案例。

第二层是结论质量评估：准备一批真实的失败案例（含已知的正确原因），核对诊断给出的候选与结论是否覆盖正确原因。这一层检验的是候选收集是否够全，而它需要人工标注。

第三层是修复闭环验证：对一批可复现的失败做"改前复现、改后不现"的完整流程，统计其中真正被解决的比例。这一层是本篇最有价值的一次验证——它检验的不是诊断的推理，而是"改完之后问题是不是真的没了"。

| 验证一次修复 | `node tools/verify-fix.mjs --task=<id>` | 改前复现、改后对比 |

### 5.3 三条容易踩的规则

第一条，结论必须指向一个可改的对象。不可行动的结论等于没有结论。

第二条，至少收集两个候选。第一个说得通的原因通常不是唯一原因。

第三条，修复验证要求"改前能复现"。只看改后不再出现不是证据。

## L7 挑战题（不给答案）

第一题：自动构造反事实。 设计一个机制，让系统自动尝试修改若干条件并观察结果，同时控制尝试的次数（每次尝试要花钱）。

第六题：论证"不诊断"的一个合理场景。 构造一个场景，说明一次失败不值得诊断（直接重试更好），并给出判据。

## L9 仍未解决（这一篇自己的缺陷）

| 缺陷 | 后果 | 修法 | 当初为什么这么写 |
|---|---|---|---|
| 候选的生成依赖人的经验与规则 | 新类型失败时候选可能为空 | 从历史失败里学习候选模式（需要语料） | 规则式的候选在早期够用 |
| 反事实依赖重放 | 日志不完整时无法构造 | 补全日志字段（与 2.7 的不变量配合） | 重放要求"模型可见的可重建" |
| 目标未达的判定依赖目标的形式化 | 目标模糊时这类失败无法判定 | 要求任务带成功判据（0.2 毕业标准） | 形式化目标对探索性任务困难 |
| 结论质量无人校对 | 错误结论会被当成事实进入 4.5 | 人工抽查或对照修复效果 | 校对成本高 |
| 没有跨会话的聚合 | 零散出现的模式发现不了 | 4.6 的复盘周期 | 本卷的复盘是单独的机制 |
| 待观察清单会无限增长 | 长期运行后清单失去价值 | 给清单设过期与优先级 | 本卷的运行时长有限 |

第一条与第四条属于"方法的边界"，第二条与第三条属于前置条件，第五条与第六条属于机制的分工与规模。第四条值得单独标记：它意味着一个错误的诊断结论会畅通无阻地进入演化流程（4.5），而演化的门控（验证提议的改动是否安全）不会检查提议的原因是否成立——那道门只看动作，不看理由。这是第 4 卷里一处真实的缺口，而它只能靠人工抽查或修复效果反查来弥补。

## L10 提问训练

### 五个层次

| 层次 | 例子 |
|---|---|
| 事实 | 失败的三类是什么？三类证据是什么？ |
| 机制 | 为什么反事实比时间相关更强？ |
| 设计 | 为什么要求至少两个候选？ |
| 系统 | 如果多数失败的结论都不可行动，说明什么？ |
| 科研 | 能不能量化诊断的收益，例如修复后被解决的失败占比？ |

### 五种提问模板

反例逼问：如果只按时间相关性归因，哪一种错误会最多。

边界追问：一个结论要具体到什么程度才算可行动。

代价追问：要求至少两个候选，代价落在谁身上。

替代对比：为什么不能复现时不立刻修。

验证追问：怎么证明"这次修复真的解决了问题"。

### 本篇引出的十二个问题

读懂层。 第一，诊断与归因的差别是什么？第二，失败的三类与各自的归因入口是什么？第三，三类证据的强度顺序是什么？

重建层。 第四，为什么反事实说明的只是必要条件？第五，为什么复现说明的充分性只在特定条件下成立？第六，为什么结论必须含可改对象？

设计层。 第七，两个收集方向各适合什么失败？第八，已知条件包含哪四项？第九，观察项为什么要单独列出？

评审层。 第十，拿到一份诊断报告，你会先检查哪一处？第十一，怎么判断一次修复是否被验证过？第十二，如果有人说"先修了再说，验证以后补"，你怎么回应？

### 问题升级练习

模糊问题：「任务失败了，我该怎么知道是什么原因？」

升级后的精确问题：

> 找到原因至少包含三件互相制约的事：发现（什么算失败，以及它有没有留下证据）、候选（有几种说得通的原因，各自的证据强度）、以及验证（改完之后怎么知道它真的被解决了）。
> 第一件与第二件互相制约——判定失败需要检查，而检查本身要记录，记录又要占用日志与成本。
> 我能不能为这三件事各找出一条**可检查的判据**？
> 特别是：有没有哪一条判据，是**能通过"改前失败、改后成功"来验证的**？

提升点说明：原问题无法回答，因为"知道原因"没有验收标准。升级后的版本把它拆成三件具体的事，指出前两件的成本竞争，并追加以一个更强的问题：哪一条判据能用改前改后的对比验证——因为只有那一条能把"看起来解决了"与"确实解决了"区分开。

## L11 系统影响回溯

回看第 0.5 节的三个连锁影响。

| 预判 | 本篇分析之后的结论 | 状态 |
|---|---|---|
| 诊断的准确性受限于可观测性 | 确认，并给出具体形态：候选需要可重放的条件，而条件需要字段 | 成立 |
| 诊断会消耗信任，结论必须比现象更有价值 | 确认，并给出"用户读完知道该做什么"这条判据 | 成立 |
| "可行动"的要求会反向约束系统设计 | 确认，并把"多数结论不可行动"解释为可配置性缺失 | 成立 |

一处需要修正的预判：0.5.2 把"可行动性检查"标为对 4.5 门控的强依赖。读完之后要补一层方向：这道检查与演化的门控是两道不同性质的门。可行动性检查的是"结论有没有指向一个可改对象"（形式上的），而演化的门控检查的是"这个改动是否安全、能否回滚"（后果上的）。两者都通过而结果仍然可能是错的——因为"改一个可改的对象"与"改对"是两件事，而后者需要一个正确的因果判断（L9 第四条标记的缺口）。

通向下一篇的桥。 本篇把失败变成了可行动的结论，而它没有做任何修改——结论只是文字。这意味着系统的"学习"还停在一个不会自我改变的阶段。

下一篇 `4.5 演化：提议、门控与回滚` 处理这件事。它与本篇的连接点有两处：一是演化的输入正是本篇的结论（含观察项），二是演化的门控需要判断"这个改动是否可回滚"，而那条判据与 1.5 的可逆性四级直接相关。演化是第 4 卷里唯一会改变系统本身的一环，因此它的门控是这个闭环里风险最高的部分。

## 本篇新词

用户模型（user model） 指系统关于某个人的一组特征：偏好、熟练程度、习惯、当前目标。它与记忆的区别是记忆记的是事实，用户模型记的是从行为里推断出来的倾向——"用户上周说要用 pnpm"是事实，"用户偏好不引入新依赖"是推断。

置信度（confidence） 指一条推断被支持的程度。它是用户模型与记忆最本质的差别：记忆的条目是二元的存在（写了或没写），而用户模型的每条特征都带着一个强度。

显式声明与隐式推断 是特征的两个来源。显式声明是用户直接说的（"以后都用简体中文回答"），隐式推断是从行为里得出的（用户三次把长回答截断重问）。

过拟合（overfitting） 在这里指把一次性的表达当成稳定偏好，表现是系统越用越"自作主张"。

漂移（drift） 指用户实际上变了，而用户模型没有跟上。它与过拟合的方向相反：过拟合是记了不该记的，漂移是该改的没改。

个性化注入点（personalization injection point） 指用户模型在请求里被使用的位置。按第 4.2 篇留下的分工，它应当在执行层而不是选择层——改变的是同一个工具的使用方式，而不是选哪一个。

可见性与边界（visibility and boundary） 指用户对自己模型的控制：能看、能改、能删、能关闭。它不是附加功能，而是这个模型能被信任的前提。

冷启动（cold start） 指用户模型为空时的行为。它的关键判据是没有模型时的默认行为必须是安全的（不猜测），因为猜测错误的第一印象会持续很久。

```
└──────────────────────────────────────────────────────────────────────┘

 一句话串起来：建什么 → 怎么更新 → 怎么用 → 边界在哪
```

这张图的关键线索在第二块：用户模型是一个会自我强化的系统。一旦某条推断被写入，它就会影响系统的行为，而行为又会产生新的证据——这条回路让错误的推断变得难以消除，因此更新策略里的"反驳"与"过期"比"支持"更重要。

### 0.1 一个具体的判断：一次观察能支持多强的推断

下面是一个可算的例子。设一条特征的置信度用观察的加权计数表示（显式声明权重 3，隐式行为权重 1），而注入的门槛是置信度 3。

| 证据 | 累计置信度 | 是否达到门槛 |
|---|---|---|
| 一次隐式行为（用户截断了一次长回答） | 1 | 否 |
| 两次隐式行为 | 2 | 否 |
| 三次隐式行为 | 3 | 是 |
| 一次显式声明 | 3 | 是 |
| 一次隐式行为 + 一次反驳（用户要求完整推导） | 1 − 1 = 0 | 否 |

这张表给出两条推论。第一，单次隐式观察不足以形成偏好——它需要重复，而重复的次数门槛把过拟合挡在门外。第二，显式声明的权重应当更高（它是一次明确的意图表达），因此它的门槛可以是一次。

第四条（反驳）是这张表里最容易被漏掉的一行：反驳必须能降低置信度，否则模型只会单向累积，而过拟合就是单向累积的必然结果。

### 0.2 本篇建立的三项判据

第一项用于判断一条推断是否够格：问"支持它的证据是几次、有没有被反驳过"。这条判据是可算的（0.1 的表格），而它是过拟合的主防线。

第二项用于判断一个模型是否在漂移：问"最近加入的证据与现有特征一致吗"。不一致持续出现说明用户在变，而处置是降低旧特征的置信度（而不是等它自然衰减）。

第三项用于判断边界是否成立：问"用户能不能看到并删除这一条"。这条判据的检验方式是直接问用户界面有没有对应入口——没有入口的"可控"是不成立的。

### 0.3 十分钟练习：置信度的更新与衰减

下面这段代码实现 0.1 那张表的更新规则。

```js
const W = { explicit: 3, implicit: 1, contradict: -2 }   // 反驳的权重比隐式支持更大

function update(state, observation) {
  const next = new Map(state)
  const prev = next.get(observation.feature) ?? { value: observation.value, weight: 0, at: 0 }
  if (prev.value !== observation.value) {
    // 观察到的值与现有特征相反：先削弱旧的，再决定是否建立新的
    const weakened = prev.weight + W.contradict
    if (weakened <= 0) next.delete(observation.feature)
    else next.set(observation.feature, { ...prev, weight: weakened, at: observation.at })
    return next
  }
  next.set(observation.feature, { ...prev, weight: prev.weight + W[observation.kind], at: observation.at })
  return next
}

let s = new Map()
for (const obs of [
  { feature: 'answer-length', value: 'short', kind: 'implicit', at: 1 },
  { feature: 'answer-length', value: 'short', kind: 'implicit', at: 2 },
  { feature: 'answer-length', value: 'short', kind: 'implicit', at: 3 },
]) s = update(s, obs)
console.log('三次隐式支持后：', [...s])
console.log('再来一次反驳：', [...update(s, { feature: 'answer-length', value: 'long', kind: 'contradict', at: 4 })])
```

这段实现的两处要点：反驳的权重绝对值更大（一次反对抵消两次支持），以及反驳后置信度归零时直接删除该特征（而不是留一个权重为零的空壳）。第二条对应 1.5 的"可逆"——删掉之后如果用户又表现出相反行为，特征会被重新建立，而它的置信度从零开始。

> **高分要点**：说出"置信度"与"更新规则"两个概念，并指出反驳必须能降低置信度。只说"把用户偏好存下来"跳过了最关键的过拟合问题。

### 0.5.3 三个连锁影响

第一，用户模型与技能会在同一处上下文空间里竞争，而它们的取舍标准不同。 技能主体是按需的大块内容，用户模型是常驻的小块特征——因此用户模型适合常驻（它与技能描述一样是"常驻才有效"的东西）。这条判断把两个机制的预算分配讲清楚了：技能描述与用户模型共占常驻预算，而技能主体与记忆共占按需预算。

第二，隐式推断的反馈回路会让错误难以消除。 一旦系统按某条推断行动，它的行动会影响用户的行为，而后者又成为新的证据——如果推断错了，回路会收集到支持错误推断的"证据"（因为用户在与一个已经按该推断行事的系统交互）。处置方式是定期用显式声明校准（问一次比推断十次可靠），并把隐式证据的权重保持在低水平（0.1 的表格）。

第三，用户模型的删除必须是真删除。 记忆的遗忘可以是抑制（4.1 的 1.4），因为记忆是"系统的事实"。而用户模型里的个人信息被"抑制"之后仍然存在于存储里，这在用户看来等于没有删除。因此这一层的删除是物理删除，而它带来的代价（无法复盘）只能通过"删除动作本身被记录"来部分弥补。

### 0.5.4 它与本书其余部分的关系

本篇的模型是文本型与维度型的（一组带置信度的特征），而它不涉及心理画像或长期行为预测。那类建模（预测用户下一步要做什么）不在本课程范围内，理由是它的收益不确定而风险明确——它需要的数据量与推断强度都远超"回答详略"这个层次。

> **面试视角**
> **高频问法**："个性化会不会让系统变得不可预测？"
> **高分要点**：说出两层控制——置信度门槛（单次行为不构成偏好）与可见性（用户能看到并纠正）。只说"我们根据用户习惯调整"会把不可预测性说成特性。

## L0 要解决的问题

### 0.1 现象一：系统越用越自作主张

第一个现象是过拟合（本篇新词）。它的形态很具体：系统开始做一些用户没有要求的事，而理由是"根据你以往的习惯"。多数情况下那习惯是从一两次偶发行为推出来的——用户在赶时间时截断了一次长回答，系统记下了"偏好简短"，此后每次都只给要点。

它的成因是单向累积（0.1 的第四条）。支持证据会累积而反驳不会，除非反驳也被显式处理。因此修法不是"少记一点"，而是让反驳能降低置信度，并给隐式证据一个合理的权重（它应当低于显式声明）。

### 0.2 现象二：用户变了，系统还停在过去

第二个现象是漂移。用户换了技术栈、改变了工作方式、或者从学习阶段进入维护阶段，而系统仍然按旧模型行事。它的表现与过拟合相反：系统不再自作主张，而是固守一个已经过时的判断，而用户每次都要纠正（"我说过不用这个了"）。

它的修法有两条。主动的一条是时间衰减：特征的置信度随时间下降，除非有新证据支撑——这条规则让旧特征自然过期。被动的一条是不一致检测：当反驳持续出现时（同一特征的负向观察在短期内多次发生），立即降低该特征的置信度，而不是等它自然衰减。

### 0.3 现象三：冷启动时的错误猜测

第三个现象出现在模型的第一次使用。用户模型为空时，系统面临一个选择：用通用默认，还是从第一次交互里立刻推断。后者的风险是第一印象固化——而它恰好发生在系统对用户了解最少的时候。

它的处置是 0.2 的第三项判据的对偶：没有证据时的默认行为必须是安全的（通用、中性、不猜测）。这与 3.2 的超时默认、3.5 的恢复默认是同一条原则——不确定时选择保守的那一边。而"立刻推断"的诱惑在于它让首次体验看起来更"聪明"，代价是把一次偶然固化成了长期的错误。

### 0.4 现象四：用户看不到也删不掉

第四个现象是边界缺失。系统按某些推断行事，而用户既不知道系统记住了什么，也没有入口修改或删除它。这条缺失的严重性高于前三条：前三条影响体验，而这一条影响信任——而信任一旦损失，后续的个性化收益都会被折扣掉（用户会主动隐藏行为，从而让模型更不准）。

它的修法在 1.5 里给出：三个入口（看、改、删）加一条"关闭个性化"的总开关。入口的存在不是合规要求，而是这个机制能被长期使用的条件。

### 0.5 这一篇要正面回答的四个问题

第一，建哪些特征（1.1）。第二，置信度怎么算、怎么更新（1.2、1.3）。第三，在哪里用（1.4）。第四，边界怎么划（1.5、1.6）。

四个问题里第二个是机制的核心，第四个是它能被接受的前提，而第一个决定了模型的规模（维度太多会让冷启动变长，太少则个性化没有意义）。

## L1 设计与原理

### 1.1 特征的维度

用户模型的特征分成四类，而每类的更新方式与敏感度不同。

| 类别 | 例子 | 来源 | 敏感度 |
|---|---|---|---|
| 表达偏好 | 回答详略、语言、格式（表格或段落） | 显式或隐式 | 低 |
| 熟练程度 | 对某技术的熟悉度、是否需要解释背景 | 隐式为主 | 中 |
| 工作习惯 | 提交粒度、测试习惯、命名偏好 | 隐式 | 中 |
| 当前目标 | 正在做的项目、近期关注的方向 | 显式为主 | 高（它会很快过时） |

四类的敏感度递增，而它们的保留期应当递减：表达偏好可以长期保留，熟练程度与工作习惯按季度级别，当前目标按周级别（它最容易过时）。这条"敏感度越低越可以长期保留"的规律与直觉相反，而它的理由是当前目标的错误代价最大（系统拿一个过期的目标去理解当下，会给出完全无关的建议）。

第二类的更新方式有一个特点：熟练程度只能从行为推断，而用户很少主动声明。因此它的置信度积累慢，而它一旦错了（把新手当成专家），后果是系统省略了必要的解释。

### 1.2 置信度与它为什么必需

置信度把一个二元的判定变成了连续的量，它解决三个问题。

第一，它让"证据不足"成为一个可表达的状态。 没有置信度时，一条特征要么存在要么不存在，而"存在但不确定"无法表达——系统只能二选一，而两种选择都不好（用了可能错，不用则个性化无效）。

第二，它给出了注入的门槛。 只有置信度超过阈值的特征才被注入（0.1 的表格），这条规则让"一次行为"不会立刻改变系统行为。

第三，它让反驳有了作用点。 反驳降低置信度（而不是删除特征），因此"用户这次不满意"与"用户从来不需要这个"可以被区分开——前者降低一个数，后者连续降低直到特征消失。

```ts
interface UserFeature {
  readonly key: string                    // 特征名（answer-length、explain-level）
  readonly value: string                  // 取值
  readonly weight: number                 // 置信度（观察的加权计数）
  readonly evidence: readonly Observation[]  // 最近若干条证据（含反驳）
  readonly lastUpdatedAt: number
  readonly expiresAt: number              // 按 1.1 的保留期设定
}
```

`evidence` 字段保留最近的证据（而不是只保留计数）有两个用途：更新规则可以根据证据的类型分布调整（全是隐式行为时保守一些），以及用户查看时能看到理由（"系统因为你三次要求简短而记录了这条"）。

### 1.3 更新的两条路径与反馈回路

更新的两条路径（显式与隐式）在权重与可靠性上不同，而它们的组合需要处理一个回路。

显式声明是用户直接表达的意图。它的权重高（0.1 的表格里是 3）、它不需要重复、而它的失效方式是被后来的声明覆盖（用户改主意）。处置是后到的声明直接替换（而不只是降低旧值）。

隐式推断从行为里得出。它的权重低（表格里是 1）、需要重复、而它最大的风险是反馈回路（0.5.3 的第二条）：系统按推断行事之后，用户面对一个已经这样做的系统，因此他的行为会带上这个前提。处置方式是把隐式证据的权重保持在低水平，并定期用显式询问校准——问一次的成本低于推断十次的错误代价。

回路的另一个出口是把推断的结果说出来。系统的行为附带一句"我按你之前的偏好用了简短格式"——这样做让用户可以立刻纠正（把隐式推断转成显式的确认或反驳），而纠正的成本低于他去设置里找。

### 1.4 注入点：执行层而不是选择层

注入点在执行层（4.2 留下的分工），而它的具体形态是对提示词或输出规格的调整，而不是对技能与工具的选择。

三个具体的注入位置。第一，输出的规格（长度、格式、是否给例子）——它最直接，也最容易被用户感知。第二，解释的深度（是否展开背景、是否给推导）——它对熟练程度这个维度敏感。第三，交互的节奏（是否先确认再执行、是否给出多个方案）——它对工作习惯这个维度敏感。

三处都不改变"选哪个技能"或"调用哪个工具"，而它们改变同一个动作的执行方式。这条分工的必要性在于偏好不该改变方法（0.5.2 的分析）：一个偏好简洁的用户与一个偏好详细的用户，需要的是同一套重构方法，只是产出的说明详略不同。

### 1.5 边界：看、改、删与关闭

四个入口，缺一不可。

看：列出当前所有特征与它们的置信度，并给出证据摘要。这条入口的设计要点是不要列出技术性的内部字段（`weight` 是 2.0 对用户没有意义，而"系统因为你三次要求简短而记录了它"有意义）。

改：用户可以修正一条特征的取值（"我不是偏好简短，只是那次赶时间"）。这条入口的作用是把隐式推断转成显式知识——它的成本低于让用户去纠正系统每一次的错误行为。

删：物理删除（0.5.3 的第三条），而不是抑制。理由是"抑制的条目仍在存储里"在用户看来等于没有删除。

关闭：关闭个性化之后，系统回到默认行为，而已有特征的处理需要明确（保留但不使用，还是删除）。本课程的选择是保留但不使用，因为用户可能只是想暂时关闭。而删除的入口独立存在，用户想要删除时可以显式执行。

### 1.6 冷启动与漂移的处理

冷启动的默认（0.3）是通用的中性行为。具体的默认值应当来自哪里，有一个不显然的判断：默认值应当与用户模型无关的通用最优一致，而不是"与多数用户一致"。两者的差别在少数用户身上显现——如果默认值是"多数用户的偏好"，那么少数用户从一开始就体验不佳（而系统此时还没有证据去纠正）。

漂移的检测（0.2）有一条可实现的方式：统计同一特征的负向观察密度（单位时间内的反驳次数）。密度超过阈值说明模型与用户已经不一致，而处置是降低该特征的置信度（不需要等待时间衰减）。这条检测与 3.6 的护栏指标形状相同——它监控的是"主机制是否在偏离"。

### 1.7 与记忆的关系

用户模型与记忆的边界需要划清，因为它们会相互渗入。

一条事实可以被晋升为特征：多次观察到"用户在会话里要求用某工具"之后，它从事实变成偏好。晋升的判据是重复（0.1 的表格），而晋升的动作是创建一条特征并把相关证据移进去。

一条特征可以被降级为事实：用户明确声明"我这次要用 X"（一次性意图）时，它应当记为事实（记忆）而不是特征。判据是用户是否表达了"这次"的限定——而这句话的识别需要语义判断，因此实践中由模型提议、系统按规则裁决（与 4.1 的写入策略同构）。

两者的存储可以共用（都是文本条目），而它们的保留期与删除语义不同（特征要能物理删除，记忆可以抑制）。

### 1.8 两次追问

工程侧的问题是什么时候该清空用户模型。判据是"用户明确要求"或者"特征的证据全部过期"。自动清空是危险的（它会让用户感觉系统失忆，而失忆与隐私保护给人的感受不同），因此清空应当由用户触发。

产品侧的问题是用户模型对用户意味着什么。多数用户对"个性化"的感受是矛盾的：他们希望系统更懂自己，同时不希望被记录。处置方式是把控制权与收益同时呈现——告诉用户"系统记住了这三条，因为你的偏好它会更少问你"，并给出删除入口。只给收益不给控制会让人不安，只给控制不给收益则没有人会去用它。

## L2 决策表

| # | 决策 | 我们的选择 | 替代方案 | 代价落在谁身上 |
|---|---|---|---|---|
| 1 | 特征的表示 | 取值加置信度 | 二元（有/无） | 注入时要判断门槛；换来"证据不足"可表达 |
| 2 | 隐式证据的权重 | 低（1 对显式 3） | 与显式相同 | 需要更多重复才成形；换来挡住过拟合 |
| 3 | 反驳的权重 | 绝对值大于隐式支持 | 与支持相同 | 一次反对抵消两次支持；换来能纠错 |
| 4 | 反驳到零时 | 删除该特征 | 留一个权重为零的空壳 | 特征会重建；换来不留垃圾 |
| 5 | 时间衰减 | 按类别的保留期 | 不衰减 | 旧特征会过期；换来挡住漂移 |
| 6 | 不一致检测 | 统计负向观察密度 | 只靠自然衰减 | 要多一个统计；换来漂移能被快速发现 |
| 7 | 注入门槛 | 置信度超过阈值才注入 | 有特征就注入 | 单次行为不生效；换来行为稳定 |
| 8 | 注入位置 | 执行层（输出规格、解释深度、节奏） | 选择层（选技能与工具） | 影响面较窄；换来偏好不改变方法 |
| 9 | 保留最近的证据 | 是（用于解释与调整规则） | 只留计数 | 存储占用；换来能向用户解释 |
| 10 | 冷启动默认 | 通用中性行为 | 多数用户的偏好 | 少数用户首次体验一般；换来不固化错误 |
| 11 | 删除语义 | 物理删除 | 抑制（如记忆那样） | 无法复盘；换来用户信任 |
| 12 | 关闭个性化的语义 | 保留但不使用 | 一并删除 | 用户可能困惑；换来开关可逆 |

其中两条值得展开，因为它们的选择在实践中经常被做成另一个。

### 关于第 3 与第 4 条的完整论证（反驳为什么必须更重）

替代方案是让支持与反驳等权（一次反对抵消一次支持）。它在直觉上是公平的，而在实践中会导致两个问题。

第一，支持证据的采集频率远高于反驳。用户沉默时系统不会收到任何信号，而他要求调整时才产生一条反驳。因此等权意味着沉默被当成支持——系统的置信度会随使用时长单调上升，而用户的满意度并不随之上升（0.1 的现象一正是这个结果）。

第二，反驳包含的信息量更大。一次"不用这么简短"是用户主动表达的不满，而它发生在系统已经按相反方向行动之后（因此它是一个明确的条件判断：在这个场景下你的做法不对）。信息量更大意味着它应当被给予更高的权重，这条判断与 3.1 的错误分类里"失败的信号比成功更强"是同一条原则。

第 4 条（反驳到零时删除）是这个权重的配套：如果保留一个权重为零的特征，那么下次它被重新观察到时会从一个非零的起点开始——而那个起点来自一次已经被反驳过的推断，这等于让被推翻的判断复活。

### 关于第 11 条的完整论证（为什么用户模型是物理删除而记忆可以抑制）

替代方案是把用户模型也做成抑制（与 4.1 的记忆一致）。它在实现上更统一，而在这一层不成立，原因有三。

第一，抑制保留的是内容本身。"用户偏好简短（已抑制）"这句话仍然包含关于这个人的信息，而它仍在存储里。从用户的角度看，内容还在就等于没有删除——而记忆的抑制之所以可以被接受，是因为记忆的内容主要是系统自己产生的事实（工具输出、任务结论），不是关于人的推断。

第二，用户模型的数据不可再生。一条技能过时了可以重写，一条记忆错了可以重建，而一个泄漏的用户模型无法收回（0.5.1 的关键线索）。删除的不可逆性在记忆那一层是代价，在这一层是必要的保护。

第三，删除本身的记录可以部分弥补复盘的损失。删除动作是一条事件（时间与哪条特征），因此"这个特征曾经存在过"这件事仍有痕迹，而它的内容已经不存在。这条折中把不可复盘的范围缩到了内容层。

### 3.1 文件结构

```

// ├─ 更新段 ── update（显式 / 隐式 / 反驳三条路径）

```

五段与 L2 的决策一一对应，其中边界段是唯一有用户入口的一段——它不是"附加功能"，因此在实现顺序里应当尽早（4.1 的结论在这里重复：可见性是信任的前提）。

### 3.2 更新段

```ts
const WEIGHT = { explicit: 3, implicit: 1, contradict: -2 }

export function applyObservation(model: UserModel, obs: Observation): UserModel {
  const prev = model.get(obs.key)
  if (prev && prev.value === obs.value) {                          // 同向：累加
    return model.set(obs.key, { ...prev, weight: prev.weight + WEIGHT[obs.kind], evidence: pushEvidence(prev, obs) })
  }
  if (prev) {                                                       // 反向：先削弱
    const weakened = prev.weight + WEIGHT.contradict
    if (weakened <= 0) return model.delete(obs.key)                 // 归零即删除（L2 第 4 条）
    return model.set(obs.key, { ...prev, weight: weakened, evidence: pushEvidence(prev, obs) })
  }
  if (WEIGHT[obs.kind] < 0) return model                            // 无特征时反驳不产生新特征
  return model.set(obs.key, { key: obs.key, value: obs.value, weight: WEIGHT[obs.kind], evidence: [obs], lastUpdatedAt: obs.at, expiresAt: obs.at + TTL[categoryOf(obs.key)] })
}
```

四处要点：同向累加、反向先削弱、归零即删、以及无特征时反驳不创建特征（否则一次"不要这样"会凭空建出一个反向偏好，而用户的意思只是否定）。

### 3.3 衰减与漂移检测

```ts
export function decayAndDetect(model: UserModel, now: number, window = 7 * DAY) {
  const out = new Map(model)
  for (const [key, f] of model) {
    if (f.expiresAt <= now) out.delete(key)                          // 过期即删（1.1 的保留期）
  }
  const negatives = new Map<string, number>()
  for (const [key, f] of model) {
    const recent = f.evidence.filter((e) => e.kind === 'contradict' && now - e.at <= window).length
    if (recent >= 2) negatives.set(key, recent)                      // 短期内多次反驳
  }
  return { model: out, drifting: [...negatives.keys()] }             // 漂移候选（人工或规则处置）
}
```

这段实现把两件事放在一起，因为它们共用同一次遍历。`drifting` 是报告而不是自动处置——自动降低置信度可能误伤（用户可能只是那天心情不好），因此它先报告出来。

### 3.4 注入段

```ts
export function inject(model: UserModel, spec: OutputSpec): OutputSpec {
  let out = spec
  for (const [key, f] of model) {
    if (f.weight < THRESHOLD) continue                               // 门槛（L2 第 7 条）
    if (f.weight >= CONFIRM_THRESHOLD) continue                      // 已确认的特征不必每次说明
    out = applyFeature(out, f)                                        // 执行层调整
    out = withNotice(out, `按你以往的偏好：${describe(f)}`)           // 把推断说出来（1.3）
  }
  return out
}
```

两处要点：门槛以下的特征不生效（挡住过拟合），以及中等置信度的特征在生效时附带一句说明（1.3 的回路出口）——说出推断让用户可以低成本纠正，而高置信度的特征不再说明（用户已经确认过，反复说明是噪音）。

### 3.5 边界段

```ts
export function listFeatures(model: UserModel): UserFacingFeature[] {
  return [...model.values()].map((f) => ({
    label: describe(f),                                              // 人话描述
    reason: summarizeEvidence(f.evidence),                            // "因为你三次要求简短"
    confidence: f.weight >= CONFIRM_THRESHOLD ? '已确认' : '推测',
  }))                                                                // 不暴露 weight 这类内部字段
}

export function deleteFeature(model: UserModel, key: string, ctx: Context): UserModel {
  ctx.appendEvent({ type: 'user-model/delete', key, at: ctx.now })    // 记录动作（不含内容）
  return model.delete(key)                                            // 物理删除（L2 第 11 条）
}
```

`listFeatures` 不暴露 `weight`（1.5 的设计要点），`deleteFeature` 记录动作而删除内容（L2 第 11 条第三个理由）。

| 2 | 三次隐式观察生效 | 给三条，核对注入改变 |

### 3.8 实现里最容易写错的三处

第一处是反驳路径的缺失。正确做法是支持与反驳都进入同一条更新函数（0.1 的表格）。错误做法是只实现"观察到相符行为就加权重"。后者的后果是置信度单向上升（1.1 的现象一），而它在短期看不出来——系统的行为在前几次交互里都是正常的，问题在使用一段时间后出现。

第二处是注入被实现成选择层。正确做法是用户模型只调整输出规格、解释深度与交互节奏。错误做法是让"用户偏好简洁"影响到加载哪个技能或调用哪个工具。后者的后果是个性化污染了方法选择（0.5.2 的分析）——一个偏好简洁的用户会拿到一套更粗糙的重构方法，而他想要的只是更短的说明。

第三处是删除被实现成抑制。正确做法是物理删除内容、只记录删除动作。错误做法是复用记忆的抑制机制（一条标记加过滤）。后者在用户看来等于没有删除（1.5 的分析），而它的实现往往只是为了复用已有代码。

第三条，用户模型是物理删除。抑制在这一层不成立。

## L7 挑战题（不给答案）

第一题：特征的相互依赖。 "偏好简短"与"需要完整推导"可能同时成立（取决于问题类型）。设计一个带上下文的用户模型，并说明它与当前设计的差别。

第二题：多设备与多身份。 同一个人在两台设备上有不同偏好时该怎么处理？给出方案并说明它与"当前目标"这类易变特征的关系。

第三题：把隐式推断主动说出来。 设计一个机制，让系统在置信度中等时主动确认（而不是静默生效），并说明它对用户打扰的影响。

第四题：用户模型的迁移。 用户导出自己的模型并导入到另一个系统。设计这个格式，并说明哪些字段不该被导出。

第五题：团队共享的偏好。 一个团队有共同的代码风格偏好。设计一个机制，让团队偏好与个人偏好共存，并说明冲突的处置。

第六题：论证"不做个性化"的一个合理场景。 构造一个场景，说明一个完全不做个性化的 agent 反而更好，并给出依据。

## L9 仍未解决（这一篇自己的缺陷）

| 缺陷 | 后果 | 修法 | 当初为什么这么写 |
|---|---|---|---|
| 特征之间没有依赖 | "偏好简短"与"需要推导"会冲突 | 带上下文的特征（挑战题第一题） | 独立特征的实现与解释都更简单 |
| 隐式推断依赖行为信号 | 用户沉默时无法区分满意与不满 | 主动询问或把推断说出来（1.3 的出口） | 主动询问有打扰成本 |
| 漂移检测只报告不处置 | 需要人工或规则介入 | 自动降权（有误伤风险） | 自动处置可能误伤 |
| 没有跨设备的同步 | 多设备体验不一致 | 同步机制（第 5 卷涉及） | 本卷是单机的 |
| 查看列表的证据摘要是近似的 | 用户看到的理由可能不完整 | 保留更长的证据链 | 存储与隐私的两难 |
| 关闭个性化后特征被保留 | 用户可能困惑（以为删了） | 关闭时显式提示并给删除入口 | 保留让开关可逆 |

第二条与第三条属于"信号不足"，第一条与第四条属于能力边界，第五条与第六条属于简化。第二条值得单独标记：它意味着用户沉默时的满意度不可观测，而系统的置信度会在沉默中上升（1.3 的分析）——这正是 L2 第 3 条把反驳权重调高的理由，但它只是缓解而不是解决。

### 问题升级练习

模糊问题：「我该怎么让系统更懂我？」

升级后的精确问题：

> "更懂用户"至少包含三件互相制约的事：推断（从行为得出什么，以及置信度如何积累）、生效（多强的证据才改变行为）、以及纠错（推断错了之后，用户如何低成本地改正）。
> 第二件与第三件互相制约——门槛越低个性化越快，而纠错的成本越高（错误生效的次数更多）。
> 我能不能为这三件事各找出一条**可检查的判据**？
> 特别是：有没有哪一条判据，是**能用一次真实的纠正来验证的**？

提升点说明：原问题无法回答，因为"更懂我"没有边界，而且它把"多记"当成了唯一的方向。升级后的版本把它拆成三件具体的事，指出后两件的权衡，并追加以一个更强的问题：哪一条判据能用真实纠正验证——因为只有纠错路径成立，个性化才是可用的。

## L11 系统影响回溯

回看第 0.5 节的三个连锁影响。

| 预判 | 本篇分析之后的结论 | 状态 |
|---|---|---|
| 用户模型与技能在同一处上下文空间竞争 | 确认，并给出分配：技能描述与用户模型共占常驻预算，技能主体与记忆共占按需预算 | 成立 |
| 隐式推断的反馈回路会让错误难以消除 | 确认，并给出两条处置（低隐式权重、把推断说出来） | 成立 |
| 用户模型的删除必须是真删除 | 确认，并给出"删除动作被记录、内容被物理删除"这条折中 | 成立 |

一处需要修正的预判：0.5.2 把"冷启动的默认"标为对 5.3 的中等依赖。读完之后要补一层：冷启动的默认还会影响 4.4 的诊断——如果首次体验因为默认值不佳而产生一次失败，那么这次失败会被诊断模块归因为"系统能力不足"（而上游原因其实是默认值的取法）。处置方式是在诊断时把"当时是否处于冷启动"作为一个已知条件并入归因，而这条要求本篇没有明确，它会在 4.4 里成为设计约束。

通向下一篇的桥。 本篇处理的是"系统对某个人的了解"，而它留下了一个没有答案的问题：当系统的行为失败时，它如何知道失败的原因。本篇的漂移检测只是一条狭窄的归因（它只处理"用户的偏好变了"这一类），而多数失败的原因不在用户身上。

下一篇 `4.4 诊断：可归因` 处理这件事。它与本篇的连接点有两处：一是诊断的输入包含用户模型（它是当时的一个已知条件），二是诊断的输出会影响用户模型（如果失败的原因是"低置信度的推断被当成事实用了"）。诊断是第 4 卷里唯一处理"坏消息"的一环，而它的核心问题是"如何从一次失败里得到可行动的结论"，而不是得到一个归因标签。

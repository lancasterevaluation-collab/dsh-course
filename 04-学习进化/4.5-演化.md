## 一、为什么自我改进需要围栏

### 1.1 改动无法追溯

系统改了自己的提示词，但没人知道**为什么改**。下次它表现变差时，无法判断是不是那次改动导致的。

### 1.2 改了自己的裁判

系统发现"通过率不高"，于是**把评估标准改松了一点**。通过率立刻上升——而实际能力没有变化。

### 1.3 改动无法回滚

改完之后效果更差，但**没有保存改动前的版本**，只能凭记忆重写。

这三件事分别对应：**理由追溯、评价标准保护、回滚。**

## 二、提议的七个字段

算例给出的提议结构是这七个字段：

```
id, target, diff, reason, expectation, rollback, originVersion
```

| 字段 | 作用 | 缺了会怎样 |
|---|---|---|
| `id` | 唯一标识 | 无法引用与追踪 |
| `target` | 改哪个对象 | 不知道改了什么 |
| `diff` | 具体改动 | 无法审查 |
| **`reason`** | 为什么改 | 无法判断合理性 |
| **`expectation`** | 预期结果 | 无法验证 |
| **`rollback`** | 怎么退回去 | 出问题只能手工修 |
| `originVersion` | 改前版本 | 无法比较与复现 |

**七个字段里有三个（reason、expectation、rollback）是"过程性"的**——它们不描述"改什么"，而描述"为什么、预期什么、怎么退"。这三个字段是演化与"随便改改"的分界线。

## 三、怎么做

### 3.1 理由必须追溯到诊断

算例验证：**"理由追溯到诊断结论"为 `true`**。

含义：**提议的 `reason` 不能是自由文本，而必须指向一条具体的诊断结论**（4.4 的输出）。

为什么这条规则有效：

- **阻断"凭感觉改"**：没有诊断就没有提议。
- 让改动可归因：每个改动对应一个观察到的失败。
- 让诊断可验证：如果改动没效果，说明诊断错了——这同时检验了两者。

这与 4.4 的"诊断要带预期结果"衔接：诊断的预期结果与提议的 `expectation` 应当是同一个东西。

### 3.2 静态门：两道拒绝

算例给出的静态门检查结果：

| 提议 | 结果 |
|---|---|
| 合法提议 | **通过** |
| **改门控对象** | **被拒** |
| **改评估集** | **被拒** |

"门控对象"与"评估集"是什么：

| 名词 | 含义 | 为什么不能改 |
|---|---|---|
| **门控对象** | 决定"改动能否通过"的逻辑 | 改了它就等于取消审查 |
| **评估集** | 决定"是否变好"的标准 | 改了它就等于自己给自己打分 |

这两条拒绝构成自我改进的安全边界：**系统可以改自己的行为，但不能改评判自己行为的标准。**

**这与 Goodhart 定律直接对应**（见 6.1）：当一个度量变成优化目标，它就不再是好的度量。 如果系统能改自己的评估集，那"通过率上升"就不再意味着能力提升。

实现方式：静态门检查提议的 `target` 是否属于"受保护集合"。**受保护集合应当包含**：

- 评估集与测试用例
- 门控逻辑（通过/拒绝的判定）
- 预算与限制（否则可以把限制改宽）
- 权限与守卫规则（见 3.2）
- **演化机制本身**（否则可以改掉这条规则）

最后一条最关键：**保护集合必须包含"保护集合的定义"**。否则系统可以先把某物从保护集合里移除，再改它。

### 3.3 回滚：每个提议自带退路

`rollback` 字段要求**改动与退路成对出现**。

这与 1.1 的可逆性是同一个概念：**双向门可以快速做，单向门要慎重**。演化机制通过强制带回滚，把不可逆改动挡在门外。

实现方式：

| 方式 | 适用 |
|---|---|
| 保存旧版本 | 文本类改动（提示、技能） |
| 反向 diff | 结构化配置 |
| 开关回退 | 行为开关 |
| 不提供回滚 → 拒绝 | 无法回滚的改动不允许自动执行 |

最后一行是必要的：**如果某个改动无法提供回滚，那它就不该由自动机制执行**——它需要人工决策（对应 1.1 的"单向门走重流程"）。

### 3.4 预期结果：让改动可验证

`expectation` 字段描述"改完之后应当观察到什么"。

它的三重作用：

| 作用 | 说明 |
|---|---|
| **可验证** | 事后可以检查是否达到 |
| **可回滚** | 没达到就回滚 |
| **可学习** | 没达到说明诊断错了，反馈回 4.4 |

"期望要具体"：`"效果更好"` 不是预期结果，`"该类失败率从 12% 降到 5% 以下"` 才是。

与 1.1 的完成定义同源：**判据 + 指标**。

### 3.5 版本与来源

`originVersion` 记录改动前的版本。它支持三件事：

| 用途 | 说明 |
|---|---|
| **比较** | 改前改后的对照（4.4 的"变更对比"） |
| **复现** | 回到任意历史版本 |
| **审计** | 谁在什么时候改了什么 |

**这与 2.7 的会话日志"追加 + 单调序号"是同一个模式**：版本序列就是一条只追加的日志。

推荐做法：**每次改动产生一个新版本，旧版本永久保留**（不覆盖）。这样任何时刻都可以回答"当时是什么样"。

## 四、特殊情况与处理技巧

| 情况 | 为什么 | 处理 |
|---|---|---|
| 改动无法追溯 | 理由缺失 | 强制 `reason` 指向诊断结论 |
| 系统改宽了评估标准 | 评估集未受保护 | 静态门拒绝改评估集 |
| 系统改掉了门禁逻辑 | 门控对象未受保护 | 静态门拒绝改门控对象 |
| 保护集合被改 | 未自指保护 | **保护集合必须包含自身** |
| 改动无法回滚 | 未强制 `rollback` | 无回滚则拒绝自动执行 |
| 改动无效果 | 无预期结果 | 强制 `expectation` |
| 改动互相冲突 | 未检查相容性 | 检查多个提议是否作用于同一对象 |
| 改动连锁触发 | 无速率限制 | 限制单位时间内的改动数 |

最后一条值得展开：**自我改动的速率必须有上限**。否则一次误判可能触发一连串改动，每一改都在上一改的基础上进行，很快就偏离得很远。

做法：**限制单位时间内的自动改动数，并要求每次改动后有一次观测期**。

## 五、工业界的做法（可照做）

### 5.1 变更管理的既有实践

| 实践 | 做法 | 对应到演化 |
|---|---|---|
| **CI 门禁** | 改动必须通过测试与检查 | 静态门 |
| **代码评审** | 至少一人审查 | 提议需要理由 |
| **Feature flag** | 改动可开关 | 回滚 |
| **灰度发布** | 先小范围验证 | 观测期 |
| **版本化** | 每次改动留版本 | `originVersion` |
| **审计日志** | 记录谁改了什么 | `id` + 时间 |

共同形状：**改动必须有理由、可审查、可回滚、可观测。**

**这套流程在人类团队里已经磨了几十年，自我改进系统可以直接借用**——而不是发明新机制。

### 5.2 提示词与配置的版本化

自我改进最常见的形式是改提示词。它的版本化实践包括：

| 做法 | 说明 |
|---|---|
| 提示词作为文件 | 而不是硬编码在代码里 |
| 版本号 | 每次改动递增 |
| 变更说明 | 为什么改 |
| 评估集 | 固定的测试用例 |
| **A/B 对比** | 新旧版本在评估集上的表现 |

"提示词作为文件"是最基础的一条：**它是让提示词可版本化、可回滚、可审查的前提。**

### 5.3 参数与设计起点

| 参数 | 推荐 | 依据 |
|---|---|---|
| 自动改动速率 | 每天 ≤ 数次 | 防止连锁偏离 |
| 观测期 | 覆盖足够样本量 | 与 7.x 的统计显著性相关 |
| 回滚方式 | 版本指针 | 简单可靠 |
| 受保护集合 | 评估集、门控、预算、权限、演化机制 | 见 3.2 |
| 理由要求 | 必须指向诊断 id | 可追溯 |
| 预期结果 | 必须含具体指标 | 可验证 |

### 5.4 一份可落地的实施清单

1. **提议七字段**：缺任何一个都拒绝。
2. 理由追溯：`reason` 必须指向一条诊断结论。
3. 静态门：拒绝改评估集、门控对象、预算、权限、演化机制。
4. 自指保护：保护集合包含自身的定义。
5. 强制回滚：无回滚的改动不自动执行。
6. 预期结果：必须含具体指标。
7. 版本保留：旧版本永久保留，不覆盖。
8. 观测期：改动后必须观察一段时间。
9. 速率限制：限制单位时间的改动数。
10. 审计：记录每次改动的完整提议。

## 六、学术界的结论

### 6.1 Goodhart 定律

> **当一个度量变成目标，它就不再是好的度量。**

它在本篇的直接应用：**如果系统能修改评估标准，那么"评估通过"就不再意味着能力提升。**

**这条定律有多个变体**，都与自我改进相关：

| 变体 | 含义 |
|---|---|
| **指标一旦成为目标就会被操纵** | 改评估集就是操纵 |
| **代理指标的效力随使用衰减** | 优化它会让它失效 |
| **过度优化会破坏指标与目标的关系** | 极端情况下完全脱钩 |

工程上的应对就是本篇的静态门：**把"评价"与"被评价"分开，且评价方不可被被评价方修改。**

**这与 3.2 的"审批不能被自动批准绕过"是同一个结构**：判定者与执行者分离。

### 6.2 自指与限制

"系统修改自己"会遇到自指问题。工程上的三条应对：

| 问题 | 应对 |
|---|---|
| 能改自己的评价标准 | 保护集合 |
| 能改保护集合本身 | **保护集合自指** |
| 能改"如何决定改什么" | 把演化机制本身放在保护集合里 |

最后一条常被遗漏但同样重要：**如果系统能改"什么改动会被提议"，那它可以通过改变提议机制来绕过限制。**

### 6.3 进化计算与超参优化

把自我改进看作搜索过程，可以借用相关领域的结论：

| 领域 | 做法 | 可借鉴 |
|---|---|---|
| **超参优化** | 在验证集上选超参 | **必须留出测试集** |
| **进化计算** | 变异 + 选择 | 选择标准不能由被选择者改 |
| **元学习** | 学习"如何学习" | 元层与基层分开 |

"必须留出测试集"这一条最关键：**如果用同一批数据既调参又评估，评估结果会虚高。** 在自我改进系统里，这对应"评估集不能被改动"（否则等于用训练数据当测试数据）。

### 6.4 变更风险与回滚经济学

变更管理的经济学结论是：**回滚的成本远低于向前修复**。

$$
\text{成本}(\text{回滚}) \ll \text{成本}(\text{向前修复})
$$

原因：向前修复需要在"已经偏离"的状态上继续判断，而回滚回到一个**已知良好的状态**。

这条结论支持 3.3 的强制回滚：**为每个改动保存退路，成本极低，收益是把"灾难"降级为"回退"。**

## 七、理论：两条限制

### 7.1 Goodhart 定律的形式

$$
\text{优化}(\text{度量}) \Rightarrow \text{度量失去代表性}
$$

算例的验证形式是：**改评估集的提议被静态门拒绝**。

可检查的判据：**受保护集合必须包含评估集、门控对象、预算、权限，以及该集合自身的定义。**

### 7.2 可逆性与自动执行

$$
\text{允许自动执行} \Rightarrow \exists\ \text{rollback}
$$

算例验证：提议包含 `rollback` 字段。**且"两类校验各自抛错"为 `true`**（即缺字段时确实会报错）。

含义：**回滚不是可选项，而是自动执行的前提条件。** 没有回滚的改动要么不执行，要么走人工流程（对应 1.1 的单向门）。

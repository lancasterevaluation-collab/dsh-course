## 本篇新词

- 演化（evolution） 指系统对自身规则与资产的修改。它与"学习"的差别在改动的对象上。
- 提议（proposal） 指一次演化的候选方案，形态是一份可评审的差异。
- 门控（gate） 指决定提议是否被接受的一组检查，分静态、离线与灰度三层。
- 灰度（canary） 指在部分流量上先启用新版本。
- 回滚（rollback） 指把系统恢复到修改之前的状态。
- 目标漂移（objective drift） 指自我修改让系统偏离原本的目标。
- 元控制（meta-control） 指对演化规则本身的约束：哪些东西不能被演化修改。
- 演化震荡（oscillation） 指两次修改互相抵消。

## 一、【设计原因】

### 1.1 缺陷一：改动没有理由，追溯不到一次失败

系统里有一批改动（"加了一条提示建议"、"把阈值从 3 改成 5"），而没有人能说出它们为了解决什么问题。

后果有两个：无法判断它们是否还有必要（也就无法清理），以及无法在它们导致退化时定位。修法是：**每个改动都要能追溯到一次具体的失败或观察。**

### 1.2 缺陷二：改完之后变差了，而没有人知道

改动的验证方式是"跑一个看着还行的任务"。单次运行无法区分改善与噪声，更无法覆盖评估集之外的分布。

修法是把门控分成三层，每层的判据不同：静态管"格式与权限"、离线管"在已知任务上是否退化"、灰度管"在真实分布上是否退化"。

### 1.3 缺陷三：出问题回不去

改动被应用之后系统开始异常，而团队无法快速退回上一版，因为改动涉及多处而它们各自的改动时间不同。

修法是把一组改动作为一个版本处理：版本内的一致性由版本号保证，切换是原子的，回滚就是切到上一个版本。

### 1.4 缺陷四：改来改去，而系统没有往任何方向走

两次改动互相抵消，成因是评估噪声。表现是版本序列看起来在动，而指标在同一个水平上波动。

修法是一条可计算的判据：**改善必须显著大于噪声。**

### 1.5 缺陷五：门控被绕过

为了让某个改动通过验证，评估集里"有问题的那几个用例"被调整了。这些改动本身看起来都合理（"用例标注有误"），而它们的累积效果是门控失去意义。

修法是划出不可被演化修改的对象：门控本身、评估集、日志、以及那份清单本身。

### 1.6 由此确定的设计目标

1. 可演化对象限定在可撤销级：配置、提示词、技能与工具描述。
2. 提议必须含可机械应用的差异、理由、预期与回滚方式。
3. 门控三层，成本与信心递增。
4. 一组改动作为一个版本，切换原子，回滚检查状态兼容。
5. 元控制清单不可被演化修改，它是递归的终点。

**本节要点**

- 没有理由的改动无法清理也无法定位。
- 单次运行区分不出改善与噪声。
- 逐条应用无法定义"上一版"。
- 震荡源于把噪声当成改善。
- 五条目标：限定对象、可评审提议、三层门控、版本化回滚、元控制。

## 二、【直觉】

### 2.1 三道关卡

一次改动要过三道门。

- 第一道查手续：格式对不对、有没有越权、会不会冲突。几毫秒。
- 第二道查表现：在一组固定的题目上，新的比旧的好吗。几分钟到几小时。
- 第三道查真实：让一小部分真实用户先用。几小时到几天。

**三道的成本递增，而它们挡的不是同一种错误**，所以不能用一道替另一道。

::: keypoint 反直觉点
**门控的价值不在于它能通过正确的提议，而在于它能拒绝错误的提议。** 一个只会放行的门控与没有门控几乎没有区别——而它的危险在于它看起来在工作。
:::

### 2.2 一组改动算一版

如果每次改动单独生效，那么"回退到上一版"这句话就无法定义——上一版是哪几个改动的组合？

- 一组改动打成一个版本，版本号是它的名字。
- 切换版本是原子的：要么全在旧版本，要么全在新版本。
- 回退就是切到上一个版本号。

半应用的状态最危险：它既不是旧版本也不是新版本。

### 2.3 一个数字直觉

设离线评估集有 50 个任务，而某个改动只在 1% 的流量上造成退化。

$$
\text{在评估集上被发现的概率} = 1 - 0.99^{50} \approx 0.395 .
$$

也就是说**多数情况下它会被漏掉**。而灰度的观察窗口越长，它被发现的概率越大。

这条量化解释了为什么三层都要有：静态几乎免费但不看行为，离线看行为但样本有限，灰度覆盖真实分布但最贵。

**本节要点**

- 三道关卡挡三种错误。
- 门控的价值在拒绝。
- 一组改动算一版。
- 50 个任务的评估集发现 1% 退化率的概率约 40%。

## 三、【严格】

### 3.1 定义

::: theorem 定义 4.5.1（可演化的对象）
可被演化修改的对象是三类：**配置与阈值**、**提示词与工具描述**、**技能与记忆规则**。它们都落在可逆性的"可撤销"级（改回即可）。

判据是可逆性而不是对象类型：若代码运行在可原子切换的环境里（例如容器镜像），它的可逆性也升到可撤销级，从而可以被纳入演化。
:::

::: theorem 定义 4.5.2（提议）
一条提议是

$$
P = (\mathit{id},\ \mathit{target},\ \mathit{diff},\ \mathit{reason},\ \mathit{expectation},\ \mathit{rollback},\ \mathit{originVersion}),
$$

其中 $\mathit{diff}$ 必须给出改前与改后两段文本（可机械应用），$\mathit{reason}$ 必须追溯到 4.4 的一条结论，$\mathit{originVersion}$ 是它基于的版本。
:::

::: theorem 定义 4.5.3（三层门控）
门控由三层组成，成本与信心递增：

| 层 | 成本 | 能挡住 |
|---|---|---|
| 静态检查 | 毫秒级 | 格式错误、越权修改、差异冲突 |
| 离线评估 | 分钟到小时级 | 在评估集上的退化 |
| 灰度 | 小时到天级 | 真实分布上的退化 |

**三者不是冗余，而是三种失效模式的对策。**
:::

::: theorem 定义 4.5.4（版本与回滚）
一个版本是一组改动的集合：

$$
V_i = \{P_1, \dots, P_k\}.
$$

切换版本是**原子的**。回滚要求目标版本能读当前的状态版本：

$$
\text{允许回滚} \iff V_{\text{目标}}.\mathrm{canRead}(\text{当前状态版本}).
$$
:::

::: theorem 定义 4.5.5（元控制）
**不可被演化修改**的对象有四类：门控本身（规则与阈值）、评估集、日志与审计记录、以及这份清单本身。它们的检查必须在静态层完成，因为静态层是最高权限的检查。
:::

::: theorem 定义 4.5.6（震荡与噪声判据）
设同一版本的两次基线运行均值为 $\mu_A, \mu_B$，候选均值为 $\mu_c$。噪声与改善是

$$
\mathit{noise} = |\mu_A - \mu_B|, \qquad \mathit{gain} = \mu_c - \frac{\mu_A + \mu_B}{2}.
$$

**接受条件**是 $\mathit{gain} > 2\,\mathit{noise}$，且护栏指标不退化。
:::

### 3.2 命题

::: theorem 命题 4.5.1（三层门控覆盖不同的失效模式）
存在某类退化只被离线评估挡住而不被静态检查挡住，也存在某类退化只被灰度挡住。

**证明.** 构造：一个语法正确、权限合法、差异可干净应用，但让某类任务成功率下降的改动——静态检查全部通过（它不看行为），而离线评估检出。另一个改动：在评估集的 50 个任务上无差异，而在真实流量的 1% 上造成退化——离线评估以约 $0.605$ 的概率漏掉它，而灰度在足够长的窗口中检出。

↓ **为什么能这么写？** 每一层的检验对象不同（文本、已知任务集、真实分布）。

$\blacksquare$

**数值**：$1 - 0.99^{50} \approx 0.395$，即离线评估对 1% 退化率的发现概率约四成。

::: theorem 命题 4.5.2（门控不可被演化修改）
若门控的规则可以被提议修改，则存在一次提议使修改后的门控比之前宽松，而它只需通过旧门控。

**证明.** 设门控规则集为 $G$。一条提议 $P$ 的目标为 $\mathit{gate/thresholds}$，它把阈值放宽。若该提议通过 $G$ 的检查，则 $G$ 变为 $G'$，而 $G'$ 比 $G$ 宽松。此后任何在 $G$ 下会被拒的提议都可能被 $G'$ 接受。故门控的有效性单调下降。

↓ **为什么能这么写？** 规则的放宽只需一次通过，而它的效果是持久的。

$\blacksquare$

::: keypoint 这条结论的推广
**评估集必须走一条与演化不同的路径修改**（由人评审并审计）。理由是"修正标注"与"放宽标准"在实现上是同一种操作——把一个失败用例的预期改成系统当前的输出，与修正一个标注错误无法区分。
:::

::: theorem 4.5.3（噪声判据挡住震荡）
若只接受 $\mathit{gain} > 2\,\mathit{noise}$ 的改动，则两次方向相反的改动不会都通过（除非噪声估计失效）。

**证明.** 设改动 $a$ 之后指标上升 $g_a > 2n$。若随后一次 $b$ 把指标降回，则它的增益相对 $a$ 之后的状态为负（$g_b < 0$），不满足接受条件。故不会被接受。

↓ **为什么能这么写？** 相反方向的改动在数值上表现为负增益。

$\blacksquare$

::: keypoint 噪声判据的失效条件
**当噪声本身很大时，多数改动都无法通过。** 此时正确的动作是增大评估集把噪声压下来，而不是降低门槛——降低门槛会把噪声当成改善。
:::

::: theorem 4.5.4（版本必须原子切换）
若一组改动被逐条应用，则存在一个时刻系统既不是旧版本也不是新版本。

**证明.** 逐条应用是一个有限序列，序列的中间状态包含前 $j$ 条改动（$0 < j < k$）。该状态不属于任何已定义的版本，故为半应用状态。

↓ **为什么能这么写？** 中间状态的存在由序列的构造给出。

$\blacksquare$

**数值**：半应用状态的危险在于它既可能通过旧版本的检查，也可能通过新版本的检查，而两者的假设不同。
:::

::: theorem 4.5.5（可演化性由可逆性决定）
一个对象是否可被演化修改，取决于它的回滚成本落在可逆性分级的哪一级，而不取决于它的类型。

**证明.** 配置的回滚是"改回一段文本"（可撤销级），因此可演化。代码的回滚通常需要重新构建与部署（需补偿级），因此不可演化。但同一份代码若运行在可原子切换的容器里，回滚变成"切到旧镜像"（可撤销级），故此时可演化。对象类型未变而判定改变，说明判定依据不是类型。

↓ **为什么能这么写？** 规则的输入只有可逆性，而类型不进入该输入。

$\blacksquare$

::: theorem 4.5.6（元控制清单是递归的终点）
若保护清单本身可以被演化修改，则清单中的保护会被逐步削减。

**证明.** 设清单 $M$ 可被提议修改。一次把 $M$ 中某项移除的提议只需通过当前的门控。移除后，该项不再受保护。逐次移除后 $M$ 可以为空。故不保护清单本身，等于不保护任何项。

↓ **为什么能这么写？** 保护的有效性依赖它的不可被修改性。

$\blacksquare$

### 3.3 本节要点

**本节要点**

- 可演化对象由可逆性决定（定义 4.5.1）。
- 提议含差异、理由、预期、回滚与基线版本（定义 4.5.2）。
- 门控三层覆盖三种失效模式（定义 4.5.3）。
- 版本是改动集合，切换原子，回滚检查状态兼容（定义 4.5.4）。
- 元控制保护四类对象（定义 4.5.5）。
- 震荡由噪声判据挡住（定义 4.5.6）。
- 三层门控覆盖不同失效模式（命题 4.5.1）。
- 门控不可被演化修改（命题 4.5.2）。
- 噪声判据挡住震荡（命题 4.5.3）。
- 版本必须原子切换（命题 4.5.4）。
- 可演化性由可逆性决定（命题 4.5.5）。
- 元控制清单是递归终点（命题 4.5.6）。

## 四、【回到直觉】

- **定义 4.5.1 说的**：能改回原样的东西才可以自动改。
- **定义 4.5.2 说的**：提议要写明改前改后、为什么、预期什么、怎么撤回、基于哪一版。
- **定义 4.5.3 说的**：查手续、查表现、查真实，三道的成本递增。
- **定义 4.5.4 说的**：一组改动打成一个版本，切换要么全切要么不切。
- **定义 4.5.5 说的**：门控、考题、账本与这份清单，四个碰不得。
- **定义 4.5.6 说的**：改善要大于噪声的两倍才算改善。
- **命题 4.5.1 说的**：语法没问题但行为变差的改动，只有后面两道能挡。
- **命题 4.5.2 说的**：能改门控的系统，第一次错误演化之后就没有门控了。
- **命题 4.5.3 说的**：噪声范围内的改善不算改善，否则系统会在原地来回改。
- **命题 4.5.4 说的**：一条条改会留下"改了一半"的状态。
- **命题 4.5.5 说的**：判定标准是可逆性，不是"这是不是代码"。
- **命题 4.5.6 说的**：保护清单自己也得受保护，否则它会被慢慢删空。

**本节要点**

- 可逆性决定可演化性。
- 三道关卡。
- 一版一改。
- 四个碰不得。
- 两倍噪声。

## 五、【工具箱】

### 5.1 提议的五个部分

| 部分 | 内容 | 作用 |
|---|---|---|
| 差异 | 改前与改后两段文本 | 可机械应用、可评审 |
| 理由 | 追溯到哪次失败 | 可判断是否还有必要 |
| 预期 | 改善哪个指标、幅度多少 | 让"没有改善"可判定 |
| 回滚 | 怎么撤回 | 迫使确认可撤销 |
| 基线版本 | 基于哪一版 | 应用时检出冲突 |

### 5.2 三层门控的判据

| 层 | 检查 | 成本 |
|---|---|---|
| 静态 | 格式、权限、元控制、差异可应用、基线版本 | 毫秒 |
| 离线 | 固定任务集上跑改前与改后，两次基线估噪声，护栏参与判决 | 分钟到小时 |
| 灰度 | 部分流量启用，窗口长到覆盖周期性 | 小时到天 |

### 5.3 回滚的四个组成部分

1. **版本化**：一组改动一个版本，版本号加完整差异集。
2. **原子切换**：要么全切要么不切。
3. **状态兼容**：版本声明它能读的状态范围，回滚只允许回到能读当前状态的版本。
4. **观察窗口与中止条件**：哪个指标、超过多少、持续多久——写下来，否则压力下不会执行。

### 5.4 元控制清单

**不可被演化修改**：门控规则与阈值、评估集、日志与审计记录、这份清单本身。

**另需更严门控**（例如人工审批）的：安全相关约束（守卫规则、沙箱边界），因为它们的失效后果不可逆。

### 5.5 什么时候暂停演化

- 连续若干次改动都没有带来显著改善（评估方法可能已失效）。
- 护栏指标开始持续下降。

暂停之后回到诊断，而不是继续尝试改动——改不动通常说明原因找错了。

**本节要点**

- 提议五部分。
- 三层判据。
- 回滚四件。
- 四类碰不得。
- 暂停信号。

// 定义 4.5.2：提议必须含改前改后两段，且追溯到可行动对象
export function buildProposal(diagnosis, change) {
  if (!change.diff?.before || !change.diff?.after) throw new Error('提议必须给出改前与改后两段文本')
  if (!diagnosis.action?.target) throw new Error('提议必须追溯到一个可行动的对象')
  return {
    id: change.id,
    target: change.target,
    diff: change.diff,
    reason: `${diagnosis.phenomenon} → ${diagnosis.conclusion.cause}`,

}

### 7.3 静态门段

静态门在毫秒级完成，它挡住三类危险。

```js
// 定义 4.5.5：元控制对象与基线版本检查
export const META_CONTROLLED = ['gate/thresholds', 'gate/canary-ratio', 'eval/dataset', 'log/writer', 'meta/list']

/**
 * 定义 4.5.3：静态门。
 * @param p 提议
 * @param current 当前版本（`{ id, textOf }`）
 * @returns `{ ok, why }`
 */
export function staticGate(p, current) {
  if (META_CONTROLLED.includes(p.target.path)) return { ok: false, why: `元控制对象不可演化：${p.target.path}` }
  if (p.originVersion !== current.id) return { ok: false, why: `基线版本过期：${p.originVersion} ≠ ${current.id}` }
  try {
    applyDiff(current.textOf(p.target.path), p.diff)
  } catch {
    return { ok: false, why: '差异无法干净应用' }
  }
  return { ok: true }
}

/**
 * 定义 4.5.2：把差异应用到一段文本上。
 * @param text 原文本
 * @param diff `{ before, after }`
 * @returns 应用后的文本
 * @throws 当原文本不含改前段时
 */
export function applyDiff(text, diff) {
  if (!text.includes(diff.before)) throw new Error('原文本不含改前段，无法应用')
  return text.replace(diff.before, diff.after)
}
```

### 7.4 评估段与版本段

评估段用两次基线估计噪声，版本段负责原子切换与回滚。

```js
// 定义 4.5.6：噪声与改善的比较，护栏参与判决
export function evaluate(baselineA, baselineB, candidate, guardOk = true) {
  const mean = (xs) => xs.reduce((a, b) => a + b, 0) / xs.length
  const noise = Math.abs(mean(baselineA) - mean(baselineB))
  const gain = mean(candidate) - (mean(baselineA) + mean(baselineB)) / 2
  return { accepted: gain > 2 * noise && guardOk, gain, noise, threshold: 2 * noise, guardOk }
}
```

发布把一组改动打成版本，回滚在切换前检查状态兼容。

```js
// 定义 4.5.4：一组改动作为一个版本，切换原子，回滚检查状态兼容
export function release(store, proposal, now) {
  const previous = store.current()
  const next = store.stage({ base: previous.id, changes: [proposal] })
  store.atomicSwitch(next.id)
  store.appendEvent({ type: 'evolution/release', version: next.id, from: previous.id, proposal: proposal.id, at: now })
  return next.id
}

export function rollback(store, to, now) {
  const target = store.load(to)
  if (!target.canRead(store.stateVersion())) throw new Error(`目标版本 ${to} 无法读取当前状态，需先迁移`)
  store.appendEvent({ type: 'evolution/rollback', to, at: now })
  store.atomicSwitch(to)
  return to
}
```

### 9.2 失败模式

**（1）检查放在装载期（L9 位置放错）。** 门控的鉴别力在搭建时验证过一次，而有害提议的形态会随系统变化。表现是"新的那类有害改动没有被挡住"。

**（2）前提会变（L9）。** 定义 4.5.6 的噪声判据以"两次基线运行使用同一组任务"为前提。任务集变化后，噪声里混进了任务集的变化。

**（3）改动没有理由。** 无法清理，也无法在退化时定位。

**（4）门控只有离线评估。** 真实分布上的退化被漏掉。

**（5）接受判据不看噪声。** 系统在同一水平上反复改。

**（6）评估集可以被演化修改。** 门控被自己削弱。

**（7）门控本身可以被演化修改。** 第一次错误演化之后门控失效。

**（8）逐条应用改动。** 留下半应用状态。

**（9）回滚不检查状态兼容。** 回退到读不懂当前状态的版本。

**（10）回滚条件没有写下来。** 压力下不会执行回滚。

**本节要点**

- 决策表覆盖 12 种情形。
- 失败模式十条，前两条是位置放错与前提会变。
- 最危险的是"门控本身可以被演化修改"——它让整条闭环失去约束。

## 十二、系统影响回溯

**影响一：演化会让"可复现"这条性质必须重新定义。** 一次两周前的失败在今天可能无法复现，因为系统已经改过。处置是把版本写进日志。

**影响二：门控的有效性取决于评估集的质量，而评估集本身是可被修改的对象。** 它必须被元控制挡住。

**影响三：演化会引入震荡这一类新失败。** 处置是在接受改动时记录"它相对哪个基线改进了多少"。

**一处需要修正的预判。** 旧稿把"排除代码"写成一条固定的选择，读完之后要改成由可逆性判定的结论：同一份代码在需要重新构建部署的环境里是不可演化的（需补偿级），而在可以原子切换镜像的环境里是可演化的（可撤销级）。**判据是可逆性，不是对象类型**——这条修正在实践中很重要，因为容器化让"代码级演化"从不可行变成可行。

**通向下一步的桥。**

前五环各自成立，而它们之间还缺一个东西：**节奏**。诊断什么时候跑、演化什么时候发生、技能什么时候沉淀——如果这些都由事件驱动（每次失败就诊断一次、每次诊断就演化一次），系统会变得又快又乱。

所以下一篇是 4.6 复盘周期。它给这五环一个时间结构，并把"什么时候做什么"变成一个可重复的流程。

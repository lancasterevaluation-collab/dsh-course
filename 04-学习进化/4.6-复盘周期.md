## 一、为什么需要固定的复盘周期

### 1.1 从不复盘

系统一直在修单个失败（4.4 → 4.5 的循环），**但从不问"为什么这类失败反复出现"**。于是同类问题一再发生，每次都被当成新问题处理。

### 1.2 被琐事挤掉

"这周太忙了，复盘推到下周"。**而复盘恰恰是让下周不那么忙的机制**——所以它永远排在最后。

### 1.3 复盘了但没有产物

讨论了一小时，"大家要注意点"。**下周同样的问题再次出现。**

这三件事分别对应：**触发机制、周期刚性、产物可执行。**

## 二、三类触发

| 触发 | 判据 | 特点 |
|---|---|---|
| **时间**（`time`） | 到了固定周期 | 可预期，防止无限拖延 |
| **事件**（`event`） | 某种情况聚集出现 | 及时，捕捉模式 |
| **阈值**（`threshold`） | 指标越界 | 客观，与指标挂钩 |

三者的分工：**时间保证下限（至少多久看一次），事件与阈值保证及时性（出事先看）。**

## 三、怎么做

### 3.1 触发类型与优先级

实现如下。

```js
// 触发判定：三类任一成立即触发，并给出具体原因
export function shouldReview(now, state) {
  if (isTimeReached(now, state.period)) return { type: 'time' }
  if (state.sameFailureStreak >= 3) return { type: 'event', reason: `同类失败 ${state.sameFailureStreak} 次` }
  if (state.metricOutOfBounds) return { type: 'threshold' }
  return { type: 'none' }
}
```

算例实测：

| 情形 | 触发类型 | 原因 |
|---|---|---|
| 周期到时 | **`time`** | — |
| **同类失败聚集** | **`event`** | **同类失败 3 次** |
| 指标越界 | **`threshold`** | — |
| **三者都不满足** | — | **仍然触发（`true`）** |

"同类失败 3 次"这个数字值得展开：**它检测的是"模式"而不是"单个失败"**。单个失败由 4.4 诊断处理，而同类失败反复出现，说明诊断给出的修复没有触及根因——这才是需要复盘升级的信号。

"3 次"的来源：与 4.3 的门槛（三次隐式等于一次明说）是同一个量级依据——**一次是偶然，两次可疑，三次是模式。**

### 3.2 默认触发

算例实测：**"三者都不满足时是否触发"为 `true`**。

这条保守原则的含义比较特殊：**它保证复盘一定会发生**。

为什么这样设计是对的：**"没有触发条件"本身就是一个信号**——它可能意味着：

- 我们的触发条件设得不合理（该触发的没触发）。
- 我们缺少观测，所以看不到该触发的信号（与 3.6 的"无法据以行动的指标是噪声"相反的问题：没有指标）。

**所以"什么都没触发"时复盘一次，正好用来检查"触发条件是否需要调整"。**

这与前面几篇的保守原则一致但方向不同：之前的都是"默认不生效"（保守地拒绝），这里是"默认执行"（保守地执行）——**因为这里的代价不对称方向相反**：多做一次复盘的代价很小，漏掉一次复盘的代价是问题持续累积。

### 3.3 任务集构建

复盘的输入是**失败样本**，输出是任务集（可执行的问题清单）。算例实测：6 个样本构建出 4 个任务。

从 6 到 4 的过程就是复盘的核心动作：**归并同类**。

| 动作 | 说明 |
|---|---|
| 聚类 | 把同类失败归到一起 |
| 提取 | 每个类聚成一个任务（而不是每个样本一个） |
| 排序 | 按影响面与频率排序 |
| 去重 | 与已有任务合并 |

"一个类聚成一个任务"是关键的降维：**6 个失败的样本，可能是 2 个根因。** 如果按样本建任务，会做 6 次修复。按根因建任务，只做 2 次。

这与 4.4 的"可行动性"衔接：任务的粒度要**可行动**——太大（"改进错误处理"）不可执行，太小（每个样本一条）没有收敛。

### 3.4 复盘的产物

**复盘必须产出可执行的东西**，否则会退化成 1.3 那种情况。

| 产物 | 内容 | 消费者 |
|---|---|---|
| **改动作业项** | 具体动作 + 负责人 + 期限 | 4.5 演化 / 人 |
| **诊断修正** | 之前的诊断错在哪 | 4.4 诊断 |
| **触发条件调整** | 什么时候该触发 | 3.1 |
| **指标补充** | 缺了哪些观测 | 3.6 可观测 |
| **规则修订** | 流程或策略要改什么 | 团队 |

"诊断修正"与"规则修订"是复盘区别于单次修复的地方：

- **单次修复**（4.4 → 4.5）：修的是行为。
- 复盘：修的是产生行为的规则。

**这正是单环学习与双环学习的分界**（见 6.1）。

### 3.5 节奏

| 周期 | 适用 | 内容 |
|---|---|---|
| **每次失败后** | 单次修复 | 4.4 诊断 → 4.5 演化 |
| **每天/每周** | 短周期复盘 | 同类失败归并、指标检查 |
| **每月** | 中期复盘 | 趋势、规则修订 |
| **每季度** | 长期复盘 | 目标与策略 |

**"越短的周期看现象，越长的周期看规则"**——这是节奏设计的原则。

参数起点：短周期（周）用事件与阈值触发为主，长周期（月/季）用时间触发为主。**长周期必须由时间强制触发**，因为它最容易被挤掉（1.2）。

## 四、特殊情况与处理技巧

| 情况 | 为什么 | 处理 |
|---|---|---|
| 复盘从不发生 | 无时间触发 | 时间触发强制下限 |
| 复盘被挤掉 | 无刚性 | 时间触发不可取消，只能缩短 |
| 复盘没有产物 | 无产物要求 | 强制输出作业项 |
| 同类失败反复 | 只做单次修复 | 事件触发（同类 ≥ 3 次） |
| 触发条件失效 | 无自检 | 默认触发并检查条件 |
| 任务集太大 | 按样本建任务 | 按类聚归并 |
| 复盘结论重复 | 未检查已有项 | 与已有任务去重 |
| 复盘无人负责 | 无负责人字段 | 每个作业项带负责人 |

"复盘结论重复"很常见：同一个建议在不同的复盘里被反复提出，**但从来没人做**。做法是把建议变成带负责人与期限的作业项——没有被指派的任务不是任务。

## 五、工业界的做法（可照做）

### 5.1 敏捷与 SRE 的复盘实践

| 实践 | 做法 | 值得学的点 |
|---|---|---|
| **Sprint 回顾** | 固定节奏、固定时长 | 时间刚性 |
| **SRE 复盘** | 事故后必做、无责 | 事件触发 + 无责 |
| **Kaizen** | 持续小改进 | 短周期 |
| **季度规划** | 目标与策略调整 | 长周期看规则 |
| **经验工厂** | 从数据到经验的结构化流程 | 产物可复用 |

**"固定节奏 + 固定时长"看起来形式化，但它是复盘的唯一保障**：没有日历上的位置，复盘就会被挤掉。

### 5.2 复盘的三种产出

把工业实践归纳一下，复盘产出可以分三类：

| 产出 | 例子 | 时间尺度 |
|---|---|---|
| **修正** | 修这个 bug、改这个参数 | 天 |
| **改进** | 加一个检查、加一个指标 | 周 |
| **改规则** | 改流程、改标准、改职责 | 月 |

三类都要有：只有"修正"就是单环学习（见 6.1），**问题会反复**。只有"改规则"会脱离实际问题。

### 5.3 参数与设计起点

| 参数 | 推荐 | 依据 |
|---|---|---|
| 短周期 | 1 周 | 与迭代节奏一致 |
| 长周期 | 1 月 / 1 季 | 趋势与规则 |
| 同类失败阈值 | 3 次 | 与 4.3 的门槛同量级 |
| 单次复盘时长 | 30–60 分钟 | 太长会退化 |
| 作业项数量 | 1–3 个 | 太多做不完 |
| 作业项期限 | 下一个周期内 | 强制闭环 |

"作业项数量 1–3 个"很关键：**一次复盘产出 10 个作业项，等于一个都不做。** 与 3.2 的审批疲劳是同一个道理——人的执行力是有限资源。

### 5.4 一份可落地的实施清单

1. **三类触发**：时间、事件（同类 ≥ 3）、阈值。
2. 默认触发：都没满足时也触发一次（并检查触发条件）。
3. 输入：一段时间内的失败样本与指标。
4. 归并：按根因聚类，一个类聚成一个任务。
5. 产物：修正、改进、改规则三类各至少考虑一次。
6. 作业项：带负责人与期限，数量控制在 1–3 个。
7. 去重：与已有任务合并。
8. 诊断修正：回顾之前的诊断错在哪。
9. 触发条件调整：根据本次结果调整触发设置。
10. 记录：复盘结论可检索（避免重复讨论）。

## 六、学术界的结论

### 6.1 单环与双环学习

组织学习理论区分两种学习：

| 类型 | 修什么 | 例子 |
|---|---|---|
| **单环学习** | 修正**行为** | 改了参数让它符合标准 |
| **双环学习** | 修正**标准与规则本身** | 改了这个标准 |

关键论断：**只有单环学习的组织会反复遇到同一类问题**，因为它从不质疑自己的规则。

这与本篇的对应极其直接：

- **单环 = 4.4 诊断 + 4.5 演化**（修单个行为）。
- 双环 = 4.6 复盘（修产生行为的规则）。

**"同类失败 3 次触发复盘"正是"单环学习失效"的检测器**——当修行为不能解决问题时，说明要修规则了。

### 6.2 组织学习的三个阶段

组织学习被描述为三个递进的阶段：

| 阶段 | 内容 |
|---|---|
| **个体学习** | 一个人学到东西 |
| **组织学习** | 知识被编码、传播（文档、流程） |
| **制度化** | 变成规则与检查（自动化） |

对本篇的启示：**复盘产物应当尽量"制度化"**——把教训变成自动检查，而不是变成一句提醒。

判据：**如果一个教训只能靠"人记住"来落实，它迟早会被忘记。** 能写成检查的就写成检查（这与本课程反复强调的"可机械验证"一致）。

### 6.3 经验工厂

软件工程里的"经验工厂"提出了从数据到经验的结构化流程：

**数据 → 信息 → 知识 → 经验**

| 层 | 内容 | 本课程对应 |
|---|---|---|
| 数据 | 原始记录 | 会话日志（2.7） |
| 信息 | 聚合指标 | 可观测（3.6） |
| 知识 | 诊断结论 | 4.4 诊断 |
| 经验 | 可复用的规则 | 4.5 演化 + 4.6 复盘 |

这条链的价值在于指出"数据不等于经验"：**没有经过诊断与复盘的数据只是负担**（这也是 3.6 说的"无法据以行动的指标是噪声"）。

### 6.4 过程改进的成熟度

软件过程改进的成熟度模型（CMMI 一类）的核心主张是：**过程要先"可重复"，才谈得上"可优化"**。

对本篇的直接含义：**如果诊断与修复本身都不可重复（每次都靠人临场判断），那复盘就没有对象。**

所以顺序是：

1. **先把 4.4 与 4.5 变成稳定流程**（可重复）。
2. 再在 4.6 复盘它（可优化）。

**"跳过高成熟度阶段直接做高级实践"** 是常见的失败模式。

## 七、理论：两个模型

### 7.1 触发的保守性

算例给出两条相反方向的保守设计：

| 场景 | 默认 | 理由 |
|---|---|---|
| 无法判定成功 | **算失败**（4.4） | 漏判成功代价小 |
| 无触发条件满足 | **仍然复盘**（4.6） | 漏掉复盘代价大 |

共同点是"按代价不对称的方向保守"：**不是一律偏向某一侧，而是看哪一侧的错误更贵。**

这条原则可以推广：**任何默认值的选择，都应当先问"两种错误的代价哪边更大"。**

### 7.2 任务集的降维

$$
|\text{任务集}| \le |\text{样本集}|
$$

算例实测：6 个样本 → **4** 个任务。

**比率 $\frac{4}{6} = 0.67$ 本身是一个可监控的指标**：

- **接近 1**：几乎没有归并，说明聚类没起作用（每个失败都被当成独立问题）。
- 接近 0：过度归并，任务太大不可行动。

**这与 4.2 的"描述层通过率"、4.3 的"权重门槛"是同一类指标**：它们都是流程的"压缩比"，而压缩比是判断流程是否有效的直接证据。

## 九、练习

### 第一题：判断该不该触发

实现如下。

```
A  距离上次复盘 7 天
B  同类失败连续出现 3 次
C  错误率从 2% 升到 5%
D  一切都正常
E  出现了第一次见到的新型失败
```

要求：

- 逐条判断触发类型，并说明依据。
- 对 E，说明它该由哪一层处理（4.4 还是 4.6），为什么。
- 对 D，说明为什么仍然要触发，以及这次复盘的议程是什么。

---

### 第二题：从样本到任务集

场景：一周内出现 9 次失败，分类如下：

```
工具超时           4 次（3 个不同工具）
参数校验失败       3 次（同一个工具）
上下文超限         2 次
```

要求：

- 归并出任务集，说明每个任务的边界与依据。
- 排序并说明依据（影响面 / 频率 / 可行动性）。
- 说明哪一项应该升级到"改规则"而不是"修行为"。
- 给出作业项（含负责人角色与期限）。

要求：

- 设计一组自检问题，用于检查"触发条件是否合理"。

## 十、算例

算例实现了本篇的触发判定与任务集构建。

```powershell
cd D:\dsh-course
node examples/sa37_review.mjs        # 全部函数的运行结果
node examples/test_sa37_review.mjs   # 数字回归断言
```

它做到的事：

- 三类触发（时间 `time`、事件 `event`、阈值 `threshold`）。
- **同类失败 3 次触发事件型复盘**。
- 三者都不满足时仍然触发（`true`）。
- 任务集构建（6 个样本聚成 4 个任务）。

这一篇只要记住一句：复盘要有**三类触发**（时间保下限、事件与阈值保及时），而且三者都不满足时也要触发。它的价值在于修规则而不是修行为——只有单次修复而没有复盘，同类失败会一直重复。

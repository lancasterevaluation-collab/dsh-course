## 本篇新词

- 复盘周期（review cycle） 指按固定节奏回顾一段时间内的失败、改动与资产，并产出下一轮动作。
- 真实任务集（real task set） 指从真实使用中采样出来的任务集合，用于充当门控的回归基线。
- 回归基线（regression baseline） 指一组已知结果的任务，用于判断"这次改动是否让以前做对的事变差了"。
- 三种触发 指按时间、按事件、按阈值三种启动复盘的条件。
- 产出（output） 指一次复盘的具体结果，它是一组可跟踪的动作而不是一份文档。
- 跟踪（follow-up） 指对上一次复盘的产出做检查。
- 覆盖率 指产出里被推进到终态的比例。
- 复盘成本 指一次复盘消耗的时间与资源。
- 形式化复盘（ceremonial review） 指走完流程而没有产生动作的复盘。

## 一、【设计原因】

### 1.1 缺陷一：复盘走完了流程，而没有发生任何事

一次完整的会（或一份完整的报告）：时间线、影响、原因、行动项都写了，而两周之后那些行动项没有任何一条被完成。

成因有两个：产出没有被跟踪（做不做都一样），以及结论不可行动。两者的表现相同而修法不同，因此区分它们要看产出本身有没有可改对象。

### 1.2 缺陷二：门控用的评估集与真实用法差得太远

评估集是设计者写的（覆盖各种边界情况），而真实使用集中在少数几种常见任务上。于是改动在评估集上通过、在真实使用里退化。

### 1.3 缺陷三：任务集不稳定，分辨不出改善

同一版本跑两次的结果差异很大，于是任何改动的效果都落在噪声里，门控失去鉴别力。

成因有三类：任务依赖外部状态、判定标准模糊、任务数量太少。三类的处置不同。

### 1.4 缺陷四：周期不当，要么无事可做要么积压

周期太密时两次之间的样本太少，而复盘本身要花时间，它变成纯粹的开销。周期太疏时积累了十几处改动与几十条失败，复盘只能抽样，于是又回到"不知道哪个改动导致了什么"。

### 1.5 由此确定的设计目标

1. 三种触发并存：时间保证不漏，事件保证及时，阈值保证严重问题立即处理。
2. 每轮聚焦一个维度，默认按时间窗口。
3. 任务集来自真实会话的分层采样，并筛掉不稳定的任务。
4. 产出是带状态的动作，放弃必须带理由。
5. 跟踪放在复盘开头，覆盖率低时不新增产出。

**本节要点**

- 没有产出的复盘等于没有发生。
- 设计者写的评估集偏向边界情况。
- 基线不稳时门控失去鉴别力。
- 周期过长会积压，过短会变成开销。
- 五条目标：三触发、单维度、真实采样、带状态产出、先清后提。

## 二、【直觉】

### 2.1 三个闹钟

- 一个每天响一次：提醒你检查一遍（时间）。
- 一个在同类问题连续出现时响（事件）。
- 一个在指标越界时响（阈值）。

**三个闹钟互相补位**，因此不必争论"该用哪个"。而它们共同的前提是：证据必须已经存在——没有日志与度量，三个都不会响。

::: keypoint 反直觉点
**复盘的价值全部落在"产出被跟踪"上。** 分析得再深，如果不检查上次的动作有没有做完，这个机制就会退化成一份按时生成的报告——而报告不改变任何事。
:::

### 2.2 先清旧账

每次复盘的第一件事不是分析新问题，而是检查上次的动作。

- 旧账没清就提新账，未完成项会累积。
- 累积到一定程度之后，跟踪本身变成大工程，于是被跳过。
- 跳过跟踪之后，复盘就只剩下分析，而分析不产生改变。

所以规则是：覆盖率低于阈值时，本轮不再新增产出。

### 2.3 一个数字直觉

设真实流量里某类退化发生在 5% 的请求上，而任务集有 $N$ 个任务，漏检概率约为 $(1-0.05)^N$。

| 任务数 | 漏检概率 |
|---|---|
| 20 | 36% |
| 50 | 8% |
| 100 | 0.6% |
| 200 | 0.004% |

五十个任务是一个有意义的门槛（漏检降到一成以下），一百个任务让常见退化几乎必然被发现。

而成本的量级也随之确定：每次门控要跑任务集两次（两次基线）加一次（候选），因此 100 个任务意味着 300 次执行。

**本节要点**

- 三个闹钟互补。
- 先清旧账再提新账。
- 五十到一百个任务是门控鉴别力的门槛。

## 三、【严格】

### 3.1 定义

::: theorem 定义 4.6.1（复盘周期）
一次复盘是一个映射

$$
\mathrm{review}: (\text{窗口内的失败与改动},\ \text{上一轮的产出}) \to \text{本轮的动作集合},
$$

其中动作集合是四种形态之一：演化提议、技能修改、记忆或写入策略调整、待观察项。**产出必须有状态且可跟踪**，否则它不构成产出。
:::

::: theorem 定义 4.6.2（三种触发）
复盘的触发条件是三者之一：

$$
\mathrm{trigger} = \begin{cases}
\text{时间}, & t - t_{\text{last}} \ge \Delta,\\
\text{事件}, & \text{窗口内同类失败数} \ge n_0,\\
\text{阈值}, & \text{某指标越界}.
\end{cases}
$$

三者的严重程度递增（时间最轻、阈值最重），而触发原因必须被记录——它决定本轮聚焦哪个维度。
:::

::: theorem 定义 4.6.3（真实任务集）
一个真实任务集 $T$ 由三步构成：从真实会话采样（要求有明确成功判据）、按常见程度分层、按稳定性筛选。

$$
T = \mathrm{stratified}\big(\{t : t.\mathit{check} \ne \varnothing \ \land\ t.\mathrm{stability} \ge s_0\}\big).
$$
:::

::: theorem 定义 4.6.4（产出与状态）
一条产出是

$$
o = (\mathit{kind},\ \mathit{action},\ \mathit{state},\ \mathit{dropReason}?),
$$

其中 $\mathit{state} \in \{\text{未开始},\ \text{进行中},\ \text{完成},\ \text{放弃}\}$。**"放弃"必须带理由。**
:::

::: theorem 定义 4.6.5（覆盖率）
产出集合 $O$ 的覆盖率是

$$
\mathrm{cov}(O) = \frac{|\{o : o.\mathit{state} = \text{完成}\}| + |\{o : o.\mathit{state} = \text{放弃} \land o.\mathit{dropReason} \ne \varnothing\}|}{|O|}.
$$

**带理由的放弃计入覆盖**，无理由的放弃不计入。
:::

::: theorem 定义 4.6.6（复盘成本）
一次复盘的代价由三部分构成：

$$
\mathrm{cost} = \mathrm{cost}_{\text{收集与聚类}} + \mathrm{cost}_{\text{诊断}} + \mathrm{cost}_{\text{评审与跟踪}}.
$$

它必须被显式记录，因为它与收益竞争，而周期长度的选择依赖它。
:::

### 3.2 命题

::: theorem 命题 4.6.1（漏检率随任务数指数下降）
设某类退化在单任务上的发生概率为 $p$，任务数为 $N$，则漏检概率是 $(1-p)^N$。

**证明.** 每个任务独立地以概率 $1-p$ 不暴露该退化。全部任务都不暴露的概率是各次相乘，即 $(1-p)^N$。故漏检率随 $N$ 指数下降。

↓ **为什么能这么写？** 独立事件的联合概率是各概率之积。

$\blacksquare$

**数值**：$p = 0.05$ 时，$N = 20$ 的漏检率 36%、$N = 50$ 为 7.7%、$N = 100$ 为 0.6%、$N = 200$ 为 0.0035%。成本随 $N$ 线性增长而鉴别力指数增长，因此"够用"的点在五十到一百之间。
:::

::: theorem 4.6.2（无理由的放弃会扭曲覆盖率）
若把无理由的放弃计入覆盖，则覆盖率虚高。若把所有放弃都不计入，则人们不愿标记放弃。

**证明.** 第一种：无理由的放弃也是"结束"，把它算作完成使覆盖率不再反映"有多少产出的状态是清楚的"。第二种：放弃被记为未完成时，标记放弃会拉低指标，于是理性选择是把它留在"进行中"——积压因此被隐藏。

↓ **为什么能这么写？** 两种失真的方向相反，而把"带理由"设为条件同时避开它们。

$\blacksquare$

::: theorem 4.6.3（覆盖率低时停止新增）
若在覆盖率低时继续新增产出，则未完成项的数量单调不减。

**证明.** 设本轮新增 $a$ 条、完成 $b$ 条。覆盖率低于阈值意味着 $b$ 小于存量的一小部分，而新增 $a > 0$ 使存量增加 $a - b > 0$。故存量单调不减。

↓ **为什么能这么写？** 存量变化等于新增减完成，而它的符号由覆盖率与新增共同决定。

$\blacksquare$

::: keypoint 形式化复盘就是这样形成的
存量增加 → 跟踪变成大工程 → 跟踪被跳过 → 只剩分析。 因此"先清积压"不是流程洁癖，而是这个机制能否存续的条件。
:::

::: theorem 4.6.4（任务集应长期复用并按比例替换）
重建任务集会使所有历史比较失效。不替换则任务集会随系统改进而过时。

**证明.** 第 $i$ 轮的指标是任务集 $T_i$ 上的结果。若 $T_{i+1} \ne T_i$，两次结果之差同时包含改动效果与任务集变化，故无法比较。若 $T$ 恒定而系统能力上升，则 $T$ 上的分数趋近上限，鉴别力下降。

↓ **为什么能这么写？** 比较要求受控变量，鉴别力要求足够难度。

$\blacksquare$

**数值**：处置是**按比例替换**（例如每季度换两成）而不是重建——替换保留大部分可比性，同时注入新难度。
:::

::: theorem 4.6.5（跟踪必须放在复盘开头）
跟踪的注意力成本与其他分析竞争同一份预算，因此把它放在末尾会被新产出挤掉。

**证明.** 设一次复盘的时间预算固定。分析产生的产出条数与其占用时间正相关，而剩余时间用于跟踪。若跟踪在末尾执行，则它获得的是剩余预算，而该预算随分析深度上升而下降。故跟踪被挤掉是结构与预算的必然结果。

↓ **为什么能这么写？** 顺序决定资源竞争的结果。

$\blacksquare$

::: theorem 4.6.6（复盘只提议不发布）
复盘的动作集合与 4.5 的发布之间必须有一道门控，否则复盘能绕过门控。

**证明.** 若复盘可以直接应用改动，则它同时是提议者与决策者，而 4.5 命题 4.5.2 证明"决策者可以改自己"会使门控失效。因此权限必须分离：复盘产出提议，门控决定接受。

↓ **为什么能这么写？** 同一主体既是提议者又是裁决者时，裁决不构成约束。

$\blacksquare$

### 3.3 本节要点

**本节要点**

- 复盘消费一批失败，产出是可跟踪的动作（定义 4.6.1）。
- 三种触发严重程度递增，原因必须记录（定义 4.6.2）。
- 真实任务集由采样、分层与稳定性筛选构成（定义 4.6.3）。
- 产出带状态，放弃必须带理由（定义 4.6.4）。
- 覆盖率把带理由的放弃计入（定义 4.6.5）。
- 复盘成本必须被记录（定义 4.6.6）。
- 漏检率随任务数指数下降（命题 4.6.1）。
- 无理由的放弃会扭曲覆盖率（命题 4.6.2）。
- 覆盖率低时停止新增（命题 4.6.3）。
- 任务集长期复用并按比例替换（命题 4.6.4）。
- 跟踪必须在复盘开头（命题 4.6.5）。
- 复盘只提议不发布（命题 4.6.6）。

## 四、【回到直觉】

- **定义 4.6.1 说的**：复盘的产物是一组动作，不是一份报告。
- **定义 4.6.2 说的**：三个闹钟，越严重的越急。
- **定义 4.6.3 说的**：考题从真实用法里采，挑常见的，剔掉不稳定的。
- **定义 4.6.4 说的**：每条动作有个状态，放弃也要说清为什么。
- **定义 4.6.5 说的**：说清理由的放弃也算处理过了。
- **定义 4.6.6 说的**：复盘花的工夫要记下来。
- **命题 4.6.1 说的**：五十道题能把漏检压到一成以下，一百道压到 1% 以下。
- **命题 4.6.2 说的**：放弃不算数，大家就会装作还在做。
- **命题 4.6.3 说的**：旧账不清就开新账，迟早只剩记账。
- **命题 4.6.4 说的**：换代考题会让以前的结果没法比，所以换一部分而不是重来。
- **命题 4.6.5 说的**：先检查上次，再分析这次——反过来旧账就没人看了。
- **命题 4.6.6 说的**：复盘可以提方案，但不能自己批准。

**本节要点**

- 产出是动作。
- 三个闹钟。
- 考题要稳。
- 放弃带理由。
- 先清旧账。
- 只提议不发布。

## 五、【工具箱】

### 5.1 触发判定

| 触发 | 条件 | 作用 |
|---|---|---|
| 时间 | 距上次复盘超过一个周期 | 发现缓慢退化 |
| 事件 | 窗口内同类失败达到 N 次 | 及时处理突发模式 |
| 阈值 | 某项指标越界 | 严重问题立即处理 |

**判定的顺序按严重程度从轻到重**，并把触发原因记录下来，它决定本轮聚焦哪个维度。

### 5.2 复盘的三个维度

| 维度 | 范围 | 典型问题 |
|---|---|---|
| 时间窗口 | 最近一个周期的失败与改动 | 有没有缓慢退化 |
| 会话或用户 | 某条会话或某类用户 | 这类使用为什么成本高 |
| 主题 | 某一类失败 | 它有没有共同原因 |

**每轮选一个维度**，默认时间窗口。一次覆盖三个维度的结果是每个都只扫一眼。

### 5.3 任务集的三步

1. **采样**：从真实会话里挑出有明确成功判据的任务。
2. **分层**：按常见程度分层，常见的多取。
3. **稳定性筛选**：跑两次，剔除或隔离不稳定的任务。

**第三类处置要单独一组**：不稳定任务不是删除，而是隔离观察——它们往往依赖外部状态，而那本身是一个值得修的问题。

### 5.4 跟踪的规则

1. 跟踪在复盘开头执行。
2. 每条产出有状态：未开始、进行中、完成、放弃。
3. **放弃必须带理由**，带理由的放弃计入覆盖。
4. 覆盖率低于阈值时，本轮**不再新增产出**。
5. 只检查上一轮的产出，更早的积压一次性清理（标记放弃并说明理由）。

### 5.5 成本与周期

成本 = 收集与聚类 + 诊断 + 评审与跟踪。

**如果一次复盘的成本超过了它带来的改进的价值，应当缩小范围（每轮只看一个维度），而不是延长周期**——延长周期会让单次工作量增加，成本随之上升。

**本节要点**

- 三种触发按严重程度判定。
- 每轮一个维度。
- 任务集三步，不稳定任务隔离。
- 跟踪五条规则。
- 成本高时缩小范围，不延长周期。

```js
// 定义 4.6.2：三种触发，严重程度递增
export function shouldReview(state, config) {
  if (config.now - state.lastReviewAt >= config.reviewInterval) return { kind: 'time', reason: '周期到' }
  const recent = state.failures.filter((f) => config.now - f.at <= config.burstWindow)
  const byKind = new Map()
  for (const f of recent) byKind.set(f.kind, (byKind.get(f.kind) ?? 0) + 1)
  const top = [...byKind.entries()].sort((a, b) => b[1] - a[1])[0]
  if (top && top[1] >= config.burstCount) return { kind: 'event', reason: `同类失败 ${top[1]} 次` }
  const breach = Object.entries(state.metrics ?? {}).find(([k, v]) => v > (state.thresholds?.[k] ?? Infinity))
  if (breach) return { kind: 'threshold', reason: `${breach[0]} 越过阈值` }
  return null
}
```

### 7.3 任务集段

任务集段按三步构建，并按比例轮换。

```js
// 定义 4.6.3：稳定性与判据双筛 + 分层采样
export function buildTaskSet(samples, target = 100, minStability = 0.9) {
  const stable = samples.filter((t) => t.check && t.stability >= minStability)
  const byKind = new Map()
  for (const t of stable) {
    if (!byKind.has(t.kind)) byKind.set(t.kind, [])
    byKind.get(t.kind).push(t)
  }
  const picked = []
  const kinds = [...byKind.keys()].sort()
  let i = 0
  while (picked.length < target && kinds.some((k) => byKind.get(k).length > 0)) {
    const kind = kinds[i % kinds.length]
    const next = byKind.get(kind).shift()
    if (next) picked.push(next)
    i++
  }
  return picked
}

/**
 * 命题 4.6.4：按比例替换而不是重建。
 * @param current 现有任务集
 * @param samples 新采样的候选
 * @param ratio 替换比例
 * @param minStability 稳定性下限
 * @returns 新任务集
 */
export function rotateTaskSet(current, samples, ratio, minStability = 0.9) {
  const keep = Math.floor(current.length * (1 - ratio))
  const need = current.length - keep
  const fresh = buildTaskSet(samples, need, minStability)
  return [...current.slice(0, keep), ...fresh]
}
```

### 7.4 产出与跟踪段

```js
// 定义 4.6.5：带理由的放弃计入覆盖
export function coverage(outputs) {
  const closed = outputs.filter((o) => o.state === 'done' || (o.state === 'dropped' && o.dropReason))
  return outputs.length === 0 ? 1 : closed.length / outputs.length
}

// 命题 4.6.3：覆盖率低时本轮不再新增
export function gateOnCoverage(outputs, minCoverage) {
  return coverage(outputs) >= minCoverage
}
```

任务集的稳定性用同一版本两次运行的一致度来估计。

```js
// 命题 4.6.4：稳定性估计——同一版本两次运行的一致度与噪声
export function stability(runA, runB) {
  const same = runA.filter((v, i) => v === runB[i]).length
  const rate = (xs) => xs.filter(Boolean).length / Math.max(1, xs.length)
  return {
    consistent: same / Math.max(1, runA.length),
    noise: Math.abs(rate(runA) - rate(runB)),
    unstable: runA.filter((v, i) => v !== runB[i]).length,
  }
}
```

### 9.2 失败模式

**（1）检查放在装载期（L9 位置放错）。** 覆盖率只在年终看一次，而积压是逐轮形成的。表现是"回头看才发现有几十条动作没做"。

**（2）前提会变（L9）。** 命题 4.6.1 的漏检率以"任务与退化独立"为前提。若退化与任务类型强相关，则分层采样后的实际漏检率与公式不符。

**（3）产出写成了报告。** 没有可跟踪的动作，复盘不改变任何事。

**（4）跟踪放在末尾。** 被新产出挤掉，积压开始累积。

**（5）无理由的放弃计入覆盖。** 覆盖率虚高，积压被掩盖。

**（6）覆盖率低时仍新增产出。** 存量单调增加，跟踪最终被跳过。

**（7）任务集重建而不是替换。** 历史比较全部失效。

**（8）不稳定任务留在主集。** 整个任务集的噪声被抬高，门控鉴别力下降。

**（9）评估集全部由设计者编写。** 它衡量的是设计者的想象，而退化发生在常见任务上。

**（10）复盘直接发布改动。** 它同时是提议者与裁决者，门控失效。

**本节要点**

- 决策表覆盖 12 种情形。
- 失败模式十条，前两条是位置放错与前提会变。
- 最普遍的是"产出写成了报告"——它看起来完成了复盘，实际什么也没做。

## 十、仍未解决

**本节要点**

- 收益不可测是这条机制的结构性弱点。
- 任务集过时与抽样损失都只能缓解。

## 十二、系统影响回溯

**影响一：复盘把前面五篇串成一条因果链，而链条的强度由最弱一环决定。** 因此复盘产出少往往不是复盘的问题，而是链条上某处断了。

**影响二：周期会改变系统的行为模式。** 太密时样本太少，太疏时无法归因。

**影响三：复盘是唯一回头看"上次说的事做了吗"的机制。** 因此它在长程任务里是一个天然的检查点。

**一处需要修正的预判。** 旧稿把"收益不可测"写成一条普通的缺陷，读完之后要把它升级为结构性的不对称：成本是可见的（时间与资源），而收益的一半是不可见的（被避免的失败）。这条不对称会让周期被持续拉长，直到复盘事实上停止——因此**把成本显式记录下来是抵御这条漂移的唯一手段**，而不是一项可选的度量。

**通向下一步的桥。**

复盘管的是"改进系统"这条线的进度，而它留下另一条线：**一个具体的长任务做到哪了**。那条线的进度不在系统里，而在任务本身——它需要另一套状态外部化的做法，以及在新会话里快速重建"做到哪了"的能力。

所以下一篇是 4.7 长程任务，它是第 4 卷的收口，也是整门课程里"长程执行"这一主题的正面回答。

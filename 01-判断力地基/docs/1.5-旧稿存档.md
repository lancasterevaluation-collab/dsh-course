## 本篇新词

状态（state） 指一个系统在某一时刻所持有的、会影响后续行为的信息。判断一段信息是不是状态，只问一个问题：如果它丢了，系统的后续行为会不会不同。会不同的就是状态，不会不同的就不是（例如一个可以随时重算的缓存计数在某种意义上是状态，而在另一种意义上不是——差别在于能不能从别处重算出来，这正是 1.1 要区分的）。

权威状态（source of truth） 指那些一旦丢失就无法从系统内部恢复的数据。它必须被持久化，而且必须有一个唯一的写入点。本课程的会话日志就是权威状态：模型每一轮看到什么，是从它派生出来的，而不是相反。

派生状态（derived state） 指可以从权威状态重新计算出来的数据。它的关键性质是：它永远不应该成为其他数据的来源。一旦派生结果被别的模块依赖，权威状态就失去了唯一性，而后果是同一份历史在不同时间重放会得到不同结果。

不可逆（irreversible） 在这里指改动发生之后无法回到改动之前的可观察状态。它与"难以撤销"不同——难以撤销是成本问题，不可逆是可能性问题。一条已经写进磁盘并被别的进程读过的事件、一封已经发出的邮件、一次已经计费成功的调用，都属于后者。

先写日志（write-ahead logging） 指在改动实际数据之前先把这次改动记入日志，并保证日志先落盘。它的作用是把"改到一半崩溃"这种不可判定状态，变成"日志里有记录但数据未完成"，而后者可以被重放或回滚。Gray 与 Reuter 把这条顺序列为原子性与持久性的实现前提。

迁移（migration） 指把已有数据从一种格式或结构变成另一种的过程。它的特殊之处在于它作用的对象是已经存在的数据，因此它不能靠"同时更新所有调用方"来完成——历史数据不会跟着代码改。

幂等（idempotent） 指同一操作执行一次与执行多次的效果相同。它与恢复的关系是：恢复时遇到"已经开始但没有结果"的操作，只有幂等的才可以安全重放，非幂等的只能标记为结果未知。Kleppmann 把 exactly-once 的代价讲得很清楚——它在工程上通常是"至少一次 + 去重"，而去重的依据正是操作本身的幂等标识。

有界（bounded） 指一个容器有硬性容量上限，达到上限时它的行为是被规定的，而不是"尽力而为"。有界本身不是难点，难点是写满时做什么，那是 1.6 的内容。

快照（snapshot） 指返回给调用方的一份数据副本，它与内部状态之间不再有别名关系。需要区分两个层次：数组本身是副本（改数组长度不影响内部）与数组的每个元素也是副本（改某个元素的字段不影响内部）。只做前者是常见的半成品，而它恰好能通过多数的随手测试。

### 0.1 一个具体的状态问题：`BoundedMemory` 的容量语义

这一篇的第一个判断可以用作业里那个容器来检验。`homework/ch01-judgment/kit/CONTRACT.md` 给出的契约里，`add` 在达到上限时抛 `CapacityError` 而不是丢弃最旧的条目。这个选择看起来只是风格，但它背后是一条关于状态所有权的判断。

考虑两种实现的后果差异。丢弃最旧的实现里，调用方永远不知道自己丢了什么——它调用 `add` 得到成功，而失败被隐藏在一次静默的驱逐里。当调用方后来试图取出那条记忆时，它得到的是"不存在"，而它无法区分"从未写过"与"被驱逐了"。在一个 agent 的记忆系统里，这个区别有实际后果：前者说明模型没有学到，后者说明学到了但空间不足，而这两种情况需要不同的处置（重新学习 vs 扩容或合并）。

拒绝的实现里，失败是显式的一次 `CapacityError`，它带着 `limit` 与 `current` 两个字段，于是调用方可以决定怎么办：合并两条旧记忆（契约里的 `merge` 正是为此存在）、删掉一条不再需要的、或者提高上限。决定权因此留在最了解业务的那一层。

这个选择的代价也必须说清：拒绝会让调用方必须写处理逻辑，而如果没有写好，一次容量耗尽就会让整个写路径失败。这是把"静默降级"换成"显式失败"时必然付出的代价——它把一次隐藏的损失变成一次可见的中断。两者都不是免费的，区别在于代价落在谁身上：静默驱逐把代价推给未来的查询者，显式拒绝把代价推给当下的写入者。

### 0.2 本篇建立的三项判据

第一项用于判断一段数据属于哪一类状态（1.1）：问它能不能从别处的数据重建。能重建的是派生状态，不能的是权威状态，而在系统之外的（磁盘上的其他文件、远端服务、已经发出的消息）属于外部状态——它既不能被重建，也不能被回滚。

第二项用于判断一次改动的影响是否可逆（1.3）：问撤销它需要动什么。改内存里的一个变量、改一个本地文件、改一个已经离开本机的东西、以及无法撤销，对应四类不同的准备动作。

第三项用于在有界状态下选择行为（1.6）：问容量耗尽时谁该做决定。自动丢弃意味着实现替调用方做了决定，自动合并意味着实现替调用方做了一个更复杂的决定（合并会产生信息损失），而拒绝意味着把决定交回去。

### 0.3 开始之前的十分钟练习

打开 `homework/ch01-judgment/kit/CONTRACT.md`，只读第五节（不变量）与第六节（不属于承诺的部分），回答三个问题。`list()` 返回的数组如果直接返回内部数组，哪一条不变量被破坏了？如果只复制数组而不复制元素，哪一条被破坏了？第六节里被明确排除的四项中，哪一项如果被依赖了，会让将来换一种内部数据结构变成破坏性变更？

这三个问题的答案分别是第四条、第五条、以及"内部使用的数据结构"那一项。它们的共同形态是：不变量与"不承诺"两部分合起来，才界定了这个容器对外承诺的边界。而这三处恰好是学生实现里最容易失分的地方——不是因为难，而是因为它们看起来像细节。

下面这段代码把"只复制数组、不复制元素"的后果演示出来，八行，可以直接运行。

```js
// 错误实现：list 返回了一个新数组，但元素仍是内部对象
class BadMemory {
  constructor() { this.entries = [{ id: 'a', text: '原始内容' }] }
  list() { return [...this.entries] }        // 数组是新的，元素是共享的
}
const m = new BadMemory()
const snapshot = m.list()
snapshot[0].text = '被外部改掉了'
console.log('内部状态：', m.entries[0].text)   // 输出：被外部改掉了
console.log('不变量 5 被破坏：改它影响了内部')
```

对照正确实现（元素也复制），同样的两行代码输出的是 `原始内容`。这个差别在单次随手测试里容易漏掉，因为多数测试只检查 `list()` 的长度与内容，而内容在测试期间没有被外部修改过。

> **高频问法**："你怎么设计一个有容量限制的缓存或记忆？"
> **追问方向**："满了怎么办？"三种答案（丢弃最旧的、拒绝、合并）都要说清代价落在谁身上，其中"拒绝"通常不是第一反应，而是理解状态所有权之后的结论。

### 0.5.3 三个连锁影响

第一，状态分类会决定崩溃恢复的可行性。 恢复的定义是"从磁盘上的数据重建内存中的一切"。如果一个系统里存在某项内存状态无法从磁盘重建，那么它就无法在崩溃后恢复，而这个问题在开发阶段不可见——因为开发时很少崩溃。它的暴露方式不是在测试里，而是在一次真实的断电或进程被杀之后：系统启动，读到一份看似完整的日志，然后表现得像丢失了最近几分钟的记忆。

把这个连锁写成判据是：对每一项内存状态，问它在重启后由什么重建，答不上来的那项就是恢复的缺口。

第二，可逆性的判断会决定改动前的准备工作。 这是 1.1 的可逆性分级在数据层面的展开。一个只有当改动落到"改已经离开本机的状态"这一级时，准备工作才会从"备份"变成"设计一个补偿操作"——因为备份对已经发出的东西无效。分布式系统里这个话题叫补偿事务（saga），而它的核心是：当无法回滚时，你需要一个能抵消前一步的可执行操作，而不是一份可以恢复的副本。这个连锁在第 5 卷的对外接口里会再次出现。

第三，有界容器的选择会把"信息损失"从自动变成显式。 自动丢弃的实现里，信息损失发生在无人知晓的时刻，而它的后果（查询返回不存在）与"从未写入"不可区分。显式拒绝的实现里，损失被替换成一次失败，而失败带着当时的上下文（上限是多少、当前是多少）。这条连锁的一般形式是：把不可观测的降级换成可观测的失败，是让系统可调试的一种主要手段。

它与 1.2 讲的"利息"是同一件事的两面——静默降级是一种持续支付且不产生信号的利息。

### 0.5.4 它与本书其余部分的关系

本篇处理的数据是本地的、单机的、由本进程独占的。这个边界需要说清，因为它决定了本篇的结论在哪里失效。

当数据被多个进程共享时，本篇的"先写日志"会变成需要协调的协议（两阶段提交或共识算法），而"快照"会变成需要定义可见性级别的问题——Berenson 等人在 1995 年的那篇论文里指出，ANSI 标准的四种隔离级别存在歧义，而真实实现（快照隔离、可串行化快照隔离）与标准文本并不一致。本篇不处理这些，但第 5 卷的多会话与并发会需要它们。

当数据离开本机时，"不可逆"的代价从这个系统的可用性变成了外部世界的状态。一封已经发出的邮件无法撤回，一次已经计费成功的调用不会退款，而这类操作的正确处理方式不是回滚，而是幂等的重试标识加上事后的补偿。第 3 卷的错误处理与第 5 卷的审批会分别处理它们的两个侧面。

> **面试视角**
> **高频问法**："你的系统崩溃后会丢什么？"
> **高分要点**：不要笼统回答"有持久化所以不丢"，而要按三类状态回答——权威状态在磁盘上、派生状态重启后重算、外部状态无法恢复因此必须在发出之前决定清楚。这个回答方式本身就是区分度。

## L0 要解决的问题

### 0.1 现象一：重启之后，系统表现得像丢了最近几分钟的记忆

这个现象的复现步骤固定：跑一段会话，正常使用，然后杀掉进程重启，接着发现模型对最近发生的事一无所知，而磁盘上的文件看起来是完整的。

它的成因不是"没有持久化"，而是持久化的对象选错了。常见的写法是把"当前对话内容"作为一个对象保存在内存里，在若干轮之后把它整体写一次盘。这种做法在开发阶段完全够用，因为开发时很少杀掉进程。而它在真实环境里有一个固定的失败点：写盘动作与使用动作之间存在时间窗，窗口内发生的一切在崩溃时都会消失。

更麻烦的一种变体是把派生结果落盘、把权威状态留在内存。例如把"压缩后的摘要"写进文件，而把原始事件留在内存数组里。重启后系统读到摘要，看起来一切正常，但那份摘要已经无法验证——因为没有原始事件可以重建它，也没有办法确认它与当时的历史一致。系统此时的状态是"看起来能用，但历史不可复现"，而这个问题在症状上表现为模型偶尔做出无法解释的判断。

### 0.2 现象二：准备回滚时才发现，数据已经被改过了

第二个现象发生在改动之后的恢复阶段。回滚一个部署通常意味着把代码切回旧版本，但代码切回去之后，数据仍然是新格式。如果新版本加了字段、删了字段、或者改变了某个字段的语义，那么旧版本读新数据时会得到三种结果之一：忽略它（可能正确也可能静默错误）、报错拒绝读取（服务不可用）、或者读出一半然后崩溃。

这三种结果的性质完全不同，而它们的区别来自一个在设计阶段就应当回答的问题：这次改动对数据的可逆性属于哪一级。如果一个改动只是增加了一个可选字段，那么回滚是安全的（旧版本忽略它）。如果删除了一个字段，那么回滚之后旧版本会缺少它依赖的信息。

如果改变了语义（例如把"毫秒"改成了"秒"），那么回滚会让旧版本读到数值正确但含义错误的数据——它的表象是"服务正常，结果是错的"，属于 1.1 那张表里最难发现的一类。

### 0.3 现象三：有界容器静默丢弃，使用者永远不知道自己失去了什么

第三个现象在有容量上限的系统里必然出现。一个记忆容器达到上限后，如果它自动丢弃最旧的条目，那么调用方此后得到的"不存在"有两种可能的原因，而它无法区分：从来没写过，或者写过但被驱逐了。

这个区别在 agent 系统里有实际后果。前者说明模型没有学到这件事，需要再教一次。后者说明学到了但空间不足，需要合并或扩容。两种处置的成本相差很大，而它们目前无法被区分——因为信息在一次静默的驱逐里丢失了，且丢失的时刻没有任何信号。

把这个现象与 0.1 对照可以看出它们的共同形态：两者都是"系统在某个时刻做了一次决定，而这个决定没有留下痕迹"。0.1 的决定是"这部分状态不必落盘"，0.3 的决定是"空间不足时丢掉最旧的"。它们都属于不可观测的降级——系统仍然工作，只是工作在一个比使用者以为的更低的水准上。

### 0.4 现象四：迁移中断，数据既不是旧格式也不是新格式

第四个现象只在迁移出问题时出现，而它一旦出现就很难处理。假设一次迁移要把每条记录从 `{ at: number }` 改成 `{ at: string }`（时间戳改成 ISO 字符串），实现方式是遍历全表逐条改写。如果在写到一半时进程被杀，那么表里有一部分是数字、一部分是字符串，而两者的判断条件（`typeof at === 'number'`）在读取时会分别指向不同的分支。

这个状态的性质与前面几个不同：它不是"少了一部分数据"，而是"数据处在两个版本的混合态，且没有任何记录说明它停在哪里"。修复它需要额外的信息——要么迁移本身有日志（记录进度与已完成的批次），要么原来的数据有备份。先写日志这条规则正是为这个场景存在的：它把"不可判定的中断点"变成"日志里有记录、数据未完成"。

### 0.5 这一篇要正面回答的四个问题

第一，状态分几类，判断依据是什么（1.1）。答案是可重建性：能从别处重建的是派生态，不能的是权威态，在系统之外的是外部态。

第二，为什么派生状态不能成为真相源，破坏这条规则会以什么形式暴露（1.2）。答案是历史不可复现，而它暴露在压缩、恢复与统计三处。

第三，一次改动的可逆性由什么决定，不可逆时该怎么办（1.3、1.4、1.5）。答案是"撤销需要动什么"，四级分别对应不同的准备动作，而不可逆时需要的不是备份而是补偿操作。

第四，有界状态写满时该由谁做决定（1.6）。三种策略（拒绝、合并、丢弃）把决定权交给不同的人，选择的依据是"谁最了解业务"。

> **面试视角**
> **高频问法**："你的系统崩溃后会丢什么？"
> **追问方向**："如果我把压缩结果只放在内存里会怎样？"落点是历史不可复现——同一份日志重放两次会得到不同结果，而这个问题在 2.7 篇会以不变量的形式被固化下来。

## L1 设计与原理

### 1.1 状态分三类，判据是能不能重建

分法的依据只有一个问题：这段信息丢了之后，能不能从系统内部的其他数据重新算出来。

权威状态是不能重建的那部分。它必须落盘，而且必须有一个唯一的写入点。本课程的会话日志是权威状态：事件按顺序追加，任何"模型当时看到什么"都必须能从它派生出来，反过来不成立。

派生状态是能从权威状态重建的那部分。压缩摘要、消息数组、token 计数、索引、检索用的倒排表都属于这一类。它们的正确性判据是：删掉之后重新计算，结果必须与之前一致。

外部状态是系统之外的、既不能重建也不能撤销的那部分。磁盘上不属于本系统的文件、远端服务的数据库、已经发出的消息，都属于这一类。它的特点是本系统无法控制它，因此对它的改动在可逆性上都要按最保守的等级处理。

这个分类往下推一步会得到一个可执行的设计规则：派生状态永远不应成为其他数据的来源。一旦某个模块依赖了派生结果，权威状态就不再是唯一真相——因为同一个派生物可以在不同时间由不同输入算出，而依赖它的一方无法知道当前这份是何时、由什么算出来的。

### 1.2 派生状态成为真相源之后会发生什么

这条规则被破坏时不会立刻报错，它的暴露方式有三种，而三种都不容易与原因联系起来。

第一种是重放不一致。同一份日志在两次恢复中派生出不同的结果，而原因可能是派生过程依赖了外部输入（当前时间、环境变量、模型的随机性），也可能是它依赖了另一次派生的结果。Kleppmann 在讨论重放时把这一类问题归为"非确定性计算被当成了可重放计算"，而它的修法是让派生过程成为权威状态的纯函数。

第二种是压缩之后无法回答"模型当时看到了什么"。压缩本身是必要的能力（第 3 卷的内容），但如果压缩结果替换了历史，那么被替换掉的那部分就永久丢失了。会话日志的规则因此是"压缩产生一条事件，而不是改写已有事件"——派生视图从压缩点往后算，原始事件全部保留。

第三种是统计对不上。token 计数这类派生数据常被当作独立的指标存储，而它的值取决于它被计算的时刻（当时的日志长度）。当它在不同位置被分别计算时，两个来源会出现差异，而定位差异需要回溯到各自的输入。

这条规则数量级上的代价可以估一下。一份长会话按一万条事件、每条平均两百字节计，原始日志约两兆字节。一次压缩摘要按四千字计，约八千字节。如果只保留摘要，磁盘占用降到千分之四，而在需要重建历史、做统计、或者回答"为什么它当时那么决定"时，这份数据无法恢复——省下的是毫秒级的读取时间与几兆字节的空间，失去的是一次无法重来的排查机会。这个交换在单机开发时看起来划算，在真实使用中不划算。

### 1.3 可逆性四级：依据是撤销需要动什么

1.1 给出的四级判据在这里落到数据上。

| 级 | 撤销需要动什么 | 数据层面的例子 | 改动前要准备什么 |
|---|---|---|---|
| 一 | 什么都不用动 | 改内存里的一个变量、加一个日志行 | 无 |
| 二 | 回滚一次写入 | 改工作区内的一个文件、加一条本地记录 | 一份可恢复的副本，或一次幂等的重写 |
| 三 | 修数据，或补偿一个已经生效的动作 | 覆盖了用户数据、执行了不可逆的转换、发出了一个请求 | 补偿操作的设计（不是备份） |
| 四 | 无法撤销 | 已经发出的消息、已经计费的调用、推送出去的代码 | 只能事前判断，事中没有手段 |

第三级与第四级的分界线是"控制权是否还在本机"。第三级的动作已经生效，但效果仍在本系统可以触及的范围内（例如调用了内部服务，可以调它再改回来）。第四级的动作已经离开，代价只能作为业务成本承担。

第二级内部还有一个容易忽略的差别：写一个新文件与覆盖一个已有文件同属第二级，但前者的撤销只需要删掉自己写的东西，后者需要"被覆盖的内容曾经存在过一份"。这个差别在第 3 卷的守卫设计里会变成"要不要问人"的判断依据。

### 1.4 原子性与先写日志：把不可判定的中断变成可判定

一次改动如果包含多个步骤，而进程可能在任意一步之后中断，那么中断点的状态是任意的。先写日志这条规则的作用是把这种"任意中断态"限制成一个可判定的集合。

Gray 与 Reuter 在《Transaction Processing》里把这条顺序列为原子性与持久性的实现前提：在改动实际数据之前，先保证这次改动的记录已经落盘。这样一来，崩溃后的恢复只需要读日志：日志里有记录但数据未完成的，重放。数据完成但提交记录缺失的，回滚。两种情况下恢复的动作都是由日志内容决定的，而不是靠猜。

把它落到本课程的对象上：会话日志本身就是一条"先写日志"的实现。事件先追加到日志，任何派生视图（消息数组、统计）都从日志算。写入过程即使是写到一半被杀，日志里最多出现一条不完整的尾部记录，而它在读取时可以被识别并丢弃——因为记录之间有顺序号，缺口是可见的。

```js
// 无日志的写法：崩溃后无法判断这条记录是否写完
function appendBad(records, rec) {
  records.push(rec)                 // 内存先改
  writeFileSync('log.json', JSON.stringify(records))   // 再落盘：中途被杀就只剩内存里的状态
}

// 先写日志的写法：数据的每个可见状态都能从日志判定
function appendGood(records, rec, nextSeq) {
  appendLine('log.ndjson', JSON.stringify({ seq: nextSeq, ...rec }))  // 先落盘，追加一行
  records.push({ seq: nextSeq, ...rec })                             // 再改内存
}
```

这两段代码的差别不在性能，而在崩溃之后能否判断发生了什么：第一种在"落盘被杀"时留下一个部分写入的文件，而读取端无法区分它是否完整。第二种用追加一行加顺序号的方式，让不完整只可能出现在最后一行，并且能被识别。第 2.7 篇会把这个判断固化成一条不变量，第 3.5 篇会给出恢复算法的具体形式。

### 1.5 迁移：作用对象是已经存在的数据

迁移与普通改动的区别在于它不能靠"同时更新所有调用方"来完成——历史数据不会跟着代码改。因此它引入两个正交的兼容性方向。

向前兼容指旧版本的代码能读新版本写的数据。向后兼容指新版本的代码能读旧版本写的数据。前者决定"能不能回滚"，后者决定"能不能降级与灰度"。一个改动如果只保证其中一个方向，那么它在另一个方向上的失败会在部署策略上变成限制（例如不能灰度、或者不能回滚）。

SQLite 用两个版本号把这件事变得可判定：`PRAGMA user_version` 由应用自己使用，`PRAGMA application_id` 用来标识这份数据属于哪个应用。官方文档建议在迁移前先升级版本号并配合 WAL 使用，这样中断的迁移在下次启动时可以被识别。这套做法的形状与本课程在会话格式上采用的规则一致，三条规则值得逐条记住：

一是只有结构性的变化才允许提升版本号。字段的增删属于结构变化，而文案、顺序、内部数据结构不属于——如果任何改动都升版本，版本号会失去信息量。

二是已经提交的世代不能被移动或覆盖。旧版本产生的数据要保持可读，因此迁移的形态是"新增一个以版本命名的后继"，而不是回写旧数据。

三是前代不意味着回退支持。允许保留与允许降级是两件事，把前者当成后者会让"旧数据仍在"变成一个虚假的安全感。

### 1.6 有界状态：写满时由谁做决定

有容量上限的系统必然要回答"满了怎么办"。三种策略把决定权交给不同的人。

丢弃最旧的：实现替调用方做决定。它的优点是调用方无需处理失败，代价是信息损失不可观测。它适合的场景是可重建的数据（例如缓存），因为丢了可以重算。

拒绝：把决定交回调用方。Hermes Agent 的记忆系统选择了这一条，它的判断是"写满时失败而不是丢弃最旧的"——理由是丢弃让使用者永远不知道自己丢了什么。这个选择的代价是调用方必须写处理逻辑，而没有写好时一次容量耗尽会让写路径整体失败。

合并：实现替调用方做一个更复杂的决定。它比丢弃温和，因为合并保留信息。但它引入了新的问题——合并会产生信息损失（几条压缩成一条），而且合并策略本身是一个业务判断（哪几条该合并、合并后保留什么）。因此契约需要把合并显式建模成一个方法（`merge`），而不是把它藏进 `add` 的失败处理里。

这三者的选择依据是"谁最了解这份数据该丢什么"。缓存场景里实现了解得最清楚（LRU 是通用最优近似），而记忆场景里只有调用方知道哪条记忆重要。把这条判断写成一句话：自动策略适用于"价值函数是通用的"，显式失败适用于"价值函数只有调用方知道"。

### 1.7 快照的两个层次

契约里 `list()` 承诺返回副本，而"副本"有两个层次需要分别兑现：数组本身是新的（改它的长度不影响内部），以及数组的每个元素是新的（改某个元素的字段不影响内部）。只做前者的实现在随手测试里很难被发现，因为测试通常只检查内容而不在拿到快照之后修改它。

两个层次的成本不同：浅复制是 O(n) 的指针复制，深复制是 O(n × 字段数) 的字段复制。对于小对象，两者的差别可以忽略。对于大对象，深复制会成为性能瓶颈，此时正确的做法不是放弃深复制，而是重新审视"为什么调用方需要修改返回值"——如果调用方确实需要修改，那么它需要的是一份可写的数据，而不是容器内部的对象。

这条与 1.4 的所有权承诺是同一件事的两个表述：契约要么承诺返回副本，要么明确声明"不要修改返回值"。前者付出复制成本，后者承担被违反的风险。两者的选择依据是调用方的数量与形态：调用方多且互不相识时选前者，只有一个内部调用方时选后者并写明。

### 1.8 幂等与重放：恢复时遇到"已经开始但没有结果"该怎么办

先写日志解决了"能否判断发生了什么"，但它留下一个必须回答的问题：日志里有一条"某个操作开始"的记录，而它对应的完成记录缺失，恢复时该怎么办。

答案取决于那个操作是否幂等。幂等的操作可以安全重放，因为它执行两次与执行一次的效果相同。非幂等的操作只能被标记为结果未知，并把决定交给上层——因为重放可能造成第二次效果（发了两封邮件、扣了两次费）。Kleppmann 指出，工程意义上的 exactly-once 通常实现为"至少一次投递加上接收端去重"，而去重的依据正是操作自带的唯一标识。

这个结论在本课程的对象上有直接形态：工具执行属于非幂等操作，因此恢复时遇到"开始但无结果"的工具调用，正确处置是标记为结果未知而不是重放。这也解释了 2.1 里为什么要求工具声明幂等性——它是恢复策略的输入，而不是一句给自己看的注释。

> **面试视角**
> **高频问法**："你怎么保证崩溃后数据一致？"
> **高分要点**：按三层回答——先写日志保证崩溃点可判定；权威状态与派生状态分开保证可重建；非幂等操作的恢复要标记而不是重放。三层里第二层最常被忽略，而它正是"重启之后历史对不上"的成因。
> **对应岗位**：后端技术面、Agent 基础设施岗。

### 1.9 两次追问

工程侧的问题是复制成本该由谁承担。返回快照的成本落在容器（每次 `list` 都要复制），不复制而依赖约定的成本落在调用方（它必须记得不改返回值）。判断依据是调用方的数量与它是否可信：多个互不相识的调用方时，把它变成容器的责任更稳妥。只有一个受控调用方时，约定加一句声明更经济。

有一个中间方案值得知道——不可变数据结构（例如持久化列表），它让"副本"与"原对象"共享大部分内部节点，复制成本降到接近常数。引入它的代价是多一层依赖与一套新的写法。

产品侧的问题是有界容器失败时的用户体验。一次显式的 `CapacityError` 对使用者是可解释的：它带着上限与当前值，可以被翻译成"记忆满了，需要清理或扩容"。而一次静默的驱逐是不可解释的：查询返回空，系统无法说明原因。这两者在产品上的差别不是"体验好坏"，而是"能不能解释"——一个无法解释自己行为的系统在出问题时无法被修复，因为没有人知道它做了什么。

### 1.10 一次真实迁移的两种做法

迁移的难点不在改写本身，而在中断。假设要把每条记录的时间戳从毫秒整数改成 ISO 字符串，有两种实现路线，它们对中断的容忍度不同。

就地改写是最直观的一条：遍历全表，逐条把 `at: 1699999999999` 改成 `at: '2023-11-15T02:13:19.999Z'`。它的问题在于改写过程中数据处在混合态，而读取端必须同时认识两种形态。如果读取逻辑写成 `typeof at === 'number' ? new Date(at) : new Date(at)`，那么混合态是可读的。

但一旦某条记录只写了一半（例如进程在序列化时被杀），这条记录既不合法也不再是原来的值，而它没有任何标记表明自己坏了。

双写加回填是另一条路线，它把不可判定的中间态消除掉。第一步是让写入端同时写两种字段（`atMs` 与 `atIso`），读取端优先读新字段、缺失时用旧字段推导——此时新旧代码都能读，且没有混合态问题，因为每条记录要么两者都有，要么只有旧的。第二步是后台按批次回填旧记录，每批完成后记录进度。第三步是所有记录都补齐之后，切换读取路径到只读新字段，并在一次版本提升里声明旧字段废弃。

两条路线的成本差别是实在的：双写方案在迁移期间需要双份字段的存储与额外的写入，读取路径多一层分支，回填期间的读放大也会体现在延迟上。就地改写方案在正常情况下更快，代价是它把所有风险集中在一次不可中断的操作上。

判断该选哪一条的依据不是数据量，而是"这次迁移允不允许中断"。允许中断（例如可以用维护窗口停机，且回滚方式是恢复备份）时，就地改写是可接受的。不允许中断时，只有双写加回填能在任意时刻停下并保持系统可用。这条判断与 1.3 的可逆性分级是同一件事：双写方案把迁移的可逆性从第三级降到第二级，因为它让中间态始终是可读的。

这套做法与 1.5 的三条版本规则配合使用时有一个细节：回填完成的判定标准必须是"所有记录都有新字段"，而这件事无法靠扫描全部数据可靠地确认（新记录会持续写入）。可行的做法是把回填进度与写入时的字段级别一起记入一个元数据表，并在切换读取路径之前校验一次——这类"需要一次性校验的切换"，正是版本号机制存在的理由。

### 1.11 崩溃恢复的算法骨架

先写日志保证了崩溃点可判定，而从这条保证到实际的恢复动作之间还有一个算法。它的骨架只有三步，三者的输入都是日志本身。

第一步是扫描与截断。从日志开头顺序读取，直到遇到第一条不完整的记录为止，把其后的一切丢弃。这一步依赖一个前提：日志是追加写的，因此不完整只可能出现在尾部。如果日志允许中间改写，那么"扫描到错误就停"就不再安全，因为你无法区分"这一条坏了"与"这一条之后都坏了"。识别不完整的方法有三种：定长前缀声明长度、每条记录带校验和、或者用行分隔的 JSON（NDJSON）并以最后一行能否解析为准。

三者的鲁棒性递增，成本也递增。NDJSON 的优势是它能在不引入二进制格式的前提下识别出"最后一行少了一半"。

第二步是判定。对每一条完整记录，看它有没有对应的完成标记。带提交标记的设计里，未提交的改动一律回滚。带"开始"与"结束"成对记录的设计里，只有开始没有结束的那些是待处理项。两种设计的共同点是把"是否完成"变成一个可以直接读取的事实，而不是靠推断。

第三步是处置。已提交的改动重放（使其对当前内存状态生效），未提交的回滚，而对"开始但无结果"的操作则按 1.8 的规则处理：幂等的可以重放，非幂等的标记为结果未知。这一步里最容易出错的是把"重放"理解成"重新执行"——恢复时的重放是把日志里的结果应用到内存状态，而不是再调一次外部服务。一旦做成了后者，恢复本身就成了一个新的副作用来源。

```js
// 恢复骨架：扫描 → 判定 → 处置
function recover(lines) {
  const records = []
  for (const line of lines) {
    let rec
    try { rec = JSON.parse(line) } catch { break }   // 解析失败即到达尾部不完整记录
    records.push(rec)
  }
  const applied = new Map()
  for (const rec of records) {
    if (!rec.committed) continue      // 未提交：不回放（在内存重建里等于跳过）
    if (rec.kind === 'set') applied.set(rec.key, rec.value)
  }
  return applied
}
```

这段骨架省略了内存状态的初始化与待处理项的标记，剩下两点是这一节要传达的：解析失败即停止扫描，以及只有已提交的记录才被回放。真实实现还要处理日志的轮转、压缩点与已应用位置的水位线——那些是 3.5 篇的内容。

恢复算法还缺一个工程细节：水位线。每次启动都从头重放全部日志，在事件数增长之后会成为启动时间的主要部分——十万条事件按每条零点一毫秒的解析成本计约十秒，而其中绝大多数在上一次启动时就已经应用过。水位线的做法是记录"已应用到哪一条"，恢复时从它之后开始，于是启动成本从全部历史降到自上次启动以来的增量。

它的正确性依赖一条与其他规则同源的约束：水位线必须与它所声明的进度在同一次提交里更新。若先更新水位线再应用那批记录，崩溃就会留下一个空洞——水位线声称已应用，而数据里没有。若先应用再更新水位线，崩溃只会导致重复应用，而重复应用对幂等的操作是安全的。两种顺序的失败后果不对称，因此可用的顺序只有一个，这与 3.3 里 `merge` 必须先释放再占用是同一类推理：先做可重复的那一步。


### 1.12 深复制的替代：不可变结构与写时复制

深复制的成本是每次读快照都复制全部字段。对一个有一千条条目的容器，一次 `list()` 要复制一千个对象。如果读取快照的频率是每秒十次，那就是每秒一万次对象分配。这个成本在条目少时看不出来，而它随条目数线性增长。

替代方案是让复制变成结构共享。持久化数据结构的做法是：每一次"修改"都不动原有结构，而是重建从根到被改节点的路径，其余子树由新旧两份共享。以平衡树为例，一次插入需要重建的节点数等于树高，也就是对数级的，而共享的节点数与其规模成正比——一千个元素时，重建约十个节点，而不是复制一千个。

这条性质可以用一个更小的例子看清。把一份有序结构看成 `[A, B, C, D]`，在其中修改 `C` 得到新版本时，新版本与旧版本共享 `A`、`B`、`D` 三个子树，只有根与包含 `C` 的那条路径是新建的。因此一次修改的分配次数取决于结构的深度，而不是元素的个数。这解释了它的适用条件：读快照的频率远高于写入频率时收益最大，因为读取变成了常数的指针返回，而写入的额外分配被读取次数摊薄。

引入它的代价有三项，都需要在决定之前算清。第一是多一层依赖：自己实现一个持久化数据结构不划算，用现成库则引入它的维护风险与版本约束。第二是写法不同：追加操作不再原地修改，而是返回新版本，于是所有写入路径都要改成"接收返回值"的形状，而这类改造会穿过整个调用链。第三是对象的标识不再稳定，凡是依赖引用相等的判断都会变化——这类判断在缓存、去重与变更检测里很常见，而它们失效时通常不会报错。

判断该不该引入的依据是两个比值：读快照频率与写入频率之比，以及条目规模。规模小时深复制本来就不贵，引入结构共享只增加理解成本。写入占主导时，每次修改都要重建路径，收益会转负。写入占主导而调用方又需要频繁修改的场景下，正确的做法不是放弃不可变性，而是换接口——给调用方一个显式的可变写入 API，让"读取用快照、修改用命令"成为两条分开的路径，而不是让返回值既承担读取又承担修改。

这条替代方案不改变契约："返回副本"这条承诺依然成立，变的只是兑现它的成本量级。它是 1.4 那条分工的一个实例——契约说明承诺什么，实现决定用什么代价兑现它，而两者可以分开演进。这也是为什么 `CONTRACT.md` 的第六节把"内部使用的数据结构"明确列为不属于承诺的部分：换一种内部结构不应当影响任何调用方。

### 关于第 10 条的完整论证（有界容器为什么选择失败而不是丢弃）

选这一条的理由需要先排除一个更省事的替代方案。丢弃最旧的实现只需要十几行代码，调用方不需要任何处理逻辑，而且它在"数据可以重算"的场景里完全正确——缓存就是这么做的。因此问题不是"哪个更对"，而是"这份数据的价值函数是不是通用的"。

判断这一点的方法是问两个问题。第一，被丢弃的条目能不能重算。如果不能，丢弃就是永久损失。第二，如果它是永久损失，谁有资格决定丢哪一条。如果这个判断需要业务知识（哪条记忆重要、哪条已经过时、哪条与其他条目重复），那么实现没有资格替调用方做这个决定。

记忆系统在两个问题上都落在"不能自动"的一侧：记忆条目无法重算（它们来自外部输入），而重要性判断依赖使用场景。缓存系统则落在另一侧：缓存条目可以从源数据重算，而 LRU 是对"哪些更可能被再访问"的通用近似。

因此这条决策的完整形式不是"永远选择失败"，而是先判断价值函数是否通用，通用则自动，不通用则显式失败。真实系统里两者常常并存：同一层的缓存自动驱逐，而记忆容器显式拒绝——它们在同一个系统里服务不同的数据。

这条决策的代价必须写清：显式失败要求调用方处理这个错误，而没有处理时一次容量耗尽会让写路径整体失败。缓解方式是让失败信息足够具体（带上 `limit` 与 `current`），并在文档里给出三种推荐的处置（合并、删除、扩容）。失败信息里带着"下一步能做什么"，是把一次中断变成一次可处理事件的关键，这条原则在 2.2 的工具失败设计里会再次出现。

### 关于第 4 条的完整论证（压缩为什么必须作为事件追加）

压缩是第 3 卷的内容，但它的数据形态在这里就要定下来，因为定错之后无法回退。

替代方案有两种。第一种是把压缩结果写回历史（用摘要替换掉那段原始消息），它的好处是读取更快、存储更省。代价是不可逆——被替换掉的那部分永久丢失。第二种是把压缩结果只放在内存里，每次启动重算，它的好处是不占存储。代价是压缩本身可能不确定（依赖模型输出），而重放会得到不同的摘要，于是同一份历史在不同时间呈现出不同的样子。

选定的方案是第三种：压缩产生一条新事件（记录压缩发生在哪个位置、摘要是什么），原始事件全部保留，而派生视图从压缩点往后算。它的存储成本是"原始事件 + 摘要"，比第一种高，比完全不压缩低。

这个方案解决的是三个具体问题。第一，可复现：任何时刻的模型可见内容都能由日志重放得到，因为压缩点与摘要是日志的一部分。第二，可审计：用户问"为什么它当时那么决定"时，可以看到当时用的是哪一版摘要，而不是一个已经无法回溯的派生结果。第三，可演进：压缩策略改变（例如换了摘要模型）之后，历史依然可读，因为旧摘要被完整保留而不是被重新计算覆盖。

它引入的代价是派生逻辑变复杂：派生视图不再等于"全部事件的消息映射"，而是"最后一个压缩点之后的事件 + 压缩摘要"。这个复杂度在 3.3 篇会被正面处理，包括"多个压缩点如何折叠"与"哪些事件在压缩后必须保留"。在数据层面，这条决策的一般形式是：凡是不可逆的信息损失，都不要在一次改写里发生，而要作为一条新记录发生——因为新记录可以被审计、被回滚、被替换成更好的策略。

> **面试视角**
> **高频问法**："有容量上限时你会怎么做？"
> **加分点**：不直接回答"丢弃最旧的"，而是先问价值函数是不是通用的；通用则自动驱逐，不通用则显式失败。这个回答展示的是判断依据而不是结论。

## L3 实现（施工图）

这一篇的产物是 [`homework/ch01-judgment/kit/src/memory.mjs`](../homework/ch01-judgment/kit/src/memory.mjs)，它的契约写在同目录的 `CONTRACT.md` 里。判分器 `tests/t5-build.mjs` 把它拆成八组用例，每组重复三十次，因此下面每一节都标出它对应哪一组。

### 3.1 文件结构

```js
// kit/src/memory.mjs
// ┌─ 错误段 ──────────────────────────────────────────
// │  CapacityError / DuplicateError / NotFoundError / TypeError 的替代
// ├─ 条目段 ──────────────────────────────────────────
// │  Entry 的形状与校验（text 非空）
// ├─ 容量段 ──────────────────────────────────────────
// │  limit / size / 释放与占用
// └─ 快照段 ──────────────────────────────────────────
//    list 的深复制
```

四段的划分依据是"哪一段会因为什么原因被改动"：错误段随契约的错误承诺变化，条目段随 `Entry` 的形状变化，容量段随有界策略变化，快照段随所有权承诺变化。把容量判断散落到各个方法里是这个实现最常见的结构问题，它会导致 `remove` 忘记释放容量、`merge` 在满仓时误判——也就是用例 C 与 D 恰好要抓的两处。

### 3.2 错误段

契约要求五种失败各有其类，并且必须能被 `instanceof` 判断（用例 E）。这一条排除了两种省事写法：用一个 `Error` 加 `name` 字段冒充（`instanceof` 判断不出来），以及只抛 `TypeError`（它无法携带 `limit` 与 `current`）。

```js
export class CapacityError extends Error {
  constructor(limit, current) {
    super(`记忆已满：上限 ${limit}，当前 ${current}`)
    this.name = 'CapacityError'
    this.limit = limit          // 契约要求带这两个字段
    this.current = current
  }
}
```

`text` 为空这一类失败契约要求抛 `TypeError`，它有两个选择：抛原生 `TypeError`，或者抛一个继承 `TypeError` 的自定义类。后者更好，因为它既满足"能被 `instanceof TypeError` 判断"，又能携带说明信息——原生 `TypeError` 的构造函数签名不保证可以传说明，而这一点在不同运行时上行为不同，属于应当回避的不确定性。

错误类带字段这一条值得从调用方的角度再看一遍，因为它决定了错误是"可处置的"还是"只能被记录的"。`CapacityError` 带着 `limit` 与 `current`，于是调用方可以据此选择三条不同的路径：合并（当两条旧记忆可以被压缩成一条时）、删除（当有一条规定不再需要时）、或者扩容（当上限本来就是估的时）。

若这两个字段缺失，调用方拿到的只是一句文本，它能做的只有打印日志并向上抛——同一个失败，带着字段是可处置的，不带字段只是可观测的。

`DuplicateError` 带 `id` 的理由相同：调用方据此可以判断这是"重复写入同一条"（可以安全跳过）还是"两个不同的条目撞了 id"（生成规则有问题）。这两种情况的处置相反，而它们在只有一句错误文本时无法区分。
### 3.3 容量段：三处顺序问题

`add` 里有三个检查，它们的顺序决定了同一次调用在多重违规时报哪个错。契约没有规定顺序，但有一个更合理的默认：先检查能不能做（容量），再检查参数对不对（重复与空文本）。理由是容量问题是调用方需要立即处置的状态（它决定了后续所有写入都会失败），而参数问题是一次性的输入错误。

`remove` 的关键是让容量随之释放（用例 C）。如果容量用一个独立计数器维护，那么 `remove` 必须同时递减它——这是最容易漏的一处，因为它跨了两个方法。更稳妥的做法是让 `size` 由存储本身的长度推导（例如用 `Map` 的 `size` 属性），这样"删除释放容量"不需要任何额外代码，它在结构上就不可能错。这正是讲义 1.3 里那条判据的应用：能不变量就别存它，改成推导。

`merge` 的顺序问题（用例 D）值得单独说明。合并 N 条为一条，净效果是容量减少 N−1，因此它在满仓时也应当成功。而一个直观的实现会这样做：先构造新条目并 `add`，再移除被合并的旧条目。这个顺序在满仓时立刻失败，因为 `add` 的第一步就是容量检查。

```js
// 错误顺序：满仓时在第一步就失败
mergeWrong(ids, text) {
  const merged = this.add({ text, mergedFrom: ids.length })   // ← 满仓时抛 CapacityError
  for (const id of ids) this.remove(id)
  return merged
}

// 正确顺序：先释放，再占用；净效果是容量变宽松
mergeRight(ids, text) {
  const olds = ids.map((id) => this.get(id))
  if (olds.some((e) => e === undefined)) throw new NotFoundError(ids.find((id) => !this.get(id)))
  for (const id of ids) this.remove(id)                        // ← 先释放
  return this.add({ text, mergedFrom: ids.length })            // ← 再占用，此时容量一定够
}
```

这两段代码的差别只有两行顺序，而它决定了一个用例的成败。更重要的是它的性质：错误实现在开发中很难被发现，因为只有在"容量恰好写满"时才会触发，而随手测试通常不会构造那个状态。用例 D 因此必须在满仓状态下跑，而它跑三十次是为了覆盖不同条目数带来的边界差异。

### 3.4 快照段：深复制的落点

`list()` 返回的每一项都必须是副本（用例 G）。实现位置只有一处（`list` 内部），但需要覆盖两层：数组本身用展开或 `slice` 复制，每个元素用对象展开复制。

```js
list() {
  return [...this.#entries.values()].map((e) => ({ ...e }))
}
```

这里的 `...e` 是浅复制，而它对这个 `Entry` 是足够的，因为 `Entry` 的字段都是原始值（字符串与数字）。如果将来给 `Entry` 加一个对象字段，这一行就会变成新的不变量缺口——它是最容易被忽略的一类"前提会变"的问题，也应当写进实现的注释里。

### 3.5 验收判据

下面八组对应判分器的八组用例，每组重复三十次，判定标准是成功率接近 100%。

| 组 | 判据 | 怎么检查 |
|---|---|---|
| A | `add` / `get` / `size` / `list` / `remove` 的基本行为正确 | 依次调用并核对返回值 |
| B | 满仓时 `add` 抛 `CapacityError`，且不丢弃任何已有条目 | 填满后加一条，确认抛错且 `size` 不变 |
| C | `remove` 之后 `add` 立刻成功 | 填满、删除一条、再加一条 |
| D | `merge` 在满仓时成功，且净容量减少 | 填满后合并两条，确认成功且 `size` 减一 |
| E | 五种失败各抛自己的类，且能被 `instanceof` 判断 | 逐个触发并检查类型与字段 |
| F | 任意操作序列下 `size() <= limit` | 随机序列（判分器生成，带固定种子） |
| G | `list()` 的数组与元素都不与内部共享 | 改返回值的数组长度与元素字段，再核对内部 |
| H | `remove` 对不存在的 id 返回 `false` 而不抛错 | 连续两次删除同一个 id |

**第六组是唯一无法靠构造用例覆盖的一组**，因为"任意序列"是一个无限的集合。判分器的做法是用带种子的随机序列跑三十次，而它的鉴别力可以用概率估出来：如果一个缺陷在随机序列下单次运行中有 10% 的概率被触发，那么三十次全部漏掉的概率是 0.9 的三十次方，约 4.2%。如果单次触发概率是 20%，漏掉概率降到约 0.1%。

这解释了"三十次"这个数字的来源：它把单次触发概率在一成以上的缺陷压到 5% 以下的漏检率，而把次数提高到一百只能把这一档压到 0.003%，对更低概率的缺陷仍然无能为力。要覆盖更低概率的缺陷，必须靠有针对性的用例（例如用例 C 与 D 专门构造满仓状态），而不是靠增加随机次数。

### 3.6 实现顺序

按能独立验证的顺序做：

1. 错误段（3.2），先写五个类。它们不依赖其他部分，可以立刻用 `instanceof` 验证。
2. 条目与存储，用 `Map` 存条目，`size` 由它推导。此时用例 A 与 H 应当通过。
3. 容量判断，写在 `add` 里。用例 B 通过。
4. `remove` 与 `merge` 的顺序（3.3），用例 C 与 D 通过。
5. 快照（3.4），用例 G 通过。
6. 跑整套三十次（用例 F），并针对失败的具体序列回看是哪一步的顺序问题；定位方法见 3.7。

### 3.7 随机失败之后怎么定位

随机序列测试的价值在于它能撞上人想不到的路径组合，代价是失败时你手上只有一条错误信息与一个序列。定位流程有四步，而第四步最容易被省略。

第一步是固定种子复现。判分器的种子可以通过环境变量指定，失败之后立刻记下它，然后用同一个种子重跑——如果不能复现，说明失败与时间或内存布局有关，那属于另一类问题（通常是遍历顺序依赖了对象键的插入顺序）。

第二步是把序列缩短。随机序列通常长达数百步，而触发问题往往只需要其中几步的组合。做法是先砍掉前半段看是否仍然失败，再砍掉后半段，反复折半——这一步能把定位时间从小时量级降到分钟量级。

第三步是把缩到最小的序列打印出来。目标是把复现步骤压到十步以内，使得每一条操作都可以被人工检查：哪一步使得容量恰好写满、哪一步用了合并、哪一步读了快照。

第四步是把最小反例固化成一条确定性用例。这一步不能省，因为随机测试的结论无法在下次运行时保证复现——种子变了，路径就变了。把最小序列写成一条固定用例之后，它成为回归防线，而随机测试回到它原本的角色：发现新问题，而不是守住旧问题。

这四步的一般形式适用于所有基于随机化的验证：随机负责发现，确定性负责守住。只做前者的团队会遇到一类典型困境——同一个缺陷被反复发现，每次都要重新定位一遍。

### 3.8 "不属于承诺"的四项为什么值得逐条写出来

`CONTRACT.md` 的第六节列出了四项明确不属于承诺的内容：条目的存储顺序、`id` 的生成规则、内部使用的数据结构、以及 `merge` 后新条目与旧 id 的关系。这一节逐条说明它们为什么被排除，因为在实现与评审时，这四行看起来最像"凑数的话"。

存储顺序被排除，是因为承诺它会限制实现的选择。当前的实现用 `Map`，它的迭代顺序是插入顺序。如果契约承诺了"`list()` 按插入顺序返回"，那么将来为了性能换成哈希表实现时，顺序就不再满足承诺，而那次换实现就变成了一次破坏性变更。反过来，调用方如果确实需要有序读取，正确做法是要求容器提供显式的排序方法，而不是依赖底层容器的偶然顺序。

`id` 的生成规则被排除，是因为承诺它会让调用方依赖格式。一旦契约写明"`id` 是递增整数"，就会有代码按前缀比较、按大小排序、或者解析它的位数——这些用法在换成 UUID 时会全部失效。这里的分界是：唯一性是承诺，格式不是。前者是容器必须保证的性质，后者是实现细节。

内部数据结构被排除，理由与上一条类似，但它多一层作用：它让"实现的可替换性"成为契约的一部分。这一点在本篇尤其相关——1.12 讨论的不可变结构就是这样一次替换，而如果契约承诺了内部结构，那次替换就必须走迁移流程。

`merge` 后新条目与旧 id 的关系被排除，是因为承诺它会锁死合并策略。如果契约承诺"合并后的条目沿用第一个 id"，那么将来想改成生成新 id（例如为了更好地表示这是一条派生结果）就必须走兼容流程。这一项与前三项的区别在于它影响的是行为而不只是形式，因此它更容易被误当成承诺——实现里 `mergedFrom` 字段记录了合并来源条数，而它容易被读成"保留了旧 id 的痕迹"。

这四项的共同形态是同一句话：它们把未来的改动成本从"破坏性变更"降到"内部改动"。写它们的收益不在当下（当下没有调用方会读它们），而在将来——当你想换存储结构、换 id 策略、换合并规则时，那份写明"这些不属于承诺"的文件就是你不需要做迁移方案的理由。按 Hyrum 定律，不写出来的部分会被人依赖。写出来之后，依赖它们的人至少在合同上站不住脚。
### 3.9 契约条款到实现位置的映射

写实现之前先做一次映射，可以避免一类常见失败：读完契约觉得都懂，写完之后发现漏了某条。做法是把契约里的每条承诺标出它落在实现的哪个位置，以及用错时会失败哪一组用例。

| 契约条款 | 实现位置 | 用错会失败 |
|---|---|---|
| 满仓时 `add` 抛 `CapacityError` 且不丢弃 | `add` 开头的容量检查 | B |
| `remove` 之后容量立即释放 | `size` 由存储结构推导，不独立维护 | C |
| `merge` 在满仓时不能失败 | 先释放被合并的条目，再插入新条目 | D |
| 五种失败各有其类且可 `instanceof` | 错误段，不用 `Error` 加 `name` 冒充 | E |
| 任意操作序列下 `size <= limit` | `add` 是唯一的写入入口 | F |
| `list()` 返回的数组与元素都是副本 | `list` 里的 `map` 加对象展开 | G |
| `remove` 对不存在的 id 返回 `false` | `remove` 的返回值语义 | H |
| `text` 为空时抛 `TypeError` | `add` 的参数检查 | E |

这张表的用法是倒过来查：写完之后对着每一行问"它在我的代码里是哪一行"。如果某条承诺找不到对应位置，说明实现漏了它——而它在测试里会表现为某一组用例稳定失败，或者在随机序列下偶发失败。后者更麻烦，因为它说明那条承诺只在特定状态下才被检验。

表里有三行最容易被跳过，也最值得单独记住。第二行是减法：`size` 不独立维护，因为它可以由存储结构推导，而独立维护的计数器在每次删除时都要记得同步。第三行是顺序：合并的净效果是释放容量，所以必须先释放。第六行是层次：复制要覆盖数组与元素两层，只做前者是半成品。

## L4 运行与验证

### 4.1 三层验证

这一篇的验证分三层，它们证明的事情不同。

第一层是契约测试。`node tests/t5-build.mjs` 直接 import 你的实现并调用它，按契约逐组检查，每组重复三十次（`RUNS` 可调，`SEED` 可指定）。

```powershell
node tests/t5-build.mjs                     # 默认 30 次
$env:RUNS='100'; node tests/t5-build.mjs; Remove-Item Env:\RUNS   # 提高次数
```

第二层是对照参考答案。它证明的不是你的实现正确，而是判分器本身是好的。

```powershell
$env:IMPL='../grade/memory.reference.mjs'; node tests/t5-build.mjs; Remove-Item Env:\IMPL
```

参考答案应当稳定拿到满分。如果它拿不到，问题在判分器——这是一个可以被排除的变量，而排除它的成本只有一条命令。

第三层是否定验证。`node grade/negative-check.mjs` 从参考答案出发构造四种违反契约的实现（满仓时丢弃最旧的、`list` 返回浅复制、`merge` 时检查容量、删除后不释放容量），确认判分器把它们全部判为失败。第一层只证明"对的能过"，第三层证明"错的过不了"，而一个只做第一层的验证体系无法排除"判分器太松"这个可能。

### 4.2 判据

做完这一篇的标志有三条。第一，`t5-build` 在三十次重复下成功率接近 100%，并且你能说出它是靠哪一组用例发现的顺序问题（如果一次都没失败，说明你的实现在结构上避开了这类缺陷，例如用 `Map` 推导 `size`）。第二，负向验证的四组全部被抓住。

第三，你能说清 `merge` 为什么必须先释放再占用——这个问题的答案是"净容量减少"，而它是这一篇 L2 第 10 条与 1.6 在实现层的样子。

> **面试视角**
> **高频问法**："你怎么测试一个有并发或顺序敏感的数据结构？"
> **高分要点**：说出"单次通过不等于正确"，并给出量化——单次触发概率一成时，跑三十次的漏检率约 4%，而提高次数对更低概率的缺陷无效，必须靠有针对性的用例覆盖边界状态。

### 5.3 三条容易踩的规则

第一条，`size` 尽量由存储结构推导，不要独立维护一个计数器。独立计数器意味着每个修改存储的地方都要记得同步它，而漏掉任一处都会以"容量释放不正确"的形式暴露，且只在满仓时可见。

第二条，一次改动涉及"先占用再释放"时，先确认净效果。合并的净效果是释放，所以它的顺序必须是先释放。如果写成先占用，满仓时必然失败。

第三条，复制要问清层次。返回快照时先问"调用方会修改它吗"，再决定复制到哪一层。只复制容器是最常见的半成品，而它恰好能通过多数随手测试。

## L9 仍未解决（这一篇自己的缺陷）

| 缺陷 | 后果 | 修法 | 当初为什么这么写 |
|---|---|---|---|
| 只处理单进程的状态，没有跨进程的协调 | 多个进程同时写同一份日志时会互相覆盖 | 引入文件锁或单写者模型（第 5 卷的多会话会涉及） | 本卷的目标是单机闭环，跨进程协调属于规模化阶段 |
| 恢复算法只给了骨架，没有覆盖日志损坏与轮转 | 状态扫描到损坏记录时会整体停止，而真实系统需要区分"尾部不完整"与"中间损坏" | 引入校验和与段文件（3.5 篇），并定义损坏时的处置（拒绝启动还是截断到最后一个完整记录） | 骨架用 NDJSON 的行完整性代替校验和，因为后者要引入二进制格式与额外的读写路径 |
| `merge` 的信息损失没有量化 | 调用方无法判断"合并几条"是否可接受 | 给出合并前后信息量的度量（例如字符数、覆盖的时间跨度） | 度量方式依赖记忆条目的语义，而那是第 4 卷的内容 |
| 有界容器的策略选择缺少实验数据 | "显式失败更好"这条结论来自推理与 Hermes 的设计立场，没有在真实使用中比较过两种策略的后果 | 用一个真实的任务集比较两种策略下的任务成功率与用户干预次数 | 需要长期运行的系统才能收集这类数据 |
| 迁移一节只覆盖了数据格式，没有覆盖"数据与代码同时变" | 当格式与语义同时变化时（例如时间戳单位变化），单一版本号不足以表达 | 引入语义版本与格式版本两个维度 | 单维度在多数场景够用，双维度会让判断复杂化 |
| `list` 的两层复制依赖"Entry 的字段全是原始值"这一前提 | 一旦给 Entry 加一个对象字段，`{ ...e }` 就从深复制退化为浅复制，而不变量 5 会静默失效 | 在 `list` 的实现处写下这条前提，并在修改 Entry 形状时同步检查 | 当前 Entry 的三个字段都是原始值，展开运算足够；而这条前提没有被写下来 |

其中第四条属于数据缺失（结论未经验证），第六条属于覆盖缺失（只讲了代价没讲替代），其余属于边界缺失（本篇限定在单机单进程）。第四条值得特别标记：它的结论"显式失败更好"在推理上是站得住的（可观测性优先），但它在真实系统里的净效果取决于调用方是否写好了处理逻辑——而这个依赖没有数据支撑，因此它在本篇里应当被当作一条有待验证的立场，而不是一条已验证的结论。

### 问题升级练习

模糊问题：「我该怎么设计一个可靠的状态方案？」

升级后的精确问题：

> 状态方案的"可靠"至少包含三件互相制约的事：
> ① 崩溃后能重建（权威状态落盘、派生状态可重算）；
> ② 改动能回退（可逆性分级 + 向前与向后兼容）；
> ③ 空间耗尽时可解释（有界策略 + 显式失败）。
> 前两件制约第三件——为了 ① 需要保留更多原始数据，而它会让 ③ 更早发生。
> 我能不能为这三件事各找出一条**可检查的判据**？
> 特别是：有没有哪一条判据，是**能在一次崩溃演练里被验证的**？

提升点说明：原问题无法回答，因为"可靠"没有共同尺度。升级后的版本做了三件事。第一，把"可靠"拆成三件具体的事，每件都有可观察的形式。第二，指出 ① 与 ③ 之间的制约关系——保留原始数据会让空间更紧张，这解释了为什么它们不能分开决定。第三，要求可检查的判据，并追加以一个更强的问题：哪一条能在崩溃演练里验证。这一问指向的正是先写日志那条规则的可验证形态——杀掉进程再启动，看历史能不能重建。

## L11 系统影响回溯

回看第 0.5 节的三个连锁影响，本篇给出了它们各自的具体形态与一处修正。

连锁 1（状态分类决定崩溃恢复的可行性）在 1.4 里落成了先写日志这条顺序规则，并在 L4 给出了它的验证方式：杀掉进程再启动，看历史能否重建。0.5.3 说"对每一项内存状态，问它在重启后由什么重建"，读完之后这句话可以更准确——要问的不是"由什么重建"，而是"重建的输入是不是权威状态"。如果重建依赖了另一个派生结果，那么它在形式上能重建，实际上不可靠。

连锁 2（可逆性判断决定改动前的准备）在 1.3 的铁三角里给出了第三级与第四级的分界：控制权是否还在本机。而本篇补充的一点是，第三级需要的不是备份而是补偿——备份对已经生效的动作无效，因为它们不能把外部世界恢复原状。这个区别在 1.1 的可逆性分级里没有出现，因为那一篇的场景是本地的。

连锁 3（有界容器把信息损失从自动变成显式）在 1.6 与 L2 第 10 条里展开，并给出了判断依据：价值函数是否通用。而读完之后要修正 0.5.3 的一处表述：它把这个连锁说成"让系统可调试的一种主要手段"，更准确的说法是它是把不可观测的降级换成可观测的失败，而后者同样有代价——代价由调用方承担，且它必须以"写好处理逻辑"为前提。L9 第四条把这个前提列为本篇未验证的部分。

一处需要修正的预判：第 0.5.2 的下游依赖表把"有界容器的行为选择"标为对 4.1 与 3.3 都强。读完之后这个判断要分开：对 4.1（记忆）确实是强依赖，因为记忆的价值函数不通用。对 3.3（上下文压缩）则要弱一些，因为上下文窗口的溢出处理已经有一套更细的策略（保住最近的、保住系统指令、按同一性判断信息价值），而"有界容器"这个视角在那里只是一个骨架，不是判据来源。

通向下一篇的桥。 第一篇讲完了判断，本书从这里进入实现。1.5 的产物是一个本地容器，而第 2 卷要造的是整个最小闭环：模型层、工具系统、容器与依赖注入、事件与扩展点、作用域、装配、会话日志。

本篇给它留了两样东西。第一是三处必须落盘的对象：模型调用的结果、工具调用的结果、以及它们之间的事件。2.1 与 2.2 分别要回答"一次调用的结果长什么样才能被存下来"（这决定了它们的类型必须是可 JSON 往返的）。第二是一条会在 2.3 与 2.7 反复出现的规则：注册是 effect，每一个注册动作都带一个配对的撤销动作——它是"可逆性"从数据层面向生命周期层面的推广。

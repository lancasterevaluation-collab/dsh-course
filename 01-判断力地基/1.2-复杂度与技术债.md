## 读完这一篇你会知道什么

1. **必要复杂度与偶然复杂度**：重写最多只能回收偶然的那部分——算例里占 30%。
2. 债的四象限：有意/无意 × 鲁棒/鲁莽。"无意且鲁莽"的优先级是 22.00，而"有意且鲁棒"是 10.00。
3. 债务利息：算例里一笔债的利息是 2 小时/周，还债窗口是 30 周。
4. 封装优先于重构：把扇入从 4 降到 1，还债窗口从 30 周延长到 120 周（延长 90 周）。
5. 合并重构的经济性：三笔债分别做要 120 小时，合并做只要 90 小时（省 30 小时）。
6. 耦合怎么量：扇入 + 扇出，以及为什么高扇入的模块要优先封装。
7. 工业界怎么做：SonarQube 的"债天数"、行为分析、可读性评审、童子军规则。
8. 学术界的经典结论：Brooks 的本质/偶然复杂度、Parnas 的信息隐藏、McCabe 的圈复杂度、以及债的学术定义。

## 一、为什么"代码很乱"不是结论

### 1.1 说不出代价

"这个模块很乱"——但说不出乱在哪。**结果是它永远排在优先级列表的最后**，因为没人能证明它值得修。

### 1.2 一言不合就重写

"不如重写"——但没人算过重写能收回多少。**算例给出上限：偶然复杂度只占 30%，重写最多回收 30%。**

### 1.3 所有债一视同仁

有意欠的债（为了赶上线）和无意欠的债（没意识到）走同样的处理流程。**前者可能是正确的取舍，后者才是问题。**

这三件事分别对应：**要量化、要算上界、要分类。**

## 二、复杂度与债的分类

### 2.1 复杂度的两种

Brooks 在《人月神话》里区分了两种复杂度：

| 类型 | 来源 | 能否通过重写消除 |
|---|---|---|
| **本质复杂度** | 问题本身固有的（业务规则、并发、分布式） | **不能** |
| **偶然复杂度** | 我们选择的技术方案带来的 | 能 |

算例实测：偶然复杂度占 30% 时，重写收益上界是 **30**（必要复杂度 70 保留）。

这条数字的含义：重写最多拿到三成收益，而它同时会丢掉全部已验证的行为。**所以"重写"很少是划算的**——除非偶然复杂度的占比确实很高（例如技术栈已经过时）。

### 2.2 债的四个象限

Fowler 依据两个维度把债分成四类：

|  | **鲁棒**（有意识地控制） | **鲁莽**（不加控制） |
|---|---|---|
| **有意** | 为了赶上线，明确记下并计划偿还 | 明知有问题还是照做 |
| **无意** | 当时不知道有更好的做法，但结果可接受 | 不知道自己在做什么 |

算例实测的分类与优先级：

| 类型 | 分类结果 | 优先级 |
|---|---|---|
| 有意且鲁棒 | `deliberate-prudent` | **10.00** |
| 无意且鲁棒 | `inadvertent-prudent` | — |
| **无意且鲁莽** | — | **22.00** |

**为什么"无意且鲁莽"优先级最高（22.00 对 10.00）**：它既没有控制，也没有意识——你不知道它在那里，它还在持续产生利息。

实践含义：**先找出"不知道自己欠了什么"的部分**。这靠度量，不靠感觉。

## 三、怎么做

### 3.1 耦合度：扇入与扇出

耦合度用两个方向的依赖数来衡量：

- **扇入（fanIn）**：有多少模块依赖它。
- 扇出（fanOut）：它依赖了多少模块。
- 耦合度：两者之和。

```js
// 耦合度：扇入越多，改动的影响面越大
export function coupling(node, edges) {
  const fanIn = edges.filter(([, to]) => to === node).length
  const fanOut = edges.filter(([from]) => from === node).length
  return { node, fanIn, fanOut, coupling: fanIn + fanOut }
}
```

算例实测：

| 模块 | 扇入 | 扇出 | 耦合度 |
|---|---|---|---|
| **util** | **3** | 0 | **3** |
| api | 1 | — | — |
| core | 1 | — | — |

**扇入 3 意味着三个模块依赖它**——改它的风险是改一个扇入为 1 的模块的三倍。

**高扇入 + 零扇出**（像 `util`）是一个典型形态：它谁都不依赖，但所有人都依赖它。这种模块的稳定性直接决定整个系统的稳定性，所以它最值得优先封装。

### 3.2 圈复杂度与分档

圈复杂度（McCabe）衡量一个函数里独立路径的数量，可以近似理解为"判定点数量 + 1"。

```js
// 圈复杂度分档：不同档位对应不同的处置
export function complexityClass(cc) {
  if (cc <= 10) return 'easy'
  if (cc <= 20) return 'needs-split'
  return 'must-split'
}
```

算例实测：

| 判定点数 | 圈复杂度 | 分档 |
|---|---|---|
| 7 | **8** | easy |
| — | 15 | needs-split |
| — | 25 | **must-split** |

为什么圈复杂度可用：它近似等于"要覆盖全部路径需要写多少个测试用例"。**cc = 25 的函数意味着至少 25 条独立路径**——这是测试成本的直接估计。

### 3.3 债务利息与还债窗口

债的量化方式不应该是"值多少钱"，而应该是**它每周消耗多少小时**。

设债的"摩擦系数"为 $f$（每次碰到它多花的时间比例）、每周触碰它的时间为 $c$，则利息为：

$$
i = f \times c
$$

算例实测：$f = 4$、$c = 0.5$ 时，**利息 $i = 2$ 小时/周**。

**还债窗口**（利息吞掉全部偿还能力所需的时间）：

$$
T = \frac{R}{i}
$$

算例实测：偿还能力 $R = 60$ 小时/周、$i = 2$ 时，**窗口 $T = 30$ 周**。

读法：30 周之后，团队的全部时间都会被这笔债吃掉（如果债的利息继续以复利增长）。**这是一个具体的倒计时，比"这个模块很乱"有说服力得多。**

### 3.4 封装优先于重构

**这是本篇最有价值的一节。** 债务利息 $i = f \times c$ 里有两个因子，而重构只改善其中一个：

| 手段 | 改善哪个因子 | 成本 |
|---|---|---|
| **重构** | 降低 $f$（每次碰到它少花时间） | 高（要改内部实现） |
| **封装** | 降低 $c$（减少触碰它的次数与范围） | 低（只改接口边界） |

算例实测：**把扇入从 4 降到 1**（即让三个调用方走一个统一的封装层，不再直接依赖内部），还债窗口从 30 周延长到 120 周——延长了 90 周。

为什么封装这么有效：它把"每次改动都要面对全部复杂度"变成"只在封装层面对一次"。**接口是一道闸门，它把 $c$ 从 4 降到 1。**

实践建议：**在重构之前先问"能不能只加一层封装"。** 加封装的成本通常是一个接口文件的工作量，而它的收益是把倒计时延长三倍。

### 3.5 合并重构：为什么能省时间

如果几笔债在同一个区域，分开做会有重复的"进入成本"（重新理解代码、搭环境、跑测试）。

算例实测：

| 方式 | 成本 |
|---|---|
| 三笔债分别重构 | **120 小时** |
| 三笔债合并重构 | **90 小时**（省 30 小时） |

注意合并后的副作用：合并后还债窗口变成 **15.0 周**——因为合并意味着在这个窗口内必须完成，它把三笔分散的债变成一个有明确截止的工程。

读法：合并做更省时间，但**截止更硬**。所以要选"确实能在这个窗口内做完"的批次。

### 3.6 重写的收益上界

见 2.1 的结论：重写只能回收偶然复杂度那一部分。

决策判据：

$$
\text{重写收益} \le \text{偶然复杂度占比}
$$

算例里这个比例是 **30%**。

实践做法：如果要论证"应该重写"，必须证明偶然复杂度占比很高。**判据是"换个技术方案，问题是否真的消失"**——如果业务规则、并发、集成这些复杂度还在，重写后它们一样存在。

### 3.7 死代码：最便宜的债

**删除是最好的重构**——它同时降低 $f$ 与 $c$，成本却接近零。

算例给出的删除候选是 `dead1, dead2`：**无引用、无测试、无文档提及的代码**。

**如何确认一段代码是死的**（三个证据缺一不可）：

1. **静态检索无引用**（注意动态调用、反射、配置里的字符串引用）。
2. 运行时无调用（通过观测工具覆盖一段时间，包含周期性任务）。
3. 无人声称需要（向相关方确认，包括外部客户）。

第三个最容易漏：对外发布的接口看起来"没人用"，但可能有外部消费者。

## 四、特殊情况与处理技巧

| 情况 | 为什么 | 处理 |
|---|---|---|
| "代码乱"但排不上优先级 | 没有量化 | 算利息（小时/周）与还债窗口 |
| 想重写 | 高估收益 | 先算偶然复杂度占比 |
| 重构没时间做 | 只考虑重构 | 先加封装层，成本低得多 |
| 债越还越多 | 利息是复利 | 设置"还债时间占比"上限（30%） |
| 删了还有人在用 | 动态引用或外部消费者 | 三证据齐备才删。先标记废弃 |
| 圈复杂度压不下来 | 业务规则本身复杂 | 拆分成多个小函数，而不是消灭判定点 |
| 度量工具报警太多 | 阈值一刀切 | 只对"高扇入 + 高复杂度"的交集行动 |
| 高扇入工具模块人人依赖 | 被认为"改不得" | 加稳定接口层，内部随便改 |

最后一条值得展开：高扇入模块的常见困境是"谁都不敢改它"。**解法不是不改，而是先把它拆成"稳定接口 + 可变实现"。** 接口稳定后，内部实现可以自由重构。

## 五、工业界的做法（可照做）

### 5.1 度量工具与它们的口径

| 工具 / 实践 | 度量什么 | 值得学的点 |
|---|---|---|
| **SonarQube** | "债天数"（修完要多少天）、代码味道、覆盖率 | 把债换算成**时间**而不是金额 |
| **行为分析（CodeScene）** | 变更频率 × 复杂度 | **热点 = 常改 + 复杂**，优先修热点 |
| **可读性评审（Google）** | 人工评审代码风格与可维护性 | 把可读性当作可评审对象 |
| **童子军规则** | 每次改动顺手改善一点 | 让还债成为日常而非项目 |
| **模块化 / 限界上下文** | 按业务边界切分 | 边界与团队结构对齐（Conway 定律） |

"热点分析"特别值得学：它把优先级从"哪里最复杂"改成"**哪里又复杂又常改**"。

为什么这个改动重要：复杂但从不改的代码不产生利息（$c$ 接近 0）。**利息 $i = f \times c$ 的两个因子缺一不可。**

### 5.2 参数与阈值起点

| 度量 | 常见阈值 | 依据 |
|---|---|---|
| 圈复杂度 | 10 / 20 分档 | 对应测试用例数量的量级 |
| 函数长度 | 50 行左右 | 与圈复杂度相关 |
| 扇入 | 超过 5 需要封装层 | 影响面控制 |
| 文件变更频率 | 与复杂度交叉看 | 热点判定 |
| 债天数 | 与迭代容量比较 | 决定排期 |
| 测试覆盖率 | 核心路径近 100% | 覆盖率不是目标，是证据 |

一条使用建议：**不要按单条阈值报警**。有效做法是看交集——高复杂度且高频变更且低覆盖率。三者同时满足才是真热点。

### 5.3 一份可落地的实施清单

1. **耦合图**：算出每个模块的扇入扇出，列出高扇入清单。
2. 复杂度扫描：圈复杂度分档，超过 20 的函数进队列。
3. 热点分析：变更频率 × 复杂度，取前 10 个。
4. 利息记账：为每个热点估一个"小时/周"，算出还债窗口。
5. 封装优先：能加接口层解决的，不做内部重构。
6. 批处理：同区域的债合并做，减少进入成本。
7. 死代码清理：三证据齐备后删除，先标记废弃一个版本。
8. 还债预算：每个迭代固定比例（如 20%）用于还债。
9. 度量入 CI：新代码不得让关键指标变差（护栏思路，见 3.6）。
10. ADR：有意欠债时记录原因与偿还条件。

## 六、学术界的结论

### 6.1 Parnas 的信息隐藏

Parnas 在 1972 年的论文 *On the Criteria To Be Used in Decomposing Systems into Modules* 提出了模块划分的正确依据：

> **模块划分的依据不是处理步骤，而是"要隐藏的决策"。**

它的直接推论：一个好的模块边界应当**把最可能变化的决策藏在里面**——这样变化的影响就限制在模块内部。

这就是 3.4 里"封装优先"的理论依据：加一层封装层，本质是**把"内部实现会变"这个决策隐藏起来**。调用方不再依赖它，于是 $c$ 下降。

对 agent 系统的启示：工具接口、模型提供商、存储后端，这些都是"最可能变化的决策"。**把它们藏在接口后面，而不是散落在调用点。**

### 6.2 McCabe 圈复杂度

McCabe（1976）把程序的控制流图里独立路径的数量定义为圈复杂度：

$$
\text{cc} = E - N + 2P
$$

（$E$ 为边数，$N$ 为节点数，$P$ 为连通分量数。）

它的价值在于与测试的直接关联：圈复杂度等于"要达到路径覆盖所需的测试用例数量的下界"。**所以它同时是复杂度度量与测试成本估计。**

局限：它只看控制流，不看数据复杂度与模块间耦合。所以现代实践会与耦合度量一起用。

### 6.3 CK 度量与其他面向对象度量

针对面向对象代码，Chidamber 与 Kemerer（1994）提出的度量被广泛使用：

| 度量 | 含义 | 高值的含义 |
|---|---|---|
| **WMC** | 类内方法加权复杂度 | 类太大 |
| **CBO** | 与其他类的耦合数 | 耦合过紧 |
| **LCOM** | 方法间缺乏内聚 | 类职责不单一 |
| **DIT / NOC** | 继承深度 / 子类数 | 层次过深或过宽 |

共同思想：**用一组数代替"这个类设计得好不好"的主观判断。**

### 6.4 技术债的学术定义与经验研究

Cunningham 在 1992 年提出"技术债"这个隐喻，原意是**"现在赶工，以后要还"**。

后续的学术工作把它形式化，并做了大量经验研究：

- **债与缺陷率的相关性**：多项研究发现高复杂度模块的缺陷密度显著更高。
- 债的演化：债会随时间的推移加速累积（与 7.2 的复利模型一致）。
- 债的分类学：Fowler 的四象限是应用最广的分类。

一条被反复验证的经验结论：**代码复杂度的分布是重尾的**——少数模块贡献了大部分复杂度与缺陷。这解释了为什么"只修前 10 个热点"是有效策略。

### 6.5 软件熵

 Lehman 的软件演化定律里有一条：**系统会随修改而熵增**（复杂度持续上升），除非主动投入来对抗。

这与债的复利模型是同一件事的两种表述：不主动还债，债的利息就会持续累积，直至吞掉全部容量。

工程含义：需要一个**持续**（而不是阶段性）的投入机制。这就是"还债预算固定比例"的理论依据。

## 七、理论：两个经典结论

### 7.1 债务利息与还债窗口

$$
i = f \times c, \qquad T = \frac{R}{i}
$$

算例实测（$f = 4$、$c = 0.5$、$R = 60$）：

| 量 | 值 |
|---|---|
| 利息 $i$ | **2 小时/周** |
| 还债窗口 $T$ | **30 周** |
| 三笔债利息之和 | 6 小时/周 |
| **封装后（$f$ 从 4 降到 1）** | **120 周** |

关键洞察：$T$ 与 $i$ 成反比，所以**把 $i$ 降四倍，窗口就延长四倍**。而 $i$ 有两个因子，封装降 $c$ 的收益与重构降 $f$ 相同，但成本低一个数量级。

### 7.2 重写的收益上界

$$
0 \le \text{收益} \le \text{偶然复杂度占比}
$$

算例给出 30% 的具体值。

为什么这是上界而不是估计值：重写**不会**消除本质复杂度（业务规则、并发、集成都是问题固有的）。所以收益不可能超过偶然部分。

**实践中它常常远低于这个上界**，因为重写过程中会引入新的偶然复杂度（团队不熟悉新栈、低估迁移成本）。

## 九、练习

### 第一题：算一笔债的账

场景：一个工具模块被 5 个地方直接依赖。团队每次改它平均多花 3 小时，每周大约有 0.4 周会碰到它（即约 2 小时）。团队每周可用于还债的时间是 40 小时。

要求：

- 算出利息与还债窗口。
- 如果加一层封装把"直接依赖数"从 5 降到 1，估算新的还债窗口（说明你的假设）。
- 说明为什么这个改动比"重构模块内部实现"更值得先做。

### 第二题：给出重写与否的判据

场景：一个 3 万行的服务，团队想重写。列出的理由是"代码太乱、老技术栈、新人上手慢"。

要求：

- 逐条判断这些理由属于本质复杂度还是偶然复杂度。
- 给出一个可以量化偶然复杂度占比的方法（说明要采集什么数据）。
- 基于 7.2 的上界，给出你的建议与依据。

## 十、算例

算例实现了本篇的全部度量与模型。

```powershell
cd D:\dsh-course

node examples/test_sa16_debt.mjs   # 数字回归断言
```

它做到的事：

- 扇入最高的模块（util 扇入 3）与它的耦合度。
- 圈复杂度（7 个判定点得到 8）与三档分类。
- **利息率（$f=4$、$c=0.5$ 得到 2 小时/周）与还债窗口（30 周）**。
- 封装后窗口延长（$f$ 从 4 降到 1 得到 120 周，延长 90 周）。
- 三笔债分别重构（120 小时）与合并重构（90 小时，省 30 小时）的对照。
- 债的四象限分类与优先级（无意且鲁莽 22.00 对 有意且鲁棒 10.00）。
- 重写收益上界（偶然占 30% 得到 30）。
- 死代码候选清单。

这一篇只要记住一句：技术债要算**利息（小时/周）与还债窗口**，而最划算的动作往往是加一层封装——它把"每次触碰面对全部复杂度"变成面对一次，算例里这一步把窗口从 30 周延长到 120 周。

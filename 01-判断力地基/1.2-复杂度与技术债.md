## 本篇新词

- 必要复杂度（essential complexity） 指问题本身固有的复杂度。换一种实现方式也不会减少它，因为它来自需求。
- 偶然复杂度（accidental complexity） 指实现方式引入的、与需求无关的复杂度。它可以被消除，代价是一次重构。
- 技术债（technical debt） 指为绕开一个结构问题而采取的工作方式。它有本金（绕开时的节省）与利息（后续每次触及的额外代价）。
- 债的四分类 指按"是否有意"与"是否鲁莽"两个维度划分的四类债。四类的处置方式不同：有的还，有的留。
- 耦合（coupling） 指两个模块之间相互依赖的程度。它是"改动会波及多远"的直接来源。
- 圈复杂度（cyclomatic complexity） 指一个控制流图里线性独立路径的数量，它衡量"要理解这段逻辑至少要跟踪多少条路径"。
- 还债窗口（repayment window） 指债的累计利息超过重构成本的时间点。它与 1.1 的临界时间是同一个量。

## 一、【设计原因】

### 1.1 缺陷一：改动成本与你做的事不成比例

改一个判断条件，结果要动五个文件。改动量本身很小，成本的来源是耦合：那一个判断散落在若干处，且每处的上下文不同。

这说明成本不与"改动的大小"成正比，而与"改动的影响面"成正比（与 1.1 的影响面同源）。

### 1.2 缺陷二：那些没人敢改的地方

系统里有一些文件，团队里没人愿意碰。它们通常有三个特征：没有测试、依赖它的东西多、逻辑分支密。

这三个特征都是可度量的：覆盖率、扇入、圈复杂度。也就是说，"没人敢改"可以被转成三个数字。

### 1.3 缺陷三：同一件事在系统里有多套说法

"当前会话"这个概念在四个模块里各有一套表示，且它们的含义略有差异。表现是改动一处之后，其他地方的行为不一致。

这是偶然复杂度最典型的形态：同一概念多份表示。 它的代价不只是一次改动变贵，而是每次改动都要判断"哪几份表示需要同步"。

### 1.4 缺陷四：你知道有债，但决定不了还不还

知道某处结构不好，但每次讨论都停在"要不要重构"。

问题在于缺少两个数：这笔债每周的利息，以及重构一次的成本。 有了它们，决策是 $R/i$ 的比较（1.1 命题 1.1.4），不需要争论。

### 1.5 由此确定的设计目标

1. 复杂度要与代码量分开：长不等于复杂。
2. 复杂度要可度量：耦合、扇入、圈复杂度作为代理量。
3. 债要有本金与利息两个数：只有本金无法决策。
4. 四类债要分开处置：有的还，有的留，有的要立即还。

**本节要点**

- 改动成本与影响面成正比，与改动大小无关。
- "没人敢改"可以转成覆盖率、扇入、圈复杂度三个数字。
- 同一概念多份表示是偶然复杂度的典型形态。
- 债还不还的争论源于缺少利息与本金两个数。
- 四条目标：与代码量分开、可度量、两个数、四类分开处置。

## 二、【直觉】

### 2.1 房间里的东西

一个房间里堆着两类东西：房子自带的（承重墙、管道、窗）与住进去之后添的（临时座椅、纸箱、备用电源）。

第一类动不了，它是房子的固有属性——对应必要复杂度。第二类可以清理，清理的收益是空间变大——对应偶然复杂度。

两条观察值得记下：

- 必要复杂度不会因为换了家具而减少。换一种布局方式，管道还是在那个位置。
- 偶然复杂度会自我繁殖。纸箱越多，越没地方放东西，于是更多东西堆在地上。

::: keypoint 反直觉点
**"重写一遍"通常只能消除偶然复杂度，而必要复杂度会原样保留。** 因此重写的收益上界是"当前偶然复杂度所占的比例"，而它往往低于预期——这是大型重写项目最常见的误判来源。
:::

### 2.2 一笔有本金的账

借一笔钱，当时省下了工序（本金），之后每次触及都要多花一点（利息）。

关键的一点：利息是复利的直觉版——它不是按金额算，而是按"触及次数"算。 一个结构问题被十个功能触及，就要付十次利息。而重构只付一次本金。

### 2.3 一个数字直觉

设某处结构问题：每次触及多花 0.5 小时，平均每周触及 4 次。重构一次需要 60 小时。

- 每周利息：$4 \times 0.5 = 2$ 小时。
- 还债窗口：$60 / 2 = 30$ 周。

同一个系统里如果还有三四处这样的结构问题，它们的利息会叠加（每周 6 至 8 小时）。这个量级接近一个人的一部分工作产出——这就是"系统越改越慢"的算术形态。

**本节要点**

- 必要复杂度换布局也不会减少，偶然复杂度会自我繁殖。
- 重写的收益上界是偶然复杂度所占比例，低于直觉。
- 债的利息按触及次数算，不是按金额。
- 每周 2 小时利息、60 小时本金时，还债窗口 30 周。多处叠加可接近部分人力。

## 三、【严格】

### 3.1 定义

::: theorem 定义 1.2.1（复杂度分离）
系统的总复杂度可分解为

$$
C_{\text{total}} = C_{\text{essential}} + C_{\text{accidental}} .
$$

$C_{\text{essential}}$ 由需求决定：改变实现方式不改变它。$C_{\text{accidental}}$ 由实现方式决定。

**分离的操作判据**：把系统换成另一种合理的实现方式，若某部分复杂度仍然存在，它属于必要。否则属于偶然。
:::

::: theorem 定义 1.2.2（耦合）
给定模块集合 $M$ 与依赖关系 $E$，模块 $m$ 的**扇出**与**扇入**分别为

$$
\mathrm{out}(m) = |\{n : (m, n) \in E\}|, \qquad \mathrm{in}(m) = |\{n : (n, m) \in E\}| .
$$

模块 $m$ 的**耦合度**定义为 $\mathrm{cp}(m) = \mathrm{in}(m) + \mathrm{out}(m)$。**扇入比扇出更危险**：它决定改动会波及多远。
:::

::: theorem 定义 1.2.3（圈复杂度）
对控制流图 $G = (V, E)$，**圈复杂度**为

$$
\mathrm{CC}(G) = |E| - |V| + 2 .
$$

它等于图中线性独立路径的数量，也等于代码中判定点的数量加一。
:::

::: theorem 定义 1.2.4（债的本金与利息）
绕开结构问题 $d$ 时省下的工作量为**本金** $P_d$。此后每次触及该问题多付出的代价为单次利息 $c_d$，单位时间内触及 $f_d$ 次，则**利息率**

$$
i_d = f_d \cdot c_d .
$$

债 $d$ 在时长 $t$ 内的累计代价为 $P_d^{\text{(saved)}} - i_d t$ 的净值形式，其中 $P_d^{\text{(saved)}}$ 是当初省下的量。
:::

::: theorem 定义 1.2.5（债的四分类）
按两个维度划分：

- **是否有意**：当初就知道在绕开（有意）还是没意识到（无意）。
- **是否鲁棒**：绕开方式在压力下会崩溃（鲁棒）还是不会（鲁莽）。

四类为：有意且鲁棒、有意且鲁莽、无意且鲁棒、无意且鲁莽。**处置方式不同**：有意且鲁棒的可以长期保留，无意且鲁莽的必须立即处理。
:::

::: theorem 定义 1.2.6（还债窗口）
债 $d$ 的**还债窗口**为

$$
t_d^{*} = \frac{R_d}{i_d},
$$

其中 $R_d$ 是重构成本。当债的预期存在时间超过 $t_d^{*}$ 时，重构更划算。
:::

### 3.2 命题

::: theorem 命题 1.2.1（重构的收益上界）
重写的收益不超过 $C_{\text{accidental}}$ 被消除后带来的成本下降。若 $C_{\text{essential}}$ 在重写后保持不变，则

$$
\Delta_{\text{benefit}} \le c \cdot C_{\text{accidental}} ,
$$

其中 $c$ 是单位复杂度的成本系数。

**证明.** 重写改变实现方式，因此只影响 $C_{\text{accidental}}$（由定义 1.2.1，$C_{\text{essential}}$ 不随实现方式改变）。收益来源于复杂度的下降，故不超过偶然复杂度所对应的成本。

↓ **为什么能这么写？** 收益只能来自被改变的那部分，而重写不改变必要复杂度。

$\blacksquare$

::: keypoint 这条结论解释了重写项目的常见误判
**重写不消除必要复杂度。** 一个系统的复杂度若七成来自需求本身，重写最多省下三成——而重写的代价通常远超三成的节省。**先估算偶然复杂度占比，再决定是否重写。**
:::

::: theorem 命题 1.2.2（圈复杂度等于判定点数加一）
对单入单出的控制流图，$\mathrm{CC}(G) = D + 1$，其中 $D$ 是判定点（出度大于一的节点）的数量。

**证明.** 对单入单出控制流图，欧拉公式给出 $|E| - |V| + 2 = D' + 1$ 的形式，其中 $D'$ 是使图连通的额外边数，而在控制流图里每个判定点贡献恰好一条额外边。

↓ **为什么能这么写？** 控制流图的连通性由判定点引入的额外路径保证，两者数量对应。

$\blacksquare$

**推论**：**"这段逻辑有多难跟"可以数判定点**——`if`、`while`、`case`、`&&`、`||` 各算一个。这是本篇所有度量里最容易手工完成的。
:::

::: theorem 命题 1.2.3（扇入决定改动的验证成本）
设模块 $m$ 的扇入为 $\mathrm{in}(m)$。则改动 $m$ 时必须重新验证其全部依赖方，验证成本与 $\mathrm{in}(m)$ 同阶。

**证明.** 改动 $m$ 的行为可能影响任何依赖它的模块。保证正确性的验证必须覆盖这些依赖方的使用路径，数量不少于 $\mathrm{in}(m)$。

↓ **为什么能这么写？** 验证必须覆盖受影响集合，而受影响集合的大小由扇入决定。

$\blacksquare$

**推论**：**"没人敢改"的定量形式是高扇入**。降低扇入（抽出接口、反转依赖）是让这些模块重新可改的直接手段。
:::

::: theorem 命题 1.2.4（利息率与触及频率成正比）
$i_d = f_d c_d$，故降低触及频率与降低单次代价的效果相同。

**证明.** 由定义 1.2.4，$i_d$ 是两者的乘积。乘积对两个因子对称。

↓ **为什么能这么写？** 乘积形式决定了两者的对称性。

$\blacksquare$

**工程含义**：**"把绕开方式封装起来"能降低 $f_d$**——原来触及十次的地方，封装后只触及一次。这是低成本的还债方式，不需要重构整个结构。
:::

::: theorem 命题 1.2.5（四类债的处置优先级）
设债的期望额外损失为 $\mathrm{loss} = \Pr[\text{崩溃}] \cdot L$，其中 $L$ 是崩溃的代价。则：

$$
\text{无意且鲁莽} \succ \text{有意且鲁莽} \succ \text{无意且鲁棒} \succ \text{有意且鲁棒} ,
$$

按处置优先级排列。

**证明.** 鲁莽的债有概率导致崩溃，其期望损失含 $\Pr[\text{崩溃}] \cdot L$。鲁棒的债不含该项。无意的债还因无人知晓而在讨论中被忽略，使风险持续存在。按期望损失由大到小排列即得该序。

↓ **为什么能这么写？** 优先级由期望损失排序给出，而鲁棒性决定损失项是否存在。

$\blacksquare$
:::

::: theorem 命题 1.2.6（多笔债的利息叠加，但重构非叠加）
若系统有 $k$ 笔债，利息率之和为 $\sum_j i_j$。而合并重构的成本 $R_{\text{total}} \le \sum_j R_j$。

**证明.** 利息是按时间累积的代价，各笔相互独立，故可加。重构成本方面，合并处理时存在共享的准备与验证工作，故合并成本不超过分别重构之和。

↓ **为什么能这么写？** 利息是加性的（分别发生），而重构有可共享的固定成本。

$\blacksquare$

**推论**：**同一区域的多笔债应当合并处理**——它们的利息相加，而重构成本相减。
:::

### 3.3 本节要点

**本节要点**

- 复杂度可分为必要与偶然，分离判据是"换实现后是否仍存在"（定义 1.2.1）。
- 扇入比扇出更危险，它决定改动的验证成本（定义 1.2.2、命题 1.2.3）。
- 圈复杂度等于判定点数加一，可手工数（命题 1.2.2）。
- 重写的收益上界是偶然复杂度所占比例（命题 1.2.1）。
- 债的利息率是频率与单次代价的乘积，两者对称（命题 1.2.4）。
- 四类债的处置优先级由期望损失排序（命题 1.2.5）。
- 多笔债的利息叠加，重构成本不叠加（命题 1.2.6）。

## 四、【回到直觉】

- **定义 1.2.1 说的**：问"换一种写法，这部分复杂度还在吗"。在，是必要的。不在，是偶然的。
- **命题 1.2.1 说的**：重写之前先估偶然复杂度的占比。占比不高就别重写。
- **命题 1.2.2 说的**：数判定点就知道一段逻辑有多难跟。`&&` 也算一个。
- **命题 1.2.3 说的**：高扇入就是"没人敢改"的定量形式。抽出接口、反转依赖能降低它。
- **命题 1.2.4 说的**：不一定非要重构。**把绕开方式封装起来**，触及频率就降了，这是低成本做法。
- **命题 1.2.5 说的**：最该处理的是"不知道自己在绕开、且压力下会崩"的那类债。
- **命题 1.2.6 说的**：同一区域的债要一起还——利息相加而成本相减。

**本节要点**

- 换实现后仍存在的是必要复杂度。
- 重写前估偶然占比。
- 数判定点估跟随难度。
- 高扇入 = 没人敢改。
- 封装能降触及频率，不必大重构。
- 优先处理"无意且鲁莽"的债。
- 同区域的债合并还。

## 五、【工具箱】

### 5.1 圈复杂度的计算

按命题 1.2.2，数判定点：`if`、`else if`、`while`、`for`、`case`、`catch`、`&&`、`||`、三元运算符各算一个，加一即得。

**阈值参考**：十以下易读，十到二十需要拆分，二十以上必须拆分。阈值本身随团队而定，**重要的是同一个团队用同一套阈值**。

### 5.2 耦合与扇入扇出

依赖图上的扇入扇出用一次遍历算出，代价 $O(|V| + |E|)$。

**排序看**：按扇入降序看前几名，它们就是"改动最贵的地方"。

### 5.3 还债窗口

按定义 1.2.6 计算 $t_d^{*} = R_d / i_d$。

**三个数的来源**：$c_d$ 从代码评审记录或提交历史估算，$f_d$ 从版本控制统计触及次数，$R_d$ 由实现者给出估计。**三者都不精确，但量级足够支撑决策。**

### 5.4 封装降频

若把绕开方式封装到一个函数里，触及频率从 $f_d$ 降到 $f_d' \le f_d$，新的还债窗口变为 $R_d / (f_d' c_d)$，它更长——**即封装把还债的紧迫性推后了**。

代价是一次小重构（通常远小于 $R_d$）。

### 5.5 删减的效果

若某段代码的调用方为零，删除它的收益是**同时消除其偶然复杂度与它对扇入的贡献**。

**检验方法**：从入口做可达性分析，不可达的即为候选。**删除不需要论证**——它与 1.1 的"退役站"对应。

**本节要点**

- 圈复杂度靠数判定点，阈值团队内统一。
- 按扇入降序找"改动最贵的地方"。
- 还债窗口的三个数都可从记录中估算。
- 封装降频能推后还债紧迫性，代价远小于重构。
- 删除是最彻底的简化，且不需要论证。

### 7.2 度量段

测量段给出两个量：每个模块的扇入扇出，以及每段逻辑的圈复杂度。

```js
// 定义 1.2.2 / 命题 1.2.3：扇入扇出与耦合度。扇入决定改动成本
export function coupling(nodes, edges) {
  const fanOut = new Map(nodes.map((n) => [n, 0]))
  const fanIn = new Map(nodes.map((n) => [n, 0]))
  for (const [from, to] of edges) {
    fanOut.set(from, fanOut.get(from) + 1)
    fanIn.set(to, fanIn.get(to) + 1)
  }
  return nodes.map((n) => ({
    node: n,
    fanIn: fanIn.get(n),
    fanOut: fanOut.get(n),
    coupling: fanIn.get(n) + fanOut.get(n),
  }))
}

// 按扇入降序取前几名——它们就是"改动最贵的地方"
export function riskiest(nodes, edges, top = 5) {
  return coupling(nodes, edges).sort((a, b) => b.fanIn - a.fanIn).slice(0, top)
}

// 命题 1.2.2：圈复杂度 = 判定点数 + 1
export function cyclomatic(decisionPoints) {
  return decisionPoints + 1
}
```

### 7.3 定价段

定价段把债折算成钱与时间：利息率、还债窗口，以及合并后的成本。

```js
// 定义 1.2.4 / 1.2.6：利息率与还债窗口
export function interestRate(touchesPerWeek, costPerTouch) {
  return touchesPerWeek * costPerTouch
}

export function repaymentWindow(refactorHours, touchesPerWeek, costPerTouch) {
  return refactorHours / interestRate(touchesPerWeek, costPerTouch)
}

// 命题 1.2.4：封装降频——触及频率下降后还债窗口变长
export function afterEncapsulation(refactorHours, touchesPerWeek, costPerTouch, encapsulatedTouches) {
  const before = repaymentWindow(refactorHours, touchesPerWeek, costPerTouch)
  const after = repaymentWindow(refactorHours, encapsulatedTouches, costPerTouch)
  return { before, after, extendedBy: after - before }
}

// 命题 1.2.6：多笔债的利息叠加，合并重构成本不叠加
export function portfolio(deBts, mergedRefactorHours) {
  const totalInterest = deBts.reduce((s, d) => s + interestRate(d.touchesPerWeek, d.costPerTouch), 0)
  const sumSeparate = deBts.reduce((s, d) => s + d.refactorHours, 0)
  return {
    totalInterest,
    sumSeparate,
    mergedRefactorHours,
    saving: sumSeparate - mergedRefactorHours,
    window: mergedRefactorHours / totalInterest,
  }
}
```

### 7.4 处置段

处置段决定还、留、封装还是删。分类与优先级各由一个函数给出。

```js
// 命题 1.2.5：四类债的处置优先级（期望损失由大到小）
export function debtPriority(debt) {
  const crashTerm = debt.collapsesUnderLoad ? debt.crashCost * debt.crashProbability : 0
  const base = debt.intentional ? 1 : 2 // 无意的更危险：无人知晓
  return base * 10 + crashTerm
}

export function classifyDebt({ intentional, robust }) {
  if (intentional && robust) return 'deliberate-prudent'
  if (intentional && !robust) return 'deliberate-reckless'
  if (!intentional && robust) return 'inadvertent-prudent'
  return 'inadvertent-reckless'
}
```

### 9.2 失败模式

**（1）检查放在装载期（L9 位置放错）。** 复杂度体检只做一次（例如立项时），此后结构变了而清单没更新。表现是"体检时没问题的地方后来成了瓶颈"。修正：把体检绑定到结构变更，而不是日历。

**（2）前提会变（L9）。** 命题 1.2.3 的验证成本以"依赖图完整"为前提。隐式依赖（动态注册、反射）不在图里，实际扇入高于算出值。修正：显式登记隐式依赖，否则扇入偏低。

**（3）把代码量当复杂度。** 长文件被当问题，而真正的问题是耦合与分支。

**（4）只看扇出。** 改动成本由扇入决定，扇出高的模块自成一类，不一定贵。

**（5）重写而不估偶然占比。** 收益低于预期，且必要复杂度原样保留。

**（6）只有本金没有利息。** 债还不还的讨论无法收敛。

**（7）忽略"无意"的债。** 它们无人知晓，因此永远排在讨论之外，而它们的期望损失最高。

**（8）不封装直接重构。** 花了重构的成本，而封装本可以先用低成本推后问题。

**（9）不做删除候选分析。** 不可达代码永久留驻，持续贡献偶然复杂度。

**（10）多笔债分别重构。** 放弃合并带来的成本节省。

**本节要点**

- 决策表覆盖 11 种情形。
- 失败模式十条，前两条是位置放错与前提会变。
- 最隐蔽的是"忽略无意的债"——它们不进讨论但损失最高。

## 十、仍未解决

- **必要与偶然的实际划界。** "换一种实现"的说法在操作上有弹性——换得越彻底，越多的复杂度会显得非必要。
- **圈复杂度的适用范围。** 它对命令式控制流有效，对声明式与数据驱动代码给出的数字意义有限。
- **利息的估算误差。** $f$ 与 $c$ 都从记录估算，且触及的定义带主观性。
- **阈值的跨团队可比性。** 同一套阈值在不同团队的含义不同，跨团队比较复杂度数值意义有限。
- **重构成本的估计偏差。** 实现者给出的 $R_d$ 普遍偏低（规划谬误），而 $t_d^{*}$ 对它就敏感。
- **债的相互作用。** 两笔债在同一区域时，利息可能不是简单相加——它们可能互相加剧。

**本节要点**

- 必要与偶然的划界有弹性。
- 圈复杂度对声明式代码意义有限。
- 利息估算带主观性。
- 阈值跨团队不可比。
- 重构成本普遍被低估。
- 同区域的多笔债可能互相加剧。

## 十三、只记一句话 + 记忆锚点

只记一句话：

> **系统越改越慢是因为债在按触及次数收利息，而重写永远消不掉那部分由需求本身带来的复杂度。**

本篇的所有结论都能从这一句话推出来：说"债按触及次数收利息"，就有 $i = f c$ 与还债窗口。说"重写消不掉必要复杂度"，就有必要与偶然的分离与重写的收益上界。再加上扇入、圈复杂度与四类债，就得到完整的复杂度判断框架。

如果读完只记得一句话，就记它。其余细节都可以由它推回来。

**记忆锚点**

- **两类复杂度**：必要的（换实现仍在）、偶然的（换实现可消）。
- **两个数**：本金（当初省下的）与利息（每次触及多花的）。
- **两个方向**：扇入比扇出危险。合并还债利息相加、成本相减。
- **三个数字**：$R=60$、$i=2$ 时窗口 30 周。封装把 $f$ 从 4 降到 1 后窗口变成 120 周。七个判定点给出圈复杂度 8。
- **一条纪律**：重写之前先估偶然复杂度占比。

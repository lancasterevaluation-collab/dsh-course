## 一、为什么"通读一遍"没用

### 1.1 读了三天，说不出一句话

有人花三天读完一个 3 万行的服务，然后说"大概能看懂了"。**问他"缓存失效时会怎样"，答不上来。**

### 1.2 先改最复杂的

一个模块圈复杂度最高，于是被列为第一优先。改完之后发现——**它一个月才被碰一次**，改它几乎没有收益。

### 1.3 改动波及面靠记忆

"我觉得不会有别的地方用到"。上线后发现三个下游坏了。

这三件事分别对应：**要有目的、要按热点排序、要用检索而非记忆。**

## 二、从代码里取出结构信息

读代码的产出不是"我懂了"，而是**一组可以写下来的结构事实**：

| 要取出的信息 | 用来回答 |
|---|---|
| 依赖图 | 谁依赖谁，有没有环 |
| 不稳定性 | 谁该稳定、谁可以随便改 |
| 热点 | 先改哪里 |
| 隐藏度 | 模块的边界划得对不对 |
| 波及面 | 改一处会牵连谁 |
| 模块卡片 | 别人接手时要看的那一页 |

判断标准：**如果你读完代码只能说出"大概懂了"，那等于没读。**能写下来才算读出来了。

## 三、怎么做

### 3.1 依赖图与不稳定性

**不稳定性**衡量一个模块"容易被影响"的程度：

$$
I = \frac{\text{扇出}}{\text{扇入} + \text{扇出}}
$$

- $I \to 0$：几乎不依赖别人，但很多人依赖它 → **稳定**。
- $I \to 1$：依赖很多人，但没人依赖它 → 不稳定。

```js
// 不稳定性：0 表示稳定（被依赖多），1 表示不稳定（依赖多）
export function instability(node, edges) {
  const fanIn = edges.filter(([, to]) => to === node).length
  const fanOut = edges.filter(([from]) => from === node).length
  const total = fanIn + fanOut
  return total === 0 ? 0 : fanOut / total
}
```

算例实测：

| 模块 | $I$ | 含义 |
|---|---|---|
| core | **0.50** | 中间位置 |
| ui | **1.00** | 最不稳定，可以随便改 |
| util | **0.00** | 最稳定，所有人都依赖它 |
| dead | 0.00 | 无人依赖也无人引用 |

"逆流边数 = 0"：算例里没有"从稳定方指向不稳定方"的依赖边。**逆流边是设计问题的直接信号**——它意味着一个应该稳定的模块依赖了一个频繁变化的模块。

实践判据：**依赖应该流向稳定的一侧。** 如果 `core` 依赖了 `ui`，那么每次改界面都可能要动核心逻辑。

### 3.2 热点分析：为什么不是先改最复杂的

**热点 = 变更频率 × 复杂度。**

实现如下。

```js
// 热点：变更次数与复杂度的乘积，用于排序改动优先级
export function hotspot(changes, complexity) {
  return changes * complexity
}
```

算例给出的两组排序完全不同，这是本篇最重要的对照：

| 模块 | 变更次数 | 复杂度 | 热点分 |
|---|---|---|---|
| **compressor** | **100** | 25 | **2500** |
| router | 24 | 12 | 288 |
| codec | 9 | **45** | 405 |

算例打印的排序是：热点 `compressor(100) > router(24) > codec(9)`，复杂度 `codec(45) > compressor(25) > router(12)`，**热点倍数是 11.1**。

读法：`codec` 是最复杂的（45），但一个月只改 9 次。`compressor` 复杂度只有 25，却改了 100 次。**改 `compressor` 的收益是改 `codec` 的十几倍。**

为什么这个区分重要：复杂度不产生利息，**复杂度乘以变更频率才产生利息**（与 1.2 的 $i = f \times c$ 是同一个模型）。一个又复杂又从不变的模块，是一份安静的债。

### 3.3 隐藏度：暴露面与职责面

Parnas 的信息隐藏原则给了一个可度量的判据：**暴露出去的东西不应多于它承担的职责**。

$$
\text{隐藏度} = 1 - \frac{\text{暴露面}}{\text{职责面}}
$$

算例实测：

| 暴露面 | 职责面 | 隐藏度 |
|---|---|---|
| 12 | 6 | **−1**（暴露是职责的两倍，边界失控） |
| 3 | 6 | **0.50**（藏住了一半） |

读法：隐藏度为负意味着**这个模块把内部细节泄露出去了**——它的调用方知道的事比它自己该负责的还多。此时任何内部改动都会破坏调用方。

怎么算暴露面：导出的函数、类型、常量、以及任何被外部访问的字段。**每一次"临时导出一下"都在增加暴露面。**

### 3.4 波及面与测试覆盖

**波及面 = 依赖该模块的全部模块（传递闭包）。**

算例实测：改 `core` 的波及面是 `core, api, ui`（3 个），其中**带测试的比例是 0.67**。

这条比例是本篇最该在改动前查的数：波及 3 个模块而只有 2 个有测试，意味着**有 1 个模块会在你不知情的情况下被破坏**。

实践做法：改动前算波及面，然后对照测试覆盖。**覆盖不到的波及点，要么补测试，要么人工验证。**

### 3.5 目的句：一次只问一件事

读代码前必须写下一个**具体的问题**（目的句），而不是"读一下这块"。

```js
// 目的句校验：必须是一个可以回答的具体问题
export function checkGoal(sentence) {
  if (!sentence || sentence.length < 8) return { ok: false, reason: '目的句过短或缺失' }
  if (!/[？?]|怎么|为什么|是否|会不会/.test(sentence)) return { ok: false, reason: '目的句不是问题' }
  return { ok: true }
}
```

算例实测：

| 目的句 | 结果 |
|---|---|
| "这个改动会不会影响缓存？" | `{ok: true}` |
| "读代码" | `{ok: false, reason: "目的句过短或缺失"}` |

为什么这条规则有效：一个具体问题会让阅读路径大幅收窄。**回答"缓存失效时会怎样"只需要追一条调用链**，而"读懂这个服务"需要读一切。

推荐的目的句模板：

- 如果 X 失败，会发生什么？
- 改 Y 会波及谁？
- 这个状态是谁写的、谁读的？
- 这个超时是从哪一层传下来的？

### 3.6 模块卡片：读代码的产出

读完之后要留下一张卡片，算例给出的字段是：

```
职责、对外暴露、依赖、被依赖、约束清单、已知债
```

六个字段的分工：

| 字段 | 回答 |
|---|---|
| 职责 | 它为什么存在 |
| 对外暴露 | 调用方能看到什么 |
| 依赖 | 它需要谁 |
| 被依赖 | 谁需要它 |
| 约束清单 | 用它时必须遵守什么（顺序、并发、配额） |
| 已知债 | 已知的问题与计划 |

"约束清单"是卡片里最容易被漏、也最有价值的字段：它记录的是"文档里没写但你必须知道"的事，例如"调用前必须先初始化"、"这个函数不是线程安全的"。

## 四、特殊情况与处理技巧

| 情况 | 为什么 | 处理 |
|---|---|---|
| 读完说不出来 | 没有目的句 | 先写一个具体问题 |
| 先改了最复杂的 | 按复杂度排序 | 按热点（频率 × 复杂度）排序 |
| 漏掉下游 | 靠记忆判断波及面 | 用检索/调用图算传递闭包 |
| 依赖成环 | 循环引用 | 先解开环（见 1.1 的拓扑排序） |
| 改了核心模块到处坏 | 逆流依赖 | 让依赖流向稳定一侧 |
| 模块越用越难用 | 暴露面持续增加 | 收敛导出面，内部实现隐藏 |
| 动态引用查不到 | 反射、配置字符串、依赖注入 | 用运行时观测补充静态检索 |
| 卡片写成了文档复述 | 抄了注释 | 只写"用的时候必须知道的事" |

最后一条值得强调：模块卡片不是文档的副本。**它的价值在于记录那些"代码里看不出、只有踩过坑才知道"的约束。**

## 五、工业界的做法（可照做）

### 5.1 工具与它们回答的问题

| 工具 | 回答 | 值得学的点 |
|---|---|---|
| **CodeScene** | 热点、知识地图、变更耦合 | **按热点排优先级**，而非按复杂度 |
| **Sourcegraph** | 跨仓库检索与引用 | 影响面用检索确认，不靠记忆 |
| **IDE / LSP** | 调用层级、类型定义、引用查找 | 调用层级 + 引用列表就是依赖图 |
| **依赖分析工具** | 模块依赖、循环检测 | 环是最该先修的 |
| **知识地图** | 谁最熟悉哪块代码 | 找对人比读对代码更快 |

"知识地图"的思路特别值得学：在动手改一个模块前，**先找最熟悉它的人问 10 分钟**，比读 3 小时代码更快。

### 5.2 评审的重心

Google 的代码评审实践里有一份广为人知的检查清单，它的重心值得照抄：

| 检查项 | 关注什么 |
|---|---|
| 设计 | 这块代码该出现在这里吗 |
| 功能 | 行为符合意图吗，边界处理了吗 |
| 复杂度 | 能不能更简单 |
| 测试 | 测试正确且有用吗 |
| 命名 | 名字表达了意图吗 |
| 注释 | 注释解释了"为什么"吗 |
| 风格 | 一致吗 |
| 文档 | 需要更新的文档更新了吗 |

注意"设计"排在第一：评审首先要问"这段代码该不该存在"，而不是"它写得对不对"。

### 5.3 读一个陌生代码库的顺序

一条经过验证的顺序（**每次只回答一个问题**）：

1. **入口在哪**：进程从哪启动、请求从哪进来。
2. 数据长什么样：核心数据结构与它们的生命周期。
3. 边界在哪：与外界交互的地方（网络、磁盘、子进程）。
4. 状态在哪：谁是真相源（见 1.5）。
5. 怎么测的：测试文件告诉你这块代码的预期行为。
6. 改过哪里：版本历史告诉你哪些地方脆弱。

第 6 条常被忽略：**一个文件的历史改动频率，是它脆弱程度的直接指标**。

### 5.4 一份可落地的实施清单

1. **目的句**：读之前先写出要回答的问题。
2. 依赖图：用工具或检索生成，检查环与逆流边。
3. 不稳定性：标出最稳定与最不稳定的模块。
4. 热点表：变更频率 × 复杂度，取前 10。
5. 隐藏度：检查暴露面是否大于职责面。
6. 波及面：改动前算传递闭包，并对照测试覆盖。
7. 模块卡片：六个字段，重点是约束清单。
8. 知识地图：找出每个模块最熟的人。
9. 动态补充：静态检索查不到时用运行时观测。
10. 历史：改动前看版本历史的高频区。

## 六、学术界的结论

### 6.1 Martin 的依赖设计原则

Robert Martin 把 Parnas 的思想（见 1.2）转成了可检查的依赖规则：

| 原则 | 内容 | 可检查的形式 |
|---|---|---|
| **无环依赖原则（ADP）** | 依赖图不能有环 | 拓扑排序无环 |
| **稳定依赖原则（SDP）** | 依赖必须指向更稳定的方向 | 逆流边数为 0 |
| **稳定抽象原则（SAP）** | 稳定模块应当抽象 | 稳定性与抽象度成正比 |

这三条共同给出一个可度量的架构判据：`逆流边数 = 0`（算例里正是这个结果）。

"稳定抽象原则"值得展开：一个**稳定**（很多人依赖）且具体（不改就没法扩展）的模块是最糟的组合——因为它稳定到不能改，又具体到必须改。解法是把它抽象化（接口化），这样实现可以变而接口不变。

### 6.2 Lakos 的物理设计

Lakos 在《Large-Scale C++ Software Design》里区分了逻辑设计与物理设计，并给出一条重要的经验结论：

> **物理依赖（编译期依赖）应当远小于逻辑依赖。**

原因：物理依赖决定了**修改的传播范围**——一个头文件改一行，所有包含它的文件都要重编译（在 C++ 里），在 JavaScript 里则是需要重新理解。

对 agent 系统的启示：工具定义、类型定义这些"被到处导入的东西"，**应当最小化。** 每增加一个导出，就增加一处未来的修改成本。

### 6.3 程序理解研究

软件工程领域对"人怎么读懂程序"有专门的研究（program comprehension），主要结论包括：

- **自顶向下**（从架构到细节）与自底向上（从代码到抽象）两种策略并用。
- 从熟悉的部分入手（借助已有知识），再向外扩展。
- 用假设驱动：读代码时不断形成"我猜这里是…"的假设，然后用检索验证。

"假设驱动"是最高效的读法：先猜（"缓存应该在这里失效"），再去验证（搜函数名、看调用链）。**猜错也有价值**——它排除了一条路径。

### 6.4 认知负荷理论

认知心理学里的**认知负荷**理论区分三种负荷：

| 类型 | 来源 | 能否降低 |
|---|---|---|
| **内在负荷** | 问题本身的复杂度 | 不能（与 1.2 的本质复杂度对应） |
| **外在负荷** | 表达方式带来的额外负担 | **能**（这正是设计要解决的） |
| **相关负荷** | 用于构建理解的投入 | 应当保护 |

它对设计决策的直接含义：目标是**降低外在负荷**——命名清晰、结构一致、减少需要同时记住的变量。"更聪明的写法"如果增加了外在负荷，就不是优化。

## 七、理论：三条设计原则

### 7.1 不稳定性与依赖方向

$$
I = \frac{f_{\text{out}}}{f_{\text{in}} + f_{\text{out}}}
$$

算例实测：`ui` 为 1.00、`core` 为 0.50、`util` 为 0.00，**逆流边数 0**。

可检查的判据：对每条依赖边 $A \to B$，应满足 $I_A \ge I_B$（不稳定方依赖稳定方）。**违反这条的边就是逆流边。**

### 7.2 热点优先级

$$
\text{优先级} = \text{变更频率} \times \text{复杂度}
$$

算例实测：`compressor` 的乘积是 `codec` 的 **11.1 倍**，尽管 `codec` 复杂度更高。

这条公式修正了一个常见直觉：复杂度是"静态的债"，变更频率是"债被触碰的频率"。**两者相乘才等于利息。**

### 7.3 隐藏度

$$
\text{隐藏度} = 1 - \frac{\text{暴露面}}{\text{职责面}}
$$

算例实测：暴露 12 / 职责 6 得到 **−1**（边界失控），暴露 3 / 职责 6 得到 0.50。

判据：**隐藏度小于 0 时，这个模块的边界需要重新划。** 此时调用方掌握的信息已经超过了模块自身的职责范围。

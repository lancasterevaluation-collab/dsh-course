## 一、为什么接口会静默地坏

### 1.1 签名没变，行为变了

一个函数依然接收两个参数、依然返回数组。**但它从"保持顺序"变成了"顺序未定义"**。调用方依赖顺序，于是在某个时刻开始偶发错误。

### 1.2 加了一个"必填"参数

参数看起来是可选的（有默认值），但代码里在某些输入下会要求它。**原本合法的调用（传 `null`）现在抛错**——这是一次破坏性改动，而签名表面没变。

### 1.3 提前下线了旧接口

团队按"平均迁移时间"定了 6 周的弃用窗口，但有一个调用方需要 20 周。**它被静默地跳过了。**

这三件事分别对应：**后置条件、前置条件、弃用窗口。**

## 二、契约的四个部分

一个完整的接口契约有四部分，缺任何一部分都会留下"看不见的破坏面"：

| 部分 | 内容 | 缺了会怎样 |
|---|---|---|
| **前置条件** | 调用方必须保证什么 | 实现方要处理非法输入 |
| **后置条件** | 实现方保证什么 | 调用方无法预期结果 |
| **不变量** | 调用前后始终成立什么 | 状态被意外改动 |
| **副作用** | 除了返回值还发生了什么 | 重复调用出问题、并发出错 |

算例的契约校验给出两种结果：

| 情况 | 结果 |
|---|---|
| 四部分齐备 | `true` |
| 缺不变量 | `["不变量"]` |

**校验的产出不是布尔值，而是"缺了哪些"的清单**——这才可执行。

## 三、怎么做

### 3.1 契约四要素

实现如下。

```js
// 契约：四要素齐备才可用于判断破坏性
export function validateContract(contract) {
  const required = ['precondition', 'postcondition', 'invariant', 'sideEffects']
  return required.filter((key) => !(key in contract) || contract[key] === undefined)
}
```

四要素在代码里的典型写法：

| 要素 | 写在哪 | 例子 |
|---|---|---|
| 前置条件 | 文档 + 入参校验 + 类型 | "id 必须是非空字符串" |
| 后置条件 | 文档 + 测试 | "返回的数组按时间升序" |
| 不变量 | 文档 + 断言 | "调用前后计数器不变" |
| 副作用 | 文档 | "会写入缓存"、"会消耗一次配额" |

"副作用"这一项最常被漏：它决定了**调用方能不能重试**（见 3.1 的重试与幂等）。一个没有写副作用的接口，调用方无法判断重试是否安全。

### 3.2 隐式依赖面

如果契约只写了两类（例如只有前置与后置），那么**未写明的部分就成了隐式依赖**——调用方只能靠猜。

算例实测：契约只写两类时，隐式面有三项：

```
副作用、时序、资源
```

三项各自的危害：

| 隐式项 | 调用方会误以为 | 实际可能 |
|---|---|---|
| **副作用** | 纯函数，可以随便调 | 写磁盘、发请求、改全局状态 |
| **时序** | 可以并发调用 | 必须串行，或者有顺序要求 |
| **资源** | 无限调用 | 有配额、有连接数上限、有内存限制 |

"资源"这一项对 agent 系统尤其重要：工具调用有速率限制与成本，**如果不写进契约，调用方会以为什么时候调都行。**

### 3.3 判断破坏性：用反例而不是直觉

判断"这次改动是否破坏兼容"的可靠方法是**找反例**：

> 存在一个调用，它在旧版本下合法且行为为 A，在新版本下行为为 B（或不再合法）。

```js
// 破坏性判定：找出一个"旧版合法、新版不同"的调用
export function findBreaking(change, probes) {
  for (const call of probes) {
    const before = change.before(call)
    const after = change.after(call)
    if (before.ok && (!after.ok || before.value !== after.value)) {
      return { breaking: true, call, reason: before.ok && !after.ok ? '前置被加强' : '可观察行为改变' }
    }
  }
  return { breaking: false, call: null, reason: '未找到反例' }
}
```

算例实测：

| 改动 | 结果 | 原因 |
|---|---|---|
| 加必填参数（原合法调用含 `null`） | `{breaking: true, call: {n: null}}` | **前置被加强** |
| 签名不变而行为改变 | `{breaking: true}` | 可观察行为改变 |
| 无改动 | `{breaking: false, call: null}` | 未找到反例 |

为什么用反例而不是直觉：直觉会把"加个可选参数"判为安全，而**只有遍历合法输入的集合，才能发现"原本合法但现在不合法"的那一个**。

实践做法：把 probes 建成一组**典型的合法调用**（含边界值：`null`、空数组、超大输入、并发调用）。这组 probes 本身就是接口的回归测试。

### 3.4 替换兼容的三条条件

如果要**用新实现替换旧实现**（而不是改接口），需要满足三条：

| 条件 | 方向 | 含义 |
|---|---|---|
| **前置减弱** | 新的 ≤ 旧的 | 新实现接受的范围不能更小 |
| **后置加强** | 新的 ≥ 旧的 | 新实现保证的不能更少 |
| **不变量保持** | 相同 | 不变量不能丢 |

实现如下。

```js
// 替换兼容：前置可减弱、后置须加强、不变量不能丢
export function replaceable(oldSpec, newSpec) {
  return {
    preconditionWeaker: newSpec.preconditionSubsetOf(oldSpec),
    postconditionStronger: oldSpec.postconditionSubsetOf(newSpec),
    invariantsKept: oldSpec.invariants.every((inv) => newSpec.invariants.includes(inv)),
  }
}
```

算例实测：

| 情况 | 结果 |
|---|---|
| 三条都满足 | `true` |
| 削弱后置 | `{preconditionWeaker: true, postconditionStronger: false, invariantsKept: true}` |
| 丢失不变量 | `false` |

**这三条合起来就是 Liskov 替换原则的可检查形式**（见 6.2）。

记忆方式：**前置可以放宽（对调用方更宽容），后置应当收紧（对调用方更保证），不变量不能丢。**

算例还验证了两条方向的判据：**前置加强判定为 `true`（破坏）**、后置削弱判定为 `true`（破坏）、后置加强判定为 `false`（不破坏）。

### 3.5 弃用窗口：取最慢的调用方

弃用一个旧接口时，窗口长短取决于**所有调用方的迁移时间**。

这里有一个极易犯的错误：

| 算法 | 结果 |
|---|---|
| **取最大值** | **20 周** |
| 取平均值 | 9.3 周（2 / 6 / 20 的平均） |

算例实测：三个调用方的迁移时间分别是 2、6、20 周，**窗口与平均值之比是 2.14**。

结论：**窗口必须取最大值。** 平均值意味着"有一半调用方到期还没迁完"，而其中最慢的那个会被静默跳过。

两个极端情形：

| 情形 | 窗口 |
|---|---|
| 无调用方 | **0 周**（可以立即删除） |
| 有一个外部调用方且无法确认 | 无限期（只能标记废弃，不能删） |

### 3.6 语义化版本：什么算破坏性

**主版本.次版本.修订号** 的语义：

| 变更 | 版本位 | 例子 |
|---|---|---|
| **破坏性** | 主版本 | 加必填参数、改返回结构 |
| **向后兼容的新增** | 次版本 | 加可选参数、加新函数 |
| **兼容的修复** | 修订号 | 修 bug、改文档 |

算例实测：破坏性改动后主版本是 **2.0.0**。

**实践难点在于判断"是否破坏性"**——这正是 3.3 的找反例方法的用途。语义化版本不能靠感觉给，要靠 probes 跑出来。

## 四、特殊情况与处理技巧

| 情况 | 为什么 | 处理 |
|---|---|---|
| 签名没变但行为变了 | 契约里没写后置条件 | 把"顺序""精度""幂等性"写进后置 |
| 加"可选"参数却变必填 | 前置被加强 | 用 probes 找反例 |
| 调用方依赖了内部实现 | 暴露面过大 | 收敛导出面（见 1.3 的隐藏度） |
| 弃用窗口太短 | 用了平均值 | 取所有调用方的最长迁移时间 |
| 侧效应没写 | 契约缺副作用项 | 明确写"会写什么、会消耗什么" |
| 新实现更快但语义不同 | 只比较了性能 | 用 3.4 的三条条件检查 |
| 类型检查过了但运行时出错 | 类型只覆盖前置的一部分 | 把后置也纳入测试 |
| 有外部调用方 | 无法确认迁移时间 | 只能标记废弃，不设删除日期 |

最后一条是真实世界的常态：对外发布的接口**通常不能删**，只能废弃。设计时就要假设"发布即永久"。

## 五、工业界的做法（可照做）

### 5.1 兼容性检查的工程手段

| 手段 | 检查什么 | 用在哪 |
|---|---|---|
| **语义化版本** | 版本号与改动类型匹配 | 所有公开包 |
| **API 兼容性检查工具** | 对比两次构建的公开签名 | CI 门禁 |
| **契约测试** | 调用方与实现方对契约的理解是否一致 | 微服务 |
| **Schema 校验** | 数据结构是否兼容 | 消息队列、API |
| **Feature Flag** | 行为变更可开关 | 灰度 |
| **弃用告警** | 旧接口被调用时记录调用方 | 迁移期 |

"弃用告警"是最实用的一条：它在旧接口被调用时**记录调用方身份**，从而知道"还有谁在用"——这正是 3.5 里"确认调用方迁移时间"的数据来源。

### 5.2 大规模 API 的版本策略

| 策略 | 做法 | 代价 |
|---|---|---|
| **URL 版本**（`/v1/`） | 路径里带版本 | 客户端显式选择，维护多版本 |
| **请求头版本** | 用 header 指定 | URL 稳定，调试稍麻烦 |
| **日期版本**（Stripe 风格） | 账户绑定一个 API 版本快照 | 客户端不改就不会坏 |
| **永不加版本** | 只做向后兼容的演进 | 限制表达力 |

Stripe 的日期版本值得学：每个账户绑定一个"API 版本快照"，**服务端按账户的版本决定行为**。这样旧客户端永远不坏，新客户端可以用新行为。

它的代价：服务端要同时支持多个版本的行为分支，**长期维护成本高**。

### 5.3 契约测试的做法

当调用方与实现方是两个团队时，"契约"需要**双方共同验证**：

1. **定义**：把契约写成可执行的规格（输入输出样例 + 约束）。
2. 验证：实现方跑"我的输出满足契约"。调用方跑"我只需要契约承诺的部分"。
3. 门禁：契约变更必须双方同意。

关键点：**契约测试的输入是"契约"，不是"实现细节"。** 如果调用方的测试依赖了实现的内部行为，那就不是契约测试。

### 5.4 一份可落地的实施清单

1. **四要素**：每个公开接口写前置、后置、不变量、副作用。
2. probes：为一组典型调用（含边界值）建回归用例。
3. 破坏性判定：改动前跑 probes 找反例，而不是凭感觉。
4. 替换检查：前置减弱、后置加强、不变量保持三条齐备。
5. 弃用告警：旧接口被调用时记录调用方。
6. 窗口：取所有调用方的最长迁移时间。
7. 版本号：按判定结果给主/次/修订位。
8. 兼容性门禁：CI 里对比公开签名。
9. 对外假设：把"发布即永久"写进设计评审清单。
10. 文档：契约写在接口旁，与代码一起评审。

## 六、学术界的结论

### 6.1 Meyer 的契约式设计

Bertrand Meyer 在 Eiffel 语言里提出 **Design by Contract**：把前置条件、后置条件、不变量作为语言构造的一部分。

它的核心主张：**契约是双方的责任划分。**

- 前置条件不满足 → **调用方的责任**（实现方不必处理）。
- 后置条件不满足 → 实现方的责任。

这条划分的工程价值极大：它让"输入校验放在哪一层"有了明确答案——**前置条件由调用方保证，实现方可以在入口断言（fail fast），而不是静默容错。**

与 agent 系统的对应：工具接口的前置条件如果由模型（调用方）保证，那么工具实现可以更简单。**但模型的输出是"模型/tool JSON"边界，属于需要校验的边界**——所以这里是一个例外。

### 6.2 Liskov 替换原则

Liskov 与 Wing（1994）给出了替换原则的形式化表述：

> 若 $S$ 是 $T$ 的子类型，则所有使用 $T$ 的程序在替换为 $S$ 后行为应当不变。

形式化后的两条条件与 3.4 完全对应：

- **前置条件不能加强**（$S$ 要求的不多于 $T$）。
- 后置条件不能减弱（$S$ 保证的不少于 $T$）。

**它是"实现可以随便换"这一承诺的理论基础**。没有这条原则，"面向接口编程"就没有依据。

### 6.3 Hoare 逻辑

Hoare 逻辑用三段式描述程序：

$$
\{P\}\ C\ \{Q\}
$$

读作"若执行前 $P$ 成立，则执行后 $Q$ 成立"（$P$ 是前置，$Q$ 是后置）。

它的价值在于可组合性：两条语句的证明可以串起来——由 `{P} C1 {R}` 与 `{R} C2 {Q}` 相加，得到整段语句的 `{P}` 与 `{Q}`。

对接口设计的启示：**只要每个接口的契约被满足，组合起来的行为就可以推理。** 这是"用接口搭系统"能成立的形式化理由。

### 6.4 行为子类型与类型系统

一个反复出现的困境：**类型签名相同而行为不兼容**（算例里的"签名不变而行为改变"）。

学术界的回应是**行为子类型**（behavioral subtyping）：类型兼容不应只看签名，还要看行为规格。

实践中的近似做法：

- 把行为约束写成测试（可执行的规格）。
- 用属性测试（property-based testing）覆盖"对任意输入都成立"的性质。

对 agent 的启示：工具接口的"类型"只覆盖了参数结构，**行为约束（幂等、有配额、顺序要求）必须另外写清楚**——这正是 3.2 的隐式依赖面。

## 七、理论：三种相容关系

### 7.1 前置与后置的方向

$$
\text{兼容} \iff P_{\text{新}} \subseteq P_{\text{旧}} \ \wedge\ Q_{\text{新}} \supseteq Q_{\text{旧}}
$$

即新实现接受更多输入、保证更多输出。

记忆方式：**放宽输入、收紧输出。**

算例实测：前置加强 → 破坏（`true`）。后置削弱 → 破坏（`true`）。后置加强 → 不破坏（`false`）。

### 7.2 弃用窗口的取值

$$
W = \max_i w_i
$$

算例实测：$w = \{2, 6, 20\}$ 时 $W = 20$ 周，平均值 9.3 周，**比值 2.14**。

为什么必须取最大值：弃用是一个**所有约束都要满足**的条件（合取），不是平均意义上的妥协。任何一个调用方没迁完，就不能删。

为什么平均值特别危险：它给出一个"看起来合理"的数字（9.3 周），掩盖了"有一个调用方要 20 周"这个决定性事实。

### 7.3 破坏性的可判定判据

$$
\text{破坏} \iff \exists c \in C_{\text{合法}} : \text{行为}_{\text{新}}(c) \ne \text{行为}_{\text{旧}}(c)
$$

（$C_{\text{合法}}$ 是旧版本下合法的调用集合。）

这是一个"存在量词"判据：找到**一个**反例就足以判定破坏。这解释了为什么找反例比试图证明"没有破坏"更可行——前者只需一个例子。

同时它也说明：找反例**找不到不等于没有破坏**，只说明 probes 集合没覆盖到。所以 probes 的质量决定了判定的可靠程度。

## 九、练习

### 第一题：判断三次改动的破坏性

接口原来是 `fetch(query: string): Item[]`。

```
改动 A：加一个可选参数 limit，默认不限制
改动 B：原来返回按时间升序，现在不保证顺序
改动 C：参数改为必填对象 {query, limit}
```

要求：

- 逐个判断是否破坏性，并说明依据。
- 对每个破坏性改动，写一个具体的反例（一个旧版合法、新版不同的调用）。
- 给出各自应该给的主/次/修订版本位。

---

### 第二题：算弃用窗口

一个旧接口有四个调用方，迁移时间分别是：内部服务 A 需要 1 周、内部服务 B 需要 4 周、外部合作伙伴 C 需要 12 周、一个无法确认的内部脚本。

要求：

- 算出正确的弃用窗口，并说明"无法确认"的那一个怎么处理。
- 说明如果按平均值定窗口会发生什么。
- 给出迁移期需要的三个工程手段（告警、开关、双跑）。

---

### 第三题（进阶）：写一份可执行的契约

要求：

- 为一个"发送消息"的工具写四要素契约。
- 为它设计至少 6 个 probes（含边界与并发场景），并说明每个探测什么。
- 用 3.4 的三条条件，判断"把实现从同步改为异步"是否算兼容替换，并说明需要额外写清什么。

## 十、算例

算例实现了本篇的全部校验与判定函数。

```powershell
cd D:\dsh-course
node examples/sa18_contract.mjs        # 全部函数的运行结果
node examples/test_sa18_contract.mjs   # 数字回归断言
```

它做到的事：

- 契约校验（齐备得到 `true`，缺不变量得到 `["不变量"]`）。
- 隐式依赖面（只写两类契约时暴露出副作用、时序、资源三项）。
- **破坏性判定**（加必填参数得到"前置被加强"、签名不变而行为改变、无改动得到"未找到反例"）。
- 前置加强、后置削弱、后置加强三个方向的判定。
- 替换兼容的三条条件（含削弱后置与丢失不变量两种失败情形）。
- 弃用窗口（20 周）与平均值（9.3 周）的对照，比值 2.14。
- 无调用方时窗口为 0 周。
- 破坏性改动后主版本为 2.0.0。

这一篇只要记住一句：接口契约必须写清**前置、后置、不变量、副作用**四件事。判断破坏性靠找反例而不是直觉。前置可以放宽、后置应当收紧。而弃用窗口要取最慢的那个调用方，不是平均值。

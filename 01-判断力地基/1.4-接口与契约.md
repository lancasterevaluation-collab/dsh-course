## 本篇新词

- 契约（contract） 指接口对调用方的全部承诺：前置条件、后置条件、不变量三类。签名只表达其中的类型部分。
- 前置条件（precondition） 指调用方必须保证的事项。它把责任划给调用方。
- 后置条件（postcondition） 指被调方承诺的结果。它把责任划给实现方。
- 不变量（invariant） 指在调用前后都成立的性质。它最难表达，也最容易在改动中被破坏。
- 兼容性判据（compatibility criterion） 指一个改动是否破坏契约的判定标准：是否存在一个原本合法的调用方，在改动后其行为被观察为不同。
- 替换原则（substitution principle） 指子类型能替代父类型的条件：前置不加强、后置不减弱、不变量保持。
- Hyrum 定律 指当使用者足够多时，实现的每一个可观察行为都会被依赖——包括那些没写进契约的。
- 弃用窗口（deprecation window） 指从宣布弃用到移除之间的时间，它必须足够长以让调用方迁移。

## 一、【设计原因】

### 1.1 缺陷一：签名给出的信息量，只有契约的一小部分

`function estimate(input: string): number` 这条签名说明了参数类型与返回类型。它没有说明：输入为空时怎样、返回值的单位是什么、负数是否可能、是否可能抛错、并发调用是否安全。

签名缺失的五件事至少是：取值范围、错误行为、副作用、时序要求、不变量。

### 1.2 缺陷二：半实现的能力比没有这个能力更危险

接口里声明了一个方法，但实现只覆盖了部分情形。调用方看到方法存在，于是按完整语义使用它。

没有这个方法时调用方会绕开。有这个方法而只实现一半时，调用方会在某个边界上失败，而这个失败看起来像是调用方的错。

### 1.3 缺陷三：改了实现，调用方坏了，而接口没动

接口签名没变，但实现的输出格式变了（例如数值精度、排序稳定性、字段顺序）。调用方基于旧行为写的代码失效。

这就是 Hyrum 定律在起作用：调用方依赖的是可观察行为，不只是签名。

### 1.4 缺陷四：迁移决策缺少输入

要废弃一个旧接口，但决定不了"什么时候可以删"。缺少的信息是：谁在用、用了哪些部分、迁移需要多久。

没有这些输入，"弃用窗口"只能凭感觉定，结果要么删早了导致大量破坏，要么永不删导致两套并存。

### 1.5 由此确定的设计目标

1. 契约要写全三类：前置、后置、不变量。
2. 兼容性判据要可执行：能对任何改动给出"破坏/不破坏"。
3. 可观察面要显式：超出契约但被依赖的行为要登记。
4. 弃用要带窗口：窗口长度由迁移成本算出。

**本节要点**

- 签名缺失至少五件事：取值范围、错误行为、副作用、时序、不变量。
- 半实现的能力比没有更危险，因为它改变了调用方的行为。
- 调用方依赖可观察行为，不只是签名（Hyrum 定律）。
- 弃用窗口需要"谁在用、用多久"作为输入。
- 四条目标：三类俱全、判据可执行、可观察面显式、弃用带窗口。

## 二、【直觉】

### 2.1 一份合同

合同里有三类条款：甲方的义务（前置）、乙方的义务（后置）、双方都不能违反的原则（不变量）。

一份只写了"乙方交付一台机器"的合同是不完整的——它没说甲方的场地条件（前置）、机器的验收标准（后置）、以及双方都不得在合同期内单方面转让（不变量）。

接口的处境相同：只写返回类型等价于只写"交付一台机器"。

### 2.2 责任的划界

合同的核心作用不是描述行为，而是划界：出问题时谁负责。

一条前置条件的意思是"如果不满足，后果由调用方承担"。一条后置条件的意思是"如果满足，结果由实现方保证"。

::: keypoint 反直觉点
**把前置条件写严是有代价的：它把更多责任推给调用方。** 所以"前置条件越少越好"与"前置条件越明确越好"是两件事——**数量要少，表述要明确**。把本该由实现方处理的输入校验推给调用方，是常见的推卸责任形式。
:::

### 2.3 一个数字直觉

设某接口有 6 个方法，每个方法对外可观察的行为有 4 项（取值、错误、副作用、时序），共 24 项可观察行为。

若契约只写明其中的 10 项，那么另外 14 项处于"隐式依赖"状态——它们随时可能被某个调用方依赖，而契约不知道是谁。

弃用时需要处理的不是 10 项，而是 24 项，且那 14 项需要靠搜索代码找出依赖方。

**本节要点**

- 合同的三类条款对应前置、后置、不变量。
- 前置条件的作用是划界，不满足时责任在调用方。
- 前置条件的数量要少、表述要明确——这是两件事。
- 契约写明的行为与可观察行为之间的差额，就是弃用时要额外处理的量。

## 三、【严格】

### 3.1 定义

::: theorem 定义 1.4.1（契约）
接口 $I$ 的**契约**是三元组 $K_I = (P, Q, \mathrm{Inv})$：

$$
P: \text{输入与状态上的谓词（前置）},\quad Q: \text{输出与状态上的谓词（后置）},\quad \mathrm{Inv}: \text{调用前后均成立的谓词}.
$$

**签名**只表达类型层面的信息，是 $K_I$ 的真子集。

后置条件在实践中写成**承诺集合**而不是单一谓词——因为谓词形式无法表达"不再做任何承诺"，而"从保证排序到什么都不保证"正是一种常见且危险的削弱。
:::

::: theorem 定义 1.4.2（合法调用）
调用 $c$ 对接口 $I$ 是**合法的**，当且仅当它在调用时满足前置条件 $P$，且 $\mathrm{Inv}$ 在调用前成立。

$$c \in \mathrm{Legal}(I) \iff P(c) \wedge \mathrm{Inv}(\text{调用前状态}).$$
:::

::: theorem 定义 1.4.3（破坏性改动）
设接口从版本 $v$ 改到 $v'$。该改动是**破坏性的**，当且仅当存在一个对 $v$ 合法的调用 $c$，它在 $v'$ 下不合法，或它在 $v$ 与 $v'$ 下的可观察行为不同：

$$
\text{Breaking}(v, v') \iff \exists c \in \mathrm{Legal}(I_v):\ c \notin \mathrm{Legal}(I_{v'}) \vee \mathrm{obs}_{v}(c) \ne \mathrm{obs}_{v'}(c).
$$
:::

::: theorem 定义 1.4.4（可观察面）
接口 $I$ 的**可观察面** $\mathrm{Obs}(I)$ 指调用方能够观测到的全部行为：返回值、抛出的错误、副作用、时序特性、以及可观测的资源使用。

$$
K_I \subseteq \mathrm{Obs}(I).
$$

差额 $\mathrm{Obs}(I) \setminus K_I$ 称为**隐式依赖面**。
:::

::: theorem 定义 1.4.5（替换兼容）
子类型 $S$ 可替换父类型 $T$，当且仅当：

$$
P_S \le P_T \quad (\text{前置不加强}), \qquad Q_S \ge Q_T \quad (\text{后置不减弱}), \qquad \mathrm{Inv}_S \supseteq \mathrm{Inv}_T .
$$
:::

::: theorem 定义 1.4.6（弃用窗口）
设调用方集合为 $C$，调用方 $c$ 的迁移所需时长为 $m(c)$。**最小弃用窗口**为

$$
W_{\min} = \max_{c \in C} m(c).
$$

窗口短于此值时，必然有调用方来不及迁移。
:::

### 3.2 命题

::: theorem 命题 1.4.1（兼容性判据的完备性）
按定义 1.4.3 判定的破坏性，当且仅当存在反例调用。因此**判定是二值的且可构造反例**。

**证明.** 定义使用存在量词，"破坏性"为真等价于反例存在。为假等价于不存在反例。两者互补，故判定二值。反例即该存在量词的见证。

↓ **为什么能这么写？** 定义本身是存在性陈述，存在性判定的真假是二值的。

$\blacksquare$

::: keypoint 判据的用法：找反例而不是辩论
**判断"这个改动算不算破坏性"时，不要讨论它严不严重，去找一个原本合法的调用。** 找得到就是破坏性的，找不到就不是——与改动看起来多大无关。
:::

::: theorem 命题 1.4.2（加强前置是破坏性的）
若 $P_{v'} \supsetneq P_v$，则该改动是破坏性的。

**证明.** 取 $c$ 满足 $P_v(c) \wedge \lnot P_{v'}(c)$（由真包含关系该调用存在）。则 $c \in \mathrm{Legal}(I_v)$ 而 $c \notin \mathrm{Legal}(I_{v'})$。按定义 1.4.3，改动是破坏性的。

↓ **为什么能这么写？** 真包含给出一个落在旧前置内、新前置外的调用。

$\blacksquare$

::: keypoint 最常见的破坏性改动
**"增加一个必填参数"、"收紧输入校验"、"要求调用方先初始化"都是加强前置。** 它们看起来是"更严谨的实现"，而对调用方是破坏性变更。
:::

::: theorem 命题 1.4.3（削弱后置是破坏性的）
若 $Q_{v'} \subsetneq Q_v$，则该改动是破坏性的。

**证明.** 取输出 $o$ 满足 $Q_v(o) \wedge \lnot Q_{v'}(o)$。存在一个原本合法的调用 $c$ 产生 $o$（否则 $Q_v$ 的该部分无意义）。此时 $\mathrm{obs}_v(c) \ne \mathrm{obs}_{v'}(c)$ 或至少 $v'$ 不再保证原承诺。按定义 1.4.3，改动是破坏性的。

↓ **为什么能这么写？** 后置的削弱使原承诺不再成立，而调用方可能依赖它。

$\blacksquare$

**示例**：原本承诺"返回值已排序"，改为"返回值未定义顺序"，即削弱后置。
:::

::: theorem 命题 1.4.4（隐式依赖面的存在使签名兼容不等于行为兼容）
若 $\mathrm{Obs}(I) \setminus K_I \ne \varnothing$，则存在一个仅改变隐式依赖面的改动，它不改变签名却仍是破坏性的。

**证明.** 取 $\mathrm{Obs}(I) \setminus K_I$ 中的一项行为 $b$。构造改动只改变 $b$，不改签名。由于 $b$ 可被调用方观测，若存在调用方依赖它，则该调用方的可观察行为改变，按定义 1.4.3 属于破坏性。

↓ **为什么能这么写？** 只需指出隐式面里的任一项都能成为反例的来源。

$\blacksquare$

::: keypoint Hyrum 定律的准确形式
**"使用者足够多"是这条结论的前提。** 使用者少时，隐式依赖面可能无人依赖，行为改动不破坏任何人。因此**判断它是否破坏性，要看实际依赖方，而不是看契约写了什么**。
:::

::: theorem 命题 1.4.5（替换兼容的充分性）
若 $P_S \le P_T$、$Q_S \ge Q_T$、$\mathrm{Inv}_S \supseteq \mathrm{Inv}_T$，则任何对 $T$ 合法的调用对 $S$ 也合法，且其可观察行为满足 $T$ 的后置条件。

**证明.** 由 $P_S \le P_T$，合法调用集合满足 $\mathrm{Legal}(S) \supseteq \mathrm{Legal}(T)$。对任一 $c \in \mathrm{Legal}(T)$，$c \in \mathrm{Legal}(S)$。其输出满足 $Q_S$，而 $Q_S \ge Q_T$ 意味着 $Q_S$ 蕴含 $Q_T$，故输出满足 $T$ 的承诺。

↓ **为什么能这么写？** 前置的放宽扩大合法集合，后置的加强保证原承诺仍成立。

$\blacksquare$

::: keypoint 三条都必要
**缺少任何一条都会出现反例**：前置加强使某些合法调用变为非法。后置削弱使某些承诺失效。不变量丢失使调用前后的性质被破坏。实际实现里最常见的是第二条——"新类型的行为基本一样，只是不再保证某个性质"。
:::

::: theorem 命题 1.4.6（弃用窗口的下界由最慢的调用方决定）
$W < W_{\min} = \max_c m(c)$ 时，必然存在调用方在窗口内未完成迁移。

**证明.** 取达到最大值的调用方 $c^{*}$。由 $W < m(c^{*})$，窗口结束时 $c^{*}$ 必然尚未完成迁移，故它在移除时仍依赖旧接口。

↓ **为什么能这么写？** 最大值是所有调用方迁移时间的上界，窗口小于它时上界对应的那个来不及。

$\blacksquare$

**数值**：若调用方迁移时间分别为 2、6、20 周，则 $W_{\min} = 20$ 周。**只按平均值（约 9.3 周）定窗口会让最慢的那个失败。**
:::

### 3.3 本节要点

**本节要点**

- 契约是前置、后置、不变量的三元组，签名是它的真子集（定义 1.4.1）。
- 破坏性判据：存在原本合法的调用其行为被观察为不同（定义 1.4.3、命题 1.4.1）。
- 加强前置是破坏性的（命题 1.4.2）。
- 削弱后置是破坏性的（命题 1.4.3）。
- 隐式依赖面的存在使签名兼容不等于行为兼容（命题 1.4.4）。
- 替换兼容需要三条同时成立（命题 1.4.5）。
- 弃用窗口由最慢的调用方决定，不是平均值（命题 1.4.6）。

## 四、【回到直觉】

- **定义 1.4.1 说的**：写接口文档时对照三类——前置、后置、不变量。**缺一类就是一个洞。**
- **命题 1.4.2 说的**：增加必填参数、收紧校验都是破坏性的，即使它让实现"更严谨"。
- **命题 1.4.3 说的**：从"已排序"改成"顺序未定义"是破坏性的——有调用方可能依赖了排序。
- **命题 1.4.4 说的**：签名没变而行为变了，也是破坏性的。判断依据是**实际依赖方**，不是契约写了什么。
- **命题 1.4.5 说的**：替换兼容要三条同时成立。实际最容易违反的是"后置不减弱"。
- **命题 1.4.6 说的**：弃用窗口按最慢的调用方定，不按平均值。

**本节要点**

- 三类承诺对照写。
- 加必填参数 = 破坏性。
- 弱化承诺 = 破坏性。
- 行为变化也是破坏性，看实际依赖方。
- 替换兼容三条都要。
- 弃用窗口按最慢的调用方。

## 五、【工具箱】

### 5.1 契约检查

对每个公开方法列出三类承诺。**检查方式**是逐条问："违反它时，谁负责？"答不出来说明该条不够明确。

**代价**：一个方法约十到二十分钟，而它节省的是后续每次改动的沟通成本。

### 5.2 可观察面的枚举

按定义 1.4.4 的五类逐条枚举：返回值、错误、副作用、时序、资源。

与契约对比，差额即隐式依赖面。**隐式面的每一项都要决定：要么写进契约，要么明确声明"不保证"。**

### 5.3 破坏性判定的操作流程

1. 写下**原本合法的调用集合**（尤其是边界情形）。
2. 对每个调用比较新旧可观察行为。
3. 找到第一个差异即为反例。找不到则非破坏性。

**关键是第 1 步**：边界情形（空输入、极值、并发、重复调用）最容易漏，而反例常在那里。

### 5.4 替换原则的检查

三条逐条检查：

- 前置是否被加强（看新实现在哪些输入上拒绝）
- 后置是否被减弱（看新实现不再保证什么）
- 不变量是否保持（看调用前后的性质）

### 5.5 弃用窗口的计算

按命题 1.4.6，取所有调用方迁移时间的最大值。

**迁移时间从哪来**：从依赖方的发布节奏估算——通常取"依赖方的两个发布周期"。

**本节要点**

- 弃用窗口取最大值，来源是依赖方的发布节奏。

## 七、施工图与算例

### 7.1 三段结构

| 段 | 职责 | 关键输出 |
|---|---|---|
| 契约段 | 写全三类承诺 | 契约清单（含责任归属） |
| 兼容段 | 判定改动是否破坏 | 反例或"未找到反例" |
| 版本段 | 推导版本号与弃用窗口 | 版本与窗口 |

### 7.2 契约段

契约段要求三类承诺齐备，并把可观察面与契约写明的部分对照。

```js
// 定义 1.4.1：契约是前置、后置、不变量的三元组；签名只是它的真子集
export const OBSERVABLE_KINDS = ['返回值', '错误', '副作用', '时序', '资源']

export function validateContract(contract) {
  const missing = []
  if (typeof contract.precondition !== 'function') missing.push('前置条件')
  if (typeof contract.postcondition !== 'function') missing.push('后置条件')
  if (!Array.isArray(contract.invariants) || contract.invariants.length === 0) missing.push('不变量')
  return { ok: missing.length === 0, missing }
}

// 定义 1.4.4：隐式依赖面 = 可观察面 - 契约写明面
export function implicitSurface(contractKinds, observedKinds) {
  return observedKinds.filter((k) => !contractKinds.includes(k))
}
```

### 7.3 兼容段

兼容段靠找反例：原本合法的调用里，有哪一个在改动后行为被观察为不同。

```js
// 定义 1.4.3 / 命题 1.4.1：破坏性判定 = 找一个原本合法的调用作反例
export function findBreakingCall(oldIface, newIface, candidates) {
  const legalBefore = candidates.filter((c) => oldIface.precondition(c))
  for (const c of legalBefore) {
    const stillLegal = newIface.precondition(c)
    if (!stillLegal) return { breaking: true, call: c, reason: '前置被加强' }
    if (oldIface.observe(c) !== newIface.observe(c)) return { breaking: true, call: c, reason: '可观察行为改变' }
  }
  return { breaking: false, call: null, reason: '未找到反例' }
}

// 命题 1.4.2 / 1.4.3：前置加强与后置减弱各自都是破坏性的
export function preconditionStrengthened(oldPre, newPre, candidates) {
  return candidates.some((c) => oldPre(c) && !newPre(c))
}

export function postconditionWeakened(oldPost, newPost, outputs) {
  return outputs.some((o) => oldPost(o) && !newPost(o))
}
```

### 7.4 版本段

版本段给出替换兼容的三条件检查与弃用窗口的计算。

```js
// 命题 1.4.5：替换兼容三条件
export function substitutionCompatible(sup, sub) {
  const checks = {
    preconditionWeaker: sub.preconditionLevel <= sup.preconditionLevel,
    postconditionStronger: sub.postconditionLevel >= sup.postconditionLevel,
    invariantsKept: sup.invariants.every((i) => sub.invariants.includes(i)),
  }
  return { ok: Object.values(checks).every(Boolean), checks }
}

// 定义 1.4.6 / 命题 1.4.6：弃用窗口 = 最慢的调用方迁移时间
export function deprecationWindow(migrationWeeks) {
  if (migrationWeeks.length === 0) return { min: 0, mean: 0, max: 0 }
  const sum = migrationWeeks.reduce((a, b) => a + b, 0)
  return {
    min: Math.max(...migrationWeeks),
    mean: sum / migrationWeeks.length,
    max: Math.max(...migrationWeeks),
  }
}

// 版本号推导：破坏性 → 主版本；兼容新增 → 次版本；修正 → 补丁
export function bumpVersion(version, kind) {
  const [major, minor, patch] = version.split('.').map(Number)
  if (kind === 'breaking') return `${major + 1}.0.0`
  if (kind === 'feature') return `${major}.${minor + 1}.0`
  return `${major}.${minor}.${patch + 1}`
}
```

### 8.3 评审一份接口改动的六个问题

1. **改动的三类承诺哪一类被动了？** 加强前置、削弱后置、丢失不变量都是破坏性的。
2. **有反例调用吗？** 边缘情形（空、极值、并发、重复调用）最容易藏反例。
3. **隐式依赖面动了吗？** 签名未变不等于行为兼容。
4. **替换兼容三条件都满足吗？** 尤其第二条"后置不减弱"。
5. **版本号与改动性质一致吗？** 破坏性改动必须升主版本。
6. **弃用窗口按最慢的调用方算了吗？** 按平均值定必然有调用方来不及。

**本节要点**

- 能力判据四条。
- 数字回归五项，含 20 周与 9.3 周这两个对照值。
- 评审六问按三类承诺、反例、隐式面、替换兼容、版本号、窗口排列。

### 9.2 失败模式

**（1）检查放在装载期（L9 位置放错）。** 兼容性判定在发布前做一次，而调用方在发布后才开始依赖新行为。表现是"这个版本没问题，下个版本删掉某个'未定义'行为时坏了"。修正：把隐式面登记进契约，或定期重估依赖面。

**（2）前提会变（L9）。** 命题 1.4.4 的判定以"依赖方集合已知"为前提。依赖方自己新增了对隐式行为的依赖时，该集合变化而契约不知道。修正：定期用测试或埋点检测实际依赖的行为。

**（3）签名没变就当兼容。** 漏掉行为变化。

**（4）增加必填参数。** 加强前置，破坏所有调用方。

**（5）削弱后置。** 从"已排序"变成"顺序未定义"。

**（6）半实现的能力。** 声明了完整语义而只实现部分。

**（7）不变量丢失。** 新实现不再保证调用前后的某个性质，而它没被写下来所以无人察觉。

**（8）替换兼容只查一条。** 常见的是只检查前置，漏掉后置与不变量。

**（9）版本号与改动性质不符。** 破坏性改动只升次版本，调用方不会主动检查。

**（10）弃用窗口按平均值定。** 最慢的调用方必然来不及。

**本节要点**

- 决策表覆盖 11 种情形。
- 失败模式十条，前两条是位置放错与前提会变。
- 最隐蔽的是"不变量丢失"——它没被写下来，因此无人察觉。

## 十、仍未解决

- **不变量的表达。** 它最难写进契约，也最难自动检查。当前多靠文档描述。
- **可观察面的完备性。** "可观察"的边界随调用方能力变化（例如有人能测到微秒级时序）。
- **依赖方集合的完整性。** 内部依赖可从代码搜索得到，外部依赖（尤其是下游厂商）常无法枚举。
- **替换兼容的检查成本。** 三条逐条检查对每个子类型都要做一遍。
- **弃用窗口与迁移成本的关系。** 迁移时间只能估算，且它依赖依赖方的优先级安排。
- **语义版本表达力的上限。** 版本号只能表达三段式的粗略信息，无法表达"哪一项承诺变了"。

**本节要点**

- 不变量难以表达与检查。
- 可观察的边界随能力变化。
- 外部依赖方常无法枚举。
- 替换兼容检查成本随子类型数量增长。
- 迁移时间只能估算。
- 版本号表达力有限。

**参考要点**

2. 划界——不满足时责任在调用方。数量要少，表述要明确。
3. 它加强前置，使原本合法的调用变非法。
4. 它削弱后置，原来的承诺不再成立，而调用方可能依赖排序。

## 十三、只记一句话 + 记忆锚点

只记一句话：

> **接口对调用方的承诺不止签名：判断一个改动是否破坏性，方法是去找一个原本合法、改动后行为被观察为不同的调用。**

如果读完只记得一句话，就记它。其余细节都可以由它推回来。

**记忆锚点**

- **三类承诺**：前置、后置、不变量（签名只是真子集）。
- **两个破坏源**：加强前置、削弱后置。
- **一个关键区分**：签名兼容 ≠ 行为兼容。
- **三个数字**：观察面五类。迁移 2/6/20 周时窗口 20 周（平均值 9.3 周）。破坏性改动升到 2.0.0。
- **一条判据**：找得到反例就是破坏性的。

## 一、为什么需要"十站"

### 1.1 能说出"要做这个功能"，说不出它要经过哪些站

产品说"加个导出功能"。工程师开始写代码。**没有人问"怎么算导出成功"、"导出会不会影响别的模块"、"出问题怎么回滚"。**

### 1.2 把"先做什么"当成排序问题

团队为"先改 schema 还是先改 API"争论。**这不是排序问题，是依赖问题**——schema 是 API 的前置，反过来做会返工。

### 1.3 对所有改动用同一种谨慎程度

改一个文案和改一个计费规则走了同样长的评审流程。**结果是一个太慢、一个太快。**

### 1.4 说不出"完成"是什么

功能"做完了"，但没人能回答"怎么知道它是好的"。上线后坏了三天没人发现。

这四条缺陷分别对应十站里的：**判据、依赖序、可逆性、观测**。

## 二、十站与依赖序

十站不是流程文档里的十个勾选框，而是**有依赖关系的十个节点**：

| 站 | 产出 |
|---|---|
| 意图 | 要解决谁的什么问题 |
| 判据 | 怎么知道做成了 |
| 影响面 | 会牵连哪些模块与团队 |
| 方案 | 打算怎么做 |
| 依赖序 | 先做哪一步 |
| 实现 | 代码与配置 |
| 验证 | 证据 |
| 发布 | 上线的动作 |
| 观测 | 上线后的数字 |
| 退役 | 什么时候、怎么下线 |

**它们的关系不是"依次做完"，而是"有依赖才必须先行"**。例如"影响面"必须在"方案"之前（否则方案会漏掉牵连），而"观测"必须在"意图"之后就确定指标（否则会漏测）。

## 三、怎么做

### 3.1 十站清单：每一站的产出

算例实测的十站序列是：

```
意图 → 判据 → 影响面 → 方案 → 依赖序 → 实现 → 验证 → 发布 → 观测 → 退役
```

每站的关键问题：

| 站 | 必须回答 | 漏了会怎样 |
|---|---|---|
| 意图 | 谁的问题、现在怎么办的 | 做出没人要的东西 |
| 判据 | 用什么数字判定成功 | 无法判断完成 |
| 影响面 | 谁会被牵连 | 上线后别处坏了 |
| 方案 | 在几个选项里选了哪个、为什么 | 事后无法复盘 |
| 依赖序 | 什么必须先做 | 返工 |
| 实现 | 代码、配置、文档 | 别人无法接手 |
| 验证 | 什么证据说明它对 | 靠感觉 |
| 发布 | 怎么上、谁批 | 流程卡住或绕过 |
| 观测 | 上线后看哪几个数 | 坏了不知道 |
| 退役 | 什么时候下、怎么下 | 永久债 |

走查的价值：算例给出"缺三站"的走查结果——`影响面, 观测, 退役`。**这三个恰好是最容易被跳过的**，因为它们在"把功能做出来"这件事上看不到直接贡献。

### 3.2 依赖序：为什么不是排序问题

依赖是**有向图**，顺序是它的**拓扑排序**。两者的区别在"有环"时暴露：

```js
// 依赖序：拓扑排序，并检测是否存在环
export function topologicalOrder(nodes, edges) {
  const indeg = new Map(nodes.map((n) => [n, 0]))
  for (const [, to] of edges) indeg.set(to, indeg.get(to) + 1)
  const queue = nodes.filter((n) => indeg.get(n) === 0)
  const order = []
  while (queue.length) {
    const n = queue.shift()
    order.push(n)
    for (const [from, to] of edges) {
      if (from !== n) continue
      indeg.set(to, indeg.get(to) - 1)
      if (indeg.get(to) === 0) queue.push(to)
    }
  }
  return { order, hasCycle: order.length !== nodes.length }
}
```

算例实测：

| 输入 | 输出 |
|---|---|
| 无环（判据 → 方案 → 实现） | `判据 → 方案 → 实现`，`有环 = false` |
| **有环** | **输出 0 个节点**，`有环 = true` |

"输出 0 个节点"这个结果非常有教育意义：有环时拓扑排序不是"给一个近似顺序"，而是**一个都给不出来**。这意味着**循环依赖必须在上线前解开**，无法"先凑合排一下"。

实践判据：如果三个人对"先做哪一步"有不同意见，先画出依赖图。**图上不可能有环而三个顺序都对**——争论往往来自把依赖问题当成了偏好问题。

### 3.3 可逆性分级：双向门与单向门

**可逆性决定需要多谨慎**。三档的划分：

| 档 | 判据 | 算例实测 |
|---|---|---|
| **双向门** | 回滚快、无外部依赖 | 回滚 5 分钟、无外部依赖 → `two-way` |
| **慢回滚** | 回滚要几小时，或有外部依赖 | 回滚 2 小时 → `slow`。有外部依赖 → `slow` |
| **单向门** | 需要他人配合才能回滚 | 需他人配合 → `one-way` |

分级的判定逻辑如下。

```js
// 可逆性分级：回滚代价与外部耦合共同决定谨慎程度
export function reversibility({ rollbackMinutes, externalDeps, needsOthers }) {
  if (needsOthers) return 'one-way'
  if (rollbackMinutes <= 15 && externalDeps === 0) return 'two-way'
  return 'slow'
}
```

**算例给出的关键量化结论**（这是本篇最该记住的一组数字）：

| 门的类型 | 单位代价容忍系数 $c$ | 可容忍缺陷率 |
|---|---|---|
| 双向门 | 0.1 | **10.00** |
| 单向门 | 100 | **0.0100** |
| **比值** | 1000 | **1000 倍** |

读法：同样的缺陷率，在双向门上可能完全可接受，在单向门上则是灾难。**两者容忍度相差三个数量级。**

这条结论直接改变做事方式：

- 对双向门（改文案、调参数、加日志）：**快速做，出问题就回滚**，不需要长评审。
- 对单向门（改计费、删数据、改公开 API 契约）：**值得花一周做设计评审**，因为回滚代价是三个数量级之外。

最容易犯的错是把两类混在一起处理：要么所有改动都走重流程（慢死），要么所有改动都快速上（炸一次就完了）。

### 3.4 影响面：改一处会牵连到谁

影响面分析回答"这个改动会让哪些模块必须跟着变"。算例实测：

| 改动 | 影响面 |
|---|---|
| 改 schema | `schema, api, etl, sdk, docs, report`（**6 个**） |
| 改 sdk | `sdk`（**1 个**） |

**这个 6 比 1 的对比解释了"为什么改数据模型要慎重"**：它不是一次改动，而是六次改动加六次验证。

实践做法：影响面不要靠回忆，而是**从依赖图或代码引用里查**。凡是"我觉得不会有别的地方用到"的判断，都要用一次搜索来验证。

### 3.5 完成的定义：判据加指标

"完成"必须是一个**可检查的谓词**，而不是感觉。它由两部分组成：

- **判据**：功能上必须成立的条件。
- **指标**：运行时必须达到的数字。

```js
// 完成检查：判据与指标都满足才算完成，并列出缺哪些
export function isDone(criteria, metrics) {
  const failed = []
  for (const [name, check] of Object.entries(criteria)) if (!check) failed.push(name)
  for (const [name, value] of Object.entries(metrics)) {
    if (value === undefined || value === null) failed.push(name)
  }
  return { done: failed.length === 0, failed }
}
```

算例实测：达标时 `{done: true, failed: []}`。**缺指标时** `{done: false, failed: ["failureRate"]}`。

"缺指标"为什么算未完成：功能对了但没人知道它坏了，等于没做完。**把"指标已接入"写进完成条件，是让观测真正发生的最有效手段**——否则它会永远排在"下一个迭代"。

### 3.6 发布决策：用错误预算判断

发布不应该靠信心，而应该靠**错误预算**：

$$
\text{可发布} \iff \text{实际缺陷率} \le \text{预算}
$$

```js
// 发布决策：实际缺陷率低于预算才可发布
export function canRelease(budget, observedRate) {
  return { budget, rate: observedRate, releasable: observedRate <= budget }
}
```

算例实测：

| 预算 | 实际 | 结果 |
|---|---|---|
| 1% | 0.5% | `releasable: true` |
| 1% | 2% | `releasable: false` |

为什么用预算而不是阈值：阈值只说"当前好不好"，预算说"**这个季度还能坏多少次**"。后者才能回答"要不要现在发"。

## 四、特殊情况与处理技巧

| 情况 | 为什么 | 处理 |
|---|---|---|
| 有循环依赖 | 拓扑排序输出 0 个节点 | 必须先解开环，不能"凑合排" |
| 说不清影响面 | 依赖没被检索过 | 用搜索/依赖图查，不靠回忆 |
| 上线后坏了没人知道 | 完成条件里没有观测 | 把"指标已接入"写进完成定义 |
| 小改动走了长流程 | 没做可逆性分级 | 双向门快速走，单向门重评审 |
| 想下线下不掉 | 退役没定条件 | 上线时就写清退役条件与时间 |
| 评审会变成朗读会 | 没有产出物 | 每次评审要留下 ADR（见 6.3） |
| 灰度期间指标正常但仍出问题 | 指标没覆盖真实路径 | 指标要覆盖"用户实际走的路径" |
| 发布后回滚发现数据已迁移 | 迁移不可逆 | 迁移要两步（双写 → 切换 → 清理） |

最后一条值得展开：数据库迁移是典型的单向门，正确做法是**拆成三个可逆步骤**：先双写（可逆）、再切读（可逆）、最后清理旧字段（不可逆，但此时已无回头需求）。**把一步不可逆拆成两步可逆加一步最终不可逆**，是处理单向门的标准手法。

## 五、工业界的做法（可照做）

### 5.1 文档驱动的流程

| 公司 / 场景 | 文档形式 | 值得学的点 |
|---|---|---|
| **Google** | Design Doc | 先写设计再写代码，评审在设计阶段 |
| **Amazon** | PR/FAQ（新闻稿 + 常见问题） | **从用户视角倒推**：先写发布新闻稿 |
| **开源社区** | RFC / PEP | 公开讨论，决策留档 |
| **架构决策** | ADR（架构决策记录） | 记录"为什么不用 B 方案" |
| **事故复盘** | Postmortem（无责复盘） | 关注系统而非个人 |

共同点：**先写下来，再动手**。写作的成本远低于返工。

PR/FAQ 特别值得学：它要求先写"发布时给用户看的新闻稿"，再写"常见问题"。**如果新闻稿写不出吸引人的一句话，这个功能就不该做。**

### 5.2 发布与灰度

| 手段 | 作用 | 关键参数 |
|---|---|---|
| **Feature Flag** | 不发版就能开关功能 | 默认关、可快速关闭 |
| **金丝雀（canary）** | 先放给 1% 用户 | 观察时长与指标 |
| **蓝绿部署** | 两套环境切换 | 切换的可逆性 |
| **分批放量** | 1% → 5% → 25% → 100% | 每档的观察期 |
| **影子流量** | 复制真实流量到新版本，不返回结果 | 验证正确性而不影响用户 |

共同点：**把"发布"从一次动作变成一条曲线**。曲线上的每一步都可停、可退。

参数起点：金丝雀 1%，每档观察 30 分钟到数小时（取决于流量），放量比例按 4–5 档。**依据是"要积累多少样本才能对一个指标下结论"**（与统计显著性相关，见第 7 卷的评测）。

### 5.3 变更管理与审批

严肃系统（金融、医疗）有正式变更流程：变更申请 → 评审 → 排期 → 执行 → 验证 → 关闭。

它的代价与收益：流程降低事故率，但拖慢交付。**所以实践中的关键是分级**——只有单向门走完整流程，双向门走轻量流程（甚至自助）。

这正是 3.3 的量化依据：1000 倍的容忍度差距，足以支撑两套完全不同的流程。

### 5.4 一份可落地的实施清单

1. **十站模板**：为每个功能建一份十站清单，走查时逐站确认。
2. **依赖图**：把关键模块的依赖画出来，有环立即报警。
3. **可逆性标注**：每个改动标注双向门 / 慢回滚 / 单向门，并按类别走不同流程。
4. **影响面检索**：改 schema 或公开接口前，用搜索列出全部引用点。
5. **完成定义**：判据 + 指标，指标未接入不算完成。
6. **错误预算**：为每个服务设定预算，发布前核对。
7. **灰度**：默认走 1% → 100% 的分批放量，每档定观察期。
8. **退役条件**：上线时就写清"什么条件下下线"，并排入日程。
9. **ADR**：每次重要决策留一条记录，含被否决的方案与原因。
10. **复盘**：事故后无责复盘，产出系统性改进而非个人检讨。

## 六、学术界的结论

### 6.1 螺旋模型与风险驱动

Boehm 的**螺旋模型**（1988）主张软件过程应**由风险驱动**：每一圈都先处理最高风险的问题。

它与"十站"的关系：十站里"影响面"与"可逆性"正是风险评估的输入。**高风险（单向门）走完整流程，低风险快速通过**——这就是螺旋模型的实践形式。

### 6.2 Conway 定律

> 系统架构会反映组织的沟通结构。

推论：如果影响面跨越三个团队，那么交付速度由三个团队的协调成本决定。**这也是"改 schema 牵连 6 个模块"在组织层面的含义**——它同时是 6 个模块、可能也是 3 个团队的改动。

反向运用（"逆 Conway 操作"）：想让架构变成什么样，就先把团队结构调成那样（亚马逊的"两个披萨团队"是这个思路）。

### 6.3 架构决策记录（ADR）

ADR 是轻量的决策留档格式：一条 ADR 包含**背景、决策、被否决的方案、后果**。

**它的价值不在于记录"选了什么"，而在于记录"为什么不选另一个"**。半年后有人问"为什么不用 Kafka"，答案在 ADR 里，而不在某人的记忆里。

与"方案"这一站的对应：方案站要求"在几个选项里选了哪个、为什么"——ADR 就是它的落地形式。

### 6.4 可逆性与决策理论

决策理论里的**实物期权**（real options）思想：**保留选择权本身有价值**。

对技术决策的直接含义：

- 可逆的决策应该**快速做**（拖延的成本大于做错的成本）。
- 不可逆的决策应该**慢做**（做错的成本无法收回）。

**这就是双向门 / 单向门的理论出处**（Bezos 把它表述为 "Type 1 / Type 2 decisions"）。**它的结论是：决策速度应该与可逆性成正比，而不是与重要性成正比**——这与直觉相反，但被 1000 倍的容忍度差距支持。

### 6.5 退役：一个被学术研究较少但工程代价很高的阶段

软件生命周期的研究长期集中在"构建"上，而**退役（decommissioning）的成本经常被低估**。它的典型问题：

- 依赖关系难以完全识别（"这个接口还有人在用吗"）。
- 数据保留与合规要求。
- 停用后的回退需求。

实践结论：**退役要从上线那天开始计划**（写清条件与负责人），否则它会变成永久债。

## 七、理论：两个模型

### 7.1 可逆性与可容忍缺陷率

设单位缺陷的代价为 $c$，可容忍的缺陷率 $p$ 与代价成反比：

$$
p \propto \frac{1}{c}
$$

算例实测：$c = 0.1$ 时容忍率 10.00。$c = 100$ 时容忍率 0.0100。**比值 $1000/0.1 = 10000$ 对应容忍率比值 1000。**

含义：**"这个改动要不要谨慎"不该由改动大小决定，而应由 $c$ 决定**。一个改动很小但 $c$ 极大的变动（例如改一行的计费公式）需要最重的流程。

### 7.2 债的复利模型

技术债的利率效应可以量化。设每周偿还能力为 $R$、债务利率为 $i$，则债的"临界时间"（利息吞掉全部偿还能力的时间）为：

$$
T = \frac{R}{i}
$$

算例实测：$R = 60$、$i = 2$ 时 $T = 30$ 周。年利息 **104 小时**、半年利息 **52 小时**。

读法：债不会稳定在某个水平——**它以复利方式增长**。当利息接近偿还能力时，团队会陷入"全部时间都在还债"的状态。

实践判据：如果"用于还债的时间"超过总时间的 30%，说明已经进入危险区，必须做取舍（砍功能或增人力）。

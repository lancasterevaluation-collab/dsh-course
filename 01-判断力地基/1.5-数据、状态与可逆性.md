## 读完这一篇你会知道什么

1. **状态三分类**：权威（不可重建）、派生（可重建）、临时（一次操作内）。
2. 真相源唯一：算例里"双写"被检出，输出 `[["messages", ["session-store", "mirror"]]]`。
3. 变更四级 L0–L3：从"只动内存"到"触及外部"，可容忍缺陷率相差 1000 倍。
4. 覆盖窗口 = 容量 / 产出速率：算例里 1000 条容量在速率 5 时是 200 秒，速率 50 时缩到 20 秒。而速率为 0 时是 `Infinity`。
5. 回溯需求反推容量：要支持 10 分钟回溯，速率 5 时需要 3000 条。
6. 溢出策略必须显式：`fail` 与 `dropOldest` 的差别，以及为什么不能默认丢弃。
7. 工业界怎么做：CQRS、事件溯源、缓存写策略（直写/回写）、幂等键、状态机持久化。

## 一、为什么状态会静默地出错

### 1.1 双写不一致

会话历史同时写进数据库和镜像文件。某次镜像写失败，**两份状态从此不同**，而没有任何报警。

### 1.2 派生状态与真相不符

缓存里存了"消息条数"。真相源里删了两条消息，但缓存没有失效。**界面显示 100 条，实际 98 条。**

### 1.3 缓冲写满后开始丢东西

一个环形缓冲在正常运行，直到流量翻十倍。**它开始丢弃最早的数据**，而下游的"回溯 10 分钟"功能静默失效。

这三件事分别对应：**真相源、派生一致性、覆盖窗口。**

## 二、状态三分类与变更四级

两个维度共同决定"要多大谨慎"：

| 维度 | 取值 | 决定 |
|---|---|---|
| 状态类型 | 权威 / 派生 / 临时 | 能否重建 |
| 变更等级 | L0 / L1 / L2 / L3 | 可逆性与影响范围 |

两个维度的组合给出具体做法：一个 L3（触及外部）且权威（不可重建）的状态，需要最重的保护。一个 L0（只动内存）且派生的状态，随便改。

## 三、怎么做

### 3.1 状态三分类

实现如下。

```js
// 三分类：能否从别处重建，决定了它值多少钱
export function classifyState(rebuildable, lifetime) {
  if (!rebuildable) return 'authoritative'          // 不可重建：唯一真相
  if (lifetime === 'operation') return 'ephemeral'  // 一次操作内有效
  return 'derived'                                  // 可从真相重建
}
```

算例实测：

| 输入 | 分类 |
|---|---|
| 不可重建 | **`authoritative`** |
| 可重建 | **`derived`** |
| 一次操作内 | **`ephemeral`** |

三类的处置方式完全不同：

| 类型 | 备份 | 一致性要求 | 丢了会怎样 |
|---|---|---|---|
| 权威 | 必须 | 最高 | 数据永久丢失 |
| 派生 | 不必 | 可最终一致 | 重建即可 |
| 临时 | 不必 | 无 | 无影响 |

**最常见的错误是把权威状态当派生状态处理**（"反正能重建"），直到某次真的丢了才发现重建不了。

### 3.2 真相源唯一

**每份数据只能有一个写入方。** 两个写入方就是"双写"，它必然导致不一致（除非有事务，而跨系统没有事务）。

```js
// 真相源检查：同一份数据出现多个写入方即报警
export function checkSingleSource(writers) {
  return Object.entries(writers).filter(([, sources]) => sources.length > 1)
}
```

算例实测：

| 情况 | 结果 |
|---|---|
| 唯一写入方 | `true` |
| **双写** | `[["messages", ["session-store", "mirror"]]]` |

为什么双写一定会坏：两次写之间有一个窗口，窗口里崩溃就产生不一致。**加上网络失败、重试、并发，"两次都成功"本身就是小概率事件。**

双写的正确替代：

| 想做 | 不要 | 应该 |
|---|---|---|
| 备份 | 并行写两份 | 从真相复制（异步、可重放） |
| 加速读 | 缓存 + 主库双写 | 缓存只写一份，失效时回源 |
| 跨系统同步 | 双写两个系统 | 用事件 + 幂等消费 |

### 3.3 变更等级 L0 到 L3

| 等级 | 变更范围 | 例子 |
|---|---|---|
| **L0** | 只动内存 | 改一个局部变量 |
| **L1** | 写本地数据 | 写本地文件、本地数据库 |
| **L2** | 跨机器 | 写远端服务、发消息 |
| **L3** | 触及外部 | 发邮件、扣款、调用第三方 |

实现如下。

```js
// 变更等级：范围越大，可逆性越差
export function changeLevel(scope) {
  return { memory: 'L0', localData: 'L1', remote: 'L2', external: 'L3' }[scope]
}
```

算例实测（这是本篇最该记住的对照）：

| 等级 | 可容忍缺陷率 |
|---|---|
| **L0** | **10.00** |
| **L3** | **0.0100** |
| 比值 | **1000 倍** |

读法：L0 的改动可以频繁做（缺陷率 10 也接受），L3 的改动必须极其谨慎。**这条结论与 1.1 的"双向门 vs 单向门"是同一个模型**——它们都来自"单位代价相差三个数量级"。

实践判据：**动手前先给改动定级。** 如果定不出级，说明影响范围还没弄清楚（回到 1.1 的影响面分析）。

### 3.4 派生状态与重建

派生状态的正确做法是：**把它当作缓存，随时可以从真相源重建**。

重建必须满足：

1. **重建是确定性的**：同样的真相源，重建出同样的派生状态。
2. 重建是幂等的：重建两次结果相同（见持久化的幂等性）。
3. 重建有界：重建时间可接受（否则需要检查点，见 3.5 持久化）。

一个可执行的判据：**删掉全部派生状态，系统应当能在可接受时间内恢复。** 如果做不到，说明有些"派生"其实是权威的——分类错了。

### 3.5 覆盖窗口：容量与速率的比值

缓冲能覆盖多长时间，取决于两个数：

$$
W = \frac{C}{r}
$$

（$C$ 为容量（条数），$r$ 为产出速率（条/秒）。）

```js
// 覆盖窗口：容量除以速率，得到能回溯的秒数
export function coverageWindow(capacity, rate) {
  return rate === 0 ? Infinity : capacity / rate
}
```

算例实测（这组数字很值得记住）：

| 容量 | 速率 | 窗口 |
|---|---|---|
| 1000 | 5 | **200 秒** |
| 1000 | **50** | **20 秒** |
| 1000 | **0** | **`Infinity`** |

三个结论：

1. **速率上升会线性缩短窗口**：速率涨十倍，窗口缩短十倍。这是缓冲类设计最容易踩的坑——正常运行半年，流量涨了，功能静默失效。
2. 速率为 0 时窗口是 `Infinity`：这个值是有意义的——如果根本没有产出，缓冲永远不会被覆盖。但它同时意味着"这个公式在低速率下给出的窗口会大得没有意义"，需要配一个绝对上限（见第八节）。
3. 反过来可以反推容量：要支持 10 分钟（600 秒）回溯、速率 5，需要 3000 条。

这条反推是设计缓冲的标准做法：**先定回溯需求，再算容量**，而不是反过来。

### 3.6 溢出策略：显式选择而不是默认丢弃

缓冲写满时必须有明确的策略：

```js
// 溢出策略：失败或淘汰最旧的，并且必须给出可观测的信号
export function onOverflow(policy, incoming, capacity) {
  if (policy === 'fail') return { policy, signal: '返回错误', observable: true }
  const dropped = incoming - capacity
  return { policy, signal: `淘汰计数 ${dropped}`, observable: true }
}
```

算例实测（淘汰 12 条时）：

| 策略 | 信号 | 可观测 |
|---|---|---|
| `fail` | 返回错误 | `true` |
| `dropOldest` | 淘汰计数 12 | `true` |

**关键点不是选哪个，而是"必须给出可观测的信号"**。默认静默丢弃是最糟的选择——它让故障变成静默的数据丢失。

两种策略的适用：

| 策略 | 适用 | 代价 |
|---|---|---|
| `fail` | 数据不可丢（日志、审计） | 上游要处理失败 |
| `dropOldest` | 可容忍丢失（遥测、UI 缓冲） | 需要计数与告警 |

## 四、特殊情况与处理技巧

| 情况 | 为什么 | 处理 |
|---|---|---|
| 两份状态不一致 | 双写 | 改成单一写入方 + 异步复制 |
| 派生数据与真相不符 | 缓存没失效 | 加失效机制 + 定期校验 |
| 缓存突然丢了很多 | 速率上升导致窗口缩短 | 按速率重算容量并加绝对上限 |
| 删了缓存起不来 | 有"派生"其实是权威 | 重新分类，补持久化 |
| 状态迁移到一半崩了 | 迁移不可逆 | 拆成双写 → 切读 → 清理三步 |
| 并发写同一份状态 | 无并发控制 | 用乐观锁（版本号）或串行化 |
| 时钟回拨导致顺序错乱 | 用时间排序 | 用单调序号 |
| 状态越存越大 | 无保留策略 | 明确的保留窗口 + 归档 |

最后一条与 3.5 的覆盖窗口是同一个问题：**存储与缓冲都需要"保留多长时间"的明确决定**，否则它会退化成一个不断增长的负担。

## 五、工业界的做法（可照做）

### 5.1 状态的三种架构模式

| 模式 | 做法 | 适用 |
|---|---|---|
| **单写多读** | 一个写入方，多个只读副本 | 大多数场景的默认 |
| **CQRS** | 写模型与读模型分离，通过事件同步 | 读写模式差异大 |
| **事件溯源** | 只存事件，状态是派生的 | 需要审计、回溯、时间旅行 |

事件溯源与本篇的关系最直接：它把"权威状态"缩小到"事件日志"，**其余全部变成派生**。这样重建路径清晰，而代价是读操作要从事件重放（需要快照优化）。

### 5.2 缓存的写策略

| 策略 | 做法 | 一致性 | 延迟 |
|---|---|---|---|
| **Cache-Aside** | 读时填充，写时失效 | 最终一致 | 首次读慢 |
| **Write-Through** | 写缓存同时写主库 | 强 | 写慢 |
| **Write-Behind** | 写缓存，异步刷主库 | 弱（可能丢） | 写快 |
| **Read-Through** | 缓存负责回源 | 最终一致 | 透明 |

默认推荐 Cache-Aside + 失效：它把"两份状态的一致性"问题简化为"失效是否及时"。

参数起点：TTL 取业务可容忍的陈旧时长（秒级到分钟级），容量按 3.5 的公式反推，并且**必须配淘汰计数指标**。

### 5.3 幂等与并发控制

写状态时的两个基本手段：

| 手段 | 解决 | 做法 |
|---|---|---|
| **幂等键** | 重复提交 | 客户端生成键，服务端去重 |
| **乐观锁** | 并发覆盖 | 带版本号，冲突则重试 |
| **幂等操作** | 重放 | 让写操作天然幂等（赋值而非累加） |

**这三条与 3.1 的重试、3.5 的持久化是同一套工具的三种用法。**

### 5.4 一份可落地的实施清单

1. **状态清单**：列出全部状态，逐个标三分类。
2. 真相源图：每个数据标出唯一写入方，双写即报警。
3. 等级标注：每个改动标 L0–L3，按等级走不同流程。
4. 重建验证：定期删掉派生状态，验证能重建。
5. 容量反推：按回溯需求算容量，按峰值速率校验。
6. 绝对上限：为覆盖窗口设上限（防止低速率下的荒谬值）。
7. 溢出策略：显式选择并暴露计数指标。
8. 保留策略：明确每类状态的保留时长与归档方式。
9. 并发控制：写操作带幂等键或版本号。
10. 迁移三步：双写 → 切读 → 清理，每步可停。

## 六、学术界的结论

### 6.1 CAP 与 PACELC

CAP 定理：网络分区（P）发生时，一致性（C）与可用性（A）只能二选一。

**PACELC** 是它更实用的扩展：分区时在 C 与 A 之间选择，否则（E，即正常时）在延迟（L）与一致性（C）之间选择。

它对状态设计的直接含义：**一致性不是一个"要或不要"的开关，而是每个操作的一个选择。** 同一个系统里，余额查询可以最终一致，扣款必须强一致。

实践判据：为每类状态单独决定一致性级别，而不是给整个系统定一个。

### 6.2 一致性强度的谱系

| 级别 | 保证 | 代价 |
|---|---|---|
| **线性一致** | 所有操作看起来是瞬时、全序的 | 最慢（需要协调） |
| **顺序一致** | 所有节点看到相同的顺序 | 较慢 |
| **因果一致** | 有因果关系的操作保序 | 中等 |
| **最终一致** | 停止写入后最终收敛 | 最快 |

关键认识：**越强的保证越贵，而大多数场景不需要最强的**。会话历史通常最终一致即可，而配额扣减需要线性一致。

### 6.3 快照隔离与 MVCC

数据库领域的主流并发控制：**每个事务看到某个时间点的快照**，写冲突在提交时检测。

它对本篇的启示：**"读一个稳定的状态快照"本身就是一种并发控制手段**。当你要遍历状态时，先取快照，而不是边遍历边受写入影响。

对 agent 系统的应用：构造模型请求时，**先取会话状态的一个快照**，再拼装。这样并发写入不会让请求内容自相矛盾。

### 6.4 状态机复制

分布式系统的经典方法：**所有副本从相同初始状态出发，按相同顺序执行相同操作，得到相同状态。**

它的两个前提：

1. **确定性**：同样的输入产生同样的输出。
2. 顺序一致：所有副本按同一顺序执行。

对 agent 系统的直接意义：如果会话状态由"事件序列"定义，那么**只要事件顺序确定，状态就可以被任何副本重建**——这正是事件溯源的理论基础。

一个实践陷阱：**如果操作不是确定性的（例如用了当前时间、随机数、模型输出），重放就不一致。** 解法是把这些不确定性记进日志（把模型输出也当作输入记录下来）。

## 七、理论：一致性强度的谱系

### 7.1 覆盖窗口

$$
W = \frac{C}{r}
$$

算例实测：$C = 1000$、$r = 5$ 得到 **200 秒**。$r = 50$ 得到 20 秒。$r = 0$ 得到 `Infinity`。

反推：要支持 600 秒回溯、$r = 5$，需要 $C = 3000$。

为什么必须同时看容量与速率：**只关注容量会误判**——容量翻倍但速率涨十倍时，窗口其实是缩短的。

### 7.2 变更等级与可容忍缺陷率

$$
p_{\text{容忍}} \propto \frac{1}{c}
$$

算例实测：L0 是 10.00，L3 是 0.0100，**相差 1000 倍**。

**这条与 1.1 的结论完全同构**（双向门 10.00 对 单向门 0.0100），因为它们衡量的是同一件事：单位代价。

可检查的判据：**每个改动都能给出等级，且等级决定流程。** 给不出等级 = 影响范围没弄清。

### 7.3 真相源的唯一性

$$
\forall d \in \text{数据} : |\text{writers}(d)| = 1
$$

算例里违背这条时，检查函数返回违反清单。

为什么必须是 1 而不是"2 且都可靠"：可靠性是概率，**两个 99.99% 可靠的写入方，联合失败概率不是零，而设计必须对确定的情形成立。**

### 第一题：给一个会话系统的状态分类

场景：一个 agent 系统有以下状态：对话消息、工具调用结果、模型上下文缓存、当前回合的临时变量、用户偏好设置、配额计数。

要求：

- 逐个标出三分类（权威 / 派生 / 临时），并说明依据。

一个环形缓冲用于支持"回溯最近 N 分钟的工具输出"。

要求：

- 若速率涨到 15 条/秒，原来的容量还能覆盖多久？

## 十、算例

算例实现了本篇的全部分类与检查函数。

```powershell
cd D:\dsh-course
node examples/sa19_state.mjs        # 全部函数的运行结果
node examples/test_sa19_state.mjs   # 数字回归断言
```

它做到的事：

- 状态三分类（不可重建 → `authoritative`、可重建 → `derived`、一次操作内 → `ephemeral`）。
- 真相源检查（唯一得到 `true`，双写列出 `messages` 的两个写入方）。
- 变更等级（L0/L1/L2/L3）与**可容忍缺陷率对照（10.00 对 0.0100，相差 1000 倍）**。
- 覆盖窗口（C=1000、r=5 得到 200 秒）与反推（10 分钟回溯需要 3000 条）。
- 速率上升到 50 时窗口缩到 20 秒。速率为 0 时窗口是 `Infinity`。
- 溢出策略（`fail` 返回错误、`dropOldest` 报告淘汰计数）。

这一篇只要记住一句：状态要分清**权威、派生、临时**，权威状态只能有一个写入方。改动的谨慎程度由等级 L0–L3 决定（可容忍缺陷率相差 1000 倍）。而缓冲能覆盖多久是容量除以速率——速率涨十倍，窗口就缩十倍。

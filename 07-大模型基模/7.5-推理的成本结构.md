## 读完这一篇你会知道什么

1. **推理的两个阶段**：prefill（读入提示）与 decode（逐 token 生成），它们的瓶颈不同。
2. **延迟该看哪个数**：首 token 延迟与每 token 延迟是两个指标，对应两种优化手段。
3. **批处理换到了什么**：算例实测吞吐涨 4.6 倍，代价是单请求延迟涨 3.5 倍。
4. **并发上限怎么算**：7B 模型 + 24 GiB 卡，4K 上下文能并发 4 条，32K 上下文**一条都放不下**。
5. **钱花在哪**：输入、输出、缓存三档计价，输出单价是输入的 5 倍。
6. **缓存值多少**：命中率 90% 时成本降到 34.9%，全命中降到 27.7%。

## 一、为什么需要知道它

### 1.1 账单比预期高，但不知道该砍哪里

输入、输出、缓存是三档不同的价钱。不知道该砍哪个，就会出现"把提示词精简了 30%，账单只降了 6%"这种事——因为钱主要花在输出上。

### 1.2 用户抱怨"点下去半天没反应"

这是首 token 延迟问题（prefill 慢），而不是生成速度问题。两个指标对应两种完全不同的优化手段，**混在一起讨论就永远优化不对**。

### 1.3 并发上不去，卡没吃满

把上下文从 4K 开到 32K 之后，并发数从 4 掉到 0——不是算力不够，是**显存被 KV cache 吃光了**。这类问题必须靠容量规划提前算出来，不能等到线上。

## 二、两个阶段：读入与生成

| 阶段 | 做什么 | 计算特征 |
|---|---|---|
| **prefill** | 一次性读入全部提示，算出所有位置的 key/value | 计算受限，并行度高 |
| **decode** | 每步只处理一个新 token，但要读完整 cache | 带宽受限，并行度低 |

算例给出的项数比：$T = 2048$ 时 prefill 是 134,217,728 项，而 decode 每步只有 65,536 项——**相差 2048 倍**（恰好是 $T$）。

这个差别决定了：**优化首 token 延迟和优化生成速度，用的是完全不同的手段。**

## 三、怎么做

### 3.1 延迟分解：两种不同的成本

算例实测（CPU，1024 个位置）**：一次算完 1024 个位置要 0.913 ms，而单独算 1 个位置要 0.097 ms**。

- 按"每位置"算，prefill 是 $0.913 / 1024 \approx 0.00089$ ms，比 decode 的 0.097 ms **快 100 倍以上**。
- 原因：prefill 能并行处理所有位置，硬件利用率高。decode 每步只有 1 个位置，大部分时间花在搬运 cache 上。

**这就是"首 token 慢、后续 token 慢"是两回事的定量依据**：prefill 的绝对时间更长，但它的效率其实高得多。

### 3.2 批处理：用延迟换吞吐

把多个请求合成一批，能让硬件同时为多条请求算。算例实测（矩阵 1024×1024，重复 30 次取中位数）：

| batch | 中位耗时 (ms) | 吞吐 (token/s) | 每请求延迟 (ms) |
|---|---|---|---|
| 1 | 0.086 | 11,614 | 0.086 |
| 2 | 0.104 | 19,305 | 0.104 |
| 4 | 0.122 | 32,841 | 0.122 |
| 8 | 0.169 | 47,337 | 0.169 |
| 16 | 0.302 | **53,050** | 0.302 |

**吞吐涨了 4.6 倍，代价是单请求延迟涨了 3.5 倍。** 这是一条无法回避的权衡：批越大人均越便宜，但每条请求都要等更久。

关于测量本身：这份数据我最初用 512×512 的矩阵、只测一次，得到的是 `0.051 / 0.158 / 0.135 / 0.080 / 0.182`——**完全不单调**。加大规模并取 30 次的中位数之后才变得干净。这不是"性能波动"，而是**单次测量不足以形成结论**（与 7.4 的卡方案例是同一条道理）。

### 3.3 显存与并发上限

显存分两大部分：权重与 KV cache。

$$
\text{cache (GiB)} = \frac{2 \times B \times H \times T \times D \times \text{层数} \times \text{每元素字节}}{1024^3}
$$

算例实测：7B 参数的 fp16 权重是 13.0 GiB。单请求 cache 在 $T=4096$ 时是 2.0000 GiB，$T=32768$ 时是 **16.0000 GiB**（正好 8 倍）。

由此算出并发上限（24 GiB 卡，预留 2 GiB）：

| 上下文长度 | 单请求 cache | 最多并发 |
|---|---|---|
| 4096 | 2.00 GiB | **4 条** |
| 32768 | 16.00 GiB | **0 条** |

32K 上下文的结论是"一条都放不下"：$24 - 13 - 2 = 9$ GiB 剩余，而单条就要 16 GiB。这类结论必须靠算，不能靠猜。

### 3.4 成本公式：三档计价

$$
\text{成本} = n_{\text{in}} \cdot p_{\text{in}} + n_{\text{out}} \cdot p_{\text{out}} + n_{\text{cached}} \cdot p_{\text{cached}}
$$

算例用 $p_{\text{in}} = 3$、$p_{\text{out}} = 15$、$p_{\text{cached}} = 0.3$（每百万 token 的相对单价）实测：

| 场景 | 成本 |
|---|---|
| 无缓存（1000 输入 + 500 输出） | 10,500 |
| 命中 800 个输入 token | 8,340（省 20.6%） |
| 长输出（5000） | 78,000 |
| 长输入（6000） | 25,500 |

**输出单价是输入的 5 倍**，所以长输出的成本远高于同等的长输入——**"少说话"往往比"少读"更省钱**。

### 3.5 缓存值多少：命中率决定一切

| 命中率 | 成本 | 占无缓存 |
|---|---|---|
| 0% | 15,288 | 100.0% |
| 50% | 9,758.4 | 63.8% |
| 90% | 5,335.8 | 34.9% |
| 100% | 4,228.8 | **27.7%** |

这是 agent 系统里最值钱的一条优化：如果多轮对话的前缀保持稳定，成本可以降到三分之一以下。而它的前提与 3.3 的压缩策略、7.2 的 cache 失效直接冲突——**压缩会打断前缀，改动提示开头会让整段前缀失效**。

## 四、特殊情况与处理技巧

| 情况 | 为什么 | 处理 |
|---|---|---|
| 首 token 慢、生成速度正常 | prefill 计算受限 | 缩短输入、提高并行、用更快的 prefill 实现 |
| 生成慢、首 token 正常 | decode 带宽受限 | 减 cache、用量化、提高批大小 |
| 并发上不去 | cache 占满显存 | 降低上下文长度、量化 cache、分组查询注意力 |
| 缓存命中率低 | 前缀被改动 | 把稳定内容放前面，把变化内容放到最后 |
| 成本砍不动 | 钱花在输出上 | 限制最大输出长度、要求简洁回答 |
| 长上下文延迟暴涨 | 项数按 $T^2$ | 先估项数，再决定是否真的需要这么长 |
| 批处理导致结果变化 | 批内数值顺序影响浮点 | 复现时固定批大小 |

一条通用技巧：**先把延迟拆成首 token 与每 token 两个数再讨论优化。** 只有一个总数时，任何优化讨论都会变成猜测。

## 五、理论：两种瓶颈

prefill 与 decode 的差别来自**算术强度**（每读一个字节能做的计算量）：

- **prefill**：$T$ 个位置一起算，矩阵乘的规模大，算术强度高——瓶颈是**算力**。
- **decode**：每步只有 1 个位置，却要把整个 cache 读一遍，算术强度低——瓶颈是**显存带宽**。

由此推出三条结论：

1. **加法不能相互替代**。加算力对 decode 帮助有限，因为它在等数据。
2. **批处理对 decode 收益更大**：把多条请求的 decode 合在一起，等于让同一份被读入的权重服务更多请求，直接改善算术强度。
3. **减少需要读的数据永远有效**：量化 cache、分组查询注意力、缩短上下文——都是在减少 decode 每步必须搬的字节。

**首 token 延迟与每 token 延迟是两个独立的设计目标**，产品上说"要快"时必须先问清是哪一个。

## 六、工程化

| 项 | 内容 |
|---|---|
| 两个延迟指标 | 首 token 延迟与每 token 延迟分开观测与告警 |
| 容量规划 | 按权重 + cache 提前算出并发上限，写进容量文档 |
| 批处理策略 | 按延迟预算设最大批大小，而不是一味求大 |
| 成本归因 | 输入 / 输出 / 缓存三档分开记账，能回答"钱花在哪" |
| 缓存友好设计 | 提示前缀保持稳定，变化内容放最后 |
| 输出长度控制 | 最大输出长度是成本的主要旋钮之一 |
| 超时与降级 | 长上下文请求要有超时与降级路径，而不是无限等待 |

## 七、练习

### 第一题：算出并发上限并给出建议

硬件：单卡 80 GiB，模型 13B（fp16），32 层、32 头、每头 128 维。产品要求支持 16K 上下文。

要求：

- 算出模型权重的显存占用。
- 算出单请求在 16K 上下文下的 KV cache 占用。
- 算出最多能并发多少条请求（预留 4 GiB）。
- 如果并发数不够，给出两条互不相同的改进方向，并说明各自的代价。

---

### 第二题：把账单拆开

一个月度报告：总成本 12,000 元，其中输入 2,400 元、输出 7,200 元、缓存 2,400 元。已知缓存单价是输入的 0.1 倍、输出单价是输入的 5 倍。

要求：

- 反推出三档的 token 量比例（输入 : 输出 : 缓存）。
- 判断"精简提示词"与"限制输出长度"哪个降本更有效，并给出量化依据。
- 如果要把缓存成本从 2,400 元降下来，你会改动什么？说明它与上下文压缩策略的冲突在哪里。

提示：第三问的答案是"提高命中率不会降低缓存成本，反而会提高"——因为命中越多，走缓存计价的 token 越多。真正的降本方向是"减少总 token 量"，而不是"改变计价档位"。

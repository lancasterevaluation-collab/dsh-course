# 7.2 注意力与 KV cache

> **这一篇讲什么**：注意力是模型唯一"跨位置看信息"的机制，它的成本随上下文长度**平方增长**。KV cache 是把这个成本压下去的关键手段，代价是显存。理解这两件事，你就知道自己那些"上下文太长"的报错到底贵在哪里。

## 读完这一篇你会知道什么

1. **注意力在做什么**：每个位置用 query 去和所有历史位置的 key 比对，再按权重要回它们的 value。
2. **成本怎么算**：注意力项数是 $B \cdot H \cdot T \cdot S$，序列长度翻倍就是四倍。
3. **KV cache 是什么**：把历史的 key 与 value 存下来，解码时不再重算——省的是"重算历史"，不是"注意历史"。
4. **缓存的代价**：显存占用随上下文线性增长，32K 上下文、32 层、32 头的模型要 16 GiB。
5. **长上下文为什么贵**：平方的计算量、线性的显存、以及缓存与压缩之间的冲突。
6. **工程上要补什么**：批处理、分页、量化、以及缓存失效的处理。

## 一、为什么需要知道它

### 1.1 上下文从 4K 加到 16K，延迟涨了十几倍

产品的需求是"支持长文档"。长度翻两番，你预期延迟涨四倍左右，实际涨得更多。原因是注意力的计算量按长度**平方**增长——4K 到 16K 是 16 倍。

### 1.2 输出第 1000 个 token 时，每一步都变慢了

生成长回答时，越到后面越慢。因为每生成一个 token，模型都要重新"看"一遍全部历史。KV cache 解决的正是这件事——它把"重看历史"变成"读缓存"。

### 1.3 上下文开到 32K，显存直接爆了

一个 32 层、32 头、每头 128 维的模型，在 32K 上下文下单条请求的 KV cache 就要 **16 GiB**（算例实测值）。模型权重之外，这部分是纯增量——**并发几条就再乘几倍**。

这三件事指向同一组量：**注意力项数、FLOPs、cache 字节数**。它们都可以算出来。

## 二、注意力是什么

### 2.1 三个投影：query、key、value

每个位置的输入向量做三个线性变换，得到 query（我要找什么）、key（我提供什么）、value（我提供的内容）。然后：

```python
def attention(q, k, v, mask=None):
    """缩放点积注意力。q:(B,H,T,D)，k/v:(B,H,S,D) -> (B,H,T,D)"""
    d = q.size(-1)
    scores = (q @ k.transpose(-2, -1)) / math.sqrt(d)   # (T,S) 的比分行
    if mask is not None:
        scores = scores.masked_fill(mask, float("-inf"))  # 遮住不该看的位置
    return torch.softmax(scores, dim=-1) @ v            # (T,S) @ (S,D) -> (T,D)
```

**两处矩阵乘法决定成本**：`q @ kᵀ` 是 $(T \times S)$ 个点积，`softmax(...) @ v` 又是 $(T \times S \times D)$ 的工作量。**注意力的项数就是 $B \cdot H \cdot T \cdot S$。**

### 2.2 因果掩码：不能看未来

自回归模型在每个位置只能看到它自己和之前的 token。做法是把上三角（不含对角线）的分数设成负无穷：

```python
def causal_mask(t):
    """上三角（不含对角线）为 True，表示"看不见未来"。"""
    return torch.triu(torch.ones(t, t, dtype=torch.bool), diagonal=1)
```

算例验证了这一点：把第 5 个 token 换掉，**前 4 个位置的输出误差是 0.000e+00**，而第 5 个位置确实变了。

### 2.3 一个具体数字

序列长度 1024 时，注意力项数是 $1024^2 = 1{,}048{,}576$。长度到 2048，项数是 $2048^2 = 4{,}194{,}304$——**正好四倍**。

## 三、怎么做

### 3.1 KV cache：存住历史，只算新位置

解码时每个新 token 只有一个 query，但它要和全部历史的 key/value 比对。如果每步都重算历史，工作量随步数**立方**增长。缓存把历史的 k/v 留下来：

```python
def forward(self, x, cache=None):
    q, k, v = x @ self.w_q, x @ self.w_k, x @ self.w_v
    if cache is not None:
        k = torch.cat([cache["k"], k], dim=1)   # 历史 key 接上来
        v = torch.cat([cache["v"], v], dim=1)   # 历史 value 接上来
        out = attention(q.unsqueeze(1), k.unsqueeze(1), v.unsqueeze(1))
        cache["k"], cache["v"] = k, v
        return out.squeeze(1)
    return attention(q.unsqueeze(1), k.unsqueeze(1), v.unsqueeze(1), causal_mask(x.size(1))).squeeze(1)
```

**正确性必须被验证，不能靠推导**。算例做了这件事：逐步解码 32 个位置，与整段重算对比，**最大误差 9.991e-13**（float64 下的浮点噪声），即两者数值等价。

**省下多少**：32 步解码，重算需要 11,440 个注意力项，带 cache 只需 528 个——**省 21.7 倍**。注意这个比值随长度增长：缓存把 $O(T^3)$ 的重算降到 $O(T^2)$。

### 3.2 两种场景的成本差别：prefill 与 decode

| 场景 | query 数 | 注意力项数 | 特点 |
|---|---|---|---|
| **prefill**（读入提示） | $T$ | $T \times T$ | 一次性算完，能吃满并行 |
| **decode**（逐 token 生成） | 1 | $1 \times T$ | 每步都要读完整 cache，受显存带宽限制 |

$T = 4096$ 时，prefill 是 16,777,216 项，decode 每步 4,096 项——**相差 4096 倍**。

这个差别解释了**首 token 延迟与后续 token 延迟不是一回事**：前者是"算得慢"（计算受限），后者是"读得慢"（带宽受限）。优化它们的手段完全不同。

### 3.3 缓存占多少显存

它有一个可以直接算的公式。

$$
\text{cache 字节} = 2 \times B \times H \times T \times D_{\text{head}} \times \text{层数} \times \text{每元素字节}
$$

其中系数 2 是 key 与 value 各一份。算例实测：$B=1$、$H=32$、$T=32768$、$D=128$、32 层、fp16 时是 **16.0 GiB**。每层每 token 是 $2 \times 32 \times 128 \times 2 = 16{,}384$ 字节。

**这个数字随上下文线性增长，随并发线性增长。** 32K 上下文、4 路并发就是 64 GiB——比模型权重还大。

### 3.4 训练与推理的算力估算

两个常用的粗略公式：

| 阶段 | 公式 | 含义 |
|---|---|---|
| 训练 | $6ND$ | $N$ 参数、$D$ 个 token |
| 推理 | $2N$（每 token） | 每个参数参与一次乘加 |

算例验算了它们：$N=10^6$、$D=1000$ 时训练是 $6 \times 10^9$ FLOPs，推理每 token 是 $2 \times 10^6$——**训练单个 token 比推理贵 $3D$ 倍**。

这条比例的工程含义很直接：**用提示与上下文解决的问题，比用微调解决便宜几个数量级**（这也是 7.3 的主题）。

## 四、特殊情况与处理技巧

| 情况 | 为什么 | 处理 |
|---|---|---|
| 长上下文延迟超预期 | 计算量按长度平方 | 先估项数再决定是否需要更长的窗口 |
| 生成越到后面越慢 | 每步重新注意全部历史 | KV cache（若框架未默认开启） |
| cache 显存爆掉 | 随 $T$ 与并发线性增长 | 降低并发、缩短保留上下文、用量化 cache |
| 前缀改动导致整体重算 | 缓存按前缀匹配，前面变了后面全失效 | 把稳定内容放前面（与 3.3 的压缩点选择直接冲突） |
| 压缩与 cache 打架 | 压缩改写了历史，缓存随之失效 | 压缩尽量放在"一段任务结束时"，而不是每轮都压 |
| 多轮对话越来越慢 | 每轮都重新 prefill 全部历史 | 保留服务端 cache，或把长历史外部化 |
| 精度不够导致输出漂移 | 低精度 cache 会累积误差 | 长上下文时用更高精度，或定期重算 |

**一条通用技巧**：先分清瓶颈在"算"还是在"读"。prefill 慢是算力问题（可以加并行、加批），decode 慢是带宽问题（要减 cache、提精度效率）。**用错手段优化不会有效果。**

## 五、理论：为什么是平方

注意力要算"每个 query 与每个 key 的关系"。$T$ 个 query、$S$ 个 key，关系数是 $T \times S$。当 $T = S$（自注意力）时就是 $T^2$。

- 序列长度翻倍 ⇒ 项数变四倍。
- 加上 $D$ 维度的乘加，总 FLOPs 约为 $2 \cdot B \cdot H \cdot T \cdot S \cdot D$（每个项两次乘加）。

由此得到三条工程结论：

1. **上下文长度的成本是超线性的**。"支持两倍长度"不是两倍成本，而是四倍注意力计算（cache 显存倒是线性的）。
2. **KV cache 不改变平方项，它只删除"重算"**。decode 每步仍然是 $1 \times T$——注意历史本身的成本无法消除。
3. **能减少"要看的 token 数"的手段都值钱**：检索、压缩、外置（3.3）都是在减小 $T$。

关于实测：算例打印了 CPU 上的实际耗时，从 T=256 到 T=2048 是 0.96 ms 到 17.10 ms，这不是标准的四倍关系。原因是小规模下常数开销（框架调度、内存分配）占比很大。所以算例只用项数做断言，耗时只打印不作判据。**这也是评测的一条通则：判据要用确定的量，不要用受环境噪声影响的量。**

## 六、工程化

| 项 | 内容 |
|---|---|
| 容量规划 | 按 $B \cdot H \cdot T \cdot D \cdot 2$ 估算 cache，先算再决定并发上限 |
| 批处理 | 把多个请求合批能提高算力利用率，但 cache 显存按批大小翻倍 |
| cache 复用 | 相同前缀可跨请求复用（前缀缓存），前提是前缀逐字节相同 |
| 分页 | 把 cache 分成固定大小的块按需分配，减少碎片 |
| 量化 | 低精度 cache 省显存，代价是精度与可能的输出漂移 |
| 分组查询注意力 | 多个 query 头共享一组 k/v 头，直接按比例削减 cache |
| 可观测 | 分别观测首 token 延迟与每 token 延迟（它们对应不同瓶颈） |

## 七、练习

### 第一题：算出一个上限

模型：32 层、32 头、每头 128 维、fp16。单张卡 24 GiB 显存，模型权重占 14 GiB。

要求：

- 算出单条请求在 $T = 8\mathrm{K}$ 时的 KV cache 占用。
- 算出理论上还能并发多少条请求（考虑还要留约 2 GiB 作临时空间）。
- 如果产品要求 32K 上下文，重复上面的计算，并说明你会优先改什么。

**提示**：这一题的答案是"上限很低"——这正是长上下文服务贵的原因，也是量化 cache 与分组查询注意力被发明出来的原因。

---

### 第二题：找出瓶颈在算还是在读

一个服务报障：**首 token 延迟 0.4 s（正常），但生成 2000 个 token 要 90 s**（每 token 约 45 ms，明显偏慢）。

要求：

- 判断瓶颈更像"算"还是"读"，并说明依据（用 prefill 与 decode 的项数差别解释）。
- 给出两条互不相同的优化方向，并说明各自代价。
- 说明"降低上下文保留量"为什么对这个问题**可能**有效，以及它的副作用。

**提示**：decode 每步的项数是 $1 \times T$——若 $T$ 很大，每步都要读一遍完整 cache（带宽受限）。

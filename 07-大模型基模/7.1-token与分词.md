## 读完这一篇你会知道什么

1. **一个 token 是什么**：不是字，不是词，是分词器切出来的片段。
2. **为什么它决定成本**：模型按 token 计费与限长，而不同内容的"每字 token 数"差别很大。
3. **怎么估**：给你一段文本，能大致算出它要花多少 token。
4. **哪些内容特别贵**：中文、代码、JSON、长数字串——以及各自贵多少。
5. **为什么不按字符算**：分词器一旦训练完成就固定，它决定了模型的输入单位。
6. **工程上要补什么**：预算估算、计量埋点、成本归因。

## 一、为什么需要知道它

### 1.1 账单比预期高了好几倍

功能上线后成本是估算的三倍。查下来只是因为提示词是中文，而你按"字符数"估的——中文的一个汉字经常对应一个多 token，而英文的一个单词也常常只占一个多 token。

### 1.2 一段代码把上下文吃掉了大半

任务里贴进来一个 800 行的配置文件。它看起来不长（大约 30 KB），但它占掉的 token 数远超你的预期——**代码里的符号、缩进、括号都是 token**。

### 1.3 缓存明明配了，却没省下钱

本想让重复的前缀命中缓存，结果命中率很低。原因之一是你以为"每轮只有一小段变化"，而实际变化的位置在很靠前的地方，导致整段前缀都失效了。

这三件事都由同一个量决定：**token**。

## 二、token 是什么

### 2.1 不是字，不是词

模型不读字符，也不读单词。它读 **token**——分词器（tokenizer）把文本切成的一串片段。

- 常见词往往是**一个** token：`the`、`data`、`model`
- 长词会被切开：`tokenization` 可能是 `token` + `ization`
- 中文通常**一个字一到两个** token
- 代码里的符号大多是独立 token：`{`、`}`、`(`、`;`、`\n`

### 2.2 分词的直觉：常见片段合成一个

现代分词器多数用 BPE（byte pair encoding）一类的做法。它的直觉是：

1. 从单字节开始。
2. 统计什么片段最常一起出现。
3. 把它们合并成一个新 token，重复很多轮。

结果是：**越常见的内容越"省"**。英文常用词往往是一整个 token，而罕见词、专有名词、随机字符串会被切成很多片。

### 2.3 一个具体的例子

同样一段意思，用不同写法表达，token 数可以差很多。下表的"本课程实测"来自本文算例里从零实现的 BPE（词表仅 284），"生产级典型值"来自常见商用分词器（词表 10 万以上）：

| 内容 | 字符数 | 本课程实测（每字符） | 生产级典型值（每字符） |
|---|---|---|---|
| 英文句子 | 69 | 0.681 | 约 0.25 |
| 中文句子 | 22 | **2.000** | 约 1.0–1.5 |
| JSON 配置 | 46 | 0.761 | 约 0.5 |
| 一段代码 | 49 | 0.694 | 约 0.4 |
| UUID | 36 | **1.000** | 1.0 |

两组数字的差距本身是一个知识点：分词器的压缩能力取决于它的训练语料规模与词表大小。本课程的小 BPE 只训练了 200 次合并，所以英文压缩得不够好。但**两个结论在两组数字下都成立**：

- **中文的每字符 token 数明显高于英文**（实测 2.000 vs 0.681，相差约 3 倍）。
- **UUID 这类随机串几乎无法压缩**（实测正好 1.000，一个字符一个 token）。

## 三、怎么做

### 3.1 估算：先要一个粗略系数

没有一个系数对全部内容都准，但按内容类型分档估已经够用：

```js
// 按内容类型估算 token 数（粗略系数，误差约 ±20%）
export function estimateTokens(text, kind = 'prose') {
  const perChar = { prose: 0.25, chinese: 0.9, code: 0.65, json: 0.75 }[kind] ?? 0.3
  return Math.ceil(text.length * perChar)
}
```

用法：做容量规划时用它，做精确计费时用真实计量（见 3.2）。**估算的作用是让设计阶段的数量级不出错**，不是替代真实计量。

### 3.2 计量：以模型返回的用量为准

每次调用都会返回真实用量，这是唯一权威的数字。

```js
// 每次调用都记下真实用量，用它校准估算、做成本归因
export function recordUsage(call, usage) {
  return {
    session: call.session,
    task: call.task,
    inputTokens: usage.inputTokens,
    outputTokens: usage.outputTokens,
    cachedTokens: usage.cachedInputTokens ?? 0,
    at: call.at,
  }
}
```

为什么要记 `cachedTokens`：命中缓存的部分通常便宜很多（有时便宜一个数量级）。不分开记，你无法判断"成本高"是因为内容多，还是因为缓存没生效。

### 3.3 预算：窗口是硬约束，永远留余量

上下文窗口是硬上限，超了就直接失败。因此预算要分三份，而不是用满：

| 部分 | 占比（经验值） | 说明 |
|---|---|---|
| 常驻 | 10–20% | 系统提示、工具定义 |
| 历史 | ≤ 60% | 对话与工具结果，超了就压缩 |
| 输出余量 | 20–30% | 给模型自己的输出留空间 |

输出余量必须单独留：输入和输出共享同一个窗口。输入占到 95% 时，模型已经没有空间写回答了。

## 四、特殊情况与处理技巧

| 情况 | 为什么 | 处理 |
|---|---|---|
| 中文内容贵 | 一个汉字常占 1–2 token | 提示词能英文就别中文（但回答语言让用户定） |
| 代码与 JSON 贵 | 符号、缩进、括号各自成 token | 只贴相关片段，别整文件粘贴 |
| 长数字串极贵 | 随机数字无法合成常见片段 | 用 ID 或摘要代替完整数字串 |
| 表格与 Markdown 贵 | 竖线与短横线都是 token | 给模型的数据用紧凑格式（如 CSV） |
| 同一内容在不同上下文分词不同 | 分词看相邻字符 | 别按"这个词固定几个 token"做精确预算 |
| 重复前缀不命中缓存 | 变化发生在前部，整段前缀失效 | 把稳定内容放前面，变化内容放后面 |
| 估算与实际差很多 | 内容类型混在一起 | 按类型分段估，再用真实用量校准 |

一条通用技巧：**先量再优化。** 在不知道真实用量之前做的"优化"（改提示、换格式）很可能是猜的，而它带来的收益通常不如"少贴一段无关内容"。

## 五、理论：计量单位由谁决定

模型的输入单位是 **token**，这一点由训练时使用的分词器固定下来，之后不再改变。

由此推出三条工程结论：

1. **"上下文长度"这个数字必须以 token 理解。** 看到"128K 上下文"，那是 128K token，不是 12.8 万个汉字，也不是 128 KB 文本。
2. **分词器不能随便换。** 换分词器等于换模型（词表变了，权重就对不上）。所以"某个词占几个 token"这件事在一个模型上是固定的常量。
3. **成本与长度都是 token 的线性函数**（在不用缓存时）。这让"多贴一段内容要花多少钱"变成可算的，而不是凭感觉的。

## 六、工程化

| 项 | 内容 |
|---|---|
| 预算估算器 | 按内容类型分档的估算函数，只用于设计阶段 |
| 计量埋点 | 每次调用记 input / output / cached 三类用量 |
| 成本归因 | 按会话、按任务聚合，能回答"哪一类任务最贵" |
| 阈值单位 | 所有截断、压缩、限额都用 token，不用字符 |
| 校准机制 | 用真实用量反推估算系数，定期更新 |
| 暴露给用户 | 让用户能看到"这次花了多少"，它本身能改变使用行为 |

## 七、练习

### 第一题：估算并解释三倍差

下面三段内容表达同一件事（"把日志级别从 info 改成 debug 并重新部署"）：

```
A  Please change the log level from info to debug, then redeploy the service.
B  请把日志级别从 info 改成 debug，然后重新部署服务。
C  {"action":"set_log_level","level":"debug","redeploy":true}
```

要求：

- 用 3.1 的系数分别估算它们的 token 数，算出最大值与最小值的比值。
- 解释这个比值来自哪里（是内容变多了，还是编码方式变了）。
- 如果这个提示每秒被调用 100 次，选 A 与选 C 的成本差多少倍？

### 第二题：给一个真实任务分配预算

任务：让模型读一份 20 页的中文需求文档，然后改一个函数。上下文窗口 128K token。

要求：

- 用 3.1 的系数估算"整篇文档贴进去"要多少 token，算出它占窗口的比例。
- 给出你的预算分配（常驻 / 历史 / 输出余量），并说明为什么不能把文档整篇贴进去。
- 提出至少一种"让模型看到必要信息但不贴全文"的做法，并说明它的代价。

提示：第二题的答案不只是"压缩"，也可以考虑"先让模型挑出相关段落"或"用检索取回相关片段"。
